1. 클러스터 안에 깃 서버를 세우고 Argo CD를 붙여, 커밋 하나가 8초 만에 배포되는 것을 시각으로 확인한다.

31.1지금 클러스터가 어느 커밋인지 모른다

M27에서 감사 로그로 "누가 무엇을 지웠나"를 답할 수 있게 됐다. 그런데 더 기본적인 질문에는 아직 답하지 못한다 — 지금 클러스터에 배포된 것이 저장소의 어느 상태인가.

이 교재를 여기까지 따라오면서 클러스터에 손을 댄 방법을 세어 보면 이렇다. kubectl apply -f, kubectl apply -k, helm install, helm upgrade, kubectl patch, kubectl scale, kubectl edit, 그리고 M27에서는 docker exec로 노드 안의 파일까지 고쳤다. 이 중 어느 것도 저장소에 기록을 남기지 않았다.

결과는 두 가지 문제로 나타난다. 하나는 재현 불가다 — 클러스터를 새로 만들어 같은 상태로 되돌리려면 지난 30개 모듈을 순서대로 다시 해야 한다. rebuild.sh가 M14 시점까지만 복구하는 것이 그 한계를 그대로 보여 준다. 다른 하나는 드리프트다 — 급해서 손으로 고친 것이 매니페스트에 반영되지 않은 채 남아 있고, 다음 배포가 그것을 조용히 덮는다.

GitOps는 이 문제를 방향을 뒤집어 푼다. 사람이 클러스터를 바꾸는 대신 저장소를 바꾸고, 클러스터 안의 컨트롤러가 저장소를 따라가게 한다. 그러면 "지금 어느 커밋인가"에 항상 답할 수 있고, 손으로 바꾼 것은 되돌아간다 — 이 두 번째 성질이 처음에는 불편하게 느껴진다. 그 불편함을 31.5에서 직접 겪는다.

31.2이론 — 풀 기반과 네 가지 원칙

책 매핑18.1~18.3 깃옵스 원칙·풀 기반과 푸시 기반·저장소 구조 전략 · 18.4 시크릿 관리 스펙트럼

네 가지 원칙

GitOps를 규정하는 네 문장이 있다. 선언적일 것(원하는 상태를 명령이 아니라 선언으로 적는다), 버전이 있고 불변일 것(그 선언이 커밋으로 남는다), 자동으로 당겨질 것(에이전트가 스스로 가져간다), 계속 조정될 것(차이가 생기면 없앤다).

앞의 둘은 이미 하고 있다. 매니페스트는 선언이고 저장소에 있다. 이 모듈이 더하는 것은 뒤의 둘 — 당기기와 조정이다.

풀이 푸시와 다른 점

M29에서 파이프라인을 이미지까지만 만들고 멈춘 이유를 여기서 설명한다. CI가 kubectl apply를 하려면 CI 러너가 클러스터 자격 증명을 갖고 있어야 한다. 그것은 M23의 관점에서 가장 큰 권한을 가장 넓게 노출된 곳에 두는 일이다 — CI 러너는 외부 네트워크에 있고, 서드파티 액션을 실행하고, 포크한 PR도 돌린다.

풀 방식에서는 클러스터 안의 컨트롤러가 저장소를 읽는다. 저장소에는 읽기 권한만 주면 되고, 클러스터로 들어오는 인바운드 구멍이 필요 없다. 클러스터를 열 개로 늘려도 각 클러스터가 알아서 당겨가므로 CI 설정은 그대로다 — M32의 글로벌 롤아웃이 이 성질에 기댄다.

대가도 있다. 배포가 언제 끝났는지 CI가 모른다. 파이프라인은 커밋에서 끝나고, 실제 반영은 나중에 클러스터에서 일어난다. 배포 완료를 기다려야 하는 워크플로(예: 배포 후 E2E 테스트)는 별도로 확인 단계를 붙여야 한다.

조정은 계속 돈다

조정reconciliation은 한 번 하고 끝나는 것이 아니라 주기적으로 도는 루프다. 저장소가 안 바뀌어도 컨트롤러는 계속 비교하고, 클러스터 쪽이 달라져 있으면 되돌린다. M08에서 배운 컨트롤 루프가 저장소까지 확장된 형태다.

여기서 나오는 두 옵션이 이 모듈의 실습 대상이다. selfHeal은 클러스터에서 바뀐 것을 되돌리고, prune은 저장소에서 사라진 것을 클러스터에서도 지운다. 둘 다 기본값이 꺼져 있는데, 켜지 않으면 "저장소가 정본"이라는 말이 절반만 참이 된다.

시크릿이라는 예외

모든 것을 저장소에 둔다는 원칙에는 비밀번호라는 예외가 생긴다. 시크릿을 평문으로 커밋하면 저장소를 읽을 수 있는 모두가 볼 수 있고, 한 번 커밋되면 이력에서 지우기 어렵다 — 나중에 파일을 지워도 과거 커밋에 남는다.

대응은 세 갈래다. 암호화해서 커밋(SOPS·Sealed Secrets), 참조만 커밋(External Secrets가 외부 비밀 관리 시스템에서 가져온다), 그리고 아예 다른 경로로 전달(설치 시 --set). 31.6에서 첫 번째를 실습하고, 나머지는 판단 기준만 정리한다.

31.3따라하기 ① 저장소와 컨트롤러

1단계 — 클러스터 안에 깃 서버를 세운다

목적실습을 자기 완결로 만든다. 깃허브를 쓰면 토큰과 네트워크가 실습의 변수가 된다.

# git daemon 은 별도 패키지다. alpine/git 이미지에는 없어서 직접 만든다.
cat > course/labs/apps/gitserver/Dockerfile <<'EOF'
FROM alpine:3.22
RUN apk add --no-cache git git-daemon && \
    adduser -D -u 1000 -h /repos git && \
    mkdir -p /repos && chown -R 1000:1000 /repos
USER 1000
EXPOSE 9418
ENTRYPOINT ["git", "daemon", "--verbose", "--export-all", "--base-path=/repos", \
            "--reuseaddr", "--enable=upload-pack", "--port=9418"]
EOF
docker build -t gitserver:1 course/labs/apps/gitserver
kind load docker-image gitserver:1 --name study
kubectl apply -f course/labs/k8s/gitops/00-gitserver.yaml

매니페스트에 들어간 환경 변수 셋이 눈에 띌 것이다. 31.7의 두 번째 실패에서 만든 것이다.

          env:
            - {name: GIT_CONFIG_COUNT,  value: "1"}
            - {name: GIT_CONFIG_KEY_0,  value: "safe.directory"}
            - {name: GIT_CONFIG_VALUE_0, value: "*"}

git daemon을 고른 이유가 있다. HTTP로 저장소를 내주려면 git-http-backend를 CGI로 돌려야 하는데, 그러려면 웹 서버 설정이 실습의 절반을 차지한다. git://는 인증이 없어서 운영에는 절대 쓰지 않지만 클러스터 내부 실습에는 충분하다.

2단계 — 저장소 내용을 만든다

목적배포할 것을 정한다. M28에서 만든 kustomize base를 그대로 쓴다.

mkdir -p /tmp/gitops/app-repo/apps/journal
cp course/labs/k8s/journal/{10-config,20-redis,30-journal-api,40-web-static,60-pdb,70-hpa}.yaml \
   course/labs/k8s/journal/index.html /tmp/gitops/app-repo/apps/journal/

cat > /tmp/gitops/app-repo/apps/journal/kustomization.yaml <<'EOF'
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
namespace: gitops-journal
resources:
  - 10-config.yaml
  - 20-redis.yaml
  - 30-journal-api.yaml
  - 40-web-static.yaml
  - 60-pdb.yaml
  - 70-hpa.yaml
configMapGenerator:
  - name: web-content
    files: [index.html]
images:
  - name: journal-api
    newTag: v1
EOF

cd /tmp/gitops/app-repo && git init -q -b main && git add -A
git commit -qm "저널 앱 초기 상태"

00-namespace.yaml과 50-ingress.yaml을 뺐다. 네임스페이스는 PSA 라벨을 붙여서 우리가 만들고, 인그레스는 journal.local 호스트가 기존 배포와 겹치기 때문이다. 무엇을 GitOps에 넣고 무엇을 뺄지가 실제로는 이런 구체적인 이유로 정해진다.

3단계 — Argo CD를 설치한다

목적조정 루프를 클러스터 안에 넣는다.

kubectl create ns argocd
kubectl apply -n argocd --server-side \
  -f https://raw.githubusercontent.com/argoproj/argo-cd/v3.5.2/manifests/install.yaml
kubectl -n argocd get deploy,sts --no-headers
출력

판정--server-side가 여기서도 필요하다. M30에서 본 것과 같은 이유(CRD 주석 크기)이고, 큰 프로젝트를 설치할 때의 기본값이라고 생각하는 편이 낫다.

설치가 네임스페이스에 NetworkPolicy 7개를 함께 넣는다. M25에서 손으로 만든 것을 이 프로젝트는 기본으로 배포한다 — 구성요소마다 필요한 통신만 열어 둔 형태이고, 좋은 예제이므로 kubectl -n argocd get netpol -o yaml로 한 번 읽어 볼 값이 있다.

4단계 — 애플리케이션을 선언한다

목적"저장소의 이 경로가 클러스터의 이 네임스페이스"를 오브젝트로 적는다.

kubectl create ns gitops-journal
kubectl label ns gitops-journal \
  pod-security.kubernetes.io/enforce=restricted \
  pod-security.kubernetes.io/enforce-version=latest

cat > course/labs/k8s/gitops/10-application.yaml <<'EOF'
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: journal
  namespace: argocd
spec:
  project: default
  source:
    repoURL: git://gitserver.gitops.svc/repo.git
    targetRevision: main
    path: apps/journal
  destination:
    server: https://kubernetes.default.svc
    namespace: gitops-journal
  syncPolicy:
    automated:
      prune: true       # 저장소에서 사라진 리소스를 클러스터에서도 지운다
      selfHeal: true    # 클러스터에서 손으로 바꾼 것을 되돌린다
    syncOptions:
      - CreateNamespace=false
EOF
kubectl apply -f course/labs/k8s/gitops/10-application.yaml
kubectl -n argocd get application journal \
  -o jsonpath='{.status.sync.status}{" / "}{.status.health.status}{"\n"}'
kubectl -n gitops-journal get po,deploy,sts,hpa,pdb --no-headers

판정아무도 kubectl apply를 치지 않았는데 워크로드 전체가 떴다. Application 하나가 커밋과 네임스페이스를 잇는 유일한 선언이고, 그 뒤로는 사람이 개입하지 않는다. restricted 네임스페이스에서 뜬 것도 확인해 둔다 — M24의 기준을 GitOps 경로로도 통과한다.

중간에 Health가 Degraded로 보일 수 있다. 파드가 뜨는 중에는 정상이며, 몇십 초 뒤 Healthy가 된다. Sync와 Health는 다른 축이다 — 저장소와 같은가(Sync)와 워크로드가 건강한가(Health)를 각각 본다.

31.4따라하기 ② 커밋이 배포다

1단계 — 저장소를 고치고 커밋한다

목적배포 절차가 커밋 하나가 되는 것을 확인한다.

cd /tmp/gitops/app-repo
sed -i '' 's/LOG_LEVEL: "info"/LOG_LEVEL: "warn"/' apps/journal/10-config.yaml
sed -i '' 's/    newTag: v1/    newTag: v2/' apps/journal/kustomization.yaml
git add -A && git commit -qm "운영 준비: 로그 수준 warn, 이미지 v2"

실제 GitOps라면 여기서 git push로 끝난다. 이 실습의 깃 서버는 읽기 전용이라 베어 저장소를 다시 만들어 복사하는 스크립트를 쓴다 — 절차의 본질(커밋이 배포다)은 같다.

bash course/labs/scripts/gitops-push.sh /tmp/gitops/app-repo

스크립트 마지막 줄이 argocd.argoproj.io/refresh: hard 주석을 붙인다. Argo CD는 기본으로 3분마다 저장소를 확인하는데, 실습에서 3분을 기다리지 않으려는 것이다. 운영에서는 저장소의 웹훅으로 이 확인을 즉시 트리거한다.

2단계 — 반영되는 것을 시각으로 본다

목적"얼마나 걸리는가"를 감이 아니라 시각으로 남긴다.

for i in $(seq 1 10); do
  L=$(kubectl -n gitops-journal get cm journal-config -o jsonpath='{.data.LOG_LEVEL}')
  I=$(kubectl -n gitops-journal get deploy journal-api -o jsonpath='{.spec.template.spec.containers[0].image}')
  echo "  $(date +%H:%M:%S)  LOG_LEVEL=$L  image=$I"
  [ "$L" = "warn" ] && break
  sleep 8
done
출력
01:06:29 LOG_LEVEL=info image=journal-api:v1 01:06:37 LOG_LEVEL=warn image=journal-api:v2
판정8초 만에 컨피그맵과 이미지가 함께 바뀌었다. 둘이 같은 커밋에 있었기 때문에 같이 반영된다 — 코드 변경과 설정 변경의 순서를 사람이 맞출 필요가 없다는 것이 M29 8절에서 말한 "한 저장소"의 실질적인 값이다.

3단계 — 저장소에서 지우면 클러스터에서도 지워진다

목적prune: true가 무엇을 하는지 확인한다. 이 옵션이 없으면 저장소가 절반만 정본이다.

cd /tmp/gitops/app-repo
# kustomization.yaml 의 resources 에서 60-pdb.yaml 을 빼고 파일도 지운다
rm apps/journal/60-pdb.yaml
git add -A && git commit -qm "PDB 제거 — 파드가 2개뿐이라 드레인을 막는다"
bash course/labs/scripts/gitops-push.sh /tmp/gitops/app-repo
출력
01:07:19 PDB 수=1 01:07:27 PDB 수=0
판정커밋에서 지운 것이 8초 뒤 클러스터에서도 사라졌다. prune: false였다면 PDB는 영원히 남는다 — 저장소에는 없고 클러스터에는 있는 리소스가 쌓이고, 시간이 지나면 그것이 왜 있는지 아무도 모르게 된다.

prune을 켜는 것이 무서운 이유도 분명하다. 실수로 파일을 지운 커밋이 곧바로 클러스터의 삭제가 된다. 그래서 실무에서는 prune을 켜되 중요 리소스에 Prune=false 주석을 붙이거나(예: PVC), prune 결과를 사람이 승인하게 한다.

31.5따라하기 ③ 드리프트를 만들어 본다

이 절이 이 모듈의 핵심이다. 지금까지 30개 모듈 동안 해 온 방식이 더 이상 통하지 않는다는 것을 몸으로 확인한다.

1단계 — 레플리카를 손으로 바꾼다

목적가장 흔한 긴급 대응 — "일단 늘려 놓자" — 가 어떻게 되는지 본다.

date +%H:%M:%S
kubectl -n gitops-journal scale deploy web-static --replicas=5
for i in $(seq 1 12); do
  R=$(kubectl -n gitops-journal get deploy web-static -o jsonpath='{.spec.replicas}')
  echo "  $(date +%H:%M:%S)  replicas=$R"
  [ "$R" = "2" ] && break
  sleep 5
done
출력
01:04:20 deployment.apps/web-static scaled 01:04:20 replicas=5 01:04:25 replicas=2
판정5초. 명령은 성공했고 아무 오류도 없었는데 5초 뒤 원래대로 돌아갔다. 이것이 GitOps를 도입한 팀에서 가장 먼저 나오는 불만이고, 동시에 도입한 이유다 — 저장소에 없는 변경은 남지 않는다.

2단계 — 리소스를 지워 본다

목적삭제도 되돌아오는지 확인한다. 클러스터가 저장소보다 적을 때의 동작이다.

kubectl -n gitops-journal delete svc web-static
for i in $(seq 1 12); do
  if kubectl -n gitops-journal get svc web-static >/dev/null 2>&1; then
    echo "  $(date +%H:%M:%S)  서비스 되살아남"; break
  fi
  echo "  $(date +%H:%M:%S)  아직 없음"; sleep 5
done
출력
service "web-static" deleted from gitops-journal namespace 01:04:32 아직 없음 01:04:37 서비스 되살아남
판정6초 만에 되살아났다. ClusterIP는 새로 할당된다는 점에 주의한다 — 같은 이름의 다른 서비스가 만들어진 것이고, 그 사이 그 IP를 캐시하고 있던 클라이언트는 잠깐 실패한다. "되돌아온다"가 "아무 일도 없었다"는 뜻은 아니다.

3단계 — 설정값을 바꿔 본다

목적복구 시점이 즉시가 아니라는 것을 확인한다. 조정 루프에는 주기가 있다.

kubectl -n gitops-journal patch cm journal-config -p '{"data":{"LOG_LEVEL":"debug"}}'
sleep 12; kubectl -n gitops-journal get cm journal-config -o jsonpath='{.data.LOG_LEVEL}{"\n"}'
sleep 20; kubectl -n gitops-journal get cm journal-config -o jsonpath='{.data.LOG_LEVEL}{"\n"}'
출력
debug info
판정12초 뒤에는 아직 debug였고 32초 뒤에 info로 돌아왔다. selfHeal은 즉시가 아니다. 그 사이에 파드가 재시작하면 바뀐 값을 읽어 갈 수도 있다 — 손으로 바꾼 것이 짧게 유효했다가 사라지는 이 상태가 디버깅을 어렵게 만든다.

그래서 GitOps 클러스터에서 디버깅용 임시 변경은 하지 않는다. 정말 필요하면 애플리케이션의 자동 동기화를 잠깐 끄고(syncPolicy에서 automated 제거), 끝나면 다시 켠다. 끄는 것도 기록에 남는 행위여야 한다.

31.6따라하기 ④ 시크릿을 커밋 가능하게

지금 저장소의 20-redis.yaml에는 비밀번호가 평문으로 들어 있다. 실습이니 그렇게 두었지만, 저장소가 정본이 된 이상 이 문제를 정면으로 봐야 한다.

1단계 — 키를 만든다

목적암호화의 대상이 되는 키를 만든다. 이 키는 저장소에 들어가지 않는다.

brew install sops age      # 없으면
age-keygen -o age.key
출력
Public key: age1d7gyfuu6e9de0h6dz949x0h840ka49ctu9napu04p567yzspu3rqdrrmhp

age는 GPG를 대신하는 단순한 파일 암호화 도구다. 키가 한 줄짜리 문자열이라 다루기 쉽고, 공개 키로 암호화하고 개인 키로 푼다. age.key 파일에 둘 다 들어 있으므로 이 파일은 절대 커밋하지 않는다 — .gitignore에 먼저 넣는다.

2단계 — 값만 암호화한다

목적파일 전체를 암호화하지 않는다. diff가 읽히는 형태로 만드는 것이 요점이다.

sops --encrypt --age "$PUB" \
  --encrypted-regex '^(data|stringData)$' \
  secret.yaml > secret.enc.yaml
출력 (secret.enc.yaml)
apiVersion: v1 kind: Secret metadata: name: journal-secret namespace: gitops-journal type: Opaque stringData: REDIS_PASSWORD: ENC[AES256_GCM,data:MTzKK6B81UQRa9s=,iv:kzLZ1GPMhUGjxVYFmmV+x6BGo/m8+4N/gG3EnwNx1Go=,tag:YfbNaJ70duLK5hKnR4H/cA==,type:str] sops: age: - recipient: age1d7gyfuu6e9de0h6dz949x0h840ka49ctu9napu04p567yzspu3rqdrrmhp encrypted_regex: ^(data|stringData)$
판정--encrypted-regex가 핵심이다. 이름·네임스페이스·타입은 평문으로 남아서 리뷰어가 "어느 시크릿을 바꿨는지" 볼 수 있고, 값만 암호문이다. 파일 전체를 암호화하면 모든 변경이 알아볼 수 없는 diff가 되어 리뷰가 불가능해진다.

3단계 — 안전한지 확인한다

목적"암호화했다"를 믿지 않고 확인한다.

grep -c 's3cr3t-pass' secret.enc.yaml
export SOPS_AGE_KEY_FILE=$PWD/age.key
sops --decrypt secret.enc.yaml | grep REDIS_PASSWORD
SOPS_AGE_KEY_FILE=/dev/null sops --decrypt secret.enc.yaml
출력
0 REDIS_PASSWORD: s3cr3t-pass order for SOPS to recover the file, at least one key has to be successful, but none were.
판정세 줄이 각각 다른 것을 확인한다. 평문이 파일에 없고, 키가 있으면 원래 값이 복원되고, 키가 없으면 읽히지 않는다. 이 세 가지를 확인하지 않고 커밋하는 것은 위험하다 — --encrypted-regex를 잘못 쓰면 아무것도 암호화되지 않은 채 "sops" 섹션만 붙은 파일이 나온다.

Argo CD는 SOPS를 기본으로 풀지 못한다. 복호화하려면 ksops 같은 플러그인을 repo-server에 넣거나, argocd-vault-plugin을 쓰거나, 아예 다른 접근(External Secrets Operator가 외부 비밀 저장소에서 가져오기)을 쓴다. 즉 암호화는 저장소 문제를 풀지만 클러스터 쪽 복호화 경로는 별도로 만들어야 한다.

이 교재는 여기까지만 한다. 복호화 플러그인 설치는 도구마다 절차가 다르고, 어느 것을 고르든 키를 클러스터 어딘가에 두어야 하는 문제는 남는다. 그 키를 어떻게 보호할 것인지가 진짜 질문이고, 답은 대개 클라우드의 KMS로 옮기는 것이다.

31.7일부러 실패시키기

실패 ① — 정적 파일로 내준 저장소는 읽지 못한다

목적깃 서버를 처음 세울 때 가장 먼저 시도하는 방법이 왜 안 되는지 본다.

nginx로 .git 디렉터리를 그대로 내주고 git update-server-info를 돌리면 이른바 dumb HTTP 저장소가 된다. HTTP 응답은 정상이다.

curl -s -o /dev/null -w '%{http_code}\n' http://gitserver.gitops.svc/repo.git/info/refs
출력
200

그런데 Argo CD는 읽지 못한다.

출력 (Application의 status.conditions)
Failed to load target state: failed to generate manifest for source 1 of 1: rpc error: code = Unknown desc = failed to list refs: unexpected EOF
판정메시지가 원인을 가리키지 않는다 — unexpected EOF는 "파일이 없다"가 아니라 기대한 프로토콜 응답이 아니다라는 뜻이다. Argo CD의 깃 클라이언트는 smart 프로토콜(git-upload-pack과 대화하는 방식)만 말하고, 정적 파일 나열은 프로토콜이 아니다.

이 오류를 만났을 때 확인할 것은 하나다 — 같은 URL로 git ls-remote가 되는가. 되지 않으면 저장소 서버 쪽 문제이고, 되는데 Argo CD만 안 되면 인증이나 네트워크 문제다.

kubectl -n argocd exec deploy/argocd-repo-server -c argocd-repo-server -- \
  git ls-remote git://gitserver.gitops.svc/repo.git

실패 ② — 소유자가 다르면 git이 저장소를 거부한다

목적컨테이너와 볼륨을 함께 쓸 때 반복해서 만나는 문제를 깃에서 확인한다.

kubectl -n gitops logs deploy/gitserver --tail=8
출력
[37] Request upload-pack for '/repo.git' fatal: detected dubious ownership in repository at '/repos/repo.git' To add an exception for this directory, call: git config --global --add safe.directory /repos/repo.git [11] [37] Disconnected (with error)
kubectl -n gitops exec deploy/gitserver -- ls -ld /repos /repos/repo.git
kubectl -n gitops exec deploy/gitserver -- id
출력
drwxrwxrwx 3 root root 4096 /repos drwxr-xr-x 6 101 101 4096 /repos/repo.git uid=1000(git) gid=1000(git) groups=1000(git)
판정저장소 디렉터리의 소유자가 101인데 프로세스는 1000이다. 이전에 이 PVC를 쓴 파드(nginx-unprivileged, uid 101)가 남긴 소유권이다. git은 다른 사용자 소유의 저장소를 신뢰하지 않는다 — 훅 스크립트를 통한 공격을 막기 위한 2022년 이후의 기본 동작이고, 컨테이너 환경에서는 이 보호가 자주 오작동처럼 느껴진다.

두 가지 해법이 있다. 소유권을 맞추는 것이 정석이고(fsGroup과 chown), 실습에서는 예외를 여는 쪽을 택했다.

          env:
            - {name: GIT_CONFIG_COUNT,  value: "1"}
            - {name: GIT_CONFIG_KEY_0,  value: "safe.directory"}
            - {name: GIT_CONFIG_VALUE_0, value: "*"}

GIT_CONFIG_COUNT·GIT_CONFIG_KEY_n·GIT_CONFIG_VALUE_n은 설정 파일 없이 환경 변수로 git 설정을 주입하는 방법이다. 읽기 전용 파일시스템으로 도는 컨테이너에서 유용하다.

실패 ③ — 긴급 수정이 사라진다

목적31.5의 측정을 장애 상황의 이야기로 다시 읽는다. 이것이 GitOps 도입 후 가장 자주 겪는 사고다.

새벽에 트래픽이 몰려 web-static을 5개로 늘렸다고 하자. 명령은 성공했고 파드도 떴다.

출력
01:04:20 replicas=5 01:04:25 replicas=2
판정5초 뒤 원래대로다. 대응한 사람은 대개 이것을 즉시 알아채지 못한다 — 명령이 성공했고 오류가 없었기 때문이다. 몇 분 뒤 "왜 아직 느리지"로 돌아오고, 그때 kubectl get을 다시 쳐 보고서야 안다.

올바른 절차는 셋 중 하나다. 커밋한다(가장 옳지만 새벽에 리뷰를 받아야 한다). 자동 동기화를 끈다(kubectl -n argocd patch app journal --type=json -p '[{"op":"remove","path":"/spec/syncPolicy/automated"}]') — 끄고 나면 다시 켜는 것을 잊지 않도록 어딘가에 기록한다. 아니면 애초에 사람이 손댈 값을 저장소 밖에 둔다(HPA에 맡기는 것이 그 예다 — journal-api의 레플리카는 M17 이후 저장소에 없다).

세 번째가 설계로 푸는 방법이다. 자주 손대야 하는 값이 있다면 그것은 매니페스트가 아니라 컨트롤러가 정해야 한다는 신호다.

31.8운영 관점 — 저장소 구조와 긴급 상황

저장소를 어떻게 나눌 것인가

세 가지 배치가 흔하고, 선택 기준은 누가 무엇을 승인하는가다.

앱과 매니페스트를 한 저장소에(이 교재의 배치) 두면 코드와 설정이 한 커밋에 들어간다. 팀이 자기 서비스를 온전히 소유할 때 가장 단순하다. 단점은 배포 권한과 코드 권한이 같아진다는 것 — 코드를 고칠 수 있는 사람이 곧 배포할 수 있는 사람이다.

매니페스트만 별도 저장소에 두면 그 저장소의 승인 규칙으로 배포를 통제할 수 있다. CI는 이미지를 만들고 매니페스트 저장소에 태그를 커밋한다. 규제가 있는 환경에서 흔하고, 대가는 변경 하나가 두 개의 PR이 되는 것이다.

환경마다 별도 저장소나 브랜치는 겉보기에 깔끔하지만 권하지 않는 경우가 많다. 브랜치로 환경을 나누면 dev의 변경을 prod로 옮길 때 병합이 필요하고, 그 병합에 환경별 차이가 섞여 충돌이 반복된다. M28의 오버레이처럼 같은 브랜치에서 디렉터리로 나누는 편이 낫다.

동기화 주기와 웹훅

Argo CD의 기본 폴링 주기는 3분이다. 배포가 3분씩 걸린다는 뜻이라 대개 웹훅을 붙인다 — 저장소가 푸시를 알리면 즉시 확인한다. 다만 웹훅은 최적화이지 정확성의 근거가 아니다. 웹훅이 실패해도 폴링이 결국 따라잡으므로, 웹훅 장애가 배포 누락으로 이어지지 않는다. 이것이 풀 기반의 성질이다.

반대로 selfHeal의 주기는 배포 주기가 아니다. 31.5에서 5초·6초·32초로 제각각이었던 이유는 이벤트로 감지한 것과 주기적 비교로 감지한 것이 섞였기 때문이다. 드리프트 복구 시간을 SLO로 약속하면 안 된다.

이 교재의 배치

journal 네임스페이스의 원래 배포는 GitOps로 옮기지 않는다. 이 모듈의 실습은 gitops-journal에서 따로 했다. 이유는 실용적이다 — 남은 모듈에서 kubectl로 직접 실험할 일이 계속 있고(M36의 카오스 주입이 특히 그렇다), selfHeal이 그것을 계속 되돌리면 실습이 성립하지 않는다.

이것은 교재의 사정이지 권고가 아니다. 실제 운영 클러스터에서 "손으로 실험할 일이 많아서 GitOps를 안 쓴다"는 이유는 성립하지 않는다 — 그 실험이 많다는 것 자체가 문제의 신호다.

GitOps가 답이 아닌 것

GitOps는 선언할 수 있는 것에만 적용된다. M27에서 고친 컨트롤 플레인 매니페스트, 노드의 커널 파라미터, 클라우드 리소스는 이 루프 밖에 있다. 그것들을 같은 방식으로 다루려면 별도의 도구(클러스터 API, 테라폼과 그 오퍼레이터)가 필요하고, 도구가 늘어나면 "어느 도구가 이 리소스의 주인인가"라는 문제가 새로 생긴다.

M32에서 클러스터를 여럿으로 늘릴 때 이 질문이 다시 나온다. 그때는 클러스터 자체를 선언으로 만드는 방향을 본다.

31.9체크포인트와 정리

다음 모듈로 넘어가기 전 확인
  • kubectl -n gitops get po -l app=gitserver --no-headers | grep -c Running → 1
  • kubectl -n argocd exec deploy/argocd-repo-server -c argocd-repo-server -- git ls-remote git://gitserver.gitops.svc/repo.git | wc -l → 2 (HEAD와 refs/heads/main)
  • kubectl -n argocd get application journal -o jsonpath='{.status.sync.status}' → Synced
  • kubectl -n argocd get application journal -o jsonpath='{.status.health.status}' → Healthy
  • kubectl -n argocd get application journal -o jsonpath='{.spec.syncPolicy.automated.selfHeal}' → true
  • kubectl -n gitops-journal get cm journal-config -o jsonpath='{.data.LOG_LEVEL}' → warn (커밋으로 바꾼 값)

# 애플리케이션을 먼저 지운다 (prune 이 켜져 있으므로 리소스가 함께 정리된다)

kubectl delete ns gitops-journal gitops --ignore-not-found

# Argo CD 는 남긴다. 남아 있는지 확인
kubectl -n argocd get deploy --no-headers | wc -l

Argo CD 컨트롤러는 지우지 않는다. M32에서 여러 클러스터에 같은 애플리케이션을 배포할 때 다시 쓰고, M38 캡스톤의 배포 경로가 이것이다.

age.key는 저장소에 커밋하지 않았는지 마지막으로 확인한다. git log --all --full-history -- '*age.key'가 비어 있어야 한다 — 한 번 들어가면 이력에서 지우는 것이 매우 번거롭다.

다음 모듈

지금까지 클러스터는 하나였다. 저장소 하나가 클러스터 하나를 정의했고, 배포는 그 안에서 끝났다. 실제 서비스는 지역마다 클러스터가 따로 있고, 같은 변경을 여러 클러스터에 순서대로 내보내면서 중간에 멈출 수 있어야 한다.

M32에서 그 순서를 만든다. 한 클러스터에서 확인하고 다음으로 넘어가는 절차, 지역별 차이를 오버레이로 다루는 방법, 그리고 사고가 났을 때 되돌리는 순서를 다룬다. 이 모듈에서 만든 Application이 ApplicationSet으로 확장되는 지점이다.
