핵심 3줄

1. 흩어진 kubectl create의 결과를 한 디렉터리의 매니페스트로 다시 쓰면, 지우고 다시 만드는 일이 명령 한 줄이 된다.

14.1흩어진 것을 한 덩어리로

지금 default 네임스페이스를 열어 보면 M10의 디플로이먼트, M11의 서비스 셋, M12의 명령 한 줄로 만든 정적 서버와 인그레스와 Gateway가 순서 없이 쌓여 있다. M13은 자기가 만든 것을 지웠지만, 지웠다는 사실도 남아 있지 않다. 어느 것이 어느 모듈에서 왔는지 클러스터는 기억하지 않는다.

문제는 재현이다. 지금 이 클러스터를 지우면 같은 상태를 다시 만들 방법이 없다. 명령을 어떤 순서로 쳤는지가 어디에도 남아 있지 않기 때문이다. 책 1.2가 "선언형이 진실 공급원"이라고 말하는 이유가 여기서 실감난다 — 명령형은 일을 시키고 결과를 남기지 않고, 선언형은 원하는 상태를 파일로 남긴다.

그래서 이 모듈은 새 기능을 거의 배우지 않는다. M08~M13에서 만든 것을 파일로 다시 쓰고, 그 파일들이 서로 어떻게 맞물리는지 확인한다. 새로 나오는 것은 저장소를 위한 스테이트풀셋 하나다. 여기서 확정하는 매니페스트와 차트를 Part 3부터 Part 8까지 전부 실습 대상으로 재사용한다. 프로브(M15)도, HPA(M17)도, PromQL 쿼리(M20)도, 카오스 실험(M36)도 이 앱을 건드린다.

14.2무엇이 무엇에 의존하는가

책 1.7~1.11이 배포하는 저널 애플리케이션은 세 덩어리다. 진입점(인그레스), 무상태 워크로드 둘(정적 파일 서버·API), 상태를 가진 저장소 하나(레디스). 이 모듈에서 만들 것도 같은 모양이다.

의존 방향이 한쪽이라는 점이 중요하다. API는 레디스를 알아야 하지만 레디스는 API를 모른다. 정적 파일 서버는 아무것도 모른다. 그래서 배포 순서를 강제할 필요가 없다 — API가 레디스보다 먼저 떠도 /readyz가 503을 돌려주며 기다리고(M04에서 본 server.ts의 설계 — REDIS_URL이 있는데 연결이 안 열려 있으면 503), 레디스가 준비되면 저절로 트래픽을 받는다.

파일을 어떻게 나누는가

책 1.11은 "서비스마다 디렉터리를 나누라"고 말한다. 서비스가 열 개를 넘어가면 맞는 조언이지만, 세 개짜리 앱에서 디렉터리를 셋으로 나누면 파일을 여닫는 품이 더 든다. 이 과정은 한 디렉터리 · 번호 접두사로 간다.

왜 default가 아니라 새 네임스페이스인가

네임스페이스 하나가 곧 삭제 단위다. kubectl delete ns journal 한 줄이면 이 앱이 만든 모든 것이 사라진다. default에 쌓아 두면 무엇을 지워야 할지 매번 목록을 만들어야 한다. 책 2.3.2가 개발자마다 네임스페이스를 주라고 말하는 것도 같은 이유다 — 격리보다 정리가 쉬워지는 것이 실무에서 더 자주 도움이 된다.

대신 대가가 있다. M13에서 default에 만들었던 journal-config와 journal-secret은 — 지우지 않고 남겨 두었더라도 — 여기서 쓸 수 없다. 컨피그맵과 시크릿은 네임스페이스를 넘지 못한다. 그래서 10-config.yaml에 같은 것을 다시 정의한다. M13 실패 ①에서 봤던 세 가지 원인 중 세 번째가 바로 이것이었다.

네임스페이스를 파일 안에 적지 않았다. 각 파일의 metadata.namespace는 비워 두고 kustomization.yaml이 한 번에 채운다. 같은 파일을 다른 네임스페이스에 복제하기 쉬워진다. 비밀번호에 @ · : · /가 없는 것은 3단계에서 이 값이 URL 안에 들어가기 때문이다 — URL 구분 문자가 섞이면 클라이언트마다 다르게 파싱한다.

2단계. 레디스를 스테이트풀셋으로 쓴다

목적저장소는 디플로이먼트로 배포하면 안 되는 이유를 파일 형태로 확인한다.

스테이트풀셋 (StatefulSet)은 디플로이먼트와 같이 파드 집합을 관리하지만, 파드마다 고정된 이름(서수)과 전용 PVC (PersistentVolumeClaim) — "이만한 저장 공간을 달라"는 요청 오브젝트 — 를 붙여 주고, 생성·삭제를 순서대로 한다. 레디스처럼 재시작 뒤에도 같은 데이터를 물고 와야 하는 워크로드를 위한 컨트롤러다.

# course/labs/k8s/journal/20-redis.yaml
# 레디스 — 상태를 가진 워크로드. 디플로이먼트가 아니라 스테이트풀셋을 쓴다.
# 차이 세 가지: 파드 이름이 고정(redis-0), 파드마다 자기 PVC, 순서대로 생성·삭제.
apiVersion: v1
kind: Service
metadata:
  name: redis                      # 스테이트풀셋의 serviceName 과 같아야 한다
  labels:
    app: redis
spec:
  clusterIP: None                  # 헤드리스 — redis-0.redis 라는 고정 DNS 이름을 만든다
  selector:
    app: redis
  ports:
    - name: redis
      port: 6379
      targetPort: 6379
---
apiVersion: v1
kind: Service
metadata:
  name: redis-read                 # 책 1장의 읽기 전용 서비스 자리
  labels:
    app: redis
spec:
  type: ClusterIP
  selector:
    app: redis                     # 복제본이 1개인 지금은 redis 와 같은 파드를 가리킨다
  ports:
    - name: redis
      port: 6379
      targetPort: 6379
---
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: redis
spec:
  serviceName: redis               # 헤드리스 서비스 이름. 파드 DNS 는 <파드>.<이 이름> 이 된다
  replicas: 1
  selector:
    matchLabels:
      app: redis
  template:
    metadata:
      labels:
        app: redis
    spec:
      containers:
        - name: redis
          image: redis:8.2-alpine
          imagePullPolicy: IfNotPresent
          # $(VAR) 는 쿠버네티스가 같은 컨테이너의 env 에서 치환한다. 셸이 하는 일이 아니다.
          args: ["--requirepass", "$(REDIS_PASSWORD)", "--appendonly", "yes"]
          env:
            - name: REDIS_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: journal-secret
                  key: REDIS_PASSWORD
          ports:
            - name: redis
              containerPort: 6379
          readinessProbe:
            exec:
              command: ["sh", "-c", "redis-cli -a \"$REDIS_PASSWORD\" ping | grep -q PONG"]
            initialDelaySeconds: 3
            periodSeconds: 5
          volumeMounts:
            - name: data
              mountPath: /data     # appendonly 파일이 여기 쌓인다
  # 디플로이먼트에는 없는 필드. 파드마다 PVC 를 하나씩 만들어 붙인다.
  volumeClaimTemplates:
    - metadata:
        name: data
      spec:
        accessModes: ["ReadWriteOnce"]
        # storageClassName 을 생략하면 클러스터의 기본 스토리지클래스를 쓴다.
        # kind 는 local-path-provisioner 의 standard 가 기본이다: kubectl get sc
        resources:
          requests:
            storage: 1Gi
필드디플로이먼트에는왜 스테이트풀셋에 필요한가
serviceName없다파드마다 redis-0.redis 같은 고정 DNS 이름을 만든다. IP가 바뀌어도 이름은 그대로다
volumeClaimTemplates없다파드가 만들어질 때 그 파드 전용 PVC를 만든다. 파드를 지워도 PVC는 남고, 다시 만들어진 파드가 같은 PVC를 물고 온다
파드 이름임의 접미사 (-cbdf4d977-cp2xz)서수 (redis-0, redis-1). 생성은 0→1→2, 삭제는 그 반대 순서
레디스 이미지 태그와 라이선스 redis:8.2-alpine으로 고정한다(2026-09-05 확인). Redis는 8.0부터 AGPLv3를 선택지로 되돌렸지만 여전히 BSD가 아니다. 이 이유로 리눅스 재단이 포크한 Valkey를 쓰는 조직이 늘고 있고, 프로토콜과 명령이 호환되므로 이 실습의 이미지 이름만 바꿔도 그대로 돌아간다. 책은 Redis를 쓰므로 이 과정도 Redis로 간다. 실습 당일 태그가 살아 있는지 확인하라. https://hub.docker.com/_/redis · https://valkey.io/

3단계. API와 정적 서버, 진입점을 쓴다

목적M10의 디플로이먼트에 레디스 연결과 설정 주입을 더하고, M12의 정적 서버와 인그레스를 파일로 옮긴다.

# course/labs/k8s/journal/30-journal-api.yaml
# 저널 API — M10 의 디플로이먼트에 레디스 연결과 설정 주입을 더했다.
apiVersion: apps/v1
kind: Deployment
metadata:
  name: journal-api
  labels:
    app: journal-api
spec:
  replicas: 3
  selector:
    matchLabels:
      app: journal-api
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0
  template:
    metadata:
      labels:
        app: journal-api
    spec:
      containers:
        - name: api
          image: journal-api:v1
          imagePullPolicy: IfNotPresent      # kind load 로 넣은 로컬 이미지라 당겨오지 않는다
          ports:
            - name: http
              containerPort: 8080
          env:
            - name: APP_VERSION
              value: "v1"
            - name: LOG_LEVEL
              valueFrom:
                configMapKeyRef:
                  name: journal-config
                  key: LOG_LEVEL
            - name: REDIS_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: journal-secret
                  key: REDIS_PASSWORD
            # redis-0.redis 는 스테이트풀셋이 보장하는 고정 이름이다.
            # 파드가 다시 만들어져 IP 가 바뀌어도 이 이름은 그대로다.
            - name: REDIS_URL
              value: "redis://default:$(REDIS_PASSWORD)@redis-0.redis:6379"
          readinessProbe:
            httpGet:
              path: /readyz                  # 레디스에 못 붙으면 503 을 돌려준다
              port: http
            periodSeconds: 2
          livenessProbe:
            httpGet:
              path: /healthz
              port: http
            periodSeconds: 10
            failureThreshold: 3
---
apiVersion: v1
kind: Service
metadata:
  name: journal-api
spec:
  type: ClusterIP
  selector:
    app: journal-api
  ports:
    - name: http
      port: 8080
      targetPort: http

M10 파일과 달라진 곳은 셋이다. 복제본이 4에서 3으로(노트북 자원), 포트에 http라는 이름이 붙어 서비스와 프로브가 번호 대신 이름으로 가리키고, env에 컨피그맵·시크릿 주입과 REDIS_URL이 들어왔다. livenessProbe도 새로 붙었다 — 값이 왜 그 숫자인지는 M15가 다룬다.

REDIS_URL 안의 $(REDIS_PASSWORD)가 핵심이다. 시크릿 값을 URL 문자열 안에 조립해야 하는데, 시크릿을 매니페스트에 평문으로 적을 수는 없다. 쿠버네티스는 같은 컨테이너의 다른 env 항목을 $(이름) 문법으로 치환해 준다. 셸이 하는 일이 아니므로 sh -c로 감쌀 필요가 없다. 단, 치환되는 항목이 먼저 정의돼 있어야 한다 — 그래서 REDIS_PASSWORD가 REDIS_URL 위에 있다.

      labels:
        app: web-static

              readOnly: true

그 경로는 파드가 스케줄된 워커 노드 컨테이너 안의 디렉터리다. 다시 말해 도커 컨테이너 하나가 죽으면 이 데이터는 사라진다. kind 클러스터를 지우면 당연히 함께 사라진다. 실습 환경의 한계를 정확히 알고 쓰는 것이 중요하다.

목적스테이트풀셋이 주는 것이 이름뿐인지, 데이터까지인지 판정한다.

kubectl exec -n journal redis-0 -- sh -c 'redis-cli -a "$REDIS_PASSWORD" --no-auth-warning dbsize'

kubectl delete pod redis-0 -n journal
kubectl wait --for=condition=Ready pod/redis-0 -n journal --timeout=120s

kubectl get pod redis-0 -n journal -o wide
kubectl exec -n journal redis-0 -- sh -c 'redis-cli -a "$REDIS_PASSWORD" --no-auth-warning dbsize'
curl -s -H "Host: journal.local" http://localhost:18080/api/entries
  • --no-auth-warning — -a로 비밀번호를 주면 redis-cli가 표준 오류로 경고를 뱉는다. 판정에 방해되므로 끈다
  • kubectl wait — 준비될 때까지 블로킹한다. sleep으로 어림잡는 것보다 정확하고 스크립트에 쓰기 좋다
실행 결과 — 삭제 전 1, 삭제 후에도 1. IP 와 노드는 환경마다 다르다
1 pod "redis-0" deleted from journal namespace pod/redis-0 condition met NAME READY STATUS RESTARTS AGE IP NODE NOMINATED NODE READINESS GATES redis-0 1/1 Running 0 5s 10.244.2.62 study-worker2 <none> <none> 1 {"entries":["{\"text\":\"첫 엔트리\"}"]}
판정파드 이름은 그대로 redis-0, AGE 5s로 새 파드인데, dbsize는 그대로 1이고 8단계에서 쓴 엔트리가 그대로 읽힌다. PVC data-redis-0이 새 파드에 다시 붙었기 때문이다. API가 redis-0.redis라는 이름으로 접속하므로 IP가 바뀐 것도 문제가 되지 않는다.

디플로이먼트로 같은 것을 했다면 파드 이름이 바뀌고, 볼륨이 없으니 데이터도 사라진다. 이 차이 하나가 "저장소는 스테이트풀셋"이라는 규칙의 전부다.

스테이트풀셋을 지우면 PVC는 어떻게 되나 기본값은 남긴다. kubectl delete statefulset redis를 해도 data-redis-0은 그대로 있고, 같은 이름의 스테이트풀셋을 다시 만들면 데이터를 물고 돌아온다. 실수로 지웠을 때의 안전장치지만, 정리했다고 생각한 볼륨이 요금을 계속 먹는 원인이기도 하다. 동작을 바꾸려면 spec.persistentVolumeClaimRetentionPolicy를 쓴다. 네임스페이스째 지우면(kubectl delete ns journal) PVC도 함께 사라진다. https://kubernetes.io/docs/concepts/workloads/controllers/statefulset/#persistentvolumeclaim-retention

여기서는 스테이트풀셋을 저널 앱의 부품으로 썼다. 볼륨 확장, 스냅샷, 파드별 볼륨을 가진 다중 복제본, 순서 있는 업데이트는 M18에서 따로 파고든다.

여기서 한 번 끊는다

14.5따라하기 ③ 같은 것을 Helm 차트로

지금 만든 매니페스트는 journal 네임스페이스 하나에만 맞다. 개발용을 하나 더 띄우려면 파일을 통째로 복사해 이름과 호스트와 복제본 수를 고쳐야 한다. 복사본이 둘이 되는 순간 한쪽만 고치는 사고가 시작된다.

Helm은 매니페스트를 템플릿과 값으로 나눈다. 템플릿과 기본값을 묶은 디렉터리가 차트 (Chart), 차트를 값과 함께 클러스터에 설치한 결과 하나가 릴리스 (Release)다. 같은 차트로 릴리스를 여럿 만들 수 있고, 릴리스의 변경 이력은 리비전 (Revision)으로 쌓인다. 구조는 한 벌만 두고, 환경마다 다른 것은 값 파일에만 적는다. 값이 늘어나는 것은 괜찮지만 구조가 복제되는 것은 위험하다 — 이 구분이 Helm을 쓰는 이유의 전부다.

13단계. 이름 규칙을 함수로 뺀다

목적같은 차트를 한 클러스터에 여러 번 설치할 수 있게 만든다.

# course/labs/charts/journal/templates/_helpers.tpl
{{/*
  이름 규칙을 한곳에 모은다. 릴리스 이름이 journal 이면 journal-api,
  prod 면 prod-api 가 되도록 모든 리소스가 이 함수를 통해 이름을 만든다.
  같은 클러스터에 같은 차트를 두 번 설치할 수 있는 이유다.
*/}}
{{- define "journal.fullname" -}}
{{- .Release.Name | trunc 63 | trimSuffix "-" -}}
{{- end -}}

{{/* 모든 리소스에 붙이는 공통 레이블. app.kubernetes.io/* 는 쿠버네티스 권장 레이블이다. */}}
{{- define "journal.labels" -}}
app.kubernetes.io/name: journal
app.kubernetes.io/instance: {{ .Release.Name }}
app.kubernetes.io/version: {{ .Chart.AppVersion | quote }}
app.kubernetes.io/managed-by: {{ .Release.Service }}
helm.sh/chart: {{ printf "%s-%s" .Chart.Name .Chart.Version }}
{{- end -}}

{{- define "journal.selectorLabels" -}}
app.kubernetes.io/name: journal
app.kubernetes.io/instance: {{ .Release.Name }}
{{- end -}}

{{- define "journal.apiImage" -}}
{{- $tag := .Values.api.image.tag | default .Chart.AppVersion -}}
{{- printf "%s:%s" .Values.api.image.repository $tag -}}

레이블을 둘로 나눈 것에도 이유가 있다. journal.labels에는 app.kubernetes.io/version처럼 릴리스마다 바뀌는 값이 들어 있다. 이것을 셀렉터에 넣으면 다음 helm upgrade가 field is immutable로 거부된다. 그래서 셀렉터에는 절대 바뀌지 않는 두 개만 쓴다.

include정의한 템플릿을 불러온다. template과 달리 결과를 문자열로 돌려줘 | nindent 같은 파이프에 넣을 수 있다
toYaml값 트리를 YAML로 직렬화한다. resources: {}처럼 구조를 통째로 받을 때 쓴다
$.Template.BasePath차트의 templates 경로. $는 최상위 컨텍스트로, if 블록 안에서도 .이 아닌 원본을 가리킨다

값 파일에 달라지는 것만 적었다. 이미지 이름, 포트, 프로브 설정처럼 환경이 바뀌어도 같은 것은 values.yaml에 한 번만 있다. 값 파일이 커지고 있다면 그것은 템플릿이 충분히 추상화되지 않았다는 신호다.

운영 비밀번호는 파일에 적지 않는다. 설치할 때 주입한다. 아래 명령은 읽기만 하고 실행하지 않는다 — 노트북에 API 파드 6개와 10Gi PVC가 생기고, 이 모듈의 정리 절은 journal-prod를 지우지 않는다.

# 읽기만 한다. 실행하지 않는다.
helm upgrade --install prod course/labs/charts/journal \
  -n journal-prod --create-namespace \
  -f course/labs/charts/journal/values-prod.yaml \
  --set redis.password="$REDIS_PASSWORD"

이것도 완전한 해법은 아니다 — 셸 히스토리와 CI 로그에 남는다. 제대로 된 답은 External Secrets나 SOPS이고 M31에서 다룬다. 이 모듈에서는 "값 파일에 평문을 적지 않는다"까지만 지킨다.

14.7일부러 실패시키기

실패 ① — kubectl로 만든 것 위에 helm install

같은 이름으로 Helm 릴리스를 journal 네임스페이스에 설치해 본다. 매니페스트와 차트가 같은 앱을 만드니 될 것 같지만 그렇지 않다.

helm install journal course/labs/charts/journal -n journal
helm list -n journal
실행 결과 — 에러 원문은 한 줄이다. 읽기 쉽게 세미콜론 뒤에서 줄을 나눴다
Error: INSTALLATION FAILED: unable to continue with install: Secret "journal-secret" in namespace "journal" exists and cannot be imported into the current release: invalid ownership metadata; label validation error: key "app.kubernetes.io/managed-by" must equal "Helm": current value is "kustomize"; annotation validation error: missing key "meta.helm.sh/release-name": must be set to "journal"; annotation validation error: missing key "meta.helm.sh/release-namespace": must be set to "journal" NAME NAMESPACE REVISION UPDATED STATUS CHART APP VERSION
판정INSTALLATION FAILED, 그리고 helm list는 헤더만 돌려준다 — 릴리스가 기록조차 되지 않았다. 첫 충돌이 Secret인 것은 15단계에서 본 Helm의 설치 순서(Secret이 ConfigMap보다 먼저) 때문이다.

Helm은 자기가 만든 리소스에 소유권 표시를 남긴다. 레이블 app.kubernetes.io/managed-by: Helm과 어노테이션 meta.helm.sh/release-name·-namespace 세 가지다. 이 표시가 없거나 다른 값이면 "내 것이 아닌데 덮어쓸 수 없다"며 멈춘다.

여기서 current value is "kustomize"가 보이는 것은 우리가 kustomization.yaml에 그 레이블을 직접 적었기 때문이다. 표시가 정직하게 동작한 셈이다. 레이블을 안 붙였더라면 같은 자리가 missing key "app.kubernetes.io/managed-by"로 바뀐다.

이 안전장치가 없다면 어떻게 되는지가 중요하다. Helm이 남의 리소스를 릴리스에 편입시켰다가 helm uninstall 때 같이 지워 버린다. 실무에서 "헬름으로 하나 지웠더니 관계없는 것까지 사라졌다"는 사고의 원형이 이것이다.

고치는 방법은 셋이고, 상황에 따라 다르다.

  • 다른 네임스페이스에 설치한다 — 지금 실습에서 택한 길(journal-dev)
  • 기존 것을 지우고 Helm으로 다시 만든다: kubectl delete -k ... 후 helm install. 데이터가 있으면 PVC는 남기고 옮길 수 있다
  • 기존 리소스에 소유권 레이블·어노테이션을 손으로 붙여 입양시킨다. 세 개를 정확히 맞춰야 하고 실수하면 위 사고가 난다. 리소스가 적을 때만 쓴다

더 나은 규칙은 애초에 한 리소스를 한 도구만 관리하게 하는 것이다. kustomize와 Helm을 섞어 쓰는 것 자체는 문제가 아니지만, 같은 오브젝트를 둘이 주장하면 반드시 사고가 난다.

kubectl apply -k course/labs/k8s/journal
실행 결과 — 마지막 에러 원문은 한 줄이다. 서버가 채운 필드는 ... 로 줄이고 읽기 쉽게 줄을 나눴다

판정나머지 열한 개는 지나가고 스테이트풀셋만 field is immutable로 거부된다. 다른 리소스 뒤에 나오는 것은 apply -k가 리소스를 차례로 보내기 때문이다.

스테이트풀셋에서 나중에 바꿀 수 있는 필드는 정해져 있다 — replicas, ordinals, template, updateStrategy, persistentVolumeClaimRetentionPolicy, minReadySeconds. volumeClaimTemplates는 그 목록에 없다. 이미 만들어진 PVC들과 템플릿이 어긋나는 상태를 컨트롤러가 표현할 수 없기 때문이다.

실무에서 볼륨을 늘리는 순서는 이렇다.

  1. 스토리지클래스가 allowVolumeExpansion: true인지 확인한다. kind의 standard는 false라 여기서 끝난다
  2. true라면 PVC를 직접 수정한다: kubectl patch pvc data-redis-0 -p '{"spec":{"resources":{"requests":{"storage":"2Gi"}}}}'
  3. 스테이트풀셋은 --cascade=orphan으로 지웠다가 새 템플릿으로 다시 만든다. 파드는 살아 있고 PVC도 그대로다

즉 기존 볼륨은 PVC로, 앞으로 만들 볼륨은 템플릿으로 각각 바꿔야 한다. 순서를 반대로 하면 이미 있는 PVC는 그대로인 채 새 파드만 큰 볼륨을 받는 어긋난 상태가 된다.

실습을 계속하려면 2Gi를 1Gi로 되돌린다. 되돌리지 않으면 rebuild.sh의 apply -k가 같은 자리에서 멈춘다.

실습 규모와 운영 규모가 갈리는 지점

레디스가 복제본 1개다. 이 파드가 죽으면 다시 뜰 때까지 앱 전체가 /readyz 503이 된다 — 10단계에서 kubectl wait가 끝나기까지의 몇 초가 그 시간이다. 운영에서는 Sentinel이나 매니지드 서비스를 쓴다. 이 과정은 "저장소를 클러스터 안에 두는 것의 대가"를 보여 주는 데까지만 간다.

PV가 노드의 로컬 경로다. 9단계에서 본 대로 워커 노드 컨테이너 안의 디렉터리이므로 노드가 죽으면 데이터도 죽는다. 운영에서는 네트워크 볼륨과 Retain 정책, 그리고 볼륨과 별도인 백업이 셋 다 있어야 한다.

비밀번호가 값 파일에 있다. M31까지의 임시 상태이고, 지금 단계에서도 values-prod.yaml에는 적지 않는 습관을 들인다. 16단계의 --set이 그 습관의 첫 단계다.

이미지 태그가 v1이다. 태그는 옮겨 붙을 수 있으므로(M07) 운영에서는 다이제스트(@sha256:...)까지 고정한다. 이 과정에서는 kind에 직접 적재한 이미지라 태그로 충분하다.

Helm 3 · Helm 4 이 모듈은 Helm 4.2.4로 검증했다(2026-09-05). 여기서 쓴 명령(lint · template · install · upgrade · history · rollback · get values)과 apiVersion: v2 차트 형식은 Helm 3에서도 같다. 두 버전의 차이는 M28에서 따로 다룬다. Helm 3의 보안 지원은 2027-02-10에 끝나므로 새로 만드는 파이프라인은 4로 간다. 실습 당일 helm version으로 자기 버전을 확인하고, 검색 결과에 helm init이나 tiller가 나오면 그것은 Helm 2 시절 문서다 — 지금 따라 하면 안 된다. https://helm.sh/docs/ · https://helm.sh/blog/

  • course/labs/k8s/journal/ — 매니페스트 6개 + index.html + kustomization.yaml. M15~M27의 정본이다. 이후 모듈이 프로브·리소스·PDB 등을 고칠 때 이 디렉터리의 파일을 고치고, 각 모듈의 "남기는 파일"에 무엇을 고쳤는지 적는다
  • course/labs/charts/journal/ — 차트 한 벌. M15~M27 동안은 k8s/journal/과 의도적으로 갈라진 채 두고, M28이 "왜 갈라졌는가"를 소재로 한 번에 따라잡는다. 그 사이에 차트를 고치지 않는다
  • course/labs/scripts/rebuild.sh — 빈 클러스터에서 여기까지 복구하는 스크립트
  • 클러스터에 남는 것: 네임스페이스 journal(계속 쓴다), journal-dev(아래에서 지운다). kind 노드의 journal-api:v1·v2 이미지 — v2는 M15 프로브 실습이 롤링 업데이트 대상으로 쓴다
  • default에는 아무것도 남지 않는다. curlbox도 6단계에서 지웠다 — M15 1단계에서 부하 루프용으로 다시 만든다(sleep infinity로)

정리

journal 네임스페이스는 지우지 않는다. M15부터 계속 쓴다. Helm 실습용으로 만든 개발 환경만 정리한다.

helm uninstall dev -n journal-dev
kubectl delete ns journal-dev
kubectl get pv | grep journal-dev
실행 결과
release "dev" uninstalled namespace "journal-dev" deleted

helm uninstall은 릴리스가 만든 리소스를 지우지만 PVC는 남긴다. 네임스페이스를 통째로 지워야 data-dev-redis-0까지 사라진다. 마지막 grep이 아무것도 안 내면 됐다. 이 모듈에서는 부하 생성 루프를 띄우지 않았으므로 따로 죽일 프로세스는 없다.

지금 배포한 journal-api에는 readinessProbe와 livenessProbe가 이미 붙어 있지만, 값이 왜 그 숫자인지는 설명하지 않았다.
