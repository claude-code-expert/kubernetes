오토스케일링

M16에서 붙인 requests.cpu: 50m이 이 모듈의 전제다. HPA는 "지금 쓰는 CPU가 requests의 몇 퍼센트인가"로 파드 수를 정하므로, 그 숫자가 없으면 오토스케일링은 시작조차 하지 않는다. 부하를 걸어 파드가 늘어나는 것을 보고, 부하가 끝나도 5분 동안 줄지 않는 이유를 찾은 뒤 그 시간을 직접 조정한다.

중반80분Kubernetes 1.37.0k6 v2.2.0
2026-09-05 검증 (kind v0.33.0 · metrics-server v0.9.0) · 버전 숫자는 실습 당일 kubectl version·k6 version으로 다시 확인한다
사전 조건
  • M16 완료 — journal-api에 requests가 있다. 확인: kubectl -n journal get deploy journal-api -o jsonpath='{.spec.template.spec.containers[0].resources.requests.cpu}'가 50m
  • metrics-server가 값을 돌려준다 (M01). 확인: kubectl top pod -n journal에 수치가 나온다
  • k6가 설치돼 있다 (M01). 확인: k6 version
  • 인그레스로 앱에 닿는다 (M12). 확인: curl -s -o /dev/null -w '%{http_code}' -H 'Host: journal.local' http://localhost:18080/api/entries가 200
  • 고칠 파일: course/labs/k8s/journal/30-journal-api.yaml · kustomization.yaml
  • 새로 쓰는 파일: course/labs/k8s/journal/70-hpa.yaml · course/labs/scripts/k6-rampup.js

핵심 3줄

1. HPA를 걸고 k6로 부하를 주며 파드가 3개에서 8개로 늘어나는 과정을 15초 간격으로 기록한다.

2. 부하를 걷은 뒤에도 5분 가까이 파드가 줄지 않는 것을 재고, 그 지연이 어디서 오는지 describe hpa의 조건에서 확인한다.

3. behavior로 축소 지연을 30초로 줄여 같은 실험을 반복하고, 두 설정의 확장 경로와 복귀 시간을 숫자로 비교한다.

17.1왜 파드 수를 손으로 정하면 안 되나

M10부터 지금까지 journal-api의 파드 수는 매니페스트에 적힌 replicas: 3이었다. 이 숫자는 누가 정했나. 아무도 재지 않았고, 그냥 셋이었다.

손으로 정한 숫자에는 두 가지 비용이 붙는다. 최대 부하에 맞춰 잡으면 평소에 노는 파드 값을 계속 낸다. 평소에 맞춰 잡으면 몰릴 때 응답이 무너진다. 둘 사이 어딘가로 정해도, 부하가 언제 얼마나 몰릴지 미리 알 수 없다는 문제는 그대로다.

M16에서 requests.cpu: 50m을 붙인 것이 여기서 쓰인다. 그 숫자가 있으면 "지금 이 파드가 예약한 몫의 몇 퍼센트를 쓰고 있는가"를 계산할 수 있고, 그 비율이 목표보다 높으면 파드를 늘리고 낮으면 줄이면 된다. 사람이 정하던 숫자를 측정값에서 유도하는 숫자로 바꾸는 것이다.

그런데 늘리는 것과 줄이는 것은 대칭이 아니다. 늦게 늘리면 요청이 떨어지고, 급하게 줄이면 부하가 다시 올 때 또 늘려야 한다. 이 비대칭을 쿠버네티스가 어떻게 처리하는지, 그 기본값이 우리 상황에 맞는지가 이 모듈에서 실제로 잴 대상이다.

17.2이론 — 세 층의 오토스케일링과 한 줄의 공식

책 8.3.7 이후는 오토스케일링을 세 층으로 나눈다. 늘리는 대상이 서로 다르다.

층무엇을 늘리나언제 쓰나이 과정에서
HPA (수평)파드 개수요청이 늘어 처리량이 부족할 때이 모듈에서 실습한다
VPA (수직)파드 하나의 requests·limits값을 잘못 잡았을 때. 적정값 추천도 한다개념만. HPA와 같은 지표로 함께 쓰면 서로 싸운다
클러스터 오토스케일러노드 수파드가 Pending인데 넣을 노드가 없을 때kind에서는 성립하지 않는다. 노드가 고정이다

세 층은 위에서 아래로 이어진다. HPA가 파드를 늘리려는데 노드에 자리가 없으면 파드는 Pending이 되고(M16 3단계에서 본 그 상태다), 그때 노드를 늘리는 것이 클러스터 오토스케일러다. 클라우드에서는 이 자리에 Karpenter 같은 도구가 들어가 "어떤 인스턴스 타입을 몇 대 살 것인가"까지 정한다. 노트북 클러스터에서는 노드가 고정이므로 HPA가 maxReplicas에 닿으면 거기서 끝난다는 것을 전제로 실습한다.

파드 수를 정하는 공식

HPA 컨트롤러는 기본 15초마다 깨어나 아래 한 줄을 계산한다.

desiredReplicas = ceil( currentReplicas × ( currentMetricValue / desiredMetricValue ) )

여기서 desiredMetricValue가 노드 용량의 몇 퍼센트가 아니라 requests의 몇 퍼센트라는 점이 핵심이다. requests.cpu: 50m에 목표 50%면 파드당 25m가 기준선이고, 실제 사용량이 파드당 48m이면 ceil(3 × 48/25) = ceil(5.76) = 6이 된다. requests가 없으면 분모를 만들 수 없어 계산 자체가 성립하지 않는다 — 17.7 실패 ①이 그 장면이다.

왜 줄일 때만 기다리나

부하는 오르내린다. 매 계산마다 그대로 따르면 파드 수가 위아래로 진동하고, 파드가 뜨고 지는 데 드는 비용(이미지 준비, 프로브 통과, 커넥션 재수립)이 이득보다 커진다. 이것을 진동 thrashing이라고 한다.

쿠버네티스는 이를 안정화 윈도우 stabilization window로 막는다. 축소할 때는 지난 300초 동안 계산된 권고값 중 가장 큰 값을 쓴다. 부하가 잠깐 꺼졌다고 바로 줄이지 않고, 5분 내내 낮았을 때만 줄인다는 뜻이다. 확장은 반대로 기본값이 0초다 — 부족한 상태를 끄는 것이 더 비싸기 때문이다.

이 5분이 우리 상황에 맞는지는 재 봐야 안다. 17.5에서 기본값 그대로 재고, 17.6에서 바꿔서 다시 잰다.

17.3따라하기 ① 부하 도구를 세우고 크기를 맞춘다

M15의 loadgen.sh는 실패 건수를 세는 도구였다. 여기서는 요청률을 정확히 고정해야 하므로 k6를 쓴다.

1단계 — k6 스크립트를 만든다

목적초당 요청 수를 일정하게 유지하는 부하를 만든다. 이 값이 일정해야 파드 수 변화가 부하 변화 때문인지 아닌지 구분할 수 있다.

course/labs/scripts/k6-rampup.js로 저장한다.

import http from 'k6/http';
import { check } from 'k6';

const RPS = Number(__ENV.RPS || 120);
const DURATION = __ENV.DURATION || '5m';
const HOST = __ENV.HOST || 'journal.local';
const PORT = __ENV.PORT || '18080';

export const options = {
  scenarios: {
    steady: {
      executor: 'constant-arrival-rate',
      rate: RPS,
      timeUnit: '1s',
      duration: DURATION,
      preAllocatedVUs: 20,
      maxVUs: 100,
    },
  },
  thresholds: {
    http_req_failed: ['rate<0.01'],
  },
};

export default function () {
  const r = http.get(`http://localhost:${PORT}/api/entries`, { headers: { Host: HOST } });
  check(r, { 'status 200': (x) => x.status === 200 });
}
설정뜻
executor: 'constant-arrival-rate'초당 요청 수를 고정한다. VU 수를 고정하는 방식과 다르다
preAllocatedVUs / maxVUs요청률을 지키기 위해 k6가 쓸 수 있는 동시 실행 단위. 응답이 느려지면 늘려서 rate를 맞춘다
thresholds기준을 못 지키면 k6가 실패로 끝난다. 부하는 계속 돈다

왜 VU 수가 아니라 요청률을 고정하나. VU 수만 정하면 앱이 빨라질수록 요청이 더 많이 들어간다. HPA가 파드를 늘려 응답이 빨라지면 부하도 같이 커지고, 그러면 "같은 부하에 파드가 몇 개 필요한가"를 잴 수 없게 된다. 부하를 상수로 고정해야 파드 수만 변수로 남는다.

2단계 — 부하 크기를 맞춘다

목적파드가 단계적으로 늘어나는 것이 보이는 요청률을 찾는다. 너무 세면 한 번에 최대치로 뛰어 과정이 사라진다.

먼저 유휴 상태의 CPU를 본다.

출력

파드당 2m, requests 50m의 4%다. 요청률을 바꿔 가며 얼마나 오르는지 잰다.

요청률파드당 CPUrequests(50m) 대비

판정목표가 50%(25m)이므로 120 rps면 필요 파드 수가 약 두 배가 된다 — 3개에서 6개 안팎이다. 마지막 줄처럼 세게 걸면 계산상 필요 파드가 80개를 넘어 첫 계산에서 곧바로 maxReplicas로 뛴다. 그러면 늘어나는 과정을 볼 수 없다. 이 표의 수치는 노트북 성능에 따라 다르므로, 자기 환경에서 requests 대비 100% 언저리가 되는 요청률을 찾아 그 값을 쓴다.

17.4따라하기 ② HPA를 걸고 늘어나는 것을 본다

3단계 — HPA를 만든다

목적파드 수의 결정권을 사람에게서 컨트롤러로 넘긴다.

cat <<'EOF' | kubectl -n journal apply -f -
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: {name: journal-api}
spec:
  scaleTargetRef: {apiVersion: apps/v1, kind: Deployment, name: journal-api}
  minReplicas: 3
  maxReplicas: 8
  metrics:
    - type: Resource
      resource:
        name: cpu
        target: {type: Utilization, averageUtilization: 50}
EOF
필드뜻
minReplicas: 3M16에서 만든 PDB의 minAvailable: 2보다 커야 한다. 같거나 작으면 노드를 비울 수 없다
maxReplicas: 8상한. 이 값에 닿으면 부하가 더 늘어도 파드는 그대로다
type: Utilizationrequests 대비 백분율. AverageValue로 두면 절대값(100m 같은)을 기준으로 삼는다

kubectl autoscale 한 줄로도 만들 수 있지만 YAML로 쓴다. 17.6에서 behavior를 더할 자리가 필요하고, 명령형으로 만든 것은 파일로 남지 않기 때문이다(M08 8.7).

kubectl -n journal get hpa journal-api
출력
NAME REFERENCE REFERENCE TARGETS MINPODS MAXPODS REPLICAS AGE journal-api Deployment/journal-api cpu: 3%/50% 3 8 3 35s
판정TARGETS가 3%/50%다. 앞이 현재값, 뒤가 목표다. 여기가 <unknown>이면 17.7 실패 ①로 간다. 값이 나오기까지 15~30초 걸리므로 바로 안 보인다고 놀랄 필요는 없다.

4단계 — 관찰 스크립트를 띄우고 부하를 건다

목적파드 수가 언제 어떻게 바뀌는지 시각과 함께 기록한다. 나중에 축소 지연을 재려면 시각이 필요하다.

터미널 두 개를 쓴다. 첫 번째에서 관찰을 시작한다.

while true; do
  read cur tgt des <<<"$(kubectl -n journal get hpa journal-api \
    -o jsonpath='{.status.currentMetrics[0].resource.current.averageUtilization} {.spec.metrics[0].resource.target.averageUtilization} {.status.desiredReplicas}')"
  ready=$(kubectl -n journal get po -l app=journal-api --no-headers | grep -c '1/1')
  printf '%s  %3s%%  목표 %s%%  desired=%s  ready=%s\n' "$(date +%T)" "${cur:-?}" "${tgt:-?}" "${des:-?}" "$ready"
  sleep 15
done

kubectl get hpa의 TARGETS 열은 cpu: 3%/50%처럼 공백이 들어 있어 awk로 자르면 어긋난다. jsonpath로 필요한 값만 꺼내는 편이 안전하다. 멈추는 방법은 Ctrl-C다.

두 번째 터미널에서 부하를 건다.

k6 run -e RPS=120 -e DURATION=5m course/labs/scripts/k6-rampup.js
인자 전달 방식 k6 run RPS=120 script.js처럼 쓰면 accepts 1 arg(s), received 3 오류가 난다. k6는 스크립트 경로 하나만 인자로 받는다. 스크립트 안의 __ENV로 값을 넘기려면 -e KEY=VALUE를 쓴다.

판정부하 시작 약 8초 뒤에 첫 확장이 일어났고, 53초 만에 maxReplicas 8에 닿았다. 사용률이 목표 50% 아래로 내려가면서 안정됐다. 시각과 파드 수가 함께 기록돼 있어야 다음 절에서 축소 지연을 잴 수 있다.

5단계 — 부하 쪽 결과도 확인한다

목적파드가 늘어나는 동안 사용자 쪽 응답이 실제로 유지됐는지 본다. 파드 수만 보면 절반만 본 것이다.

k6 출력 (일부)
checks_succeeded...: 100.00% 36001 out of 36001 http_req_duration..: avg=2.07ms min=602µs med=1.78ms max=55.77ms p(90)=3.37ms p(95)=3.71ms http_req_failed....: 0.00% 0 out of 36001 http_reqs..........: 36001 120.001577/s
판정36001건 전부 성공, p95가 3.71ms다. 요청률도 정확히 120/s로 유지됐다. 확장이 늦었다면 http_req_failed나 p(95)에 흔적이 남는다.

8개가 정답이었나

안정 구간의 사용률은 39~49%였다. 목표가 50%이므로 이 상태에서의 권고값은 ceil(8 × 40/50) = 7이다. 3에서 8로 뛴 것은 과잉 확장이었다. 파드가 3개일 때 사용률이 81%로 측정됐고 그 값으로 계산하면 ceil(5 × 81/50) = 9가 나와 상한 8에 걸린 것이다.

이 과잉이 문제가 되는 이유는 다음 절에서 드러난다. 축소가 8에서 7로 시작한 것이 우연이 아니다.

17.5따라하기 ③ 왜 바로 줄지 않는가

6단계 — 부하가 끝난 뒤를 계속 지켜본다

목적CPU가 떨어진 시각과 파드가 줄어든 시각의 차이를 잰다.

k6가 끝나도 관찰 스크립트는 그대로 둔다.

관찰 출력 (부하 종료 이후)

판정CPU는 부하 종료와 거의 동시에 3%로 떨어졌는데, 첫 축소는 약 3분 6초 뒤, 3개로 완전히 돌아온 것은 약 4분 52초 뒤였다. 그동안 쓰지도 않는 파드 다섯 개가 떠 있었다.

7단계 — HPA에게 왜 안 줄이는지 묻는다

목적지연의 원인을 추측하지 않고 컨트롤러가 남긴 조건에서 읽는다.

kubectl -n journal describe hpa journal-api | sed -n '/Conditions:/,/Events:/p'
출력
Conditions: Type Status Reason Message ---- ------ ------ ------- AbleToScale True ScaleDownStabilized recent recommendations were higher than current one, applying the highest recent recommendation ScalingActive True ValidMetricFound the HPA was able to successfully calculate a replica count from cpu resource utilization (percentage of request) ScalingLimited False DesiredWithinRange the desired count is within the acceptable range
판정ScaleDownStabilized — "최근 권고값이 지금 것보다 컸으므로 그중 가장 큰 값을 쓰고 있다"는 뜻이다. 지금 계산하면 3이 나오지만 5분 전에는 8이었고, 안정화 윈도우가 그 8을 아직 기억하고 있다.

축소가 8이 아니라 7에서 시작한 이유

안정화 윈도우는 지난 300초 안의 모든 권고값 중 최댓값을 쓴다. 19:28:31 시점의 창은 19:23:31부터인데, 그 구간에서 사용률은 이미 39~49%로 내려가 있었고 그때의 권고값은 ceil(8 × 40/50) = 7이었다. 창 안에 8이 남아 있지 않았으므로 7이 최댓값이 된 것이다.

그래서 축소는 계단식으로 내려온다. 창이 앞으로 밀릴 때마다 더 큰 옛 권고값이 하나씩 빠지고, 남은 것 중 최댓값이 새 목표가 된다. CPU가 3%로 떨어진 19:25:44로부터 300초가 지난 19:30:44 무렵에 창 안이 전부 낮은 값이 되고, 그때 최소치인 3으로 내려온다 — 실제 기록은 19:30:12였다.

이 동작 자체는 합리적이다. 문제는 5분이 우리 상황에 맞느냐다. 트래픽이 하루 종일 오르내리는 서비스라면 5분은 안전장치지만, 짧은 배치 작업이 끝난 뒤라면 5분치 파드 값을 그냥 버리는 셈이다. 다음 절에서 이 값을 바꾼다.

17.6따라하기 ④ behavior로 조정한다

8단계 — 확장·축소 정책을 명시한다

목적기본값에 맡기지 않고 확장 속도와 축소 지연을 직접 정한다.

cat <<'EOF' | kubectl -n journal apply -f -
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: {name: journal-api}
spec:
  scaleTargetRef: {apiVersion: apps/v1, kind: Deployment, name: journal-api}
  minReplicas: 3
  maxReplicas: 8
  metrics:
    - type: Resource
      resource:
        name: cpu
        target: {type: Utilization, averageUtilization: 50}
  behavior:
    scaleUp:
      stabilizationWindowSeconds: 0
      policies: [{type: Percent, value: 50, periodSeconds: 30}]
    scaleDown:
      stabilizationWindowSeconds: 30
      policies: [{type: Pods, value: 1, periodSeconds: 30}]
EOF
설정뜻
scaleUp.stabilizationWindowSeconds: 0확장은 기다리지 않는다. 기본값도 0이다
scaleUp.policies: Percent 50 / 30초30초마다 최대 50%까지만 늘린다. 3개면 다음 단계는 5개(ceil(4.5))다
scaleDown.stabilizationWindowSeconds: 30축소는 30초만 기다린다. 기본값 300초에서 줄였다
scaleDown.policies: Pods 1 / 30초30초마다 한 개씩만 줄인다. 한꺼번에 빠져 남은 파드가 몰리는 것을 막는다

scaleUp에 상한 정책을 두는 이유는 17.4에서 본 과잉 확장 때문이다. 한 번의 측정으로 3에서 8로 뛰는 대신 단계를 밟게 하면, 파드가 늘어 사용률이 내려간 것을 반영하며 필요한 만큼에서 멈춘다.

실패 ② 매니페스트의 replicas가 HPA의 결정을 되돌린다

30-journal-api.yaml에는 아직 replicas: 3이 남아 있다. HPA가 8로 올려 둔 상태에서 apply를 하면 어떻게 되는지 본다. 배포 파이프라인이 주기적으로 apply를 도는 환경에서 실제로 일어나는 일이다.

재현 
kubectl -n journal scale deploy journal-api --replicas=6
kubectl -n journal get deploy journal-api -o jsonpath='{.spec.replicas}{"\n"}'

kubectl apply -k course/labs/k8s/journal
kubectl -n journal get deploy journal-api -o jsonpath='{.spec.replicas}{"\n"}'
출력
6 deployment.apps/journal-api configured 3
원인

kubectl apply는 매니페스트에 적힌 값을 진실로 삼는다. 파일에 replicas: 3이 있으면 HPA가 무엇을 정했든 3으로 되돌린다. 부하가 몰려 8개로 늘어난 순간 배포가 돌면 파드가 3개로 줄고 그 상태로 요청을 받는다. 그리고 HPA가 다시 늘리는 데 수십 초가 걸린다.

고친다 — replicas의 주인을 하나로 만든다 
# 30-journal-api.yaml 에서 replicas 줄을 지운다
spec:
  # replicas 를 적지 않는다 (M17). HPA 가 이 필드의 주인이다 —
  # 여기에 숫자를 남겨 두면 apply 할 때마다 HPA 가 정한 값이 이 값으로 되돌아간다.
  selector:
    matchLabels:
      app: journal-api
kubectl -n journal scale deploy journal-api --replicas=6
kubectl apply -k course/labs/k8s/journal
for i in 1 2 3 4 5 6; do
  echo "+${i}s: $(kubectl -n journal get deploy journal-api -o jsonpath='{.spec.replicas}')"
  sleep 1
done
출력
+1s: 6 +2s: 6 +3s: 6 +4s: 6 +5s: 6 +6s: 6
판정apply가 파드 수를 건드리지 않는다. replicas를 처음 지운 apply는 한 번 값이 떨어진다 — 필드가 제거되면서 기본값으로 돌아갔다가 HPA가 minReplicas로 올린 것이다. 그 이후의 apply부터 안정된다.

같은 원리가 GitOps에서도 그대로 적용된다. Flux나 Argo CD가 주기적으로 매니페스트를 맞추므로, HPA가 관리하는 필드를 파일에 남겨 두면 30초마다 파드 수가 되돌아간다. M31에서 드리프트 복구를 다룰 때 이 구분이 다시 나온다.

17.8운영 관점 — 무엇을 기준으로 늘릴 것인가

이 모듈은 CPU를 기준으로 썼다. 그것이 가장 쉽게 얻을 수 있는 지표이기 때문이지, 가장 좋은 기준이어서가 아니다.

CPU가 기준으로 잘 맞는 것은 CPU가 병목인 워크로드뿐이다. 이미지 변환이나 압축처럼 계산이 일인 서비스가 여기 해당한다. 반면 대부분의 API 서버는 대기가 일이다 — 데이터베이스 응답을 기다리고, 외부 호출을 기다린다. 이런 서비스는 요청이 밀려 응답이 느려지는데도 CPU는 낮게 유지된다. 큐가 쌓이고 P99가 무너지는 동안 HPA는 "20%밖에 안 쓰는데 왜 늘려"라고 판단한다.

그래서 실무에서는 초당 요청 수, 큐 길이, 활성 커넥션 수 같은 지표로 확장하는 쪽이 실제 부하에 가깝다. HPA는 이런 지표도 받을 수 있다.

지표 종류어디서 오나예
Resourcemetrics-server이 모듈에서 쓴 CPU·메모리
Pods · Object커스텀 메트릭 API (프로메테우스 어댑터)파드당 초당 요청 수, 인그레스의 활성 커넥션 수
External외부 메트릭 API클라우드 큐의 메시지 수

커스텀 메트릭을 쓰려면 그 값을 수집·저장하고 쿠버네티스의 메트릭 API로 노출하는 층이 필요하다. metrics-server는 최근값만 들고 있고 기록을 남기지 않아서 이 역할을 못 한다. 프로메테우스를 세우고 어댑터를 붙이는 것이 M19~M20의 산출물이며, 그것이 갖춰진 뒤에야 "P99가 300ms를 넘으면 늘린다" 같은 규칙을 쓸 수 있다.

메모리로 확장하지 않는 이유

메모리를 기준으로 삼는 설정을 종종 보는데, 대개 잘 작동하지 않는다. JVM이나 Go 런타임은 한번 확보한 메모리를 잘 반납하지 않는다. 부하가 끝나도 사용량이 내려가지 않으므로 HPA는 축소 신호를 받지 못하고, 파드는 늘어난 채로 남는다. 반대로 메모리가 정말 부족하면 확장이 아니라 OOMKilled가 먼저 온다(M16 실패 ③). 메모리는 limits로 막을 대상이지 확장 신호로 쓸 대상이 아니다.

HPA와 VPA를 같이 쓰면

둘 다 CPU를 보고 있으면 서로의 결정을 무너뜨린다. HPA가 파드를 늘려 파드당 사용량이 내려가면 VPA는 requests를 낮추고, requests가 낮아지면 사용률(백분율)이 다시 올라 HPA가 또 늘린다. 같은 지표에 두 컨트롤러를 붙이지 않는 것이 원칙이고, 굳이 함께 쓴다면 VPA는 메모리만 조정하게 두고 HPA가 CPU를 맡는 식으로 나눈다.

확장에는 시간이 든다

이 실습에서 파드는 1초 안에 떴다. 실제 서비스는 이미지를 받고, 런타임이 올라오고, 커넥션 풀을 채우고, 캐시를 데우는 데 수십 초가 걸린다 — M15에서 sleep 8로 흉내 냈던 그 시간이다. HPA가 확장을 결정하고 나서 실제로 트래픽을 받기까지의 지연이 부하가 몰리는 속도보다 느리면, 오토스케일링은 있으나 마나다. 스파이크가 빠른 서비스는 미리 여유를 두거나(minReplicas를 올린다) 예측 기반으로 미리 늘리는 편이 낫고, 이 판단의 근거도 결국 관측이다.

정리

k6와 관찰 루프를 반드시 멈춘다. k6는 포그라운드로 돌면 Ctrl-C로 끝나지만, 백그라운드로 띄웠다면 남아 있을 수 있다.

# 부하가 남아 있지 않은지 확인하고 정리한다
pkill -f k6-rampup 2>/dev/null
# 관찰 루프를 돌린 터미널에서는 Ctrl-C

# 실험 네임스페이스
kubectl delete ns m17 --ignore-not-found

# 파드 수가 최소치로 돌아왔는지 (안정화 윈도우 30초 + 계단식 축소만큼 걸린다)
kubectl -n journal get hpa journal-api
출력
NAME REFERENCE TARGETS MINPODS MAXPODS REPLICAS AGE journal-api Deployment/journal-api cpu: 3%/50% 3 8 3 42m

HPA는 지우지 않는다. 다음 모듈들이 이 상태를 전제로 진행한다. 파드 수가 3보다 크면 부하가 아직 남아 있다는 뜻이므로 pkill을 다시 확인한다.

다음 모듈

M15부터 여기까지 다룬 것은 전부 상태가 없는 워크로드였다. 파드를 죽여도 되고 옮겨도 되고 늘렸다 줄여도 됐다. M18은 그것이 통하지 않는 쪽을 다룬다 — journal 네임스페이스에서 지금까지 한 번도 건드리지 않은 redis-0이 그 대상이다. M16에서 노드를 비울 때 --pod-selector로 레디스를 제외했던 것도, 이 파드가 노드에 묶인 볼륨을 들고 있기 때문이다. PVC와 스토리지클래스, 스테이트풀셋이 디플로이먼트와 다른 세 가지, 그리고 kind의 기본 스토리지가 볼륨 확장을 거부하는 것을 실패로 재현한다.
