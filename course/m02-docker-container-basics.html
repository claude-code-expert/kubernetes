컨테이너는 프로세스다

컨테이너를 "가벼운 가상 머신"으로 배우면 나중에 반드시 막힌다. 실제로는 격리된 리눅스 프로세스 하나다. 이 모듈에서 같은 프로세스를 안에서는 PID 1로, 밖에서는 다섯 자리 PID로 확인한다.

초반50분Docker Engine 29.2.1
2026-09-03 macOS(Apple Silicon) · nginx:1.29-alpine · alpine:3.22 에서 전 명령 실행 검증 · 버전은 실습 당일 다시 확인한다
사전 조건
  • M01 완료 — 컨테이너 런타임이 실행 중 (docker version에 Server 줄이 나온다)
  • kind 클러스터는 이 모듈에서 쓰지 않는다. 떠 있어도 상관없다

핵심 3줄

1. docker exec web ps의 PID 1과 docker top web의 호스트 PID를 inspect의 State.Pid로 맞춰 보고, 둘이 같은 프로세스의 두 이름임을 확인한다. 격리는 가림막이지 별도의 컴퓨터가 아니다.

2. run · ps · logs · exec · stop · rm 여섯 개로 컨테이너 하나의 수명 전체를 다루고, ps -a로 종료된 것까지 찾아 지운다.

3. --memory=32m을 걸어 일부러 넘기고, 아무 로그 없이 남은 종료 코드 137과 OOMKilled=true를 읽는다. 이 숫자를 M16에서 쿠버네티스의 OOMKilled로 다시 만난다.

2.1왜 프로세스인지가 중요한가

M01에서 만든 클러스터의 노드 3개는 도커 컨테이너였다. 그 안에서 다시 컨테이너가 돌고, 그것이 파드다. 이 구조가 이상하게 들린다면 컨테이너를 가상 머신으로 이해하고 있기 때문이다.

가상 머신은 게스트 운영체제 커널을 따로 부팅한다. 컨테이너는 그러지 않는다. 호스트 커널을 그대로 쓰면서 시야만 가린다. 그래서 부팅이 없고, 시작이 밀리초 단위이며, 컨테이너 안에서 uname -r을 치면 호스트 커널 버전이 나온다.

이 차이는 나중에 실무 판단으로 이어진다. 컨테이너가 메모리를 넘게 쓰면 리눅스 커널의 OOM 킬러가 그 프로세스를 죽인다 — 애플리케이션의 예외 처리가 아니라 커널의 결정이라 로그조차 안 남는 경우가 있다(2.5절에서 재현하고, 쿠버네티스에서는 M16에서 다시 만난다). 컨테이너 안에서 top을 쳐도 호스트 전체 메모리가 보이는 것, 컨테이너를 지워도 볼륨은 남는 것, 파드의 여러 컨테이너가 localhost로 통신하는 것(M09) 전부 같은 원리에서 나온다.

2.2이론 — 격리를 만드는 두 기능

리눅스 커널의 두 기능이 컨테이너의 전부라고 해도 크게 틀리지 않다.

기능하는 일이 모듈에서 확인하는 방법
네임스페이스 (Namespace)보이는 것을 가른다. PID · 네트워크 · 마운트 · 호스트네임 · 사용자 등 종류별로 따로 있다. 컨테이너 안에서는 자기 프로세스만, 자기 네트워크 인터페이스만 보인다안에서 ps → PID 1, 밖에서 docker top → 다섯 자리 PID
cgroup (Control Group)쓸 수 있는 양을 가른다. CPU · 메모리 · 디스크 I/O에 상한을 걸고 사용량을 잰다--memory=32m을 넘겨 OOM으로 죽이기

둘의 역할 분담이 명확하다. 네임스페이스는 보이는 범위, cgroup은 쓸 수 있는 양. 쿠버네티스에서 이 둘은 각각 파드(같은 네트워크 네임스페이스를 공유하는 컨테이너 묶음, M09)와 리소스 requests/limits(cgroup 설정값, M16)로 다시 등장한다. 지금 손으로 확인해 두면 그때 개념을 새로 배울 필요가 없다.

맥과 윈도우에서는 한 겹이 더 있다 네임스페이스와 cgroup은 리눅스 커널 기능이다. 맥에는 없다. 그래서 Docker Desktop · OrbStack · Colima는 전부 안쪽에 리눅스 VM을 하나 띄우고 컨테이너를 그 안에서 돌린다. 이 모듈에서 "호스트에서 본 PID"라고 할 때의 호스트는 맥이 아니라 그 리눅스 VM이다. 그래서 맥 터미널의 ps로는 컨테이너 프로세스가 보이지 않고, docker top으로 VM 안을 들여다봐야 한다. 리눅스에서 실습하는 사람은 ps -ef | grep nginx로 바로 보인다.

2.3따라하기 ① 실행하고 접속한다

1단계. 웹 서버 컨테이너를 띄운다

목적이미지를 받아 실행하고, 호스트 포트로 접속 경로를 낸다.

docker run -d --name web -p 8081:80 nginx:1.29-alpine
  • -d — 백그라운드(detached) 실행. 빼면 터미널이 붙잡힌다
  • --name web — 이름을 붙인다. 안 붙이면 nostalgic_hopper 같은 임의 이름이 생기고 이후 명령마다 컨테이너 ID를 복사해야 한다
  • -p 8081:80 — 호스트:컨테이너 순서다. 맥의 8081로 온 요청을 컨테이너의 80으로 넘긴다. 순서를 뒤집으면 접속이 안 된다
  • nginx:1.29-alpine — 이미지 이름과 태그. 태그를 항상 적는다. 생략하면 latest가 되고, 그것이 어느 버전인지는 시점에 따라 다르다
실행 결과 (첫 실행은 이미지를 받는다)
Unable to find image 'nginx:1.29-alpine' locally 1.29-alpine: Pulling from library/nginx ... Digest: sha256:5616878291a2eed594aee8db4dade5878cf7edcb475e59193904b198d9b830de Status: Downloaded newer image for nginx:1.29-alpine aa694ff9927e2aef59be14c72bedf17836b93f56ce0dae8b130a12f63538baf2

마지막 줄의 64자리 16진수가 컨테이너 ID다. 앞 12자리만 써도 대부분의 명령에서 통한다. Digest: 줄은 M03에서 다룬다.

판정마지막에 긴 ID 한 줄이 출력되면 성공이다. 에러 메시지 없이 ID만 나온다.

2단계. 상태를 확인하고 접속한다

목적컨테이너가 살아 있는지, 포트가 실제로 연결됐는지 확인한다.

docker ps --filter name=web
실행 결과
CONTAINER ID IMAGE COMMAND CREATED STATUS PORTS NAMES aa694ff9927e nginx:1.29-alpine "/docker-entrypoint.…" 1 second ago Up Less than a second 0.0.0.0:8081->80/tcp, [::]:8081->80/tcp web

읽을 곳은 두 군데다. STATUS가 Up으로 시작하는가(Exited면 죽은 것), PORTS에 8081->80이 있는가. COMMAND는 이미지에 정의된 시작 명령으로, 이 프로세스가 죽으면 컨테이너도 끝난다.

curl -s -o /dev/null -w '%{http_code} %{size_download}bytes\n' http://localhost:8081/
실행 결과
200 896bytes
판정200. 브라우저로 http://localhost:8081을 열면 nginx 기본 페이지가 나온다.

3단계. 로그를 본다

목적컨테이너의 표준 출력이 곧 로그라는 원칙을 확인한다. 이 원칙이 M22 로그 수집의 전제다.

docker logs web | tail -6
실행 결과
2026/09/03 12:40:21 [notice] 1#1: start worker process 41 2026/09/03 12:40:21 [notice] 1#1: start worker process 42 2026/09/03 12:40:21 [notice] 1#1: start worker process 43 192.168.65.1 - - [03/Sep/2026:12:40:21 +0000] "GET / HTTP/1.1" 200 896 "-" "curl/8.7.1" "-"

방금 보낸 curl 요청이 액세스 로그로 찍혔다. 여기서 눈여겨볼 것은 nginx가 로그 파일을 쓰지 않았다는 점이다 — 컨테이너용 이미지들은 로그를 표준 출력으로 보낸다. 파일에 쓰면 컨테이너를 지울 때 함께 사라지고, 밖에서 수집할 방법이 없기 때문이다. 앞의 1#1은 마스터 프로세스의 PID가 1이라는 뜻이다 — 다음 절의 주제다.

실시간으로 보려면 -f를 붙인다. docker logs -f web은 Ctrl+C로 빠져나온다(컨테이너는 계속 돈다).

판정마지막 줄에 "GET / HTTP/1.1" 200이 들어 있는 액세스 로그 한 줄이 있다 — 2단계의 curl 한 번이 로그 한 줄이다. 그 줄이 없으면 2단계 요청이 컨테이너까지 오지 않은 것이므로 docker ps의 PORTS를 다시 본다. 앞 줄들의 1#1은 마스터 프로세스의 PID가 1이라는 뜻이다. 앞의 타임스탬프와 클라이언트 IP는 환경마다 다르다.

2.4따라하기 ② 안과 밖에서 같은 프로세스 보기

이 모듈의 핵심 실습이다. 같은 프로세스를 두 시야에서 본다.

4단계. 컨테이너 안에서 프로세스 목록을 본다

목적PID 네임스페이스가 시야를 어떻게 가리는지 확인한다.

docker exec web ps -eo pid,ppid,comm
  • exec — 이미 돌고 있는 컨테이너 안에서 명령을 하나 더 실행한다. 새 컨테이너를 만드는 run과 다르다
  • 셸로 들어가려면 docker exec -it web sh (-i 표준 입력 유지, -t 터미널 할당). 나올 때는 exit
실행 결과 (앞부분)
PID PPID COMMAND 1 0 nginx 30 1 nginx 31 1 nginx 32 1 nginx 33 1 nginx

컨테이너 안에서 nginx 마스터는 PID 1이다. 그리고 이 목록에는 맥에서 돌고 있는 수백 개의 프로세스가 하나도 보이지 않는다. 컨테이너가 자기만의 PID 네임스페이스를 갖기 때문이다.

PID 1이라는 사실에는 실무적 의미가 있다. 리눅스에서 PID 1은 init 자리이고, 커널은 PID 1에게 시그널을 특별 취급한다 — 핸들러를 등록하지 않은 프로세스는 SIGTERM을 무시한다. 종료 신호를 처리하지 않는 애플리케이션을 PID 1로 띄우면 docker stop이 10초를 기다렸다가 SIGKILL로 강제 종료한다. 쿠버네티스에서도 똑같이 일어나며, 그때는 롤아웃마다 커넥션이 끊긴다(M15에서 preStop 훅과 terminationGracePeriodSeconds로 다룬다).

5단계. 밖에서 같은 프로세스를 찾는다

목적컨테이너가 별도의 컴퓨터가 아니라 호스트의 프로세스임을 확인한다.

docker top web
docker inspect -f 'Pid={{.State.Pid}} Status={{.State.Status}}' web
실행 결과 (일부)
UID PID PPID C STIME TTY TIME CMD root 98137 98115 7 12:40 ? 00:00:00 nginx: master process nginx -g daemon off; statd 98181 98137 0 12:40 ? 00:00:00 nginx: worker process statd 98182 98137 0 12:40 ? 00:00:00 nginx: worker process ...(worker 프로세스가 이어진다) Pid=98137 Status=running

안에서 PID 1이던 마스터가 밖에서는 98137이다. 같은 프로세스이고 번호만 두 개다. 워커들도 안에서는 30번대, 밖에서는 98181 이후로 이어진다. 프로세스가 두 벌 있는 것이 아니라, 네임스페이스가 번호를 다시 매겨 보여줄 뿐이다.

사용자 이름이 statd로 나오는 것도 같은 이유다. 컨테이너 안의 nginx 사용자 UID가 호스트에서는 우연히 statd에 해당하는 번호였을 뿐이다. UID는 숫자이고, 이름은 각자의 /etc/passwd가 붙인다. 이 사실은 M24에서 runAsNonRoot와 파일 권한을 다룰 때 다시 쓰인다.

판정docker top의 마스터 PID(다섯 자리)와 inspect의 Pid= 값이 같다. 그 프로세스가 컨테이너 안에서는 1번이다.

리눅스에서 실습 중이라면 여기에 한 단계를 더 할 수 있다. ps -ef | grep 98137로 호스트 프로세스 목록에서 직접 찾아진다. 맥·윈도우는 리눅스 VM 안이라 맥 터미널의 ps로는 보이지 않는다.

6단계. 자원 사용량을 실시간으로 본다

목적cgroup이 사용량을 재고 있다는 것을 확인한다.

docker stats --no-stream web
  • --no-stream — 한 번만 찍고 끝낸다. 빼면 실시간 갱신 화면이 되고 Ctrl+C로 나온다
실행 결과
CONTAINER ID NAME CPU % MEM USAGE / LIMIT MEM % NET I/O BLOCK I/O PIDS aa694ff9927e web 0.00% 11.86MiB / 7.652GiB 0.15% 1.8kB / 1.68kB 520kB / 8.19kB 15

LIMIT가 7.652GiB — 이 컨테이너에는 메모리 제한을 걸지 않았으므로 런타임 VM 전체 메모리가 상한으로 표시된다. 제한 없는 컨테이너 하나가 호스트 메모리를 다 먹고 다른 컨테이너를 굶길 수 있다는 뜻이다. 다음 절에서 상한을 걸어본다.

판정MEM USAGE가 수 MiB에서 수십 MiB, LIMIT가 1.3절에서 런타임에 준 메모리(GiB 단위)와 같은 자릿수, PIDS가 4단계에서 본 프로세스 수와 비슷하면 정상이다. 수치 자체는 환경마다 다르다. LIMIT가 GiB가 아니라 MiB로 나오면 이 컨테이너에 제한이 걸린 것이므로 docker inspect -f '{{.HostConfig.Memory}}' web을 본다(0이 정상).

2.5따라하기 ③ 자원 제한과 OOM

7단계. 메모리 상한을 걸고 일부러 넘긴다

목적cgroup의 상한을 넘겼을 때 무슨 일이 일어나는지 직접 본다. 쿠버네티스의 OOMKilled와 같은 사건이다.

docker run --name oomtest --memory=32m alpine:3.22 \
  sh -c "dd if=/dev/zero of=/dev/shm/fill bs=1M count=200"
echo "exit=$?"
  • --memory=32m — cgroup 메모리 상한 32MiB
  • dd ... of=/dev/shm/fill bs=1M count=200 — 공유 메모리에 200MiB를 쓴다. 상한의 6배 이상이라 반드시 넘는다
  • -d를 붙이지 않았으므로 컨테이너가 끝날 때까지 기다린다
실행 결과
exit=137

아무 메시지도 없다. dd는 에러를 출력하지 못했다 — 프로세스가 커널에 의해 즉시 죽었기 때문이다. 남은 단서는 종료 코드 137뿐이고, 이 숫자는 128 + 9, 즉 SIGKILL로 종료됐다는 뜻이다.

docker inspect -f 'ExitCode={{.State.ExitCode}} OOMKilled={{.State.OOMKilled}}' oomtest
docker ps -a --filter name=oomtest --format 'table {{.Names}}\t{{.Status}}'
실행 결과
ExitCode=137 OOMKilled=true NAMES STATUS oomtest Exited (137) Less than a second ago
판정OOMKilled=true. 애플리케이션이 스스로 종료한 것이 아니라 커널이 죽였다는 기록이다.

이 장면을 기억해 둔다. M16(리소스 · QoS · 축출)에서 파드가 같은 방식으로 죽으면 kubectl describe pod의 Last State에 Reason: OOMKilled, Exit Code: 137이 그대로 나온다. 그때 "애플리케이션 로그에 아무것도 없는데 왜 죽었나"라는 질문은 이미 답이 나와 있다 — 로그를 남길 틈 없이 커널이 죽였기 때문이다.

2.6수명 주기 정리

지금까지 쓴 명령을 컨테이너의 상태 전이로 정리한다. 상태를 알면 "왜 docker ps에 안 보이지?" 같은 질문이 사라진다.

명령상태 변화메모
docker create없음 → Created만들기만 하고 실행하지 않는다. 거의 쓰지 않는다
docker run없음 → Runningcreate + start. 이미지가 없으면 pull도 한다
docker stopRunning → ExitedSIGTERM 후 10초 유예, 그다음 SIGKILL
docker startExited → Running같은 컨테이너를 다시 켠다. 안에 쓴 파일도 그대로다
docker restartRunning → Runningstop + start
docker rmExited → 없음컨테이너 계층 — 컨테이너가 쓴 파일이 쌓이는 쓰기 가능 레이어(파일시스템 변경분 한 뭉치, M03에서 정의) — 가 사라진다. 이미지는 남는다

중요한 구분 하나. docker ps는 Running만 보여준다. 종료된 컨테이너까지 보려면 docker ps -a다. 실습을 반복하다 보면 Exited 컨테이너가 쌓여 이름 충돌(name is already in use)이 나는데, 이때 docker ps -a로 확인하고 지우면 된다. 애초에 남기지 않으려면 docker run --rm으로 실행한다 — 종료와 동시에 삭제된다.

2.7일부러 실패시키기

실패 ① — 돌고 있는 컨테이너를 지우려 한다 
docker rm web
실행 결과
Error response from daemon: cannot remove container "web": container is running: stop the container before removing or force remove

도커는 실행 중인 컨테이너를 실수로 지우지 못하게 막는다. 해결은 두 가지이고, 둘의 차이가 중요하다. 단, 여기서는 아직 실행하지 않는다 — web은 바로 아래 실패②와 2.8 체크포인트에서 계속 쓰이므로, 두 명령은 2.9 정리에서 친다.

# 권장 — 정상 종료 후 삭제 (2.9에서 실행)
docker stop web && docker rm web

# 급할 때 — SIGKILL로 즉시 종료 후 삭제
docker rm -f web

docker stop은 먼저 SIGTERM을 보내고 기본 10초를 기다린 뒤에야 SIGKILL한다. 애플리케이션이 처리 중인 요청을 마무리할 기회를 주는 것이다. rm -f는 그 유예가 없다. 실습에서는 어느 쪽이든 상관없지만, 이 유예 시간(그레이스 피리어드) 개념은 쿠버네티스에서 terminationGracePeriodSeconds라는 이름으로 그대로 나온다(M15).

실패 ② — 같은 호스트 포트를 두 번 쓴다

web이 8081을 쓰는 상태에서 하나를 더 띄운다.

docker run -d --name web2 -p 8081:80 nginx:1.29-alpine
실행 결과
docker: Error response from daemon: failed to set up container networking: driver failed programming external connectivity on endpoint web2 (05fc0bd3354b...): Bind for 0.0.0.0:8081 failed: port is already allocated

M01에서 kind가 443에 부딪힌 것과 같은 종류의 실패다. 호스트 포트는 하나의 프로세스만 점유한다. 해결은 다른 포트를 쓰는 것(-p 8082:80)뿐이다.

여기서 한 가지를 짚고 넘어간다. 컨테이너를 여러 개 띄울 때마다 호스트 포트를 손으로 배정하는 이 방식은 서비스가 열 개, 백 개가 되면 관리가 불가능해진다. 쿠버네티스가 서비스와 인그레스라는 추상을 두는 이유가 이것이다(M11 · M12) — 그때는 포트를 사람이 고르지 않는다.

실패한 컨테이너는 Created 상태로 남아 있으므로 지운다: docker rm web2.

2.8체크포인트

다음 모듈로 넘어가기 전 확인

web이 아직 돌고 있는 상태에서 확인한다(실패①의 삭제 명령은 2.9에서 친다).

  • docker ps --filter name=web --format '{{.Status}} {{.Ports}}' → Up으로 시작하고 0.0.0.0:8081->80/tcp가 있다
  • curl -s -o /dev/null -w '%{http_code}\n' http://localhost:8081/ → 200
  • docker exec web ps -o pid,comm | sed -n 2p → 1 nginx
  • test "$(docker inspect -f '{{.State.Pid}}' web)" = "$(docker top web -o pid | sed -n 2p | tr -d ' ')" && echo same → same (안의 PID 1이 밖에서는 inspect의 State.Pid다)
  • docker inspect -f '{{.State.OOMKilled}} {{.State.ExitCode}}' oomtest → true 137
  • docker ps -a --filter name=oomtest --format '{{.Status}}' → Exited (137) … — docker ps에는 없고 -a에만 보인다
  • docker ps -a --filter name=web2 --format '{{.Names}}' → 빈 출력 (실패②의 web2를 지웠다)
  • (이해 확인) -p 8081:80에서 어느 쪽이 호스트 포트인지, 네임스페이스와 cgroup이 각각 무엇을 가르는지 한 문장씩 말한다
이 모듈이 남기는 파일
  • 로컬 이미지 캐시에 nginx:1.29-alpine, alpine:3.22 — M03에서 레이어를 들여다볼 재료
  • 파일 산출물은 없다. 다음 모듈부터 course/labs/apps/에 파일이 쌓인다

2.9정리

# web 은 2.7 실패①에서 미뤄둔 권장 방식으로 — SIGTERM 후 삭제
docker stop web && docker rm web

# 이미 종료된 oomtest, 실패②에서 지우지 않았다면 web2 까지
docker rm -f oomtest web2 2>/dev/null

# 남은 것이 없는지 확인
docker ps -a --filter name=web --filter name=oomtest

docker stop web이 즉시 끝나면 nginx가 SIGTERM(정확히는 이미지에 지정된 SIGQUIT)을 받아 스스로 종료한 것이고, 10초를 꽉 기다렸다면 시그널을 처리하지 못해 SIGKILL로 넘어간 것이다 — 4단계의 PID 1 이야기가 여기서 눈에 보인다. 마지막 명령은 헤더 줄만 남아야 한다.

이미지는 지우지 않는다. M03에서 nginx:1.29-alpine의 레이어 구조를 들여다본다. 디스크가 급하면 docker system df로 사용량을 보고 docker system prune으로 정리할 수 있다 — 다만 prune은 멈춰 있는 컨테이너와 미사용 이미지를 모두 지우므로, 다른 작업용 컨테이너가 있는 사람은 목록을 확인하고 실행한다.
