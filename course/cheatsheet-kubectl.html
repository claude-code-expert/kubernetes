kubectl 치트시트

38개 모듈 본문에서 실제로 실행한 명령만 뽑아 용도별로 다시 묶었다. 실습 순서를 따르지 않으므로 처음부터 읽을 필요가 없다. 손이 멈췄을 때 해당 절만 펴 보는 용도다.

참고 자료kubectl v1.37.0Kubernetes 1.37
2026-09-09 작성 · 플래그는 kubectl v1.37.0의 --help로 확인 · 실습 당일 kubectl version으로 클라이언트 버전을 다시 확인한다

이 문서를 쓰는 법

1. 명령에는 프롬프트 기호가 없다. 블록을 통째로 복사해 붙여넣는다.

2. <꺾쇠>로 감싼 자리는 각자의 이름으로 바꾼다. 그 밖의 값은 그대로 동작한다.

3. 각 절 끝의 모듈 링크는 그 명령을 실행 결과·실패 사례와 함께 다루는 곳이다. 치트시트에는 출력을 싣지 않는다.

1컨텍스트와 네임스페이스

사고의 절반은 여기서 난다. 스테이징을 지운다고 친 명령이 운영에서 돌거나, 아무것도 없다고 당황한 네임스페이스가 사실 default였던 경우다. kubectl은 어느 클러스터의 어느 네임스페이스인지를 매번 묻지 않는다. 그래서 무엇에 붙어 있는지 먼저 확인하는 습관이 명령 자체보다 중요하다.

명령하는 일
kubectl config get-contexts등록된 컨텍스트 목록. *가 붙은 줄이 지금 붙어 있는 곳이다
kubectl config current-context현재 컨텍스트 이름만 한 줄로. 스크립트의 안전장치로 쓴다
kubectl config use-context kind-study컨텍스트 전환. kind가 만드는 이름은 kind-<클러스터명>이다
kubectl config set-context --current --namespace=journal현재 컨텍스트의 기본 네임스페이스 변경. 이후 -n을 생략할 수 있다
kubectl config view --minify현재 컨텍스트에 해당하는 설정만. 클러스터 주소와 네임스페이스를 한눈에 본다
kubectl --context kind-edge get nodes전환하지 않고 이 명령만 다른 클러스터에서. 멀티클러스터에서는 전환보다 안전하다
kubectl get pods -A모든 네임스페이스. --all-namespaces의 축약

set-context --namespace로 기본값을 바꿔 두면 편하지만, 바꿔 놓은 것을 잊는 것이 그다음 사고다. 절충안은 기본값을 건드리지 않고 매 명령에 -n을 붙이는 쪽이다. 이 과정의 문서가 -n journal을 매번 반복해서 적는 이유가 그것이다 — 복사해 붙여넣은 명령이 어디서 실행되든 같은 곳을 가리킨다.

2조회 — get 과 출력 포맷

get은 목록을, describe는 한 오브젝트의 사연을 본다. 문제를 만났을 때 get으로 범위를 좁히고 describe로 파고드는 순서가 굳어야 한다.

명령하는 일
kubectl get pods기본 목록. READY·STATUS·RESTARTS·AGE
kubectl get pods -o wide파드 IP와 어느 노드에 떴는지가 붙는다. 스케줄링과 네트워크를 볼 때 기본값
kubectl get deploy,rs,pods여러 종류를 한 번에. 디플로이먼트 → 레플리카셋 → 파드의 3층 구조가 한 화면에 보인다
kubectl get pod <이름> -o yaml서버가 채운 필드까지 전부. 내가 쓴 것과 기본값이 채운 것의 차이를 볼 때
kubectl get pod <이름> -o kyaml1.37에 들어온 KYAML 출력. 들여쓰기가 모호한 YAML보다 붙여넣기 사고가 적다
kubectl get pods -w변화를 계속 흘려 본다. 롤아웃·스케일 관찰용. Ctrl+C로 끝낸다
kubectl get pods --sort-by=.status.startTime가장 최근에 뜬 파드를 맨 아래로. 재시작 추적에 쓴다
kubectl get pods --show-labels레이블을 컬럼으로. 셀렉터가 안 맞을 때 첫 번째로 칠 명령
kubectl get pvc,pv클레임과 실제 볼륨. Pending이면 스토리지클래스를 본다
kubectl get all -n journal주요 워크로드·서비스. 전부가 아니다 — 아래 15절 참조

3레이블 셀렉터와 필드 셀렉터

쿠버네티스에서 오브젝트를 묶는 것은 이름이 아니라 레이블이다. 서비스가 파드를 찾는 것도, Deployment가 자기 파드를 세는 것도 셀렉터다. 레이블 한 글자가 틀리면 아무 에러 없이 아무것도 선택되지 않는다 — 이 조용한 실패가 이 과정에서 가장 많이 재현하는 고장이다.

표현뜻
-l app=journal-api같음
-l app!=journal-api다름
-l 'env in (dev,stage)'집합 포함. 따옴표가 필요하다
-l 'app=web,tier=front'쉼표는 AND다. OR은 없다
-l 'canary'키가 존재하기만 하면 (값 무관)
-l '!canary'키가 없는 것만
--field-selector status.phase=Running레이블이 아니라 오브젝트 필드로. 지원 필드는 종류마다 다르다
--field-selector spec.nodeName=study-worker특정 노드에 뜬 파드만

셀렉터가 비었을 때 kubectl은 No resources found라고만 한다. 오타인지 정말 없는 것인지 구분하려면 --show-labels로 실제 레이블을 눈으로 확인하는 수밖에 없다.

4진단 — describe · events · logs

파드가 뜨지 않을 때 로그부터 보는 것은 순서가 틀렸다. 컨테이너가 시작조차 못 했다면 로그가 없다. 그때 답이 있는 곳은 이벤트다. 스케줄 실패, 이미지 풀 실패, 볼륨 마운트 실패는 전부 이벤트에 남는다. 로그는 컨테이너가 돌기 시작한 뒤의 이야기다.

이벤트 — 시작 못 한 이유

명령하는 일
kubectl describe pod <이름>스펙·상태·마운트·이벤트를 한 화면에. 이벤트는 맨 아래에 있다
kubectl describe pod <이름> | tail -n 20이벤트만 보려고 뒤를 자른다. 스펙이 길 때 실용적이다
kubectl get events --sort-by=.lastTimestamp네임스페이스 전체 이벤트를 시간순으로. 기본 출력은 시간순이 아니다
kubectl events --for pod/<이름> -w한 오브젝트의 이벤트만 실시간으로. get events보다 읽기 쉽다

이벤트는 기본 한 시간만 보관된다(--event-ttl). 어제 난 사고를 이벤트로 조사할 수는 없다 — 그래서 로그 수집과 감사 로그가 따로 필요하다.

로그 — 돌기 시작한 뒤

명령하는 일
kubectl logs <파드>기본. 컨테이너가 하나일 때만 컨테이너 지정을 생략할 수 있다
kubectl logs <파드> -c <컨테이너>다중 컨테이너 파드에서 하나를 골라. 사이드카를 볼 때
kubectl logs <파드> --previous죽기 직전 인스턴스의 로그. CrashLoopBackOff를 만나면 이것부터 친다
kubectl logs -f <파드>실시간 추적
kubectl logs deploy/journal-api --tail=50 --since=10m디플로이먼트 이름으로. 파드 하나를 골라 붙는다
kubectl logs -l app=journal-api --max-log-requests=10 --prefix레이블로 여러 파드를 한꺼번에. --prefix로 어느 파드인지 표시한다
kubectl logs -f -l app=web --timestamps시각을 붙여 여러 파드의 순서를 맞춘다

--previous가 이 표에서 가장 값이 크다. 재시작한 파드에 그냥 logs를 치면 새로 뜬 인스턴스의 빈 로그가 나온다. 죽은 이유는 이전 인스턴스가 갖고 나갔다.

5컨테이너 안으로 — exec · cp · port-forward · debug

클러스터 안에서만 보이는 것이 있다. 서비스 이름의 DNS 해석, 네트워크 정책이 실제로 막는지, 마운트된 파일의 내용 — 전부 파드 안에서 확인해야 답이 나온다.

명령하는 일
kubectl exec -it <파드> -- sh셸을 붙인다. -- 뒤가 컨테이너 안에서 실행할 명령이다
kubectl exec <파드> -c <컨테이너> -- env일회성 명령. 환경변수가 실제로 주입됐는지 확인
kubectl exec <파드> -- cat /etc/config/app.properties컨피그맵이 마운트된 실제 내용
kubectl cp <파드>:/tmp/heap.hprof ./heap.hprof파드에서 파일을 꺼낸다. 컨테이너에 tar가 있어야 한다
kubectl port-forward svc/journal-api 8080:80로컬 8080을 서비스 80으로. 인그레스 없이 바로 접근한다
kubectl port-forward -n monitoring svc/prometheus 9090포트가 같으면 한 번만 쓴다
kubectl run curlbox --image=alpine:3.22 --restart=Never -- sh -c "sleep infinity"클러스터 안에서 쓸 임시 도구 파드. 태그를 박는다
kubectl run probe --rm -it --image=curlimages/curl:8.19.0 --restart=Never -- sh--rm으로 나가면 지워지는 일회용
kubectl debug -it <파드> --image=alpine:3.22 --target=<컨테이너>돌아가는 파드에 임시 컨테이너를 붙인다. 셸이 없는 distroless 이미지 진단용
kubectl debug node/study-worker -it --image=alpine:3.22노드의 네임스페이스에 붙는 파드. 노드 파일시스템이 /host에 보인다
exec 이 안 될 때 OCI runtime exec failed ... "sh": executable file not found이 나오면 컨테이너에 셸이 없는 것이다. distroless·scratch 기반 이미지가 그렇고, 이는 공격 표면을 줄인 결과지 고장이 아니다. 이미지에 셸을 도로 넣지 말고 kubectl debug --target으로 임시 컨테이너를 붙인다. --profile로 권한 수준을 고를 수 있다 — general(기본) · baseline · restricted · netadmin · sysadmin.

port-forward는 붙어 있는 동안만 산다. 터미널을 닫으면 끊기고, 파드가 재시작하면 그대로 죽는다. 상시 접근에 쓰는 물건이 아니라 지금 이 순간 확인하기 위한 도구다.

6만들기 — 명령형과 선언형

같은 디플로이먼트를 두 가지로 만들 수 있다. create deployment 한 줄로 만드는 것이 명령형, YAML을 써서 apply하는 것이 선언형이다. 배우는 동안에는 명령형이 빠르고, 운영에서는 선언형만 남는다 — 명령형은 무엇을 했는지 기록이 남지 않기 때문이다.

명령형 — 빠르게 만들고 버린다

명령하는 일
kubectl create deployment web --image=nginx:1.29-alpine디플로이먼트 하나
kubectl expose deploy web --port=80 --target-port=8080서비스를 붙인다. 셀렉터는 디플로이먼트에서 자동으로 가져온다
kubectl create ns journal네임스페이스
kubectl scale deploy/web --replicas=5레플리카 수 변경
kubectl autoscale deploy/web --min=2 --max=10 --cpu-percent=50HPA 생성

선언형 — 파일이 정본이다

명령하는 일
kubectl apply -f manifest.yaml없으면 만들고 있으면 맞춘다. 여러 번 실행해도 결과가 같다
kubectl apply -f ./dir/디렉터리 전체. 파일 이름 순서로 적용된다
kubectl apply -k course/labs/k8s/journal/kustomize. kustomization.yaml이 있는 디렉터리를 통째로
kubectl kustomize course/labs/k8s/overlays/dev클러스터에 보내지 않고 렌더 결과만 본다. 오버레이 검증의 기본
kubectl diff -f manifest.yaml적용하면 무엇이 바뀌는지 미리 본다. 운영 클러스터에서 apply 전에 친다
kubectl apply --server-side -f manifest.yaml서버 사이드 어플라이. 필드 소유권을 서버가 추적해 도구 간 충돌을 드러낸다
kubectl apply --dry-run=server -f manifest.yaml어드미션까지 태워 보고 만들지는 않는다. 정책 위반을 배포 전에 잡는다

둘을 잇는 다리 — YAML 뼈대 뽑기

YAML을 처음부터 손으로 쓰지 않는다. 명령형으로 만든 것을 --dry-run=client -o yaml로 뽑아 고치는 쪽이 훨씬 빠르고 오타가 적다.

kubectl create deployment web --image=nginx:1.29-alpine \
  --dry-run=client -o yaml > web-deploy.yaml

표준입력으로 바로 넘길 수도 있다. 문서에서 한 번 쓰고 버릴 매니페스트에 쓴다.

kubectl apply -f - <<'EOF'
apiVersion: v1
kind: Namespace
metadata:
  name: sample
EOF

7고치기 — set · patch · edit

이미 떠 있는 것을 고치는 방법이 셋이다. 셋 다 클러스터의 상태를 바꾸지만 깃에 있는 파일은 바꾸지 않는다. 이 어긋남이 나중에 apply 한 번으로 되돌아가는 사고의 원인이다.

명령하는 일쓰는 곳
kubectl set image deploy/journal-api app=journal-api:v2이미지만 교체롤아웃 관찰 실습. 배포 파이프라인
kubectl set env deploy/web LOG_LEVEL=debug환경변수 추가·변경일시적인 디버깅
kubectl set resources deploy/web --limits=cpu=200m리소스 한계 변경스로틀링 재현
kubectl patch deploy web -p '{"spec":{"replicas":3}}'전략적 병합 패치. 준 필드만 바꾼다스크립트에서 한 필드만
kubectl patch deploy web --type=json -p '[{"op":"remove","path":"/spec/template/spec/nodeSelector"}]'JSON 패치. 삭제는 이쪽이어야 한다필드를 없앨 때
kubectl edit deploy web에디터로 연다. 저장하면 즉시 적용급할 때만
kubectl label pod web tier=front --overwrite레이블 추가·덮어쓰기. --overwrite 없으면 기존 키에 실패한다셀렉터 실험
kubectl label ns journal pod-security.kubernetes.io/enforce=restricted네임스페이스 레이블. PSA는 이걸로 켠다파드 보안 표준
kubectl annotate deploy/web kubernetes.io/change-cause="v2 배포"어노테이션. rollout history의 CHANGE-CAUSE에 나온다배포 이력 남기기

8워크로드 운영 — rollout · scale · wait

배포는 명령이 돌아온 시점에 끝난 것이 아니다. apply는 "원하는 상태를 접수했다"까지고, 실제로 새 파드가 뜨고 준비 상태가 되기까지는 시간이 걸린다. 그 사이를 보는 명령들이다.

명령하는 일
kubectl rollout status deploy/journal-api --timeout=120s롤아웃이 끝날 때까지 블록. 실패하면 0이 아닌 종료 코드 — CI에서 쓸 수 있다
kubectl rollout history deploy/journal-api리비전 목록
kubectl rollout history deploy/journal-api --revision=2그 리비전의 파드 템플릿
kubectl rollout undo deploy/journal-api직전 리비전으로 되돌린다
kubectl rollout undo deploy/journal-api --to-revision=2특정 리비전으로
kubectl rollout restart deploy/journal-api스펙을 바꾸지 않고 파드를 새로 뜨게 한다. 컨피그맵 갱신 반영에 쓴다
kubectl rollout pause deploy/web / resume롤아웃 중단·재개. 여러 필드를 고치는 동안 배포가 여러 번 일어나는 것을 막는다
kubectl scale deploy/web --replicas=00으로 줄여 잠시 끈다. 지우지 않고 멈추는 방법
kubectl wait --for=condition=Available deploy/web --timeout=120s조건 충족까지 대기
kubectl wait --for=condition=Ready pod -l app=web --timeout=60s레이블로 고른 파드 전부가 준비될 때까지
kubectl wait --for=delete pod/<이름> --timeout=60s삭제 완료까지. 정리 스크립트에서 다음 단계와 겹치지 않게 한다
kubectl wait --for=jsonpath='{.status.phase}'=Running pod/<이름>임의 필드로 대기. 조건이 정의되지 않은 커스텀 리소스에 쓴다

rollout restart가 컨피그맵 갱신에 필요한 이유가 있다. 볼륨으로 마운트한 컨피그맵은 값이 바뀌면 파일이 갱신되지만, env로 주입한 값은 프로세스가 시작할 때 한 번 읽히고 끝이다. 컨피그맵을 고쳤는데 앱이 옛 값을 쓰고 있다면 대개 이 차이다.

9설정과 시크릿

시크릿은 암호화가 아니라 base64 인코딩이다. 클러스터에 접근할 수 있으면 누구나 읽는다. 이름이 주는 안심과 실제 보호 수준이 다르다는 것이 이 절의 핵심이다.

명령하는 일
kubectl create configmap app-config --from-literal=LOG_LEVEL=info키·값 하나씩
kubectl create configmap app-config --from-file=./app.properties파일 이름이 키, 내용이 값
kubectl create configmap app-config --from-env-file=./.envKEY=VALUE 줄마다 키가 하나씩
kubectl create secret generic db --from-literal=password=s3cr3t제네릭 시크릿
kubectl create secret docker-registry ghcr --docker-server=ghcr.io --docker-username=<유저> --docker-password=<토큰>프라이빗 레지스트리 인증
kubectl get secret db -o jsonpath='{.data.password}' | base64 -d값을 되읽는다. base64는 보호가 아니다
kubectl create token <서비스어카운트> --duration=1h수명 있는 SA 토큰 발급
kubectl create configmap app-config --from-file=./app.properties --dry-run=client -o yaml | kubectl apply -f -기존 컨피그맵 갱신. create만으로는 이미 있으면 실패한다
낡은 정보 정정 — 서비스어카운트 토큰 검색하면 kubectl get sa <이름> -o jsonpath='{.secrets[0].name}'으로 토큰 시크릿을 찾는 방법이 나온다. 1.24부터 서비스어카운트에 토큰 시크릿이 자동으로 만들어지지 않는다. 이 명령은 빈 값을 돌려주고, 그것을 "권한 문제"로 오해하면서 시간을 버린다. 지금은 kubectl create token으로 필요할 때 수명 있는 토큰을 받는다. 근거: kubernetes.io/docs/concepts/security/service-accounts (2026-09-09 확인)

10노드 운영 — top · cordon · drain · taint

노드를 점검하거나 교체할 때 파드를 먼저 비워야 한다. 순서를 틀리면 파드가 새로 뜨자마자 다시 그 노드로 스케줄된다.

명령하는 일
kubectl top nodes노드별 CPU·메모리 실사용. metrics-server가 있어야 한다
kubectl top pods --containers --sort-by=memory컨테이너 단위로 쪼개 메모리 순 정렬
kubectl describe node study-worker할당량·테인트·조건. Allocated resources 블록이 요청 합계다
kubectl cordon study-worker새 파드를 받지 않게 표시. 기존 파드는 그대로 둔다
kubectl drain study-worker --ignore-daemonsets --delete-emptydir-data --timeout=120scordon + 기존 파드 축출. 데몬셋은 어차피 못 옮기므로 무시해야 진행된다
kubectl uncordon study-worker다시 스케줄 가능하게. 점검이 끝나면 반드시
kubectl taint node study-worker gpu=true:NoSchedule톨러레이션이 없는 파드를 밀어낸다
kubectl taint node study-worker gpu=true:NoSchedule-테인트 제거. 끝의 하이픈이 제거를 뜻한다
kubectl label node study-worker disk=ssd노드 레이블. nodeSelector·어피니티가 이걸 본다

top이 error: Metrics API not available을 낸다면 클러스터에 metrics-server가 없는 것이다. kind에는 기본으로 들어 있지 않고, kubelet 인증서에 IP SAN이 없어 --kubelet-insecure-tls 없이는 파드가 Ready가 되지 않는다.

drain이 진행되지 않고 멈춰 있다면 대개 PodDisruptionBudget이 막고 있는 것이다. 이는 고장이 아니라 PDB가 제 일을 하는 것이다 — 레플리카가 최소 개수뿐이면 축출할 수 없다.

13삭제와 정리

파드를 지웠는데 다시 살아난다면 고장이 아니다. 디플로이먼트가 원하는 상태를 유지하는 것이고, 그것이 바로 이 시스템이 하는 일이다. 지워야 할 것은 파드가 아니라 그것을 만드는 컨트롤러다.

명령하는 일
kubectl delete -f manifest.yaml만든 것과 같은 파일로 지운다. 가장 안전한 정리
kubectl delete -k course/labs/k8s/journal/kustomize로 만든 것을 통째로
kubectl delete deploy journal-api컨트롤러를 지운다. 레플리카셋과 파드가 딸려 사라진다
kubectl delete pods -l app=web레이블로 골라서. 컨트롤러가 있으면 곧바로 새로 뜬다
kubectl delete ns journal네임스페이스 안의 모든 것이 사라진다. 실습 탈출구
kubectl delete pod <이름> --grace-period=0 --force즉시 강제 삭제. 아래 경고 참조
kubectl delete pod <이름> --wait=false삭제 요청만 보내고 기다리지 않는다
--force 는 문제를 옮기는 것이다 --grace-period=0 --force는 kubelet의 확인 없이 API에서 오브젝트만 지운다. 컨테이너는 노드에서 계속 돌고 있을 수 있다. 스테이트풀셋에서는 같은 아이덴티티의 파드가 둘이 되어 데이터를 동시에 쓰는 상태를 만들 수 있다. 파드가 Terminating에서 멈춰 있다면 대개 종료 훅이나 파이널라이저가 원인이므로, 왜 안 끝나는지를 먼저 본다.

네임스페이스가 Terminating에서 멈추면 대개 파이널라이저가 걸린 리소스가 남은 것이다. 무엇이 남았는지는 이렇게 본다.

  | xargs -n1 kubectl get --show-kind --ignore-not-found -n journal

14출력 가공 — jsonpath · custom-columns

치트시트에서 가장 오래 쓰게 되는 절이다. 파드 이름을 눈으로 읽어 복사하는 대신 -o name으로 뽑아 다음 명령에 넘기면, 열 개짜리 작업이 한 줄이 된다.

표현결과

15헷갈리는 것 다섯

apply · create · replace

create는 없을 때만 성공하고 이미 있으면 AlreadyExists로 실패한다. replace는 오브젝트를 통째로 바꾼다 — 파일에 없는 필드는 사라진다. apply는 없으면 만들고 있으면 파일에 적힌 필드만 맞춘다. 반복 실행해도 결과가 같아야 하는 자동화에서는 apply만 쓴다.

파드를 지웠는데 다시 생긴다

디플로이먼트가 파드 수를 유지하고 있다. 지우려면 컨트롤러를 지워야 한다. 반대로 재시작이 목적이라면 파드를 지우는 것도 방법이지만, 의도를 드러내는 쪽은 kubectl rollout restart다.

get all은 전부가 아니다

all은 주요 워크로드와 서비스를 가리키는 별칭일 뿐이다. 컨피그맵·시크릿·PVC·인그레스·네트워크 정책·CRD는 여기에 안 나온다. 지웠다고 생각한 것이 남아 다음 실습을 방해하는 원인이 대개 이것이다. 실제로 무엇이 남았는지는 13절 마지막 명령으로 센다.

-n · -A · --context

-n은 네임스페이스, -A는 모든 네임스페이스, --context는 클러스터 자체가 바뀐다. 앞의 둘을 아무리 정확히 써도 컨텍스트가 틀렸으면 남의 클러스터를 보고 있는 것이다.

Pending 과 CrashLoopBackOff

Pending은 아직 시작하지 않았다는 뜻이고 답은 이벤트에 있다 — 스케줄할 노드가 없거나, 이미지를 못 받거나, PVC가 바인딩되지 않았다. CrashLoopBackOff는 시작했다가 죽기를 반복하는 것이고 답은 logs --previous에 있다. 둘은 보는 곳이 다르다.

이미지 latest 태그노드마다 다른 이미지가 돌 수 있고, 롤백할 지점이 없다태그를 박거나 다이제스트로. M26에서 API 서버가 거부하게 만든다
버전 스큐 kubectl은 API 서버와 마이너 한 칸 차이까지만 지원된다. 1.37 서버에는 1.36~1.38 클라이언트가 안전하다. 사내 클러스터가 1.35인데 로컬 kubectl이 1.37이면 대체로 동작하지만, 새 서브커맨드가 서버에 없는 API를 부르면 그때 깨진다. 사고가 나면 kubectl version부터 확인한다. 근거: kubernetes.io/releases/version-skew-policy (2026-09-09 확인)

17셸 설정

하루에 kubectl을 백 번 친다면 자동완성과 별칭이 오타를 줄인다. 특히 네임스페이스 이름과 파드 접미사는 손으로 칠 값이 아니다.

zsh 자동완성. ~/.zshrc에 넣는다.

source <(kubectl completion zsh)
alias k=kubectl
compdef __start_kubectl k

bash라면 이렇게 한다.

source <(kubectl completion bash)
alias k=kubectl
complete -o default -F __start_kubectl k
설정효과
export KUBE_EDITOR="code --wait"kubectl edit이 쓸 에디터
export KUBECONFIG=~/.kube/config:~/.kube/edge.yaml여러 kubeconfig를 콜론으로 병합. 컨텍스트가 합쳐져 보인다
kubectl --v=6 get pods실제로 어떤 URL을 호출했는지. RBAC 거부의 원인을 찾을 때
kubectl --v=8 get pods요청·응답 본문까지. 시끄럽지만 API 동작을 배울 때 쓸모 있다
kubectl get pods --request-timeout=5s응답 없는 클러스터에서 매달리지 않는다

자동완성을 켜면 kubectl -n <탭>으로 네임스페이스가, kubectl logs <탭>으로 파드 이름이 채워진다. 파드 접미사를 눈으로 옮겨 적다가 한 글자 틀리는 사고가 여기서 사라진다.
