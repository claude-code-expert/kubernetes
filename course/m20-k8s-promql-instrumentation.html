PromQL과 애플리케이션 계측

M19에서 http_server_requests_seconds_count를 질의했을 때 결과가 0건이었다. 앱은 지표를 내놓고 있는데 아무도 가져가지 않는 상태다. 이 모듈에서 그 연결을 만들되, 세 번 실패시키고 세 번 고친다. 그다음 요청률·에러율·지연을 직접 질의하고, 평균 45ms 뒤에 숨은 790ms짜리 요청을 찾아낸다.

핵심 3줄

1. ServiceMonitor의 라벨 세 겹을 하나씩 어긋뜨려 타깃이 에러 없이 조용히 사라지는 세 가지 방식을 재현하고 각각의 진단 경로를 익힌다.

2. 언어가 다른 두 앱에 같은 이름·같은 라벨의 지표를 붙이고, 요청률·에러율·지연을 하나의 질의로 함께 뽑는다.

3. 히스토그램 버킷을 잘못 잡으면 P50이 평균과 25배 어긋나는 것을 재현하고, 경계를 고쳐 실제 값을 되찾는다.

20.1왜 앱은 긁히지 않는가 20.2이론 — 무엇을 재야 하는가 20.3따라하기 ① 라벨 세 겹을 잇는다 20.4따라하기 ② 두 번째 앱에 계측을 붙인다 20.5따라하기 ③ RED 질의를 쓴다 20.6따라하기 ④ 평균 뒤에 숨은 것을 찾는다 20.7일부러 실패시키기 20.8운영 관점 — 계측의 값과 대가 20.9체크포인트와 정리

20.1왜 앱은 긁히지 않는가

M19 10단계에서 두 명령의 결과가 어긋났다. 파드 안에서 /actuator/prometheus를 부르면 274개 계열이 나오는데, 프로메테우스에 http_server_requests_seconds_count를 물으면 0건이었다.

클러스터 구성요소들은 전부 잘 나온다. kubelet도 KSM도 etcd도 나온다. 차이는 하나다 — 그것들의 스크레이프 설정은 차트가 함께 만들어 줬고, 우리 앱의 것은 아무도 만들지 않았다.

이 연결을 만드는 오브젝트가 ServiceMonitor다. 그런데 이것은 만들기는 쉽고 제대로 만들었는지 확인하기가 어렵다. 잘못 만들어도 kubectl apply는 성공하고, 오브젝트는 목록에 보이고, 오퍼레이터 로그에는 아무 말도 없다. 그저 타깃이 생기지 않을 뿐이다.

그래서 이 모듈은 성공 사례를 먼저 보여주지 않는다. 실무에서 실제로 겪는 세 가지 어긋남을 순서대로 만들고, 각각을 어떤 명령으로 진단하는지를 익힌 다음에 연결한다. 그 뒤라야 "왜 안 나오지"를 혼자 풀 수 있다.

20.2이론 — 무엇을 재야 하는가

지표를 붙일 수 있다고 해서 아무거나 붙이면 대시보드가 늘어날 뿐 판단은 늘지 않는다. 책 3.3이 소개하는 세 가지 묶음은 무엇부터 재야 하는가에 대한 답이고, 각각 대상이 다르다.

묶음무엇을대상
USE사용률 · 포화도 · 오류
Utilization · Saturation · Errors		자원 — CPU, 메모리, 디스크, 큐
RED요청률 · 에러율 · 지연

4 골든 시그널지연 · 트래픽 · 오류 · 포화도둘을 합친 것. 구글 SRE 책의 분류
SLO"99%의 요청이 200ms 안에"사용자와의 약속. M21에서 알림의 기준이 된다

USE는 원인 쪽에, RED는 증상 쪽에 가깝다. CPU가 90%인 것(USE)은 문제일 수도 아닐 수도 있지만, P99가 3초인 것(RED)은 사용자가 이미 겪고 있는 일이다. 그래서 알림은 RED에 걸고 원인 규명은 USE로 내려간다 — 이것이 책 3.5가 말하는 계층적 모니터링의 실제 순서다.

M19까지 우리가 가진 것은 전부 USE 쪽이었다. cAdvisor의 CPU·메모리, 노드 익스포터의 디스크. RED는 애플리케이션만 답할 수 있다 — 밖에서는 요청이 성공했는지 실패했는지 알 수 없기 때문이다. 그것이 앱을 계측해야 하는 이유다.

ServiceMonitor — 라벨 세 겹

프로메테우스 오퍼레이터를 쓰는 설치에서는 스크레이프 설정을 직접 쓰지 않는다. ServiceMonitor라는 오브젝트를 만들면 오퍼레이터가 그것을 읽어 설정을 생성한다. 연결이 성립하려면 세 곳의 라벨이 맞아야 한다.

세 겹이 각각 다른 사람의 책임이라는 점이 중요하다. ①은 클러스터에 프로메테우스를 세운 사람이 정했고(release: kps), ②와 ③은 앱을 배포하는 사람이 쓴다. 앱 팀이 ①의 규칙을 모르면 아무리 정확한 ServiceMonitor를 써도 연결되지 않는다.

20.3따라하기 ① 라벨 세 겹을 잇는다

1단계 — 먼저 틀리게 만들어 본다

목적가장 흔한 어긋남을 재현하고, 그것이 얼마나 조용한지 확인한다.

공식 문서 예제를 그대로 옮기면 대개 이런 모습이 된다. release 라벨이 없다.

cat <<'EOF' | kubectl apply -f -

EOF

2단계 — 진단한다

목적로그가 없을 때 어디를 봐야 하는지 순서를 익힌다. 세 명령이면 끝난다.

# ① 프로메테우스가 무엇으로 고르는가
kubectl -n monitoring get prometheus -o jsonpath='{.items[0].spec.serviceMonitorSelector}'

# ② 내 ServiceMonitor 에 그 라벨이 있는가
kubectl -n apps get servicemonitor order-api -o jsonpath='{.metadata.labels}'

# ③ 생성된 스크레이프 설정에 내 앱이 들어갔는가
kubectl -n monitoring get secret prometheus-kps-kube-prometheus-stack-prometheus \
  -o jsonpath='{.data.prometheus\.yaml\.gz}' | base64 -d | gunzip | grep -c 'apps/order-api'
출력
{"matchLabels":{"release":"kps"}} 0
판정①은 release: kps를 요구하는데 ②는 비어 있다(둘째 줄이 빈 줄이다). ③이 0이라는 것은 오퍼레이터가 만든 설정에 이 앱이 아예 없다는 뜻이다. ③은 특히 유용하다 — 오퍼레이터가 최종적으로 무엇을 만들었는지를 직접 보는 명령이라, 라벨 문제든 다른 문제든 여기서 갈린다.

3단계 — 고친다

목적①을 맞추고 연결이 실제로 생기는지 확인한다.

kubectl -n apps label servicemonitor order-api release=kps

판정파드 수만큼 타깃이 생겼다. 타깃은 서비스가 아니라 파드 단위다 — 서비스 뒤에 파드가 둘이면 둘 다 긁는다. 그래야 "3번 파드만 느리다"를 볼 수 있다. IP는 환경마다 다르다.

20.4따라하기 ② 두 번째 앱에 계측을 붙인다

order-api는 Micrometer가 알아서 지표를 만들어 줬다. journal-api에는 그런 것이 없다 — 직접 붙인다. 그러면서 두 앱의 지표 이름을 맞추는 일이 왜 중요한지 보게 된다.

4단계 — prom-client로 계측한다

목적Node 앱에 RED를 낼 수 있는 최소한의 지표를 붙인다.

# package.json 의 dependencies 에 추가
"prom-client": "^15.1.3"

src/server.ts에 넣을 것은 세 덩어리다 — 히스토그램 정의, 라벨 정규화 함수, 미들웨어.

import client from 'prom-client';

// 프로세스·런타임 기본 지표(메모리·GC·이벤트 루프 지연 등)를 등록한다.
client.collectDefaultMetrics();

// 이름과 라벨을 order-api(Micrometer) 와 맞춘다.
// 두 앱의 지표 이름이 다르면 대시보드와 알림 규칙을 앱마다 따로 써야 한다.
const httpDuration = new client.Histogram({
  name: 'http_server_requests_seconds',
  help: 'HTTP 요청 처리 시간(초)',
  labelNames: ['method', 'uri', 'status', 'outcome'] as const,
  buckets: [0.05, 0.1, 0.2, 0.5, 1],
});

// uri 라벨에 실제 경로를 그대로 넣으면 안 된다. /api/entries/123 같은 값이
// 요청마다 새 시계열을 만들어 카디널리티가 폭발한다 (M19 8절).
function normalizeUri(req: Request): string {
  const known = ['/healthz', '/readyz', '/metrics', '/api/entries'];
  return known.includes(req.path) ? req.path : 'other';
}

function outcomeOf(status: number): string {
  if (status < 300) return 'SUCCESS';
  if (status < 400) return 'REDIRECTION';
  if (status < 500) return 'CLIENT_ERROR';
  return 'SERVER_ERROR';
}
const app = express();
app.use(express.json());

// 모든 요청의 소요 시간을 잰다. 라우트보다 먼저 등록해야 전부 잡힌다.
app.use((req: Request, res: Response, next: NextFunction) => {
  const end = httpDuration.startTimer();
  res.on('finish', () => {
    end({
      method: req.method,
      uri: normalizeUri(req),
      status: String(res.statusCode),
      outcome: outcomeOf(res.statusCode),
    });
  });
  next();
});

// 프로메테우스가 긁어 갈 엔드포인트.
// order-api 는 액추에이터가 /actuator/prometheus 로 열지만, 여기서는 직접 연다.
app.get('/metrics', async (_req: Request, res: Response) => {
  res.set('Content-Type', client.register.contentType);
  res.end(await client.register.metrics());
});
선택이유
미들웨어를 라우트보다 먼저나중에 등록하면 그 앞의 라우트가 처리한 요청은 잡히지 않는다
res.on('finish')응답이 끝난 시점에 상태 코드가 확정된다. 요청 시작 시점에는 알 수 없다
normalizeUri경로에 ID가 들어가면 시계열이 무한히 늘어난다. 알려진 경로만 라벨로 쓰고 나머지는 other
선언을 app 위에const는 호이스팅되지 않는다. 미들웨어보다 아래에 두면 요청이 올 때 ReferenceError가 난다
빌드가 한 번 깨진다 package.json에 의존성만 더하고 빌드하면 이렇게 실패한다.

5단계 — 두 앱의 지표를 나란히 본다

목적이름을 맞춘 것이 실제로 맞았는지, 그리고 무엇이 여전히 다른지 확인한다.

kubectl -n journal exec deploy/journal-api -- \
  sh -c 'wget -qO- localhost:8080/metrics | grep "^http_server_requests_seconds_bucket" | head -1'

kubectl -n apps exec deploy/order-api -- \
  sh -c 'curl -s localhost:8080/actuator/prometheus | grep "^http_server_requests_seconds_bucket" | head -1'
출력
http_server_requests_seconds_bucket{le="0.05",method="GET",uri="/healthz",status="200",outcome="SUCCESS"} 1 http_server_requests_seconds_bucket{error="none",exception="none",method="GET",outcome="SUCCESS",status="200",uri="/actuator/health/**",le="0.001"} 16
판정지표 이름과 핵심 라벨 넷(method·uri·status·outcome)이 같다. 덕분에 20.5의 질의 하나가 두 앱을 함께 다룰 수 있다.

다른 점도 둘 있다. Micrometer는 error·exception 라벨을 더 붙이고, 버킷 경계가 다르다(le="0.05" vs le="0.001"). 앞의 것은 무해하지만 뒤의 것은 20.7 실패 ③에서 문제가 된다.

6단계 — ServiceMonitor를 파일로 남긴다

목적3단계에서 kubectl label로 급하게 고친 것을 매니페스트로 옮기고, 두 번째 앱의 것도 함께 쓴다.

course/labs/k8s/monitoring/90-servicemonitors.yaml로 저장한다.

---
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: order-api
  namespace: apps
  labels:
    release: kps                      # ① 이것이 없으면 오퍼레이터가 이 오브젝트를 보지 않는다
spec:
  selector:
    matchLabels:
      app.kubernetes.io/name: order-api   # ② Service 에 붙은 라벨
  namespaceSelector:
    matchNames: [apps]
  endpoints:
    - port: http                      # ③ Service 의 포트 이름
      path: /actuator/prometheus      # 스프링 액추에이터의 경로
      interval: 30s
      scrapeTimeout: 10s
---
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: journal-api
  namespace: journal
  labels:
    release: kps
spec:
  selector:
    matchLabels:
      app: journal-api
  namespaceSelector:
    matchNames: [journal]
  endpoints:
    - port: http
      path: /metrics                  # prom-client 를 직접 붙였으므로 경로가 다르다
      interval: 30s
      scrapeTimeout: 10s
kubectl apply -f course/labs/k8s/monitoring/90-servicemonitors.yaml

20.5따라하기 ③ RED 질의를 쓴다

7단계 — 부하를 만든다

목적정상 요청만으로는 에러율도 지연 분포도 볼 것이 없다. 일부러 느린 요청과 실패를 섞는다.

order-api의 ChaosController가 /api/chaos/slow와 /api/chaos/error를 제공한다. course/labs/scripts/k6-red.js로 저장한다.

export const options = {
  scenarios: {
    // 정상 트래픽 — RED 의 R(요청률)과 D(지연)의 기준선을 만든다
    normal: {
      executor: 'constant-arrival-rate',
      rate: 30, timeUnit: '1s', duration: DURATION,
      preAllocatedVUs: 20, maxVUs: 60, exec: 'normal',
    },
    // 느린 요청 — 히스토그램 꼬리를 만든다. P50 은 그대로인데 P99 만 오른다
    slow: {
      executor: 'constant-arrival-rate',
      rate: 2, timeUnit: '1s', duration: DURATION,
      preAllocatedVUs: 10, maxVUs: 40, exec: 'slow',
    },
    // 에러 — RED 의 E
    errors: {
      executor: 'constant-arrival-rate',
      rate: 3, timeUnit: '1s', duration: DURATION,
      preAllocatedVUs: 5, maxVUs: 20, exec: 'errors',
    },
  },
};

export function normal() {
  http.get(`${ORDER}/api/orders`);
  http.get(`http://localhost:${JOURNAL_PORT}/api/entries`, { headers: { Host: 'journal.local' } });
}
export function slow()   { http.get(`${ORDER}/api/chaos/slow?ms=800`); }
export function errors() { http.get(`${ORDER}/api/chaos/error?rate=0.7`); }
kubectl -n apps port-forward svc/order-api 18082:8080 &

출력 (k6 요약)

판정k6가 보는 것은 클라이언트 관점이다. 여기서는 두 앱의 요청이 섞여 있어 p95가 5.73ms로 나오지만, 서버 쪽에서 앱별로 나눠 보면 전혀 다른 그림이 나온다 — 다음 단계가 그것이다.

8단계 — R · E · D를 각각 뽑는다

목적이름을 맞춰 둔 덕에 질의 하나로 두 앱을 함께 다룰 수 있다는 것을 확인한다.

세 질의 모두 rate()로 시작한다. 카운터는 계속 증가하기만 하므로 그 자체로는 의미가 없고 증가 속도가 의미다.

# R — 초당 요청 수
sum by (job) (rate(http_server_requests_seconds_count[5m]))
출력
job=order-api = 23.35 job=journal-api = 20.82
# E — 5xx 비율
sum by (job) (rate(http_server_requests_seconds_count{status=~"5.."}[5m]))
  / sum by (job) (rate(http_server_requests_seconds_count[5m]))
출력
job=order-api = 0.0594

order-api는 5.94%가 나왔는데 journal-api는 아예 결과가 없다. 값이 0인 것이 아니라 시계열이 없다.

판정분자에 status=~"5.."인 시계열이 하나도 없으면 나눗셈의 결과도 없다. PromQL의 이항 연산은 양쪽에 다 있는 라벨 조합에 대해서만 계산하기 때문이다. 대시보드에서 이 패널이 No data가 되고, 알림 규칙이라면 에러가 없어서 조용한 것인지 규칙이 잘못된 것인지 구분되지 않는다.

빈 결과를 0으로 채우려면 or로 대체 항을 둔다.

sum by (job) (rate(http_server_requests_seconds_count{status=~"5.."}[5m]))
  / sum by (job) (rate(http_server_requests_seconds_count[5m]))
or (sum by (job) (rate(http_server_requests_seconds_count[5m])) * 0)
출력
job=order-api = 0.05979 job=journal-api = 0

뒤쪽 항은 "전체 요청률에 0을 곱한 것"이다. 값은 항상 0이지만 라벨 조합은 살아 있으므로 앞이 비었을 때 자리를 채운다.

# D — 평균 지연
sum by (job) (rate(http_server_requests_seconds_sum[5m]))
  / sum by (job) (rate(http_server_requests_seconds_count[5m]))
출력
job=order-api = 0.045 (45ms) job=journal-api = 0.00103 (1.03ms)
판정세 질의가 나왔다. _count와 _sum은 히스토그램이 자동으로 만들어 주는 짝이고, 둘을 나누면 평균이 된다. 그런데 평균은 위험한 숫자다 — 다음 절에서 그 이유를 본다.

20.6따라하기 ④ 평균 뒤에 숨은 것을 찾는다

8단계에서 order-api의 평균 지연이 45ms로 나왔다. 나쁘지 않아 보인다. 그런데 7단계의 부하에는 800ms짜리 요청이 초당 2건씩 섞여 있었다 — 평균이 그것을 삼켰다.

9단계 — 분위수를 계산한다

목적같은 데이터에서 평균과 P99가 얼마나 다른지 본다.

histogram_quantile(0.50, sum by (job, le) (rate(http_server_requests_seconds_bucket[5m])))
histogram_quantile(0.95, sum by (job, le) (rate(http_server_requests_seconds_bucket[5m])))
histogram_quantile(0.99, sum by (job, le) (rate(http_server_requests_seconds_bucket[5m])))
부분뜻
_bucket히스토그램이 만드는 누적 카운터. le(less than or equal) 라벨이 경계다
sum by (job, le)파드별로 흩어진 버킷을 앱 단위로 합친다. le를 반드시 남겨야 분위수를 계산할 수 있다
histogram_quantile버킷 사이를 선형 보간해 분위수를 추정한다. 정확한 값이 아니라 추정이다
출력 (order-api)
P50 = 0.00059 (0.59ms) P95 = 0.7252 (725ms) P99 = 0.7895 (790ms)
판정절반의 요청은 0.59ms에 끝나는데 상위 1%는 790ms다. 1300배 차이다. 평균 45ms는 두 무리 사이 어디에도 해당하지 않는 숫자였다 — 그런 응답 시간을 겪는 요청은 사실상 없다.

10단계 — 범인을 찾는다

목적"느리다"에서 "무엇이 느린가"로 좁힌다. 집계 축을 바꾸는 것이 전부다.

histogram_quantile(0.99,
  sum by (uri, le) (rate(http_server_requests_seconds_bucket{job="order-api"}[5m])))
출력
uri=/api/chaos/slow = 0.8047 uri=/actuator/prometheus = 0.006739 uri=/actuator/health/** = 0.003423 uri=/api/orders = 0.001389 uri=/api/chaos/error = 0.001274
판정job 대신 uri로 묶었을 뿐인데 범인이 드러났다. /api/chaos/slow가 805ms이고 나머지는 전부 7ms 이하다. 정상 엔드포인트는 멀쩡한데 하나가 전체 P99를 끌어올린 것이고, 앱 단위 평균만 봤다면 "서비스가 좀 느리네" 이상은 알 수 없었다.

이것이 4단계에서 uri를 라벨로 넣은 이유다. 라벨은 나중에 쪼개 볼 축을 미리 정해 두는 일이고, 계측할 때 넣지 않은 축으로는 나중에 쪼갤 수 없다. 반대로 아무 축이나 넣으면 M19 8절의 카디널리티 문제가 온다 — 그 균형이 계측 설계다.

20.7일부러 실패시키기

실패 ① 포트를 숫자로 적으면

Service의 포트가 8080이니 ServiceMonitor에도 8080이라고 쓰는 것이 자연스러워 보인다.

재현 
kubectl -n apps patch servicemonitor order-api --type=json \
  -p='[{"op":"replace","path":"/spec/endpoints/0/port","value":"8080"}]'
출력 (1분 뒤)
servicemonitor.monitoring.coreos.com/order-api patched order-api 타깃: 0 건 / 전체 28 order-api 4m24s <- ServiceMonitor 는 그대로 있다
원인

endpoints[].port는 Service의 포트 이름을 가리킨다. 숫자를 쓰려면 targetPort 필드를 써야 하고, 이름과 숫자는 서로 다른 필드다. 1단계와 같은 방식으로 조용히 사라진다.

고친다 
kubectl -n apps patch servicemonitor order-api --type=json \
  -p='[{"op":"replace","path":"/spec/endpoints/0/port","value":"http"}]'
판정타깃이 2건으로 돌아온다. Service에 포트 이름을 붙이는 습관(M11부터 name: http를 써 온 이유)이 여기서 값을 한다 — 이름이 없으면 ServiceMonitor를 쓸 수 없다.

실패 ② Service의 labels와 selector를 헷갈리면

6단계에서 journal-api의 ServiceMonitor를 app: journal-api로 골랐는데 잡히지 않았다. Service에 그 라벨이 분명히 있어 보였다.

진단 
kubectl -n journal get svc journal-api \
  -o jsonpath='metadata.labels = {.metadata.labels}{"\n"}spec.selector = {.spec.selector}{"\n"}'
출력
metadata.labels = {"app.kubernetes.io/managed-by":"kustomize","app.kubernetes.io/part-of":"journal"} spec.selector = {"app":"journal-api"}
원인

app: journal-api는 spec.selector에 있다. 그것은 "이 서비스가 어느 파드를 묶을까"이고, ServiceMonitor가 보는 것은 metadata.labels — "이 서비스는 누구인가"다. 두 필드가 같은 값을 갖는 경우가 많아 구분이 흐려지는데, M14의 kustomization이 includeSelectors: false로 공통 라벨을 붙이면서 둘이 갈렸다.

고친다

  ...

실패 ③ 버킷 경계를 베껴 오면 분위수가 허수가 된다

4단계에서 journal-api의 버킷을 [0.05, 0.1, 0.2, 0.5, 1]로 잡았다. order-api의 SLO 경계를 그대로 옮긴 값이다. 8단계에서 이 앱의 평균이 1.03ms였는데 분위수를 계산해 보면 이상하다.

재현 
histogram_quantile(0.50, sum by (le) (rate(http_server_requests_seconds_bucket{job="journal-api"}[5m])))
출력
평균 = 1.03 ms P50 = 25.00 ms

평균보다 P50이 25배 크다. 지연 분포가 아무리 이상해도 이런 일은 생기지 않는다. 버킷을 직접 들여다본다.

sum by (le) (rate(http_server_requests_seconds_bucket{job="journal-api"}[5m]))
출력
le= 0.05 20.533/s le= 0.1 20.533/s le= 0.2 20.533/s le= 0.5 20.533/s le= 1.0 20.533/s le= +Inf 20.533/s
원인

모든 버킷의 값이 같다. 누적 히스토그램에서 이것은 전부 첫 버킷 안에 들어갔다는 뜻이다. 가장 작은 경계가 50ms인데 이 앱은 1ms대에서 응답하므로 당연하다.

histogram_quantile은 버킷 사이를 선형 보간한다. 모든 값이 [0, 0.05] 구간에 있으면 P50은 그 구간의 절반인 0.025가 된다. 데이터가 아니라 보간이 만들어 낸 숫자다. 정확히 같은 방식으로 P95도 P99도 전부 가짜가 된다.

고친다 
  // 버킷 경계는 이 앱의 실제 지연 분포에 맞춰야 한다.
  // 처음에는 order-api 의 SLO 경계(50ms~1s)를 그대로 베꼈는데, 이 앱은 1ms 대에서
  // 응답하므로 모든 요청이 첫 버킷에 몰렸다. 그러면 P50 이 [0, 0.05] 구간의
  // 선형 보간값(25ms)으로 나온다 — 평균 1ms 와 25배 차이 나는 허수다.
  buckets: [0.0005, 0.001, 0.0025, 0.005, 0.01, 0.025, 0.05, 0.1, 0.25, 0.5, 1],

다시 빌드·배포하고 부하를 준 뒤 같은 질의를 친다.

출력
le= 0.0005 1.007/s le= 0.001 10.255/s le= 0.0025 21.071/s le= 0.005 21.580/s le= 0.01 21.582/s ... 평균 = 1.15 ms P50 = 1.09 ms P95 = 2.45 ms P99 = 4.88 ms
판정버킷마다 값이 다르다 — 분포가 실제로 담겼다는 뜻이다. P50이 1.09ms로 평균과 맞고, P99가 4.88ms로 꼬리를 보여준다. 같은 앱, 같은 부하인데 숫자가 달라진 것은 재는 자를 바꿨기 때문이다.
경계는 함부로 바꾸지 않는다 버킷 경계를 바꾸면 옛 정의의 시계열이 보존 기간 동안 그대로 남아 새 것과 섞인다. 실제로 바꾼 직후 질의에 옛 경계(le=0.2)가 0.191/s로 잠시 보였다. 그 구간의 그래프는 두 정의가 겹쳐 신뢰할 수 없으므로, 경계는 계측을 설계할 때 정하고 이후에는 되도록 건드리지 않는다. 바꿔야 한다면 대시보드와 알림의 임계값도 함께 재검토한다.

20.8운영 관점 — 계측의 값과 대가

M19에서 시계열이 84,771개였다. 두 앱을 계측한 뒤를 다시 센다.

M19 (계측 전)M20 (계측 후)버킷 조정 후
전체 시계열84,77187,63087,705
http_server_requests_seconds 계열—712—
order-api 버킷 시계열—592592
journal-api 버킷 시계열—72144

앱 둘을 계측한 대가가 시계열 약 3,000개다. 눈여겨볼 것은 두 앱의 차이다. order-api가 journal-api의 네 배에서 여덟 배인데, 이유는 두 가지다 — Micrometer의 기본 지수 버킷이 훨씬 촘촘하고, error·exception 라벨이 곱해진다.

그리고 실패 ③에서 경계를 6개에서 12개로 늘리자 journal-api의 버킷 시계열이 정확히 두 배가 됐다(72 → 144). 버킷 하나가 시계열 하나다. 분위수의 정확도와 저장 비용이 정비례한다는 뜻이고, 그래서 "P99를 봐야 하는 지표"에만 히스토그램을 켜는 것이 원칙이다.

어느 지표에 히스토그램을 켤 것인가

기준은 그 값의 분포를 봐야 판단이 달라지는가다. 요청 처리 시간은 그렇다 — 평균만으로는 20.6에서 본 것처럼 사용자가 겪는 것을 못 본다. 반면 "현재 활성 커넥션 수"는 게이지 하나로 충분하고, 분포를 나눠 봐도 할 수 있는 일이 없다.

비용을 줄이는 방법도 있다. Micrometer라면 특정 URI에만 히스토그램을 켜거나, 프로메테우스 쪽에서 metricRelabelings로 필요 없는 버킷을 버릴 수 있다. 다만 버린 것은 나중에 되살릴 수 없으므로, 지우기 전에 정말 안 볼 것인지를 확인한다.

평균을 대시보드에 두지 않는다

20.6의 결과를 다시 보면 order-api의 평균 45ms는 어떤 요청도 겪지 않은 값이었다. 절반은 0.59ms, 상위 1%는 790ms다. 평균은 이 둘을 섞어 아무도 경험하지 않는 숫자를 만든다.

그래서 지연은 P50·P95·P99를 함께 본다. P50은 "보통의 경험", P95·P99는 "나쁜 경험"이고, 둘 사이가 벌어지는 것 자체가 신호다. 20.6에서 P50과 P99가 1300배 차이 났을 때 이미 두 종류의 요청이 섞여 있다는 것을 알 수 있었고, uri로 쪼개니 실제로 그랬다.

이름 규약이 왜 규약인가

4단계에서 journal-api의 지표 이름을 order-api에 맞춘 덕에 8단계의 질의 하나가 두 앱을 함께 다뤘다. 맞추지 않았다면 대시보드 패널을 앱마다 따로 만들고, 알림 규칙도 따로 쓰고, 앱이 하나 늘 때마다 그 일을 반복해야 한다.

정하는 쪽이 프레임워크일 때는 그것을 따르는 편이 쉽다. Micrometer가 http_server_requests_seconds를 쓰므로 Node 앱을 거기 맞췄다. 반대로 했다면 Spring 쪽 이름을 전부 바꾸는 설정을 써야 했을 것이다. 규약은 다수가 이미 쓰는 것을 고르는 편이 유지 비용이 낮다.

20.9체크포인트와 정리

다음 모듈로 넘어가기 전 확인
  • kubectl get servicemonitor -A -l release=kps --no-headers | grep -cE 'order-api|journal-api' → 2
  • kubectl -n journal get svc journal-api -o jsonpath='{.metadata.labels.app}' → journal-api
  • port-forward 후 타깃 집계 → down이 0이고 앱 타깃(/metrics·/actuator/prometheus)이 5건
  • 질의 sum by (job) (rate(http_server_requests_seconds_count[5m])) → order-api와 journal-api 두 줄
  • 질의 histogram_quantile(0.99, sum by (job, le) (rate(http_server_requests_seconds_bucket[5m]))) → 두 줄, 값이 나온다
  • 질의 histogram_quantile(0.50, sum by (le) (rate(http_server_requests_seconds_bucket{job="journal-api"}[5m]))) → 0.01 미만 (버킷을 고쳤다면 평균과 비슷하게 나온다)
  • 질의 count({__name__="http_server_requests_seconds_bucket",job="journal-api"}) → 144 안팎
  • kubectl -n journal exec deploy/journal-api -- sh -c 'wget -qO- localhost:8080/metrics | grep -c "^[a-z]"' → 90 이상
  • pgrep -f 'k6-red' || echo none → none
  • pgrep -f 'port-forward.*18082' || echo none → none
  • (이해 확인) 5xx가 한 건도 없는 앱의 에러율 질의가 0이 아니라 결과 없음인 이유를 적어 본다
  • (이해 확인) 평균 45ms · P50 0.59ms · P99 790ms가 동시에 나올 수 있는 이유를 적어 본다
이 모듈이 남기는 파일
  • course/labs/k8s/monitoring/90-servicemonitors.yaml — 두 앱의 스크레이프 등록. M21의 알림 규칙이 여기서 들어온 지표를 쓴다
  • course/labs/scripts/k6-red.js — 정상·지연·에러가 섞인 부하. M21에서 알림을 발화시키는 데 그대로 쓴다
  • course/labs/apps/journal-api/src/server.ts · package.json · package-lock.json — prom-client 계측 추가
  • course/labs/k8s/journal/30-journal-api.yaml — Service에 app: journal-api 라벨 추가
  • 클러스터: 타깃 33개 전부 up. 두 앱의 RED 지표가 3일치 쌓이기 시작했다

관측 스택과 두 앱은 지우지 않는다. M21이 이 지표 위에 대시보드와 알림을 얹는다. 프로메테우스가 계속 3일치를 쌓고 있으므로, 며칠 뒤 실습을 재개해도 이 모듈에서 만든 부하의 흔적을 그래프로 되짚을 수 있다 — M19에서 세운 기록층이 이제 실제로 일하기 시작했다.

다음 모듈

지금은 질의를 칠 때만 값을 본다. 아무도 터미널을 보고 있지 않을 때 P99가 3초가 되면 그 사실을 알 방법이 없다. M21에서 두 가지를 만든다 — 늘 켜 두고 볼 수 있는 대시보드와, 사람을 부르는 알림이다. 대시보드는 M19 13단계에서 본 사이드카 방식으로 ConfigMap에 코드로 담고, 알림은 이 모듈에서 쓴 RED 질의를 임계값과 함께 PrometheusRule로 옮긴다. 그리고 ChaosController로 실제 지연과 에러를 만들어 pending → firing → resolved 상태 전이를 직접 관찰한다.
