핵심 3줄

1. 자주 바뀌는 것을 뒤에 둔다. 의존성 파일을 먼저 복사하고 소스를 나중에 복사하면 소스만 고쳤을 때 npm ci가 캐시로 넘어간다.

2. 멀티스테이지로 빌드 도구를 최종 이미지에서 뺀다. 컴파일러와 개발 의존성은 실행에 필요 없다.

3. 이미지 크기는 두 숫자다 — 디스크 사용량과 내려받는 크기. 파드가 뜰 때마다 네트워크로 오는 것은 후자다.

4.1왜 이미지 크기가 운영 문제인가

M03까지는 남이 만든 이미지만 다뤘다. 레이어를 읽는 법은 배웠지만 만드는 법은 아니었고, 유일하게 직접 만든 docker commit 이미지는 무엇이 들었는지 아무도 재현할 수 없었다. 이제 Dockerfile로 직접 만든다 — 그리고 처음 쓰는 Dockerfile이 왜 1.68GB짜리 이미지를 내놓는지부터 본다.

노트북에서는 이미지가 1.6GB든 200MB든 체감 차이가 없다. 한 번 받으면 캐시에 남기 때문이다. 문제는 클러스터에서 시작된다. 파드가 새 노드에 스케줄되면 그 노드는 이미지를 처음부터 받는다. 오토스케일링으로 노드가 늘어날 때, 롤아웃으로 파드가 전 노드에 재배치될 때, 노드가 죽어 파드가 옮겨갈 때마다 반복된다. 이미지가 400MB면 노드 10개에 배포할 때 4GB가 레지스트리에서 나가고, 그동안 파드는 ContainerCreating에 머문다. 장애 대응 중 롤백이 3분 걸리는 이유가 대개 이것이다.

크기는 보안 문제이기도 하다. 최종 이미지에 컴파일러 · 패키지 관리자 · 셸이 남아 있으면 공격자가 컨테이너에 침입했을 때 쓸 도구가 그만큼 많다. M24에서 readOnlyRootFilesystem과 넌루트를 다룰 때, 그리고 M07에서 취약점을 스캔할 때 이 선택의 결과를 숫자로 보게 된다.

4.2실습 대상과 기준선 — 저널 API를 순진하게 빌드한다

이 과정 전체에서 배포할 애플리케이션이다. 책 1장의 저널 서비스를 최소 형태로 옮긴 것으로, 엔트리를 추가·조회하는 REST API다. 레디스가 있으면 레디스에, 없으면 메모리에 저장한다 — M14에서 레디스와 함께 배포한다.

const server = app.listen(PORT, () => {

connectRedis().catch((e) => log('error', 'redis connect failed', { detail: String(e) }));

// SIGTERM 을 처리하지 않으면 PID 1 은 종료 신호를 무시한다 (M02 · M15).

1단계. 가장 흔한 형태로 써서 기준선을 만든다

목적개선 전의 기준선을 만든다. 이 형태가 왜 문제인지는 숫자로 확인한다.

# Dockerfile.naive — 흔히 처음 쓰는 형태
FROM node:22
WORKDIR /app
COPY . .
RUN npm install && npm run build
EXPOSE 8080
CMD ["node", "dist/server.js"]
지시어하는 일
FROM베이스 이미지. 여기서 시작해 레이어를 쌓는다
WORKDIR이후 명령의 작업 디렉터리. 없으면 만든다. RUN cd /app과 달리 다음 지시어까지 유지된다

2단계. 크기를 확인한다

목적개선 전 숫자를 적어 둔다. 4.4절의 결과와 비교할 기준이다.

docker images journal-api
실행 결과
WARNING: This output is designed for human readability. For machine-readable output, please use --format. IMAGE ID DISK USAGE CONTENT SIZE EXTRA journal-api:naive e8278a4826ef 1.68GB 413MB

두 숫자를 구분해서 읽는다. DISK USAGE는 로컬 디스크에 풀어놓은 크기, CONTENT SIZE는 레지스트리에서 압축된 상태로 오가는 크기다. 노드가 이미지를 받을 때 네트워크로 흐르는 양은 413MB 쪽이다. ID는 빌드마다 다르다.

판정DISK USAGE 1.68GB, CONTENT SIZE 413MB. 애플리케이션 소스는 3KB도 안 된다. 나머지가 전부 베이스 이미지와 의존성이다.

4.3이론 — 빌드 캐시가 깨지는 지점

책 5.4가 컨테이너 빌드에서 요구하는 것은 두 가지다 — 빌드가 빠르게 반복되어야 하고, 최종 이미지에는 실행에 필요한 것만 남아야 한다. 앞의 것은 캐시, 뒤의 것은 멀티스테이지의 문제다.

BuildKit(도커의 빌드 엔진)은 지시어마다 캐시를 확인한다. RUN은 명령 문자열이 같으면 캐시를 쓴다. 명령이 실제로 무엇을 하는지는 보지 않기 때문에 RUN apt-get update는 몇 달 전 캐시를 그대로 쓸 수 있다. COPY와 ADD는 반대로 복사할 파일 내용을 본다 — 한 글자라도 바뀌면 캐시가 깨진다. 그리고 한 지시어의 캐시가 깨지면 그 아래 전부가 다시 실행된다. 이 마지막 규칙이 핵심이다.

Dockerfile.naive는 COPY . .가 RUN npm install보다 위에 있다. 소스 파일을 한 글자 고치면 COPY 캐시가 깨지고, 그 아래 npm install이 통째로 다시 돈다. 의존성은 하나도 안 바뀌었는데도 그렇다. 고치는 방법은 변경 빈도 순으로 정렬하는 것이다. 거의 안 바뀌는 것(베이스 이미지, 의존성 목록)을 위에, 매번 바뀌는 것(소스)을 아래에 둔다.

한 가지 예외를 미리 알아둔다. ARG · ENV · EXPOSE · CMD 같은 지시어는 파일시스템 레이어를 만들지 않고 이미지 설정(config)에만 기록된다. 그래서 환경 변수 값을 바꿔도 그 아래 COPY의 캐시는 깨지지 않는다 — 4.5절에서 직접 본다.

멀티스테이지 빌드

멀티스테이지 (Multi-stage)는 한 Dockerfile에 FROM을 여러 개 쓰는 방식이다. 앞 스테이지에서 컴파일하고, 마지막 스테이지에서 결과물만 가져온다. 앞 스테이지의 컴파일러 · 소스 · 개발 의존성은 최종 이미지에 남지 않는다.

베이스 선택크기대가
node:22 (데비안 풀)가장 크다없음. 디버깅 도구가 다 있다
node:22-alpine훨씬 작다musl libc — 네이티브 모듈이 드물게 깨진다. 검증 필요
node:22-slim중간데비안 기반이라 호환성 문제가 적다
distroless가장 작다셸이 없다. kubectl exec로 들어가 ls도 못 친다. 디버깅은 에페메랄 컨테이너로만(M24)

이 과정은 알파인을 쓴다. 셸이 남아 있어 실습 중 컨테이너 안을 들여다볼 수 있고, 크기도 충분히 작다. 프로덕션에서 distroless를 쓸지는 팀의 디버깅 관행에 달린 문제이지 크기만으로 정할 일이 아니다.

4.4따라하기 ① 멀티스테이지로 다시 쓴다

3단계. 스테이지를 셋으로 나눈다

목적빌드 도구와 개발 의존성을 최종 이미지에서 제거한다.

# Dockerfile — 멀티스테이지 빌드
# 1단계: 의존성 설치와 타입스크립트 컴파일
FROM node:22-alpine AS build
WORKDIR /app
# 의존성 파일만 먼저 복사한다. 소스가 바뀌어도 이 레이어의 캐시는 살아남는다.
COPY package.json package-lock.json* ./
RUN npm ci
COPY tsconfig.json ./
COPY src ./src
RUN npm run build

# 2단계: 런타임 의존성만 다시 설치 (devDependencies 제외)
FROM node:22-alpine AS deps
WORKDIR /app
COPY package.json package-lock.json* ./
RUN npm ci --omit=dev

# 3단계: 실행 이미지 — 소스도 빌드 도구도 없다
FROM node:22-alpine
# 빌드할 때 버전을 새긴다: docker build --build-arg APP_VERSION=v2 ...
ARG APP_VERSION=v1
ENV NODE_ENV=production APP_VERSION=${APP_VERSION}
WORKDIR /app
# 넌루트로 실행한다 (M24 파드 시큐리티의 전제).
USER node
COPY --from=deps  --chown=node:node /app/node_modules ./node_modules
COPY --from=build --chown=node:node /app/dist ./dist
COPY --chown=node:node package.json ./
EXPOSE 8080
CMD ["node", "dist/server.js"]

순진한 쪽과 다른 점을 짚는다. package.json과 락 파일을 먼저 복사하고 npm ci를 돌린 뒤에야 소스를 복사한다 — 소스만 고치면 npm ci는 캐시된다. npm install 대신 npm ci를 쓰는 것은 락 파일을 그대로 따르고 락과 package.json이 어긋나면 실패하기 때문이다. 빌드마다 같은 의존성 트리가 나온다. 스테이지는 셋이다. build는 컴파일용(타입스크립트 포함), deps는 런타임 의존성만(--omit=dev), 마지막 스테이지는 두 곳에서 결과물만 가져온다. USER node로 루트 실행을 피한다 — 노드 공식 이미지에 이미 있는 계정이다.

ARG APP_VERSION과 ENV APP_VERSION 두 줄은 이 과정의 뒤쪽을 위한 장치다. server.ts는 process.env.APP_VERSION ?? 'v1'로 버전을 읽으므로, 소스를 고치지 않고 --build-arg APP_VERSION=v2만 붙이면 v2라고 응답하는 이미지가 나온다. M10 롤아웃과 M15 프로브 실습이 이 v2를 쓰고, course/labs/scripts/rebuild.sh도 같은 플래그로 두 이미지를 만든다.

docker build -t journal-api:v1 .
docker images journal-api
실행 결과
WARNING: This output is designed for human readability. For machine-readable output, please use --format. IMAGE ID DISK USAGE CONTENT SIZE EXTRA journal-api:naive e8278a4826ef 1.68GB 413MB journal-api:v1 a23856a8fe78 246MB 59.3MB
판정디스크 1.68GB → 246MB, 내려받는 크기 413MB → 59.3MB. 배포할 때 오가는 양이 7분의 1이 됐다.

레이어 수도 줄었다. docker image inspect journal-api:v1 -f '{{len .RootFS.Layers}}'는 8, naive는 11이다.

4단계. 실제로 도는지 확인한다

목적작게 만드는 데 성공했지만 동작이 깨졌을 수 있다. 크기를 줄인 뒤에는 반드시 실행해 본다.

docker run -d --name jtest -p 8082:8080 journal-api:v1
sleep 2
curl -s localhost:8082/healthz; echo
curl -s -X POST localhost:8082/api/entries -H 'content-type: application/json' -d '{"text":"first entry"}'; echo
curl -s localhost:8082/api/entries; echo
실행 결과
{"status":"ok","version":"v1","pod":"3c5ec542e9a0"} {"id":"1788596147604"} {"entries":["{\"text\":\"first entry\"}"]}

pod 필드는 프로세스의 HOSTNAME 환경 변수다. 도커는 컨테이너 ID 앞 12자리를 호스트명으로 주므로 이 값은 실행할 때마다 다르다. 쿠버네티스는 여기에 파드 이름을 넣어 주기 때문에, M10에서 요청이 어느 파드로 갔는지 이 필드로 본다. id는 타임스탬프라 역시 매번 다르다.

docker logs jtest | head -3
docker exec jtest id
실행 결과
{"level":"info","msg":"no REDIS_URL, using in-memory store"} {"level":"info","msg":"listening","port":8080,"version":"v1"} uid=1000(node) gid=1000(node) groups=1000(node)
판정API가 응답하고, 로그가 JSON 한 줄로 표준 출력에 나가며, 프로세스가 uid=1000(node) — 루트가 아니다. 세 가지가 M22 로그 수집과 M24 보안 정책의 전제 조건이다.
docker rm -f jtest

4.5따라하기 ② 캐시 동작 비교

5단계. 소스를 한 줄 고치고 두 방식을 다시 빌드한다

목적레이어 순서가 실제로 무엇을 건너뛰게 하는지 눈으로 본다. 소스는 실험이 끝나면 원래대로 되돌린다.

cp src/server.ts /tmp/server.ts.bak            # 되돌릴 사본
echo '// cache test' >> src/server.ts          # 소스 한 줄 변경
docker build --progress=plain -t journal-api:cache-test .
  • --progress=plain — 단계별 로그를 접지 않고 전부 출력한다. CACHED 표시를 보려면 필요하다
실행 결과 (멀티스테이지 — 스테이지 단계 줄만 남겼다)
#7 [build 3/7] COPY package.json package-lock.json* ./ #7 CACHED #8 [build 4/7] RUN npm ci #8 CACHED #9 [build 5/7] COPY tsconfig.json ./ #9 CACHED #10 [build 6/7] COPY src ./src #10 DONE 0.0s #11 [build 7/7] RUN npm run build #11 DONE 1.5s #12 [deps 4/4] RUN npm ci --omit=dev #12 CACHED #13 [stage-2 3/5] COPY --from=deps --chown=node:node /app/node_modules ./node_modules #13 CACHED #14 [stage-2 4/5] COPY --from=build --chown=node:node /app/dist ./dist #14 DONE 0.0s

npm ci 두 개가 모두 CACHED다. 다시 실행된 것은 소스 복사와 컴파일, 그리고 컴파일 결과를 가져오는 COPY뿐이다.

docker build --progress=plain -f Dockerfile.naive -t journal-api:naive2 .
실행 결과 (순진한 쪽)
#6 [2/4] WORKDIR /app #6 CACHED #7 [3/4] COPY . . #7 DONE 0.0s #8 [4/4] RUN npm install && npm run build #8 DONE 2.4s
판정순진한 쪽은 npm install이 다시 돌았다. 의존성은 하나도 바뀌지 않았는데도 그렇다.
mv /tmp/server.ts.bak src/server.ts             # 소스 되돌리기
tail -n 2 src/server.ts                         # 마지막 줄이 }); 이면 원래대로다

이 예제는 의존성이 두 개뿐이라 2.4초에 끝났다. 실제 프로젝트에서 이 자리는 npm ci, ./gradlew build, go mod download, pip install -r requirements.txt이며 1~5분이 걸린다. 하루에 스무 번 빌드하면 순서 하나 때문에 한 시간이 날아간다. CI에서는 이 비용이 그대로 요금이 된다(M29).

6단계. 소스를 건드리지 않고 v2 이미지를 만든다

목적3단계에 넣은 ARG APP_VERSION으로 버전만 다른 이미지를 만들고, 이때 캐시가 어디까지 살아남는지 본다. 이 v2가 M07에서 클러스터에 올라가 M10 롤아웃의 대상이 된다.

docker build --progress=plain --build-arg APP_VERSION=v2 -t journal-api:v2 .
  • --build-arg 이름=값 — Dockerfile의 ARG 기본값을 덮어쓴다. 소스는 그대로다
실행 결과 (스테이지 단계 줄만 남겼다)
#9 [build 4/7] RUN npm ci #9 CACHED #10 [build 7/7] RUN npm run build #10 CACHED #11 [stage-2 3/5] COPY --from=deps --chown=node:node /app/node_modules ./node_modules #11 CACHED #13 [deps 4/4] RUN npm ci --omit=dev #13 CACHED #14 [build 6/7] COPY src ./src #14 CACHED #15 [stage-2 5/5] COPY --chown=node:node package.json ./ #15 CACHED

전부 CACHED다. ARG와 ENV는 레이어가 아니라 이미지 설정에 기록되므로(4.3절) 파일시스템 레이어는 v1과 완전히 같고, 두 이미지는 설정 한 줄만 다르다. 디스크에서도 레이어를 공유한다.

docker run -d --name jtest2 -p 8082:8080 journal-api:v2
sleep 2
curl -s localhost:8082/healthz; echo
docker rm -f jtest2
실행 결과
{"status":"ok","version":"v2","pod":"d319e38b3e2b"}
판정"version":"v2". 소스 파일은 한 글자도 바뀌지 않았다. 이 방식이 실제 CI에서 깃 SHA나 릴리스 번호를 이미지에 새기는 방법이다(M29).

4.6일부러 실패시키기

실패 ① — .dockerignore 없이 빌드 컨텍스트를 통째로 보낸다

COPY . .의 .은 빌드 컨텍스트 전체다. 로컬에서 npm install을 한 번이라도 돌렸다면 node_modules/가 거기 있고, 그것이 통째로 이미지로 들어간다. 로컬에서 만들어진 node_modules는 맥용으로 컴파일된 네이티브 모듈을 포함할 수 있어서, 리눅스 컨테이너 안에서 실행하면 알 수 없는 에러가 난다. .git/이 함께 들어가면 삭제한 파일의 이력과 커밋에 섞여 들어간 자격 증명까지 이미지에 실린다.

막는 방법은 .dockerignore다.

# course/labs/apps/journal-api/.dockerignore
node_modules
dist
npm-debug.log
.git
.gitignore
Dockerfile*
.dockerignore
*.md

확인은 빌드 로그의 [internal] load build context 단계에 찍히는 전송량으로 한다. 지금 작업 디렉터리에는 node_modules가 없으므로 먼저 컨테이너 안에서 하나 만든다(로컬에 Node.js가 없어도 된다). 그 뒤 .dockerignore를 잠깐 다른 이름으로 바꾸고 Dockerfile.naive로 빌드한다 — COPY . .를 쓰는 쪽이라야 컨텍스트 전체가 전송된다.

docker run --rm -v "$PWD":/app -w /app node:22-alpine npm ci
du -sh node_modules

mv .dockerignore .dockerignore.off
docker build --progress=plain -f Dockerfile.naive -t journal-api:fat . 2>&1 | grep -A2 'load build context'
mv .dockerignore.off .dockerignore
실행 결과 (.dockerignore 없음)
41M node_modules #5 [internal] load build context #5 transferring context: 33.05MB 0.3s done #5 DONE 0.3s
docker build --progress=plain -f Dockerfile.naive -t journal-api:naive . 2>&1 | grep -A2 'load build context'
실행 결과 (.dockerignore 있음)
#5 [internal] load build context #5 transferring context: 161B 0.0s done #5 DONE 0.0s
판정33.05MB 대 161B. 같은 디렉터리, 같은 Dockerfile인데 .dockerignore 한 파일이 전송량을 20만 배 갈랐다. journal-api:fat 안에는 맥에서 만든 node_modules가 그대로 들어가 있다.

한 가지 더 확인할 것이 있다. 같은 실험을 멀티스테이지 Dockerfile로 하면 .dockerignore가 있든 없든 161B가 나온다. BuildKit은 Dockerfile의 COPY가 실제로 가리키는 경로만 전송하기 때문이다. 그래서 COPY . .를 안 쓰면 안전하다고 생각하기 쉬운데, .dockerignore는 그래도 둔다 — Dockerfile은 바뀌고, 누군가 편의로 COPY . .를 넣는 날 이 파일이 사고를 막는다. 실험이 끝났으면 rm -rf node_modules로 지워도 된다. 이미지 빌드에는 필요 없다.

실패 ② — 락 파일 없이 npm ci를 쓴다

npm ci는 락 파일을 요구한다. 락 파일을 잠깐 치우고 빌드해 본다.

mv package-lock.json /tmp/package-lock.json.bak
docker build -t journal-api:nolock .
mv /tmp/package-lock.json.bak package-lock.json
실행 결과 (핵심 줄만)
#8 0.297 npm error code EUSAGE #8 0.297 npm error #8 0.297 npm error The `npm ci` command can only install with an existing package-lock.json or #8 0.297 npm error npm-shrinkwrap.json with lockfileVersion >= 1. Run an install with npm@5 or #8 0.297 npm error later to generate a package-lock.json file, then try again. ... #8 ERROR: process "/bin/sh -c npm ci --omit=dev" did not complete successfully: exit code: 1 ------ Dockerfile:16 -------------------- 16 | >>> RUN npm ci --omit=dev -------------------- ERROR: failed to build: failed to solve: process "/bin/sh -c npm ci --omit=dev" did not complete successfully: exit code: 1

COPY package.json package-lock.json* ./의 * 덕에 복사 단계는 통과하고, npm ci에서 멈춘다. build와 deps 두 스테이지가 병렬로 돌기 때문에 어느 쪽의 npm ci가 먼저 에러를 내는지는 실행마다 다르다 — 위에서는 deps(Dockerfile:16)였다.

판정npm error The `npm ci` command can only install with an existing package-lock.json이 보이고 이미지가 만들어지지 않는다. 락 파일을 되돌린 뒤 docker build -t journal-api:v1 .이 다시 전부 CACHED로 끝나면 복구된 것이다.

고치는 방법은 락 파일을 만들어 저장소에 커밋하는 것이다. 로컬 노드 버전이 프로젝트와 다르거나 아예 설치돼 있지 않다면 컨테이너 안에서 만들면 된다 — 이 저장소의 락 파일도 그렇게 만들었다.

docker run --rm -v "$PWD":/app -w /app node:22-alpine npm install --package-lock-only

여기서 npm install을 쓰면 락 파일이 없어도 빌드는 되지만, 그날그날 다른 버전이 설치돼 어제 통과한 테스트가 오늘 실패하는 상황이 생긴다. 재현 가능한 빌드는 락 파일에서 시작한다.

4.7운영 관점 — 멀티 아키텍처 빌드

애플 실리콘 맥에서 빌드한 이미지는 arm64다. 클러스터 노드가 amd64면 파드가 뜨지 않는다.

이 상황에서 나오는 메시지
exec /app/entrypoint: exec format error

M01의 kind 노드는 맥과 같은 아키텍처라 이 문제가 드러나지 않는다. 사내 클러스터나 클라우드에 올릴 때 처음 만난다. 지금 만든 이미지가 어느 아키텍처인지는 바로 확인할 수 있다.

docker image inspect journal-api:v1 -f '{{.Os}}/{{.Architecture}}'
실행 결과
linux/arm64

인텔 맥이나 리눅스라면 linux/amd64다. 한 이미지 이름으로 두 아키텍처를 담으려면 buildx로 두 플랫폼을 동시에 빌드해 레지스트리로 푸시한다. 이 절의 명령은 여기서 실행하지 않는다 — 푸시할 레지스트리가 아직 없다. M07에서 로컬 레지스트리 localhost:5001을 세운 뒤에 돌아와서 해 볼 수 있고, 그때의 명령은 이 모양이다.

# M07 이후에 실행한다. 빌더를 하나 만들고 사용 (최초 1회)
docker buildx create --name multi --use

# 두 아키텍처를 동시에 빌드해 로컬 레지스트리로 푸시
docker buildx build --platform linux/amd64,linux/arm64 \
  -t localhost:5001/journal-api:v1-multi --push .

--push가 필요한 이유가 있다. 여러 아키텍처를 묶은 매니페스트 리스트 (Manifest List)는 로컬 이미지 저장소에 그대로 담기 어려워, 레지스트리로 바로 올리는 것이 표준 흐름이다. 다른 아키텍처 쪽은 QEMU 에뮬레이션으로 빌드되므로 네이티브보다 몇 배 느리다 — CI에서 멀티 아키텍처 빌드가 유독 오래 걸리는 이유다.

4.8체크포인트와 정리

다음 모듈로 넘어가기 전 확인
  • docker images journal-api --format '{{.Repository}}:{{.Tag}} {{.Size}}' → journal-api:v1 246MB와 journal-api:v2 246MB 두 줄이 있다
  • docker run -d --name jcheck -p 8082:8080 journal-api:v1 && sleep 2 && curl -s -o /dev/null -w '%{http_code}\n' localhost:8082/healthz → 200
  • docker exec jcheck id -u → 1000 (확인 뒤 docker rm -f jcheck)
  • docker run --rm journal-api:v2 node -e 'console.log(process.env.APP_VERSION)' → v2
  • docker build --progress=plain -t journal-api:v1 . 2>&1 | grep -A1 'RUN npm ci$' → 다음 줄이 CACHED
  • ls package-lock.json src/server.ts → 두 파일 모두 있고, tail -n 1 src/server.ts가 }); — 4.5절의 사본 되돌리기가 끝났다
  • (이해 확인) DISK USAGE와 CONTENT SIZE 중 노드가 이미지를 받을 때 네트워크로 흐르는 쪽은 어느 것인가
  • (이해 확인) .dockerignore가 막는 사고 두 가지 — 맥용 node_modules와 .git의 이력
이 모듈이 남기는 파일
  • course/labs/apps/journal-api/ — 소스 · Dockerfile(ARG APP_VERSION 포함) · Dockerfile.naive · .dockerignore · 락 파일. 소스는 4.5절 실험 전과 같다
  • 로컬 이미지 journal-api:v1 — M05 · M06 · M07에서 계속 쓴다. M07에서 레지스트리로 올리고 kind 클러스터에 적재한다
  • 로컬 이미지 journal-api:v2 — --build-arg APP_VERSION=v2로 만든 것. M07에서 함께 적재하고 M10 롤아웃 · M15 프로브 실습의 입력이 된다

v1과 v2는 지우지 않는다. 다음 모듈이 v1을 그대로 쓴다. 실험용으로 만든 이미지는 지운다.

docker rmi journal-api:naive journal-api:naive2 journal-api:cache-test journal-api:fat

journal-api:nolock은 빌드가 실패했으므로 만들어지지 않았다. 4.6절에서 만든 node_modules/를 지우지 않았다면 rm -rf node_modules.
