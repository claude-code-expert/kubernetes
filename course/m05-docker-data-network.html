데이터와 네트워크

컨테이너를 지우면 안에 쓴 것은 사라진다. 그리고 기본 네트워크에서는 컨테이너끼리 이름으로 부르지 못한다. 두 문제를 볼륨과 사용자 정의 네트워크로 해결하면서, 쿠버네티스의 퍼시스턴트 볼륨과 서비스 디스커버리가 왜 그렇게 생겼는지 미리 본다.

초반50분Docker Engine 29.2.1
2026-09-05 검증 · redis:8.2-alpine · journal-api:v1 (M04 산출물) · 여기 적힌 버전 숫자는 실습 당일 docker version과 각 이미지의 태그 목록에서 다시 확인한다
사전 조건
  • M04 완료 — 로컬에 journal-api:v1 이미지가 있다 (docker images journal-api로 확인)
  • 이 모듈이 새로 받는 이미지: redis:8.2-alpine(5.3절), nginx:1.29-alpine(5.4절), alpine:3.22(5.5절). 미리 받아 두려면 docker pull 세 번

핵심 3줄

1. 컨테이너의 쓰기 레이어는 컨테이너와 함께 죽는다. 살아남아야 하는 데이터는 볼륨에 둔다.

2. 기본 bridge 네트워크에는 이름 해석이 없다. 사용자 정의 네트워크를 만들면 컨테이너 이름이 곧 호스트명이 된다.

3. 이 두 가지가 쿠버네티스에서 PersistentVolumeClaim(M18)과 Service(M11)라는 이름으로 다시 나온다. 원리는 같고 규모만 다르다.

5.1왜 이 두 가지가 같은 모듈인가 5.2이론 — 저장 방식 세 가지 5.3따라하기 ① 데이터를 잃어보고, 살린다 5.4따라하기 ② 바인드 마운트 5.5따라하기 ③ 이름으로 부르기 5.6일부러 실패시키기 5.7쿠버네티스에서는 어떻게 되는가 5.8체크포인트와 정리

5.1왜 이 두 가지가 같은 모듈인가

M04에서 만든 저널 API는 엔트리를 메모리 Map에 담는다. 컨테이너를 재시작하면 전부 사라진다. 실제 서비스라면 저장소가 필요하고, 그 저장소는 별도 컨테이너(레디스)가 된다.

저장소를 분리하는 순간 두 문제가 동시에 생긴다. 레디스의 데이터를 어떻게 살릴 것인가, 그리고 API가 레디스를 어떻게 찾을 것인가. 앞의 것이 볼륨, 뒤의 것이 네트워크다. 두 문제는 한 애플리케이션을 여러 컨테이너로 쪼개는 순간 항상 함께 온다 — 그래서 한 모듈에서 다룬다.

이 모듈이 끝나면 저널 API가 레디스에 데이터를 쓰고, 레디스 컨테이너를 삭제한 뒤 다시 만들어도 그 데이터가 남아 있는 것을 확인한다. M06에서 이 구성을 파일 하나로 묶고, M14에서 같은 구성을 쿠버네티스에 올린다.

5.2이론 — 저장 방식 세 가지

M03에서 본 것처럼 컨테이너는 이미지 레이어 위에 쓰기 가능한 레이어 하나를 얹은 것이다. 그 레이어는 docker rm과 함께 사라진다. 밖에 두는 방법이 셋 있다.

방식실체쓰는 곳주의
볼륨 (Volume)도커가 관리하는 저장 영역. 이름으로 부른다데이터베이스 데이터 등 운영 데이터호스트 경로를 몰라도 된다. 백업은 별도 방법으로
바인드 마운트 (Bind Mount)호스트의 특정 디렉터리를 그대로 연결개발 중 소스 코드, 설정 파일 주입호스트 경로에 의존한다. 다른 사람의 노트북에서 깨진다
tmpfs메모리에만 존재임시 파일, 비밀 값을 디스크에 안 남기고 싶을 때컨테이너가 죽으면 사라진다

고르는 기준은 단순하다. 사라지면 곤란한 데이터는 볼륨, 내 노트북에서만 필요한 연결은 바인드 마운트. 실무에서 사고가 나는 경우는 대개 그 반대로 쓸 때다 — 프로덕션 데이터베이스를 바인드 마운트로 띄웠다가 호스트를 옮기며 데이터를 잃는 식이다.

네트워크

도커는 기본 네트워크 bridge를 하나 갖고 있고, 별다른 지정이 없으면 컨테이너가 여기 붙는다. 이 기본 네트워크에는 내장 DNS가 없다 — 컨테이너 이름으로 상대를 찾을 수 없고 IP를 직접 알아야 한다. 그런데 컨테이너 IP는 재시작할 때마다 바뀐다.

docker network create로 만든 사용자 정의 네트워크는 다르다. 도커의 내장 DNS가 컨테이너 이름을 IP로 풀어준다. 같은 네트워크에 있는 컨테이너끼리 redis1:6379처럼 이름으로 접속할 수 있고, IP가 바뀌어도 이름은 그대로다.

이 구조를 기억해 둔다. 쿠버네티스에서 파드 IP는 훨씬 더 자주 바뀌고(파드는 언제든 죽고 다시 만들어진다), 그래서 Service라는 안정적인 이름과 주소를 앞에 세운다(M11). 문제와 해결 방식이 같다.

5.3따라하기 ① 데이터를 잃어보고, 살린다

1단계. 볼륨 없이 레디스를 띄우고 데이터를 잃는다

목적문제를 먼저 겪는다. 해결책부터 배우면 왜 필요한지 잊는다.

docker run -d --name tmpredis redis:8.2-alpine
docker exec tmpredis redis-cli set gone '{"text":"lost"}'
docker exec tmpredis redis-cli get gone
실행 결과
OK {"text":"lost"}
# 컨테이너를 지우고 같은 명령으로 다시 만든다
docker rm -f tmpredis
docker run -d --name tmpredis redis:8.2-alpine
docker exec tmpredis redis-cli get gone
실행 결과
(빈 줄 — 아무것도 없다)
판정키가 사라졌다. 에러도 경고도 없이 그냥 없다. 컨테이너의 쓰기 레이어와 함께 지워졌기 때문이다.
docker rm -f tmpredis

2단계. 볼륨을 만들고 붙인다

목적같은 실험을 볼륨과 함께 반복해 결과를 비교한다.

docker volume create journal-data
docker volume inspect journal-data
실행 결과
journal-data [ { "CreatedAt": "2026-09-03T12:50:57Z", "Driver": "local", "Labels": null, "Mountpoint": "/var/lib/docker/volumes/journal-data/_data", "Name": "journal-data", "Options": null, "Scope": "local" } ]

Mountpoint는 리눅스 VM 안의 경로다(M02 참조). 맥 터미널에서 그 경로로 cd해도 없다. 볼륨을 쓸 때 호스트 경로를 신경 쓰지 않아도 되는 것이 바인드 마운트와의 차이다. CreatedAt은 환경마다 다르다.

docker run -d --name redis1 -v journal-data:/data redis:8.2-alpine redis-server --save 60 1
sleep 2
docker exec redis1 redis-cli set entry:1 '{"text":"survives"}'
docker exec redis1 redis-cli save
docker exec redis1 redis-cli get entry:1
  • -v journal-data:/data — 볼륨이름:컨테이너경로. 레디스 이미지는 /data에 파일을 쓰도록 만들어져 있다
  • redis-server --save 60 1 — 60초 안에 1개 이상 변경되면 디스크에 저장. 실습에서 즉시 확인하려고 redis-cli save로 한 번 강제 저장한다
실행 결과
OK OK {"text":"survives"}
# 컨테이너를 지우고 같은 볼륨으로 다시 만든다
docker rm -f redis1
docker run -d --name redis1 -v journal-data:/data redis:8.2-alpine
sleep 2
docker exec redis1 redis-cli get entry:1
실행 결과
{"text":"survives"}
판정컨테이너는 새것인데 데이터가 남아 있다. 볼륨은 컨테이너 수명과 무관하게 존재한다.

이 실험의 마지막 문장이 M18의 전부다. 쿠버네티스에서 파드는 훨씬 더 자주 죽고, 그래서 데이터는 파드가 아니라 PersistentVolume에 둔다.

5.4따라하기 ② 바인드 마운트

3단계. 호스트 디렉터리를 컨테이너에 연결한다

목적이미지를 다시 빌드하지 않고 콘텐츠를 바꾸는 개발 루프를 만든다.

mkdir -p /tmp/site
echo '<h1>bind mount from host</h1>' > /tmp/site/index.html

docker run -d --name bindweb -p 8084:80 \
  -v /tmp/site:/usr/share/nginx/html:ro nginx:1.29-alpine
sleep 1
curl -s localhost:8084/
  • -v /tmp/site:/usr/share/nginx/html:ro — 앞이 호스트 절대 경로라는 점이 볼륨과 다르다. 슬래시로 시작하면 바인드 마운트, 이름이면 볼륨이다
  • :ro — 읽기 전용. 컨테이너가 호스트 파일을 고치지 못하게 한다
실행 결과
<h1>bind mount from host</h1>
# 호스트에서 파일을 고치고 다시 요청한다 — 재빌드도 재시작도 없다
echo '<h1>edited on host</h1>' > /tmp/site/index.html
curl -s localhost:8084/
실행 결과
<h1>edited on host</h1>
판정컨테이너를 건드리지 않았는데 응답이 바뀌었다. 같은 디렉터리를 양쪽이 보고 있기 때문이다.

:ro가 실제로 막는지도 확인한다.

docker exec bindweb sh -c 'echo x > /usr/share/nginx/html/test.html'
실행 결과
sh: can't create /usr/share/nginx/html/test.html: Read-only file system

읽기 전용 마운트는 방어의 한 겹이다. 침입한 프로세스가 웹 루트에 파일을 심는 것을 막는다. 쿠버네티스에서 같은 발상이 readOnlyRootFilesystem: true로 나타난다(M24).

docker rm -f bindweb

5.5따라하기 ③ 이름으로 부르기

4단계. 기본 네트워크에서 이름 해석이 안 되는 것을 확인한다

목적사용자 정의 네트워크가 왜 필요한지 먼저 확인한다.

# redis1 은 기본 bridge 에 붙어 있다
docker run --rm alpine:3.22 sh -c "nslookup redis1"
실행 결과
Non-authoritative answer: ** server can't find redis1: NXDOMAIN
판정NXDOMAIN — 그런 이름은 없다. 기본 bridge 네트워크에는 컨테이너 이름을 풀어줄 DNS가 없다.

5단계. 네트워크를 만들고 다시 시도한다

목적사용자 정의 네트워크를 만들고, 레디스를 그 안으로 옮겨 이름이 풀리는지 확인한다. 볼륨은 그대로 붙이므로 데이터는 유지된다.

docker network create journal-net

docker rm -f redis1
docker run -d --name redis1 --network journal-net -v journal-data:/data redis:8.2-alpine

docker run --rm --network journal-net alpine:3.22 sh -c "nslookup redis1"
  • --network journal-net — 컨테이너를 기본 bridge가 아니라 이 네트워크에 붙인다. 같은 네트워크의 컨테이너끼리만 이름으로 서로 보인다
실행 결과
Non-authoritative answer: Name: redis1 Address: 172.21.0.2
판정이름이 IP로 풀렸다. --network journal-net을 붙인 컨테이너끼리만 서로 보인다 — 네트워크가 격리 경계이기도 하다. IP 값은 환경마다 다르다.

6단계. 저널 API를 레디스에 연결한다

목적M04에서 만든 애플리케이션을 실제 저장소에 붙여, 두 컨테이너짜리 시스템을 완성한다.

docker run -d --name app1 --network journal-net \
  -e REDIS_URL=redis://redis1:6379 -p 8083:8080 journal-api:v1
sleep 2
curl -s localhost:8083/readyz; echo
curl -s localhost:8083/api/entries; echo
docker logs app1 | head -3
  • -e REDIS_URL=redis://redis1:6379 — 환경 변수로 설정을 주입한다. 이미지를 다시 빌드하지 않고 접속 대상을 바꿀 수 있다. 이 방식이 쿠버네티스에서 ConfigMap이 된다(M13)
  • 주소에 IP가 아니라 redis1이라는 이름이 들어간 것이 핵심이다
실행 결과
{"status":"ready"} {"entries":["{\"text\":\"survives\"}"]} {"level":"info","msg":"listening","port":8080,"version":"v1"} {"level":"info","msg":"redis connected","url":"redis://redis1:6379"}
판정/readyz가 ready이고, /api/entries에 5.3절에서 넣은 데이터가 그대로 나온다. 그 사이 레디스 컨테이너는 두 번 삭제되고 다시 만들어졌는데도 그렇다 — 볼륨과 이름 기반 연결이 함께 동작한 결과다.
docker network inspect journal-net -f '{{range .Containers}}{{.Name}} {{.IPv4Address}}{{"\n"}}{{end}}'
실행 결과
app1 172.21.0.3/16 redis1 172.21.0.2/16

두 컨테이너가 같은 네트워크의 이웃한 IP를 받았다. 애플리케이션은 이 숫자를 전혀 몰라도 된다.

5.6일부러 실패시키기

실패 ① — 네트워크를 안 맞추고 이름으로 부른다

가장 흔한 실수다. 애플리케이션만 네트워크를 지정하지 않고 띄운다.

docker run -d --name app-bad -e REDIS_URL=redis://redis1:6379 -p 8085:8080 journal-api:v1
sleep 4
curl -s -w ' [http %{http_code}]\n' localhost:8085/readyz
curl -s -w ' [http %{http_code}]\n' localhost:8085/healthz
docker logs app-bad | head -3
  • -w ' [http %{http_code}]\n' — 응답 본문 뒤에 HTTP 상태 코드를 붙여 출력한다. 본문만 보면 200과 503을 구분하기 어렵다
실행 결과
{"status":"not ready","reason":"redis not connected"} [http 503] {"status":"ok","version":"v1","pod":"c8382eaf294d"} [http 200] {"level":"info","msg":"listening","port":8080,"version":"v1"} {"level":"error","msg":"redis error","detail":"Error: getaddrinfo ENOTFOUND redis1"} {"level":"error","msg":"redis error","detail":"Error: getaddrinfo ENOTFOUND redis1"}

app-bad는 기본 bridge에, redis1은 journal-net에 있다. 이름이 풀리지 않아 getaddrinfo ENOTFOUND redis1이 반복된다. pod 값은 컨테이너 ID 앞 12자리라 환경마다 다르다(M04 4.4절).

판정두 엔드포인트의 답이 다르다는 것이 핵심이다. /healthz는 200 — 프로세스는 멀쩡히 살아 있다. /readyz는 503 — 하지만 저장소에 못 붙어서 일을 할 수는 없다.

이 구분이 M15의 주제다. 살아 있음(liveness)과 준비됨(readiness)을 한 신호로 합치면 둘 중 하나가 틀린다. 여기서 라이브니스가 실패하도록 만들었다면 쿠버네티스는 컨테이너를 재시작했을 것이고, 레디스가 돌아올 때까지 무한 재시작에 빠졌을 것이다. 반대로 레디니스만 실패시키면 트래픽에서 빠진 채 조용히 기다리다가 레디스가 살아나는 순간 복귀한다.

해결은 네트워크를 맞추는 것이다. 컨테이너를 지우고 --network를 붙여 다시 만든다.

docker rm -f app-bad
docker run -d --name app-bad --network journal-net \
  -e REDIS_URL=redis://redis1:6379 -p 8085:8080 journal-api:v1
sleep 2
curl -s -w ' [http %{http_code}]\n' localhost:8085/readyz
docker logs app-bad | head -3
실행 결과
{"status":"ready"} [http 200] {"level":"info","msg":"listening","port":8080,"version":"v1"} {"level":"info","msg":"redis connected","url":"redis://redis1:6379"}
판정/readyz가 503 → 200으로 바뀌고, 로그의 ENOTFOUND가 redis connected로 바뀌었다. 이미지도 환경 변수도 그대로다 — 달라진 것은 --network journal-net 하나다.

이미 떠 있는 컨테이너를 지우지 않고 네트워크에 나중에 붙이는 방법도 있다: docker network connect journal-net app-bad. 컨테이너는 여러 네트워크에 동시에 속할 수 있다.

실패 ② — 볼륨이 붙어 있는데 지우려 한다 
docker volume rm journal-data
실행 결과
Error response from daemon: remove journal-data: volume is in use - [bb355b24588d...]

사용 중인 볼륨은 지워지지 않는다. 대괄호 안이 그 볼륨을 쓰는 컨테이너 ID다(환경마다 다르다). docker ps -a --filter volume=journal-data로 확인하고 컨테이너를 먼저 정리한다.

반대 방향의 사고가 더 위험하다. docker compose down -v나 docker system prune --volumes는 확인 없이 볼륨을 지운다. 실습 환경이라 다행이지만, 같은 명령을 데이터가 든 환경에서 치면 되돌릴 방법이 없다. 볼륨을 지우는 명령에는 항상 -v나 --volumes가 들어 있으니 그 플래그를 보면 한 번 멈추는 습관을 들인다.

5.7쿠버네티스에서는 어떻게 되는가

지금 만든 두 컨테이너 구성이 뒤쪽 모듈에서 어떻게 번역되는지 미리 표로 본다. 새로 배우는 개념이 아니라 같은 문제의 큰 버전이라는 것을 알아두면 M11 · M18이 훨씬 가볍다.

도커에서쿠버네티스에서달라지는 점
-v journal-data:/dataPersistentVolumeClaim + 볼륨 마운트 (M18)노드가 여러 대라 "어느 노드에서든 붙을 수 있는가"가 문제가 된다
--network journal-net같은 네임스페이스 — 쿠버네티스에서 리소스를 묶는 논리적 구획으로, M02의 리눅스 커널 네임스페이스와는 이름만 같은 다른 개념이다 (M08). 기본적으로 모두 통신 가능기본이 전부 허용이라 오히려 NetworkPolicy로 막아야 한다 (M25)
redis://redis1:6379redis://redis:6379 — Service 이름 (M11)이름 뒤에 파드가 여러 개 있고 로드밸런싱된다
-e REDIS_URL=...ConfigMap · Secret 주입 (M13)값을 이미지·매니페스트와 분리해 버전 관리한다
-p 8083:8080Service + Ingress/Gateway (M11 · M12)포트를 사람이 고르지 않는다

5.8체크포인트와 정리

다음 모듈로 넘어가기 전 확인
  • docker volume ls --filter name=journal-data --format '{{.Name}}' → journal-data
  • docker exec redis1 redis-cli get entry:1 → {"text":"survives"} — 레디스 컨테이너를 두 번 지우고 다시 만든 뒤에도 남아 있는 값이다
  • docker run --rm --network journal-net alpine:3.22 nslookup redis1 → 출력에 Name: redis1과 그 아래 Address: 172.… 줄이 있다 (IP는 환경마다 다르다)
  • docker run --rm alpine:3.22 nslookup redis1 2>&1 | grep NXDOMAIN → ** server can't find redis1: NXDOMAIN이 한 줄 이상 나온다 (기본 bridge에서는 안 풀린다)
  • curl -s -o /dev/null -w '%{http_code}\n' localhost:8083/readyz → 200 (app1이 redis1에 이름으로 붙어 있다)
  • docker volume rm journal-data → volume is in use 에러 (붙어 있는 컨테이너가 있는 한 지워지지 않는다)
  • (이해 확인) -v /tmp/site:/usr/share/nginx/html과 -v journal-data:/data는 각각 무엇인가 — 슬래시로 시작하면 바인드 마운트, 이름이면 볼륨
  • (이해 확인) 실패 ①에서 /healthz가 200인데 /readyz가 503인 이유
이 모듈이 남기는 파일
  • 볼륨 journal-data(안에 entry:1), 네트워크 journal-net, 컨테이너 redis1 · app1 · app-bad
  • 파일은 없다. 이 구성을 파일로 옮기는 것이 M06이다 — compose.yaml이 여기서 친 네 명령을 대신한다. 지금 상태를 그대로 두고 넘어가도 되고, 아래처럼 정리해도 된다
# 컨테이너만 정리 (볼륨의 데이터는 남는다)
docker rm -f app1 app-bad redis1

# 전부 정리하려면 — 볼륨의 데이터가 사라진다
# docker network rm journal-net
# docker volume rm journal-data
