CRD와 오퍼레이터 구현

여기까지 쓴 것은 전부 쿠버네티스가 이미 아는 리소스였다 — 디플로이먼트·서비스, 그리고 남이 만든 CRD(M30의 Rollout, M31의 Application). 우리 조직에만 있는 개념을 표현하려면 리소스 종류 자체를 새로 만들어야 한다. 이 모듈에서 JournalSite라는 종류를 정의하고, 그것을 지켜보며 실제 리소스를 만드는 조정 루프를 셸로 한 번, Go로 한 번 만든다. 두 번 만드는 이유는 둘의 차이가 컨트롤러의 본질이기 때문이다.

  • M30·M31에서 남이 만든 CRD를 썼다. 이 모듈은 그 안쪽이다
  • Go와 kubebuilder가 있다: brew install go kubebuilder. 확인: go version · kubebuilder version
  • journal-api:v1 이미지가 kind에 적재돼 있다

핵심 3줄

1. CRD를 손으로 써서 스키마 검증·기본값·printer column·status 서브리소스가 각각 무엇을 하는지 거부 메시지로 확인한다.

2. 조정 루프를 셸 스크립트로 만들어 오퍼레이터가 하는 일이 세 단계뿐임을 확인하고, ownerReferences로 삭제가 전파되는 것을 본다.

3. 같은 것을 kubebuilder로 만들어, 폴링과 감시의 차이를 초 단위로 비교한다.

33.1우리 개념을 담을 그릇이 없다 33.2이론 — API 오브젝트와 조정 루프 33.3따라하기 ① CRD를 손으로 쓴다 33.4따라하기 ② 셸로 만드는 조정 루프 33.5따라하기 ③ kubebuilder로 뼈대를 33.6따라하기 ④ 조정 함수를 쓴다 33.7일부러 실패시키기 33.8운영 관점 — 만들 것인가 쓸 것인가 33.9체크포인트와 정리

33.1우리 개념을 담을 그릇이 없다

M28에서 저널 앱 한 벌을 배포하려고 매니페스트 여섯 개를 썼다. 컨피그맵, 시크릿, 스테이트풀셋, 디플로이먼트 둘, HPA, PDB. 그 여섯 개가 함께 있어야 의미가 있는 한 덩어리인데, 쿠버네티스는 그것을 한 덩어리로 보지 않는다.

결과는 몇 가지 불편으로 나타난다. 이 덩어리를 하나의 이름으로 부를 수 없고, 덩어리 전체가 준비됐는지 한 줄로 물어볼 수 없으며, 지울 때 여섯 개를 각각 지워야 한다. 헬름 차트가 이 문제의 절반을 푼다 — 배포 단위를 묶어 준다. 그런데 차트는 클러스터 안에 존재하지 않는다. kubectl get으로 조회할 수 없고, 다른 컨트롤러가 참조할 수도 없다.

남은 방법이 리소스 종류를 새로 만드는 것이다. JournalSite라는 종류를 정의하면 kubectl get journalsites로 목록을 보고, status로 준비 상태를 묻고, 지우면 딸린 것이 함께 사라진다. 이 모듈에서 만들 것이 그것이다.

그리고 이것은 이미 여러 번 써 온 구조다. M30의 Rollout도, M31의 Application도 같은 방식으로 만들어졌다. 그것들이 어떻게 동작하는지가 이 모듈에서 안쪽에서 보인다.

33.2이론 — API 오브젝트와 조정 루프

책 매핑21.1~21.7 API 오브젝트·리소스·그룹·버전·카인드, 조정 루프, 검증, 오퍼레이터 라이프사이클

이름이 네 겹이다

새 리소스를 정의할 때 적어야 하는 이름이 여럿이라 헷갈린다. 각각 다른 것을 가리킨다.

이름예무엇
그룹study.example.com이름 충돌을 막는 네임스페이스. 조직 도메인을 거꾸로 쓴다
버전v1alpha1같은 종류의 다른 스키마. 여러 버전이 동시에 제공될 수 있다
카인드JournalSiteYAML의 kind:에 쓰는 이름. 대문자로 시작한다
리소스journalsitesURL 경로와 kubectl get에 쓰는 복수형

CRD 자체의 이름은 <복수형>.<그룹>으로 강제된다 — journalsites.study.example.com이 아니면 거부당한다. 이 규칙 덕분에 남의 CRD와 절대 겹치지 않는다.

spec과 status는 다른 사람이 쓴다

모든 쿠버네티스 오브젝트의 구조가 같다. spec은 원하는 상태이고 사용자가 쓴다. status는 실제 상태이고 컨트롤러가 쓴다. 이 분리를 CRD에서 subresources: {status: {}}로 선언하면 API가 둘을 다른 엔드포인트로 다룬다.

분리하지 않으면 사고가 난다. 사용자가 kubectl apply로 spec을 바꾸는 순간 컨트롤러가 방금 쓴 status가 지워지고, 컨트롤러가 status를 쓸 때 사용자가 방금 고친 spec을 덮는다. 서브리소스로 나누면 각자 자기 것만 쓴다.

조정 함수가 지켜야 할 세 가지

멱등하다. 같은 입력으로 몇 번을 불러도 결과가 같아야 한다. 컨트롤러는 같은 오브젝트에 대해 조정을 여러 번 부르고, 그 횟수는 보장되지 않는다.

전체를 다시 계산한다. 조정 함수는 "무엇이 바뀌었는지"를 인자로 받지 않는다. 오브젝트 이름만 받고, 현재 상태를 처음부터 읽어 원하는 상태와 비교한다. 이 설계 덕분에 이벤트를 놓쳐도 다음 조정에서 복구된다 — M08에서 본 컨트롤 루프의 성질 그대로다.

빨리 끝난다. 오래 걸리는 일은 나눠서 requeue로 다시 부르게 한다. 조정 함수 안에서 몇 분을 기다리면 그동안 다른 오브젝트가 처리되지 않는다.

소유권이 삭제를 전파한다

ownerReferences는 "이 오브젝트는 저 오브젝트에 딸린 것"이라는 표시다. 부모가 사라지면 가비지 컬렉터가 자식을 지운다 — 컨트롤러가 삭제 로직을 쓰지 않아도 된다. 33.4에서 이것을 확인한다.

삭제 전에 무언가를 해야 한다면(외부 리소스 정리 같은) finalizers를 쓴다. 다만 파이널라이저를 붙인 컨트롤러가 죽으면 오브젝트가 영원히 지워지지 않는 상태가 되므로, 꼭 필요할 때만 쓴다.

33.3따라하기 ① CRD를 손으로 쓴다

생성기를 쓰기 전에 손으로 한 번 쓴다. 33.5에서 마커가 무엇으로 번역되는지 알아보려면 번역 결과를 먼저 알아야 한다.

1단계 — 정의를 만든다

목적스키마·기본값·검증·표시 열·서브리소스를 한 파일에 담는다.

# 핵심만 (전문은 course/labs/k8s/crd/00-journalsite-crd.yaml)
spec:
  group: study.example.com
  names: {plural: journalsites, kind: JournalSite, shortNames: [js]}
  versions:
    - name: v1alpha1
      served: true
      storage: true
      subresources:
        status: {}
      additionalPrinterColumns:
        - {name: Replicas, type: integer, jsonPath: .spec.replicas}
        - {name: Ready,    type: string,  jsonPath: .status.readyReplicas}
        - {name: Phase,    type: string,  jsonPath: .status.phase}
      schema:
        openAPIV3Schema:
          type: object
          properties:
            spec:
              required: [image]
              properties:
                image:
                  type: string
                  pattern: '^[a-z0-9./-]+:[a-zA-Z0-9._-]+$'
                  not: {pattern: ':latest$'}
                replicas: {type: integer, minimum: 1, maximum: 10, default: 2}
                logLevel: {type: string, enum: [debug, info, warn, error], default: info}
필드없으면
subresources.statusspec과 status가 한 엔드포인트라 서로 덮어쓴다
additionalPrinterColumnskubectl get에 NAME과 AGE만 나온다
default쓰지 않은 필드가 없는 채로 저장된다. 컨트롤러가 nil 처리를 해야 한다
served/storage여러 버전을 둘 때 어느 것을 제공하고 어느 것으로 저장할지. 정확히 하나만 storage: true

2단계 — 검증이 실제로 거부하는지 본다

목적스키마가 API 서버에서 걸린다는 것을 확인한다. 컨트롤러는 아직 없다.

kubectl apply -f course/labs/k8s/crd/00-journalsite-crd.yaml
kubectl create ns m33

cat <<'EOF' | kubectl -n m33 apply -f -
apiVersion: study.example.com/v1alpha1
kind: JournalSite
metadata: {name: bad-latest}
spec: {image: "journal-api:latest"}
EOF
출력
The JournalSite "bad-latest" is invalid: <nil>: Invalid value: "": "spec.image" must not validate the schema (not)
판정거부는 됐는데 메시지가 사람에게 쓸모없다. not 키워드는 "이 스키마를 만족하면 안 된다"만 말하고 이유를 담을 자리가 없다. 33.6에서 CEL로 바꾸면 우리가 쓴 문장이 나온다.
# 태그 없음
spec: {image: "journal-api"}
# 범위 초과
spec: {image: "journal-api:v1", replicas: 50}
출력
The JournalSite "bad-notag" is invalid: spec.image: Invalid value: "journal-api": spec.image in body should match '^[a-z0-9./-]+:[a-zA-Z0-9._-]+$' The JournalSite "bad-replicas" is invalid: spec.replicas: Invalid value: 50: spec.replicas in body should be less than or equal to 10
판정이 둘은 메시지가 쓸 만하다. 필드 경로와 실제 값과 어긴 규칙이 다 들어 있다. 검증을 스키마에 두면 컨트롤러가 없어도 잘못된 오브젝트가 저장되지 않는다는 점이 중요하다.

3단계 — 기본값과 표시 열을 확인한다

목적쓰지 않은 필드가 어떻게 되는지 본다.

cat <<'EOF' | kubectl -n m33 apply -f -
apiVersion: study.example.com/v1alpha1
kind: JournalSite
metadata: {name: demo}
spec: {image: "journal-api:v1", replicas: 3}
EOF
kubectl -n m33 get js
kubectl -n m33 get js demo -o jsonpath='{.spec}{"\n"}'
출력
NAME REPLICAS IMAGE READY PHASE AGE demo 3 journal-api:v1 0s {"image":"journal-api:v1","logLevel":"info","replicas":3}
판정logLevel을 쓰지 않았는데 info가 들어 있다 — 기본값이 저장 시점에 채워진다. READY와 PHASE 열은 비어 있다. status를 쓰는 것이 없기 때문이고, 지금 이 오브젝트는 아무 일도 하지 않는 데이터일 뿐이다. 다음 절에서 그것을 움직이는 것을 만든다.

33.4따라하기 ② 셸로 만드는 조정 루프

Go를 쓰기 전에 셸로 한 번 만든다. 오퍼레이터의 개념과 도구를 분리해서 보기 위해서다.

1단계 — 세 단계를 그대로 쓴다

목적조정이 무엇인지 30줄로 확인한다.

# course/labs/scripts/shell-operator.sh 의 뼈대
while true; do
  for NAME in $(kubectl -n "$NS" get journalsites -o jsonpath='{.items[*].metadata.name}'); do
    # ① 원하는 상태
    SPEC=$(kubectl -n "$NS" get js "$NAME" -o json)
    IMAGE=$(...)  WANT=$(...)  OWNER_UID=$(...)

    # ② 차이를 없앤다 — apply 는 그 자체로 멱등하다
    cat <<YAML | kubectl -n "$NS" apply -f - >/dev/null
    ... ownerReferences 에 JournalSite 를 박은 디플로이먼트 ...
YAML

    # ③ status 를 갱신한다 — --subresource=status 가 없으면 spec 을 덮어쓴다
    READY=$(kubectl -n "$NS" get deploy "${NAME}-api" -o jsonpath='{.status.readyReplicas}')
    kubectl -n "$NS" patch js "$NAME" --subresource=status --type=merge -p ...
  done
  sleep "$INTERVAL"
done

진짜 컨트롤러와 다른 점은 성능과 정확성이지 개념이 아니다. watch 대신 폴링, 캐시 없음, 동시성 제어 없음, 재시도 백오프 없음 — 이 넷이 프레임워크가 해 주는 일이다.

--subresource=status를 빼면 패치가 spec에 적용된다. 그러면 스키마 검증에 걸려 거부되거나(운이 좋은 경우), spec에 없는 필드가 조용히 무시된다. 서브리소스를 선언했으면 쓸 때도 명시해야 한다.

2단계 — 돌려 본다

목적데이터였던 오브젝트가 실제 리소스를 만드는 것을 확인한다.

kubectl -n m33 get js,deploy --no-headers
출력

판정READY와 PHASE 열이 채워졌다. 33.3에서 비어 있던 그 열이다 — status를 쓰는 것이 생겼기 때문이다.

3단계 — 세 가지 상황을 만들어 본다

목적조정 루프가 어느 방향의 차이든 없애는지 확인한다.

kubectl -n m33 patch js demo --type=merge -p '{"spec":{"replicas":1}}'   # 원하는 상태가 바뀜
kubectl -n m33 delete deploy demo-api                                    # 실제 상태가 사라짐
kubectl -n m33 delete js demo                                            # 부모가 사라짐
출력 (루프 로그)
01:34:36 demo want=3 ready=3 phase=Ready 01:34:41 demo want=1 ready=1 phase=Ready <- spec 변경 반영 01:34:52 demo want=1 ready=0 phase=Progressing <- 디플로이먼트 삭제 감지 01:34:57 demo want=1 ready=1 phase=Ready <- 재생성
kubectl -n m33 get deploy,po --no-headers
출력 (JournalSite 삭제 후)

판정세 번째가 특히 중요하다. 스크립트에는 삭제 로직이 한 줄도 없다. ownerReferences를 박아 뒀기 때문에 가비지 컬렉터가 알아서 치웠다. 삭제 전파를 직접 구현하려 들면 경합과 누락이 반드시 생긴다 — 쿠버네티스가 제공하는 이 장치를 쓴다.

다만 삭제 감지가 5초 뒤 다음 주기였다는 점을 기억해 둔다. 33.6에서 이 숫자가 바뀐다.

33.5따라하기 ③ kubebuilder로 뼈대를

1단계 — 프로젝트와 API를 만든다

목적손으로 쓸 것과 생성될 것을 나눈다.

mkdir -p /tmp/operator && cd /tmp/operator
kubebuilder init --domain example.com --repo example.com/journalsite-operator
kubebuilder create api --group study --version v1alpha1 --kind JournalSite --resource --controller
ls api/v1alpha1/ internal/controller/
출력
api/v1alpha1/: groupversion_info.go journalsite_types.go zz_generated.deepcopy.go internal/controller/: journalsite_controller.go journalsite_controller_test.go suite_test.go
판정--domain example.com + --group study가 합쳐져 study.example.com 그룹이 된다. 33.3에서 손으로 쓴 것과 같은 그룹이어야 같은 CRD를 다루므로, 이 조합을 맞추는 것이 중요하다.

고칠 파일은 둘이다. journalsite_types.go(타입과 검증)와 journalsite_controller.go(조정 함수). zz_generated.deepcopy.go와 config/crd/bases/는 생성물이라 직접 고치지 않는다.

2단계 — 타입과 검증을 쓴다

목적33.3의 YAML을 Go 주석으로 다시 쓴다.

type JournalSiteSpec struct {
	// +kubebuilder:validation:Pattern=`^[a-z0-9./-]+:[a-zA-Z0-9._-]+$`
	Image string `json:"image"`

	// +kubebuilder:validation:Minimum=1
	// +kubebuilder:validation:Maximum=10
	// +kubebuilder:default=2
	Replicas int32 `json:"replicas,omitempty"`

	// +kubebuilder:validation:Enum=debug;info;warn;error
	// +kubebuilder:default=info
	LogLevel string `json:"logLevel,omitempty"`
}

type JournalSiteStatus struct {
	ReadyReplicas int32  `json:"readyReplicas"`
	Phase         string `json:"phase,omitempty"`
	// 어느 세대의 spec 을 반영한 status 인지
	ObservedGeneration int64 `json:"observedGeneration,omitempty"`
	// +listType=map
	// +listMapKey=type
	Conditions []metav1.Condition `json:"conditions,omitempty"`
}
// 오브젝트 타입 위의 마커
// +kubebuilder:subresource:status
// +kubebuilder:resource:shortName=js
// +kubebuilder:printcolumn:name="Ready",type=integer,JSONPath=`.status.readyReplicas`
// +kubebuilder:printcolumn:name="Phase",type=string,JSONPath=`.status.phase`

ObservedGeneration이 왜 필요한지 짚어 둔다. metadata.generation은 spec이 바뀔 때만 올라간다. 컨트롤러가 조정을 마치고 그 값을 status에 적으면, 둘을 비교해 "status가 최신 spec을 반영했는가"를 알 수 있다. 이것이 없으면 낡은 status를 보고 "준비됐다"고 판단하는 사고가 난다.

Conditions의 +listType=map도 형식적인 것이 아니다. 이 마커가 있어야 서버 사이드 어플라이가 조건을 type별로 병합한다. 없으면 두 컨트롤러가 서로의 조건을 통째로 덮어쓴다.

33.6따라하기 ④ 조정 함수를 쓴다

1단계 — 33.4의 세 단계를 Go로 옮긴다

목적같은 논리를 프레임워크 위에서 쓴다. 구조가 셸과 같다는 것을 확인한다.

func (r *JournalSiteReconciler) Reconcile(ctx context.Context, req ctrl.Request) (ctrl.Result, error) {
	// ① 원하는 상태
	var site studyv1alpha1.JournalSite
	if err := r.Get(ctx, req.NamespacedName, &site); err != nil {
		// 이미 지워졌으면 할 일이 없다. 딸린 것은 가비지 컬렉터가 치운다.
		return ctrl.Result{}, client.IgnoreNotFound(err)
	}

	// ② 차이를 없앤다
	want := r.desiredDeployment(&site)
	if err := ctrl.SetControllerReference(&site, want, r.Scheme); err != nil {
		return ctrl.Result{}, err
	}
	...

	// ③ status 를 갱신한다
	site.Status.ObservedGeneration = site.Generation
	if err := r.Status().Update(ctx, &site); err != nil { ... }
	return ctrl.Result{}, nil
}

SetControllerReference가 셸에서 손으로 쓴 ownerReferences 블록을 대신한다. client.IgnoreNotFound는 "이미 지워짐"을 오류가 아니라 정상 종료로 다루는 관용구다 — 이것을 빼면 삭제할 때마다 오류 로그가 쌓인다.

기존 디플로이먼트를 고칠 때 전체를 덮지 않고 우리가 관리하는 필드만 맞추는 것에 주의한다. 통째로 덮으면 HPA가 정한 replicas를 지우고, M17에서 본 "필드의 주인이 둘인" 상황이 된다.

2단계 — 감시 대상을 선언한다

목적셸의 폴링을 대신하는 부분이다. 이 한 줄이 33.4와의 가장 큰 차이다.

func (r *JournalSiteReconciler) SetupWithManager(mgr ctrl.Manager) error {
	return ctrl.NewControllerManagedBy(mgr).
		For(&studyv1alpha1.JournalSite{}).
		// 우리가 만든 디플로이먼트가 바뀌어도 조정이 돈다
		Owns(&appsv1.Deployment{}).
		Named("journalsite").
		Complete(r)
}

For는 "이 종류를 지켜본다", Owns는 "이 종류가 바뀌면 소유자의 조정을 부른다"이다. Owns가 없으면 누가 디플로이먼트를 지워도 컨트롤러가 모르고, 다음 JournalSite 변경 때까지 방치된다.

4단계 — 폴링과 감시를 재 본다

목적33.4의 5초와 비교한다. 같은 실험, 다른 구현.

판정삭제한 시각과 재생성 로그의 시각이 같은 초다. 셸 오퍼레이터는 01:34:52에 감지해 01:34:57에 복구했다 — 최대 5초를 기다린다. 폴링 간격을 줄이면 되지 않느냐고 생각하기 쉬운데, 그러면 오브젝트 수 × 초당 요청만큼 API 서버 부하가 늘어난다. 감시는 변화가 있을 때만 깨어나므로 그 비용이 없다.

5단계 — status를 읽는다

목적컨트롤러가 남긴 정보로 사람이 판단할 수 있는지 확인한다.

kubectl -n m33 patch js site-a --type=merge -p '{"spec":{"replicas":3}}'
kubectl -n m33 get js site-a -o jsonpath='{.status}' | python3 -m json.tool
출력
{ "conditions": [ { "lastTransitionTime": "2026-09-05T16:38:50Z", "message": "3/3 준비됨", "reason": "AllReplicasReady", "status": "True", "type": "Available" } ], "observedGeneration": 2, "phase": "Ready", "readyReplicas": 3 }
판정observedGeneration: 2가 핵심이다 — spec을 두 번 고쳤고 status가 그 두 번째를 반영했다는 뜻이다. 이 값이 metadata.generation보다 작으면 아직 조정이 끝나지 않은 것이고, 그때의 phase: Ready는 옛 정보다. 자동화가 이 오브젝트를 보고 판단한다면 두 값을 함께 봐야 한다.

33.7일부러 실패시키기

실패 ① — 셸 변수 이름이 시스템 것과 겹친다

목적33.4를 처음 돌렸을 때 실제로 난 오류다. 원인이 스크립트 논리와 무관하다.

bash course/labs/scripts/shell-operator.sh m33 5
출력
조정 루프 시작 — 네임스페이스 m33, 간격 5초 (Ctrl+C 로 종료) scripts/shell-operator.sh: line 27: UID: readonly variable
판정UID는 셸이 미리 정해 둔 읽기 전용 변수(현재 사용자의 uid)다. 오브젝트의 metadata.uid를 담으려고 같은 이름을 썼다가 대입이 거부됐다. 루프는 계속 돌았지만 ownerReferences의 uid가 비어 디플로이먼트가 만들어지지 않았다 — 오류 한 줄이 지나가고 아무것도 되지 않는 형태라 원인을 찾기까지 시간이 걸린다.

OWNER_UID로 바꿔 해결했다. 셸에서 예약된 이름은 UID·PATH·HOME·PWD·IFS 등이고, 스크립트 변수는 접두사를 붙이는 습관이 이 부류의 사고를 막는다.

실패 ② — not: pattern의 거부 메시지를 사람이 못 읽는다

목적검증을 어디에 어떻게 쓸지 고르는 기준을 만든다.

33.3에서 본 메시지를 다시 본다.

출력
The JournalSite "bad-latest" is invalid: <nil>: Invalid value: "": "spec.image" must not validate the schema (not)

필드 이름은 있지만 어떤 값이 왜 안 되는지가 없다. CEL로 바꾼다 — M26에서 어드미션 정책에 쓴 그 언어다.

// +kubebuilder:validation:XValidation:rule="!self.endsWith(':latest')",message="latest 태그는 쓸 수 없다"
Image string `json:"image"`
생성된 CRD
x-kubernetes-validations: - message: latest 태그는 쓸 수 없다 rule: '!self.endsWith('':latest'')'
거부 메시지
The JournalSite "bad-latest" is invalid: spec.image: Invalid value: "journal-api:latest": latest 태그는 쓸 수 없다
판정같은 규칙, 같은 거부, 완전히 다른 사용자 경험이다. 값과 우리가 쓴 문장이 함께 나온다. 검증 규칙을 만들 때는 거부당한 사람이 무엇을 고쳐야 하는지 알 수 있는가를 기준으로 방식을 고른다.

세 층 중 어디에 걸 것인지도 정리해 둔다. 스키마는 형식(타입·범위·열거)에, CEL은 한 오브젝트 안에서 판단되는 규칙에, 어드미션 정책(M26)은 여러 종류의 리소스에 걸쳐 적용할 규칙에 쓴다. latest 금지는 우리 CRD만이 아니라 모든 디플로이먼트에도 필요하므로, 실제로는 둘 다 있는 것이 맞다.

33.8운영 관점 — 만들 것인가 쓸 것인가

CRD를 만들지 말아야 할 때

새 리소스 종류를 만드는 것은 API를 하나 더 운영하는 일이다. 버전을 올려야 하고, 스키마를 바꿀 때 기존 오브젝트를 변환해야 하고, 컨트롤러가 죽으면 그 종류의 오브젝트가 전부 멈춘다.

그래서 먼저 물어볼 것이 있다. 헬름 차트로 충분한가. 배포를 묶는 것이 목적이라면 차트가 더 싸다. 기존 리소스의 조합으로 표현되는가. 잡·크론잡·컨피그맵으로 되는 일에 CRD를 만들 이유가 없다.

CRD가 값을 내는 경우는 대체로 셋이다. 지속적인 조정이 필요할 때(누가 바꿔도 되돌아와야 한다), 상태를 관측 가능한 형태로 노출해야 할 때(다른 시스템이 status를 읽는다), 도메인 개념이 실제로 새로울 때(우리 조직에만 있는 "고객사 환경" 같은 것).

버전을 올릴 때가 진짜 시험이다

v1alpha1으로 시작한 것이 언젠가 v1beta1이 되고 v1이 된다. 그때 이미 저장된 오브젝트들을 어떻게 할 것인가가 오퍼레이터 운영의 가장 어려운 부분이다.

필드를 추가하는 것은 대체로 안전하다. 이름을 바꾸거나 제거하는 것은 안전하지 않고, 두 버전을 동시에 제공하면서 변환 웹훅을 두거나, 새 필드를 추가하고 옛 필드를 한동안 함께 유지하는 방식을 쓴다. alpha 버전에는 호환성 약속이 없다는 관례가 이 어려움 때문에 있다 — 그러니 알파일 때 스키마를 충분히 흔들어 보는 편이 낫다.

컨트롤러를 어디서 돌릴 것인가

이 모듈은 make run으로 로컬 프로세스에서 돌렸다. 개발 중에는 이 방식이 압도적으로 빠르다 — 코드를 고치고 다시 돌리면 끝이고, 이미지 빌드도 배포도 없다.

실제 운영에서는 클러스터 안의 디플로이먼트로 돌린다(make deploy). 그때 새로 생기는 것이 RBAC이다. 컨트롤러가 쓰는 권한이 +kubebuilder:rbac 마커에서 생성되는데, 마커를 빠뜨리면 배포한 뒤에야 Forbidden으로 알게 된다 — 로컬에서는 개발자의 관리자 권한으로 돌아서 아무 문제가 없기 때문이다. M23에서 본 인가 오류가 여기서 다시 나온다.

고가용성도 생각할 거리다. 컨트롤러를 여러 개 띄우면 같은 오브젝트를 동시에 조정할 수 있어서, 프레임워크의 리더 선출을 켜고 한 번에 하나만 일하게 한다. kubebuilder 뼈대에 그 옵션이 이미 들어 있다.

이 교재가 만든 것과 쓴 것

M30의 Argo Rollouts와 M31의 Argo CD는 남이 만든 오퍼레이터다. 둘 다 이 모듈에서 만든 구조와 정확히 같다 — CRD로 종류를 정의하고, 컨트롤러가 조정하고, status로 결과를 알린다. M30에서 Rollout의 status를 읽어 판정한 것이 이 모듈의 observedGeneration·conditions와 같은 구조다.

다음 모듈에서 클러스터를 넘나드는 서비스를 다룰 때도 같은 패턴이 나온다 — 표준이 없는 자리를 컨트롤러가 채운다.

다음 모듈

M32에서 클러스터를 둘로 늘렸을 때 배포는 나눴지만 서비스는 나누지 않았다. 각 리전의 앱은 자기 클러스터 안에서만 통신했고, 클러스터 밖의 데이터베이스나 다른 클러스터의 서비스를 부르는 방법은 다루지 않았다.

M34에서 그 경로를 만든다. 셀렉터 없는 서비스와 엔드포인트를 손으로 써서 클러스터 밖 주소를 서비스처럼 쓰고, ExternalName이 무엇을 하고 무엇을 못 하는지 확인한다. 그리고 클러스터 사이에 서비스를 공유할 때 표준이 어디까지 왔는지 정리한다.
