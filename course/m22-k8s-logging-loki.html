M21의 알림이 "에러율 5.9%"라고 말해 준다. 그런데 그 에러가 무엇이었는지는 메트릭이 답하지 못한다. 이 모듈에서 로그를 클러스터 밖으로 모은다. 먼저 kubectl logs가 어디서 멈추는지 재현하고, Loki와 Alloy를 세운 뒤, 로그 라벨을 잘못 잡으면 스트림이 어떻게 66배가 되는지 직접 만들어 본다.

핵심 3줄

1. 파드를 지우면 kubectl logs가 NotFound를 돌려주는 것을 확인하고, Loki와 Alloy로 로그를 파드 바깥에 남긴다.

2. 수집기를 세워도 앱이 요청마다 로그를 남기지 않으면 볼 것이 없다 — 두 앱에 각각 다른 방법으로 요청 로그를 켠다.

3. 로그 필드를 라벨로 승격시켜 스트림이 3개에서 66개가 되는 것을 직접 만들고 되돌린다.

22.1알림은 "몇 건"까지만 말한다 22.2이론 — 무엇을 모으고 어디에 둘 것인가 22.3따라하기 ① kubectl logs가 멈추는 곳 22.4따라하기 ② Loki와 Alloy를 세운다 22.5따라하기 ③ 앱이 로그를 남기게 한다 22.6따라하기 ④ LogQL로 찾는다 22.7일부러 실패시키기 22.8운영 관점 — 로그는 비싸다 22.9체크포인트와 정리

22.1알림은 "몇 건"까지만 말한다

M21에서 AppHighErrorRate가 발화했을 때 알림이 알려준 것은 "order-api 에러율 5.9%"였다. 대응하는 사람이 다음에 하는 질문은 정해져 있다 — 무슨 에러인가.

메트릭은 그 질문에 답할 수 없다. http_server_requests_seconds_count{status="500"}는 500이 몇 번 났는지만 안다. 어떤 요청이었는지, 스택 트레이스가 무엇이었는지, 같은 사용자의 연속 요청이었는지는 숫자로 압축되면서 사라진 정보다.

M19 2절에서 메트릭과 로그를 나눌 때 이렇게 적었다 — "지금 에러율이 몇 퍼센트인가"는 메트릭이, "그 에러가 정확히 무엇이었나"는 로그가 답한다. 지금까지 앞쪽만 만들었다.

그리고 지금 우리가 로그를 보는 방법은 kubectl logs 하나뿐인데, 이것은 파드가 살아 있을 때만 쓸 수 있다. 새벽에 죽은 파드가 재시작되고 나면 그 파드가 무슨 말을 남겼는지 볼 방법이 없다. 22.3에서 그 경계를 정확히 확인한다.

22.2이론 — 무엇을 모으고 어디에 둘 것인가

책 3.8은 클러스터에서 모아야 할 로그를 넷으로 나눈다.

대상무엇이 모듈에서
노드kubelet, 컨테이너 런타임, 시스템 데몬수집 대상에 들어간다
컨트롤 플레인apiserver, 스케줄러, 컨트롤러 매니저, etcd수집되지 않는다 — 22.4에서 이유를 본다
감사 audit누가 무엇을 언제 요청했는가M27 보안에서 다룬다
애플리케이션앱이 stdout으로 내보내는 것이 모듈의 주 대상

stdout 원칙

컨테이너 안에서 파일에 로그를 쓰면 파드가 사라질 때 함께 사라진다. 볼륨을 붙여 남길 수도 있지만 그러면 노드에 묶이고(M18), 수집기가 그 파일의 위치와 형식을 알아야 한다.

표준 방식은 표준 출력으로 내보내고 나머지는 플랫폼에 맡기는 것이다. 컨테이너 런타임이 그것을 노드의 파일로 받아 두고, 수집기가 그 파일이나 쿠버네티스 API를 통해 읽어 간다. 앱은 자기가 어디에 저장되는지 몰라도 된다.

사이드카로 로그를 모으는 방식도 있다 — 앱이 파일에 쓰고 같은 파드의 다른 컨테이너가 그것을 읽어 stdout으로 옮기는 것이다. 앱을 고칠 수 없을 때 쓰지만, 파드마다 컨테이너가 하나씩 늘고 메모리도 그만큼 든다. 고칠 수 있으면 앱이 직접 stdout으로 내보내는 편이 낫다.

로키가 프로메테우스와 닮은 점과 다른 점

로키는 "프로메테우스인데 로그용"이라고 소개되곤 한다. 닮은 것은 라벨로 대상을 고른다는 점이다. {namespace="journal", app="journal-api"}처럼 쓰는 것이 프로메테우스의 셀렉터와 같다.

다른 것이 중요하다. 로키는 로그 본문을 인덱싱하지 않는다. 라벨만 인덱싱하고 본문은 압축해 통째로 저장한다. 그래서 저장 비용이 싸고, 대신 본문 검색은 해당 스트림을 전부 읽어 훑는 방식이다. 라벨로 범위를 좁힌 뒤 본문을 훑는 것이 로키의 사용법이고, 라벨을 잘못 잡으면 그 구조가 무너진다 — 22.7 실패 ③에서 직접 만든다.

Promtail과 loki-stack은 쓰지 않는다 검색하면 대부분 Promtail로 수집하고 loki-stack 차트로 설치한다. 둘 다 지금은 쓰면 안 되는 것인데, helm search repo에는 아무 표시 없이 그대로 나온다.
helm search repo grafana/promtail → 6.17.1 / appVersion 3.5.1
helm search repo grafana/loki-stack → 2.10.3 / appVersion v2.9.3
차트 메타데이터를 직접 봐야 보인다.
helm show chart grafana/promtail | grep deprecated → deprecated: true
helm show chart grafana/loki-stack | grep deprecated → deprecated: true
Promtail은 2026-03-02로 수명이 끝났고 후속은 Grafana Alloy다. loki-stack은 appVersion이 v2.9.3 — Loki 2.x 대에 멈춰 있다(현재 3.6.12). 이 모듈은 grafana/loki와 grafana/alloy를 따로 설치한다. 근거: helm show chart 출력 · grafana.com/docs/loki (Promtail EOL) · 2026-09-05 확인

22.3따라하기 ① kubectl logs가 멈추는 곳

1단계 — 로그를 남기고 죽는 파드를 만든다

목적로그가 언제까지 보이고 언제 사라지는지 경계를 정확히 잡는다.

kubectl create ns m22

cat <<'EOF' | kubectl -n m22 apply -f -
apiVersion: v1
kind: Pod
metadata: {name: noisy}
spec:
  restartPolicy: Never
  containers:
    - name: c
      image: alpine:3.22
      resources: {requests: {cpu: 10m, memory: 16Mi}}
      command: ["sh","-c","i=0; while [ $i -lt 30 ]; do echo \"{\\\"level\\\":\\\"info\\\",\\\"msg\\\":\\\"작업 $i\\\"}\"; i=$((i+1)); sleep 1; done; echo '{\"level\":\"error\",\"msg\":\"마지막에 터졌다\"}'; exit 1"]
EOF

30초 동안 로그를 찍고 마지막에 에러를 남기며 죽는 파드다. 세 시점에서 kubectl logs를 쳐 본다.

# ① 실행 중
kubectl -n m22 logs noisy | tail -3
출력
{"level":"info","msg":"작업 10"} {"level":"info","msg":"작업 11"} {"level":"info","msg":"작업 12"}
# ② 끝난 뒤
kubectl -n m22 get pod noisy --no-headers
kubectl -n m22 logs noisy | tail -2
출력
noisy 0/1 Error 0 33s {"level":"info","msg":"작업 29"} {"level":"error","msg":"마지막에 터졌다"}
판정파드가 Error 상태로 끝났는데도 로그는 남아 있다. 여기까지는 kubectl logs로 충분하다 — 죽은 파드의 마지막 말을 읽을 수 있다.
# ③ 파드를 지우면
kubectl -n m22 delete pod noisy
kubectl -n m22 logs noisy
출력
pod "noisy" deleted from m22 namespace error: error from server (NotFound): pods "noisy" not found in namespace "m22"
판정파드 오브젝트가 사라지면 로그도 사라진다. kubectl logs는 파드에 붙어 있는 기능이지 로그 저장소가 아니다.

지워지는 일은 늘 일어난다

"파드를 안 지우면 되지 않나" 싶지만, 실제로는 우리가 이 과정에서 이미 여러 번 지웠다.

언제어디서 봤나
롤아웃할 때마다 옛 파드가 지워진다M10 · M15
HPA가 축소하면 파드가 사라진다M17 — 8개에서 3개로
노드를 비우면 파드가 다른 노드로 옮겨진다M16 drain
OOM으로 죽고 재시작되면 옛 컨테이너 로그는 회전 대상이 된다M16 실패 ③

그리고 노드 자체의 로그 회전도 있다 — kubelet은 컨테이너 로그 파일 크기가 커지면 잘라 낸다. 파드가 살아 있어도 오래된 로그는 사라진다. 로그를 클러스터 밖에 모아야 하는 이유가 이것이다.

3단계 — 로키를 설치한다

목적단일 인스턴스로 최소 구성을 만든다. 기본값은 노트북에 맞지 않는다.

course/labs/monitoring/loki-values.yaml의 핵심 부분이다.

deploymentMode: SingleBinary

loki:
  auth_enabled: false          # 켜면 모든 요청에 X-Scope-OrgID 헤더가 필요해진다
  commonConfig:
    path_prefix: /var/loki
    replication_factor: 1      # 단일 인스턴스이므로 1. 기본값(3)이면 기동하지 못한다
  storage:
    type: filesystem
    bucketNames: {chunks: chunks, ruler: ruler, admin: admin}
  schemaConfig:                # 명시하지 않으면 최근 차트는 설치가 실패한다
    configs:
      - from: "2024-04-01"
        store: tsdb
        object_store: filesystem
        schema: v13
        index: {prefix: loki_index_, period: 24h}
  limits_config:
    allow_structured_metadata: true
    volume_enabled: true
    retention_period: 72h      # 실습용. 책 3.8 은 운영에서 30~45일을 권한다

singleBinary:
  replicas: 1
  nodeSelector:
    workload: observability    # 관측 스택을 한 노드에 모은다 (M16 · M19)
  persistence: {enabled: true, size: 10Gi}
  resources:
    requests: {cpu: 100m, memory: 384Mi}
    limits: {memory: 900Mi}

차트가 SingleBinary 모드에서도 마이크로서비스 컴포넌트를 기본으로 켜므로 전부 replicas: 0으로 내려야 한다(backend·read·write·ingester·querier·compactor 등). 캐시(chunksCache·resultsCache)도 memcached 파드를 띄우므로 끈다 — 전체 값 파일은 저장소를 본다.

helm upgrade --install loki grafana/loki --namespace logging --create-namespace \
  --version 7.3.0 -f course/labs/monitoring/loki-values.yaml --wait --timeout 10m

kubectl -n logging get po --no-headers
출력
loki-0 2/2 Running 0 78s loki-gateway-7747766d57-zg8tw 1/1 Running 0 78s
판정파드 둘이면 된다. loki-0이 스테이트풀셋(M18 — 로그 데이터를 PVC에 들고 있다)이고 loki-gateway가 앞단의 nginx다. 파드가 여럿 뜬다면 위의 replicas: 0이 빠진 것이다.

4단계 — Alloy를 설치한다

목적파드 로그를 읽어 로키로 보내는 수집기를 노드마다 띄운다.

Alloy의 설정은 파이프라인 네 토막이다. course/labs/monitoring/alloy-values.yaml에 쓴다.

      // 1) 클러스터의 파드를 발견한다
      discovery.kubernetes "pods" {
        role = "pod"
      }

      // 2) 어떤 라벨을 붙일지 고른다. **여기서 고르지 않은 메타데이터는 버려진다.**
      //    라벨 하나가 스트림 하나이므로, 값의 가짓수가 많은 것을 넣으면
      //    카디널리티가 폭발한다 (M19 8절의 프로메테우스 라벨과 같은 문제다).
      discovery.relabel "pod_logs" {
        targets = discovery.kubernetes.pods.targets
        rule { source_labels = ["__meta_kubernetes_namespace"];            target_label = "namespace" }
        rule { source_labels = ["__meta_kubernetes_pod_name"];             target_label = "pod" }
        rule { source_labels = ["__meta_kubernetes_pod_container_name"];   target_label = "container" }
        // 두 앱이 서로 다른 라벨 규칙을 쓴다.
        // journal-api 는 app, order-api 는 app.kubernetes.io/name 이다.
        rule { source_labels = ["__meta_kubernetes_pod_label_app_kubernetes_io_name"]; regex = "(.+)"; target_label = "app" }
        rule { source_labels = ["__meta_kubernetes_pod_label_app"];                    regex = "(.+)"; target_label = "app" }
      }

      // 3) 쿠버네티스 API 로 로그를 읽는다.
      //    호스트의 /var/log 를 마운트하는 방식과 달리 특권 컨테이너가 필요 없다 (M24).
      loki.source.kubernetes "pods" {
        targets    = discovery.relabel.pod_logs.output
        forward_to = [loki.write.default.receiver]
      }

      // 4) 로키로 밀어 넣는다
      loki.write "default" {
        endpoint {
          url = "http://loki-gateway.logging.svc.cluster.local/loki/api/v1/push"
        }
      }
라벨 둘을 separator로 잇지 않는다 처음에는 source_labels에 둘을 나열하고 separator = ""로 이었다. 둘 다 가진 파드에서 값이 붙어 버린다.
app = "kube-prometheus-stack-prometheus-operatorkube-prometheus-stack-operator"
regex = "(.+)"를 붙인 규칙 두 개로 나누면 값이 있을 때만 적용되어 해결된다. 
helm upgrade --install alloy grafana/alloy --namespace logging \
  --version 1.12.1 -f course/labs/monitoring/alloy-values.yaml --wait --timeout 8m

kubectl -n logging get po --no-headers | grep alloy
출력
alloy-r6r76 2/2 Running 0 33s alloy-xqznt 2/2 Running 0 33s
판정데몬셋인데 2개다. 노드는 셋인데 컨트롤 플레인에는 뜨지 않았다 — 톨러레이션이 없어 테인트를 견디지 못한다(M16 7단계). 그래서 22.2 표의 "컨트롤 플레인" 로그가 수집되지 않는다. 실습에서는 그대로 두지만, 운영이라면 톨러레이션을 넣어야 apiserver·스케줄러의 로그를 볼 수 있다.

22.5따라하기 ③ 앱이 로그를 남기게 한다

5단계 — 수집기가 무엇을 받고 있는지 본다

목적설치가 끝났다고 로그가 보이는 것이 아니라는 것을 확인한다.

kubectl -n logging port-forward svc/loki-gateway 3100:80 &

curl -sG http://localhost:3100/loki/api/v1/labels
curl -sG http://localhost:3100/loki/api/v1/query_range \
  --data-urlencode 'query={namespace="journal", app="journal-api"}' \
  --data-urlencode "start=$(( $(date +%s) - 600 ))000000000" \
  --data-urlencode "end=$(date +%s)000000000"

6단계 — journal-api에 구조화 요청 로그를 붙인다

목적메트릭과 같은 자리에서 로그도 남긴다. M20에서 만든 미들웨어를 그대로 쓴다.

src/server.ts의 계측 미들웨어에 로그 한 줄을 더한다.

  const end = httpDuration.startTimer();
  const startedAt = Date.now();
  res.on('finish', () => {
    const uri = normalizeUri(req);
    end({ method: req.method, uri, status: String(res.statusCode), outcome: outcomeOf(res.statusCode) });

    // 요청 로그 (M22). 메트릭은 "몇 건인가"를, 로그는 "무엇이었나"를 답한다.
    // 프로브 요청까지 남기면 로그의 대부분이 헬스 체크가 된다 — 걸러 낸다.
    if (uri === '/healthz' || uri === '/readyz' || uri === '/metrics') return;
    log(res.statusCode >= 500 ? 'error' : 'info', 'request', {
      method: req.method,
      // path 를 그대로 남긴다. 라벨이 아니라 로그 본문이므로 카디널리티 문제가 없다 (22.8).
      path: req.originalUrl,
      status: res.statusCode,
      durationMs: Date.now() - startedAt,
      pod: INSTANCE,
    });
  });

메트릭의 uri 라벨은 normalizeUri()로 정규화했지만 로그의 path는 원본을 그대로 남긴다. 라벨이 아니라 본문이므로 값의 가짓수가 문제되지 않고, 오히려 "어느 요청이었나"를 답하려면 원본이 필요하다. 이 구분이 22.7 실패 ③의 핵심이다.

22.6따라하기 ④ LogQL로 찾는다

부하를 걸어 로그를 쌓은 뒤 질의한다. M20에서 만든 k6-red.js를 그대로 쓴다.

8단계 — 얼마나 들어오고 있는지 센다

목적LogQL이 프로메테우스처럼 집계 함수를 갖고 있다는 것을 확인한다.

sum by (app) (count_over_time({namespace=~"journal|apps"}[5m]))
sum by (app) (rate({namespace=~"journal|apps"}[5m]))
출력
app=journal-api = 3158 app=order-api = 3794 app=web-static = 120 app=journal-api = 9.03 (줄/초) app=web-static = 0.4
판정로그 줄 수를 시계열처럼 다룰 수 있다. count_over_time과 rate는 프로메테우스와 같은 이름이고 하는 일도 같다 — 다만 세는 대상이 샘플이 아니라 로그 줄이다.

9단계 — 구조화 로그에서 필드를 꺼낸다

목적| json 파서를 쓰고, 그것이 왜 자주 실패하는지 본다.

sum by (status) (count_over_time({namespace="journal", app="journal-api"} | json [5m]))
출력
pipeline error: 'JSONParserErr' for series: '{__error__="JSONParserErr", __error_details__="Value looks like object, but can't find closing '}' symbol", app="journal-api", container="api", ...

질의 전체가 실패했다. JSON이 아닌 줄이 하나라도 섞이면 이렇게 된다 — 우리 앱은 기동 로그도 JSON이지만, 긴 줄이 잘리거나 다른 컨테이너의 줄이 섞이면 언제든 생긴다.

sum by (status) (count_over_time({namespace="journal", app="journal-api"} | json | __error__="" [5m]))
출력
status=200 = 2700 status=(없음) = 9
판정| __error__=""로 파싱 실패한 줄을 걸러 내면 동작한다. 파서 뒤에는 거의 항상 이 필터가 붙는다고 생각하는 편이 낫다. status가 없는 9줄은 기동 로그처럼 request가 아닌 줄이다.

10단계 — 형식이 다른 로그는 pattern으로

목적JSON이 아닌 액세스 로그에서도 필드를 꺼낸다.

톰캣 액세스 로그는 공백으로 나뉜 고정 형식이다. | pattern이 그런 줄에 이름을 붙인다.

sum by (status) (count_over_time({namespace="apps", app="order-api"}
  | pattern `<_> <_> <_> [<_>] "<method> <path> <_>" <status> <_> <dur>` [5m]))
출력
status=200 = 3423 status=500 = 208 status=(없음) = 178
판정<_>는 "여기 뭔가 있는데 이름은 필요 없다"는 뜻이고, <status>처럼 이름을 주면 그 자리의 값이 필드가 된다. 이름이 없는 178줄은 스프링 기동 로그다 — 패턴에 맞지 않아 필드가 비었다.

11단계 — 로그와 메트릭을 대조한다

목적같은 사건을 두 시스템에서 세어 보고, 숫자가 다른 이유를 이해한다.

# 로그 쪽
sum(count_over_time({namespace="apps", app="order-api"} |~ " 500 " [5m]))
# 메트릭 쪽
sum(increase(http_server_requests_seconds_count{job="order-api",status=~"5.."}[5m]))
출력
[로그] 208 [메트릭] 249.8
판정같은 5분인데 숫자가 다르다. 로그는 실제로 찍힌 줄 수(정수)이고, increase()는 구간 경계에서 외삽하므로 소수점이 붙고 대개 더 크게 나온다.

이 차이를 없애려 하면 안 된다. 두 시스템은 다른 질문에 답하도록 만들어졌다 — 메트릭은 추세와 비율에, 로그는 개별 사건에 정확하다. 대시보드에서 두 숫자를 나란히 놓고 "왜 다르냐"는 질문을 받는 일이 자주 있는데, 답은 "원래 다르다"이다.

22.7일부러 실패시키기

실패 ① 로그를 켰는데 아무것도 안 나온다

7단계에서 ROTATE를 빠뜨렸을 때의 상태다. 환경 변수는 다 들어갔는데 로그가 없다.

진단 
kubectl -n apps get deploy order-api \
  -o jsonpath='{range .spec.template.spec.containers[0].env[*]}{.name}={.value}{"\n"}{end}'
출력
SERVER_TOMCAT_ACCESSLOG_ENABLED=true SERVER_TOMCAT_ACCESSLOG_DIRECTORY=/dev SERVER_TOMCAT_ACCESSLOG_PREFIX=stdout SERVER_TOMCAT_ACCESSLOG_SUFFIX= SERVER_TOMCAT_ACCESSLOG_BUFFERED=false

설정은 정확히 들어갔다. 그런데 요청을 보내도 kubectl logs에는 기동 로그만 있다.

원인

톰캣의 액세스 로그 밸브는 기본적으로 파일을 회전시킨다. 회전이 켜져 있으면 파일명 뒤에 날짜를 붙이므로 실제 대상이 /dev/stdout.2026-09-05가 되고, 그런 파일은 없다. 톰캣은 이 실패를 조용히 넘긴다.

고친다 
            - name: SERVER_TOMCAT_ACCESSLOG_ROTATE
              value: "false"
판정적용하고 요청을 보내면 액세스 로그가 나온다. "설정을 넣었는데 결과가 없다"는 상황에서는 그 설정이 만드는 대상을 확인해야 한다 — 여기서는 파일 경로였다.

실패 ② | json 하나에 질의 전체가 깨진다

9단계에서 이미 만났다. 다시 정리해 둔다.

재현 
{namespace="journal", app="journal-api"} | json | status >= 400
출력
pipeline error: 'JSONParserErr' ... "Value looks like object, but can't find closing '}' symbol"
원인

로키의 파이프라인은 줄마다 적용되는데, 파싱에 실패한 줄에 __error__ 라벨이 붙고 그것이 결과에 섞여 질의를 실패시킨다. 로그는 형식이 섞이는 것이 정상이므로(기동 로그, 라이브러리가 찍는 줄, 잘린 줄) 이 상황은 예외가 아니라 기본값에 가깝다.

고친다 
{namespace="journal", app="journal-api"} | json | __error__="" | status >= 400
판정파서 바로 뒤에 | __error__=""를 붙이는 것이 관용이다. 파싱 실패가 얼마나 되는지 궁금하면 반대로 | __error__!=""로 세어 본다 — 그 수가 크면 로그 형식을 정리해야 한다는 신호다.

실패 ③ 로그 필드를 라벨로 올리면 스트림이 폭발한다

"path로 자주 검색하니 라벨로 만들면 빠르겠다"는 판단이 이 사고를 만든다. 실제로 만들어 본다.

실험 전 상태 
curl -sG http://localhost:3100/loki/api/v1/series \
  --data-urlencode 'match[]={namespace="journal"}' \
  --data-urlencode "start=..." --data-urlencode "end=..."
출력
journal 네임스페이스 스트림: 8 전체 스트림: 35
재현 — Alloy에 승격 단계를 넣는다 
      // ⚠ 실험용 — 로그 필드를 라벨로 승격시킨다. 실습 뒤 되돌린다.
      loki.process "explode" {
        stage.json {
          expressions = { path = "path", status = "status" }
        }
        stage.labels {
          values = { path = "", status = "" }
        }
        forward_to = [loki.write.default.receiver]
      }

그리고 loki.source.kubernetes의 forward_to를 loki.process.explode.receiver로 바꿔 이 단계를 거치게 한다.

helm upgrade alloy grafana/alloy -n logging --version 1.12.1 -f .../alloy-values.yaml --wait

이제 서로 다른 경로로 요청을 보낸다. 실제 서비스에서 /api/orders/12345처럼 ID가 경로에 들어가는 상황을 흉내 낸 것이다.

kubectl -n journal exec curlbox -- sh -c \
  'i=1; while [ $i -le 60 ]; do curl -s -o /dev/null "http://journal-api:8080/api/entries?req=$i"; i=$((i+1)); done'
출력
journal-api 스트림: 66 서로 다른 path 라벨: 61 /api/entries?req=20 /api/entries?req=32 /api/entries?req=2 전체 path 값: 61 라벨 목록: [..., 'namespace', 'path', 'pod', 'service_name', 'status']
실험 전실험 후
journal-api 스트림366
path 라벨 값없음61
판정요청 60건이 스트림 60개를 만들었다. 라벨 조합 하나가 스트림 하나이고, 스트림마다 인덱스 항목과 청크가 따로 생긴다. 실제 서비스라면 하루에 수십만 스트림이 되고, 로키의 인제스터가 메모리를 다 쓴다.
고친다 — 되돌린다 
# loki.process 단계를 지우고 forward_to 를 loki.write.default.receiver 로 되돌린 뒤
helm upgrade alloy grafana/alloy -n logging --version 1.12.1 -f .../alloy-values.yaml --wait

같은 정보를 찾는 올바른 방법은 라벨로 범위를 좁히고 본문을 훑는 것이다.

{namespace="journal", app="journal-api"} | json | __error__="" | path =~ "/api/entries.*"

이쪽은 스트림을 늘리지 않는다. path가 본문 안에 있고, 파서가 질의 시점에 꺼내기 때문이다. 느린 대신 안전하다는 것이 로키의 설계이고, 라벨을 늘리는 것은 그 설계를 거스르는 일이다.

승격이 필요한 값이 정말 있다면 구조화 메타데이터를 쓴다(allow_structured_metadata: true가 3단계 값 파일에 이미 있다). 라벨 인덱스를 늘리지 않으면서 줄마다 필드를 붙이는 방식이다.

22.8운영 관점 — 로그는 비싸다

8단계에서 두 앱이 5분에 약 7,000줄을 찍었다. 부하가 30rps 남짓인 실습 환경에서다. 초당 300건을 받는 서비스라면 같은 비율로 하루 수천만 줄이 된다.

무엇을 찍지 않을 것인가

6단계에서 journal-api의 프로브 요청을 걸러 냈다. 걸러 내지 않으면 어떻게 되는지는 7단계의 order-api가 보여준다 — 액세스 로그의 상당수가 /actuator/health/readiness다. readiness가 5초마다, liveness가 10초마다, 파드가 둘이면 프로브만으로 시간당 2,000줄이 넘는다.

기준은 그 줄을 나중에 읽을 일이 있는가다. 프로브 성공 로그는 읽지 않는다 — 프로브 실패는 이미 이벤트와 메트릭에 남는다(M15). 마찬가지로 "요청을 받았다"와 "요청을 처리했다"를 둘 다 찍을 이유가 없고, 정상 응답의 본문은 더더욱 없다.

보존 기간

3단계에서 retention_period: 72h로 잡았다. 책 3.8은 운영에서 30~45일을 권하는데, 근거는 장애 조사 주기다 — 월요일에 지난주 금요일 사건을 조사할 수 있어야 하고, 반복되는 문제라면 몇 주 전과 비교할 수 있어야 한다.

다만 모든 로그를 같은 기간 보관할 이유는 없다. 감사 로그는 규정상 더 길게, 디버그 로그는 며칠이면 충분하다. 로키는 스트림 단위로 보존 기간을 다르게 줄 수 있으므로, 라벨 설계가 여기서도 값을 한다.

로그 레벨을 런타임에 바꿀 수 있게

평상시 info로 두고 문제가 생겼을 때만 debug로 올리는 것이 이상적이지만, 그러려면 재배포 없이 레벨을 바꿀 수 있어야 한다. M13에서 journal-api에 LOG_LEVEL을 컨피그맵으로 주입한 것이 그 준비였고, 스프링 부트는 액추에이터의 /actuator/loggers로 런타임 변경을 지원한다(우리 설정은 그 엔드포인트를 열지 않았다 — M19 3단계의 include: health,info,prometheus).

재배포로 레벨을 바꾸면 파드가 새로 뜨면서 문제 상황이 사라진다. 재현이 어려운 버그일수록 이 차이가 크다.

메트릭과 로그를 잇는 것

11단계에서 두 시스템의 숫자가 달랐다. 실무에서 필요한 것은 숫자를 맞추는 것이 아니라 같은 사건으로 이동하는 것이다 — 그래프에서 5xx가 튄 지점을 클릭하면 그 시각의 로그로 넘어가는 흐름이다.

그라파나는 데이터소스 사이 링크로 이것을 지원하고, 더 나아가면 트레이스 trace가 있다. 요청 하나에 ID를 붙여 메트릭·로그·트레이스가 같은 ID를 갖게 하면 세 층을 오갈 수 있다. 이 과정에서는 다루지 않지만, 6단계에서 로그에 pod 필드를 넣어 둔 것이 가장 단순한 형태의 연결이다 — 메트릭에서 특정 파드가 느린 것을 보고 그 파드의 로그로 좁힐 수 있다.

# Alloy 설정이 실험 상태로 남아 있지 않은지 확인한다
kubectl -n logging get cm alloy -o jsonpath='{.data.config\.alloy}' | grep -c 'loki.process'
출력
0

0이면 실험을 되돌린 것이다. 1 이상이면 alloy-values.yaml에서 loki.process "explode" 블록을 지우고 helm upgrade를 다시 한다.

되돌린 뒤에도 /loki/api/v1/labels에는 path가 한동안 남는다 — 보존 기간(72시간) 안의 옛 스트림이 아직 인덱스에 있기 때문이고 고장이 아니다. 새 스트림에 붙지 않는 것이 확인의 기준이다.

로그 스택은 지우지 않는다. Part 5 이후의 모듈들이 이 위에서 이어지고, 특히 M36 카오스 실험에서 "파드를 죽였을 때 무슨 로그가 남는가"가 판정 근거가 된다. 노트북 메모리가 부족하면 kubectl -n logging scale sts loki --replicas=0으로 잠시 내려 두고 나중에 되돌린다 — PVC에 데이터가 남아 있으므로 잃지 않는다(M18).

Part 4를 마치면 클러스터에서 무슨 일이 일어나는지 볼 수 있다. 그런데 지금까지 이 클러스터에서 우리는 무엇이든 할 수 있었다 — 어느 네임스페이스든 지우고, 노드 설정을 고치고, 시크릿을 평문으로 읽었다. 실제 클러스터에서 그런 권한을 가진 사람은 극소수다.
