어드미션 컨트롤과 정책 엔진

M24의 PSA와 M25의 네트워크 정책은 쿠버네티스가 미리 정해 둔 규칙이었다. 조직에는 그 목록에 없는 규칙이 있다 — "latest 태그 금지", "허용된 레지스트리만", "토큰은 기본으로 끈다". 이 모듈에서 그 규칙을 CEL 표현식으로 써서 API 서버 안에 심고, 경고에서 거부로 승격하는 순서와 이미 배포된 위반을 찾아내는 방법을 함께 만든다.

중후반100분Kubernetes 1.37.0
2026-09-05 검증 (kind v0.33.0) · 버전 숫자는 실습 당일 kubectl version으로 다시 확인한다
사전 조건
  • M23 완료 — 요청이 인증·인가를 지나는 것을 봤다
  • M24 완료 — 어드미션이 파드를 거부하는 것을 봤다. 이 모듈은 그 자리에 직접 만든 규칙을 얹는다
  • 클러스터가 1.30 이상. 확인: kubectl api-resources --api-group=admissionregistration.k8s.io에 validatingadmissionpolicies
  • 새로 만들 파일: course/labs/k8s/policy/의 00-no-latest.yaml·10-allowed-registries.yaml·20-default-no-token.yaml · course/labs/scripts/policy-audit.sh

핵심 3줄

1. CEL 한 줄로 latest 태그를 거부하는 정책을 만들고, Warn에서 Deny로 승격하는 순서를 밟는다.

2. 서버 드라이런으로 이미 배포된 위반을 클러스터 전체에서 찾아내는 스크립트를 만든다 — 정책을 켜기 전에 반드시 하는 일이다.

3. 표현식 오타 하나가 위반이 없는 배포까지 전부 막는 상황을 재현하고, 그것을 미리 잡는 자리(status.typeChecking)를 확인한다.

26.1규칙이 사람 머릿속에만 있다 26.2이론 — 요청 파이프라인과 CEL 26.3따라하기 ① latest 태그를 막는다 26.4따라하기 ② 이미 배포된 위반을 찾는다 26.5따라하기 ③ 목록을 정책 밖으로 뺀다 26.6따라하기 ④ 기본값을 주입한다 26.7일부러 실패시키기 26.8운영 관점 — 어디까지 정책으로 만들 것인가 26.9체크포인트와 정리

26.1규칙이 사람 머릿속에만 있다

이 교재는 M02부터 latest 태그를 쓰지 않는다는 규칙을 지켜 왔다. 매니페스트마다 태그를 박았고, 도커 이미지에 다이제스트를 적었다. 그런데 그 규칙은 지금 어디에도 기록되어 있지 않다 — 문서에 문장으로 있을 뿐, 클러스터는 nginx:latest를 아무 저항 없이 받는다.

규칙이 문서에만 있으면 세 가지가 일어난다. 새로 온 사람이 모른다. 급할 때 예외가 생긴다. 그리고 예외가 몇 개인지 아무도 세지 못한다. 세 번째가 가장 나쁘다 — 규칙을 지키자는 결정보다 지금 무엇이 어긋나 있는지 아는 것이 먼저인데, 그것을 셀 방법이 없다.

M24에서 이미 이 문제의 절반을 봤다. PSA는 "비루트로 실행하라"는 규칙을 라벨 하나로 강제했고, 강제한 순간 우리 워크로드 셋이 전부 거부당했다. 위반이 몇 개인지 그때 즉시 알게 됐다. 다만 PSA가 강제할 수 있는 것은 쿠버네티스가 미리 정의한 항목뿐이다. latest 태그도, 레지스트리 화이트리스트도, 리소스 요청 필수화도 그 목록에 없다.

예전에는 이런 규칙을 어드미션 웹훅admission webhook으로 만들었다. 클러스터 안에 HTTPS 서버를 띄우고, API 서버가 모든 요청을 그 서버에 물어보게 하는 방식이다. 규칙 하나 때문에 운영해야 할 서비스가 하나 늘어나고, 그 서비스가 죽으면 클러스터의 쓰기가 멈춘다. 1.30부터 그 대가 없이 같은 일을 하는 길이 생겼고, 그것이 이 모듈의 주제다.

26.2이론 — 요청 파이프라인과 CEL

책 매핑17.1 요청 파이프라인 · 11장 정책 엔진(제약 조건 템플릿·감사)과 현재의 대안

요청은 네 관문을 지난다

kubectl apply 한 번이 저장되기까지 API 서버는 네 단계를 거친다. 인증(누구인가) → 인가(이 동사를 허용하는가, M23) → 어드미션 → etcd 저장이다. 어드미션은 다시 둘로 나뉘는데, 뮤테이팅이 먼저고 밸리데이팅이 나중이다. 순서에 이유가 있다 — 검증은 변형이 끝난 최종 형태를 봐야 한다. 기본값을 채워 넣는 쪽이 먼저 돌지 않으면, 검증이 아직 채워지지 않은 필드를 보고 거부하게 된다.

이 순서는 M24에서 이미 겪었다. PSA가 파드를 거부한 것은 밸리데이팅 단계였고, 서비스어카운트 토큰 볼륨이 자동으로 붙은 것은 뮤테이팅 단계였다. 26.6에서 이 순서 때문에 같은 정책이 대상에 따라 효과가 달라지는 것을 측정한다.

정책과 바인딩이 나뉘어 있다

ValidatingAdmissionPolicyVAP는 검사 내용만 담는다. 그 검사를 어느 네임스페이스에, 경고로 할지 거부로 할지는 ValidatingAdmissionPolicyBinding이 정한다. M23의 Role과 RoleBinding, M20의 ServiceMonitor와 라벨 연결과 같은 구조다 — 정의와 적용 범위를 따로 배포한다.

이 분리가 실무에서 하는 일이 승격이다. 같은 정책에 바인딩을 [Warn]으로 먼저 붙여 아무도 막지 않으면서 경고만 흘리고, 위반이 정리된 뒤 [Deny]로 바꾼다. 정책 파일은 그대로 두고 바인딩 한 줄만 고치는 것이 승격의 전부다. 세 번째 값 [Audit]은 감사 로그에 남기는데, 그것은 감사 로깅을 켜야 의미가 있으므로 M27에서 다룬다.

CEL — API 서버 안에서 도는 표현식

검사 내용은 CELCommon Expression Language로 쓴다. 표현식 하나가 true면 통과, false면 위반이다. 다음 세 이름이 대부분의 정책에서 쓰인다.

이름무엇
object지금 들어온 리소스. 삭제 요청에서는 null이다
oldObject수정 전 상태. 생성 요청에서는 null이다
paramsparamKind로 연결한 외부 리소스 (26.5)

목록을 다루는 all()·exists()·map()이 자주 쓰인다. containers.all(c, 조건)은 "모든 컨테이너가 조건을 만족한다"이고, 컨테이너가 하나도 없으면 참이다. 빈 목록에서 all()이 참이 되는 것은 CEL만의 규칙이 아니라 수학적 관례인데, 정책을 쓸 때는 "조건을 만족하는 것이 하나도 없다"와 "전부 만족한다"가 같은 값이 되는 지점이므로 주의한다.

CEL이 못 하는 것도 분명하다. 외부에 HTTP 요청을 보낼 수 없고, 클러스터의 다른 리소스를 조회할 수 없으며(params 하나만 예외), 상태를 저장할 수 없다. "이미 같은 호스트를 쓰는 인그레스가 있는지"처럼 다른 리소스를 봐야 하는 규칙은 VAP로 만들 수 없다. 그때는 여전히 웹훅이 필요하고, 그 선택 기준은 26.8에 쓴다.

이 클러스터에 이미 들어 있다

VAP는 앞으로 쓸 기능이 아니라 이미 쓰이고 있는 기능이다. M13에서 Gateway API를 설치했을 때 정책 하나가 함께 들어왔다.

kubectl get validatingadmissionpolicy
출력
NAME VALIDATIONS PARAMKIND AGE safe-upgrades.gateway.networking.k8s.io 2 <unset> 2d

Gateway API가 자기 CRD를 보호하려고 싣고 온 것이다. 웹훅이었다면 그 프로젝트가 우리 클러스터에 파드와 인증서를 배포해야 했다. 정책 오브젝트 하나로 끝나는 것이 이 방식의 실질적인 이점이다.

26.3따라하기 ① latest 태그를 막는다

1단계 — 무엇을 쓸 수 있는지 먼저 본다

목적클러스터 버전에 따라 쓸 수 있는 것이 다르다. 특히 뮤테이팅 쪽은 최근에야 정식이 됐다.

kubectl api-resources --api-group=admissionregistration.k8s.io
출력
NAME APIVERSION NAMESPACED KIND mutatingadmissionpolicies admissionregistration.k8s.io/v1 false MutatingAdmissionPolicy mutatingadmissionpolicybindings admissionregistration.k8s.io/v1 false MutatingAdmissionPolicyBinding mutatingwebhookconfigurations admissionregistration.k8s.io/v1 false MutatingWebhookConfiguration validatingadmissionpolicies admissionregistration.k8s.io/v1 false ValidatingAdmissionPolicy validatingadmissionpolicybindings admissionregistration.k8s.io/v1 false ValidatingAdmissionPolicyBinding validatingwebhookconfigurations admissionregistration.k8s.io/v1 false ValidatingWebhookConfiguration
판정여섯 줄 전부 v1이고 NAMESPACED가 false다. 정책은 클러스터 범위라서 네임스페이스마다 만들지 않는다 — 범위를 좁히는 것은 바인딩의 일이다. 오래된 클러스터에서는 v1beta1로 나오거나 mutatingadmissionpolicies 줄이 아예 없을 수 있고, 그때는 이 모듈의 26.6을 건너뛴다.

2단계 — 정책을 쓴다

목적조직 규칙 하나를 CEL 표현식으로 옮긴다.

mkdir -p course/labs/k8s/policy
cat > course/labs/k8s/policy/00-no-latest.yaml <<'EOF'
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicy
metadata:
  name: no-latest-tag
spec:
  failurePolicy: Fail
  matchConstraints:
    resourceRules:
      - apiGroups:   ["apps"]
        apiVersions: ["v1"]
        operations:  ["CREATE", "UPDATE"]
        resources:   ["deployments", "statefulsets", "daemonsets"]
  validations:
    - expression: >-
        object.spec.template.spec.containers.all(c,
          !c.image.endsWith(":latest") && c.image.contains(":"))
      message: "이미지에 :latest 를 쓰거나 태그를 생략할 수 없다. 고정 태그나 다이제스트를 쓴다."
      reason: Invalid
EOF
kubectl apply -f course/labs/k8s/policy/00-no-latest.yaml
필드뜻
failurePolicy표현식 평가 자체가 실패했을 때. Fail은 거부, Ignore는 통과. 26.7에서 이 값의 무게를 본다
matchConstraints어떤 리소스의 어떤 동사를 볼 것인가. 파드가 아니라 컨트롤러를 대상으로 한 이유는 아래에 쓴다
expression참이면 통과. contains(":")는 태그를 아예 생략한 nginx도 잡으려는 것이다
reason거부 시 HTTP 상태 코드로 번역된다. Invalid는 422

대상을 파드가 아니라 디플로이먼트로 잡은 이유는 M24에서 배운 것이다. 파드에 걸면 거부가 레플리카셋 컨트롤러의 이벤트로 가서, apply를 친 사람은 아무 메시지도 받지 못한다. 컨트롤러를 대상으로 잡아야 거부가 사람의 터미널에 도착한다.

3단계 — 정책만 있을 때 무슨 일이 일어나는지 본다

목적정책과 바인딩이 나뉘어 있다는 것을 말이 아니라 결과로 확인한다.

kubectl create ns m26
cat <<'EOF' | kubectl -n m26 apply -f -
apiVersion: apps/v1
kind: Deployment
metadata: {name: bad}
spec:
  replicas: 1
  selector: {matchLabels: {app: bad}}
  template:
    metadata: {labels: {app: bad}}
    spec:
      containers:
        - name: web
          image: nginx:latest
EOF
출력
deployment.apps/bad created
판정경고도 거부도 없다. 정책만 만들면 아무것도 검사하지 않는다. M23에서 Role만 만들고 RoleBinding을 빼먹었을 때와 같은 상황이고, 이것이 "정책을 넣었는데 안 막혀요"의 첫 번째 원인이다.

4단계 — 경고부터 붙인다

목적운영 클러스터에 정책을 넣는 순서를 그대로 따른다. 처음부터 거부로 넣지 않는다.

kubectl label ns m26 policy=enforced

cat <<'EOF' | kubectl apply -f -
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicyBinding
metadata:
  name: no-latest-tag-binding
spec:
  policyName: no-latest-tag
  validationActions: [Warn]
  matchResources:
    namespaceSelector:
      matchLabels:
        policy: enforced
EOF
sleep 5

sleep 5가 실습 편의를 위한 것이 아니다. 바인딩을 만들거나 고친 직후 몇 초 동안은 이전 동작이 나온다. 실측에서 바인딩을 만들자마자 친 요청은 경고 없이 통과했고, 5초 뒤 같은 요청에 경고가 붙었다. 정책을 CI에서 테스트할 때 이 지연을 넣지 않으면 테스트가 간헐적으로 통과한다.

cat <<'EOF' | kubectl -n m26 apply -f -
apiVersion: apps/v1
kind: Deployment
metadata: {name: bad3}
spec:
  replicas: 1
  selector: {matchLabels: {app: bad3}}
  template:
    metadata: {labels: {app: bad3}}
    spec:
      containers:
        - name: web
          image: nginx:latest
EOF
출력
Warning: Validation failed for ValidatingAdmissionPolicy 'no-latest-tag' with binding 'no-latest-tag-binding': 이미지에 :latest 를 쓰거나 태그를 생략할 수 없다. 고정 태그나 다이제스트를 쓴다. deployment.apps/bad3 created
판정경고가 나오고 생성은 된다. 이 상태로 며칠 두면 팀의 CI 로그와 터미널에 경고가 쌓이고, 그 사이에 매니페스트를 고칠 시간이 생긴다. 메시지에 정책 이름과 바인딩 이름이 둘 다 들어 있는 것이 중요하다 — 정책은 하나인데 바인딩이 여러 개일 때 어느 범위에서 걸렸는지 알아야 한다.

5단계 — 거부로 승격한다

목적정책 파일을 건드리지 않고 바인딩 한 줄로 강도를 바꾼다.

kubectl patch validatingadmissionpolicybinding no-latest-tag-binding --type=json \
  -p '[{"op":"replace","path":"/spec/validationActions","value":["Deny"]}]'
sleep 5

cat <<'EOF' | kubectl -n m26 apply -f -
apiVersion: apps/v1
kind: Deployment
metadata: {name: bad2}
spec:
  replicas: 1
  selector: {matchLabels: {app: bad2}}
  template:
    metadata: {labels: {app: bad2}}
    spec:
      containers:
        - name: web
          image: nginx:latest
EOF
출력
The deployments "bad2" is invalid: : ValidatingAdmissionPolicy 'no-latest-tag' with binding 'no-latest-tag-binding' denied request: 이미지에 :latest 를 쓰거나 태그를 생략할 수 없다. 고정 태그나 다이제스트를 쓴다.
판정Warning:이 is invalid:로 바뀌었고 created 줄이 사라졌다. 우리가 쓴 message가 그대로 사람에게 전달된다는 점이 중요하다 — 메시지는 오류 문구가 아니라 지시문으로 쓴다. "정책 위반"이라고만 쓰면 받은 사람이 무엇을 고쳐야 할지 모른다.

26.4따라하기 ② 이미 배포된 위반을 찾는다

26.3의 bad와 bad3은 아직 돌고 있다. 정책은 새 요청에만 걸리기 때문이다. 운영에서 이 성질은 안전장치이면서 동시에 함정이다 — 정책을 켰다고 클러스터가 깨끗해지지 않는다.

1단계 — 아직 돌고 있는지 확인한다

목적"거부됐다"와 "사라졌다"를 구분한다.

kubectl -n m26 get deploy
출력
NAME READY UP-TO-DATE AVAILABLE AGE bad 1/1 1 1 4m bad3 1/1 1 1 3m34s
판정nginx:latest로 만든 둘이 정상 동작 중이다. 다음에 이 디플로이먼트를 수정하려는 순간 거부당한다 — matchConstraints에 UPDATE를 넣었기 때문이다. 즉 위반은 "지금 배포를 시도한 사람"이 아니라 다음에 이 리소스를 건드리는 사람에게 터진다.

2단계 — 한 번에 훑어보면 왜 안 되는지 본다

목적먼저 떠오르는 방법을 시도해서 그 한계를 확인한다.

kubectl get deploy,sts,ds -A -o yaml | kubectl apply --dry-run=server -f - 2>&1 | grep 'no-latest-tag'
출력
Warning: Validation failed for ValidatingAdmissionPolicy 'no-latest-tag' with binding 'no-latest-tag-binding': 이미지에 :latest 를 쓰거나 태그를 생략할 수 없다. 고정 태그나 다이제스트를 쓴다.
판정위반이 있다는 것은 알겠는데 어느 리소스인지가 없다. 경고는 요청 단위로 나오는데 이 방식은 여러 리소스를 한 요청에 담았기 때문이다. 하나씩 돌려야 이름이 붙는다.

3단계 — 감사 스크립트를 만든다

목적정책을 Deny로 올리기 전에 반드시 하는 작업을 재실행 가능한 형태로 남긴다.

cat > course/labs/scripts/policy-audit.sh <<'EOF'
#!/usr/bin/env bash
set -u
POLICY="${1:-no-latest-tag}"

RESULT=$(
  kubectl get deploy,sts,ds -A \
    -o custom-columns=K:.kind,NS:.metadata.namespace,N:.metadata.name --no-headers |
  while read -r KIND NS NAME; do
    HIT=$(kubectl -n "$NS" get "$KIND" "$NAME" -o yaml |
          kubectl apply --dry-run=server -f - 2>&1 |
          grep -c "ValidatingAdmissionPolicy '$POLICY'")
    [ "$HIT" -gt 0 ] && echo "위반: $NS/$KIND/$NAME"
  done
)
if [ -z "$RESULT" ]; then echo "(위반 없음)"; else echo "$RESULT"; fi
EOF
chmod +x course/labs/scripts/policy-audit.sh
bash course/labs/scripts/policy-audit.sh
출력
위반: m26/Deployment/bad 위반: m26/Deployment/bad3
판정클러스터 전체에서 이 둘만 나온다. 관측 스택·인그레스·게이트웨이·우리 앱 두 개를 모두 훑고도 위반이 없다는 뜻이고, 교재가 M02부터 지켜 온 태그 고정 규약이 실제로 지켜졌다는 증거다. 규칙을 정책으로 옮길 때 얻는 첫 번째 값이 이 숫자다 — 지키자는 결정보다 지금 몇 개가 어긋나 있는지가 먼저다.

스크립트에서 while을 파이프 뒤에 두면 서브셸에서 돌기 때문에 안에서 바꾼 변수가 밖으로 나오지 않는다. 그래서 결과를 RESULT에 모아서 마지막에 판정한다. 처음 쓸 때 이 함정에 걸려 "위반이 있는데도 (위반 없음)이 함께 출력되는" 상태가 됐다.

26.5따라하기 ③ 목록을 정책 밖으로 뺀다

"허용된 레지스트리만 쓴다"는 규칙을 그대로 CEL에 박으면, 레지스트리를 하나 추가할 때마다 정책을 다시 배포해야 한다. 정책 변경은 클러스터 전체에 영향을 주므로 승인 절차가 붙는 일이고, 목록 갱신이 그 절차를 타야 할 이유는 없다. paramKind가 그 둘을 분리한다.

1단계 — 목록을 컨피그맵에 둔다

목적바뀌는 것(목록)과 바뀌지 않는 것(검사 방식)을 다른 오브젝트로 나눈다.

kubectl create ns policy
kubectl -n policy create cm allowed-registries \
  --from-literal=registries='docker.io,ghcr.io,registry.k8s.io,quay.io'

2단계 — params를 읽는 정책을 쓴다

목적표현식이 길어질 때 variables로 쪼개는 방법을 함께 익힌다.

cat > course/labs/k8s/policy/10-allowed-registries.yaml <<'EOF'
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicy
metadata: {name: allowed-registries}
spec:
  failurePolicy: Fail
  paramKind: {apiVersion: v1, kind: ConfigMap}
  matchConstraints:
    resourceRules:
      - apiGroups:   ["apps"]
        apiVersions: ["v1"]
        operations:  ["CREATE", "UPDATE"]
        resources:   ["deployments", "statefulsets", "daemonsets"]
  variables:
    - name: allowed
      expression: "params.data.registries.split(',')"
    - name: images
      expression: "object.spec.template.spec.containers.map(c, c.image)"
  validations:
    - expression: >-
        variables.images.all(i,
          variables.allowed.exists(r, i.startsWith(r + '/'))
          || (!i.split('/')[0].contains('.') && 'docker.io' in variables.allowed))
      messageExpression: >-
        "허용되지 않은 레지스트리다. 허용 목록: " + params.data.registries
EOF
kubectl apply -f course/labs/k8s/policy/10-allowed-registries.yaml

messageExpression은 message와 달리 표현식이다. 거부 메시지에 실제 허용 목록을 넣을 수 있어서, 받은 사람이 정책 파일을 열어 보지 않고도 무엇이 허용되는지 안다.

variables는 표현식 안에서 variables.이름으로 참조한다. 같은 값을 여러 번 쓸 때 평가가 한 번만 일어나므로 성능에도 도움이 되지만, 실제 이유는 읽기 쉬워서다 — 한 줄짜리 CEL은 두 달 뒤에 아무도 못 읽는다.

두 번째 조건절(!i.split('/')[0].contains('.'))의 이유는 26.7 실패 ②에서 만든다. 지금은 이 줄이 없다고 생각하고 넘어가도 된다.

3단계 — 바인딩에서 어느 컨피그맵을 쓸지 지정한다

목적같은 정책을 환경마다 다른 목록으로 굴리는 구조를 만든다.

cat <<'EOF' | kubectl apply -f -
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicyBinding
metadata: {name: allowed-registries-binding}
spec:
  policyName: allowed-registries
  paramRef:
    name: allowed-registries
    namespace: policy
    parameterNotFoundAction: Deny
  validationActions: [Deny]
  matchResources:
    namespaceSelector:
      matchLabels: {policy: enforced}
EOF
sleep 5

parameterNotFoundAction: Deny는 컨피그맵이 없을 때의 동작이다. Allow로 두면 누군가 컨피그맵을 지우는 순간 정책이 조용히 무력화된다. 정책의 파라미터는 정책의 일부이므로 없으면 거부하는 쪽이 맞다.

cat <<'EOF' | kubectl -n m26 apply -f -
apiVersion: apps/v1
kind: Deployment
metadata: {name: evil}
spec:
  replicas: 1
  selector: {matchLabels: {app: evil}}
  template:
    metadata: {labels: {app: evil}}
    spec:
      containers: [{name: web, image: "evil.example.com/web:1.0"}]
EOF
출력
The deployments "evil" is invalid: : ValidatingAdmissionPolicy 'allowed-registries' with binding 'allowed-registries-binding' denied request: 허용되지 않은 레지스트리다. 허용 목록: docker.io,ghcr.io,registry.k8s.io,quay.io
판정메시지에 허용 목록이 들어 있다. 이 목록은 정책이 아니라 컨피그맵에서 온 값이다.

4단계 — 목록만 바꿔 본다

목적분리해 둔 값을 실제로 확인한다. 정책은 손대지 않는다.

kubectl -n policy patch cm allowed-registries \
  -p '{"data":{"registries":"docker.io,ghcr.io,registry.k8s.io,quay.io,evil.example.com"}}'
sleep 5
# 위와 완전히 같은 매니페스트를 다시 적용한다
출력
deployment.apps/evil created
판정정책 오브젝트는 그대로인데 판정이 바뀌었다. 운영에서는 이 컨피그맵을 다른 저장소·다른 승인 흐름에 둘 수 있다는 뜻이다 — 정책 변경은 플랫폼 팀, 목록 갱신은 보안 팀 식으로.

확인이 끝나면 목록을 원래대로 되돌린다.

kubectl -n policy patch cm allowed-registries \
  -p '{"data":{"registries":"docker.io,ghcr.io,registry.k8s.io,quay.io"}}'
kubectl -n m26 delete deploy evil

26.6따라하기 ④ 기본값을 주입한다

여기까지는 전부 거부였다. M24에서 매니페스트마다 손으로 넣은 automountServiceAccountToken: false를 아무도 쓰지 않아도 붙게 만든다. 검증이 아니라 변형이다.

1단계 — 파드를 대상으로 걸어 본다

목적가장 자연스러운 선택(토큰은 파드의 속성이니 파드에 건다)이 어떻게 되는지 먼저 본다.

cat <<'EOF' | kubectl apply -f -
apiVersion: admissionregistration.k8s.io/v1
kind: MutatingAdmissionPolicy
metadata: {name: default-no-token-pod}
spec:
  failurePolicy: Fail
  reinvocationPolicy: Never
  matchConstraints:
    resourceRules:
      - apiGroups: [""]
        apiVersions: ["v1"]
        operations: ["CREATE"]
        resources: ["pods"]
  mutations:
    - patchType: ApplyConfiguration
      applyConfiguration:
        expression: >-
          Object{ spec: Object.spec{ automountServiceAccountToken: false } }
---
apiVersion: admissionregistration.k8s.io/v1
kind: MutatingAdmissionPolicyBinding
metadata: {name: default-no-token-pod-binding}
spec:
  policyName: default-no-token-pod
  matchResources:
    namespaceSelector:
      matchLabels: {policy: enforced}
EOF
sleep 6
kubectl -n m26 run tokentest --image=curlimages/curl:8.19.0 --restart=Never \
  --command -- sleep 300
kubectl -n m26 wait --for=condition=Ready pod/tokentest --timeout=90s

Object{...} 문법은 부분 적용 구성이다. 전체 파드 스펙을 다시 쓰는 게 아니라 바꿀 필드만 적으면 서버가 병합한다. reinvocationPolicy: Never는 다른 변형이 이 뒤에 리소스를 또 바꿔도 다시 부르지 않는다는 뜻이고, 정책끼리 무한히 서로를 되돌리는 상황을 막는다.

kubectl -n m26 get po tokentest -o jsonpath='{.spec.automountServiceAccountToken}{"\n"}'
kubectl -n m26 exec tokentest -- ls /var/run/secrets/kubernetes.io/serviceaccount/
출력
false ca.crt namespace token
판정필드는 false인데 토큰이 그대로 마운트돼 있다. 26.2에서 본 순서 때문이다 — 서비스어카운트 어드미션이 토큰 볼륨을 먼저 넣었고, 그 뒤에 우리 정책이 필드만 바꿨다. 필드는 "볼륨을 넣을지 말지 결정할 때 참조되는 값"이지 볼륨을 지우는 스위치가 아니다.

2단계 — 대상을 디플로이먼트로 옮긴다

목적파드가 만들어지기 전에 템플릿을 고치면 순서 문제가 사라지는지 확인한다.

kubectl delete mutatingadmissionpolicybinding default-no-token-pod-binding
kubectl delete mutatingadmissionpolicy default-no-token-pod
kubectl -n m26 delete pod tokentest

cat > course/labs/k8s/policy/20-default-no-token.yaml <<'EOF'
apiVersion: admissionregistration.k8s.io/v1
kind: MutatingAdmissionPolicy
metadata: {name: default-no-token}
spec:
  failurePolicy: Fail
  reinvocationPolicy: Never
  matchConstraints:
    resourceRules:
      - apiGroups:   ["apps"]
        apiVersions: ["v1"]
        operations:  ["CREATE", "UPDATE"]
        resources:   ["deployments"]
  mutations:
    - patchType: ApplyConfiguration
      applyConfiguration:
        expression: >-
          Object{ spec: Object.spec{ template: Object.spec.template{
            spec: Object.spec.template.spec{ automountServiceAccountToken: false } } } }
---
apiVersion: admissionregistration.k8s.io/v1
kind: MutatingAdmissionPolicyBinding
metadata: {name: default-no-token-binding}
spec:
  policyName: default-no-token
  matchResources:
    namespaceSelector:
      matchLabels: {policy: enforced}
EOF
kubectl apply -f course/labs/k8s/policy/20-default-no-token.yaml
sleep 6

cat <<'EOF' | kubectl -n m26 apply -f -
apiVersion: apps/v1

출력

판정템플릿에 필드가 붙었고, 볼륨 목록이 비어 있고, 토큰 디렉터리 자체가 없다. 아무도 매니페스트에 그 줄을 쓰지 않았는데 M24에서 손으로 넣었던 설정이 자동으로 적용된 것이다. 변형 정책은 "어느 리소스를 대상으로 하는가"가 효과를 좌우한다 — 같은 표현식이 대상에 따라 되기도 하고 안 되기도 한다.

변형 정책은 남이 쓴 매니페스트를 몰래 바꾸는 도구다. 배포한 사람이 자기 YAML과 클러스터의 실제 상태가 다르다는 것을 모르면 디버깅이 아주 어려워진다. 그래서 변형은 기본값을 채우는 데만 쓰고, 사용자가 명시한 값을 덮어쓰지 않는 것이 관례다. 위 표현식도 사용자가 true를 명시했다면 그것을 덮어쓴다 — 실제 운영에 넣는다면 has(object.spec.template.spec.automountServiceAccountToken)으로 이미 값이 있는지 먼저 확인하는 조건을 붙여야 한다.

26.7일부러 실패시키기

실패 ① — 표현식 오타가 클러스터의 배포를 전부 막는다

목적정책 하나의 오타가 어디까지 번지는지 본다. 이 모듈에서 가장 위험한 실수다.

cat <<'EOF' | kubectl apply -f -
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicy
metadata: {name: broken-cel}
spec:
  failurePolicy: Fail
  matchConstraints:
    resourceRules:
      - apiGroups: ["apps"]
        apiVersions: ["v1"]
        operations: ["CREATE","UPDATE"]
        resources: ["deployments"]
  validations:
    - expression: "object.spec.replicas > '3'"
      message: "레플리카는 3 이하"
EOF
출력
validatingadmissionpolicy.admissionregistration.k8s.io/broken-cel created

숫자와 문자열을 비교하는 표현식인데 생성이 성공했다. 오류는 다른 곳에 있다.

kubectl get validatingadmissionpolicy broken-cel -o jsonpath='{.status}' | python3 -m json.tool
출력
{ "observedGeneration": 1, "typeChecking": { "expressionWarnings": [ { "fieldRef": "spec.validations[0].expression", "warning": "apps/v1, Kind=Deployment: ERROR: <input>:1:22: found no matching overload for '_>_' applied to '(int, string)'\n | object.spec.replicas > '3'\n | .....................^\n" } ] } }

이 상태로 Deny 바인딩을 붙이고, 위반이 전혀 없는 디플로이먼트를 올린다.

cat <<'EOF' | kubectl apply -f -
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicyBinding
metadata: {name: broken-cel-binding}
spec:
  policyName: broken-cel
  validationActions: [Deny]
  matchResources:
    namespaceSelector:
      matchLabels: {policy: enforced}
EOF
sleep 6
# image: nginx:1.29-alpine — 태그도 레지스트리도 문제없는 디플로이먼트
출력
The deployments "good" is invalid: : ValidatingAdmissionPolicy 'broken-cel' with binding 'broken-cel-binding' denied request: expression 'object.spec.replicas > '3'' resulted in error: no such overload
판정정책과 아무 상관 없는 배포가 거부됐다. failurePolicy: Fail은 "평가에 실패하면 거부"라는 뜻이고, 표현식이 깨져 있으면 모든 요청의 평가가 실패한다. 바인딩의 범위가 클러스터 전체였다면 그 클러스터의 모든 디플로이먼트 배포가 이 시점에 멈춘다.

막는 방법은 셋이다. 첫째, 정책을 만든 뒤 status.typeChecking을 확인한다. 비어 있어야 한다. 둘째, 바인딩을 항상 [Warn]으로 먼저 붙인다 — Warn에서는 평가 실패도 경고로만 나온다. 셋째, 좁은 네임스페이스에서 먼저 시험한다. 이 세 가지가 26.3의 승격 순서를 지켜야 하는 진짜 이유다.

kubectl delete validatingadmissionpolicybinding broken-cel-binding
kubectl delete validatingadmissionpolicy broken-cel

failurePolicy: Ignore로 두면 이 사고는 나지 않지만, 대신 정책이 조용히 아무것도 검사하지 않는 상태가 된다. 보안 정책에서는 대개 Fail이 맞고, 그래서 검증을 앞에 두는 것이다.

실패 ② — 레지스트리 정책이 도커 허브 이미지를 막는다

목적맞는 것 같은 표현식이 실제 이미지 이름 규칙과 어긋나는 지점을 찾는다.

26.5의 표현식에서 마지막 조건절을 빼고(즉 variables.allowed.exists(r, i.startsWith(r + '/'))만 남기고) 도커 허브 이미지를 배포한다.

# containers: [{name: c, image: "curlimages/curl:8.19.0"}]
출력
The deployments "tokendeploy" is invalid: : ValidatingAdmissionPolicy 'allowed-registries' with binding 'allowed-registries-binding' denied request: 허용되지 않은 레지스트리다. 허용 목록: docker.io,ghcr.io,registry.k8s.io,quay.io
판정docker.io가 허용 목록에 있는데 도커 허브 이미지가 막혔다. 이미지 이름에서 레지스트리 호스트가 생략돼 있기 때문이다. curlimages/curl은 컨테이너 런타임이 docker.io/curlimages/curl로 해석하지만, 정책이 보는 문자열에는 그 해석이 반영돼 있지 않다. 정책은 런타임이 아니라 문자열을 본다.

이 문제는 M02에서 다뤘던 이미지 이름 규칙과 같은 것이다. 호스트를 생략하면 도커 허브, 슬래시가 없으면 library/ 네임스페이스. 정책도 그 규칙을 알아야 한다.

    - expression: >-
        variables.images.all(i,
          variables.allowed.exists(r, i.startsWith(r + '/'))
          || (!i.split('/')[0].contains('.') && 'docker.io' in variables.allowed))

첫 구간에 점이 있으면 호스트, 없으면 생략된 것으로 본다. 완벽하지는 않다 — 포트가 붙은 localhost:5000/app이나 점 없는 사내 호스트명은 이 판별을 통과하지 못한다. 정책을 쓸 때는 이런 예외를 어디까지 감당할지를 먼저 정하고, 감당하지 않기로 한 것은 주석으로 남긴다.

고친 뒤
deployment.apps/tokendeploy created The deployments "evil2" is invalid: : ValidatingAdmissionPolicy 'allowed-registries' with binding 'allowed-registries-binding' denied request: 허용되지 않은 레지스트리다. 허용 목록: docker.io,ghcr.io,registry.k8s.io,quay.io
판정통과시킬 것은 통과하고 막을 것은 여전히 막힌다. 정책을 고칠 때는 항상 두 방향을 같이 확인한다 — 열었을 때 막던 것까지 열리지 않았는지. M25의 네트워크 정책에서 배운 것과 같은 습관이다.

26.8운영 관점 — 어디까지 정책으로 만들 것인가

VAP로 되는 것과 안 되는 것

VAP는 요청 하나만 보고 판정할 수 있는 규칙에 맞는다. 태그·레지스트리·리소스 요청 필수화·라벨 규약·레플리카 상한이 전부 여기 들어간다. 반대로 다른 리소스를 조회해야 하는 규칙(같은 호스트를 쓰는 인그레스가 이미 있는가), 외부 시스템에 물어봐야 하는 규칙(이 이미지가 스캐너에서 통과했는가), 상태를 기억해야 하는 규칙은 표현식만으로 만들 수 없다.

그 경우에 남는 선택이 웹훅이고, 웹훅을 직접 만드는 대신 정책 엔진을 쓴다. 책이 소개하는 게이트키퍼는 제약 조건 템플릿(Rego로 검사 로직)과 제약 조건(적용 범위)을 나누는데, VAP의 정책·바인딩 분리는 그 구조를 쿠버네티스가 내장한 것이다. 지금 새로 시작한다면 먼저 VAP로 써 보고, 표현식으로 안 되는 것만 엔진에 맡기는 순서가 맞다. 엔진 하나를 운영하는 비용이 규칙 몇 개보다 크기 때문이다.

이미지 서명 검증은 여기서 하지 않는다

M07에서 이미지 서명을 예고했다. 서명 검증은 레지스트리에 붙어 서명을 내려받고 공개 키로 검증해야 하므로 CEL로는 불가능하다. 집행 지점은 어드미션이 맞지만 구현은 전용 컨트롤러(예: 정책 엔진의 이미지 검증 기능)를 쓴다. 이 교재에서는 M29의 CI에서 서명을 만드는 쪽을 다루고, 클러스터에서 검증하는 쪽은 구조만 설명한다 — 키 관리까지 실습에 넣으면 모듈 하나로 끝나지 않는다.

정책을 조직에 넣는 순서

이 모듈에서 밟은 순서가 그대로 실무 순서다. 정책을 쓴다 → status.typeChecking이 비었는지 본다 → 좁은 네임스페이스에 Warn으로 붙인다 → 감사 스크립트로 기존 위반을 센다 → 위반이 0이 되면 범위를 넓히고 Deny로 올린다. 이 중 어느 단계를 건너뛰어도 26.7의 사고가 난다.

범위를 넓힐 때 kube-system은 대개 제외한다. 시스템 구성요소는 우리가 고칠 수 없는 매니페스트로 배포되고, 거기서 정책이 걸리면 클러스터 복구가 막힌다. 바인딩의 namespaceSelector에 matchExpressions로 NotIn 조건을 쓴다.

  matchResources:
    namespaceSelector:
      matchExpressions:
        - {key: kubernetes.io/metadata.name, operator: NotIn, values: [kube-system]}

M24에서 PSA의 privileged 수준을 시스템 네임스페이스에 남겨 둔 것과 같은 판단이다. 정책은 우리가 고칠 수 있는 것에만 건다.

26.9체크포인트와 정리

다음 모듈로 넘어가기 전 확인
  • kubectl get validatingadmissionpolicy no-latest-tag allowed-registries -o name | wc -l → 2
  • kubectl get validatingadmissionpolicy no-latest-tag -o jsonpath='{.status.typeChecking}' → {}
  • kubectl get validatingadmissionpolicybinding no-latest-tag-binding -o jsonpath='{.spec.validationActions}' → ["Deny"]
  • kubectl -n m26 create deploy x --image=nginx:latest --dry-run=server → denied request 문구가 나온다
  • kubectl -n m26 create deploy y --image=evil.example.com/w:1.0 --dry-run=server → 허용되지 않은 레지스트리
  • kubectl -n m26 create deploy z --image=registry.k8s.io/pause:3.10 --dry-run=server → created (server dry run)
  • bash course/labs/scripts/policy-audit.sh → 위반: m26/Deployment/bad가 목록에 있다
  • kubectl get mutatingadmissionpolicybinding default-no-token-binding -o name → 출력이 있다
  • kubectl -n m26 get deploy tokendeploy -o jsonpath='{.spec.template.spec.automountServiceAccountToken}' → false (매니페스트에는 그 줄이 없다)
  • kubectl -n policy get cm allowed-registries -o jsonpath='{.data.registries}' → docker.io,ghcr.io,registry.k8s.io,quay.io
  • kubectl get ns m26 -o jsonpath='{.metadata.labels.policy}' → enforced
  • ls course/labs/k8s/policy/ → 파일 4개
  • (이해 확인) Warn 바인딩과 failurePolicy: Ignore가 각각 무엇을 무력화하는지 구분해서 적는다
  • (이해 확인) 같은 변형 표현식을 파드에 걸었을 때와 디플로이먼트에 걸었을 때 결과가 달랐던 이유를 한 문장으로 적는다
이 모듈이 남기는 파일
  • course/labs/k8s/policy/00-no-latest.yaml — 정책 + Deny 바인딩
  • course/labs/k8s/policy/10-allowed-registries.yaml — policy 네임스페이스·컨피그맵·파라미터 정책
  • course/labs/k8s/policy/20-default-no-token.yaml — 변형 정책 (디플로이먼트 대상)
  • course/labs/k8s/policy/kustomization.yaml — kubectl apply -k로 한 번에
  • course/labs/scripts/policy-audit.sh — 기존 위반 감사. M29의 CI에서 다시 쓴다
  • 클러스터: 정책 2개 + 변형 정책 1개. policy=enforced 라벨이 붙은 네임스페이스에만 적용된다

정리

# 실습 네임스페이스를 지운다 (안의 디플로이먼트도 함께 사라진다)
kubectl delete ns m26 m26b --ignore-not-found

# 정책은 남긴다. 남아 있는지 확인
kubectl get validatingadmissionpolicy,mutatingadmissionpolicy --no-headers | awk '{print $1}'

정책과 policy 네임스페이스는 지우지 않는다. M27의 태세 점검에서 "정책이 걸리지 않은 네임스페이스"를 찾는 실습이 이 상태를 전제하고, M29의 CI 파이프라인이 policy-audit.sh를 그대로 호출한다.

journal과 apps에는 아직 policy=enforced 라벨을 붙이지 않았다. 지금 붙이면 우리 워크로드가 어떻게 되는지는 M27에서 감사와 함께 확인한다.
