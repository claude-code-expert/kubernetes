프로브와 파드 라이프사이클

M10에서 롤아웃 중 요청 17건이 실패했다. M14의 매니페스트에는 프로브 두 줄이 들어 있지만 왜 그 값인지는 아무도 설명하지 않았다. 이 모듈에서 프로브를 떼었다 붙였다 하며 실패 건수를 직접 센다. 프로브만으로는 0이 되지 않는다는 것을 숫자로 확인하고, 무엇이 남은 실패를 없애는지 찾는다.

사전 조건
  • M14 완료 — journal 네임스페이스에 저널 애플리케이션이 떠 있다. 확인: kubectl get deploy,sts -n journal에 journal-api 3/3, web-static 2/2, redis 1/1
  • 이미지 journal-api:v1과 journal-api:v2가 kind 노드에 적재돼 있다 (M07). 확인: docker exec study-worker crictl images | grep journal이 두 줄
  • 고칠 파일: course/labs/k8s/journal/30-journal-api.yaml — 이 모듈이 정본으로 고친다
  • 새로 쓰는 파일: course/labs/scripts/loadgen.sh
  • 꼬였으면: bash course/labs/scripts/rebuild.sh로 M14 상태로 되돌린다

핵심 3줄

1. 롤아웃 중 실패 건수를 재는 측정 도구를 세우고, 프로브를 떼었다 붙이며 그 숫자가 어떻게 변하는지 직접 센다.

2. readiness가 언제 일하고 언제 일하지 않는지를 구분한다 — 빠르게 뜨는 앱에서는 아무것도 하지 않고, 느리게 뜨는 앱에서는 실패율을 90%에서 0.4%로 끌어내린다.

3. 남은 실패를 preStop으로 0으로 만들고, liveness가 느린 시작을 죽이는 CrashLoop을 재현한 뒤 startupProbe로 고친다.

15.1왜 프로브 두 줄로는 부족한가 15.2이론 — 프로브 셋과 종료 창 15.3따라하기 ① 재는 도구부터 세운다 15.4따라하기 ② 프로브를 떼고 재본다 15.5따라하기 ③ 느린 시작을 흉내 낸다 15.6따라하기 ④ 종료 창을 닫는다 15.7일부러 실패시키기 — liveness가 앱을 죽인다 15.8운영 관점 — 값은 어떻게 정하나 15.9체크포인트와 정리

15.1왜 프로브 두 줄로는 부족한가

M10에서 롤링 업데이트를 하며 요청 루프를 돌렸을 때 실패가 17건 나왔다. 그때는 "이건 M15에서 해결한다"고 미뤄 뒀다. M14에서 저널 애플리케이션을 매니페스트로 다시 쓸 때 readinessProbe와 livenessProbe를 넣었지만, periodSeconds: 2가 왜 2인지, 그 두 줄이 17건을 실제로 없앴는지는 확인하지 않았다.

흔한 설명은 이렇다 — "레디니스 프로브를 넣으면 준비되지 않은 파드로 트래픽이 가지 않으므로 무중단 배포가 된다." 절반만 맞는 말이다. 이 모듈에서 실제로 재보면 프로브를 아예 다 떼어도 실패 건수가 거의 같은 구간이 있고, 반대로 프로브 하나가 실패율을 90%에서 0.4%로 바꾸는 구간이 있다. 둘을 가르는 것은 프로브의 유무가 아니라 애플리케이션이 뜨는 데 걸리는 시간이다.

그리고 프로브를 제대로 넣어도 남는 실패가 있다. 파드가 종료될 때 엔드포인트 목록에서 빠지는 일과 프로세스가 죽는 일이 동시에 끝나지 않기 때문이다. 이 시간 차를 종료 창이라고 부르겠다. 프로브는 이 문제를 고치지 못한다 — 프로브는 "이 파드가 지금 어떤 상태인가"를 보고할 뿐, 종료 순서를 조정하지 않는다. 무엇이 고치는지는 15.6에서 숫자로 확인한다.

이 모듈은 설명을 먼저 하지 않는다. 재는 도구를 세우고, 구성을 하나씩 바꿔가며 실패 건수를 센다. 이론은 그 숫자를 설명하는 데 필요한 만큼만 15.2에 둔다.

15.2이론 — 프로브 셋과 종료 창

책 5.7은 롤링 업데이트의 안전장치로 레디니스 프로브 readiness probe와 서비스 수준의 헬스 체크 두 가지를 든다. 쿠버네티스가 실제로 제공하는 프로브는 셋이고, 셋은 실패했을 때 무슨 일이 일어나는가로 나뉜다.

프로브묻는 것실패하면언제 도는가
readinessProbe지금 트래픽을 받을 준비가 됐는가엔드포인트에서 빠진다. 컨테이너는 그대로 산다컨테이너가 사는 내내
livenessProbe살아 있는가. 재시작이 답인 상태인가컨테이너를 재시작한다startup이 성공한 뒤부터
startupProbe아직 뜨는 중인가임계값을 다 쓰면 컨테이너를 재시작한다기동 시 한 번. 성공하면 더 이상 돌지 않는다

readiness와 liveness를 가르는 기준은 "실패했을 때 기다리면 나아지는가"다. 데이터베이스 커넥션 풀이 아직 안 찼다면 기다리면 낫는다 — readiness다. 이벤트 루프가 데드락에 빠져 영영 돌아오지 않는다면 기다려도 낫지 않는다 — liveness다. 이 구분을 놓치고 liveness에 readiness의 조건을 넣으면, 잠깐 느려진 것만으로 컨테이너가 재시작되고 부하가 남은 파드로 몰려 연쇄 재시작이 난다.

startupProbe는 나머지 둘과 성격이 다르다. 기동에만 관여하고, 성공한 뒤에는 완전히 사라진다. 이것이 있는 이유는 liveness의 임계값이 두 가지 서로 다른 시간을 동시에 맡을 수 없기 때문이다. 뜨는 데 40초 걸리는 앱을 liveness 하나로 감당하려면 임계값을 40초보다 크게 잡아야 하는데, 그러면 정상 운영 중에 앱이 멎었을 때도 40초를 기다린 뒤에야 재시작한다. startupProbe가 기동 구간을 떼어 맡으면 liveness는 운영 구간에 맞는 짧은 값을 쓸 수 있다.

종료 창 — 프로브가 고치지 못하는 것

파드를 지우라는 명령이 apiserver에 닿으면 두 가지 일이 병렬로 시작된다. 하나는 엔드포인트 컨트롤러가 엔드포인트슬라이스 EndpointSlice에서 이 파드를 빼고, 그 변경이 각 노드의 kube-proxy와 인그레스 컨트롤러까지 전파되는 경로다(M11에서 본 그 목록이다). 다른 하나는 kubelet이 컨테이너에 SIGTERM을 보내고 프로세스가 종료되는 경로다.

둘 중 뒤쪽이 훨씬 빠르다. 프로세스는 밀리초 단위로 죽고, 규칙 전파는 여러 컴포넌트를 거친다. 그 사이 트래픽 규칙에는 아직 남아 있는데 받을 프로세스가 없는 구간이 생긴다. 여기로 들어온 요청이 실패한다.

preStop 훅은 SIGTERM을 보내기 전에 실행되고, 훅이 끝날 때까지 kubelet은 SIGTERM을 보내지 않는다. 그래서 preStop에 sleep을 넣으면 프로세스가 그만큼 더 살아서 응답한다 — 규칙 전파가 끝날 시간을 벌어 주는 것이다. 애플리케이션을 고치는 것이 아니라 죽는 순서를 늦추는 처방이다.

이 sleep이 도는 동안에도 terminationGracePeriodSeconds는 함께 흐른다. 이 시간을 넘기면 kubelet이 SIGKILL로 끊으므로, preStop을 늘릴 때는 유예 시간도 같이 늘려야 한다. 둘의 관계를 모르고 preStop만 30초로 잡으면 유예 시간 기본값 30초에 걸려 앱이 커넥션을 닫을 시간을 못 받는다.

책과 다른 점 책 5.7은 "레디니스 프로브를 두면 무중단 배포가 된다"는 취지로 서술한다. 이 모듈의 실측에서는 레디니스 프로브만으로는 0이 되지 않았다. 종료 창은 프로브가 아니라 preStop과 유예 시간이 닫는다. 책이 틀렸다기보다 2024년 시점에 널리 쓰이던 설명이 종료 쪽을 생략한 것이고, 이 모듈은 그 생략된 절반을 숫자로 채운다. 근거: kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/ (Termination of Pods) · 2026-09-05 접근

15.3따라하기 ① 재는 도구부터 세운다

실패 건수를 비교하려면 먼저 아무것도 하지 않을 때 실패가 0인 도구가 있어야 한다. 이것을 확인하지 않고 재면, 도구가 흘리는 실패를 롤아웃 탓으로 돌리게 된다.

1단계 — 부하 스크립트를 만든다

목적클러스터 안에서 서비스에 직접 요청을 보내며 응답 코드를 세는 도구를 둔다.

M10의 curlbox는 M14 6단계에서 지웠다. 여기서 다시 만드는데, 이번에는 sleep infinity로 띄워 수명 제한이 없게 하고 스크립트로 감싼다. course/labs/scripts/loadgen.sh로 저장한다.

#!/usr/bin/env bash
# course/labs/scripts/loadgen.sh
#   start   부하 시작 (curlbox 가 없으면 만든다)
#   report  지금까지의 코드 분포
#   reset   카운터만 0으로
#   stop    부하 종료
#   clean   부하 종료 + curlbox 삭제
set -uo pipefail

NS="${NS:-journal}"
SVC="${SVC:-journal-api}"
PORT="${PORT:-8080}"
PATHNAME="${PATHNAME:-/api/entries}"
PARALLEL="${PARALLEL:-4}"
INTERVAL="${INTERVAL:-0.02}"
POD=curlbox

k() { kubectl -n "$NS" "$@"; }

ensure_pod() {
  if ! k get pod "$POD" >/dev/null 2>&1; then
    echo "curlbox 가 없다. 만든다."
    k run "$POD" --image=alpine:3.22 --restart=Never -- sleep infinity >/dev/null
    k wait --for=condition=Ready "pod/$POD" --timeout=90s >/dev/null
  fi
  k exec "$POD" -- sh -c 'command -v curl >/dev/null || apk add -q curl'
}

case "${1:-}" in
  start)
    ensure_pod
    k exec "$POD" -- sh -c "
      rm -f /tmp/codes.*.txt
      touch /tmp/run
      i=1
      while [ \$i -le $PARALLEL ]; do
        ( while [ -f /tmp/run ]; do
            curl -s -o /dev/null -w '%{http_code}\n' --max-time 2 \
              http://$SVC:$PORT$PATHNAME >> /tmp/codes.\$i.txt 2>/dev/null
            sleep $INTERVAL
          done ) &
        i=\$((i+1))
      done
    " >/dev/null 2>&1 &
    sleep 3
    echo "부하 시작 — $SVC:$PORT$PATHNAME 에 동시 $PARALLEL 줄, 요청 간격 ${INTERVAL}초"
    echo "멈추려면: bash \$0 stop"
    ;;
  report)
    echo "요청 수 / 응답 코드 분포:"
    k exec "$POD" -- sh -c 'cat /tmp/codes.*.txt 2>/dev/null | wc -l; cat /tmp/codes.*.txt 2>/dev/null | sort | uniq -c | sort -rn'
    ;;
  reset)
    k exec "$POD" -- sh -c 'for f in /tmp/codes.*.txt; do : > "$f"; done' 2>/dev/null
    echo "카운터를 0으로 되돌렸다. 부하는 계속 돈다."
    ;;
  stop)
    k exec "$POD" -- sh -c 'rm -f /tmp/run' 2>/dev/null
    sleep 2
    echo "부하 종료. 마지막 집계:"
    k exec "$POD" -- sh -c 'cat /tmp/codes.*.txt 2>/dev/null | wc -l; cat /tmp/codes.*.txt 2>/dev/null | sort | uniq -c | sort -rn'
    ;;
  clean)
    k exec "$POD" -- sh -c 'rm -f /tmp/run' 2>/dev/null
    k delete pod "$POD" --ignore-not-found
    ;;
  *)
    sed -n '3,12p' "$0"
    exit 1
    ;;
esac
값뜻
PARALLEL=4동시에 도는 요청 줄 수
INTERVAL=0.02한 줄이 요청과 요청 사이에 쉬는 시간. 넷을 합쳐 약 158 req/s
--max-time 22초 안에 응답이 없으면 실패로 센다. 종료 중인 파드에 붙어 무한정 기다리지 않기 위해서다
%{http_code}응답 코드만 찍는다. 연결 자체가 실패하면 curl은 000을 준다

이 도구는 인그레스를 거치지 않는다. 호스트에서 localhost:18080으로 재면 인그레스 컨트롤러가 업스트림 실패를 자체적으로 다시 시도해서, 파드가 실제로 떨어뜨린 요청이 가려진다(같은 롤아웃을 그 경로로 재면 1~3건으로 나온다). 이 모듈이 재려는 것은 컨트롤러의 재시도 성능이 아니라 서비스에서 파드까지 한 구간이므로, 그 구간만 남기고 잰다.

2단계 — 잡음 바닥을 확인한다

목적롤아웃을 하지 않는 동안 이 도구가 실패를 0으로 내는지 본다. 여기서 0이 아니면 이후 측정은 전부 무의미하다.

bash course/labs/scripts/loadgen.sh start
sleep 20
bash course/labs/scripts/loadgen.sh stop
출력
부하 시작 — journal-api:8080/api/entries 에 동시 4 줄, 요청 간격 0.02초 멈추려면: bash ./course/labs/scripts/loadgen.sh stop 부하 종료. 마지막 집계: 3156 3156 200
판정3156건 전부 200. 실패 0이면 도구가 쓸 만하다. 요청 수는 노트북 성능에 따라 다르지만 실패가 한 건이라도 나오면 병렬 수를 줄이거나 INTERVAL을 늘려 0이 나오는 설정을 먼저 찾는다.
부하를 세게 걸면 왜 안 되나 sleep을 빼고 동시 8줄로 올려 봤더니 롤아웃을 하지 않아도 37~93%가 실패했다. 요청이 초당 1700건을 넘으면서 curlbox 파드 하나가 소켓을 다 써 버린 것이다. 측정 도구가 측정 대상보다 먼저 무너진 상태이고, 이 상태에서 나온 숫자는 프로브와 아무 관계가 없다. 부하 자체를 목적으로 하는 측정은 M17 오토스케일링과 M37 로드 테스팅에서 k6로 한다.

15.4따라하기 ② 프로브를 떼고 재본다

지금 journal-api에는 M14에서 넣은 readiness와 liveness가 있다. 이 상태로 한 번 재고, 프로브를 다 뗀 상태로 한 번 더 재서 비교한다.

3단계 — 지금 구성 그대로 롤아웃한다

목적M14가 남긴 프로브 두 줄이 실제로 몇 건을 막고 있는지 기준값을 얻는다.

부하를 걸어 둔 채 이미지를 v1에서 v2로 바꾸고, 롤아웃이 끝나면 집계한다.

bash course/labs/scripts/loadgen.sh start
kubectl -n journal set image deploy/journal-api api=journal-api:v2
kubectl -n journal rollout status deploy/journal-api
sleep 6
bash course/labs/scripts/loadgen.sh stop
출력 (끝부분)
deployment "journal-api" successfully rolled out 부하 종료. 마지막 집계: 1584 1576 200 8 000
판정1584건 중 8건 실패(0.51%). 실패 코드가 전부 000이다 — HTTP 상태 코드가 아니라 연결 자체가 안 된 것이다. 502나 503이 아니라는 점이 중요하다. 받아 줄 프로세스가 아예 없었다는 뜻이고, 이것이 종료 창의 흔적이다.

4단계 — 프로브를 전부 떼고 같은 것을 잰다

목적프로브가 이 상황에서 실제로 얼마나 기여하는지 뺄셈으로 확인한다.

kubectl -n journal patch deploy journal-api --type=json \
  -p='[{"op":"remove","path":"/spec/template/spec/containers/0/readinessProbe"},
       {"op":"remove","path":"/spec/template/spec/containers/0/livenessProbe"}]'
kubectl -n journal rollout status deploy/journal-api

bash course/labs/scripts/loadgen.sh start
kubectl -n journal set image deploy/journal-api api=journal-api:v1
kubectl -n journal rollout status deploy/journal-api
sleep 6
bash course/labs/scripts/loadgen.sh stop
옵션뜻

왜 차이가 없었나

이 애플리케이션은 node dist/server.js 한 줄로 뜨고, 포트를 여는 데 0.3초쯤 걸린다. readiness 프로브가 "준비됐는가"를 처음 물으러 갈 때쯤이면 이미 준비돼 있다. readiness가 막을 요청이 애초에 없었던 것이다. 프로브를 떼자 롤아웃이 1초로 빨라진 것도 같은 이유다 — 기다릴 것이 없으니 확인 절차만 사라졌다.

그리고 남은 8~9건은 프로브를 넣든 빼든 그대로다. 이 실패는 새 파드가 뜨는 쪽이 아니라 옛 파드가 죽는 쪽에서 나오기 때문이다. readiness는 종료 순서에 관여하지 않는다.

여기서 두 갈래로 나뉜다. 시작이 느린 앱에서 readiness가 무엇을 하는지는 15.5에서, 종료 창을 무엇이 닫는지는 15.6에서 확인한다.

15.5따라하기 ③ 느린 시작을 흉내 낸다

readiness가 일하는 장면을 보려면 느리게 뜨는 앱이 필요하다. 저널 API를 고치는 대신 컨테이너의 command를 덮어써 8초를 지연시킨다. JVM 애플리케이션, 커넥션 풀 예열, 캐시 적재가 있는 서비스에서는 이 8초가 흉내가 아니다 — M19에서 두 번째 실습 앱으로 들어오는 Spring Boot order-api가 그 예다.

5단계 — 8초 늦게 뜨게 만든다 (프로브 없는 상태 그대로)

목적readiness 없이 느린 앱을 롤아웃하면 무슨 일이 벌어지는지 본다.

kubectl -n journal patch deploy journal-api --type=json \
  -p='[{"op":"add","path":"/spec/template/spec/containers/0/command",
        "value":["sh","-c","sleep 8; exec node dist/server.js"]}]'
kubectl -n journal rollout status deploy/journal-api

bash course/labs/scripts/loadgen.sh start
kubectl -n journal set image deploy/journal-api api=journal-api:v2
kubectl -n journal rollout status deploy/journal-api
sleep 6
bash course/labs/scripts/loadgen.sh stop

exec를 붙이는 이유는 M02에서 본 PID 1 문제다. exec 없이 sh -c "sleep 8; node ..."로 쓰면 sh가 PID 1이 되고 노드 프로세스는 자식이 되어, kubelet이 보낸 SIGTERM을 앱이 받지 못한다.

판정1515건 중 1360건 실패(89.8%). 그런데 rollout status는 2초 만에 successfully rolled out을 찍었다. 롤아웃이 성공을 보고하는 것과 서비스가 되는 것은 다른 일이다.

readiness가 없으면 kubelet은 컨테이너가 시작되는 즉시 파드를 Ready로 표시한다. 엔드포인트슬라이스에 IP가 올라가고 트래픽이 들어오는데, 그 안에서는 sleep 8이 돌고 있다. 세 파드가 차례로 교체되는 동안 서비스 뒤에 있는 파드 대부분이 이 상태였다.

롤아웃이 느려진 것이 아니다

2초에서 27초가 된 것을 두고 "프로브가 배포를 느리게 만든다"고 읽으면 거꾸로다. 이 앱은 파드 하나당 8초가 필요하고 파드가 셋이니, maxSurge: 1·maxUnavailable: 0으로 하나씩 교체하면 27초가 원래 걸려야 하는 시간이다. 프로브가 없던 2초는 빨랐던 것이 아니라 준비되지 않은 파드를 준비됐다고 보고한 시간이다.

이것이 readiness의 두 번째 역할이다. 트래픽을 막는 것이 첫째고, 롤아웃의 진행 속도를 실제 준비 속도에 묶는 것이 둘째다. maxUnavailable: 0이 의미를 갖는 것도 readiness가 있을 때뿐이다 — "사용 가능한 파드 수를 줄이지 않는다"는 약속에서 '사용 가능'을 판정하는 것이 readiness이기 때문이다.

남은 20건은 여전히 종료 쪽이다. 다음 절에서 닫는다.

15.6따라하기 ④ 종료 창을 닫는다

15.7일부러 실패시키기 — liveness가 앱을 죽인다

느린 시작 설정을 그대로 둔 채, liveness의 임계값을 조급하게 바꾼다. 흔히 하는 실수다 — "빨리 감지해야 좋은 것 아닌가" 하고 periodSeconds와 failureThreshold를 둘 다 낮춘다.

실패 ① 2초마다 확인하고 한 번 실패하면 재시작

재현 
kubectl -n journal patch deploy journal-api --type=json \
  -p='[{"op":"add","path":"/spec/template/spec/containers/0/livenessProbe",
        "value":{"httpGet":{"path":"/healthz","port":"http"},
                 "periodSeconds":2,"failureThreshold":1}}]'
kubectl -n journal set image deploy/journal-api api=journal-api:v2

sleep 75
kubectl -n journal get pods -l app=journal-api
출력
NAME READY STATUS RESTARTS AGE journal-api-68d5cfbd5b-mfnn2 1/1 Running 0 2m12s journal-api-74bd45f64-26qt7 0/1 Running 4 (31s ago) 80s journal-api-74bd45f64-6thhc 0/1 CrashLoopBackOff 3 (21s ago) 69s journal-api-74bd45f64-t2xr9 0/1 CrashLoopBackOff 3 (10s ago) 59s

파드 접미사와 시간은 환경마다 다르다. 새 파드 셋이 전부 0/1이고 RESTARTS가 올라가는데, 옛 파드 하나는 1/1 Running으로 남아 있다. maxUnavailable: 0이 지키고 있어 서비스는 계속되지만 롤아웃은 앞으로 나아가지 못한다.

원인 읽기 
kubectl -n journal describe pod journal-api-74bd45f64-t2xr9 | sed -n '/^Events:/,$p'
출력

Killing … failed liveness probe, will be restarted가 결정적인 줄이다. 그리고 두 프로브의 실패 횟수를 비교하면 사정이 보인다 — readiness는 21번 실패했는데 아무 일도 없었고, liveness는 4번 실패에 네 번 다 재시작이 일어났다. 같은 실패에 대해 두 프로브가 하는 일이 다르다는 것이 이 화면에 그대로 있다.

종료 이유를 본다

출력

판정Exit Code: 0이고 Reason: Completed다. 애플리케이션은 고장나지 않았다. SIGTERM을 받고 정상 종료했을 뿐이고, 죽인 것은 liveness다. CrashLoopBackOff를 보면 앱의 버그부터 의심하기 쉽지만, 종료 코드가 0이면 범인은 밖에 있다.

RESTARTS가 0이고 롤아웃이 끝났다. liveness는 그대로 periodSeconds: 2·failureThreshold: 1인데도 아무도 죽지 않았다. 실패가 사라진 것이 아니라 받아 낸 주체가 바뀐 것이다.

판정기동 중 8번 실패했지만 그것을 받은 것이 Startup probe다. startupProbe가 성공하기 전까지 liveness는 시작조차 하지 않으므로, 조급한 liveness 값이 기동을 방해하지 못한다. periodSeconds: 1 × failureThreshold: 30 = 30초가 이 앱에 허용된 기동 시간이고, 이를 넘기면 그때는 재시작하는 것이 맞다.

실패 ② preStop만 늘리고 유예 시간을 그대로 두면

재현하지 않는다 — 서술

preStop을 40초로 잡고 terminationGracePeriodSeconds를 기본값 30으로 두면, kubelet은 30초에 SIGKILL을 보낸다. preStop의 sleep이 아직 도는 중이므로 애플리케이션은 SIGTERM을 받아 보지도 못한 채 끊긴다. 커넥션을 정리할 기회가 없어져 오히려 실패가 늘어난다. 두 값은 항상 함께 움직여야 한다 — terminationGracePeriodSeconds는 preStop 시간에 앱이 커넥션을 닫는 시간을 더한 것보다 커야 한다.

15.8운영 관점 — 값은 어떻게 정하나

이 실습에서 preStop: sleep 10이 0을 만들었다고 해서 10초가 정답은 아니다. 이 값이 덮어야 하는 것은 엔드포인트 변경이 모든 트래픽 경로에 전파되는 시간이고, 그 시간은 노드 수, kube-proxy 모드, 인그레스 컨트롤러 종류, 서비스 메시 유무에 따라 달라진다. 노드 3개짜리 kind에서 10초면 충분했지만 노드가 수백 개인 클러스터에서는 더 걸릴 수 있고, 반대로 엔드포인트 변경을 직접 구독하는 게이트웨이를 쓰면 훨씬 짧아진다.

정하는 방법은 이 모듈이 한 그대로다. 부하를 걸고 롤아웃하면서 실패가 0이 되는 최소값을 찾은 뒤, 여유를 얹는다. 짐작으로 정한 값은 클러스터가 커질 때 조용히 깨진다.

프로브 값에도 같은 원칙이 적용되지만 방향이 다르다. periodSeconds를 줄이면 감지가 빨라지는 대신 kubelet이 보내는 요청이 늘고, 애플리케이션의 헬스 엔드포인트가 무거우면 그 자체가 부하가 된다. 헬스 엔드포인트에서 데이터베이스를 조회하는 구현을 자주 보는데, 이렇게 하면 데이터베이스가 잠깐 느려졌을 때 모든 파드의 liveness가 동시에 실패해 전체가 재시작된다. 장애를 감지하려고 넣은 장치가 장애를 증폭시키는 구조다. liveness는 프로세스 자신의 상태만 봐야 하고, 의존하는 외부 서비스의 상태는 readiness가 본다.

상황어느 프로브왜
데이터베이스에 아직 못 붙었다readiness기다리면 낫는다. 재시작해도 데이터베이스가 살아나지는 않는다
이벤트 루프가 멎어 응답이 없다liveness기다려도 낫지 않는다. 프로세스를 다시 만드는 것이 유일한 복구다
기동에 40초가 걸린다startupliveness 임계값을 40초로 늘리면 운영 중 감지도 40초가 된다
큐가 밀려 처리가 느려졌다readiness트래픽을 잠시 덜 받으면 회복된다. 재시작하면 처리 중이던 것까지 잃는다

마지막으로, 이 모듈이 고친 것은 labs/k8s/journal/30-journal-api.yaml이다. 같은 앱의 Helm 차트(labs/charts/journal/templates/api.yaml)에는 아직 startupProbe도 preStop도 없다. 두 정의가 여기서 갈라지기 시작하며, 이 상태는 M28까지 유지된다 — M28이 "왜 갈라졌고 어떻게 따라잡는가"를 실습 소재로 쓴다.

15.9체크포인트와 정리

매니페스트를 정본으로 고친다

지금까지는 kubectl patch로 실험했다. 실험 결과를 매니페스트에 옮겨 적어야 apply -k로 재현된다. course/labs/k8s/journal/30-journal-api.yaml의 컨테이너 부분을 아래로 바꾼다.

    spec:
      # preStop(10초) + 앱이 커넥션을 닫는 시간을 합친 것보다 넉넉해야 한다.
      # 이 시간을 넘기면 kubelet 이 SIGKILL 로 끊는다. 기본값도 30 이지만 명시한다 —
      # preStop 을 늘릴 때 함께 늘려야 하는 값이기 때문이다.
      terminationGracePeriodSeconds: 30
      containers:
        - name: api
          image: journal-api:v1
          # ... 생략: ports · env 는 M14 그대로 ...
          # ── 프로브 3종 (M15) ──────────────────────────────────────────────
          # startup: 느리게 뜨는 동안 liveness 가 죽이지 못하게 막는다.
          #   최대 1초 x 30회 = 30초를 기다린다. 이 시간을 넘기면 그때는 재시작이 맞다.
          startupProbe:
            httpGet:
              path: /healthz
              port: http
            periodSeconds: 1
            failureThreshold: 30
          # readiness: 트래픽을 받을 준비가 됐는가. 실패하면 엔드포인트에서 빠진다.
          #   레디스에 못 붙으면 앱이 503 을 돌려준다.
          readinessProbe:
            httpGet:
              path: /readyz
              port: http
            periodSeconds: 2
          # liveness: 살아 있는가. 실패하면 컨테이너를 재시작한다.
          #   startup 이 성공한 뒤에야 시작한다. 임계값을 readiness 보다 느슨하게 잡는다 —
          #   조급한 liveness 는 고치지 못하는 것을 재시작으로 덮으려 든다.
          livenessProbe:
            httpGet:
              path: /healthz
              port: http
            periodSeconds: 10
            failureThreshold: 3
          # preStop: 엔드포인트에서 빠지는 일과 프로세스가 죽는 일은 동시에 끝나지 않는다.
          #   그 사이가 종료 창이고, 여기서 요청이 떨어진다. 잠깐 더 살아서 시간을 벌어 준다.
          #   실측(M15): 없을 때 20건 실패 → 5초에서 2~3건 → 10초에서 0건.
          lifecycle:
            preStop:
              exec:
                command: ["sh", "-c", "sleep 10"]

10단계 — 흉내 낸 지연을 걷어내고 매니페스트로 되돌린다

목적실험용 command 덮어쓰기를 없애고, 파일이 클러스터의 진실이 되게 한다.

kubectl apply는 자기가 마지막으로 적용한 필드만 관리한다. command는 patch로 넣은 것이라 apply가 지우지 못하므로 직접 걷어내야 한다.

kubectl -n journal patch deploy journal-api --type=json \
  -p='[{"op":"remove","path":"/spec/template/spec/containers/0/command"}]'
kubectl apply -k course/labs/k8s/journal
kubectl -n journal rollout status deploy/journal-api
출력 (일부)
deployment.apps/journal-api configured statefulset.apps/redis unchanged deployment "journal-api" successfully rolled out
판정kubectl -n journal get deploy journal-api -o jsonpath='{.spec.template.spec.containers[0].command}'가 빈 값이면 지연이 걷혔다.

11단계 — 최종 구성으로 마지막 측정

목적파일에 적힌 그대로의 구성이 실패 0을 내는지 확인한다.

bash course/labs/scripts/loadgen.sh start
kubectl -n journal set image deploy/journal-api api=journal-api:v2
kubectl -n journal rollout status deploy/journal-api
sleep 6
bash course/labs/scripts/loadgen.sh stop
출력 (끝부분)
deployment "journal-api" successfully rolled out 부하 종료. 마지막 집계: 2692 2692 200
판정2692건 전부 200. 실패 0이면 이 모듈은 끝났다.
다음 모듈로 넘어가기 전 확인
  • bash course/labs/scripts/loadgen.sh start 후 20초 뒤 stop → 실패 0 (롤아웃 없이)
  • 부하를 건 채 kubectl -n journal set image deploy/journal-api api=journal-api:v2 → 집계에 000이 0건
  • kubectl -n journal get deploy journal-api -o jsonpath='{.spec.template.spec.containers[0].startupProbe.failureThreshold}' → 30
  • kubectl -n journal get deploy journal-api -o jsonpath='{.spec.template.spec.containers[0].lifecycle.preStop.exec.command}' → ["sh","-c","sleep 10"]
  • kubectl -n journal get deploy journal-api -o jsonpath='{.spec.template.spec.terminationGracePeriodSeconds}' → 30
  • kubectl -n journal get deploy journal-api -o jsonpath='{.spec.template.spec.containers[0].command}' → 빈 출력 (실험용 지연이 걷혔다)
  • 롤아웃 중 kubectl -n journal get endpointslices -l kubernetes.io/service-name=journal-api -o yaml | grep -c 'terminating: true' → 1 이상
  • kubectl -n journal get pods -l app=journal-api → READY 1/1 세 줄, RESTARTS 0
  • kubectl -n journal get pod curlbox → NotFound (정리했다면)
  • (이해 확인) 5단계의 89.8%와 4단계의 0.55%는 둘 다 readiness가 없는 구성이다. 왜 한쪽만 무너졌는지 한 문장으로 적어 본다
  • (이해 확인) 실패 ①에서 종료 코드가 0인데도 CrashLoopBackOff였다. 이때 무엇부터 의심해야 하는지 적어 본다
이 모듈이 남기는 파일
  • course/labs/scripts/loadgen.sh — 부하·집계 도구. M16 스케줄링과 M17 오토스케일링에서 다시 쓴다
  • course/labs/k8s/journal/30-journal-api.yaml — 프로브 3종 + preStop + terminationGracePeriodSeconds가 들어간 정본. M16이 여기에 resources를 더한다
  • labs/charts/journal/templates/api.yaml은 고치지 않았다. M28에서 차트가 이 변경을 따라잡는다
  • 클러스터: journal 네임스페이스가 프로브 3종을 갖춘 상태. curlbox는 정리했다

정리

부하 루프를 반드시 멈춘다. loadgen.sh가 띄운 루프는 파드 안에서 돌기 때문에 터미널을 닫아도 계속 요청을 보낸다.

# 부하 종료 + curlbox 삭제
bash course/labs/scripts/loadgen.sh clean

# 남아 있는지 확인 — 아무것도 나오지 않아야 한다
kubectl -n journal get pod curlbox
출력
pod "curlbox" deleted from journal namespace Error from server (NotFound): pods "curlbox" not found

NotFound가 정상이다. 저널 애플리케이션은 다음 모듈이 쓰므로 지우지 않는다. 실험 중 매니페스트와 클러스터가 어긋났다고 판단되면 bash course/labs/scripts/rebuild.sh로 M14 상태까지 되돌린 뒤 이 모듈의 매니페스트 변경만 다시 적용한다.

이 모듈은 파드가 언제 트래픽을 받고 언제 죽는지를 다뤘다.
