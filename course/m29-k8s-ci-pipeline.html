CI — 빌드·테스트·이미지

M28까지 만든 검사는 전부 손으로 쳐야 돌아간다. 이미지도 손으로 빌드해서 kind load로 넣었다. 이 모듈에서 커밋 하나가 타입 검사 → 테스트 → 이미지 → 스캔 → 어드미션 → 실제 기동을 지나가게 만든다. 그리고 두 관문이 실제로 파이프라인을 세우는 것을 본다 — 깨진 테스트 하나가 이미지를 만들지 못하게 하고, 베이스 이미지의 CVE 하나가 배포를 막는다.

후반100분Node 24 · Docker 29.x
2026-09-06 검증 (kind v0.33.0 · Kubernetes 1.37.0 · trivy 0.69.0) · 버전 숫자는 실습 당일 다시 확인한다
사전 조건
  • M28 완료 — 차트와 오버레이가 검사 가능한 상태다
  • M27의 스캔 결과를 봤다. 그 숫자가 이 모듈의 임계값이 된다
  • M26의 policy-audit.sh가 있다. 파이프라인의 한 단계로 들어간다
  • Node 24와 Docker가 로컬에 있다. 확인: node --version · docker version --format '{{.Server.Version}}'
  • 새로 만들 파일: apps/journal-api/src/labels.ts · labels.test.ts · course/labs/scripts/ci.sh · .github/workflows/ci.yaml

핵심 3줄

1. 테스트할 수 있는 형태로 코드를 나누고, 그 테스트를 Dockerfile 안에서 돌려 이미지 생성의 관문으로 만든다.

2. 테스트를 깨뜨려 이미지 태그가 만들어지지 않는 것을 확인하고, 스캔 임계값에 걸려 파이프라인이 멈추는 것을 본 뒤 베이스 이미지를 올려 통과시킨다.

3. 같은 태그로 다시 빌드해도 클러스터가 알아채지 못하는 것을 재현하고, 커밋 SHA를 태그로 쓰는 이유를 확인한다.

29.1지금은 사람이 순서를 기억한다

M07에서 이미지를 만들었고, M28에서 차트를 고쳤고, M26에서 정책을 걸었다. 이 셋을 한 번에 통과시키는 순서가 있는데 그 순서는 아무 데도 적혀 있지 않다. 지금까지는 필요할 때마다 손으로 쳤고, 무엇을 빠뜨렸는지는 클러스터에서 파드가 안 뜰 때 알았다.

구체적으로 세어 보면 이렇다. 코드를 고치면 npm run build를 해야 하고, 이미지를 다시 만들어야 하고, kind load로 넣어야 하고, 매니페스트의 태그를 바꿔야 하고, helm lint를 돌려야 하고, 정책에 걸리지 않는지 확인해야 한다. 여섯 단계 중 하나만 빠뜨려도 증상은 "안 되네요"로 똑같다.

더 나쁜 것은 테스트가 아예 없다는 것이다. package.json에 test 스크립트는 있지만 테스트 파일이 없어서, 지금 npm test를 치면 아무것도 실행되지 않고 성공한다. 책 5.3의 "테스트가 실패하면 빌드도 실패한다"를 적용하려면 실패할 수 있는 테스트가 먼저 있어야 한다.

이 모듈은 두 가지를 만든다. 하나는 순서를 코드로 적은 것(로컬 스크립트와 워크플로 파일)이고, 다른 하나는 사람이 건너뛸 수 없는 관문이다. 두 번째가 더 중요하다 — 스크립트는 안 돌릴 수 있지만, 이미지 빌드 안에 들어간 테스트는 건너뛸 방법이 없다.

29.2이론 — 관문의 순서와 각자 잡는 것

책 매핑5.1 앱 코드와 구성 코드 한 저장소 · 5.2 작은 커밋과 빠른 피드백 · 5.3 테스트가 실패하면 빌드도 실패 · 5.5 latest 금지

순서는 비용순이다

파이프라인의 단계 순서를 정하는 규칙은 하나다. 싸고 빠른 검사를 앞에 둔다. 타입 오류를 5분짜리 이미지 빌드가 끝난 뒤에 알 이유가 없고, 이름 오타를 일회용 클러스터를 띄운 뒤에 알 이유는 더더욱 없다.

다만 순서만 정하면 되는 게 아니다. 각 관문이 앞의 관문이 잡지 못하는 것을 잡아야 그 단계를 둘 값어치가 있다. 앞 단계와 같은 것을 잡는 단계는 시간만 쓴다.

M28의 두 실패가 이 그림을 정당화한다. nameSuffix가 환경 변수를 안 고친 것도, 패치가 env 순서를 바꾼 것도 렌더링과 어드미션을 멀쩡히 통과했다. 오직 실제로 띄워 보는 단계에서만 잡힌다. 그 단계가 가장 비싸지만, 없으면 그만큼이 운영에서 터진다.

관문은 우회할 수 없어야 한다

CI 서버에서 npm test를 돌리는 것과 Dockerfile 안에서 돌리는 것은 보장의 성질이 다르다. 앞의 것은 그 파이프라인을 지날 때만 유효하고, 뒤의 것은 누가 어디서 docker build를 하든 유효하다. 개발자가 급해서 로컬에서 빌드해 밀어 넣는 상황이 실제로 일어나므로, 이 차이가 중요하다.

대가는 중복이다. 워크플로의 check 잡에서 한 번, 이미지 빌드에서 또 한 번 테스트가 돈다. 앞의 것은 빨리 알기 위해, 뒤의 것은 확실히 하기 위해 있다. 목적이 다르므로 중복이 아니다.

태그는 포인터다

M26에서 latest를 정책으로 막았는데, 이유의 절반만 다뤘다. 나머지 절반은 어떤 고정 태그든 다시 쓰면 같은 문제가 생긴다는 것이다. v2로 다시 빌드해서 밀어 넣으면 레지스트리의 v2가 가리키는 내용물이 바뀐다. 클러스터의 파드는 이미 내려받은 것을 계속 쓰므로, 같은 태그가 노드마다 다른 것을 가리키는 상태가 된다. 29.7에서 이것을 재현한다.

해법은 커밋 SHA를 태그로 쓰는 것이다. 커밋이 바뀌면 태그가 바뀌므로 절대 재사용되지 않는다. 더 엄격하게 가면 다이제스트(@sha256:...)로 배포하는데, 이 교재는 infra/kind-cluster.yaml의 노드 이미지에 이미 그렇게 하고 있다.

29.3따라하기 ① 테스트할 수 있게 나눈다

1단계 — 무엇을 테스트할지 고른다

목적테스트가 없는 코드에 테스트를 붙일 때 어디부터인지를 정한다.

server.ts에서 테스트할 값이 있는 곳은 순수 함수 둘이다. normalizeUri는 M19에서 카디널리티 폭발을 막으려고 만든 것이고, outcomeOf는 M20의 PromQL이 쓰는 라벨을 만든다. 이 둘이 틀리면 대시보드와 알림이 조용히 잘못된 값을 그린다 — 앱은 200을 잘 돌려주므로 아무도 모른다.

HTTP 핸들러를 테스트하지 않는 이유도 분명히 해 둔다. 핸들러는 레디스에 의존하므로 목을 만들어야 하고, 그 목이 실제 레디스와 다르게 동작하면 테스트는 통과하는데 운영에서 깨진다. 그 층은 M28의 helm test가 진짜 레디스를 상대로 검사한다. 단위 테스트는 순수 로직에, 통합 테스트는 진짜 의존성에.

2단계 — 순수 함수를 분리한다

목적서버를 띄우지 않고 부를 수 있게 만든다. 분리 자체가 테스트 가능성을 만든다.

cat > course/labs/apps/journal-api/src/labels.ts <<'EOF'
// uri 라벨에 실제 경로를 그대로 넣으면 안 된다. /api/entries/123 같은 값이
// 요청마다 새 시계열을 만들어 카디널리티가 폭발한다 (M19 8절).
const KNOWN = ['/healthz', '/readyz', '/metrics', '/api/entries'];

export function normalizeUri(path: string): string {
  return KNOWN.includes(path) ? path : 'other';
}

export function outcomeOf(status: number): string {
  if (status < 200) return 'INFORMATIONAL';
  if (status < 300) return 'SUCCESS';
  if (status < 400) return 'REDIRECTION';
  if (status < 500) return 'CLIENT_ERROR';
  return 'SERVER_ERROR';
}
EOF

server.ts에서 두 함수를 지우고 import로 바꾼다. 함수 시그니처가 Request에서 string으로 바뀐 것에 주의한다 — 테스트에서 Request 객체를 만들지 않아도 되게 하려는 것이고, 이것이 "테스트 가능하게 만든다"의 실제 내용이다.

import { normalizeUri, outcomeOf } from './labels.js';
...
    const uri = normalizeUri(req.path);

3단계 — 테스트를 쓴다

목적Node에 내장된 테스트 러너를 쓴다. 의존성을 늘리지 않는다.

cat > course/labs/apps/journal-api/src/labels.test.ts <<'EOF'
import { test } from 'node:test';
import assert from 'node:assert/strict';
import { normalizeUri, outcomeOf } from './labels.js';

test('알려진 경로는 그대로 둔다', () => {
  assert.equal(normalizeUri('/api/entries'), '/api/entries');
  assert.equal(normalizeUri('/healthz'), '/healthz');
});

test('모르는 경로는 other 하나로 몰아넣는다 — 카디널리티 폭발 방지', () => {
  assert.equal(normalizeUri('/api/entries/12345'), 'other');
  // 서로 다른 두 요청이 같은 라벨이 되는 것이 목적이다
  assert.equal(normalizeUri('/x/1'), normalizeUri('/x/2'));
});

test('상태 코드를 결과 구간으로 접는다', () => {
  assert.equal(outcomeOf(200), 'SUCCESS');
  assert.equal(outcomeOf(404), 'CLIENT_ERROR');
  assert.equal(outcomeOf(503), 'SERVER_ERROR');
});

test('경계값 — 구간의 시작과 끝', () => {
  assert.equal(outcomeOf(199), 'INFORMATIONAL');
  assert.equal(outcomeOf(299), 'SUCCESS');
  assert.equal(outcomeOf(499), 'CLIENT_ERROR');
  assert.equal(outcomeOf(500), 'SERVER_ERROR');
});
EOF

두 번째 테스트의 마지막 줄이 이 테스트 묶음에서 유일하게 값을 확인하지 않는 단언이다. normalizeUri('/x/1')과 normalizeUri('/x/2')가 서로 같기만 하면 목적을 달성한다 — 무엇으로 접히는지는 중요하지 않다. 테스트가 의도를 표현하는 방식이다.

네 번째는 경계값이다. <와 <=를 헷갈리는 것은 흔한 실수이고, 그 실수를 잡는 유일한 방법이 구간의 끝값을 확인하는 것이다.

4단계 — 스크립트를 정리하고 돌린다

목적파이프라인이 부를 이름을 정한다. CI와 로컬이 같은 명령을 써야 한다.

# package.json 의 scripts
  "build": "tsc",
  "test": "node --test dist/**/*.test.js",
  "typecheck": "tsc --noEmit"
cd course/labs/apps/journal-api
npm ci
npm run typecheck
npm run build
npm test
출력
✔ 알려진 경로는 그대로 둔다 (0.275458ms) ✔ 모르는 경로는 other 하나로 몰아넣는다 — 카디널리티 폭발 방지 (0.05075ms) ✔ 상태 코드를 결과 구간으로 접는다 (0.045042ms) ✔ 경계값 — 구간의 시작과 끝 (0.061791ms) ℹ tests 4 ℹ pass 4 ℹ fail 0 ℹ duration_ms 37.123458
판정4개가 37밀리초에 끝난다. 이 속도가 앞 단계에 두는 이유다 — 개발자가 커밋 전에 습관적으로 칠 만큼 빨라야 한다. 1분이 넘어가면 아무도 로컬에서 돌리지 않고, 그러면 피드백이 CI를 기다리는 5분으로 늘어난다.

typecheck를 build와 따로 둔 이유가 있다. tsc --noEmit은 파일을 만들지 않아서 더 빠르고 부작용이 없다. 파이프라인에서는 이것을 먼저 돌려 타입 오류를 즉시 알고, 실제 컴파일은 이미지 빌드 안에서 한다.

29.4따라하기 ② 테스트를 이미지의 관문으로

1단계 — Dockerfile에 테스트 스테이지를 넣는다

목적어디서 docker build를 하든 테스트가 돌게 만든다.

# 2단계: 테스트. 실패하면 여기서 빌드가 멈추고 이미지가 만들어지지 않는다 (책 5.3).
FROM build AS test
RUN npm test

이대로 두면 이 스테이지가 아예 실행되지 않는다. BuildKit은 최종 이미지가 참조하지 않는 스테이지를 건너뛴다. 테스트를 관문으로 만들려면 최종 스테이지가 test에 의존해야 한다.

# test 스테이지를 참조하지 않으면 buildkit 이 그 스테이지를 아예 건너뛴다.
COPY --from=test  --chown=node:node /app/package.json ./package.json

package.json을 굳이 test 스테이지에서 가져오는 것이 그 장치다. 파일 자체는 어느 스테이지에서 가져와도 같지만, 참조가 생기면 그 스테이지가 반드시 실행된다. 다른 방법은 CI에서 --target test로 한 번 더 빌드하는 것인데, 그러면 로컬 빌드에서는 관문이 사라진다.

docker build -t journal-api:ci-test --build-arg APP_VERSION=v2 course/labs/apps/journal-api
출력 (테스트 스테이지 부분)
#13 0.258 # tests 4 #13 0.258 # pass 4 #13 0.258 # fail 0 #13 DONE 0.3s #14 [stage-3 3/5] COPY --from=test --chown=node:node /app/package.json ./package.json
판정빌드 로그 안에 테스트 결과가 있다. #14가 test 스테이지를 참조하는 줄이고, 이 줄이 있어야 #13이 돈다.

2단계 — 스캔을 붙인다

목적M27에서 손으로 한 스캔을 임계값이 있는 관문으로 바꾼다.

docker run --rm -v /var/run/docker.sock:/var/run/docker.sock \
  aquasec/trivy:0.69.0 image --scanners vuln \
  --severity CRITICAL --exit-code 1 --quiet journal-api:ci-test
플래그뜻
--severity CRITICAL이 등급만 본다. M27에서 잰 대로 HIGH까지 내리면 베이스 이미지만으로 계속 깨진다
--exit-code 1발견되면 종료 코드를 1로. 이 플래그가 없으면 스캔은 보고서일 뿐 관문이 아니다
--ignore-unfixed(워크플로에서 사용) 고칠 방법이 아직 없는 것은 제외한다. 없으면 손쓸 수 없는 것 때문에 빌드가 막힌다

이 명령의 결과는 29.7에서 본다 — 실제로 걸린다.

29.5따라하기 ③ 로컬 파이프라인

1단계 — 단계를 스크립트로 적는다

목적CI 서버에 올리기 전에 같은 명령을 로컬에서 돌린다. "내 컴퓨터에서는 되는데"의 절반은 두 곳이 다른 명령을 쓰기 때문이다.

cat > course/labs/scripts/ci.sh <<'EOF'
#!/usr/bin/env bash
set -euo pipefail
cd "$(dirname "$0")/.."          # course/labs
APP=apps/journal-api

# 이미지 태그는 커밋 해시다. latest 는 쓰지 않는다 (M26 의 정책이 거부한다).
SHA=$(git rev-parse --short HEAD 2>/dev/null || date +%Y%m%d%H%M%S)
IMAGE="journal-api:${SHA}"
STEPS=("$@")
[ ${#STEPS[@]} -eq 0 ] && STEPS=(typecheck build scan chart manifest policy)
has() { printf '%s\n' "${STEPS[@]}" | grep -qx "$1"; }
...
EOF
chmod +x course/labs/scripts/ci.sh

전문은 course/labs/scripts/ci.sh에 있다. 설계에서 두 가지를 의도했다. 단계를 인자로 고를 수 있게 한 것(ci.sh typecheck chart)은 고치는 중에 관련 단계만 빨리 돌리기 위해서고, set -euo pipefail은 중간 명령이 실패했을 때 다음 단계로 넘어가지 않게 하기 위해서다. 후자가 없으면 스크립트가 끝까지 돌고 마지막에 "전부 통과"를 찍는다.

2단계 — 빠른 단계부터 돌린다

목적클러스터도 도커도 필요 없는 부분이 얼마나 되는지 확인한다.

bash course/labs/scripts/ci.sh typecheck chart manifest
출력
▶ 1) 타입 검사 — 컨테이너 없이 가장 빠르게 깨진다 > journal-api@1.0.0 typecheck > tsc --noEmit ▶ 4) 차트 검사 — 렌더링과 스키마 ==> Linting charts/journal [INFO] Chart.yaml: icon is recommended 1 chart(s) linted, 0 chart(s) failed helm template OK ▶ 5) 매니페스트 검사 — 오버레이가 빌드되는가 kustomize build OK (base + 오버레이 2개) 전부 통과. 배포할 이미지: journal-api:20260906002848
판정태그가 20260906002848이다 — 커밋 해시가 아니라 타임스탬프다. 이 저장소에 아직 커밋이 없어서 git rev-parse가 실패했고 폴백이 동작했다. 폴백이 있는 것과 없는 것의 차이가 여기서 드러난다. 폴백이 없었다면 set -e 때문에 스크립트가 첫 줄에서 죽었다.

3단계 — 무거운 단계를 붙인다

목적이미지 빌드와 스캔까지 연결한다.

bash course/labs/scripts/ci.sh build scan

이 명령이 29.7의 두 번째 실패를 만든다. 먼저 그것을 보고 온다.

29.6따라하기 ④ 워크플로로 옮긴다

로컬 스크립트와 워크플로 파일은 같은 순서, 다른 실행 환경이다. 워크플로에서만 되는 것(병렬 잡, 캐시, 서명)을 더한다.

1단계 — 잡을 나눈다

목적서로 기다릴 필요가 없는 것을 병렬로 돌린다.

jobs:
  check:      # 타입·테스트           — 컨테이너 없이
  manifests:  # helm lint · kustomize — 클러스터 없이
  image:
    needs: [check, manifests]
  e2e:
    needs: image

check와 manifests는 서로 무관하므로 동시에 돈다. 코드가 깨졌든 차트가 깨졌든 둘 다 알고 싶지, 하나를 고친 뒤 다른 하나를 알고 싶지는 않다. 반대로 image는 둘 다 통과해야 시작한다 — 깨진 코드로 이미지를 만들 이유가 없다.

concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true

같은 브랜치에 새 커밋이 오면 앞의 실행을 취소한다. 이것이 없으면 러너가 이미 낡은 커밋을 검사하느라 붙잡혀 있고, 급할 때 그 대기가 그대로 배포 지연이 된다.

2단계 — 태그를 커밋 SHA로

목적M26의 정책과 29.7의 실패를 동시에 피한다.

      - id: meta
        run: echo "tag=${GITHUB_SHA::7}" >> "$GITHUB_OUTPUT"

      - uses: docker/build-push-action@v6
        with:
          context: ${{ env.APP_DIR }}
          push: true
          tags: ${{ env.IMAGE }}:${{ steps.meta.outputs.tag }}
          build-args: APP_VERSION=${{ steps.meta.outputs.tag }}
          cache-from: type=gha
          cache-to: type=gha,mode=max

APP_VERSION에도 같은 값을 넣는 것이 중요하다. M09에서 만든 /healthz의 version 필드가 이 값을 돌려주므로, 클러스터에서 도는 파드가 어느 커밋인지를 HTTP 한 번으로 알 수 있게 된다. 이미지 태그와 앱이 보고하는 버전이 어긋나면 그 자체가 사고다.

cache-from: type=gha는 레이어 캐시를 GitHub Actions 캐시에 둔다. M07에서 본 레이어 순서(package.json 먼저, 소스 나중)가 여기서 값을 낸다 — 의존성이 안 바뀌면 npm ci 레이어를 다시 만들지 않는다.

3단계 — 서명과 e2e를 붙인다

목적M07에서 예고한 이미지 서명의 만드는 쪽을 여기서 처리한다.

      - uses: sigstore/cosign-installer@v3
      - run: cosign sign --yes ${{ env.IMAGE }}:${{ steps.meta.outputs.tag }}

키가 없는 것에 주의한다. id-token: write 권한으로 받은 짧은 수명의 토큰으로 서명하고, 서명 기록은 공개 투명성 로그에 남는다. 보관할 개인 키가 없다는 것이 이 방식의 요점이다 — 키 유출과 키 교체 문제가 사라진다.

검증하는 쪽은 클러스터의 어드미션인데, M26에서 확인했듯 CEL로는 레지스트리를 조회할 수 없어 전용 컨트롤러가 필요하다. 이 교재는 서명을 만드는 데까지만 한다.

  e2e:
    needs: image
    steps:
      - uses: helm/kind-action@v1
        with:
          version: v0.33.0
          node_image: kindest/node:v1.37.0
          cluster_name: ci
      - run: |
          helm install ci course/labs/charts/journal \
            -n ci --create-namespace \
            -f course/labs/charts/journal/values-dev.yaml \
            --wait --timeout 300s
      - run: helm test ci -n ci --logs

일회용 클러스터를 띄우는 잡이다. M28의 두 실패는 이 단계에서만 잡힌다. 비용이 크므로 모든 커밋에 돌릴지 main 병합에만 돌릴지는 팀이 정하는데, 판단 기준은 "이 단계가 잡는 사고가 얼마나 자주 나는가"다.

29.7일부러 실패시키기

실패 ① — 테스트가 깨지면 이미지가 만들어지지 않는다

목적관문이 진짜 관문인지 확인한다. 확인하지 않은 관문은 관문이 아니다.

cat >> course/labs/apps/journal-api/src/labels.test.ts <<'EOF'

// 일부러 틀린 기대값
test('일부러 실패시키는 테스트', () => {
  assert.equal(outcomeOf(404), 'SUCCESS');
});
EOF
docker build -t journal-api:ci-fail course/labs/apps/journal-api
출력
#12 0.236 not ok 5 - 일부러 실패시키는 테스트 #12 0.236 + 'CLIENT_ERROR' #12 0.236 actual: 'CLIENT_ERROR' #12 0.240 # fail 1 #12 ERROR: process "/bin/sh -c npm test" did not complete successfully: exit code: 1 ERROR: failed to build: failed to solve: process "/bin/sh -c npm test" did not complete successfully: exit code: 1
docker images journal-api --format '{{.Tag}}' | sort
출력
ci-test naive v1 v1-hardened v2 v3
판정ci-fail 태그가 없다. 빌드가 중간에 멈췄으므로 이미지가 만들어지지 않았고, 만들어지지 않은 이미지는 배포할 수 없다. 책 5.3이 말하는 것이 이 상태다 — 실패한 빌드에서 나온 산출물이 존재하지 않는 것이 "빌드도 실패한다"의 실제 내용이다.

테스트를 지우고 넘어간다. 이 실험에서 확인할 것은 하나 더 있다 — docker build의 종료 코드다. CI가 이 코드를 보고 파이프라인을 멈추므로, 스크립트에서 || true를 붙이면 관문이 사라진다.

실패 ② — 베이스 이미지의 CVE가 배포를 막는다

목적M27에서 "숫자만 본" 것이 파이프라인에서 어떻게 작동하는지 본다.

bash course/labs/scripts/ci.sh build scan
출력
Node.js (node-pkg) ================== Total: 1 (CRITICAL: 1) ┌────────────────────┬────────────────┬──────────┬────────┬───────────────────┬───────────────┐ │ Library │ Vulnerability │ Severity │ Status │ Installed Version │ Fixed Version │ ├────────────────────┼────────────────┼──────────┼────────┼───────────────────┼───────────────┤ │ tar (package.json) │ CVE-2026-59873 │ CRITICAL │ fixed │ 7.5.11 │ 7.5.19 │ └────────────────────┴────────────────┴──────────┴────────┴───────────────────┴───────────────┘ CRITICAL 취약점이 있다. 베이스 이미지부터 확인한다 (M27 8절)
판정파이프라인이 멈췄다. 그런데 tar는 우리가 설치한 의존성이 아니다 — package.json에 없다. 베이스 이미지에 들어 있는 npm이 들고 있는 것이고, M27에서 층을 나눠 본 그 결과가 여기서 파이프라인을 세운 것이다.

M27의 표를 그대로 쓴다. node:24-alpine은 HIGH 6에 CRITICAL 0이었다.

sed -i '' 's/FROM node:22-alpine/FROM node:24-alpine/g' course/labs/apps/journal-api/Dockerfile
bash course/labs/scripts/ci.sh build scan
출력
CRITICAL 없음 전부 통과. 배포할 이미지: journal-api:20260906002910

베이스를 올렸으니 실제로 도는지 확인한다. 스캔을 통과했다는 것과 동작한다는 것은 다르다.

kind load docker-image journal-api:20260906002910 --name study
kubectl -n m29 run smoke --image=journal-api:20260906002910 --image-pull-policy=IfNotPresent \
  --restart=Never --env=REDIS_URL=redis://none:6379
kubectl -n m29 exec smoke -- node --version
kubectl -n m29 exec smoke -- id
kubectl -n m29 exec smoke -- wget -qO- http://127.0.0.1:8080/healthz
출력

판정uid가 여전히 1000이다 — M24에서 USER 1000으로 고쳤던 것이 새 베이스에서도 유효하다. 베이스 이미지를 올릴 때 사용자 번호가 바뀌는 것이 흔한 사고인데(M19의 order-api에서 실제로 겪었다), 여기서는 무사했다.

wget http://localhost:8080은 can't connect to remote host로 실패하고 127.0.0.1은 성공한다. Node가 localhost를 ::1로 먼저 풀고 Express는 IPv4에 붙어 있기 때문이다. 컨테이너 안에서 자기 자신을 부를 때는 127.0.0.1을 쓰는 편이 안전하다. 프로브가 httpGet을 쓰는 한 이 문제는 없다 — kubelet이 파드 IP로 부른다.

실패 ③ — 같은 태그로 다시 빌드하면 클러스터가 모른다

목적커밋 SHA를 태그로 쓰는 이유를 재현으로 만든다.

docker build -t journal-api:v2 --build-arg APP_VERSION=v2 course/labs/apps/journal-api
kind load docker-image journal-api:v2 --name study
kubectl -n journal get po -l app=journal-api --no-headers
출력
journal-api-59546f4fbc-9kjnz 1/1 Running 0 72m journal-api-59546f4fbc-bdb4x 1/1 Running 0 72m journal-api-59546f4fbc-nlrjn 1/1 Running 0 72m
kubectl -n journal exec deploy/journal-api -- node --version
출력
v22.23.2
판정새 베이스로 다시 빌드해서 노드에 적재했는데 파드는 72분째 재시작이 없고 여전히 Node 22를 돌리고 있다. 태그가 가리키는 내용은 바뀌었지만 파드 스펙은 그대로라 롤아웃이 일어날 이유가 없고, 이미 내려받은 이미지가 있으니 다시 당기지도 않는다.

이 상태의 위험은 노드마다 다를 수 있다는 것이다. 새 노드가 합류하면 그 노드는 새 v2를 받는다. 같은 디플로이먼트의 파드가 노드에 따라 다른 코드를 돌리게 되고, 증상은 "가끔 이상하다"로 나타난다.

해결은 태그를 재사용하지 않는 것이다. ci.sh와 워크플로가 커밋 SHA를 쓰는 이유가 이것이고, M26에서 latest를 막은 것도 같은 문제의 특수한 경우다.

29.8운영 관점 — 무엇을 언제 막을 것인가

임계값은 올릴 수 있게 정한다

스캔 임계값을 CRITICAL로 시작한 것은 타협이 아니라 순서다. M27에서 잰 숫자대로 HIGH까지 내리면 베이스 이미지만으로 6~12개가 걸려 파이프라인이 상시로 빨간불이 된다. 그리고 상시로 빨간 신호는 아무도 보지 않는 신호가 된다.

실무의 순서는 이렇다. 막을 수 있는 것부터 막고(CRITICAL), 베이스 이미지를 정리하고, 남은 것에 기한이 있는 예외를 붙이고, 그다음 임계값을 내린다. --ignore-unfixed도 같은 성격이다 — 고칠 방법이 아직 없는 것 때문에 배포를 막으면 그 관문은 곧 꺼진다.

어디까지 CI에서 하는가

이 파이프라인은 이미지를 만들고 검사하는 데서 끝난다. 클러스터에 배포하는 것은 하지 않는다. 이유는 M31에서 다룰 GitOps와 관계가 있다 — CI가 클러스터에 직접 kubectl apply를 하려면 CI 러너가 클러스터 자격 증명을 갖고 있어야 하고, 그것은 M23에서 본 권한 설계의 관점에서 가장 큰 권한을 가장 넓게 노출된 곳에 두는 일이다.

대안은 CI가 저장소에 이미지 태그를 커밋하는 것까지만 하고, 클러스터 안의 무언가가 그것을 당겨 가게 하는 것이다. 그러면 자격 증명이 클러스터 밖으로 나가지 않는다. M31이 그 구조를 만든다.

한 저장소에 둘 것과 나눌 것

책 5.1은 앱 코드와 구성 코드를 한 저장소에 두라고 한다. 이 교재의 배치가 그것이다 — apps/와 k8s/와 charts/가 한 저장소에 있어서, 코드 변경과 매니페스트 변경이 한 커밋에 들어간다. 환경 변수를 추가하는 변경이 코드와 컨피그맵을 동시에 고쳐야 할 때, 두 저장소로 나뉘어 있으면 순서를 사람이 맞춰야 한다.

나누는 경우도 있다. 배포 대상 클러스터가 여럿이고 환경별 값이 별도의 승인 절차를 타야 할 때는 구성만 따로 두는 편이 낫다. M26에서 정책의 파라미터를 컨피그맵으로 뺀 것과 같은 판단이고, 기준도 같다 — 변경 주기와 승인 주체가 다르면 나눈다.

파이프라인이 느려질 때

관문을 늘리면 반드시 느려지고, 느린 파이프라인은 우회하고 싶어진다. 대응은 세 가지다. 캐시를 쓴다(cache-from: type=gha). 병렬로 돌린다(check와 manifests). 그리고 비싼 단계를 모든 커밋에 돌리지 않는다 — e2e를 PR에서는 건너뛰고 main 병합에서만 돌리는 식이다.

세 번째는 위험을 옮기는 것이지 없애는 것이 아니다. 옮긴 위험이 어디로 갔는지 알고 있어야 한다 — main에 들어간 뒤에 깨지면 되돌리는 비용이 PR에서 잡는 것보다 크다. M28의 helm rollback과 M30의 배포 전략이 그 비용을 낮추는 장치다.

# 실습 네임스페이스와 임시 이미지를 지운다
kubectl delete ns m29 --ignore-not-found
docker rmi journal-api:ci-test 2>/dev/null

# 클러스터의 저널 앱은 그대로인지 확인한다
kubectl -n journal get deploy,sts --no-headers

journal-api:v2는 새 베이스로 다시 빌드된 상태로 남는다. 클러스터의 파드는 아직 옛 바이트를 돌리고 있는데(29.7 실패 ③), 이 어긋남은 M30에서 배포 전략을 실습하면서 새 버전을 내보내는 과정으로 해소한다.

ci.sh와 워크플로 파일은 지우지 않는다. M31의 GitOps가 이 파이프라인의 끝에 이어 붙고, M38 캡스톤에서 전체를 한 번 더 돌린다.

다음 모듈

파이프라인이 이미지를 만들어 놨는데 클러스터에 내보내는 방법은 아직 하나뿐이다 — M10에서 본 롤링 업데이트. 새 버전이 나쁘면 maxSurge·maxUnavailable이 정한 속도로 전체 트래픽이 그쪽으로 옮겨 간다.

M30에서 그 사이에 판단할 지점을 만든다. 새 버전에 트래픽 일부만 보내고, M20에서 만든 메트릭으로 에러율과 지연을 비교해 계속할지 되돌릴지 정한다. 판정 기준을 사람이 아니라 PromQL로 쓰는 것이 이 모듈의 핵심이다.
