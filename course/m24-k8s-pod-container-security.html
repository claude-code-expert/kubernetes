파드와 컨테이너 보안

M23의 RBAC은 API를 통해 무엇을 할 수 있는가를 정한다. 파드가 일단 뜨고 나면 그 안에서 하는 일 — 루트로 실행하고, 호스트 파일시스템을 마운트하고, 커널 기능을 요구하는 것 — 은 RBAC이 관여하지 않는다. 이 모듈에서 네임스페이스에 라벨 하나를 붙여 그것을 강제하고, 지금 잘 돌고 있는 파드들이 거부되는 것부터 본다.

중후반90분Kubernetes 1.37.0
2026-09-05 검증 (kind v0.33.0) · 버전 숫자는 실습 당일 kubectl version으로 다시 확인한다
사전 조건
  • M23 완료 — journal 네임스페이스에 dev 계정이 있다
  • 세 워크로드가 떠 있다. 확인: kubectl -n journal get deploy,sts에 journal-api·web-static·redis
  • 이미지를 다시 빌드할 수 있다. 확인: docker images journal-api에 v1·v2
  • 고칠 파일: course/labs/apps/journal-api/Dockerfile · course/labs/k8s/journal/의 20-redis.yaml·30-journal-api.yaml·40-web-static.yaml

핵심 3줄

1. 네임스페이스에 restricted 라벨을 붙여 지금 워크로드가 어떤 항목에서 걸리는지 네 가지를 한 번에 받아 본다.

2. 어드미션을 통과한 뒤 kubelet이 다시 막는 상황을 재현하고, 두 문지기의 증상이 어떻게 다른지 구분한다.

3. 세 워크로드를 전부 통과시킨다 — 그 과정에서 Dockerfile을 고치고 이미지 하나를 바꾼다.

24.1파드 안에서는 무엇이든 할 수 있었다 24.2이론 — 세 수준과 세 모드 24.3따라하기 ① 거부당해 본다 24.4따라하기 ② 두 번째 문지기 24.5따라하기 ③ 세 수준을 비교한다 24.6따라하기 ④ 실제 워크로드를 통과시킨다 24.7일부러 실패시키기 24.8운영 관점 — 어디까지 강제할 것인가 24.9체크포인트와 정리

24.1파드 안에서는 무엇이든 할 수 있었다

M23에서 dev 계정의 권한을 좁혔다. 그 계정은 시크릿을 읽을 수 없고 다른 네임스페이스를 볼 수 없다. 그런데 그 계정으로 디플로이먼트를 수정할 수는 있다 — 그리고 파드 스펙에는 이런 것을 적을 수 있다.

      securityContext:
        privileged: true
      volumes:
        - name: h
          hostPath: {path: /}

이 두 줄이면 컨테이너가 노드의 파일시스템 전체를 읽고, 커널 기능을 제한 없이 쓴다. M19에서 우리가 docker exec로 했던 일 — 정적 파드 매니페스트 수정 — 을 파드 안에서 할 수 있다는 뜻이다. 네임스페이스 하나의 배포 권한이 노드 전체의 권한이 된다.

지금 우리 클러스터의 파드들이 어떤 상태인지 본다.

kubectl -n journal get deploy journal-api \
  -o jsonpath='pod={.spec.template.spec.securityContext}{"\n"}container={.spec.template.spec.containers[0].securityContext}{"\n"}'
출력
pod={} container=

둘 다 비어 있다. 아무것도 제한하지 않았고, 이것이 쿠버네티스의 기본값이다. RBAC이 "누가 무엇을 요청할 수 있는가"를 정한다면, 이 모듈에서 켜는 것은 "어떤 파드를 만들 수 있는가"다.

24.2이론 — 세 수준과 세 모드

책 10.1이 다루는 파드 시큐리티 어드미션 Pod Security Admission, PSA은 apiserver에 내장된 어드미션 컨트롤러다. 별도 설치가 필요 없고, 네임스페이스에 라벨을 붙이는 것으로 켠다.

세 수준

수준막는 것쓰는 곳
privileged아무것도 막지 않는다CNI·CSI·모니터링 에이전트 같은 시스템 구성요소
baseline알려진 권한 상승 경로 — hostPath, privileged, hostNetwork, 위험한 capability기존 워크로드를 옮길 때의 현실적인 출발점
restricted여기에 더해 모범 사례까지 — 비루트 실행, 모든 capability 제거, seccomp 프로파일새로 만드는 워크로드의 기본값

수준은 누적이다. restricted는 baseline이 막는 것을 전부 막고 더 막는다.

세 모드

모드하는 일언제
enforce위반하는 파드를 거부한다준비가 끝난 뒤
audit감사 로그에 기록만 한다영향 범위를 조사할 때
warnkubectl 화면에 경고를 띄운다사람에게 알릴 때

세 모드를 동시에 걸 수 있고, 각각 다른 수준을 지정할 수 있다. 흔한 이행 방식이 이것이다 — enforce=baseline으로 최소한을 막으면서 warn=restricted·audit=restricted로 나머지 위반을 수집한다.

pod-security.kubernetes.io/enforce: baseline
pod-security.kubernetes.io/warn: restricted
pod-security.kubernetes.io/audit: restricted

문지기는 둘이다

어드미션을 통과했다고 컨테이너가 뜨는 것은 아니다. PSA는 파드 스펙만 보고, kubelet은 실제 이미지를 본다. 스펙에 runAsNonRoot: true가 있어도 이미지가 정말 비루트로 뜨는지는 kubelet이 확인하고, 확인할 수 없으면 거부한다 — 24.4에서 그 상황을 만든다.

24.3따라하기 ① 거부당해 본다

1단계 — 실험용 네임스페이스에 restricted를 건다

목적운영 중인 네임스페이스를 건드리지 않고 위반 항목을 먼저 수집한다.

kubectl create ns m24
kubectl label ns m24 \
  pod-security.kubernetes.io/enforce=restricted \
  pod-security.kubernetes.io/enforce-version=latest \
  pod-security.kubernetes.io/warn=restricted \
  pod-security.kubernetes.io/audit=restricted

enforce-version=latest는 "이 클러스터 버전의 최신 정의를 쓴다"는 뜻이다. 특정 버전(v1.30 같은)으로 고정할 수도 있는데, 그러면 클러스터를 올려도 판정 기준이 그대로여서 업그레이드가 워크로드를 깨지 않는다. 실습에서는 최신을 쓴다.

2단계 — 지금 잘 돌고 있는 것을 그대로 올린다

목적추상적인 "위반"이 아니라 우리 앱이 무엇에 걸리는지 목록으로 받는다.

cat <<'EOF' | kubectl -n m24 apply -f -
apiVersion: apps/v1
kind: Deployment
metadata: {name: journal-api}
spec:
  replicas: 1
  selector: {matchLabels: {app: journal-api}}
  template:
    metadata: {labels: {app: journal-api}}
    spec:
      containers:
        - name: api
          image: journal-api:v1
          imagePullPolicy: IfNotPresent
          ports: [{name: http, containerPort: 8080}]
          resources:
            requests: {cpu: 50m, memory: 64Mi}
            limits: {memory: 192Mi}
EOF
출력
Warning: would violate PodSecurity "restricted:latest": allowPrivilegeEscalation != false (container "api" must set securityContext.allowPrivilegeEscalation=false), unrestricted capabilities (container "api" must set securityContext.capabilities.drop=["ALL"]), runAsNonRoot != true (pod or container "api" must set securityContext.runAsNonRoot=true), seccompProfile (pod or container "api" must set securityContext.seccompProfile.type to "RuntimeDefault" or "Localhost") deployment.apps/journal-api created
판정위반 네 가지가 한 번에 나온다. 그런데 마지막 줄이 created다 — kubectl apply는 성공했다. Warning은 warn 모드가 띄운 것이고, enforce는 아직 아무것도 거부하지 않았다.

3단계 — 파드가 어디로 갔는지 찾는다

목적"apply는 성공했는데 파드가 없다"는 상황의 진단 경로를 익힌다.

kubectl -n m24 get deploy,rs,po
출력
deployment.apps/journal-api 0/1 0 0 20s replicaset.apps/journal-api-6f567bb4d4 1 0 0 20s

디플로이먼트도 레플리카셋도 있는데 파드가 한 줄도 없다. 레플리카셋의 이벤트를 본다.

RS=$(kubectl -n m24 get rs -o jsonpath='{.items[0].metadata.name}')
kubectl -n m24 describe rs $RS | sed -n '/^Events:/,$p' | head -5
출력 (반복되는 줄은 줄였다)
Events: Type Reason Age From Message ---- ------ ---- ---- ------- Warning FailedCreate 20s replicaset-controller Error creating: pods "journal-api-6f567bb4d4-9jnlv" is forbidden: violates PodSecurity "restricted:latest": allowPrivilegeEscalation != false (container "api" must set securityContext.allowPrivilegeEscalation=false), unrestricted capabilities (container "api" must set securityContext.capabilities.drop=["ALL"]), runAsNonRoot != true (pod or container "api" must set securityContext.runAsNonRoot=true), seccompProfile (pod or container "api" must set securityContext.seccompProfile.type to "RuntimeDefault" or "Localhost")
판정여기에 진짜 거부가 있다. 어드미션은 파드에 걸리는데 파드를 만드는 것은 우리가 아니라 레플리카셋 컨트롤러이기 때문에, 거부가 우리 터미널이 아니라 컨트롤러의 이벤트로 간다. 파드 이름이 여러 개인 것은 컨트롤러가 계속 재시도했기 때문이다.

디플로이먼트의 상태 조건에도 남는다. 이쪽이 더 찾기 쉽다.

kubectl -n m24 get deploy journal-api \
  -o jsonpath='{range .status.conditions[*]}{.type}={.status} {.reason}{"\n"}{end}'
출력
Progressing=True NewReplicaSetCreated Available=False MinimumReplicasUnavailable ReplicaFailure=True FailedCreate

ReplicaFailure=True가 신호다. 이 조건은 파드를 만들지도 못했을 때만 붙는다 — 파드가 떴다가 죽는 것(M15의 CrashLoop)과는 다른 상태다.

24.4따라하기 ② 두 번째 문지기

4단계 — 네 가지를 채운다

목적거부 메시지가 요구한 것을 그대로 옮겨 어드미션을 통과시킨다.

메시지의 항목이 그대로 필드 이름이다. 컨테이너 수준 둘과 파드 수준 둘로 나뉜다.

kubectl -n m24 patch deploy journal-api --type=json -p='[
 {"op":"add","path":"/spec/template/spec/containers/0/securityContext",
  "value":{"allowPrivilegeEscalation":false,"capabilities":{"drop":["ALL"]}}},
 {"op":"add","path":"/spec/template/spec/securityContext",
  "value":{"runAsNonRoot":true,"seccompProfile":{"type":"RuntimeDefault"}}}]'
필드막는 것
allowPrivilegeEscalation: false프로세스가 setuid 바이너리로 권한을 올리는 것
capabilities.drop: ["ALL"]컨테이너 런타임이 기본으로 주는 커널 기능 전부. 필요하면 add로 하나씩 되돌린다
runAsNonRoot: trueUID 0으로 실행하는 것
seccompProfile.type: RuntimeDefault런타임의 기본 시스템 콜 필터를 적용한다. 없으면 필터가 없다
kubectl -n m24 get deploy,po
출력
deployment.apps/journal-api 0/1 1 0 51s pod/journal-api-798b755857-kqcsc 0/1 CreateContainerConfigError 0 10s
판정파드가 만들어졌다. 어드미션은 통과한 것이다. 그런데 CreateContainerConfigError다 — 3단계와 증상이 완전히 다르다. 그때는 파드가 없었고 지금은 파드가 있다.

5단계 — kubelet이 무엇을 거부했는지 읽는다

목적두 번째 문지기의 메시지를 확인한다.

POD=$(kubectl -n m24 get po -o jsonpath='{.items[0].metadata.name}')
kubectl -n m24 describe pod $POD | sed -n '/^Events:/,$p'
출력
Normal Scheduled 17s default-scheduler Successfully assigned m24/journal-api-798b755857-kqcsc to study-worker Normal Pulled 3s (x3 over 17s) kubelet Container image "journal-api:v1" already present on machine Warning Failed 3s (x3 over 17s) kubelet Error: container has runAsNonRoot and image has non-numeric user (node), cannot verify user is non-root
원인

image has non-numeric user (node). M04에서 쓴 Dockerfile을 보면 이유가 나온다.

grep -h '^USER' course/labs/apps/journal-api/Dockerfile course/labs/apps/order-api/Dockerfile
출력
USER node USER 10001

journal-api는 이름으로, order-api는 숫자로 지정했다. kubelet은 이미지 안의 /etc/passwd를 읽지 않으므로 node가 UID 몇인지 알 수 없고, 비루트인지 확인할 수 없으면 거부한다. M19에서 order-api의 Dockerfile을 고치며 USER 10001로 숫자를 쓴 것이 여기서 값을 한다.

고친다 — 두 가지 방법

파드 스펙에서 숫자를 명시하거나, Dockerfile을 고친다. 먼저 스펙 쪽으로 확인한다.

kubectl -n m24 patch deploy journal-api --type=json \
  -p='[{"op":"add","path":"/spec/template/spec/securityContext/runAsUser","value":1000}]'

kubectl -n m24 get deploy,po
kubectl -n m24 exec deploy/journal-api -- id
출력
deployment.apps/journal-api 1/1 1 1 84s pod/journal-api-758b9f55f5-jswwm 1/1 Running 0 12s uid=1000(node) gid=1000(node) groups=1000(node)
판정떴다. 다만 이 방법은 파드 스펙마다 UID를 적어야 하고, 이미지가 바뀌어 UID가 달라지면 조용히 어긋난다. 근본은 Dockerfile이므로 그쪽을 고치는 편이 낫다 — 24.6에서 그렇게 한다.

6단계 — readOnlyRootFilesystem을 더해 본다

목적restricted가 요구하지는 않지만 함께 쓰는 설정의 영향을 확인한다.

kubectl -n m24 patch deploy journal-api --type=json \
  -p='[{"op":"add","path":"/spec/template/spec/containers/0/securityContext/readOnlyRootFilesystem","value":true}]'

kubectl -n m24 exec deploy/journal-api -- sh -c 'touch /tmp/x; touch /app/x'
출력
touch: /tmp/x: Read-only file system touch: /app/x: Read-only file system
판정파드는 잘 뜨지만 /tmp까지 쓸 수 없다. 이것을 모르고 켜면 임시 파일을 쓰는 앱이 조용히 실패한다 — 그래서 대개 emptyDir을 /tmp에 붙여 쓰기 가능한 곳만 열어 둔다.
      volumes:
        - name: tmp
          emptyDir: {}
      containers:
        - name: api
          volumeMounts:
            - name: tmp
              mountPath: /tmp

우리 앱은 /tmp를 쓰지 않으므로 이 실습에서는 readOnlyRootFilesystem을 최종 매니페스트에 넣지 않는다. 넣을지 말지는 앱이 결정한다는 것이 요점이고, 이런 판단을 하려면 앱이 어디에 쓰는지 알아야 한다.

24.5따라하기 ③ 세 수준을 비교한다

7단계 — 세 네임스페이스를 만든다

목적같은 파드를 세 수준에 각각 던져 무엇이 어디서 막히는지 표로 만든다.

for LVL in privileged baseline restricted; do
  kubectl create ns psa-$LVL
  kubectl label ns psa-$LVL \
    pod-security.kubernetes.io/enforce=$LVL \
    pod-security.kubernetes.io/enforce-version=latest
done

파드 세 종류를 던진다 — 아무 설정 없는 것, hostPath를 쓰는 것, privileged: true인 것.

파드privilegedbaselinerestricted
아무 설정 없음 (루트로 실행)생성생성거부
hostPath: / 마운트생성거부거부
privileged: true생성거부거부
거부 메시지
pods "hostp" is forbidden: violates PodSecurity "baseline:latest": hostPath volumes (volume "h") pods "privpod" is forbidden: violates PodSecurity "baseline:latest": privileged (container "c" must not set securityContext.privileged=true)
판정baseline은 루트 실행을 막지 않는다. 첫 줄이 그것을 보여준다 — 아무 설정 없는 파드가 baseline에서는 뜬다. 기존 워크로드를 옮길 때 baseline부터 시작하는 것이 현실적인 이유이고, 동시에 baseline이 충분하지 않은 이유이기도 하다.

8단계 — privileged 수준이 무엇을 허용하는지 본다

목적"막지 않는다"가 실제로 무슨 뜻인지 확인한다.

kubectl -n psa-privileged exec hostp -- head -3 /host/var/lib/kubelet/config.yaml
출력
apiVersion: kubelet.config.k8s.io/v1beta1 authentication: anonymous:
판정컨테이너 안에서 노드의 kubelet 설정을 읽고 있다. 같은 방식으로 컨트롤 플레인 노드라면 /etc/kubernetes/pki의 인증서에 닿는다. hostPath 하나가 노드 전체의 권한과 같다는 것이 이 출력의 뜻이고, baseline이 그것부터 막는 이유다.

24.6따라하기 ④ 실제 워크로드를 통과시킨다

실험 네임스페이스에서 배운 것을 journal에 적용한다. 순서가 중요하다 — enforce를 먼저 걸면 운영 중인 앱이 롤아웃할 때 죽는다.

9단계 — warn 모드로 영향 범위를 본다

목적강제하기 전에 무엇이 걸리는지 수집한다.

kubectl label ns journal \
  pod-security.kubernetes.io/warn=restricted \
  pod-security.kubernetes.io/warn-version=latest \
  pod-security.kubernetes.io/audit=restricted --overwrite

kubectl apply -k course/labs/k8s/journal
출력 (일부)
deployment.apps/journal-api unchanged deployment.apps/web-static unchanged Warning: would violate PodSecurity "restricted:latest": allowPrivilegeEscalation != false (container "redis" must set ...) statefulset.apps/redis configured
판정경고가 redis에만 나왔다. journal-api와 web-static은 unchanged라 검증조차 되지 않았다 — PSA는 생성하거나 수정할 때만 본다. warn 모드를 걸었다고 기존 워크로드의 위반이 저절로 드러나지는 않는다.

이것이 audit 모드가 함께 필요한 이유다. 감사 로그에는 파드가 실제로 만들어질 때마다 기록이 남으므로, 롤아웃이 한 번 돌면 위반이 드러난다. 감사 로그를 켜는 것은 M27에서 다룬다.

10단계 — Dockerfile을 고친다

목적5단계에서 파드 스펙으로 우회한 것을 근본에서 고친다.

# course/labs/apps/journal-api/Dockerfile
# 숫자로 지정한다. 이름(node)으로 두면 kubelet 이 runAsNonRoot 를 검증하지 못해
# CreateContainerConfigError 로 막힌다 (M24):
#   container has runAsNonRoot and image has non-numeric user (node), cannot verify user is non-root
USER 1000
for v in v1 v2; do docker build -t "journal-api:$v" --build-arg "APP_VERSION=$v" course/labs/apps/journal-api; done
kind load docker-image journal-api:v1 journal-api:v2 --name study
판정이제 이미지 자체가 숫자 UID를 갖는다. 파드 스펙의 runAsUser는 여전히 적는 편이 낫지만 — 명시적이고, 이미지가 바뀌어도 의도가 남는다 — 없어도 동작한다.

11단계 — 세 워크로드의 매니페스트를 고친다

목적실험에서 확인한 설정을 정본에 옮긴다. 이미지마다 UID가 다르다는 것이 여기서 드러난다.

먼저 각 이미지가 어떤 사용자를 갖고 있는지 확인한다.

docker run --rm --entrypoint sh redis:8.2-alpine -c 'getent passwd redis'
docker run --rm --entrypoint sh nginx:1.29-alpine -c 'getent passwd nginx'
출력
redis:x:999:1000::/home/redis:/sbin/nologin nginx:x:101:101:nginx:/var/cache/nginx:/sbin/nologin

journal-api와 redis에는 같은 형태를 넣는다. 30-journal-api.yaml의 파드 스펙이다.

      # ── 파드 수준 보안 (M24) ────────────────────────────────────────
      # restricted 프로파일이 요구하는 셋. seccompProfile 은 파드 수준에서 한 번만 쓰면
      # 모든 컨테이너에 적용된다.
      securityContext:
        runAsNonRoot: true
        runAsUser: 1000
        seccompProfile:
          type: RuntimeDefault
      # 이 앱은 쿠버네티스 API 를 호출하지 않는다. 토큰을 넣어 둘 이유가 없다 (M23 8절).
      automountServiceAccountToken: false
          # ── 컨테이너 수준 보안 (M24) ─────────────────────────────────
          securityContext:
            allowPrivilegeEscalation: false
            capabilities:
              drop: ["ALL"]

redis에는 fsGroup이 하나 더 필요하다.

      securityContext:
        runAsNonRoot: true
        runAsUser: 999              # 이미지 안의 redis 사용자
        fsGroup: 999                # PVC 의 소유자를 이 그룹으로 바꿔 준다 (M18)
        seccompProfile:
          type: RuntimeDefault

fsGroup이 없으면 비루트로 뜬 레디스가 자기 PVC에 쓰지 못한다. 볼륨은 기본적으로 루트 소유로 마운트되기 때문이다 — M18의 스토리지와 이 모듈의 보안이 만나는 지점이다.

12단계 — 이미지를 바꿔야 하는 경우

목적설정만으로는 해결되지 않는 상황을 확인한다.

nginx는 nginx 사용자를 갖고 있지만 루트로 시작한다 — 마스터 프로세스가 루트로 뜨고 워커만 nginx로 떨어뜨리는 구조다. restricted는 그 시작 자체를 막는다.

docker run --rm --entrypoint sh nginxinc/nginx-unprivileged:1.29-alpine -c 'id; grep -m1 listen /etc/nginx/conf.d/default.conf'
출력
uid=101(nginx) gid=101(nginx) groups=101(nginx) listen 8080;

비루트 이미지는 8080을 듣는다. 1024 미만 포트는 비루트가 열 수 없기 때문이고, 이것이 이미지를 바꿀 때 함께 바뀌는 것이다.

      containers:
        - name: nginx
          # 공식 nginx 이미지는 루트로 시작해 워커만 nginx 사용자로 떨어뜨린다.
          # restricted 프로파일은 그 시작조차 허용하지 않으므로 비루트 이미지를 쓴다.
          # 대신 80 이 아니라 8080 을 듣는다 — 1024 미만 포트는 비루트가 열 수 없다.
          image: nginxinc/nginx-unprivileged:1.29-alpine
          ports:
            - name: http
              containerPort: 8080

서비스는 고치지 않아도 된다. M11부터 포트를 이름(targetPort: http)으로 참조해 왔기 때문에 숫자가 바뀌어도 연결이 유지된다 — 그 습관이 여기서 값을 한다.

kubectl apply -k course/labs/k8s/journal
kubectl -n journal rollout status deploy/web-static
kubectl -n journal rollout status statefulset/redis
출력
deployment.apps/web-static configured statefulset.apps/redis configured deployment "web-static" successfully rolled out partitioned roll out complete: 1 new pods have been updated...
판정경고가 하나도 나오지 않는다. 세 워크로드가 모두 restricted를 만족한다. 앱이 실제로 동작하는지 확인한다.
curl -s -o /dev/null -w '/api/entries: %{http_code}\n' -H 'Host: journal.local' http://localhost:18080/api/entries
curl -s -o /dev/null -w '/ (정적):    %{http_code}\n' -H 'Host: journal.local' http://localhost:18080/
출력
/api/entries: 200 / (정적): 200

13단계 — enforce로 올린다

목적경고를 강제로 바꾸고, 그 뒤에도 운영이 되는지 확인한다.

kubectl label ns journal \
  pod-security.kubernetes.io/enforce=restricted \
  pod-security.kubernetes.io/enforce-version=latest --overwrite

kubectl -n journal rollout restart deploy/journal-api
kubectl -n journal rollout status deploy/journal-api
출력
namespace/journal labeled deployment "journal-api" successfully rolled out

이제 규칙을 지키지 않는 파드는 들어올 수 없다.

kubectl -n journal run rootpod --image=alpine:3.22 --restart=Never -- sleep 60
출력
Error from server (Forbidden): pods "rootpod" is forbidden: violates PodSecurity "restricted:latest": allowPrivilegeEscalation != false (container "rootpod" must set ...)
판정이번에는 Warning이 아니라 Error from server (Forbidden)이고, 파드가 만들어지지 않는다. kubectl run처럼 파드를 직접 만드는 명령은 거부가 터미널에 바로 오지만, 디플로이먼트를 통하면 3단계처럼 컨트롤러 이벤트로 간다.

24.7일부러 실패시키기

실패 ① apply는 성공했는데 파드가 없다

3단계에서 이미 만났다. 진단 순서를 정리해 둔다.

증상 
kubectl apply -f deploy.yaml     # created — 성공
kubectl get pods                 # 아무것도 없다
kubectl get deploy               # 0/1
진단 — 세 곳을 순서대로
순서명령보는 것
①kubectl get deploy X -o jsonpath='{.status.conditions[*].type}'ReplicaFailure가 있는가
②kubectl describe rs의 EventsFailedCreate의 메시지 전문
③kubectl get ns X --show-labels어떤 PSA 라벨이 걸려 있는가
판정ReplicaFailure=True이면 파드를 만들지도 못한 것이다. 파드가 떴다가 죽는 것(CrashLoopBackOff)과는 완전히 다른 상태이고, 볼 곳도 다르다 — 이쪽은 파드 로그가 아예 없다.

실패 ② 스펙은 맞는데 컨테이너가 안 뜬다

4·5단계에서 만난 상황이다. 어드미션을 통과했으므로 파드는 있는데 CreateContainerConfigError다.

원인

두 문지기의 판단 근거가 다르다. PSA는 스펙에 runAsNonRoot: true가 적혀 있는가만 보고, kubelet은 이미지가 정말 비루트인가를 확인한다. USER node처럼 이름으로 적힌 이미지는 확인할 수 없으므로 kubelet이 거부한다.

고친다

둘 중 하나면 된다. Dockerfile에 숫자 UID를 쓰는 것이 근본이고, 남의 이미지를 쓸 때는 파드 스펙에 runAsUser를 적는 것이 방법이다. 남의 이미지의 UID를 확인하는 법은 이렇다.

docker run --rm --entrypoint sh <이미지> -c 'id'
docker inspect <이미지> --format '{{.Config.User}}'
판정두 번째 명령이 빈 값이면 그 이미지는 루트로 실행되도록 만들어진 것이고, restricted에서 쓰려면 runAsUser를 스펙에서 강제하거나 이미지를 바꿔야 한다. 강제했을 때 앱이 파일 권한 때문에 실패하는 경우가 흔하므로 — 12단계의 nginx가 그 예다 — 비루트로 만들어진 이미지를 찾는 편이 빠르다.

실패 ③ warn을 걸었는데 아무 경고도 안 나온다

9단계에서 journal에 warn=restricted를 걸었는데 redis만 경고가 나왔다.

원인

PSA는 파드를 만들거나 파드 템플릿을 바꿀 때 동작하는 어드미션 컨트롤러다. kubectl apply가 unchanged를 돌려주면 apiserver에 쓰기가 일어나지 않았다는 뜻이고, 그러면 검증도 없다. 이미 떠 있는 파드는 정책을 어기고 있어도 계속 돈다.

고친다 — 강제로 재검증한다 
# 파드 템플릿을 실제로 바꿔 롤아웃을 일으킨다
kubectl -n journal rollout restart deploy/journal-api

# 또는 드라이런으로 검증만 시킨다 (실제로 바꾸지 않는다)
kubectl -n journal apply -k course/labs/k8s/journal --dry-run=server
판정--dry-run=server는 apiserver에 요청을 보내 어드미션까지 태우고 저장만 하지 않는다. 운영 중인 워크로드를 건드리지 않고 정책 위반을 조사하는 방법이고, enforce를 켜기 전에 반드시 해야 할 일이다.

클러스터 전체를 조사하려면 감사 로그(audit 모드)가 필요하다. 파드가 실제로 만들어질 때마다 기록이 남으므로, 며칠 두면 롤아웃이 도는 워크로드의 위반이 모인다. 감사 로그를 켜고 읽는 것은 M27에서 다룬다.

24.8운영 관점 — 어디까지 강제할 것인가

이 모듈에서 journal 하나를 restricted로 올렸다. 클러스터 전체에 같은 것을 하려면 순서와 예외가 필요하다.

이행 순서

단계라벨얻는 것
1warn=restricted · audit=restricted위반 수집. 아무것도 막지 않는다
2enforce=baseline 추가가장 위험한 것부터 막는다. 대부분의 워크로드가 통과한다
3워크로드 수정securityContext·Dockerfile·이미지
4enforce=restricted완료

2단계를 건너뛰고 바로 restricted를 강제하면 롤아웃이 도는 순간 서비스가 멈춘다. 그런데 3단계에서 본 것처럼 강제한 직후에는 아무 일도 일어나지 않는다 — 이미 떠 있는 파드는 그대로이기 때문이다. 그래서 사고는 며칠 뒤 배포할 때 터진다.

예외를 어떻게 다룰 것인가

시스템 구성요소는 restricted를 지킬 수 없다. CNI는 호스트 네트워크가 필요하고, CSI 드라이버는 호스트 경로를 마운트해야 하며, 노드 익스포터는 /proc을 읽는다. 우리 클러스터에서도 kube-system과 logging의 Alloy가 그렇다.

이런 것들은 네임스페이스를 나눠 예외를 격리한다. 애플리케이션 네임스페이스는 restricted로 두고, 시스템 네임스페이스만 privileged로 남기는 것이다. 예외를 파드 단위로 두면 관리할 수 없다 — PSA가 네임스페이스 단위로만 동작하는 것도 이 설계를 강제하기 위해서다.

PSA로 안 되는 것

PSA는 정해진 세 프로파일만 적용할 수 있다. "이미지는 사내 레지스트리에서만", "모든 파드에 team 라벨 필수", "latest 태그 금지" 같은 규칙은 표현할 수 없다.

그런 것은 M26에서 다룬다 — 내장 ValidatingAdmissionPolicy로 조건을 직접 쓰거나, Kyverno 같은 정책 엔진을 쓴다. PSA는 가장 흔한 위험을 설치 없이 막는 장치이고, 그 이상은 다른 도구의 몫이다.

보안은 층으로 쌓인다

지금까지 세 층이 쌓였다. M23의 RBAC이 API 요청을, 이 모듈의 PSA가 파드 스펙을, seccomp가 시스템 콜을 제한한다. 여기에 M25가 네트워크를 더한다.

어느 하나도 충분하지 않다는 것이 요점이다. RBAC이 완벽해도 파드가 hostPath를 쓰면 노드를 가져가고, PSA가 완벽해도 파드가 클러스터의 모든 서비스에 접근할 수 있으면 하나가 뚫렸을 때 전부 뚫린다. 한 층이 무너져도 다음 층이 남는 것이 목적이다.

24.9체크포인트와 정리

다음 모듈로 넘어가기 전 확인
  • kubectl get ns journal -o jsonpath='{.metadata.labels.pod-security\.kubernetes\.io/enforce}' → restricted
  • kubectl -n journal get po --no-headers | grep -vc Running → 0
  • kubectl -n journal exec deploy/journal-api -- id → uid=1000
  • kubectl -n journal get deploy journal-api -o jsonpath='{.spec.template.spec.automountServiceAccountToken}' → false
  • kubectl -n journal get deploy web-static -o jsonpath='{.spec.template.spec.containers[0].image}' → nginxinc/nginx-unprivileged:1.29-alpine
  • kubectl -n journal get sts redis -o jsonpath='{.spec.template.spec.securityContext.fsGroup}' → 999
  • grep '^USER' course/labs/apps/journal-api/Dockerfile → USER 1000
  • kubectl -n journal run rootpod --image=alpine:3.22 --restart=Never -- sleep 60 → Forbidden
  • curl -s -o /dev/null -w '%{http_code}' -H 'Host: journal.local' http://localhost:18080/api/entries → 200
  • curl -s -o /dev/null -w '%{http_code}' -H 'Host: journal.local' http://localhost:18080/ → 200
  • kubectl get ns m24 psa-privileged psa-baseline psa-restricted → 전부 NotFound
  • (이해 확인) apply가 성공했는데 파드가 없을 때와 파드가 CreateContainerConfigError일 때, 각각 어디를 봐야 하는지 적어 본다
  • (이해 확인) warn=restricted를 걸었는데 경고가 안 나오는 이유를 적어 본다
이 모듈이 남기는 파일
  • course/labs/apps/journal-api/Dockerfile — USER node → USER 1000
  • course/labs/k8s/journal/30-journal-api.yaml · 20-redis.yaml · 40-web-static.yaml — securityContext와 automountServiceAccountToken: false. web-static은 이미지와 포트도 바뀌었다
  • 클러스터: journal 네임스페이스가 enforce=restricted. 세 워크로드가 비루트로 돈다
  • apps 네임스페이스는 아직 걸지 않았다 — order-api는 이미 USER 10001이고 securityContext도 M19에서 넣었으므로, 라벨만 붙이면 통과한다. M27에서 클러스터 전체 태세를 볼 때 함께 다룬다

정리

# 실험 네임스페이스 넷을 지운다 (안의 파드도 함께 사라진다)
kubectl delete ns m24 psa-privileged psa-baseline psa-restricted --ignore-not-found

# 남아 있는지 확인
kubectl get ns --no-headers | awk '{print $1}'

journal의 restricted 라벨과 매니페스트 변경은 되돌리지 않는다. M25에서 네트워크 정책을 걸 때 같은 네임스페이스를 쓰고, M36 카오스 실험에서도 이 상태가 전제다.

실습 중 만든 파드가 journal에 남아 있으면 enforce=restricted 때문에 재시작되지 못한다. kubectl -n journal get po로 예상치 못한 파드가 없는지 한 번 확인한다.

다음 모듈

파드가 무엇을 할 수 있는지는 제한했다. 그런데 어디와 통신할 수 있는지는 아직 아무 제한이 없다. 지금 클러스터에서는 어느 네임스페이스의 어느 파드든 다른 모든 파드에 접근할 수 있다 — apps의 order-api가 journal의 레디스에 붙을 수 있고, 비밀번호만 알면 데이터를 읽는다.

M25에서 그것을 먼저 확인하고 default-deny를 건다. 그다음 필요한 경로만 열면서 DNS를 빠뜨려 모든 이름 해석이 죽는 흔한 사고를 재현한다 — 이그레스 정책의 대표적인 함정이다.
