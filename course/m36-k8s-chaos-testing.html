카오스 테스팅

Part 1부터 여기까지 만드는 것을 했다. 프로브를 걸고, 리소스를 정하고, 정책을 붙이고, 알림을 만들었다. 그것들이 실제로 동작하는지는 대부분 정상 상황에서만 확인했다. 이 모듈에서 클러스터를 계획적으로 망가뜨린다 — 파드를 죽이고, 통신에 지연을 넣고, CPU를 태우고, 앱이 오류를 내게 한다. 가설을 먼저 쓰고 실험으로 검증하며, 측정 도구가 먼저 막히는 것부터 겪는다.

핵심 3줄

1. 실험을 시작하기 전에 측정 도구가 동작하는지 확인한다 — M24와 M25가 부하 생성기를 두 번 막는다.

2. 파드 킬·지연·CPU 고갈을 주입하고 가설과 실측을 표로 남긴다. 지연 실험이 앱의 레디스 호출 횟수를 드러낸다.

3. 앱이 500을 내게 해서 M21의 알림이 실제로 발화하는지 확인하고, 퍼즈로 입력 검증이 없다는 것을 찾아낸다.

36.1만든 것이 동작하는지 모른다

M15에서 preStop을 10초로 잡았다. 그때 실패 요청이 20건에서 0건이 되는 것을 쟀으므로 그 설정은 검증됐다. 그런데 그 뒤로 스물한 개 모듈이 지나갔다. 이미지가 두 번 바뀌었고, 리소스와 보안 컨텍스트가 붙었고, 네트워크가 화이트리스트가 됐다.

지금도 파드 하나가 죽었을 때 요청이 떨어지지 않는지 아무도 모른다. M21에서 만든 알림도 마찬가지다 — 규칙을 쓰고 문법이 맞는 것은 확인했지만, 실제 장애에서 울리는지는 확인하지 않았다.

이런 것들의 공통점이 있다. 정상일 때는 아무것도 알려 주지 않는다. 프로브가 잘못 설정돼 있어도, 알림 표현식이 틀렸어도, PDB가 무의미해도 평소에는 증상이 없다. 그리고 진짜 장애가 났을 때 동작하지 않는다는 것을 그때 처음 안다.

카오스 테스팅은 그 확인을 계획된 시간에 앞당기는 것이다. 새벽 3시에 알게 될 일을 평일 오후에 알게 하고, 그때는 옆에 사람이 있고 되돌릴 준비가 돼 있다. 이 모듈의 실험 다섯 개 중 둘이 가설을 벗어난 결과를 냈다 — 그것이 이 방식의 값이다.

36.2이론 — 게임 데이와 폭발 반경

책 매핑20.1.1 목표 · 20.1.2 전제 조건 · 20.1.3 통신 카오스 · 20.1.4 작동 카오스 · 20.1.5 퍼즈 테스팅

전제 조건 둘이 먼저다

카오스 실험을 시작하기 전에 갖춰야 할 것이 둘이다. 관측이 없으면 무슨 일이 일어났는지 모르고, 자동 복구가 없으면 실험이 곧 장애다. 이 교재가 Part 4(관측)와 Part 3(안정성)을 먼저 한 이유가 그것이다.

여기에 하나를 더한다 — 측정 도구가 동작하는가. 36.3에서 부하 생성기가 두 번 막히는데, 그 상태로 실험을 시작했다면 "모든 요청이 실패한다"를 앱의 고장으로 오진했을 것이다.

가설을 먼저 쓴다

순서가 바뀌면 실험이 아니라 관찰이 된다. 주입하고 나서 결과를 보고 "그럴 줄 알았다"고 쓰는 것은 아무것도 검증하지 않는다.

가설에는 숫자가 있어야 한다. "괜찮을 것이다"가 아니라 "실패 요청 0건, P95 50ms 미만"이다. 그래야 결과가 가설을 지지하는지 판정할 수 있고, 정상 상태를 먼저 재는 일이 실험의 절반이 된다.

폭발 반경은 명시적으로 좁힌다

Chaos Mesh의 mode가 그 장치다. one은 하나, fixed는 지정한 수, all은 전부다. all은 실험이 아니라 사고이고, selector의 네임스페이스와 라벨이 그 위의 울타리다.

duration도 안전장치다. 실험 오브젝트를 지우는 것을 잊어도 스스로 끝난다. 이것이 없는 실험은 퇴근 후에도 계속 돈다.

여기에 중단 조건을 미리 정해 둔다 — "실패율 5%를 넘으면 즉시 삭제". 실험 중에 판단하려 들면 늦는다.

세 종류의 카오스

책은 셋으로 나눈다. 통신(20.1.3)은 네트워크를 건드린다 — 지연, 손실, 분단. 작동(20.1.4)은 프로세스와 자원을 건드린다 — 죽이기, CPU·메모리 고갈, 디스크. 퍼즈(20.1.5)는 입력을 건드린다.

셋이 찾는 것이 다르다. 통신 카오스는 타임아웃과 재시도 설계를, 작동 카오스는 복제와 자동 복구를, 퍼즈는 입력 검증을 시험한다. 이 모듈은 셋을 모두 해 본다.

36.3따라하기 ① 측정 도구부터 고친다

1단계 — Chaos Mesh를 설치한다

목적실험 도구를 넣는다. kind에서 걸리는 설정이 하나 있다.

helm repo add chaos-mesh https://charts.chaos-mesh.org
cat > course/labs/chaos/values.yaml <<'EOF'
chaosDaemon:
  runtime: containerd
  socketPath: /run/containerd/containerd.sock
dashboard:
  create: false
dnsServer:
  create: false
EOF
helm install chaos-mesh chaos-mesh/chaos-mesh --version 2.8.4 \
  -n chaos-mesh --create-namespace -f course/labs/chaos/values.yaml --wait --timeout 300s

runtime: containerd가 필수다. 기본값은 도커이고, kind는 containerd를 쓰므로 카오스 데몬이 컨테이너를 찾지 못한다. 대시보드는 만들지 않는다 — 실험은 매니페스트로 한다는 것이 이 모듈의 방침이고, UI로 클릭한 실험은 재현되지도 리뷰되지도 않는다.

kubectl -n chaos-mesh get po --no-headers
kubectl get crd | grep -c chaos-mesh
출력
chaos-controller-manager-65457d5957-hb6bf 1/1 Running 0 22s chaos-daemon-bsh82 1/1 Running 0 22s chaos-daemon-lwbmz 1/1 Running 0 22s 23
판정데몬이 2개다. 노드는 셋인데 컨트롤 플레인에는 테인트가 있어 뜨지 않았다 — 그 노드의 파드에는 실험을 주입할 수 없다는 뜻이다. 실습에서는 워커에만 워크로드가 있으니 문제가 없지만, 실제 클러스터에서 일부 노드에 데몬이 없으면 실험이 조용히 건너뛴다.

2단계 — 부하 생성기를 켠다 (두 번 막힌다)

목적실험 전 정상 상태를 재려는데, 도구가 먼저 고장 나 있다.

bash course/labs/scripts/loadgen.sh start
출력
Error from server (NotFound): pods "curlbox" not found
판정M15에서 만든 스크립트가 kubectl run으로 파드를 만드는데, M24에서 journal에 restricted를 걸었기 때문에 그 파드가 거부됐다. 오류 메시지는 "파드가 없다"라서 원인을 가리키지 않는다 — 거부는 kubectl run 단계에서 났고 스크립트가 그것을 삼켰다.

고친다. securityContext를 갖춘 매니페스트로 만들고, 이미지도 바꾼다 — 비루트라 apk add curl을 할 수 없으므로 curl이 들어 있는 이미지를 쓴다.

판정이번엔 파드는 떴는데 전부 000이다. M25의 default-deny가 부하 생성기의 경로를 막았다 — 허용한 것은 인그레스와 프로메테우스뿐이고, 클러스터 안에서 직접 때리는 것은 그 목록에 없다.

진단용 경로를 명시적으로 연다. 라벨로 대상을 좁히고, 실험이 끝나면 지운다.

판정정상 상태를 잡았다 — 약 170 req/s, 실패 2건(0.05%). 이 두 건은 파드가 준비되기 전의 첫 요청들이다. 이제 실험을 시작할 수 있다.

여기서 배운 것을 정리해 둔다. 보안 설정을 강화한 뒤 진단 도구를 다시 확인하지 않으면, 사고 대응 중에 그 사실을 알게 된다. M24·M25를 한 시점과 이 모듈 사이에 열한 개 모듈이 있었고, 그동안 아무도 눈치채지 못했다.

36.4따라하기 ② 파드를 죽인다

1단계 — 손으로 먼저 한다

목적도구 없이 되는 실험은 도구 없이 한다. 가설 검증에 도구가 필요한 것은 아니다.

가설: journal-api 파드 하나가 죽어도 실패 요청은 0이다. 근거: M15의 preStop 10초와 프로브 3종, M16의 PDB.

bash course/labs/scripts/loadgen.sh reset
P=$(kubectl -n journal get po -l app=journal-api -o jsonpath='{.items[0].metadata.name}')
kubectl -n journal delete pod $P --wait=false
sleep 45
bash course/labs/scripts/loadgen.sh report
출력
요청 수 / 응답 코드 분포: 10236 10236 200
판정가설 성립. 1만 건 넘게 보내는 동안 실패가 없다. M15에서 preStop 없이 쟀을 때 20건이 떨어졌던 것과 비교하면, 그 설정이 21개 모듈이 지난 지금도 유효하다는 확인이다.

2단계 — 도구로 한다

목적실험을 매니페스트로 만든다. 그래야 반복하고 리뷰하고 저장소에 남긴다.

apiVersion: chaos-mesh.org/v1alpha1
kind: PodChaos
metadata: {name: kill-one-api, namespace: journal}
spec:
  action: pod-kill
  mode: one              # <- 폭발 반경. all 로 두면 실험이 아니라 사고다
  selector:
    namespaces: [journal]
    labelSelectors: {app: journal-api}
  duration: "10s"
kubectl apply -f course/labs/chaos/10-podchaos.yaml
kubectl -n journal get podchaos --no-headers
kubectl -n journal get podchaos kill-one-api \
  -o jsonpath='{.status.experiment.containerRecords[*].id}{"\n"}'
bash course/labs/scripts/loadgen.sh report
출력
kill-one-api 25s journal/journal-api-59546f4fbc-jhw6k 요청 수 / 응답 코드 분포: 16971 16971 200
판정status에 어느 파드를 죽였는지가 남는다. 실험 기록이 오브젝트에 있다는 것이 UI로 클릭하는 것과의 차이다 — 나중에 "그날 무엇을 했나"를 클러스터에 물어볼 수 있다.

반복 실험은 Schedule로 만든다. 한 번 살아남는 것과 계속 살아남는 것은 다르다 — 1분마다 한 마리씩 죽이면서 실패율이 유지되는지 보는 것이 더 강한 검증이다.

kind: Schedule
spec:
  schedule: "*/1 * * * *"
  concurrencyPolicy: Forbid    # M35 의 크론잡과 같은 개념
  historyLimit: 3
  type: PodChaos
  podChaos: {action: pod-kill, mode: one, selector: {...}}

36.5따라하기 ③ 느리게 만든다

1단계 — 레디스로 가는 길에 지연을 넣는다

목적통신 카오스(20.1.3). 죽는 것보다 느려지는 것이 다루기 어렵다.

가설: 200ms 지연이 생기면 응답이 그만큼 느려지지만 실패는 없다.

kind: NetworkChaos
spec:
  action: delay
  mode: all
  selector:
    namespaces: [journal]
    labelSelectors: {app: journal-api}
  direction: to
  target:                        # <- 어느 쪽으로 가는 트래픽인가
    mode: all
    selector:
      namespaces: [journal]
      labelSelectors: {app: redis}
  delay: {latency: "200ms"}
  duration: "60s"

direction과 target이 폭발 반경을 만든다. journal-api에서 redis로 가는 트래픽만 느려지고, 인그레스에서 오는 것과 프로메테우스 스크레이프는 그대로다.

kubectl -n journal exec curlbox -- sh -c \
  'for i in 1 2 3; do curl -s -o /dev/null -w "%{time_total}s %{http_code}\n" \
     --max-time 5 http://journal-api:8080/api/entries; done'
출력 (지연 중 / 평상시)
0.404048s 200 0.404748s 200 0.403853s 200 0.001518s 200 0.001321s 200 0.001141s 200
판정가설은 성립했다. 그런데 404ms는 200ms의 두 배다. 요청 하나가 레디스를 두 번 부른다는 뜻이고, 실제로 그렇다 — KEYS로 키 목록을 받고 MGET으로 값을 받는다. 지연 실험이 호출 횟수를 드러냈다 — 코드를 읽지 않고 알아낸 사실이다.

이것이 통신 카오스의 부수적인 값이다. 외부 의존이 하나 느려졌을 때 우리 응답이 몇 배로 느려지는가가 곧 그 의존을 몇 번 부르는지를 말해 준다. 실측값이 예상보다 크면 줄일 수 있는 호출이 있다는 신호다.

2단계 — 타임아웃을 넘겨 본다

목적느림이 죽음이 되는 지점을 찾는다.

가설: 지연이 클라이언트 타임아웃(2초)을 넘으면 실패가 나타난다. 부하 생성기의 --max-time 2가 그 타임아웃이다.

  delay: {latency: "1500ms"}     # 왕복 2회 = 3초 > 2초
  duration: "45s"
출력 (평상시 20초 / 지연 40초)
2368 2368 200 109 76 000 33 200
판정처리량이 118 req/s에서 2.7 req/s로 떨어졌고 70%가 실패했다. 백엔드는 살아 있고 응답도 하는데 클라이언트가 기다려 주지 않는다 — 느림과 죽음의 경계는 클라이언트가 정한다.

여기서 나오는 설계 질문이 있다. 타임아웃을 늘리면 될까. 늘리면 실패는 줄지만 느린 요청이 커넥션을 붙잡아 처리량이 더 떨어지고, 결국 앞단이 밀린다. 타임아웃은 포기하는 시점을 정하는 것이지 성공률을 올리는 손잡이가 아니다.

3단계 — CPU를 태운다

목적작동 카오스(20.1.4). M17의 HPA가 실제로 반응하는지 본다.

가설: 파드 하나의 CPU를 고갈시키면 ① HPA가 파드를 늘리고 ② 실패는 없다.

kind: StressChaos
spec:
  mode: one
  selector:
    namespaces: [journal]
    labelSelectors: {app: journal-api}
  stressors:
    cpu: {workers: 2, load: 100}
  duration: "90s"
kubectl -n journal get hpa journal-api --no-headers   # 실험 전 / 중
kubectl top pods -n journal -l app=journal-api --no-headers
출력
실험 전: journal-api cpu: 33%/50% 3 8 4 실험 중: journal-api cpu: 1051%/50% 3 8 5 → 8 journal-api-...-nlrjn 2022m 43Mi <- 스트레스 받은 파드 journal-api-...-4vldx 34m 34Mi journal-api-...-9h6sb 47m 37Mi journal-api-...-bdb4x 23m 38Mi ... (나머지도 22~47m) 요청 18,756건 전부 200
판정가설은 성립했다 — 실패 0건, HPA가 최대치까지 늘렸다. 그런데 늘린 것이 옳았는가는 다른 질문이다. 파드 하나가 2022m을 쓰는 동안 나머지 일곱은 22~47m으로 놀고 있었다. HPA는 평균을 보므로 한 파드의 이상이 전체 평균을 1051%로 만들었고, 클러스터 자원을 8배로 쓰게 했다.

이것이 M17에서 다룬 HPA의 성질이 장애 상황에서 어떻게 나타나는지다. 한 파드가 비정상일 때 필요한 것은 파드를 늘리는 것이 아니라 그 파드를 빼는 것인데, HPA에는 그런 개념이 없다. 그 일은 프로브(M15)가 해야 하고, CPU 고갈은 프로브를 실패시키지 않는다(요청은 여전히 처리된다, 느릴 뿐). 두 장치 사이에 틈이 있다는 것을 이 실험이 보여 준다.

36.6따라하기 ④ 오류와 알림

1단계 — 밖에서 연결을 끊는다

목적앱을 고치지 않고 HTTP 응답을 바꾼다. 그리고 알림이 울리지 않는 것을 본다.

kind: HTTPChaos
spec:
  mode: all
  selector:
    namespaces: [journal]
    labelSelectors: {app: journal-api}
  target: Request
  port: 8080
  path: "/api/entries"
  method: "GET"
  abort: true
  duration: "180s"
bash course/labs/scripts/loadgen.sh report
curl -s -o /dev/null -m 5 -w '%{http_code}\n' -H 'Host: journal.local' http://localhost:18080/api/entries
curl -s -o /dev/null -m 5 -w '%{http_code}\n' -H 'Host: journal.local' http://localhost:18080/
출력
4291 4291 000 502 200
판정API는 완전히 죽었고 정적 파일은 200이다 — 폭발 반경이 path와 labelSelectors로 제한됐다. 인그레스는 502를 준다: 업스트림이 연결을 끊었을 때의 표준 응답이다.
# 프로메테우스 /api/v1/alerts 에서 우리 알림만
출력
(AppHighErrorRate 가 없다) KubeHpaMaxedOut pending warning Watchdog firing none
판정에러율 알림이 울리지 않는다. 요청이 앱에 도달하지 못했으므로 http_server_requests_seconds_count가 증가하지 않았고, 에러율의 분모도 분자도 0이다. 알림은 관측 지점 뒤의 고장만 본다 — 이것이 이 실험에서 얻은 가장 중요한 사실이다.

대응은 관측 지점을 앞으로도 두는 것이다. 인그레스 컨트롤러의 메트릭(5xx 비율)이나 클러스터 밖에서의 합성 모니터링이 이 구멍을 메운다. M21에서 앱 지표만으로 알림을 만든 것이 절반의 커버리지였다는 뜻이다.

2단계 — 앱이 스스로 오류를 내게 한다

목적메트릭에 기록되는 고장을 만들어 알림 경로 전체를 검증한다.

가설: 에러율이 50%가 되면 AppHighErrorRate가 2분 안에 발화한다.

# M30 에서 만든 손잡이를 쓴다. FAULT_RATE 는 v3 이미지에만 있다.
kubectl -n journal set image deploy/journal-api api=journal-api:v3
kubectl -n journal set env deploy/journal-api FAULT_RATE=0.5
kubectl -n journal rollout status deploy/journal-api
출력 (45초 부하)
7153 3616 200 3537 500
# 2분 30초 뒤 알림과 에러율 쿼리
출력
AppHighErrorRate firing journal-api — journal-api 에러율 35.5% 에러율(2m rate): 48.6 %
판정가설 성립. M21에서 쓴 규칙이 실제 장애에서 울렸다 — 규칙의 문법이 맞는 것과 울리는 것 사이의 간격을 여기서 메웠다. 알림 메시지의 35.5%와 지금 쿼리의 48.6%가 다른 것은 발화 시점의 값과 지금 값이기 때문이고, 시간창(2분)이 겹쳐 있어 생긴 차이다.

실험이 끝나면 반드시 되돌린다. 되돌리는 것을 실험 시트의 항목으로 두는 것이 좋다 — 앞의 실험들은 duration이 있어 저절로 끝나지만, 이것은 배포를 바꾼 것이라 사람이 되돌려야 한다.

kubectl -n journal set env deploy/journal-api FAULT_RATE-
kubectl -n journal set image deploy/journal-api api=journal-api:v1

3단계 — 퍼즈

목적입력을 흔든다(20.1.5). 500이 나오는 지점을 찾는 것이 목표다.

무작위 바이트열보다 경계값과 형식 위반이 버그를 잘 찾는다. 빈 객체, null, 타입 위반, 아주 긴 값, JSON이 아닌 것.

bash course/labs/scripts/fuzz-api.sh 26
출력
퍼즈 시작 — 26 회 --- 응답 코드 분포 24 201 2 400 판정: 통과 — 500 대 없음
판정가설(500이 나오지 않는다)은 성립했다. 그런데 이 결과가 더 나쁘다. 26번 중 24번이 201 Created다 — 서버가 거의 모든 것을 받아들여 저장했다는 뜻이다.
for P in '{}' '{"text":null}' '{"text":123}' '{"text":[1,2,3]}' 'not json at all' '[]'; do
  ... POST 해서 코드만 본다 ...
done
kubectl -n journal exec curlbox -- curl -s http://journal-api:8080/api/entries
출력
{} -> 201 {"text":null} -> 201 {"text":123} -> 201 {"text":[1,2,3]} -> 201 not json at all -> 400 [] -> 201 총 31 건 {} {"text":""} {"text":{"nested":"object"}} {"text":"ok","extra":"모르는 필드"}
판정입력 검증이 전혀 없다. 400이 나온 것은 JSON 파서가 거부한 하나뿐이고, JSON이기만 하면 무엇이든 저장된다. 퍼즈가 찾으려던 충돌(500)은 없었지만 데이터 오염을 찾았다 — 이 앱을 그대로 쓰면 저장소가 쓰레기로 찬다.

조치는 둘이다. 앱에 스키마 검증을 넣고(text가 문자열이고 길이 제한이 있어야 한다), 퍼즈를 CI에 넣는다(M29의 파이프라인에 한 단계로). 그리고 실험이 만든 쓰레기 31건을 지운다 — 카오스 실험은 뒷정리까지가 실험이다.

36.7일부러 실패시키기

실패 ① — 측정 도구가 막혀 앱을 오진한다

목적36.3에서 겪은 것을 사고의 형태로 다시 본다.

출력
요청 수 / 응답 코드 분포: 52 52 000
판정이 화면만 보면 "앱이 완전히 죽었다"고 읽힌다. 실제로는 앱이 멀쩡하고 측정 도구가 막힌 것이다. 카오스 실험 중에 이 화면을 봤다면 실험을 중단하고 앱을 뒤졌을 것이고, 아무 문제도 찾지 못했을 것이다.

구분하는 방법이 있다. 다른 경로로 같은 것을 확인한다 — 인그레스로 부르고(curl -H 'Host: journal.local'), 프로메테우스 타깃 상태를 보고, 파드 로그를 본다. 셋 중 하나라도 정상이면 측정 도구를 의심한다.

더 나은 대응은 실험 전에 정상 상태를 재는 것이다. 게임 데이 4단계의 첫 단계가 그것이고, 이 실습에서 그 단계가 실제로 값을 냈다 — 주입하기 전에 도구가 고장 난 것을 알았다.

실패 ② — 알림이 울리지 않는 고장이 있다

목적36.6의 관찰을 관측 설계의 문제로 정리한다.

두 실험을 나란히 놓는다. 둘 다 사용자가 보기에 서비스가 죽은 상태다.

고장사용자가 보는 것앱 메트릭알림
HTTPChaos abort502증가하지 않음울리지 않음
FAULT_RATE=0.55005xx 카운터 증가2분 뒤 발화
판정같은 심각도의 장애인데 한쪽만 알림이 울린다. M21의 규칙이 http_server_requests_seconds_count에만 의존하기 때문이고, 그 지표가 증가하지 않는 고장은 보이지 않는다. 파드가 통째로 죽는 경우는 AppTargetDown이 잡지만, 이 실험처럼 파드는 살아 있는데 요청이 앞에서 끊기는 상황은 어느 규칙에도 걸리지 않는다.

메우는 방법이 셋이다. 인그레스 컨트롤러의 메트릭으로 5xx 비율을 보고(사용자에게 가장 가깝다), 합성 모니터링으로 클러스터 밖에서 주기적으로 부르고, 트래픽 부재를 알림으로 만든다(rate(...) == 0 — 요청이 아예 없는 것도 이상 신호다).

세 번째가 특히 값싸다. M21에서 쓴 or vector(0) 기법으로 지표가 사라진 것과 0인 것을 구분할 수 있고, 야간처럼 원래 트래픽이 없는 시간대는 시간 조건으로 뺀다.

36.8운영 관점 — 실험 시트와 스테이징의 한계

시트가 실험을 실험으로 만든다

이 모듈의 산출물 중 매니페스트보다 중요한 것이 chaos/GAMEDAY.md다. 각 실험이 가설·근거·폭발 반경·중단 조건·실측·판정·배운 것으로 정리돼 있다.

이 형식이 강제하는 것이 있다. 가설을 쓰려면 정상 상태를 숫자로 정의해야 하고, 중단 조건을 쓰려면 얼마까지 감당할지 미리 정해야 한다. 그리고 "배운 것" 칸이 비어 있으면 그 실험은 할 필요가 없었다.

이 모듈의 다섯 실험 중 셋에서 가설 밖의 것을 배웠다 — 레디스 호출이 두 번이라는 것, HPA가 한 파드 때문에 전체를 늘린다는 것, 입력 검증이 없다는 것. 가설이 맞았다는 확인보다 이쪽이 값이 크다.

실험을 언제 어디서 돌릴 것인가

순서가 있다. 개발 클러스터에서 도구를 익히고, 스테이징에서 실험을 설계하고, 운영에서 폭발 반경을 좁혀 돌린다. 마지막 단계를 건너뛰면 실험의 값이 크게 떨어지는데, 스테이징에서 재현되지 않는 것이 많기 때문이다.

책이 정리한 스테이징의 한계를 이 교재의 경험으로 다시 쓰면 이렇다.

재현되지 않는 것이 모듈에서의 예
실제 트래픽 양과 분포실험 ③의 HPA 반응은 부하가 있어야 나온다
실제 데이터 크기레디스에 3건일 때와 300만 건일 때 KEYS의 비용이 다르다
실제 노드 수와 배치데몬이 없는 노드에는 실험이 주입되지 않는다
사용자의 재시도 행동실패하면 사람은 새로고침을 누른다 — 부하가 늘어난다
외부 의존의 실제 지연실험 ②는 우리가 정한 200ms지 실제 값이 아니다
시간며칠에 걸쳐 새는 메모리는 90초 실험에서 안 보인다

운영에서 돌릴 때의 최소 조건

세 가지가 갖춰져야 한다. 중단 버튼(실험 오브젝트를 지우면 즉시 멈추는가 — duration과 함께 확인한다), 알림 경로(실험이 진짜 장애를 만들었을 때 사람이 안다), 공지(다른 팀이 그 시간대의 이상을 실험으로 이해한다).

세 번째를 빠뜨리면 실험이 다른 팀의 장애 대응을 유발한다. 실험 시간과 대상을 미리 알리는 것이 게임 데이의 절반이다.

다음에 추가할 실험

이 모듈에서 다루지 않은 것 중 값이 큰 것 셋을 적어 둔다. 노드 하나를 통째로 잃는 실험(M16의 PDB와 토폴로지 분산이 그때 시험된다), DNS 장애(M25에서 본 이그레스 사고를 DNSChaos로 재현), 디스크 가득 참(M18의 볼륨 확장이 그때 필요해진다).

공통점이 있다. 앞의 모듈에서 만든 것을 시험한다는 것이다. 카오스 실험은 새로운 것을 찾는 도구가 아니라 이미 넣은 안전장치를 확인하는 도구다.

# 배포를 원래대로 되돌렸는지 확인한다
kubectl -n journal get deploy journal-api \
  -o jsonpath='{.spec.template.spec.containers[0].image}{"\n"}'
kubectl -n journal get deploy journal-api \
  -o jsonpath='{.spec.template.spec.containers[0].env[*].name}{"\n"}'

journal-api:v1이고 FAULT_RATE가 없어야 한다. 실험이 배포를 바꾼 것은 사람이 되돌린다 — duration이 지켜 주지 않는 유일한 경우다.

Chaos Mesh와 allow-loadgen 정책은 남긴다. M37의 부하 시험에서 부하와 장애를 겹쳐서 보고, M38 캡스톤의 검증 절차에 실험 시트가 들어간다.

HPA가 8개까지 올라가 있으면 부하를 멈춘 뒤 몇 분 안에 stabilizationWindowSeconds(M17에서 120초로 잡았다)를 지나 줄어든다. 급하면 kubectl -n journal delete hpa journal-api 없이 기다린다 — HPA를 지우면 replicas가 그 자리에 고정된다.

다음 모듈

이 모듈의 부하 생성기는 측정 도구지 부하 도구가 아니다. 초당 170건을 보내며 응답 코드를 세는 것이 전부이고, 목표 RPS를 정하거나 분위수를 보거나 시나리오를 나누지 못한다.

M37에서 k6로 제대로 된 부하 시험을 만든다. 목표 RPS를 계단식으로 올리며 어디서 무너지는지를 찾고, M20의 히스토그램과 k6가 각각 재는 지연이 왜 다른지를 확인한다. 그리고 이 모듈의 카오스와 겹쳐서 부하가 있는 상태의 장애를 본다.
