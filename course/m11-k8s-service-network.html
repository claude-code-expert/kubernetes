서비스와 클러스터 네트워크

M08에서 파드를 지웠더니 IP가 다른 새 파드가 생겼다. 그럼 그 파드를 부르던 쪽은 어떻게 되나. 서비스는 그 문제 하나를 풀기 위해 존재한다 — 그리고 셀렉터 오타 하나면 그 해결책이 조용히 무력화된다.

핵심 3줄

1. 서비스는 고정된 이름과 가상 IP다. 뒤에 있는 파드가 바뀌어도 앞은 그대로다.

2. 연결은 레이블 셀렉터로 맺어지고, 실제 대상 목록은 EndpointSlice에 적힌다. 문제가 생기면 여기부터 본다.

3. 셀렉터가 어긋나면 서비스는 정상으로 보이고 엔드포인트만 비어 있다. 호출하는 쪽은 connection refused만 받는다.

11.1왜 expose 한 줄로는 안 되는가

M10에서 kubectl expose deploy journal-api --port=8080 한 줄로 서비스를 만들어 부하 측정에 썼다. 잘 동작했다. 그런데 그 한 줄이 무엇을 만들었는지, 요청이 journal-api:8080이라는 이름에서 어떻게 파드까지 갔는지는 보지 않았다.

보지 않아도 됐던 이유는 셀렉터를 디플로이먼트에서 자동으로 베껴 왔기 때문이다. 실무에서 서비스는 사람이 파일로 쓰고, 셀렉터·포트·타입을 직접 적는다. 그 셋 중 하나만 어긋나도 서비스는 정상으로 보이면서 트래픽을 아무 데도 보내지 않는다 — M09 실패 ①에서 예고한 "조용한 0개"가 서비스에서는 어떻게 나타나는지, 그리고 그것을 어디서 잡아내는지가 이 모듈의 절반이다.

나머지 절반은 M08 7단계의 질문이다. 파드를 지우면 IP가 다른 새 파드가 생겼다. 그럼 그 파드를 부르던 쪽은 어디로 요청을 보내야 하나. M10에서 expose로 만든 서비스는 정리 블록에서 지웠으므로, 같은 것을 파일로 다시 만들면서 그 안을 들여다본다.

11.2이론 — 네 가지 서비스 타입

M05의 도커 네트워크에서는 컨테이너 이름이 곧 주소였다. 쿠버네티스에서는 파드가 훨씬 자주 죽고 다시 만들어지므로, 파드 이름을 주소로 쓸 수 없다. 그래서 파드 집합 앞에 고정된 이름을 세운다. 책 9.3(쿠버네티스 서비스)이 아래 네 타입을 나열하는 절이다.

타입접근 범위쓰는 곳
ClusterIP (기본)클러스터 내부만대부분의 서비스 간 통신. 외부 노출은 인그레스가 담당한다(M12)
NodePort모든 노드의 특정 포트(30000~32767)로드밸런서가 없는 환경, 온프레미스 진입점. 포트를 사람이 관리해야 한다
LoadBalancer클라우드 로드밸런서가 붙은 외부 IP클라우드에서 외부 공개. 로컬 kind에서는 EXTERNAL-IP가 <pending>으로 남는다
ExternalName—클러스터 밖 주소에 클러스터 안 이름을 붙인다. CNAME으로만 동작하고 프록시하지 않는다(M34)

여기에 타입은 아니지만 중요한 변형이 하나 더 있다. clusterIP: None인 헤드리스 서비스 (Headless Service)는 가상 IP를 만들지 않고 DNS 조회에 파드 IP를 그대로 돌려준다. 클라이언트가 개별 파드를 직접 골라야 하는 경우 — 데이터베이스 복제본, 카프카 브로커 — 에 쓰며, 스테이트풀셋과 짝을 이룬다 — M14에서 레디스로 처음 쓰고 M18에서 파고든다.

11.3이론 — 요청이 파드에 닿기까지

서비스 이름으로 요청을 보내면 네 단계를 거친다. 어느 단계가 깨졌는지 아는 것이 네트워크 문제 진단의 전부다. 책 9.1(쿠버네티스 네트워킹 원리)이 파드 네트워크와 CNI를, 9.2(서비스 디스커버리)가 아래 1단계의 DNS 이름 규칙을 다룬다.

  1. DNS — CoreDNS가 journal-api를 서비스의 ClusterIP로 바꾼다
  2. 연결 시도 — 클라이언트가 그 가상 IP로 패킷을 보낸다. 이 IP를 가진 네트워크 인터페이스는 어디에도 없다
  3. kube-proxy 규칙 — 노드의 커널 규칙(iptables 또는 nftables)이 그 패킷의 목적지를 실제 파드 IP 중 하나로 바꾼다(DNAT)
  4. 파드 도착 — CNI 플러그인이 만든 네트워크로 해당 파드에 전달된다

대상 파드 목록은 엔드포인트슬라이스 (EndpointSlice)라는 오브젝트에 들어 있다. 엔드포인트 컨트롤러가 셀렉터에 맞는 파드를 찾아 준비된(ready) 것만 여기에 넣고, kube-proxy가 이 목록을 보고 규칙을 만든다. 파드가 죽거나 레디니스 프로브가 실패하면 목록에서 빠진다 — M10의 롤아웃 중 트래픽이 옮겨간 것이 이 메커니즘이다.

Endpoints 와 EndpointSlice 예전에는 Endpoints라는 오브젝트 하나에 모든 파드 IP를 담았다. 파드가 수천 개인 서비스에서 갱신 비용이 커져 여러 조각으로 나눈 EndpointSlice가 도입됐고, 지금은 이쪽이 정본이다. Endpoints API는 1.33에서 deprecated됐다 — 검색하면 kubectl get endpoints가 많이 나오지만, 이 과정은 kubectl get endpointslices를 쓴다. 출처: kubernetes.io/docs/concepts/services-networking/endpoint-slices/

11.4따라하기 ① ClusterIP와 엔드포인트

1단계. 서비스 세 개를 만든다

목적M10에서 expose로 만든 것을 파일로 다시 쓰고, 타입이 다른 서비스 셋을 나란히 만들어 비교한다.

# course/labs/k8s/m11-services.yaml
apiVersion: v1
kind: Service
metadata:
  name: journal-api            # 이 이름이 클러스터 안 DNS 이름이 된다
spec:
  type: ClusterIP              # 기본값. 클러스터 내부에서만 접근 가능
  selector:
    app: journal-api           # 이 레이블을 가진 파드로 트래픽을 보낸다
  ports:
    - name: http
      port: 8080               # 서비스가 여는 포트
      targetPort: 8080         # 파드의 포트
---
apiVersion: v1
kind: Service
metadata:
  name: journal-api-nodeport
spec:
  type: NodePort
  selector:
    app: journal-api
  ports:
    - port: 8080
      targetPort: 8080
      nodePort: 30080          # 30000~32767 범위. 생략하면 자동 할당
---
apiVersion: v1
kind: Service
metadata:
  name: journal-api-headless
spec:
  clusterIP: None              # 헤드리스 — 가상 IP 없이 파드 IP를 직접 돌려준다
  selector:
    app: journal-api
  ports:
    - port: 8080

port와 targetPort를 구분한다. 앞은 서비스가 받는 포트, 뒤는 파드가 듣는 포트다. 여기서는 둘 다 8080이지만, 서비스를 80으로 열고 파드는 8080을 쓰는 구성이 흔하다.

kubectl apply -f course/labs/k8s/m11-services.yaml
kubectl get svc
실행 결과
service/journal-api created service/journal-api-nodeport created service/journal-api-headless created NAME TYPE CLUSTER-IP EXTERNAL-IP PORT(S) AGE journal-api ClusterIP 10.96.48.160 <none> 8080/TCP 0s journal-api-headless ClusterIP None <none> 8080/TCP 0s journal-api-nodeport NodePort 10.96.14.138 <none> 8080:30080/TCP 0s kubernetes ClusterIP 10.96.0.1 <none> 443/TCP 42h
판정새 서비스 3행의 AGE가 같다 — M10 정리에서 expose로 만든 것을 지웠으므로 셋이 지금 함께 생겼다. CLUSTER-IP는 환경마다 다르고, 이 문서의 나머지 출력은 10.96.48.160을 기준으로 이어진다. kubernetes 서비스의 AGE는 클러스터를 만든 시점부터다.

헤드리스 서비스의 CLUSTER-IP가 None이다. kubernetes 서비스는 클러스터가 기본으로 만든 것으로, 파드 안에서 apiserver를 부를 때 쓰는 주소다(M23에서 다시 나온다).

2단계. 엔드포인트를 확인한다

목적서비스를 만든 뒤 반드시 확인해야 할 것. 여기가 비어 있으면 서비스는 무용지물이다.

kubectl get endpointslices -l kubernetes.io/service-name=journal-api

kubectl get endpointslices -l kubernetes.io/service-name=journal-api \
  -o jsonpath='{range .items[*].endpoints[*]}{.addresses[0]}{" ready="}{.conditions.ready}{"\n"}{end}'
실행 결과
NAME ADDRESSTYPE PORTS ENDPOINTS AGE journal-api-ptw2m IPv4 8080 10.244.1.56,10.244.1.57,10.244.2.61 + 1 more... 0s 10.244.1.56 ready=true 10.244.1.57 ready=true 10.244.2.61 ready=true 10.244.2.60 ready=true
  • -l kubernetes.io/service-name=journal-api — 엔드포인트슬라이스는 이름이 <서비스>-<임의문자열>이라 이름으로 찍을 수 없다. 서비스 이름이 이 레이블에 들어 있으므로 레이블로 고른다
  • -o jsonpath='{range ...}{end}' — 목록을 한 항목씩 돌며 원하는 필드만 찍는다. ENDPOINTS 열은 3개까지만 보여주고 나머지를 + N more...로 접기 때문에 전부 보려면 이렇게 뽑는다
판정파드 4개의 IP가 전부 ready=true로 등록됐다. kubectl get pods -l app=journal-api -o wide의 IP 열과 같은 값이어야 한다. IP는 환경마다 다르다.

3단계. 부하가 실제로 나뉘는지 본다

목적서비스 하나가 파드 여럿에 요청을 나누는지 응답의 pod 필드로 확인한다.

kubectl exec curlbox -- sh -c 'for i in $(seq 1 12); do curl -s -m 2 http://journal-api:8080/healthz; echo; done' \
  | sort | uniq -c
실행 결과
3 {"status":"ok","version":"v1","pod":"journal-api-55c87ff598-4fb2b"} 2 {"status":"ok","version":"v1","pod":"journal-api-55c87ff598-52xh5"} 2 {"status":"ok","version":"v1","pod":"journal-api-55c87ff598-mr9c2"} 5 {"status":"ok","version":"v1","pod":"journal-api-55c87ff598-w2qss"}
판정12번의 요청이 파드 4개에 나뉘었다(55c87ff598은 M10의 v1 레플리카셋 해시다). 균등하지 않은 것이 정상이다 — 커널 규칙이 확률적으로 고르기 때문이며, 요청 수가 많아질수록 고르게 수렴한다. 파드 이름 접미사와 분포는 환경마다 다르다.

서비스를 만든 직후 바로 치면 응답 대신 빈 줄이 몇 개 섞여 나올 수 있다(이 검증에서는 1단계 직후 12번 중 6번이 빈 줄이었다). kube-proxy가 각 노드의 규칙을 갱신하는 데 1~2초가 걸리기 때문이며, 몇 초 뒤 다시 치면 사라진다. 이 지연은 M10의 17건과 같은 뿌리다 — 서비스 목록이 바뀐 것과 노드의 규칙이 바뀐 것은 같은 순간이 아니다.

주의할 점이 하나 있다. 이 분산은 연결 단위다. HTTP keep-alive로 커넥션을 유지하는 클라이언트는 한 파드에 계속 붙어 있는다. gRPC처럼 커넥션을 오래 쓰는 프로토콜에서 부하가 한쪽에 몰리는 현상이 여기서 나오고, 해결책이 클라이언트 측 로드밸런싱이나 서비스 메시(M25)다.

11.5따라하기 ② DNS와 헤드리스

4단계. 이름이 무엇으로 풀리는지 비교한다

목적같은 이름 규칙의 두 서비스가 DNS에서 무엇으로 풀리는지 비교한다. 정식 이름(FQDN)으로 조회한다 — 이유는 이 단계 끝에 있다.

kubectl exec curlbox -- nslookup journal-api.default.svc.cluster.local
kubectl exec curlbox -- nslookup journal-api-headless.default.svc.cluster.local
실행 결과 — ClusterIP
Server: 10.96.0.10 Address: 10.96.0.10:53 Name: journal-api.default.svc.cluster.local Address: 10.96.48.160
실행 결과 — 헤드리스
Server: 10.96.0.10 Address: 10.96.0.10:53 Name: journal-api-headless.default.svc.cluster.local Address: 10.244.2.60 Name: journal-api-headless.default.svc.cluster.local Address: 10.244.1.57 Name: journal-api-headless.default.svc.cluster.local Address: 10.244.2.61 Name: journal-api-headless.default.svc.cluster.local Address: 10.244.1.56
판정맨 위 Server: 10.96.0.10은 질문을 받은 DNS 서버 — CoreDNS의 ClusterIP다. ClusterIP 서비스는 1단계 CLUSTER-IP와 같은 가상 IP 하나, 헤드리스는 2단계 엔드포인트슬라이스에 있던 파드 IP 네 개를 돌려준다. 헤드리스에서는 어느 파드로 갈지 클라이언트가 정한다. 헤드리스 응답의 순서는 조회마다 바뀐다.

이름의 전체 형태 — 그리고 짧은 이름으로 조회하면 생기는 잡음

서비스의 정식 이름은 <서비스>.<네임스페이스>.svc.cluster.local이다. 같은 네임스페이스 안에서는 journal-api만 써도 되는데, 파드의 /etc/resolv.conf에 검색 도메인이 설정돼 있어 뒤를 자동으로 붙여주기 때문이다.

kubectl exec curlbox -- cat /etc/resolv.conf
실행 결과
search default.svc.cluster.local svc.cluster.local cluster.local nameserver 10.96.0.10 options ndots:5

search 줄이 그 목록이다. curl http://journal-api:8080이 되는 이유는 리졸버가 journal-api.default.svc.cluster.local을 먼저 만들어 물어보기 때문이다. 다른 네임스페이스의 서비스를 부를 때는 journal-api.other-ns처럼 네임스페이스를 붙인다 — 두 번째 검색 도메인 svc.cluster.local이 뒤에 붙어 정식 이름이 된다. 짧은 이름이 안 될 때 이것부터 의심한다.

그런데 위에서 왜 짧은 이름 대신 정식 이름으로 조회했는가. busybox 계열(alpine 포함)의 nslookup은 검색 도메인을 전부 순회하며 실패한 조회를 그대로 찍기 때문이다. 짧은 이름으로 치면 이런 화면이 나온다.

kubectl exec curlbox -- nslookup journal-api
실행 결과 (빈 줄은 줄였다)
Server: 10.96.0.10 Address: 10.96.0.10:53 ** server can't find journal-api.cluster.local: NXDOMAIN ** server can't find journal-api.svc.cluster.local: NXDOMAIN ** server can't find journal-api.cluster.local: NXDOMAIN ** server can't find journal-api.svc.cluster.local: NXDOMAIN Name: journal-api.default.svc.cluster.local Address: 10.96.48.160 command terminated with exit code 1

답은 나왔는데(Name:/Address: 두 줄) NXDOMAIN 네 줄이 섞여 있고 종료 코드가 1이다. 실패한 검색 도메인 두 개(svc.cluster.local, cluster.local)에 대해 A와 AAAA 레코드를 각각 물어본 결과가 찍힌 것이며, 에러가 아니다. 이 화면을 보고 "DNS가 깨졌다"고 판단하는 실수가 흔하다. 진단할 때는 정식 이름으로 조회하거나, 애플리케이션이 쓰는 방식 그대로 curl로 확인한다.

11.6따라하기 ③ NodePort

5단계. 노드 포트로 접근한다

목적클러스터 밖에서 들어오는 가장 원시적인 방법을 확인하고, 왜 실무에서 이것만 쓰지 않는지 이해한다.

docker exec study-worker curl -s -m 3 http://localhost:30080/healthz
docker exec study-control-plane curl -s -m 3 http://localhost:30080/healthz
실행 결과
{"status":"ok","version":"v1","pod":"journal-api-55c87ff598-4fb2b"} {"status":"ok","version":"v1","pod":"journal-api-55c87ff598-52xh5"}
판정모든 노드에서 30080이 열려 있다. 파드가 그 노드에 없어도 된다 — 받은 노드가 알아서 다른 노드의 파드로 넘긴다.

맥에서 직접 curl localhost:30080이 안 되는 이유는 M01의 kind 설정(labs/infra/kind-cluster.yaml)이 호스트 18080→노드 80, 호스트 18443→노드 443 두 개만 넘겼기 때문이다(M12 인그레스용). 노드 포트 30080을 호스트에서 직접 열려면 extraPortMappings에 containerPort: 30080을 추가해 클러스터를 다시 만들어야 한다 — 그래서 여기서는 노드 컨테이너 안에서 docker exec로 확인했다.

NodePort의 한계

  • 포트 범위가 30000~32767로 제한된다. 서비스마다 번호를 배정하고 사람이 기억해야 한다
  • 노드 IP를 클라이언트가 알아야 한다. 노드가 교체되면 주소가 바뀐다
  • TLS 종료, 경로 기반 라우팅, 가상 호스트 같은 L7 기능이 없다

그래서 실무의 외부 노출은 대부분 인그레스나 Gateway API가 담당하고(M12), NodePort는 그 인그레스 컨트롤러 자신을 노출하는 데 쓰이는 정도다.

11.7일부러 실패시키기

실패 ① — 셀렉터 오타 (이 과정에서 가장 중요한 실패)

M09에서 예고한 상황이다. app: journal-api를 app: journal-app으로 잘못 쓴 서비스를 만든다.

cat <<'EOF' | kubectl apply -f -
apiVersion: v1
kind: Service
metadata:
  name: journal-api-typo
spec:
  selector:
    app: journal-app
  ports:
    - port: 8080
EOF

kubectl get svc journal-api-typo
kubectl get endpointslices -l kubernetes.io/service-name=journal-api-typo
실행 결과
service/journal-api-typo created NAME TYPE CLUSTER-IP EXTERNAL-IP PORT(S) AGE journal-api-typo ClusterIP 10.96.167.241 <none> 8080/TCP 1s NAME ADDRESSTYPE PORTS ENDPOINTS AGE journal-api-typo-q85s6 IPv4 <unset> <unset> 1s

서비스는 정상적으로 만들어졌고 ClusterIP까지 받았다. 경고도 이벤트도 없다. 하지만 ENDPOINTS가 <unset> — 대상이 하나도 없다.

kubectl exec curlbox -- sh -c 'curl -s -m 3 http://journal-api-typo:8080/healthz; echo "exit=$?"'
실행 결과
exit=7

curl 종료 코드 7은 Failed to connect다. DNS는 정상적으로 풀렸고(서비스가 존재하니까), 연결만 안 된다. 호출하는 쪽 개발자가 보는 것은 이것뿐이다 — 상대 서비스가 죽었는지, 네트워크가 막혔는지, 셀렉터가 틀렸는지 구분할 단서가 없다.

진단 순서이 증상을 만나면 순서대로 확인한다. ① kubectl get endpointslices -l kubernetes.io/service-name=<서비스> — 비어 있으면 셀렉터 문제. ② 비어 있지 않은데 안 되면 파드의 레디니스 상태. ③ 그것도 정상이면 네트워크 정책(M25)이나 포트 불일치.
kubectl describe svc journal-api-typo | grep -E "Selector|Endpoints"
kubectl get pods -l app=journal-app        # 이 셀렉터에 맞는 파드가 있나?
실행 결과
Selector: app=journal-app Endpoints: No resources found in default namespace.

서비스의 셀렉터와 실제 파드 레이블을 나란히 놓고 비교하는 것이 확실한 방법이다.

kubectl delete svc journal-api-typo
실행 결과
service "journal-api-typo" deleted from default namespace
실패 ② — 포트를 잘못 맞춘다

셀렉터는 맞지만 targetPort를 앱이 듣지 않는 8000으로 적은 서비스를 만든다.

cat <<'EOF' | kubectl apply -f -
apiVersion: v1
kind: Service
metadata:
  name: journal-api-badport
spec:
  selector:
    app: journal-api
  ports:
    - port: 8080
      targetPort: 8000
EOF
sleep 6
kubectl get endpointslices -l kubernetes.io/service-name=journal-api-badport
kubectl exec curlbox -- sh -c 'curl -s -m 3 http://journal-api-badport:8080/healthz; echo "exit=$?"'
실행 결과
service/journal-api-badport created NAME ADDRESSTYPE PORTS ENDPOINTS AGE journal-api-badport-ntpp9 IPv4 8000 10.244.1.56,10.244.1.57,10.244.2.61 + 1 more... 6s exit=7

실패 ①과 같은 exit=7(연결 거부)인데, 엔드포인트슬라이스는 파드 IP 네 개로 차 있다. 다른 점은 PORTS 열 — 8000이다. 파드에서 8000을 듣는 프로세스가 없으니 커널이 연결을 거절한다. 그래서 진단 순서의 ①(엔드포인트가 비었나)과 ②(차 있는데 안 되나)를 구분해야 한다. ②에서는 describe로 포트를 본다. sleep을 넣은 이유 — 서비스를 만든 직후 바로 치면 규칙이 아직 없어 exit=28(타임아웃)이 나올 수 있다(이 검증에서 실제로 그랬다).

kubectl describe svc journal-api-badport | grep -E "^Selector|^TargetPort|^Endpoints"
kubectl delete svc journal-api-badport
실행 결과
Selector: app=journal-api TargetPort: 8000/TCP Endpoints: 10.244.1.56:8000,10.244.1.57:8000,10.244.2.61:8000 + 1 more... service "journal-api-badport" deleted from default namespace
판정Endpoints에 IP는 있고 포트가 :8000이다. 파드의 containerPort(8080)와 다르면 이 실패다. 증상은 셀렉터 오타와 같은 connection refused지만 엔드포인트슬라이스가 차 있다는 점이 다르다.

이 실수를 줄이는 방법은 targetPort에 숫자 대신 이름을 쓰는 것이다.

# 파드 쪽
          ports:
            - name: http
              containerPort: 8080
# 서비스 쪽
    - port: 80
      targetPort: http     # 숫자가 아니라 이름으로 참조

파드의 포트가 바뀌어도 서비스를 고칠 필요가 없어진다.

실패 ③ — 로컬에서 LoadBalancer 타입을 쓴다 
kubectl expose deploy journal-api --type=LoadBalancer --port=8080 --name=journal-lb
kubectl get svc journal-lb
sleep 20
kubectl get svc journal-lb
실행 결과
service/journal-lb exposed NAME TYPE CLUSTER-IP EXTERNAL-IP PORT(S) AGE journal-lb LoadBalancer 10.96.173.76 <pending> 8080:32241/TCP 0s NAME TYPE CLUSTER-IP EXTERNAL-IP PORT(S) AGE journal-lb LoadBalancer 10.96.173.76 <pending> 8080:32241/TCP 20s
판정20초 뒤에도 EXTERNAL-IP가 <pending>. 클라우드에서는 이 자리에 1~2분 안에 외부 IP가 채워진다. PORT(S)의 32241은 LoadBalancer 타입이 내부적으로 NodePort도 함께 연다는 것을 보여준다 — 클라우드 로드밸런서가 그 노드 포트로 트래픽을 넘기는 구조다. 번호는 환경마다 다르다.

EXTERNAL-IP가 <pending>에서 영원히 멈춘다. 이 타입은 클라우드 사업자의 컨트롤러가 실제 로드밸런서를 만들어 IP를 채워주는 구조인데, kind에는 그런 컨트롤러가 없기 때문이다.

로컬에서 흉내내려면 MetalLB나 cloud-provider-kind 같은 도구를 따로 설치해야 한다. 이 과정은 그러지 않고 인그레스(M12)로 외부 접근을 만든다 — 실무에서도 서비스마다 로드밸런서를 하나씩 만드는 것보다 인그레스 하나 뒤에 여러 서비스를 두는 편이 비용과 관리 면에서 낫다.

kubectl delete svc journal-lb
실행 결과
service "journal-lb" deleted from default namespace

11.8체크포인트와 정리

다음 모듈로 넘어가기 전 확인
  • kubectl get svc journal-api journal-api-headless journal-api-nodeport → 3행. journal-api-headless의 CLUSTER-IP가 None, journal-api-nodeport의 PORT(S)가 8080:30080/TCP
  • kubectl get endpointslices -l kubernetes.io/service-name=journal-api -o jsonpath='{.items[0].endpoints[*].conditions.ready}' → true true true true
  • kubectl exec curlbox -- sh -c 'for i in $(seq 1 12); do curl -s -m 2 http://journal-api:8080/healthz; echo; done' | sort -u | wc -l → 2 이상 (응답한 파드가 둘 이상. 12번이면 보통 4)
  • kubectl exec curlbox -- nslookup journal-api-headless.default.svc.cluster.local | grep -c Address: → 5 (DNS 서버 1 + 파드 4)
  • docker exec study-worker curl -s -o /dev/null -w '%{http_code}\n' http://localhost:30080/healthz → 200
  • kubectl get svc journal-api-typo journal-api-badport journal-lb → 세 이름 모두 Error from server (NotFound) (실패 ①②③을 정리했다)
  • (이해 확인) connection refused를 받았을 때 확인하는 순서 세 단계 — 실패 ①의 진단 순서로 답하고, 실패 ②가 어느 단계에서 갈리는지 말한다
  • (이해 확인) kind에서 LoadBalancer가 <pending>인 이유와, 실무에서 서비스마다 로드밸런서를 두지 않고 무엇을 쓰는지 (M12)
