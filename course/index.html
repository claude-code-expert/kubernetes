도커 & 쿠버네티스 — 이론과 따라하기

컨테이너를 한 번도 실행해본 적 없는 사람이 38개 모듈을 순서대로 따라 하면, 노트북 한 대 위에 관측·보안·GitOps·카오스 검증까지 갖춘 클러스터를 스스로 세운다. 클라우드 계정 없이 전 과정을 완주한다.

Kubernetes 1.37kind v0.33.0Docker Engine 29.xHelm 4.x
버전 확인일 2026-09-03 · 이론 축 『쿠버네티스 창시자에게 배우는 모범 사례 2판』(한빛미디어, 2024)

이 과정의 규칙

1. 모든 모듈은 앞 모듈이 남긴 파일을 입력으로 받는다. 건너뛰면 다음 실습의 사전 조건이 깨진다.

2. 명령에는 실행 결과와 성공 판정 기준이 항상 붙는다. 화면이 문서와 다르면 거기서 멈추고 원인을 찾는다.

3. 모듈마다 일부러 실패시키는 단계가 하나씩 있다. 고장을 본 적 없는 사람은 고칠 수 없다.

1전체 로드맵 — 8개 파트 38개 모듈 2난이도 5단계 — 같은 것을 세 번 배운다 3고정 버전 매트릭스 4문서 읽는 법 5실습 파일 구조 6진행 방식

1전체 로드맵 — 8개 파트 38개 모듈

파트는 순서대로 쌓인다. 도커에서 이미지를 만들 줄 알아야 쿠버네티스에 배포할 것이 생기고, 배포한 것이 있어야 관측할 대상이 생기며, 관측 스택이 있어야 카오스 실험의 판정 도구가 생긴다.

Part 6. 배포 자동화 — 후반

모듈제목끝나면 할 수 있는 것

M30배포 전략과 롤아웃 판정블루/그린을 서비스 셀렉터 교체로 만들고, Argo Rollouts 카나리에 PromQL 판정을 붙인다. 40% 확률로 실패하는 버전이 성공률 0.615 로 자동 롤백되는 것을 측정값과 함께 본다.
M31GitOps클러스터 안에 깃 서버와 Argo CD 를 세우고 커밋 하나가 8초 만에 배포되는 것을 확인한다. kubectl 로 만든 변경이 5초 만에 되돌아가는 것을 측정하고, SOPS 로 시크릿을 커밋 가능한 형태로 만든다.
M32글로벌 롤아웃과 사고 대응kind 클러스터 두 개를 리전으로 등록하고 ApplicationSet 으로 리전 수만큼 배포한다. 카나리 리전에 먼저 배포해 검사 스크립트로 판정하고, 존재하지 않는 태그와 리전별 구성요소 편차를 재현해 러너북으로 정리한다.

2난이도 5단계 — 같은 것을 세 번 배운다

이 과정은 주제를 한 번 훑고 넘어가지 않는다. 같은 오브젝트를 세 번, 매번 다른 깊이로 다시 만난다. 처음에는 눈으로 보기 위해, 두 번째는 고장을 재현하기 위해, 세 번째는 사람이 손대지 않게 만들기 위해서다. 아래 단계는 파트 경계와 정확히 일치하며, 각 모듈 첫머리의 난이도 표시가 이 표를 따른다.

단계모듈회당 평균명령의 성격대표 명령
초반M01~M0755분한 줄 명령으로 만들고 눈으로 확인docker run, docker build, docker compose up
초반→중반M08~M1470분쿠버네티스 오브젝트를 만들고 YAML로 다시 쓴다kubectl create deployment, kubectl expose, kubectl apply -k, helm install
중반M15~M2290분선언형으로 고치고 실패를 재현한다kubectl apply -f, kubectl top, kubectl drain, PromQL rate(), histogram_quantile()
중후반M23~M2795분권한 · 정책 · 감사로 사람이 못 하게 막는다kubectl auth can-i, PSA 라벨, NetworkPolicy, ValidatingAdmissionPolicy, 감사 로그 질의
후반M28~M38115분사람이 apply 하지 않는다. 파이프라인 · 정책 · 실험이 대신한다kubectl argo rollouts promote, Argo CD Application, kubectl apply -f podchaos.yaml, k6 run

시간은 읽기 · 명령 실행 · 대기(롤아웃 · 분석 · 부하)를 더해 산정한 값이고 숙련도에 따라 ±30% 차이가 난다. 전체 합은 약 55시간이다. 한 모듈이 예외적으로 무겁다 — M14는 다른 모듈의 두 배(135분)라 단독 회차로 잡는다.

배포 하나를 예로 들면 이렇게 올라간다. M08에서는 kubectl create deployment web --image=nginx:1.29-alpine 한 줄로 만든다. M10에서는 같은 것을 YAML로 다시 쓰고 이미지를 바꿔 롤링 업데이트를 관찰한 뒤 rollout undo로 되돌린다. M30에서는 아무도 명령을 치지 않는다 — 커밋이 들어오면 카나리가 20%로 나가고, M20에서 만든 에러율 지표가 임계를 넘으면 자동으로 롤백된다.

4문서 읽는 법

모든 모듈은 같은 순서로 쓰여 있다. 익숙해지면 필요한 블록만 골라 읽을 수 있다.

블록무엇이 들어 있나
사전 조건앞 모듈이 남긴 어떤 파일이 있어야 하는지. 없으면 돌아갈 모듈 링크
핵심 3줄이 모듈이 끝나면 할 수 있는 것
왜 이걸 하나앞 모듈의 결과가 왜 부족한지. 이 모듈의 존재 이유
이론실습에서 마주칠 개념만. 책의 해당 절 번호가 붙는다
따라하기단계마다 목적 → 명령 → 옵션 설명 → 실행 결과 → 판정
일부러 실패시키기실제로 겪을 실수를 재현하고 에러 메시지를 읽은 뒤 고친다
체크포인트무엇이 보이면 성공인지. 판정 가능한 문장으로
정리리소스 삭제. 부하 루프를 띄웠다면 종료 방법

명령 블록에는 프롬프트 기호를 붙이지 않았다. 블록 전체를 복사해 붙여넣으면 된다. 실행 결과는 점선 테두리 블록으로 구분돼 있고, 환경마다 달라지는 값(파드 이름 접미사, IP, 시각)은 그대로 두었다 — 같을 필요가 없는 값이다.

5실습 파일 구조

문서의 코드 블록이 정본이고 labs/는 그 추출본이다. 타이핑이 목적이 아닌 파일(긴 values, 대시보드 JSON)은 여기서 복사해 쓴다.

course/labs/
  infra/        kind 클러스터 설정
  scripts/      preflight.sh · rebuild.sh · 부하 생성
  apps/         애플리케이션 소스와 Dockerfile
  k8s/          매니페스트
  charts/       헬름 차트
  monitoring/   values 파일 · 대시보드 JSON
  chaos/        카오스 실험 정의 · 게임 데이 시트

scripts/rebuild.sh는 빈 클러스터에서 M14 시점 상태까지 한 번에 복구한다. 뒤쪽 모듈에서 실습이 꼬였을 때 처음부터 다시 하지 않아도 되는 탈출구다.
