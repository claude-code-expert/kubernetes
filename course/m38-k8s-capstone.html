38.1흩어진 것을 하나로 묶는다

M01에서 kind 클러스터를 만들었고 M37에서 그 클러스터의 용량을 쟀다. 그 사이에 만든 것이 파일 수십 개, 클러스터 오브젝트 수백 개다. 각 모듈의 끝에서 확인했지만, 전체가 동시에 성립하는지는 확인한 적이 없다.

실제로 어긋난 것이 있었다. M36에서 부하 생성기를 켰을 때 M15에서 만든 스크립트가 M24·M25 때문에 동작하지 않았다. 열한 개 모듈 동안 아무도 몰랐고, 카오스 실험을 시작하려는 순간에 알았다. 이런 종류의 어긋남은 쓰려고 할 때만 드러난다.

그래서 이 모듈은 확인 자체를 산출물로 만든다. 49개 항목을 자동으로 검사하는 스크립트를 만들면, 클러스터를 새로 세울 때마다 어디가 빠졌는지 즉시 안다.

그리고 마지막으로, 지금까지 만든 관측이 사람의 손에서 실제로 쓸모가 있는지를 시험한다. 장애 세 개를 심고 90분 안에 원인을 찾게 하는 것 — 대시보드를 만든 것과 그것으로 문제를 푸는 것은 다른 일이다.

38.2이론 — 실험과 판정

책 매핑20.3.1 실험의 목표 · 20.3.2 전제 · 20.3.3 구축. A/B 테스트와 기능 플래그, 관측이 실험 판정의 도구인 이유

카오스와 실험은 목적이 다르다

M36의 카오스는 이미 만든 것이 동작하는지를 확인했다. 가설은 "잘 버틸 것이다"였고, 성립하면 아무것도 바꾸지 않는다.

이 모듈의 실험은 둘 중 무엇이 나은지를 고른다. 가설은 "B가 A보다 낫다"이고, 판정 결과가 배포 결정이 된다. 그래서 실험에는 카오스에 없는 요구가 하나 더 있다 — 공정한 비교다.

공정한 비교의 조건

같은 트래픽이 두 구현에 가야 하고, 같은 방식으로 측정돼야 하고, 다른 조건이 같아야 한다. 이 셋 중 하나만 어긋나도 결론이 뒤집힌다.

가장 흔한 오염이 시간이다. A를 오전에 재고 B를 오후에 재면 트래픽 패턴이 달라 비교가 성립하지 않는다. 동시에 돌리는 것이 이 문제를 없애고, 그것이 A/B 실험을 순차 배포가 아니라 병렬 배포로 하는 이유다.

M37에서 이 함정에 실제로 걸렸다 — limit을 제거한 뒤의 측정이 기준보다 느렸는데, 그 사이 HPA가 파드를 늘려 클러스터 상태가 달랐다. 비교하려는 것 말고 다른 것이 바뀌지 않았는지를 항상 확인한다.

판정 기준을 먼저 정한다

M30의 카나리와 같다. 어떤 지표를 어느 값으로 판정할지를 실험 전에 쓴다. 나중에 정하면 보고 싶은 결론에 맞는 지표를 고르게 된다.

지표는 최소 셋을 본다. 에러율(정확성), 지연(성능), 처리량(용량). 하나만 좋아지고 둘이 나빠지는 경우가 흔하고, 무엇을 얼마나 맞바꿀지가 실제 결정이다.

기능 플래그의 자리

이 모듈은 배포 단위로 두 구현을 나눴다 — 디플로이먼트 둘, 서비스 하나. 코드 안의 플래그로 나누는 방법도 있고 각각 장단이 있다.

배포로 나누면 이미지가 달라서 완전히 다른 구현을 비교할 수 있고, 되돌리는 것이 파드를 지우는 일이다. 코드 안 플래그는 사용자 단위로 나눌 수 있고(같은 사용자는 항상 같은 변형을 본다) 배포 없이 켜고 끌 수 있다. 대신 죽은 코드가 쌓인다 — 실험이 끝난 뒤 플래그를 걷어 내는 일을 아무도 하지 않는 것이 이 방식의 고질병이다.

38.3따라하기 ① 두 구현을 나란히

1단계 — 서비스 하나, 디플로이먼트 둘

목적같은 트래픽이 두 구현에 나뉘어 가게 만든다.

apiVersion: v1
kind: Service
metadata:
  name: journal-ab
  namespace: m38
  labels: {app: journal-api-ab}
spec:
  selector: {app: journal-api-ab}      # variant 는 고르지 않는다 — 둘 다 받는다
  ports: [{name: http, port: 8080, targetPort: http}]
# variant-a: journal-api:v1
# variant-b: journal-api:v3 + FAULT_RATE=0.05   (새 구현이 5% 실패한다고 가정)
  template:
    metadata:
      labels: {app: journal-api-ab, variant: a}    # <- 서비스가 고르는 라벨 + 구분용 라벨

서비스의 selector에 variant가 없는 것이 핵심이다. 두 디플로이먼트가 같은 서비스 뒤에 서고, 파드 수가 같으므로 트래픽이 반반 간다 — M30의 카나리와 같은 방식이고, 여기서는 비율을 옮기는 것이 아니라 고정해서 비교하는 것이 목적이다.

2단계 — 측정 경로를 만든다

목적두 변형의 지표가 구분되어 프로메테우스에 들어가게 한다.

apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: journal-ab
  namespace: m38
  labels: {release: kps}          # M20 의 3단 라벨 사슬
spec:
  selector:
    matchLabels: {app: journal-api-ab}
  endpoints:
    - {port: http, path: /metrics, interval: 10s}

지표에는 variant 라벨이 없다 — 앱이 그것을 모르기 때문이다. 대신 pod 라벨이 들어오고, 파드 이름이 variant-a-...·variant-b-...이므로 질의에서 갈라낼 수 있다. 38.4에서 그 방법을 쓴다.

앱을 고쳐 variant 라벨을 직접 붙이는 것이 더 깔끔하지만, 실험 때문에 앱을 고치는 것은 그 자체로 변수를 하나 더 만든다. 파드 이름으로 가르는 편이 실험의 순도를 지킨다.

3단계 — 같은 트래픽을 보낸다

목적비교가 성립하려면 같은 부하여야 한다.

# k8s/experiment/20-load.yaml — 서비스 이름으로 부른다. 어느 변형에 갈지는 서비스가 정한다
command: ["sh","-c","while true; do curl -s -o /dev/null -m 3 http://journal-ab:8080/api/entries; sleep 0.03; done"]
kubectl apply -f course/labs/k8s/experiment/10-ab.yaml
kubectl apply -f course/labs/k8s/experiment/20-load.yaml
kubectl -n m38 get po --no-headers
출력
variant-a-64f79d4bf-kk86j 1/1 Running 0 30s variant-a-64f79d4bf-s2w4q 1/1 Running 0 30s variant-b-56bf997756-m4bj6 1/1 Running 0 30s variant-b-56bf997756-trp9k 1/1 Running 0 30s
판정네 파드가 한 서비스 뒤에 있다. 부하 생성기는 어느 변형에 보내는지 모른다 — 그것이 공정한 비교의 조건이다.

38.4따라하기 ② 메트릭으로 판정한다

1단계 — 먼저 틀린 질의를 쓴다

목적가장 자연스러운 질의가 절반만 답하는 것을 확인한다.

100 * (
  sum by (pod) (rate(http_server_requests_seconds_count{namespace="m38",status=~"5.."}[2m]))
  /
  sum by (pod) (rate(http_server_requests_seconds_count{namespace="m38"}[2m]))
)
출력
variant-b-56bf997756-m4bj6 4.98 % variant-b-56bf997756-trp9k 4.16 %
판정변형 A가 없다. A에는 5xx가 없어서 분자의 시계열이 존재하지 않고, 없는 것과 나누면 결과도 없다. 이 화면만 보면 "A는 측정이 안 됐나"로 읽히는데, 실제로는 A가 완벽했다는 뜻이다. M21에서 본 그 함정이다.

실험 판정에서 이 오류는 특히 위험하다. 가장 좋은 변형이 결과에서 사라진다. 그리고 대시보드에 그려 놓으면 선이 하나만 보여서 눈치채기 더 어렵다.

2단계 — 변형으로 묶고 빈 결과를 0으로

목적파드 이름에서 variant를 뽑아내고, 없는 값을 0으로 만든다.

(
  sum by (variant) (label_replace(
    rate(http_server_requests_seconds_count{namespace="m38",status=~"5.."}[2m]),
    "variant", "$1", "pod", "variant-([ab])-.*"))
  or
  sum by (variant) (label_replace(
    rate(http_server_requests_seconds_count{namespace="m38"}[2m]),
    "variant", "$1", "pod", "variant-([ab])-.*")) * 0
)
/
sum by (variant) (label_replace(
  rate(http_server_requests_seconds_count{namespace="m38"}[2m]),
  "variant", "$1", "pod", "variant-([ab])-.*")) * 100

label_replace가 파드 이름의 일부를 새 라벨로 만든다. 정규식의 괄호가 $1이 되고, 그것이 variant 라벨이 된다. or ... * 0은 M21에서 쓴 기법이다 — 분자가 없을 때 전체 시계열 집합에 0을 채운다.

출력
에러율 변형 a : 0.0 % 변형 b : 4.55 % 처리량 변형 a : 27.0 req/s 변형 b : 29.0 req/s P95 변형 a : 0.49 ms 변형 b : 0.48 ms
판정세 지표가 다 나왔다. 지연과 처리량은 사실상 같고 에러율만 다르다. B가 조금 더 많은 요청을 받은 것(29 vs 27)은 A보다 빨리 실패해서 그만큼 더 받았기 때문이다 — 실패가 처리량을 올리는 착시이고, 처리량만 보면 B가 나아 보인다.

3단계 — 판정하고 정리한다

목적실험은 결정으로 끝난다. 결정하지 않으면 두 구현이 영원히 남는다.

지표변형 A변형 B판정
에러율0.0%4.55%A 우세
P95 지연0.49ms0.48ms차이 없음
처리량27 req/s29 req/s차이 없음 (실패로 인한 착시)
판정B를 기각한다. 지연 개선을 기대했다면 그것도 없었고, 에러율만 나빠졌다. 결정이 명확할 때는 실험을 오래 끌 이유가 없다 — 바로 끝내고 자원을 회수한다.

결과가 애매할 때가 더 어렵다. 지연이 5% 좋아지고 에러율이 0.1% 나빠졌다면? 그때 필요한 것이 실험 전에 정해 둔 기준이다 — "에러율이 나빠지면 지연 개선과 무관하게 기각한다"처럼. 결과를 보고 기준을 정하면 원하는 결론이 나온다.

38.5따라하기 ③ 통주 점검

1단계 — 무엇을 검사할지 정한다

목적각 모듈이 남긴 것 중 없으면 다음이 깨지는 것만 고른다.

두 종류를 섞는다. 파일이 있는가(저장소 쪽)와 클러스터에 있는가(런타임 쪽). 파일만 검사하면 "매니페스트는 있는데 적용되지 않은" 상태를 놓치고, 클러스터만 검사하면 재현할 근거가 없는 상태를 놓친다.

# scripts/capstone-check.sh 의 뼈대
check() {          # 값이 정확히 일치하는가
  local desc="$1" want="$2"; shift 2
  local got; got=$("$@" 2>/dev/null | tr -d '\n')
  if [ "$got" = "$want" ]; then ok "$desc"; else no "$desc" "기대 '$want' 실제 '$got'"; fi
}
check_gt0()  { ... }   # 0 보다 큰가
check_file() { ... }   # 파일이 있는가

검사 항목 중 몇 개는 의도된 결정을 지킨다. M16 cpu limit 없음이 그것이다 — 누군가 "안전을 위해" 걸었다면 이 점검이 잡는다. 없어야 할 것을 검사하는 항목이 있는 것이 좋은 점검 목록의 특징이다.

2단계 — 돌린다

목적전체가 동시에 성립하는지 한 번에 본다.

bash course/labs/scripts/capstone-check.sh
bash course/labs/scripts/capstone-check.sh part5   # 한 파트만
출력 (일부)
Part 3 — 안정성 (M15~M18) ✓ M15 프로브 3종 ✓ M15 preStop ✓ M16 cpu limit 없음 (의도된 결정) ✓ M16 토폴로지 분산 ✓ M17 HPA (1) ✓ M16 PDB (1) ✓ M18 레디스 볼륨 Part 5 — 보안 (M23~M27) ✓ M24 PSA restricted ✓ M24 비루트 실행 ✓ M25 네트워크 정책 (8) ✓ M26 어드미션 정책 (2) ✓ M26 정책 감사 스크립트 ✓ M27 감사 로깅 ✓ M27 CIS 진단 잡 결과 통과 49 · 실패 0 전부 통과 — 통주 완료
판정49개가 전부 통과한다. 이 스크립트가 있으면 클러스터를 새로 세울 때마다 어디까지 왔는지를 한 줄로 안다. 종료 코드로 판정하므로 CI에도 넣을 수 있다.

처음 돌렸을 때 1건이 실패했다. 원인은 클러스터가 아니라 점검 스크립트 자체였다 — resources.limits를 문자열로 비교했는데 kubectl의 출력 형식이 예상과 달랐다({"memory":"192Mi"} vs map[memory:192Mi]). 점검 도구도 검증 대상이다.

38.6따라하기 ④ 장애 세 개

캡스톤의 본체다. 강사가 셋을 심고 수강생이 90분 안에 원인을 찾는다. 셋은 각각 다른 층의 진단 능력을 시험하도록 골랐다.

1단계 — 주입 도구를 만든다

목적심고 걷는 것이 한 명령이어야 한다. 손으로 심으면 걷는 것을 잊는다.

bash course/labs/scripts/incident.sh inject 1     # 심는다
bash course/labs/scripts/incident.sh clear  all   # 전부 걷는다

수강생에게는 번호도 개수도 알려 주지 않는다. "무언가 이상하다"에서 시작하는 것이 실제 상황과 같고, 몇 개인지 아는 것만으로도 난이도가 크게 달라진다.

2단계 — 장애 1: 관측이 사라진다

목적M20의 라벨 사슬을 시험한다. 서비스는 멀쩡한데 보이지 않는 상황이다.

kubectl -n journal patch servicemonitor journal-api --type=merge \
  -p '{"metadata":{"labels":{"release":"kps-typo"}}}'
증상 (실측)
프로메테우스 journal-api 타깃 수: 0 인그레스 /api/entries: 200 파드: 전부 Running · 이벤트 없음 AppTargetDown 알림: 울리지 않는다
판정알림이 울리지 않는 것이 이 장애의 핵심이다. AppTargetDown은 up == 0을 보는데, 타깃이 down이 아니라 아예 없어서 그 시계열 자체가 존재하지 않는다. 없는 것과 0인 것의 차이가 여기서 다시 나온다.

찾아가는 길은 정해져 있다. 프로메테우스의 Targets에서 목록에 없다는 것을 먼저 확인하고(down이면 다른 문제다), serviceMonitorSelector와 ServiceMonitor의 라벨을 대조한다.

3단계 — 장애 2: 이름 해석이 죽는다

목적M25의 이그레스 정책을 시험한다. 증상이 늦게 나타나는 유형이다.

kubectl -n journal delete netpol allow-dns
증상 (실측)
파드 안에서: nslookup redis-0.redis -> ;; connection timed out 인그레스 /api/entries: 200 <- 지금 도는 요청은 멀쩡하다 web-static 재시작 -> 정상 기동 <- 이 파드는 DNS 없이도 뜬다
판정서비스가 정상으로 보이는데 파드 안에서는 이름이 안 풀린다. 이 장애는 다음 재시작 때 터진다 — 저널 API가 재시작하면 레디스에 못 붙어 /readyz가 503이 된다. M25에서 재현한 그 사고이고, 배포한 날이 아니라 며칠 뒤 새벽에 터지는 형태다.

구분 포인트가 하나 있다. timed out은 DNS 서버에 닿지 못한 것이고 NXDOMAIN은 서버가 "없다"고 답한 것이다. 뒤의 것은 정상 동작일 수 있다(검색 도메인을 순서대로 시도하는 중). 이 둘을 헷갈리면 엉뚱한 곳을 판다.

4단계 — 장애 3: 한가한데 느리다

목적M37의 병목 진단을 시험한다. 모든 지표가 정상을 가리키는 상황이다.

kubectl -n journal patch deploy journal-api --type=json \
  -p '[{"op":"add","path":"/spec/template/spec/containers/0/resources/limits/cpu","value":"50m"}]'
증상 (실측, 150 rps 부하 중)
lat_list: avg=3.42s p(90)=22.7s p(95)=31.13s max=45.08s http_req_failed: 80.29% (4,922 / 6,130) kubectl top pods: 50m / 48m <- limit 에 정확히 붙어 있다 파드: 전부 Running · 재시작 0 · 이벤트 없음
판정서비스의 80%가 실패하는데 파드는 건강하고 이벤트도 없다. top이 보여 주는 50m이 유일한 단서인데, 그것이 limit과 같은 값이라는 것을 알아채야 한다. 그다음이 스로틀링 질의다.

세 장애가 서로 다른 도구를 요구하는 것이 이 설계의 의도다. 1번은 프로메테우스의 타깃 화면, 2번은 kubectl exec로 파드 안에서의 관찰, 3번은 cAdvisor 지표. 대시보드 하나만 보고 세 개를 다 풀 수는 없다.

5단계 — 시트와 채점

목적답이 아니라 경로를 남기게 한다.

chaos/incidents/WORKSHEET.md가 수강생용이다. 각 장애마다 관찰한 증상 · 정상과 다른 첫 지점 · 확인한 명령과 출력 · 원인 · 조치 · 재발 방지를 적는다.

시작 전 5분 동안 정상 상태를 먼저 적게 하는 칸이 있다. 이것이 없으면 "무엇이 비정상인지"를 말할 수 없고, M36의 게임 데이에서 배운 원칙 그대로다.

채점 항목배점
세 장애의 증상을 정확히 기술30
각 장애의 원인을 지목30
원인을 어떤 관찰로 좁혔는지 설명30
재발 방지책 제안10
판정세 번째 항목이 이 채점의 요점이다. 원인만 맞히고 경로를 설명하지 못하면 절반만 준다 — 운영에서 필요한 것은 답이 아니라 답에 이르는 절차이고, 다음에 만날 장애는 이 셋이 아니다.

38.7일부러 실패시키기

실패 ① — 가장 좋은 변형이 결과에서 사라진다

목적38.4의 첫 질의를 실험을 망치는 형태로 다시 본다.

실험 대시보드에 에러율 패널을 만들고 두 변형을 비교한다고 하자. 질의는 자연스럽게 이렇게 쓴다.

sum by (pod) (rate(...{status=~"5.."}[2m])) / sum by (pod) (rate(...[2m]))
패널에 보이는 것
variant-b-...-m4bj6 4.98 % variant-b-...-trp9k 4.16 %
판정선이 둘만 그려진다. B의 두 파드다. 그런데 화면에는 "A가 없다"는 표시가 없으므로, 이 패널만 보면 B가 전부인 것처럼 보인다. 심하면 "A는 트래픽을 안 받나?"로 판단해 서비스 셀렉터를 뒤지게 된다.

이 오류가 실험에서 특히 나쁜 이유가 있다. 완벽한 변형이 사라지는 방향으로 틀린다 — 에러가 없을수록 결과에서 빠진다. 반대로 틀렸다면(에러가 있는 쪽이 사라졌다면) 금방 알아챘을 것이다.

고치는 방법은 M21에서 쓴 것과 같다. 분모 쪽 시계열 집합에 * 0을 or로 더해 없는 값을 0으로 만든다. 습관으로 만들 규칙은 하나다 — 비율을 그릴 때는 항상 분자가 없을 경우를 처리한다.

실패 ② — 점검 스크립트가 틀렸다

목적38.5에서 실제로 난 실패를 도구 신뢰의 문제로 정리한다.

첫 실행 결과
✗ M16 cpu limit 없음 (의도된 결정) (기대 'map[memory:192Mi]' 실제 '{"memory":"192Mi"}') 결과 통과 48 · 실패 1
판정클러스터는 정상이었고 기대값을 잘못 쓴 것이었다. jsonpath가 맵을 출력하는 형식이 Go의 기본 표현(map[...])이 아니라 JSON({...})이었다. 이 실패가 친절한 형태였던 것이 다행이다 — 기대값과 실제값을 함께 찍었기 때문에 30초 만에 알았다.

더 나쁜 경우를 생각해 본다. 검사가 통과하는 쪽으로 틀렸다면 아무도 몰랐을 것이다. M32에서 겪은 것이 그것이다 — "준비된 파드 수"만 보는 검사가 실패한 배포에 통과를 줬다.

그래서 점검 스크립트에는 스스로를 시험하는 절차가 필요하다. 일부러 깨뜨려 보고 검사가 실패하는지 확인한다 — 38.6의 장애 주입 스크립트가 그 역할을 겸한다. incident.sh inject 3을 넣고 capstone-check.sh part3을 돌리면 M16 cpu limit 없음 항목이 실패해야 한다.

고쳐 쓴 검사는 값의 형식에 기대지 않는다.

check "M16 cpu limit 없음 (의도된 결정)" "0" \
  bash -c "kubectl -n journal get deploy journal-api \
    -o jsonpath='{...resources.limits.cpu}' | wc -c | tr -d ' '"

있는지 없는지만 보면 출력 형식이 바뀌어도 깨지지 않는다. 점검 항목을 쓸 때 가장 단순한 판정 기준을 고르는 것이 오래 가는 방법이다.

38.8운영 관점 — 여기서부터 어디로

이 교재가 만든 것

서른여덟 개 모듈의 산출물을 한 문장으로 줄이면 이렇다. 단일 노드 도커에서 시작해, 3노드 클러스터에서 관측·보안·배포 자동화·검증을 갖춘 애플리케이션 한 벌이다. 그 과정에서 실제로 겪은 실패가 60개 남짓이고, 그것들이 이 교재의 본체다.

산출물의 구조도 정리해 둔다. infra/(클러스터), apps/(앱 소스), k8s/(매니페스트), charts/(헬름), monitoring/(관측 값), chaos/(실험), operator/(CRD), scripts/(도구 12종). 역할로 나눈 것이 모듈로 나누지 않은 이유는 실제 저장소가 그렇게 생겼기 때문이다.

이 교재가 다루지 않은 것

정직하게 적어 둔다. 실제 클라우드(관리형 클러스터, 로드밸런서, IAM 연동), 스토리지의 실제(복제, 백업, 재해 복구), 대규모(수백 노드에서 달라지는 것들), 비용(자원 사용을 돈으로 환산하고 줄이는 일), 조직(여러 팀이 한 클러스터를 나눠 쓰는 운영).

마지막이 특히 크다. 이 교재의 클러스터는 한 사람이 전부를 관리했다. 실제로는 플랫폼 팀과 애플리케이션 팀이 나뉘고, M23의 RBAC과 M26의 정책이 그 경계에서 진짜 의미를 갖는다.

다음에 할 것 셋

① 자기 애플리케이션으로 다시 한다. 이 교재의 저널 앱은 일부러 단순하게 만들었다. 실제 앱은 의존이 많고, 상태가 크고, 기동이 느리다 — 그때 M15의 프로브 값과 M16의 리소스 값이 전혀 다른 숫자가 된다.

② 관리형 클러스터에서 같은 것을 한다. kind와 다른 점이 어디인지가 그 자체로 학습이다. 로드밸런서, 스토리지 클래스, 노드 자동 확장, 그리고 M27에서 우리가 고친 컨트롤 플레인을 건드릴 수 없다는 제약.

③ 운영 중인 클러스터에 점검 목록을 적용한다. M27 8절의 표와 M38의 capstone-check.sh를 자기 클러스터에 맞게 고쳐 돌리면, 지금 무엇이 빠져 있는지가 목록으로 나온다. 그것이 다음에 할 일의 우선순위다.

이 교재를 강의로 쓸 때

각 모듈은 앞 모듈의 산출물을 입력으로 받는다. 건너뛰면 사전 조건이 깨지므로, 모듈 첫머리의 사전 조건 블록을 반드시 확인시킨다. 시간이 부족하면 모듈을 빼는 대신 따라하기의 일부를 시연으로 돌린다 — 일부러 실패시키기 블록은 빼지 않는다. 그것이 이 교재에서 가장 오래 기억되는 부분이다.

캡스톤은 클러스터를 새로 만들어 시작하는 것이 이상적이다. rebuild.sh가 M14 시점까지 복구하므로 그 뒤는 각 모듈의 매니페스트를 순서대로 적용한다. 시간이 없으면 기존 클러스터에 장애만 심어도 되지만, 통주 점검을 먼저 돌려 출발선이 같은지 확인한다.

과정을 마치며

M01에서 컨테이너 하나를 띄웠고, 여기서 클러스터 전체를 검증했다. 그 사이에 실패를 60번 넘게 재현했다 — 프로브 임계값 때문에 파드가 계속 죽고, 라벨 하나가 틀려 타깃이 안 잡히고, 하이픈 하나가 네임스페이스를 열고, 셸 변수 이름이 시스템 것과 겹치고, cpu limit 하나가 P99를 4000배로 만들었다.

그 실패들이 이 교재의 실제 내용이다. 성공하는 절차는 문서에 적혀 있지만, 무엇이 어떻게 틀어지는지는 겪어야 안다. 다음에 만날 장애는 여기 있는 것이 아니겠지만, 증상에서 원인으로 좁혀 가는 절차는 같다.
