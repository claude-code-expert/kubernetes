로드 테스팅

M36의 부하 생성기는 측정 도구지 부하 도구가 아니었다. 초당 170건을 보내며 응답 코드를 세는 것이 전부다. 이 모듈에서 k6로 램프업·정상·스파이크·회복의 네 구간을 만들고, cpu limit 하나로 P99를 3.54ms에서 14.74초로 만든 뒤 그 원인을 PromQL로 찾는다. 그리고 kubectl top이 한가하다고 말하는데 실제로는 96% 스로틀링인 상태를 확인한다.

37.1얼마나 견디는지 모른다

M17에서 HPA를 만들 때 최대 8개로 정했다. M16에서 requests를 50m으로 잡았다. 두 숫자 모두 근거가 약했다 — 실습에서 관찰한 값에 여유를 얹은 것이고, "이 클러스터가 초당 몇 건을 견디는가"를 물으면 답할 수 없다.

이 질문에 답하지 못하면 세 가지를 못 한다. 용량을 계획할 수 없고(다음 달 트래픽이 두 배가 되면 무엇이 먼저 무너지는가), 튜닝의 효과를 알 수 없고(리소스를 올렸는데 나아졌는가), SLO를 약속할 수 없다(P99 200ms를 지킨다는 말의 근거가 없다).

부하 시험이 그 답을 만든다. 다만 제대로 만들지 않으면 틀린 답을 확신하게 된다 — 한 엔드포인트만 반복해서 때리면 캐시가 다 맞아 실제보다 좋은 수치가 나오고, 에러율만 보면 보내지도 못한 요청을 성공으로 센다. 이 모듈은 그 함정들을 하나씩 겪는다.

그리고 M16에서 미뤄 둔 숙제를 여기서 한다. cpu limit을 걸지 않기로 한 결정이 옳았는지를 숫자로 확인한다.

37.2이론 — 실제와 가까운 부하

책 매핑20.2.1 목표 · 20.2.2 전제 조건 · 20.2.3 실제와 가까운 트래픽 생성 · 20.2.4~20.2.5 튜닝

부하율을 고정한다

k6에는 두 방식이 있다. VU 기반(가상 사용자 N명이 쉬지 않고 요청)과 도착률 기반(초당 N건을 보낸다). 용량 측정에는 도착률 기반을 쓴다.

이유가 분명하다. VU 방식은 앱이 빨라질수록 부하가 커진다 — 응답이 두 배 빨라지면 요청도 두 배가 된다. 그러면 "파드를 늘렸더니 부하도 늘어" 개선을 측정할 수 없다. 도착률을 고정해야 "같은 부하에 자원이 얼마나 필요한가"를 잰다.

도착률 방식의 대가가 dropped_iterations다. 목표 속도로 발사하지 못하면 그 요청은 버려지고, 응답이 없으므로 에러율에도 잡히지 않는다. 37.7에서 이것 때문에 결과를 잘못 읽는 상황을 만든다.

한 엔드포인트만 때리면 안 된다

책 20.2.3의 요점이다. 읽기만 반복하면 캐시가 전부 맞고, 쓰기만 반복하면 실제와 다른 잠금 경합이 생긴다. 실제 트래픽의 비율을 흉내 내야 병목이 실제와 같은 자리에 나타난다.

비율은 접근 로그에서 가져온다(M22의 파이프라인이 그 데이터를 갖고 있다). 이 모듈에서는 읽기 70%·쓰기 15%·정적 15%를 가정했는데, 자기 서비스의 실제 비율로 바꿔 써야 의미가 있다.

그리고 엔드포인트별로 따로 잰다. 전체 P99만 보면 어느 경로가 느린지 모르고, 느린 경로의 비중이 작으면 전체 분위수에 묻힌다.

네 구간

시나리오를 네 구간으로 나눈다. 램프업은 계단으로 올리며 꺾이는 지점을 찾고, 정상은 같은 부하를 유지하며 안정 상태를 재고, 스파이크는 오토스케일링이 따라오지 못하는 구간을 만들고, 회복은 스파이크 뒤에 원래대로 돌아오는지 본다.

네 번째가 자주 빠지는데 중요하다. 회복되지 않으면 무언가 새고 있다 — 커넥션 풀이 고갈됐거나, 큐가 밀렸거나, 메모리가 회수되지 않은 것이다.

37.3따라하기 ① 시나리오를 쓴다

1단계 — 네 구간을 정의한다

목적한 번 실행으로 램프업부터 회복까지 본다. startTime으로 순서를 만든다.

const full = {
  rampup: {
    executor: 'ramping-arrival-rate',
    startRate: 20, timeUnit: '1s',
    preAllocatedVUs: 50, maxVUs: 400,
    stages: [
      { target: 50,     duration: '30s' },
      { target: 100,    duration: '30s' },
      { target: STEADY, duration: '30s' },
    ],
  },
  steady:  { executor: 'constant-arrival-rate', rate: STEADY, duration: '90s', startTime: '90s',  ... },
  spike:   { executor: 'constant-arrival-rate', rate: PEAK,   duration: '30s', startTime: '180s', ... },
  recover: { executor: 'constant-arrival-rate', rate: STEADY, duration: '60s', startTime: '210s', ... },
};

preAllocatedVUs와 maxVUs는 부하를 만들 쪽의 여유다. 응답이 느려지면 한 요청이 VU를 오래 붙잡으므로, 목표 속도를 유지하려면 VU가 더 필요하다. 부족하면 dropped_iterations가 생긴다 — 앱이 아니라 k6가 부족한 것일 수 있으니 이 값을 넉넉히 준다.

2단계 — 엔드포인트를 섞고 따로 잰다

목적실제 트래픽 비율을 흉내 내고, 경로별 지연을 남긴다.

const dList = new Trend('lat_list', true);
const dWrite = new Trend('lat_write', true);
const dStatic = new Trend('lat_static', true);

export default function () {
  const r = Math.random();
  if (r < 0.70) {                       // 70% 목록 읽기
    const res = http.get(`${BASE}/api/entries`, { headers: { Host: HOST } });
    dList.add(res.timings.duration);
  } else if (r < 0.85) {                // 15% 쓰기
    const res = http.post(`${BASE}/api/entries`, JSON.stringify({ text: `load ${Date.now()}` }), ...);
    dWrite.add(res.timings.duration);
  } else {                              // 15% 정적
    const res = http.get(`${BASE}/`, { headers: { Host: HOST } });
    dStatic.add(res.timings.duration);
  }
}
export const options = {
  scenarios: PROFILE === 'full' ? full : single,
  thresholds: {
    http_req_failed: ['rate<0.01'],
    'lat_list': ['p(99)<500'],
  },
};

thresholds가 이 스크립트를 테스트로 만든다. 임계값을 넘으면 k6가 종료 코드 99로 끝나므로 M29의 파이프라인에 그대로 게이트로 넣을 수 있다 — 성능 회귀를 배포 전에 잡는 자리다.

37.4따라하기 ② 병목을 만든다

M16에서 cpu limit을 일부러 걸지 않았다. "초과하면 죽는 게 아니라 조여진다"는 이유였는데, 그 조여짐이 실제로 어떤 값인지는 재지 않았다. 지금 잰다.

1단계 — cpu limit을 건다

목적흔히 하는 "안전을 위해 limit을 건다"는 선택의 결과를 본다.

kubectl -n journal patch deploy journal-api --type=json \
  -p '[{"op":"add","path":"/spec/template/spec/containers/0/resources/limits/cpu","value":"50m"}]'
kubectl -n journal rollout status deploy/journal-api

k6 run -e PROFILE=steady -e RPS=150 -e DURATION=90s course/labs/scripts/k6-capacity.js
출력
✗ 'p(99)<500' p(99)=14.74s ✗ write 2xx ↳ 99% — ✓ 1882 / ✗ 4 lat_list: avg=3.63s med=3.03s p(90)=6.62s p(95)=7.71s max=16.11s http_req_failed: 0.03% 4 out of 12800 http_reqs : 12800 121.306328/s
판정P99가 3.54ms에서 14.74초가 됐다 — 4000배다. 그리고 150 rps를 채우지 못하고 121로 떨어졌다. 실패율은 0.03%에 불과해서, 에러율만 보는 감시로는 이 상태를 잡지 못한다.

requests: 50m과 limits: 50m을 같게 만든 것이 이 실험의 설정이다. 그러면 QoS가 Guaranteed가 되는데(M16), Guaranteed가 좋은 것이라고만 알고 있으면 이 결과가 뜻밖일 수 있다. QoS는 축출 순서의 이야기이지 성능의 이야기가 아니다.

2단계 — kubectl top을 본다 (그리고 속는다)

목적가장 먼저 치는 명령이 왜 이 문제를 못 잡는지 확인한다.

kubectl top pods -n journal -l app=journal-api --no-headers
출력
journal-api-6575b5fd6c-5rd75 20m 42Mi journal-api-6575b5fd6c-9cv2k 36m 48Mi journal-api-6575b5fd6c-9shsx 32m 63Mi journal-api-6575b5fd6c-c2lb7 5m 46Mi journal-api-6575b5fd6c-jbf4r 4m 42Mi
판정전부 한가해 보인다. limit이 50m인데 20~36m만 쓰고 있으니 "CPU는 문제가 아니다"라고 읽게 된다. 그런데 P99는 14초다. top이 보여 주는 것은 실제로 쓴 시간이고, 쓰고 싶었는데 못 쓴 시간은 여기 없다.

3단계 — 스로틀링을 잰다

목적보이지 않던 것을 보이게 한다. 이 질의가 이 모듈의 핵심 도구다.

sum by (pod) (rate(container_cpu_cfs_throttled_periods_total{namespace="journal",container="api"}[2m]))
/
sum by (pod) (rate(container_cpu_cfs_periods_total{namespace="journal",container="api"}[2m]))
출력
journal-api-6575b5fd6c-c2lb7 96.2 % journal-api-6575b5fd6c-sxbvb 87.8 % journal-api-6575b5fd6c-9cv2k 92.1 % journal-api-6575b5fd6c-9shsx 91.4 % journal-api-6575b5fd6c-vfmg9 91.3 %
판정88~96%의 주기가 스로틀됐다. 리눅스의 CFS는 100ms 단위로 할당량을 주는데, 50m은 그 100ms 중 5ms만 쓸 수 있다는 뜻이다. 5ms를 다 쓰면 나머지 95ms는 실행 가능한 상태로 대기하고, 그 대기가 응답 시간에 그대로 더해진다.

왜 top과 어긋나는지 설명된다. 5ms씩 100ms마다 쓰면 평균 사용률은 50m 근처로 나오고, 그것이 top이 보여 주는 값이다. 바쁜 것과 조여진 것이 같은 숫자로 보인다.

container_cpu_cfs_throttled_periods_total은 cAdvisor가 내보내는 지표다 — M19에서 세 출처를 구분할 때 본 그 cAdvisor이고, 노드에서만 알 수 있는 정보라 앱 지표에는 절대 나타나지 않는다.

37.5따라하기 ③ 찾고 고치고 다시 잰다

1단계 — limit을 올린다

목적원인이 맞았는지 같은 측정으로 확인한다.

  -p '[{"op":"replace","path":"/spec/template/spec/containers/0/resources/limits/cpu","value":"500m"}]'
k6 run -e PROFILE=steady -e RPS=150 -e DURATION=90s course/labs/scripts/k6-capacity.js
출력
✓ 'p(99)<500' p(99)=7.71ms lat_list: avg=5.05ms p(95)=6.01ms http_req_failed: 0.00% 0 out of 13500 http_reqs : 13500 149.99904/s 스로틀링: 전 파드 0.0 %
판정스로틀링이 0%가 되고 P99가 7.71ms로 돌아왔다. 150 rps도 다시 달성한다. 원인이 맞았다.

2단계 — limit을 제거한다 (M16의 결정으로)

목적세 가지 구성을 나란히 비교한다.

판정가운데 줄만 자릿수가 다르다. 그런데 마지막 두 줄이 기준(첫 줄)보다 느리다 — 이것을 "limit을 제거해서 느려졌다"고 읽으면 틀린다. 그 사이 HPA가 파드를 8개까지 늘렸고 클러스터가 더 바빠졌다. 같은 조건에서 잰 값이 아니다.

부하 시험에서 가장 흔한 오류가 이것이다. 비교하려는 것 말고 다른 것이 바뀌지 않았는지를 항상 확인한다. 엄밀하게 하려면 각 측정 전에 클러스터를 같은 상태로 되돌려야 한다 — HPA를 고정하고, 파드 수를 맞추고, 몇 분 안정시킨다.

3단계 — 전체 프로파일을 돌린다

목적램프업부터 회복까지 한 번에 보며 구간별 차이를 잡는다.

k6 run -e STEADY=150 -e PEAK=400 course/labs/scripts/k6-capacity.js
출력
✓ 'rate<0.01' rate=0.00% ✓ 'p(99)<500' p(99)=29.34ms lat_list : avg=11.63ms p(90)=16.52ms p(95)=20.49ms lat_write : avg=2.26ms p(95)=7.79ms lat_static: avg=726.12µs p(95)=1.15ms http_req_failed: 0.00% 0 out of 41551 http_reqs : 41551 153.889275/s
판정스파이크 400 rps에서도 실패가 0이다. 다만 그 이유는 HPA가 이미 8개까지 늘어난 상태였기 때문이고, 파드가 3개인 상태에서 갑자기 400이 왔다면 결과가 달랐을 것이다. 스파이크 시험은 시작 상태를 함께 적어야 재현된다.

lat_write가 lat_list보다 다섯 배 빠른 것도 눈에 띈다. 쓰기는 레디스에 SET 한 번이고 읽기는 KEYS + MGET 두 번이다 — 읽기가 무거운 앱이라는 사실이 이 표에 그대로 나온다. 최적화한다면 KEYS를 없애는 것이 첫 번째 후보다.

37.6따라하기 ④ 한계와 측정 지점

1단계 — 무너지는 지점을 찾는다

목적용량의 상한을 숫자로 만든다.

k6 run -e PROFILE=steady -e RPS=800 -e DURATION=60s course/labs/scripts/k6-capacity.js
출력
lat_list: avg=1.9s p(90)=2.6s p(95)=2.77s max=3.51s http_req_failed : 0.00% 1 out of 23931 http_reqs : 23931 386.047245/s dropped_iterations: 24069 388.273417/s
판정에러율 0.00%인데 절반이 버려졌다. 목표 800 rps 중 386만 실제로 나갔고, 나머지 24,069건은 발사조차 되지 못했다. 요약의 http_req_failed만 보면 "800 rps에서도 문제없다"는 정반대 결론이 나온다.

dropped_iterations가 생기는 이유는 둘이다. VU가 부족하거나(maxVUs를 올려 확인한다), 대상이 느려서 VU가 다 붙잡혀 있거나. 여기서는 후자다 — P95가 2.77초이므로 VU 하나가 요청 하나에 2.8초를 쓰고, 600 VU로는 초당 214건밖에 못 보낸다.

이 클러스터의 용량은 "P95 50ms 이하를 지키며 약 300 rps" 정도로 정리된다. 그 이상은 지연이 급격히 나빠진다.

2단계 — 앱과 k6가 재는 값을 비교한다

목적M20의 히스토그램과 k6의 숫자가 왜 다른지 확인한다. 둘 다 맞다.

# k6 를 300 rps 로 돌리는 동안 프로메테우스에 질의한다
histogram_quantile(0.95, sum by (le) (rate(
  http_server_requests_seconds_bucket{namespace="journal",job="journal-api",uri="/api/entries"}[1m])))

sum(rate(http_server_requests_seconds_count{namespace="journal",job="journal-api"}[1m]))
출력
앱 P95 : 48.42 ms 앱 요청률 : 258.7 req/s k6 lat_list p95 : 70.49 ms k6 http_reqs : 27000 299.824729/s
판정두 값의 차이가 각각 이유가 있다. 지연 22ms는 인그레스 컨트롤러 통과 시간과 네트워크, 그리고 k6 쪽의 큐잉이다 — 사용자가 겪는 것은 70ms 쪽이다. 요청률 41건은 15%가 정적 파일로 가서 journal-api에 오지 않기 때문이다: 300 × 0.85 = 255 ≈ 258.7.

여기서 나오는 원칙이 있다. SLO는 사용자에게 가까운 지점에서 재야 한다. 앱의 히스토그램은 원인을 찾는 데 좋고(어느 핸들러가 느린가), 약속을 지켰는지 판정하는 데는 클라이언트 쪽 측정이 맞다. M21에서 만든 알림이 앱 지표를 쓰는 것은 탐지가 목적이고, SLO 판정은 별도의 측정이 필요하다.

37.7일부러 실패시키기

실패 ① — 에러율만 보고 정상이라고 판정한다

목적37.6의 800 rps 결과를 잘못 읽는 방법을 명시한다.

보고서에 이렇게 적었다고 하자.

800 rps 부하 시험 결과: 에러율 0.00% (1 / 23,931). 목표 달성.
판정모든 숫자가 사실이고 결론이 틀렸다. 23,931건은 실제로 보낸 요청의 수이지 목표한 48,000건이 아니다. 절반은 발사되지 못했고, 그 요청들은 실제 사용자였다면 브라우저가 멈춰 있는 상태다.

부하 시험 결과를 읽을 때 반드시 함께 보는 세 숫자가 있다. 목표 rps(설정값), 달성 rps(http_reqs의 초당 값), dropped_iterations. 셋 중 하나라도 빠지면 결론이 흔들린다.

VU 기반 시험에서는 이 함정이 다른 형태로 나타난다 — dropped_iterations가 없는 대신 부하 자체가 조용히 줄어든다. 응답이 느려지면 VU가 요청을 덜 보내고, 그러면 "부하를 유지했는데 괜찮았다"는 착각이 생긴다. 도착률 기반이 최소한 버렸다고 말해 준다는 점에서 낫다.

실패 ② — kubectl top으로 CPU를 판단한다

목적37.4의 관찰을 진단 절차의 문제로 정리한다.

P99가 14초인 상태에서 가장 먼저 치는 명령이 kubectl top이고, 그 결과가 20m / 42Mi다. CPU도 메모리도 여유가 있다. 그러면 다음 수순은 대개 이렇다 — 네트워크를 의심하고, 레디스를 의심하고, 애플리케이션 코드를 뒤진다. 전부 헛수고다.

보이는 것실제
top: 20~36m 사용limit 50m 중 대부분을 쓰고 있다
CPU 여유 있음주기의 88~96%가 대기
에러율 0.03%P99 14.74초
판정세 신호가 모두 "정상"을 가리키는데 서비스는 사실상 죽어 있다. 스로틀링은 사용률로 드러나지 않는다 — 별도의 지표를 봐야 하고, 그 지표를 대시보드에 두지 않았다면 이 상태를 영원히 진단하지 못한다.

대응은 대시보드에 스로틀링 패널을 두는 것이다. M21에서 만든 대시보드에 다음 한 줄을 더한다.

sum by (pod) (rate(container_cpu_cfs_throttled_periods_total{namespace="$ns"}[5m]))
/
sum by (pod) (rate(container_cpu_cfs_periods_total{namespace="$ns"}[5m]))

알림으로도 만들 값이 있다. 스로틀링 25% 이상이 5분 지속이면 그 파드는 성능 문제를 겪고 있고, 사용자가 알아채기 전에 대응할 수 있다.

37.8운영 관점 — 용량 산정과 튜닝 순서

cpu limit을 걸 것인가

M16에서 미룬 결정을 이제 숫자로 말할 수 있다. cpu limit을 걸면 그 값이 성능의 상한이 된다. 그리고 그 상한에 부딪혔을 때 증상이 가장 진단하기 어려운 형태(정상으로 보이는 지표 + 느린 응답)로 나타난다.

그럼에도 거는 경우가 있다. 다중 테넌트 클러스터에서 이웃을 보호해야 할 때, 비용을 예측 가능하게 만들어야 할 때, 버그로 CPU를 무한히 쓰는 것을 막아야 할 때다. 이때도 원칙이 있다 — 실측한 최대 사용량의 여러 배로 넉넉히 잡고, 스로틀링을 반드시 감시한다. requests와 limits를 같게 만드는 것은 QoS를 위해서지 성능을 위해서가 아니다.

메모리는 반대다. 메모리 limit은 걸어야 한다 — 초과하면 조여지는 것이 아니라 OOMKilled이고, limit이 없으면 한 파드가 노드 전체를 죽인다. M16에서 메모리는 걸고 CPU는 걸지 않은 것이 이 비대칭 때문이다.

튜닝의 순서

부하 시험에서 병목을 찾았을 때 손대는 순서가 있다. 앞의 것이 싸고 효과가 크다.

① 설정 — 스로틀링(이 모듈), 커넥션 풀 크기, 타임아웃. 코드를 고치지 않고 되돌리기도 쉽다. ② 규모 — 파드 수(HPA 상한), 노드 크기. 돈으로 해결하는 자리이고, 수평 확장이 되는 워크로드인지가 전제다. ③ 코드 — 이 앱이라면 KEYS 제거가 여기 해당한다. 효과가 가장 크지만 가장 비싸고 위험하다.

순서를 지키지 않으면 고치지 않아도 될 것을 고친다. 이 모듈에서 만든 병목은 ①로 해결됐고, 코드는 한 줄도 건드리지 않았다.

용량 산정을 숫자로 쓰는 법

이 모듈의 측정을 정리하면 이 클러스터의 용량은 이렇게 적힌다.

항목값근거
안정 처리량약 300 rpsP95 70ms, 실패 0%, dropped 0
한계 처리량약 386 rps800 목표에서 실제 달성치, P95 2.77초
파드당 처리량약 40 rps300 rps ÷ 8 파드
스파이크 여력400 rps 30초파드 8개 상태에서 실패 0

이 표가 있으면 계획을 세울 수 있다. 트래픽이 500 rps가 될 예정이면 파드 상한을 13개로 올리고 노드를 확인한다. 그리고 측정 조건을 함께 적는 것이 중요하다 — 파드 수, 데이터 크기, 부하 구성비. 조건이 바뀌면 숫자도 바뀐다.

파이프라인에 넣기

thresholds 덕분에 이 스크립트는 테스트다. M29의 파이프라인에 짧은 버전(예: 60초, 100 rps)을 넣으면 성능 회귀를 배포 전에 잡는다.

주의할 것은 일회용 클러스터의 성능이 운영과 다르다는 점이다. 절대값을 임계값으로 쓰면 CI 환경의 변동 때문에 자주 깨지므로, 같은 CI 환경에서의 이전 측정 대비 비율로 판정하거나 임계값을 넉넉히 잡는다. 깨지는 것을 무시하기 시작하면 그 게이트는 없는 것과 같다 — M29 8절에서 스캔 임계값에 대해 말한 것과 같은 원칙이다.

  • ls course/labs/scripts/k6-capacity.js → 파일이 있다
  • grep -c "ramping-arrival-rate" course/labs/scripts/k6-capacity.js → 1
  • grep -c "lat_list\|lat_write\|lat_static" course/labs/scripts/k6-capacity.js → 3 이상 (엔드포인트별 측정)
  • grep -c "thresholds" course/labs/scripts/k6-capacity.js → 1

  • 같은 실행에서 dropped_iterations → 출력에 없거나 0
  • kubectl -n journal get deploy journal-api -o jsonpath='{.spec.template.spec.containers[0].resources.limits}' → cpu가 없다 (memory만)
  • 프로메테우스에서 스로틀링 질의 → 빈 결과(cpu limit이 없으면 CFS 할당량 자체가 없어 지표가 만들어지지 않는다). 37.4의 limit 50m 상태에서만 값이 나온다
  • k6 run -e PROFILE=steady -e RPS=800 -e DURATION=30s ... → dropped_iterations가 0보다 크다
  • kubectl -n journal get hpa journal-api --no-headers → REPLICAS가 MAXPODS 이하
  • (이해 확인) kubectl top이 20m을 보여 주는데 P99가 14초일 수 있는 이유를 적는다
  • (이해 확인) 앱의 P95(48ms)와 k6의 P95(70ms) 중 SLO 판정에 쓸 값과 그 이유를 적는다
이 모듈이 남기는 파일
  • course/labs/scripts/k6-capacity.js — 네 구간 시나리오 + 엔드포인트 가중치 + 임계값
  • 측정 기록: 37.5의 전후 비교표와 37.8의 용량 표 (M38 캡스톤 보고서에 들어간다)
  • 클러스터: 변경 없음 — cpu limit은 실험 후 제거했다

정리

# k6 가 남아 있으면 끈다 (포그라운드로 돌렸으면 이미 끝났다)
pkill -f k6-capacity 2>/dev/null

# cpu limit 이 제거됐는지 확인한다 — 실험이 남긴 가장 위험한 흔적이다
kubectl -n journal get deploy journal-api \
  -o jsonpath='{.spec.template.spec.containers[0].resources}{"\n"}'

# 부하로 만들어진 엔트리를 지운다 (쓰기 15% 가 실제로 저장됐다)
PW=$(kubectl -n journal get secret journal-secret -o jsonpath='{.data.REDIS_PASSWORD}' | base64 -d)
kubectl -n journal exec redis-0 -- sh -c \
  "redis-cli -a '$PW' --scan --pattern 'entry:*' | head -2000 | xargs -r redis-cli -a '$PW' DEL"

limits에 memory만 있고 cpu가 없어야 한다. 실험이 배포를 바꾼 것은 사람이 되돌린다 — M36에서 배운 규칙이 여기서도 같다.

부하 시험은 데이터를 남긴다. 쓰기 15%가 전부 레디스에 저장됐고, 그대로 두면 다음 측정의 KEYS가 느려져 결과가 조금씩 나빠진다. 측정 환경을 같게 유지하는 것도 시험의 일부다.
