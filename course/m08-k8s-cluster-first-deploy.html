클러스터 구조와 첫 배포

Compose에서는 컨테이너가 죽으면 도커가 같은 자리에 다시 띄웠다. 쿠버네티스는 다르다 — 파드를 지우면 다른 파드가 생긴다. 이 한 문장의 차이가 선언형 시스템의 전부이고, 이 모듈에서 그것을 눈으로 확인한다.

초반→중반60분Kubernetes 1.37.0
2026-09-05 검증 · kind 3노드 클러스터 · 버전 숫자는 실습 당일 kubectl version으로 다시 확인한다
사전 조건
  • M01의 kind 클러스터가 떠 있다 — course/labs/scripts/preflight.sh 실패 0
  • M07에서 journal-api:v1을 노드에 적재했다 (이 모듈에서는 nginx를 쓰지만 M09부터 필요하다)

핵심 3줄

1. 모든 명령은 apiserver로 가고, 상태는 etcd에 적히며, 컨트롤러가 그 상태에 현실을 맞춘다. kubectl은 그 흐름의 입력 도구일 뿐이다.

2. 파드를 지워도 개수는 유지된다. 되살아나는 것이 아니라 새로 만들어진다 — 이름도 IP도 다르다.

3. describe의 Events가 1차 진단 도구다. 무엇이 언제 왜 일어났는지 시간순으로 적혀 있다.

8.1왜 Compose로는 안 되는가 8.2이론 — 명령 하나가 지나가는 길 8.3따라하기 ① 첫 배포 8.4따라하기 ② 들여다보기 8.5따라하기 ③ 죽여보기 8.6일부러 실패시키기 8.7운영 관점 — 명령형에서 선언형으로 8.8체크포인트와 정리

8.1왜 Compose로는 안 되는가

M06의 Compose 구성은 잘 동작했다. 3서비스가 순서대로 뜨고, 헬스체크가 붙고, --scale api=3으로 복제까지 됐다. 그런데 그 전부가 머신 한 대 이야기다.

그 머신이 죽으면 서비스도 죽는다. 부하가 늘어 머신을 한 대 더 붙이면, 어느 컨테이너를 어느 머신에 둘지 사람이 정해야 한다. 컨테이너가 죽었을 때 그 머신에 자리가 없으면 도커는 다른 머신으로 옮겨주지 않는다. 배포할 때는 compose up이 컨테이너를 지우고 새로 만드는 동안 서비스가 끊긴다.

쿠버네티스는 이 네 가지를 자동화한다 — 배치(어느 노드에 둘지), 자가 복구(죽으면 다시 만들기), 확장(개수 조절), 무중단 교체(롤아웃). 대신 배워야 할 개념이 늘어난다. 이 모듈에서 그 개념들이 어디에 있는지 지도를 먼저 그린다.

8.2이론 — 명령 하나가 지나가는 길

M01에서 컨트롤 플레인 컴포넌트 네 개를 봤다. 이제 그것들이 순서대로 무엇을 하는지 본다. kubectl create deployment web --image=nginx --replicas=3 한 줄이 실행될 때의 흐름이다. 책 1.3(디플로이먼트를 이용한 복제 서비스 생성)이 이 명령으로 만들어지는 오브젝트를 설명하고, 이 절은 그 명령이 클러스터 안에서 어떤 경로로 처리되는지를 본다.

흐름의 성격이 중요하다. kubectl은 "파드를 만들어라"라고 지시하지 않는다. "이런 상태였으면 좋겠다"를 기록할 뿐이고, 그 뒤는 각 컨트롤러가 알아서 현실을 그 상태에 맞춘다. 이것을 조정 루프 (Reconciliation Loop)라고 하며, 쿠버네티스의 모든 동작이 이 패턴이다. M33에서 직접 하나 만든다.

오브젝트 세 겹

배포 하나에 오브젝트가 세 종류 생긴다. 이름이 헷갈리기 쉬우니 역할로 구분한다.

오브젝트역할사람이 직접 다루나
디플로이먼트 (Deployment)"이 이미지를 3개 돌려라, 버전이 바뀌면 이렇게 교체해라"그렇다. 사람이 쓰는 단위
레플리카셋 (ReplicaSet)특정 버전의 파드 개수를 유지아니다. 디플로이먼트가 버전마다 하나씩 만든다
파드 (Pod)실제로 실행되는 컨테이너 묶음. 스케줄링 단위아니다. 직접 만들면 자가 복구가 없다

8.3따라하기 ① 첫 배포

1단계. 배포한다

목적명령 한 줄로 세 겹의 오브젝트가 생기는 것을 확인한다.

kubectl create deployment web --image=nginx:1.29-alpine --replicas=3
실행 결과
deployment.apps/web created

만들어진 것은 디플로이먼트 하나뿐이다. 나머지는 컨트롤러가 만든다.

kubectl get deploy,rs,pods -l app=web
  • -l app=web — 레이블 셀렉터. create deployment가 app=web 레이블을 자동으로 붙였다. 레이블이 모든 연결의 기반이라는 것은 M09의 주제다
  • 쉼표로 여러 종류를 한 번에 조회할 수 있다
실행 결과 (8초 시점)
NAME READY UP-TO-DATE AVAILABLE AGE deployment.apps/web 3/3 3 3 8s NAME DESIRED CURRENT READY AGE replicaset.apps/web-587bcb4dcb 3 3 3 8s NAME READY STATUS RESTARTS AGE pod/web-587bcb4dcb-sxkmn 1/1 Running 0 8s pod/web-587bcb4dcb-w4sgl 1/1 Running 0 8s pod/web-587bcb4dcb-zpgcp 1/1 Running 0 8s

파드 이름 뒤의 다섯 글자(sxkmn 같은)는 환경마다 다르다. 이 문서의 나머지 출력은 전부 이 세 파드를 기준으로 이어진다.

이름 구조를 읽는다. 레플리카셋 이름 web-587bcb4dcb의 뒤쪽은 파드 템플릿의 해시다 — 이미지나 설정을 바꾸면 다른 해시의 레플리카셋이 새로 생긴다(M10 롤아웃의 원리). 파드 이름은 그 뒤에 임의 문자열이 하나 더 붙는다.

판정디플로이먼트 READY 3/3, 파드 3개가 Running · 1/1. 1/1은 파드 안 컨테이너 1개 중 1개가 준비됐다는 뜻이다.

2단계. 어느 노드에 갔는지 본다

목적스케줄러가 한 일을 확인한다. Compose에는 없던 단계다.

kubectl get pods -l app=web -o wide
실행 결과
NAME READY STATUS RESTARTS AGE IP NODE NOMINATED NODE READINESS GATES web-587bcb4dcb-sxkmn 1/1 Running 0 8s 10.244.1.38 study-worker <none> <none> web-587bcb4dcb-w4sgl 1/1 Running 0 8s 10.244.1.39 study-worker <none> <none> web-587bcb4dcb-zpgcp 1/1 Running 0 8s 10.244.2.37 study-worker2 <none> <none>
판정NODE 열에 노드 이름이 둘 이상 나오고, IP 열이 파드마다 다르다. 어느 파드가 어느 노드에 가는지는 환경마다 다르다. 마지막 두 열(NOMINATED NODE, READINESS GATES)은 -o wide가 항상 붙이는 열이며 지금은 <none>이면 정상이다.

NODE 열에 study-worker와 study-worker2가 섞여 나온다. 사람이 지정하지 않았는데 스케줄러가 나눠 배치했다. 컨트롤 플레인 노드에는 기본적으로 일반 파드가 가지 않는다 — node-role.kubernetes.io/control-plane 테인트가 걸려 있기 때문이며 M16에서 다룬다.

IP 열의 10.244.x.x가 파드 IP다. 노드 IP(kubectl get nodes -o wide의 INTERNAL-IP, 이 클러스터에서는 172.20.x.x)와 다른 대역이며, 클러스터 안에서만 의미가 있다. 노드 IP 대역은 도커가 비어 있는 대역을 골라 kind 네트워크에 배정하므로 환경마다 다르다 — 172.18.x.x가 흔하다. 이 IP로 직접 접속하는 코드를 쓰면 안 되는 이유는 8.5절에서 확인한다.

3단계. 접속한다

목적Service를 만들기 전에 임시로 접속하는 방법을 익힌다. 디버깅에서 계속 쓴다.

kubectl port-forward deploy/web 8091:80
실행 결과 (터미널이 붙잡힌다)
Forwarding from 127.0.0.1:8091 -> 80 Forwarding from [::1]:8091 -> 80

다른 터미널에서:

curl -s -o /dev/null -w 'HTTP %{http_code}\n' localhost:8091/
실행 결과 (양쪽 터미널)
HTTP 200 Handling connection for 8091
판정HTTP 200. 포워딩 쪽 터미널에 Handling connection이 찍힌다. Ctrl+C로 종료한다.

port-forward는 디버깅용이다. 내 kubectl 세션이 살아 있는 동안만 유효하고, 디플로이먼트를 지정하면 파드 하나만 골라 연결한다(로드밸런싱이 아니다). 실제 접속 경로는 M11의 Service, M12의 인그레스로 만든다.

여기서 익히는 네 명령이 앞으로 30개 모듈에서 계속 쓰인다.

4단계. describe — 이벤트를 읽는다

목적오브젝트 하나의 상태와 그 오브젝트에 일어난 일을 시간순으로 읽는다. 앞으로 모든 장애 조사의 첫 명령이다.

kubectl describe deploy web | head -12
kubectl describe deploy web | grep -A5 "Events:"
실행 결과
Name: web Namespace: default CreationTimestamp: Sat, 05 Sep 2026 17:22:35 +0900 Labels: app=web Annotations: deployment.kubernetes.io/revision: 1 Selector: app=web Replicas: 3 desired | 3 updated | 3 total | 3 available | 0 unavailable StrategyType: RollingUpdate MinReadySeconds: 0 RollingUpdateStrategy: 25% max unavailable, 25% max surge Pod Template: Labels: app=web Events: Type Reason Age From Message ---- ------ ---- ---- ------- Normal ScalingReplicaSet 8s deployment-controller Scaled up replica set web-587bcb4dcb from 0 to 3
판정Replicas 줄이 3 desired | ... | 3 available, Events에 ScalingReplicaSet 한 건. CreationTimestamp는 환경마다 다르다.

읽을 곳은 Replicas 줄과 Events다. 3 desired | 3 available이면 정상이고, desired와 available이 다르면 문제가 진행 중이라는 뜻이다. Events의 From 열은 누가 그 일을 했는지 알려준다 — deployment-controller, default-scheduler, kubelet. 장애가 났을 때 이 열을 보면 어느 단계에서 멈췄는지 바로 좁혀진다.

RollingUpdateStrategy: 25% max unavailable, 25% max surge는 지정하지 않은 기본값이다. M10에서 이 숫자를 바꿔가며 롤아웃 동작을 관찰한다.

5단계. logs와 exec

목적컨테이너의 표준 출력을 읽고 컨테이너 안에서 명령을 실행한다. 대상을 이름이 아니라 레이블로 고르는 것이 M02와 다른 점이다.

# 디플로이먼트의 파드 하나에서 로그 (여러 개면 하나만 고른다)
kubectl logs deploy/web | tail -3
실행 결과
Found 3 pods, using pod/web-587bcb4dcb-sxkmn 2026/09/05 08:22:35 [notice] 1#1: start worker process 45 2026/09/05 08:22:35 [notice] 1#1: start worker process 46 2026/09/05 08:22:35 [notice] 1#1: start worker process 47

첫 줄 Found 3 pods, using pod/...이 중요하다. 디플로이먼트를 지정하면 kubectl이 파드 하나를 임의로 고른다. 나머지 두 파드의 로그는 보이지 않는다.

# 레이블로 여러 파드의 로그를 한 번에
kubectl logs -l app=web --tail=2 --prefix
  • --tail=2 — 파드마다 마지막 2줄만
  • --prefix — 줄 앞에 [pod/이름/컨테이너]를 붙여 어느 파드의 줄인지 구분한다
실행 결과
[pod/web-587bcb4dcb-sxkmn/nginx] 2026/09/05 08:22:35 [notice] 1#1: start worker process 46 [pod/web-587bcb4dcb-sxkmn/nginx] 2026/09/05 08:22:35 [notice] 1#1: start worker process 47 [pod/web-587bcb4dcb-w4sgl/nginx] 2026/09/05 08:22:35 [notice] 1#1: start worker process 46 [pod/web-587bcb4dcb-w4sgl/nginx] 2026/09/05 08:22:35 [notice] 1#1: start worker process 47 [pod/web-587bcb4dcb-zpgcp/nginx] 2026/09/05 08:22:35 [notice] 1#1: start worker process 46 [pod/web-587bcb4dcb-zpgcp/nginx] 2026/09/05 08:22:35 [notice] 1#1: start worker process 47
# 컨테이너 안에서 명령 실행
POD=$(kubectl get pod -l app=web -o jsonpath='{.items[0].metadata.name}')
kubectl exec $POD -- nginx -v
  • -o jsonpath='{.items[0].metadata.name}' — 목록의 첫 파드 이름만 뽑는다. 파드 이름은 매번 바뀌므로 이렇게 변수에 담아 쓴다
실행 결과
nginx version: nginx/1.29.8
판정--prefix 출력에 파드 이름 세 개가 모두 보이고, nginx -v가 nginx/1.29.x를 돌려준다. 타임스탬프는 환경마다 다르다.

M02의 docker logs · docker exec와 같은 도구다. 달라진 점은 대상을 이름이 아니라 레이블로 고를 수 있다는 것 — 파드 이름은 매번 바뀌므로 스크립트에 박을 수 없다. 셸로 들어가려면 kubectl exec -it $POD -- sh.

6단계. explain과 api-resources — 문서를 클러스터에 묻는다

목적필드 이름이 기억나지 않을 때 검색 대신 클러스터에 직접 묻는 습관을 만든다.

kubectl explain deployment.spec.replicas
kubectl api-resources --namespaced=true | head -8
실행 결과
GROUP: apps KIND: Deployment VERSION: v1 FIELD: replicas <integer> DESCRIPTION: ... NAME SHORTNAMES APIVERSION NAMESPACED KIND bindings v1 true Binding configmaps cm v1 true ConfigMap endpoints ep v1 true Endpoints events ev v1 true Event limitranges limits v1 true LimitRange persistentvolumeclaims pvc v1 true PersistentVolumeClaim pods po v1 true Pod
판정explain은 FIELD: replicas <integer>를, api-resources는 헤더 포함 8행을 출력한다(head -8). DESCRIPTION 아래는 길어서 ...로 줄였다.

explain이 보여주는 것은 이 클러스터 버전의 스키마다. 블로그의 예제가 안 되는 이유가 필드 이름이 바뀌었기 때문인 경우가 많은데, explain은 절대 틀리지 않는다. --recursive를 붙이면 하위 필드를 전부 펼친다.

api-resources의 SHORTNAMES도 알아둔다 — kubectl get po, kubectl get svc, kubectl get pvc처럼 줄여 쓸 수 있다.

8.5따라하기 ③ 죽여보기

7단계. 파드를 지운다

목적이 과정에서 가장 중요한 관찰. 자가 복구가 어떤 방식으로 일어나는지 본다.

POD=$(kubectl get pod -l app=web -o jsonpath='{.items[0].metadata.name}')
echo "지울 파드: $POD"
kubectl delete pod $POD
sleep 5
kubectl get pods -l app=web
실행 결과
지울 파드: web-587bcb4dcb-sxkmn pod "web-587bcb4dcb-sxkmn" deleted from default namespace NAME READY STATUS RESTARTS AGE web-587bcb4dcb-mshk4 1/1 Running 0 6s web-587bcb4dcb-w4sgl 1/1 Running 0 24s web-587bcb4dcb-zpgcp 1/1 Running 0 24s
판정여전히 3개다. 그런데 지운 파드는 돌아오지 않았다 — -sxkmn은 사라지고 -mshk4라는 새 파드가 생겼다. AGE도 6초로 다르다.

이 차이가 핵심이다. 도커는 같은 컨테이너를 다시 시작했지만, 쿠버네티스는 규격에 맞는 새 파드를 만든다. 이름도 IP도 다르고, 심지어 다른 노드일 수 있다. 그래서 파드 IP를 어딘가에 적어두는 설계는 반드시 깨진다(M11에서 Service가 필요한 이유).

8단계. 이벤트로 누가 무엇을 했는지 확인한다

목적7단계에서 파드가 바뀌는 동안 클러스터 안에서 어떤 컴포넌트가 무엇을 했는지 이벤트 목록으로 되짚는다.

kubectl get events --sort-by=.lastTimestamp \
  -o custom-columns='TIME:.lastTimestamp,TYPE:.type,REASON:.reason,OBJECT:.involvedObject.name,MSG:.message' | tail -8
실행 결과
2026-09-05T08:22:35Z Normal SuccessfulCreate web-587bcb4dcb Created pod: web-587bcb4dcb-sxkmn 2026-09-05T08:22:35Z Normal SuccessfulCreate web-587bcb4dcb Created pod: web-587bcb4dcb-zpgcp 2026-09-05T08:22:53Z Normal SuccessfulCreate web-587bcb4dcb Created pod: web-587bcb4dcb-mshk4 2026-09-05T08:22:53Z Normal Scheduled web-587bcb4dcb-mshk4 Successfully assigned default/web-587bcb4dcb-mshk4 to study-worker2 2026-09-05T08:22:53Z Normal Killing web-587bcb4dcb-sxkmn Stopping container nginx 2026-09-05T08:22:54Z Normal Started web-587bcb4dcb-mshk4 Container started 2026-09-05T08:22:54Z Normal Created web-587bcb4dcb-mshk4 Container created 2026-09-05T08:22:54Z Normal Pulled web-587bcb4dcb-mshk4 Container image "nginx:1.29-alpine" already present on machine and can be accessed by the pod

tail -8로 잘라 헤더 행은 빠졌다. 앞 두 줄은 1단계에서 파드가 만들어질 때의 이벤트고, 7단계의 삭제는 :53부터다 — 레플리카셋이 SuccessfulCreate로 새 파드를 만들고, 스케줄러가 Scheduled로 노드를 정하고, 옛 파드는 Killing, 새 파드는 kubelet이 Pulled → Created → Started로 실행했다. 8.2절 그림의 ③ ④ ⑤ ⑥이 그대로다. already present on machine은 M07에서 이미지가 노드에 있기 때문이다.

한 가지 주의 — --sort-by=.lastTimestamp는 초 단위로 정렬하므로 같은 초 안의 순서는 뒤섞일 수 있다. 위 출력에서 Started가 Created보다 먼저 찍힌 것이 그 예다. 순서가 아니라 REASON으로 단계를 대조한다.

판정지운 파드에 Killing, 새 파드에 Scheduled · Pulled · Created · Started가 각 한 건씩 있다. 타임스탬프와 파드 이름은 환경마다 다르다.
이벤트는 사라진다 기본 보존 기간이 1시간이다. 어제 새벽의 장애를 이벤트로 조사할 수는 없다. 그래서 이벤트를 로그 시스템으로 내보내는 구성이 필요하고, M22 로깅에서 다룬다. 지금은 "장애 직후에는 이벤트부터 본다"는 습관만 들인다.

9단계. 개수를 바꿔본다

목적의도한 상태(replicas)만 바꾸면 컨트롤러가 현실을 맞추는 것을 확인한다.

kubectl scale deploy/web --replicas=5
kubectl get pods -l app=web --watch
실행 결과 (약 8초 뒤 Ctrl+C)
deployment.apps/web scaled NAME READY STATUS RESTARTS AGE web-587bcb4dcb-5dcdx 0/1 ContainerCreating 0 0s web-587bcb4dcb-jh4pk 0/1 ContainerCreating 0 0s web-587bcb4dcb-mshk4 1/1 Running 0 26s web-587bcb4dcb-w4sgl 1/1 Running 0 44s web-587bcb4dcb-zpgcp 1/1 Running 0 44s web-587bcb4dcb-5dcdx 0/1 ContainerCreating 0 0s web-587bcb4dcb-jh4pk 0/1 ContainerCreating 0 0s web-587bcb4dcb-jh4pk 1/1 Running 0 0s web-587bcb4dcb-5dcdx 1/1 Running 0 0s

--watch는 처음에 현재 목록을 찍고, 그 뒤로는 변화가 생길 때마다 줄을 추가한다. 새 파드 2개가 ContainerCreating → Running으로 넘어가는 것이 보인다(이미지가 노드에 있어 1초 안에 끝난다. Pending 단계는 너무 짧아 이 출력에는 잡히지 않았다). Ctrl+C로 나온다.

kubectl scale deploy/web --replicas=3
sleep 5
kubectl get pods -l app=web
실행 결과
deployment.apps/web scaled NAME READY STATUS RESTARTS AGE web-587bcb4dcb-jh4pk 1/1 Running 0 14s web-587bcb4dcb-w4sgl 1/1 Running 0 58s web-587bcb4dcb-zpgcp 1/1 Running 0 58s
판정5개에서 다시 3개. 사라진 것은 -mshk4와 -5dcdx다 — 방금 만든 것 둘이 아니라, 새 파드 하나(-jh4pk)가 남고 7단계에서 생긴 파드가 지워졌다. 어느 파드가 지워지는지는 환경마다 다르다.

줄이면 파드가 종료된다. 어느 것을 지울지는 컨트롤러가 정한다 — 준비되지 않은 파드, 같은 노드에 몰려 있는 파드, 재시작이 잦은 파드를 먼저 고르고, 조건이 같으면 최근에 만든 것을 먼저 지운다. 위 결과처럼 "가장 새것"이 아닌 파드가 지워지는 것은 노드 분산 규칙 때문이다. 중요한 상태를 가진 워크로드에서는 이 임의성이 문제가 되며, 그래서 StatefulSet이 따로 있다(M18).

8.6일부러 실패시키기

실패 ① — 파드를 직접 만들고 지워본다

디플로이먼트 없이 파드만 만들면 어떻게 되는지 확인한다. M07에서 이미 한 번 했던 kubectl run이 바로 그것이다.

kubectl run solo --image=nginx:1.29-alpine
kubectl get pod solo
kubectl delete pod solo
sleep 3
kubectl get pod solo
실행 결과
pod/solo created NAME READY STATUS RESTARTS AGE solo 1/1 Running 0 5s pod "solo" deleted from default namespace Error from server (NotFound): pods "solo" not found
판정돌아오지 않는다. 파드를 지켜보는 컨트롤러가 없기 때문이다.

규칙 하나가 여기서 나온다 — 파드를 직접 만들지 않는다. 항상 디플로이먼트(또는 스테이트풀셋 · 데몬셋 · 잡)를 통해 만든다. kubectl run은 일회성 디버깅 파드를 띄울 때만 쓴다. 노드가 죽으면 그 위의 단독 파드는 그냥 사라진다.

실패 ② — 엉뚱한 네임스페이스에서 찾는다 
kubectl get pods -n kube-system -l app=web
kubectl get pods --all-namespaces -l app=web
실행 결과
No resources found in kube-system namespace. NAMESPACE NAME READY STATUS RESTARTS AGE default web-587bcb4dcb-jh4pk 1/1 Running 0 23s default web-587bcb4dcb-w4sgl 1/1 Running 0 67s default web-587bcb4dcb-zpgcp 1/1 Running 0 67s
판정첫 명령은 No resources found in kube-system namespace., 둘째 명령은 NAMESPACE 열이 default인 파드 3행.

No resources found는 "없다"가 아니라 "여기에는 없다"이다. 네임스페이스 (Namespace)는 오브젝트 이름의 유효 범위이고, 지정하지 않으면 현재 컨텍스트의 기본값(default)이 쓰인다. M02에서 본 리눅스 커널 네임스페이스(프로세스의 시야를 가르는 커널 기능)와 이름만 같고 다른 것이다 — 이쪽은 apiserver가 관리하는 논리적 구획이며 커널과는 무관하다. M09에서 자세히 다루지만, 지금 익힐 습관은 두 가지다 — 안 보이면 --all-namespaces(줄여서 -A)로 한 번 더 찾아본다, 그리고 kubectl config set-context --current --namespace=<이름>으로 기본값을 바꿔둘 수 있다는 것.

8.7운영 관점 — 명령형에서 선언형으로

지금까지 쓴 kubectl create deployment와 kubectl scale은 명령형이다. 편하지만 두 가지가 없다 — 이력과 재현성. 어제 누가 scale --replicas=7을 쳤는지 클러스터는 기억하지만 팀은 모른다.

책 1.2절의 지적이 이것이다. 명령형으로 구성한 클러스터는 "어떻게 그 상태가 됐는지" 알 수 없고, 그래서 문제를 재현하기 어렵다. 지금 만든 디플로이먼트를 파일로 뽑아본다.

kubectl get deploy web -o yaml | grep -A8 "^spec:"
실행 결과 (일부)
spec: progressDeadlineSeconds: 600 replicas: 3 revisionHistoryLimit: 10 selector: matchLabels: app: web strategy: rollingUpdate:

내가 지정하지 않은 필드가 잔뜩 채워져 있다. apiserver가 기본값을 적용한 결과이며, 여기에 status와 managedFields까지 붙어 실제 출력은 수십 줄이다. 이것을 그대로 파일로 저장하면 안 된다 — 클러스터 고유의 값(uid, resourceVersion, creationTimestamp)이 섞여 다른 클러스터에서 적용되지 않는다.

M09부터는 매니페스트를 손으로 쓴다(M09의 파드 YAML, M10의 labs/k8s/m10-journal-deployment.yaml). 그 파일들은 이 과정이 미리 써 두었으므로 여기서 만든 것을 저장할 필요는 없다. 다만 빈 화면에서 뼈대가 필요할 때 쓰는 방법 하나는 지금 알아둔다.

# 실제로 만들지 않고 YAML만 화면에 출력한다
kubectl create deployment web --image=nginx:1.29-alpine --replicas=3 \
  --dry-run=client -o yaml
실행 결과
apiVersion: apps/v1 kind: Deployment metadata: labels: app: web name: web spec: replicas: 3 selector: matchLabels: app: web strategy: {} template: metadata: labels: app: web spec: containers: - image: nginx:1.29-alpine name: nginx resources: {} status: {}

위의 kubectl get -o yaml 출력과 비교하면 클러스터 고유의 값이 하나도 없다. M10의 매니페스트는 이 뼈대에 strategy와 readinessProbe를 채운 것이다. 비어 있는 strategy: {}, resources: {}, status: {}는 지워도 되고 두어도 된다.

  • --dry-run=client — 클라이언트에서만 처리하고 서버에 보내지 않는다. 뼈대 생성용
  • --dry-run=server — 서버로 보내되 저장하지 않는다. 어드미션 검증까지 통과하는지 확인할 수 있어 CI에서 매니페스트를 검사할 때 쓴다(M29)

8.8체크포인트와 정리

다음 모듈로 넘어가기 전 확인
  • kubectl get deploy,rs -l app=web → 디플로이먼트 READY 3/3, 레플리카셋 행이 1개이고 DESIRED 3
  • BEFORE=$(kubectl get pod -l app=web -o jsonpath='{.items[0].metadata.name}'); kubectl delete pod $BEFORE; sleep 20; kubectl get pods -l app=web → Running 3행이고, 그 안에 $BEFORE와 같은 이름은 없다
  • kubectl describe deploy web | grep -A4 Events: → From 열에 deployment-controller, Reason에 ScalingReplicaSet
  • kubectl explain deployment.spec.replicas | grep FIELD → FIELD: replicas <integer>
  • kubectl get pod solo → Error from server (NotFound) (실패 ①에서 지운 파드가 돌아오지 않았다)
  • kubectl get pods -A -l app=web --no-headers | wc -l → 3, 같은 명령에서 -A를 빼도 3 (지금 기본 네임스페이스가 default라는 뜻)
  • (이해 확인) 디플로이먼트 · 레플리카셋 · 파드 세 겹 중 사람이 직접 다루는 것은 어느 것이고, 왜 파드를 직접 만들면 안 되는가 — 실패 ①의 결과로 답한다
이 모듈이 남기는 파일
  • 이 모듈은 파일을 남기지 않는다. 클러스터에 web 디플로이먼트(파드 3개)가 남으며, M09 정리 블록이 함께 지운다
  • 진단 3종 세트 — describe · logs · get events. 이후 모든 모듈의 "일부러 실패시키기"에서 이 셋으로 원인을 찾는다

kubectl delete deploy web
