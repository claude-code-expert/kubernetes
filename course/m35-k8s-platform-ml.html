플랫폼 패턴과 ML 워크로드

여기까지 다룬 워크로드는 전부 계속 도는 것이었다 — 디플로이먼트와 스테이트풀셋. 데이터 처리와 모델 훈련은 시작해서 끝나는 일이고, 다른 도구와 다른 실패 처리를 쓴다. 이 모듈에서 인덱스 잡으로 분산 훈련의 형태를 만들고, 재시도해도 소용없는 실패를 구분해 파드 4개를 1개로 줄인다. 그리고 M33의 CRD를 포함한 확장 지점 지도를 정리해, 다음에 무엇을 만들지 고르는 기준을 만든다.

2. 같은 실패에 podFailurePolicy가 있고 없고에 따라 파드 1개와 4개가 되는 것을 측정한다.

35.1끝나는 일은 다르게 다룬다

M10에서 디플로이먼트를 다룰 때 Job과 CronJob은 이름만 보고 넘어갔다. 이 교재의 실습 대상이 계속 도는 웹 서비스였기 때문인데, 실제 클러스터에서 도는 것의 상당 부분은 시작해서 끝나는 일이다 — 야간 집계, 데이터 마이그레이션, 리포트 생성, 모델 훈련.

이런 일에는 지금까지 쓴 도구가 맞지 않는다. 레디니스 프로브가 의미 없다(트래픽을 받지 않는다). 롤링 업데이트도 의미 없다(교체가 아니라 실행이다). 재시작 정책이 반대다 — 디플로이먼트의 파드는 죽으면 무조건 다시 뜨는 것이 맞지만, 배치 작업은 다시 해도 소용없는 실패가 있다.

ML 워크로드가 이 문제를 가장 선명하게 보여 준다. 훈련 한 번이 몇 시간 걸리고, GPU를 요구하고, 중간에 실패하면 비싼 자원을 그만큼 낭비한다. 그래서 배치 잡의 설정 하나하나가 돈으로 환산되고, "일단 재시도" 같은 기본값이 통하지 않는다.

이 모듈은 두 가지를 한다. 배치 워크로드의 도구를 실측으로 익히고, 지금까지 만든 확장 방법들 — CRD(M33), 어드미션 정책(M26), CSI(M18) — 을 하나의 지도로 정리한다. Part 7의 마무리이자, Part 8에서 클러스터 전체를 흔들기 전의 정리다.

35.2이론 — 배치의 두 축과 확장 지점

책 매핑15장 고수준 추상화(감싸기 vs 확장), 확장 지점 지도 · 14장 ML 워크플로, 특수 하드웨어, DRA와 디바이스 플러그인

completions와 parallelism은 다른 값이다

배치 잡의 설계는 두 숫자로 시작한다. completions는 총 몇 조각인가이고 parallelism은 동시에 몇 개를 돌릴 것인가다. 이 둘이 같으면 전부 한꺼번에 돌고, parallelism이 작으면 순서대로 나눠서 돈다.

이 값을 정하는 것이 자원과 시간을 맞바꾸는 일이다. GPU가 두 장인데 parallelism: 8로 두면 여섯 개는 Pending에서 기다리고, 클러스터의 다른 워크로드에 영향을 준다. M16의 requests가 여기서 동시 실행 가능한 수를 실질적으로 결정한다.

completionMode: Indexed를 켜면 각 파드가 자기 번호를 받는다. 번호로 데이터의 어느 부분을 처리할지 정하면 조정자 없이 일을 나눌 수 있다 — 분산 훈련의 데이터 병렬이 이 형태다.

실패는 한 종류가 아니다

backoffLimit만 있으면 모든 실패가 똑같다. 입력 파일이 잘못돼서 실패한 것도, 노드가 빠져서 죽은 것도 같은 횟수만큼 재시도한다. 앞의 것은 몇 번을 해도 결과가 같고, 뒤의 것은 재시도 횟수에 세면 안 되는 실패다.

podFailurePolicy가 그 둘을 나눈다. 종료 코드로 "이 실패는 즉시 포기"를 정하고, 파드 조건으로 "이 실패는 세지 않음"을 정한다. 35.4에서 같은 실패에 파드 수가 4개와 1개로 갈리는 것을 측정한다.

확장 지점은 층마다 다르다

지금까지 쿠버네티스를 확장하는 방법을 여럿 썼다. 정리하면 무엇을 바꾸고 싶은가로 나뉜다.

바꾸고 싶은 것도구모듈
새 리소스 종류CRD + 컨트롤러M33
기존 리소스의 검사·수정어드미션 정책(VAP/MAP) 또는 웹훅M26
특수 장치 요청DRA (resource.k8s.io)이 모듈
스토리지 종류CSI 드라이버M18
배치 순서·우선순위PriorityClass, 스케줄러 플러그인M16
컨테이너 런타임RuntimeClass—

책이 말하는 감싸기 vs 확장의 구분이 여기서 실질적이다. 감싸기는 기존 리소스를 조합해 더 쉽게 쓰게 만드는 것이고(헬름 차트, 내부 CLI), 확장은 API 자체를 늘리는 것이다. 감싸기는 싸고 확장은 비싸므로, 감싸기로 되는지 먼저 확인하는 것이 순서다.

35.3따라하기 ① 인덱스 잡

1단계 — 여섯 조각을 둘씩 돌린다

목적두 숫자의 관계를 눈으로 본다.

spec:
  completions: 6         # 총 조각
  parallelism: 2         # 동시 실행
  completionMode: Indexed
  backoffLimit: 3
  ttlSecondsAfterFinished: 600
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: worker
          command:
            - sh
            - -c
            - |
              I="${JOB_COMPLETION_INDEX}"
              echo "샤드 ${I} 시작 (파드 ${HOSTNAME})"
              sleep $(( 3 + I ))
              echo "샤드 ${I} 완료: loss=0.$(( 90 - I * 7 ))"

restartPolicy: Never가 배치의 기본이다. OnFailure로 두면 같은 파드 안에서 컨테이너만 다시 시작하는데, 그러면 backoffLimit의 계산이 달라지고 실패한 시도의 로그가 사라진다. Never는 파드를 새로 만들므로 실패한 파드가 남아 로그를 볼 수 있다.

kubectl apply -f course/labs/k8s/batch/10-indexed-job.yaml
kubectl -n m35 get job,po --no-headers
출력 (20초 뒤)
job.batch/train-shards Running 4/6 20s pod/train-shards-0-q9drg 0/1 Completed 0 20s pod/train-shards-1-xpztj 0/1 Completed 0 20s pod/train-shards-2-x26fw 0/1 Completed 0 14s pod/train-shards-3-scm5v 0/1 Completed 0 13s pod/train-shards-4-n42kv 1/1 Running 0 6s pod/train-shards-5-jnbv5 1/1 Running 0 4s
판정파드 이름에 인덱스가 들어 있다(train-shards-0-q9drg). 나이를 보면 순서가 보인다 — 0과 1이 먼저, 끝나는 대로 2와 3, 그다음 4와 5. parallelism: 2가 지켜졌고, 동시에 도는 파드는 항상 둘이었다.

2단계 — 결과를 확인한다

목적각 샤드가 다른 일을 했는지 로그로 본다.

kubectl -n m35 wait --for=condition=Complete job/train-shards --timeout=180s
kubectl -n m35 get job train-shards \
  -o jsonpath='{.status.succeeded}/{.spec.completions}{" completedIndexes="}{.status.completedIndexes}{"\n"}'
for P in $(kubectl -n m35 get po -l job-name=train-shards -o name); do
  kubectl -n m35 logs $P | tail -1
done | sort
출력
6/6 completedIndexes=0-5 샤드 0 완료: loss=0.90 샤드 1 완료: loss=0.83 샤드 2 완료: loss=0.76 샤드 3 완료: loss=0.69 샤드 4 완료: loss=0.62 샤드 5 완료: loss=0.55
판정completedIndexes=0-5는 범위 표기다. 일부만 끝났으면 0-2,4처럼 나오므로, 어느 샤드가 남았는지를 이 한 줄로 안다. 각 파드가 자기 번호로 다른 값을 냈다 — 조정자 없이 일을 나눈 것이다.

실제 훈련에서는 인덱스로 데이터 샤드를 고르고, 결과를 공유 스토리지나 오브젝트 스토리지에 쓴다. 파드끼리 직접 통신하는 형태(모델 병렬, all-reduce)라면 서로를 찾을 방법이 추가로 필요하고, 그때 헤드리스 서비스(M11)나 전용 오퍼레이터(M33)를 쓴다.

35.4따라하기 ② 실패를 구분한다

1단계 — 재시도해도 소용없는 실패를 만든다

목적기본 동작을 먼저 본다. 무엇이 문제인지 알아야 정책이 필요한 이유가 보인다.

spec:
  completions: 1
  backoffLimit: 3
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: worker
          command: ["sh","-c","echo '입력 형식이 잘못됐다'; exit 42"]
kubectl -n m35 get po -l job-name=retry-blind --no-headers | wc -l
kubectl -n m35 get job retry-blind \
  -o jsonpath='{.status.failed}{" "}{.status.conditions[?(@.type=="Failed")].reason}{"\n"}'
출력
4 4 BackoffLimitExceeded
판정파드 4개(최초 1 + 재시도 3)가 만들어졌고 전부 같은 이유로 죽었다. 입력이 잘못된 것이므로 몇 번을 해도 결과가 같다. 실습에서는 몇 초지만, GPU를 쓰는 훈련이라면 같은 실패에 네 번의 비용을 낸다.

재시도 사이의 대기 시간이 지수적으로 늘어난다는 점도 함께 본다(10초·20초·40초…). 그래서 backoffLimit: 6짜리 잡이 확실히 실패하는 데까지 몇 분이 걸린다 — 파이프라인이 그만큼 늦게 실패를 안다.

2단계 — 종료 코드로 구분한다

목적애플리케이션이 실패의 종류를 알려 주게 만들고, 잡이 그것을 읽게 한다.

spec:
  backoffLimit: 6            # 원래대로면 6번 재시도한다
  podFailurePolicy:
    rules:
      # 종료 코드 42 = "입력이 잘못됐다". 다시 해도 같으니 즉시 포기한다.
      - action: FailJob
        onExitCodes:
          containerName: worker
          operator: In
          values: [42]
      # 노드가 빠져서 죽은 것은 재시도 횟수에 세지 않는다.
      - action: Ignore
        onPodConditions:
          - type: DisruptionTarget
kubectl -n m35 get po -l job-name=fail-fast --no-headers | wc -l
kubectl -n m35 get job fail-fast -o jsonpath='{.status}' | python3 -m json.tool | head -8
출력
1 { "conditions": [ { "message": "Container worker for pod m35/fail-fast-z9css failed with exit code 42 matching FailJob rule at index 0", "reason": "PodFailurePolicy", "status": "True", "type": "FailureTarget"
판정backoffLimit: 6인데 파드가 하나다. 메시지에 어느 규칙이 걸렸는지(rule at index 0)까지 들어 있어서, 정책이 여럿일 때 무엇이 작동했는지 안다. 같은 실패에 파드 4개와 1개 — 이 차이가 배치 워크로드에서 곧 비용이다.

두 번째 규칙(Ignore + DisruptionTarget)이 반대 방향의 장치다. 노드 드레인(M17)이나 선점 때문에 파드가 죽은 것은 우리 코드의 문제가 아니므로 재시도 횟수에 세지 않는다. 이것이 없으면 클러스터가 바쁜 날 멀쩡한 잡이 BackoffLimitExceeded로 실패한다.

앱 쪽에도 할 일이 있다. 종료 코드를 구분해서 내야 이 정책이 의미를 갖는다. 모든 오류에 exit 1을 내는 프로그램에는 이 기능을 쓸 수 없다 — 배치 작업을 만들 때 종료 코드 규약을 먼저 정한다.

35.5따라하기 ③ 주기 실행

1단계 — 겹침을 어떻게 다룰지 정한다

목적크론잡에서 실제로 사고가 나는 자리를 먼저 막는다.

spec:
  schedule: "*/1 * * * *"        # 실습용. 실제로는 "0 3 * * *" 같은 값
  concurrencyPolicy: Forbid      # 지난 실행이 안 끝났으면 건너뛴다
  startingDeadlineSeconds: 30    # 늦게 깨어났을 때 만회할 범위
  successfulJobsHistoryLimit: 2
  failedJobsHistoryLimit: 1
  jobTemplate:
    spec:
      backoffLimit: 1
      activeDeadlineSeconds: 40  # 잡 자체의 시간 상한
필드기본값기본값이 위험한 이유
concurrencyPolicyAllow실행이 밀리면 겹쳐서 계속 쌓인다. 같은 데이터를 두 프로세스가 동시에 고친다
startingDeadlineSeconds없음컨트롤러가 오래 멈췄다가 깨어나면 놓친 실행을 한꺼번에 만든다
successfulJobsHistoryLimit3기본값은 무난하다. 다만 잡이 남으면 파드도 남는다
activeDeadlineSeconds없음무한 루프에 빠진 배치를 아무도 끊지 않는다

2단계 — 3분 동안 지켜본다

목적히스토리 제한이 실제로 지켜지는지 본다.

kubectl apply -f course/labs/k8s/batch/30-cronjob.yaml
sleep 190
kubectl -n m35 get cronjob --no-headers
kubectl -n m35 get job --no-headers | grep nightly
출력
nightly-eval */1 * * * * <none> False 1 3s 3m10s nightly-eval-29810463 Complete 1/1 12s 2m3s nightly-eval-29810464 Complete 1/1 13s 63s nightly-eval-29810465 Running 0/1 3s 3s
kubectl -n m35 logs job/nightly-eval-29810464
sleep 70
kubectl -n m35 get job --no-headers | grep nightly | wc -l
출력

판정네 번째 실행이 돌았는데 잡은 2개만 남았다 — successfulJobsHistoryLimit: 2가 오래된 것을 지웠다. 잡 이름의 숫자(29810463)는 스케줄 시각을 분 단위로 센 값이라 실행 시각을 이름으로 추적할 수 있다.

3단계 — 멈춘다

목적장애 대응에서 가장 자주 쓰는 조작이다. 지우지 않고 멈춘다.

kubectl -n m35 patch cronjob nightly-eval --type=merge -p '{"spec":{"suspend":true}}'
kubectl -n m35 get cronjob nightly-eval -o jsonpath='{.spec.suspend}{"\n"}'
출력
true

suspend: true는 새 실행만 막는다 — 이미 도는 잡은 계속 돈다. 그것도 멈추려면 잡을 따로 지운다. 크론잡을 삭제하면 이력도 함께 사라지므로, 원인을 조사하는 동안에는 suspend가 맞다.

판정v1이다 — 정식 기능이라 기능 게이트를 켤 필요가 없다. 예전 방식인 디바이스 플러그인(nvidia.com/gpu: 1처럼 확장 자원으로 세는 것)과 달리, DRA는 장치의 속성을 표현하고 고를 수 있다 — "메모리 40GiB 이상인 GPU 한 장" 같은 요청이 가능해진다.

2단계 — 광고된 장치가 있는지 본다

목적API가 있는 것과 쓸 수 있는 것이 다르다는 것을 확인한다.

kubectl get resourceslices
kubectl get deviceclasses
출력
No resources found No resources found
판정둘 다 비어 있다. ResourceSlice는 드라이버가 "이 노드에 이런 장치가 있다"고 광고하는 것이고, DeviceClass도 드라이버가 만든다. 쿠버네티스는 API와 스케줄링만 제공하고 장치 자체는 모른다 — CSI가 스토리지에 대해 하는 일과 같은 구조다.

3단계 — 요청해 보고 어떻게 막히는지 본다

목적드라이버가 없을 때의 증상을 미리 알아 둔다. GPU 클러스터에서 실제로 만나는 오류다.

apiVersion: resource.k8s.io/v1
kind: ResourceClaimTemplate
metadata: {name: gpu-claim, namespace: m35}
spec:
  spec:
    devices:
      requests:
        - name: gpu
          exactly:
            deviceClassName: gpu.example.com
            allocationMode: ExactCount
            count: 1
---
# 잡의 파드 스펙
spec:
  resourceClaims:
    - name: gpu
      resourceClaimTemplateName: gpu-claim
  containers:
    - name: trainer
      resources:
        claims:
          - name: gpu
kubectl apply -f course/labs/k8s/batch/40-dra-example.yaml
kubectl -n m35 get po -l job-name=train-gpu --no-headers
kubectl -n m35 describe po -l job-name=train-gpu | sed -n '/Events:/,$p' | tail -3
출력
train-gpu-w684h 0/1 Pending 0 20s Warning FailedScheduling 20s default-scheduler 0/3 nodes are available: request gpu: device class gpu.example.com does not exist. preemption: 0/3 nodes are available: 3 Preemption is not helpful for scheduling.
판정메시지가 정확하다 — device class gpu.example.com does not exist. M16에서 본 Insufficient cpu와 형태가 같고, 스케줄러가 이유를 이벤트로 남기는 규칙이 확장 자원에도 그대로 적용된다. Pending에서 멈춘 파드를 만나면 언제나 describe의 이벤트부터 본다.

선언의 구조도 짚어 둔다. 청구(ResourceClaim)와 사용(resources.claims)이 분리돼 있다. 파드가 청구를 만들고, 컨테이너가 그중 어느 것을 쓸지 말한다 — 여러 컨테이너가 같은 GPU를 공유하는 경우를 표현하기 위해서다. M18의 PVC와 volumeMounts가 나뉘어 있던 것과 같은 구조다.

35.7일부러 실패시키기

실패 ① — 끝나지 않는 잡을 아무도 끊지 않는다

목적배치에서 가장 비싼 사고를 재현한다. GPU 잡이라면 이것이 그대로 청구서다.

spec:
  backoffLimit: 0
  activeDeadlineSeconds: 15
  template:
    spec:
      containers:
        - name: worker
          command: ["sh","-c","echo '끝나지 않는 훈련'; sleep 600"]
kubectl -n m35 get job too-long \
  -o jsonpath='{.status.conditions[*].reason}{" | "}{.status.conditions[*].message}{"\n"}'
kubectl -n m35 get po -l job-name=too-long --no-headers
출력 (30초 뒤)
DeadlineExceeded | Job was active longer than specified deadline too-long-nkkk2 1/1 Terminating 0 30s
판정15초를 넘기자 잡이 DeadlineExceeded가 되고 파드가 종료된다. activeDeadlineSeconds가 없으면 이 잡은 10분을 다 채운다 — 그리고 실제 상황에서는 몇 시간, 며칠이 된다. 배치 잡을 만들 때 "정상이라면 최대 얼마"를 반드시 적는다.

값을 정하는 기준은 실측이다. 정상 실행의 최장 시간을 재고 여유를 얹는다. 너무 짧으면 정상 잡이 끊기고, 너무 길면 장치가 없는 것과 같다 — M15에서 프로브 임계값을 정한 것과 같은 판단이다.

실패 ② — 종료 코드를 구분하지 않아 정책이 무력해진다

목적35.4의 정책이 앱의 협조 없이는 동작하지 않는다는 것을 정리한다.

podFailurePolicy는 종료 코드를 본다. 그런데 대부분의 프로그램은 모든 오류에 1을 낸다. 파이썬 스크립트가 예외로 죽으면 1, 인자가 잘못돼도 1, 파일이 없어도 1이다.

  podFailurePolicy:
    rules:
      - action: FailJob
        onExitCodes: {containerName: worker, operator: In, values: [1]}
판정이렇게 쓰면 일시적인 실패까지 즉시 포기한다 — 네트워크가 잠깐 끊겨 죽은 것도 1이기 때문이다. 정책이 있으나 마나가 아니라 반대로 해로워진다.

필요한 것은 앱 쪽 규약이다. 예를 들어 2는 입력 오류, 3은 설정 오류, 1은 그 외로 정하고, 정책에서 2와 3만 FailJob으로 잡는다. 배치 작업의 종료 코드는 API다 — 문서로 남기고 바꿀 때는 정책도 함께 본다.

규약을 만들 수 없는 남의 프로그램이라면 래퍼 스크립트로 감싼다. 출력을 보고 종료 코드를 다시 매기는 것이고, M35 이론에서 말한 감싸기의 가장 작은 사례다.

35.8운영 관점 — 확장 지점 고르기

감싸기로 되는지 먼저 본다

새 기능을 요구받았을 때 순서가 있다. 기존 리소스의 조합으로 되는가 → 템플릿이나 스크립트로 감싸면 되는가 → 정책으로 강제하면 되는가(M26) → 새 리소스 종류가 필요한가(M33).

앞의 것일수록 싸다. 헬름 차트는 운영할 프로세스가 없고, 어드미션 정책은 CEL 몇 줄이며, CRD는 컨트롤러를 상시 운영해야 한다. 이 순서를 건너뛰고 CRD부터 만드는 것이 플랫폼 팀의 흔한 실수다.

CRD가 맞는 신호는 M33에서 정리한 대로 셋이다 — 지속적인 조정, 상태 노출, 새로운 도메인 개념. 셋 다 없으면 감싸기로 충분하다.

ML 워크로드에서 실제로 필요한 것

이 모듈에서 만든 인덱스 잡은 가장 단순한 형태다. 실제 분산 훈련은 여기서 두 가지가 더 필요하다.

갱 스케줄링 — 워커 8개가 모두 동시에 확보돼야 훈련이 시작된다. 6개만 뜨면 그 6개가 GPU를 잡은 채 기다리고, 다른 잡도 시작하지 못한다(교착). 기본 스케줄러는 파드를 하나씩 배치하므로 이 문제를 풀지 못하고, 전용 스케줄러나 오퍼레이터가 필요하다.

체크포인트와 재개 — 몇 시간짜리 훈련이 중간에 죽으면 처음부터 하는 것은 감당하기 어렵다. 주기적으로 상태를 저장하고 재시작 때 이어받아야 하는데, 이것은 애플리케이션의 일이지 쿠버네티스가 해 주지 않는다. 다만 저장할 곳(M18의 PVC나 오브젝트 스토리지)과 재시도 정책(35.4)을 맞춰 주는 것이 플랫폼의 몫이다.

둘 다 필요하면 ML 전용 오퍼레이터를 쓰는 것이 현실적인 선택이다. 그것들이 하는 일이 M33에서 만든 구조 그대로이므로, 어떻게 동작하는지 알고 고를 수 있다는 것이 이 두 모듈의 값이다.

배치 잡이 클러스터에 주는 부담

배치 워크로드는 자원 사용이 튄다. 평소에는 비어 있다가 야간에 몰리고, 그때 웹 서비스와 노드를 다툰다. 대응은 셋이다.

우선순위를 나눈다 — PriorityClass로 배치를 낮게 두면 자원이 부족할 때 배치가 먼저 밀려난다(선점). 노드를 나눈다 — M16의 테인트와 톨러레이션으로 배치 전용 노드를 만든다. 쿼터로 상한을 둔다 — M17의 ResourceQuota를 배치 네임스페이스에 걸어 아무리 많이 던져도 그 이상은 안 돌게 한다.

세 번째가 가장 자주 필요하다. 배치 잡은 사람이 실수로 대량 생성하기 쉽고(스크립트 오류로 잡 수천 개), 쿼터가 없으면 그것이 클러스터 전체를 마비시킨다.

35.9체크포인트와 정리

다음 모듈로 넘어가기 전 확인

먼저 읽는다. 아래 잡들은 ttlSecondsAfterFinished: 600이 붙어 있어 완료 10분 뒤 스스로 사라진다. 시간이 지났다면 kubectl apply -f course/labs/k8s/batch/로 다시 만든 뒤 확인한다 — 사라지는 것 자체가 그 필드가 동작한다는 증거다.

  • kubectl -n m35 get job train-shards -o jsonpath='{.status.succeeded}' → 6
  • kubectl -n m35 get job train-shards -o jsonpath='{.status.completedIndexes}' → 0-5
  • kubectl -n m35 get po -l job-name=train-shards --no-headers | grep -c 'train-shards-0-' → 1 (파드 이름에 인덱스가 있다)
  • kubectl -n m35 get po -l job-name=fail-fast --no-headers | wc -l → 1
  • kubectl -n m35 get po -l job-name=retry-blind --no-headers | wc -l → 4
  • kubectl -n m35 get job fail-fast -o jsonpath='{.status.conditions[0].reason}' → PodFailurePolicy
  • kubectl -n m35 get job retry-blind -o jsonpath='{.status.conditions[?(@.type=="Failed")].reason}' → BackoffLimitExceeded
  • kubectl -n m35 get job too-long -o jsonpath='{.status.conditions[*].reason}' → DeadlineExceeded가 들어 있다
  • kubectl -n m35 get cronjob nightly-eval -o jsonpath='{.spec.concurrencyPolicy}' → Forbid
  • kubectl -n m35 get cronjob nightly-eval -o jsonpath='{.spec.suspend}' → true
  • kubectl -n m35 get job --no-headers | grep -c nightly → 2 이하 (히스토리 제한)
  • kubectl api-resources --api-group=resource.k8s.io --no-headers | wc -l → 5
  • kubectl get resourceslices --no-headers 2>&1 | grep -c 'No resources' → 1 (드라이버가 없다)
  • (이해 확인) completions와 parallelism을 각각 늘렸을 때 무엇이 달라지는지 적는다
  • (이해 확인) podFailurePolicy에서 exit 1을 FailJob으로 잡으면 왜 해로운지 적는다

다음 모듈

Part 1부터 여기까지 만드는 것을 했다. 프로브를 걸고, 리소스를 정하고, 정책을 붙이고, 배포 절차를 만들었다. 그것들이 실제로 동작하는지는 대부분 정상 상황에서만 확인했다 — 파드를 하나 지워 보고, 롤아웃을 한 번 되돌려 봤을 뿐이다.

M36에서 클러스터를 계획적으로 망가뜨린다. 파드를 무작위로 죽이고, 네트워크에 지연을 넣고, CPU를 고갈시킨다. 그리고 그때 M21에서 만든 알림이 실제로 울리는지, M15의 종료 창이 정말 요청을 지키는지를 확인한다. 가설을 먼저 쓰고 실험으로 검증하는 것이 이 파트의 방식이다.
