리소스 · QoS · 스케줄링

M15까지 만든 저널 애플리케이션의 모든 파드는 BestEffort다. 스케줄러는 이 파드에 얼마가 필요한지 모르고, 노드가 빠듯해지면 가장 먼저 쫓겨난다. 이 모듈에서 requests를 붙여 Pending을 일부러 만들고 이벤트에서 원인을 읽은 뒤, 파드를 어느 노드에 놓을지 통제하고, 노드를 안전하게 비운다.

사전 조건

  • metrics-server가 떠 있다 (M01). 확인: kubectl top nodes가 수치를 돌려준다. error: Metrics API not available이 나오면 M01 1.5로 돌아간다
  • 워커 노드가 2개 이상이다. 확인: kubectl get nodes에 study-worker, study-worker2
  • 고칠 파일: course/labs/k8s/journal/의 20-redis.yaml · 30-journal-api.yaml · 40-web-static.yaml · kustomization.yaml
  • 새로 쓰는 파일: course/labs/k8s/journal/60-pdb.yaml

핵심 3줄

1. 노드가 텅 비어 있는데도 파드가 Pending이 되는 상황을 만들고, describe의 이벤트 한 줄에서 원인을 읽어낸다.

2. nodeSelector · 테인트 · topologySpreadConstraints로 파드를 어디에 놓을지 정하고, 실패했을 때 스케줄러가 남기는 메시지가 원인마다 어떻게 다른지 구분한다.

3. PDB를 걸고 노드를 비워 본다. 값을 잘못 잡으면 노드를 영원히 못 비운다는 것을 교착 상태로 직접 확인한다.

16.1왜 BestEffort가 문제인가 16.2이론 — 두 개의 자, 그리고 세 등급 16.3따라하기 ① requests가 자리를 정한다 16.4따라하기 ② 어느 노드에 놓을지 고른다 16.5따라하기 ③ 고르게 편다 16.6따라하기 ④ 네임스페이스 단위로 막는다 16.7따라하기 ⑤ 노드를 비운다 16.8일부러 실패시키기 16.9운영 관점 — limits를 걸 것인가 16.10체크포인트와 정리

16.1왜 BestEffort가 문제인가

M15를 마친 상태에서 저널 네임스페이스의 QoS 등급을 본다.

kubectl -n journal get pods -o custom-columns='NAME:.metadata.name,QOS:.status.qosClass,NODE:.spec.nodeName'
출력
NAME QOS NODE journal-api-76db5cfb9f-gw9fz BestEffort study-worker2 journal-api-76db5cfb9f-kwwt8 BestEffort study-worker2 journal-api-76db5cfb9f-p5vkw BestEffort study-worker redis-0 BestEffort study-worker2 web-static-74cfbb9764-krnjh BestEffort study-worker2 web-static-74cfbb9764-pcnsf BestEffort study-worker

전부 BestEffort다. 그리고 노드 배치를 보면 study-worker2에 넷, study-worker에 둘이 몰려 있다. 둘 다 우연이 아니라 우리가 아무것도 지시하지 않은 결과다.

BestEffort는 "이 파드가 얼마를 쓸지 모른다"는 뜻이다. 결과가 두 갈래로 나타난다. 첫째, 스케줄러가 이 파드를 무게 없는 것으로 취급한다 — 노드에 몇 개를 넣든 계산상 늘 자리가 있다. 둘째, 노드에 메모리가 부족해지면 축출 대상 1순위가 된다. 데이터베이스든 프론트엔드든 가리지 않는다.

레디스가 BestEffort인 것이 특히 위험하다. 노드가 빠듯해지면 상태를 들고 있는 파드가 먼저 죽는다. M14에서 PVC를 붙여 데이터는 살렸지만, 축출 순서까지 고려하지는 않았다.

그런데 requests를 붙이는 순간 새로운 문제가 생긴다. 노드가 텅 비어 있는데도 파드가 뜨지 않는 상황이다. 왜 그런지가 이 모듈의 절반이다.

16.2이론 — 두 개의 자, 그리고 세 등급

책 8.1은 리소스 관리를 클러스터 운영자의 관점에서 다룬다. 실습에서 마주칠 개념만 추리면 셋이다 — 스케줄러가 무엇을 보고 결정하는가, requests와 limits가 각각 무엇을 하는가, 부족할 때 누가 먼저 밀려나는가.

스케줄러가 파드 하나를 놓기까지

스케줄러는 두 단계로 일한다. 먼저 필터링 filtering 단계에서 불가능한 노드를 걸러낸다 — requests를 감당할 여유가 없는 노드, 테인트를 견디지 못하는 노드, nodeSelector에 맞지 않는 노드가 여기서 탈락한다. 남은 노드가 하나도 없으면 파드는 Pending이 되고, 탈락 이유가 이벤트에 그대로 적힌다. 이 모듈에서 반복해 읽을 문장이 그것이다.

살아남은 노드가 있으면 점수 매기기 scoring 단계에서 그중 가장 나은 곳을 고른다. 자원이 고르게 퍼지는 쪽, 이미지가 이미 있는 노드, 같은 서비스의 파드가 덜 몰린 곳에 점수를 준다. 필터링은 가부를 정하고 점수는 선호를 정한다 — 이 구분이 requiredDuringScheduling과 preferredDuringScheduling이라는 이름으로 매니페스트에도 그대로 나온다.

중요한 것은 스케줄러가 배치 시점에만 관여한다는 점이다. 한번 노드에 올라간 파드는 그 노드가 한가해지든 붐비든 스스로 옮겨 가지 않는다. 16.7에서 노드를 비운 뒤 되돌려도 파드가 돌아오지 않는 것을 직접 보게 된다.

requests와 limits — 서로 다른 두 사람이 읽는다

requests는 스케줄러가 읽는 예약값이다. "이만큼은 확보돼야 한다"는 선언이고, 노드에 남은 예약 가능량을 계산하는 데만 쓰인다. limits는 커널이 읽는 상한이다. cgroup에 그대로 내려가 런타임에 강제된다. 둘은 다른 층에서 다른 목적으로 동작하며, 그래서 같은 노드를 두고 정반대의 보고를 하는 일이 생긴다.

초과했을 때의 처리도 자원에 따라 다르다. 메모리는 압축할 수 없으므로 상한을 넘으면 컨테이너를 죽인다(OOMKilled). CPU는 압축할 수 있으므로 죽이지 않고 조인다 — 주어진 몫을 다 쓰면 다음 주기까지 기다리게 한다. 이것을 스로틀링 throttling이라고 한다. 증상이 전혀 다르다. 메모리 초과는 재시작으로 드러나고 CPU 초과는 조용히 느려지기만 한다. 16.9에서 둘 다 확인한다.

QoS 세 등급 — 스스로 정하지 않는다

QoS 등급은 필드로 지정하는 것이 아니라 requests와 limits를 어떻게 적었는지에 따라 자동으로 결정된다.

등급조건메모리 부족 시
Guaranteed모든 컨테이너에서 requests == limits (cpu·memory 둘 다)마지막까지 남는다
Burstablerequests가 있고 Guaranteed 조건은 아니다두 번째로 밀린다. 예약을 많이 초과해 쓰고 있는 파드가 먼저
BestEffortrequests도 limits도 없다가장 먼저 쫓겨난다

등급을 올리는 방법은 매니페스트를 고치는 것뿐이다. Guaranteed가 늘 정답은 아니다 — requests == limits로 묶으면 여유가 있어도 더 쓸 수 없고, 노드의 자원이 예약만 채운 채 놀게 된다. 이 트레이드오프는 16.9에서 다시 본다.

16.3따라하기 ① requests가 자리를 정한다

1단계 — 세 등급을 한 번에 만든다

목적QoS가 매니페스트의 어떤 차이에서 갈리는지 눈으로 확인한다.

실험용 네임스페이스를 따로 쓴다. journal을 건드리지 않기 위해서다.

kubectl create ns m16

cat <<'EOF' | kubectl -n m16 apply -f -
apiVersion: v1
kind: Pod
metadata: {name: qos-besteffort, labels: {demo: qos}}
spec:
  containers: [{name: c, image: nginx:1.29-alpine}]
---
apiVersion: v1
kind: Pod
metadata: {name: qos-burstable, labels: {demo: qos}}
spec:
  containers:
    - name: c
      image: nginx:1.29-alpine
      resources: {requests: {cpu: 50m, memory: 64Mi}, limits: {cpu: 200m, memory: 128Mi}}
---
apiVersion: v1
kind: Pod
metadata: {name: qos-guaranteed, labels: {demo: qos}}
spec:
  containers:
    - name: c
      image: nginx:1.29-alpine
      resources: {requests: {cpu: 100m, memory: 128Mi}, limits: {cpu: 100m, memory: 128Mi}}
EOF
확인 
kubectl -n m16 get pods -l demo=qos \
  -o custom-columns='NAME:.metadata.name,QOS:.status.qosClass,STATUS:.status.phase'
NAME QOS STATUS qos-besteffort BestEffort Running qos-burstable Burstable Running qos-guaranteed Guaranteed Running
판정세 등급이 그대로 나온다. qosClass는 우리가 적은 적이 없는 필드다 — apiserver가 resources를 보고 채운 것이다.

2단계 — 노드 용량을 확인한다

목적다음 단계에서 얼마를 요청해야 자리가 모자라는지 계산할 근거를 얻는다.

kubectl get nodes -o custom-columns='NAME:.metadata.name,CPU:.status.capacity.cpu,ALLOC-CPU:.status.allocatable.cpu'
출력
NAME CPU ALLOC-CPU study-control-plane 14 14 study-worker 14 14 study-worker2 14 14
필드뜻
capacity노트북이 이 노드에 준 전체 자원
allocatable그중 파드에 나눠 줄 수 있는 몫. kubelet과 시스템 데몬 몫을 뺀 값이다
판정워커 한 대에 14 CPU다. 이 값은 노트북 사양에 따라 다르다 — 자기 환경의 숫자를 적어 두고 다음 단계에서 그 값을 기준으로 요청량을 정한다. 아래 예시는 14 기준이므로, 8 CPU 노트북이라면 13 대신 7을 쓴다.

3단계 — 자리가 모자라게 만든다

목적Pending을 재현하고, 스케줄러가 남기는 이벤트를 읽는 연습을 한다.

워커 한 대가 14 CPU이고 워커는 두 대다. 파드 하나가 13 CPU를 요구하면 두 개까지만 들어간다.

cat <<'EOF' | kubectl -n m16 apply -f -
apiVersion: apps/v1
kind: Deployment
metadata: {name: hungry}
spec:
  replicas: 3
  selector: {matchLabels: {app: hungry}}
  template:
    metadata: {labels: {app: hungry}}
    spec:
      containers:
        - name: c
          image: nginx:1.29-alpine
          resources:
            requests: {cpu: "13", memory: 256Mi}
EOF
kubectl -n m16 get pods -l app=hungry -o wide
출력
NAME READY STATUS RESTARTS AGE IP NODE NOMINATED NODE hungry-75bc79769c-2984x 1/1 Running 0 15s 10.244.2.113 study-worker2 <none> hungry-75bc79769c-9vdtp 1/1 Running 0 15s 10.244.1.117 study-worker <none> hungry-75bc79769c-k2dbb 0/1 Pending 0 15s <none> <none> <none>

IP와 파드 접미사는 환경마다 다르다.

판정둘은 떴고 하나는 Pending이다. NODE가 <none>이면 아직 어느 노드에도 배정되지 않았다는 뜻이다.

4단계 — 왜 못 떴는지 이벤트에서 읽는다

목적추측하지 않고 스케줄러가 남긴 문장을 그대로 읽는다. 이 모듈에서 가장 자주 쓸 명령이다.

POD=$(kubectl -n m16 get po -l app=hungry --field-selector=status.phase=Pending \
        -o jsonpath='{.items[0].metadata.name}')
kubectl -n m16 describe pod $POD | tail -n 4
출력
Events: Type Reason Age From Message ---- ------ ---- ---- ------- Warning FailedScheduling 15s default-scheduler 0/3 nodes are available: 1 node(s) had untolerated taint(s), 2 Insufficient cpu. preemption: 0/3 nodes are available: 1 Preemption is not helpful for scheduling, 2 No preemption victims found for incoming pod.

한 줄에 세 가지가 들어 있다. 0/3 nodes are available은 세 노드 전부 탈락했다는 뜻이고, 이어지는 절이 노드를 이유별로 묶은 것이다 — 1 node(s) had untolerated taint(s)는 컨트롤 플레인(테인트가 걸려 있다), 2 Insufficient cpu는 워커 둘이다. 뒤쪽 preemption: 절은 "우선순위가 낮은 파드를 밀어내서라도 자리를 만들 수 있는가"를 따져 본 결과이고, 여기서는 밀어낼 대상이 없다.

판정Reason이 FailedScheduling이고 메시지에 Insufficient cpu가 보이면 requests가 노드 여유보다 크다는 뜻이다. 16.4·16.5에서 같은 자리에 다른 문구가 나오는 경우를 보게 되는데, 그 문구가 곧 원인이다.

5단계 — 같은 노드를 두 개의 자로 잰다

목적requests가 사용량이 아니라 예약이라는 것을 두 명령의 출력 차이로 확인한다.

kubectl top node study-worker
kubectl describe node study-worker | sed -n '/Allocated resources/,/hugepages-1Gi/p'
출력
NAME CPU(cores) CPU(%) MEMORY(bytes) MEMORY(%) study-worker 34m 0% 452Mi 5% Allocated resources: (Total limits may be over 100 percent, i.e., overcommitted.) Resource Requests Limits -------- -------- ------ cpu 13250m (94%) 300m (2%) memory 498Mi (6%) 256Mi (3%)
판정같은 노드가 실사용 0%, 예약 94%다. 둘 다 맞는 값이다. 새 파드를 받을지 말지는 아래 자로만 판단하므로, 노드가 놀고 있어도 Pending이 난다. 운영에서 "노드가 한가한데 파드가 안 뜬다"는 신고가 들어오면 이 두 명령을 나란히 쳐 보는 것이 첫 진단이다.

여기서 정리해 둔다 — requests를 실제 사용량보다 크게 잡으면 노드가 놀면서도 파드를 못 받고, 작게 잡으면 노드가 초과 할당돼 실제로 자원이 모자랄 때 축출이 일어난다. 적정값을 정하는 근거는 실측이며, 그 실측 도구가 M19~M21에서 세우는 관측 스택이다.

kubectl -n m16 delete deploy hungry

16.4따라하기 ② 어느 노드에 놓을지 고른다

지금까지는 "자리가 있느냐"만 봤다. 이제 자리가 있어도 거기에 놓지 말라거나 거기에만 놓으라고 지시한다. 방향이 반대인 두 장치가 있다 — nodeSelector는 파드가 노드를 고르고, 테인트는 노드가 파드를 거른다.

6단계 — 라벨을 붙이고 그 노드만 고르게 한다

목적가장 단순한 배치 지시인 nodeSelector의 동작과, 맞는 노드가 없을 때의 메시지를 확인한다.

kubectl label node study-worker2 disktype=ssd

cat <<'EOF' | kubectl -n m16 apply -f -
apiVersion: v1
kind: Pod
metadata: {name: pinned}
spec:
  nodeSelector: {disktype: ssd}
  containers: [{name: c, image: nginx:1.29-alpine, resources: {requests: {cpu: 10m}}}]
---
apiVersion: v1
kind: Pod
metadata: {name: pinned-nowhere}
spec:
  nodeSelector: {disktype: nvme}
  containers: [{name: c, image: nginx:1.29-alpine, resources: {requests: {cpu: 10m}}}]
EOF
kubectl -n m16 get po pinned pinned-nowhere \
  -o custom-columns='NAME:.metadata.name,STATUS:.status.phase,NODE:.spec.nodeName'
출력
NAME STATUS NODE pinned Running study-worker2 pinned-nowhere Pending <none>
kubectl -n m16 describe pod pinned-nowhere | tail -n 3
출력
Warning FailedScheduling 10s default-scheduler 0/3 nodes are available: 1 node(s) had untolerated taint(s), 2 node(s) didn't match Pod's node affinity/selector. preemption: 0/3 nodes are available: 3 Preemption is not helpful for scheduling.
판정4단계와 같은 FailedScheduling이지만 문구가 didn't match Pod's node affinity/selector로 바뀌었다. 자원이 아니라 조건이 안 맞은 것이다. 두 문구를 구분할 줄 알면 Pending 진단의 절반이 끝난다.

nodeSelector는 "정확히 일치, 아니면 배치 불가"밖에 표현하지 못한다. "가능하면 A에, 안 되면 아무 데나"처럼 선호를 표현하려면 affinity의 preferredDuringSchedulingIgnoredDuringExecution을 쓴다. 이름이 긴 이유는 16.2에서 말한 필터링(required)과 점수(preferred)의 구분을 이름에 담았기 때문이고, 뒤의 IgnoredDuringExecution은 이미 실행 중인 파드에는 소급 적용하지 않는다는 뜻이다 — 조건이 깨져도 쫓아내지 않는다.

7단계 — 노드가 파드를 거르게 한다

목적테인트와 톨러레이션이 nodeSelector와 방향이 반대라는 것을 확인한다.

nodeSelector는 파드가 "나는 저기로 가겠다"고 말하는 것이고, 테인트는 노드가 "나는 아무나 받지 않는다"고 말하는 것이다. 컨트롤 플레인에 사용자 파드가 뜨지 않는 것도 이 장치 때문이다.

kubectl taint node study-worker2 tier=batch:NoSchedule

cat <<'EOF' | kubectl -n m16 apply -f -
apiVersion: v1
kind: Pod
metadata: {name: no-toleration}
spec:
  nodeSelector: {kubernetes.io/hostname: study-worker2}
  containers: [{name: c, image: nginx:1.29-alpine, resources: {requests: {cpu: 10m}}}]
---
apiVersion: v1
kind: Pod
metadata: {name: with-toleration}
spec:
  nodeSelector: {kubernetes.io/hostname: study-worker2}
  tolerations: [{key: tier, operator: Equal, value: batch, effect: NoSchedule}]
  containers: [{name: c, image: nginx:1.29-alpine, resources: {requests: {cpu: 10m}}}]
EOF
값뜻
NoSchedule새 파드를 받지 않는다. 이미 떠 있는 파드는 그대로 둔다
NoExecute새 파드도 안 받고, 톨러레이션 없는 기존 파드는 쫓아낸다
PreferNoSchedule되도록 받지 않는다. 다른 자리가 없으면 받는다
kubectl -n m16 get po no-toleration with-toleration \
  -o custom-columns='NAME:.metadata.name,STATUS:.status.phase,NODE:.spec.nodeName'
출력
NAME STATUS NODE no-toleration Pending <none> with-toleration Running study-worker2
판정같은 nodeSelector를 가진 두 파드의 운명이 톨러레이션 유무로 갈렸다. describe pod no-toleration의 이벤트에는 2 node(s) had untolerated taint(s)가 나온다 — 이번에는 컨트롤 플레인과 study-worker2 둘 다 테인트 때문에 탈락했다.

톨러레이션은 허가일 뿐 배치 지시가 아니다. 테인트를 견딜 수 있게 될 뿐, 그 노드로 가라는 뜻은 아니다. "전용 노드에만 보내고 싶다"면 테인트(다른 파드 차단)와 nodeSelector(이 파드를 그쪽으로)를 함께 써야 한다.

kubectl taint node study-worker2 tier-
kubectl -n m16 delete pod no-toleration with-toleration pinned pinned-nowhere

16.5따라하기 ③ 고르게 편다

16.1에서 본 것처럼 journal-api 파드 셋이 2:1로 몰려 있다. 노드 하나가 빠지면 용량의 3분의 2가 한꺼번에 사라진다는 뜻이다. 이제 저널 애플리케이션 자체를 고친다.

8단계 — requests를 붙이고 고르게 펴라고 지시한다

목적실습용 파드가 아니라 실제 애플리케이션에 resources와 분산 제약을 넣는다.

course/labs/k8s/journal/30-journal-api.yaml의 파드 스펙에 두 곳을 더한다.

    spec:
      terminationGracePeriodSeconds: 30
      # 파드를 노드에 고르게 편다 (M16). 한 노드에 몰려 있으면 그 노드가 빠질 때 전부 같이 빠진다.
      # nodeTaintsPolicy: Honor 가 없으면 테인트 걸린 control-plane 도 도메인으로 세어
      # 어디에 놓아도 skew 가 1 을 넘게 되고, 스케줄이 통째로 막힌다. 기본값은 Ignore 다.
      topologySpreadConstraints:
        - maxSkew: 1
          topologyKey: kubernetes.io/hostname
          whenUnsatisfiable: DoNotSchedule
          nodeTaintsPolicy: Honor
          labelSelector:
            matchLabels:
              app: journal-api
      containers:
        - name: api
          # ... 생략: image · ports · env 는 그대로 ...
          # requests 가 스케줄링을 결정하고 limits 가 런타임을 제한한다 (M16).
          # cpu limit 을 걸지 않는 이유: 초과하면 죽는 것이 아니라 조여진다(스로틀링).
          # 여유가 있을 때 더 쓰게 두는 편이 낫다. memory 는 초과하면 OOMKilled 이므로 건다.
          resources:
            requests:
              cpu: 50m
              memory: 64Mi
            limits:
              memory: 192Mi
필드뜻
maxSkew: 1도메인 사이 파드 수 차이가 1을 넘지 않게 한다
topologyKey무엇을 도메인으로 볼지. kubernetes.io/hostname이면 노드 단위, topology.kubernetes.io/zone이면 가용 영역 단위다
whenUnsatisfiable: DoNotSchedule지킬 수 없으면 배치하지 않는다. ScheduleAnyway로 두면 선호로만 작동한다
nodeTaintsPolicy: Honor톨러레이션 없이 갈 수 없는 노드는 도메인에서 제외한다. 기본값은 Ignore이고, 그것이 16.8 실패 ①의 원인이다

redis와 web-static에도 requests를 넣어 네임스페이스 전체를 Burstable로 맞춘다. 값은 kubectl top pod로 잰 실제 사용량(각각 10Mi·11Mi 안팎)에 여유를 얹은 것이다.

# 20-redis.yaml 의 컨테이너에
          resources:
            requests: {cpu: 25m, memory: 32Mi}
            limits: {memory: 128Mi}

# 40-web-static.yaml 의 컨테이너에
          resources:
            requests: {cpu: 10m, memory: 16Mi}
            limits: {memory: 64Mi}
kubectl apply -k course/labs/k8s/journal
kubectl -n journal rollout status deploy/journal-api
출력
deployment.apps/journal-api configured deployment.apps/web-static configured statefulset.apps/redis configured deployment "journal-api" successfully rolled out
판정롤아웃이 끝나면 QoS와 배치가 함께 바뀐다.
kubectl -n journal get po -o custom-columns='NAME:.metadata.name,QOS:.status.qosClass,NODE:.spec.nodeName' --no-headers
출력
journal-api-599bf98c7-jgs98 Burstable study-worker journal-api-599bf98c7-npq44 Burstable study-worker journal-api-599bf98c7-w9wzf Burstable study-worker2 redis-0 Burstable study-worker2 web-static-fc76c78dc-djd77 Burstable study-worker2 web-static-fc76c78dc-ww9x6 Burstable study-worker
판정BestEffort가 하나도 없다. journal-api는 2:1인데, 도메인이 둘이고 파드가 셋이므로 maxSkew: 1을 만족하는 최선의 배치다. 3:0이나 1:2가 나오면 제약이 적용되지 않은 것이니 매니페스트를 다시 확인한다.

topologySpreadConstraints도 배치 시점에만 작동한다. 이미 몰려 있는 파드를 지금 펴 주지는 않는다 — 위에서 분산이 바뀐 것은 롤아웃으로 파드가 새로 만들어졌기 때문이다. 운영 중에 쏠림을 재조정하려면 별도의 도구(descheduler)가 필요하고, 이 과정에서는 다루지 않는다.

16.6따라하기 ④ 네임스페이스 단위로 막는다

지금까지는 파드 하나하나에 적는 값이었다. 팀이 여럿인 클러스터에서는 한 팀이 클러스터 전체를 먹지 않게 네임스페이스 단위로 총량을 건다.

9단계 — 총량과 기본값을 함께 건다

목적ResourceQuota(총량 상한)와 LimitRange(개별 파드의 기본값·상한)가 어떻게 다른지 확인한다.

cat <<'EOF' | kubectl -n m16 apply -f -
apiVersion: v1
kind: ResourceQuota
metadata: {name: team-quota}
spec:
  hard:
    requests.cpu: "500m"
    requests.memory: 512Mi
    limits.memory: 1Gi
    pods: "5"
---
apiVersion: v1
kind: LimitRange
metadata: {name: team-defaults}
spec:
  limits:
    - type: Container
      default: {cpu: 200m, memory: 128Mi}
      defaultRequest: {cpu: 50m, memory: 64Mi}
      max: {cpu: "1", memory: 512Mi}
EOF
필드뜻
defaultlimits를 안 적은 컨테이너에 넣어 줄 값
defaultRequestrequests를 안 적은 컨테이너에 넣어 줄 값
max이 값을 넘는 limits는 아예 거부한다

ResourceQuota에 requests.cpu가 들어 있으면 그 네임스페이스에서는 requests를 안 적은 파드를 만들 수 없다. 총량을 셀 수 없기 때문이다. 그래서 쿼터는 보통 LimitRange와 짝으로 건다 — 한쪽이 총량을 막고 다른 쪽이 빈칸을 채운다.

10단계 — 아무것도 안 적고 파드를 만들어 본다

목적LimitRange가 실제로 값을 채워 넣는지 확인한다.

kubectl -n m16 run defaulted --image=nginx:1.29-alpine --restart=Never
kubectl -n m16 get pod defaulted -o jsonpath='{.spec.containers[0].resources}{"\n"}{.status.qosClass}{"\n"}'
출력
{"limits":{"cpu":"200m","memory":"128Mi"},"requests":{"cpu":"50m","memory":"64Mi"}} Burstable
판정kubectl run은 resources를 적을 자리가 없는 명령인데도 값이 들어 있고 QoS가 Burstable이다. 어드미션 단계에서 LimitRange가 채운 것이다. 요청이 apiserver를 지나며 변형되는 이 지점은 M26에서 어드미션 컨트롤로 다시 다룬다.

11단계 — 한도를 넘겨 본다

목적거부 메시지 두 종류를 구분한다. 총량 초과와 개별 상한 초과는 다른 장치가 막는다.

kubectl -n m16 run toobig --image=nginx:1.29-alpine --restart=Never \
  --overrides='{"spec":{"containers":[{"name":"toobig","image":"nginx:1.29-alpine","resources":{"requests":{"cpu":"600m"},"limits":{"cpu":"600m","memory":"128Mi"}}}]}}'
출력
Error from server (Forbidden): pods "toobig" is forbidden: exceeded quota: team-quota, requested: requests.cpu=600m, used: requests.cpu=50m, limited: requests.cpu=500m
kubectl -n m16 run overmax --image=nginx:1.29-alpine --restart=Never \
  --overrides='{"spec":{"containers":[{"name":"overmax","image":"nginx:1.29-alpine","resources":{"requests":{"cpu":"2"},"limits":{"cpu":"2"}}}]}}'
출력
Error from server (Forbidden): pods "overmax" is forbidden: maximum cpu usage per Container is 1, but limit is 2
판정둘 다 Forbidden이지만 뒤 문장이 다르다. exceeded quota는 네임스페이스 총량이고, maximum cpu usage per Container는 개별 컨테이너 상한이다. 그리고 이 거부는 스케줄링 전에 일어난다 — 3단계의 Pending과 달리 파드 오브젝트 자체가 만들어지지 않는다. kubectl -n m16 describe quota team-quota로 현재 사용량을 확인할 수 있다.

16.7따라하기 ⑤ 노드를 비운다

노드를 교체하거나 클러스터를 업그레이드하려면 노드를 비워야 한다. 그냥 비우면 그 노드에 있던 파드가 한꺼번에 사라진다. 파드 중단 예산 PodDisruptionBudget은 "이런 작업 중에도 최소 몇 개는 살아 있어야 한다"를 선언해 둔다.

12단계 — PDB를 만든다

목적노드를 비우는 동안 지켜야 할 최소 가용 파드 수를 선언한다.

course/labs/k8s/journal/60-pdb.yaml로 저장하고 kustomization.yaml의 resources에 추가한다.

apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: journal-api
spec:
  minAvailable: 2
  selector:
    matchLabels:
      app: journal-api
kubectl apply -k course/labs/k8s/journal
kubectl -n journal get pdb
출력
NAME MIN AVAILABLE MAX UNAVAILABLE ALLOWED DISRUPTIONS AGE journal-api 2 N/A 1 5s
판정ALLOWED DISRUPTIONS가 1이다. 지금 한 개까지는 비켜 줘도 된다는 뜻이고, 이 값이 0이면 아무것도 못 옮긴다. 16.8 실패 ②가 그 상황이다.

13단계 — 노드를 비운다

목적PDB가 축출을 조절하는 것을 실시간으로 본다.

kubectl drain study-worker --ignore-daemonsets --pod-selector app=journal-api --timeout=120s
옵션뜻
--ignore-daemonsets데몬셋 파드는 어차피 모든 노드에 하나씩 있어야 하므로 옮기지 않는다. 없으면 drain이 거부된다
--pod-selector이 실습에서는 journal-api만 옮긴다. 레디스는 노드 로컬 PVC를 쓰고 있어 옮기면 데이터에 닿지 못한다 — 스테이트풀 워크로드의 drain은 M18에서 다룬다
--timeout이 시간 안에 못 비우면 포기한다. 없으면 무한정 재시도한다
출력 (일부)
node/study-worker cordoned evicting pod journal/journal-api-6486566f5b-n9p4q error when evicting pods/"journal-api-6486566f5b-n9p4q" -n "journal" (will retry after 5s): Cannot evict pod as it would violate the pod's disruption budget. evicting pod journal/journal-api-6486566f5b-n9p4q pod/journal-api-6486566f5b-n9z44 evicted pod/journal-api-6486566f5b-n9p4q evicted node/study-worker drained
판정중간에 Cannot evict pod as it would violate the pod's disruption budget이 한 번 나왔다가 재시도 뒤 성공했다. 이것이 PDB가 제대로 일한 모습이다 — 막은 것이 아니라 기다리게 한 것이다. 첫 파드가 다른 노드에서 Ready가 되고 나서야 두 번째가 비켜났다.

첫 줄의 cordoned는 drain이 가장 먼저 하는 일이다. 노드에 node.kubernetes.io/unschedulable 테인트를 걸어 새 파드가 들어오지 못하게 막는다. 이것을 하지 않으면 방금 쫓아낸 파드가 같은 노드로 되돌아온다.

14단계 — 되돌린다

목적노드를 다시 스케줄 가능하게 만들고, 파드가 자동으로 돌아오지 않는다는 것을 확인한다.

kubectl uncordon study-worker
kubectl -n journal get po -l app=journal-api --no-headers -o custom-columns='N:.spec.nodeName' | sort | uniq -c
출력
node/study-worker uncordoned 3 study-worker2
판정노드는 다시 Ready이고 스케줄도 가능한데 파드 셋은 전부 study-worker2에 남아 있다. topologySpreadConstraints가 있는데도 그렇다 — 16.2에서 말한 대로 스케줄러는 배치 시점에만 관여한다. 균형을 되찾으려면 파드를 새로 만들어야 한다.
kubectl -n journal rollout restart deploy/journal-api
kubectl -n journal rollout status deploy/journal-api
kubectl -n journal get po -l app=journal-api --no-headers -o custom-columns='N:.spec.nodeName' | sort | uniq -c
출력
deployment "journal-api" successfully rolled out 2 study-worker 1 study-worker2
판정2:1로 돌아왔다. 노드 유지보수 뒤에 rollout restart로 균형을 되찾는 것은 실무에서 자주 하는 마무리다.

16.8일부러 실패시키기

실패 ① topologySpreadConstraints를 넣었더니 아무것도 안 뜬다

8단계에서 nodeTaintsPolicy: Honor를 뺀 채로 적용하면 어떻게 되는지 본다. 문서를 보고 그대로 따라 쓰면 대개 이 상태가 된다 — 이 필드는 필수가 아니고 예제에도 잘 나오지 않기 때문이다.

재현 
kubectl -n journal patch deploy journal-api --type=json -p='[
 {"op":"replace","path":"/spec/template/spec/topologySpreadConstraints",
  "value":[{"maxSkew":1,"topologyKey":"kubernetes.io/hostname",
            "whenUnsatisfiable":"DoNotSchedule",
            "labelSelector":{"matchLabels":{"app":"journal-api"}}}]}]'
kubectl -n journal rollout status deploy/journal-api --timeout=60s
출력
Waiting for deployment "journal-api" rollout to finish: 1 out of 3 new replicas have been updated... error: timed out waiting for the condition

롤아웃이 첫 파드에서 멈춘다. 그 파드를 들여다본다.

kubectl -n journal describe pod -l app=journal-api | grep -A3 'Warning  FailedScheduling' | head -4
출력
Warning FailedScheduling 20s (x3 over 3m32s) default-scheduler 0/3 nodes are available: 1 node(s) had untolerated taint(s), 2 node(s) didn't match pod topology spread constraints. preemption: 0/3 nodes are available: 1 Preemption is not helpful for scheduling, 2 No preemption victims found for incoming pod.
원인

didn't match pod topology spread constraints. 노드는 넉넉하고 라벨도 맞는데 분산 제약이 막았다. 이유는 도메인을 세는 방식에 있다. nodeTaintsPolicy의 기본값은 Ignore이고, 이는 톨러레이션이 없어 갈 수도 없는 노드까지 도메인으로 센다는 뜻이다. 컨트롤 플레인을 파드 0개짜리 도메인으로 세면 계산은 이렇게 된다.

도메인현재 파드 수여기에 하나 더 놓으면가장 적은 도메인과의 차이
study-control-plane0 (테인트로 갈 수 없다)——
study-worker344 − 0 = 4 > 1 ✗
study-worker2233 − 0 = 3 > 1 ✗

어디에 놓아도 maxSkew: 1을 어긴다. 균형을 맞출 유일한 방법은 컨트롤 플레인에 놓는 것인데 거기는 테인트가 막는다. 그래서 교착이다. whenUnsatisfiable: ScheduleAnyway였다면 경고 없이 아무 데나 놓였을 것이므로 이 함정은 DoNotSchedule에서만 드러난다.

고친다 
kubectl -n journal patch deploy journal-api --type=json -p='[
 {"op":"add","path":"/spec/template/spec/topologySpreadConstraints/0/nodeTaintsPolicy",
  "value":"Honor"}]'
kubectl -n journal rollout status deploy/journal-api
출력
deployment "journal-api" successfully rolled out
판정Honor를 넣으면 컨트롤 플레인이 도메인 계산에서 빠지고, 워커 둘 사이에서만 균형을 맞추면 되므로 배치가 성립한다. 매니페스트에도 이 필드를 반드시 남긴다 — 이것이 8단계 주석에 그 이유를 적어 둔 까닭이다.

실패 ② PDB를 안전하게 잡았더니 노드를 영원히 못 비운다

레플리카가 3개이니 3개를 다 지키면 가장 안전하겠다고 생각해 minAvailable: 3으로 잡는다.

재현 
kubectl -n journal patch pdb journal-api --type=json \
  -p='[{"op":"replace","path":"/spec/minAvailable","value":3}]'
kubectl -n journal get pdb journal-api
출력
NAME MIN AVAILABLE MAX UNAVAILABLE ALLOWED DISRUPTIONS AGE journal-api 3 N/A 0 33s
kubectl drain study-worker --ignore-daemonsets --pod-selector app=journal-api --timeout=45s
출력 (반복되는 부분을 줄였다)
node/study-worker cordoned evicting pod journal/journal-api-6486566f5b-n9z44 error when evicting pods/"journal-api-6486566f5b-n9z44" -n "journal" (will retry after 5s): Cannot evict pod as it would violate the pod's disruption budget. evicting pod journal/journal-api-6486566f5b-n9z44 error when evicting pods/"journal-api-6486566f5b-n9z44" -n "journal" (will retry after 5s): Cannot evict pod as it would violate the pod's disruption budget. ... There was an error when evicting pods. error: timed out waiting for the condition
원인

ALLOWED DISRUPTIONS가 0이다. 파드가 3개인데 3개를 지키라고 했으니 하나도 옮길 수 없다. 13단계에서는 같은 메시지가 한 번 나왔다가 성공했지만 여기서는 영원히 반복된다. 차이는 예산이 남아 있느냐다.

더 나쁜 점은 노드가 cordoned 상태로 남는다는 것이다. drain은 실패했는데 스케줄 금지는 걸려 있으므로, 알아채지 못하면 그 노드는 계속 새 파드를 못 받는다. 클러스터 업그레이드 스크립트가 이 상태에서 멈춰 있는 것을 발견하는 일이 실제로 흔하다.

고친다 
kubectl -n journal patch pdb journal-api --type=json \
  -p='[{"op":"replace","path":"/spec/minAvailable","value":2}]'
kubectl uncordon study-worker
kubectl -n journal get pdb journal-api
출력
node/study-worker uncordoned NAME MIN AVAILABLE MAX UNAVAILABLE ALLOWED DISRUPTIONS AGE journal-api 2 N/A 1 2m
판정ALLOWED DISRUPTIONS가 1로 바뀌면 노드를 비울 수 있다. PDB는 지킬 값이 아니라 내줄 여유를 선언하는 것이라고 읽는 편이 실수를 줄인다. 레플리카를 늘리지 않은 채 minAvailable만 올리면 안전해지는 것이 아니라 운영이 막힌다.

참고로 PDB는 자발적 중단에만 적용된다. 노드가 갑자기 죽거나 커널이 파드를 축출하는 것은 막지 못한다. 그쪽 대비는 파드를 여러 노드에 펴 두는 것, 즉 8단계의 topologySpreadConstraints다.

실패 ③ 메모리를 넘겨도 OOM이 나지 않는다

M02에서 docker run --memory로 본 종료 코드 137을 쿠버네티스에서 재현한다. 그런데 처음 시도는 실패한다.

재현 
cat <<'EOF' | kubectl -n m16 apply -f -
apiVersion: v1
kind: Pod
metadata: {name: oomtest}
spec:
  restartPolicy: Never
  containers:
    - name: c
      image: node:22-alpine
      resources:
        requests: {cpu: 50m, memory: 64Mi}
        limits: {cpu: 200m, memory: 96Mi}
      command: ["node","-e","const a=[];setInterval(()=>{a.push(Buffer.alloc(8*1024*1024));console.log('할당',a.length*8,'MiB')},200)"]
EOF
kubectl -n m16 get pod oomtest
kubectl -n m16 logs oomtest | tail -2
출력
NAME READY STATUS RESTARTS AGE oomtest 1/1 Running 0 26s 할당 824 MiB 할당 832 MiB

96Mi 제한인데 832 MiB를 "할당"하고도 멀쩡하다. 제한이 안 걸린 것인지부터 확인한다.

kubectl -n m16 exec oomtest -- sh -c 'cat /sys/fs/cgroup/memory.max; cat /sys/fs/cgroup/memory.current'
출력
100663296 13766656
원인

memory.max는 100663296바이트 = 96Mi로 제대로 걸려 있다. 그런데 memory.current는 13MB뿐이다. 832 MiB를 할당했다고 믿었지만 실제로 쓴 메모리는 13MB였다.

커널은 익명 메모리를 요청받으면 주소 공간만 내주고 물리 페이지는 처음 쓰는 순간에 붙인다. Buffer.alloc()은 0으로 채워 주는 API인데, 갓 받아 온 익명 페이지는 이미 0이므로 굳이 쓸 일이 없다. 그래서 물리 페이지가 붙지 않고 cgroup 사용량도 오르지 않는다. 메모리 한계 테스트가 통과했다고 안심하는 흔한 오해가 여기서 나온다.

고친다 — 실제로 페이지를 만진다 
kubectl -n m16 delete pod oomtest

cat <<'EOF' | kubectl -n m16 apply -f -
apiVersion: v1
kind: Pod
metadata: {name: oomtest}
spec:
  restartPolicy: Never
  containers:
    - name: c
      image: node:22-alpine
      resources:
        requests: {cpu: 50m, memory: 64Mi}
        limits: {cpu: 200m, memory: 96Mi}
      # allocUnsafe + fill 로 실제로 페이지를 만진다.
      command: ["node","-e","const a=[];setInterval(()=>{const b=Buffer.allocUnsafe(8*1024*1024);b.fill(1);a.push(b);console.log('touched',a.length*8,'MiB')},200)"]
EOF
kubectl -n m16 get pod oomtest
kubectl -n m16 describe pod oomtest | sed -n '/    State:/,/    Ready:/p'
출력
NAME READY STATUS RESTARTS AGE oomtest 0/1 OOMKilled 0 20s State: Terminated Reason: OOMKilled Exit Code: 137 Started: Sat, 05 Sep 2026 18:50:00 +0900 Finished: Sat, 05 Sep 2026 18:50:02 +0900 Ready: False
판정Reason: OOMKilled, Exit Code: 137. M02에서 docker run --memory=32m으로 본 그 숫자다 — 컨테이너 런타임이 바뀌어도 커널이 하는 일은 같다. 로그의 마지막 줄은 touched 80 MiB였고, 96Mi에 닿기 직전에 죽었다.

restartPolicy: Never가 아니었다면 이 파드는 재시작을 반복하며 CrashLoopBackOff가 된다. M15 실패 ①과 겉모습이 같지만 원인이 다르다 — 그때는 종료 코드가 0이었고 여기서는 137이다. 종료 코드가 진단의 갈림길이다.

16.9운영 관점 — limits를 걸 것인가

8단계의 매니페스트에서 memory에는 limits를 걸었지만 cpu에는 걸지 않았다. 의도적인 비대칭이고, 그 근거는 두 자원의 초과 처리 방식이 다르다는 데 있다.

15단계 — CPU 제한이 무엇을 하는지 본다

목적CPU limit이 죽이지 않고 조인다는 것을 cgroup 수치로 확인한다.

cat <<'EOF' | kubectl -n m16 apply -f -
apiVersion: v1
kind: Pod
metadata: {name: throttled}
spec:
  containers:
    - name: c
      image: node:22-alpine
      resources:
        requests: {cpu: 100m, memory: 64Mi}
        limits: {cpu: 100m, memory: 128Mi}   # 0.1 코어 = 100ms 주기마다 10ms
      command: ["node","-e","let n=0;const t=Date.now();while(Date.now()-t<60000){n++};console.log(n)"]
EOF
kubectl -n m16 exec throttled -- cat /sys/fs/cgroup/cpu.max
kubectl -n m16 exec throttled -- cat /sys/fs/cgroup/cpu.stat | head -6
kubectl top pod throttled -n m16
출력
10000 100000 usage_usec 1971540 user_usec 1927173 system_usec 44366 nice_usec 0 nr_periods 197 nr_throttled 197 NAME CPU(cores) MEMORY(bytes) throttled 100m 10Mi
판정cpu.max의 10000 100000은 100ms 주기마다 10ms만 쓸 수 있다는 뜻이고, 그것이 limits.cpu: 100m의 실체다. nr_periods 197 중 nr_throttled 197 — 모든 주기에서 조여졌다. 이 프로세스는 한 코어를 다 쓰려 했지만 매번 10ms 만에 멈춰 다음 주기를 기다렸다. 파드는 죽지 않았고 kubectl top은 정확히 100m을 보고한다 — 겉으로는 아무 문제가 없어 보인다.

여기가 CPU limit의 함정이다. 증상이 지표에 드러나지 않는다. 파드는 Running이고 재시작도 없고 CPU 사용률은 한도에 딱 붙어 "잘 쓰고 있는 것"처럼 보인다. 실제로는 응답 시간이 길어지고 있는데, 그것을 알려면 nr_throttled를 봐야 하고 그러려면 메트릭 수집이 필요하다. M19에서 세우는 프로메테우스가 이 값을 container_cpu_cfs_throttled_seconds_total로 수집하고, M37에서 부하를 걸며 스로틀링과 응답 시간의 관계를 잰다.

그래서 이 교재는 메모리에는 limit을 걸고 CPU에는 걸지 않는 쪽을 기본으로 삼는다. 메모리는 압축할 수 없어 상한이 없으면 노드 전체를 위협하지만, CPU는 남는 것을 나눠 쓰게 두는 편이 낫다. 다만 이것이 모든 상황의 정답은 아니다.

상황선택근거
일반 웹 애플리케이션cpu limit 없음, memory limit 있음여유가 있을 때 더 빨리 응답하는 편이 낫다. 메모리 누수는 노드를 위협한다
지연에 민감한 서비스Guaranteed (requests == limits)다른 파드의 변동에 영향받지 않는 대신, 남는 자원을 못 쓴다
배치·크론 작업cpu limit 있음야간 배치가 온라인 서비스의 CPU를 다 먹는 것을 막는다
여러 팀이 공유하는 클러스터네임스페이스 쿼터 + LimitRange파드별 판단에 맡기면 결국 누군가 다 먹는다

마지막으로 값을 정하는 방법이다. requests는 평상시 사용량에 여유를 얹어 잡고, limits는 정상 범위의 최대치에 잡는다. 둘 다 짐작이 아니라 실측이어야 하는데, 지금은 kubectl top이 보여 주는 순간값뿐이라 근거가 약하다. 시간에 걸친 분포(평균이 아니라 P95·P99)를 보려면 메트릭을 저장해야 하고, 그것이 Part 4에서 관측 스택을 세우는 이유 중 하나다.
