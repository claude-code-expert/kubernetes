컨피그맵과 시크릿

같은 값을 환경 변수와 볼륨 두 방식으로 주입하고, 값을 바꾼 뒤 70초를 기다린다. 한쪽만 바뀐다. 그리고 시크릿을 base64 -d 한 줄로 열어보며 "시크릿은 암호화가 아니다"를 확인한다.

초반→중반50분Kubernetes 1.37.0
2026-09-05 검증 · kind v0.33.0 · 버전은 실습 당일 다시 확인한다
사전 조건
  • M12 완료 — default 네임스페이스에 journal-api(파드 4개) · web-static · 인그레스 journal이 있고 curl -H 'Host: journal.local' http://localhost:18080/api/entries가 200을 돌려준다. 이 모듈의 실습은 별도의 config-demo 파드로 하며 M12가 남긴 것을 직접 건드리지는 않는다. M12의 산출물은 M14가 journal 네임스페이스로 한꺼번에 옮긴다
  • 매니페스트: course/labs/k8s/m13-config.yaml · m13-missing-key.yaml

핵심 3줄

1. 환경 변수는 시작할 때 고정된다. 컨피그맵을 바꿔도 파드를 다시 시작하기 전까지 옛 값을 본다.

2. 볼륨 마운트는 갱신된다. 대신 반영에 1분 안팎이 걸리고, 애플리케이션이 파일을 다시 읽어야 한다.

3. 시크릿은 base64로 인코딩될 뿐이다. 실제 보호는 etcd 암호화 · RBAC · 외부 시크릿 저장소가 한다.

13.1왜 설정을 밖으로 빼는가

M12까지 클러스터에는 저널 API 파드 4개, 정적 파일 서버, 그 앞의 인그레스가 있다. 밖에서 들어오는 길은 정리됐다. 그런데 안에서 앱이 읽는 값은 어디에 있나 — m10-journal-deployment.yaml의 env에 APP_VERSION: "v1" 한 줄이 박혀 있는 것이 전부다.

M14에서 이 API 뒤에 레디스를 붙인다. 그러면 레디스 주소와 비밀번호가 필요한데, 지금 방식대로 디플로이먼트의 env에 value:로 적으면 비밀번호가 매니페스트에, 그러니까 깃에 올라간다. 로그 레벨 하나를 바꾸려고 디플로이먼트 파일을 고쳐 다시 apply하는 것도 어색하다. 값과 워크로드 정의가 한 파일에 있으면 둘 중 하나만 바꾸는 일이 항상 다른 쪽을 건드린다.

M04에서 만든 이미지가 설정을 하나도 품지 않고 전부 환경 변수로 받도록 만든 것은 이 순간을 위한 설계였다. 설정을 이미지에 넣으면 환경마다 이미지를 따로 빌드해야 하고, 개발용 이미지와 운영용 이미지가 다르면 운영에서 처음 실행되는 코드가 생긴다. 책 5.6이 "불변 이미지를 환경 사이로 승격시킨다"고 말하는 이유다 — 같은 이미지를 개발 → 스테이징 → 운영으로 그대로 옮기고, 바뀌는 것은 주입하는 설정뿐이어야 한다. 그 설정을 담는 그릇이 이 모듈의 두 오브젝트다.

컨피그맵 (ConfigMap)은 키-값 쌍을 담는 네임스페이스 오브젝트로, 파드가 환경 변수나 파일로 읽어 간다(책 1.5). 시크릿 (Secret)은 같은 모양이지만 비밀번호 · 토큰 · 인증서처럼 노출되면 안 되는 값을 위한 것이고, 저장 형태와 kubelet의 취급이 조금 다르다(책 1.6). 둘의 차이는 표 한 장이면 된다.

ConfigMapSecret
담는 것공개돼도 되는 설정 — 로그 레벨, 기능 플래그, 엔드포인트 주소비밀번호, API 키, 인증서, 토큰
저장 형태평문base64 (암호화 아님)
크기 제한둘 다 1MiB. 큰 파일은 볼륨이나 오브젝트 스토리지로
다른 점—기본적으로 kubelet이 디스크에 쓰지 않고 tmpfs에 둔다. RBAC로 따로 제한하는 것이 관례

13.2따라하기 ① 두 가지 주입 방식

1단계. 한 파드에 두 방식을 함께 넣는다

목적차이를 비교하려면 같은 값을 두 경로로 넣어야 한다.

# course/labs/k8s/m13-config.yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: journal-config
data:
  APP_GREETING: "hello from configmap v1"
  app.properties: |
    greeting=hello from configmap v1
    log.level=info
---
apiVersion: v1
kind: Secret
metadata:
  name: journal-secret
type: Opaque
stringData:                      # stringData 에 평문을 적으면 저장 시 base64 로 인코딩된다
  REDIS_PASSWORD: "s3cr3t-pass"
---
apiVersion: v1
kind: Pod
metadata:
  name: config-demo
spec:
  containers:
    - name: app
      image: alpine:3.22
      command: ["sh", "-c", "while true; do sleep 5; done"]
      env:
        - name: APP_GREETING                # ① 환경 변수로 주입 — 시작 시점에 고정
          valueFrom:
            configMapKeyRef:
              name: journal-config
              key: APP_GREETING
        - name: REDIS_PASSWORD
          valueFrom:
            secretKeyRef:
              name: journal-secret
              key: REDIS_PASSWORD
      volumeMounts:
        - name: config                      # ② 볼륨으로 주입 — 갱신이 반영된다
          mountPath: /etc/journal
          readOnly: true
  volumes:
    - name: config
      configMap:
        name: journal-config

stringData와 data의 차이를 짚는다. data에는 이미 base64로 인코딩한 값을 적어야 하고, stringData에는 평문을 적으면 apiserver가 인코딩해준다. 손으로 쓸 때는 stringData가 실수가 적다. 비밀번호에 @나 :를 넣지 않은 것에도 이유가 있다 — M14에서 이 값이 redis://default:비밀번호@호스트:6379 형태의 URL 안에 들어가는데, URL 구분 문자가 비밀번호에 섞이면 클라이언트마다 다르게 해석한다.

kubectl apply -f course/labs/k8s/m13-config.yaml
kubectl wait --for=condition=Ready pod/config-demo --timeout=60s
kubectl exec config-demo -- printenv APP_GREETING REDIS_PASSWORD
실행 결과
pod/config-demo condition met hello from configmap v1 s3cr3t-pass
판정두 값이 환경 변수로 들어왔다. 그리고 지금 비밀번호가 터미널에 평문으로 찍혔다 — 13.5 실패 ③이 말하는 유출이 이미 한 번 일어난 것이다.

2단계. 볼륨 쪽을 들여다본다

목적컨피그맵의 키가 파일 시스템에서 어떤 모양으로 나타나는지 본다.

kubectl exec config-demo -- ls -l /etc/journal
kubectl exec config-demo -- cat /etc/journal/app.properties
실행 결과 — 날짜·시각은 환경마다 다르다
total 0 lrwxrwxrwx 1 root root 19 Sep 5 08:26 APP_GREETING -> ..data/APP_GREETING lrwxrwxrwx 1 root root 21 Sep 5 08:26 app.properties -> ..data/app.properties greeting=hello from configmap v1 log.level=info
판정키 하나가 파일 하나다. 그리고 파일이 아니라 심볼릭 링크(lrwxrwxrwx, -> ..data/)다.

갱신할 때 새 디렉터리를 만들고 ..data 링크를 통째로 바꾸는 방식이라, 애플리케이션이 파일을 반쯤 읽은 상태에서 내용이 바뀌는 일이 없다(원자적 교체). 여러 줄 값은 그대로 파일 내용이 된다.

13.3따라하기 ② 값을 바꿔본다

3단계. 컨피그맵을 수정하고 즉시 확인한다

목적두 주입 경로가 갱신에 어떻게 반응하는지 시간차를 두고 관찰한다. 먼저 바꾼 직후를 본다.

kubectl patch configmap journal-config --type merge -p \
  '{"data":{"APP_GREETING":"hello from configmap v2","app.properties":"greeting=hello from configmap v2\nlog.level=debug\n"}}'

kubectl exec config-demo -- printenv APP_GREETING
kubectl exec config-demo -- cat /etc/journal/app.properties
실행 결과 — 수정 직후
configmap/journal-config patched hello from configmap v1 greeting=hello from configmap v1 log.level=info
판정둘 다 옛 값이다. 볼륨 쪽도 아직 안 바뀌었다 — kubelet이 주기적으로 확인해 갱신하기 때문에 시간이 걸린다.

4단계. 70초 뒤에 다시 본다

목적kubelet 동기화 주기가 지난 뒤 어느 쪽이 바뀌었는지 판정한다.

sleep 70
kubectl exec config-demo -- printenv APP_GREETING
kubectl exec config-demo -- cat /etc/journal/app.properties
실행 결과
hello from configmap v1 greeting=hello from configmap v2 log.level=debug
판정볼륨은 v2로 바뀌었고, 환경 변수는 여전히 v1이다. 컨테이너의 환경 변수는 프로세스가 시작될 때 커널이 전달하는 것이라 나중에 바꿀 방법이 없다.

실무 규칙은 여기서 그대로 따라 나온다. 환경 변수로 주입한 설정을 바꿨으면 파드를 다시 만들어야 하고, 그 명령은 kubectl rollout restart deploy/<이름>이다. 반대로 런타임에 바뀌어야 하는 값 — 로그 레벨, 기능 플래그 — 은 볼륨으로 주입하고 애플리케이션이 파일 변경을 감지해 다시 읽도록 만든다. 다만 볼륨도 즉시 반영되지 않는다는 것을 방금 봤다. 기본 kubelet 동기화 주기 1분에 캐시 지연이 더해지므로, "설정을 바꿨는데 왜 안 되지"의 절반은 아직 안 온 것이다.

컨피그맵이 바뀌면 자동으로 롤아웃하고 싶다면 쿠버네티스에는 그 기능이 없다. 실무에서는 컨피그맵 내용의 해시를 파드 템플릿의 어노테이션에 넣어 내용이 바뀌면 템플릿이 바뀌게 만든다. Helm에서는 checksum/config 어노테이션 패턴, Kustomize에서는 configMapGenerator가 이름에 해시를 붙여 같은 효과를 낸다. 둘 다 M14에서 실제로 쓴다. 이 방법의 장점은 롤아웃 이력이 남고 롤백이 가능하다는 것이다.

13.4따라하기 ③ 시크릿을 열어본다

5단계. 저장된 값을 확인한다

목적시크릿이 클러스터에 어떤 형태로 저장되는지, 그것을 되돌리는 데 무엇이 필요한지 본다.

kubectl get secret journal-secret -o jsonpath='{.data.REDIS_PASSWORD}'; echo
kubectl get secret journal-secret -o jsonpath='{.data.REDIS_PASSWORD}' | base64 -d; echo
실행 결과
czNjcjN0LXBhc3M= s3cr3t-pass
판정명령 한 줄로 평문이 나온다. base64는 암호화가 아니라 인코딩이다 — 바이너리 값을 안전하게 실어 나르기 위한 것이지 감추기 위한 것이 아니다.

그러면 무엇이 시크릿을 보호하나. 답은 이 명령을 칠 수 있는 사람이 누구인가이다. 시크릿 읽기 권한은 RBAC로 제한되고(M23), 그 권한이 있는 사람에게는 처음부터 평문이나 마찬가지다.

6단계. 예상 못 한 곳에 평문이 남는다

목적kubectl apply가 남기는 흔적을 확인한다. 실무에서 자주 놓치는 지점이다.

kubectl get secret journal-secret -o yaml | head -12
실행 결과 — 7번째 줄의 JSON 은 실제로 한 줄이다(가로로 스크롤된다). 타임스탬프와 resourceVersion 은 환경마다 다르다
apiVersion: v1 data: REDIS_PASSWORD: czNjcjN0LXBhc3M= kind: Secret metadata: annotations: kubectl.kubernetes.io/last-applied-configuration: | {"apiVersion":"v1","kind":"Secret","metadata":{"annotations":{},"name":"journal-secret","namespace":"default"},"stringData":{"REDIS_PASSWORD":"s3cr3t-pass"},"type":"Opaque"} creationTimestamp: "2026-09-03T13:23:42Z" name: journal-secret namespace: default resourceVersion: "350913"
판정어노테이션 안에 평문 비밀번호가 그대로 들어 있다("stringData":{"REDIS_PASSWORD":"s3cr3t-pass"}). stringData로 쓴 매니페스트를 kubectl apply가 통째로 기록했기 때문이다.

영향이 작지 않다. 클러스터 백업, kubectl get -o yaml 출력을 붙여넣은 이슈, 오브젝트를 덤프하는 모니터링 도구 어디에나 평문이 따라간다. 피하는 방법이 몇 가지 있다.

  • 시크릿은 kubectl apply 대신 kubectl create secret이나 서버 사이드 적용(--server-side)으로 만든다
  • 애초에 매니페스트에 평문을 두지 않는다 — SOPS로 암호화해 커밋하거나(M31), External Secrets로 외부 저장소에서 가져온다
  • 이미 남았다면 어노테이션을 지운다: kubectl annotate secret journal-secret kubectl.kubernetes.io/last-applied-configuration-

13.5일부러 실패시키기

실패 ① — 없는 키를 참조한다

컨피그맵에 없는 키를 configMapKeyRef로 가리키는 파드를 하나 만든다.

# course/labs/k8s/m13-missing-key.yaml
apiVersion: v1
kind: Pod
metadata:
  name: missing-key
spec:
  containers:
    - name: app
      image: alpine:3.22
      command: ["sh", "-c", "while true; do sleep 5; done"]
      env:
        - name: NOPE
          valueFrom:
            configMapKeyRef:
              name: journal-config
              key: NOT_THERE            # 이 키는 없다
kubectl apply -f course/labs/k8s/m13-missing-key.yaml
sleep 10
kubectl get pod missing-key
kubectl describe pod missing-key | sed -n '/Events:/,$p'
실행 결과 — 노드 이름과 Age 는 환경마다 다르다
pod/missing-key created NAME READY STATUS RESTARTS AGE missing-key 0/1 CreateContainerConfigError 0 12s Events: Type Reason Age From Message ---- ------ ---- ---- ------- Normal Scheduled 12s default-scheduler Successfully assigned default/missing-key to study-worker2 Normal Pulled 11s (x2 over 12s) kubelet spec.containers{app}: Container image "alpine:3.22" already present on machine and can be accessed by the pod Warning Failed 11s (x2 over 12s) kubelet spec.containers{app}: Error: couldn't find key NOT_THERE in ConfigMap default/journal-config
판정STATUS가 CreateContainerConfigError, 그리고 이벤트의 마지막 줄이 원인을 그대로 말한다 — couldn't find key NOT_THERE in ConfigMap default/journal-config. 어느 네임스페이스의 어느 컨피그맵에서 어느 키를 찾았는지까지 적혀 있다.

CreateContainerConfigError는 컨테이너를 만들기 전 단계에서 실패했다는 뜻이다. 이미지 문제(ErrImagePull)도, 애플리케이션 문제(CrashLoopBackOff)도 아니다 — 주입할 설정을 못 찾은 것이다. 이벤트의 Pulled 줄이 그 증거다: 이미지는 이미 노드에 있고, 그 다음 단계에서 막혔다. 원인은 셋 중 하나다.

  • 컨피그맵/시크릿 이름이 틀렸다
  • 키 이름이 틀렸다 (이 경우 — 메시지의 couldn't find key)
  • 같은 네임스페이스에 없다 — 컨피그맵과 시크릿은 네임스페이스를 넘지 못한다. 이때는 메시지가 configmap "..." not found가 된다

키가 없어도 파드가 뜨게 하려면 optional: true를 준다. 다만 그러면 값이 없는 채로 실행되므로, 애플리케이션이 그 상황을 처리할 수 있어야 한다. 이 파드는 고치지 않고 13.7에서 지운다.

실패 ② — 불변 컨피그맵을 수정한다

불변 컨피그맵 (immutable ConfigMap)은 immutable: true를 켠 컨피그맵이다. 켠 뒤에는 data도, 그 플래그 자체도 바꿀 수 없다. 직접 확인한다.

kubectl create configmap frozen --from-literal=key=v1
kubectl patch configmap frozen -p '{"immutable":true}'
kubectl patch configmap frozen --type merge -p '{"data":{"key":"v2"}}'
kubectl patch configmap frozen -p '{"immutable":false}'
실행 결과
configmap/frozen created configmap/frozen patched The ConfigMap "frozen" is invalid: data: Forbidden: field is immutable when `immutable` is set The ConfigMap "frozen" is invalid: immutable: Forbidden: field is immutable when `immutable` is set
판정세 번째 명령이 data: Forbidden으로 거부되고, 플래그를 되돌리려는 네 번째 명령도 immutable: Forbidden으로 거부된다. 한 번 잠그면 지우고 다시 만드는 것 외에 길이 없다.

왜 일부러 못 바꾸게 만드나. 두 가지 이유다. 실수로 운영 설정을 바꾸는 사고를 막고, 클러스터 성능을 개선한다 — 불변으로 표시된 컨피그맵은 kubelet이 변경을 감시하지 않아 apiserver 부하가 줄어든다. 파드 수가 많은 클러스터에서 의미 있는 차이다.

불변 컨피그맵을 바꾸려면 새 이름으로 만들고 파드가 그것을 보게 해야 한다. 이것이 불편해 보이지만, 사실은 13.3절의 "내용이 바뀌면 새 리소스를 만든다"는 패턴과 같고 롤백도 쉬워진다.

실패 ③ — 시크릿을 로그에 흘린다 (재현하지 않는다 — 서술)

이 실패는 일부러 만들지 않는다. 한 번 흘린 값은 회수할 수 없기 때문이다. 대신 이미 일어난 것을 짚는다 — 1단계의 printenv REDIS_PASSWORD가 비밀번호를 터미널에 찍었고, 그 터미널의 스크롤백과 셸 히스토리에 남아 있다. 코드에서 console.log(process.env) 한 줄이면 같은 일이 매 요청마다 일어나고, 그 로그는 M22에서 만들 로그 수집 파이프라인을 타고 저장소로 가서 보존 기간 동안 검색 가능한 상태로 남는다.

이런 종류의 유출은 되돌릴 수 없다 — 로그를 지우는 것보다 비밀번호를 교체하는 것이 정답이다. 그래서 시크릿에는 회전(rotation) 계획이 필요하고, 회전이 쉬우려면 애초에 코드가 아니라 외부 저장소에서 값을 받아야 한다(13.6절).

13.6시크릿을 실제로 보호하는 방법

13.4절에서 확인한 대로 Secret 오브젝트 자체는 보호 장치가 아니다. 실제 보호는 층으로 쌓는다.

층하는 일이 과정에서
RBAC누가 시크릿을 읽을 수 있는지 제한한다. 가장 기본이고 가장 자주 빠뜨린다M23
etcd 저장 시 암호화apiserver가 etcd에 쓸 때 암호화한다. 안 켜면 etcd 백업 파일에 평문이 남는다M27

마지막 항목이 방향을 보여준다. 가장 안전한 시크릿은 존재하지 않는 시크릿이다. 데이터베이스 비밀번호 대신 IAM 인증을, API 키 대신 짧은 수명의 토큰을 쓰는 쪽으로 가는 것이 최근 흐름이다.

13.7체크포인트와 정리

다음 모듈로 넘어가기 전 확인
  • kubectl exec config-demo -- printenv APP_GREETING → hello from configmap v1 (3단계에서 v2로 바꿨는데도)
  • kubectl exec config-demo -- cat /etc/journal/app.properties → greeting=hello from configmap v2 와 log.level=debug
  • kubectl exec config-demo -- ls -l /etc/journal | grep -c -- '-> ..data/' → 2
  • kubectl get secret journal-secret -o jsonpath='{.data.REDIS_PASSWORD}' | base64 -d; echo → s3cr3t-pass
  • kubectl get secret journal-secret -o jsonpath='{.metadata.annotations.kubectl\.kubernetes\.io/last-applied-configuration}' | grep -o 's3cr3t-pass' → s3cr3t-pass (어노테이션 안의 평문)
  • kubectl get pod missing-key -o jsonpath='{.status.containerStatuses[0].state.waiting.reason}{"\n"}' → CreateContainerConfigError
  • kubectl patch configmap frozen --type merge -p '{"data":{"key":"v3"}}' → Forbidden: field is immutable when `immutable` is set
  • (이해 확인) CreateContainerConfigError를 보면 확인할 세 가지 — 이름 · 키 · 네임스페이스 — 를 말하고, 이벤트 메시지에서 셋 중 어느 것인지 가려낸다
  • (이해 확인) 시크릿 보호가 왜 한 층으로 끝나지 않는지, 13.6의 표에서 두 층을 골라 각각 무엇을 막는지 말한다
