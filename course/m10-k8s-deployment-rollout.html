디플로이먼트와 롤아웃

버전을 바꾸는 동안 서비스가 끊기지 않는지 실제로 측정한다. 40초 동안 11,754건 성공, 17건 실패 — 무중단 설정을 했는데도 0이 아니었다. 그 17건이 어디서 왔는지가 이 모듈의 핵심이다.

초반→중반60분Kubernetes 1.37.0
2026-09-05 검증 · journal-api:v1 · v2 · 버전 숫자는 실습 당일 kubectl version으로 다시 확인한다
사전 조건
  • M09 완료 — kubectl apply -f로 매니페스트를 적용하고 -l로 골라낼 수 있다. 9.5절 7단계에서 컨텍스트 네임스페이스를 default로 되돌렸다
  • journal-api:v1과 journal-api:v2 이미지가 kind 노드에 적재돼 있다 (M07 산출물. 10.3절 1단계에서 확인하고, 없으면 그 자리에서 만든다)
  • 매니페스트: course/labs/k8s/m10-journal-deployment.yaml

핵심 3줄

1. 디플로이먼트는 버전마다 레플리카셋을 하나씩 만든다. 롤아웃은 새 레플리카셋을 늘리고 옛 것을 줄이는 일이다.

2. maxSurge와 maxUnavailable이 교체 속도와 안전 마진을 정한다. maxUnavailable: 0이면 용량이 줄지 않는다.

3. 그래도 요청이 몇 건 실패한다. 파드가 종료될 때 엔드포인트에서 빠지는 것과 실제로 죽는 것이 동시에 일어나지 않기 때문이다 — M15에서 해결한다.

10.1왜 파드 YAML만으로는 안 되는가 10.2이론 — 롤아웃은 무엇을 하는가 10.3따라하기 ① 무중단 측정 10.4따라하기 ② 이력과 되돌리기 10.5일부러 실패시키기 10.6남은 17건의 정체 10.7체크포인트와 정리

10.1왜 파드 YAML만으로는 안 되는가

M09에서 파드 매니페스트를 직접 써서 apply했다. 컨테이너 둘을 한 파드에 넣고 init 컨테이너로 순서까지 강제했으니 파드 하나를 정의하는 일은 끝났다. 그런데 그 파드의 journal-api:v1을 v2로 바꾸려면 어떻게 하나.

파드의 spec.containers[].image는 만든 뒤에도 바꿀 수 있는 몇 안 되는 필드다. 하지만 바꾸는 순간 kubelet이 그 컨테이너를 그 자리에서 죽이고 새 이미지로 다시 띄운다 — 그 사이 요청은 받을 수 없다. 파드가 여럿이면 하나씩 손으로 바꿔야 하고, 잘못됐을 때 되돌리는 방법은 다시 손으로 v1을 적는 것뿐이다. 무엇을 언제 바꿨는지는 어디에도 남지 않는다. 그리고 M08 실패 ①에서 봤듯, 직접 만든 파드는 노드가 죽으면 돌아오지 않는다.

필요한 것은 "이 템플릿의 파드를 N개 유지하고, 템플릿이 바뀌면 순서대로 교체하고, 바뀐 이력을 기억하는" 오브젝트다. M08에서 명령 한 줄로 만들었던 디플로이먼트가 그것이고, 이 모듈에서는 그것을 파일로 쓰고 버전을 바꿔 본다. 한 가지를 더 한다 — "무중단"이라는 말을 믿지 않고, 교체가 진행되는 동안 요청을 계속 보내 실패 건수를 센다.

10.2이론 — 롤아웃은 무엇을 하는가

M08에서 디플로이먼트가 레플리카셋을 만들고, 레플리카셋이 파드를 만든다고 했다. 왜 두 겹인지는 버전을 바꿔볼 때 드러난다. 책 1.3.2가 디플로이먼트 오브젝트의 정의를, 6.3이 롤아웃 절차를 다룬다.

디플로이먼트의 파드 템플릿이 바뀌면(이미지·환경변수·리소스 등) 그 템플릿의 해시가 달라지고, 디플로이먼트는 새 해시의 레플리카셋을 새로 만든다. 그리고 새 레플리카셋의 개수를 늘리면서 옛 레플리카셋의 개수를 줄인다. 이 교체 과정 전체가 롤아웃 (Rollout)이고, 한 번에 전부가 아니라 몇 개씩 늘리고 줄이는 방식이 롤링 업데이트 (Rolling Update)다. 템플릿이 바뀔 때마다 번호가 하나 올라가는 것이 리비전 (Revision)이며, 레플리카셋 하나가 리비전 하나에 대응한다. 다 끝나면 옛 레플리카셋은 0개인 채로 남는다 — 이것이 롤백의 재료다.

파라미터의미기본값
maxSurge목표 개수보다 더 만들 수 있는 파드 수(또는 %)25%
maxUnavailable사용 불가 상태를 허용할 파드 수(또는 %)25%

둘의 조합이 성격을 정한다. maxUnavailable: 0에 maxSurge: 1이면 용량을 절대 줄이지 않는다 — 새 파드가 준비된 뒤에야 옛 파드를 빼므로 느리지만 안전하고, 대신 노드에 파드 하나 분량의 여유가 있어야 한다. 기본값인 25% / 25%는 빠르지만 롤아웃 중 용량이 최대 25% 줄어들어, 부하가 높은 시간대에는 남은 파드가 몰린 트래픽을 감당해야 한다. maxSurge: 0은 추가 파드를 만들지 않으므로 클러스터에 여유가 없을 때 쓰지만 반드시 용량이 줄어든다. 이 모듈의 매니페스트는 첫 번째 조합을 쓴다.

여기서 레디니스 프로브가 전제 조건이라는 점이 중요하다. "새 파드가 준비됐다"를 판단할 방법이 없으면 쿠버네티스는 컨테이너가 시작된 것만으로 준비됐다고 보고 옛 파드를 뺀다. 애플리케이션이 아직 초기화 중이면 그 순간 요청이 실패한다. 책 5.7이 롤링 업데이트의 필수 장치로 레디니스 프로브와 preStop 훅 두 가지를 꼽는 이유다. 레디니스 프로브와 서비스의 엔드포인트 목록은 이 모듈에서 "준비된 파드만 트래픽을 받게 하는 장치"로만 쓴다 — 프로브의 종류와 임계값은 M15에서, 엔드포인트가 어떻게 갱신되는지는 M11에서 제대로 다룬다.

매니페스트

M08 8.7절의 뼈대에 롤아웃 전략과 레디니스 프로브를 채운 것이다. 주석이 붙은 줄이 이 모듈에서 건드리는 부분이다.

# course/labs/k8s/m10-journal-deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: journal-api
  labels:
    app: journal-api
spec:
  replicas: 4
  selector:
    matchLabels:
      app: journal-api          # 이 셀렉터가 아래 template.labels 와 같아야 한다
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1               # 목표 개수보다 최대 1개 더 만들 수 있다
      maxUnavailable: 0         # 사용 불가 파드는 0개 — 무중단
  template:
    metadata:
      labels:
        app: journal-api
    spec:
      containers:
        - name: api
          image: journal-api:v1
          imagePullPolicy: IfNotPresent
          ports:
            - containerPort: 8080
          env:
            - name: APP_VERSION
              value: "v1"
          readinessProbe:       # 준비되기 전에는 트래픽을 받지 않는다 (M15에서 자세히)
            httpGet:
              path: /readyz
              port: 8080
            periodSeconds: 2
selector 와 template.labels 는 반드시 일치해야 한다 spec.selector.matchLabels는 "내가 관리할 파드"의 조건이고, spec.template.metadata.labels는 "내가 만들 파드"에 붙일 꼬리표다. 둘이 어긋나면 만든 파드를 자기 것으로 인식하지 못해 무한히 파드를 만든다. 1.16부터는 apiserver가 이 불일치를 거부하지만, 셀렉터는 생성 후 변경이 불가능하다는 제약이 남아 있다 — 레이블 체계를 처음에 잘 정해야 하는 이유(M09).

10.3따라하기 ① 무중단 측정

1단계. 버전이 다른 이미지 두 개를 만든다

목적롤아웃을 관찰하려면 구분되는 버전이 필요하다. M07에서 v1·v2를 이미 적재했다면 이 단계는 확인만 하면 된다.

M04의 Dockerfile 마지막 스테이지에는 버전을 새기는 두 줄이 들어 있다. 빌드 인자 하나로 같은 소스에서 다른 버전의 이미지를 만드는 장치이며, M10은 그것을 이용해 v2를 굽는다.

# course/labs/apps/journal-api/Dockerfile 마지막 스테이지 (M04에서 넣어 둔 것)
ARG APP_VERSION=v1
ENV NODE_ENV=production APP_VERSION=${APP_VERSION}
cd course/labs/apps/journal-api
docker build --build-arg APP_VERSION=v1 -t journal-api:v1 .
docker build --build-arg APP_VERSION=v2 -t journal-api:v2 .
docker run --rm journal-api:v2 node -e "console.log(process.env.APP_VERSION)"

v2
kind load docker-image journal-api:v1 journal-api:v2 --name study

판정노드 3개 × 이미지 2개 = 6줄. M07에서 적재한 것과 이미지 ID가 같으면 그 이미지는 found to be already present on all nodes. 한 줄로 끝난다. 방금 다시 빌드했다면 ID가 달라져 위처럼 다시 적재된다. ID 값은 환경마다 다르다(여기서는 줄여 적었다).

ARG는 빌드 중에만 존재하고, ENV로 옮겨야 실행 시점에 남는다. 이 방식으로 커밋 해시나 빌드 번호를 이미지에 새기면 나중에 "이 파드가 어느 커밋인가"를 이미지에 물어볼 수 있다(M29).

판정READY 4/4, 레플리카셋 해시가 55c87ff598. 이 해시는 파드 템플릿에서 계산되므로 같은 버전의 클러스터에서 같은 매니페스트를 쓰면 같은 값이 나온다 — 이 문서와 M11의 출력에서 55c87ff598은 v1 템플릿을 뜻한다. 파드 4행 중 뒤 2행은 ...로 줄였다. 파드 이름 뒤 다섯 글자는 환경마다 다르다.

측정하려면 클러스터 안에서 계속 요청을 보낼 무언가가 필요하다. 서비스와 요청용 파드를 만든다. 서비스는 M11의 주제지만 여기서는 "파드들 앞에 놓는 안정적인 이름" 정도로만 쓴다.

kubectl expose deploy journal-api --port=8080 --name=journal-api
kubectl run curlbox --image=alpine:3.22 --restart=Never -- sh -c "sleep infinity"
sleep 5
kubectl exec curlbox -- apk add --no-cache curl
  • expose — 디플로이먼트의 셀렉터를 그대로 가져와 서비스를 만든다. M11에서 파일로 다시 쓴다
  • --restart=Never — 디플로이먼트 없이 파드 하나만 만든다. 디버깅용 도구 파드는 이렇게 만든다(M08 실패 ①에서 말한 예외)
  • sleep infinity — 이 파드는 M11까지 살아 있어야 한다. sleep 3600으로 두면 60분 뒤 Completed로 끝나 다음 모듈에서 exec가 실패한다

3단계. 부하를 걸어둔 채 롤아웃한다

목적"무중단"을 말이 아니라 숫자로 확인한다.

# 터미널 1 — 40초 동안 계속 요청하며 성공/실패를 센다
kubectl exec curlbox -- sh -c 'ok=0; err=0; end=$(( $(date +%s) + 40 ));
  while [ $(date +%s) -lt $end ]; do
    if curl -sf -m 2 http://journal-api:8080/healthz >/dev/null; then ok=$((ok+1)); else err=$((err+1)); fi
  done; echo "성공=$ok 실패=$err"'

# 터미널 2 — 부하가 도는 동안 이미지를 교체한다
kubectl set image deploy/journal-api api=journal-api:v2
kubectl rollout status deploy/journal-api

판정실패율 0.14%. 0이 아니다. maxUnavailable: 0에 레디니스 프로브까지 붙였는데도 17건이 실패했다. 원인은 10.6절에서 다룬다 — 이 숫자가 M15의 출발점이다.

10.4따라하기 ② 이력과 되돌리기

4단계. 레플리카셋이 남아 있는 것을 확인한다

목적롤아웃이 "새 레플리카셋을 늘리고 옛 것을 줄이는 일"이라는 10.2절의 설명을 오브젝트로 확인한다.

kubectl get rs -l app=journal-api
실행 결과
NAME DESIRED CURRENT READY AGE journal-api-55c87ff598 0 0 0 41s journal-api-975dd69b9 4 4 4 4s
판정레플리카셋 2개. v1(55c87ff598)은 0 0 0, v2(975dd69b9)는 4 4 4. AGE는 환경마다 다르다.

옛 레플리카셋이 0개로 남아 있다. 파드는 없지만 정의는 보존된다 — 되돌릴 때 이 정의를 다시 4개로 늘리기만 하면 된다. 몇 개까지 보관할지는 revisionHistoryLimit(기본 10)가 정한다.

5단계. 이력을 본다

목적리비전 번호와 레플리카셋의 대응을 확인하고, 이력에 사유를 남기는 방법과 그 한계를 본다.

kubectl rollout history deploy/journal-api
실행 결과
deployment.apps/journal-api REVISION CHANGE-CAUSE 1 <none> 2 <none>

CHANGE-CAUSE가 비어 있다. 무엇을 왜 바꿨는지 클러스터는 모른다. 어노테이션으로 남길 수 있다.

kubectl annotate deploy/journal-api kubernetes.io/change-cause="v2 로 업그레이드" --overwrite
kubectl rollout history deploy/journal-api
실행 결과
deployment.apps/journal-api annotated deployment.apps/journal-api REVISION CHANGE-CAUSE 1 <none> 2 v2 로 업그레이드
판정리비전 번호는 그대로 1과 2이고, 2의 CHANGE-CAUSE만 채워졌다.

어노테이션은 새 리비전을 만들지 않는다. 파드 템플릿이 바뀐 것이 아니므로 롤아웃이 일어나지 않고, 디플로이먼트 컨트롤러가 현재(최신) 리비전의 레플리카셋에 그 어노테이션을 옮겨 적는다. 그래서 change-cause는 이미지를 바꾸기 전에 적어두는 것이 맞다 — 바꾼 뒤에 적어도 위처럼 최신 리비전에 붙기는 하지만, 그 사이에 또 롤아웃이 있었다면 엉뚱한 리비전에 붙는다. "annotate를 치면 리비전이 하나 는다"고 적힌 자료가 검색되는데, 틀렸다.

다만 이것을 사람이 매번 적는 것은 현실적이지 않다. 실무의 답은 매니페스트를 깃에 두고 커밋 메시지를 이력으로 삼는 것이다 — 그것이 M31 GitOps다. rollout history는 사고 상황에서 "몇 번으로 되돌릴지" 고를 때 쓰는 도구로 남는다.

6단계. 되돌린다

목적이전 리비전으로 되돌리고, 그때 리비전 번호에 무슨 일이 생기는지 본다.

kubectl rollout undo deploy/journal-api
kubectl get deploy journal-api -o jsonpath='{.spec.template.spec.containers[0].image}'; echo
실행 결과
Warning: resource deployments/journal-api was previously managed with 'kubectl apply'. Rolling back will not update the kubectl.kubernetes.io/last-applied-configuration annotation, which may cause unexpected behavior on future 'kubectl apply' operations. Consider using 'kubectl apply' with your previous configuration file instead. deployment.apps/journal-api rolled back journal-api:v1

경고는 원문이 한 줄이다(터미널 폭에 맞춰 접혀 보인다). 마지막 줄 journal-api:v1이 두 번째 명령의 출력 — 템플릿의 이미지가 v1로 돌아갔다.

kubectl rollout status deploy/journal-api
kubectl rollout history deploy/journal-api
실행 결과 (status 의 진행 줄은 생략)
deployment "journal-api" successfully rolled out deployment.apps/journal-api REVISION CHANGE-CAUSE 2 v2 로 업그레이드 3 <none>
판정리비전 1이 사라지고 3이 생겼다. undo는 "1로 돌아가기"가 아니라 "1의 템플릿으로 새 리비전 3을 만들기"다. 레플리카셋은 새로 만들지 않고 55c87ff598을 다시 4개로 늘리지만, 번호는 새로 받는다. --to-revision=N을 쓸 때 이 번호 이동을 모르면 엉뚱한 리비전을 고른다.

경고를 그냥 넘기지 않는다. undo는 클러스터의 상태만 되돌리고 파일은 그대로다. 다음에 누군가 원래 파일로 kubectl apply를 하면 방금 되돌린 것이 도로 적용된다. 그래서 실무의 롤백 순서는 이렇다.

  1. 급하면 rollout undo로 먼저 불을 끈다
  2. 곧바로 매니페스트(또는 깃 저장소)를 같은 상태로 되돌린다

2번을 잊으면 다음 배포나 GitOps 동기화 때 장애가 그대로 재현된다 — 실제로 자주 일어나는 사고다.

--to-revision=2처럼 특정 리비전을 지정할 수도 있다(위 이력에서 2가 v2다). 인자가 없으면 바로 이전 리비전으로 간다.

10.5일부러 실패시키기

실패 ① — 존재하지 않는 이미지로 배포한다

가장 흔한 배포 사고를 재현한다. 태그 오타나 CI가 이미지를 아직 안 올린 상태에서 배포하는 경우다.

kubectl set image deploy/journal-api api=journal-api:v99
sleep 12
kubectl get pods -l app=journal-api
kubectl rollout status deploy/journal-api --timeout=10s; echo "exit=$?"
실행 결과
deployment.apps/journal-api image updated NAME READY STATUS RESTARTS AGE journal-api-544b4499df-wcl96 0/1 ErrImagePull 0 12s journal-api-55c87ff598-4fb2b 1/1 Running 0 41s journal-api-55c87ff598-52xh5 1/1 Running 0 40s journal-api-55c87ff598-mr9c2 1/1 Running 0 38s journal-api-55c87ff598-w2qss 1/1 Running 0 39s Waiting for deployment "journal-api" rollout to finish: 1 out of 4 new replicas have been updated... error: timed out waiting for the condition exit=1
판정여기서 봐야 할 것은 기존 파드 4개(v1, 55c87ff598)가 그대로 살아 있다는 사실이다. 6단계에서 되돌린 직후라 AGE가 40초 안팎이다. 서비스는 멀쩡히 동작한다. 새 파드 하나(544b4499df)만 ErrImagePull에 갇혀 있다 — 보는 시점에 따라 ImagePullBackOff로 보일 수도 있다. kubelet이 재시도 간격을 늘리는 중이라는 뜻이며 같은 상태다.

maxUnavailable: 0이 여기서 값을 한다. 새 파드가 준비되지 않았으므로 옛 파드를 하나도 빼지 않았다. 기본값(25%)이었다면 파드 1개를 미리 뺀 뒤 새 파드를 기다렸을 것이고, 용량이 75%로 떨어진 채 멈춰 있었을 것이다.

rollout status의 종료 코드 1도 중요하다. CI/CD 파이프라인은 이 코드를 보고 배포 실패를 판정한다(M29 · M30). --timeout을 주지 않으면 progressDeadlineSeconds(기본 600초)까지 기다린다.

kubectl rollout undo deploy/journal-api
sleep 5
kubectl get pods -l app=journal-api
kubectl get rs -l app=journal-api
실행 결과
Warning: resource deployments/journal-api was previously managed with 'kubectl apply'. Rolling back will not update the kubectl.kubernetes.io/last-applied-configuration annotation, which may cause unexpected behavior on future 'kubectl apply' operations. Consider using 'kubectl apply' with your previous configuration file instead. deployment.apps/journal-api rolled back NAME READY STATUS RESTARTS AGE journal-api-55c87ff598-4fb2b 1/1 Running 0 58s journal-api-55c87ff598-52xh5 1/1 Running 0 57s journal-api-55c87ff598-mr9c2 1/1 Running 0 55s journal-api-55c87ff598-w2qss 1/1 Running 0 56s NAME DESIRED CURRENT READY AGE journal-api-544b4499df 0 0 0 29s journal-api-55c87ff598 4 4 4 99s journal-api-975dd69b9 0 0 0 62s
판정ErrImagePull 파드가 사라지고 v1 파드 4개는 재시작 없이 그대로다(AGE가 이어진다). 레플리카셋은 3개 — v1(55c87ff598) 4개, v2(975dd69b9) 0개, v99(544b4499df) 0개 — 가 이력으로 남았다. M11은 이 상태에서 시작한다. AGE는 3단계의 부하 측정 시간에 따라 다르다.
실패 ② — 셀렉터를 바꾸려 한다

매니페스트의 spec.selector.matchLabels만 app: journal로 바꾸고 적용해 본다. 원본을 건드리지 않도록 sed로 사본을 만든다 — 셀렉터 줄은 들여쓰기가 6칸이고 템플릿 레이블 줄은 8칸이라 앞의 공백 6칸으로 구분된다.

sed 's/^      app: journal-api .*/      app: journal/' \
  course/labs/k8s/m10-journal-deployment.yaml > /tmp/m10-selector-typo.yaml
grep -n 'app:' /tmp/m10-selector-typo.yaml
kubectl apply -f /tmp/m10-selector-typo.yaml
실행 결과
7: app: journal-api 12: app: journal 21: app: journal-api The Deployment "journal-api" is invalid: * spec.template.metadata.labels: Invalid value: {"app":"journal-api"}: `selector` does not match template `labels` * spec.selector: Invalid value: {"matchLabels":{"app":"journal"}}: field is immutable
판정grep에서 12행(셀렉터)만 바뀌었고 7행(디플로이먼트 자체의 레이블)·21행(템플릿 레이블)은 그대로다. apply는 두 줄로 거부된다 — 첫 줄은 셀렉터와 템플릿 레이블이 어긋났다는 것, 둘째 줄은 셀렉터 자체가 불변이라는 것. 템플릿 레이블도 함께 app: journal로 바꾸면 첫 줄은 사라지고 field is immutable 한 줄만 남는다. 어느 쪽이든 클러스터의 디플로이먼트는 바뀌지 않았다(kubectl describe deploy journal-api | grep Selector → Selector: app=journal-api). kubectl patch로 셀렉터만 고쳐도 같은 두 줄이 나온다.

field is immutable — 생성 후 바꿀 수 없는 필드다. 정말 바꿔야 한다면 디플로이먼트를 지우고 다시 만들어야 하고, 그동안 서비스가 끊긴다. 다행히 방법이 있다.

# 기존 디플로이먼트를 지우되 파드는 남긴다
kubectl delete deploy journal-api --cascade=orphan
# 새 셀렉터로 만든 뒤, 남은 옛 파드를 정리한다

--cascade=orphan은 M18 스테이트풀셋에서도 같은 목적으로 쓴다. 다만 이 작업이 필요해진 시점에 이미 레이블 설계가 잘못된 것이므로, 처음 정할 때 신중해야 한다는 결론은 그대로다.

10.6남은 17건의 정체

실패 17건은 어디서 왔을까. 파드가 종료될 때 두 가지 일이 병렬로 일어나기 때문이다.

  1. 엔드포인트 컨트롤러가 그 파드를 서비스 대상 목록에서 뺀다 → 각 노드의 kube-proxy가 라우팅 규칙을 갱신한다
  2. kubelet이 그 파드의 컨테이너에 SIGTERM을 보낸다

두 경로는 서로를 기다리지 않는다. 그래서 이미 죽기 시작한 파드로 트래픽이 몇 밀리초 더 들어온다. 클러스터가 클수록 라우팅 규칙 전파가 늦어져 이 창이 넓어진다.

해결책은 파드를 일부러 천천히 죽이는 것이다. preStop 훅으로 몇 초 기다린 뒤 종료 절차를 시작하면, 그 사이에 라우팅에서 빠지므로 새 요청이 오지 않는다. 그다음 애플리케이션이 처리 중이던 요청을 마무리하고 종료한다(M04에서 넣어둔 SIGTERM 핸들러의 역할).

          lifecycle:
            preStop:
              exec:
                command: ["sh", "-c", "sleep 5"]
          terminationGracePeriodSeconds: 30

M15에서 이 설정을 넣고 같은 측정을 반복해 실패 건수가 어떻게 달라지는지 비교한다. 지금은 "무중단 배포"라는 말이 설정 하나로 완성되지 않는다는 사실만 확인하고 넘어간다 — 롤아웃 전략, 레디니스 프로브, 종료 훅, 애플리케이션의 시그널 처리, 네 가지가 다 맞아야 0에 가까워진다.

10.7체크포인트와 정리

다음 모듈로 넘어가기 전 확인
  • kubectl get deploy journal-api → READY 4/4
  • kubectl get deploy journal-api -o jsonpath='{.spec.template.spec.containers[0].image}' → journal-api:v1 (실패 ①의 undo까지 마친 상태)
  • kubectl get rs -l app=journal-api --no-headers | wc -l → 3 (v1 · v2 · v99 레플리카셋. DESIRED가 4인 것은 55c87ff598 하나)
  • kubectl rollout history deploy/journal-api → 리비전 행 3개, 그중 하나의 CHANGE-CAUSE가 v2 로 업그레이드
  • kubectl exec curlbox -- curl -s -o /dev/null -w '%{http_code}\n' http://journal-api:8080/healthz → 200 (아래 정리 블록에서 서비스를 지우기 전에 확인한다)
  • kubectl get pod curlbox -o jsonpath='{.spec.containers[0].command}' → 출력에 sleep infinity가 들어 있다. 3600이면 M11 전에 Completed로 죽는다
  • (이해 확인) maxUnavailable: 0이 실패 ①에서 무엇을 지켰는가 — 기본값 25%였다면 파드 몇 개가 먼저 사라졌을지 답한다
  • (이해 확인) rollout undo 뒤에 매니페스트(또는 깃)를 왜 같이 되돌려야 하는가 — 6단계의 경고문으로 답한다
