지금까지 만든 이미지는 이 노트북에만 있다. 클러스터 노드가 그것을 받으려면 레지스트리가 필요하다. 올리는 방법과 함께, 올라간 이미지에 무엇이 딸려 들어갔는지 — 취약점 13건이 어디서 왔고 어떻게 2건으로 만드는지 확인한다.

7.1왜 레지스트리가 필요한가

M01에서 만든 클러스터의 워커 노드는 도커 컨테이너다. 그 안에는 별도의 컨테이너 런타임(containerd)이 있고, 맥의 이미지 캐시를 보지 못한다. 파드를 배포하면 노드는 자기가 아는 곳 — 레지스트리에서 이미지를 찾는다.

레지스트리 (Registry)는 이미지를 저장하고 배포하는 서버다. Docker Hub가 가장 유명하지만, 실무에서는 사내 레지스트리(Harbor, Nexus)나 클라우드 레지스트리(ECR, GCR, ACR)를 쓰는 경우가 더 많다. 이유는 셋이다 — Docker Hub의 익명 풀 요청 제한, 사내 코드가 든 이미지를 외부에 두지 않으려는 정책, 그리고 클러스터와 같은 네트워크에서 받는 속도.

이 모듈에서는 레지스트리를 컨테이너로 직접 띄운다. 레지스트리 실습은 계정도 인터넷도 필요 없고, 실제 레지스트리와 같은 API(/v2/)를 쓰기 때문에 동작을 그대로 관찰할 수 있다. 인터넷이 필요한 곳은 7.4절의 취약점 스캔 한 군데다.

7.2이론 — 이미지 공급망

책 1.3.1은 이미지 관리 모범 사례를 말하면서 이미지 빌드가 공급망 공격 (Supply-chain Attack)에 취약하다고 지적한다. 내 코드가 안전해도 이미지 안에는 내가 쓰지 않은 것들이 잔뜩 들어 있기 때문이다. M04에서 만든 246MB 이미지 안에서 저널 API 소스는 3KB도 안 된다. 나머지는 전부 남이 만든 것이다.

층들어오는 것내가 통제하는 방법
베이스 이미지OS 패키지 수십 개, 때로는 언어 런타임과 그 도구더 작은 베이스 선택, 정기적 재빌드
의존성직접 쓰는 라이브러리 + 그것들이 끌어오는 전이 의존성락 파일 고정, 스캔, 정기 업데이트
빌드 과정빌드 중 받아오는 스크립트, 캐시재현 가능한 빌드, npm ci 류의 고정 설치
내 코드애플리케이션코드 리뷰, 테스트

이 층들이 공격 경로가 되는 방식은 두 가지다. 하나는 이미 들어 있는 취약점 — 베이스 이미지의 OS 패키지나 전이 의존성에 알려진 CVE가 있고, 그 이미지가 그대로 배포된다. 다른 하나는 바꿔치기 — 빌드가 참조하는 태그가 다른 내용을 가리키게 되거나, 레지스트리와 노드 사이에서 이미지가 다른 것으로 대체된다. M03에서 배운 태그와 다이제스트의 구분이 여기서 실전 의미를 갖는다. 태그는 움직이고 다이제스트는 내용에 묶여 있으므로, "스캔한 이미지"와 "배포된 이미지"가 같은 것임을 보장하는 유일한 방법은 다이제스트다.

책 19.4(코드 보안)는 대응을 두 지점에 둔다. 빌드 시점에 스캔해 기준을 넘는 이미지를 CI에서 막고, 배포 시점에 클러스터가 검증된 이미지만 받아들이게 한다. 앞의 것이 이 모듈이고 뒤의 것이 M26이다. 두 지점 사이에 시간이 흐른다는 점이 중요하다 — 스캔을 통과한 이미지도 다음 주에 새 CVE가 공개되면 취약한 이미지가 된다. 그래서 스캔은 한 번이 아니라 레지스트리에 있는 이미지를 주기적으로 다시 돌리는 일이 된다.

확인 방법은 세 가지가 있고, 답하는 질문이 다르다. 취약점 스캔은 "이미지에 든 패키지 중 알려진 CVE가 있는 것은 무엇인가"에 답한다. 이 모듈에서 Trivy로 한다. SBOM(Software Bill of Materials)은 "이미지에 무엇이 들었는가"의 목록 자체다. 나중에 새 CVE가 공개됐을 때 "우리 이미지 중 그 패키지가 든 것은 어느 것인가"를 이미지를 다시 스캔하지 않고 목록 검색으로 답할 수 있다 — 이미지가 수백 개일 때 스캔과 목록 검색의 비용 차이가 이 도구의 존재 이유다. 서명은 "이 이미지를 우리가 빌드했는가"에 답한다. 빌드 파이프라인이 다이제스트에 서명하고, 클러스터의 어드미션 단계가 서명 없는 이미지를 거절한다. 스캔은 내용을 보고, SBOM은 내용을 기록하고, 서명은 출처를 증명한다. 셋 중 하나로 나머지를 대신할 수 없다.

이 과정의 배치는 이렇다. 여기서는 스캔을 실습하고 SBOM과 서명은 개념만 본다. M29(CI)에서 SBOM 생성과 이미지 서명을 파이프라인에 넣고, M26(어드미션 컨트롤)에서 서명되지 않은 이미지를 막는 정책을 만든다 — 그 정책이 여기서 예고한 서명 검증의 집행 지점이다.

7.3따라하기 ① 로컬 레지스트리

1단계. 레지스트리를 띄운다

목적이미지를 밀어 넣을 목적지를 만든다. 실제 레지스트리와 같은 API를 쓰는 컨테이너 하나다.

cd course/labs/apps/journal-api
docker run -d --name registry -p 5001:5000 registry:3.1.1
sleep 2
docker exec registry registry --version
curl -s localhost:5001/v2/_catalog
  • registry:3.1.1 — CNCF Distribution 프로젝트의 공식 레지스트리 구현. 검색 결과에 많이 보이는 registry:2는 이전 메이저 라인이다. 메이저만 적은 registry:3은 내일 다른 이미지를 가리킬 수 있으므로 패치 버전까지 박는다 (3.1.1 — 2026-09-05 확인, 실습 당일 재확인)
  • 호스트 포트는 5001을 쓴다. 맥에서 5000은 시스템 서비스가 점유하는 경우가 많다(M02의 포트 충돌)
실행 결과
registry github.com/distribution/distribution/v3 3.1.1 {"repositories":[]}
판정버전 줄에 3.1.1이 찍히고, 빈 목록이 JSON으로 돌아오면 레지스트리 API가 살아 있다.

2단계. 태그를 붙이고 푸시한다

목적이미지 이름에 레지스트리 주소가 포함된다는 규칙을 익힌다.

docker tag journal-api:v1 localhost:5001/journal-api:v1
docker push localhost:5001/journal-api:v1

이름 규칙이 [레지스트리주소/][네임스페이스/]이름:태그다. 레지스트리 주소를 생략하면 Docker Hub로 간다 — nginx:1.29-alpine이 실제로는 docker.io/library/nginx:1.29-alpine인 이유다. 그래서 푸시하려면 먼저 태그를 다시 붙여야 한다. docker push journal-api:v1은 Docker Hub의 존재하지 않는 저장소로 향한다.

실행 결과 (Waiting 줄은 생략)
The push refers to repository [localhost:5001/journal-api] 58db720c7371: Pushed 7219ec201c38: Pushed 3d098bfa22b2: Pushed 5de55e5ef9c0: Layer already exists b05773cc67e1: Layer already exists ... v1: digest: sha256:6d8310e7b3c2c19e5dd95e748e963ccfaabd5fde53268d63070745a0f6997ea3 size: 856

레이어 단위로 올라갔다(M03에서 본 그 레이어들이다). 위 출력은 같은 레지스트리에 이전 빌드를 한 번 올린 뒤의 것이라 베이스 이미지 레이어들이 Layer already exists다 — 빈 레지스트리에 처음 올리면 전부 Pushed로 나온다. 마지막 줄의 digest:가 이 이미지의 내용 주소이며, 이 값은 빌드마다 다르다. 배포 매니페스트(쿠버네티스에 "무엇을 어떻게 띄울지" 선언하는 YAML, M08부터 쓴다)에 박을 값이 이것이다.

curl -s localhost:5001/v2/_catalog
curl -s localhost:5001/v2/journal-api/tags/list
실행 결과
{"repositories":["journal-api"]} {"name":"journal-api","tags":["v1"]}
판정저장소와 태그가 목록에 보인다. 이 두 API는 사내 레지스트리 점검 스크립트에서도 그대로 쓴다.

3단계. 다이제스트로 받아서 태그로 받은 것과 비교한다

목적M03에서 배운 다이제스트 지정을 실제 배포 경로에서 확인하고, 다이제스트로 받은 이미지와 태그로 받은 이미지가 같은 것인지 ID로 대조한다.

# 로컬 사본을 지운 뒤 다이제스트로 받는다 (다이제스트는 2단계 출력의 값을 쓴다)
docker rmi localhost:5001/journal-api:v1
docker pull localhost:5001/journal-api@sha256:6d8310e7b3c2c19e5dd95e748e963ccfaabd5fde53268d63070745a0f6997ea3
실행 결과
Untagged: localhost:5001/journal-api:v1 localhost:5001/journal-api@sha256:6d8310e7b3c2…: Pulling from journal-api Digest: sha256:6d8310e7b3c2c19e5dd95e748e963ccfaabd5fde53268d63070745a0f6997ea3 Status: Downloaded newer image for localhost:5001/journal-api@sha256:6d8310e7b3c2… localhost:5001/journal-api@sha256:6d8310e7b3c2…

rmi가 Untagged만 찍고 Deleted가 없는 것은 같은 이미지에 journal-api:v1 태그가 남아 있기 때문이다. 태그로 받을 때와 달리, 다이제스트 pull은 그 사이 누군가 v1 태그를 다른 이미지로 덮어썼더라도 원래 이미지를 가져온다. M29의 CI 파이프라인에서 빌드한 이미지를 배포로 넘길 때 태그가 아니라 다이제스트를 넘기는 이유다.

docker image inspect -f '{{.Id}}' localhost:5001/journal-api@sha256:6d8310e7b3c2c19e5dd95e748e963ccfaabd5fde53268d63070745a0f6997ea3
docker image inspect -f '{{.Id}}' localhost:5001/journal-api:v1
docker image inspect -f '{{.Id}}' journal-api:v1

판정세 줄이 같은 값이다. 다이제스트로 받은 것, 태그로 받은 것, 로컬에서 빌드한 것이 모두 한 이미지다. 이 환경에서는 Id가 푸시 다이제스트와 같은 값으로 나오는데, Docker Engine 29의 containerd 이미지 저장소가 이미지 ID로 매니페스트 다이제스트를 쓰기 때문이다. 다른 저장소 설정에서는 Id가 다른 값(설정 다이제스트)이지만, 세 줄이 같다는 판정은 변하지 않는다.

7.4따라하기 ② 취약점 스캔과 개선

스캐너는 Trivy를 쓴다. 컨테이너로 실행하므로 설치가 필요 없고, 로그인도 요구하지 않는다. 태그는 aquasec/trivy:0.74.0으로 고정한다 — M03에서 정한 latest 금지는 도구 이미지에도 적용된다 (0.74.0은 2026-09-05 확인, 실습 당일 docker run --rm aquasec/trivy:0.74.0 --version으로 재확인).

4단계. 현재 이미지를 스캔한다

목적M04에서 만든 이미지에 알려진 취약점이 몇 건 있고 어디서 왔는지 본다.

docker run --rm -v /var/run/docker.sock:/var/run/docker.sock \
  aquasec/trivy:0.74.0 image --scanners vuln --severity HIGH,CRITICAL journal-api:v1
  • -v /var/run/docker.sock:... — 스캐너 컨테이너가 호스트의 이미지를 읽게 한다
  • --scanners vuln — 취약점만. 빼면 시크릿 탐지까지 돌아 느려진다
  • --severity HIGH,CRITICAL — 심각도를 좁힌다. 빼면 LOW·MEDIUM까지 나와 수백 줄이 된다
  • 처음 실행하면 취약점 DB(수십 MB)를 내려받느라 시간이 걸린다. 결과 개수는 DB 갱신에 따라 날마다 달라진다

5단계. 쓰지 않는 것을 들어내고 다시 스캔한다

목적"공격 표면을 줄인다"는 말을 숫자로 확인한다.

Dockerfile.hardened는 M04의 Dockerfile과 마지막 스테이지의 RUN rm -rf 한 줄만 다르다. 앞의 두 스테이지는 같으므로 마지막 스테이지만 싣는다.

# Dockerfile.hardened — 마지막 스테이지에 한 줄을 추가
FROM node:22-alpine
ARG APP_VERSION=v1
ENV NODE_ENV=production APP_VERSION=${APP_VERSION}
# npm · npx 는 애플리케이션 실행에 필요 없다. 지우면 스캔 결과가 줄어든다.
RUN rm -rf /usr/local/lib/node_modules/npm /usr/local/bin/npm /usr/local/bin/npx
WORKDIR /app
USER node
COPY --from=deps  --chown=node:node /app/node_modules ./node_modules
COPY --from=build --chown=node:node /app/dist ./dist
COPY --chown=node:node package.json ./
EXPOSE 8080
CMD ["node", "dist/server.js"]
cd course/labs/apps/journal-api
docker build -f Dockerfile.hardened -t journal-api:v1-hardened .
docker run --rm -v /var/run/docker.sock:/var/run/docker.sock \
  aquasec/trivy:0.74.0 image --scanners vuln --severity HIGH,CRITICAL journal-api:v1-hardened

cd를 빠뜨리면 failed to read dockerfile로 멈춘다 — M06에서 apps/에 있었다면 지금 한 단계 아래로 내려와야 한다. 빌드는 앞 두 스테이지가 M04 캐시를 그대로 쓰므로 몇 초면 끝난다.

실행 결과 (요약 부분)
2026-09-05T08:22:13Z INFO Detected OS family="alpine" version="3.24.1" ... journal-api:v1-hardened (alpine 3.24.1) Total: 2 (HIGH: 2, CRITICAL: 0)
판정Node.js (node-pkg) 섹션이 통째로 사라졌다. Total: 줄이 하나뿐이다. 13건 → 2건. 남은 2건은 알파인 베이스의 OS 패키지이므로, 베이스 이미지가 갱신될 때 함께 해결된다.

여기서 한 가지를 분명히 해둔다. 이 조치는 실행에 필요 없는 도구를 지운 것이지 취약점을 고친 것이 아니다. 하지만 효과는 실질적이다 — 컨테이너에 침입한 공격자가 패키지를 설치하거나 스크립트를 받아올 도구가 없어진다. 같은 발상의 끝이 distroless 이미지(셸조차 없음)이고, M24에서 readOnlyRootFilesystem과 함께 다룬다.

크기는 거의 안 줄었다(docker images journal-api:v1-hardened로 보면 246MB 그대로). 취약점 개수와 이미지 크기는 다른 축이라는 것도 함께 기억한다.

6단계. 스캔을 게이트로 만든다

목적스캔 결과를 사람이 읽는 표가 아니라 스크립트가 판단할 수 있는 종료 코드로 받는다. CI에서 빌드를 실패시키는 장치다.

# 심각도 HIGH 이상이 하나라도 있으면 종료 코드 1
docker run --rm -v /var/run/docker.sock:/var/run/docker.sock \
  aquasec/trivy:0.74.0 image --scanners vuln --severity HIGH,CRITICAL \
  --exit-code 1 journal-api:v1 > /dev/null
echo $?
  • --exit-code 1 — 조건에 맞는 취약점이 있으면 그 값으로 종료한다. 기본은 취약점이 있어도 0
  • > /dev/null — 표는 버리고 종료 코드만 본다. CI에서는 표를 아티팩트로 남기고 종료 코드로 판정한다
실행 결과
1
판정echo $?가 1. 13건이 있는 journal-api:v1은 이 게이트를 통과하지 못한다. journal-api:v1-hardened로 바꿔 돌려도 알파인 2건 때문에 역시 1이다 — 게이트를 CRITICAL만으로 좁히거나 --ignore-unfixed(수정 버전이 아직 없는 것은 제외)를 붙여야 0이 되며, 어느 쪽을 택할지가 팀의 정책이다.

책 5.3의 원칙 — 파이프라인에서 테스트가 실패하면 빌드도 실패한 것 — 이 스캔에도 그대로 적용된다. M29에서 이 명령을 GitHub Actions 워크플로에 넣는다. 실무에서는 처음부터 --exit-code 1을 켜면 기존 이미지들 때문에 전부 빨간불이 되므로, 보통 새로 생긴 취약점만 막고 기존 것은 기한을 정해 줄여나간다.

7.5따라하기 ③ 클러스터에 올린다

Part 1의 결승선이다. 만든 이미지를 M01의 클러스터에서 실행한다. 올릴 이미지는 journal-api:v1과 journal-api:v2 둘이다 — M10 롤아웃이 v1에서 v2로 바꾸는 실습이고, M15 프로브 실습도 두 버전을 쓴다.

왜 취약점을 줄인 v1-hardened가 아니라 v1을 올리는지 밝혀 둔다. M08~M18의 매니페스트와 course/labs/scripts/rebuild.sh가 journal-api:v1 · v2 태그와 M04의 Dockerfile을 기준으로 짜여 있다. v1-hardened는 스캔 전후를 비교하기 위한 실험 이미지로 남기고, 노드에는 뒤 모듈이 참조하는 태그를 올린다. 실무라면 RUN rm -rf … npm 한 줄을 Dockerfile 본체에 넣어 모든 빌드가 hardened가 되게 하는 것이 맞다 — 이 과정은 M24(파드 시큐리티)에서 실행 이미지 다듬기를 한 번에 다룰 때 그 선택을 다시 꺼낸다.

7단계. v2 이미지를 확인한다

실패 ① — 노드에 없는 이미지를 요청한다

Successfully assigned … to study-worker는 스케줄링이 성공했다는 뜻이다 — 노드 배치 문제가 아니다. docker.io/library/journal-api:v9는 노드가 Docker Hub를 찾아갔다는 뜻이다. 레지스트리 주소가 없는 이름은 이렇게 해석된다(7.3절). 마지막으로 pull access denied, repository does not exist or may require authorization 한 줄에는 세 가지 가능성이 섞여 있다. 이름 오타, 이미지 없음, 인증 실패.

실무에서 이 메시지를 만나면 순서대로 확인한다. ① 이미지 이름과 태그 오타(가장 흔하다), ② 노드에 이미지가 실제로 있는지(crictl images), ③ 프라이빗 레지스트리라면 imagePullSecrets가 붙어 있는지. 잠시 후 상태는 ImagePullBackOff로 바뀌는데, 재시도 간격을 점점 늘리며 기다리는 상태라는 뜻이다.

kubectl delete pod journal-missing --now
실패 ② — HTTP 레지스트리에 localhost 가 아닌 주소로 푸시한다

로컬 레지스트리는 TLS 없이 떴다. localhost:5001은 도커가 예외로 허용하지만, 같은 레지스트리를 맥의 네트워크 주소로 부르면 다른 머신에서 접근하는 것과 같은 취급을 받는다.

IP=$(ipconfig getifaddr en0)          # 맥의 네트워크 주소. 리눅스는 hostname -I | awk '{print $1}'
docker tag journal-api:v1 $IP:5001/journal-api:v1
docker push $IP:5001/journal-api:v1
docker rmi $IP:5001/journal-api:v1    # 실험용 태그 정리
실행 결과 (Waiting 줄 생략. 주소는 필자 환경의 값이라 <IP>로 바꿔 적었다)
failed to do request: Head "https://<IP>:5001/v2/journal-api/blobs/sha256:3d098bfa22b2…": http: server gave HTTP response to HTTPS client Untagged: <IP>:5001/journal-api:v1

Head "https://…" — 도커가 HTTPS로 말을 걸었고, 레지스트리는 HTTP로 답했다. 도커는 localhost와 127.0.0.0/8을 제외한 모든 레지스트리에 HTTPS를 요구한다. 해결책이 둘인데 방향이 정반대다. 실습에서는 데몬 설정에 insecure-registries로 예외를 준다 — 편하지만 통신이 평문이다. 실무에서는 인증서를 붙인다 — 사내 CA로 발급하고 노드에 신뢰 인증서를 배포한다.

이 과정은 localhost만 쓰므로 예외 설정이 필요 없다. 다만 사내에서 "일단 insecure-registries로 열어두자"가 그대로 굳는 경우가 많다는 것은 알아둔다 — 이미지가 평문으로 오간다는 뜻이고, 중간에서 바꿔치기할 수 있다는 뜻이다. 7.2절에서 말한 두 번째 공격 경로가 이것이며, M26에서 서명되지 않은 이미지를 막는 정책이 필요한 이유 중 하나다.
