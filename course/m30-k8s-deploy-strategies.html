배포 전략과 롤아웃 판정

M29의 파이프라인은 이미지를 만들어 놓고 멈춘다. 클러스터에 내보내는 방법은 아직 하나뿐이고 — M10의 롤링 업데이트 — 그것은 나쁜 버전을 전체로 퍼뜨리는 중에 나쁘다는 것을 알게 한다. 이 모듈에서 트래픽을 조금만 보내고 M20에서 만든 메트릭으로 계속할지 정하는 구조를 만든다. 판정 기준을 사람이 아니라 PromQL로 쓴다.

30.1롤링은 나쁜 버전을 퍼뜨리면서 알려 준다

M10에서 롤링 업데이트를 봤다. maxSurge: 1·maxUnavailable: 0으로 파드를 하나씩 교체하고, 프로브가 통과하지 못하면 롤아웃이 멈춘다. 여기까지는 안전장치가 있다.

문제는 프로브가 통과하는 나쁜 버전이다. 앱이 뜨고 /readyz가 200을 주는데 요청의 40%가 500을 내는 상황에서, 롤링 업데이트는 아무것도 눈치채지 못하고 끝까지 진행한다. 프로브는 "이 파드가 살아 있는가"만 보고 "이 버전이 좋은가"는 보지 않기 때문이다.

그때 무슨 일이 일어나는지 세어 보면 이렇다. 파드가 3개일 때 첫 파드가 교체되면 요청의 3분의 1이 나쁜 버전으로 간다. 알림이 울리기까지 M21에서 정한 for: 2m이 걸리고, 그 2분 사이에 롤아웃은 나머지 둘도 교체한다. 알림을 받았을 때는 이미 100%가 나쁜 버전이다.

필요한 것은 두 가지다. 영향 범위를 비율로 묶는 것과 진행할지 말지를 판정할 근거다. 근거는 이미 있다 — M20에서 만든 http_server_requests_seconds가 상태 코드별로 요청을 세고 있다. 이 모듈은 그 지표를 배포 결정에 연결한다.

30.2이론 — 세 전략과 판정 메트릭

책 매핑5.7 롤링·블루그린·카나리 각각의 대가 · 6장 버저닝과 릴리스 레이블 규약

무엇을 사고 무엇을 파는가

롤링은 자원을 거의 더 쓰지 않는다. 대신 되돌리는 데 내보낼 때와 같은 시간이 든다 — 되돌리기도 롤링이기 때문이다. 급할 때 이 시간이 길게 느껴진다.

블루/그린은 두 버전을 동시에 띄워 두고 스위치를 넘긴다. 전환도 복구도 순간이고, 전환 전에 새 버전을 실제 클러스터에서 미리 확인할 수 있다. 대가는 자원이다 — 항상 두 배를 점유한다.

카나리는 트래픽 일부만 새 버전으로 보낸다. 나쁜 버전이 영향을 주는 범위가 비율로 제한되고, 그 사이에 판정할 시간이 생긴다. 대가는 배포 시간과 판정할 메트릭이 반드시 있어야 한다는 전제다.

마지막 전제가 이 모듈이 Part 4(관측) 뒤에 있는 이유다. 메트릭이 없으면 카나리는 그냥 느린 롤링이다 — 사람이 눈으로 대시보드를 보다가 "괜찮은 것 같은데요"로 승격하는 절차가 되고, 그건 자동화가 아니다.

트래픽을 나누는 두 방법

"20%를 새 버전으로"를 구현하는 방법은 둘이다. 레플리카 수로 나누는 것과 라우팅 규칙으로 나누는 것.

앞의 것은 추가 구성요소가 필요 없다. 파드 5개 중 1개를 새 버전으로 만들면 Service가 균등 분배하므로 대략 20%가 간다. 정확하지 않고(반올림), 파드 수가 적으면 세밀하게 나눌 수 없다 — 파드 3개로는 33% 단위가 최소다.

뒤의 것은 인그레스 컨트롤러나 메시가 가중치를 받아 준다. 파드 수와 무관하게 1%도 가능하다. 대신 그 구성요소와의 연동 설정이 필요하고, M25에서 본 대로 메시는 그 자체로 비용이다.

이 모듈은 앞의 방법을 쓴다. 판정에 필요한 만큼의 트래픽만 흐르면 되고, 실습 클러스터에서 추가 구성요소 없이 원리를 볼 수 있기 때문이다.

Rollout은 Deployment를 대신한다

여기서 커스텀 리소스custom resource가 처음 나온다. 쿠버네티스는 Deployment·Service처럼 기본으로 아는 리소스 종류 외에, 누구나 새 종류를 등록할 수 있게 열어 두었다. 등록하는 오브젝트가 CustomResourceDefinition(CRD)이고, 등록하고 나면 kubectl get rollouts처럼 기본 리소스와 똑같이 다룰 수 있다. Argo Rollouts를 설치하면 CRD 다섯 개가 함께 들어온다.

지금은 남이 만든 것을 쓰는 쪽이다. 직접 만드는 쪽(CRD를 정의하고 그것을 지켜보는 컨트롤러를 쓰는 일)은 M33에서 다룬다 — 그때 이 Rollout이 안쪽에서 어떻게 동작하는지가 보인다.

Rolloutargoproj.io/v1alpha1은 Deployment를 대체하는 커스텀 리소스다. 안에 두는 것은 같다 — replicas·selector·template. 다른 것은 strategy이고, 거기에 단계와 분석을 쓴다. 컨트롤러는 여전히 ReplicaSet을 만들어 파드를 관리하므로, 아래층은 우리가 아는 그대로다.

대체라는 점이 중요하다. 기존 Deployment를 Rollout으로 바꾸면 같은 이름의 두 리소스가 같은 파드를 두고 다투는 상황이 생길 수 있다. 전환할 때는 디플로이먼트를 먼저 지우거나, Argo Rollouts가 제공하는 workloadRef로 기존 디플로이먼트를 참조하게 한다.

30.3따라하기 ① 블루/그린

추가 도구 없이 쿠버네티스 기본 기능만으로 만든다. 디플로이먼트 둘 + 서비스 둘이 전부다.

1단계 — 네임스페이스부터 restricted로

목적배포 전략 실습이라고 보안을 낮추지 않는다. M24의 기준을 그대로 건다.

cat > course/labs/k8s/rollouts/00-namespace.yaml <<'EOF'
apiVersion: v1
kind: Namespace
metadata:
  name: m30
  labels:
    pod-security.kubernetes.io/enforce: restricted
    pod-security.kubernetes.io/enforce-version: latest
EOF
kubectl apply -f course/labs/k8s/rollouts/00-namespace.yaml

이 라벨 때문에 kubectl run으로 진단 파드를 띄울 수 없다. M25에서 겪은 것과 같고, 이 모듈에서는 securityContext를 갖춘 파드 매니페스트를 직접 쓴다. 보안 설정이 실습을 불편하게 만드는 것이 아니라, 불편함이 그 설정이 동작한다는 증거다.

2단계 — 두 벌을 띄우고 서비스를 하나만 연결한다

목적블루/그린의 구조를 만든다. color 라벨 하나가 스위치다.

# 핵심만 (전문은 course/labs/k8s/rollouts/10-bluegreen.yaml)
apiVersion: v1
kind: Service
metadata: {name: bg, namespace: m30}
spec:
  selector: {app: bg, color: blue}      # <- 이 줄이 스위치
  ports: [{name: http, port: 8080, targetPort: http}]
---
apiVersion: v1
kind: Service
metadata: {name: bg-preview, namespace: m30}
spec:
  selector: {app: bg, color: green}     # <- 전환 전에 확인하는 입구
  ports: [{name: http, port: 8080, targetPort: http}]
kubectl apply -f course/labs/k8s/rollouts/10-bluegreen.yaml
kubectl -n m30 get po --no-headers
출력
bg-blue-778ccc6864-lr672 1/1 Running 0 25s bg-blue-778ccc6864-qnmst 1/1 Running 0 25s bg-green-7d6768b6f-6xpsd 1/1 Running 0 25s bg-green-7d6768b6f-h4wpv 1/1 Running 0 25s
판정파드가 넷이다. 트래픽을 받는 것은 둘뿐인데 넷 분량의 자원을 쓴다 — 이것이 블루/그린의 가격표다. 실습에서는 파드 넷이지만 운영 규모에서는 클러스터 절반이 놀고 있는 상태가 된다.

3단계 — 전환 전에 확인한다

목적블루/그린의 실질적인 장점을 쓴다. 진짜 클러스터에서 새 버전을 확인한다.

for i in 1 2 3 4; do kubectl -n m30 exec c -- curl -s -m 4 http://bg:8080/healthz; echo; done
kubectl -n m30 exec c -- curl -s -m 4 http://bg-preview:8080/healthz
출력
{"status":"ok","version":"blue","pod":"bg-blue-778ccc6864-qnmst"} {"status":"ok","version":"blue","pod":"bg-blue-778ccc6864-qnmst"} {"status":"ok","version":"blue","pod":"bg-blue-778ccc6864-lr672"} {"status":"ok","version":"blue","pod":"bg-blue-778ccc6864-lr672"} {"status":"ok","version":"green","pod":"bg-green-7d6768b6f-6xpsd"}
판정실사용 입구는 blue만, 프리뷰 입구는 green만 준다. green은 이미 클러스터에서 돌고 있고 레디스에도 붙어 있다 — 스테이징에서 확인하는 것과 근본적으로 다른 점이다. 같은 네트워크 정책, 같은 시크릿, 같은 노드에서 검증한다.

4단계 — 전환하고 되돌린다

목적전환 속도와 전환이 반영되는 속도가 다르다는 것을 확인한다.

kubectl -n m30 patch svc bg -p '{"spec":{"selector":{"app":"bg","color":"green"}}}'
for i in $(seq 1 6); do kubectl -n m30 exec c -- curl -s -m 4 http://bg:8080/healthz; echo; done

되돌리는 것도 같은 명령이다.

kubectl -n m30 patch svc bg -p '{"spec":{"selector":{"app":"bg","color":"blue"}}}'
kubectl -n m30 exec c -- curl -s -m 4 http://bg:8080/healthz
출력 (patch 직후 첫 요청)

판정되돌렸는데 아직 green이 나온다. 셀렉터가 바뀌면 엔드포인트슬라이스를 다시 계산해야 하고, 그것을 각 노드의 kube-proxy가 받아 규칙을 고쳐야 한다. 그 사이의 요청은 옛 대상으로 간다.

판정수렴했다. 이 지연은 보통 1초 안쪽이지만 0은 아니다. "블루/그린은 무중단"이라는 표현이 정확하지 않은 이유이고, 전환 순간에 진행 중이던 요청은 M15에서 다룬 종료 창의 문제를 그대로 겪는다.

30.4따라하기 ② 카나리 준비

1단계 — Argo Rollouts를 설치한다

목적컨트롤러와 CRD를 넣는다. 첫 명령이 실패하는데, 그 실패가 이 절의 교재다.

kubectl create ns argo-rollouts
kubectl apply -n argo-rollouts \
  -f https://github.com/argoproj/argo-rollouts/releases/download/v1.10.0/install.yaml
출력
deployment.apps/argo-rollouts created Error from server (Invalid): error when creating "https://...install.yaml": CustomResourceDefinition.apiextensions.k8s.io "rollouts.argoproj.io" is invalid: metadata.annotations: Too long: may not be more than 262144 bytes
판정디플로이먼트는 만들어졌는데 CRD 두 개가 실패했다. kubectl apply는 적용한 매니페스트 전체를 kubectl.kubernetes.io/last-applied-configuration 주석에 저장하는데, 큰 CRD는 그 주석이 256KiB 한계를 넘는다. Argo Rollouts처럼 스키마가 방대한 CRD에서 자주 만나는 오류다.
kubectl apply -n argo-rollouts --server-side \
  -f https://github.com/argoproj/argo-rollouts/releases/download/v1.10.0/install.yaml
출력
customresourcedefinition.apiextensions.k8s.io/rollouts.argoproj.io serverside-applied customresourcedefinition.apiextensions.k8s.io/analysistemplates.argoproj.io serverside-applied customresourcedefinition.apiextensions.k8s.io/analysisruns.argoproj.io serverside-applied

--server-side는 주석 대신 서버가 필드 소유권을 기록한다. 클라이언트가 매니페스트를 통째로 들고 있을 필요가 없어서 크기 제한이 사라진다. M28에서 --dry-run=server를 쓴 것과 같은 계열의 기능이고, 큰 CRD를 다룰 때는 이쪽이 기본값이라고 생각하는 편이 낫다.

# kubectl 플러그인 (진행 상황을 보기 위해)
curl -sSL -o kubectl-argo-rollouts \
  https://github.com/argoproj/argo-rollouts/releases/download/v1.10.0/kubectl-argo-rollouts-darwin-arm64
chmod +x kubectl-argo-rollouts && sudo mv kubectl-argo-rollouts /usr/local/bin/
kubectl argo rollouts version
출력
kubectl-argo-rollouts: v1.10.0+d90700a

2단계 — 판정 기준을 PromQL로 쓴다

목적이 모듈에서 가장 중요한 파일이다. "좋은 배포"의 정의를 코드로 적는다.

apiVersion: argoproj.io/v1alpha1
kind: AnalysisTemplate
metadata: {name: success-rate, namespace: m30}
spec:
  args:
    - name: canary-hash
  metrics:
    - name: success-rate
      interval: 20s
      count: 3                 # 20초 간격으로 3회 본다
      failureLimit: 1          # 3회 중 1회까지는 봐준다
      successCondition: "result[0] >= 0.95"
      provider:
        prometheus:
          address: http://kps-kube-prometheus-stack-prometheus.monitoring.svc:9090
          query: |
            sum(rate(http_server_requests_seconds_count{
              namespace="m30",
              pod=~"canary-{{args.canary-hash}}-.*",
              status!~"5.."}[45s]))
            /
            sum(rate(http_server_requests_seconds_count{
              namespace="m30",
              pod=~"canary-{{args.canary-hash}}-.*"}[45s]))
필드정하는 것
count · interval몇 번, 얼마 간격으로 볼 것인가. 판정에 걸리는 최소 시간이 여기서 정해진다(20초×3 = 1분)
failureLimit몇 번까지 봐줄 것인가. 0이면 순간적인 흔들림 하나로 롤백된다
successCondition쿼리 결과에 대한 조건. result[0]이 첫 시계열의 값이다
{{args.canary-hash}}Argo가 채우는 값. 카나리 파드만 세기 위해 필요하다

[45s]를 interval인 20초보다 길게 잡은 이유가 있다. 스크레이프 간격이 10초이므로 rate()의 창이 20초면 표본이 두 개뿐이고, 하나만 놓쳐도 값이 없거나 튄다. 창은 스크레이프 간격의 최소 4배로 잡는 것이 M20에서 정한 규칙이다.

분모와 분자에 같은 pod=~ 필터가 들어가는 것이 핵심이다. 이것이 없으면 stable 파드의 성공까지 함께 세어 카나리가 아무리 나빠도 전체 성공률이 크게 떨어지지 않는다 — 카나리가 20%일 때 100% 실패해도 전체는 80%다.

3단계 — Rollout과 ServiceMonitor를 만든다

목적단계와 분석을 연결한다. 그리고 메트릭이 프로메테우스에 들어가는 경로를 만든다.

spec:
  replicas: 5
  strategy:
    canary:
      analysis:
        templates:
          - templateName: success-rate
        startingStep: 2          # 20% 단계부터 분석을 시작한다
        args:
          - name: canary-hash
            valueFrom:
              podTemplateHashValue: Latest
      steps:
        - setWeight: 20
        - pause: {duration: 60s}
        - setWeight: 60
        - pause: {duration: 60s}
        - setWeight: 100

ServiceMonitor는 M20에서 만든 것과 같은 형태다. release: kps 라벨이 빠지면 오브젝트는 만들어지고 타깃은 생기지 않으며, 분석은 데이터가 없어 실패한다 — M20의 3단 라벨 사슬이 여기서 배포 결정에 직접 영향을 준다.

kubectl apply -f course/labs/k8s/rollouts/20-canary.yaml
kubectl argo rollouts get rollout canary -n m30
출력
Name: canary Status: ✔ Healthy Strategy: Canary Step: 5/5 SetWeight: 100 ActualWeight: 100 Images: journal-api:v2 (stable)
판정첫 배포인데 단계를 전부 건너뛰고 5/5다. 비교할 stable 버전이 없으므로 카나리가 성립하지 않기 때문이고, 이것이 올바른 동작이다. 카나리는 두 번째 배포부터 의미가 있다.

4단계 — 판정에 쓸 트래픽을 만든다

목적메트릭이 없으면 분석은 판정할 수 없다. 실습 클러스터에는 사용자가 없으므로 만들어 준다.

# course/labs/k8s/rollouts/30-load.yaml — curl 루프 파드 2개
kubectl apply -f course/labs/k8s/rollouts/30-load.yaml
# 프로메테우스에서 확인
sum(rate(http_server_requests_seconds_count{namespace="m30"}[1m]))
출력
m30 요청률: 30.4 m30 타깃 수: 5
판정초당 30건, 타깃 5개. 카나리가 20%면 초당 6건이 새 버전으로 간다. 분석 창 45초 동안 270건이므로 성공률을 판정하기에 충분하다. 트래픽이 이보다 훨씬 적으면 표본이 부족해 판정이 흔들리고, 그때는 interval과 창을 늘려야 한다.

30.5따라하기 ③ 나쁜 버전을 배포한다

1단계 — 앱에 고장 손잡이를 넣는다

목적"프로브는 통과하는데 요청은 실패하는" 버전을 만든다. 30.1에서 말한 그 상황이다.

// M30 — 나쁜 버전을 만들기 위한 손잡이. 0 이면 아무 일도 하지 않는다.
const FAULT_RATE = Number(process.env.FAULT_RATE ?? 0);

app.get('/api/entries', async (_req, res) => {
  if (FAULT_RATE > 0 && Math.random() < FAULT_RATE) {
    log('error', 'injected fault', { rate: FAULT_RATE });
    res.status(500).json({ error: 'injected fault' });
    return;
  }
  ...
});

/healthz와 /readyz는 건드리지 않았다. 프로브는 계속 통과한다 — 그래야 이 실험이 성립한다.

카오스 주입 코드를 애플리케이션에 두는 것은 실습을 위한 선택이다. 운영 코드에 두면 언젠가 실수로 켜진다. M36에서는 이 방식 대신 애플리케이션 밖에서 장애를 주입하는 도구(Chaos Mesh)를 쓴다.

docker build -t journal-api:v3 --build-arg APP_VERSION=v3 course/labs/apps/journal-api
kind load docker-image journal-api:v3 --name study

2단계 — 배포하고 20%에서 멈추는 것을 본다

목적영향 범위가 실제로 제한되는지 파드 수로 확인한다.

kubectl -n m30 patch rollout canary --type=json -p '[
 {"op":"replace","path":"/spec/template/spec/containers/0/image","value":"journal-api:v3"},
 {"op":"replace","path":"/spec/template/spec/containers/0/env",
  "value":[{"name":"APP_VERSION","value":"v3"},{"name":"FAULT_RATE","value":"0.4"}]}
]'
kubectl argo rollouts get rollout canary -n m30
출력

판정Updated: 1 / Desired: 5 — 다섯 중 하나만 새 버전이다. Ready: 5인 것에 주의한다. 나쁜 버전의 파드도 Ready다 — 프로브를 통과하기 때문이다. 롤링 업데이트였다면 여기서 아무 저항 없이 나머지 넷도 교체됐을 것이다.

3단계 — 분석이 판정한다

목적사람이 개입하지 않고 되돌아가는지 확인한다.

kubectl argo rollouts get rollout canary -n m30
출력 (약 90초 뒤)
Status: ✖ Degraded Message: RolloutAborted: Rollout aborted update to revision 2: Background analysis phase error/failed: Metric "success-rate" assessed Failed due to failed (2) > failureLimit (1) Strategy: Canary Step: 0/5 SetWeight: 0 ActualWeight: 0 Images: journal-api:v2 (stable) Replicas: Desired: 5 Updated: 0 Ready: 5 NAME KIND STATUS AGE ├──# revision:2 │ ├──⧉ canary-84b759b894 ReplicaSet • ScaledDown 2m14s canary │ └──α canary-84b759b894-2 AnalysisRun ✖ Failed 74s ✖ 2 └──# revision:1 └──⧉ canary-586fbb4df5 ReplicaSet ✔ Healthy 3m52s stable
판정메시지에 판정 근거가 그대로 있다 — failed (2) > failureLimit (1). 카나리 레플리카셋은 ScaledDown이고 stable이 5개를 유지한다. 사람이 아무것도 하지 않았다.

실제 측정값을 본다.

kubectl -n m30 get analysisrun canary-84b759b894-2 -o jsonpath='{.status.metricResults[0]}' | python3 -m json.tool
출력
{ "count": 2, "failed": 2, "measurements": [ { "phase": "Failed", "value": "[0.6153846153846154]" }, { "phase": "Failed", "value": "[0.6584031997502411]" } ], "metadata": { "ResolvedPrometheusQuery": "sum(rate(http_server_requests_seconds_count{namespace=\"m30\", pod=~\"canary-84b759b894-.*\", status!~\"5..\"}[45s])) / sum(rate(...)[45s]))" }, "phase": "Failed" }
판정성공률 0.615·0.658. FAULT_RATE=0.4를 넣었으니 이론값 0.6에 가깝다 — 주입한 고장이 지표에 그대로 나타났다. ResolvedPrometheusQuery에 {{args.canary-hash}}가 실제 해시로 치환된 것이 보인다. 분석이 왜 그렇게 판정했는지 쿼리까지 남는다는 점이 중요하다 — 나중에 "왜 롤백됐지"를 재현할 수 있다.

목적같은 파이프라인이 좋은 버전은 통과시키는지 확인한다. 막기만 하는 관문은 곧 꺼진다.

2단계 — 기다리지 않고 승격한다

목적급할 때 쓰는 명령을 급하지 않을 때 익힌다.

출력 (승격 전 → 후)

판정pause를 건너뛰고 다음 단계로 갔다. promote --full을 쓰면 남은 단계를 전부 건너뛴다. 자동 판정이 있는데도 이 명령이 필요한 경우는 장애 대응 중 핫픽스를 내보낼 때다 — 그때는 분석을 기다리는 1분이 길다.

3단계 — 중단하고 되돌린다

목적abort와 undo가 다른 명령이라는 것을 확인한다. 장애 대응에서 헷갈리면 곤란하다.

kubectl argo rollouts abort canary -n m30
kubectl argo rollouts get rollout canary -n m30
출력
rollout 'canary' aborted Status: ✖ Degraded Message: RolloutAborted: Rollout aborted update to revision 4 SetWeight: 0 ActualWeight: 0 Images: journal-api:v3 (stable)
판정트래픽은 즉시 stable로 돌아갔는데 상태가 Degraded다. abort는 진행을 멈추는 명령이지 스펙을 되돌리는 명령이 아니다 — spec.template에는 여전히 새 버전이 적혀 있고, 그래서 "원하는 상태"와 "실제 상태"가 어긋난 채로 남는다.
kubectl argo rollouts undo canary -n m30
kubectl argo rollouts get rollout canary -n m30
출력
rollout 'canary' undo Status: ✔ Healthy Step: 5/5 SetWeight: 100 Images: journal-api:v3 (stable)
판정undo가 스펙을 이전 리비전으로 되돌려 Healthy가 됐다. 실무의 순서는 abort → 원인 파악 → undo 또는 고쳐서 재배포다. abort만 하고 방치하면 다음 사람이 Degraded를 보고 무슨 일인지 모른다.

30.7일부러 실패시키기

실패 ① — CRD가 커서 apply가 거부된다

목적30.4에서 만난 오류를 이유까지 정리한다. 다른 프로젝트를 설치할 때 반드시 다시 만난다.

출력
Error from server (Invalid): CustomResourceDefinition.apiextensions.k8s.io "rollouts.argoproj.io" is invalid: metadata.annotations: Too long: may not be more than 262144 bytes
판정API 서버가 거부한 것은 CRD 자체가 아니라 주석의 크기다. kubectl apply는 다음 번 3방향 병합을 위해 적용한 매니페스트 전체를 주석에 복사하는데, etcd의 값 크기 제한에 걸린다. 이 오류는 매니페스트가 잘못된 것처럼 보이지만 도구의 방식 때문이라 검색해도 엉뚱한 답이 많이 나온다.

세 가지 해법이 있고 성질이 다르다. --server-side는 병합을 서버가 하게 해서 주석을 없앤다(권장). kubectl create는 주석을 만들지 않지만 다음 업그레이드에서 apply가 안 된다. --force-conflicts는 다른 문제(필드 소유권 충돌)의 해법이라 여기서는 도움이 안 된다.

실패 ② — 분모에 stable을 섞으면 카나리가 통과한다

목적판정 쿼리를 잘못 쓰면 관문이 조용히 열린다는 것을 계산으로 확인한다.

다음처럼 pod 필터 없이 쓰기 쉽다. 네임스페이스 전체의 성공률을 보는 것이니 그럴듯해 보인다.

            sum(rate(http_server_requests_seconds_count{
              namespace="m30", status!~"5.."}[45s]))
            /
            sum(rate(http_server_requests_seconds_count{
              namespace="m30"}[45s]))

30.5의 상황에 이 쿼리를 대입한다. 카나리가 20%, 그 카나리의 성공률이 0.6이면 전체 성공률은 이렇게 된다.

(0.8 × 1.0) + (0.2 × 0.6) = 0.92        # 아직 0.95 미만이라 걸린다
# 그런데 카나리가 10% 라면
(0.9 × 1.0) + (0.1 × 0.6) = 0.96        # 통과한다
판정같은 나쁜 버전인데 카나리 비율이 작을수록 통과하기 쉬워진다. 비율을 낮춰 안전하게 하려는 의도가 정반대의 결과를 낳는다 — 영향은 줄지만 탐지도 함께 줄어든다. 분모와 분자를 모두 카나리로 한정해야 이 왜곡이 사라진다.

실측 쿼리가 ResolvedPrometheusQuery에 남는 것이 여기서 값을 낸다. 롤백이 안 됐을 때 "무엇을 물어봤는지"부터 확인할 수 있기 때문이다.

실패 ③ — 트래픽이 없으면 판정할 수 없다

목적메트릭 기반 판정이 메트릭이 없을 때 어떻게 되는지 확인한다.

# 부하 생성기를 멈추고 배포한다
kubectl -n m30 scale deploy load --replicas=0

분모가 0이 되므로 PromQL의 나눗셈 결과는 빈 결과다. successCondition: result[0] >= 0.95는 result[0]이 없으므로 평가할 수 없고, Argo는 이것을 Error로 처리한다. failureLimit과 별개로 consecutiveErrorLimit(기본 4)에 걸리면 롤아웃이 중단된다.

판정트래픽이 없는 서비스는 카나리로 배포할 수 없다. 야간에 요청이 0에 수렴하는 내부 서비스가 여기 해당한다. 대응은 셋이다 — 분석에 or vector(1)을 넣어 빈 결과를 성공으로 보거나(M21에서 쓴 기법), 합성 트래픽을 만들거나, 그런 서비스는 블루/그린으로 배포한다.

30.8운영 관점 — 무엇으로 판정할 것인가

성공률만으로는 부족하다

이 모듈은 성공률 하나로 판정했다. 실무에서는 최소 둘을 본다 — 에러율과 지연이다. 새 버전이 500을 내지 않으면서 P99가 3배가 되는 경우가 실제로 흔하고, 그건 성공률로는 잡히지 않는다. M20에서 만든 히스토그램이 있으므로 메트릭을 하나 더하면 된다.

    - name: latency-p99
      successCondition: "result[0] <= 0.5"
      provider:
        prometheus:
          query: |
            histogram_quantile(0.99, sum by (le) (rate(
              http_server_requests_seconds_bucket{namespace="m30",
                pod=~"canary-{{args.canary-hash}}-.*"}[45s])))

메트릭이 여러 개면 모두 통과해야 승격한다. 여기서 흔한 실수는 임계값을 절대값으로 쓰는 것이다 — 부하가 몰리는 시간대에는 stable도 P99가 오르므로, 절대값 기준은 그 시간대에 정상 배포까지 막는다. 더 나은 방법은 stable과 비교하는 것이다(카나리 P99가 stable P99의 1.2배 이하).

판정 시간과 표본 수

30.4에서 [45s] 창과 20초 간격을 정할 때 쓴 계산을 일반화하면 이렇다. 초당 요청 수 × 카나리 비율 × 창 길이가 판정에 쓰이는 표본 수다. 이 값이 수백 미만이면 성공률이 통계적으로 흔들려서, 정상 배포가 우연히 롤백되거나 나쁜 배포가 통과한다.

표본이 부족할 때 늘릴 수 있는 것은 셋이다 — 창(느려진다), 카나리 비율(영향이 커진다), 합성 트래픽(만들어야 한다). 셋 다 대가가 있고, 이 선택이 서비스마다 다른 것이 정상이다.

어느 전략을 언제 쓰는가

세 전략은 대체재가 아니라 상황별 선택이다. 판단 기준은 두 질문으로 좁혀진다.

되돌리는 데 걸리는 시간이 중요한가. 그렇다면 블루/그린이다. 결제나 정산처럼 몇 초의 오작동도 비싼 곳에서, 스위치 한 번으로 돌아가는 값이 두 배 자원보다 크다.

새 버전을 판정할 지표가 있는가. 있으면 카나리다. 없으면 카나리를 도입하기 전에 지표부터 만든다 — 순서가 반대면 "카나리를 켰는데 아무것도 안 잡힌다"가 된다.

둘 다 아니면 롤링으로 충분하다. 대부분의 내부 서비스가 여기 해당하고, 모든 서비스에 카나리를 다는 것은 과한 투자다. Argo Rollouts를 클러스터에 넣는 것 자체도 운영해야 할 컨트롤러가 하나 느는 일이다.

이 교재의 저널 앱은

journal 네임스페이스의 배포는 롤링 그대로 둔다. M10에서 만든 maxSurge: 1·maxUnavailable: 0이고, 이 모듈의 실습은 별도 네임스페이스에서 했다. 이유는 위 기준 그대로다 — 실습용 앱의 배포 위험은 낮고, 카나리를 붙이면 이후 모든 모듈에서 배포가 3분씩 걸린다.

M31에서 GitOps를 붙일 때 이 결정을 한 번 더 본다. 배포 전략과 배포 트리거는 다른 축이라, 깃 커밋이 배포를 일으키는 것과 그 배포가 카나리인지 롤링인지는 따로 정한다.

  • kubectl -n argo-rollouts get deploy argo-rollouts -o jsonpath='{.status.readyReplicas}' → 1
  • kubectl get crd rollouts.argoproj.io -o jsonpath='{.metadata.name}' → rollouts.argoproj.io
  • kubectl argo rollouts version | head -1 → v1.10.0으로 시작한다
  • kubectl -n m30 get svc bg -o jsonpath='{.spec.selector.color}' → blue
  • kubectl -n m30 get svc bg-preview -o jsonpath='{.spec.selector.color}' → green
  • kubectl -n m30 exec c -- curl -s http://bg:8080/healthz → "version":"blue"
  • kubectl argo rollouts get rollout canary -n m30 | grep Status → Healthy
  • kubectl -n m30 get rollout canary -o jsonpath='{.spec.template.spec.containers[0].image}' → journal-api:v3
  • kubectl -n m30 get analysisrun --no-headers | grep -c Failed → 1 (나쁜 버전이 실제로 걸렸다)
  • kubectl -n m30 get analysisrun --no-headers | grep -c Successful → 1 이상
  • kubectl -n m30 get analysisrun -o jsonpath='{.items[?(@.status.phase=="Failed")].status.metricResults[0].measurements[0].value}' → 0.95 미만의 값
  • kubectl -n m30 get servicemonitor canary -o jsonpath='{.metadata.labels.release}' → kps

# 부하 생성기를 먼저 멈춘다 (계속 돌면 프로메테우스에 계속 쌓인다)
kubectl -n m30 scale deploy load --replicas=0

kubectl delete ns m30 --ignore-not-found

# 컨트롤러는 남긴다. 남아 있는지 확인
kubectl -n argo-rollouts get deploy --no-headers

Argo Rollouts 컨트롤러와 CRD는 지우지 않는다. M32에서 여러 클러스터에 같은 배포를 내보낼 때 다시 쓰고, M38 캡스톤의 배포 절차에 들어간다.

journal-api:v3 이미지는 남는다. FAULT_RATE를 켜지 않으면 v2와 동작이 같으므로 그대로 둬도 문제가 없고, M36의 카오스 실험에서 애플리케이션 내부 고장과 외부에서 주입한 고장을 비교할 때 다시 쓴다.

다음 모듈

배포 전략은 생겼는데 배포를 누가 시작하는지는 여전히 사람이다. M29의 파이프라인은 이미지까지 만들고 멈췄고, 이 모듈에서는 kubectl patch를 손으로 쳤다. 그리고 지금 클러스터의 상태가 저장소의 어느 커밋에 해당하는지 아무도 답할 수 없다.

M31에서 저장소를 상태의 정본으로 만든다. 클러스터 안의 컨트롤러가 저장소를 지켜보다가 차이를 없애고, 사람이 kubectl로 바꾼 것을 되돌려 놓는다. 그 되돌림을 직접 겪어 보는 것이 이 모듈의 핵심 실습이다.
