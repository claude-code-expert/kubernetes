1.1왜 로컬 클러스터인가

쿠버네티스를 배우는 가장 흔한 실패는 클라우드 계정부터 만드는 것이다. 관리형 클러스터는 켜두면 돈이 나가고, 그래서 실습이 끝나면 지우고, 다음 주에 다시 만들면서 30분을 쓴다. 부수는 것이 아까운 환경에서는 일부러 망가뜨리는 실습을 할 수 없다.

이 과정은 반대로 간다. 클러스터를 20초에 만들고 5초에 지운다. 노드를 drain으로 비우고, 파드를 죽이고, 네트워크 정책으로 통신을 끊고, 나중에는 카오스 도구로 일부러 장애를 주입한다. 되돌리는 방법이 "다시 만든다"이기 때문에 무엇이든 해볼 수 있다.

대신 로컬 클러스터가 못 하는 것도 분명히 해둔다. 클라우드 로드밸런서(type: LoadBalancer의 실제 외부 IP), 여러 가용 영역, 노드 오토스케일링, 클라우드 IAM 연동은 흉내만 낸다. 해당 모듈에서 "여기까지가 로컬, 여기부터는 클라우드"를 매번 표시한다.

도구 선택 — 결정 두 개

첫째, 컨테이너를 실제로 실행할 런타임. 맥과 윈도우는 리눅스 컨테이너를 직접 못 돌리므로 어느 선택지든 내부적으로 경량 리눅스 VM을 띄운다.

런타임고르는 이유
Docker Desktop공식 제품, 크로스 플랫폼, GUI 대시보드. 회사 표준이 이미 이것이면 그대로 쓴다. 직원 250인 이상 또는 연매출 1천만 달러 이상 기업은 유료 구독이 필요하다
OrbStack (맥)시작이 몇 초, 유휴 상태 메모리·배터리 소모가 낮다. docker CLI 완전 호환이라 이 과정의 명령이 그대로 동작한다. 개인 사용 무료
ColimaGUI 없이 CLI만, 전부 오픈소스여야 할 때

둘째, 그 위에 클러스터를 만들 도구. 이 과정은 kind (Kubernetes IN Docker)로 통일한다. 도커 컨테이너 하나를 쿠버네티스 노드 하나로 쓰는 공식 SIG 도구다. 노드를 여러 개 만드는 것이 설정 파일 몇 줄이고, 이 과정의 M16(스케줄링)·M18(스토리지)·M25(네트워크 정책)은 노드가 2개 이상이어야 실습이 성립한다. 런타임에 내장된 단일 노드 쿠버네티스나 minikube로도 앞쪽 모듈은 되지만, 중간에 도구를 바꾸면 명령과 출력이 달라진다.

1.2이론 — 무엇이 어디서 도는가

명령을 치기 전에 층을 한 번 정리한다. 앞으로 kubectl get pods가 안 될 때, 어느 층이 죽었는지 짚을 수 있어야 한다.

그 전에 낱말 하나를 먼저 둔다. 파드 (Pod)는 쿠버네티스가 만들고 지우는 최소 단위로, 컨테이너 한 개 이상을 같은 네트워크 공간에 묶어 한 노드에 올린다. 이 모듈에서는 1.5절 4단계에서 kube-system의 파드 목록을 읽을 때 처음 쓰이고, 제대로 다루는 것은 M09다.

컨트롤 플레인 (Control Plane)은 클러스터의 두뇌다. 네 컴포넌트가 각각 하는 일이 다르고, 이 구분은 앞으로 장애를 진단할 때마다 쓰인다.

컴포넌트하는 일죽으면
kube-apiserver모든 요청의 유일한 입구. 인증 · 인가 · 어드미션을 거쳐 etcd에 쓴다kubectl이 전부 실패한다. 이미 뜬 파드는 계속 돈다
etcd클러스터의 모든 상태를 저장하는 키-값 저장소. 유일한 진실 공급원apiserver가 읽고 쓸 곳을 잃는다. 백업이 없으면 복구 불가
kube-scheduler새 파드를 어느 노드에 놓을지 결정한다 (M16의 주제)새 파드가 Pending에서 멈춘다. 기존 파드는 무사하다
kube-controller-manager의도한 상태와 실제 상태를 계속 비교해 좁힌다. 파드가 죽으면 다시 만드는 주체자가 복구가 멈춘다. 파드를 지워도 되살아나지 않는다

노드 쪽은 둘이다. kubelet은 apiserver에서 "이 노드에 이 파드를 띄워라"를 받아 컨테이너 런타임(containerd)에 지시하고 상태를 보고한다. kube-proxy는 서비스 IP로 온 트래픽을 실제 파드로 넘기는 규칙을 관리한다(M11의 주제).

kind의 특이점 kind에서는 컨트롤 플레인 컴포넌트도 파드로 뜬다(스태틱 파드). 그래서 kubectl get pods -n kube-system에 etcd-study-control-plane 같은 이름이 보인다. 관리형 클러스터(EKS · GKE · AKS)에서는 컨트롤 플레인이 클라우드 사업자 쪽에 숨어 있어 이 목록에 나타나지 않는다 — 로컬에서만 볼 수 있는 학습 기회다.

1.3설치

맥 기준이다. 리눅스는 각 도구의 공식 설치 안내를 따르되 이후 명령은 동일하다.

# 1) Homebrew (이미 있으면 건너뛴다)
/bin/bash -c "$(curl -fsSL https://raw.githubusercontent.com/Homebrew/install/HEAD/install.sh)"

# 2) 컨테이너 런타임 — 하나만 고른다
brew install --cask docker        # Docker Desktop
# brew install --cask orbstack    # OrbStack을 쓸 경우

# 3) 도구 4종 — kind · helm · kubectl · k6
brew install kind helm kubernetes-cli k6

# 4) JDK 21 — Homebrew의 openjdk@21은 PATH에 자동 등록되지 않으므로 한 줄을 셸 설정에 넣는다
brew install openjdk@21
echo 'export PATH="/opt/homebrew/opt/openjdk@21/bin:$PATH"' >> ~/.zshrc
source ~/.zshrc

뒤의 둘은 이 모듈에서 쓰지 않는다. k6는 M17 오토스케일링과 M37 부하 실험에서 요청을 쏘는 도구이고, JDK 21은 M19부터 실습 대상이 되는 Spring Boot 앱(order-api)을 빌드하는 데 필요하다. 지금 깔아두는 이유는 그 모듈들의 첫 10분을 설치로 쓰지 않기 위해서다. 클러스터 위에 설치해야 하는 metrics-server는 클러스터를 만든 뒤 1.5절 7단계에서 올린다.

설치가 끝나면 런타임 앱을 한 번 실행해 둔다. 데몬이 떠 있어야 kind가 노드 컨테이너를 만든다. 그다음 버전을 확인한다.

docker version --format 'Server {{.Server.Version}}'
kind version
kubectl version --client
helm version --short
k6 version
java -version

런타임 메모리를 먼저 올려둔다

Part 4에서 프로메테우스 스택을 설치하면 파드가 20개 넘게 뜬다. 기본값(보통 2~4GiB)으로는 그때 가서 Pending과 OOMKilled를 만난다. 지금 올려두는 편이 낫다. Docker Desktop은 Settings → Resources, OrbStack은 Settings → System에서 메모리 8GiB · CPU 4코어 · 디스크 40GiB 이상으로 맞춘다.

노트북 사양이 빠듯하면 메모리를 6GiB 미만밖에 못 주는 환경이라면 워커 노드를 1개로 줄인다(설정 파일에서 - role: worker 한 줄 삭제). M16 스케줄링 실습의 노드 분산 부분만 관찰 대상이 줄고, 나머지 모듈은 그대로 진행된다.

1.4클러스터 설정 파일

클러스터는 kind create cluster 한 줄로도 뜬다. 하지만 그러면 단일 노드에 포트가 하나도 열리지 않는다. 이 과정에서 쓸 구성을 파일로 고정한다. course/labs/infra/kind-cluster.yaml로 저장한다.

# course/labs/infra/kind-cluster.yaml
# 노드 3개 (control-plane 1 + worker 2). M16 스케줄링 실습에 워커가 2개 이상 필요하다.
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
name: study
nodes:
  - role: control-plane
    # M12 인그레스 실습에서 호스트 18080/18443을 노드로 넘긴다.
    # (80·443·8080 은 맥에서 다른 프로세스가 이미 쓰는 경우가 많다)
    kubeadmConfigPatches:
      - |
        kind: InitConfiguration
        nodeRegistration:
          kubeletExtraArgs:
            node-labels: "ingress-ready=true"
    extraPortMappings:
      - containerPort: 80
        hostPort: 18080
        protocol: TCP
      - containerPort: 443
        hostPort: 18443
        protocol: TCP
  - role: worker
  - role: worker
항목의미
nodes목록의 항목 하나가 도커 컨테이너 하나이자 쿠버네티스 노드 하나다
extraPortMappings맥의 포트를 노드 컨테이너 포트로 연결한다. M12에서 인그레스 컨트롤러를 여기에 붙여 브라우저로 접속한다
node-labels: ingress-ready=true인그레스 컨트롤러가 이 노드를 골라 뜨도록 표시해 둔다. 레이블이 배치를 결정하는 첫 사례로, M09에서 다시 다룬다
name: study클러스터 이름. kubeconfig 컨텍스트는 kind-study가 된다

1.5따라하기 — 클러스터 생성과 확인

1단계. 노드 이미지를 다이제스트로 고정해 생성한다

목적반년 뒤 같은 명령을 쳐도 같은 쿠버네티스 버전이 뜨게 만든다.

cd course/labs/infra

kind create cluster --config kind-cluster.yaml \
  --image kindest/node:v1.37.0@sha256:a1ed56cfb0e7b93589bdf97c8cd566405a265939e3620fc4f5de89adff580ae5
  • --config — 위에서 만든 설정 파일. 없으면 단일 노드로 뜬다
  • --image — 노드 이미지. @sha256: 뒤가 다이제스트 (Digest)로, 이미지 내용에서 계산된 값이라 절대 바뀌지 않는다. kindest/node:v1.37.0이라는 태그만 쓰면 같은 태그에 다른 이미지가 올라갔을 때 다른 클러스터가 뜬다. 다이제스트는 kind 릴리스 노트에 적혀 있다
실행 결과 (약 20초)
Creating cluster "study" ... ✓ Ensuring node image (kindest/node:v1.37.0) 🖼 ✓ Preparing nodes 📦 📦 📦 ✓ Writing configuration 📜 ✓ Starting control-plane 🕹 ✓ Installing CNI 🔌 ✓ Installing StorageClass 💾 ✓ Joining worker nodes 🚜 Set kubectl context to "kind-study" You can now use your cluster with: kubectl cluster-info --context kind-study

4단계. 컨트롤 플레인 컴포넌트를 파드 목록에서 찾는다

목적1.2절의 표에 있던 이름들을 실제 클러스터에서 확인한다.

읽는 법이 있다. etcd · kube-apiserver · kube-controller-manager · kube-scheduler는 컨트롤 플레인 노드에만 하나씩 있다. 반면 kube-proxy와 kindnet(kind의 CNI 플러그인)은 노드마다 하나씩 — 노드 3개니까 3개다. 노드마다 하나를 보장하는 컨트롤러가 데몬셋 (DaemonSet)이다. kindnet과 kube-proxy가 왜 데몬셋으로 도는지는 M09의 워크로드 컨트롤러 지도(Deployment · StatefulSet · DaemonSet · Job)가 이 장면을 그대로 이어받아 설명한다. coredns는 클러스터 안 DNS로, 이름이 IP로 바뀌는 모든 통신이 여기를 거친다(M11).

판정모든 파드가 Running이고 READY가 1/1. kube-proxy와 kindnet이 각각 3개면 노드 3개가 모두 정상 합류한 것이다.

5단계. apiserver 자체 진단을 읽는다

목적get nodes가 되는 것과 apiserver가 완전히 건강한 것은 다르다. 내장 진단 엔드포인트를 쓰는 법을 익힌다.

kubectl get --raw='/readyz?verbose' | tail -5
  • --raw — kubectl이 해석하지 않고 apiserver의 HTTP 응답을 그대로 보여준다. 오브젝트가 아닌 진단 엔드포인트를 볼 때 쓴다
  • ?verbose — 항목별 결과를 모두 출력한다. 빼면 ok 한 줄만 나온다
실행 결과 (마지막 5줄)
[+]poststarthook/apiservice-openapi-controller ok [+]poststarthook/apiservice-openapiv3-controller ok [+]shutdown ok readyz check passed
판정마지막 줄이 readyz check passed. 개별 항목에 [-]가 있으면 그 이름으로 검색하면 원인이 좁혀진다.

6단계. 어느 클러스터에 명령을 보내고 있는지 확인한다

목적엉뚱한 클러스터에 명령을 쏘는 사고를 막는 습관을 첫날에 들인다.

kubectl config get-contexts
실행 결과
CURRENT NAME CLUSTER AUTHINFO NAMESPACE * kind-study kind-study kind-study

컨텍스트 (Context)는 "어느 클러스터에, 어떤 사용자로, 어느 네임스페이스에서" 명령을 보낼지 묶어놓은 접속 프로필이다. 여기서 네임스페이스는 M09에서 다루는 쿠버네티스 네임스페이스(오브젝트를 나누는 이름 공간)이며, M02에서 만나는 리눅스 커널 네임스페이스와는 이름만 같은 다른 것이다. ~/.kube/config에 저장되고, kind는 클러스터를 만들면서 자동 등록한 뒤 현재 컨텍스트로 바꿔준다. 회사 클러스터가 같은 파일에 등록돼 있는 사람은 *가 어디 붙어 있는지 매번 확인한다 — 운영 클러스터에 실습 명령을 치는 사고의 대부분이 여기서 난다.

판정*가 kind-study 줄에 있다. 아니면 kubectl config use-context kind-study.

7단계. metrics-server를 설치해 kubectl top이 수치를 돌려주게 한다

목적노드와 파드의 CPU · 메모리 사용량을 읽는 kubectl top은 metrics-server가 있어야 동작하는데 kind에는 기본으로 들어 있지 않다. M16 kubectl top과 M17 HPA(오토스케일러가 이 수치로 계산한다)의 전제라서 지금 깔아둔다.

kubectl apply -f https://github.com/kubernetes-sigs/metrics-server/releases/download/v0.9.0/components.yaml
kubectl -n kube-system rollout status deploy/metrics-server --timeout=45s
  • components.yaml — 프로젝트가 릴리스마다 함께 배포하는 공식 설치 매니페스트. v0.9.0은 2026-07-13 릴리스로 호환표에서 Kubernetes 1.34 이상을 지원한다(2026-09-05 확인, 실습 당일 릴리스 페이지에서 재확인). releases/latest/download/…로 쓰면 몇 달 뒤 다른 버전이 깔리므로 버전을 박아 적는다
  • rollout status --timeout — 디플로이먼트의 파드가 준비될 때까지 기다리되 45초를 넘기면 포기한다
실행 결과
serviceaccount/metrics-server created ...(RBAC · service 생성 줄 생략) deployment.apps/metrics-server created apiservice.apiregistration.k8s.io/v1beta1.metrics.k8s.io created Waiting for deployment "metrics-server" rollout to finish: 0 of 1 updated replicas are available... error: timed out waiting for the condition

공식 매니페스트를 그대로 적용하면 kind에서는 뜨지 않는다. 이것은 예상된 실패다. 무엇이 문제인지 로그를 읽는다.

kubectl -n kube-system get deploy metrics-server
kubectl top nodes
kubectl -n kube-system logs deploy/metrics-server --tail=3
실행 결과 (IP · 타임스탬프는 환경마다 다르다)
NAME READY UP-TO-DATE AVAILABLE AGE metrics-server 0/1 1 0 45s error: Metrics API not available E0905 08:13:50.412499 1 scraper.go:149] "Failed to scrape node" err="Get \"https://172.20.0.3:10250/metrics/resource\": tls: failed to verify certificate: x509: cannot validate certificate for 172.20.0.3 because it doesn't contain any IP SANs" node="study-worker2" I0905 08:13:51.372949 1 server.go:192] "Failed probe" probe="metric-storage-ready" err="no metrics to serve"

metrics-server는 각 노드의 kubelet(:10250)에서 수치를 긁어오는데, kind 노드의 kubelet 인증서에는 IP 주소가 SAN으로 들어 있지 않다. 그래서 TLS 검증이 실패하고 긁어올 것이 없으니 준비 프로브도 계속 실패한다. 해결은 kubelet 인증서 검증을 끄는 인자 하나를 컨테이너 args에 덧붙이는 것이다.

kubectl -n kube-system patch deploy metrics-server --type=json \
  -p='[{"op":"add","path":"/spec/template/spec/containers/0/args/-","value":"--kubelet-insecure-tls"}]'
kubectl -n kube-system rollout status deploy/metrics-server --timeout=90s
  • patch --type=json — 오브젝트의 한 필드만 고친다. args/-의 -는 "배열 끝에 추가"라는 JSON Patch 표기다. 파일을 내려받아 고쳐 다시 apply해도 결과는 같다
실행 결과
deployment.apps/metrics-server patched Waiting for deployment "metrics-server" rollout to finish: 1 old replicas are pending termination... deployment "metrics-server" successfully rolled out

롤아웃이 끝난 뒤 첫 수집까지 15~30초가 더 걸린다. 그 사이에 치면 아직 Metrics API not available이 나오므로 한 번 더 기다렸다가 확인한다.

kubectl top nodes
실행 결과 (수치는 환경마다 다르다)
NAME CPU(cores) CPU(%) MEMORY(bytes) MEMORY(%) study-control-plane 152m 1% 1704Mi 21% study-worker 39m 0% 600Mi 7% study-worker2 129m 0% 553Mi 7%
판정노드 3줄에 CPU · 메모리 수치가 채워진다. 30초를 더 기다려도 Metrics API not available이면 kubectl -n kube-system get deploy metrics-server -o jsonpath='{.spec.template.spec.containers[0].args}'로 --kubelet-insecure-tls가 들어갔는지 본다.
--kubelet-insecure-tls는 로컬용이다 이 인자는 kubelet 인증서를 검증하지 않겠다는 뜻이다. kind처럼 노트북 안에서 닫힌 클러스터에서는 상관없지만, 운영 클러스터에서는 kubelet 서빙 인증서를 클러스터 CA로 발급받게 하고 이 인자 없이 띄운다. 관리형 클러스터(EKS · GKE · AKS)는 metrics-server가 이미 들어 있거나 애드온으로 제공되므로 이 단계 자체가 없다.

1.6일부러 실패시키기

이 과정의 모든 모듈에는 고장을 재현하는 단계가 있다. 첫 고장은 실제로 이 문서를 만들며 만난 것이다.

실패 ① — 호스트 포트가 이미 쓰이고 있다

설정 파일의 hostPort를 80과 443으로 두고 클러스터를 만들면 이런 일이 생긴다.

실행 결과
• Preparing nodes 📦 📦 📦 ... ✗ Preparing nodes 📦 📦 📦 Deleted nodes: ["study-control-plane" "study-worker2" "study-worker"] ERROR: failed to create cluster: command "docker run --name study-control-plane ... --publish=0.0.0.0:443:443/TCP ..." failed with error: exit status 125 Command Output: docker: Error response from daemon: ports are not available: exposing port TCP 0.0.0.0:443 -> 127.0.0.1:0: listen tcp4 0.0.0.0:443: bind: address already in use

읽는 순서는 맨 아래부터다. 마지막 줄 bind: address already in use가 진짜 원인이고, 그 위의 failed to create cluster는 결과일 뿐이다. 맥에서는 443을 다른 개발 도구나 VPN 클라이언트가 이미 잡고 있는 경우가 흔하다. 눈여겨볼 것이 하나 더 있다 — kind는 실패하자 만들다 만 노드 3개를 스스로 지웠다(Deleted nodes). 반쯤 만들어진 클러스터가 남지 않으므로 원인만 고치고 같은 명령을 다시 치면 된다.

누가 그 포트를 쓰는지 먼저 본다.

sudo lsof -nP -iTCP:443 -sTCP:LISTEN
  • -nP — 호스트명 · 포트명을 숫자 그대로 보여준다(역방향 조회로 느려지는 것을 막는다)
  • -iTCP:443 -sTCP:LISTEN — TCP 443에서 대기(LISTEN) 중인 소켓만. 붙어 있는 클라이언트 연결은 걸러낸다
  • sudo — 다른 사용자(root 포함)가 띄운 프로세스까지 보려면 필요하다. 내 프로세스만 볼 때는 빼도 된다
실행 결과 — 이 문서를 만든 환경에서는 80도 다른 도커 컨테이너가 잡고 있어 그쪽으로 확인한 예다 (PID · DEVICE 값은 환경마다 다르다)
COMMAND PID USER FD TYPE DEVICE SIZE/OFF NODE NAME com.docke 82374 mini 89u IPv6 0x203bbccd81169dc4 0t0 TCP *:80 (LISTEN)

COMMAND 열이 범인이다. com.docke는 com.docker.backend가 잘린 것으로, 다른 도커 컨테이너가 -p 80:…으로 그 포트를 이미 내보내고 있다는 뜻이다. VPN 클라이언트나 로컬 개발 서버라면 그 이름이 여기 찍힌다. 아무 줄도 안 나오면 sudo를 빼고 쳤을 가능성이 크다.

해결은 둘 중 하나다. 그 프로세스를 끄거나, 설정 파일의 hostPort를 18080 / 18443으로 바꾼다. 이 과정은 후자를 택했고, 1.4절의 파일이 이미 그렇게 돼 있으므로 같은 명령을 다시 치면 된다.

kind create cluster --config kind-cluster.yaml \
  --image kindest/node:v1.37.0@sha256:a1ed56cfb0e7b93589bdf97c8cd566405a265939e3620fc4f5de89adff580ae5

이 과정이 80/443 대신 18080/18443을 쓰는 이유가 이것이다. 8080도 피한 이유가 있다 — 맥에서 8080은 개발 서버나 로컬 AI 도구가 이미 쓰는 일이 잦고, 127.0.0.1:8080에 먼저 바인드된 프로세스가 있으면 도커가 0.0.0.0:8080을 잡아도 localhost 요청은 그쪽으로 간다. 충돌 없는 대역을 고르는 편이 낫다. M12에서 인그레스에 접속할 때 주소가 http://localhost:18080이 된다.

실패 ② — kubectl과 서버의 버전이 어긋난다

Docker Desktop을 설치하면 자체 kubectl이 /usr/local/bin에 함께 깔린다. 그게 서버보다 낡으면 이렇게 된다.

kubectl version
실행 결과
Client Version: v1.34.1 Kustomize Version: v5.7.1 Server Version: v1.37.0 Warning: version difference between client (1.34) and server (1.37) exceeds the supported minor version skew of +/-1

쿠버네티스는 클라이언트와 서버의 마이너 버전 차이를 ±1까지만 보장한다. 여기서는 3이나 벌어졌다. 당장은 대부분의 명령이 동작하지만, 새 API에서 필드가 통째로 누락되거나 kubectl explain이 낡은 스키마를 보여주는 식으로 조용히 어긋난다. 학습 중에 이런 종류의 오차가 섞이면 원인을 찾는 데 시간을 다 쓴다.

# 어느 kubectl이 잡히는지 확인
which -a kubectl

# 서버에 맞는 버전을 설치하고 PATH 우선순위를 확인
brew install kubernetes-cli
export PATH="/opt/homebrew/bin:$PATH"   # 셸 설정 파일에도 넣어둔다
kubectl version
해결 후
Client Version: v1.37.0 Kustomize Version: v5.8.1 Server Version: v1.37.0

경고 줄이 사라졌다. 1.7절의 사전 점검 스크립트가 이 항목을 매번 확인한다.

  • ~/.kube/config의 kind-study 컨텍스트
  • 클러스터 안: kube-system의 metrics-server 디플로이먼트. 파일이 아니라 클러스터를 지우면 함께 사라지므로, 재생성 뒤에는 1.5절 7단계를 다시 하거나 아래 rebuild.sh를 돌린다

course/labs/scripts/rebuild.sh는 이 모듈의 산출물이 아니지만 여기서 존재를 알려둔다. M14에서 완성되며, 빈 클러스터에서 M14 시점 상태(이미지 · 네임스페이스 · 헬름 릴리스)까지 한 번에 되돌린다. 뒤쪽 모듈에서 실습이 꼬여 무엇이 남았는지조차 모르게 됐을 때 처음부터 다시 하지 않아도 되는 탈출구다 — kind delete cluster --name study 다음에 RECREATE=1 bash course/labs/scripts/rebuild.sh. M14 전까지는 이 스크립트가 없으므로 1.9절의 재생성으로 충분하다.

1.9정리와 재생성

실습을 끝냈거나 클러스터가 알 수 없는 상태가 됐을 때. kind에서는 고치는 것보다 다시 만드는 것이 빠른 경우가 많다.

# 클러스터 삭제 (5초)
kind delete cluster --name study

# 무엇이 남았는지 확인
kind get clusters
docker ps -a --filter "label=io.x-k8s.kind.cluster=study"
실행 결과
Deleting cluster "study" ... Deleted nodes: ["study-control-plane" "study-worker" "study-worker2"] No kind clusters found.

노드 컨테이너가 지워지므로 docker ps -a에도 아무것도 남지 않는다. 다만 노드 이미지(약 1GiB)는 캐시에 남아 다음 생성이 훨씬 빠르다. 이미지까지 지우려면 docker rmi kindest/node:v1.37.0.

클러스터 안에만 저장한 데이터(PVC 내용, 설치한 헬름 릴리스, 만든 오브젝트, 1.5절 7단계의 metrics-server)는 함께 사라진다. 실습 중 만든 YAML은 course/labs/에 파일로 남아 있으므로 다시 apply하면 된다. 이것이 선언형으로 관리하는 이유다 — 클러스터는 언제든 버릴 수 있고, 진실은 파일에 있다(M08에서 다시 다룬다).

부하 · 백그라운드 작업 주의 뒤쪽 모듈에서 부하 생성 루프를 띄운 채로 클러스터를 지우면 셸에 루프만 남아 계속 에러를 뱉는다. 해당 모듈마다 종료 방법을 함께 적어 두었으니 정리 순서는 부하 종료 → 클러스터 삭제다.

다음 모듈

클러스터는 생겼지만 아직 배포할 것이 없다. M02부터 M07까지는 쿠버네티스를 잠시 두고 도커로 내려간다 — 컨테이너가 무엇인지 손으로 확인하고, 배포할 이미지를 직접 만든다. 여기서 만든 이미지가 M07에서 이 클러스터로 올라간다.
