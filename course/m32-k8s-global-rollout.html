글로벌 롤아웃과 사고 대응

M31까지 클러스터는 하나였다. 실제 서비스는 지역마다 클러스터가 따로 있고, 같은 변경을 여러 클러스터에 순서대로 내보내면서 중간에 멈출 수 있어야 한다. 이 모듈에서 kind 클러스터를 하나 더 만들어 리전 둘을 흉내 내고, 카나리 리전 → 판정 → 확산의 순서를 만든다. 그리고 그 판정이 나쁜 배포를 실제로 막는 것과, 매니페스트가 같아도 클러스터가 다르면 다르게 동작하는 것을 확인한다.

32.1클러스터가 둘이 되는 순간 달라지는 것

M31에서 만든 구조는 클러스터 하나를 가정한다. 저장소가 바뀌면 컨트롤러가 당겨가고, 그것으로 배포가 끝난다. 클러스터가 둘이 되면 질문이 하나 늘어난다 — 어느 쪽부터 갈 것인가.

둘을 동시에 배포하면 클러스터가 하나일 때와 위험이 같다. 나쁜 버전이 두 곳 모두에서 동시에 터지고, 되돌릴 곳도 두 곳이 된다. 여러 클러스터를 가지는 값어치는 그것들을 순서대로 다룰 때 나온다 — 한 곳에서 확인하고 다음으로 가면, 나쁜 버전이 영향을 주는 범위가 클러스터 하나로 묶인다.

M30의 카나리와 구조가 같다. 다른 것은 단위다. 거기서는 파드의 비율로 나눴고 여기서는 클러스터로 나눈다. 그리고 클러스터 단위이기 때문에 M30에서는 없던 문제가 생긴다 — 같은 매니페스트가 클러스터마다 다르게 동작할 수 있다. 32.7에서 그것을 실제로 만난다.

이 모듈에서 만드는 것은 세 가지다. 리전을 선언으로 등록하는 방법, 확산 전에 통과해야 하는 검사, 그리고 새벽에 읽을 러너북이다. 마지막 것이 실제로는 가장 자주 쓰인다.

32.2이론 — 리전 타입과 롤아웃 순서

책 매핑7.1 이미지 분산 · 7.2 배포 파라미터화 · 7.3 사전 롤아웃 검사 · 7.4 카나리 리전 · 7.5 리전 타입 식별과 문제 발생 시 대처

리전은 세 종류로 나뉜다

모든 리전을 똑같이 다루면 순서를 정할 수 없다. 실무에서 쓰는 구분은 대개 셋이다.

카나리 리전은 가장 먼저 받는 곳이다. 트래픽이 적고, 문제가 생겨도 영향이 작으며, 그럼에도 실제 사용자가 있어야 한다 — 아무도 안 쓰는 리전은 카나리가 아니라 그냥 스테이징이다. 주 리전은 트래픽의 대부분이 있는 곳이고 마지막에 받는다. 특수 리전은 규제·데이터 주권·다른 클라우드 사업자 같은 이유로 구성이 다른 곳이고, 별도 순서와 별도 검증이 필요하다.

이 구분을 어디에 적을 것인가가 실제 설계다. 문서에 적으면 코드가 모르고, 코드에 하드코딩하면 리전을 늘릴 때마다 코드를 고친다. 이 모듈은 클러스터 등록 정보의 라벨에 적는다 — 그러면 리전을 더할 때 시크릿 하나와 디렉터리 하나만 추가하면 된다.

파라미터화의 경계

리전마다 다른 것과 같은 것을 나누는 기준이 필요하다. 실용적인 규칙은 "같아야 하는 것이 기본이고, 다른 것은 이유를 적는다"이다.

이 모듈의 두 리전에서 다른 것은 셋뿐이다. 규모(노드 수가 달라서), REGION 값(로그와 메트릭에 어느 리전인지 남기려고), 토폴로지 분산(노드가 하나뿐인 리전에서는 제약이 스케줄을 막아서). 이미지 태그는 일시적으로만 달라진다 — 카나리가 앞서 있는 동안이고, 확산이 끝나면 다시 같아진다.

반대로 리전마다 달라지기 쉬운데 같게 유지해야 하는 것도 있다. 리소스 요청, 프로브 설정, 보안 컨텍스트가 그렇다. 이것들이 리전마다 다르면 한 리전에서 재현되지 않는 문제가 생기고, 카나리 리전의 판정이 의미를 잃는다.

사전 검사는 종료 코드여야 한다

"확인하고 넘어간다"를 사람의 눈으로 하면 새벽 3시에는 하지 않는다. 검사는 스크립트여야 하고, 결과는 종료 코드여야 한다 — 그래야 파이프라인에 넣을 수 있고, 사람이 실행해도 판단이 개입하지 않는다.

무엇을 검사할지가 이 스크립트의 전부다. 32.7에서 보듯 "파드가 준비된 개수"만 보면 나쁜 배포를 통과시킨다. 롤아웃이 끝났는지, 기대한 이미지가 도는지, 실제로 응답하는지를 각각 봐야 하고, 사고가 날 때마다 항목이 하나씩 늘어난다.

32.3따라하기 ① 두 번째 리전을 만든다

1단계 — 여유 메모리를 먼저 센다

목적클러스터를 하나 더 띄우면 기존 클러스터가 죽을 수 있다. 죽이고 나서 알면 늦다.

docker stats --no-stream --format '{{.Name}} {{.MemUsage}}'
docker info --format '{{.MemTotal}}'
판정실측 환경에서는 컨테이너 합계 5.83GiB / 7.65GiB였다. 노드 하나짜리 kind 클러스터가 대략 0.3~1GiB를 쓰므로 가능하다고 판단했고, 만든 뒤 6.13GiB가 됐다. 여유가 1GiB 미만이면 이 모듈은 기존 클러스터를 위험에 빠뜨린다 — 그때는 32.4의 오버레이 구조만 렌더링으로 확인하고 넘어간다.

2단계 — 최소 구성으로 만든다

목적리전 흉내에 필요한 최소만 띄운다. 워커 노드는 두지 않는다.

cat > course/labs/infra/kind-edge.yaml <<'EOF'
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
name: edge
nodes:
  - role: control-plane
    image: kindest/node:v1.37.0@sha256:a1ed56cfb0e7b93589bdf97c8cd566405a265939e3620fc4f5de89adff580ae5
EOF
kind create cluster --config course/labs/infra/kind-edge.yaml
kubectl config get-contexts -o name
출력
kind-edge kind-study

이 모듈부터는 모든 명령에 --context를 붙인다. 컨텍스트를 바꿔 놓고 잊는 것이 멀티 클러스터 작업에서 가장 흔한 사고이고, kubectl config use-context로 전환하는 습관은 어느 클러스터에 명령을 쳤는지 나중에 알 수 없게 만든다.

3단계 — 두 클러스터가 서로 닿는지 확인한다

목적Argo CD가 edge의 API 서버에 접속할 수 있어야 한다. 안 되면 뒤의 모든 것이 무의미하다.

EDGE_IP=$(docker inspect edge-control-plane \
  --format '{{(index .NetworkSettings.Networks "kind").IPAddress}}')
echo $EDGE_IP

kubectl --context kind-study run netcheck --image=curlimages/curl:8.19.0 \
  --restart=Never --command -- sleep 60
kubectl --context kind-study exec netcheck -- \
  curl -sk -o /dev/null -m 6 -w 'edge API: %{http_code}\n' https://$EDGE_IP:6443/version
출력
172.20.0.5 edge API: 200
판정kind가 만드는 클러스터는 같은 도커 네트워크(kind)를 공유하므로 노드끼리 직접 통신한다. 실제 환경이라면 이 자리가 VPC 피어링이나 공인 엔드포인트가 되고, 거기서 막히는 경우가 실무에서는 대부분이다.

4단계 — Argo CD가 쓸 계정을 만든다

목적다른 클러스터에 들어갈 자격 증명을 만든다. M23의 문법을 그대로 쓴다.

# edge 클러스터에서
kubectl --context kind-edge apply -f course/labs/k8s/multi/00-edge-rbac.yaml
apiVersion: v1
kind: Secret
metadata:
  name: argocd-manager-token
  namespace: kube-system
  annotations:
    kubernetes.io/service-account.name: argocd-manager
type: kubernetes.io/service-account-token

토큰을 kubectl create token이 아니라 시크릿으로 만드는 것에 주의한다. M23에서 본 대로 create token은 수명이 짧아 컨트롤러가 쓰기에 맞지 않는다 — 만료되면 동기화가 조용히 멈춘다. 이 방식의 토큰은 만료가 없고, 대신 유출되면 회수할 방법이 시크릿 삭제뿐이다.

실습이라 cluster-admin을 줬다. 실제로는 배포할 네임스페이스에 한정한 Role과 RoleBinding으로 좁힌다 — GitOps 컨트롤러가 클러스터 전체 관리자 권한을 갖는 것은 M23의 관점에서 큰 위험이고, 저장소에 커밋할 수 있는 사람이 곧 클러스터 관리자가 된다는 뜻이다.

32.4따라하기 ② 리전 수만큼 배포한다

1단계 — 클러스터를 라벨과 함께 등록한다

목적리전 메타데이터를 오브젝트에 적는다. 문서가 아니라.

apiVersion: v1
kind: Secret
metadata:
  name: cluster-edge
  namespace: argocd
  labels:
    argocd.argoproj.io/secret-type: cluster
    region: edge
    tier: canary
type: Opaque
stringData:
  name: edge
  server: https://172.20.0.5:6443
  config: |
    {"bearerToken": "...", "tlsClientConfig": {"insecure": false, "caData": "..."}}

로컬 클러스터도 명시적으로 등록한다. Argo CD는 자기가 사는 클러스터를 in-cluster로 자동 인식하지만, 그 항목에는 라벨을 붙일 수 없어서 다음 단계의 클러스터 생성기가 고르지 못한다.

kubectl --context kind-study -n argocd get secret \
  -l argocd.argoproj.io/secret-type=cluster \
  -o custom-columns=NAME:.metadata.name,REGION:.metadata.labels.region,TIER:.metadata.labels.tier
출력
NAME REGION TIER cluster-edge edge canary cluster-primary primary prod

2단계 — 저장소를 리전 구조로 만든다

목적공통과 차이를 디렉터리로 나눈다. M28의 base·오버레이 구조 그대로다.

base/                    공통 정의 (매니페스트 + kustomization)
regions/edge/            카나리 — 규모를 줄이고 REGION=edge
regions/primary/         주 리전 — REGION=primary
# regions/edge/kustomization.yaml 의 차이 부분
patches:
  - target: {kind: HorizontalPodAutoscaler}
    patch: |-
      - {op: replace, path: /spec/minReplicas, value: 1}
      - {op: replace, path: /spec/maxReplicas, value: 2}
  # 노드가 하나뿐이라 분산 제약이 스케줄을 막는다
  - target: {kind: Deployment, name: journal-api}
    patch: |-
      - {op: remove, path: /spec/template/spec/topologySpreadConstraints}
configMapGenerator:
  - name: journal-config
    behavior: merge
    literals: [REGION=edge]

차이가 셋뿐이라는 점을 확인하고 넘어간다. 차이가 늘어나면 카나리 리전의 판정이 약해진다 — 거기서 통과한 것이 주 리전에서도 통과하리라는 보장이 그만큼 줄어든다.

3단계 — ApplicationSet 하나로 리전 전체를 덮는다

목적리전을 더할 때 배포 정의를 고치지 않아도 되게 만든다.

apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata: {name: journal-regions, namespace: argocd}
spec:
  goTemplate: true
  goTemplateOptions: ["missingkey=error"]
  generators:
    - clusters:
        selector:
          matchLabels:
            argocd.argoproj.io/secret-type: cluster
  template:
    metadata:
      name: 'journal-{{.metadata.labels.region}}'
    spec:
      source:
        repoURL: git://gitserver.gitops.svc/repo.git
        targetRevision: main
        path: 'regions/{{.metadata.labels.region}}'
      destination:
        server: '{{.server}}'
        namespace: 'journal'
      syncPolicy:
        automated: {prune: true, selfHeal: true}

missingkey=error가 중요하다. 이것이 없으면 region 라벨이 없는 클러스터에서 경로가 regions/<no value>가 되어 조용히 실패한다. 템플릿의 값이 비었을 때 에러로 만드는 것이 디버깅 시간을 크게 줄인다.

kubectl --context kind-study apply -f course/labs/k8s/multi/20-applicationset.yaml
kubectl --context kind-study -n argocd get applications \
  -o custom-columns=NAME:.metadata.name,SERVER:.spec.destination.server,PATH:.spec.source.path,SYNC:.status.sync.status
출력
NAME SERVER PATH SYNC journal-edge https://172.20.0.5:6443 regions/edge Synced journal-primary https://kubernetes.default.svc regions/primary Synced
판정Application 둘이 자동으로 만들어졌다. 이름·경로·대상 서버가 전부 클러스터 라벨에서 나왔다. 리전을 세 번째로 추가하려면 시크릿 하나와 디렉터리 하나만 만들면 되고, 이 파일은 그대로다.
kubectl --context kind-edge  -n journal         get deploy,sts --no-headers
kubectl --context kind-study -n journal-primary get deploy,sts --no-headers
출력
deployment.apps/journal-api 1/1 1 1 deployment.apps/web-static 1/1 1 1 statefulset.apps/redis 1/1 deployment.apps/journal-api 3/3 3 3 deployment.apps/web-static 2/2 2 2 statefulset.apps/redis 1/1
판정같은 base에서 나왔는데 규모가 다르다. edge는 1개, primary는 3개다. 차이는 오버레이에만 있고 저장소의 공통 정의는 하나다.

32.5따라하기 ③ 카나리 리전 먼저

1단계 — 카나리 리전에만 새 버전을 커밋한다

목적영향 범위를 클러스터 하나로 묶는다.

kind load docker-image journal-api:v2 --name edge   # 리전에 이미지가 있어야 한다

# regions/edge/kustomization.yaml 에만 추가
images:
  - name: journal-api
    newTag: v2

git commit -m "카나리 리전에 v2 배포" && bash course/labs/scripts/gitops-push.sh ...
출력
01:18:53 edge=journal-api:v1 primary=journal-api:v1 01:19:01 edge=journal-api:v2 primary=journal-api:v1
판정8초 만에 edge만 바뀌었고 primary는 그대로다. 같은 저장소, 같은 커밋인데 한 리전만 움직였다 — 디렉터리를 나눈 것이 이 효과를 만든다.

kind load를 먼저 한 것에 주의한다. 실제 환경에서는 레지스트리 복제가 이 자리에 온다. 리전에 이미지가 도착하지 않은 채로 매니페스트만 가면 ImagePullBackOff가 되고, 그것이 32.7의 재현이다.

2단계 — 검사 스크립트를 만든다

목적"확인했다"를 사람의 판단이 아니라 종료 코드로 만든다.

# course/labs/scripts/region-check.sh — 다섯 가지를 본다
# ① 워크로드가 원하는 수만큼 준비됐는가
# ② 재시작이 5회 이상 쌓이지 않았는가
# ②-b 진행 중인 롤아웃이 멈춰 있지 않은가   <- 32.7 이후 추가한 항목
# ③ 기대한 이미지가 돌고 있는가
# ④ /readyz 가 응답하는가
bash course/labs/scripts/region-check.sh kind-edge journal journal-api:v2
echo "종료코드=$?"
출력
워크로드 준비 OK 최대 재시작 수 0 롤아웃 journal-api 완료 롤아웃 web-static 완료 이미지 journal-api:v2 readyz {"status":"ready"} 판정: 통과 — 다음 리전으로 확산해도 된다 종료코드=0
판정종료 코드 0이 확산의 조건이다. 파이프라인에서는 이 스크립트 뒤에 확산 단계를 두면 실패 시 자동으로 멈춘다. 사람이 돌릴 때도 판단이 개입하지 않는다는 점이 같은 값어치를 낸다.

3단계 — 확산한다

목적공통 정의를 올려 나머지 리전이 따라오게 한다.

# base/kustomization.yaml 의 newTag 를 v2 로
git commit -m "확산: 전 리전 v2" && bash course/labs/scripts/gitops-push.sh ...
출력
01:19:40 primary=journal-api:v1 01:19:48 primary=journal-api:v2

이제 regions/edge의 newTag: v2는 중복이다. 확산이 끝나면 지우는 것이 좋다 — 남겨 두면 다음 배포 때 base를 올려도 edge가 따라오지 않고, 왜 한 리전만 옛 버전인지를 찾느라 시간을 쓴다.

32.6따라하기 ④ 검사와 롤백

1단계 — 나쁜 배포를 카나리에 보낸다

목적검사가 실제로 막는지 확인한다. 확인하지 않은 관문은 관문이 아니다.

# regions/edge 의 태그를 존재하지 않는 v99 로 바꿔 커밋·푸시
kubectl --context kind-edge -n journal get po --no-headers
출력
journal-api-798f987f5b-jnhlf 0/1 ImagePullBackOff 0 45s journal-api-7cb7597d96-2749k 1/1 Running 0 111s redis-0 1/1 Running 0 2m47s web-static-88f866755-9kmt7 1/1 Running 0 2m47s
판정새 파드는 못 뜨는데 옛 파드가 살아 있어 서비스는 정상이다. maxUnavailable: 0이 만든 상황이고, 이것 때문에 "준비된 파드 수" 검사는 통과한다 — 32.7의 실패 ①이 바로 이 지점이다.

2단계 — 검사가 잡는다

목적확산이 멈추는 것을 종료 코드로 확인한다.

bash course/labs/scripts/region-check.sh kind-edge journal journal-api:v99
echo "종료코드=$?"
출력
워크로드 준비 OK 최대 재시작 수 0 롤아웃 journal-api 실패: 20초 안에 끝나지 않음 롤아웃 web-static 완료 이미지 journal-api:v99 readyz 실패: 응답 없음 판정: 실패 — 확산하지 않는다 종료코드=1
판정첫 줄이 OK인데 종료 코드는 1이다. 다섯 검사 중 둘이 잡았다 — rollout status가 20초 안에 끝나지 않았고, 새 파드에 대한 readyz가 응답하지 않았다. 검사를 여러 각도로 두는 이유가 이것이다.

3단계 — 되돌린다

목적GitOps 클러스터에서 롤백이 무엇인지 확인한다. kubectl로 고치면 5초 뒤 되돌아온다(M31).

git revert --no-edit HEAD
bash course/labs/scripts/gitops-push.sh ...
출력
cd9b843 Revert "카나리 리전에 v99 (존재하지 않는 태그)" 04d6eda 카나리 리전에 v99 (존재하지 않는 태그) 01:21:29 edge=journal-api:v99 01:21:37 edge=journal-api:v2
판정8초. git reset이 아니라 git revert를 쓴 것이 요점이다 — 무슨 일이 있었는지가 이력에 남는다. 사고 회고에서 "언제 무엇을 되돌렸나"를 저장소에서 읽을 수 있어야 하고, 되돌린 커밋을 지우면 그 기록이 사라진다.
bash course/labs/scripts/region-check.sh kind-edge journal journal-api:v2
출력
판정: 통과 — 다음 리전으로 확산해도 된다

롤백 뒤에도 같은 검사를 다시 돌린다. 되돌렸다고 정상이라는 보장이 없다 — 되돌리는 과정에서 다른 것이 깨졌을 수 있다.

32.7일부러 실패시키기

실패 ① — "준비된 파드 수"만 보면 나쁜 배포를 통과시킨다

목적검사 항목을 고르는 것이 왜 어려운지 확인한다.

32.6의 상황을 다시 본다. v99 배포로 새 파드가 ImagePullBackOff인데 디플로이먼트의 readyReplicas는 여전히 기대값과 같다.

kubectl --context kind-edge -n journal get deploy journal-api \
  -o jsonpath='{.spec.replicas} / {.status.readyReplicas}{"\n"}'
출력
1 / 1
판정롤링 업데이트가 maxUnavailable: 0이라 새 파드가 준비될 때까지 옛 파드를 내리지 않는다. 그래서 "원하는 만큼 준비됨"은 계속 참이다. M15에서 이 설정을 무중단을 위해 넣었는데, 그 성질이 여기서는 검사를 무력화한다.

처음 쓴 region-check.sh에는 이 항목이 없었고, 그래서 실패한 배포에 "통과"를 줬다. 고친 방법은 rollout status를 타임아웃과 함께 보는 것이다.

for D in journal-api web-static; do
  if ! kubectl --context "$CTX" -n "$NS" rollout status "deploy/$D" --timeout=20s >/dev/null 2>&1; then
    say "롤아웃 $D" "실패: 20초 안에 끝나지 않음"; FAIL=1
  fi
done

"원하는 개수만큼 준비됨"과 "롤아웃이 끝남"은 다른 조건이다. 사전 검사를 쓸 때 이 둘을 모두 넣는다.

검사 스크립트를 처음 만들 때 또 하나 걸렸다. 셸 안의 파이썬에서 따옴표 이스케이프를 잘못 써서 SyntaxError가 났는데, 스크립트는 그대로 진행해 OK를 출력했다. 검사 도구 자체가 실패했는데 검사는 통과한 것이라 가장 위험한 형태다. 파이프에 || { echo 오류; exit 2; }를 붙여 도구 실패와 검사 실패를 구분한다.

실패 ② — 매니페스트가 같아도 클러스터가 다르면 다르게 동작한다

목적멀티 클러스터에서만 생기는 문제를 직접 만난다. 이 모듈에서 실제로 걸렸다.

롤백을 마치고 모든 파드가 정상인데 한 리전만 상태가 나빴다.

kubectl --context kind-study -n argocd get applications \
  -o custom-columns=NAME:.metadata.name,SYNC:.status.sync.status,HEALTH:.status.health.status
출력
NAME SYNC HEALTH journal-edge Synced Degraded journal-primary Synced Healthy

개별 리소스를 훑어도 Degraded인 것이 없었다. 워크로드로 내려가서 본다.

kubectl --context kind-edge -n journal get hpa
kubectl --context kind-edge -n journal describe hpa journal-api | sed -n '/Conditions/,/Events/p'
출력
journal-api Deployment/journal-api cpu: <unknown>/50% 1 2 1 Type Status Reason Message ScalingActive False FailedGetResourceMetric the HPA was unable to compute the replica count: failed to get cpu utilization: unable to get metrics for resource cpu: unable to fetch metrics from resource metrics API: the server could not find the requested resource (get pods.metrics.k8s.io)
kubectl --context kind-edge get apiservice v1beta1.metrics.k8s.io
출력
Error from server (NotFound): apiservices.apiregistration.k8s.io "v1beta1.metrics.k8s.io" not found
판정edge 클러스터에 metrics-server가 없다. M01에서 study 클러스터에는 설치했지만 새로 만든 클러스터에는 없었고, 같은 매니페스트의 HPA가 한 리전에서만 동작하지 않았다. 증상이 애플리케이션이 아니라 클러스터 수준에 있어서, 리소스를 아무리 들여다봐도 원인이 보이지 않는다.
kubectl --context kind-edge apply -f \
  https://github.com/kubernetes-sigs/metrics-server/releases/download/v0.9.0/components.yaml
kubectl --context kind-edge -n kube-system patch deploy metrics-server --type=json \
  -p '[{"op":"add","path":"/spec/template/spec/containers/0/args/-","value":"--kubelet-insecure-tls"}]'
출력 (설치 후)
kubectl --context kind-edge top nodes edge-control-plane 158m 1% 848Mi 10% journal-api Deployment/journal-api cpu: 8%/50% 1 2 1 journal-edge Synced Healthy journal-primary Synced Healthy

여기서 얻는 규칙은 하나다. 리전을 추가할 때 애플리케이션보다 먼저 전제 구성요소를 맞춘다. metrics-server, 인그레스 컨트롤러, CRD, 스토리지클래스가 그 목록이고, 이것을 클러스터 부트스트랩이라고 부른다. 애플리케이션 배포와는 다른 층이며 다른 순서로 관리한다 — 32.8에 그 이야기를 적는다.

32.8운영 관점 — 러너북과 리전 편차

러너북은 설명이 아니라 순서다

이 모듈의 산출물 중 실무에서 가장 자주 쓰이는 것은 k8s/multi/RUNBOOK.md다. 새벽 3시에 읽는 문서이므로 설명을 쓰지 않고 순서를 쓴다. 체크박스, 복사해서 붙일 명령, 판단 기준 표가 전부다.

러너북에서 가장 중요한 항목은 마지막 절이다 — "이번에 사전 검사가 잡지 못한 것을 region-check.sh에 추가한다." 32.7의 실패 ①이 그 과정을 실제로 보여 준다. 검사 항목은 처음부터 완전할 수 없고, 사고 하나가 항목 하나가 되면서 자란다.

리전 편차를 관리하는 두 층

32.7의 실패 ②는 층이 나뉘어 있지 않아서 생긴 문제다. 실무에서는 배포를 두 층으로 나눈다.

부트스트랩 층은 클러스터가 갖춰야 할 것 — metrics-server, 인그레스, 관측 스택, CRD, 정책 — 이고, 클러스터가 만들어질 때 한 번 적용된다. 애플리케이션 층이 이 모듈에서 다룬 것이다. 부트스트랩이 끝나지 않은 클러스터에 애플리케이션을 배포하면 32.7이 재현된다.

Argo CD로 두 층을 모두 관리할 수 있다 — 부트스트랩용 ApplicationSet을 따로 두는 것이 흔한 구성이고, 새 클러스터를 등록하면 그것이 먼저 동기화된다. 이 교재는 부트스트랩을 rebuild.sh와 각 모듈의 수동 설치로 해 왔는데, 클러스터가 여럿이 되는 순간 그 방식은 유지되지 않는다.

이미지 분산이 먼저다

32.5에서 kind load를 먼저 했다. 실제 환경에서 이 자리는 레지스트리 복제이고, 여기가 글로벌 롤아웃에서 가장 자주 병목이 된다. 리전이 다섯이면 이미지가 다섯 곳에 도착해야 하고, 도착 확인 없이 매니페스트만 보내면 그 리전은 ImagePullBackOff가 된다.

러너북 A절에 "모든 리전의 클러스터에 그 이미지가 있는가"를 넣은 이유다. 확인 방법은 환경마다 다르지만(레지스트리 API 조회, 복제 상태 확인), 확인 없이 넘어가지 않는다는 원칙은 같다.

되돌릴 수 없는 변경

이 모듈의 롤백은 git revert 한 줄이었다. 그것이 통하는 이유는 변경이 되돌릴 수 있는 것이었기 때문이다 — 이미지 태그를 바꾼 것뿐이다.

되돌릴 수 없는 변경이 섞이면 이야기가 달라진다. 데이터베이스 스키마를 바꾸는 마이그레이션, 메시지 형식 변경, 저장된 데이터의 구조 변경이 그렇다. 옛 코드로 되돌려도 데이터는 새 형식으로 남아 있다. 이런 변경은 두 단계로 나눈다 — 먼저 두 형식을 모두 읽을 수 있는 버전을 배포하고, 그 배포가 안정된 뒤에 형식을 바꾼다. 러너북 A절의 마지막 체크 항목이 이것을 묻는다.

Part 6이 끝났다. 여기까지 쓴 것은 전부 쿠버네티스가 이미 아는 리소스였다 — 디플로이먼트, 서비스, 인그레스, 그리고 남이 만든 CRD(Rollout, Application). 우리 조직에만 있는 개념 — "저널 서비스 한 벌"이나 "고객사 하나의 환경" — 을 표현하려면 리소스 종류 자체를 새로 만들어야 한다.

M33에서 CRD로 새 리소스 종류를 정의하고, 그것을 지켜보며 실제 리소스를 만드는 오퍼레이터를 쓴다. M30의 Argo Rollouts와 M31의 Argo CD가 어떻게 동작하는지가 그때 안쪽에서 보인다.
