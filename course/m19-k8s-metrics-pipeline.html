메트릭 파이프라인과 프로메테우스 스택

Part 3에서 정한 숫자들은 근거가 얇다. requests.cpu: 50m은 kubectl top의 순간값에서 왔고, HPA 목표 50%는 그냥 정한 값이다. kubectl top은 기록을 남기지 않기 때문에 이보다 나은 근거를 만들 수 없다. 이 모듈에서 기록하는 층을 세우고, 클러스터의 메트릭이 어디서 오는지를 말이 아니라 질의로 구분한다.

핵심 3줄

1. 언어가 다른 두 번째 앱을 클러스터에 들여오고, 그 과정에서 베이스 이미지 태그가 움직여 빌드가 깨진 것을 직접 고친다.

2. 프로메테우스 스택을 설치해 타깃 6개가 DOWN인 상태를 확인하고, 원인을 노드 안에서 찾아 28/28로 만든다.

3. cAdvisor · kube-state-metrics · metrics-server가 같은 파드에 대해 각각 무엇을 답하는지 질의로 구분한다.

19.1kubectl top으로는 알 수 없는 것

M16에서 requests.cpu: 50m을 정할 때 근거로 삼은 것은 kubectl top pod가 보여준 2m이었다. 그 값이 평상시 사용량인지, 하루 중 가장 낮은 순간이었는지, 한 시간 전에는 얼마였는지 알 방법이 없었다.

M17에서는 더 곤란했다. HPA가 파드를 8개까지 늘렸다가 줄이는 과정을 15초마다 kubectl get hpa로 찍어 관찰 로그를 만들었다. 그 로그가 없었다면 "왜 3분이나 안 줄었는가"를 되짚을 수 없었을 것이다. 사람이 터미널을 지키고 있는 동안에만 기록이 남는 상태였다.

M17 8절에서 CPU가 나쁜 확장 기준일 수 있다고 했다 — 대기가 일인 API 서버는 큐가 쌓이고 P99가 무너지는 동안 CPU가 20%에 머문다. 그런 판단을 하려면 P99가 있어야 하는데, P99는 순간값에서 계산할 수 없다. 분포는 시간에 걸친 기록에서만 나온다.

이 모듈에서 세우는 것은 그 기록층이다. 그리고 기록을 시작하는 순간 새로운 질문이 생긴다 — 지금 클러스터에서 나오는 메트릭은 대체 누가 만들어 낸 것인가. kubectl top의 숫자와 프로메테우스의 숫자는 같은 것인가 다른 것인가. 그 구분이 이 모듈의 후반부다.

19.2이론 — 누가 무엇을 재는가

책 3.1은 메트릭과 로그를 나눈다. 메트릭은 시간에 따라 변하는 숫자이고 로그는 일어난 일의 기록이다. 둘은 답할 수 있는 질문이 다르다 — "지금 에러율이 몇 퍼센트인가"는 메트릭이, "그 에러가 정확히 무엇이었나"는 로그가 답한다. 메트릭으로 이상을 발견하고 로그로 원인을 찾는 것이 일반적인 순서이고, 이 과정도 M19~M21에서 메트릭을, M22에서 로그를 다룬다.

책 3.2가 나누는 두 번째 축은 블랙박스 black-box와 화이트박스 white-box다. 블랙박스는 밖에서 두드려 보는 것이다 — "이 URL이 200을 돌려주는가". 화이트박스는 안에서 스스로 보고하는 것이다 — "커넥션 풀에 여유가 몇 개 남았는가". 블랙박스는 사용자가 겪는 것에 가깝고 화이트박스는 원인에 가깝다. 이 모듈이 세우는 것은 화이트박스 쪽이다.

풀 모델 — 왜 긁어 가는가

프로메테우스는 애플리케이션이 지표를 보내오기를 기다리지 않는다. 주기적으로 찾아가 긁어 온다. 이것을 풀 모델이라고 하고, 반대는 앱이 수집기로 밀어 넣는 푸시 모델이다.

풀 모델의 값은 대상이 살아 있는지를 수집 자체가 알려준다는 데 있다. 긁으러 갔는데 응답이 없으면 그 사실이 up=0이라는 메트릭이 된다. 푸시 모델에서는 지표가 안 오는 것이 "앱이 죽었다"인지 "앱이 한가하다"인지 구분되지 않는다. 대신 풀 모델은 프로메테우스가 대상에 네트워크로 닿을 수 있어야 하고, 짧게 살다 죽는 배치 작업처럼 긁으러 갈 때쯤 이미 없는 대상에는 맞지 않는다.

클러스터 메트릭의 세 출처

책 3.4가 구분하는 것이 이 부분이고, 실습에서 가장 자주 헷갈리는 지점이다. 세 가지는 서로 다른 질문에 답한다.

출처답하는 질문대표 메트릭
cAdvisor (kubelet 내장)이 컨테이너가 실제로 얼마나 쓰고 있나container_memory_working_set_bytes
container_cpu_usage_seconds_total
kube-state-metrics KSM오브젝트에 무엇이라고 적혀 있나kube_deployment_spec_replicas
kube_pod_container_resource_requests
애플리케이션 자신이 앱이 무슨 일을 했나http_server_requests_seconds

여기에 metrics-server는 들어 있지 않다. metrics-server는 수집원이 아니라 소비자다 — cAdvisor와 같은 곳(kubelet)에서 값을 읽어 kubectl top과 HPA에 제공한다. 다른 점은 보관이다. metrics-server는 최근값 하나만 메모리에 들고 있고, 프로메테우스는 시계열로 쌓는다. M17에서 HPA는 잘 동작했지만 "그때 왜 그랬는지"를 나중에 되짚을 수 없었던 이유가 이것이다.

세 출처의 값이 어긋날 때가 진단의 출발점이다. KSM이 replicas=3이라는데 cAdvisor에 파드가 둘만 보이면 하나가 안 뜬 것이고, cAdvisor의 메모리가 KSM의 requests를 훨씬 넘고 있으면 requests를 잘못 잡은 것이다. 19.5에서 이 대조를 직접 한다.

19.3따라하기 ① 두 번째 앱을 들여온다

지금까지 실습 대상은 journal-api 하나였다. Node로 만든 이 앱은 0.3초에 뜨고 메모리를 25Mi쯤 쓴다 — M15에서 프로브 실습을 하려고 sleep 8로 느린 기동을 흉내 내야 했을 만큼 가볍다.

실제 클러스터에는 이런 앱만 있지 않다. 여기서 JVM 애플리케이션을 하나 들여온다. 기동이 느리고 메모리를 많이 쓰며, 메트릭을 노출하는 방식도 다르다. 그 차이 자체가 이 파트의 교재다.

1단계 — 기존 자산을 가져온다

목적이미 검증된 Spring Boot 앱을 course의 실습 파일로 편입한다.

docs/kubernetes-monitoring/kubernetes/labs/apps/order-api에 Spring Boot 4.1.0 애플리케이션이 있다. Micrometer로 /actuator/prometheus를 노출하고, M21에서 쓸 지연·에러 생성기(ChaosController)를 갖고 있다.

DST=course/labs/apps/order-api
mkdir -p "$DST"
rsync -a --exclude '.gradle' --exclude 'build' "$SRC/" "$DST/"
find "$DST" -type f | head

이 앱의 application.yml에서 눈여겨볼 두 줄이 있다.

management:
  endpoints:
    web:
      exposure:
        # 필요한 것만 연다. '*' 로 열면 env·heapdump 같은 민감 엔드포인트까지 노출된다.
        include: health,info,prometheus
  metrics:

2단계 — 빌드가 깨진다. 고친다

목적가져온 Dockerfile을 그대로 빌드해 보고, 실패 원인을 이 과정이 이미 가르친 개념으로 설명한다.

먼저 그래들 래퍼가 없다. Dockerfile이 ./gradlew를 호출하므로 만들어 준다.

cd course/labs/apps/order-api
gradle wrapper --gradle-version 9.2.0

그리고 빌드한다.

docker build -t order-api:v1 .
출력 (끝부분)
> [stage-1 3/7] RUN useradd -u 1000 -m app: 0.136 useradd: UID 1000 is not unique ------ Dockerfile:10 -------------------- 8 | FROM eclipse-temurin:21-jre 9 | WORKDIR /app 10 | >>> RUN useradd -u 1000 -m app 11 | USER 1000 -------------------- ERROR: failed to build: failed to solve: process "/bin/sh -c useradd -u 1000 -m app" did not complete successfully: exit code: 4

이 Dockerfile은 작성 당시 동작했다. 지금 깨진 이유를 베이스 이미지에서 확인한다.

docker run --rm eclipse-temurin:21-jre getent passwd 1000
출력
ubuntu:x:1000:1000:Ubuntu:/home/ubuntu:/bin/bash
판정베이스 이미지에 이미 UID 1000을 쓰는 ubuntu 사용자가 있다. 이미지가 우분투 기반으로 바뀌면서 생긴 것이고, 21-jre라는 태그는 그대로인데 내용이 달라졌다. M03에서 "태그는 움직이는 포인터"라고 배운 것이 이 파일을 깨뜨린 실제 사례다.

두 곳을 고친다. UID를 겹치지 않는 값으로 바꾸고, 베이스 이미지를 다이제스트까지 고정한다.

# 지금 태그가 가리키는 다이제스트를 확인한다
docker pull -q eclipse-temurin:21-jdk
docker image inspect eclipse-temurin:21-jdk --format '{{index .RepoDigests 0}}'
docker image inspect eclipse-temurin:21-jre --format '{{index .RepoDigests 0}}'

그 값을 Dockerfile에 박는다.

FROM eclipse-temurin@sha256:<jdk 다이제스트> AS builder
WORKDIR /build
COPY . .
RUN ./gradlew bootJar --no-daemon
# 스프링 부트 계층 추출. 의존성과 애플리케이션 코드를 다른 레이어로 나눠
# 소스만 고쳤을 때 무거운 의존성 레이어가 캐시에 남게 한다 (M04 의 그 원리다).
RUN cp build/libs/*.jar app.jar \
 && java -Djarmode=tools -jar app.jar extract --layers --launcher --destination extracted

FROM eclipse-temurin@sha256:<jre 다이제스트>
WORKDIR /app
# UID 1000 은 베이스 이미지가 이미 쓰고 있다. 충돌하지 않는 값을 골라 명시한다.
RUN useradd -u 10001 -m app
USER 10001
COPY --from=builder /build/extracted/dependencies/ ./
COPY --from=builder /build/extracted/spring-boot-loader/ ./
COPY --from=builder /build/extracted/snapshot-dependencies/ ./
COPY --from=builder /build/extracted/application/ ./
# 컨테이너 메모리 제한(M16 의 limits)의 70% 를 힙 상한으로 삼는다.
# 이 옵션이 없으면 JVM 이 호스트 전체 메모리를 기준으로 힙을 잡아 OOMKilled 가 난다.
ENV JAVA_TOOL_OPTIONS="-XX:MaxRAMPercentage=70.0"
ENTRYPOINT ["java", "org.springframework.boot.loader.launch.JarLauncher"]
docker build -t order-api:v1 .
docker images order-api --format '{{.Repository}}:{{.Tag}} {{.Size}}'
출력

판정524MB다. M04에서 멀티스테이지로 246MB까지 줄인 journal-api(내려받는 크기 59.3MB)와 비교하면 여덟 배가 넘는다. JVM 런타임의 대가이고, 이 차이가 파드 기동 시간과 노드 메모리에 그대로 나타난다.

3단계 — 클러스터에 배포한다

목적두 앱이 다른 네임스페이스에 공존하는 상태를 만든다. M20의 스크레이프 대상 선택이 이 구분을 쓴다.

kind load docker-image order-api:v1 --name study
kubectl apply -f course/labs/k8s/apps/
kubectl -n apps rollout status deploy/order-api

매니페스트에서 journal-api와 다른 점 세 가지를 짚어 둔다.

      terminationGracePeriodSeconds: 40     # JVM 은 종료에 시간이 더 걸린다 (M15)
      securityContext:                      # 이 블록의 의미는 M24 에서 다룬다
        runAsUser: 10001                    # Dockerfile 에서 만든 UID. 루트로 돌지 않는다
      containers:
        - name: order-api
          startupProbe:                     # M15 에서는 흉내였던 것이 여기서는 진짜다
            httpGet: {path: /actuator/health/liveness, port: http}
            periodSeconds: 2
            failureThreshold: 30
          resources:
            requests:
              cpu: 200m                     # journal-api 는 50m 이었다 (M16)
              memory: 384Mi

securityContext는 파드가 어떤 권한으로 도는지를 정하는 블록이다. 여기서는 "루트가 아닌 10001번 사용자로 돈다"만 읽고 넘어간다 — 어떤 항목이 있고 무엇을 강제할 수 있는지는 M24에서 정면으로 다룬다. 지금 이 줄이 있는 이유는 order-api의 이미지가 그렇게 만들어져 있어서다.

목적기본값에 맡기지 않고 보존 기간·저장소·배치를 정한다. 기본값은 노트북에 맞지 않는다.

helm repo update
helm search repo prometheus-community/kube-prometheus-stack --versions | head -3
출력
NAME CHART VERSION APP VERSION DESCRIPTION prometheus-community/kube-prometheus-stack 89.2.2 v0.93.1 kube-prometheus-stack collects Kubernetes manif... prometheus-community/kube-prometheus-stack 89.2.1 v0.93.1 kube-prometheus-stack collects Kubernetes manif...

관측 스택을 한 노드에 모은다. M16에서 쓴 nodeSelector가 여기서 다시 쓰인다.

kubectl label node study-worker2 workload=observability

course/labs/monitoring/kps-values.yaml의 핵심 부분이다. 전체는 저장소 파일을 참조한다.

prometheus:
  service:
    # NodePort 를 쓰지 않는다. kind 설정(M01)이 호스트로 넘긴 포트는 18080/18443 뿐이고,
    # 그 둘은 인그레스가 쓰고 있다. 프로메테우스 UI 는 port-forward 로 본다.
    type: ClusterIP
  prometheusSpec:
    # 관측 스택을 한 노드에 모은다 (M16 nodeSelector).
    # 흩어 놓으면 관측 대상이 앓을 때 관측 스택도 같이 앓는다.
    nodeSelector:
      workload: observability
    scrapeInterval: 30s
    evaluationInterval: 30s
    # 실습용. 노트북 디스크를 아끼려고 짧게 잡는다.
    # 운영에서는 보존 기간이 곧 "얼마나 오래된 장애를 되짚을 수 있는가"다.
    retention: 3d
    retentionSize: 4GB
    # storageSpec 을 생략하면 emptyDir 이 되어 파드가 재시작되면 지표가 전부 사라진다.
    storageSpec:
      volumeClaimTemplate:
        spec:
          accessModes: ["ReadWriteOnce"]
          resources:
            requests:
              storage: 8Gi
    resources:

19.7일부러 실패시키기

실패 ① 컨트롤 플레인 타깃 6개가 DOWN이다

6단계에서 본 상태다. 설치는 성공했고 파드는 다 Running인데 타깃 여섯이 DOWN이다. 무엇이 문제인지부터 읽는다.

원인 읽기

kube-controller-manager: Get "https://172.20.0.4:10257/metrics": dial tcp 172.20.0.4:10257: connect: connection refused kube-etcd: Get "http://172.20.0.4:2381/metrics": dial tcp 172.20.0.4:2381: connect: connection refused kube-proxy: Get "http://172.20.0.2:10249/metrics": dial tcp 172.20.0.2:10249: connect: connection refused kube-proxy: Get "http://172.20.0.3:10249/metrics": dial tcp 172.20.0.3:10249: connect: connection refused kube-proxy: Get "http://172.20.0.4:10249/metrics": dial tcp 172.20.0.4:10249: connect: connection refused kube-scheduler: Get "https://172.20.0.4:10259/metrics": dial tcp 172.20.0.4:10259: connect: connection refused

전부 connection refused다. 인증서 문제도 권한 문제도 아니고 그 포트에서 아무도 듣고 있지 않다. 노드 안에서 확인한다.

원인

네 구성요소가 메트릭을 루프백에만 열고 있다. 자기 노드 안에서만 접근할 수 있다는 뜻이고, 다른 노드에 있는 프로메테우스는 닿을 수 없다. kind의 기본값이 이렇고, 기본 보안 설정으로는 합당하다 — 메트릭 포트는 인증 없이 클러스터 내부 정보를 내놓기 때문이다.

여기서 두 가지가 드러난다. 첫째, 차트를 설치했다고 관측이 되는 것이 아니다. 차트는 "이 주소를 긁어라"라는 설정을 만들 뿐이고 대상이 열려 있는지는 모른다. 둘째, DOWN인 타깃은 조용하다 — 어디에도 빨간불이 켜지지 않고, 그 구성요소의 지표만 조용히 비어 있다. 스케줄러가 이상해져도 대시보드에 아무것도 안 나오는 상태다.

고친다 
docker exec study-control-plane sh -c "
  sed -i 's|--bind-address=127.0.0.1|--bind-address=0.0.0.0|' /etc/kubernetes/manifests/kube-controller-manager.yaml
  sed -i 's|--bind-address=127.0.0.1|--bind-address=0.0.0.0|' /etc/kubernetes/manifests/kube-scheduler.yaml
  sed -i 's|--listen-metrics-urls=http://127.0.0.1:2381|--listen-metrics-urls=http://0.0.0.0:2381|' /etc/kubernetes/manifests/etcd.yaml"

/etc/kubernetes/manifests는 정적 파드 static pod 디렉터리다. kubelet이 이 디렉터리를 지켜보다가 파일이 바뀌면 파드를 다시 만든다. apiserver를 거치지 않으므로 apiserver 자신도 이 방식으로 뜬다 — 닭과 달걀 문제를 푸는 장치다.

kube-proxy는 정적 파드가 아니라 데몬셋이므로 ConfigMap을 고치고 다시 굴린다.

kubectl -n kube-system get cm kube-proxy -o yaml \
  | sed 's|metricsBindAddress: ""|metricsBindAddress: "0.0.0.0:10249"|' \
  | kubectl apply -f -
kubectl -n kube-system rollout restart ds kube-proxy
kubectl -n kube-system rollout status ds kube-proxy
중간에 apiserver가 잠깐 끊긴다 정적 파드 셋이 동시에 재기동되는 동안 apiserver도 영향을 받아 Error from server (Timeout): the server was unable to return a response in the time allotted가 날 수 있다. 실제로 이 실습에서 kube-proxy ConfigMap 수정이 한 번 실패했다. 컨트롤 플레인이 안정될 때까지 기다렸다가 같은 명령을 다시 치면 된다.

1~2분 뒤 다시 센다.

curl -s 'http://localhost:9090/api/v1/targets?state=any' | python3 -c "
import json,sys,collections

print('총', len(d), dict(collections.Counter(t['health'] for t in d)))"

판정28/28이다. kube-controller-manager·kube-scheduler·kube-etcd·kube-proxy가 전부 살아났다. 이제 etcd_request_duration_seconds나 scheduler_pending_pods 같은 지표를 볼 수 있고, 12단계에서 상위 시계열에 etcd_가 등장한 것도 이 수정 덕분이다.

실패 ② 노출하는데 수집되지 않는다

10단계에서 이미 만난 상태다. 앱은 /actuator/prometheus로 274개 계열을 내놓고 있는데 프로메테우스에는 http_server_requests_seconds_count가 0건이다.

원인

프로메테우스는 긁을 대상 목록을 스스로 발견하지 않는다. 오퍼레이터가 관리하는 이 설치에서는 ServiceMonitor·PodMonitor라는 오브젝트가 그 목록이 되고, 차트는 자기가 설치한 구성요소들의 것만 만들어 줬다.

kubectl get servicemonitor -A --no-headers | wc -l
kubectl get servicemonitor -n apps --no-headers 2>/dev/null | wc -l
판정monitoring 네임스페이스에는 여럿 있고 apps에는 하나도 없다. 앱을 배포하는 것과 그 앱을 관측 대상으로 등록하는 것은 별개의 일이며, 후자를 잊는 것이 실무에서 가장 흔한 관측 공백이다.

고치는 것은 M20의 1단계다. 거기서 라벨 세 겹이 어떻게 연결되는지 보고, 일부러 어긋뜨려 타깃이 사라지는 것까지 재현한다.

19.8운영 관점 — 무엇을 재지 않을 것인가

12단계에서 본 84,771개는 파드 스무 개 남짓한 클러스터의 숫자다. 프로메테우스의 메모리 사용량은 대체로 활성 시계열 수에 비례하므로, 이 값이 곧 비용이다.

시계열이 늘어나는 방식은 두 가지다. 지표 종류가 느는 것과 라벨 카디널리티 label cardinality가 느는 것인데, 사고는 거의 항상 후자에서 난다. 라벨 하나가 가질 수 있는 값의 가짓수가 곱셈으로 들어가기 때문이다. method(5가지) × status(6가지) × uri(10가지)면 300개지만, uri에 /api/orders/{id}의 실제 id가 들어가면 주문 수만큼 시계열이 생긴다. 하루 만에 수십만 개가 되고 프로메테우스가 메모리를 다 쓴다.

규칙은 단순하다. 값의 가짓수가 유한하고 미리 알 수 있는 것만 라벨로 쓴다. 사용자 ID, 주문 번호, 요청 ID, IP 주소, 타임스탬프는 라벨이 아니다. 그런 것을 붙여 조회하고 싶으면 로그에 남기고 로그 쪽에서 찾는다 — M22의 주제이고, 거기서 같은 실수를 로그 라벨로 재현한다.

히스토그램도 같은 계산이 필요하다. 3단계의 slo: 50ms,100ms,200ms,500ms,1s는 경계를 다섯 개 더한다는 뜻이고, 기본 버킷에 더해져 시계열이 그만큼 는다. P99를 봐야 하는 지표에만 켜는 것이 원칙이다.

보존 기간은 무엇으로 정하나

retention: 3d는 실습용으로 정한 값이지만, 운영에서 이 숫자를 정하는 기준은 "장애를 며칠 뒤에 되짚는가"다. 금요일 밤 장애를 월요일에 분석한다면 3일로는 모자란다. 반대로 무한정 늘릴 수도 없다 — 로컬 디스크에 쌓는 구조라 저장소가 곧 노드의 크기다.

일반적인 해법은 두 층으로 나누는 것이다. 최근 며칠은 프로메테우스가 원본 해상도로 들고, 그보다 오래된 것은 원격 저장소로 넘겨 해상도를 낮춰 오래 보관한다. 이 과정에서는 다루지 않지만, retentionSize와 retention 중 먼저 걸리는 쪽이 이긴다는 11단계의 사실은 기억해 둘 만하다 — 기간만 늘려 놓고 용량을 그대로 두면 실제 보존은 늘지 않는다.

관측 스택을 어디에 둘 것인가

4단계에서 nodeSelector: workload: observability로 관측 스택을 한 노드에 모았다. 관측 대상과 섞어 놓으면 대상이 앓을 때 관측 스택도 같이 앓는다 — 노드 메모리가 모자라 파드가 축출될 때 프로메테우스가 함께 죽으면, 무슨 일이 있었는지 볼 방법이 사라진다. M16의 QoS로 말하면 관측 스택은 Guaranteed에 가깝게 두는 것이 맞다.

더 나아가면 관측 스택을 다른 클러스터에 두기도 한다. 클러스터 자체가 죽었을 때도 지표가 남아 있어야 하기 때문이다. 노트북 한 대에서는 할 수 없는 이야기지만, "관측 대상과 관측자를 얼마나 분리할 것인가"라는 질문은 규모와 무관하게 같다.
