이미지와 레이어

태그는 움직인다. 다이제스트는 움직이지 않는다. 이 한 문장의 차이가 "내 노트북에서는 됐는데요"의 절반을 만든다. 이미지를 열어 레이어를 세고, 태그와 다이제스트를 손으로 구분한다.

초반40분Docker Engine 29.2.1
2026-09-03 검증 · nginx:1.29-alpine · alpine:3.22 · 버전은 실습 당일 다시 확인한다
사전 조건
  • M02 완료 — 로컬에 nginx:1.29-alpine과 alpine:3.22 이미지가 받아져 있다
  • 없으면 docker pull nginx:1.29-alpine alpine:3.22

핵심 3줄

1. docker history와 image inspect로 nginx 이미지 92.7MB가 어느 레이어에서 왔는지 짚고, 20줄짜리 히스토리 뒤에 실제 파일시스템 레이어는 8개뿐임을 센다.

2. docker tag로 같은 이름을 다른 이미지에 옮겨 태그는 포인터임을 3초 만에 재현하고, 되돌릴 수 없는 참조가 필요한 자리에는 이름@sha256:…으로 받는다.

3. docker system df로 회수 가능한 용량을 읽고, kind 노드 이미지를 날리지 않는 범위의 prune을 고른다.

3.1왜 레이어를 알아야 하나

M02에서 docker run nginx:1.29-alpine을 쳤을 때 도커는 92.7MB를 받아왔다. 다음에 같은 베이스를 쓰는 다른 이미지를 받으면 그만큼을 다시 받지 않는다. 이 구조를 모르면 빌드가 5초에 끝날 수 있는 상황에서 5분을 기다리게 된다(M04의 주제).

더 중요한 이유는 재현성이다. 팀원 A의 노트북에서는 통과한 테스트가 CI에서 실패한다. 둘 다 myapp:latest를 썼는데 내용이 다르기 때문이다. 쿠버네티스에서는 이 문제가 더 조용히 온다 — 파드가 재시작되면서 같은 태그를 다시 받았는데 그 사이 레지스트리의 태그가 다른 이미지를 가리키게 되면, 클러스터 안에서 버전이 섞인 파드가 돌아간다. 원인을 찾기 가장 어려운 종류의 장애다.

3.2이론 — 레이어 · 태그 · 다이제스트

레이어

레이어 (Layer)는 파일시스템의 변경분 한 뭉치다. Dockerfile의 RUN · COPY · ADD 명령 하나가 레이어 하나를 만든다. 이미지는 이 레이어들을 순서대로 쌓아 올린 것이고, 실행할 때 유니온 파일시스템 (Union Filesystem)이 여러 층을 겹쳐 하나의 디렉터리 트리로 보여준다.

모든 레이어는 읽기 전용이다. 컨테이너를 실행하면 맨 위에 쓰기 가능한 레이어가 하나 추가되고, 컨테이너 안에서 만든 파일은 전부 여기 쌓인다. docker rm으로 컨테이너를 지우면 이 레이어만 사라진다 — 이미지는 그대로다. M02에서 컨테이너를 지워도 이미지가 남아 있던 이유가 이것이고, 컨테이너 안의 데이터를 살리려면 볼륨이 필요한 이유이기도 하다(M05).

레이어는 내용으로 식별되므로 공유된다. 같은 알파인 베이스를 쓰는 이미지가 다섯 개면 그 베이스 레이어는 디스크에 한 벌만 있다. 레지스트리에서 받을 때도 이미 가진 레이어는 건너뛴다.

태그와 다이제스트

태그다이제스트
생김새nginx:1.29-alpinenginx@sha256:5616878291a2…
정체사람이 붙인 이름. 가리키는 대상을 바꿀 수 있다이미지 내용을 SHA-256으로 계산한 값. 내용이 1바이트만 달라도 완전히 달라진다
같은 문자열이 내일도 같은 이미지인가보장 없음보장됨
쓰는 곳사람이 읽고 고르는 자리재현이 필요한 자리 — CI, 프로덕션 배포 매니페스트, M01의 kind 노드 이미지

표의 "배포 매니페스트"는 쿠버네티스에 무엇을 띄울지 적은 YAML(파드 · 디플로이먼트 정의, M08부터)을 말한다. 이 모듈 뒤쪽에서 나오는 "레지스트리 매니페스트"는 다른 것이다 — 레지스트리가 이미지 하나의 레이어 목록과 설정을 적어둔 JSON 문서(OCI 이미지 매니페스트)로, 다이제스트는 바로 이 문서를 해시한 값이다. 두 낱말이 같은 문장에 나오면 앞에 붙은 수식어로 구분한다.

latest를 쓰지 않는 근거 — 책 1.3.1

책 1.3.1(이미지 관리 모범 사례)은 컨테이너 빌드 자체는 다루지 않는다고 선을 그으면서도 두 가지는 못 박는다. 프로덕션에서 latest 태그를 쓰지 말 것, 그리고 태그가 소스의 어느 시점을 가리키는지 알 수 있는 전략(버전 번호나 커밋 해시)을 세울 것. 이 과정이 첫 도커 모듈부터 태그를 강제하는 근거가 이 절이다.

이유는 위 표에 다 들어 있다. latest는 특별한 태그가 아니라 태그를 생략했을 때 채워지는 기본값일 뿐이고, "가장 최신"을 보장하지 않으며, 누군가 마지막으로 그 이름을 붙인 이미지를 가리킨다. 문제는 이것이 움직이는 포인터라는 점이 배포 시스템 안에서 세 번 증폭된다는 데 있다. 첫째, 무엇이 배포됐는지 기록이 남지 않는다 — 매니페스트에 myapp:latest라고 적혀 있으면 지난주 장애 때 돌던 것이 어느 빌드였는지 알 길이 없다. 둘째, 롤백이 불가능하다 — 이전 버전을 가리키는 이름이 없으므로 "직전으로 되돌린다"는 명령을 만들 수 없다. 셋째, 쿠버네티스는 노드에 이미 같은 태그의 이미지가 있으면 다시 받지 않는 것이 기본(imagePullPolicy: IfNotPresent)인데, latest만은 예외로 매번 받도록 정책이 바뀐다. 그래서 노드 A는 어제 캐시한 것을, 노드 B는 오늘 받은 것을 돌리는 상황이 같은 디플로이먼트 안에서 생긴다. 3.5절의 실패①이 이 셋째 상황을 노트북 한 대에서 재현한다.

반대로 태그를 커밋 해시나 버전으로 박으면 세 문제가 함께 사라진다. 매니페스트가 곧 배포 기록이 되고(책 1.2가 말하는 선언형 관리의 전제), 롤백은 이전 태그로 되돌리는 한 줄이 되며(M10), 모든 노드가 같은 바이트를 돈다. 여기서 더 나가 재현이 결정적인 자리 — CI 베이스 이미지, M01의 kind 노드 — 에는 태그 대신 다이제스트를 쓴다. 이 과정은 이 규칙을 예제 매니페스트에까지 적용하고, M26에서는 아예 클러스터가 latest 태그를 거부하도록 어드미션 정책을 만든다.

3.3따라하기 ① 이미지를 열어본다

1단계. 이미지 목록과 크기를 본다

목적이미지 하나가 차지하는 크기와 식별자를 확인한다.

docker images nginx --digests
실행 결과
REPOSITORY TAG DIGEST IMAGE ID CREATED SIZE nginx 1.29-alpine sha256:5616878291a2eed594aee8db4dade5878cf7edcb475e59193904b198d9b830de 5616878291a2 4 months ago 92.7MB

CREATED가 4개월 전인 것에 주의한다. 이것은 이미지가 빌드된 시각이지 내가 받은 시각이 아니다. 공식 이미지도 몇 달씩 그대로인 경우가 있고, 그 사이 베이스 OS에 보안 패치가 나왔을 수 있다 — M07에서 취약점 스캔으로 확인한다.

2단계. 레이어별 크기를 읽는다

목적92.7MB가 어디서 왔는지 분해한다. 이미지를 줄이려면 어디를 손대야 하는지 보인다.

docker history nginx:1.29-alpine

읽는 법이 셋이다.

  • 맨 아래가 시작점이다. ADD alpine-minirootfs… 9.35MB가 알파인 리눅스 루트 파일시스템, 즉 베이스 이미지다. 그 위로 nginx 설치(RUN … apkArch) 50.7MB가 얹혔다
  • 0B 레이어가 많다. ENV · CMD · EXPOSE · ENTRYPOINT는 메타데이터만 바꾸므로 파일이 늘지 않는다. 이미지 크기를 줄일 때 이런 줄은 건드릴 필요가 없다
  • <missing>은 오류가 아니다. 중간 레이어들은 별도의 이미지 ID를 갖지 않고 최상위 이미지에만 ID가 붙기 때문에 이렇게 표시된다
판정가장 큰 레이어가 RUN으로 시작하는 줄이다. 이미지를 줄이는 작업은 거의 항상 RUN 레이어를 손보는 일이라는 것이 M04의 출발점이다.

3.4따라하기 ② 태그와 다이제스트

4단계. 태그를 하나 더 붙여본다

목적태그가 이름표일 뿐 복사가 아니라는 것을 확인한다.

docker tag nginx:1.29-alpine myweb:v1
docker images --format 'table {{.Repository}}\t{{.Tag}}\t{{.ID}}\t{{.Size}}' | grep -E 'REPOSITORY|nginx|myweb|alpine'
실행 결과
REPOSITORY TAG IMAGE ID SIZE alpine 3.22 14358309a308 13.4MB myweb v1 5616878291a2 92.7MB nginx 1.29-alpine 5616878291a2 92.7MB
판정myweb:v1과 nginx:1.29-alpine의 IMAGE ID가 같다. 디스크 사용량도 92.7MB가 두 배로 늘지 않았다 — SIZE 열은 각 이미지의 총 크기를 보여줄 뿐이고 실제로는 같은 레이어를 공유한다.

이름만 붙었을 뿐 이미지는 하나다. docker rmi myweb:v1을 하면 태그만 떨어져 나가고 이미지 자체는 nginx:1.29-alpine이 참조하는 한 남는다.

5단계. 다이제스트로 받아본다

목적재현이 필요한 자리에서 쓰는 방식을 익힌다. M01에서 kind 노드 이미지에 쓴 것과 같은 방법이다.

docker images alpine --digests
실행 결과
REPOSITORY TAG DIGEST IMAGE ID CREATED SIZE alpine 3.22 sha256:14358309a308569c32bdc37e2e0e9694be33a9d99e68afb0f5ff33cc1f695dce 14358309a308 2 months ago 13.4MB
docker pull alpine@sha256:14358309a308569c32bdc37e2e0e9694be33a9d99e68afb0f5ff33cc1f695dce
실행 결과
Digest: sha256:14358309a308569c32bdc37e2e0e9694be33a9d99e68afb0f5ff33cc1f695dce Status: Image is up to date for alpine@sha256:14358309a308569c32bdc37e2e0e9694be33a9d99e68afb0f5ff33cc1f695dce docker.io/library/alpine@sha256:14358309a308569c32bdc37e2e0e9694be33a9d99e68afb0f5ff33cc1f695dce

이미 같은 내용을 갖고 있으므로 아무것도 받지 않고 up to date로 끝났다. 이 명령은 1년 뒤에 실행해도 정확히 같은 이미지를 가져온다. 태그였다면 그 사이 알파인 3.22의 패치 릴리스가 나오면서 다른 내용을 받았을 것이다.

docker image inspect alpine:3.22 -f 'Id={{.Id}}{{"\n"}}RepoDigests={{.RepoDigests}}'
실행 결과
Id=sha256:14358309a308569c32bdc37e2e0e9694be33a9d99e68afb0f5ff33cc1f695dce RepoDigests=[alpine@sha256:14358309a308569c32bdc37e2e0e9694be33a9d99e68afb0f5ff33cc1f695dce]
이 환경에서 Id와 RepoDigest가 같은 이유 Docker 29의 기본 이미지 저장 방식(containerd 이미지 스토어)에서는 이미지 ID가 레지스트리 매니페스트(3.2절에서 구분한 OCI 이미지 매니페스트) 다이제스트와 같은 값이다. 예전 방식(그래프 드라이버)을 쓰는 환경에서는 ID가 이미지 설정의 다이제스트라서 RepoDigests와 다른 값으로 보인다. 둘 다 정상이며, 어느 쪽이든 레지스트리에 배포할 때 쓰는 값은 RepoDigests다. 매니페스트에 다이제스트를 박을 때는 이 필드를 복사한다. 출처: docs.docker.com/engine/storage/containerd/

3.5일부러 실패시키기

실패 ① — 태그를 옮겨 같은 이름이 다른 것을 가리키게 만든다

재현성이 깨지는 상황을 3초 만에 만들어 본다.

# myweb:v1 은 지금 nginx 이미지를 가리킨다
docker images myweb

# 같은 태그를 알파인에 붙인다
docker tag alpine:3.22 myweb:v1
docker images myweb
실행 결과 — 태그 이동 전
WARNING: This output is designed for human readability. For machine-readable output, please use --format. IMAGE ID DISK USAGE CONTENT SIZE EXTRA myweb:v1 5616878291a2 92.7MB 26.7MB
실행 결과 — 태그 이동 후
WARNING: This output is designed for human readability. For machine-readable output, please use --format. IMAGE ID DISK USAGE CONTENT SIZE EXTRA myweb:v1 14358309a308 13.4MB 4.21MB

Docker 29의 docker images <이름>은 위와 같은 새 표를 쓴다. DISK USAGE는 압축을 푼 로컬 사용량, CONTENT SIZE는 레지스트리에서 받는 압축 크기다. 스크립트에서 쓸 때는 경고 문구대로 --format을 지정한다.

같은 myweb:v1인데 내용이 완전히 다른 이미지가 됐다. 아무 경고도, 확인도 없었다. 레지스트리에 푸시할 때도 마찬가지로 조용히 덮인다.

이제 이 상황이 팀에서 어떻게 나타나는지 생각해 본다. 어제 myweb:v1을 받은 사람과 오늘 받은 사람이 다른 것을 실행한다. 쿠버네티스에서는 파드가 재시작될 때만 새로 받으므로 같은 디플로이먼트 안에서 파드마다 다른 버전이 돌 수 있다. 그래서 이 과정의 규칙은 두 가지다 — 태그를 재사용하지 않는다(빌드마다 새 태그: 깃 커밋 해시 등, M29), 재현이 중요한 자리에는 다이제스트를 쓴다.

# 정리: 실습용 태그 제거
docker rmi myweb:v1
실패 ② — 없는 태그를 요청한다 
docker pull nginx:1.29-alpin
실행 결과
Error response from daemon: failed to resolve reference "docker.io/library/nginx:1.29-alpin": docker.io/library/nginx:1.29-alpin: not found

오타 하나다. 이 메시지는 앞으로 쿠버네티스에서 ErrImagePull · ImagePullBackOff라는 이름으로 다시 만난다(M10). 그때 원인은 셋 중 하나다 — 태그 오타, 레지스트리 인증 실패, 이미지가 실제로 없음. 지금 이 메시지를 본 사람은 첫 번째를 먼저 의심할 수 있다.

3.6디스크 관리

실습을 반복하면 디스크가 빠르게 찬다. 무엇이 얼마나 쓰고 있는지 먼저 본다.

docker system df
출력 형태 — 아래는 이 과정을 몇 주 반복한 노트북의 값이다. 수강생의 숫자는 이보다 훨씬 작고, 값을 맞춰 볼 필요는 없다
TYPE TOTAL ACTIVE SIZE RECLAIMABLE Images 15 6 25.68GB 17.71GB (68%) Containers 8 8 114.8MB 0B (0%) Local Volumes 20 5 4.239GB 1.913GB (45%) Build Cache 176 0 18.4GB 16.58GB

표는 항상 이 네 줄이다. 읽을 열은 RECLAIMABLE 하나로, 지금 아무것도 참조하지 않아 지워도 되는 양이다. M01~M03만 마친 시점이면 이미지 몇 개에 수백 MB 수준이고 빌드 캐시는 0에 가깝다. 위 예처럼 Build Cache가 수십 GB로 자라는 것은 M04부터 빌드를 반복하면서 생기는 일이다 — 그때 이 명령을 다시 쳐서 숫자가 어떻게 달라졌는지 보면 된다.

명령지우는 것주의
docker image prune태그가 없는(dangling) 이미지안전한 편
docker builder prune빌드 캐시다음 빌드가 느려질 뿐
docker system prune멈춘 컨테이너 + 미사용 네트워크 + dangling 이미지 + 빌드 캐시다른 작업용 컨테이너가 멈춰 있으면 함께 지워진다
docker system prune -a --volumes위 + 사용 중이지 않은 모든 이미지와 볼륨볼륨의 데이터가 사라진다. 실행 전 docker volume ls를 확인한다

이 과정에서는 docker builder prune과 docker image prune까지만 습관으로 삼는다. kind 클러스터가 떠 있는 상태에서 system prune -a를 돌리면 노드 이미지까지 지워져 클러스터를 다시 만들어야 한다.

3.7체크포인트

다음 모듈로 넘어가기 전 확인
  • docker history nginx:1.29-alpine --format 'table {{.Size}}\t{{.CreatedBy}}' | head -2 → 첫 데이터 줄이 50.7MB, RUN으로 시작한다 (가장 큰 레이어가 맨 위)
  • docker history nginx:1.29-alpine --format '{{.Size}}' | grep -c '^0B$' → 12 (히스토리 20줄 중 메타데이터만 바꾼 줄)
  • docker image inspect nginx:1.29-alpine -f '{{len .RootFS.Layers}}' → 8
  • docker images --digests --format '{{.Repository}}:{{.Tag}} {{.Digest}}' alpine → alpine:3.22 sha256:14358309a308…
  • docker pull alpine@sha256:14358309a308569c32bdc37e2e0e9694be33a9d99e68afb0f5ff33cc1f695dce → Status: Image is up to date 줄
  • docker images myweb --format '{{.Repository}}' → 빈 출력 (3.5절에서 태그를 지웠다)
  • docker pull nginx:1.29-alpin → 마지막이 not found로 끝나는 에러 한 줄
  • docker system df --format '{{.Type}} {{.Reclaimable}}' → 4줄, 각 줄 끝에 회수 가능한 용량
  • (이해 확인) 태그와 다이제스트의 차이를 한 문장으로 말하고, 0B 레이어가 왜 생기는지 ENV · CMD를 예로 설명한다
이 모듈이 남기는 파일
  • 파일 산출물은 없다. 로컬 이미지 캐시의 nginx:1.29-alpine · alpine:3.22가 M05~M07의 재료로 남는다
  • 실습용 태그 myweb:v1은 3.5절에서 지웠다. 남아 있다면 docker rmi myweb:v1

3.8정리

이 모듈은 컨테이너를 띄우지 않았고, 만든 것은 태그 하나(myweb:v1)뿐이며 그것은 3.5절 실패①의 마지막 명령에서 지웠다. 남아 있는지 확인만 한다.

docker images myweb
docker rmi myweb:v1 2>/dev/null || true

이미지는 지우지 않는다. nginx:1.29-alpine은 M05(볼륨 · 네트워크)와 M06(Compose)에서 그대로 실행하고, alpine:3.22는 M07까지 디버그용 셸로 쓴다. 지우면 다음 모듈 첫머리에서 다시 받게 되니 손해만 있다.

디스크가 정말 급하면 3.6절의 순서를 따른다 — docker system df로 RECLAIMABLE을 먼저 읽고, docker image prune(태그 없는 이미지만)과 docker builder prune(빌드 캐시)까지만 쓴다. docker system prune -a는 kind 노드 이미지까지 지워 M01 클러스터를 다시 만들어야 하므로 이 과정에서는 손대지 않는다.

다음 모듈

지금까지는 남이 만든 이미지를 받아 썼다. M04에서 직접 만든다. 같은 애플리케이션으로 두 가지를 비교한다 — COPY 줄의 순서 하나로 소스 한 줄을 고친 뒤의 재빌드에서 의존성 설치가 CACHED로 건너뛰어져 마지막 단계가 2.7초에서 1.6초로 줄고(실제 프로젝트에서는 이 자리가 몇 분짜리다), 멀티스테이지 빌드로 이미지가 1.68GB에서 246MB로, 배포 때 내려받는 양은 413MB에서 59.3MB로 줄어든다. 두 실험 모두 이 모듈에서 본 docker history로 어느 레이어가 달라졌는지 확인하며 진행한다.
