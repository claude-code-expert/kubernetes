인그레스와 Gateway API

M06의 nginx.conf가 하던 경로 라우팅을 클러스터 리소스로 옮긴다. 그리고 같은 라우팅을 Gateway API v1.6으로 다시 쓴다 — 왜 표준이 하나 더 생겼는지는 두 매니페스트를 나란히 놓으면 보인다.

2026-09-05 검증 · Kubernetes 1.37.0 · Helm 4.2.4 · 버전은 실습 당일 다시 확인한다
사전 조건
  • M11 완료 — default 네임스페이스에 journal-api 디플로이먼트(파드 4개)와 서비스 journal-api, curlbox 파드가 있다. 확인: kubectl get endpointslices -l kubernetes.io/service-name=journal-api의 ENDPOINTS가 비어 있지 않다
  • M01의 kind 설정(course/labs/infra/kind-cluster.yaml)에 extraPortMappings(18080 → 80)와 ingress-ready=true 라벨이 있다
  • 매니페스트: course/labs/k8s/m12-ingress.yaml · m12-gateway.yaml · 값 파일 course/labs/monitoring/ingress-nginx-values.yaml

핵심 3줄

1. 인그레스 컨트롤러를 Helm으로 설치하고, journal.local 하나로 들어온 요청을 /api와 /에서 다른 서비스로 갈라 보낸다.

2. describe ingress의 Backends와 HTTP 404/200으로 "컨트롤러까지는 왔는가, 규칙이 잡혔는가"를 갈라 진단한다.

3. 같은 라우팅을 Gateway API의 Gateway · HTTPRoute로 다시 쓰고, ResolvedRefs 조건으로 잘못된 참조를 요청을 보내기 전에 잡아낸다.

12.1왜 서비스만으로는 부족한가 12.2이론 — 인그레스: 규칙과 컨트롤러 12.3따라하기 ① 라우팅 대상과 컨트롤러 설치 12.4따라하기 ② 경로 기반 라우팅 12.5이론 — 인그레스에서 Gateway API로 12.6따라하기 ③ 같은 라우팅을 Gateway API로 12.7일부러 실패시키기 12.8체크포인트와 정리

12.1왜 서비스만으로는 부족한가

M11에서 확인한 것 — ClusterIP는 클러스터 안에서만 보이고, NodePort는 포트 번호를 사람이 관리해야 하며, LoadBalancer는 서비스마다 로드밸런서를 하나씩 만든다.

그런데 실제 웹 서비스에 필요한 것은 이런 것들이다. journal.example.com이라는 하나의 주소로 들어와서, /api는 API 서비스로 /는 정적 파일 서버로 가고, TLS는 진입점에서 종료되고, 호스트 이름에 따라 다른 팀의 서비스로 분기한다. 이것은 전부 HTTP를 이해해야 할 수 있는 일 — L7 계층이다.

서비스는 L4(TCP/UDP)에서 동작하므로 HTTP 경로를 모른다. 그래서 L7 진입점이 따로 필요하고, 그것이 인그레스와 Gateway API다.

12.2이론 — 인그레스: 규칙과 컨트롤러

인그레스 (Ingress)는 "이 호스트의 이 경로로 온 HTTP 요청을 저 서비스의 저 포트로 보내라"는 규칙을 적은 오브젝트다(책 1.4, 9.3.5). 규칙 하나는 호스트 이름, 경로와 매칭 방식(pathType), 백엔드 서비스 이름과 포트 세 조각으로 이루어진다. 인그레스 자체는 규칙을 적은 종이에 가깝다. 그 종이를 읽고 실제로 트래픽을 받아 프록시하는 인그레스 컨트롤러 (Ingress Controller)가 없으면 아무 일도 일어나지 않는다. 인그레스를 만들었는데 접속이 안 된다는 신고의 첫 번째 원인이 이것이다 — 컨트롤러는 클러스터에 기본으로 들어 있지 않으며 따로 설치해야 한다.

컨트롤러가 여럿일 수 있으므로 인그레스는 ingressClassName으로 "누가 이 규칙을 처리할지"를 지정하고, 컨트롤러는 자기 IngressClass에 해당하는 인그레스만 읽는다. 이 이름이 틀리면 어느 컨트롤러도 규칙을 집어 가지 않고, 그 사실을 알려 주는 이벤트도 없다(12.7 실패 ①).

컨트롤러 설치본에는 대개 어드미션 웹훅 (Admission Webhook)이 함께 온다. apiserver가 오브젝트를 저장하기 직전에 외부 서비스에 "이 요청을 받아도 되는가"를 묻는 확장 지점이며, ingress-nginx는 이것으로 문법이 틀린 인그레스나 다른 인그레스와 호스트·경로가 겹치는 인그레스를 적용 시점에 거부한다(12.7 실패 ②). 웹훅이라는 확장 지점 자체는 M26에서 제대로 다룬다.

12.3따라하기 ① 라우팅 대상과 컨트롤러 설치

1단계. 라우팅 대상을 하나 더 만든다

목적경로로 갈라 보내려면 서비스가 둘 필요하다. journal-api는 M11이 남겼으니 정적 파일 서버를 하나 더 세운다.

kubectl create deploy web-static --image=nginx:1.29-alpine
kubectl expose deploy web-static --port=80
kubectl rollout status deploy/web-static --timeout=120s
kubectl get deploy,svc web-static

M08 8.7에서 선언형으로 넘어온 뒤 처음으로 명령형을 다시 쓴다. 이유는 하나다 — 정적 파일 서버는 이 모듈의 주제가 아니라 라우팅 대상일 뿐이고, M14에서 매니페스트(40-web-static.yaml)로 다시 쓸 때까지만 쓰는 일회용이다. 두 줄로 끝나는 것을 파일로 만들 이유가 없다.

실행 결과
deployment.apps/web-static created service/web-static exposed Waiting for deployment "web-static" rollout to finish: 0 of 1 updated replicas are available... deployment "web-static" successfully rolled out NAME READY UP-TO-DATE AVAILABLE AGE deployment.apps/web-static 1/1 1 1 0s NAME TYPE CLUSTER-IP EXTERNAL-IP PORT(S) AGE service/web-static ClusterIP 10.96.100.195 <none> 80/TCP 0s
판정디플로이먼트 READY 1/1, 서비스 web-static이 ClusterIP로 80 포트를 연다. CLUSTER-IP 값은 환경마다 다르다.

2단계. 값 파일을 읽고 차트 저장소를 등록한다

목적kind에는 LoadBalancer도, 노드 80 포트를 열어 줄 클라우드도 없다. 그 제약을 값 파일 네 줄로 푼다.

# course/labs/monitoring/ingress-nginx-values.yaml
controller:
  hostPort:
    enabled: true            # 노드의 80/443 을 컨트롤러가 직접 잡는다
  service:
    type: NodePort           # kind 에는 LoadBalancer 를 만들어 줄 컨트롤러가 없다
  nodeSelector:
    ingress-ready: "true"    # M01 kind 설정에서 붙인 라벨
  tolerations:
    - key: node-role.kubernetes.io/control-plane
      operator: Equal
      effect: NoSchedule
  watchIngressWithoutClass: true

hostPort로 노드의 80 포트를 잡고, 그 노드는 nodeSelector로 컨트롤 플레인(M01에서 ingress-ready=true 라벨을 붙인 노드)으로 고정하며, 컨트롤 플레인에 걸린 테인트를 tolerations로 통과한다(M16의 주제). 그 노드의 80은 kind 설정에 의해 맥의 18080으로 연결돼 있다. 마지막 줄 watchIngressWithoutClass는 클래스를 적지 않은 인그레스도 이 컨트롤러가 처리하게 한다 — 편의 옵션이고, 그 대가는 12.7 실패 ①에서 본다.

helm repo add ingress-nginx https://kubernetes.github.io/ingress-nginx
helm repo update
실행 결과
"ingress-nginx" has been added to your repositories Hang tight while we grab the latest from your chart repositories... ...Successfully got an update from the "ingress-nginx" chart repository Update Complete. ⎈Happy Helming!⎈
판정두 번째 명령이 Update Complete로 끝난다. 저장소가 이미 등록돼 있었다면 첫 줄이 already exists with the same configuration, skipping으로 바뀌는데, 그것도 정상이다.

3단계. 컨트롤러를 설치한다

목적차트 버전을 고정해 설치하고, 파드가 준비될 때까지 기다린다.

helm upgrade --install ingress-nginx ingress-nginx/ingress-nginx \
  --namespace ingress-nginx --create-namespace \
  --version 4.15.1 -f course/labs/monitoring/ingress-nginx-values.yaml \
  --wait --timeout 5m
  • upgrade --install — 없으면 설치, 있으면 갱신. 여러 번 실행해도 안전하다. M14의 rebuild.sh가 같은 명령을 다시 돌린다
  • --version — 차트 버전을 고정한다. 안 적으면 그날의 최신이 설치돼 재현이 깨진다
  • --wait — 파드가 준비될 때까지 기다린다. 스크립트에서 다음 단계로 넘어가기 전에 필요하다

ingress-nginx 는 은퇴한 프로젝트다 — 그런데 왜 계속 쓰나 쿠버네티스 공식 블로그가 2025-11-11에 ingress-nginx의 은퇴를 공지했다. 2026년 3월까지만 최선 노력(best-effort)으로 유지하고, 그 뒤로는 릴리스도, 버그 수정도, 보안 취약점 패치도 없다. 이미 설치된 것은 계속 동작하고 설치 산출물도 남아 있지만, 새로 도입하는 조직에는 "이미 쓰고 있지 않다면 배포하지 말라"고 저장소 README가 못 박는다. 2026-09-05 확인 기준으로 차트 저장소의 최신은 4.15.1(앱 1.15.1)이고 이 문서도 그 버전을 쓴다 — 그러나 저장소에 새 태그가 있다는 것이 패치 약속을 뜻하지는 않는다. 그럼에도 이 교재가 ingress-nginx를 쓰는 이유는 둘이다. 첫째, 인그레스 컨트롤러 중 설치 자료와 트러블슈팅 사례가 가장 많아 "인그레스라는 개념"을 배우는 데 마찰이 가장 적다. 둘째, M14의 저널 애플리케이션과 rebuild.sh가 이미 이 컨트롤러의 어드미션 웹훅과 IngressClass nginx에 묶여 있다. 실습 도구로 쓰는 것과 운영에 새로 들이는 것은 다른 결정이다. 신규 설계라면 Gateway API 구현체(Envoy Gateway · NGINX Gateway Fabric · Cilium · Istio · 클라우드 사업자의 것)를 고른다 — 공식 공지가 권하는 대체 경로가 그것이고, 이 모듈의 12.6에서 실제로 하나를 설치해 같은 라우팅을 만들어 본다. 인그레스를 반드시 유지해야 한다면 공식 문서의 컨트롤러 목록에서 유지되는 다른 구현체를 고른다. https://kubernetes.io/blog/2025/11/11/ingress-nginx-retirement/ · https://github.com/kubernetes/ingress-nginx (README) · 2026-09-05 접근 확인

4단계. 설치된 것을 확인한다

kubectl get pods,svc -n ingress-nginx
kubectl get ingressclass

-admission 서비스가 12.2에서 말한 어드미션 웹훅이다. apiserver가 인그레스를 저장하기 전에 이 서비스에 물어보고, 거부당하면 오브젝트는 만들어지지 않는다.

12.4따라하기 ② 경로 기반 라우팅

5단계. 인그레스를 만든다

목적M06의 nginx.conf가 하던 두 줄짜리 분기를 클러스터 오브젝트로 옮긴다.

# course/labs/k8s/m12-ingress.yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: journal
spec:
  ingressClassName: nginx
  rules:
    - host: journal.local
      http:
        paths:
          - path: /api
            pathType: Prefix
            backend:
              service:
                name: journal-api
                port:
                  number: 8080
          - path: /
            pathType: Prefix
            backend:
              service:
                name: web-static
                port:
                  number: 80

M06의 nginx 설정과 같은 내용이다. 달라진 것은 이 규칙이 클러스터의 오브젝트라는 점 — 백엔드 파드가 늘거나 줄어도 자동으로 반영되고, 설정 파일을 컨테이너에 넣거나 리로드할 필요가 없다.

kubectl apply -f course/labs/k8s/m12-ingress.yaml
kubectl get ingress
kubectl describe ingress journal | sed -n '/Rules:/,/Annotations/p'
실행 결과 — 파드 IP 는 환경마다 다르다
ingress.networking.k8s.io/journal created NAME CLASS HOSTS ADDRESS PORTS AGE journal nginx journal.local 80 8s Rules: Host Path Backends ---- ---- -------- journal.local /api journal-api:8080 (10.244.1.40:8080,10.244.1.41:8080,10.244.2.40:8080 + 1 more...) / web-static:80 (10.244.1.42:80) Annotations: <none>
판정Backends에 실제 파드 IP가 채워져 있다. /api 뒤에 IP 3개와 + 1 more... — M11이 남긴 파드 4개다. 비어 있다면 서비스의 엔드포인트가 비었다는 뜻이고, M11의 진단 순서로 돌아간다. ADDRESS 열은 컨트롤러가 상태를 써 주기까지 몇십 초 비어 있다가 컨트롤러 서비스의 IP로 채워진다.

6단계. 호스트 헤더를 붙여 접속한다

목적같은 주소로 들어온 요청이 경로에 따라 다른 서비스로 가는 것을 확인한다.

curl -s -H 'Host: journal.local' http://localhost:18080/ | head -4
curl -s -H 'Host: journal.local' http://localhost:18080/api/entries
  • -H 'Host: journal.local' — 인그레스 규칙이 호스트 이름으로 매칭하므로 필요하다. DNS를 건드리지 않고 테스트하는 방법이다. 브라우저로 보려면 /etc/hosts에 127.0.0.1 journal.local을 추가한다
  • localhost:18080 — 맥 18080 → 컨트롤 플레인 노드 80 → 인그레스 컨트롤러
실행 결과
<!DOCTYPE html> <html> <head> <title>Welcome to nginx!</title> {"entries":[]}
판정/는 정적 서버의 nginx 기본 페이지, /api/entries는 저널 API의 JSON. 하나의 진입점이 두 서비스로 나눠 보냈다. 인그레스를 만든 직후라면 컨트롤러가 설정을 다시 읽는 몇 초 동안 404가 나올 수 있다 — 한 번 더 시도한다.

경로 매칭 규칙 하나를 짚는다. 위 매니페스트에서 /api가 /보다 먼저 쓰여 있지만, 순서가 매칭을 정하는 것은 아니다. 인그레스는 더 긴 경로가 우선한다. pathType은 세 가지 — Prefix(경로 세그먼트 단위 접두사), Exact(정확히 일치), ImplementationSpecific(컨트롤러가 정한다. 이식성이 없으므로 피한다).

7단계. 등록되지 않은 호스트는 어떻게 되나

목적"연결이 안 된다"와 "규칙이 안 잡힌다"를 상태 코드로 가르는 기준을 만든다.

curl -s -o /dev/null -w 'HTTP %{http_code}\n' -H 'Host: wrong.local' http://localhost:18080/
curl -s -o /dev/null -w 'HTTP %{http_code}\n' http://localhost:18080/
실행 결과
HTTP 404 HTTP 404
판정둘 다 404. 규칙에 없는 호스트는 컨트롤러의 기본 백엔드가 받아 404를 돌려주고, 호스트 헤더를 아예 안 보내도 마찬가지다.

접속이 안 될 때 404가 나오면 컨트롤러까지는 도달한 것이고, 연결 자체가 안 되면 그 앞(포트 매핑, 컨트롤러 파드)의 문제다. 이 구분이 진단 시간을 줄인다.

12.5이론 — 인그레스에서 Gateway API로

인그레스는 오래 쓰였지만 두 가지 한계가 분명했다(책 9.3.6).

첫째, 표준이 표현하지 못하는 것이 너무 많았다. 헤더 기반 라우팅, 트래픽 분할(카나리), 재시도, 타임아웃, 리다이렉트 — 전부 표준 스펙에 없어서 각 컨트롤러의 어노테이션으로 갔다. nginx.ingress.kubernetes.io/canary-weight: "10" 같은 것을 쓰는 순간 그 매니페스트는 다른 컨트롤러로 옮길 수 없다. 12.3의 은퇴 공지가 뼈아픈 이유가 여기 있다 — 어노테이션에 의존한 인그레스는 컨트롤러를 바꾸면 전부 다시 써야 한다.

둘째, 역할이 뒤섞였다. 인그레스 하나에 TLS 인증서(인프라 팀 관심사)와 경로 라우팅(개발 팀 관심사)이 함께 들어 있어, 개발자가 라우팅을 바꾸려면 인프라 설정이 든 파일을 건드려야 했다.

Gateway API는 인그레스의 후속으로 만들어진 쿠버네티스 SIG-Network의 L4·L7 라우팅 표준이다. 코어 API가 아니라 CRD로 배포되며, 이 둘을 리소스 분리로 해결한다.

리소스정의하는 것보통 누가 소유하나

Gateway리스너 — 포트, 프로토콜, TLS, 어느 네임스페이스의 라우트를 허용할지인프라 · 플랫폼 팀
HTTPRoute (GRPCRoute · TCPRoute · UDPRoute)경로 · 헤더 매칭과 백엔드, 트래픽 가중치애플리케이션 팀

9단계. Gateway와 HTTPRoute를 만든다

목적5단계의 인그레스와 같은 라우팅을 두 리소스로 나눠 쓴다.

# course/labs/k8s/m12-gateway.yaml
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: journal-gateway
spec:
  gatewayClassName: nginx        # 어떤 구현체가 이 게이트웨이를 맡을지
  listeners:
    - name: http
      protocol: HTTP
      port: 80
      hostname: "gw.journal.local"
      allowedRoutes:
        namespaces:
          from: Same             # 같은 네임스페이스의 라우트만 붙을 수 있다
---
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: journal-route
spec:
  parentRefs:
    - name: journal-gateway      # 이 게이트웨이에 붙는다
  hostnames:
    - "gw.journal.local"
  rules:
    - matches:
        - path:
            type: PathPrefix
            value: /api
      backendRefs:
        - name: journal-api
          port: 8080
    - matches:
        - path:
            type: PathPrefix
            value: /
      backendRefs:
        - name: web-static
          port: 80

allowedRoutes가 인그레스에 없던 개념이다. 게이트웨이 소유자가 어느 네임스페이스의 라우트를 받아들일지 정한다 — 다른 팀이 임의로 우리 게이트웨이에 라우트를 붙이는 것을 막는 장치이며, 멀티테넌트 클러스터에서 필요하다.

12단계. 인그레스로는 어노테이션이 필요했던 것 — 읽기만 한다

목적헤더 기반 분기와 트래픽 분할이 표준 필드라는 것을 눈으로 확인한다. 여기서는 적용하지 않는다 — journal-api-v2 서비스가 아직 없다. M30 카나리 배포에서 이 형태를 실제로 쓴다.

  rules:
    # 헤더가 있으면 새 버전으로
    - matches:
        - path: { type: PathPrefix, value: /api }
          headers:
            - name: x-canary
              value: "true"
      backendRefs:
        - name: journal-api-v2
          port: 8080
    # 나머지는 90:10 으로 나눈다
    - matches:
        - path: { type: PathPrefix, value: /api }
      backendRefs:
        - name: journal-api
          port: 8080
          weight: 90
        - name: journal-api-v2
          port: 8080
          weight: 10

같은 것을 ingress-nginx로 하려면 nginx.ingress.kubernetes.io/canary, canary-weight, canary-by-header 어노테이션을 조합해야 하고, 다른 컨트롤러에서는 통하지 않는다.

12.7일부러 실패시키기

세 실패는 모두 default 네임스페이스에서 재현했고, 각각 고친 뒤 원상태로 돌린다.

실패 ① — ingressClassName 을 틀리게 적는다 (그리고 아무 신호가 없다)

인그레스를 만들었는데 접속이 안 되는 가장 흔한 원인이다. 클래스 이름에 오타를 내면 어느 컨트롤러도 그 규칙을 집어 가지 않는다. 호스트를 하나 더 써서 재현한다.

kubectl apply -f - <<'EOF'
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: journal-typo
spec:
  ingressClassName: ngnix          # nginx 의 오타
  rules:
    - host: typo.journal.local
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: web-static
                port:
                  number: 80
EOF
kubectl get ingress journal-typo
curl -s -o /dev/null -w 'HTTP %{http_code}\n' -H 'Host: typo.journal.local' http://localhost:18080/
kubectl describe ingress journal-typo | tail -n 6
실행 결과
ingress.networking.k8s.io/journal-typo created NAME CLASS HOSTS ADDRESS PORTS AGE journal-typo ngnix typo.journal.local 80 9s HTTP 404 Rules: Host Path Backends ---- ---- -------- typo.journal.local / web-static:80 (10.244.1.42:80) Annotations: <none> Events: <none>

세 가지가 보인다. 오브젝트는 정상적으로 만들어졌고(apiserver는 클래스 이름이 실존하는지 검사하지 않는다), Backends에 파드 IP까지 채워져 있으며, Events가 <none>이다. 그런데 404다 — 컨트롤러까지는 갔지만(7단계의 기준) 이 호스트의 규칙을 아무도 nginx 설정에 쓰지 않았다. 아무 신호가 없다는 것이 이 실패의 특징이다. 진단은 CLASS 열과 kubectl get ingressclass의 이름을 눈으로 대조하는 것 하나다.

kubectl get ingressclass
kubectl patch ingress journal-typo --type merge -p '{"spec":{"ingressClassName":"nginx"}}'
sleep 10
curl -s -o /dev/null -w 'HTTP %{http_code}\n' -H 'Host: typo.journal.local' http://localhost:18080/
kubectl delete ingress journal-typo
실행 결과
NAME CONTROLLER PARAMETERS AGE nginx k8s.io/ingress-nginx <none> 71s ingress.networking.k8s.io/journal-typo patched HTTP 200 ingress.networking.k8s.io "journal-typo" deleted from default namespace
판정클래스 이름을 고치자 200. 컨트롤러가 설정을 다시 읽는 몇 초를 sleep 10으로 기다렸다.

이 실습의 값 파일에는 watchIngressWithoutClass: true가 들어 있어 클래스를 아예 안 적은 인그레스는 nginx가 잡는다. 그러나 틀리게 적은 것은 잡지 않는다 — "없음"과 "다른 이름"은 다르다. 편의 옵션에 기대지 말고 항상 명시하는 편이 낫다. 컨트롤러가 둘 이상인 환경에서는 이 옵션 자체가 둘 다 같은 인그레스를 처리하려 드는 사고의 원인이 된다. 기본 클래스를 정하는 정식 방법은 kubectl annotate ingressclass nginx ingressclass.kubernetes.io/is-default-class=true다.

실패 ② — 같은 호스트 · 경로를 두 인그레스가 주장한다

  name: journal-api-only
spec:
  ingressClassName: nginx
  rules:
    - host: journal.local
      http:
        paths:
          - path: /api
            pathType: Prefix
            backend:
              service:
                name: journal-api
                port:
                  number: 8080
EOF
실행 결과 — 원문은 한 줄이다. 읽기 쉽게 줄을 나눴다
Error from server (BadRequest): error when creating "STDIN": admission webhook "validate.nginx.ingress.kubernetes.io" denied the request: host "journal.local" and path "/api" is already defined in ingress default/journal
판정admission webhook ... denied the request. 오브젝트는 만들어지지 않았다 — kubectl get ingress에 journal 하나만 있다. 메시지의 default/journal은 그 호스트·경로를 먼저 차지한 인그레스의 네임스페이스와 이름이다.

4단계에서 본 -admission 서비스가 한 일이다. 같은 호스트·경로를 두 인그레스가 주장하면 어느 쪽이 이기는지 정의되지 않으므로 컨트롤러가 아예 거부한다. 웹훅이 없었다면 조용히 둘 중 하나가 무시됐을 것이고, 그편이 훨씬 찾기 어렵다. 이 웹훅은 네임스페이스를 가리지 않는다 — M14에서 journal 네임스페이스에 같은 규칙을 다시 만들 때 이 메시지를 한 번 더 만나게 되고, 그때는 default의 인그레스를 지우는 것이 답이다. 고칠 것은 없다. 만들어진 것이 없으니 되돌릴 것도 없다.

실패 ③ — HTTPRoute 의 백엔드 서비스 이름을 틀린다

인그레스와 Gateway API의 차이가 가장 잘 드러나는 지점이다. 인그레스에서 백엔드 서비스 이름을 틀리면 매니페스트는 그대로 적용되고, 요청을 보내야 503으로 알게 되며, 원인은 컨트롤러 로그를 봐야 한다. HTTPRoute는 다르다. 9단계의 라우트에서 journal-api를 journal-apo로 바꿔 본다.

kubectl patch httproute journal-route --type json \
  -p '[{"op":"replace","path":"/spec/rules/0/backendRefs/0/name","value":"journal-apo"}]'
sleep 5
kubectl get httproute journal-route \
  -o jsonpath='{range .status.parents[0].conditions[*]}{.type}={.status} {.reason}: {.message}{"\n"}{end}'
docker exec study-worker curl -s -o /dev/null -w 'HTTP %{http_code}\n' -H 'Host: gw.journal.local' http://localhost:32287/api/entries
  • --type json — JSON Patch. 배열의 특정 원소(rules/0/backendRefs/0) 한 필드만 바꿀 때 merge 패치보다 정확하다
  • {range ...}{end} — jsonpath로 조건 배열을 한 줄에 하나씩 찍는다. describe보다 짧고 스크립트에서 판정하기 좋다
실행 결과 — 포트 번호는 11단계에서 읽은 자기 값으로
httproute.gateway.networking.k8s.io/journal-route patched Accepted=True Accepted: The Route is accepted ResolvedRefs=False BackendNotFound: spec.rules[0].backendRefs[0].name: Not found: "journal-apo" HTTP 500
판정ResolvedRefs=False, Reason: BackendNotFound, 그리고 메시지에 어느 규칙의 어느 참조가 틀렸는지 경로(spec.rules[0].backendRefs[0].name)와 값이 적혀 있다. 요청을 보내면 500이 오지만, 보내지 않았어도 이미 상태에서 알 수 있었다.

Accepted는 여전히 True다 — 라우트가 게이트웨이에 붙는 것과 백엔드가 존재하는 것은 다른 조건이고, 둘을 따로 알려 준다. 이 덕에 CI에서 매니페스트를 적용한 뒤 ResolvedRefs가 True인지 검사하는 자동화가 가능해진다(M29).

kubectl patch httproute journal-route --type json \
  -p '[{"op":"replace","path":"/spec/rules/0/backendRefs/0/name","value":"journal-api"}]'
sleep 5
kubectl get httproute journal-route \
  -o jsonpath='{range .status.parents[0].conditions[*]}{.type}={.status} {.reason}: {.message}{"\n"}{end}'
실행 결과
httproute.gateway.networking.k8s.io/journal-route patched Accepted=True Accepted: The Route is accepted ResolvedRefs=True ResolvedRefs: All references are resolved
판정ResolvedRefs=True, 메시지 All references are resolved. 원상태다.

12.8체크포인트와 정리

다음 모듈로 넘어가기 전 확인
  • kubectl get ingressclass → nginx 행의 CONTROLLER가 k8s.io/ingress-nginx
  • kubectl get ingress journal -o jsonpath='{.spec.ingressClassName}{"\n"}' → nginx
  • curl -s -o /dev/null -w '%{http_code}\n' -H 'Host: journal.local' http://localhost:18080/api/entries → 200
  • curl -s -H 'Host: journal.local' http://localhost:18080/ | grep -c 'Welcome to nginx' → 1
  • curl -s -o /dev/null -w '%{http_code}\n' -H 'Host: wrong.local' http://localhost:18080/ → 404
  • kubectl describe ingress journal | grep -E '^ +/' → 두 줄 모두 괄호 안에 파드 IP가 있다
  • kubectl get gateway journal-gateway -o jsonpath='{.status.conditions[?(@.type=="Programmed")].status}{"\n"}' → True
  • kubectl get httproute journal-route -o jsonpath='{.status.parents[0].conditions[*].type}{"\n"}' → Accepted ResolvedRefs
  • (이해 확인) GatewayClass · Gateway · HTTPRoute가 각각 무엇을 정의하고 누가 소유하는지 한 문장씩 말한다
  • (이해 확인) 신규 설계에서 인그레스 대신 Gateway API를 고르는 근거를 12.3의 은퇴 공지와 12.5의 한계 두 가지로 댄다
이 모듈이 남기는 파일
  • course/labs/k8s/m12-ingress.yaml · m12-gateway.yaml · course/labs/monitoring/ingress-nginx-values.yaml
  • 클러스터에 남는 것 — 네임스페이스 ingress-nginx의 컨트롤러: M14의 저널 애플리케이션과 rebuild.sh가 필수로 의존한다
  • 클러스터에 남는 것 — 네임스페이스 nginx-gateway의 NGINX Gateway Fabric: M14는 default의 Gateway · HTTPRoute만 지우고 구현체는 남긴다. M30 카나리에서 다시 쓴다
  • default에 남는 것 — web-static 디플로이먼트·서비스, 인그레스 journal, Gateway journal-gateway와 HTTPRoute journal-route. 전부 M14 14.3 6단계에서 지운다

정리는 하지 않는다. default에 남긴 것들은 M14가 journal 네임스페이스로 옮기면서 한꺼번에 지우고, 그 과정에서 실패 ②의 웹훅 메시지를 한 번 더 만난다.
