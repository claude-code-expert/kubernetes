파드 · 레이블 · 네임스페이스

파드는 컨테이너 하나가 아니라 같은 운명을 공유하는 컨테이너 묶음이다. 왜 그런 단위가 필요한지 두 컨테이너를 한 파드에 넣어 확인하고, 레이블 오타 하나로 아무것도 못 찾는 상황을 만든다.

초반→중반60분Kubernetes 1.37.0
2026-09-05 검증 · journal-api:v1 (M04 · M07 산출물) · 버전 숫자는 실습 당일 kubectl version으로 다시 확인한다
사전 조건
  • M08 완료 — describe · logs · get events를 쓸 수 있다
  • M07에서 kind load docker-image journal-api:v1을 했다. 안 했다면 지금 한다
  • 매니페스트: course/labs/k8s/m09-pod-sidecar.yaml

핵심 3줄

1. 두 컨테이너를 한 파드에 넣고, 사이드카가 localhost로 본체를 호출한 것과 init 컨테이너가 쓴 파일을 본체가 읽은 것을 로그와 exec로 확인한다.

2. kubectl label로 레이블을 붙이고 -l 셀렉터로 골라낸다. 오타가 나면 에러 대신 0개가 나온다는 것을 직접 본다 — 서비스·디플로이먼트·네트워크 정책이 전부 이 셀렉터로 대상을 고르므로 이 실습에서 가장 중요한 결과다.

3. 네임스페이스를 만들어 같은 이름의 파드를 둘 띄우고, 컨텍스트의 기본 네임스페이스를 바꿔 -n 없이 조회한 뒤 되돌린다. 권한 · 쿼터 · 파드 보안 수준이 전부 이 단위로 걸린다.

9.1왜 파드라는 단위가 있나

M08에서 파드는 "컨테이너가 들어 있는 것" 정도로 지나갔다. 그런데 컨테이너를 그냥 스케줄링하면 될 것을 왜 한 겹을 더 뒀을까.

같이 있어야만 동작하는 컨테이너들이 있기 때문이다. 로그를 읽어 전송하는 에이전트는 애플리케이션과 같은 파일시스템을 봐야 하고, 프록시는 애플리케이션과 같은 네트워크에 있어야 localhost로 가로챌 수 있다. 이것들을 별도로 스케줄링하면 다른 노드에 떨어져 아무 일도 못 한다.

그래서 쿠버네티스는 "항상 같은 노드에, 같이 뜨고 같이 죽는" 묶음을 하나의 단위로 만들었다. 그것이 파드다. 대부분의 파드는 컨테이너가 하나지만, 구조는 여러 개를 담을 수 있게 되어 있다 — 그리고 M25의 서비스 메시, M22의 로그 수집이 이 구조를 쓴다.

9.2이론 — 파드 안에서 공유되는 것

공유되는 것결과M02에서 본 것
네트워크 네임스페이스같은 IP를 쓴다. 서로를 localhost로 부른다. 포트는 파드 안에서 유일해야 한다네임스페이스가 시야를 가른다
볼륨같은 볼륨을 각자 마운트해 파일을 주고받는다-v로 붙이던 볼륨
수명같은 노드에 배치되고, 파드가 지워지면 함께 지워진다—
공유되지 않는 것파일시스템(볼륨 제외), 프로세스 목록(기본 설정), 리소스 제한(컨테이너별)—

컨테이너 세 종류

파드 안 컨테이너는 역할에 따라 세 가지로 나뉜다. 일반 컨테이너는 containers:에 나열하는 것으로, 전부 동시에 시작되며 순서를 지정할 수 없다. 이 실습의 api와 sidecar가 여기 속한다.

init 컨테이너 (Init Container)는 initContainers:에 적는다. 하나씩 순서대로 실행되고, 전부 성공적으로 끝나야 일반 컨테이너가 시작된다. 설정 파일 생성, 스키마 마이그레이션, 의존 서비스 대기처럼 "본체보다 먼저 끝나야 하는 일"에 쓴다.

사이드카 (Sidecar)는 본체를 보조하는 컨테이너다. 로그 수집기나 프록시처럼 본체보다 먼저 떠서 본체보다 나중에 죽어야 하는 것이 대상인데, 일반 컨테이너로는 그 순서를 보장할 수 없다. 그래서 initContainers에 restartPolicy: Always를 준 컨테이너를 사이드카로 취급하는 기능이 들어왔다 — 1.29에서 베타(기본 활성)로 들어오고 1.33에서 GA가 됐다. 검색하면 "1.28 알파" "1.29 정식" 같은 표현이 섞여 나오는데, 지금 기준은 1.33 GA다.

사이드카를 일반 컨테이너로 두면 생기는 문제 잡(Job)에서 애플리케이션이 끝나도 사이드카가 계속 돌아 파드가 완료되지 않는다. 또 시작 순서를 보장할 수 없어 애플리케이션이 프록시보다 먼저 떠서 초기 요청을 놓친다. 네이티브 사이드카(1.29 베타 · 1.33 GA)가 들어온 이유가 이 두 가지다. 이 실습에서는 구조를 보는 것이 목적이라 일반 컨테이너로 두고, 차이는 M25 서비스 메시에서 다시 본다. 출처: kubernetes.io/docs/concepts/workloads/pods/sidecar-containers/

9.3따라하기 ① 두 컨테이너 한 파드

1단계. 매니페스트를 읽는다

목적YAML을 직접 쓴다. M08의 명령형에서 선언형으로 넘어가는 지점이다.

# course/labs/k8s/m09-pod-sidecar.yaml
apiVersion: v1
kind: Pod
metadata:
  name: journal-with-sidecar
  labels:
    app: journal
    tier: api
spec:
  initContainers:
    # 순서 강제: 이 컨테이너가 끝나야 아래 컨테이너들이 시작한다.
    - name: init-config
      image: alpine:3.22
      command: ["sh", "-c", "echo 'ready at' $(date -u +%H:%M:%S) > /shared/init.txt; echo init done"]
      volumeMounts:
        - name: shared
          mountPath: /shared
  containers:
    - name: api
      image: journal-api:v1
      imagePullPolicy: IfNotPresent
      ports:
        - containerPort: 8080
      volumeMounts:
        - name: shared
          mountPath: /shared
    - name: sidecar
      image: alpine:3.22
      # 사이드카가 같은 파드의 api 를 localhost 로 호출한다.
      command: ["sh", "-c", "apk add --no-cache curl >/dev/null 2>&1; while true; do curl -s localhost:8080/healthz; echo; sleep 10; done"]
      volumeMounts:
        - name: shared
          mountPath: /shared
  volumes:
    - name: shared
      emptyDir: {}
필드의미
apiVersion · kind어떤 종류의 오브젝트인지. 이 조합이 스키마를 결정한다. 헷갈리면 kubectl explain pod
metadata.labels이 파드에 붙는 꼬리표. 9.4절의 주제
imagePullPolicy: IfNotPresent노드에 이미지가 있으면 받지 않는다. kind load로 넣은 이미지를 쓰려면 필요하다(M07)
volumes.emptyDir파드 수명 동안만 존재하는 빈 디렉터리. 컨테이너 간 파일 공유용. 파드가 죽으면 사라진다
ports.containerPort문서용 표시에 가깝다. 이것을 적지 않아도 통신은 된다
kubectl apply -f course/labs/k8s/m09-pod-sidecar.yaml
실행 결과
pod/journal-with-sidecar created

apply는 create와 다르다. 이미 있으면 에러 대신 차이만 반영한다. 같은 파일을 여러 번 적용해도 안전하므로 이 과정은 이후 전부 apply를 쓴다.

2단계. 컨테이너 두 개가 한 파드에 있는지 확인한다

목적컨테이너 수와 IP 수를 확인한다. 이 둘의 비율이 파드라는 단위의 정의다.

kubectl get pod journal-with-sidecar -o wide
실행 결과 (20초 시점)
NAME READY STATUS RESTARTS AGE IP NODE NOMINATED NODE READINESS GATES journal-with-sidecar 2/2 Running 0 20s 10.244.1.37 study-worker <none> <none>
판정READY 2/2 — 컨테이너 2개 중 2개가 준비됐다. IP는 하나다. 두 컨테이너가 그 IP를 공유한다. IP와 NODE는 환경마다 다르다. 처음 몇 초는 Init:0/1(init 컨테이너 진행 중) → PodInitializing을 거친다.

3단계. init 컨테이너가 먼저 끝났는지 본다

목적init 컨테이너가 "끝났다"는 것이 어떤 상태로 표시되는지 본다. 이 표시를 알아야 init 실패를 구분할 수 있다.

kubectl logs journal-with-sidecar -c init-config
kubectl describe pod journal-with-sidecar | grep -E "Init Containers|Containers:|State:|Ready:" | head -12
  • -c <이름> — 파드에 컨테이너가 여럿이면 필수다. 빼면 어느 것을 원하는지 물어본다
실행 결과
init done Init Containers: State: Terminated Ready: True Containers: State: Running Ready: True State: Running Ready: True

init 컨테이너는 Terminated이면서 Ready: True다 — 할 일을 마치고 정상 종료했다는 뜻이다. 일반 컨테이너 둘은 Running. init이 실패하면 일반 컨테이너는 시작조차 하지 않고 파드가 Init:Error 또는 Init:CrashLoopBackOff에 머문다.

4단계. 공유의 증거 두 가지

목적네트워크 공유와 볼륨 공유를 각각 확인한다.

# ① 네트워크 — 사이드카가 localhost 로 api 를 호출한 결과
kubectl logs journal-with-sidecar -c sidecar | head -3

# ② 볼륨 — init 컨테이너가 쓴 파일을 api 컨테이너가 읽는다
kubectl exec journal-with-sidecar -c api -- cat /shared/init.txt
실행 결과
{"status":"ok","version":"v1","pod":"journal-with-sidecar"} {"status":"ok","version":"v1","pod":"journal-with-sidecar"} ready at 08:20:46
판정사이드카가 localhost:8080으로 API의 응답을 받았고, api 컨테이너가 init 컨테이너의 파일을 읽었다. 서로 다른 이미지, 다른 파일시스템인데도 그렇다. 시각은 환경마다 다르다.

응답의 pod 필드는 M04·M05에서 도커로 직접 돌릴 때는 "local"이었다. 앱이 환경변수 HOSTNAME을 읽어 돌려주는데, 쿠버네티스는 컨테이너의 HOSTNAME을 파드 이름으로 설정한다. 어느 파드가 응답했는지 보는 이 장치를 M11에서 로드밸런싱 확인에 쓴다. 값은 파드 이름이므로 환경마다 다르다.

여기서 제약 하나가 따라온다. 두 컨테이너가 같은 IP를 쓰므로 같은 포트를 둘 다 열 수는 없다. 파드 안에서 포트는 유일해야 한다.

9.4따라하기 ② 레이블과 셀렉터

레이블 (Label)은 오브젝트에 붙이는 키=값 꼬리표고, 셀렉터 (Selector)는 "이런 레이블을 가진 것"이라는 조건식이다. M08에서 -l app=web으로 쓴 것이 셀렉터였고, create deployment가 붙인 app=web이 레이블이었다. 레이블은 이 시스템에서 가장 단순하면서 가장 중요한 개념이다. 서비스가 어느 파드로 트래픽을 보낼지, 디플로이먼트가 어느 파드를 자기 것으로 볼지, 네트워크 정책이 어느 파드에 적용될지 — 전부 레이블 셀렉터로 정해진다.

5단계. 레이블을 보고 붙이고 고른다

목적매니페스트에 적은 레이블을 확인하고, 실행 중인 오브젝트에 레이블을 덧붙인 뒤 셀렉터로 골라낸다.

kubectl get pods --show-labels -l app=journal
실행 결과
NAME READY STATUS RESTARTS AGE LABELS journal-with-sidecar 2/2 Running 0 21s app=journal,tier=api
kubectl label pod journal-with-sidecar env=dev --overwrite
kubectl get pods -l 'app=journal,env=dev' --show-labels
실행 결과
pod/journal-with-sidecar labeled NAME READY STATUS RESTARTS AGE LABELS journal-with-sidecar 2/2 Running 0 41s app=journal,env=dev,tier=api
판정LABELS에 env=dev가 추가됐고, 두 조건을 AND로 묶은 셀렉터가 그 파드를 골랐다. --overwrite는 같은 키가 이미 있을 때 덮어쓰겠다는 뜻이다 — 없으면 에러가 난다.

셀렉터 문법은 몇 가지가 더 있다. 실무에서 쓰는 것만 정리한다.

표현의미
-l app=journal같음
-l app=journal,env=dev둘 다 만족 (AND)
-l 'app!=journal'다름
-l 'env in (dev,stage)'집합 포함
-l 'app'그 키가 존재하면 (값 무관)

레이블과 어노테이션

어노테이션 (Annotation)은 비슷하게 생겼지만 셀렉터로 고를 수 없다. 레이블은 "고르기 위한 것", 어노테이션은 "적어두기 위한 것"이다. 빌드 정보, 도구 설정, 담당자 연락처 같은 것은 어노테이션에 넣는다 — 레이블에 넣으면 인덱스가 커지고 셀렉터가 지저분해진다.

책 6장이 권장하는 릴리스 레이블 규약(app, version, env, release)은 M30에서 카나리 배포를 만들 때 실제로 쓴다. 지금은 규칙 하나만 — 레이블은 처음 정할 때 팀 전체가 합의한다. 나중에 바꾸면 그 레이블에 의존하던 서비스·정책·대시보드가 한꺼번에 깨진다.

9.5따라하기 ③ 네임스페이스

6단계. 네임스페이스를 만들고 그 안에 배포한다

목적같은 이름의 오브젝트가 네임스페이스만 다르면 공존하는 것을 확인한다.

kubectl create namespace journal-dev
kubectl get ns
실행 결과
namespace/journal-dev created NAME STATUS AGE default Active 31m journal-dev Active 0s kube-node-lease Active 31m kube-public Active 31m kube-system Active 31m local-path-storage Active 31m

기본으로 있는 것들의 역할을 짚어둔다. default는 네임스페이스를 지정하지 않았을 때 쓰이는 곳이고, kube-system은 컨트롤 플레인과 시스템 애드온이 사는 곳이다(M01에서 본 그 파드들). kube-node-lease는 노드 하트비트, kube-public은 인증 없이 읽을 수 있는 정보용, local-path-storage는 kind가 설치한 기본 스토리지 프로비저너다(M18에서 쓴다).

kubectl apply -f course/labs/k8s/m09-pod-sidecar.yaml -n journal-dev
sleep 15
kubectl get pods -n journal-dev
kubectl get pods -A -l app=journal
실행 결과
pod/journal-with-sidecar created NAME READY STATUS RESTARTS AGE journal-with-sidecar 2/2 Running 0 15s NAMESPACE NAME READY STATUS RESTARTS AGE journal-dev journal-with-sidecar 2/2 Running 0 15s default journal-with-sidecar 2/2 Running 0 4m37s
판정마지막 표에 같은 이름의 파드가 NAMESPACE만 다르게 2행. 같은 이름의 파드가 두 네임스페이스에 공존한다 — 이름의 유효 범위가 네임스페이스이기 때문이다. AGE는 환경마다 다르다.

7단계. 기본 네임스페이스를 바꾼다

목적-n을 매번 붙이는 실수를 줄인다.

kubectl config set-context --current --namespace=journal-dev
kubectl config view --minify | grep namespace
kubectl get pods
  • --current — 지금 쓰는 컨텍스트(kind-study)를 대상으로. 컨텍스트 이름을 직접 적어도 된다
  • --minify — kubeconfig 전체가 아니라 현재 컨텍스트에 관련된 부분만 출력한다
실행 결과
Context "kind-study" modified. namespace: journal-dev NAME READY STATUS RESTARTS AGE journal-with-sidecar 2/2 Running 0 15s

-n을 붙이지 않았는데 journal-dev의 파드가 나온다. 이제 default에 있는 같은 이름의 파드는 -n default를 붙여야 보이고, M08의 web 디플로이먼트를 그냥 kubectl get deploy web으로 찾으면 Error from server (NotFound)가 난다 — M08 실패 ②의 상황을 반대 방향에서 겪는 것이다.

# 확인했으면 되돌린다. 이 과정의 나머지 모듈은 default 를 기준으로 쓴다
kubectl config set-context --current --namespace=default
kubectl config view --minify | grep namespace
실행 결과
Context "kind-study" modified. namespace: default
판정마지막 줄이 namespace: default. 이것을 되돌리지 않으면 M10부터 모든 명령이 journal-dev로 가서 No resources found만 보게 된다.

네임스페이스가 이름 구분만 하는 것이 아니라는 점이 중요하다. 앞으로 붙는 것들이 전부 여기 걸린다.

네임스페이스에 걸리는 것다루는 모듈
RBAC 권한 (Role · RoleBinding)M23
리소스 쿼터 · 리밋레인지M16
파드 시큐리티 수준 (레이블로 지정)M24
네트워크 정책의 기본 범위M25
DNS 이름 (<서비스>.<네임스페이스>.svc.cluster.local)M11

책 2.3절이 개발 클러스터를 여러 사람이 나눠 쓰는 방법으로 네임스페이스를 제시하는 이유가 이것이다 — 이름 충돌을 막는 것보다, 권한과 자원을 나누는 경계로서의 역할이 크다.

9.6일부러 실패시키기

실패 ① — 레이블 오타는 에러가 아니라 0개다 
kubectl get pods -l app=jounal
실행 결과
No resources found in default namespace.

journal이 jounal이 됐을 뿐인데 에러가 나지 않는다. 셀렉터는 "조건에 맞는 것"을 찾을 뿐이고, 없으면 없는 것이 정상 결과다.

이것이 쿠버네티스에서 가장 찾기 어려운 부류의 버그를 만든다. 서비스의 셀렉터에 오타가 있으면 서비스는 정상으로 보이는데 트래픽이 아무 데도 가지 않는다(M11에서 재현). 디플로이먼트의 셀렉터와 파드 템플릿의 레이블이 어긋나면 파드가 계속 만들어지기만 한다. 네트워크 정책의 셀렉터가 어긋나면 정책이 아무에게도 적용되지 않아 보안이 뚫린 채로 조용하다.

습관 두 가지로 막는다.

  • 셀렉터를 쓰는 오브젝트를 만든 뒤에는 반드시 대상 개수를 확인한다. 서비스면 kubectl get endpointslices, 정책이면 describe의 대상 목록
  • 레이블 값을 손으로 반복해 쓰지 않는다. 매니페스트에서 복사하거나 Kustomize의 공통 레이블 기능을 쓴다(M28)
실패 ② — 파드 안에서 포트가 겹친다

파드 하나에 IP가 하나이므로 같은 포트는 한 컨테이너만 열 수 있다. 가장 단순한 재현은 같은 이미지를 두 번 넣는 것이다 — M08의 nginx 두 개를 한 파드에 담는다. 둘 다 80을 열려고 한다.

cat <<'EOF' | kubectl apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: port-clash
spec:
  containers:
    - name: web
      image: nginx:1.29-alpine
    - name: web2
      image: nginx:1.29-alpine
EOF
sleep 10
kubectl get pod port-clash
실행 결과
pod/port-clash created NAME READY STATUS RESTARTS AGE port-clash 1/2 Error 1 (7s ago) 10s

READY 1/2 — 하나는 떴고 하나는 못 떴다. STATUS는 보는 순간에 따라 Error(죽은 직후)와 CrashLoopBackOff(재시작 대기 중)를 오가고, RESTARTS는 계속 오른다. 파드 상태만으로는 왜 죽었는지 알 수 없다. 컨테이너 로그로 간다.

kubectl logs port-clash -c web2
실행 결과
nginx: [emerg] bind() to [::]:80 failed (98: Address in use) 2026/09/05 08:40:56 [notice] 1#1: try again to bind() after 500ms 2026/09/05 08:40:56 [emerg] 1#1: still could not bind() nginx: [emerg] still could not bind()
판정bind() to [::]:80 failed (98: Address in use). 먼저 뜬 web이 80을 잡고 있어서 web2가 바인드에 실패했다. 어느 쪽이 먼저 뜨는지는 containers:에 적은 순서를 따른다.

메시지는 애플리케이션마다 다르다 — nginx는 위와 같고, Go나 Node 계열은 보통 address already in use(EADDRINUSE)를 찍는다. 공통점은 컨테이너 로그를 봐야만 원인이 보인다는 것이다. 이런 상황에서 원인을 찾는 순서는 다음과 같다.

kubectl get pod <파드>                         # READY n/m 과 RESTARTS 로 어느 컨테이너가 문제인지 좁힌다
kubectl describe pod <파드>                    # Last State: Terminated / Exit Code 와 BackOff 이벤트
kubectl logs <파드> -c <컨테이너>             # 죽어 있는 동안은 마지막 실행의 로그가 그대로 나온다
kubectl logs <파드> -c <컨테이너> --previous  # 다시 Running 이 된 뒤에 직전 인스턴스의 로그를 볼 때

--previous의 의미를 정확히 알아둔다. 컨테이너가 Error·CrashLoopBackOff로 멈춰 있는 동안은 --previous 없이도 마지막 실행의 로그가 나온다(위 출력이 그것이다). --previous는 컨테이너가 재시작해 다시 Running이 된 뒤, 방금 죽은 인스턴스의 로그를 볼 때 쓴다. 이 kind 클러스터(containerd 2.3)에서는 --previous가 unable to retrieve container logs for containerd://...를 돌려주는 경우가 있었다 — 죽은 컨테이너가 이미 정리된 뒤라서다. 그때는 describe의 Last State(Reason: Error, Exit Code: 1)와 죽어 있는 동안의 logs로 대신한다.

kubectl delete pod port-clash
실패 ③ — 네임스페이스를 지우면 안의 것이 전부 사라진다 
kubectl delete namespace journal-dev
kubectl get ns journal-dev
kubectl get pods -n journal-dev
실행 결과
namespace "journal-dev" deleted Error from server (NotFound): namespaces "journal-dev" not found No resources found in journal-dev namespace.

마지막 줄에 주의한다. 없는 네임스페이스를 -n으로 지정해도 에러가 아니라 No resources found다 — 레이블 오타(실패 ①)와 같은 부류의 "조용한 0개"다. 삭제가 몇 초 걸리면 첫 get ns에 Terminating이 보일 수도 있다.

확인 질문이 없다. 네임스페이스 안의 모든 오브젝트 — 파드, 서비스, 컨피그맵, PVC까지 — 가 함께 삭제된다. PVC가 지워지면 스토리지클래스의 reclaim 정책에 따라 실제 데이터도 지워질 수 있다(M18).

삭제가 Terminating에서 멈추는 경우도 흔하다. 파이널라이저가 걸린 리소스가 남아 있기 때문인데, 원인 리소스를 찾아 정리하는 것이 정석이다. 파이널라이저를 강제로 지우는 방법이 검색하면 나오지만, 정리되지 않은 외부 자원(클라우드 로드밸런서, 디스크)이 고아로 남으므로 마지막 수단으로만 쓴다.

9.7체크포인트와 정리

다음 모듈로 넘어가기 전 확인
  • kubectl get pod journal-with-sidecar → READY 2/2 · Running
  • kubectl logs journal-with-sidecar -c sidecar --tail=1 → {"status":"ok","version":"v1","pod":"journal-with-sidecar"} (사이드카가 localhost로 api를 호출한 결과)
  • kubectl get pod journal-with-sidecar -o jsonpath='{.status.initContainerStatuses[0].state.terminated.reason}' → Completed
  • kubectl exec journal-with-sidecar -c api -- cat /shared/init.txt → ready at HH:MM:SS (init 컨테이너가 쓴 파일을 다른 컨테이너가 읽는다)
  • kubectl get pods -l 'app=journal,env=dev' --no-headers | wc -l → 1, 그리고 kubectl get pods -l app=jounal → No resources found in default namespace.
  • kubectl config view --minify -o jsonpath='{..namespace}' → default (또는 빈 출력). journal-dev가 나오면 7단계의 되돌리기를 빼먹었다
  • kubectl get ns journal-dev → Error from server (NotFound)
  • (이해 확인) 네임스페이스에 걸리는 것을 이름 말고 세 가지 이상 — 7단계의 표로 답한다
  • (이해 확인) READY 1/2 · CrashLoopBackOff를 봤을 때 원인을 찾는 명령 순서 — 실패 ②의 네 줄
이 모듈이 남기는 파일
  • course/labs/k8s/m09-pod-sidecar.yaml — 멀티 컨테이너 파드 예제
kubectl delete -f course/labs/k8s/m09-pod-sidecar.yaml
kubectl delete namespace journal-dev --ignore-not-found   # 실패 ③에서 이미 지웠다. 건너뛰었다면 여기서 지워진다
kubectl delete deploy web --ignore-not-found              # M08에서 만든 것
실행 결과
pod "journal-with-sidecar" deleted from default namespace deployment.apps "web" deleted from default namespace

--ignore-not-found를 붙인 줄은 대상이 없으면 아무 출력 없이 넘어간다(종료 코드 0). 정리 스크립트가 "이미 지워져 있어서 실패"하는 일을 막는 옵션이다.
