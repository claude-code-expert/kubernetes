Compose로 다중 서비스

M05에서 컨테이너 두 개를 띄우는 데 네 개의 명령과 여러 옵션이 필요했다. 옵션 하나를 빠뜨리면 조용히 다른 시스템이 된다. 이 모듈에서 그것을 파일 하나에 선언하고, 그 파일이 쿠버네티스 매니페스트와 무엇이 같고 다른지 본다.

초반60분Docker Compose v5.1.0
2026-09-05 검증 · journal-api:v1 · redis:8.2-alpine · nginx:1.29-alpine · Compose 버전은 실습 당일 docker compose version으로 다시 확인한다 (2026-09-05 확인값 Docker Compose version v5.1.0)
사전 조건
  • M05 완료 — 볼륨과 사용자 정의 네트워크의 동작을 확인했다. M05가 남긴 컨테이너(redis1 · app1)는 있어도 없어도 된다
  • M04의 journal-api:v1 이미지와 course/labs/apps/journal-api/ 소스
  • 작업 디렉터리: course/labs/apps/ (journal-api/의 상위). M05와 다르다

핵심 3줄

1. Compose 파일은 선언이다. 명령을 순서대로 치는 대신 원하는 상태를 적고 up 한 번으로 맞춘다 — 쿠버네티스와 같은 발상이다.

2. depends_on만으로는 부족하다. 헬스체크와 함께 써야 "떴다"가 아니라 "쓸 수 있다"를 기다린다.

3. Compose는 한 대의 머신에서 끝난다. 노드가 여러 대가 되는 순간 필요한 것들(스케줄링·자가 복구·롤아웃)이 쿠버네티스의 존재 이유다.

6.1왜 파일로 옮기는가 6.2compose.yaml 읽기 6.3따라하기 ① 3서비스 기동 6.4따라하기 ② 스케일 · 로그 · 개발 루프 6.5일부러 실패시키기 6.6운영 관점 — Compose와 쿠버네티스 6.7체크포인트와 정리

6.1왜 파일로 옮기는가

M05의 마지막 상태를 다시 만들려면 이렇게 쳐야 한다 — 볼륨 생성, 네트워크 생성, 레디스 실행(볼륨·네트워크 지정), API 실행(네트워크·환경변수·포트 지정). 네 명령에 옵션이 여덟 개다.

문제는 재현이다. 내일 다시 칠 때 --save 60 1을 빠뜨리면 레디스가 디스크에 저장하지 않고, 팀원이 -e REDIS_URL의 포트를 틀리면 그 사람 노트북에서만 안 된다. M05의 실패 ①이 정확히 이것이었다 — --network 하나가 빠졌는데 에러 없이 다른 시스템이 됐다. 명령의 이력은 남지 않지만 파일은 남는다. 그래서 구성은 파일에 적고 그 파일을 버전 관리한다.

책 1.2절이 같은 이야기를 쿠버네티스에서 한다 — 선언형 방식이 명령형보다 나은 이유는 "클러스터가 어떻게 그 상태가 됐는지" 이해하고 되살릴 수 있기 때문이다. Compose는 그 발상의 한 대짜리 버전이다.

6.2compose.yaml 읽기

책 1장의 저널 서비스는 세 조각이다 — 정적 파일 서버, API, 데이터 저장소. 그 구성을 그대로 옮긴다. course/labs/apps/compose.yaml:

name: journal

services:
  redis:
    image: redis:8.2-alpine
    command: ["redis-server", "--save", "60", "1"]
    volumes:
      - journal-data:/data
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 5s
      timeout: 3s
      retries: 5
    networks: [journal-net]

  api:
    build:
      context: ./journal-api
    image: journal-api:v1
    develop:
      watch:                          # docker compose watch — src 가 바뀌면 다시 빌드해 교체한다
        - action: rebuild
          path: ./journal-api/src
    environment:
      REDIS_URL: redis://redis:6379
      APP_VERSION: v1
    depends_on:
      redis:
        condition: service_healthy   # 레디스가 healthy 가 된 뒤에야 시작한다
    healthcheck:
      test: ["CMD-SHELL", "wget -q -O- http://localhost:8080/readyz || exit 1"]
      interval: 5s
      timeout: 3s
      retries: 5
    networks: [journal-net]

  web:
    image: nginx:1.29-alpine
    ports:
      - "8090:80"
    volumes:
      - ./static-site:/usr/share/nginx/html:ro
      - ./nginx.conf:/etc/nginx/conf.d/default.conf:ro
    depends_on:
      api:
        condition: service_healthy
    networks: [journal-net]

volumes:
  journal-data:

networks:
  journal-net:

맨 위의 name: journal이 프로젝트 (Project) 이름이다. Compose는 한 파일이 만드는 컨테이너 · 네트워크 · 볼륨을 이 이름으로 묶고, 만드는 리소스 이름 앞에 접두사로 붙인다. 생략하면 디렉터리 이름(apps)이 쓰인다 — 6.5절 실패 ③이 이 접두사 때문에 생긴다.

키의미M05의 무엇에 해당하나
services컨테이너 하나씩. 키가 곧 DNS 이름이 된다docker run --name
image / build쓸 이미지, 또는 빌드할 경로. 둘 다 있으면 빌드한 결과에 그 태그를 붙인다docker build -t + docker run
develop.watch지정한 경로가 바뀌면 다시 빌드하고 컨테이너를 교체한다 (6.4절)M05에는 없던 것
volumes (서비스)이름이면 볼륨, ./로 시작하면 바인드 마운트-v
environment환경 변수 주입-e
ports호스트:컨테이너 포트 매핑. 여기서는 web 에만 있다-p
healthcheck컨테이너가 쓸 수 있는 상태인지 주기적으로 확인M05에는 없던 것
depends_on + condition기동 순서. service_healthy는 헬스체크 통과까지 기다린다M05에서는 사람이 sleep 2로 때웠다

헬스체크 (Healthcheck)는 도커가 컨테이너 안에서 주기적으로 돌리는 명령이다. 종료 코드 0이면 healthy, 아니면 실패로 세고 retries만큼 연속 실패하면 unhealthy가 된다. 프로세스가 살아 있다는 것과 요청을 처리할 수 있다는 것은 다르다 — 레디스는 redis-cli ping이 PONG을 돌려줄 때, API는 /readyz가 200일 때 쓸 수 있다. 이 구분이 M15에서 레디니스 프로브로 그대로 이어진다.

ports가 web에만 있는 것이 중요하다. api와 redis는 호스트에 노출되지 않고 journal-net 안에서만 보인다. 외부에서 들어오는 문을 하나로 줄이는 이 구조가 M12 인그레스의 원형이다.

nginx 설정도 같은 발상이다. /는 정적 파일, /api/는 API 컨테이너로 넘긴다. course/labs/apps/nginx.conf:

server {
  listen 80;
  location / {
    root /usr/share/nginx/html;
    index index.html;
  }
  location /api/ {
    proxy_pass http://api:8080;
    proxy_set_header Host $host;
  }
}

proxy_pass http://api:8080 — IP가 아니라 서비스 이름이다. M05에서 확인한 내장 DNS가 이것을 풀어준다.

정적 파일 서버가 내보낼 페이지는 한 장이다. course/labs/apps/static-site/index.html:

<!doctype html>
<meta charset="utf-8">
<title>Journal</title>
<h1>Journal</h1>
<p>정적 파일 서버가 이 페이지를, /api 는 저널 API가 처리한다.</p>

내용은 중요하지 않다. 같은 포트로 들어온 요청이 경로에 따라 다른 컨테이너로 간다는 것을 눈으로 확인하는 표지판이다.

6.3따라하기 ① 3서비스 기동

1단계. 파일을 검증한다

목적기동 전에 병합·해석 결과를 확인한다. YAML 들여쓰기 실수를 여기서 잡는다.

cd course/labs/apps
docker compose config | head -28
실행 결과 (앞부분)
name: journal services: api: build: context: /Users/mini/project/kubernetes/course/labs/apps/journal-api dockerfile: Dockerfile depends_on: redis: condition: service_healthy required: true develop: watch: - path: /Users/mini/project/kubernetes/course/labs/apps/journal-api/src action: rebuild environment: APP_VERSION: v1 REDIS_URL: redis://redis:6379 healthcheck: test: - CMD-SHELL - wget -q -O- http://localhost:8080/readyz || exit 1 timeout: 3s interval: 5s retries: 5 image: journal-api:v1 networks: journal-net: null

상대 경로가 절대 경로로, 축약 표기가 정식 표기로 펼쳐졌다. 이것이 Compose가 실제로 해석한 내용이다. 여러 파일을 겹쳐 쓸 때(-f compose.yaml -f compose.prod.yaml) 병합 결과를 확인하는 용도로도 쓴다. 절대 경로 부분은 저장소를 받은 위치에 따라 다르다.

판정에러 없이 YAML이 출력된다. 문법 오류가 있으면 여기서 줄 번호와 함께 알려준다.

2단계. 기동한다

목적선언한 상태를 명령 하나로 만든다. 출력에서 세 서비스가 어떤 순서로 뜨는지 읽는다.

docker compose up -d
  • up — 없는 것은 만들고, 정의가 바뀐 것은 다시 만들고, 이미 맞는 것은 그대로 둔다. 여러 번 실행해도 안전하다
  • -d — 백그라운드. 빼면 모든 서비스의 로그가 터미널에 섞여 나온다(개발 중에는 이쪽이 편할 때도 있다)
실행 결과
Container journal-web-1 Creating Container journal-web-1 Created Container journal-redis-1 Starting Container journal-redis-1 Started Container journal-redis-1 Waiting Container journal-redis-1 Healthy Container journal-api-1 Starting Container journal-api-1 Started Container journal-api-1 Waiting Container journal-api-1 Healthy Container journal-web-1 Starting Container journal-web-1 Started

순서를 읽어본다. redis Started → Waiting → Healthy → 그제서야 api Starting. api도 같은 방식으로 Healthy가 된 뒤에야 web이 시작한다. depends_on에 condition: service_healthy를 준 결과다. up -d가 돌아오기까지 10초 남짓 걸리는 것도 이 대기 때문이다.

판정세 컨테이너가 모두 Started이고 중간에 Healthy 표시가 나온다.

3단계. 상태와 동작을 확인한다

목적세 컨테이너의 이름 · 헬스 상태 · 포트 노출을 한눈에 보고, 요청이 세 컨테이너를 거쳐 처리되는지 확인한다.

docker compose ps
실행 결과
NAME IMAGE SERVICE STATUS PORTS journal-api-1 journal-api:v1 api Up 5 seconds (healthy) 8080/tcp journal-redis-1 redis:8.2-alpine redis Up 11 seconds (healthy) 6379/tcp journal-web-1 nginx:1.29-alpine web Up Less than a second 0.0.0.0:8090->80/tcp

컨테이너 이름이 <프로젝트>-<서비스>-<번호> 형식이다. STATUS의 (healthy)가 헬스체크 결과이며, web에는 헬스체크를 정의하지 않아 표시가 없다. PORTS를 보면 api와 redis는 컨테이너 포트만 있고 호스트 매핑이 없다. 외부에서 직접 접근할 수 없다는 뜻이다.

curl -s localhost:8090/ | head -4
curl -s -X POST localhost:8090/api/entries -H 'content-type: application/json' -d '{"text":"via compose"}'; echo
curl -s localhost:8090/api/entries
실행 결과
<!doctype html> <meta charset="utf-8"> <title>Journal</title> <h1>Journal</h1> {"id":"1788440143639"} {"entries":["{\"text\":\"via compose\"}"]}
판정같은 8090 포트로 /는 정적 페이지를, /api/entries는 API 응답을 받았다. 요청은 web → api → redis 세 컨테이너를 거쳤다. id 값은 타임스탬프라 매번 다르다.

6.4따라하기 ② 스케일 · 로그 · 개발 루프

4단계. API를 3개로 늘린다

목적같은 서비스의 복제본을 만들고, 이름 하나 뒤에 여러 컨테이너가 서는 구조를 확인한다.

docker compose up -d --scale api=3
docker compose ps --format 'table {{.Name}}\t{{.Service}}\t{{.Status}}'
실행 결과
NAME SERVICE STATUS journal-api-1 api Up 18 seconds (healthy) journal-api-2 api Up 5 seconds (healthy) journal-api-3 api Up 5 seconds (healthy) journal-redis-1 redis Up 23 seconds (healthy) journal-web-1 web Up 12 seconds

nginx 설정은 바뀌지 않았는데 proxy_pass http://api:8080이 이제 세 컨테이너 중 하나로 간다. 도커의 내장 DNS가 api라는 이름에 세 개의 IP를 돌려주기 때문이다.

--scale이 되는 조건이 하나 있다. api에 ports를 지정했다면 두 번째 컨테이너가 같은 호스트 포트를 잡으려다 실패했을 것이다(M02의 포트 충돌). 복제 가능한 서비스는 호스트 포트를 직접 잡지 않는다 — 이 제약이 쿠버네티스에서 Service라는 계층으로 정리된다(M11).

판정api 컨테이너 3개가 모두 (healthy). 8090 요청은 계속 정상 응답한다.

5단계. 로그를 서비스 단위로 본다

목적컨테이너 세 개의 로그를 컨테이너 이름이 아니라 서비스 이름으로 한 번에 본다. 복제본이 늘수록 이 습관이 필요하다.

docker compose logs --tail=3 api
  • --tail=N — 컨테이너마다 마지막 N줄만. 빼면 처음부터 전부 나온다
  • 서비스 이름을 빼면 web · redis까지 모든 서비스의 로그가 섞여 나온다
실행 결과
api-3 | {"level":"info","msg":"listening","port":8080,"version":"v1"} api-3 | {"level":"info","msg":"redis connected","url":"redis://redis:6379"} api-1 | {"level":"info","msg":"listening","port":8080,"version":"v1"} api-1 | {"level":"info","msg":"redis connected","url":"redis://redis:6379"} api-2 | {"level":"info","msg":"listening","port":8080,"version":"v1"} api-2 | {"level":"info","msg":"redis connected","url":"redis://redis:6379"}
판정세 컨테이너의 줄이 api-1 · api-2 · api-3 접두사로 구분되어 나오고, 셋 다 redis connected가 있다. 각 컨테이너의 로그가 두 줄뿐이라 --tail=3에도 두 줄씩 나왔다. 컨테이너 순서는 실행마다 다르다.

실시간으로 따라가려면 docker compose logs -f api. 같은 줄이 나온 뒤 새 로그를 기다리며 멈춰 있고, Ctrl+C로 빠져나온다 — 컨테이너는 계속 돈다. 서비스 이름으로 로그를 모아 보는 이 방식은 쿠버네티스에서 kubectl logs -l app=journal-api --all-containers로 이어진다.

6단계. 소스가 바뀌면 자동으로 다시 빌드한다 — compose watch

목적소스를 고칠 때마다 docker build · docker compose up을 손으로 치는 대신, 파일 변경을 감지해 빌드·교체를 자동으로 하는 개발 루프를 켠다. 6.2절의 develop.watch가 이 단계의 설정이다.

복제본이 셋이면 교체할 컨테이너도 셋이라 로그가 길어진다. 먼저 하나로 줄인다.

docker compose up -d --scale api=1
실행 결과 (핵심 줄만)
Container journal-api-3 Stopping Container journal-api-2 Stopping Container journal-api-2 Stopped Container journal-api-2 Removing Container journal-api-2 Removed Container journal-api-3 Stopped Container journal-api-3 Removing Container journal-api-3 Removed Container journal-api-1 Waiting Container journal-api-1 Healthy

이제 소스 사본을 만들어 두고 watch를 켠다. watch는 포그라운드로 돌면서 터미널을 점유하므로 두 번째 터미널이 필요하다.

cp journal-api/src/server.ts /tmp/server.ts.bak      # 되돌릴 사본
docker compose watch api
실행 결과 (첫 번째 터미널 — 빌드 로그는 생략)
Image journal-api:v1 Building ... Image journal-api:v1 Built Container journal-redis-1 Running Container journal-api-1 Recreate Container journal-api-1 Recreated Container journal-redis-1 Waiting Container journal-redis-1 Healthy Container journal-api-1 Starting Container journal-api-1 Started Watch enabled

시작하자마자 한 번 빌드하고 컨테이너를 교체한 뒤 Watch enabled에서 멈춘다. 이 상태로 두고, 두 번째 터미널에서 소스를 고친다.

cd course/labs/apps
echo '// watch test' >> journal-api/src/server.ts
실행 결과 (첫 번째 터미널에 이어서 나온다 — 핵심 줄만)
Rebuilding service(s) ["api"] after changes were detected... Image journal-api:v1 Building #11 [build 6/7] COPY src ./src #11 DONE 0.0s #12 [build 7/7] RUN npm run build #12 DONE 1.5s ... Image journal-api:v1 Built service(s) ["api"] successfully built Container journal-api-1 Recreate Container journal-api-1 Recreated Container journal-api-1 Starting Container journal-api-1 Started
판정파일을 저장한 직후 Rebuilding service(s) ["api"] after changes were detected...가 뜨고, M04에서 본 캐시 동작 그대로 COPY src부터만 다시 돌아 2초 안에 새 컨테이너가 Started된다. docker compose ps를 치면 journal-api-1의 Up 시간이 방금으로 바뀌어 있다.

실험이 끝났으면 두 번째 터미널에서 소스를 되돌린다. 되돌리는 것도 변경이므로 watch가 한 번 더 빌드해 원래 이미지로 교체한다 — 그것까지 확인한 뒤 첫 번째 터미널에서 Ctrl+C로 watch를 끝낸다. 컨테이너는 계속 돈다.

mv /tmp/server.ts.bak journal-api/src/server.ts
tail -n 1 journal-api/src/server.ts          # });  이면 원래대로다

action: rebuild는 이미지를 다시 빌드하는 방식이고, 인터프리터 언어라면 action: sync로 파일만 컨테이너 안에 복사해 더 빨리 반영할 수 있다. 이 애플리케이션은 타입스크립트 컴파일이 필요해 rebuild를 쓴다. 쿠버네티스에는 이런 개발 루프가 내장돼 있지 않다 — Skaffold · Tilt 같은 별도 도구가 그 자리를 채우며, 이 과정에서는 M29의 CI가 빌드를 대신한다.

6.5일부러 실패시키기

실패 ① — depends_on 만 쓰고 헬스체크 조건을 빼면

depends_on을 조건 없이 쓰면 Compose는 의존 컨테이너가 시작됐는지만 본다. 프로세스가 살아 있는 것과 접속을 받을 준비가 된 것은 다르다. 이 실습의 레디스는 데이터가 거의 없어 0.1초 만에 뜨기 때문에, 조건을 빼도 경합이 눈에 잘 안 보인다. 실제 운영에서 레디스가 수 GB짜리 데이터 파일을 읽으며 뜨는 데 몇 초가 걸리는 상황을 sleep 5로 흉내 낸다. 파일을 두 곳 고친다.

cp compose.yaml /tmp/compose.yaml.bak            # 되돌릴 사본
  redis:
    image: redis:8.2-alpine
    command: ["sh", "-c", "sleep 5 && exec redis-server --save 60 1"]   # 느리게 뜨는 레디스 흉내
    ...
  api:
    ...
    depends_on:
      - redis          # 조건 없음 — "시작됨"만 기다린다

web은 api가 healthy가 될 때까지 기다리므로 그대로 두고 up하면 대기에 묶인다. 경합이 벌어지는 5초 창을 보려고 redis와 api만 띄운다.

docker compose down
docker compose up -d redis api
sleep 2
docker compose exec api wget -S -qO- http://localhost:8080/readyz 2>&1 | head -1
docker compose logs --no-log-prefix api | head -3
docker compose ps --format 'table {{.Name}}\t{{.Service}}\t{{.Status}}'
  • up -d redis api — 서비스 이름을 적으면 그것과 그 의존 대상만 띄운다. web은 뜨지 않는다
  • wget -S — 응답 헤더(상태 줄)를 표준 에러로 출력한다. api에는 curl이 없고 wget이 있다
  • --no-log-prefix — 컨테이너 이름 접두사를 뗀다
실행 결과 (Creating · Created 줄은 생략)
Container journal-redis-1 Starting Container journal-redis-1 Started Container journal-api-1 Starting Container journal-api-1 Started HTTP/1.1 503 Service Unavailable {"level":"info","msg":"listening","port":8080,"version":"v1"} {"level":"error","msg":"redis error","detail":"Error: connect ECONNREFUSED 172.22.0.2:6379"} {"level":"error","msg":"redis error","detail":"Error: connect ECONNREFUSED 172.22.0.2:6379"} NAME SERVICE STATUS journal-api-1 api Up 2 seconds (health: starting) journal-redis-1 redis Up 2 seconds (health: starting)

6.3절의 기동 출력과 비교한다. redis Started 다음에 Waiting · Healthy가 없고 바로 api Starting이다. API는 뜨자마자 레디스에 붙으려 하고, 레디스 컨테이너는 있지만(이름은 풀려서 172.22.0.2가 나왔다) 아직 아무도 6379를 듣지 않아 ECONNREFUSED다. M05의 ENOTFOUND(이름이 안 풀림)와 다른 에러라는 점을 눈여겨 둔다. IP는 환경마다 다르다.

판정/readyz가 503이고 로그에 connect ECONNREFUSED가 반복된다. 두 컨테이너 모두 (health: starting) — 레디스는 아직 ping에 답하지 못하고, API는 그래서 준비되지 못했다.

몇 초 뒤 다시 보면 레디스가 뜨고 API가 스스로 복구한다.

sleep 8
docker compose logs --no-log-prefix api | tail -2
docker compose exec api wget -S -qO- http://localhost:8080/readyz 2>&1 | head -1
실행 결과
{"level":"error","msg":"redis error","detail":"Error: connect ECONNREFUSED 172.22.0.2:6379"} {"level":"info","msg":"redis connected","url":"redis://redis:6379"} HTTP/1.1 200 OK

M05에서 확인했듯 이 애플리케이션은 저장소가 없어도 죽지 않고 /readyz를 503으로 돌려준 뒤 재연결을 계속한다 — 그렇게 만들었기 때문이다. 그런 방어가 없는 애플리케이션은 첫 ECONNREFUSED에서 크래시하고, 재시작 정책이 없으면 그대로 끝난다.

여기서 얻을 원칙이 둘이다. 기다림은 조건으로 표현한다(service_healthy), 그리고 애플리케이션은 의존 대상이 없어도 죽지 않게 만든다. 쿠버네티스에는 depends_on이 아예 없다 — 파드는 순서 없이 뜨고, 준비되지 않은 파드는 레디니스 프로브로 트래픽에서 빠진다(M15). 그래서 두 번째 원칙이 훨씬 더 중요해진다.

파일을 되돌리고 정상 구성으로 다시 띄운다.

mv /tmp/compose.yaml.bak compose.yaml
grep -c service_healthy compose.yaml         # 2 가 나오면 원래 파일이다
docker compose down
docker compose up -d
실패 ② — down -v 로 데이터를 날린다

정리 명령의 차이를 알아둔다. 실습 환경이니 지금 확인해 보는 편이 낫다.

명령지우는 것볼륨 데이터
docker compose stop컨테이너 중지만남는다
docker compose down컨테이너 + 네트워크남는다
docker compose down -v위 + 이 프로젝트의 볼륨사라진다
docker compose down
docker compose up -d
curl -s localhost:8090/api/entries; echo
실행 결과 (down · up 의 마지막 줄과 응답)
Network journal_journal-net Removed Container journal-web-1 Started {"entries":["{\"text\":\"via compose\"}"]}

6.3절에서 넣은 엔트리가 그대로 있다. 컨테이너와 네트워크는 지워졌다 다시 만들어졌지만 볼륨은 건드리지 않았기 때문이다. 실패 ①에서 down을 두 번 했는데도 남아 있던 이유가 이것이다.

docker compose down -v
docker compose up -d
curl -s localhost:8090/api/entries; echo
실행 결과 (핵심 줄만)
Volume journal_journal-data Removing Volume journal_journal-data Removed Container journal-web-1 Started {"entries":[]}
판정down 뒤에는 엔트리가 남고, down -v 뒤에는 {"entries":[]} — 비어 있다. 출력에 Volume journal_journal-data Removed가 찍힌 순간 데이터는 사라졌다.

-v 한 글자 차이로 데이터가 사라진다. CI 스크립트나 정리 스크립트에 down -v를 습관적으로 넣어 두면, 그 스크립트가 언젠가 데이터가 든 환경에서 돌아간다.

실패 ③ — 볼륨 이름이 M05와 다르다

M05에서 만든 볼륨은 journal-data였는데, Compose로 띄운 뒤 확인하면 이렇다.

docker volume ls --filter name=journal
docker network ls --filter name=journal
실행 결과
DRIVER VOLUME NAME local journal-data local journal_journal-data NETWORK ID NAME DRIVER SCOPE a56f9b2d7c85 journal-net bridge local 2e8f02ea1265 journal_journal-net bridge local

Compose는 프로젝트 이름을 접두사로 붙인 별도의 볼륨과 네트워크를 만든다. M05에서 넣은 데이터가 안 보이는 이유가 이것이다 — 지워진 게 아니라 다른 볼륨을 보고 있다. 실패 ②의 down -v가 지운 것도 journal_journal-data지 M05의 journal-data가 아니다. 기존 볼륨을 그대로 쓰려면 external: true로 선언한다. 네트워크 ID는 환경마다 다르다.

volumes:
  journal-data:
    external: true      # 이미 있는 journal-data 볼륨을 그대로 쓴다

"데이터가 사라졌다"는 신고의 상당수가 실제로는 이런 이름 불일치다. 지우기 전에 docker volume ls부터 본다.

6.6운영 관점 — Compose와 쿠버네티스

Compose 파일과 쿠버네티스 매니페스트는 둘 다 선언형이고 YAML이지만, 전제가 다르다.

Compose쿠버네티스
대상머신 한 대노드 여러 대
배치 결정없음 — 전부 이 머신에서 돈다스케줄러가 노드를 고른다 (M16)
컨테이너가 죽으면restart 정책에 따라 도커가 재시작컨트롤러가 새 파드를 다른 노드에라도 만든다 (M10)
기동 순서depends_on없다. 프로브로 준비 상태를 알린다 (M15)
서비스 이름내장 DNS가 컨테이너 이름을 푼다Service 오브젝트 + CoreDNS (M11)
설정 주입environment, env_fileConfigMap · Secret (M13)
업데이트up 다시 — 컨테이너를 지우고 새로 만든다 (다운타임)롤링 업데이트 (M10)

Compose로 충분한 경우가 많다 — 개발 환경, 단일 서버 배포, CI에서 의존 서비스 띄우기. 쿠버네티스가 필요해지는 지점은 노드가 여러 대가 되고, 죽은 것을 사람이 되살리기 싫어질 때다. 실습 규모에서는 이 차이가 체감되지 않는다. 다만 6단계의 watch 출력에서 Recreate → Recreated → Started 사이에는 api 컨테이너가 없다 — 복제본이 하나뿐이면 그 시간 동안 새 요청을 받을 곳이 없고, 이것이 새 컨테이너를 먼저 띄운 뒤 옛것을 내리는 롤링 업데이트(M10)가 필요한 이유다. Part 2부터 그 세계로 넘어간다.

Compose 파일을 쿠버네티스로 자동 변환하는 도구는? kompose 같은 변환 도구가 있지만 이 과정에서는 쓰지 않는다. 변환 결과는 대개 그대로 못 쓰고(프로브·리소스·레이블 규약이 빠진다), 무엇보다 매니페스트를 직접 쓰면서 배우는 것이 이 과정의 목적이다. M08~M14에서 같은 저널 애플리케이션을 손으로 옮긴다.

6.7체크포인트와 정리

다음 모듈로 넘어가기 전 확인
  • docker compose ps --format 'table {{.Name}}\t{{.Service}}\t{{.Status}}' → 세 줄. api와 redis의 STATUS에 (healthy), web은 Up
  • curl -s -o /dev/null -w '%{http_code}\n' localhost:8090/ → 200, curl -s localhost:8090/api/entries → {"entries":[…]} 형태의 JSON
  • docker compose config | grep -c service_healthy → 2 (api→redis, web→api 두 조건이 원래대로 있다)
  • docker compose config | grep -A3 'develop:' → watch: · action: rebuild · path: …/journal-api/src
  • docker compose up -d --scale api=3 && docker compose ps --format '{{.Service}}' | grep -c api → 3 (확인 뒤 docker compose up -d --scale api=1)
  • tail -n 1 journal-api/src/server.ts → }); — 6단계의 사본 되돌리기가 끝났다
  • (이해 확인) down과 down -v 중 어느 쪽이 Volume … Removed를 찍는가
  • (이해 확인) api에 ports를 주면 --scale api=3이 왜 실패하는가
이 모듈이 남기는 파일
  • course/labs/apps/compose.yaml — 3서비스 정의, develop.watch 포함. 6.5절 실패 ①의 수정은 되돌린 상태다. M14에서 이 파일의 서비스 하나하나가 쿠버네티스 매니페스트(Deployment · Service · StatefulSet)로 옮겨진다
  • course/labs/apps/nginx.conf — 경로 라우팅. M12에서 인그레스 규칙으로 다시 쓴다
  • course/labs/apps/static-site/index.html — 정적 파일 서버 콘텐츠. M14의 web 파드가 같은 내용을 ConfigMap으로 담는다
  • 실행 중인 컨테이너 journal-api-1 · journal-redis-1 · journal-web-1과 볼륨 journal_journal-data(실패 ②로 비어 있다)
# 컨테이너와 네트워크 정리 (볼륨 데이터는 남긴다)
docker compose down

# 다음 모듈에서 이미지를 레지스트리에 올린다. journal-api:v1 은 지우지 않는다
docker images journal-api

M05가 남긴 redis1 · app1 · app-bad가 아직 있다면 docker rm -f redis1 app1 app-bad. 볼륨 journal-data와 네트워크 journal-net은 두어도 된다.
