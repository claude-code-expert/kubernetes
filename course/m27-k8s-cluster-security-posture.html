클러스터 보안 태세

M23부터 인가·파드 보안·네트워크·어드미션을 하나씩 걸었다. 그런데 지금 이 클러스터가 전체적으로 어떤 상태인지는 아직 아무도 모른다 — 어제 누가 무엇을 지웠는지, 진단 도구가 무엇을 지적하는지, 파드 하나가 뚫리면 어디까지 가는지. 이 모듈에서 감사 로깅을 켜고, CIS 진단으로 지적 10개를 받아 6개를 고치고, 남은 4개는 근거를 적고 넘어가는 판단까지 한다.

27.1걸어 둔 규칙이 지금 어떤 상태인지 모른다

M23에서 dev 계정을 만들고, M24에서 journal에 restricted를 걸고, M25에서 네트워크를 화이트리스트로 바꾸고, M26에서 latest 태그를 거부하게 했다. 규칙 넷은 각각 그때 확인했다. 그런데 지금 물어보면 대답할 수 없는 질문들이 있다.

어제 저녁 누가 journal의 디플로이먼트를 지웠는가. dev 계정이 권한 밖의 일을 시도한 적이 있는가. 정책이 걸리지 않은 네임스페이스는 몇 개인가. 우리가 M19에서 관측을 위해 바꾼 설정이 보안 기준에서는 어떻게 평가되는가. 규칙을 거는 것과 상태를 아는 것은 다른 작업이고, 지금까지 우리는 앞의 것만 했다.

이 모듈은 세 종류의 눈을 만든다. 감사 로그는 일어난 일을 기록한다 — 사후에만 쓸모가 있지만, 사후에는 이것 말고 아무것도 없다. 진단 도구는 설정을 기준과 대조한다 — 아직 일어나지 않은 일을 막는다. 이미지 스캔은 우리가 배포한 것 안에 무엇이 들어 있는지 본다.

셋 다 공통점이 하나 있다. 결과가 많이 나온다는 것이다. 감사 로그는 유휴 클러스터에서도 하루 1GB를 넘고, 진단 도구는 지적을 열 개씩 뱉는다. 이 모듈에서 진짜 배울 것은 켜는 방법이 아니라 무엇을 버리고 무엇을 남길지 정하는 방법이다.

27.2이론 — 감사 로그와 공격 경로

책 매핑19.1 etcd 접근·인증·인가·TLS·kubelet과 클라우드 메타데이터·감사 로깅 · 19.4 넌루트·무배포 컨테이너, 취약점 스캔

감사 로그는 API 서버만 남긴다

쿠버네티스의 감사는 API 서버를 지나간 요청을 기록한다. M22에서 만든 로그 파이프라인이 앱이 무엇을 했는지를 남긴다면, 감사 로그는 누가 클러스터를 어떻게 바꿨는지를 남긴다. 파드 안에서 일어난 일은 여기 없다.

기록 수준은 넷이다. None(남기지 않음), Metadata(누가·언제·무엇을·결과), Request(+요청 본문), RequestResponse(+응답 본문). 수준이 올라갈수록 사후 복원력이 좋아지고 용량과 유출 위험이 함께 커진다. 시크릿을 RequestResponse로 남기면 감사 로그 자체가 시크릿 저장소가 된다 — 그래서 시크릿·컨피그맵은 대개 Metadata로 낮춘다.

정책 파일의 규칙은 위에서 아래로 평가되고 처음 일치한 규칙이 적용된다. 방화벽 ACL과 같은 구조라서 순서가 곧 의미다. 버릴 것을 위에 쓰고 남길 것을 아래에 쓰는데, 위에 너무 넓은 None을 쓰면 아래의 모든 규칙이 죽는다. 27.7의 첫 번째 실패가 정확히 이것이다.

파드에서 시작하는 경로

앱에 취약점이 있어 파드 안에서 임의 명령이 돌게 됐다고 하자. 그다음 공격자가 시도하는 것은 대개 정해져 있다.

첫째, 서비스어카운트 토큰이다. M24에서 automountServiceAccountToken: false를 넣은 이유이고, M26에서 그것을 자동으로 붙게 만든 이유다. 둘째, 노드의 kubelet API다. :10250은 그 노드의 모든 파드에서 명령을 실행할 수 있는 통로라서, 인증이 뚫리면 노드 하나가 통째로 넘어간다. 셋째, 클라우드 메타데이터 주소인 169.254.169.254다. 클라우드에서 이 주소는 인증 없이 인스턴스의 자격 증명을 내주고, 그 자격 증명은 클러스터 밖 — 스토리지·데이터베이스·다른 계정 — 까지 닿는다.

뒤의 둘은 네트워크 이그레스로 막는다. M25에서 만든 것과 같은 정책에 ipBlock과 except를 쓰는 것이 전부인데, 여기에 함정이 하나 있다. ipBlock은 클러스터 밖 IP를 위한 것이라서 파드끼리의 통신은 ipBlock으로 열리지 않는다. 27.6에서 이것 때문에 DNS가 죽는 것을 확인한다.

진단 도구가 보는 것

CIS 벤치마크CIS Kubernetes Benchmark는 컨트롤 플레인 설정을 항목별로 점검하는 공개 기준이다. kube-bench는 그 항목을 노드의 파일과 프로세스를 직접 읽어 판정한다. 그래서 이 도구는 hostPID와 호스트 경로 마운트를 요구하고, 그 권한을 요구한다는 사실 자체가 상시로 두지 않고 필요할 때만 돌리는 이유가 된다.

중요한 것은 지적을 전부 없애는 것이 목표가 아니라는 점이다. 기준은 일반적인 클러스터를 가정하고 쓰였고, 우리 클러스터에는 우리만의 사정이 있다. 27.5에서 지적 넷을 고치지 않고 근거를 적어 남긴다. 근거 없이 남은 지적과 근거가 있는 지적은 다음에 이 목록을 보는 사람에게 완전히 다른 정보다.

27.3따라하기 ① 감사 로깅을 켠다

1단계 — 지금 켜져 있지 않다는 것을 확인한다

목적기본값을 확인한다. 감사는 기본으로 꺼져 있다.

docker exec study-control-plane \
  grep -c audit /etc/kubernetes/manifests/kube-apiserver.yaml
출력
0
판정플래그가 하나도 없다. 관리형 쿠버네티스에서는 대개 클라우드 사업자가 켜서 자기 로그 서비스로 보내지만, 직접 운영하는 클러스터에서는 아무것도 기록되지 않는 상태가 기본이다.

2단계 — 정책 파일을 쓴다

목적"무엇을 버릴지"를 먼저 정한다. 전부 남기면 아무것도 읽지 못한다.

cat > course/labs/infra/audit-policy.yaml <<'EOF'
apiVersion: audit.k8s.io/v1
kind: Policy
omitStages:
  - RequestReceived
rules:
  # ① 읽기는 시스템 구성요소 것만 버린다
  - level: None
    userGroups: ["system:nodes", "system:serviceaccounts:kube-system"]
    verbs: ["get", "list", "watch"]
  - level: None
    users: ["system:apiserver", "system:kube-scheduler", "system:kube-controller-manager"]
    verbs: ["get", "list", "watch"]

  # ② 컨트롤러가 스스로 하는 쓰기는 버린다. 양이 압도적이다
  - level: None
    users:
      - system:apiserver
      - system:kube-scheduler
      - system:kube-controller-manager
    verbs: ["update", "patch"]
    resources:
      - group: ""
        resources: ["endpoints", "leases", "events"]
  - level: None
    userGroups: ["system:nodes"]
    verbs: ["update", "patch"]

  # ③ 시크릿·컨피그맵은 본문을 남기지 않는다
  - level: Metadata
    resources:
      - group: ""
        resources: ["secrets", "configmaps"]
      - group: "authentication.k8s.io"
        resources: ["tokenreviews"]

  # ④ 삭제와 권한 변경은 본문까지
  - level: RequestResponse
    verbs: ["delete", "deletecollection"]
  - level: RequestResponse
    resources:
      - group: "rbac.authorization.k8s.io"
      - group: "admissionregistration.k8s.io"

  # ⑤ 나머지 쓰기는 요청 본문까지
  - level: Request
    verbs: ["create", "update", "patch"]

  # ⑥ 나머지는 메타데이터만
  - level: Metadata
EOF

omitStages: [RequestReceived]가 첫 줄에 있는 이유가 있다. 이것이 없으면 요청 하나마다 받았을 때와 끝났을 때 두 줄이 남아 로그가 정확히 두 배가 된다. 대부분의 조사는 결과가 있는 쪽만 필요하다.

④에서 삭제를 RequestResponse로 올린 것이 이 정책의 핵심이다. 사후 조사에서 가장 자주 필요한 것이 "지워진 그것이 무엇이었는지"인데, 지워진 뒤에는 클러스터에 남아 있지 않다. 응답 본문에 마지막 상태가 들어 있어야 복원할 수 있다.

3단계 — API 서버에 플래그와 볼륨을 붙인다

목적정적 파드 매니페스트를 고쳐서 감사를 켠다. 되돌릴 수 있게 백업부터 한다.

# 되돌릴 길을 먼저 만든다
docker exec study-control-plane \
  cp /etc/kubernetes/manifests/kube-apiserver.yaml /etc/kubernetes/kube-apiserver.yaml.bak

docker exec study-control-plane mkdir -p /etc/kubernetes/audit /var/log/kubernetes/audit
docker cp course/labs/infra/audit-policy.yaml \
  study-control-plane:/etc/kubernetes/audit/policy.yaml

매니페스트에 다음을 넣는다. 명령줄 인자 다섯 개와 볼륨 두 쌍이다.

# spec.containers[0].command 에 추가
    - --audit-policy-file=/etc/kubernetes/audit/policy.yaml
    - --audit-log-path=/var/log/kubernetes/audit/audit.log
    - --audit-log-maxage=30
    - --audit-log-maxbackup=10
    - --audit-log-maxsize=100

# spec.containers[0].volumeMounts 에 추가
    - mountPath: /etc/kubernetes/audit
      name: audit-policy
      readOnly: true
    - mountPath: /var/log/kubernetes/audit
      name: audit-log

# spec.volumes 에 추가
  - hostPath:
      path: /etc/kubernetes/audit
      type: DirectoryOrCreate
    name: audit-policy
  - hostPath:
      path: /var/log/kubernetes/audit
      type: DirectoryOrCreate
    name: audit-log
플래그뜻
--audit-log-maxage보관 일수. CIS 기준은 30 이상이다
--audit-log-maxbackup회전 파일 개수. CIS 기준은 10 이상
--audit-log-maxsize회전 크기(MB). 27.4의 증가율을 보면 이 값이 하루에 몇 번 도는지 계산할 수 있다

audit-log 볼륨에 readOnly가 없는 것에 주의한다. 로그를 쓰는 경로이기 때문이고, 이 한 줄을 빠뜨리면 API 서버가 기동하다가 죽는다.

4단계 — 재시작을 기다린다

목적정적 파드는 kubectl이 관리하지 않는다. 파일이 바뀌면 kubelet이 알아서 다시 만든다.

for i in $(seq 1 40); do
  kubectl get --raw /readyz >/dev/null 2>&1 && { echo "readyz OK"; break; }
  sleep 5
done
docker exec study-control-plane ls -l /var/log/kubernetes/audit/
출력
readyz OK -rw------- 1 root root 24119 Sep 5 14:50 audit.log
판정45초 걸렸다. 그 사이 kubectl은 connection refused를 낸다 — 정상이다. 컨트롤 플레인이 없어도 이미 떠 있는 파드는 계속 돌지만, 새로 만들거나 고치는 일은 전부 멈춘다. 27.7에서 이 40초가 무엇을 깨뜨리는지 본다.

27.4따라하기 ② 로그에 질문한다

로그를 켜는 것은 절반이다. 나머지 절반은 답할 수 있는 질문의 목록을 만드는 것이다. 사고가 난 뒤에 질의를 처음 짜면 늦는다.

1단계 — 조사할 사건을 하나 만든다

목적답을 아는 질문으로 먼저 연습한다.

kubectl create ns m27
kubectl -n m27 create deploy audit-demo --image=registry.k8s.io/pause:3.10
kubectl -n m27 delete deploy audit-demo

2단계 — "누가 무엇을 지웠나"

목적가장 자주 필요한 질문이다. 시스템 계정의 삭제는 걸러 낸다.

docker exec study-control-plane cat /var/log/kubernetes/audit/audit.log |
python3 -c '
import json,sys
for l in sys.stdin:
    try: d=json.loads(l)
    except: continue
    if d.get("verb") in ("delete","deletecollection") and not d["user"]["username"].startswith("system:"):
        o=d.get("objectRef",{})
        print(d["requestReceivedTimestamp"][11:19], d["user"]["username"],
              f"{o.get(\"resource\")}/{o.get(\"name\")} in {o.get(\"namespace\")}")'
출력
14:50:34 kubernetes-admin deployments/audit-demo in m27
판정시각·주체·대상이 한 줄에 있다. kubernetes-admin은 kubeconfig의 관리자 인증서다 — 여러 사람이 같은 kubeconfig를 쓰면 이 줄로는 누구인지 알 수 없다. M23에서 계정을 나눈 이유가 여기서 실질적인 값이 된다. 감사 로그의 품질은 인증 설계에서 결정된다.

3단계 — "거부된 요청이 있었나"

목적침해 탐지에서 가장 먼저 보는 신호다. 권한 밖을 더듬는 시도는 403으로 남는다.

SRV=$(kubectl config view --minify -o jsonpath='{.clusters[0].cluster.server}')
TOKEN=$(kubectl -n journal create token dev)
curl -sk -o /dev/null -w '%{http_code}\n' -H "Authorization: Bearer $TOKEN" \
  "$SRV/api/v1/namespaces/kube-system/secrets"
출력
403

M23에서 만든 dev 계정으로 권한 밖의 요청을 한 번 만들었다. 로그에서 찾는다.

docker exec study-control-plane \
  sh -c "grep '\"code\":403' /var/log/kubernetes/audit/audit.log | tail -1" |
python3 -c '
import json,sys
d=json.loads(sys.stdin.read())
print("user     :", d["user"]["username"])
print("verb     :", d["verb"])
print("resource :", d["objectRef"].get("resource"), "in", d["objectRef"].get("namespace"))
print("decision :", d["annotations"].get("authorization.k8s.io/decision"))
print("code     :", d["responseStatus"]["code"])
print("sourceIPs:", d.get("sourceIPs"))'
출력
user : system:serviceaccount:journal:dev verb : list resource : secrets in kube-system decision : forbid code : 403 sourceIPs : ['172.20.0.1']
판정decision: forbid가 인가 단계에서 막혔다는 뜻이다. M23에서 배운 대로 Unauthorized(인증 실패)와 Forbidden(인가 실패)은 다른 사건이고, 감사 로그에서도 다른 코드(401/403)로 구분된다. 운영에서는 이 질의를 알림으로 만든다 — 서비스어카운트가 403을 연속으로 받는 것은 정상 동작에서는 거의 일어나지 않는다.

이 403이 로그에 남는 것은 정책을 한 번 고친 결과다. 처음 쓴 정책에서는 이 줄이 없었다. 27.7의 실패 ①에서 그 과정을 재현한다 — 지금 이 명령이 결과를 내지 않는다면 정책의 첫 규칙을 확인한다.

4단계 — "무엇이 로그를 채우고 있나"

목적보관 비용을 결정하기 전에 비용의 출처를 본다.

docker exec study-control-plane sh -c 'tail -2000 /var/log/kubernetes/audit/audit.log' |

c=collections.Counter()
for l in sys.stdin:
    try: d=json.loads(l)
    except: continue
    c[d["user"]["username"]]+=1
for u,n in c.most_common(6): print(f"{n:6d}  {u}")'
출력

판정사람은 한 명도 없다. 상위 전부가 컨트롤러와 오퍼레이터다 — 이들은 원하는 상태와 실제 상태를 계속 비교하느라 API를 끊임없이 부른다. 감사 로그의 용량은 사람의 활동이 아니라 클러스터에 설치한 오퍼레이터 수에 비례한다.

system:anonymous가 눈에 띈다. 익명 접근이 열려 있다는 뜻이라 놀랄 만한데, 무엇을 하는지 보면 답이 나온다.

docker exec study-control-plane sh -c 'tail -3000 /var/log/kubernetes/audit/audit.log' |

c=collections.Counter()

판정전부 헬스 체크다. kubelet이 정적 파드의 프로브를 인증 없이 부른다. 익명 접근 자체가 문제가 아니라 익명이 무엇에 닿을 수 있는지가 문제이고, 여기서는 두 엔드포인트뿐이다. 감사 로그가 있으면 이런 판단을 추측이 아니라 목록으로 한다.

27.5따라하기 ③ CIS 진단과 지적 고치기

1단계 — 진단을 잡으로 돌린다

목적컨트롤 플레인 노드의 파일과 프로세스를 읽어야 하므로 그 노드에 스케줄한다.

여기서 처음으로 잡Job을 쓴다. 디플로이먼트가 계속 도는 것을 관리한다면 잡은 한 번 돌고 끝나는 것을 관리한다 — 파드가 성공적으로 종료되면 잡이 완료되고, 실패하면 정해진 횟수만큼 다시 만든다. 진단 도구처럼 한 번 실행하고 결과만 받으면 되는 것에 맞는 컨트롤러다. 잡의 완료 조건·병렬 실행·재시도 정책은 M35에서 따로 다룬다. 여기서는 ttlSecondsAfterFinished(끝난 뒤 스스로 치워지는 시간) 하나만 알면 된다.

2단계 — 이그레스로 두 대역을 뺀다

목적M25의 정책과 같은 도구로 노드·메타데이터 경로만 닫는다.

cat > course/labs/k8s/netpol/20-block-node-metadata.yaml <<'EOF'
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: block-node-and-metadata
  namespace: m27
spec:
  podSelector: {}
  policyTypes: [Egress]
  egress:
    # ① 클러스터 밖으로 — 노드 대역과 메타데이터 주소만 뺀다

        - {protocol: TCP, port: 53}

172.20.0.0/16은 kind가 쓰는 도커 네트워크 대역이다. 실제 클러스터에서는 노드가 속한 서브넷을 적는데, 그 대역을 모르면 kubectl get nodes -o wide의 INTERNAL-IP에서 확인한다.

판정노드 경로 둘은 막혔고, DNS와 바깥 인터넷은 살아 있다. 307은 registry.k8s.io가 리다이렉트를 준 것이니 연결이 됐다는 증거다.

ipBlock은 클러스터 밖 IP를 위한 것이다. 파드끼리의 통신은 ipBlock으로 열리지 않으므로, 위 정책에서 ②를 빼면 cidr: 0.0.0.0/0이 있는데도 DNS가 죽는다(실측 확인). 파드·서비스 대상은 항상 podSelector·namespaceSelector로 쓴다. 반대로 except에 적은 대역은 다른 to 항목이 그 대역을 열어 주면 무력화된다 — 정책은 합집합이라는 M25의 규칙이 여기서도 그대로다.

27.7일부러 실패시키기

실패 ① — 읽기를 전부 버려서 403이 사라진다

목적감사 정책의 규칙 순서가 무엇을 결정하는지 본다. 이 실수는 사고가 난 뒤에야 발견된다.

27.3의 정책에서 첫 규칙을 다음처럼 쓰는 것이 자연스럽다. 읽기는 양이 많고 대개 조사에 쓸모가 없기 때문이다.

rules:
  # 읽기는 전부 버린다
  - level: None
    verbs: ["get", "list", "watch"]
  ...

이 정책으로 27.4의 403 요청을 만든 뒤 로그를 찾는다.

docker exec study-control-plane \
  sh -c "grep -c '\"code\":403' /var/log/kubernetes/audit/audit.log"
출력
0
판정한 줄도 없다. list secrets는 읽기 동사라서 첫 규칙에 걸려 버려졌고, 그 요청이 403으로 끝났다는 사실은 기록되지 않았다. 감사 정책은 결과가 아니라 요청의 모양으로 판정한다 — "거부된 것만 남긴다"는 규칙은 쓸 수 없다. 시크릿을 훑고 다니는 침해 시도는 전부 읽기 요청이므로, 이 정책은 가장 보고 싶은 것을 정확히 버린다.

고치는 방향은 "읽기를 버린다"가 아니라 "시스템 구성요소의 읽기를 버린다"이다.

  - level: None
    userGroups: ["system:nodes", "system:serviceaccounts:kube-system"]
    verbs: ["get", "list", "watch"]
  - level: None
    users: ["system:apiserver", "system:kube-scheduler", "system:kube-controller-manager"]
    verbs: ["get", "list", "watch"]

정책 파일만 바꿔서는 반영되지 않는다. API 서버가 기동할 때 한 번 읽기 때문에, 매니페스트를 건드려 정적 파드를 다시 만들어야 한다.

대가를 재 본다. 60초 동안의 증가량이다.

정책줄/분바이트/분하루 환산
읽기 전부 버림128264,117약 380MB
시스템 읽기만 버림6441,012,254약 1.4GB
판정5배다. 그리고 이 숫자는 아무도 쓰지 않는 3노드 실습 클러스터의 것이다. 403을 남기려면 이 비용을 내야 하고, 안 내려면 침해 시도를 못 본다 — 공짜인 선택지가 없다. 실무의 절충은 대개 보관 기간을 짧게(7일) 가져가고 403·삭제·RBAC 변경만 별도 저장소로 오래 남기는 형태다.

실패 ② — 컨트롤 플레인 재시작이 워크로드를 죽인다

목적"컨트롤 플레인이 잠깐 내려가도 워크로드는 돈다"가 어디까지 참인지 확인한다.

27.5에서 매니페스트를 고쳐 API 서버가 40초 정도 내려갔다. 그동안 파드는 계속 돌았다 — 인그레스로 들어오는 요청도 정상이었다. 그런데 재시작 뒤에 이런 것이 남았다.

kubectl get po -A --no-headers | awk '$4!="Running" && $4!="Completed"'
출력
monitoring kps-kube-state-metrics-674d9d494b-g2sks 0/1 CrashLoopBackOff 8 (106s ago) 3h7m
kubectl -n monitoring logs kps-kube-state-metrics-674d9d494b-g2sks --previous --tail=1
출력
E0905 14:56:41.237039 1 wrapper.go:41] "Failed to run kube-state-metrics" err="failed to create client: error while trying to communicate with apiserver: Get \"https://10.96.0.1:443/version\": dial tcp 10.96.0.1:443: connect: connection refused"
판정기동할 때 API 서버가 필요한 파드는 그 40초를 넘기지 못한다. 이미 떠 있던 파드는 멀쩡했지만, 하필 그 순간 재시작한 파드는 연결에 실패하고 죽었다. 그리고 CrashLoopBackOff의 백오프는 지수적으로 늘어나므로, API 서버가 돌아온 뒤에도 몇 분 동안 계속 죽어 있는다.

영향은 관측으로 번졌다.

# 프로메테우스 /api/v1/targets 요약
출력
전체: {'up': 31, 'unknown': 1, 'down': 1}

복구는 파드를 지우는 것으로 끝난다. 백오프를 기다리는 대신 새로 만든다.

kubectl -n monitoring delete pod -l app.kubernetes.io/name=kube-state-metrics
출력 (30초 뒤)
전체: {'up': 33}
판정여기서 얻을 습관은 두 가지다. 첫째, 컨트롤 플레인을 건드린 뒤에는 반드시 클러스터 전체 파드 상태를 훑는다 — 증상이 내가 만진 곳이 아니라 엉뚱한 네임스페이스에서 나온다. 둘째, 컨트롤 플레인 변경은 관측 스택이 가장 먼저 아프다. 장애를 봐야 할 도구가 장애 때 같이 죽는 구조라서, 실제 운영에서는 관측 스택을 별도 클러스터에 두는 선택을 한다.

27.8운영 관점 — 이미지 스캔을 어디에 둘 것인가

M07에서 이미지를 만들었고 M26에서 latest를 막았다. 남은 질문은 "그 이미지 안에 무엇이 들어 있는가"다. 클러스터에 배포된 것을 스캔한다.

docker run --rm -v /var/run/docker.sock:/var/run/docker.sock aquasec/trivy:0.69.0 \
  image --scanners vuln --severity HIGH,CRITICAL --quiet journal-api:v2
출력 (요약)
journal-api:v2 (alpine 3.24.1) os-pkgs {'HIGH': 2} Node.js lang-pkgs {'HIGH': 10, 'CRITICAL': 1} 합계: {'HIGH': 12, 'CRITICAL': 1}

여기서 멈추면 "13개를 고쳐야 한다"는 결론이 나온다. 한 걸음 더 간다 — 이 취약점들이 어디서 왔는지 보려고 베이스 이미지만 따로 스캔한다.

출력
node:22-alpine {'HIGH': 12, 'CRITICAL': 1} node:24-alpine {'HIGH': 6} gcr.io/distroless/nodejs22-debian12:nonroot {'CRITICAL': 1, 'HIGH': 5}

우리 이미지의 13개가 베이스 이미지의 13개와 같다. 우리 코드와 우리 의존성이 만든 취약점은 0개이고, 전부 베이스 이미지에 들어 있던 것이다. 그러면 할 일이 바뀐다 — 개별 CVE를 하나씩 쫓는 대신 베이스 이미지를 올리는 것이 13개를 6개로 만든다.

이것이 스캔 결과를 읽는 기본 순서다. 어느 층에서 왔는지 먼저 나눈다. OS 패키지 층이면 베이스 이미지 갱신, 언어 패키지 층이면 package-lock.json 갱신, 애플리케이션 코드면 우리가 고칠 일이다. 층을 나누지 않고 목록을 위에서부터 처리하면 고칠 수 없는 것에 시간을 쓰게 된다.

어디서 돌릴 것인가

스캔은 세 자리에 놓을 수 있고 각각 잡는 것이 다르다. CI에서 돌리면 문제 있는 이미지가 레지스트리에 올라가기 전에 막힌다 — 가장 싸게 막는 자리다. 레지스트리에서 주기적으로 돌리면 어제는 없던 CVE가 오늘 공개된 경우를 잡는다. 이미 배포된 이미지는 다시 빌드되지 않으므로 CI만으로는 이 경우를 못 본다. 어드미션에서 검사하면 배포를 막을 수 있지만, M26에서 본 대로 CEL로는 레지스트리를 조회할 수 없어 전용 컨트롤러가 필요하다.

이 교재는 M29에서 CI 자리를 만든다. 빌드 뒤 스캔을 붙이고, CRITICAL이 있으면 빌드를 실패시킨다 — 책 5.3의 "테스트가 실패하면 빌드도 실패"를 보안 검사에 그대로 적용하는 것이다. 임계값을 HIGH까지 내리면 위 결과에서 보듯 베이스 이미지만으로 빌드가 계속 깨지므로, 시작은 CRITICAL로 하고 베이스를 정리한 뒤 낮추는 순서를 쓴다.

M23~M27에서 만든 것을 하나의 점검 절차로 묶으면 다음이 된다. 클러스터를 새로 만들거나 큰 변경을 한 뒤에 이 순서로 돌린다.
