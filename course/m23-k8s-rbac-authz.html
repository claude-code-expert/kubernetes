RBAC과 인가

M01부터 M22까지 우리는 이 클러스터에서 무엇이든 할 수 있었다. 네임스페이스를 지우고, 노드의 정적 파드 매니페스트를 고치고, 시크릿을 base64 -d로 열어 봤다. 실제 클러스터에서 그런 권한을 가진 사람은 극소수다. 이 모듈에서 권한을 실제로 좁히고, 권한 밖의 명령이 어떻게 거부되는지를 메시지로 확인한다.

중후반80분Kubernetes 1.37.0
2026-09-05 검증 (kind v0.33.0) · 버전 숫자는 실습 당일 kubectl version으로 다시 확인한다
사전 조건
  • M22 완료 — journal·apps·monitoring 네임스페이스가 살아 있다
  • 지금 쓰는 kubeconfig가 관리자 권한이다. 확인: kubectl auth can-i '*' '*' --all-namespaces가 yes
  • jq는 필요 없다. 모든 출력은 jsonpath와 python3로 다룬다
  • 새로 쓰는 파일: course/labs/k8s/rbac/10-dev-role.yaml · 20-aggregated.yaml · course/labs/scripts/make-dev-kubeconfig.sh

핵심 3줄

1. journal 네임스페이스에서만 일하는 서비스어카운트를 만들고, 그 계정의 kubeconfig로 실제 Forbidden을 여러 종류 받아 본다.

2. 거부 메시지가 "누가·무엇을·어디서"를 다 말해 준다는 것을 확인하고, can-i로 명령을 치기 전에 미리 물어본다.

3. 검색하면 나오는 토큰 조회 방법이 왜 빈 값을 돌려주는지 재현하고, 지금 방식으로 바꾼다.

23.1우리는 지금까지 무엇이든 할 수 있었다 23.2이론 — 네 조각과 요청의 경로 23.3따라하기 ① 개발자 계정을 만든다 23.4따라하기 ② 거부당해 본다 23.5따라하기 ③ 치기 전에 물어본다 23.6따라하기 ④ 집약 ClusterRole 23.7일부러 실패시키기 23.8운영 관점 — 최소 권한을 실제로 지키려면 23.9체크포인트와 정리

23.1우리는 지금까지 무엇이든 할 수 있었다

M19 실패 ①에서 docker exec study-control-plane sed -i ...로 apiserver가 있는 노드의 정적 파드 매니페스트를 고쳤다. M13에서는 시크릿을 base64 -d로 열어 평문을 읽었다. M16에서는 노드에 테인트를 걸고 drain했다.

이 모든 것이 가능했던 이유는 kind가 만들어 준 kubeconfig가 클러스터 관리자이기 때문이다. 확인해 보면 이렇다.

kubectl auth can-i '*' '*' --all-namespaces
출력
yes

실무에서 이 권한을 가진 사람은 클러스터 운영자 몇 명이다. 애플리케이션 개발자는 자기 네임스페이스에서 파드를 보고 로그를 읽고 배포를 굴리는 정도이고, CI 파이프라인은 그보다 더 좁다 — 특정 디플로이먼트의 이미지만 바꿀 수 있으면 된다.

권한을 좁히는 것이 번거로워 보이지만, 좁히지 않으면 실수 하나가 클러스터 전체에 닿는다. 잘못된 네임스페이스에 delete를 치거나, CI 토큰이 유출됐을 때 그 토큰으로 할 수 있는 일이 전부이거나. 이 모듈에서 만드는 것은 그 경계다.

23.2이론 — 네 조각과 요청의 경로

책 4.4가 RBAC의 기초를, 17.2가 인가 모듈의 순서를 다룬다. 먼저 이 클러스터가 어떤 인가 방식을 쓰는지 본다.

docker exec study-control-plane \
  grep -o '\-\-authorization-mode=[^ ]*' /etc/kubernetes/manifests/kube-apiserver.yaml
출력
--authorization-mode=Node,RBAC

두 모듈이 순서대로 물어본다. Node 인가는 kubelet이 자기 노드에 있는 파드의 시크릿·컨피그맵만 읽게 제한하는 특수 모듈이고, 사람과 서비스어카운트의 권한은 RBAC이 정한다. 둘 중 하나라도 허용하면 통과이고, 아무도 허용하지 않으면 거부다 — RBAC에는 "금지" 규칙이 없다.

네 조각

오브젝트정하는 것범위
Role어떤 동사로 어떤 리소스를네임스페이스에 속한다
ClusterRole같은 것클러스터 전체 오브젝트
RoleBinding누구에게 그 역할을그 네임스페이스 안에서만
ClusterRoleBinding같은 것클러스터 전체

헷갈리는 지점은 역할이 범위를 정하지 않는다는 것이다. 범위를 정하는 것은 바인딩이다. RoleBinding에 ClusterRole을 붙일 수 있고, 그러면 정의는 클러스터의 것을 쓰되 효력은 그 네임스페이스뿐이다. 23.6에서 이것을 직접 잰다.

거부에는 두 종류가 있다

요청이 막히는 단계가 둘이고 메시지가 다르다.

단계묻는 것실패 메시지
인증 authentication너는 누구인가error: You must be logged in to the server (Unauthorized)
인가 authorization그 일을 해도 되는가Error from server (Forbidden): ... is forbidden: User "..." cannot ...

토큰이 만료됐거나 잘못됐으면 Unauthorized이고, 신원은 확인됐는데 권한이 없으면 Forbidden이다. 이 구분이 진단의 첫 갈림길이다 — 앞쪽이면 토큰을 다시 받고, 뒤쪽이면 권한을 봐야 한다.

23.3따라하기 ① 개발자 계정을 만든다

1단계 — 서비스어카운트와 Role을 쓴다

목적journal 네임스페이스에서 진단하고 배포까지만 할 수 있는 계정을 정의한다.

course/labs/k8s/rbac/10-dev-role.yaml로 저장한다.

apiVersion: v1
kind: ServiceAccount
metadata:
  name: dev
  namespace: journal
---
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: dev
  namespace: journal          # Role 은 네임스페이스에 갇힌다. 여기 밖에서는 아무 권한도 없다
rules:
  # 읽기 — 진단에 필요한 최소한
  - apiGroups: [""]
    resources: ["pods", "pods/log", "services", "configmaps", "events"]
    verbs: ["get", "list", "watch"]
  - apiGroups: ["apps"]
    resources: ["deployments", "replicasets", "statefulsets"]
    verbs: ["get", "list", "watch"]
  # 쓰기 — 배포와 롤아웃까지만
  - apiGroups: ["apps"]
    resources: ["deployments"]
    verbs: ["update", "patch"]
  - apiGroups: ["apps"]
    resources: ["deployments/scale"]
    verbs: ["update", "patch"]
  # 시크릿은 넣지 않는다. 넣으면 base64 를 벗겨 평문을 읽을 수 있다 (M13)
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: dev
  namespace: journal
subjects:
  - kind: ServiceAccount
    name: dev
    namespace: journal
roleRef:
  kind: Role
  name: dev
  apiGroup: rbac.authorization.k8s.io
선택이유
apiGroups: [""]빈 문자열이 핵심 API 그룹이다. 파드·서비스·컨피그맵이 여기 있다
pods/log서브리소스다. pods를 읽을 수 있어도 로그는 별도 권한이 필요하다
deployments/scalekubectl scale이 쓰는 서브리소스. 이것만 주면 파드 수만 바꿀 수 있다
delete가 없다파드를 직접 지울 수 없다. 롤아웃으로 교체하게 만든다
secrets가 없다M13에서 본 것처럼 시크릿 읽기는 평문 읽기와 같다
kubectl apply -f course/labs/k8s/rbac/10-dev-role.yaml
판정serviceaccount/dev created·role.../dev created·rolebinding.../dev created 셋이 나오면 된다. 아직 아무도 이 계정을 쓰지 않으므로 클러스터에는 변화가 없다.

2단계 — 그 계정의 kubeconfig를 만든다

목적권한을 말로 확인하지 않고 실제로 그 계정이 되어 명령을 쳐 본다.

course/labs/scripts/make-dev-kubeconfig.sh로 저장한다.

NS="${NS:-journal}"; SA="${SA:-dev}"; OUT="${OUT:-/tmp/dev.kubeconfig}"; TTL="${TTL:-1h}"
CTX=$(kubectl config current-context)
CLUSTER=$(kubectl config view -o jsonpath="{.contexts[?(@.name==\"$CTX\")].context.cluster}")
SERVER=$(kubectl config view -o jsonpath="{.clusters[?(@.name==\"$CLUSTER\")].cluster.server}")
CA=$(kubectl config view --raw -o jsonpath="{.clusters[?(@.name==\"$CLUSTER\")].cluster.certificate-authority-data}")

# 검색하면 나오는 방법은 .secrets[0].name 으로 토큰 시크릿을 찾는 것인데,
# 1.24 부터 그 시크릿이 자동 생성되지 않는다 (23.7 실패 ①).
TOKEN=$(kubectl -n "$NS" create token "$SA" --duration="$TTL")

cat > "$OUT" <<KEOF
apiVersion: v1
kind: Config
clusters:
  - name: $CLUSTER
    cluster: { server: $SERVER, certificate-authority-data: $CA }
users:
  - name: $SA
    user: { token: $TOKEN }
contexts:
  - name: $SA@$CLUSTER
    context: { cluster: $CLUSTER, user: $SA, namespace: $NS }
current-context: $SA@$CLUSTER
KEOF
chmod 600 "$OUT"
bash course/labs/scripts/make-dev-kubeconfig.sh
KUBECONFIG=/tmp/dev.kubeconfig kubectl auth whoami
출력
ATTRIBUTE VALUE Username system:serviceaccount:journal:dev UID 7c6c1c4e-9c1f-4fd2-9371-6c478af92ba8 Groups [system:serviceaccounts system:serviceaccounts:journal system:authenticated]
판정신원이 system:serviceaccount:<네임스페이스>:<이름> 형식으로 나온다. 이것이 23.4의 거부 메시지에 그대로 등장한다. 그룹 셋이 자동으로 붙는데, system:authenticated는 로그인한 모두를 뜻하므로 여기에 권한을 주면 사실상 전체 공개다.

이 절의 명령은 전부 개발자 계정으로 친다. 터미널에서 한 번만 지정한다.

3단계 — 허용된 일부터 확인한다

목적권한을 좁혔지만 개발자가 실제로 일할 수는 있는지 본다. 너무 좁히면 아무도 안 쓴다.

kubectl get pods
kubectl logs deploy/journal-api --tail=1
kubectl scale deploy journal-api --replicas=3
출력
journal-api-69d49f6788-fxs5p 1/1 Running 0 22m journal-api-69d49f6788-whhz5 1/1 Running 0 22m Found 3 pods, using pod/journal-api-69d49f6788-fxs5p deployment.apps/journal-api scaled
판정진단(파드 목록·로그)과 운영(스케일)이 된다. -n journal을 안 붙여도 되는 것은 kubeconfig의 컨텍스트에 네임스페이스가 박혀 있기 때문이다.

4단계 — 다섯 가지 방식으로 거부당한다

목적거부 메시지를 읽는 연습을 한다. 메시지마다 어디가 막혔는지 다르게 적혀 있다.

kubectl get secret journal-secret
kubectl delete pod --all
kubectl -n apps get pods
kubectl get nodes
kubectl create ns hack
출력
Error from server (Forbidden): secrets "journal-secret" is forbidden: User "system:serviceaccount:journal:dev" cannot get resource "secrets" in API group "" in the namespace "journal" Error from server (Forbidden): pods "journal-api-69d49f6788-fxs5p" is forbidden: User "system:serviceaccount:journal:dev" cannot delete resource "pods" in API group "" in the namespace "journal" Error from server (Forbidden): pods is forbidden: User "system:serviceaccount:journal:dev" cannot list resource "pods" in API group "" in the namespace "apps" Error from server (Forbidden): nodes is forbidden: User "system:serviceaccount:journal:dev" cannot list resource "nodes" in API group "" at the cluster scope Error from server (Forbidden): namespaces is forbidden: User "system:serviceaccount:journal:dev" cannot create resource "namespaces" in API group "" at the cluster scope

메시지가 다섯 조각으로 이루어져 있다 — 누가(User "...") 어떤 동사로(cannot get) 어떤 리소스를(resource "secrets") 어느 그룹에서(API group "") 어디서(in the namespace "journal" 또는 at the cluster scope).

판정마지막 조각이 특히 중요하다. at the cluster scope가 나오면 네임스페이스 Role로는 절대 풀 수 없다는 뜻이고, ClusterRole과 ClusterRoleBinding이 필요하다. in the namespace "apps"가 나오면 그 네임스페이스에 바인딩을 하나 더 만들면 된다.

세 번째와 다섯 번째를 비교하면 차이가 보인다. 같은 pods인데 apps 네임스페이스에서는 막혔다 — 권한이 네임스페이스에 매여 있다는 것이 이렇게 드러난다.

23.5따라하기 ③ 치기 전에 물어본다

5단계 — can-i로 미리 확인한다

목적명령을 실제로 치지 않고 권한을 확인한다. 파괴적인 명령을 시험할 때 필요하다.

for pair in "get:pods" "delete:pods" "get:secrets" "update:deployments" \
            "get:pods/log" "update:deployments/scale" "create:namespaces"; do
  V="${pair%%:*}"; R="${pair##*:}"
  printf '  %-8s %-22s -> ' "$V" "$R"
  kubectl auth can-i "$V" "$R"
done
출력
get pods -> yes delete pods -> no get secrets -> no update deployments -> yes get pods/log -> yes update deployments/scale -> yes create namespaces -> Warning: resource 'namespaces' is not namespace scoped
zsh에서 인자가 안 나뉜다 V="get pods"; kubectl auth can-i $V처럼 쓰면 zsh에서 이렇게 된다.
error: you must specify two arguments: verb resource or verb resource/resourceName.
bash와 달리 zsh는 따옴표 없는 변수 확장에서 단어를 나누지 않는다. 동사와 리소스를 따로 넘기거나 ${=V}를 쓴다. macOS의 기본 셸이 zsh이므로 자주 걸린다.

6단계 — 관리자가 남을 대신해 물어본다

목적kubeconfig를 만들지 않고 특정 계정의 권한을 점검한다. 운영에서 훨씬 자주 쓰는 방식이다.

unset KUBECONFIG      # 관리자로 돌아온다

kubectl auth can-i get    secrets -n journal --as=system:serviceaccount:journal:dev
kubectl auth can-i delete pods    -n journal --as=system:serviceaccount:journal:dev
kubectl auth can-i get    pods    -n apps    --as=system:serviceaccount:journal:dev
출력
no no no
판정--as는 가장 impersonation이다. 관리자가 다른 신원인 척하고 물어보는 것이고, 이 권한 자체가 강력하므로 impersonate 동사를 아무에게나 주면 안 된다 — 누구든 될 수 있다는 뜻이기 때문이다.

7단계 — 가진 권한을 전부 나열한다

목적Role을 읽지 않고 실제 유효 권한을 본다. 바인딩이 여럿이면 합쳐진 결과가 필요하다.

KUBECONFIG=/tmp/dev.kubeconfig kubectl auth can-i --list
출력 (앞부분)
Resources Verbs selfsubjectreviews.authentication.k8s.io [create] selfsubjectaccessreviews.authorization.k8s.io [create] selfsubjectrulesreviews.authorization.k8s.io [create] deployments.apps [get list watch update patch] configmaps [get list watch] events [get list watch] pods/log [get list watch]
판정우리가 준 것 외에 selfsubject* 셋이 더 있다. 이것은 모든 인증된 사용자에게 기본으로 주어지는 권한이고, can-i가 동작하는 이유이기도 하다 — 자기 권한을 물어보는 것 자체가 API 호출이다.

23.6따라하기 ④ 집약 ClusterRole

팀이 여럿이고 각자 다른 리소스를 다루면 "읽기 권한" 하나를 누가 관리할지가 문제가 된다. 관측 팀이 ServiceMonitor를 추가할 때마다 플랫폼 팀에게 Role 수정을 부탁하는 구조는 오래가지 않는다.

8단계 — 라벨로 규칙을 모은다

목적여러 ClusterRole의 규칙이 자동으로 합쳐지는 것을 확인한다.

course/labs/k8s/rbac/20-aggregated.yaml로 저장한다.

apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: study-viewer
aggregationRule:
  clusterRoleSelectors:
    - matchLabels:
        rbac.study.io/aggregate-to-viewer: "true"
rules: []          # 비워 둔다. 컨트롤러가 채운다 — 직접 쓰면 덮어써진다
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: study-viewer-workloads
  labels:
    rbac.study.io/aggregate-to-viewer: "true"
rules:
  - apiGroups: ["apps"]
    resources: ["deployments", "statefulsets", "daemonsets"]
    verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: study-viewer-observability
  labels:
    rbac.study.io/aggregate-to-viewer: "true"
rules:
  - apiGroups: ["monitoring.coreos.com"]
    resources: ["servicemonitors", "prometheusrules"]
    verbs: ["get", "list", "watch"]
kubectl apply -f course/labs/k8s/rbac/20-aggregated.yaml
kubectl get clusterrole study-viewer \
  -o jsonpath='{range .rules[*]}  {.apiGroups} {.resources} {.verbs}{"\n"}{end}'
출력
["monitoring.coreos.com"] ["servicemonitors","prometheusrules"] ["get","list","watch"] ["apps"] ["deployments","statefulsets","daemonsets"] ["get","list","watch"]
판정우리가 rules: []로 비워 둔 study-viewer에 두 벌의 규칙이 들어와 있다. 컨트롤러가 라벨이 맞는 ClusterRole을 찾아 합친 것이다. 이후 관측 팀이 자기 ClusterRole만 고치면 상위 역할이 자동으로 따라간다.

쿠버네티스가 기본으로 만드는 view·edit·admin도 같은 방식으로 되어 있다. CRD를 설치하는 오퍼레이터들이 rbac.authorization.k8s.io/aggregate-to-view: "true" 라벨이 붙은 ClusterRole을 함께 넣는 것이 그래서다.

9단계 — 바인딩이 범위를 정한다

목적같은 ClusterRole을 RoleBinding으로 붙였을 때 효력이 어디까지인지 잰다.

kubectl -n apps create rolebinding dev-view \
  --clusterrole=study-viewer --serviceaccount=journal:dev

for ns in apps journal monitoring; do
  printf '  ns=%-11s get deployments -> ' $ns
  kubectl auth can-i get deployments -n $ns --as=system:serviceaccount:journal:dev
done
출력
ns=apps get deployments -> yes ns=journal get deployments -> yes ns=monitoring get deployments -> no
판정"apps에서만 새로 허용됐다. journal이 yes인 것은 1단계의 Role 때문이고, monitoring은 여전히 no다. ClusterRole을 썼는데도 클러스터 전체가 되지 않는다 — 범위를 정한 것은 RoleBinding이다.

클러스터 전체로 주려면 바인딩을 바꿔야 한다.

# 이렇게 하면 모든 네임스페이스에서 조회할 수 있다 (여기서는 실행하지 않는다)
kubectl create clusterrolebinding dev-view-all \
  --clusterrole=study-viewer --serviceaccount=journal:dev

실행하지 않는 이유는 되돌리기 전에 잊기 쉬워서다. 실습에서 만든 클러스터 범위 바인딩은 네임스페이스를 지워도 남는다 — 23.9의 정리에서 명시적으로 지운다.

23.7일부러 실패시키기

실패 ① 검색하면 나오는 토큰 조회가 빈 값을 준다

서비스어카운트의 토큰을 얻는 방법으로 가장 많이 나오는 것이 이것이다.

재현 
kubectl -n journal get sa dev -o jsonpath='{.secrets}'
kubectl -n journal get sa dev -o jsonpath='{.secrets[0].name}'
출력
(빈 값) (빈 값)

다음 단계인 시크릿 조회는 이렇게 끝난다.

SECRET=$(kubectl -n journal get sa dev -o jsonpath='{.secrets[0].name}')
kubectl -n journal get secret "$SECRET" -o jsonpath='{.data.token}'
출력
error: resource name may not be empty
원인

1.24부터 서비스어카운트를 만들어도 토큰 시크릿이 자동으로 생성되지 않는다. 그 전에는 만료되지 않는 토큰이 시크릿으로 영구히 놓여 있었고, 유출되면 회수할 방법이 마땅치 않았다. 지금은 요청할 때마다 수명이 정해진 토큰을 발급하는 방식으로 바뀌었다.

고친다 
kubectl -n journal create token dev --duration=10m
kubectl -n journal create token dev --duration=10m -o json \
  | python3 -c "import json,sys; print('만료:', json.load(sys.stdin)['status']['expirationTimestamp'])"
출력
eyJhbGciOiJSUzI1NiIsImtpZCI6InEtWkw4c2Jz... 만료: 2026-09-05T14:10:09Z
판정만료 시각이 붙어 있다. 이것이 2단계 스크립트가 create token을 쓰는 이유이고, CI에 넣을 토큰도 마찬가지다 — 영구 토큰을 파일에 박아 두는 대신 파이프라인이 매번 발급받는 구조로 만든다. 옛 방식이 꼭 필요하면 kubernetes.io/service-account-token 타입 시크릿을 직접 만들 수는 있지만, 그것이 바로 1.24가 없앤 위험이다.

실패 ② Unauthorized와 Forbidden을 구분하지 못한다

토큰 한 글자를 바꿔 요청하면 무엇이 나오는지 본다.

재현 
SERVER=$(kubectl config view -o jsonpath='{.clusters[0].cluster.server}')
T=$(kubectl -n journal create token dev --duration=10m)
BAD="${T%?}X"        # 마지막 글자를 바꾼다

kubectl --kubeconfig=/dev/null --token="$BAD" --server="$SERVER" \
  --insecure-skip-tls-verify -n journal get pods
출력
error: You must be logged in to the server (Unauthorized)

같은 명령을 정상 토큰으로 치면 통과한다.

출력
journal-api-69d49f6788-fxs5p 1/1 Running 0 23m
원인과 판별

Unauthorized는 인증 단계다 — 토큰이 만료됐거나 서명이 맞지 않는다. 권한과는 무관하다. RBAC을 아무리 넓혀도 이 오류는 사라지지 않는다.

판정Unauthorized가 나오면 토큰을 다시 받고, Forbidden이면 Role을 본다. 이 구분을 못 하면 권한 문제를 토큰으로, 토큰 문제를 권한으로 풀려다 시간을 쓴다.

--kubeconfig=/dev/null을 붙인 것도 이유가 있다. 이것이 없으면 기존 kubeconfig의 관리자 인증서로 조용히 통과해 버려 실험이 성립하지 않는다.

실패 ③ 일단 되게 하려고 cluster-admin을 붙인다

권한 문제를 만났을 때 가장 빠른 해결책이 이것이고, 그래서 가장 흔한 사고이기도 하다. 무엇을 주는 것인지 먼저 본다.

확인 
kubectl get clusterrole cluster-admin -o jsonpath='{.rules}'
출력
[{"apiGroups":["*"],"resources":["*"],"verbs":["*"]},{"nonResourceURLs":["*"],"verbs":["*"]}]

모든 API 그룹의 모든 리소스에 모든 동사다. 시크릿을 읽고, 노드를 지우고, 다른 사람의 권한을 바꾸는 것까지 포함된다.

지금 누가 갖고 있나 
kubectl get clusterrolebinding -o json | python3 -c "
import json,sys
d=json.load(sys.stdin)['items']
ca=[b for b in d if b['roleRef']['name']=='cluster-admin']
print('cluster-admin 바인딩 수:',len(ca))
for b in ca:
    subs=[f\"{s['kind']}:{s['name']}\" for s in b.get('subjects',[])]
    print(f\"  {b['metadata']['name']:24} -> {subs}\")"
출력
cluster-admin 바인딩 수: 2 cluster-admin -> ['Group:system:masters'] kubeadm:cluster-admins -> ['Group:kubeadm:cluster-admins']
판정갓 만든 클러스터에는 둘뿐이고 둘 다 부트스트랩용이다. 이 목록이 시간이 지나며 길어지는 것이 클러스터의 상태를 말해 준다 — 주기적으로 이 명령을 쳐서 늘어난 항목이 있는지 보는 것이 가장 싼 점검이다.
고친다 — 무엇이 막혔는지 먼저 읽는다

Forbidden 메시지는 필요한 것을 정확히 알려준다. 23.4의 예를 다시 보면 cannot list resource "pods" in API group "" in the namespace "apps"이므로, 필요한 것은 cluster-admin이 아니라 apps 네임스페이스에 pods list 권한이다. 메시지의 다섯 조각을 그대로 Role의 필드로 옮기면 최소 권한이 나온다.

23.8운영 관점 — 최소 권한을 실제로 지키려면

"최소 권한"은 원칙으로는 쉽고 실무로는 어렵다. 어려운 이유는 필요한 권한을 미리 알 수 없기 때문이다. 파이프라인이 무슨 API를 호출하는지, 오퍼레이터가 어떤 리소스를 만드는지는 대개 돌려 봐야 안다.

넓게 주고 좁히는 대신, 좁게 주고 넓힌다

순서가 중요하다. cluster-admin으로 시작해 나중에 좁히는 계획은 거의 실행되지 않는다 — 좁히다 무언가 깨지면 되돌리기 때문이다. 반대로 최소로 시작하면 Forbidden 메시지가 필요한 것을 하나씩 알려주고, 그 메시지를 Role에 옮기는 것으로 끝난다. 23.7 실패 ③에서 본 대로 메시지에 필요한 정보가 다 들어 있다.

주기적으로 볼 것 세 가지

점검명령무엇을 보나
cluster-admin 보유자kubectl get clusterrolebinding에서 roleRef.name=cluster-admin부트스트랩 항목 외에 늘어난 것
과도한 와일드카드ClusterRole의 verbs: ["*"]·resources: ["*"]이름은 좁은데 내용은 넓은 역할
기본 그룹에 준 권한system:authenticated·system:serviceaccounts가 subject인 바인딩사실상 전체 공개

마지막이 특히 위험하다. system:authenticated는 토큰을 가진 모두이므로, 여기에 시크릿 읽기를 주면 클러스터의 모든 파드가 모든 시크릿을 읽을 수 있게 된다.

사람과 워크로드는 인증 방식이 다르다

이 모듈은 서비스어카운트를 썼다. 쿠버네티스에는 사람 사용자라는 오브젝트가 없다 — 인증서, OIDC, 프록시 헤더 같은 외부 수단으로 신원을 받고 RBAC은 그 이름에 권한을 붙인다. 그래서 실무에서는 사람은 OIDC(사내 SSO)로, 워크로드는 서비스어카운트로 나누고, 사람에게는 그룹 단위로 권한을 준다.

파드가 쓰는 서비스어카운트도 점검 대상이다. 지정하지 않으면 default 서비스어카운트가 자동으로 붙고 토큰이 마운트된다. 필요 없으면 꺼야 한다.

# 파드가 API 를 호출하지 않는다면
spec:
  automountServiceAccountToken: false

우리 앱들(journal-api·order-api)은 쿠버네티스 API를 호출하지 않는데도 토큰을 갖고 있다. 컨테이너가 탈취됐을 때 그 토큰으로 할 수 있는 일이 곧 피해 범위이므로, 안 쓰는 토큰은 없는 편이 낫다. M24에서 파드 수준 보안을 다룰 때 이 설정을 함께 넣는다.

23.9체크포인트와 정리

다음 모듈로 넘어가기 전 확인
  • kubectl -n journal get sa,role,rolebinding dev --no-headers | wc -l → 3
  • kubectl auth can-i get secrets -n journal --as=system:serviceaccount:journal:dev → no
  • kubectl auth can-i get pods -n journal --as=system:serviceaccount:journal:dev → yes
  • kubectl auth can-i get pods -n apps --as=system:serviceaccount:journal:dev → no
  • kubectl auth can-i list nodes --as=system:serviceaccount:journal:dev → no (경고 줄이 함께 나온다)
  • kubectl -n journal get sa dev -o jsonpath='{.secrets}' → 빈 값 (1.24 이후의 정상 상태)
  • kubectl -n journal create token dev --duration=10m | wc -c → 800 이상
  • kubectl get clusterrole study-viewer -o jsonpath='{.rules}' | grep -c monitoring.coreos.com → 1 (집약이 동작했다)
  • kubectl get clusterrolebinding -o json | python3 -c "import json,sys;print(len([b for b in json.load(sys.stdin)['items'] if b['roleRef']['name']=='cluster-admin']))" → 2
  • kubectl -n apps get rolebinding dev-view → NotFound (실습용 바인딩을 지웠다)
  • ls /tmp/dev.kubeconfig → No such file (토큰 파일을 지웠다)
  • (이해 확인) Unauthorized와 Forbidden을 받았을 때 각각 어디를 봐야 하는지 적어 본다
  • (이해 확인) RoleBinding에 ClusterRole을 붙이면 권한이 어디까지 미치는지 적어 본다

# 실습용 바인딩과 토큰 파일을 지운다
kubectl -n apps delete rolebinding dev-view --ignore-not-found
rm -f /tmp/dev.kubeconfig
unset KUBECONFIG

# 클러스터 범위 바인딩을 만들었다면 반드시 지운다 (네임스페이스를 지워도 남는다)

dev 계정과 study-viewer ClusterRole은 지우지 않는다. M24에서 이 계정으로 파드 보안 정책에 걸려 보고, M29에서 CI 파이프라인 계정을 만들 때 같은 패턴을 쓴다.

발급한 토큰은 수명이 지나면 저절로 무효가 되므로 따로 회수할 것이 없다. 이것이 실패 ①에서 본 영구 토큰과의 차이이고, 실습 파일에 토큰을 남기지 않는 이유이기도 하다.

다음 모듈

RBAC은 API를 통해 무엇을 할 수 있는가를 정한다. 그런데 파드가 일단 뜨고 나면 그 안에서 하는 일은 RBAC이 관여하지 않는다 — 루트로 실행하고, 호스트 파일시스템을 마운트하고, 커널 기능을 요구하는 것은 전부 파드 스펙에 적혀 있고 지금 우리 클러스터는 그것을 다 허용한다.

M24에서 파드 시큐리티 어드미션을 켠다. 네임스페이스에 라벨 하나를 붙여 restricted 수준을 강제하고, 지금 잘 돌고 있는 파드들이 거부되는 것을 먼저 본다. 그다음 securityContext를 채워 통과시킨다 — runAsNonRoot, readOnlyRootFilesystem, drop: ["ALL"]이 각각 무엇을 막는지 확인하면서.
