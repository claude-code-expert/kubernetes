# 모니터링과 로깅 — 발표 자료와 실습

『쿠버네티스 창시자에게 배우는 모범 사례 2판』 3장(모니터링과 로깅)을 바탕으로 한 발표 슬라이드와,
그 내용을 빈 kind 클러스터에서 처음부터 재현하는 실습 가이드.

| 파일 | 내용 |
|---|---|
| `slides.html` | 발표 슬라이드 93장. 브라우저로 열고 방향키로 넘긴다. `N` 발표자 노트, `P` 발표자 화면, `H` 단축키 도움말 |
| `lab-guide.html` | 실습 가이드. 명령 · 옵션 설명 · 실제 실행 결과 · 판정 기준을 단계별로 적었다 |
| `labs/` | 실습에 쓰는 모든 파일 (앱 소스, 매니페스트, Helm 값, 대시보드, k6 스크립트) |
| `src/` | 슬라이드와 가이드의 원본과 빌드 스크립트 |
| `images/` | 발표 화면 캡처. 슬라이드의 `data-cap` 키 이름(`install.png`, 여러 장이면 `red-2.png`)으로 저장하고 다시 빌드하면 그 슬라이드에 붙는다(`C` 키로 보기) |

## 발표 구성

1~3장은 개념, 4~7장은 따라하기다. 책 순서는 메트릭 → 도구 → 설치 → 로깅 → 알림인데, 발표는 알림을 로깅 앞으로 당겼다.
알림이 "몇 건"까지만 말해 주는 한계가 로그를 부르는 동기가 되기 때문이다.

| 장 | 주제 | 슬라이드 | 책 절 | 끝나면 할 수 있는 것 |
|---|---|---|---|---|
| – | 도입 | 1~7 | – | – |
| 1장 | 이론: 메트릭과 로그, 모니터링 기법 | 8~19 | 3.1 ~ 3.3 | USE · RED로 무엇을 볼지 정한다 |
| 2장 | 개념: 쿠버네티스 메트릭은 누가 만드나 | 20~34 | 3.4 ~ 3.5 | 메트릭 출처 세 곳을 메트릭 이름으로 구분한다 |
| 3장 | 도구와 프로메테우스 구조 | 35~48 | 3.6 ~ 3.7 전반 | pull 방식과 스택 구성요소 6개의 역할을 안다 |
| 4장 | 설치하고 둘러보기: Prometheus · Grafana | 49~59 | 3.7 후반 | 정상 상태(타깃 28/28 up)를 확인하고, 질문별로 화면 · 대시보드를 고른다 |
| 5장 | 앱 연결과 PromQL | 60~67 | 3.12.1 보강 | ServiceMonitor로 앱을 연결하고 RED를 분위수 · 라벨로 읽는다 |
| 6장 | 알림 받기와 대시보드 | 68~81 | 3.11 · 3.12.3 | 규칙을 만들고 알림이 수신처에 도착 · 해소되는 것을 확인한다 |
| 7장 | 로그 모으고 찾기: Loki + Alloy | 82~93 | 3.8 ~ 3.10 | 로그가 쌓이는지 확인하고 LogQL로 500 에러의 요청을 찾는다 |

자주 막히는 곳(Q&A)은 4장만 슬라이드에 두고, 5~7장 것은 `lab-guide.html` 11장 Q&A에 모았다.

## 실습 환경

macOS 기준. Docker 메모리 8GB · CPU 4 이상.

```
brew install --cask docker
brew install kind helm kubernetes-cli k6 jq
```

검증 환경 (2026-09-26): Docker 29.2.1 · kind v0.33.0 (Kubernetes v1.37.0) · kubectl v1.37.0 ·
Helm v4.2.4 · k6 v2.2.0 · kube-prometheus-stack 차트 89.2.2 · Loki 차트 7.3.0 · Alloy 차트 1.12.1

실습은 `lab-guide.html`을 열고 00부터 순서대로 따라 한다. 모든 명령은 이 폴더를 현재 디렉터리로 두고 실행한다.
