P99 · 99th PERCENTILE

가장 느린 1% 요청의 경계값

요청 100건을 빠른 순으로 줄 세웠을 때 99번째 요청의 응답 시간. "P99 790ms"는 99%는 790ms 안에 끝났고, 가장 느린 1%는 그보다 오래 걸렸다는 뜻이다. 평균이 가리는 느린 요청을 드러낸다.

ALERT · FIRING

AppHighErrorRate가 "발화"했다

AppHighErrorRate는 우리가 정의한 알림 규칙의 이름이다. 조건은 "5xx(서버 오류) 응답 비율이 5%를 넘는 상태가 2분 이상 지속". 조건이 충족되면 규칙이 firing(발화) 상태가 되고 Alertmanager가 담당자에게 알림을 보낸다.

메트릭으로 분석하고, 알림으로 확인한 뒤, 로그로 원인을 분석한다.
메트릭 → 알림 → 로그3/104
  • 1·2칸, 메트릭으로 분석: 실측. 평균 45ms, P50 0.59ms, P99 790ms. uri 라벨로 쪼개자 /api/chaos/slow 가 805ms.
  • P99 설명: 100건 중 가장 느린 1건을 빼면 나머지는 모두 이 값 이하. 정확한 계산 방법(히스토그램 버킷 + histogram_quantile)은 5장.
  • 3칸, 알림으로 확인: 사람이 대시보드를 보고 있지 않아도 규칙이 불러낸다. AppHighErrorRate 규칙은 labs/k8s/prometheusrule.yaml 에 있다. 식은 5xx 요청 비율 × 100 > 5, for: 2m. 발화 전 조건만 충족된 상태는 pending, 2분을 채우면 firing. 규칙 작성과 실제 발화 과정은 6장.
  • 4칸, 로그로 원인 분석: 알림이 말해 주는 것은 "에러율 5.9%"까지다. 어떤 요청이 왜 실패했는지는 로그가 답한다. 7장.

00MAP TERMS · 1/3 · 메트릭 수집과 저장

프로메테우스는 대상에서 메트릭을 가져와 시간 순으로 저장한다

용어원어 · 풀 네임뜻
스크레이프Scrape (직역: 긁어 오기)프로메테우스가 대상의 HTTP 주소(/metrics 등)에 주기적으로 요청해 그 순간의 메트릭 값을 읽어 가는 동작. 실습 주기는 30초
풀 방식Pull model수집기가 대상에 요청해서 가져온다. 반대는 대상이 수집기로 밀어 넣는 푸시(Push) 방식
타깃Target스크레이프할 대상 하나(주소 + 경로). 쿠버네티스에서는 라벨로 자동 발견한다. 같은 목적의 타깃 묶음은 잡(Job)
Prometheus프로메테우스 · CNCF(Cloud Native Computing Foundation) 졸업 프로젝트메트릭을 수집 · 저장 · 질의하고 알림 규칙을 평가하는 모니터링 시스템
TSDBTime Series Database · 시계열 데이터베이스(시각, 값) 쌍을 메트릭 이름 + 라벨별로 저장하는 DB. 프로메테우스는 자기 로컬 디스크에 2시간 단위 블록으로 쌓고, 보존 기한(실습: 3일 또는 4GB)이 지나면 지운다
최근 2시간치 데이터는 메모리에 있다. 들어온 값을 WAL(Write-Ahead Log · 선행 기록 로그)에 먼저 적어 두기 때문에 재시작해도 복구된다.
스크레이프는 가져오는 동작, TSDB는 시간 순 저장소5/104
  • 스크레이프: 공식 용어집에서 타깃은 "어떻게 스크레이프할지를 정의한 대상", 잡은 "같은 목적의 타깃 묶음(예: 복제된 프로세스들)", 인스턴스는 잡 안의 타깃 하나를 가리키는 라벨이다.
  • 풀 방식이라 대상은 메트릭을 HTTP로 "보여 주기만" 하면 된다. 수집 주기와 대상 목록은 프로메테우스 쪽이 정한다. 대상이 죽으면 스크레이프 실패 자체가 신호(up == 0)가 된다. 자세한 내용은 3장.
  • TSDB 공식 문서: 들어온 샘플은 2시간 블록으로 묶이고 블록마다 chunks 디렉터리, 메타데이터, 인덱스 파일을 갖는다. 현재 블록은 메모리에 있고 WAL로 보호된다. 작은 블록은 백그라운드에서 더 큰 블록으로 합쳐진다(compaction).
  • 보존 기한을 안 정하면 기본 15일. 실습 values 에서는 retention 3d, retentionSize 4GB 로 줄였다.

Alloy가 로그를 수집해 보내고, Loki가 저장하고 조회한다

용어원어 · 풀 네임뜻
stdout · stderrStandard output · Standard error (표준 출력 · 표준 에러)프로그램이 출력을 내보내는 기본 통로. 컨테이너가 여기로 쓴 줄을 런타임이 노드의 /var/log/pods 아래 파일로 남긴다
AlloyGrafana Alloy · 그라파나 랩스의 수집 에이전트OpenTelemetry Collector 배포판에 프로메테우스 파이프라인을 내장한 수집기. 파드 로그를 읽어 라벨을 붙이고 Loki로 보낸다

로그 스트림Log stream라벨이 모두 같은 로그 줄의 묶음. Loki는 먼저 라벨로 스트림을 고르고, 그 안의 로그만 검색한다
프로메테우스가 메트릭을 라벨로 다루듯, Loki는 로그를 라벨로 다룬다6/104
  • Loki 공식 설명: 프로메테우스에서 영감을 받은 로그 집계 시스템. 로그 라벨의 메타데이터만 색인하고, 실제 로그는 압축해 S3 · GCS · 로컬 파일시스템 같은 저장소에 둔다. 조회 시 색인으로 스트림을 고른 뒤 필요한 청크만 가져온다.
  • 그래서 라벨은 값의 종류가 적은 것(namespace, app)만 써야 한다. 요청 경로처럼 값이 끝없이 늘어나는 필드를 라벨로 올리면 스트림 수가 폭발한다. 7장에서 실패를 재현한다.
  • Alloy: 컴포넌트를 이어 파이프라인을 만든다. 이 실습의 흐름은 discovery.kubernetes(파드 찾기) → loki.source.kubernetes(로그 읽기) → loki.write(Loki로 전송). 7장에서 설정을 본다.
  • 책 3.10은 Promtail + loki-stack 차트로 설치한다. 둘 다 지금은 쓰지 않는다. 7장 정정 슬라이드에서 다룬다.

01USE METHOD · 책 3.3

USE: 모든 자원의 사용률·포화도·에러를 본다

"For every resource, check utilization, saturation, and errors." — Brendan Gregg
U · UTILIZATION

사용률

자원이 일을 처리하느라 바빴던 시간의 평균 비율. 예: CPU 70%, 링크 대역폭의 40%.

S · SATURATION

포화도

처리하지 못하고 쌓여 있는 작업의 양. 주로 대기열(queue) 길이로 나타난다.

E · ERRORS

에러 수

에러 이벤트 횟수. 해석이 쉬워서 먼저 확인하면 시간이 절약된다.

사용률 100%가 곧 장애는 아니다. 포화도가 0보다 커지는 순간부터 요청이 대기열에 쌓이고 지연이 늘어난다. 사용률만 보면 이 시점을 놓친다.
책 3.3: 애플리케이션 수준에는 한계가 있어 주로 인프라 모니터링에 쓴다16/104
  • 책의 예: 클러스터 노드의 네트워크를 사용률·포화도·에러 수로 보면 병목이나 네트워크 스택 문제를 쉽게 파악할 수 있다.
  • 그레그 원문 정의. 자원(resource): CPU·디스크·버스 등 서버의 물리 구성요소. 사용률: 자원이 작업을 처리하느라 바빴던 평균 시간. 포화도: 처리하지 못해 쌓인(대개 큐잉된) 추가 작업의 정도. 에러: 에러 이벤트 수.
  • 그레그는 에러를 먼저 보는 것을 "보통 더 빠르고 해석이 쉬워서" 권하는 최적화로 적는다.

  • 이 개념을 노드 메트릭 이름으로 바꾸는 것은 4장 PromQL에서 한다.

01WHERE TO APPLY

사용자가 겪는 문제는 RED로 발견하고, 원인은 USE로 찾는다

실행 대기 줄 = run queue · 버려진 패킷 = dropped packets
스와핑 = swapping(RAM이 부족해 메모리를 디스크로 내려보냄. 느려짐) · OOM 킬 = Out Of Memory kill(메모리 부족으로 강제 종료)

책 3.3: 두 방법론은 서로 보완한다. USE는 인프라를, RED는 사용자 경험을 본다18/104
  • 위 줄: 요청이 지나가는 구간마다 R·E·D 세 숫자를 둔다. 사용자가 실제로 겪는 것이라 "증상"이다.
  • 아래 줄: 그 요청을 실어 나르는 노드의 네 자원마다 U·S·E. 증상이 보였을 때 원인을 찾으러 내려가는 곳이다.
  • 스와핑: RAM이 모자라면 운영체제가 당장 안 쓰는 메모리 페이지를 디스크의 스왑 영역으로 내려보내고, 다시 필요하면 읽어 올린다. 디스크는 RAM보다 훨씬 느리므로 스왑이 잦으면 응답 지연이 크게 는다. 사용률만 보면 "95% 사용 중"으로 끝나지만 스왑이 일어나면 이미 메모리가 넘쳐 일이 밀리고 있다는 뜻이라 포화도(S)로 본다. 스왑도 부족하거나 꺼져 있으면 커널이 프로세스를 강제 종료한다(OOM 킬). 쿠버네티스 노드는 전통적으로 스왑을 끄고 운영해서, 파드 메모리 부족은 OOM 킬(컨테이너 재시작)로 먼저 드러나는 경우가 많다.
  • 프로메테우스 공식 가이드(The Zen of Prometheus): 사용자가 신경 쓰는 지표(지연·가용성)를 먼저 재고, CPU 포화 같은 내부 지표는 원인 추적과 용량 계획용으로 둔다. 알림 가이드도 "사용자에게 보이는 지연·에러에만 사람을 깨운다"고 적는다. 6장의 출발점이다.
  • 구글 SRE 책의 표현: 모니터링은 "무엇이 망가졌나(증상)와 왜 망가졌나(원인)" 두 질문에 답해야 한다.

  • 스케줄러: 아직 노드를 못 받은 파드 수. 계속 0보다 크면 노드에 자리가 없거나 스케줄러에 문제가 있다.
  • 컨트롤러 매니저: 컨트롤러별 작업 큐 길이. 쌓이면 "replicas 3으로 바꿨는데 파드가 늦게 뜬다" 같은 증상이 된다.
  • kubelet: 안에 든 cAdvisor가 컨테이너 사용량을 낸다. working set 메모리가 limit에 닿으면 커널이 컨테이너를 죽인다.
  • kube-proxy: 서비스 → 파드 규칙(iptables 등)을 다시 쓰는 데 걸리는 시간. 늦어지면 새로 뜬 파드로 트래픽이 늦게 간다.
  • CoreDNS: DNS 응답 시간. 서비스끼리는 이름으로 부르므로 여기가 느리면 모든 호출 앞에 지연이 붙는다.
  • 파드(앱): 앱이 직접 내는 메트릭. order-api는 http_server_requests_seconds 로 RED를 계산한다.

1. 평균은 없는 요청을 가리킨다

요청 절반은 1ms 안쪽, 상위 5%는 700ms를 넘는다. 45ms 근처의 요청은 거의 없다(1장 "평균의 함정").

2. 분위수로 꼬리를 본다

P50은 대부분의 경험, P99는 가장 느린 1%의 경험. 알림과 SLO는 P95 · P99로 건다.

3. 라벨로 쪼개 원인을 좁힌다

sum by (uri, le)로 바꾸자 느린 경로가 하나로 드러난다(0.805초, 나머지는 18ms 이하). 쪼갤 라벨이 계측에 있어야 가능하다.

06WHAT TO ALERT · 책 3.11

사람이 지금 무언가 할 수 있을 때만 알림을 보낸다

알림을 건다

· SLO에 영향을 주는 증상: 사용자 요청 5%가 실패, 응답 시간이 약속을 넘음

알림을 걸지 않는다

· 파드 하나가 실패할 때마다: 쿠버네티스가 스스로 재시작한다
· CPU·메모리가 높을 때: 사용자가 겪지 않으면 할 일이 없다. 원인을 찾을 때 본다
· 경험상 저절로 풀리는 문제

06HOW IT BEHAVES · 실측

발화는 for가, 해소는 rate의 창이 정한다

원인이 사라져도 rate(…[5m]) 창이 지나갈 때까지 최대 5분 firing이 유지된다. 정상 동작이다80/104
  • 실측. 20초 간격으로 /api/v1/rules 를 조회해 상태가 바뀐 시각을 기록했다.
  • 부하 시작 → pending 40초: 평가 주기 30초 + rate 창이 값을 잡는 시간.
  • pending → firing: 에러율 2분 18초(for: 2m), 지연 3분 18초(for: 3m). 규칙에 적은 값과 맞는다.
  • 부하 종료 → inactive: 5분 5초. rate(…[5m])는 매 순간 직전 5분을 보므로, 부하가 끝난 뒤에도 창 안에 에러가 남아 있는 동안 비율이 임계값을 넘는다. for는 발화 조건이지 해소 조건이 아니다.
  • 그림은 같은 절차를 먼저 돌렸을 때의 기록이다. 다시 돌린 실측(실습 가이드 8-3)은 시작→pending 30초, pending→firing은 for 값 그대로(2분 20초 · 3분 20초), 부하 종료→inactive 5분 30초. 해소되면 수신자에게 resolved 알림이 group_interval(5분) 주기에 맞춰 한 번 더 온다.
  • 빨리 꺼지게 하려고 창을 [2m]으로 줄이면 트래픽이 적을 때 비율이 요동쳐 오탐이 는다. 보통은 창을 두고 description에 "원인이 사라진 뒤에도 최대 5분간 유지"라고 적는다.

06INHIBIT vs SILENCE

억제는 규칙이 자동으로, 침묵은 사람이 기간을 정해 끈다

억제 · Inhibition 
# 같은 알림을 critical · warning 둘로 넣었을 때
severity=critical  state=active      inhibitedBy=0건
severity=warning   state=suppressed  inhibitedBy=1건

critical이 울리는 동안 같은 대상의 warning은 보내지 않는다. DB가 죽어 서비스 열 개가 경고를 내도 사람이 볼 것은 하나다.

침묵 · Silence 
# alertname=DemoAlert 에 10분 침묵
severity=critical  state=suppressed  silencedBy=1건
severity=warning   state=suppressed  silencedBy=1건

계획 작업 중에 알림을 잠시 끈다. critical까지 모두 눌린다. 반드시 끝나는 시각이 있다.

둘 다 state=suppressed지만 inhibitedBy(규칙)와 silencedBy(사람) 중 어느 쪽이 채워졌는지로 구분한다. "아는 문제니까 꺼 두자"는 침묵이 아니라 규칙이나 문제를 고칠 일이다.
침묵은 Alertmanager UI(9093)의 New Silence 또는 API로 만든다83/104
  • 실측. 실제 장애를 기다리지 않고 Alertmanager API(/api/v2/alerts)로 같은 alertname·namespace의 critical·warning 알림을 직접 밀어 넣었다.
  • 영구 침묵이 없는 것이 설계 의도다. 계획 작업이 끝나면 지운다.

앱이 파일에만 쓸 때

07HOW TO QUERY · LogQL

LogQL은 좁히고 → 거르고 → 꺼내고 → 센다

단계예언제 쓰나
① 좁히기{namespace="apps", app="order-api"}라벨로 스트림을 고른다. 항상 여기서 시작한다. 색인을 쓰므로 빠르다
② 거르기|= "/api/chaos/error" · |~ " 500 " · != "health"본문에 문자열 · 정규식이 있는(없는) 줄만. 파서보다 먼저 두면 빠르다
③ 꺼내기| json · | pattern `<_> … <status> <_> <dur>`본문에서 필드를 꺼내 status >= 500처럼 조건을 건다. 뒤에 | __error__=""
④ 세기sum by (status) (count_over_time({…} | … [5m]))줄 수를 메트릭처럼. 그래프 · 알림에 쓴다
PromQL과 모양이 같다: {라벨}로 고르고, [5m] 창으로 세고, sum by로 묶는다. 다른 점은 ②③, 본문을 거르고 꺼내는 단계가 있다는 것이다.

  • ① 없이 본문 검색만 할 수는 없다. Loki는 라벨로 스트림을 고른 뒤 그 안의 덩어리(chunk)만 연다. 좁힐수록 빠르다.
