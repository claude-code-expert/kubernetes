P99 · 99th PERCENTILE

가장 느린 1% 요청의 경계값

요청 100건을 빠른 순으로 줄 세웠을 때 99번째 요청의 응답 시간. "P99 790ms"는 99%는 790ms 안에 끝났고, 가장 느린 1%는 그보다 오래 걸렸다는 뜻이다. 평균이 가리는 느린 요청을 드러낸다.

ALERT · FIRING

AppHighErrorRate가 "발화"했다

AppHighErrorRate는 우리가 정의한 알림 규칙의 이름이다. 조건은 "5xx(서버 오류) 응답 비율이 5%를 넘는 상태가 2분 이상 지속". 조건이 충족되면 규칙이 firing(발화) 상태가 되고 Alertmanager가 담당자에게 알림을 보낸다.

  • 첫째, 얼마나 느린가입니다. 평균은 45ms로 멀쩡해 보이지만 P99는 790ms입니다. P99는 요청 100건을 빠른 순으로 세웠을 때 99번째 요청의 응답 시간, 즉 가장 느린 1%의 경계값입니다.
  • 둘째, 무엇이 느린가입니다. URI별로 나눠 보면 /api/chaos/slow 하나만 805ms입니다.
  • 셋째, 사람이 보지 않아도 알림이 옵니다. AppHighErrorRate는 5xx 응답 비율이 5%를 넘는 상태가 2분 이상 이어지면 발화하는 규칙입니다. 넷째, 알림이 난 시각의 로그에서 실패한 요청을 찾습니다.
  • 5xx는 500번대 HTTP 응답 코드로, 요청은 맞았는데 서버 쪽에서 처리하다 실패했다는 뜻입니다. 규칙의 조건이 채워진 상태를 firing, 우리말로 발화라고 하고, 발화하면 Alertmanager가 담당자에게 알림을 보냅니다.

스크레이프는 가져오는 동작, TSDB는 시간 순 저장소6/83

  • 타깃은 스크레이프할 대상 하나, 즉 주소와 경로입니다. 쿠버네티스에서는 라벨로 자동으로 찾고, 같은 목적의 타깃 묶음을 잡이라고 부릅니다.
  • 프로메테우스는 메트릭을 수집, 저장, 질의하고 알림 규칙을 평가하는 시스템입니다. 저장소 TSDB는 로컬 디스크에 2시간 단위 블록으로 쌓고, 3일 또는 4GB가 지나면 오래된 것부터 지웁니다.
  • 풀 방식의 반대는 푸시 방식으로, 대상이 수집기에게 직접 값을 보내는 방식입니다. 잡의 예를 들면, order-api 파드 두 개는 타깃 두 개이고 이 둘이 order-api라는 잡 하나로 묶입니다.
  • CNCF는 쿠버네티스를 관리하는 재단이고, 졸업 프로젝트는 널리 쓰여 성숙했다고 인정받은 단계입니다. WAL은 받은 값을 본 저장소에 넣기 전에 받은 순서대로 먼저 적어 두는 기록이라, 프로세스가 갑자기 죽어도 이 기록을 다시 읽어 복구합니다.
  • 최근 2시간치는 메모리에 있지만, 들어온 값을 WAL에 먼저 적어 두기 때문에 재시작해도 복구됩니다.

Alertmanager는 프로메테우스가 보낸 알림을 받아서 바로 넘기지 않고 세 가지를 거칩니다. 같은 알림이 여러 번 들어와도 한 번만 보내는 중복 제거, 비슷한 알림 여러 개를 한 통으로 합치는 묶기, 그리고 심각도에 따라 받을 곳을 고르는 경로 지정입니다. 그다음 Slack, 메일, PagerDuty로 보냅니다. PagerDuty는 당직자 호출 서비스입니다. 당직 일정표에 따라 지금 당번인 사람에게 전화나 앱 알림을 보내고, 확인할 때까지 반복하며, 정해진 시간 안에 아무도 받지 않으면 다음 담당자에게 넘깁니다. 그래서 새벽에도 사람을 깨워야 하는 critical 알림은 PagerDuty로, 업무 시간에 보면 되는 warning은 Slack으로 나눠 보내는 경우가 많습니다.
  • 침묵(silence)은 알림을 정해 둔 시간 동안 일부러 끄는 기능입니다. 예를 들어 밤 10시부터 30분 동안 노드를 점검한다면, 그 사이에 울릴 알림을 미리 침묵으로 막아 둡니다. 시간이 지나면 자동으로 풀립니다.
  • 억제(inhibit)는 더 심각한 알림이 울리는 동안 덜 심각한 알림을 숨기는 기능입니다. 이 실습에서는 같은 네임스페이스에서 같은 이름의 critical 알림이 울리고 있으면 warning 알림은 보내지 않습니다. 같은 문제로 알림이 두 통씩 오는 것을 막기 위해서입니다.
  • Grafana는 프로메테우스에는 PromQL로, Loki에는 LogQL로 질의해서 대시보드와 조회 화면을 그립니다. 데이터를 따로 저장하지 않고 화면을 열 때마다 가져옵니다.

01USE METHOD · 책 3.3

USE: 모든 자원의 사용률·포화도·에러를 본다

"For every resource, check utilization, saturation, and errors." — Brendan Gregg
U · UTILIZATION

사용률

자원이 일을 처리하느라 바빴던 시간의 평균 비율. 예: CPU 70%, 링크 대역폭의 40%.

S · SATURATION

포화도

처리하지 못하고 쌓여 있는 작업의 양. 주로 대기열(queue) 길이로 나타난다.

E · ERRORS

에러 수

에러 이벤트 횟수. 해석이 쉬워서 먼저 확인하면 시간이 절약된다.

사용률 100%가 곧 장애는 아니다. 포화도가 0보다 커지는 순간부터 요청이 대기열에 쌓이고 지연이 늘어난다. 사용률만 보면 이 시점을 놓친다.
책 3.3: 애플리케이션 수준에는 한계가 있어 주로 인프라 모니터링에 쓴다 · 실습 가이드 05 Grafana 5-2 섹션 참고16/83
  • USE는 모든 자원마다 사용률, 포화도, 에러 세 가지를 봅니다.
  • 사용률은 자원이 바빴던 시간의 비율로, CPU 70%처럼 나타냅니다. 포화도는 처리하지 못하고 쌓인 작업의 양으로, 주로 대기열 길이입니다. 에러는 에러 이벤트 횟수이고, 해석이 쉬워서 먼저 보면 시간이 절약됩니다.
  • 포화도의 예를 들면, CPU 코어가 4개인데 실행을 기다리는 작업이 6개라면 2개는 줄을 서서 기다립니다. 사용률은 이미 100%라 더 오르지 않지만, 줄은 계속 길어질 수 있어서 포화도를 따로 봅니다.
  • 사용률 100%가 곧 장애는 아닙니다. 포화도가 0보다 커지는 순간부터 요청이 대기열에 쌓이고 지연이 늘어나므로, 사용률만 보면 이 시점을 놓칩니다. USE는 주로 인프라에 씁니다.

01WHERE TO APPLY

사용자가 겪는 문제는 RED로 발견하고, 원인은 USE로 찾는다

RED = 서비스마다 Rate(초당 요청 수) · Errors(실패한 요청 수) · Duration(처리 시간 분포)를 본다. 모든 서비스를 같은 세 지표로 재면 대시보드 하나로 비교할 수 있다
실행 대기 줄 = run queue · 버려진 패킷 = dropped packets
스와핑 = swapping(RAM이 부족해 메모리를 디스크로 내려보냄. 느려짐) · OOM 킬 = Out Of Memory kill(메모리 부족으로 강제 종료)

책 3.3: 두 방법론은 서로 보완한다. USE는 인프라를, RED는 사용자 경험을 본다17/83
  • RED는 서비스용 방법론입니다. 서비스마다 R, 초당 요청 수와 E, 실패한 요청 수와 D, 처리 시간의 분포 세 가지를 봅니다. 모든 서비스를 같은 세 지표로 재면 대시보드 하나로 어느 서비스가 이상한지 바로 비교할 수 있습니다. 앞에서 본 USE가 CPU, 메모리, 디스크 같은 자원을 본다면 RED는 사용자가 느끼는 요청을 봅니다.
  • 위쪽 RED는 요청이 지나가는 구간마다 적용합니다. 사용자에서 Ingress, order-api, 데이터베이스까지 구간마다 초당 요청 수, 실패 수, 걸린 시간 분포를 봅니다. 사용자가 겪는 증상입니다.
  • 아래쪽 USE는 요청을 처리하는 자원마다 적용합니다. order-api 파드가 올라간 노드의 CPU, 메모리, 디스크, 네트워크마다 사용률, 포화도, 에러를 봅니다.
  • Ingress는 클러스터 밖에서 들어온 요청을 안쪽 서비스로 넘기는 입구입니다. 그림의 실행 대기 줄은 CPU를 기다리는 작업 수로 CPU의 포화도이고, 버려진 패킷은 처리하지 못해 버린 네트워크 패킷으로 네트워크의 포화도입니다.
  • 메모리의 포화도는 스와핑과 OOM 킬로 드러납니다. 스와핑은 RAM이 모자라 메모리를 디스크로 내려보내는 것이고, OOM 킬은 메모리 부족으로 강제 종료되는 것입니다.
  • 증상은 RED로 발견하고, 원인은 USE로 찾습니다.

  • kube-proxy는 서비스 주소로 온 트래픽을 파드로 보내는 규칙을 만들고, CoreDNS는 서비스 이름을 IP로 바꿔 줍니다.

02CADVISOR · 책 3.4.1

cAdvisor: 컨테이너가 실제로 얼마나 쓰는지 잰다

어디에 넣나 브라우저 localhost:9090(Prometheus 화면) → 위쪽 Query 입력칸에 붙여 넣고 Execute → 아래 Table 탭. Prometheus는 4장에서 설치하고, 이 질의는 4장 따라하기 ② 세 출처에서 직접 쳐 본다.

# order-api 파드별 메모리 (MiB)
sum by (pod) (
  container_memory_working_set_bytes{
    namespace="apps", container="order-api"}
) / 1024 / 1024
# Table 탭에 나오는 결과
{pod="order-api-77bf967968-bj8c6"}  208.0078125
{pod="order-api-77bf967968-msnb6"}  217.1484375

파드 이름 끝부분과 값은 환경마다 다르다.

메트릭뜻
container_memory_
working_set_bytes		지금 실제로 사용 중인 메모리. 노드 메모리가 모자랄 때 kubelet이 내보낼(축출) 파드를 고르는 기준. limit에 가까우면 OOM 킬 위험
container_cpu_
usage_seconds_total		CPU를 쓴 누적 초. rate()로 감싸야 초당 사용량(코어)이 된다
container_network_
receive_bytes_total		받은 네트워크 바이트 누적

메트릭 전체 목록: cAdvisor · prometheus.md · 실습 가이드 04 Prometheus 4-4 섹션 참고25/83
  • cAdvisor는 컨테이너가 실제로 얼마나 쓰는지 잽니다. 왼쪽 코드는 PromQL, 즉 프로메테우스에 보내는 질의입니다. 터미널이 아니라 브라우저의 Prometheus 화면, localhost:9090의 Query 입력칸에 붙여 넣고 Execute를 누르면 아래 Table 탭에 결과가 나옵니다. Prometheus는 4장에서 설치하니, 지금은 모양만 보고 4장 따라하기에서 직접 쳐 봅니다.
  • 질의를 안쪽부터 읽으면, container_memory_working_set_bytes 중에서 apps 네임스페이스의 order-api 컨테이너만 고르고, sum by (pod)로 파드별로 합친 뒤, 1024로 두 번 나눠 바이트를 MiB로 바꿉니다. 결과는 파드 두 개가 각각 약 208MiB, 217MiB를 쓰고 있다는 뜻입니다.
  • container_memory_working_set_bytes는 지금 실제로 사용 중인 메모리입니다. 노드 메모리가 모자랄 때 kubelet이 내보낼 파드를 고르는 기준입니다. 이렇게 내보내는 것을 축출이라고 하고, 축출된 파드는 다른 노드에서 다시 뜹니다. 또 이 값이 limit에 가까우면 OOM 킬 위험이 있습니다.
  • container_cpu_usage_seconds_total은 CPU를 쓴 누적 초라서 rate()로 감싸야 초당 사용량이 됩니다. rate()는 계속 늘기만 하는 누적값이 일정 시간 동안 초당 얼마씩 늘었는지 계산하는 함수입니다. CPU라면 결과가 0.5일 때 0.5코어를 쓰고 있다는 뜻입니다. 이름이 container_로 시작하면 cAdvisor에서 온 값입니다.

02METRICS SERVER · 책 3.4.2

metrics-server는 오토스케일링 전용이다

# 터미널에서: 등록된 메트릭 API 확인
kubectl get apiservices | grep metrics
# 결과
v1beta1.metrics.k8s.io  kube-system/metrics-server  True
# 터미널에서
kubectl top pod -n apps
NAME                        CPU(cores)  MEMORY(bytes)
order-api-77bf967968-bj8c6  6m          208Mi
order-api-77bf967968-msnb6  6m          217Mi

하는 일

각 kubelet에서 CPU·메모리를 15초마다 읽어 최근값 하나만 메모리에 둔다. 이를 metrics.k8s.io로 제공한다.

사용처

HPA · VPA · kubectl top. 대시보드 · 알림용으로는 쓰지 않는다. 지난 값을 저장하지 않기 때문이다(공식 README의 주의 문구). 그런 용도는 프로메테우스가 kubelet에서 직접 수집한다.

제공 항목: Resource metrics pipeline (CPU · 메모리뿐) · 실습 가이드 04 Prometheus 4-3 섹션 참고26/83
  • metrics-server는 오토스케일링 전용입니다. 첫 명령 kubectl get apiservices는 API 서버에 등록된 API 목록을 봅니다. 결과의 v1beta1.metrics.k8s.io 줄은 "Metrics API, 즉 파드와 노드의 CPU·메모리 사용량을 조회하는 주소로 요청이 오면 kube-system의 metrics-server가 답한다"는 등록 정보입니다. 끝의 True는 그 연결이 지금 동작한다는 뜻입니다.
  • 두 번째 명령 kubectl top pod가 바로 이 Metrics API를 씁니다. kubectl이 API 서버에 apps 네임스페이스 파드들의 사용량을 요청하면, API 서버는 직접 답하지 않고 위에서 본 등록 정보에 따라 요청을 metrics-server로 넘깁니다. metrics-server가 들고 있던 최근값을 돌려주면 kubectl이 표로 출력합니다. 그래서 metrics-server가 없으면 kubectl top은 Metrics API를 쓸 수 없다는 오류를 냅니다.
  • 표에는 order-api 파드 두 개의 CPU와 메모리가 나옵니다. CPU의 6m은 6밀리코어, 즉 0.006코어이고 1000m이 코어 하나입니다. 메모리는 208Mi, 217Mi입니다.
  • metrics-server는 각 kubelet에서 15초마다 CPU와 메모리를 읽어서, 파드마다 지금 값 하나만 메모리에 둡니다. 지난 값은 남기지 않습니다. 그래서 "지금 얼마나 쓰나"는 답할 수 있지만 "어제 이 시각에는 얼마였나"나 "지난 1시간 그래프"는 답할 수 없습니다.
  • 이 값을 사용하는 것은 셋입니다. HPA는 CPU 사용량이 목표를 넘으면 파드 개수를 늘리고, VPA는 파드 하나가 요청하는 CPU와 메모리 양을 조정하고, kubectl top은 지금 사용량을 터미널에 보여 줍니다. 셋 다 지금 값 하나만 있으면 되는 일입니다.
  • 그래서 metrics-server 공식 문서는 이 값을 모니터링 도구의 데이터 출처로 쓰지 말라고 적어 둡니다. 대시보드나 알림을 만들려고 metrics-server에서 수집하지 말고, 원래 데이터가 있는 kubelet에서 직접 가져가라는 뜻입니다. 이 실습의 프로메테우스가 바로 그렇게 kubelet의 cAdvisor 경로에서 직접 수집합니다.

03PULL MODEL

pull 방식은 수집 성공 여부로 대상이 살아 있는지 안다

# 수집에 성공하면 1, 실패하면 0
up{job="order-api", pod="order-api-…-g247f"}  1
up{job="order-api", pod="order-api-…-pjnk8"}  1

얻는 것

대상마다 up 시계열이 자동으로 생긴다. 수집에 실패하면 0이 된다. 요청이 없는 한가한 앱도 /metrics에는 응답하므로 1이다. push 방식에서는 데이터가 안 오면 죽은 건지 한가한 건지 알 수 없다.

대가 ①

프로메테우스가 대상에 네트워크로 닿아야 한다. 방화벽·네트워크 정책이 막으면 수집이 안 된다.

대가 ②

수십 초 만에 끝나는 배치 잡은 수집하러 갈 때 이미 끝나 있다. 이때는 Pushgateway에 값을 남긴다.

대가 ③

30초 간격 샘플이라 요청 하나하나를 세는 과금처럼 100% 정확도가 필요한 용도에는 맞지 않는다.

대상은 메트릭을 보여 주기만 하고, 주기와 목록은 프로메테우스가 정한다35/83
  • 프로메테우스는 대상에 가서 가져오는 pull 방식입니다. 반대인 push 방식은 대상이 수집기로 데이터를 보내는 방식입니다. pull 방식에서는 수집이 성공했는지만 보면 대상이 살아 있는지 알 수 있습니다.
  • 대상마다 up 시계열이 자동으로 생기고, 수집에 성공하면 1, 실패하면 0이 됩니다. 요청이 없는 한가한 앱도 /metrics에는 응답하므로 1입니다.
  • 대가도 있습니다. 프로메테우스가 대상에 네트워크로 닿아야 해서, 파드 사이 통신을 막는 NetworkPolicy나 방화벽이 있으면 수집이 안 됩니다. 수십 초 만에 끝나는 배치 잡은 수집하러 갈 때 이미 끝나 있어서 Pushgateway를 씁니다.
  • 또 30초 간격 샘플이라, 과금처럼 요청 하나하나를 정확히 세야 하는 용도에는 맞지 않습니다.

왜 필요한가

열면 보이는 것

  • 이렇게 열면 컴포넌트 계층의 메트릭이 보입니다. etcd_disk_wal_fsync_duration_seconds는 etcd가 쓰기 기록을 디스크에 확정하는 데 걸린 시간, scheduler_pending_pods는 아직 노드를 배정받지 못한 파드 수, workqueue_depth는 컨트롤러가 처리하지 못하고 쌓아 둔 일의 수입니다. 운영 클러스터에서는 이 포트를 방화벽이나 네트워크 정책으로 막고 인증을 겁니다.

1. 평균은 없는 요청을 가리킨다

요청 절반은 1ms 안쪽, 상위 5%는 700ms를 넘는다. 45ms 근처의 요청은 거의 없다(1장 "평균의 함정").

2. 분위수로 꼬리를 본다

P50은 요청 절반이 이 시간 안에 끝났다는 뜻, P99는 가장 느린 1%가 이 시간보다 오래 걸렸다는 뜻. 알림과 SLO는 P95 · P99로 건다.

3. 라벨로 쪼개 원인을 좁힌다

sum by (uri, le)로 바꾸자 느린 경로가 하나로 드러난다(0.805초, 나머지는 18ms 이하). 쪼갤 라벨이 계측에 있어야 가능하다.

06WHAT TO ALERT · 책 3.11

알림을 받아야 할 사항과 저절로 풀리는 문제

알림을 건다

· SLO에 영향을 주는 증상: 사용자 요청 5%가 실패, 응답 시간이 약속을 넘음
· 관측 자체의 고장: 스크레이프 실패. 이게 죽으면 다른 알림이 모두 침묵한다

알림을 걸지 않는다

· 파드 하나가 실패할 때마다: 쿠버네티스가 스스로 재시작한다
· CPU·메모리가 높을 때: 사용자가 겪지 않으면 할 일이 없다. 원인을 찾을 때 본다
· 경험상 저절로 풀리는 문제

사람 대신 자동으로 고칠 수 있는 것자동 조치
응답 없는 프로세스라이브니스 프로브(liveness probe)가 컨테이너를 재시작
디스크가 꽉 참오래된 로그를 자동 삭제해 공간 확보
책 3.11: 유저는 SLO에 영향을 미치는 이벤트만 알림 받고 싶을 것이다62/83
  • 알림을 받아야 할 사항과, 알림을 걸지 않아도 저절로 풀리는 문제를 나눕니다. 나누는 기준은 알림을 받은 사람이 지금 무언가 할 수 있느냐입니다. 할 일이 없는 알림은 사람을 지치게만 합니다.
  • 알림을 거는 것은 두 가지입니다. 첫째는 사용자가 겪는 증상입니다. 요청 5%가 실패하거나 응답이 약속한 시간보다 느린 경우처럼 SLO, 즉 서비스 목표에 영향을 주는 것입니다.
  • 둘째는 관측 자체가 끊긴 경우입니다. 스크레이프, 즉 프로메테우스가 앱의 메트릭을 가져오는 일이 실패하면 데이터가 들어오지 않습니다. 그러면 에러율 규칙도 계산할 값이 없어 조용해지기 때문에, 문제가 있어도 아무 알림이 오지 않습니다. 그래서 수집 실패에는 따로 알림을 겁니다.
  • 파드 하나가 죽을 때마다, CPU나 메모리가 높을 때마다 알림을 걸지는 않습니다. 파드는 쿠버네티스가 스스로 다시 띄우고, CPU가 높아도 사용자가 느끼지 못하면 사람이 할 일이 없습니다. 이런 값은 원인을 찾을 때 봅니다.
  • 자동으로 고칠 수 있는 것은 자동으로 고칩니다. 라이브니스 프로브는 쿠버네티스가 컨테이너에 주기적으로 "살아 있나"를 묻는 검사입니다. 응답이 없으면 컨테이너를 다시 시작합니다. 디스크가 꽉 차는 문제는 오래된 로그를 자동으로 지워서 막습니다.

06ANATOMY OF A RULE

규칙 하나 = 질의 + 임계값 + 지속 시간 + 라벨 + 메시지

apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: study-app-rules
  namespace: monitoring
  labels: {release: kps}          # ⓪ 오퍼레이터가 고르는 표시
spec:
  groups:
  - name: study-app
    interval: 30s                  # 평가 주기
    rules:
    - alert: AppHighErrorRate       # ① 이름      expr: |                       # ② 질의 (5장 E)
        100 * (
          sum by (job) (rate(…_count{status=~"5.."}[5m]))
          / sum by (job) (rate(…_count[5m]))
        ) > 5                        # ③ 임계값      for: 2m                       # ④ 지속 시간      labels:
        severity: warning           # ⑤ 누구에게 보낼지
      annotations:                   # ⑥ 메시지
        summary: "{{ $labels.job }} 에러율 {{ $value | printf "%.1f" }}%"
칸하는 일
⓪ release: kps이 라벨이 있어야 오퍼레이터가 Prometheus에 반영한다
① alert규칙 이름. Alerts 화면과 알림 메시지의 alertname
② expr5장에서 쓴 에러율 질의를 그대로 옮기고 ×100(퍼센트)
③ > 55%를 넘는 job만 결과에 남는다. 남은 줄 하나 = 알림 하나
④ for2분 동안 계속 넘어야 firing. 잠깐 튄 것은 거른다
⑤ severityAlertmanager가 이 값으로 수신자를 고른다(warning → 기본, critical → 당직)
⑥ summary알림에 들어가는 문장. $labels.job · $value가 채워지고 printf "%.1f"로 소수점 한 자리까지 잘라 "order-api 에러율 5.6%"가 된다
전체 파일: labs/k8s/prometheusrule.yaml · 실습 가이드 08 알림 8-2 섹션 참고64/83
  • 규칙 하나는 질의, 임계값, 지속 시간, 라벨, 메시지로 이루어집니다. 에러율 규칙으로 보겠습니다.
  • 맨 위 release: kps 라벨이 있어야 오퍼레이터가 이 규칙을 프로메테우스에 반영합니다. groups 아래 interval: 30s는 이 그룹의 규칙을 30초마다 계산한다는 뜻입니다. alert는 규칙 이름이고, 알림 메시지에 alertname으로 들어갑니다.
  • expr는 5장의 에러율 질의입니다. status=~"5.."는 상태 코드가 5로 시작하는 응답, 즉 서버 오류만 고른다는 뜻입니다. rate로 최근 5분의 초당 건수를 구하고, sum by (job)로 앱별로 합친 뒤 전체 요청으로 나누고 100을 곱해 퍼센트로 만듭니다.
  • > 5는 5%를 넘는 앱만 결과에 남깁니다. 남은 줄 하나가 알림 하나가 됩니다. for: 2m이라 2분 동안 계속 넘어야 firing이 되고, 잠깐 튄 값은 여기서 걸러집니다.
  • severity: warning은 업무 시간에 보면 되는 알림이라는 표시이고, Alertmanager가 이 값으로 수신자를 고릅니다. summary의 $labels.job 자리에는 앱 이름이, $value 자리에는 계산된 값이 들어갑니다. printf "%.1f"는 소수점 한 자리까지만 남기라는 뜻이라 "order-api 에러율 5.6%" 같은 문장이 됩니다.

  • routes는 위에서부터 조건이 맞는 첫 경로로 보냅니다. matchers의 =~는 정규식으로 맞춘다는 뜻입니다. 첫 경로는 "null" 수신자인데, 받을 곳이 없는 수신자라 여기로 가면 버려집니다. Watchdog처럼 항상 울리는 알림과, kind 환경에서 늘 나오는 노드 시계 경고를 여기로 보내 조용히 합니다. 둘째 경로는 critical을 당직 수신자로 보내고, 나머지는 기본 수신자로 갑니다.
  • inhibit_rules는 억제 규칙입니다. source는 기준이 되는 critical 알림, target은 숨길 warning과 info 알림입니다. equal에 적은 네임스페이스와 알림 이름이 둘 다 같을 때만 숨깁니다. 그래서 이름이 서로 다른 실습 규칙 네 개는 서로를 숨기지 않습니다.
  • 부하가 도는 동안 억제와 침묵을 직접 해 봅니다. 같은 이름의 critical과 warning 알림을 넣으면 warning이 suppressed, 즉 보내지 않고 눌러 둔 상태가 됩니다. inhibitedBy=1은 한 알림 때문에 눌렸다는 뜻입니다. 침묵을 걸면 둘 다 silencedBy=1이 되어 어느 쪽도 보내지 않습니다.

  • 설치 전에 값 파일을 봅니다. Loki는 로그를 저장하고, Alloy는 파드 로그를 읽어 Loki로 보내는 수집기입니다.
  • loki-values.yaml은 SingleBinary 모드, 복제 1개, 파일시스템 저장소로 최소 구성을 잡습니다. schemaConfig는 없으면 설치가 실패하므로 꼭 넣습니다.
  • auth_enabled: false는 멀티테넌시를 끄는 설정입니다. 켜 두면 요청마다 어느 조직의 로그인지 알리는 X-Scope-OrgID 헤더가 필요합니다. replication_factor: 1은 로그를 한 벌만 저장한다는 뜻이고, schemaConfig는 로그 색인을 어떤 형식(tsdb, v13)으로 쌓을지 정합니다.
  • retention_period: 72h는 사흘이 지난 로그를 지우겠다는 설정입니다. 실제로 지우는 일은 compactor가 하므로 retention_enabled: true와 delete_request_store를 함께 넣습니다.
  • compactor는 Loki 안에서 저장된 데이터를 정리하는 구성요소입니다. 작은 색인 파일을 합치고, 보존 기간이 지난 로그를 실제로 지웁니다. persistence 10Gi는 Loki 파드가 다시 떠도 로그가 남도록 10GiB 디스크를 붙이는 설정입니다.
  • alloy-values.yaml은 네 단계입니다. 파드를 찾고, 붙일 라벨을 고르고, 쿠버네티스 API로 로그를 읽고, Loki로 보냅니다. clustering을 켜면 Alloy 파드끼리 수집 대상을 나눠 맡아 같은 로그를 두 번 보내지 않습니다.
  • discovery.kubernetes는 클러스터의 파드 목록을 가져오고, discovery.relabel은 파드 정보 가운데 namespace, pod, app처럼 고른 것만 라벨로 남깁니다. 라벨을 아무거나 늘리면 안 되는 이유는 라벨 값 하나하나가 스트림 하나가 되기 때문입니다. 요청 경로처럼 값의 가짓수가 많은 것을 라벨로 올리면 스트림이 폭증하는데, 이것을 라벨 카디널리티 문제라고 합니다.
  • loki.source.kubernetes는 쿠버네티스 API로 파드 로그를 읽어 옵니다. 노드의 파일을 직접 읽지 않아서 특별한 권한이 필요 없습니다. loki.write는 읽은 로그를 Loki 앞단의 입구인 loki-gateway 주소로 보냅니다.

④ 세기sum by (app) (count_over_time({namespace=~"journal|apps"}[5m]))줄 수를 메트릭처럼. 그래프 · 알림에 쓴다
PromQL과 모양이 같다: {라벨}로 고르고, [5m] 창으로 세고, sum by로 묶는다. 다른 점은 본문을 거르고(②) 꺼내는(③) 단계가 있다는 점이다.
따라하기 ①에서 연 Explore의 Code 모드에 입력한다. 로그 질의는 줄 목록, 세기 질의는 Options → Type: Instant로 두면 숫자로 나온다 · 실습 가이드 10 로그 10-5 섹션 참고81/83
  • LogQL은 네 단계로 씁니다. 좁히고, 거르고, 꺼내고, 셉니다.
  • ① 좁히기는 라벨 셀렉터로 스트림을 고르는 단계입니다. 모든 질의가 여기서 시작하고, 색인을 쓰므로 빠릅니다. ② 거르기는 |=, |~, !=로 본문에 어떤 문자열이 있는 줄만 남깁니다.
  • 예를 들어 != "health"를 붙이면 헬스 체크 줄을 빼고 볼 수 있습니다. 거르기를 파서보다 앞에 두면 파싱할 줄이 줄어들어 질의가 빨라집니다.
  • ③ 꺼내기는 파서로 본문의 필드를 꺼냅니다. JSON 로그는 | json, 액세스 로그는 | pattern으로 자리를 맞춥니다. <_>는 버리는 자리이고 <status>처럼 이름을 주면 그 값이 필드가 됩니다. 뒤에 | __error__=""를 붙여 파싱에 실패한 줄을 뺍니다.
  • 처리 시간 dur로 거를 때는 단위가 마이크로초라 0.5초는 500000입니다. 줄 끝의 줄바꿈 때문에 비교 앞에 | label_format dur=`{{ trim .dur }}`를 넣고 | dur > 500000을 붙입니다.
  • ④ 세기는 count_over_time으로 줄 수를 세고 sum by로 묶습니다. PromQL과 모양이 같고, 본문을 거르고 꺼내는 단계가 더 있다는 점만 다릅니다. 로그 질의는 줄 목록으로, 세기 질의는 Type을 Instant로 두면 숫자로 나옵니다.
  • [5m]은 최근 5분 동안이라는 창입니다. 5분 안에 들어온 줄 수를 세고, sum by (app)으로 앱별로 합칩니다.
