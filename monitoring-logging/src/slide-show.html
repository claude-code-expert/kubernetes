01POD IP

Kubernetes 네트워크의 기본 단위는 Pod다

Pod마다 고유한 IP 하나를 갖는다.

클러스터 안의 다른 Pod에서 이 IP로 직접 접근할 수 있다. 그리고 Pod의 IP는 노드의 IP가 아니라 Pod 자체의 주소다.

Pod → Pod 통신에 NAT가 개입하지 않는 것이 Kubernetes 네트워크 모델의 약속이다.
order-api
app:8080
Pod IP · 172.22.0.12
Pod = 네트워크 기본 단위5/71
  • 복습: 일반적인 Pod는 자신의 IP로 다른 Pod와 통신한다.
  • 서로 다른 노드에 있어도 Pod IP로 통신할 수 있어야 한다는 것이 Kubernetes 네트워크 모델.
  • IP 할당과 실제 통신 경로는 CNI 플러그인이 구성한다.

01CNI

Pod IP와 통신 경로를 실제로 만드는 것이 CNI다

CNI는 Container Network Interface의 약자.

Kubernetes 자체가 Pod 네트워크를 구현하지 않는다. 대신 CNI 표준을 따르는 플러그인이 노드마다 실행되어 IP 배정과 경로 세팅을 맡는다.

① IPAM

Pod에 클러스터에서 겹치지 않는 IP를 할당한다.

② 인터페이스

veth pair를 만들어 Pod 네트워크 네임스페이스와 호스트를 연결한다.

③ 라우팅

같은 노드, 다른 노드, 외부로 나가는 경로를 세팅한다.

CNI = Pod IP · 통신 경로 구현자9/71
- CNI는 컨테이너 네트워크를 설정하는 플러그인 규격. - kubelet의 요청을 받은 컨테이너 런타임이 CNI를 호출해 Pod IP와 통신 경로를 구성한다. - Calico·Cilium은 이 규격을 구현한 플러그인이다. zzzz

02DEFINITION

Service의 한 문장 정의

Service는 동적으로 변하는 Pod 집합 앞에 안정적인 DNS 이름과 가상 IP를 제공하는 Kubernetes 리소스다.

다른 모든 Service 관련 개념(ClusterIP, NodePort, LoadBalancer, EndpointSlice, kube-proxy)은 이 한 줄에서 파생된다.

오늘 발표의 중심 문장12/71
  • Pod가 바뀌어도 클라이언트는 같은 Service 이름으로 호출한다.
  • 일반적인 ClusterIP Service는 DNS 이름과 가상 IP를 제공한다.
  • selector는 대상 Pod를 고르고, EndpointSlice는 실제 접속 대상 목록을 담는다.

02SELECTOR

Service는 Pod를 이름으로 나열하지 않는다.

  name: api
spec:
  selector:
    app: api
  ports:
    - port: 80
      targetPort: 8080
selector = 현재 대상 조건15/71
  • 복습: selector는 Pod 이름 대신 label로 대상을 고른다.
  • app: api가 붙은 Pod가 늘거나 줄어도 Service 정의를 매번 바꿀 필요가 없다.
  • 새 Pod도 같은 label을 가지면 Service의 연결 대상에 포함된다.
02ENDPOINT SLICE

실제 endpoint 목록은 EndpointSlice가 관리한다

selector에 매칭되는 Pod IP와 준비 상태가 저장되는 곳.

  • Kubernetes 컨트롤러가 selector를 watch해 자동 갱신.
  • 과거 Endpoints의 확장판. 여러 slice로 나눠 대규모에서도 효율.
  • kube-proxy, Cilium 등은 이걸 watch해 라우팅 규칙을 만든다.
kind: EndpointSlice
metadata:
  labels:
    kubernetes.io/service-name: api
endpoints:
  - addresses: [172.22.0.12]
    conditions: {ready: true}
  - addresses: [172.22.1.24]
    conditions: {ready: true}
  - addresses: [172.23.0.31]
    conditions: {ready: false}
Service selector → EndpointSlice → Pod IP16/71
  • 복습: EndpointSlice에는 Service의 접속 대상 IP와 준비 상태가 담긴다.
  • 대상이 많아지면 여러 Slice에 나눠 관리한다.
  • kube-proxy·Cilium이 이 정보를 보고 전달 규칙을 갱신한다. 패킷이 EndpointSlice를 통과하는 구조는 아니다.
  • 일반적인 전달에서는 준비된 대상을 사용한다.

03WHY GATEWAY

Gateway API는 두 가지 한계를 푼다

한계 1

annotation 의존

header 매칭, traffic split, protocol 확장 같은 요구가 표준 API 필드가 아니라 컨트롤러별 annotation으로 흩어졌다.

한계 2

역할 혼재

인프라 팀이 관리하는 진입 게이트웨이와 앱 팀이 관리하는 라우팅 규칙이 하나의 리소스에 섞였다.

Gateway API의 방향: 표현력을 표준 필드로 끌어올리고, 리소스를 역할별로 분리한다.
Ingress의 successor31/71
  • 문제 하나: header 조건이나 트래픽 분배를 컨트롤러마다 다르게 설정해야 했다.
  • 문제 둘: 진입점·TLS를 관리하는 운영팀과 앱 경로를 관리하는 개발팀의 설정이 섞여 있었다.
  • Gateway API는 고급 라우팅을 표준 필드로 표현하고, 담당 팀에 맞게 리소스를 나눈다.

04INGRESS RULE

ingress 정책을 한 줄씩 해석한다

kind: NetworkPolicy
spec:
  podSelector:
    matchLabels:
      app: api          # 이 정책의 대상
  policyTypes: [Ingress]
  ingress:
    - from:
        - podSelector:
            matchLabels:
              app: frontend  # 허용 출처
      ports:
        - port: 8080
          protocol: TCP

모든 다른 출처, 모든 다른 포트, UDP.

  • 예시는 frontend Pod가 api Pod의 TCP 8080으로 들어오는 요청을 허용한다.

04LIMITS

NetworkPolicy는 L3/L4 중심이고 CNI가 적용한다

한계 1

L3/L4만

IP, port, protocol 수준만 표현할 수 있다. HTTP path, method, header는 표준으로 안 됨.

한계 2

CNI 의존

실제 차단은 CNI 플러그인이 한다. NetworkPolicy를 지원하지 않는 CNI를 쓰면 정책을 만들어도 효과가 없다.

L7 정책이나 도메인 기반 egress가 필요하면?
Cilium toFQDNs, Istio AuthorizationPolicy 등 CNI/Mesh 확장이 답이다.
표준의 경계 인식47/71
  • 표준 NetworkPolicy는 IP·포트·프로토콜 중심. HTTP path·method·header는 다루지 않는다.
  • HTTP 조건은 CNI 확장이나 Mesh의 L7 정책으로 처리한다.
  • 실제 정책 적용은 CNI가 맡는다. 지원하지 않는 CNI에서는 리소스를 만들어도 차단되지 않는다.

권장 표현
  • Ingress는 stable이지만 새 기능 개발은 Gateway API로 이동했습니다.
  • Gateway API는 Ingress의 successor이며 역할 분리와 표현력을 개선합니다.
  • Gateway API는 Mesh의 설정 API로도 쓰일 수 있으며, Mesh 자체와 대체 관계가 아닙니다.
  • Istio Ambient는 Istio Sidecar의 대안이며 요구사항에 따라 고릅니다.
  • Cilium은 L3/L4에서 eBPF, L7에서는 Envoy와 결합합니다.
정확한 언어가 학습을 돕는다69/71
  • Ingress API의 유지와 ingress-nginx 프로젝트의 종료는 구분.
  • Gateway API와 Mesh는 함께 쓸 수 있다. 둘 중 하나만 고르는 관계가 아니다.
  • Ambient가 항상 Sidecar보다 좋거나, Cilium이 모든 L7 기능을 eBPF만으로 처리하는 것은 아니다.
  • API의 역할과 구현체의 기능·지원 범위를 나눠 설명한다.

Q1

Ingress를 유지할까, Gateway API로 넘어갈까?

필요 기능과 팀 역할, 컨트롤러 유지보수 상태, 전환 위험을 기준으로 답한다.

Gateway에서 90:10으로 나누면 내부 결제 버전도 나뉠까?

외부 주문 라우팅과 내부 결제 라우팅의 연결 대상과 실행 지점을 구분한다.

Q3

Mesh를 도입한다면 Istio Sidecar와 Istio Ambient 중 어느 쪽?

Pod 수, L7 사용 정도, 성숙도 요구, 운영 부담을 비교한다.

Q4

mTLS가 정상인데 요청이 거절되면 무엇을 확인할까?

workload identity, 인가 정책, L7 집행 위치, 실제 access log를 대조한다.
