02

쿠버네티스 메트릭은 누가 만드는가

같은 파드의 메모리를 세 곳이 각각 보고한다. 출처를 구분해 두면 숫자가 서로 어긋날 때 어디가 잘못됐는지 바로 짚을 수 있다.

개념 · 3.4 쿠버네티스 메트릭 개요 · 3.5 어떤 메트릭을 모니터링하나?{{PG}}
  • 1장 끝에서 남긴 두 질문에 답하는 장이다. 이 메트릭은 어떤 구성요소가 만드는가, kubectl top 과 프로메테우스의 값은 같은가.
  • 책 3.4는 cAdvisor, 메트릭 서버, kube-state-metrics 세 가지를 소개한다. 여기서는 말로 구분하지 않고 실제 메트릭 이름과 실측값으로 구분한다.
  • 책 3.5는 무엇을 모니터링할지 4계층으로 나눈다. 계층마다 실제 메트릭 이름을 붙인다.

02WHAT TO WATCH · 책 3.4

구성요소마다 볼 메트릭 하나와 그 값이 나빠질 때 생기는 일

위치구성요소대표 메트릭이 값이 나빠지면
컨트롤 플레인API 서버apiserver_request_duration_secondsAPI 요청 처리가 느려져 kubectl·컨트롤러가 모두 느려진다
컨트롤 플레인etcdetcd_disk_wal_fsync_duration_seconds디스크 쓰기 확정이 늦어져 API 서버 전체가 느려진다
컨트롤 플레인스케줄러scheduler_pending_pods노드를 배정받지 못한 파드가 쌓인다
컨트롤 플레인컨트롤러 매니저workqueue_depth처리 대기 작업이 쌓여 replicas 변경 같은 반영이 늦어진다
노드kubelet (cAdvisor)container_memory_working_set_bytes컨테이너 메모리가 limit에 닿으면 OOM 킬로 재시작된다
노드kube-proxykubeproxy_sync_proxy_rules_duration_seconds서비스 규칙 갱신이 늦어져 새 파드로 트래픽이 늦게 간다
노드CoreDNScoredns_dns_request_duration_seconds이름 조회가 느려져 서비스 간 호출 전체가 느려진다
노드파드 (앱)http_server_requests_seconds사용자 요청의 처리율·에러·지연(RED)이 나빠진다
모든 구성요소가 자기 메트릭을 프로메테우스 형식으로 직접 제공한다. 컨트롤 플레인이 느려지면 클러스터 전체가, 노드 구성요소가 느려지면 그 노드의 파드가 영향을 받는다.
책 3.4: 클러스터와 애플리케이션을 정상 가동하려면 이 모든 컴포넌트를 빠짐없이 모니터링해야 한다{{PG}}
  • 표를 위에서부터 한 행씩 읽는다. 구성요소가 하는 일, 대표 메트릭, 그 값이 나빠지면 사용자에게 어떤 증상으로 나타나는지.
  • API 서버: 요청 처리 시간 분포. kubectl 명령, 컨트롤러, kubelet 모두 API 서버를 거치므로 여기가 느리면 모든 것이 느리다.
  • etcd: WAL(Write-Ahead Log) fsync 시간 = 쓰기를 디스크에 확정하는 시간. etcd는 확정 뒤에 응답하므로 디스크가 느리면 API 서버가 기다린다. 책 3.5가 클러스터 컴포넌트에서 콕 집어 "etcd 레이턴시"를 꼽는 이유.
  • 스케줄러: 아직 노드를 못 받은 파드 수. 계속 0보다 크면 노드에 자리가 없거나 스케줄러에 문제가 있다.
  • 컨트롤러 매니저: 컨트롤러별 작업 큐 길이. 쌓이면 "replicas 3으로 바꿨는데 파드가 늦게 뜬다" 같은 증상이 된다.
  • kubelet: 안에 든 cAdvisor가 컨테이너 사용량을 낸다. working set 메모리가 limit에 닿으면 커널이 컨테이너를 죽인다.
  • kube-proxy: 서비스 → 파드 규칙(iptables 등)을 다시 쓰는 데 걸리는 시간. 늦어지면 새로 뜬 파드로 트래픽이 늦게 간다.
  • CoreDNS: DNS 응답 시간. 서비스끼리는 이름으로 부르므로 여기가 느리면 모든 호출 앞에 지연이 붙는다.
  • 파드(앱): 앱이 직접 내는 메트릭. order-api는 http_server_requests_seconds 로 RED를 계산한다.
  • 표의 메트릭 이름은 모두 실습 클러스터 프로메테우스에서 조회되는 것을 확인했다(2026-09-26).

사용량은 cAdvisor가 재고, 두 길로 나간다

{{FIG:ch03-fig6-three-sources.svg}}
metrics-server는 새로 재지 않는다. kubelet이 잰 값을 읽어 전달할 뿐이다{{PG}}
  • 위 경로: metrics-server가 각 kubelet의 /metrics/resource 에서 CPU·메모리를 15초마다(--metric-resolution=15s 기본값) 읽어 메모리에 최근값만 둔다. API 서버의 metrics.k8s.io 로 kubectl top, HPA, VPA가 가져간다.

02CADVISOR · 책 3.4.1

cAdvisor: 컨테이너가 실제로 얼마나 쓰는지 잰다

# 프로메테우스에 order-api 메모리를 묻는다
container_memory_working_set_bytes{
  namespace="apps", container="order-api"}
# 결과
order-api-8556fcb49b-7gv2m   174Mi
order-api-8556fcb49b-ctm7c   183Mi

파드 접미사와 값은 환경마다 다르다.

메트릭뜻
container_memory_
working_set_bytes		지금 실제로 붙잡고 있는 메모리. OOM 킬 판정에 쓰이는 값
container_cpu_
usage_seconds_total		CPU를 쓴 누적 초. rate()로 감싸야 초당 사용량(코어)이 된다
container_network_
receive_bytes_total		받은 네트워크 바이트 누적
이름이 container_로 시작하면 cAdvisor에서 온 값이다.
책 3.4.1: cAdvisor는 모든 컨테이너 메트릭의 진실 공급원이다{{PG}}
  • 출력은 실측이다. 명령은 curl로 프로메테우스 HTTP API를 부르는 형태지만 핵심은 질의문 한 줄이다.
  • working_set 은 캐시처럼 커널이 언제든 회수할 수 있는 메모리를 뺀 값이라, 컨테이너가 지금 실제로 필요한 메모리에 가장 가깝다. kubelet의 축출 판단과 OOM 판정도 이 값을 기준으로 한다.
  • CPU 예: rate(container_cpu_usage_seconds_total[2m]) 결과가 0.0037이면 초당 3.7밀리코어를 쓰고 있다는 뜻.

02METRICS SERVER · 책 3.4.2

metrics-server는 오토스케일링 전용이다

# 등록된 메트릭 API 확인
kubectl get apiservices | grep metrics
# 결과
v1beta1.metrics.k8s.io  kube-system/metrics-server  True
kubectl top pod -n apps
NAME                        CPU(cores)  MEMORY(bytes)
order-api-8556fcb49b-7gv2m  5m          174Mi
order-api-8556fcb49b-ctm7c  4m          182Mi

하는 일

각 kubelet에서 CPU·메모리를 15초마다 읽어 최근값 하나만 메모리에 둔다. 이를 metrics.k8s.io로 제공한다.

쓰는 쪽

HPA · VPA · kubectl top. 공식 README는 "모니터링 데이터의 출처로 쓰지 말라"고 적는다.

책 3.4.2: 메트릭 서버는 리소스 메트릭 API의 표준 구현체다{{PG}}
  • apiservices 출력은 실습 클러스터 실측(2026-09-26). 등록된 메트릭 API는 metrics.k8s.io 하나뿐이다. 커스텀·외부 메트릭 API는 어댑터를 설치해야 생긴다.
  • kubectl top 출력은 실측이다.
  • metrics-server README Caution: 오토스케일링 목적 전용이며 모니터링 솔루션으로 메트릭을 넘기거나 모니터링의 주 데이터 출처로 쓰면 안 된다. 모니터링에는 kubelet /metrics/resource 를 직접 수집하라고 안내한다.
  • 기본 수집 주기는 --metric-resolution=15s. 최소 10초.
  • 프로메테우스 타깃 목록에 metrics-server는 없다. 둘은 서로 독립된 경로다.

02CUSTOM METRICS · 책 3.4.2

CPU·메모리 말고 다른 값으로도 스케일링할 수 있다

API 그룹무엇을 담나누가 제공하나HPA에서 쓰는 예
metrics.k8s.io파드·노드의 CPU·메모리metrics-serverCPU 사용률 70% 유지
custom.metrics.k8s.io쿠버네티스 오브젝트에 붙은 메트릭어댑터(prometheus-adapter 등)파드당 초당 요청 수 100 유지

# HPA 스펙 일부: 외부 메트릭(큐 길이)으로 스케일링
- type: External
  external:
    metric:
      name: queue_messages_ready
      selector:
        matchLabels: {queue: worker_tasks}
    target: {type: AverageValue, averageValue: 30}
책 3.4.2: 프로메테우스는 커스텀 메트릭 기반 HPA를 쓸 수 있게 한 최초의 커스텀 메트릭 어댑터였다. API가 표준화된 덕분에 CPU·메모리 외에도 큐 크기 같은 값으로 스케일링할 수 있게 됐다.
API는 표준으로 고정하고, 값을 채우는 구현체만 바꿔 끼운다{{PG}}
  • 코드는 쿠버네티스 공식 HPA 문서의 External 메트릭 예시다. worker_tasks 큐의 대기 메시지가 파드당 평균 30건이 되도록 파드 수를 조절한다.
  • 실습 클러스터에는 어댑터가 없어서 custom·external API가 등록돼 있지 않다. 앞 슬라이드의 apiservices 출력이 그 확인이다.
  • 어댑터를 쓰면 "CPU는 한가한데 큐가 쌓이는" 서비스도 수요에 맞춰 늘릴 수 있다. CPU만으로 스케일링할 때의 한계를 푸는 방법이다.

02ANSWER 2 · 같은 값인가

kubectl top과 프로메테우스는 같은 kubelet에서 읽는다

KUBECTL TOP · metrics-server 
order-api-…-7gv2m   5m   174Mi
order-api-…-ctm7c   4m   182Mi

15초마다 읽은 최근값 하나. 한 시간 전 값은 물어볼 곳이 없다.

PROMETHEUS · cAdvisor 
order-api-…-7gv2m        174Mi
order-api-…-ctm7c        183Mi

30초마다 긁어 3일치를 쌓는다. 어제 같은 시각과 비교할 수 있다.

값은 사실상 같다. 둘 다 kubelet이 cgroup에서 잰 값을 읽기 때문이다. 1Mi 차이는 읽은 시점의 차이다. 다른 것은 보관이다. 지난 일을 되짚으려면 프로메테우스가 필요하다.
질문 ②: kubectl top의 값과 프로메테우스의 값은 같은가{{PG}}
  • 둘 다 실측이다. 같은 파드, 거의 같은 시각.
  • 발표 전날(2026-09-26) 실습 클러스터에서 다시 재 보니 두 값이 238Mi · 248Mi로 정확히 같았다. 파드 이름과 값은 재배포마다 달라진다.
  • 차이가 크게 나면 의심할 것: metrics-server가 오래된 값을 들고 있는지(kubectl top 이 멈춰 있는지), 프로메테우스 질의가 다른 컨테이너(예: 사이드카)까지 합치고 있는지.
  • HPA가 파드를 늘린 뒤 "그때 왜 늘었는지"를 되짚으려면 kubectl get hpa 를 주기적으로 손으로 기록해야 한다. metrics-server는 기록을 남기지 않기 때문이다.

02DRILL DOWN · 책 3.5

파드가 Pending일 때 노드에서 컴포넌트로 좁혀 가는 순서

단계메트릭 · 명령이렇게 판단한다
증상kube_pod_status_phase{phase="Pending"}0보다 크면 배치되지 못한 파드가 있다. ①로 간다
① 노드kube_node_status_allocatable 대 requests 합남은 자리가 파드 requests보다 작으면 원인은 노드 부족. 자리가 있으면 ②로 간다
② 스케줄러up{job="kube-scheduler"}0이면 스케줄러가 멈춰 있다. 1이면 아래 줄을 본다
scheduler_pending_pods{queue="unschedulable"}늘고 있으면 스케줄러는 시도했지만 맞는 노드가 없다(노드 셀렉터·taint·어피니티 조건)
② API 서버apiserver_request_duration_seconds느리면 배치 결과 기록이 늦어진다. etcd 쓰기 지연을 이어서 본다
원인 확인kubectl describe pod <이름>FailedScheduling 이벤트 메시지가 이유를 그대로 알려 준다
노드에 자리가 있는데도 Pending이면 문제는 노드가 아니라 배치를 결정하는 쪽(스케줄러)이나 결정을 기록하는 쪽(API 서버·etcd)에 있다.
노드 → 스케줄러 → API 서버·etcd → 이벤트{{PG}}
  • ① 노드에서 "사용률"이 아니라 "requests 합"을 보는 이유: 스케줄러는 실제 사용량이 아니라 requests로 자리를 계산한다. 노드 CPU가 20%만 쓰여도 requests가 꽉 차 있으면 새 파드는 들어가지 못한다.
  • 노드에 자리가 있는데도 Pending이면 컴포넌트로 옮겨 간다. 배치를 결정하는 스케줄러가 먼저, 그 결정을 기록하는 API 서버·etcd가 다음이다.
  • up{job="kube-scheduler"} 는 프로메테우스가 스케줄러를 긁는 데 성공했는지(1) 실패했는지(0)다. 스케줄러 프로세스가 죽어 있으면 0이 된다.
  • scheduler_pending_pods 의 queue="unschedulable" 은 스케줄러가 시도했지만 조건에 맞는 노드를 찾지 못해 보류한 파드 수다. 자리는 있어도 노드 셀렉터·taint·어피니티가 맞지 않으면 여기로 간다.
  • kubectl describe pod 이벤트 예: "0/3 nodes are available: 3 Insufficient cpu." 또는 "node(s) had untolerated taint". 메트릭으로 좁힌 뒤 마지막 원인은 이벤트로 확인한다.
  • 메트릭 이름은 실습 클러스터 프로메테우스에서 조회되는 것을 확인했다(scheduler_pending_pods 의 queue 라벨: active, backoff, gated, incomplete, pending, unschedulable).
