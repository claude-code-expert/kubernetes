02

쿠버네티스 메트릭은 누가 만드는가

같은 파드의 메모리를 세 곳이 각각 보고한다. 출처를 구분해 두면 숫자가 서로 어긋날 때 어디가 잘못됐는지 바로 짚을 수 있다.

개념 · 3.4 쿠버네티스 메트릭 개요 · 3.5 어떤 메트릭을 모니터링하나?{{PG}}
  • 2장은 쿠버네티스 메트릭을 누가 만드는지 봅니다.
  • 같은 파드의 메모리를 cAdvisor, metrics-server, kube-state-metrics 세 곳이 각각 보고합니다. 출처를 구분해 두면 숫자가 서로 어긋날 때 어디가 잘못됐는지 바로 짚을 수 있습니다.

용어 ① 클러스터 구성요소

용어원어 · 풀 네임뜻
컨트롤 플레인Control plane클러스터 전체를 관리하는 구성요소 묶음. API 서버·etcd·스케줄러·컨트롤러 매니저
API 서버kube-apiserver모든 요청(kubectl, 컨트롤러, kubelet)이 거치는 입구. 오브젝트를 읽고 쓴다

스케줄러kube-scheduler새 파드를 어느 노드에 놓을지 고른다. 기준은 요청량(requests)이다
컨트롤러 매니저kube-controller-manager선언된 상태(예: replicas 3)와 실제 상태를 비교해 맞춘다
kubeletkubelet (노드 에이전트)각 노드에서 파드를 실행·감시하는 에이전트. 안에 cAdvisor가 들어 있다
컨테이너 런타임Container runtimekubelet의 지시를 받아 컨테이너를 실제로 만들고 실행한다
kube-proxykube-proxy서비스 주소로 온 트래픽을 뒤의 파드로 보내는 규칙을 노드에 설정한다
CoreDNSCoreDNS클러스터 안의 DNS. 서비스 이름을 IP로 바꿔 준다
컨트롤 플레인 4개 + 노드 구성요소 4개 + 파드{{PG}}
  • 먼저 클러스터 구성요소 용어입니다. 컨트롤 플레인은 클러스터 전체를 관리하는 묶음으로, API 서버, etcd, 스케줄러, 컨트롤러 매니저 네 개입니다.
  • API 서버는 모든 요청이 거치는 입구이고, etcd는 오브젝트 상태를 저장하는 데이터베이스입니다. 스케줄러는 새 파드를 어느 노드에 놓을지 requests를 기준으로 고르고, 컨트롤러 매니저는 선언한 상태와 실제 상태를 맞춥니다.
  • requests는 파드가 "최소 이만큼은 쓰겠다"고 매니페스트에 미리 적어 두는 CPU와 메모리 양입니다. 스케줄러는 실제 사용량이 아니라 이 값을 노드의 남은 자리와 비교합니다. 컨트롤러 매니저의 예를 들면, replicas를 3으로 적었는데 파드가 2개만 떠 있으면 하나를 더 만듭니다.
  • 노드에는 kubelet, 컨테이너 런타임, kube-proxy, CoreDNS가 있습니다. 컨테이너 런타임은 containerd처럼 컨테이너를 실제로 만들고 실행하는 프로그램입니다. kubelet은 파드를 실행하고 감시하는 에이전트이고, 안에 cAdvisor가 들어 있습니다.
  • kube-proxy는 서비스 주소로 온 트래픽을 파드로 보내는 규칙을 만들고, CoreDNS는 서비스 이름을 IP로 바꿔 줍니다.

용어 ② 메트릭 수집기

용어원어 · 풀 네임뜻
cAdvisorContainer Advisorkubelet 안에 내장된 수집기. 노드의 컨테이너별 CPU·메모리·디스크·네트워크 사용량을 잰다
cgroupControl group (리눅스 커널 기능)프로세스 묶음마다 CPU·메모리·I/O를 제한하고 사용량을 기록하는 커널 기능. 컨테이너 격리의 기반
statfsstatfs (리눅스 시스템 콜)파일시스템의 전체·남은 용량을 조회하는 커널 호출. cAdvisor가 디스크 사용량을 잴 때 쓴다
metrics-serverKubernetes Metrics Server각 kubelet에서 CPU·메모리 최근값을 모아 API 서버로 제공한다. 기록은 남기지 않는다
kube-state-metricskube-state-metrics (KSM)API 서버의 오브젝트 상태(replicas, 파드 단계 등)를 읽어 메트릭으로 바꾼다. 사용량은 재지 않는다
cAdvisor는 사용량을, KSM은 선언된 상태를, metrics-server는 사용량의 최근값을 다룬다{{PG}}
  • 다음은 메트릭 수집기 용어입니다. cAdvisor는 kubelet 안에 들어 있는 수집기로, 컨테이너별 CPU, 메모리, 디스크, 네트워크 사용량을 잽니다.
  • cAdvisor가 읽는 곳이 cgroup입니다. 리눅스 커널이 프로세스 묶음마다 자원을 제한하고 사용량을 기록하는 기능입니다. 디스크 용량은 statfs라는 커널 호출로 잽니다.
  • metrics-server는 각 kubelet에서 CPU와 메모리 최근값만 모아 API 서버로 넘기고, 기록은 남기지 않습니다. kube-state-metrics는 replicas나 파드 단계 같은 오브젝트 상태를 메트릭으로 바꿉니다.
  • 정리하면 cAdvisor는 사용량, kube-state-metrics는 선언된 상태, metrics-server는 사용량의 최근값을 다룹니다.

용어 ③ 메트릭 API와 사용처

용어원어 · 풀 네임뜻

리소스 메트릭 APIResource Metrics API · metrics.k8s.io파드·노드의 CPU·메모리 사용량. metrics-server가 제공한다
HPAHorizontal Pod Autoscaler수평 파드 오토스케일러. 메트릭을 보고 파드 개수를 늘리거나 줄인다

리소스 메트릭 API는 API 집계 계층을 거쳐 API 서버에 붙는다{{PG}}
  • 세 번째는 메트릭 API와 그 사용처입니다. API 집계 계층은 외부 서버의 API를 쿠버네티스 API의 일부처럼 붙이는 구조이고, APIService 오브젝트로 등록합니다.
  • 예를 들어 metrics-server를 설치하면 APIService가 하나 등록되고, 그 뒤로는 kubectl top이 API 서버에 요청해도 뒤에서 metrics-server가 답합니다. 사용자는 metrics-server의 주소를 몰라도 됩니다.
  • 이 강의에서 쓰는 메트릭 API는 리소스 메트릭 API입니다. 파드와 노드의 CPU, 메모리 사용량을 담고 metrics-server가 제공합니다.
  • 이 메트릭은 HPA와 VPA가 사용합니다. HPA는 파드 개수를 조정합니다. 예를 들어 평균 CPU 사용률이 목표보다 높으면 파드를 늘리고, 낮으면 줄입니다. VPA는 파드 하나의 크기를 조정합니다. 실제 사용량에 비해 requests가 너무 작거나 크게 잡혀 있으면 맞는 값으로 바꿉니다.

02CADVISOR · 책 3.4.1

cAdvisor: 컨테이너가 실제로 얼마나 쓰는지 잰다

어디에 넣나 브라우저 localhost:9090(Prometheus 화면) → 위쪽 Query 입력칸에 붙여 넣고 Execute → 아래 Table 탭. Prometheus는 4장에서 설치하고, 이 질의는 4장 따라하기 ② 세 출처에서 직접 쳐 본다.

# order-api 파드별 메모리 (MiB)
sum by (pod) (
  container_memory_working_set_bytes{
    namespace="apps", container="order-api"}
) / 1024 / 1024
# Table 탭에 나오는 결과
{pod="order-api-77bf967968-bj8c6"}  208.0078125
{pod="order-api-77bf967968-msnb6"}  217.1484375

파드 이름 끝부분과 값은 환경마다 다르다.

메트릭뜻
container_memory_
working_set_bytes		지금 실제로 사용 중인 메모리. 노드 메모리가 모자랄 때 kubelet이 내보낼(축출) 파드를 고르는 기준. limit에 가까우면 OOM 킬 위험
container_cpu_
usage_seconds_total		CPU를 쓴 누적 초. rate()로 감싸야 초당 사용량(코어)이 된다
container_network_
receive_bytes_total		받은 네트워크 바이트 누적
이름이 container_로 시작하면 cAdvisor에서 온 값이다.
메트릭 전체 목록: cAdvisor · prometheus.md · 실습 가이드 04 Prometheus 4-4 섹션 참고{{PG}}
  • cAdvisor는 컨테이너가 실제로 얼마나 쓰는지 잽니다. 왼쪽 코드는 PromQL, 즉 프로메테우스에 보내는 질의입니다. 터미널이 아니라 브라우저의 Prometheus 화면, localhost:9090의 Query 입력칸에 붙여 넣고 Execute를 누르면 아래 Table 탭에 결과가 나옵니다. Prometheus는 4장에서 설치하니, 지금은 모양만 보고 4장 따라하기에서 직접 쳐 봅니다.
  • 질의를 안쪽부터 읽으면, container_memory_working_set_bytes 중에서 apps 네임스페이스의 order-api 컨테이너만 고르고, sum by (pod)로 파드별로 합친 뒤, 1024로 두 번 나눠 바이트를 MiB로 바꿉니다. 결과는 파드 두 개가 각각 약 208MiB, 217MiB를 쓰고 있다는 뜻입니다.
  • container_memory_working_set_bytes는 지금 실제로 사용 중인 메모리입니다. 노드 메모리가 모자랄 때 kubelet이 내보낼 파드를 고르는 기준입니다. 이렇게 내보내는 것을 축출이라고 하고, 축출된 파드는 다른 노드에서 다시 뜹니다. 또 이 값이 limit에 가까우면 OOM 킬 위험이 있습니다.
  • container_cpu_usage_seconds_total은 CPU를 쓴 누적 초라서 rate()로 감싸야 초당 사용량이 됩니다. rate()는 계속 늘기만 하는 누적값이 일정 시간 동안 초당 얼마씩 늘었는지 계산하는 함수입니다. CPU라면 결과가 0.5일 때 0.5코어를 쓰고 있다는 뜻입니다. 이름이 container_로 시작하면 cAdvisor에서 온 값입니다.

02METRICS SERVER · 책 3.4.2

metrics-server는 오토스케일링 전용이다

# 터미널에서: 등록된 메트릭 API 확인
kubectl get apiservices | grep metrics
# 결과
v1beta1.metrics.k8s.io  kube-system/metrics-server  True
# 터미널에서
kubectl top pod -n apps
NAME                        CPU(cores)  MEMORY(bytes)
order-api-77bf967968-bj8c6  6m          208Mi
order-api-77bf967968-msnb6  6m          217Mi

하는 일

각 kubelet에서 CPU·메모리를 15초마다 읽어 최근값 하나만 메모리에 둔다. 이를 metrics.k8s.io로 제공한다.

사용처

HPA · VPA · kubectl top. 대시보드 · 알림용으로는 쓰지 않는다. 지난 값을 저장하지 않기 때문이다(공식 README의 주의 문구). 그런 용도는 프로메테우스가 kubelet에서 직접 수집한다.

제공 항목: Resource metrics pipeline (CPU · 메모리뿐) · 실습 가이드 04 Prometheus 4-3 섹션 참고{{PG}}
  • metrics-server는 오토스케일링 전용입니다. 첫 명령 kubectl get apiservices는 API 서버에 등록된 API 목록을 봅니다. 결과의 v1beta1.metrics.k8s.io 줄은 "Metrics API, 즉 파드와 노드의 CPU·메모리 사용량을 조회하는 주소로 요청이 오면 kube-system의 metrics-server가 답한다"는 등록 정보입니다. 끝의 True는 그 연결이 지금 동작한다는 뜻입니다.
  • 두 번째 명령 kubectl top pod가 바로 이 Metrics API를 씁니다. kubectl이 API 서버에 apps 네임스페이스 파드들의 사용량을 요청하면, API 서버는 직접 답하지 않고 위에서 본 등록 정보에 따라 요청을 metrics-server로 넘깁니다. metrics-server가 들고 있던 최근값을 돌려주면 kubectl이 표로 출력합니다. 그래서 metrics-server가 없으면 kubectl top은 Metrics API를 쓸 수 없다는 오류를 냅니다.
  • 표에는 order-api 파드 두 개의 CPU와 메모리가 나옵니다. CPU의 6m은 6밀리코어, 즉 0.006코어이고 1000m이 코어 하나입니다. 메모리는 208Mi, 217Mi입니다.
  • metrics-server는 각 kubelet에서 15초마다 CPU와 메모리를 읽어서, 파드마다 지금 값 하나만 메모리에 둡니다. 지난 값은 남기지 않습니다. 그래서 "지금 얼마나 쓰나"는 답할 수 있지만 "어제 이 시각에는 얼마였나"나 "지난 1시간 그래프"는 답할 수 없습니다.
  • 이 값을 사용하는 것은 셋입니다. HPA는 CPU 사용량이 목표를 넘으면 파드 개수를 늘리고, VPA는 파드 하나가 요청하는 CPU와 메모리 양을 조정하고, kubectl top은 지금 사용량을 터미널에 보여 줍니다. 셋 다 지금 값 하나만 있으면 되는 일입니다.
  • 그래서 metrics-server 공식 문서는 이 값을 모니터링 도구의 데이터 출처로 쓰지 말라고 적어 둡니다. 대시보드나 알림을 만들려고 metrics-server에서 수집하지 말고, 원래 데이터가 있는 kubelet에서 직접 가져가라는 뜻입니다. 이 실습의 프로메테우스가 바로 그렇게 kubelet의 cAdvisor 경로에서 직접 수집합니다.

02KUBE-STATE-METRICS · 책 3.4.3

메트릭 전체 목록: kube-state-metrics · docs/metrics · 실습 가이드 04 Prometheus 4-5 섹션 참고{{PG}}
  • kube-state-metrics는 오브젝트 상태를 묻는 질문마다 답하는 메트릭이 있습니다.
  • 파드가 몇 개 배포됐고 몇 개가 대기 중인지는 kube_pod_info와 kube_pod_status_phase로 봅니다. 디플로이먼트가 의도한 개수만큼 떠 있는지는 spec_replicas와 status_replicas_available을 비교합니다.
  • 업데이트가 끝났는지는 generation 두 값을 비교합니다. metadata.generation은 디플로이먼트 스펙을 바꿀 때마다 1씩 오르는 번호이고, observed_generation은 컨트롤러가 처리를 마친 번호라서, 두 값이 같으면 마지막 변경이 반영된 것입니다. 그 밖에 노드 상태(Ready, MemoryPressure 같은 condition), 파드에 나눠 줄 수 있는 자원 양(allocatable), 새 파드를 받지 않도록 막아 둔 노드(unschedulable), 잡의 시작과 실패도 각각 메트릭이 있습니다.
  • order-api는 replicas 2, CPU requests 0.2이고, 파드마다 Running 값이 1입니다. phase 메트릭은 그 단계에 있으면 1, 아니면 0인 값이라서, 1을 더하면 Running 파드 수가 됩니다. 모두 매니페스트에 적은 값이고, kube-state-metrics는 자원을 재지 않습니다. 이름이 kube_로 시작하면 이 출처입니다.

02ANSWER 2 · 같은 값인가

kubectl top과 프로메테우스는 같은 kubelet에서 읽는다

KUBECTL TOP · metrics-server 
order-api-…-bj8c6   6m   208Mi
order-api-…-msnb6   6m   217Mi

15초마다 읽은 최근값 하나. 한 시간 전 값은 조회할 방법이 없다.

PROMETHEUS · cAdvisor 
{pod="order-api-…-bj8c6"}  208.0
{pod="order-api-…-msnb6"}  217.1

30초마다 수집해 3일치를 쌓는다. 어제 같은 시각과 비교할 수 있다.

두 값의 차이는 1Mi 안팎이다. 둘 다 kubelet이 cgroup에서 잰 값을 읽기 때문이다. 그 차이는 읽은 시점과 반올림 차이다. 다른 것은 보관이다. 지난 일을 되짚으려면 프로메테우스가 필요하다.
질문 ②: kubectl top의 값과 프로메테우스의 값은 같은가 · 실습 가이드 04 Prometheus 4-3 · 4-4 섹션 참고{{PG}}
  • kubectl top과 프로메테우스는 같은 kubelet에서 값을 읽습니다.
  • 왼쪽 kubectl top은 208Mi, 217Mi이고, 오른쪽 프로메테우스는 같은 파드가 208.0, 217.1(MiB)입니다. 차이는 1Mi 안팎으로, 읽은 시점과 반올림 차이입니다. 오른쪽 값은 앞에서 본 cAdvisor 질의를 Prometheus 화면 Query 입력칸에 넣어 얻은 결과입니다.
  • 다른 것은 보관입니다. kubectl top은 15초마다 읽은 최근값 하나라 한 시간 전 값은 없습니다. 프로메테우스는 30초마다 수집해 3일치를 쌓아서 어제 같은 시각과 비교할 수 있습니다. 지난 일을 되짚으려면 프로메테우스가 필요합니다.

  • 확인할 항목을 노드, 클러스터 컴포넌트, 애드온, 애플리케이션 네 계층으로 나눴습니다.
  • 노드는 CPU 사용률, 메모리 여유, 네트워크 송수신량, 디스크 여유 공간을 node_ 메트릭으로 봅니다. 클러스터 컴포넌트는 etcd 디스크 쓰기 지연과 API 서버 요청 지연을 봅니다.
  • 애드온은 기본 구성요소 말고 따로 설치하는 것이라 설치한 것에 따라 다릅니다. 클러스터 오토스케일러는 배치하지 못한 파드 수, 인그레스 컨트롤러는 요청 수를 봅니다. 클러스터 오토스케일러는 파드를 놓을 자리가 모자라면 노드 자체를 늘리는 도구이고, 인그레스 컨트롤러는 클러스터 밖에서 들어오는 HTTP 요청을 서비스로 나눠 주는 입구입니다.
  • 애플리케이션은 컨테이너 메모리, CPU, 네트워크 에러와, Spring Boot 같은 프레임워크가 제공하는 요청 수와 지연을 봅니다.
