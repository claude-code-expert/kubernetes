스택을 설치하고, 정상인 화면을 읽는다

kube-prometheus-stack을 설치한 뒤 무엇이 보이면 정상인지 확인한다. Prometheus와 Grafana의 화면을 어떤 질문에 어느 메뉴로 답하는지 익힌다.

실습 · 3.7 프로메테우스를 이용한 쿠버네티스 모니터링{{PG}}

04BEFORE INSTALL · 클러스터 설정

컨트롤 플레인 메트릭은 클러스터를 만들 때 열어 둔다

labs/kind-cluster.yaml (일부)

kubeadmConfigPatches:
  - |
    kind: ClusterConfiguration
    controllerManager:
      extraArgs:
        - {name: bind-address, value: "0.0.0.0"}
    scheduler:
      extraArgs:
        - {name: bind-address, value: "0.0.0.0"}
    etcd:
      local:
        extraArgs:
          - {name: listen-metrics-urls,
             value: "http://0.0.0.0:2381"}
  - |
    kind: KubeProxyConfiguration
    metricsBindAddress: "0.0.0.0:10249"

왜 필요한가

kubeadm 기본값은 네 구성요소(컨트롤러 매니저 · 스케줄러 · etcd · kube-proxy)가 메트릭 포트를 127.0.0.1에만 연다. 다른 노드에 있는 프로메테우스는 닿지 못한다.

열면 보이는 것

etcd 디스크 지연(etcd_disk_wal_fsync_duration_seconds), 스케줄 대기(scheduler_pending_pods), 컨트롤러 작업 큐(workqueue_depth). 2장 "컴포넌트" 계층의 메트릭이다.

운영 클러스터에서는 이 포트를 노드 방화벽 · 네트워크 정책으로 막고 인증을 건다.
전체 파일: labs/kind-cluster.yaml{{PG}}
  • kubeadmConfigPatches 는 kind가 kubeadm에 넘기는 설정에 덧붙는다. 쿠버네티스 1.37의 kubeadm 설정(v1beta4)은 extraArgs를 이름·값 목록으로 받는다. 예전 문서의 map 형식(bind-address: "0.0.0.0")과 다르다.
  • 이 설정 없이 설치하면 Target health에 DOWN 6개(controller-manager · etcd · scheduler · kube-proxy ×3)가 뜨고 에러는 connection refused다. 이 장 끝 Q&A에서 다룬다.
  • 실측: 이 파일로 만든 클러스터는 설치 직후 타깃 28개가 모두 up이다.

04BEFORE INSTALL · 값 파일

차트 기본값 대신 보존 기간·저장소·배치를 정한다

labs/helm/kps-values.yaml (일부)

prometheus:
  prometheusSpec:
    nodeSelector: {workload: observability}
    scrapeInterval: 30s    retention: 3d    retentionSize: 4GB    storageSpec:
      volumeClaimTemplate:
        spec:
          resources: {requests: {storage: 8Gi}}grafana:
  adminPassword: obs-study
  grafana.ini:
    plugins: {preinstall_auto_update: false}  resources:
    limits: {memory: 1Gi}
값왜
scrapeInterval 30s짧을수록 해상도가 오르고 저장량도 오른다. 15초면 저장량이 두 배
retention 3d · 4GB둘 중 먼저 닿는 쪽에서 오래된 데이터를 지운다. 며칠 전 장애까지 되짚을지가 이 값
storageSpec 8Gi없으면 emptyDir. 파드가 재시작되면 쌓은 메트릭이 전부 사라진다
nodeSelector관측 스택을 한 노드에 모은다. 관측 대상이 앓을 때 같이 앓지 않게
preinstall_auto_updateGrafana가 기동할 때 내장 플러그인을 업데이트하지 않게 한다
Grafana 메모리 1Gi대시보드 몇 개를 열면 850Mi 안팎까지 쓴다(실측)
전체 파일: labs/helm/kps-values.yaml{{PG}}
  • 값 파일 전체에는 Alertmanager 라우팅 · 수신자(6장), Grafana 대시보드 사이드카(6장), Loki 데이터소스(7장)도 들어 있다. 여기서는 설치와 저장에 관한 줄만 올렸다.
  • preinstall_auto_update: Grafana 13은 기동하면서 이미지에 든 플러그인을 최신판으로 올리려 한다. 이 이미지는 플러그인 폴더가 읽기 전용이라 업데이트가 실패하고, 그 과정에서 Prometheus · Loki 플러그인이 내려간 채 남는다(실측). 끄면 이미지에 든 버전을 그대로 쓴다.
  • Grafana 관리자 비밀번호는 실습용으로 값 파일에 적었다. 운영이라면 시크릿으로 넘긴다.

04HOW TO USE · Prometheus

Prometheus 화면은 질문에 따라 메뉴를 고른다

메뉴이런 질문일 때사용법
Status → Target health수집이 되고 있나? 어디가 끊겼나?묶음(scrape pool)별 n / n up. 필터 Unhealthy로 문제 있는 것만. DOWN 행에 마지막 에러가 보인다
Query → Table지금 값은 얼마인가?질의 결과의 최신값 한 줄씩. 라벨 전체가 보여 어느 파드 · 노드인지 확인할 때
Query → Graph언제부터 변했나? 추세는?시간 범위를 고르고 선으로 본다. rate() · histogram_quantile() 결과를 볼 때
Alerts지금 울리는 알림은?규칙별 inactive · pending · firing(6장)
Status → Rule health알림 규칙이 로드됐나?규칙 그룹과 평가 상태 · 마지막 평가 시각
Status → Configuration실제로 어떤 설정으로 긁나?오퍼레이터가 만든 scrape_configs 전체(3장)
열기: kubectl -n monitoring port-forward svc/kps-kube-prometheus-stack-prometheus 9090:9090 → http://localhost:9090{{PG}}
  • Query 입력칸은 자동 완성이 된다. 메트릭 이름 앞부분(container_, kube_, node_)만 쳐도 후보가 나온다.
  • Table은 "지금", Graph는 "흐름". 장애를 볼 때는 Graph로 언제부터인지 먼저 잡고, Table로 어느 대상인지 좁힌다.
  • 터미널에서 같은 질의를 치는 방법(HTTP API + jq)은 실습 가이드에 있다. 발표 화면에서는 브라우저를 쓴다.

04FOLLOW ALONG ② · 세 출처

따라하기 ② 같은 파드를 세 출처로 본다

#명령 · 질의볼 것 (기준값)
1kubectl top pod -n appsmetrics-server: 파드 2개, 메모리 150~200Mi
2Query: container_memory_working_set_bytes{namespace="apps", container="order-api"} / 1024 / 1024cAdvisor: 1번과 같은 값(MiB)
3Query: {__name__=~"kube_deployment_spec_replicas|kube_deployment_status_replicas_available", namespace="apps"}kube-state-metrics: 의도 2 · 실제 2
4Query: container_memory_working_set_bytes{namespace="apps", container="order-api"} (Table)라벨 namespace · pod · node · image가 붙어 있다
이름이 container_로 시작하면 cAdvisor, kube_로 시작하면 kube-state-metrics, kubectl top은 metrics-server. 쓰임새: 지금 값은 kubectl top, 지난 흐름은 cAdvisor, 의도와 실제의 차이는 kube-state-metrics.
2장의 세 출처를 실제 값으로 확인한다{{PG}}
  • 기준값(실측): cAdvisor 199.1Mi / 156.5Mi, kubectl top 198Mi / 156Mi. 둘 다 kubelet이 cgroup에서 잰 working set을 읽으므로 같다.
  • kube-state-metrics는 사용량을 재지 않는다. 매니페스트에 적은 값(replicas 2, requests.cpu 0.2)과 실제 상태(available 2, Running)를 메트릭으로 바꾼다.
  • 전체 시계열 수는 count({__name__=~".+"})로 본다. 앱을 연결하기 전 약 6만(실측 64,440 · 66,551). 상위 다섯 중 넷 이상이 _bucket(히스토그램)이다.
04HOW TO USE · Grafana

Grafana 기본 대시보드는 질문별로 하나씩 연다

대시보드이런 질문일 때볼 패널
Kubernetes / Compute Resources / Pod이 파드가 자원을 얼마나 쓰나? 한도에 가까운가?Memory Usage (WSS) · requests · limits 점선, CPU Throttling
Kubernetes / Compute Resources / Namespace (Pods)네임스페이스 안에서 누가 많이 쓰나?파드별 CPU · 메모리 표
Node Exporter / USE Method / Cluster클러스터 전체가 모자라나?CPU · 메모리의 Utilisation(사용률)과 Saturation(포화도)
etcdAPI가 느린데 저장소 탓인가?Disk sync duration(WAL fsync), RPC rate
Kubernetes / API serverAPI 서버가 에러를 내나?Availability, 요청 수 · 에러 · 지연
위 표 순서가 2장의 "앱 → 노드 → 컴포넌트"로 내려가는 순서다. 대시보드를 새로 만들기 전에 이미 있는 것부터 연다.
열기: kubectl -n monitoring port-forward svc/kps-grafana 3000:80 → http://localhost:3000 (admin / obs-study){{PG}}
  • 차트가 대시보드 20여 개를 기본으로 넣는다. Dashboards 검색칸에 이름 일부를 치면 된다.
  • 위쪽 드롭다운(namespace · pod)으로 대상을 고르고, 오른쪽 위 시간 범위를 Last 30 minutes 정도로 둔다.
  • 실측 사례: 실습 중 클러스터 두 개를 동시에 띄웠던 10분 동안 USE Method에서 메모리 사용률이 거의 100%, 메이저 페이지 폴트가 초당 8만 건, CPU 포화도가 1500%까지 올랐다. CPU 사용률은 80%에서 멈췄다. 사용률만 보면 놓치는 것을 포화도가 보여 준 예다(1장 USE).
  • Compute Resources / Pod의 메모리 패널에는 requests(빨간 점선)와 limits(주황 점선)가 함께 그려진다. 사용량(cAdvisor)과 매니페스트 값(kube-state-metrics)이 한 그래프에 겹친다.

  • 이미 만든 클러스터에서 고치려면 컨트롤 플레인 노드의 /etc/kubernetes/manifests 파일을 고치고 kube-proxy ConfigMap을 고친다(실습 가이드 Q&A). 클러스터를 다시 만드는 편이 간단하다.
  • Grafana 플러그인 문제 확인: kubectl -n monitoring logs deploy/kps-grafana -c grafana | grep 'Failed to install plugin' → pluginId=prometheus … read-only file system.
  • OOMKilled 확인: kubectl -n monitoring get pod -l app.kubernetes.io/name=grafana -o jsonpath='{.items[0].status.containerStatuses[?(@.name=="grafana")].lastState.terminated.reason}'
