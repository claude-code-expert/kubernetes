스택을 설치하고, 정상인 화면을 읽는다

kube-prometheus-stack을 설치하고 수집 대상 28개가 모두 up인지 확인한다. order-api 메모리 값 하나를 kubectl top · Prometheus · Grafana 세 곳에서 찾아 같은 값인지 비교한다.

실습 · 3.7 프로메테우스를 이용한 쿠버네티스 모니터링{{PG}}
  • 4장부터는 따라하기입니다. kind 클러스터에 kube-prometheus-stack을 설치합니다. kube-prometheus-stack은 프로메테우스, Alertmanager, Grafana, 그리고 node-exporter와 kube-state-metrics 같은 수집기를 한 번에 설치하는 Helm 차트입니다.
  • 설치가 끝나면 수집 대상 28개가 모두 up인지 확인합니다. 이어서 order-api 메모리 값 하나를 kubectl top, Prometheus, Grafana 세 곳에서 찾아 같은 값인지 비교합니다.

  • 설치와 확인에 쓰는 용어입니다. Helm은 여러 매니페스트를 한 묶음으로 설치하고 업그레이드하는 도구이고, 그 묶음을 차트라고 부릅니다. 차트를 클러스터에 설치한 한 벌이 릴리스이고, 여기서는 이름을 kps로 붙입니다.
  • 값 파일은 차트의 기본값을 덮어쓰는 설정 파일로, -f로 넘깁니다. 포트 포워드는 내 PC의 포트를 클러스터 안 서비스로 이어 주는 임시 터널이고, PVC는 파드가 재시작돼도 데이터가 남도록 저장 공간을 요청하는 것입니다.
  • 타깃은 프로메테우스가 긁어 가는 주소 하나이고, 상태는 up 또는 down입니다. up 메트릭은 타깃마다 하나씩 생기며, 마지막 수집이 성공하면 1, 실패하면 0입니다.
  • 바인드 주소는 프로그램이 연결을 받는 주소입니다. 127.0.0.1이면 자기 노드 안에서만, 0.0.0.0이면 어디서든 접근할 수 있습니다.

04BEFORE INSTALL · 클러스터 설정

컨트롤 플레인 메트릭은 클러스터를 만들 때 열어 둔다

labs/kind-cluster.yaml (일부)

kubeadmConfigPatches:
  - |
    kind: ClusterConfiguration
    controllerManager:
      extraArgs:
        - {name: bind-address, value: "0.0.0.0"}
    scheduler:
      extraArgs:
        - {name: bind-address, value: "0.0.0.0"}
    etcd:
      local:
        extraArgs:
          - {name: listen-metrics-urls,
             value: "http://0.0.0.0:2381"}
  - |
    kind: KubeProxyConfiguration
    metricsBindAddress: "0.0.0.0:10249"

왜 필요한가

kubeadm 기본값은 네 구성요소(컨트롤러 매니저 · 스케줄러 · etcd · kube-proxy)가 메트릭 포트를 127.0.0.1에만 연다. 다른 노드에 있는 프로메테우스는 닿지 못한다.

열면 보이는 것

etcd 디스크 지연(etcd_disk_wal_fsync_duration_seconds), 스케줄 대기(scheduler_pending_pods), 컨트롤러 작업 큐(workqueue_depth). 2장 "컴포넌트" 계층의 메트릭이다.

운영 클러스터에서는 이 포트를 노드 방화벽 · 네트워크 정책으로 막고 인증을 건다.
전체 파일: labs/kind-cluster.yaml · 실습 가이드 01 클러스터 1-1 섹션 참고{{PG}}
  • 설치 전에 클러스터 설정부터 봅니다. kind는 내부적으로 kubeadm이라는 도구로 클러스터를 만드는데, kubeadm은 기본으로 컨트롤러 매니저, 스케줄러, etcd, kube-proxy의 메트릭 포트를 127.0.0.1에만 엽니다. 127.0.0.1은 자기 노드 안에서만 닿는 주소라서, 다른 노드에 있는 프로메테우스는 이 메트릭을 가져가지 못합니다.
  • 그래서 kind 설정 파일의 kubeadmConfigPatches로 kubeadm 설정 일부를 덮어씁니다. kubeadmConfigPatches는 kind가 클러스터를 만들 때 kubeadm에 넘길 설정을 고치는 항목이고, extraArgs는 각 구성요소를 실행할 때 붙일 인자를 더하는 칸입니다.
  • 컨트롤러 매니저와 스케줄러는 bind-address를 0.0.0.0으로, etcd는 메트릭을 여는 주소인 listen-metrics-urls를 0.0.0.0:2381로, kube-proxy는 metricsBindAddress를 0.0.0.0:10249로 바꿉니다. 0.0.0.0은 어느 쪽에서 오는 연결이든 받겠다는 뜻입니다.
  • 이렇게 열면 컴포넌트 계층의 메트릭이 보입니다. etcd_disk_wal_fsync_duration_seconds는 etcd가 쓰기 기록을 디스크에 확정하는 데 걸린 시간, scheduler_pending_pods는 아직 노드를 배정받지 못한 파드 수, workqueue_depth는 컨트롤러가 처리하지 못하고 쌓아 둔 일의 수입니다. 운영 클러스터에서는 이 포트를 방화벽이나 네트워크 정책으로 막고 인증을 겁니다.

04BEFORE INSTALL · 값 파일

차트 기본값 대신 보존 기간·저장소·배치를 정한다

labs/helm/kps-values.yaml (일부)

prometheus:
  prometheusSpec:
    nodeSelector: {workload: observability}
    scrapeInterval: 30s    retention: 3d    retentionSize: 4GB    storageSpec:
      volumeClaimTemplate:
        spec:
          resources: {requests: {storage: 8Gi}}grafana:
  adminPassword: obs-study
  grafana.ini:
    plugins: {preinstall_auto_update: false}  resources:
    limits: {memory: 1Gi}
값왜
scrapeInterval 30s짧을수록 해상도가 오르고 저장량도 오른다. 15초면 같은 기간의 샘플 수가 두 배
retention 3d · 4GB둘 중 먼저 닿는 쪽에서 오래된 데이터를 지운다. 며칠 전 장애까지 되짚을지가 이 값
storageSpec 8Gi없으면 emptyDir. 파드가 재시작되면 쌓은 메트릭이 전부 사라진다
nodeSelector관측 스택을 한 노드에 모은다. 관측 대상 앱이 자원을 다 써 버려도 관측 도구가 같이 느려지지 않게
preinstall_auto_updateGrafana가 기동할 때 내장 플러그인을 업데이트하지 않게 한다
Grafana 메모리 1Gi대시보드 몇 개를 열면 850Mi 안팎까지 쓴다(실측)
전체 파일: labs/helm/kps-values.yaml · 실습 가이드 03 스택 설치 3-1 섹션 참고{{PG}}
  • 차트 기본값 대신 우리가 정한 값입니다. prometheusSpec은 프로메테우스 서버 설정을 적는 부분입니다. scrapeInterval은 수집 주기로 30초입니다. 짧을수록 그래프가 촘촘해지지만 저장량도 늘어서, 15초로 줄이면 같은 기간의 샘플 수가 두 배가 됩니다.
  • retention은 데이터를 며칠 보관할지, retentionSize는 디스크를 얼마까지 쓸지입니다. 3일 또는 4GB 중 먼저 닿는 쪽에서 오래된 데이터부터 지웁니다. 며칠 전 장애까지 되짚어 볼 수 있느냐가 이 값으로 정해집니다.
  • storageSpec의 volumeClaimTemplate은 프로메테우스 파드에 붙일 저장 공간 요청서, 즉 PVC를 자동으로 만드는 틀이고 크기는 8Gi입니다. 이것을 지정하지 않으면 emptyDir을 씁니다. emptyDir은 파드와 수명이 같은 임시 디스크라서 파드가 재시작되면 쌓은 메트릭이 모두 사라집니다.
  • nodeSelector는 라벨이 맞는 노드에만 파드를 올리는 설정입니다. workload=observability 라벨이 붙은 노드 한 대에 관측 스택을 모아서, 관측 대상 앱이 자원을 다 써 버려도 관측 도구가 같이 느려지지 않게 합니다.
  • Grafana는 관리자 비밀번호를 obs-study로 정합니다. preinstall_auto_update는 Grafana가 기동할 때 내장 플러그인의 새 버전을 인터넷에서 받아 오는 기능인데, 이것이 실패하면 Prometheus 데이터소스 플러그인까지 내려가서 false로 끕니다. 메모리 한도 1Gi는 Grafana가 이 값을 넘으면 강제로 재시작된다는 뜻이고, 대시보드 몇 개를 열면 850Mi 안팎까지 쓰기 때문에 여유를 둔 값입니다.

04FOLLOW ALONG ①-1 · 클러스터와 앱

따라하기 ①-1 클러스터를 만들고 앱 두 개를 올린다

접속터미널. 작업 폴더는 저장소의 monitoring-logging/로그인없음메뉴없음. 모두 터미널 명령
#명령통과 기준
1kind create cluster --config labs/kind-cluster.yaml체크 표시 7개, 마지막에 Set kubectl context to "kind-obs"
2kubectl apply -f https://github.com/kubernetes-sigs/metrics-server/releases/download/v0.9.0/components.yaml
kubectl -n kube-system patch deployment metrics-server --type=json \
  -p='[{"op":"add","path":"/spec/template/spec/containers/0/args/-","value":"--kubelet-insecure-tls"}]'
kubectl -n kube-system rollout status deployment/metrics-server --timeout=180s		successfully rolled out. 이게 없으면 뒤의 세 출처 확인에서 kubectl top이 실패한다
3docker build -t journal-api:v1 labs/apps/journal-api
docker build -t order-api:v1 labs/apps/order-api		docker images에 journal-api:v1 · order-api:v1 두 줄. 첫 빌드는 수 분
4kind load docker-image journal-api:v1 order-api:v1 --name obs오류 없이 끝난다(이미지 2개 × 노드 3대 = 6줄)
5kubectl apply -f labs/k8s/journal.yaml -f labs/k8s/order-api.yaml
kubectl -n journal rollout status deploy/journal-api --timeout=180s
kubectl -n apps rollout status deploy/order-api --timeout=240s		successfully rolled out 두 줄. journal-api 3개 · order-api 2개
6kubectl -n apps port-forward svc/order-api 18082:8080 >/dev/null 2>&1 &
kubectl -n journal port-forward svc/journal-api 18083:8080 >/dev/null 2>&1 &
sleep 2; curl -s localhost:18082/api/orders; echo		{"data":[],"message":"조회 성공",…}. 이 두 port-forward는 5 · 6 · 7장에서 계속 쓰니 끄지 않는다
설정 파일: kind-cluster.yaml · order-api.yaml · 실습 가이드 01 클러스터 · 02 앱 섹션 참고{{PG}}
  • 첫 번째 따라하기는 클러스터를 만들고 앱 두 개를 올리는 단계입니다. 모두 터미널에서 monitoring-logging 폴더를 기준으로 실행합니다.
  • 1번은 앞에서 본 설정 파일로 kind 클러스터를 만듭니다. 체크 표시 7개가 나오고 마지막에 kind-obs 컨텍스트가 설정되면 됩니다. 컨텍스트는 kubectl이 어느 클러스터에 명령을 보낼지 정하는 이름입니다.
  • 2번은 metrics-server 설치입니다. metrics-server는 kubectl top이 보여 주는 CPU와 메모리 최근값을 모으는 구성요소입니다. kubectl patch로 실행 인자에 --kubelet-insecure-tls를 한 줄 더합니다. kind의 kubelet은 스스로 서명한 인증서를 써서 metrics-server가 검증하지 못하기 때문에, 실습에서는 검증을 건너뜁니다. rollout status는 새 파드가 모두 준비될 때까지 기다렸다가 결과를 알려 주는 명령이고, successfully rolled out이 나오면 됩니다.
  • 3번은 두 앱의 이미지를 빌드합니다. -t는 이미지에 이름과 태그를 붙이는 옵션입니다. 4번 kind load는 그 이미지를 kind 노드 안으로 직접 복사합니다. kind 노드는 내 PC의 Docker 이미지를 볼 수 없어서, 레지스트리에 올리는 대신 이렇게 넣습니다. 이미지 두 개가 노드 세 대에 들어가므로 여섯 줄이 나옵니다.
  • 5번은 앱 배포입니다. journal-api 3개, order-api 2개가 뜨고 successfully rolled out 두 줄이 나오면 됩니다.
  • 6번은 두 앱을 내 PC의 18082, 18083 포트로 여는 port-forward입니다. 뒤에 붙은 >/dev/null 2>&1 &는 출력을 버리고 명령을 뒤에서 계속 돌려서, 터미널을 바로 다시 쓸 수 있게 합니다. curl로 order-api가 응답하면 통과이고, 이 두 port-forward는 뒤의 장에서도 계속 쓰므로 그대로 둡니다.
04FOLLOW ALONG ①-2 · 스택 설치

따라하기 ①-2 kube-prometheus-stack 설치

접속터미널. 작업 폴더 monitoring-logging/로그인없음메뉴없음. 모두 터미널 명령
#명령통과 기준
1helm repo add prometheus-community https://prometheus-community.github.io/helm-charts
helm repo update prometheus-community		has been added(이미 있으면 already exists), Update Complete
2kubectl label node obs-worker2 workload=observability
kubectl get nodes -L workload		WORKLOAD 열이 obs-worker2에만 observability
3helm upgrade --install kps prometheus-community/kube-prometheus-stack \
  -n monitoring --create-namespace --version 89.2.2 \
  -f labs/helm/kps-values.yaml --wait --timeout 12m		출력에 STATUS: deployed
4kubectl -n monitoring wait --for=condition=Ready pod --all --timeout=5mcondition met 8줄
5kubectl -n monitoring get pods,pvc파드 8개 Running(node-exporter 3), PVC 8Gi Bound
설정 파일: kps-values.yaml · 실습 가이드 03 스택 설치 3-1 · 3-2 섹션 참고{{PG}}
  • 이어서 모니터링 스택을 설치합니다. 1번은 차트 저장소 등록입니다. helm repo add는 차트를 받아 올 저장소 주소를 이름으로 등록하고, helm repo update는 그 저장소의 최신 차트 목록을 받아 옵니다. has been added나 already exists, 그리고 Update Complete가 나오면 됩니다.
  • 2번은 obs-worker2 노드에 workload=observability 라벨을 붙입니다. 값 파일의 nodeSelector가 이 라벨을 보고 관측 스택을 이 노드에 올립니다. get nodes의 -L workload는 그 라벨 값을 열로 보여 주는 옵션이고, WORKLOAD 열에 obs-worker2만 observability로 나오면 됩니다.
  • 3번은 helm upgrade --install로 설치합니다. 처음이면 설치하고 이미 있으면 업그레이드하는 명령이라 다시 쳐도 오류가 나지 않습니다. --create-namespace는 monitoring 네임스페이스가 없으면 만들고, --version은 차트 버전을 89.2.2로 고정해 같은 결과가 나오게 합니다. -f는 앞에서 본 값 파일을 넘기고, --wait --timeout 12m은 리소스가 모두 준비될 때까지 최대 12분 기다립니다. 출력에 STATUS: deployed가 나오면 됩니다.
  • 4번 kubectl wait는 monitoring의 모든 파드가 Ready 상태가 될 때까지 기다립니다. 파드 하나가 준비될 때마다 condition met이 한 줄씩 나와서 8줄이 됩니다.
  • 5번에서 파드 8개가 Running인지 봅니다. node-exporter는 노드마다 하나씩 뜨므로 3개입니다. PVC가 Bound라는 것은 요청한 8Gi 저장 공간이 실제 디스크에 연결됐다는 뜻이고, 여기까지 보이면 설치가 끝난 것입니다.

  • Prometheus 화면은 질문에 따라 메뉴를 고릅니다. 수집이 되고 있는지, 어디가 끊겼는지는 Status의 Target health에서 봅니다. 타깃은 scrape pool, 즉 같은 수집 설정으로 묶인 묶음별로 n / n up이라고 나옵니다. 위쪽 두 번째 칸 Filter by target health에서 DOWN을 고르면 끊긴 타깃만 남고, 그 행에 마지막 수집 에러가 나옵니다.
  • 지금 값이 얼마인지는 Query의 Table 탭에서 봅니다. 질의 결과의 최신값을 한 줄씩 보여 주고 라벨이 모두 보여서, 어느 파드, 어느 노드인지 확인할 때 씁니다. 언제부터 변했는지, 추세가 어떤지는 Graph 탭에서 시간 범위를 고르고 선으로 봅니다. 초당 증가량을 구하는 rate()나 분위수를 구하는 histogram_quantile() 결과처럼 시간에 따라 변하는 값은 Graph로 봅니다.
  • 지금 울리는 알림은 Alerts에서 규칙별 상태로 봅니다. 알림 규칙이 제대로 읽혔는지는 Status의 Rule health에서, 실제로 어떤 설정으로 수집하는지는 Status의 Configuration에서 오퍼레이터가 만든 수집 설정 전체를 봅니다.

  • Grafana는 3000 포트로 열고 localhost:3000에 admin / obs-study로 로그인합니다. 왼쪽 Dashboards에서 검색칸에 이름 일부를 넣어 열고, 대시보드 위쪽 선택칸에서 네임스페이스와 파드를 고르고, 오른쪽 위 시간 범위는 Last 30 minutes, 즉 최근 30분으로 둡니다.
  • 파드 하나가 자원을 얼마나 쓰는지는 Kubernetes / Compute Resources / Pod에서 namespace apps, pod order-api를 고르고 봅니다. Memory Usage (WSS)의 WSS는 working set size로, 앞에서 본 실제로 붙잡은 메모리입니다. 선과 함께 그려지는 점선 두 개가 requests와 limits입니다. requests는 스케줄러가 노드를 고를 때 기준으로 잡는 예약량이고, limits는 넘으면 컨테이너가 강제로 종료되는 상한입니다. CPU Throttling은 CPU limit 때문에 CPU를 덜 받은 비율입니다.
  • 네임스페이스 안에서 누가 많이 쓰는지는 Namespace (Pods) 대시보드의 파드별 표로 봅니다. 클러스터 전체가 모자란지는 Node Exporter / USE Method / Cluster에서 봅니다. Utilisation은 자원을 얼마나 쓰고 있는지, Saturation은 일이 밀려 기다리고 있는지를 보여 줍니다.
  • API가 느린 이유가 저장소인지는 etcd 대시보드의 Disk sync duration으로 봅니다. etcd가 쓰기 기록을 디스크에 확정하는 시간이라 이 값이 길면 모든 쓰기가 늦어집니다. RPC rate는 etcd가 받는 요청 수입니다. API 서버가 에러를 내는지는 Kubernetes / API server의 Availability와 요청 수, 에러, 지연으로 봅니다.
  • 패널마다 선이 그려지면 됩니다. Network Saturation은 드롭된 패킷, etcd의 Peer traffic은 etcd 노드 사이 통신이라 그런 일이 없으면 No data가 정상입니다.
