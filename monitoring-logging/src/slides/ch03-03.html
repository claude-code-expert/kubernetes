여러 출처의 메트릭을 한곳에 모으는 도구를 비교하고, 프로메테우스가 대상을 찾아 긁어 오고 저장하는 구조를 본다.

03WHY PROMETHEUS · 책 3.7

프로메테우스의 라벨에 쿠버네티스 정보가 그대로 붙는다

# 프로메테우스에 저장된 order-api 메모리 시계열 하나의 라벨 (실측, 일부)
container_memory_working_set_bytes{
  namespace="apps",  pod="order-api-77bf967968-g247f",  container="order-api",
  node="obs-worker",  image="docker.io/library/order-api:v1",
  job="kubelet",  metrics_path="/metrics/cadvisor",  instance="172.20.0.2:10250" }

쿠버네티스에서 온 라벨

namespace · pod · container · node. 쿠버네티스에서 쓰던 이름으로 그대로 나눠 본다.

수집 과정에서 붙은 라벨

job(어느 수집 설정인가) · instance(어느 주소에서 긁었나) · metrics_path.

그래서 가능한 질의

"apps 네임스페이스 전체", "obs-worker 노드 위의 컨테이너"처럼 라벨로 골라 합친다.

책 3.7: 프로메테우스는 쿠버네티스의 레이블, 서비스 디스커버리, 메타데이터와 잘 맞는 메트릭 모니터링 도구다 · 실습 가이드 04 Prometheus 4-4 섹션 참고{{PG}}
  • 라벨 세트는 실습 클러스터 프로메테우스에서 조회한 실제 값이다(2026-09-26). id, name, endpoint, service 라벨은 생략했다.
  • 이 라벨들은 서비스 디스커버리가 쿠버네티스 API에서 받아 온 메타데이터를 스크레이프할 때 붙인 것이다. 앱이나 cAdvisor가 직접 "obs-worker"를 아는 게 아니다.
  • 책 3.7: 프로메테우스는 구글 내부 시스템 보그몬(Borgmon)의 키/값 다차원 데이터 모델에서 아이디어를 가져왔고, 쿠버네티스가 레이블을 쓰는 방식과 매우 비슷하다.
03DATA MODEL · 책 3.7

메트릭은 사람이 읽을 수 있는 텍스트로 노출된다

# node-exporter의 /metrics 응답 (실측, 일부)
# HELP node_cpu_seconds_total Seconds the CPUs spent in each mode.
# TYPE node_cpu_seconds_total counter
node_cpu_seconds_total{cpu="0",mode="idle"}   1.76328028e+06
node_cpu_seconds_total{cpu="0",mode="iowait"} 59525.98
node_cpu_seconds_total{cpu="0",mode="irq"}    0
node_cpu_seconds_total{cpu="0",mode="nice"}   0
...
1.76328028e+06 = 1.76328028 × 10⁶ = 1,763,280초(약 20일). 값이 크면 지수 표기로 찍힌다. 프로메테우스는 두 표기를 똑같이 읽는다.
부분뜻
# HELP메트릭 설명
# TYPE메트릭 타입. 여기서는 counter(계속 증가)
이름node_cpu_seconds_total: CPU가 쓴 누적 초
{라벨}cpu 번호 × mode(idle, iowait …) 조합마다 별도 시계열
값긁는 순간의 숫자. 프로메테우스가 시각을 붙여 샘플로 저장
# HELP · # TYPE · 이름{라벨} 값 · node-exporter 수집기 목록: node_exporter · Collectors · 실습 가이드 04. Prometheus 4-6 섹션 참고{{PG}}
  • node-exporter 서비스에 port-forward 한 뒤 curl localhost:9100/metrics 로 받은 실제 응답이다. 책 3.7에 실린 예시와 형식이 같다.
  • 이 텍스트를 내놓기만 하면 무엇이든 프로메테우스 수집 대상이 된다. 쿠버네티스 구성요소, Nginx, Traefik, Istio, Linkerd 등이 이미 이 형식으로 메트릭을 내놓는다(책 3.7).
  • CPU 사용률은 이 counter를 그대로 보지 않고 rate()로 초당 증가량을 구해 계산한다. mode="idle"의 증가율을 1에서 빼면 사용률이다.

03METRIC TYPES

메트릭 타입 4가지와 각각을 읽는 방법

타입값의 성질예읽는 방법
Counter늘기만 한다. 재시작하면 0부터node_cpu_seconds_totalrate()로 초당 증가량을 본다
Gauge오르내린다. 지금 상태node_memory_MemAvailable_bytes값을 그대로 본다. rate()를 쓰지 않는다
Histogram값을 구간(버킷)별로 센 누적 개수http_server_requests_seconds_buckethistogram_quantile()로 P99
Summary앱이 분위수를 미리 계산해 내놓음(order-api는 쓰지 않음)파드끼리 평균 내면 틀린 값
히스토그램은 파드마다 버킷을 합친 뒤 분위수를 계산할 수 있다. 서머리는 이미 계산된 분위수라 합칠 수 없다. 파드가 여러 개인 쿠버네티스에서는 히스토그램을 쓴다.
counter는 rate로, gauge는 그대로, histogram은 histogram_quantile로{{PG}}
  • 프로메테우스 공식 가이드: 늘기만 하는 값은 counter, 오르내리는 값은 gauge. counter는 rate()로 분석하고, gauge는 상태의 스냅숏이라 rate()를 쓰지 않는다.
  • 공식 문서 예: avg(http_request_duration_seconds{quantile="0.95"}) 는 틀렸다(BAD). histogram_quantile(0.95, sum(rate(..._bucket[5m])) by (le)) 가 맞다.
  • order-api의 /actuator/prometheus 에는 http_server_requests_seconds 가 # TYPE ... histogram 으로 나온다(실측). 5장에서 이 버킷으로 P99를 계산한다.

03PULL MODEL

가져오는 방식(pull)은 대상이 죽었는지를 수집 자체로 안다

# 긁기에 성공하면 1, 실패하면 0 (실측)
up{job="order-api", pod="order-api-…-g247f"}  1
up{job="order-api", pod="order-api-…-pjnk8"}  1

얻는 것

대상마다 up 시계열이 자동으로 생긴다. 긁기에 실패하면 0이 된다. 요청이 없는 한가한 앱도 /metrics에는 응답하므로 1이다. push 방식에서는 데이터가 안 오면 죽은 건지 한가한 건지 알 수 없다.

대가 ①

프로메테우스가 대상에 네트워크로 닿아야 한다. 방화벽·네트워크 정책이 막으면 수집이 안 된다.

대가 ②

수십 초 만에 끝나는 배치 잡은 긁으러 갈 때 이미 없다. 이때는 Pushgateway에 값을 남긴다.

대가 ③

30초 간격 샘플이라 요청 하나하나를 세는 과금처럼 100% 정확도가 필요한 용도에는 맞지 않는다.

대상은 메트릭을 보여 주기만 하고, 주기와 목록은 프로메테우스가 정한다{{PG}}
  • up 값은 실습 클러스터에서 조회한 실제 결과다. order-api 파드 두 개 모두 1.
  • 푸시 방식에서는 값이 안 오는 이유가 "앱이 죽었다"인지 "보낼 게 없다"인지 수집 쪽이 구분하지 못한다.
  • 프로메테우스 공식 개요: 신뢰성을 정확도보다 우선한다. 요청별 과금처럼 100% 정확해야 하는 용도에는 권하지 않는다.

03SERVICE DISCOVERY

쿠버네티스 API에서 대상을 찾는 6가지 방법

역할 (role)무엇을 대상으로 만드나주로 쓰는 곳
node노드마다 대상 하나 (kubelet 주소)kubelet · cAdvisor
service서비스의 포트마다 대상 하나서비스 주소로 외부 점검(블랙박스)
pod파드의 컨테이너 포트마다 대상 하나서비스 없이 파드를 직접 긁을 때 (PodMonitor)
endpoints서비스 뒤의 실제 파드 주소마다 대상 하나서비스로 묶인 앱 (ServiceMonitor 기본값)
endpointsliceendpoints와 같고 EndpointSlice API를 쓴다endpoints의 후속. 공식 문서가 전환을 권장
ingress인그레스의 경로마다 대상 하나외부 URL 점검(블랙박스)
대상을 찾을 때 파드의 네임스페이스·이름·라벨이 __meta_kubernetes_* 라벨로 함께 따라온다. 앞에서 본 namespace·pod 라벨은 여기서 옮겨 붙인 것이다.
kubernetes_sd_configs 의 role 값{{PG}}
  • 프로메테우스 공식 설정 문서의 kubernetes_sd_config 역할: endpoints, endpointslice, service, pod, node, ingress.
  • 공식 문서: Endpoints API는 쿠버네티스 1.33부터 사용 중단(deprecated)되어 endpointslice 역할로의 전환을 권한다.
  • 실습 클러스터에서 오퍼레이터가 만든 수집 설정은 ServiceMonitor 마다 role: endpoints 를 쓴다(생성된 설정 파일에서 확인).
  • __meta_ 로 시작하는 라벨은 대상을 고르는 단계에서만 쓰이고 저장 전에 지워진다. 남기고 싶은 것은 relabel 규칙으로 일반 라벨에 옮긴다.

03SERVICEMONITOR · YAML

ServiceMonitor는 세 군데가 맞아야 서비스를 찾는다

ServiceMonitor · 무엇을 긁을지

apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: order-api
  namespace: apps
  labels:
    release: kps                  # ① 프로메테우스가 고르는 라벨spec:
  selector:
    matchLabels:
      app.kubernetes.io/name: order-api # ② 서비스 라벨  namespaceSelector:
    matchNames: [apps]
  endpoints:
    - port: http                # ③ 서비스 포트 이름      path: /actuator/prometheus
      interval: 30s
      scrapeTimeout: 10s

Service · order-api 앞에 있는 서비스

kind: Service
metadata:
  name: order-api
  namespace: apps
  labels:
    app.kubernetes.io/name: order-api # ②spec:
  ports:
    - name: http                # ③      port: 8080

Prometheus 리소스 · 어떤 ServiceMonitor를 읽을지

spec:
  serviceMonitorSelector:
    matchLabels:
      release: kps                # ①
전체 파일: labs/k8s/servicemonitors.yaml · 실습 가이드 06 앱 연결 6-1 섹션 참고{{PG}}
  • ① ServiceMonitor 자신의 라벨 release: kps. 프로메테우스 리소스의 serviceMonitorSelector 가 이 라벨을 가진 ServiceMonitor만 읽는다. 실습 클러스터에서 확인한 값: {"matchLabels":{"release":"kps"}}.
  • ② ServiceMonitor 의 selector 가 서비스의 metadata.labels 와 맞아야 한다. 서비스의 spec.selector(파드를 고르는 쪽)가 아니다.
  • ③ endpoints[].port 는 서비스 포트의 "이름"이다. 8080 같은 숫자를 적으면 맞는 포트가 없어 대상이 생기지 않는다.
  • 셋 중 하나라도 어긋나면 에러 없이 대상이 0개가 된다. 5장에서 일부러 어긋나게 만들어 본다.
  • kps는 helm install 때 붙인 릴리스 이름이다. 차트가 serviceMonitorSelector 를 release: 릴리스이름 으로 설정한다.
  • ServiceMonitor 코드는 저장소 파일에서 주석만 발표용으로 바꿨다. Service는 labs/k8s/order-api.yaml 의 일부.

03GENERATED CONFIG

ServiceMonitor 한 칸이 수집 설정 한 줄로 바뀐다

우리가 적은 것 · ServiceMonitor (일부)

spec:
  selector:
    matchLabels:
      app.kubernetes.io/name: order-api   # A  namespaceSelector:
    matchNames: [apps]                  # B  endpoints:
    - port: http                         # C      path: /actuator/prometheus       # D      interval: 30s                    # E      scrapeTimeout: 10s
오퍼레이터는 서비스 디스커버리(role: endpoints)로 apps 네임스페이스의 대상을 모두 받은 뒤, 조건에 맞는 것만 keep으로 남긴다.

오퍼레이터가 만든 것 · 프로메테우스 설정 (실측, 일부)

- job_name: serviceMonitor/apps/order-api/0
  kubernetes_sd_configs:
  - role: endpoints
    namespaces: {names: [apps]}            # B  scrape_interval: 30s                    # E  scrape_timeout: 10s
  metrics_path: /actuator/prometheus       # D  relabel_configs:
  - action: keep                          # A
    source_labels:
    - __meta_kubernetes_service_label_app_kubernetes_io_name    regex: (order-api);true
  - action: keep                          # C
    source_labels: [__meta_kubernetes_endpoint_port_name]    regex: http
  - source_labels: [__meta_kubernetes_namespace]
    target_label: namespace              # 라벨 붙이기
  - source_labels: [__meta_kubernetes_pod_name]
    target_label: pod
  ... (container · service · job 라벨, 샤딩 규칙)
생성된 전체 설정은 monitoring 네임스페이스의 시크릿에 압축되어 들어 있다 · 실습 가이드 06 앱 연결 6-3 섹션 참고{{PG}}
  • 왼쪽 A~E 한 칸이 오른쪽 같은 글자의 줄로 바뀐다. 오른쪽은 실습 클러스터에서 오퍼레이터가 실제로 만든 설정의 일부다.
  • A selector → 서비스 라벨로 걸러 내는 keep 규칙. 서비스 라벨은 __meta_kubernetes_service_label_… 로 들어온다.
  • B namespaceSelector → 서비스 디스커버리의 namespaces.
  • C port → 서비스 포트 이름으로 걸러 내는 keep 규칙.
  • D path → metrics_path, E interval → scrape_interval.
  • 그 아래 규칙들이 __meta_ 라벨을 namespace · pod · container · service · job 같은 일반 라벨로 옮긴다. 39번 슬라이드에서 본 라벨이 여기서 붙는다.
  • 전체 설정을 직접 보는 명령: kubectl -n monitoring get secret prometheus-kps-kube-prometheus-stack-prometheus -o jsonpath='{.data.prometheus\.yaml\.gz}' | base64 -d | gunzip
