수집 대상 · 형식 · 발견 · 관리 방식{{PG}}
  • 프로메테우스 구조에서 쓰는 용어입니다. 익스포터는 다른 시스템의 상태를 읽어 프로메테우스 형식으로 내놓는 프로그램이고, node-exporter가 대표적입니다.
  • 노출 형식은 메트릭을 HTTP로 보여 주는 텍스트 형식입니다. # HELP 줄에 설명, # TYPE 줄에 타입을 적고, 그 아래에 이름{라벨} 값 줄이 이어집니다. 샘플은 저장의 최소 단위로, 소수점 숫자(float64) 값 하나와 밀리초 단위 시각의 묶음입니다.
  • 서비스 디스커버리는 긁을 대상 목록을 쿠버네티스 API 같은 외부에서 자동으로 받아 오는 기능입니다. 파드가 새로 뜨거나 지워져도 목록을 손으로 고칠 필요가 없습니다. Pushgateway는 금방 끝나는 배치 잡이 값을 밀어 넣어 두는 곳입니다. 예를 들어 새벽에 몇 초 만에 끝나는 백업 잡은 프로메테우스가 긁으러 갈 때 이미 없으니, 끝나기 전에 결과를 Pushgateway에 남겨 둡니다.
  • 오퍼레이터는 소프트웨어의 설치와 설정을 쿠버네티스 리소스로 관리하는 컨트롤러입니다. 이 실습의 프로메테우스 오퍼레이터는 우리가 적은 리소스를 읽어 프로메테우스 설정 파일을 대신 써 줍니다. CRD는 쿠버네티스에 새 리소스 종류를 추가하는 정의로, CRD가 있어서 kubectl get servicemonitor처럼 Deployment와 같은 방식으로 다룰 수 있습니다.
  • ServiceMonitor에는 무엇을 긁을지, PrometheusRule에는 알림 규칙과 기록 규칙을 적습니다. 기록 규칙은 자주 쓰는 계산 결과를 미리 계산해 새 시계열로 저장해 두는 규칙입니다.

03WHY PROMETHEUS · 책 3.7

프로메테우스의 라벨에 쿠버네티스 정보가 그대로 붙는다

어디서 보나 브라우저 localhost:9090(Prometheus 화면) → Query 입력칸에 container_memory_working_set_bytes{namespace="apps", container="order-api"}를 넣고 Execute → Table 탭. 파드마다 아래 같은 줄이 하나씩 나온다.

# Table 탭의 한 줄 (라벨 일부)
container_memory_working_set_bytes{
  namespace="apps",  pod="order-api-77bf967968-g247f",  container="order-api",
  node="obs-worker",  image="docker.io/library/order-api:v1",
  job="kubelet",  metrics_path="/metrics/cadvisor",  instance="172.20.0.2:10250" }

쿠버네티스에서 온 라벨

namespace · pod · container · node. 쿠버네티스에서 쓰던 이름으로 그대로 나눠 본다.

수집 과정에서 붙은 라벨

job(어느 수집 설정인가) · instance(어느 주소에서 긁었나) · metrics_path.

그래서 가능한 질의

"apps 네임스페이스 전체", "obs-worker 노드 위의 컨테이너"처럼 라벨로 골라 합친다.

책 3.7: 프로메테우스는 쿠버네티스의 레이블, 서비스 디스커버리, 메타데이터와 잘 맞는 메트릭 모니터링 도구다 · 실습 가이드 04 Prometheus 4-4 섹션 참고{{PG}}
  • 이 줄은 Prometheus 화면에서 직접 볼 수 있습니다. 브라우저 localhost:9090의 Query 입력칸에 container_memory_working_set_bytes에 namespace="apps", container="order-api" 조건을 붙여 넣고 Execute를 누르면, 아래 Table 탭에 파드마다 한 줄씩 나옵니다. 중괄호 안이 그 시계열에 붙은 라벨 전체이고, 맨 끝 숫자가 바이트 단위 메모리입니다. sum by (pod)처럼 합치는 질의를 쓰면 pod 말고 다른 라벨은 사라지므로, 라벨을 다 보려면 이렇게 합치지 않은 질의를 씁니다.
  • 프로메테우스에 저장된 order-api 메모리 시계열 하나입니다. container_memory_working_set_bytes는 컨테이너가 지금 실제로 쓰고 있는 메모리 바이트 수이고, 메트릭 이름 뒤 중괄호 안이 이 시계열에 붙은 라벨입니다.
  • namespace, pod, container, node는 쿠버네티스에서 온 라벨입니다. 쿠버네티스에서 쓰던 이름 그대로 나눠 볼 수 있습니다.
  • job, instance, metrics_path는 수집 과정에서 붙은 라벨로, 어느 수집 설정이 어느 주소에서 긁었는지를 나타냅니다.
  • 그래서 "apps 네임스페이스 전체", "obs-worker 노드 위의 컨테이너"처럼 라벨로 골라서 합치는 질의가 가능합니다. 예를 들어 sum by (node)로 묶으면 노드별 메모리 합계가 됩니다.
03METRIC TYPES

메트릭 타입 4가지와 각각을 읽는 방법

타입값의 성질예읽는 방법
Counter늘기만 한다. 재시작하면 0부터node_cpu_seconds_totalrate()로 초당 증가량을 본다
Gauge오르내린다. 지금 상태node_memory_MemAvailable_bytes값을 그대로 본다. rate()를 쓰지 않는다
Histogram값을 구간(버킷)별로 센 누적 개수http_server_requests_seconds_buckethistogram_quantile()로 P99
Summary앱이 분위수를 미리 계산해 내놓음(order-api는 쓰지 않음)파드끼리 평균 내면 틀린 값
히스토그램은 파드마다 버킷을 합친 뒤 분위수를 계산할 수 있다. 서머리는 이미 계산된 분위수라 합칠 수 없다. 파드가 여러 개인 쿠버네티스에서는 히스토그램을 쓴다.
counter는 rate로, gauge는 그대로, histogram은 histogram_quantile로{{PG}}
  • 메트릭 타입은 네 가지이고, 타입마다 읽는 방법이 다릅니다.
  • Counter는 늘기만 하고 재시작하면 0부터 다시 셉니다. 누적값은 계속 커지기만 해서 지금 바쁜지 알 수 없으므로 rate()로 봅니다. rate는 최근 일정 구간, 예를 들어 5분 동안 늘어난 양을 초당 값으로 바꾸는 함수입니다. Gauge는 오르내리는 현재 상태라 값을 그대로 봅니다. 예시의 MemAvailable은 지금 새로 쓸 수 있는 메모리 양입니다.
  • Histogram은 값을 구간별로 센 누적 개수입니다. 구간을 버킷이라고 부르고, 0.1초 이하가 몇 건, 0.5초 이하가 몇 건처럼 셉니다. histogram_quantile()은 이 버킷으로 P99 같은 분위수를 계산합니다. P99는 요청 100건 중 가장 느린 1건을 뺀 나머지 99건이 모두 이 시간 안에 끝났다는 뜻입니다. Summary는 앱이 분위수를 미리 계산해서 내놓는 방식입니다.
  • 히스토그램은 파드마다 버킷을 합친 뒤 분위수를 계산할 수 있지만, 서머리는 이미 계산된 분위수라 합칠 수 없습니다. 파드 두 개의 P99를 평균 내도 전체의 P99가 되지 않기 때문입니다. 그래서 파드가 여러 개인 쿠버네티스에서는 히스토그램을 씁니다.

03PULL MODEL

가져오는 방식(pull)은 대상이 죽었는지를 수집 자체로 안다

# 긁기에 성공하면 1, 실패하면 0 (실측)
up{job="order-api", pod="order-api-…-g247f"}  1
up{job="order-api", pod="order-api-…-pjnk8"}  1

얻는 것

대상마다 up 시계열이 자동으로 생긴다. 긁기에 실패하면 0이 된다. 요청이 없는 한가한 앱도 /metrics에는 응답하므로 1이다. push 방식에서는 데이터가 안 오면 죽은 건지 한가한 건지 알 수 없다.

대가 ①

프로메테우스가 대상에 네트워크로 닿아야 한다. 방화벽·네트워크 정책이 막으면 수집이 안 된다.

대가 ②

수십 초 만에 끝나는 배치 잡은 긁으러 갈 때 이미 없다. 이때는 Pushgateway에 값을 남긴다.

대가 ③

30초 간격 샘플이라 요청 하나하나를 세는 과금처럼 100% 정확도가 필요한 용도에는 맞지 않는다.

대상은 메트릭을 보여 주기만 하고, 주기와 목록은 프로메테우스가 정한다{{PG}}
  • 프로메테우스는 대상에 가서 가져오는 pull 방식입니다. 반대인 push 방식은 대상이 수집기 쪽으로 데이터를 보내는 방식입니다. pull이라서 대상이 살아 있는지를 수집 자체로 압니다.
  • 대상마다 up 시계열이 자동으로 생기고, 긁기에 성공하면 1, 실패하면 0이 됩니다. 요청이 없는 한가한 앱도 /metrics에는 응답하므로 1입니다.
  • 대가도 있습니다. 프로메테우스가 대상에 네트워크로 닿아야 해서, 파드 사이 통신을 막는 NetworkPolicy나 방화벽이 있으면 수집이 안 됩니다. 수십 초 만에 끝나는 배치 잡은 긁으러 갈 때 이미 없어서 Pushgateway를 씁니다.
  • 또 30초 간격 샘플이라, 과금처럼 요청 하나하나를 정확히 세야 하는 용도에는 맞지 않습니다.

03SERVICE DISCOVERY

쿠버네티스 API에서 대상을 찾는 6가지 방법

역할 (role)무엇을 대상으로 만드나주로 쓰는 곳
node노드마다 대상 하나 (kubelet 주소)kubelet · cAdvisor
service서비스의 포트마다 대상 하나서비스 주소로 외부 점검(블랙박스)
pod파드의 컨테이너 포트마다 대상 하나서비스 없이 파드를 직접 긁을 때 (PodMonitor)
endpoints서비스 뒤의 실제 파드 주소마다 대상 하나서비스로 묶인 앱 (ServiceMonitor 기본값)
endpointsliceendpoints와 같고 EndpointSlice API를 쓴다endpoints의 후속. 공식 문서가 전환을 권장
ingress인그레스의 경로마다 대상 하나외부 URL 점검(블랙박스)
대상을 찾을 때 파드의 네임스페이스·이름·라벨이 __meta_kubernetes_* 라벨로 함께 따라온다. 메트릭에 붙어 있던 namespace·pod 라벨은 여기서 옮겨 붙인 것이다.
kubernetes_sd_configs 의 role 값{{PG}}
  • 프로메테우스가 쿠버네티스 API에서 대상을 찾는 방법은 role 값으로 정하고, 여섯 가지가 있습니다.
  • node는 노드마다 대상 하나로 kubelet과 cAdvisor를 긁을 때 씁니다. service와 ingress는 외부 점검용입니다. 외부 점검은 블랙박스 점검이라고도 하는데, 앱 내부 메트릭 없이 바깥에서 주소에 요청을 보내 응답이 오는지만 봅니다. pod는 서비스 없이 파드를 직접 긁을 때 쓰고, 이때는 ServiceMonitor 대신 파드를 직접 고르는 PodMonitor 리소스를 씁니다.
  • endpoints는 서비스 뒤의 실제 파드 주소마다 대상을 만들고, ServiceMonitor의 기본값입니다. endpointslice는 같은 일을 EndpointSlice API로 합니다. EndpointSlice는 파드 주소 목록을 여러 조각으로 나눠 담는 리소스라, 파드가 많을 때 목록을 갱신하는 부담이 적습니다.
  • 대상을 찾을 때 파드의 네임스페이스, 이름, 라벨이 __meta_kubernetes_* 라벨로 함께 따라옵니다. __meta_로 시작하는 라벨은 대상을 찾는 동안에만 붙는 임시 라벨이라 저장 전에 사라집니다. 그래서 필요한 것만 namespace, pod 같은 이름으로 옮겨 붙여 두고, 앞에서 본 라벨이 바로 이것입니다.

  • 오퍼레이터를 쓰면 수집 설정을 YAML 리소스로 적고, 설정 파일은 오퍼레이터가 만듭니다.
  • 흐름은 네 단계입니다. ServiceMonitor를 적용하면 오퍼레이터가 변경을 감지합니다. 오퍼레이터는 쿠버네티스 API를 watch, 즉 변경이 생기면 바로 통보받도록 지켜보고 있습니다. 이어서 프로메테우스 설정 파일에 수집 잡을 추가하고, 프로메테우스가 설정을 다시 읽어 긁기 시작합니다. 수집 잡은 같은 방식으로 긁는 대상들의 묶음입니다.
  • 주요 CRD는 넷입니다. Prometheus는 서버 자체, ServiceMonitor와 PodMonitor는 무엇을 긁을지, PrometheusRule은 알림 규칙, Alertmanager는 Alertmanager 서버 자체를 담습니다.

03SERVICEMONITOR · YAML

ServiceMonitor는 세 군데가 맞아야 서비스를 찾는다

ServiceMonitor · 무엇을 긁을지

apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: order-api
  namespace: apps
  labels:
    release: kps                  # ① 프로메테우스가 고르는 라벨spec:
  selector:
    matchLabels:
      app.kubernetes.io/name: order-api # ② 서비스 라벨  namespaceSelector:
    matchNames: [apps]
  endpoints:
    - port: http                # ③ 서비스 포트 이름      path: /actuator/prometheus
      interval: 30s
      scrapeTimeout: 10s

Service · order-api 앞에 있는 서비스

kind: Service
metadata:
  name: order-api
  namespace: apps
  labels:
    app.kubernetes.io/name: order-api # ②spec:
  ports:
    - name: http                # ③      port: 8080

Prometheus 리소스 · 어떤 ServiceMonitor를 읽을지

spec:
  serviceMonitorSelector:
    matchLabels:
      release: kps                # ①
전체 파일: labs/k8s/servicemonitors.yaml · 실습 가이드 06 앱 연결 6-1 섹션 참고{{PG}}
  • ServiceMonitor가 서비스를 찾으려면 세 군데가 맞아야 합니다.
  • ①은 ServiceMonitor의 release: kps 라벨입니다. kps는 차트를 설치할 때 붙인 릴리스 이름입니다. Prometheus 리소스의 serviceMonitorSelector가 이 라벨이 붙은 ServiceMonitor만 읽습니다.
  • ②는 selector.matchLabels의 app.kubernetes.io/name: order-api입니다. Service 자신의 metadata.labels와 맞아야 합니다.
  • ③은 endpoints의 port: http입니다. 포트 번호가 아니라 Service에 붙인 포트 이름과 맞춥니다. 셋 중 하나라도 어긋나면 에러 없이 수집 대상이 생기지 않습니다.
  • 나머지 칸에서 namespaceSelector는 apps 네임스페이스에서만 서비스를 찾으라는 뜻이고, interval 30s는 30초마다 긁기, scrapeTimeout 10s는 10초 안에 응답이 없으면 그 회차를 실패로 친다는 뜻입니다.

책 3.6~3.7 정리{{PG}}
  • 3장을 정리하겠습니다. 메트릭은 프로메테우스로 모읍니다. 라벨 기반 저장이 쿠버네티스 라벨과 같고, 구성요소들이 이미 이 형식으로 메트릭을 내놓습니다.
  • 대상은 쿠버네티스 API의 서비스 디스커버리로 자동으로 찾고, 이름과 라벨이 시계열 하나가 됩니다. 저장 단위는 값과 시각의 묶음인 샘플입니다.
  • 수집 설정은 ServiceMonitor 리소스로 적고, 오퍼레이터가 설정 파일로 바꿉니다. 다음 4장에서는 이 스택을 실제로 설치하고, 설치가 제대로 됐는지 확인합니다.
