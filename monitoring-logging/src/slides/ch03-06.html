06

규칙을 만들고, 알림을 실제로 받는다

RED 질의에 임계값과 지속 시간을 붙여 알림 규칙을 만든다. Alertmanager가 알림을 묶어 수신처로 보내고, 해소되면 다시 알리는 것까지 확인한다. 대시보드는 코드로 넣는다.

개념 + 실습 · 3.11 알림 · 3.12.3 알림 모범 사례{{PG}}
  • 대시보드는 사람이 볼 때 빠르게 판단하게 해 주고, 알림은 사람이 보지 않을 때 불러낸다. 새벽 3시에는 대시보드를 아무도 보지 않는다.
  • 흐름: 무엇에 알림을 거나 → 규칙 → 알림이 전달되는 길 → 규칙과 수신자 연결 → 알림 받기 → 라우팅 · 억제 · 침묵 → 대시보드.
  • 명령과 출력은 실습 가이드(lab-guide.html)의 절차를 kind 클러스터에서 실제로 실행한 결과다.

06WHAT TO ALERT · 책 3.11

사람이 지금 무언가 할 수 있을 때만 알림을 보낸다

알림을 건다

· SLO에 영향을 주는 증상: 사용자 요청 5%가 실패, 응답 시간이 약속을 넘음
· 관측 자체의 고장: 스크레이프 실패. 이게 죽으면 다른 알림이 모두 침묵한다

알림을 걸지 않는다

· 파드 하나가 실패할 때마다: 쿠버네티스가 스스로 재시작한다
· CPU·메모리가 높을 때: 사용자가 겪지 않으면 할 일이 없다. 원인을 찾을 때 본다
· 경험상 저절로 풀리는 문제

사람 대신 자동으로 고칠 수 있는 것자동 조치
응답 없는 프로세스라이브니스 프로브(liveness probe)가 컨테이너를 재시작
디스크가 꽉 참오래된 로그를 자동 삭제해 공간 확보
책 3.11: 유저는 SLO에 영향을 미치는 이벤트만 알림 받고 싶을 것이다{{PG}}
  • 책 3.11: 파드가 실패할 때마다 알림을 보내면 받는 사람이 무감각해진다. 쿠버네티스의 핵심은 컨테이너 상태를 자동으로 확인하고 재시작하는 기능이다.
  • 책의 예: 프론트엔드 SLO가 응답 시간 20ms인데 레이턴시가 그 이상으로 측정되면 바로 알림을 받아 조치해야 한다.
  • 프로메테우스 공식 가이드도 같은 원칙: 스택의 가장 높은 곳(사용자에게 보이는 지연·에러)에 알림을 걸고, 하위 구성요소 문제는 사용자 경험에 영향이 없으면 사람을 깨우지 않는다.

06WHERE RULES LIVE

규칙은 쿠버네티스 리소스(PrometheusRule)로 넣는다

① 파일에 적는다PrometheusRule YAML

labs/k8s/prometheusrule.yaml. 규칙 4개를 한 파일에

② 클러스터에 넣는다kubectl apply

kubectl apply -f labs/k8s/prometheusrule.yaml

③ 오퍼레이터가 옮긴다Prometheus 규칙 파일로

release: kps 라벨이 붙은 것만 골라 Prometheus에 로드

④ 프로메테우스가 평가30초마다

조건이 맞으면 pending → for를 채우면 firing

ServiceMonitor와 같은 방식

수집 대상을 ServiceMonitor로 넣었듯(5장), 알림 규칙은 PrometheusRule로 넣는다. Prometheus 설정 파일을 직접 고치지 않는다. 오퍼레이터가 ruleSelector(여기서는 release: kps)에 맞는 것만 고른다.

들어갔는지 확인하는 곳

Prometheus → Status → Rule health: 그룹 study-app, 규칙 4개 OK
Prometheus → Alerts: 규칙별 inactive · pending · firing

전체 파일: labs/k8s/prometheusrule.yaml · 실습 가이드 08 알림 8-2 섹션 참고{{PG}}
  • 순서: 파일 작성 → kubectl apply → 오퍼레이터가 Prometheus 파드 안의 규칙 파일로 옮김 → config-reloader가 Prometheus에 다시 읽게 함 → 30초 주기 평가. 적용 후 Rule health에 나타나기까지 1~2분.
  • 확인 명령: kubectl -n monitoring get prometheus -o jsonpath='{.items[0].spec.ruleSelector}' → {"matchLabels":{"release":"kps"}}. 이 라벨이 없으면 규칙이 조용히 무시된다(실습 가이드 11 Q&A).
  • 로드 직후 잠깐 state unknown(아직 평가 전)이 보인다. 30초 뒤 inactive.
06ANATOMY OF A RULE

규칙 하나 = 질의 + 임계값 + 지속 시간 + 라벨 + 메시지

apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: study-app-rules
  namespace: monitoring
  labels: {release: kps}          # ⓪ 오퍼레이터가 고르는 표시
spec:
  groups:
  - name: study-app
    interval: 30s                  # 평가 주기
    rules:
    - alert: AppHighErrorRate       # ① 이름      expr: |                       # ② 질의 (5장 E)
        100 * (
          sum by (job) (rate(…_count{status=~"5.."}[5m]))
          / sum by (job) (rate(…_count[5m]))
        ) > 5                        # ③ 임계값      for: 2m                       # ④ 지속 시간      labels:
        severity: warning           # ⑤ 누구에게 보낼지
      annotations:                   # ⑥ 메시지
        summary: "{{ $labels.job }} 에러율 {{ $value }}%"
칸하는 일
⓪ release: kps이 라벨이 있어야 오퍼레이터가 Prometheus에 올린다
① alert규칙 이름. Alerts 화면과 알림 메시지의 alertname
② expr5장에서 쓴 에러율 질의를 그대로 옮기고 ×100(퍼센트)
③ > 55%를 넘는 job만 결과에 남는다. 남은 줄 하나 = 알림 하나
④ for2분 동안 계속 넘어야 firing. 잠깐 튄 것은 거른다
⑤ severityAlertmanager가 이 값으로 수신자를 고른다(warning → 기본, critical → 당직)
⑥ summary알림에 찍히는 문장. $labels.job · $value가 채워져 "order-api 에러율 5.6%"가 된다
전체 파일: labs/k8s/prometheusrule.yaml · 실습 가이드 08 알림 8-2 섹션 참고{{PG}}
  • 새 규칙을 만드는 순서: Query 화면에서 질의를 먼저 쳐 보고 값이 맞으면 > 임계값과 for를 붙여 규칙으로 옮긴다.
  • sum by (job)으로 묶은 이유: 남은 라벨 조합마다 알림이 하나씩 생긴다. 파드별로 두면 파드 수만큼 알림이 온다.
  • 실측 알림 문장: "order-api 에러율 5.6%" (firing), 해소될 때 "order-api 에러율 5.0%" (resolved). 값은 보낼 때의 값이다.
  • 실제 파일의 expr은 http_server_requests_seconds_count 이름을 끝까지 적고 job=~"order-api|journal-api"로 두 앱만 고른다. 슬라이드에서는 줄였다.
06THE FOUR RULES

이 실습의 규칙 넷: 무엇을 보고, 언제, 누구를 부르나

규칙질의 (무엇을 보나)임계값forseverity왜
① AppTargetDownup{job=~"order-api|journal-api"} == 00 (수집 실패)1mcritical관측이 끊기면 다른 알림이 모두 침묵한다
② AppHighErrorRate5xx 비율 × 100 (5장 E)> 5%2mwarning사용자가 겪는 증상. 낮에 본다
③ AppHighLatencyP95histogram_quantile(0.95, …) (5장 P95)> 0.5초3mwarning느린 요청이 있다
④ AppSLOFastBurn200ms 넘는 요청 비율 (le="0.2" 버킷)> 14.4%2mcritical이 속도면 30일 SLO 예산을 2일에 다 쓴다. 새벽에도 깨운다
③과 ④는 둘 다 "느림"을 보지만 뜻이 다르다. ③은 느린 요청이 있다, ④는 약속(SLO)을 못 지킨다. 실측에서 ③은 울렸고 ④는 울리지 않았다(200ms 초과 5.6% < 14.4%).
전체 파일: labs/k8s/prometheusrule.yaml · 실습 가이드 08 알림 8-2 섹션 참고{{PG}}
  • 세 규칙이 RED 지표(에러 · 지연)이고 하나는 관측 자체의 고장이다. CPU · 메모리 알림은 만들지 않았다(앞 장 "무엇에 알림을 거나").
  • ④의 le="0.2"는 200ms 버킷 경계를 직접 고른다. 그 경계가 앱의 버킷 정의에 실제로 있어야 한다.
  • for 값은 발화 과정을 몇 분 안에 보려고 짧게 잡은 실습값이다. 책 3.11은 5분 이상, 5 · 10 · 30 · 60분처럼 표준화하라고 권한다.
06ALERT PATH

프로메테우스는 판단하고, Alertmanager는 전달한다

① Prometheus규칙 평가

30초마다 expr을 계산한다. 조건이 for 동안 이어지면 firing으로 Alertmanager에 보낸다

② Alertmanager묶고 · 누르고 · 고른다

group_by로 묶고, 억제 · 침묵을 적용하고, 라벨(severity)로 수신자를 고른다

③ 수신자사람에게 도착

웹훅 · Slack · PagerDuty · 메일. 해소되면 resolved를 한 번 더 보낸다

# kps-values.yaml · alertmanager.config (일부)
receivers:
  - name: study-default
    webhook_configs:      - url: http://alert-sink.monitoring.svc:8080/default
        send_resolved: true
  - name: study-critical
    webhook_configs:
      - url: http://alert-sink.monitoring.svc:8080/critical

실습의 수신자

클러스터 안에 작은 웹훅 서버(alert-sink)를 띄운다. 받은 알림을 한 줄씩 로그로 찍어 kubectl logs로 도착을 확인한다.

운영에서는

같은 자리에 slack_configs · pagerduty_configs · email_configs를 쓴다. 규칙과 라우팅은 그대로다.

수신 서버: labs/k8s/alert-sink.yaml · 값 파일: labs/helm/kps-values.yaml · 실습 가이드 08 알림 8-1 섹션 참고{{PG}}
  • 웹훅(Webhook): 알림 내용을 JSON으로 지정한 URL에 POST 한다. 모든 알림 연동의 기본 형태라, 외부 계정 없이 전달 경로 전체를 확인하기 좋다.
  • send_resolved: true 면 알림이 해소될 때도 status=resolved 로 한 번 더 보낸다. "고쳐졌다"를 사람이 따로 확인하지 않아도 된다.
  • alert-sink는 python:3.13-alpine 이미지에 스크립트 20줄을 ConfigMap으로 넣은 것이다. alertname · severity · job · summary를 한 줄로 찍는다.

06SLO BURN RATE

P95 알림은 울렸는데 SLO 알림은 울리지 않았다

# ④ 규칙의 값을 직접 계산
1 - (
  sum by (job) (rate(…_bucket{le="0.2"}[5m]))
  / sum by (job) (rate(…_count[5m])))
# 결과
order-api  5.63%   (임계 14.4%)

계산

SLO: 요청의 99%가 200ms 안에 → 오차 예산 1%. 5분 동안 예산을 14.4배 속도로 쓰면 30일 예산이 약 2일에 바닥난다. 임계 = 14.4 × 1% = 14.4%.

06ALERTMANAGER · ROUTE

Alertmanager는 묶고, 기다리고, 골라서 보낸다

# kps-values.yaml 의 alertmanager.config (일부)
route:
  group_by: [namespace, alertname]  group_wait: 30s
  group_interval: 5m
  repeat_interval: 4h
  receiver: study-default
  routes:
    - receiver: "null"
      matchers: [alertname =~ "InfoInhibitor|Watchdog|
                              NodeClockNotSynchronising"]
    - receiver: study-critical
      matchers: [severity = "critical"]
inhibit_rules:
  - source_matchers: [severity = "critical"]
    target_matchers: [severity =~ "warning|info"]
    equal: [namespace, alertname]
설정뜻
group_by같은 네임스페이스 · 같은 알림은 한 덩어리. 파드 10개가 죽어도 알림 하나
group_wait 30s첫 알림을 30초 기다려 연달아 터지는 것을 함께 보낸다
group_interval 5m같은 그룹에 새 알림이 붙으면 5분 간격으로 다시 보낸다
repeat_interval 4h해결되지 않은 알림을 4시간마다 다시 알린다
routes위에서부터 맞는 첫 경로로. critical은 당직(study-critical), 나머지는 기본
"null"보내지 않을 알림. Watchdog(상시 알림), kind 환경의 시계 경고
전체 파일: labs/helm/kps-values.yaml · 실습 가이드 08 알림 8-5 섹션 참고{{PG}}
  • 값 파일에 alertmanager.config 를 쓰면 차트 기본 설정을 통째로 대체한다. Watchdog 처리와 억제 규칙을 빠뜨리지 않는다.
  • NodeClockNotSynchronising: kind 노드는 NTP를 돌리지 않아 node-exporter가 늘 이 경고를 낸다. 실습 환경의 특성이라 null로 보냈다. 운영 노드에서는 진짜 문제이므로 버리지 않는다.
  • Watchdog은 외부 시스템이 "이 알림이 계속 오는가"로 관측 파이프라인의 생존을 감시할 때 쓴다.
  • 설정 확인: Alertmanager UI → Status 에 실제로 적용된 설정 전체가 보인다.

06ALERT FATIGUE · 책 3.12.3

하루 스무 번 울리는 알림은 울리지 않는 것과 같다

줄이는 방법설정
증상에만 건다규칙 넷 중 셋이 RED 지표. CPU·메모리 알림은 만들지 않았다
순간적인 것을 거른다for: 2~3m. 잠깐 튀는 것은 사람을 부르지 않는다
묶는다group_by: [namespace, alertname]
누른다critical이 울리는 동안 같은 대상의 warning은 억제
지운다울렸는데 아무도 조치하지 않은 알림은 지우거나 임계값을 올리거나 원인을 고친다

critical

새벽 3시에 깨워도 되는 것. 스크레이프 실패, SLO 빠른 소진

warning

업무 시간에 보면 되는 것. 에러율 5% 초과, P95 500ms 초과

책 3.12.3: 알림 피로는 담당자와 프로세스 모두에게 안 좋은 영향을 끼친다. 완벽한 알림은 없다{{PG}}
  • 책 3.12.3 세 항목: 알림 피로 주의 / 완벽한 알림은 없으니 점진적으로 개선 / 사람이 즉시 대응할 필요 없는 일시적 문제는 알리지 않고, SLO와 고객 영향 증상에만 알린다.
  • severity는 둘이면 충분하다. info 등급 알림은 아무도 보지 않는다. 알림이 아니라 대시보드에 둘 것이다.
  • "한 달에 열 번 울렸고 매번 '원래 그래요'였다"면 그 알림은 정보가 아니라 소음이다.
