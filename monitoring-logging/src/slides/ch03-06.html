06

규칙을 만들고, 알림을 실제로 받는다

RED 질의에 임계값과 지속 시간을 붙여 알림 규칙을 만든다. Alertmanager가 알림을 묶어 수신처로 보내고, 해소되면 다시 알리는 것까지 확인한다. 대시보드는 코드로 넣는다.

개념 + 실습 · 3.11 알림 · 3.12.3 알림 모범 사례{{PG}}
  • 6장은 알림입니다. 5장에서 만든 RED 질의에 임계값과 지속 시간을 붙여 알림 규칙을 만듭니다. 임계값은 이 선을 넘으면 이상으로 보겠다는 경계이고, 예를 들어 "에러율 5%"입니다. 지속 시간은 그 상태가 얼마나 이어져야 알림을 보낼지이고, 예를 들어 "2분"입니다.
  • Alertmanager가 알림을 묶어 수신처로 보내고, 문제가 풀리면 "해결됐다"는 해소 알림을 한 번 더 보내는 것까지 확인합니다. 마지막으로 대시보드를 화면에서 만들지 않고 파일로 넣는 방법을 봅니다.
06GLOSSARY · 1/2

용어 ① 알림 규칙

용어원어 · 풀 네임뜻
알림 규칙Alerting rulePromQL 조건 + 지속 시간 + 라벨. 프로메테우스가 주기적으로 평가한다
exprExpression알림 조건 질의. 결과가 하나라도 있으면 조건 성립
forfor (지속 시간)조건이 이 시간 동안 계속 성립해야 발화한다
pendingPending (대기)조건은 성립했지만 for 시간을 아직 채우지 못한 상태
firingFiring (발화)for를 채워 Alertmanager로 보내지는 상태
inactiveInactive (비활성)조건이 성립하지 않는 평상시 상태
severitySeverity (심각도) 라벨critical · warning. Alertmanager가 보낼 곳과 억제를 이 라벨로 정한다
annotationsAnnotations사람이 읽을 요약·설명·런북 링크. {{ $value }}로 현재 값을 넣는다
런북Runbook (책: 플레이북 Playbook)알림을 받았을 때 무엇을 확인하고 어떻게 조치할지 적은 문서
inactive → pending → firing → inactive{{PG}}
  • 알림 규칙은 PromQL 조건과 지속 시간, 라벨을 묶은 것입니다. 프로메테우스가 30초마다 이 조건을 계산합니다.
  • expr는 조건 질의입니다. 예를 들어 "에러율이 5보다 큰 앱"을 고르는 질의를 쓰면, 결과에 한 줄이라도 나오는 순간 조건이 성립합니다. for는 그 조건이 얼마나 오래 이어져야 알림을 보낼지입니다. for를 2분으로 두면 10초 동안 잠깐 튄 값은 알림이 되지 않습니다.
  • 상태는 세 가지입니다. 평소에는 inactive입니다. 조건은 맞았지만 for 시간을 아직 못 채우면 pending, 다시 말해 "지켜보는 중"입니다. for를 채우면 firing이 되어 Alertmanager로 보내집니다. 조건이 다시 풀리면 inactive로 돌아갑니다.
  • severity는 심각도 라벨입니다. critical은 새벽에도 사람을 깨워야 하는 것, warning은 업무 시간에 보면 되는 것으로 나눕니다. Alertmanager가 이 값을 보고 누구에게 보낼지 정합니다.
  • annotations는 사람이 읽을 문장입니다. 요약과 설명, 런북 링크를 넣고, {{ $value }} 자리에는 알림을 보내는 순간의 실제 값이 들어갑니다. 런북은 알림을 받았을 때 무엇을 확인하고 어떻게 조치할지 적어 둔 문서입니다. 새벽에 깬 담당자가 바로 따라 할 수 있게 하려고 둡니다.

용어 ② Alertmanager와 SLO

용어원어 · 풀 네임뜻

억제Inhibitioncritical이 울리는 동안 이름 · 네임스페이스가 같은 warning을 규칙으로 자동으로 누른다
침묵Silence사람이 기간을 정해 특정 알림을 끈다. 계획 작업 중에 쓴다
WatchdogWatchdog 알림늘 발화 상태인 알림. 이것이 멈추면 관측 파이프라인이 죽은 것
오차 예산Error budgetSLO가 허용하는 실패 몫. "99% 성공"이면 1%
소진 속도Burn rate오차 예산을 평소 대비 몇 배 빠르게 쓰고 있나. 14.4배면 30일 예산이 약 2일에 바닥
프로메테우스는 조건을 판단하고, Alertmanager는 누구에게 어떻게 보낼지 정한다{{PG}}
  • 라우트는 알림의 라벨을 보고 어느 수신자로 보낼지 정하는 규칙입니다. 예를 들어 severity가 critical이면 당직 담당자에게, 나머지는 팀 채널로 보내는 식입니다. 수신자는 실제로 받는 곳이고 Slack, 메일, PagerDuty, 웹훅이 있습니다. 웹훅은 정해 둔 주소로 알림 내용을 JSON으로 보내는 방식이고, 이 실습의 alert-sink가 웹훅으로 받습니다.
  • 그룹화는 같은 라벨의 알림을 한 통으로 묶는 것입니다. 같은 앱의 파드 10개에서 같은 알림이 나도 메시지는 하나만 갑니다.
  • 억제(inhibit)는 더 심각한 알림이 울리는 동안 덜 심각한 알림을 숨기는 기능입니다. 이 실습에서는 같은 네임스페이스에서 같은 이름의 critical 알림이 울리면 warning은 보내지 않습니다. 침묵(silence)은 사람이 기간을 정해 알림을 끄는 기능입니다. 예를 들어 밤 10시부터 30분 동안 노드를 점검한다면 그 사이 알림을 미리 침묵으로 막아 둡니다.
  • Watchdog은 일부러 항상 울리게 만든 알림입니다. 이 알림이 계속 들어오면 프로메테우스부터 Alertmanager까지 알림 경로가 살아 있다는 뜻이고, 이 알림이 끊기면 경로 어딘가가 죽은 것입니다.
  • SLO는 서비스가 지키기로 한 목표입니다. 예를 들어 "요청의 99%는 200ms 안에 끝난다"입니다. 오차 예산은 이 목표가 허용하는 실패 몫으로, 99%가 목표면 1%입니다. 소진 속도는 그 1%를 평소보다 몇 배 빠르게 쓰고 있는지이고, 14.4배면 30일치 예산이 약 2일 만에 바닥납니다.
  • 정리하면 프로메테우스는 조건을 판단하고, Alertmanager는 그 알림을 누구에게 어떻게 보낼지 정합니다.

06WHAT TO ALERT · 책 3.11

알림을 받아야 할 사항과 저절로 풀리는 문제

알림을 건다

· SLO에 영향을 주는 증상: 사용자 요청 5%가 실패, 응답 시간이 약속을 넘음
· 관측 자체의 고장: 스크레이프 실패. 이게 죽으면 다른 알림이 모두 침묵한다

알림을 걸지 않는다

· 파드 하나가 실패할 때마다: 쿠버네티스가 스스로 재시작한다
· CPU·메모리가 높을 때: 사용자가 겪지 않으면 할 일이 없다. 원인을 찾을 때 본다
· 경험상 저절로 풀리는 문제

사람 대신 자동으로 고칠 수 있는 것자동 조치
응답 없는 프로세스라이브니스 프로브(liveness probe)가 컨테이너를 재시작
디스크가 꽉 참오래된 로그를 자동 삭제해 공간 확보
책 3.11: 유저는 SLO에 영향을 미치는 이벤트만 알림 받고 싶을 것이다{{PG}}
  • 알림을 받아야 할 사항과, 알림을 걸지 않아도 저절로 풀리는 문제를 나눕니다. 나누는 기준은 알림을 받은 사람이 지금 무언가 할 수 있느냐입니다. 할 일이 없는 알림은 사람을 지치게만 합니다.
  • 알림을 거는 것은 두 가지입니다. 첫째는 사용자가 겪는 증상입니다. 요청 5%가 실패하거나 응답이 약속한 시간보다 느린 경우처럼 SLO, 즉 서비스 목표에 영향을 주는 것입니다.
  • 둘째는 관측 자체가 끊긴 경우입니다. 스크레이프, 즉 프로메테우스가 앱의 메트릭을 가져오는 일이 실패하면 데이터가 들어오지 않습니다. 그러면 에러율 규칙도 계산할 값이 없어 조용해지기 때문에, 문제가 있어도 아무 알림이 오지 않습니다. 그래서 수집 실패에는 따로 알림을 겁니다.
  • 파드 하나가 죽을 때마다, CPU나 메모리가 높을 때마다 알림을 걸지는 않습니다. 파드는 쿠버네티스가 스스로 다시 띄우고, CPU가 높아도 사용자가 느끼지 못하면 사람이 할 일이 없습니다. 이런 값은 원인을 찾을 때 봅니다.
  • 자동으로 고칠 수 있는 것은 자동으로 고칩니다. 라이브니스 프로브는 쿠버네티스가 컨테이너에 주기적으로 "살아 있나"를 묻는 검사입니다. 응답이 없으면 컨테이너를 다시 시작합니다. 디스크가 꽉 차는 문제는 오래된 로그를 자동으로 지워서 막습니다.

ServiceMonitor와 같은 방식

수집 대상을 ServiceMonitor로 넣었듯(5장), 알림 규칙은 PrometheusRule로 넣는다. Prometheus 설정 파일을 직접 고치지 않는다. 오퍼레이터가 ruleSelector(여기서는 release: kps)에 맞는 것만 고른다.

  • 알림 규칙은 PrometheusRule이라는 쿠버네티스 리소스로 넣습니다. 파드나 서비스처럼 YAML로 적어서 kubectl apply로 넣는 오브젝트입니다.
  • 규칙을 넣으면 오퍼레이터가 그것을 프로메테우스의 규칙 파일로 옮겨 줍니다. 오퍼레이터는 클러스터에 넣은 리소스를 보고 프로메테우스 설정을 대신 만들어 주는 프로그램입니다. 이때 release: kps 라벨이 붙은 것만 고르는데, 이 기준을 ruleSelector라고 합니다. 라벨이 빠지면 오류 없이 무시됩니다.
  • 5장에서 수집 대상을 ServiceMonitor로 넣은 것과 같은 방식입니다. 프로메테우스 설정 파일은 직접 고치지 않습니다.
  • 들어갔는지는 두 화면에서 봅니다. Status 메뉴의 Rule health에서 study-app 그룹과 규칙 4개가 OK인지 보고, Alerts 화면에서 규칙마다 inactive, pending, firing 중 어느 상태인지 봅니다.
06ANATOMY OF A RULE

규칙 하나 = 질의 + 임계값 + 지속 시간 + 라벨 + 메시지

apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: study-app-rules
  namespace: monitoring
  labels: {release: kps}          # ⓪ 오퍼레이터가 고르는 표시
spec:
  groups:
  - name: study-app
    interval: 30s                  # 평가 주기
    rules:
    - alert: AppHighErrorRate       # ① 이름      expr: |                       # ② 질의 (5장 E)
        100 * (
          sum by (job) (rate(…_count{status=~"5.."}[5m]))
          / sum by (job) (rate(…_count[5m]))
        ) > 5                        # ③ 임계값      for: 2m                       # ④ 지속 시간      labels:
        severity: warning           # ⑤ 누구에게 보낼지
      annotations:                   # ⑥ 메시지
        summary: "{{ $labels.job }} 에러율 {{ $value | printf "%.1f" }}%"
칸하는 일
⓪ release: kps이 라벨이 있어야 오퍼레이터가 Prometheus에 반영한다
① alert규칙 이름. Alerts 화면과 알림 메시지의 alertname
② expr5장에서 쓴 에러율 질의를 그대로 옮기고 ×100(퍼센트)
③ > 55%를 넘는 job만 결과에 남는다. 남은 줄 하나 = 알림 하나
④ for2분 동안 계속 넘어야 firing. 잠깐 튄 것은 거른다
⑤ severityAlertmanager가 이 값으로 수신자를 고른다(warning → 기본, critical → 당직)
⑥ summary알림에 들어가는 문장. $labels.job · $value가 채워지고 printf "%.1f"로 소수점 한 자리까지 잘라 "order-api 에러율 5.6%"가 된다
전체 파일: labs/k8s/prometheusrule.yaml · 실습 가이드 08 알림 8-2 섹션 참고{{PG}}
  • 규칙 하나는 질의, 임계값, 지속 시간, 라벨, 메시지로 이루어집니다. 에러율 규칙으로 보겠습니다.
  • 맨 위 release: kps 라벨이 있어야 오퍼레이터가 이 규칙을 프로메테우스에 반영합니다. groups 아래 interval: 30s는 이 그룹의 규칙을 30초마다 계산한다는 뜻입니다. alert는 규칙 이름이고, 알림 메시지에 alertname으로 들어갑니다.
  • expr는 5장의 에러율 질의입니다. status=~"5.."는 상태 코드가 5로 시작하는 응답, 즉 서버 오류만 고른다는 뜻입니다. rate로 최근 5분의 초당 건수를 구하고, sum by (job)로 앱별로 합친 뒤 전체 요청으로 나누고 100을 곱해 퍼센트로 만듭니다.
  • > 5는 5%를 넘는 앱만 결과에 남깁니다. 남은 줄 하나가 알림 하나가 됩니다. for: 2m이라 2분 동안 계속 넘어야 firing이 되고, 잠깐 튄 값은 여기서 걸러집니다.
  • severity: warning은 업무 시간에 보면 되는 알림이라는 표시이고, Alertmanager가 이 값으로 수신자를 고릅니다. summary의 $labels.job 자리에는 앱 이름이, $value 자리에는 계산된 값이 들어갑니다. printf "%.1f"는 소수점 한 자리까지만 남기라는 뜻이라 "order-api 에러율 5.6%" 같은 문장이 됩니다.

계산

SLO: 요청의 99%가 200ms 안에 → 오차 예산 1%. 5분 동안 예산을 14.4배 속도로 쓰면 30일 예산이 약 2일에 바닥난다. 임계 = 14.4 × 1% = 14.4%.

  • P95 알림은 울렸는데 SLO 알림은 왜 울리지 않았는지 직접 계산해 봅니다. 부하가 도는 동안 Query 화면에 질의를 붙여 넣고 Execute합니다.
  • 질의는 200ms를 넘긴 요청의 비율입니다. le="0.2" 칸에는 0.2초 안에 끝난 요청 수가 쌓여 있습니다. 이것을 전체 요청 수로 나누면 200ms 안에 끝난 비율이 되고, 1에서 빼면 200ms를 넘긴 비율이 됩니다. 결과는 0.056, 즉 5.6%입니다.
  • SLO는 요청의 99%가 200ms 안에 끝나는 것이고, 오차 예산은 1%입니다. 최근 5분 동안 이 예산을 평소의 14.4배 속도로 쓰고 있으면, 그대로 갈 경우 30일치가 약 2일에 바닥납니다. 그래서 임계값이 14.4 × 1% = 14.4%입니다. 5.6%는 여기에 한참 못 미칩니다.
  • 느린 요청은 초당 약 36건 중 2건뿐입니다. P95 알림은 "느린 요청이 있다"를 알려 주고, SLO 알림은 "이대로면 약속을 못 지킨다"를 알려 줍니다. 느리다와 위험하다는 다르고, 사람을 새벽에 깨우는 것은 SLO 알림이어야 합니다.

06ALERTMANAGER · ROUTE

Alertmanager는 묶고, 기다리고, 골라서 보낸다

# kps-values.yaml 의 alertmanager.config (일부)
route:
  group_by: [namespace, alertname]  group_wait: 30s
  group_interval: 5m
  repeat_interval: 4h
  receiver: study-default
  routes:
    - receiver: "null"
      matchers: [alertname =~ "InfoInhibitor|Watchdog|
                              NodeClockNotSynchronising"]
    - receiver: study-critical
      matchers: [severity = "critical"]
inhibit_rules:
  - source_matchers: [severity = "critical"]
    target_matchers: [severity =~ "warning|info"]
    equal: [namespace, alertname]
설정뜻
group_by같은 네임스페이스 · 같은 알림은 한 덩어리. 파드 10개가 죽어도 알림 하나
group_wait 30s첫 알림을 30초 기다려 연달아 터지는 것을 함께 보낸다
group_interval 5m같은 그룹에 새 알림이 붙으면 5분 간격으로 다시 보낸다
repeat_interval 4h해결되지 않은 알림을 4시간마다 다시 알린다
routes위에서부터 맞는 첫 경로로. critical은 당직(study-critical), 나머지는 기본
"null"보내지 않을 알림. Watchdog(상시 알림), kind 환경의 시계 경고
inhibit_rulescritical이 울리는 동안 이름 · 네임스페이스가 같은 warning을 숨긴다
직접 해 보기 (부하가 도는 동안): 억제와 침묵은 실습 가이드 8-5의 명령으로 확인한다. 같은 이름의 critical · warning 알림을 API로 넣으면 warning이 suppressed, 침묵을 걸면 둘 다 silencedBy=1. 접속은 따라하기 ①에서 띄운 Alertmanager localhost:9093 그대로.
전체 파일: labs/helm/kps-values.yaml · 실습 가이드 8-5 (억제 · 침묵 실습){{PG}}
  • Alertmanager는 알림을 묶고, 기다리고, 골라서 보냅니다. 왼쪽이 설정, 오른쪽이 그 뜻입니다.
  • group_by는 네임스페이스와 알림 이름이 같은 것을 한 통으로 묶습니다. 파드 10개가 죽어도 알림은 하나입니다. group_wait 30초는 첫 알림이 오면 30초 기다렸다가 그사이 함께 터진 것을 모아 보내는 시간입니다. group_interval 5분은 이미 보낸 묶음에 새 알림이 붙었을 때 다시 보내는 간격이고, repeat_interval 4시간은 해결되지 않은 알림을 다시 알려 주는 간격입니다.
  • routes는 위에서부터 조건이 맞는 첫 경로로 보냅니다. matchers의 =~는 정규식으로 맞춘다는 뜻입니다. 첫 경로는 "null" 수신자인데, 받을 곳이 없는 수신자라 여기로 가면 버려집니다. Watchdog처럼 항상 울리는 알림과, kind 환경에서 늘 나오는 노드 시계 경고를 여기로 보내 조용히 합니다. 둘째 경로는 critical을 당직 수신자로 보내고, 나머지는 기본 수신자로 갑니다.
  • inhibit_rules는 억제 규칙입니다. source는 기준이 되는 critical 알림, target은 숨길 warning과 info 알림입니다. equal에 적은 네임스페이스와 알림 이름이 둘 다 같을 때만 숨깁니다. 그래서 이름이 서로 다른 실습 규칙 네 개는 서로를 숨기지 않습니다.
  • 부하가 도는 동안 억제와 침묵을 직접 해 봅니다. 같은 이름의 critical과 warning 알림을 넣으면 warning이 suppressed, 즉 보내지 않고 눌러 둔 상태가 됩니다. inhibitedBy=1은 한 알림 때문에 눌렸다는 뜻입니다. 침묵을 걸면 둘 다 silencedBy=1이 되어 어느 쪽도 보내지 않습니다.

접속Grafana localhost:3000 (4장에서 띄운 port-forward)로그인admin / obs-study메뉴Dashboards → 스터디 → 스터디 — 서비스 RED
# 값 파일: Grafana 사이드카 설정
sidecar:
  dashboards:
    enabled: true
    label: grafana_dashboard    labelValue: "1"    searchNamespace: ALL
    folderAnnotation: grafana_folder    provider: {foldersFromFilesStructure: true}
# 1) 대시보드 JSON → 라벨 · 폴더 붙은 ConfigMap (다시 쳐도 된다)
kubectl -n monitoring create configmap study-dashboards \
  --from-file=labs/dashboards/study-red.json \
  --dry-run=client -o yaml | kubectl apply -f -
kubectl -n monitoring label --overwrite configmap study-dashboards grafana_dashboard=1
kubectl -n monitoring annotate --overwrite configmap study-dashboards grafana_folder=스터디
# 2) 20초 뒤 사이드카가 파일로 썼는지 본다
kubectl -n monitoring logs deploy/kps-grafana -c grafana-sc-dashboard --tail=20 | grep study-red

왜 코드로

UI에서 만든 대시보드는 Grafana 파드가 다시 뜨면 사라진다(대시보드용 영구 볼륨 없음). JSON 파일로 두면 저장소에서 버전 관리된다.

uid를 고정한다

study-red. 대시보드 주소(/d/study-red)가 이 값을 쓴다. 바뀌면 북마크와 공유한 링크가 전부 깨진다.

로그 패널은 7장에서 Loki를 설치하기 전까지 비어 있다. 정상이다. ConfigMap을 YAML로 쓸 때는 라벨 값을 "1"처럼 따옴표로 감싼다. 숫자 1은 라벨 값으로 거부된다.
대시보드: study-red.json · 실습 가이드 9-1 · 막히면 Q6{{PG}}
  • 대시보드는 화면에서 만들지 않고 ConfigMap으로 넣습니다. 화면에서 만든 대시보드는 Grafana 파드가 다시 뜨면 사라지지만, JSON 파일로 두면 저장소에서 버전 관리할 수 있습니다.
  • Grafana 파드 안에는 사이드카라는 보조 컨테이너가 같이 떠 있습니다. 이 사이드카가 클러스터의 ConfigMap을 지켜보다가, grafana_dashboard=1 라벨이 붙은 것을 찾으면 그 안의 JSON을 파일로 써서 Grafana가 읽게 합니다. searchNamespace: ALL은 모든 네임스페이스에서 찾으라는 뜻이고, folderAnnotation은 grafana_folder 어노테이션 값을 폴더 이름으로 쓰라는 뜻입니다.
  • 명령 세 줄로 ConfigMap을 만들고 라벨과 폴더를 붙입니다. 첫 줄의 --dry-run=client -o yaml | kubectl apply -f -는 바로 만들지 않고 YAML만 뽑아서 apply로 넣는 방법입니다. 이미 있으면 갱신하기 때문에 다시 실행해도 오류가 나지 않습니다. --overwrite도 같은 이유로 붙입니다.
  • 20초 뒤 사이드카 로그에 Writing … study-red.json이 보이면 들어간 것입니다. 폴더 이름 "스터디"는 로그에는 \uc2a4 같은 유니코드 코드로 나오는데, 같은 글자를 코드로 적은 것입니다.
  • Grafana에서는 Dashboards, 스터디 폴더, 스터디 — 서비스 RED 순서로 엽니다. uid는 대시보드마다 붙는 고유 이름입니다. 대시보드 주소가 /d/study-red처럼 이 값으로 만들어지기 때문에, 바뀌면 북마크와 공유한 링크가 모두 깨집니다. 그래서 고정해 둡니다. 로그 패널은 7장에서 Loki를 설치하기 전까지 비어 있는 것이 정상입니다.
  • 값 파일이나 ConfigMap YAML에 라벨을 직접 적을 때는 값을 문자열 "1"로 적습니다. 따옴표 없이 숫자 1로 적으면 쿠버네티스가 라벨 값으로 받지 않습니다. kubectl label 명령은 항상 문자열로 넣어서 이 문제가 없습니다.
