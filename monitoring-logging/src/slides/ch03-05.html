05

앱을 연결하고 PromQL로 RED를 읽는다

두 앱을 ServiceMonitor로 수집 대상에 올려 타깃 33개가 모두 up인 것을 확인한다. 부하를 넣고 order-api의 P99 790ms를 PromQL로 직접 계산한 뒤, uri로 나눠 느린 경로 /api/chaos/slow 하나를 찾는다.

실습 · 책 3.12.1: 애플리케이션의 사용률, 에러 수, 실행 시간도 모니터링한다{{PG}}
  • 5장은 우리 앱을 연결하고 PromQL로 RED를 읽는 장입니다. RED는 요청 수(Rate), 에러(Errors), 처리 시간(Duration) 세 가지로 서비스를 보는 방법입니다.
  • 먼저 두 앱을 ServiceMonitor로 수집 대상에 올리고 타깃 33개가 모두 up인지 확인합니다. 타깃은 프로메테우스가 메트릭을 긁어 가는 주소 하나를 말하고, up은 마지막 수집이 성공했다는 뜻입니다.
  • 그다음 부하를 넣고 order-api의 P99 790ms를 PromQL로 직접 계산합니다. P99는 요청 100건 중 가장 느린 1건을 뺀 나머지가 모두 이 시간 안에 끝났다는 값입니다. 마지막으로 요청 경로(uri)별로 나눠 느린 경로 /api/chaos/slow를 찾습니다.

앱은 계측 라이브러리로 내놓고, 프로메테우스는 PromQL로 계산한다{{PG}}
  • 이 장에서 쓰는 용어입니다. 계측은 앱 코드가 스스로 메트릭을 만들어 내놓게 하는 일입니다. 예를 들어 요청이 들어올 때마다 숫자를 하나 올리고 걸린 시간을 기록하는 코드가 계측입니다.
  • order-api는 Spring Boot라 Micrometer라는 라이브러리가 HTTP 요청 메트릭을 자동으로 만듭니다. 액추에이터는 Spring Boot의 운영용 주소 모음으로, 헬스 체크와 메트릭 같은 것을 내놓고 그중 /actuator/prometheus가 프로메테우스 형식의 메트릭입니다. journal-api는 Node.js라 prom-client 라이브러리로 코드에서 직접 만듭니다.
  • rate()는 카운터가 1초에 얼마씩 늘었는지 계산하는 함수입니다. 카운터는 앱이 뜬 뒤로 계속 쌓이는 값이라 숫자 자체보다 늘어나는 속도가 의미 있습니다. 예를 들어 5분 동안 300 늘었다면 초당 1입니다.
  • histogram_quantile()은 히스토그램으로 분위수를 추정하는 함수입니다. 히스토그램은 처리 시간을 구간(버킷)별로 나눠 센 것이고, le는 그 구간의 경계 라벨입니다. le="0.1"이면 0.1초 이하로 끝난 요청 수입니다.
  • 카디널리티는 메트릭 하나가 만드는 시계열 수입니다. 라벨 값의 가짓수만큼 시계열이 생기기 때문에, 예를 들어 라벨에 주문 번호를 넣으면 주문마다 시계열이 생겨 저장량이 폭증합니다. k6는 초당 요청 수를 정해 두고 그대로 부하를 넣는 도구입니다.

05INSTRUMENTATION

앱은 HTTP 엔드포인트로 메트릭을 내놓는다

접속터미널에서 localhost:18082 (order-api). 4장에서 띄운 port-forward가 필요하다살아 있나curl -s localhost:18082/api/orders → {"data":[],"message":"조회 성공",…}꺼졌으면kubectl -n apps port-forward svc/order-api 18082:8080 >/dev/null 2>&1 &

코드: OrderService.java · 메트릭 목록: Spring Boot · Metrics · prom-client · 실습 가이드 02 앱 2-5 섹션 참고{{PG}}
  • 앱은 HTTP 주소로 메트릭을 내놓고, 프로메테우스가 그 주소를 주기적으로 읽어 갑니다. 먼저 curl -s localhost:18082/api/orders로 order-api가 열려 있는지 확인합니다. 응답이 없으면 위쪽의 port-forward 명령으로 다시 엽니다.
  • 왼쪽 위 코드는 order-api가 주문 메트릭을 만드는 부분입니다. Counter는 주문 수처럼 늘기만 하는 값을 세고, Timer는 처리 시간을 잽니다. publishPercentileHistogram()을 켜면 처리 시간을 구간별로 센 히스토그램도 함께 내놓아서, 나중에 P99 같은 분위수를 계산할 수 있습니다.
  • 아래 명령은 엔드포인트에서 실제 메트릭 이름과 타입을 확인합니다. # TYPE 줄의 counter는 늘기만 하는 값, gauge는 저장된 주문 수처럼 오르내리는 현재 값, histogram은 구간별 개수입니다. _max는 최근 가장 오래 걸린 처리 시간입니다.
  • 코드의 orders.created가 orders_total로 나오는 것처럼 이름이 바뀝니다. 프로메테우스 형식에서 _created는 "카운터가 처음 만들어진 시각"을 나타내는 데 쓰이는 이름이라 라이브러리가 떼어 내고, 카운터에는 _total을 붙입니다. 그래서 메트릭 이름은 코드가 아니라 엔드포인트에서 확인합니다.
  • 오른쪽 표는 두 앱의 차이입니다. 언어와 라이브러리, 경로는 다르지만 둘 다 http_server_requests_seconds라는 같은 이름의 히스토그램을 씁니다. 그래서 같은 질의 하나로 두 앱을 함께 볼 수 있습니다.
  • 엔드포인트 응답은 사람이 읽을 수 있는 텍스트입니다. # HELP 줄에 메트릭 설명이, # TYPE 줄에 타입이 있고, 그 아래에 이름, 중괄호 안의 라벨, 값이 한 줄씩 나옵니다. 라벨 조합이 다르면 다른 시계열이라, 예를 들어 status="200"과 status="500"은 따로 쌓입니다. 프로메테우스는 이 텍스트를 긁어 온 시각을 붙여 저장합니다.

05HOW TO CONNECT · ServiceMonitor

ServiceMonitor에는 세 가지를 맞춘다

apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: order-api
  namespace: apps
  labels:
    release: kps                          # ①spec:
  selector:
    matchLabels:
      app.kubernetes.io/name: order-api   # ②  namespaceSelector: {matchNames: [apps]}
  endpoints:
    - port: http                         # ③      path: /actuator/prometheus
      interval: 30s
#맞출 상대확인 명령 → 나와야 할 값
①Prometheus가 고르는 라벨kubectl -n monitoring get prometheus -o jsonpath='{.items[0].spec.serviceMonitorSelector}' → {"matchLabels":{"release":"kps"}}
②Service의 metadata.labelskubectl -n apps get svc order-api --show-labels → LABELS에 app.kubernetes.io/name=order-api
③Service 포트의 이름kubectl -n apps get svc order-api -o jsonpath='{.spec.ports}' → "name":"http"
셋이 맞으면 오퍼레이터가 수집 설정을 만들고, 1~2분 뒤 Target health에 serviceMonitor/apps/order-api/0이 나타난다. 하나라도 어긋나면 에러 없이 타깃이 생기지 않는다. 그때는 실습 가이드 Q4의 순서로 찾는다.
전체 파일: labs/k8s/servicemonitors.yaml (order-api · journal-api 두 개) · 실습 가이드 06 앱 연결 6-1 섹션 참고{{PG}}
  • ServiceMonitor는 "이 Service의 이 포트를 긁어 가라"고 적는 쿠버네티스 리소스입니다. 프로메테우스 오퍼레이터가 이것을 읽어 프로메테우스 수집 설정을 대신 만들어 줍니다. 앱을 수집 대상에 올리려면 세 가지가 맞아야 합니다.
  • ① release: kps는 프로메테우스가 자기 것으로 고르는 표시입니다. 프로메테우스는 클러스터의 ServiceMonitor를 전부 읽지 않고 serviceMonitorSelector에 적힌 라벨이 붙은 것만 읽습니다. kps는 스택을 설치할 때 붙인 이름입니다.
  • ② matchLabels는 어떤 Service를 찾을지 정하는 조건으로, Service에 붙은 라벨과 같아야 합니다. Service가 파드를 고르는 selector가 아니라 Service 자신의 라벨이라는 점이 자주 헷갈립니다. namespaceSelector는 그 Service를 어느 네임스페이스에서 찾을지 정합니다.
  • ③ endpoints의 port: http는 포트 번호가 아니라 Service 포트의 이름입니다. path는 메트릭 주소, interval 30s는 30초마다 긁어 간다는 뜻입니다.
  • 오른쪽 표의 명령으로 셋을 하나씩 확인합니다. jsonpath는 긴 출력에서 필요한 필드만 뽑아 보는 옵션입니다. 각각 release: kps, app.kubernetes.io/name=order-api, "name":"http"가 나오면 맞습니다. 셋이 맞으면 1~2분 뒤 Target health에 serviceMonitor/apps/order-api/0이 나타나고, 하나라도 어긋나면 에러 없이 타깃이 생기지 않습니다.

05FOLLOW ALONG ① · 연결

따라하기 ① 두 앱을 수집 대상에 올린다

접속브라우저 http://localhost:9090. 안 열리면 kubectl -n monitoring port-forward svc/kps-kube-prometheus-stack-prometheus 9090:9090 >/dev/null 2>&1 &로그인없음메뉴질의는 위쪽 Query 입력칸에 붙여 넣고 Execute, 결과는 Table 탭
#명령 · 화면보이면 통과
1kubectl apply -f labs/k8s/servicemonitors.yamlorder-api created · journal-api created 두 줄
2kubectl get servicemonitor -A -l release=kps | grep -E 'apps|journal'apps order-api · journal journal-api 두 줄
31~2분 기다린 뒤 Status → Target health, 위쪽 세 번째 칸 Filter by endpoint or labels에 api (apiserver 줄은 무시)order-api 2 / 2 up · journal-api 3 / 3 up
4Query: count(up), 다음에 sum(up)둘 다 33 (기본 타깃 28 + 앱 파드 5)
5Query: http_server_requests_seconds_countjob="order-api" 줄과 job="journal-api" 줄이 각각 한 줄 이상
6Status → Configuration, 브라우저 찾기(Cmd-F · Ctrl-F)로 order-apijob_name: serviceMonitor/apps/order-api/0
타깃 하나 = 파드 하나. order-api를 3개로 늘리면 타깃도 자동으로 3개가 된다. 3번에서 타깃이 안 보이면 실습 가이드 Q4.
job 라벨 값은 Service 이름에서 온다(order-api · journal-api) · 실습 가이드 06 앱 연결 6-2 섹션 참고{{PG}}
  • 두 앱을 수집 대상에 올리는 순서입니다. Prometheus는 localhost:9090에서 열고, 로그인은 없습니다. 질의는 위쪽 Query 입력칸에 넣고 Execute를 누르면 Table 탭에 결과가 나옵니다.
  • 1번으로 ServiceMonitor 두 개를 적용하고, 2번으로 release=kps 라벨을 단 목록에 두 개가 있는지 봅니다.
  • 3번은 1~2분 기다린 뒤 Status → Target health에서 api로 검색합니다. n / n up은 전체 타깃 중 up인 수로, order-api 2 / 2 up, journal-api 3 / 3 up이면 됩니다. 숫자는 파드 수입니다.
  • 4번 up은 타깃마다 수집이 성공하면 1, 실패하면 0인 메트릭입니다. 그래서 count(up)은 타깃 수, sum(up)은 성공한 타깃 수이고, 둘이 같으면 전부 살아 있다는 뜻입니다. 둘 다 33이어야 하고, 스택 설치 직후의 기본 타깃 28개에 앱 파드 5개가 더해진 값입니다.
  • 5번 http_server_requests_seconds_count는 앱이 받은 요청 횟수를 세는 카운터입니다. job="order-api"와 job="journal-api" 줄이 보이면 두 앱의 메트릭이 들어오는 것입니다. job 라벨 값은 Service 이름에서 옵니다.
  • 6번 Status → Configuration은 프로메테우스가 지금 실제로 쓰는 설정 전체입니다. 여기에 serviceMonitor/apps/order-api/0이 있으면 오퍼레이터가 수집 설정을 만든 것입니다. 타깃은 파드 하나에 하나씩 생겨서, 파드를 늘리면 타깃도 자동으로 늘어납니다.
05HOW TO QUERY · PromQL

이 장의 질의는 모두 네 가지 모양을 조합한 것이다

모양예언제 쓰나
① 고르기http_server_requests_seconds_count{job="order-api", status=~"5.."}이름과 라벨로 시계열을 고른다. =~는 정규식
② 속도rate(http_server_requests_seconds_count[5m])카운터(누적)를 초당 값으로. 카운터는 거의 항상 rate로 감싼다
③ 합치기sum by (job) (rate(http_server_requests_seconds_count[5m]))파드 여러 개를 앱 단위로. by에 남길 라벨을 적는다
④ 비율 · 분위수sum(rate(http_server_requests_seconds_count{status=~"5.."}[5m])) / sum(rate(http_server_requests_seconds_count[5m]))
histogram_quantile(0.99, sum by (le) (rate(http_server_requests_seconds_bucket[5m])))		에러 비율, P99. 분위수는 le를 by에 꼭 남긴다
읽는 순서는 안쪽부터: 고르고 → 초당으로 바꾸고 → 앱 단위로 합치고 → 나누거나 분위수를 구한다. 5장의 RED 질의가 모두 이 순서다.
[5m]: 최근 5분의 샘플로 계산한다. 수집 주기(30초)의 4배 이상으로 둔다 · 실습 가이드 07 RED 7-2 섹션 참고{{PG}}
  • 이 장의 PromQL은 모두 네 가지 모양을 조합한 것입니다.
  • ① 고르기는 이름과 라벨로 시계열을 고릅니다. =~는 정규식으로 고른다는 뜻이고, status=~"5.."는 500부터 599까지, 즉 서버 에러 응답만 고릅니다.
  • ② 속도는 rate()로 누적 카운터를 초당 값으로 바꿉니다. 카운터는 계속 쌓이기만 해서 값 자체로는 지금 상황을 알 수 없으므로 거의 항상 rate로 감쌉니다.
  • ③ 합치기의 sum by (job)은 job 라벨만 남기고 나머지 라벨을 모두 합칩니다. 파드가 여러 개라도 앱 하나당 한 줄로 묶입니다.
  • ④는 두 값을 나눠 에러 비율을 구하거나, histogram_quantile()로 P99를 구합니다. 분위수는 구간 경계인 le가 있어야 계산할 수 있어서 by에 le를 꼭 남깁니다.
  • 읽을 때는 안쪽부터 봅니다. 고르고, 초당으로 바꾸고, 앱 단위로 합치고, 마지막에 나누거나 분위수를 구합니다. [5m]은 최근 5분의 샘플로 계산한다는 뜻으로, 수집 주기 30초의 4배 이상으로 둬야 샘플이 충분해 값이 흔들리지 않습니다.

05HOW TO READ

평균 대신 분위수를 보고, 튀면 라벨로 쪼갠다

# order-api, 같은 5분
평균   0.045   # 45ms
P50    0.00058 # 0.58ms
P95    0.725   # 725ms
P99    0.789   # 789ms

# P99를 uri로 쪼갠다
/api/chaos/slow        0.805
/actuator/prometheus   0.0178
/actuator/health/**    0.0040
/api/orders            0.0017
/api/chaos/error       0.0014

1. 평균은 없는 요청을 가리킨다

요청 절반은 1ms 안쪽, 상위 5%는 700ms를 넘는다. 45ms 근처의 요청은 거의 없다(1장 "평균의 함정").

2. 분위수로 꼬리를 본다

P50은 요청 절반이 이 시간 안에 끝났다는 뜻, P99는 가장 느린 1%가 이 시간보다 오래 걸렸다는 뜻. 알림과 SLO는 P95 · P99로 건다.

3. 라벨로 쪼개 원인을 좁힌다

sum by (uri, le)로 바꾸자 느린 경로가 하나로 드러난다(0.805초, 나머지는 18ms 이하). 쪼갤 라벨이 계측에 있어야 가능하다.

Graph 탭에서 uri별 선을 그리면 /api/chaos/slow 하나만 위로 뜬다 · 실습 가이드 07 RED 7-3 섹션 참고{{PG}}
  • 결과를 읽는 순서입니다. 왼쪽 위는 같은 5분 동안의 order-api 값입니다. 평균은 45ms지만 P50은 0.58ms, P95는 725ms, P99는 789ms입니다.
  • 첫째, 평균은 실제로 없는 요청을 가리킵니다. 요청 절반은 1ms 안쪽, 상위 5%는 700ms를 넘어서 45ms 근처의 요청은 거의 없습니다. 빠른 요청과 느린 요청이 두 무리로 나뉘어 있으면 평균은 그 사이 빈 곳에 떨어집니다.
  • 둘째, 분위수로 꼬리를 봅니다. P50은 요청 절반이 이 시간 안에 끝났다는 뜻, P95는 요청 95%가 이 시간 안에 끝났다는 뜻, P99는 가장 느린 1%가 이보다 오래 걸렸다는 뜻입니다. 알림과 SLO는 P95와 P99로 겁니다. SLO는 "요청 99%를 200ms 안에 처리한다"처럼 서비스가 지키기로 한 목표이고, 평균으로 걸면 느린 요청이 숫자에 묻히기 때문입니다.
  • 셋째, 라벨로 쪼개 원인을 좁힙니다. uri로 나누면 /api/chaos/slow만 0.805초이고 나머지는 18ms 이하입니다. 이렇게 쪼개려면 계측할 때 uri 같은 라벨이 붙어 있어야 합니다. 느린 원인이 경로 하나라는 것을 메트릭만으로 찾은 것입니다.
