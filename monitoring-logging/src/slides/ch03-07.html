07

로그를 모으고, LogQL로 원인을 찾는다

파드 로그를 Alloy로 모아 Loki에 쌓는다. 로그가 쌓이는지 확인하고, LogQL로 좁히고 거르고 꺼내는 법을 익힌다. 메트릭에서 본 에러를 같은 시각의 로그로 이어서 확인한다.

개념 + 실습 · 3.8 로깅 개요 · 3.9 로깅 도구 · 3.10 로키를 이용한 로깅{{PG}}
  • 6장 끝의 질문: 알림은 "에러율 6%"까지만 말한다. 어떤 요청에서 왜 났는지는 로그가 답한다.
  • 흐름: 무엇을 로깅하나 → 어떻게 모으나 → 도구 → 앱이 로그를 남기게 하기 → 설치하고 쌓이는지 확인 → LogQL 사용법.
  • 명령과 출력은 실습 가이드(lab-guide.html)의 절차를 kind 클러스터에서 실제로 실행한 결과다.

07WHAT TO LOG · 책 3.8

전부 로깅하면 찾기 어렵고 비싸다

판단기준
찍는다나중에 읽을 일이 있는 줄. 요청 경로·상태 코드·처리 시간, 에러와 원인
찍지 않는다프로브 성공 로그(실패는 이벤트·메트릭에 남는다), "받았다"와 "처리했다" 중복, 정상 응답 본문
보존 기간30~45일. 지난주 장애를 이번 주에 조사하고 몇 주 전과 비교할 수 있는 길이
규정상 장기 보관더 저렴한 저장소로 옮겨 보관한다(예: 금융거래기록 5년)
프로브 로그만으로도 양이 크다. readiness 5초 · liveness 10초 간격이면 파드 둘에서 시간당 2,000줄이 넘는다.
책 3.8: 노이즈가 너무 많아 문제를 빠르게 찾기 힘들어지고, 과도한 리소스가 소모되어 비용이 많이 든다{{PG}}
  • 책 3.8: 디버그 로그는 필요악이라 정답은 없다. 환경을 알수록 어떤 노이즈를 걸러야 할지 감을 잡게 된다. 엔드 유저 관점에서는 30~45일이면 충분하다.
  • 책 역주: 전자금융거래법 제22조는 금융회사 전자금융거래기록을 5년간 보존하도록 한다.
  • 실측: 두 앱에 초당 약 35건씩 넣자 5분에 약 2만 줄(journal-api 9087 · order-api 10750). 초당 300건 서비스라면 하루 수천만 줄.
  • 모든 로그를 같은 기간 보관할 필요는 없다. 감사 로그는 길게, 디버그 로그는 며칠. Loki는 스트림(라벨) 단위로 보존 기간을 다르게 줄 수 있다.
07LOG SOURCES · 책 3.8

클러스터에서 모을 로그는 네 종류다

대상무엇수집하려면
노드kubelet · 컨테이너 런타임(containerd) · 시스템 데몬노드의 저널(journald)을 읽는 수집기
컨트롤 플레인API 서버 · 스케줄러 · 컨트롤러 매니저 · etcd컨트롤 플레인 노드에도 수집기가 떠야 한다(톨러레이션 필요)
감사누가 언제 무엇을 요청했나. 보안 모니터링API 서버에 감사 정책을 켜야 생긴다. 양이 많아 정책으로 줄인다
애플리케이션앱이 stdout·stderr로 내보내는 것DaemonSet 수집기가 파드 로그를 읽는다
컨트롤러 매니저 로그는 이벤트로는 원인이 안 보일 때 쓴다. 책의 예: LoadBalancer 타입 서비스가 대기 상태로 멈춰 있을 때 이유는 컨트롤러 매니저 로그에 있다.
책 3.8: 감사 로그는 로깅 시스템을 처음 가동하면 폭발적으로 쌓일 가능성이 높다{{PG}}
  • 책은 노드 로그의 예로 도커 데몬을 든다. 현재 쿠버네티스 노드의 런타임은 containerd다.
  • 실습 구성의 Alloy는 DaemonSet인데 파드가 2개다. 컨트롤 플레인 노드의 테인트를 견디는 톨러레이션이 없어서 워커 두 대에만 떴다. 그래서 컨트롤 플레인 로그는 수집되지 않는다. 운영이라면 톨러레이션을 넣는다.
  • 감사 로그 정책은 공식 문서 "Auditing"을 참고한다.

07WHY A LOG STORE

파드가 지워지면 kubectl logs도 끝이다

# ① 실행 중
kubectl -n demo logs noisy | tail -1
{"level":"info","msg":"작업 4"}

# ② 파드가 Error로 끝난 뒤
kubectl -n demo logs noisy | tail -1
{"level":"error","msg":"마지막에 터졌다"}

# ③ 파드를 지운 뒤
kubectl -n demo delete pod noisy
kubectl -n demo logs noisy
error: ... pods "noisy" not found
파드가 지워지는 때얼마나 자주
롤아웃배포할 때마다 옛 파드가 지워진다
HPA 축소8개에서 3개로 줄면 5개가 사라진다
노드 비우기(drain)파드가 다른 노드로 옮겨진다
OOM 재시작옛 컨테이너 로그는 하나만 남는다
로그 회전파드가 살아 있어도 오래된 줄은 잘린다
kubectl logs는 파드에 붙어 있는 기능이지 로그 저장소가 아니다. 노드·파드와 수명이 분리된 별도 저장소가 필요하다.
정리: kubectl delete namespace demo · 실습 가이드 10 로그 10-1 섹션 참고{{PG}}
  • 실측. 30초 동안 JSON 로그를 찍다가 에러로 끝나는 파드를 만들었다.
  • 파드가 Error로 끝나도 로그는 남아 있다. 파드 오브젝트가 지워지는 순간 로그도 사라진다.
  • 공식 문서: 파드가 축출되면 그 컨테이너와 로그도 함께 지워진다. 클러스터 수준 로깅에는 노드·파드와 수명이 분리된 백엔드가 필요하다.

07HOW TO · 앱 로그

앱이 요청마다 stdout에 한 줄 남기게 한다

journal-api: 요청마다 JSON 한 줄 (코드에 추가)

{"level":"info","msg":"request","method":"GET",
 "path":"/api/entries","status":200,"durationMs":1,
 "pod":"journal-api-5d8fcd6cf9-rgjrf"}

order-api: 코드 수정 없이 환경 변수로 톰캣 액세스 로그를 stdout에

env:
- {name: SERVER_TOMCAT_ACCESSLOG_ENABLED,   value: "true"}
- {name: SERVER_TOMCAT_ACCESSLOG_DIRECTORY, value: /dev}
- {name: SERVER_TOMCAT_ACCESSLOG_PREFIX,    value: stdout}
- {name: SERVER_TOMCAT_ACCESSLOG_SUFFIX,    value: ""}
- {name: SERVER_TOMCAT_ACCESSLOG_ROTATE,    value: "false"}- {name: SERVER_TOMCAT_ACCESSLOG_PATTERN,
   value: '%h %l %u %t "%r" %s %b %D'}   # %D 처리 시간
127.0.0.1 - - [26/Sep/2026:12:10:42 +0000]
  "GET /api/orders HTTP/1.1" 200 93 1698
수집기는 앱이 쓴 줄만 모은다. 요청 로그는 앱이 켜야 생긴다 · 실습 가이드 10 로그 10-2 섹션 참고{{PG}}
  • 실측. 두 앱 모두 기본 상태에서는 기동할 때만 로그를 남긴다. 요청 로그를 켜야 Loki에서 찾을 것이 생긴다.
  • JSON 한 줄(journal-api)은 | json 파서로, 정해진 자리의 텍스트(order-api)는 | pattern 파서로 필드를 꺼낸다. 새로 만드는 앱이면 JSON이 다루기 쉽다.
  • journal-api: 계측 미들웨어에 로그 한 줄을 더했다. 프로브 경로(/healthz · /readyz · /metrics)는 걸러 낸다. path는 원본 그대로 남긴다. 라벨이 아니라 본문이므로 값의 가짓수가 문제되지 않는다.
  • order-api: 이미지를 다시 만들지 않고 환경 변수만으로 켰다. 남의 앱을 다룰 때 쓰는 방식. 톰캣은 경로별 제외가 없어 프로브 요청까지 모두 남는다. ROTATE=false가 빠지면 로그가 조용히 사라진다(실습 가이드 11 Q&A Q7).
  • 전체 매니페스트: labs/k8s/order-api.yaml
07BEFORE INSTALL · 값 파일

Loki는 저장, Alloy는 파드 로그를 읽어 보내는 파이프라인

loki-values.yaml (일부)

deploymentMode: SingleBinary
loki:
  auth_enabled: false
  commonConfig: {replication_factor: 1}
  storage: {type: filesystem}
  schemaConfig:             # 없으면 설치 실패
    configs: [{store: tsdb, schema: v13, …}]
  limits_config:
    allow_structured_metadata: true
    retention_period: 72hsingleBinary:
  persistence: {enabled: true, size: 10Gi}

alloy-values.yaml 파이프라인 네 토막 (일부)

// 1) 파드를 찾는다
discovery.kubernetes "pods" { role = "pod" }
// 2) 붙일 라벨을 고른다. 고르지 않은 것은 버려진다
discovery.relabel "pod_logs" {
  rule { … target_label = "namespace" }
  rule { … target_label = "pod" }
  rule { … target_label = "app" }
}
// 3) 쿠버네티스 API로 로그를 읽는다
loki.source.kubernetes "pods" { … }
// 4) Loki로 보낸다
loki.write "default" {
  endpoint { url = "http://loki-gateway.logging…/loki/api/v1/push" }
}
전체 파일: loki-values.yaml · alloy-values.yaml · 실습 가이드 10 로그 10-3 섹션 참고{{PG}}
  • 설치 명령: helm upgrade --install loki grafana/loki -n logging --create-namespace --version 7.3.0 -f labs/helm/loki-values.yaml --wait / helm upgrade --install alloy grafana/alloy -n logging --version 1.12.1 -f labs/helm/alloy-values.yaml --wait
  • 설치 결과(실측): loki-0 2/2, loki-gateway 1/1, alloy 파드 2개(워커 노드만). 파드가 여럿 뜨면 SingleBinary에서 마이크로서비스 구성요소(backend · read · write …)를 replicas: 0 으로 내리지 않은 것이다.
  • replication_factor 기본값 3이면 단일 인스턴스가 기동하지 못한다.
  • loki.source.kubernetes 는 쿠버네티스 API로 로그를 읽는다. 호스트의 /var/log 를 마운트하는 방식과 달리 특권 컨테이너가 필요 없다.
  • 두 앱의 라벨 규칙이 다르다(journal-api는 app, order-api는 app.kubernetes.io/name). regex="(.+)" 규칙 두 개로 둘 중 있는 쪽을 app 라벨로 모은다. source_labels 두 개를 separator로 이으면 둘 다 있는 파드에서 값이 붙어 버린다.
  • 라벨로 올리는 것은 namespace · pod · container · app 넷뿐이다. 값의 가짓수가 정해진 것만 라벨로 둔다.
  • retention_period 72h는 실습용. 운영은 30~45일.

07HOW TO QUERY · LogQL

LogQL은 좁히고 → 거르고 → 꺼내고 → 센다

단계예언제 쓰나
① 좁히기{namespace="apps", app="order-api"}라벨로 스트림을 고른다. 항상 여기서 시작한다. 색인을 쓰므로 빠르다
② 거르기|= "/api/chaos/error" · |~ " 500 " · != "health"본문에 문자열 · 정규식이 있는(없는) 줄만. 파서보다 먼저 두면 빠르다
③ 꺼내기| json · | pattern `<_> … <status> <_> <dur>`본문에서 필드를 꺼내 status >= 500처럼 조건을 건다. 뒤에 | __error__=""
④ 세기sum by (status) (count_over_time({…} | … [5m]))줄 수를 메트릭처럼. 그래프 · 알림에 쓴다
PromQL과 모양이 같다: {라벨}로 고르고, [5m] 창으로 세고, sum by로 묶는다. 다른 점은 ②③, 본문을 거르고 꺼내는 단계가 있다는 것이다.
Grafana Explore → Loki → Code 모드에 입력. 로그 질의는 줄 목록, 세기 질의는 그래프로 나온다 · 실습 가이드 10 로그 10-5 섹션 참고{{PG}}
  • ① 없이 본문 검색만 할 수는 없다. Loki는 라벨로 스트림을 고른 뒤 그 안의 덩어리(chunk)만 연다. 좁힐수록 빠르다.
  • pattern의 <_>는 "자리는 있지만 이름은 필요 없음", <status>처럼 이름을 주면 그 자리 값이 필드가 된다.
  • 파서 뒤의 | __error__="" 는 파싱에 실패한 줄을 뺀다. 형식이 섞인 로그에서 세기 질의가 실패하지 않게 한다(실습 가이드 11 Q&A Q8).
