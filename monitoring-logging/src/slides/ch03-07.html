07

로그를 모으고, LogQL로 원인을 찾는다

파드 로그를 Alloy로 모아 Loki에 쌓는다. order-api 로그에서 500 에러를 세고(실측 634건), 그 634건이 모두 /api/chaos/error 한 경로에서 났다는 것을 LogQL로 확인한다.

개념 + 실습 · 3.8 로깅 개요 · 3.9 로깅 도구 · 3.10 로키를 이용한 로깅{{PG}}
  • 7장은 로그입니다. 파드 로그를 Alloy로 모아 Loki에 쌓고, LogQL로 찾아봅니다.
  • Alloy는 각 노드에서 파드 로그를 읽어 보내는 수집기이고, Loki는 그 로그를 받아 쌓아 두는 저장소입니다. LogQL은 Loki에 "어떤 로그를 보여 달라"고 요청하는 질의 언어로, 프로메테우스의 PromQL과 모양이 비슷합니다.
  • 목표는 order-api 로그에서 500 에러를 세고, 그 634건이 모두 /api/chaos/error 한 경로에서 났다는 것을 로그로 확인합니다.

용어 ① 로그 수집과 저장

  • 로그 수집에 쓰는 용어입니다. 구조화 로그는 한 줄을 JSON처럼 키와 값으로 남기는 방식이라 질의할 때 필드를 바로 꺼낼 수 있습니다. 액세스 로그는 웹 서버가 요청마다 경로, 상태 코드, 처리 시간을 한 줄씩 남기는 기록입니다.
  • 예를 들어 구조화 로그는 {"level":"info","status":200,"durationMs":1}처럼 남아서, 나중에 status가 500인 줄만 골라낼 수 있습니다. 일반 문장으로 남긴 로그는 이런 조건 검색이 어렵습니다.
  • 사이드카 로그 전달기는 같은 파드에 붙어 앱의 로그 파일을 옮기는 컨테이너입니다.
  • 사이드카는 앱이 로그를 화면(stdout)이 아니라 파일에만 쓸 때 씁니다. 같은 파드에 작은 컨테이너를 하나 더 붙여 그 파일을 읽고 수집기로 넘깁니다.
  • 로그 회전은 파일이 커지면 잘라 새 파일로 바꾸는 것이라 오래된 줄이 사라집니다. 보존 기간은 저장소가 로그를 지우기 전까지 들고 있는 기간입니다.
  • 톨러레이션은 테인트가 걸린 노드에도 파드를 띄우는 설정이고, SingleBinary는 Loki의 모든 역할을 프로세스 하나로 돌리는 최소 구성입니다. 앱은 stdout으로 내보내기만 하고 수집과 보관은 플랫폼이 맡습니다.
  • 테인트는 노드에 붙이는 "아무 파드나 여기 오지 마라"는 표시이고, 컨트롤 플레인 노드에는 기본으로 걸려 있습니다. 톨러레이션은 파드에 붙이는 "그 표시를 견딜 수 있다"는 허가입니다. 둘이 짝이 맞아야 그 노드에 파드가 뜹니다.
  • stdout은 프로그램이 출력을 내보내는 기본 통로, 즉 표준 출력입니다. 컨테이너가 stdout으로 내보낸 줄은 컨테이너 런타임이 노드의 /var/log/pods 아래 파일로 남기고, kubectl logs와 수집기가 그 내용을 읽습니다. SingleBinary는 이 실습처럼 작은 규모에서 Loki를 가볍게 띄울 때 씁니다.

용어 ② LogQL

어디서 쳐 보나브라우저 localhost:3000(Grafana) → Explore → 데이터소스 Loki → 편집기 오른쪽 Code → 질의 입력 → Run query. 직접 쳐 보는 것은 Loki 설치 뒤
용어원어 · 풀 네임뜻
스트림 셀렉터Stream selector{namespace="apps", app="order-api"}. 라벨로 스트림을 고른다
줄 필터Line filter · |= |~본문에 문자열이 있는 줄만 남긴다. |~는 정규식
파서Parser · | json | pattern본문에서 필드를 꺼낸다. json은 JSON 줄, pattern은 고정 형식 줄
__error__파싱 에러 라벨파서가 실패한 줄에 붙는다. | __error__=""로 걸러 낸다
count_over_timeLogQL 함수구간 안의 로그 줄 수. 로그를 시계열처럼 센다
구조화 메타데이터Structured metadata라벨 인덱스를 늘리지 않고 줄마다 필드를 붙이는 방식
셀렉터로 좁히고 → 필터로 거르고 → 파서로 꺼낸다{{PG}}
  • LogQL 용어입니다. 스트림 셀렉터는 {namespace="apps", app="order-api"}처럼 라벨로 로그 묶음을 고르는 부분입니다.
  • 줄 필터 |=와 |~는 본문에 문자열이나 정규식이 있는 줄만 남깁니다. 파서 | json, | pattern은 본문에서 필드를 꺼내고, 파싱에 실패한 줄에는 __error__ 라벨이 붙어 | __error__=""로 걸러 냅니다.
  • 예를 들어 |= "error"는 본문에 error라는 글자가 있는 줄만 남기고, |~ " 5.. "처럼 정규식을 쓰면 500번대 상태 코드가 있는 줄을 한 번에 고릅니다. !=는 반대로 그 글자가 있는 줄을 뺍니다.
  • count_over_time은 구간 안의 줄 수를 세서 로그를 시계열처럼 다루게 합니다. 순서는 셀렉터로 좁히고, 필터로 거르고, 파서로 꺼냅니다.
  • 구조화 메타데이터는 라벨로 만들기에는 값의 가짓수가 너무 많은 정보, 예를 들어 요청마다 다른 요청 ID를 줄에 붙여 두는 방식입니다. 라벨처럼 색인하지 않아서 저장 비용이 늘지 않습니다.

07WHAT TO LOG · 책 3.8

전부 로깅하면 찾기 어렵고 비싸다

판단기준
남긴다나중에 읽을 일이 있는 줄. 요청 경로·상태 코드·처리 시간, 에러와 원인
남기지 않는다프로브 성공 로그(실패는 이벤트·메트릭에 남는다), "받았다"와 "처리했다" 중복, 정상 응답 본문
어디로 내보내나파일이 아니라 stdout · stderr. 파일에 쓰면 파드가 지워질 때 같이 사라지고 수집기도 읽지 못한다
보존 기간30~45일. 지난주 장애를 이번 주에 조사하고 몇 주 전과 비교할 수 있는 길이
규정상 장기 보관더 저렴한 저장소로 옮겨 보관한다(예: 금융거래기록 5년)
프로브 로그만으로도 양이 크다. readiness 5초 · liveness 10초 간격이면 파드 둘에서 시간당 2,000줄이 넘는다.
책 3.8: 노이즈가 너무 많아 문제를 빠르게 찾기 힘들어지고, 과도한 리소스가 소모되어 비용이 많이 든다{{PG}}
  • 전부 로깅하면 찾기 어렵고 비용이 큽니다. 그래서 무엇을 남길지부터 정합니다.
  • 남길 것은 나중에 읽을 일이 있는 줄, 즉 요청 경로, 상태 코드, 처리 시간, 에러와 원인입니다. 프로브 성공 로그, 같은 내용을 두 번 남기는 줄, 정상 응답 본문은 남기지 않습니다.
  • 프로브는 kubelet이 앱에 주기적으로 보내는 확인 요청입니다. readiness는 "요청을 받을 준비가 됐나", liveness는 "아직 살아 있나"를 확인합니다. 성공할 때마다 로그를 남기면 의미 없는 줄만 쌓입니다.
  • 어디로 내보낼지도 정해 둡니다. 앱은 로그를 파일이 아니라 표준 출력, stdout과 stderr로 내보냅니다. 컨테이너 안 파일에 쓰면 파드가 지워질 때 함께 사라지고 수집기도 읽지 못합니다. stdout으로 내보낸 줄은 노드에 남고, 이 실습에서는 Alloy가 쿠버네티스 API로 모아 Loki로 보냅니다.
  • 보존 기간은 지난주 장애를 이번 주에 조사하고 몇 주 전과 비교할 수 있도록 30~45일을 둡니다. 규정상 오래 보관해야 하는 로그는 더 저렴한 저장소로 옮깁니다.
  • 프로브 로그만으로도 양이 큽니다. readiness 5초, liveness 10초 간격이면 파드 둘에서 시간당 2,000줄이 넘습니다.
07WHY A LOG STORE

파드가 지워지면 kubectl logs도 끝이다

접속터미널 · 작업 폴더 monitoring-logging로그인필요 없음메뉴없음 (명령만)
# 준비: 30초 동안 로그를 남기고 에러로 종료되는 파드
kubectl create namespace demo
kubectl -n demo apply -f labs/k8s/noisy-pod.yaml

# ① 실행 중 (8초 뒤)
sleep 8; kubectl -n demo logs noisy | tail -1
{"level":"info","msg":"작업 4"}

# ② 30초 더 기다려 파드가 Error로 끝난 뒤
sleep 30; kubectl -n demo logs noisy | tail -1
{"level":"error","msg":"마지막에 터졌다"}

# ③ 파드를 지운 뒤
kubectl -n demo delete pod noisy
kubectl -n demo logs noisy
error: error from server (NotFound): pods "noisy"
not found in namespace "demo"
파드가 지워지는 때얼마나 자주
롤아웃배포할 때마다 옛 파드가 지워진다
HPA 축소8개에서 3개로 줄면 5개가 사라진다
노드 비우기(drain)파드가 다른 노드로 옮겨진다
OOM 재시작옛 컨테이너 로그는 하나만 남는다
로그 회전파드가 살아 있어도 오래된 줄은 잘린다
kubectl logs는 파드에 붙어 있는 기능이지 로그 저장소가 아니다. 노드·파드와 수명이 분리된 별도 저장소가 필요하다.
정리: kubectl delete namespace demo · 실습 가이드 10 로그 10-1 섹션 참고{{PG}}
  • kubectl logs만으로는 왜 부족한지 직접 보겠습니다. 30초 동안 로그를 남기고 에러로 끝나는 noisy 파드를 demo 네임스페이스에 만듭니다.
  • 8초 뒤에는 "작업 4" 같은 진행 로그가, 30초 더 지나면 마지막 줄 "마지막에 터졌다"가 보입니다. 파드가 Error로 끝나도 로그는 아직 남아 있습니다.
  • 그런데 파드를 지우고 다시 kubectl logs를 치면 NotFound가 나옵니다. 로그가 파드와 함께 사라진 것입니다.
  • 오른쪽 표처럼 파드는 롤아웃, HPA 축소, 노드 비우기, OOM 재시작, 로그 회전 때마다 지워지거나 잘립니다. 그래서 노드, 파드와 수명이 분리된 별도 로그 저장소가 필요합니다. 실습이 끝나면 demo 네임스페이스를 지웁니다.
  • HPA는 부하에 따라 파드 수를 자동으로 늘리고 줄이는 기능이라, 줄일 때 파드가 사라집니다. 노드 비우기는 노드를 점검하기 전에 그 위의 파드를 다른 노드로 옮기는 작업입니다. OOM 재시작은 컨테이너가 메모리 한도를 넘어 강제로 종료된 뒤 다시 뜨는 것인데, 이때 kubectl logs --previous로 볼 수 있는 것은 바로 직전 컨테이너 하나의 로그뿐입니다.
07LOGGING TOOLS · 책 3.9

로깅 도구는 무엇을 색인하나로 비용이 갈린다

도구운영 형태저장 · 검색 방식
Loki설치형 또는 SaaS라벨만 색인, 본문은 압축 저장. 싸지만 본문 검색은 스트림을 훑는다
Elastic Stack설치형 또는 SaaS본문 전체를 색인(전문 검색). 검색이 빠르지만 저장·메모리가 크다
Datadog · Sumo LogicSaaS벤더 저장소. 에이전트가 보낸다
클라우드 서비스클라우드 관리형CloudWatch Logs · Cloud Logging · Azure Monitor Logs
책 3.9: 로그 중앙화 도구는 운영 비용 절감 차원에서 호스티드 서비스도 검토한다. 직접 호스팅하면 며칠은 괜찮아도 환경이 커질수록 관리에 막대한 시간이 든다.
책 3.9: 데몬셋으로 실행할 수 있는지, STDOUT을 못 쓰는 앱을 위해 사이드카로도 쓸 수 있는지 살핀다{{PG}}
  • 로깅 도구는 무엇을 색인하느냐에 따라 비용이 갈립니다.
  • 색인은 책 뒤의 찾아보기처럼, 어떤 값이 어디에 있는지 미리 정리해 둔 목록입니다. 많이 색인할수록 검색은 빨라지지만 저장 공간과 메모리를 더 씁니다.
  • Loki는 라벨만 색인하고 본문은 압축해 저장합니다. 저렴하지만 본문 검색은 스트림을 훑어서 합니다. Elastic Stack은 본문 전체를 색인해 검색이 빠른 대신 저장 공간과 메모리를 많이 씁니다.
  • 스트림은 라벨 조합이 같은 로그 줄의 묶음입니다. 예를 들어 namespace가 apps이고 app이 order-api인 로그가 하나의 스트림입니다. Loki는 라벨로 스트림을 고른 뒤 그 안의 본문만 훑어서 검색합니다. 전문 검색은 본문의 모든 단어를 색인해 두는 방식입니다.
  • Datadog, Sumo Logic 같은 SaaS나 클라우드 관리형 서비스도 있습니다. 규모가 커질수록 직접 운영하는 부담이 커지므로 호스티드 서비스도 함께 검토합니다. 도구를 고를 때는 데몬셋으로 돌릴 수 있는지, 사이드카로도 쓸 수 있는지를 봅니다.
  • SaaS는 직접 설치하지 않고 업체가 운영하는 서비스를 빌려 쓰는 형태입니다. 호스티드 서비스도 같은 뜻입니다.

  • PATTERN의 기호는 한 줄에 들어갈 칸입니다. %h는 클라이언트 IP, %l과 %u는 쓰지 않는 칸이라 -로 채워지고, %t는 시각, %r은 요청 줄, %s는 상태 코드, %b는 헤더를 뺀 응답 바이트, %D는 처리 시간입니다.
  • kubectl -n apps logs deploy/order-api --tail=1의 마지막 줄에서 200은 상태 코드, 25는 응답 바이트, 662는 662마이크로초입니다.
07BEFORE INSTALL · 값 파일

Loki는 저장, Alloy는 파드 로그를 읽어 보내는 파이프라인

전체 파일: loki-values.yaml · alloy-values.yaml · 실습 가이드 10 로그 10-3 섹션 참고{{PG}}
  • 설치 전에 값 파일을 봅니다. Loki는 로그를 저장하고, Alloy는 파드 로그를 읽어 Loki로 보내는 수집기입니다.
  • loki-values.yaml은 SingleBinary 모드, 복제 1개, 파일시스템 저장소로 최소 구성을 잡습니다. schemaConfig는 없으면 설치가 실패하므로 꼭 넣습니다.
  • auth_enabled: false는 멀티테넌시를 끄는 설정입니다. 켜 두면 요청마다 어느 조직의 로그인지 알리는 X-Scope-OrgID 헤더가 필요합니다. replication_factor: 1은 로그를 한 벌만 저장한다는 뜻이고, schemaConfig는 로그 색인을 어떤 형식(tsdb, v13)으로 쌓을지 정합니다.
  • retention_period: 72h는 사흘이 지난 로그를 지우겠다는 설정입니다. 실제로 지우는 일은 compactor가 하므로 retention_enabled: true와 delete_request_store를 함께 넣습니다.
  • compactor는 Loki 안에서 저장된 데이터를 정리하는 구성요소입니다. 작은 색인 파일을 합치고, 보존 기간이 지난 로그를 실제로 지웁니다. persistence 10Gi는 Loki 파드가 다시 떠도 로그가 남도록 10GiB 디스크를 붙이는 설정입니다.
  • alloy-values.yaml은 네 단계입니다. 파드를 찾고, 붙일 라벨을 고르고, 쿠버네티스 API로 로그를 읽고, Loki로 보냅니다. clustering을 켜면 Alloy 파드끼리 수집 대상을 나눠 맡아 같은 로그를 두 번 보내지 않습니다.
  • discovery.kubernetes는 클러스터의 파드 목록을 가져오고, discovery.relabel은 파드 정보 가운데 namespace, pod, app처럼 고른 것만 라벨로 남깁니다. 라벨을 아무거나 늘리면 안 되는 이유는 라벨 값 하나하나가 스트림 하나가 되기 때문입니다. 요청 경로처럼 값의 가짓수가 많은 것을 라벨로 올리면 스트림이 폭증하는데, 이것을 라벨 카디널리티 문제라고 합니다.
  • loki.source.kubernetes는 쿠버네티스 API로 파드 로그를 읽어 옵니다. 노드의 파일을 직접 읽지 않아서 특별한 권한이 필요 없습니다. loki.write는 읽은 로그를 Loki 앞단의 입구인 loki-gateway 주소로 보냅니다.

07HOW TO QUERY · LogQL

LogQL은 좁히고 → 거르고 → 꺼내고 → 센다

단계예언제 쓰나
① 좁히기{namespace="apps", app="order-api"}라벨로 스트림을 고른다. 항상 여기서 시작한다. 색인을 쓰므로 빠르다
② 거르기|= "/api/chaos/error" · |~ " 500 " · != "health"본문에 문자열 · 정규식이 있는(없는) 줄만. 파서보다 먼저 두면 빠르다
③ 꺼내기| json · | pattern `<_> <_> <_> [<_>] "<method> <path> <_>" <status> <_> <dur>`본문에서 필드를 꺼내 status >= 500처럼 조건을 건다. 뒤에 | __error__=""
④ 세기sum by (app) (count_over_time({namespace=~"journal|apps"}[5m]))줄 수를 메트릭처럼. 그래프 · 알림에 쓴다
PromQL과 모양이 같다: {라벨}로 고르고, [5m] 창으로 세고, sum by로 묶는다. 다른 점은 본문을 거르고(②) 꺼내는(③) 단계가 있다는 점이다.
따라하기 ①에서 연 Explore의 Code 모드에 입력한다. 로그 질의는 줄 목록, 세기 질의는 Options → Type: Instant로 두면 숫자로 나온다 · 실습 가이드 10 로그 10-5 섹션 참고{{PG}}
  • LogQL은 네 단계로 씁니다. 좁히고, 거르고, 꺼내고, 셉니다.
  • ① 좁히기는 라벨 셀렉터로 스트림을 고르는 단계입니다. 모든 질의가 여기서 시작하고, 색인을 쓰므로 빠릅니다. ② 거르기는 |=, |~, !=로 본문에 어떤 문자열이 있는 줄만 남깁니다.
  • 예를 들어 != "health"를 붙이면 헬스 체크 줄을 빼고 볼 수 있습니다. 거르기를 파서보다 앞에 두면 파싱할 줄이 줄어들어 질의가 빨라집니다.
  • ③ 꺼내기는 파서로 본문의 필드를 꺼냅니다. JSON 로그는 | json, 액세스 로그는 | pattern으로 자리를 맞춥니다. <_>는 버리는 자리이고 <status>처럼 이름을 주면 그 값이 필드가 됩니다. 뒤에 | __error__=""를 붙여 파싱에 실패한 줄을 뺍니다.
  • 처리 시간 dur로 거를 때는 단위가 마이크로초라 0.5초는 500000입니다. 줄 끝의 줄바꿈 때문에 비교 앞에 | label_format dur=`{{ trim .dur }}`를 넣고 | dur > 500000을 붙입니다.
  • ④ 세기는 count_over_time으로 줄 수를 세고 sum by로 묶습니다. PromQL과 모양이 같고, 본문을 거르고 꺼내는 단계가 더 있다는 점만 다릅니다. 로그 질의는 줄 목록으로, 세기 질의는 Type을 Instant로 두면 숫자로 나옵니다.
  • [5m]은 최근 5분 동안이라는 창입니다. 5분 안에 들어온 줄 수를 세고, sum by (app)으로 앱별로 합칩니다.

5번을 하지 않으면 관측 스택과 두 앱이 그대로 남아, 다음에 4장부터 다시 해 볼 수 있다. Docker 메모리를 돌려받으려면 5번까지 한다.

  • 실습이 끝나면 부하, 포트, 클러스터를 정리합니다.
  • 1번, k6가 돌고 있으면 그 터미널에서 Ctrl-C를 누르거나 pkill -f k6-red로 멈춥니다. 2번, pkill로 port-forward를 모두 끕니다.
  • pkill은 이름으로 프로세스를 찾아 끄는 명령이고, -f는 프로그램 이름뿐 아니라 실행할 때 쓴 명령줄 전체에서 찾으라는 뜻입니다. pgrep은 끄지 않고 찾기만 합니다. 뒤의 || echo "없음"은 찾은 것이 하나도 없을 때 "없음"을 출력합니다.
  • 3번, pgrep으로 확인해서 "없음" 한 줄이 나오면 백그라운드 프로세스가 모두 멈춘 것입니다. 4번, demo 네임스페이스를 지웁니다.
  • 5번은 클러스터를 통째로 지울 때만 합니다. kind delete cluster --name obs로 노드 세 개가 지워집니다. 5번을 하지 않으면 관측 스택과 두 앱이 남아 4장부터 다시 해 볼 수 있고, Docker 메모리를 돌려받으려면 5번까지 합니다.
