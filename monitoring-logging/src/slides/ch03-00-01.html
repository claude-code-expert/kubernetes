00OUR QUESTION

"주문이 느려요"라는 제보 한 건을 끝까지 따라간다

1 · 메트릭으로 분석얼마나 느린가

P99 790ms.
평균 45ms만 보면 멀쩡해 보였다

2 · 메트릭으로 분석무엇이 느린가

URI별로 나눠 보니
/api/chaos/slow만 805ms

3 · 알림으로 확인사람이 안 봐도 알린다

AppHighErrorRate 발화
"order-api 에러율 5.9%"

4 · 로그로 원인 분석그 에러는 무엇이었나

알림이 난 시각의 로그에서
실패한 요청을 찾는다

P99 · 99th PERCENTILE

가장 느린 1% 요청의 경계값

요청 100건을 빠른 순으로 줄 세웠을 때 99번째 요청의 응답 시간. "P99 790ms"는 99%는 790ms 안에 끝났고, 가장 느린 1%는 그보다 오래 걸렸다는 뜻이다. 평균이 가리는 느린 요청을 드러낸다.

ALERT · FIRING

AppHighErrorRate가 "발화"했다

AppHighErrorRate는 우리가 정의한 알림 규칙의 이름이다. 조건은 "5xx(서버 오류) 응답 비율이 5%를 넘는 상태가 2분 이상 지속". 조건이 충족되면 규칙이 firing(발화) 상태가 되고 Alertmanager가 담당자에게 알림을 보낸다.

메트릭으로 분석하고, 알림으로 확인한 뒤, 로그로 원인을 분석한다.
메트릭 → 알림 → 로그{{PG}}
  • 오늘은 "주문이 느려요"라는 제보 한 건을 끝까지 따라갑니다. 메트릭으로 두 번 분석하고, 알림으로 확인한 뒤, 로그로 원인을 찾습니다.
  • 첫째, 얼마나 느린가입니다. 평균은 45ms로 멀쩡해 보이지만 P99는 790ms입니다. P99는 요청 100건을 빠른 순으로 세웠을 때 99번째 요청의 응답 시간, 즉 가장 느린 1%의 경계값입니다.
  • 둘째, 무엇이 느린가입니다. URI별로 나눠 보면 /api/chaos/slow 하나만 805ms입니다.
  • 셋째, 사람이 보지 않아도 알림이 옵니다. AppHighErrorRate는 5xx 응답 비율이 5%를 넘는 상태가 2분 이상 이어지면 발화하는 규칙입니다. 넷째, 알림이 난 시각의 로그에서 실패한 요청을 찾습니다.
  • 5xx는 500번대 HTTP 응답 코드로, 요청은 맞았는데 서버 쪽에서 처리하다 실패했다는 뜻입니다. 규칙의 조건이 채워진 상태를 firing, 우리말로 발화라고 하고, 발화하면 Alertmanager가 담당자에게 알림을 보냅니다.

메트릭과 로그는 수집 경로가 다르고, 보는 화면은 하나다

{{FIG:ch03-fig1-pipeline.svg}}

TSDB(Time Series Database · 시계열 데이터베이스): 값을 측정 시각과 한 쌍으로 묶어 메트릭 이름·라벨별로 시간 순서대로 쌓는 저장소. 프로메테우스에 내장되어 있다.

메트릭은 위 줄, 로그는 아래 줄{{PG}}
  • 오늘 전체 지도입니다. 위 줄이 메트릭, 아래 줄이 로그이고, 왼쪽부터 신호가 생기는 곳, 수집, 저장, 활용 순서입니다.
  • 메트릭은 노드의 node-exporter, kubelet 안의 cAdvisor, kube-state-metrics, 앱의 /actuator/prometheus에서 나옵니다. 프로메테우스가 30초마다 가져와 3일 또는 4GB까지 저장하고, Grafana로 보거나 알림 규칙이 Alertmanager로 알림을 보냅니다.
  • 로그는 컨테이너가 stdout으로 출력한 줄이 노드의 /var/log/pods 파일로 남고, Alloy가 라벨을 붙여 Loki로 보냅니다. Loki는 라벨만 색인하고, Grafana Explore에서 LogQL로 메트릭과 나란히 조회합니다.
  • 아래 TSDB는 시계열 데이터베이스입니다. 값을 측정 시각과 한 쌍으로 묶어 메트릭 이름과 라벨별로 시간 순서대로 쌓는 저장소이고, 프로메테우스 안에 들어 있습니다.

00MAP TERMS · 1/3 · 메트릭 수집과 저장

프로메테우스는 대상에서 메트릭을 가져와 시간 순으로 저장한다

용어원어 · 풀 네임뜻
스크레이프Scrape프로메테우스가 대상의 HTTP 주소(/metrics 등)에 주기적으로 요청해 그 순간의 메트릭 값을 가져가는 동작. 실습 주기는 30초
풀 방식Pull model수집기가 대상에 요청해서 가져온다. 반대는 대상이 수집기로 밀어 넣는 푸시(Push) 방식
타깃Target스크레이프할 대상 하나(주소 + 경로). 쿠버네티스에서는 라벨로 자동 발견한다. 같은 목적의 타깃 묶음은 잡(Job)
Prometheus프로메테우스 · CNCF(Cloud Native Computing Foundation) 졸업 프로젝트메트릭을 수집 · 저장 · 질의하고 알림 규칙을 평가하는 모니터링 시스템
TSDBTime Series Database · 시계열 데이터베이스(시각, 값) 쌍을 메트릭 이름 + 라벨별로 저장하는 DB. 프로메테우스는 자기 로컬 디스크에 2시간 단위 블록으로 쌓고, 보존 기한(실습: 3일 또는 4GB)이 지나면 지운다
최근 2시간치 데이터는 메모리에 있다. 들어온 값을 WAL(Write-Ahead Log · 선행 기록 로그)에 먼저 적어 두기 때문에 재시작해도 복구된다.
스크레이프는 가져오는 동작, TSDB는 시간 순 저장소{{PG}}
  • 메트릭 수집과 저장에 쓰는 용어입니다. 스크레이프는 프로메테우스가 대상의 /metrics 같은 HTTP 주소에서 메트릭을 주기적으로 가져가는 동작이고, 주기는 30초입니다. 수집기가 직접 가져오는 이 방식을 풀 방식이라고 합니다.
  • 타깃은 스크레이프할 대상 하나, 즉 주소와 경로입니다. 쿠버네티스에서는 라벨로 자동으로 찾고, 같은 목적의 타깃 묶음을 잡이라고 부릅니다.
  • 프로메테우스는 메트릭을 수집, 저장, 질의하고 알림 규칙을 평가하는 시스템입니다. 저장소 TSDB는 로컬 디스크에 2시간 단위 블록으로 쌓고, 3일 또는 4GB가 지나면 오래된 것부터 지웁니다.
  • 풀 방식의 반대는 푸시 방식으로, 대상이 수집기에게 직접 값을 보내는 방식입니다. 잡의 예를 들면, order-api 파드 두 개는 타깃 두 개이고 이 둘이 order-api라는 잡 하나로 묶입니다.
  • CNCF는 쿠버네티스를 관리하는 재단이고, 졸업 프로젝트는 널리 쓰여 성숙했다고 인정받은 단계입니다. WAL은 받은 값을 본 저장소에 넣기 전에 받은 순서대로 먼저 적어 두는 기록이라, 프로세스가 갑자기 죽어도 이 기록을 다시 읽어 복구합니다.
  • 최근 2시간치는 메모리에 있지만, 들어온 값을 WAL에 먼저 적어 두기 때문에 재시작해도 복구됩니다.

00MAP TERMS · 2/3 · 로그 수집과 저장

Alloy가 로그를 수집해 보내고, Loki가 저장하고 조회한다

용어원어 · 풀 네임뜻
stdout · stderrStandard output · Standard error (표준 출력 · 표준 에러)프로그램이 출력을 내보내는 기본 통로. 컨테이너가 여기로 쓴 줄을 런타임이 노드의 /var/log/pods 아래 파일로 남긴다
AlloyGrafana Alloy · 그라파나 랩스의 수집 에이전트OpenTelemetry Collector 배포판에 프로메테우스 파이프라인을 내장한 수집기. 파드 로그를 읽어 라벨을 붙이고 Loki로 보낸다
LokiGrafana Loki · 로그 집계 시스템로그를 저장하고 조회한다. 로그 본문은 색인하지 않고 라벨만 색인하며, 본문은 압축 덩어리(chunk)로 저장한다. 색인이 작아 저장 비용이 낮다
로그 스트림Log stream라벨이 모두 같은 로그 줄의 묶음. Loki는 먼저 라벨로 스트림을 고르고, 그 안의 로그만 검색한다
프로메테우스가 메트릭을 라벨로 다루듯, Loki는 로그를 라벨로 다룬다{{PG}}
  • 로그 수집과 저장에 쓰는 용어입니다. stdout과 stderr는 프로그램이 출력을 내보내는 기본 통로이고, 컨테이너가 여기로 쓴 줄은 노드의 /var/log/pods 아래 파일로 남습니다.
  • Alloy는 그라파나 랩스의 수집 에이전트로, 파드 로그를 읽어 라벨을 붙이고 Loki로 보냅니다. Loki는 로그를 저장하고 조회하는데, 본문은 색인하지 않고 라벨만 색인해서 저장 비용이 낮습니다.
  • OpenTelemetry Collector는 메트릭, 로그, 트레이스를 받아 가공한 뒤 다른 곳으로 보내는 표준 수집기입니다. Alloy는 이것을 바탕으로 만든 그라파나 랩스의 배포판입니다.
  • 색인은 책 뒤의 찾아보기처럼 무엇이 어디에 있는지 적어 둔 목록입니다. Loki는 namespace, app 같은 라벨의 목록만 만들고 본문은 chunk라는 압축 덩어리로 저장합니다. 그래서 본문 단어로 찾을 때는 라벨로 고른 덩어리만 풀어서 읽습니다.
  • 로그 스트림은 라벨이 모두 같은 로그 줄의 묶음입니다. Loki는 먼저 라벨로 스트림을 고르고 그 안에서만 검색합니다. 프로메테우스가 메트릭을 라벨로 다루듯, Loki는 로그를 라벨로 다룹니다.

메트릭을 제공하는 구성요소와 시각화·알림 도구

{{FIG:ch03-fig10-provide-consume.svg}}
메트릭 제공 → 저장 → 시각화·알림{{PG}}
  • 왼쪽은 메트릭을 제공하는 구성요소입니다. node-exporter는 노드의 CPU, 메모리, 디스크, 네트워크를, kubelet 안의 cAdvisor는 컨테이너별 사용량을, kube-state-metrics는 레플리카 수나 파드 단계 같은 오브젝트 상태를 메트릭으로 만듭니다. order-api는 /actuator/prometheus로 자기 요청 수, 에러, 지연을 직접 제공합니다.
  • 가운데 프로메테우스가 30초마다 수집해 시계열로 저장하고 알림 규칙을 평가합니다. 로그는 Alloy가 모아 Loki에 저장합니다.
  • 오른쪽은 메트릭을 활용하는 도구입니다. Alertmanager는 프로메테우스가 보낸 알림을 받아서 바로 넘기지 않고 세 가지를 거칩니다. 같은 알림이 여러 번 들어와도 한 번만 보내는 중복 제거, 비슷한 알림 여러 개를 한 통으로 합치는 묶기, 그리고 심각도에 따라 받을 곳을 고르는 경로 지정입니다. 그다음 Slack, 메일, PagerDuty로 보냅니다. PagerDuty는 당직자 호출 서비스입니다. 당직 일정표에 따라 지금 당번인 사람에게 전화나 앱 알림을 보내고, 확인할 때까지 반복하며, 정해진 시간 안에 아무도 받지 않으면 다음 담당자에게 넘깁니다. 그래서 새벽에도 사람을 깨워야 하는 critical 알림은 PagerDuty로, 업무 시간에 보면 되는 warning은 Slack으로 나눠 보내는 경우가 많습니다.
  • 침묵(silence)은 알림을 정해 둔 시간 동안 일부러 끄는 기능입니다. 예를 들어 밤 10시부터 30분 동안 노드를 점검한다면, 그 사이에 울릴 알림을 미리 침묵으로 막아 둡니다. 시간이 지나면 자동으로 풀립니다.
  • 억제(inhibit)는 더 심각한 알림이 울리는 동안 덜 심각한 알림을 숨기는 기능입니다. 이 실습에서는 같은 네임스페이스에서 같은 이름의 critical 알림이 울리고 있으면 warning 알림은 보내지 않습니다. 같은 문제로 알림이 두 통씩 오는 것을 막기 위해서입니다.
  • Grafana는 프로메테우스에는 PromQL로, Loki에는 LogQL로 질의해서 대시보드와 조회 화면을 그립니다. 데이터를 따로 저장하지 않고 화면을 열 때마다 가져옵니다.

USE는 자원을, RED는 서비스를 본다{{PG}}
  • USE는 자원마다 사용률, 포화도, 에러를 보는 인프라용 방법이고, RED는 서비스마다 처리율, 에러, 처리 시간을 보는 서비스용 방법입니다.
  • SLO는 "요청의 99%가 300ms 안에" 같은 서비스 수준 목표이고, SLI는 그 달성 여부를 판정하려고 재는 값, 예를 들어 300ms 안에 끝난 요청 비율입니다.
  • 레이턴시는 요청 하나를 처리하는 데 걸린 시간입니다. P99는 가장 느린 1%를 뺀 나머지가 모두 이 값 이하라는 뜻이고, P50은 중앙값입니다. 이 백분위수는 값을 구간별로 센 히스토그램으로 계산합니다.
  • SRE는 구글이 운영 업무를 소프트웨어 엔지니어링으로 다루려고 만든 방식이자 그 일을 하는 직무 이름입니다. 히스토그램은 응답 시간을 "100ms 이하 몇 건, 300ms 이하 몇 건"처럼 구간별로 센 것이고, 이 구간을 버킷이라고 부릅니다. 버킷의 개수 분포로 P99 같은 백분위수를 계산합니다.

METRIC

정해진 기간에 측정한 수치

http_server_requests_seconds_count{
  uri="/api/orders", status="500"} 731

크기가 작아 오래 보관하고 빠르게 집계할 수 있다. 대신 개별 요청의 정보는 숫자로 합쳐지면서 사라진다.

LOG

실행 중 일어난 사건의 기록

10.244.1.1 - - [05/Sep/2026:13:52:10 +0000]
  "GET /api/chaos/error HTTP/1.1" 500 15 3

요청마다 어느 경로가 언제, 얼마나 걸려 실패했는지 남는다. 대신 양이 많아 저장 비용이 크고, 개수를 세려면 전부 읽어야 한다.

메트릭으로는 느리다는 사실까지만 알 수 있고, 원인은 앱이 남긴 로그에서 찾는다. 메트릭으로 먼저 좁히고, 로그로 확인한다.
책 3.1: 메트릭과 로그는 서로 보완하지만 용도가 다르다{{PG}}
  • 메트릭은 횟수와 수치를, 로그는 사건의 내용을 알려 줍니다.
  • 왼쪽 메트릭 한 줄은 이름, 라벨, 값으로 되어 있습니다. 731은 /api/orders 경로에서 500 응답으로 끝난 요청이 지금까지 누적 731건이라는 뜻입니다. 계속 쌓이기만 하는 카운터라서, 지금 문제가 있는지는 초당 증가량을 계산해야 알 수 있습니다.
  • 오른쪽 로그는 요청 하나가 끝날 때 남는 액세스 로그 한 줄입니다. 앞에서부터 클라이언트 IP, 시각, 요청 줄, 상태 코드 500이고, 15는 응답 본문 크기(바이트), 3은 처리 시간이며 단위는 마이크로초입니다.
  • 메트릭은 작아서 오래 보관하고 빨리 집계하지만 개별 요청 정보는 숫자 안에 묻힙니다. 로그는 요청마다 무슨 일이 있었는지 남지만 양이 많습니다. 그래서 메트릭으로 먼저 좁히고 로그로 확인합니다.

  • 메트릭으로 시간과 대상을 좁힌 뒤 로그를 봅니다.
  • 첫째, 메트릭에서 에러율이 오른 것을 발견하고, 언제부터 어느 앱의 어느 uri인지 라벨로 나눠 봅니다. 둘째, 그 시간 범위와 namespace=apps, app=order-api 라벨을 로그 조회 조건에 그대로 씁니다. 셋째, 좁혀진 수백 줄에서 어느 경로가 어떤 상태 코드로 얼마 만에 실패했는지 확인합니다.
  • 순서를 거꾸로 하면 하루 수백만 줄을 훑게 됩니다. 이렇게 이어 보려면 메트릭과 로그가 namespace, pod, app처럼 같은 라벨 이름을 써야 합니다.
  • grep은 파일에서 특정 글자가 들어 있는 줄을 찾는 명령입니다. 무엇을 찾을지 모르는 상태에서 수백만 줄에 grep을 거는 것이 거꾸로 했을 때의 모습입니다.

01WHY K8S IS DIFFERENT · 책 3.3

파드는 VM처럼 고정된 대상으로 모니터링할 수 없다

항목24/7 가동 VM쿠버네티스 파드
수명몇 달~몇 년배포·축소·장애 때마다 교체. 수명이 짧다(transient)
주소·이름고정 IP · 호스트명교체될 때마다 새 IP · 새 접미사(order-api-7c9…-x2kqp)
감시 대상 등록사람이 목록에 적는다API 서버에서 라벨로 자동으로 찾는다(서비스 디스커버리)
기록호스트 디스크에 남는다파드가 지워지면 그 컨테이너 로그도 노드에서 지워진다
kubectl top해당 없음metrics-server는 메모리에 있는 최근값만 보여 준다. 한 시간 전 값은 없다
그래서 쿠버네티스 모니터링에는 두 가지가 필요하다. 대상을 라벨로 찾아 수집하는 것, 값을 시간에 걸쳐 쌓아 두는 별도 저장소. 메트릭은 프로메테우스가, 로그는 Loki가 맡는다.
책 3.3: 수명이 짧고 자주 바뀌는 파드에 맞는 모니터링 체계가 필요하다{{PG}}
  • VM은 몇 달씩 같은 IP와 호스트명으로 떠 있어서 사람이 감시 목록에 적어 두면 됩니다. 파드는 배포, 축소, 장애 때마다 교체되고 그때마다 IP와 이름 접미사가 바뀝니다.
  • 그래서 감시 대상은 API 서버에서 라벨로 자동으로 찾습니다. 이것을 서비스 디스커버리라고 합니다.
  • 기록도 다릅니다. 파드가 지워지면 그 컨테이너 로그도 노드에서 지워지고, kubectl top이 보여 주는 값은 메모리에 있는 최근값뿐이라 한 시간 전 값은 없습니다.
  • kubectl top이 쓰는 metrics-server는 각 노드의 kubelet에서 CPU와 메모리의 최근값만 모아 두는 구성요소입니다. 지난 값을 저장하지 않기 때문에 한 시간 전과 비교할 수 없습니다.
  • 그래서 라벨로 대상을 찾아 수집하는 것과, 값을 시간에 걸쳐 쌓는 저장소가 필요합니다. 메트릭은 프로메테우스가, 로그는 Loki가 맡습니다.

01USE METHOD · 책 3.3

USE: 모든 자원의 사용률·포화도·에러를 본다

"For every resource, check utilization, saturation, and errors." — Brendan Gregg
U · UTILIZATION

사용률

자원이 일을 처리하느라 바빴던 시간의 평균 비율. 예: CPU 70%, 링크 대역폭의 40%.

S · SATURATION

포화도

처리하지 못하고 쌓여 있는 작업의 양. 주로 대기열(queue) 길이로 나타난다.

E · ERRORS

에러 수

에러 이벤트 횟수. 해석이 쉬워서 먼저 확인하면 시간이 절약된다.

사용률 100%가 곧 장애는 아니다. 포화도가 0보다 커지는 순간부터 요청이 대기열에 쌓이고 지연이 늘어난다. 사용률만 보면 이 시점을 놓친다.
책 3.3: 애플리케이션 수준에는 한계가 있어 주로 인프라 모니터링에 쓴다 · 실습 가이드 05 Grafana 5-2 섹션 참고{{PG}}
  • USE는 모든 자원마다 사용률, 포화도, 에러 세 가지를 봅니다.
  • 사용률은 자원이 바빴던 시간의 비율로, CPU 70%처럼 나타냅니다. 포화도는 처리하지 못하고 쌓인 작업의 양으로, 주로 대기열 길이입니다. 에러는 에러 이벤트 횟수이고, 해석이 쉬워서 먼저 보면 시간이 절약됩니다.
  • 포화도의 예를 들면, CPU 코어가 4개인데 실행을 기다리는 작업이 6개라면 2개는 줄을 서서 기다립니다. 사용률은 이미 100%라 더 오르지 않지만, 줄은 계속 길어질 수 있어서 포화도를 따로 봅니다.
  • 사용률 100%가 곧 장애는 아닙니다. 포화도가 0보다 커지는 순간부터 요청이 대기열에 쌓이고 지연이 늘어나므로, 사용률만 보면 이 시점을 놓칩니다. USE는 주로 인프라에 씁니다.

01WHERE TO APPLY

사용자가 겪는 문제는 RED로 발견하고, 원인은 USE로 찾는다

{{FIG:ch03-fig3-use-red.svg}}

RED = 서비스마다 Rate(초당 요청 수) · Errors(실패한 요청 수) · Duration(처리 시간 분포)를 본다. 모든 서비스를 같은 세 지표로 재면 대시보드 하나로 비교할 수 있다
실행 대기 줄 = run queue · 버려진 패킷 = dropped packets
스와핑 = swapping(RAM이 부족해 메모리를 디스크로 내려보냄. 느려짐) · OOM 킬 = Out Of Memory kill(메모리 부족으로 강제 종료)

책 3.3: 두 방법론은 서로 보완한다. USE는 인프라를, RED는 사용자 경험을 본다{{PG}}
  • RED는 서비스용 방법론입니다. 서비스마다 R, 초당 요청 수와 E, 실패한 요청 수와 D, 처리 시간의 분포 세 가지를 봅니다. 모든 서비스를 같은 세 지표로 재면 대시보드 하나로 어느 서비스가 이상한지 바로 비교할 수 있습니다. 앞에서 본 USE가 CPU, 메모리, 디스크 같은 자원을 본다면 RED는 사용자가 느끼는 요청을 봅니다.
  • 위쪽 RED는 요청이 지나가는 구간마다 적용합니다. 사용자에서 Ingress, order-api, 데이터베이스까지 구간마다 초당 요청 수, 실패 수, 걸린 시간 분포를 봅니다. 사용자가 겪는 증상입니다.
  • 아래쪽 USE는 요청을 처리하는 자원마다 적용합니다. order-api 파드가 올라간 노드의 CPU, 메모리, 디스크, 네트워크마다 사용률, 포화도, 에러를 봅니다.
  • Ingress는 클러스터 밖에서 들어온 요청을 안쪽 서비스로 넘기는 입구입니다. 그림의 실행 대기 줄은 CPU를 기다리는 작업 수로 CPU의 포화도이고, 버려진 패킷은 처리하지 못해 버린 네트워크 패킷으로 네트워크의 포화도입니다.
  • 메모리의 포화도는 스와핑과 OOM 킬로 드러납니다. 스와핑은 RAM이 모자라 메모리를 디스크로 내려보내는 것이고, OOM 킬은 메모리 부족으로 강제 종료되는 것입니다.
  • 증상은 RED로 발견하고, 원인은 USE로 찾습니다.

01MEAN VS TAIL

평균 45ms는 빠른 요청도, 느린 요청도 대표하지 못한다

{{FIG:ch03-fig4-mean-vs-tail.svg}}
RED의 D(처리 시간)는 평균 대신 P50·P95·P99 분포로 본다 · 실습 가이드 07 RED 7-3 섹션 참고{{PG}}
  • order-api의 응답 시간 분포입니다. 가로축은 로그 눈금이고, 왼쪽 1ms 근처에 정상 요청 대부분이, 오른쪽 800ms 근처에 느린 요청 무리가 있습니다.
  • 로그 눈금은 한 칸 갈 때마다 값이 10배씩 커지는 축입니다. 그래서 1ms 아래의 요청과 800ms 근처의 요청을 한 그림에 함께 그릴 수 있습니다. P95는 가장 느린 5%를 뺀 나머지가 모두 이 값 이하라는 뜻입니다.
  • P50은 0.58ms로 요청 절반이 이 안에 끝났습니다. P95는 725ms, P99는 790ms입니다.
  • 평균 45ms는 두 무리 사이, 요청이 거의 없는 곳에 놓여 어느 쪽도 대표하지 못합니다. 그래서 처리 시간은 평균 대신 P50, P95, P99로 봅니다.
