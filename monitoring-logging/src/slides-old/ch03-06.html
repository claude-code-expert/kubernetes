06

아무도 보지 않을 때 사람을 부르는 규칙

RED 질의에 임계값과 지속 시간을 붙여 알림 규칙을 만들고, 실제로 발화시켜 상태가 바뀌는 시각을 잰다. Alertmanager가 알림을 묶고 누르는 방식을 본다.

개념 + 실습 · 3.11 알림 · 3.12.3 알림 모범 사례{{PG}}
  • 대시보드는 사람이 볼 때 빠르게 판단하게 해 주고, 알림은 사람이 보지 않을 때 불러낸다. 둘은 역할이 다르다. 새벽 3시에는 대시보드를 아무도 보지 않는다.
  • 명령과 출력은 실습 가이드(lab-guide.html)의 절차를 kind 클러스터에서 실제로 실행한 결과다.

06WHAT TO ALERT · 책 3.11

사람이 지금 무언가 할 수 있을 때만 알림을 보낸다

알림을 건다

· SLO에 영향을 주는 증상: 사용자 요청 5%가 실패, 응답 시간이 약속을 넘음
· 관측 자체의 고장: 스크레이프 실패. 이게 죽으면 다른 알림이 모두 침묵한다

알림을 걸지 않는다

· 파드 하나가 실패할 때마다: 쿠버네티스가 스스로 재시작한다
· CPU·메모리가 높을 때: 사용자가 겪지 않으면 할 일이 없다. 원인을 찾을 때 본다
· 경험상 저절로 풀리는 문제

사람 대신 자동으로 고칠 수 있는 것자동 조치
응답 없는 프로세스라이브니스 프로브(liveness probe)가 컨테이너를 재시작
디스크가 꽉 참오래된 로그를 자동 삭제해 공간 확보
책 3.11: 유저는 SLO에 영향을 미치는 이벤트만 알림 받고 싶을 것이다{{PG}}
  • 책 3.11: 파드가 실패할 때마다 알림을 보내면 받는 사람이 무감각해진다. 쿠버네티스의 핵심은 컨테이너 상태를 자동으로 확인하고 재시작하는 기능이다.
  • 책의 예: 프론트엔드 SLO가 응답 시간 20ms인데 레이턴시가 그 이상으로 측정되면 바로 알림을 받아 조치해야 한다.
  • 프로메테우스 공식 가이드도 같은 원칙: 스택의 가장 높은 곳(사용자에게 보이는 지연·에러)에 알림을 걸고, 하위 구성요소 문제는 사용자 경험에 영향이 없으면 사람을 깨우지 않는다.

  • Prometheus · Alerting practices
06GOOD ALERTS · 책 3.11

책의 네 가지 조언은 규칙의 어느 칸에 들어가나

책 3.11의 조언설정 위치예
임계 시간은 5분 이상, 5·10·30·60분처럼 표준화규칙의 forfor: 2m · for: 3m (짧게 잡은 실습값)
플레이북 링크, 지역·앱 소유자·영향 시스템을 함께규칙의 annotations · labelssummary · description · runbook_url
팀 전체가 아니라 문제를 맡을 사람에게Alertmanager route · receiverseverity=critical → 당직 수신자
완벽한 알림은 없다. 점진적으로 개선운영 습관울렸는데 아무도 조치하지 않은 알림은 지운다
알림 메시지만 보고도 "어디를 봐야 하나"에 시간을 쓰지 않게 만드는 것이 목표다. 대시보드 링크를 annotations에 넣어 두면 대응하는 사람이 바로 연다.
책 3.11: 임계치가 너무 짧으면 오탐 알림이 너무 자주 발생한다{{PG}}
  • 책 3.11 원문 요지: 임계치를 적어도 5분 이상으로. 표준 임계치(5분, 10분, 30분, 1시간)를 정하면 수많은 임계치를 세밀하게 관리할 필요가 없다.
  • 책: 알림이 더 큰 그룹으로 전송되면 유저는 노이즈라고 판단해 걸러낼 가능성이 높다. 알림은 실제로 그 문제를 맡아 해결할 사람에게 보낸다.
  • 실습 규칙은 발화 과정을 몇 분 안에 보려고 for를 2~3분으로 짧게 잡았다.
06PROMETHEUSRULE

RED 질의에 임계값과 지속 시간을 붙이면 규칙이 된다

kind: PrometheusRule
metadata:
  name: study-app-rules
  labels: {release: kps}     # 없으면 조용히 무시된다spec:
  groups:
  - name: study-app
    interval: 30s
    rules:
    - alert: AppHighErrorRate
      expr: |
        100 * (
          sum by (job) (rate(…_count{status=~"5.."}[5m]))
          / sum by (job) (rate(…_count[5m]))
        ) > 5      for: 2m      labels: {severity: warning}
      annotations:
        summary: "{{ $labels.job }} 에러율 {{ $value }}%"
규칙조건 · for · severity
① AppTargetDownup == 0 · 1m · critical
② AppHighErrorRate5xx 비율 > 5% · 2m · warning
③ AppHighLatencyP95P95 > 0.5초 · 3m · warning
④ AppSLOFastBurn200ms 초과 비율 > 14.4 × 1% · 2m · critical
전체 파일: labs/k8s/prometheusrule.yaml{{PG}}
  • 프로메테우스 리소스의 ruleSelector 도 {"matchLabels":{"release":"kps"}} 다(실측). ServiceMonitor와 같은 라벨 문제가 여기서도 생긴다.
  • expr 의 > 5 가 임계값이자 필터다. 남은 라벨 조합마다 알림 인스턴스가 하나씩 생기므로 sum by (job) 으로 묶는다. 파드별로 묶으면 파드 수만큼 알림이 온다.
  • ③과 ④는 둘 다 "느림"을 보지만 뜻이 다르다. ③은 느린 요청이 있다, ④는 이 속도면 SLO를 못 지킨다. 그래서 ③은 warning, ④는 critical.
  • ④의 le="0.2" 는 200ms 버킷 경계를 직접 고른다. 그 경계가 버킷 정의에 실제로 있어야 한다.
  • 적용 직후 /api/v1/rules 에서 네 규칙이 state=unknown, 30초 뒤 inactive.
06TIMELINE · 실측

발화는 for가, 해소는 rate의 창이 정한다

{{FIG:ch03-fig8-alert-timeline.svg}}
부하를 멈춘 뒤에도 5분 동안 firing이 유지됐다{{PG}}
  • 실측. 20초 간격으로 /api/v1/rules 를 조회해 상태가 바뀐 시각을 기록했다.
  • 부하 시작 → pending 40초: 평가 주기 30초 + rate 창이 값을 잡는 시간.
  • pending → firing: 에러율 2분 18초(for: 2m), 지연 3분 18초(for: 3m). 규칙에 적은 값과 맞는다.
  • 부하 종료 → inactive: 5분 5초. for는 2m인데 5분이 걸렸다. 다음 슬라이드에서 이유를 본다.
06FAILURE · 해소 지연

for를 줄여도 알림은 빨리 꺼지지 않는다

잘못된 진단

"for: 2m인데 왜 5분이나 걸리지?" for를 줄여 봐도 달라지지 않는다. for는 발화 조건이지 해소 조건이 아니다.

원인

rate(…[5m])은 매 순간 직전 5분을 본다. 22:09에 계산하면 22:04~22:09 구간이고, 22:05:59까지의 에러가 아직 들어 있다. 창이 완전히 지나가는 22:11에야 비율이 0이 된다.

확인 방법

Query → Graph에 규칙의 expr을 그대로 넣고 부하 종료 전후를 본다. 비율이 계단이 아니라 완만한 경사로 내려간다.

선택얻는 것잃는 것
창을 줄인다 [2m]빨리 울리고 빨리 꺼진다트래픽이 적으면 비율이 요동쳐 오탐이 는다
그대로 둔다안정적인 판단"고쳤는데 왜 울리지"
설명에 적는다오해를 없앤다없음
description 예: "5분 창으로 계산하므로 원인이 사라진 뒤에도 최대 5분간 유지됩니다"{{PG}}
  • 버그가 아니므로 "고친다"보다 "선택한다"가 맞다.
  • 실무에서는 대개 세 번째. 대응하는 사람이 고쳤는지 아닌지를 알림이 아니라 그래프로 판단하게 된다.
  • 창을 줄이는 것은 트래픽이 충분히 많은 서비스에서만 안전하다.
06SLO BURN RATE

P95 알림은 울렸는데 SLO 알림은 울리지 않았다

# ④ 규칙의 값을 직접 계산
1 - (
  sum by (job) (rate(…_bucket{le="0.2"}[5m]))
  / sum by (job) (rate(…_count[5m])))
# 결과
order-api  5.63%   (임계 14.4%)

계산

SLO: 요청의 99%가 200ms 안에 → 오차 예산 1%. 5분 동안 예산을 14.4배 속도로 쓰면 30일 예산이 약 2일에 바닥난다. 임계 = 14.4 × 1% = 14.4%.

③ P95 지연④ SLO 소진
말하는 것느린 요청이 있다이 속도면 약속을 못 지킨다
이번 결과firing5.63% < 14.4%, 울리지 않음
severitywarning (낮에 본다)critical (새벽에도 깨운다)
느린 요청(초당 2건)은 전체 초당 23건 중 일부였다. 느리다와 위험하다는 다르다. 사람을 깨우는 것은 ④여야 한다.
30일 ÷ 14.4 ≈ 2.08일{{PG}}
  • 실측. 넷 중 하나가 침묵한 것이 버그가 아니라 설계라는 것을 확인했다.
  • P95가 500ms를 넘었다고 바로 사람을 부르면 자주 울린다. 잠깐 느려지는 것은 늘 있고, 예산 안이면 문제가 아니다.
  • 구글 SRE 워크북은 짧은 창과 긴 창을 함께 보는 다중 창(multiwindow) 방식을 권한다. 실습 규칙은 5분 창 하나만 썼다.

06ALERTMANAGER · ROUTE

Alertmanager는 묶고, 기다리고, 골라서 보낸다

# kps-values.yaml 의 alertmanager.config (일부)
route:
  group_by: [namespace, alertname]  group_wait: 30s
  group_interval: 5m
  repeat_interval: 4h
  receiver: study-default
  routes:
    - receiver: "null"
      matchers: [alertname =~ "InfoInhibitor|Watchdog"]
    - receiver: study-critical
      matchers: [severity = "critical"]
inhibit_rules:
  - source_matchers: [severity = "critical"]
    target_matchers: [severity =~ "warning|info"]
    equal: [namespace, alertname]
설정뜻
group_by같은 네임스페이스·같은 알림은 한 덩어리. 파드 10개가 죽어도 알림 하나
group_wait 30s첫 알림을 30초 기다려 연달아 터지는 것을 함께 보낸다
group_interval 5m같은 그룹에 새 알림이 붙으면 5분 간격으로 다시 보낸다
repeat_interval 4h해결되지 않은 알림을 4시간마다 다시 알린다
Watchdog → "null"상시 알림은 사람에게 보내지 않고 버린다
전체 파일: labs/helm/kps-values.yaml{{PG}}
  • 값 파일에 alertmanager.config 를 쓰면 차트 기본 설정을 통째로 대체한다. Watchdog 처리와 억제 규칙을 빠뜨리면 안 되는 이유.
  • 수신자 study-default · study-critical 은 이름만 있고 전송처(Slack 등)는 비워 두었다. 실제로 보내려면 slack_configs 같은 블록을 채운다.
  • Watchdog은 외부 시스템이 "이 알림이 계속 오는가"로 관측 파이프라인의 생존을 감시할 때 쓴다.

06INHIBIT vs SILENCE

억제는 규칙이 자동으로, 침묵은 사람이 기간을 정해 끈다

억제 · Inhibition 
# 같은 알림을 critical · warning 둘로 넣었을 때
severity=critical  state=active      inhibitedBy=0건
severity=warning   state=suppressed  inhibitedBy=1건

critical이 울리는 동안 같은 대상의 warning은 보내지 않는다. DB가 죽어 서비스 열 개가 경고를 내도 사람이 볼 것은 하나다.

침묵 · Silence 
# alertname=DemoAlert 에 10분 침묵
severity=critical  state=suppressed  silencedBy=1건
severity=warning   state=suppressed  silencedBy=1건

계획 작업 중에 알림을 잠시 끈다. critical까지 모두 눌린다. 반드시 끝나는 시각이 있다.

둘 다 state=suppressed지만 inhibitedBy(규칙)와 silencedBy(사람) 중 어느 쪽이 채워졌는지로 구분한다. "아는 문제니까 꺼 두자"는 침묵이 아니라 규칙이나 문제를 고칠 일이다.
침묵은 Alertmanager UI(9093)의 New Silence 또는 API로 만든다{{PG}}
  • 실측. 실제 장애를 기다리지 않고 Alertmanager API(/api/v2/alerts)로 같은 alertname·namespace의 critical·warning 알림을 직접 밀어 넣었다.
  • 영구 침묵이 없는 것이 설계 의도다. 계획 작업이 끝나면 지운다.
