# 관측 스택을 한 노드에 모으기 위한 라벨
kubectl label node obs-worker2 workload=observability

kps-values.yaml (일부)

prometheus:
  service: {type: ClusterIP}
  prometheusSpec:
    nodeSelector: {workload: observability}
    scrapeInterval: 30s    retention: 3d    retentionSize: 4GB    storageSpec:
      volumeClaimTemplate:
        spec:
          resources: {requests: {storage: 8Gi}}grafana:
  adminPassword: obs-study
값왜
scrapeInterval 30s짧을수록 해상도가 오르고 저장량도 오른다. 15초면 저장량이 두 배
retention 3d · 4GB둘 중 먼저 닿는 쪽에서 오래된 데이터를 지운다. 며칠 전 장애까지 되짚을지가 이 값
storageSpec 8Gi없으면 emptyDir. 파드가 재시작되면 쌓은 메트릭이 전부 사라진다
nodeSelector관측 스택을 한 노드에 모은다. 관측 대상이 앓을 때 같이 앓지 않게
type ClusterIPUI는 port-forward로 연다. 외부 노출 불필요
전체 파일: labs/helm/kps-values.yaml{{PG}}
  • 값 파일 전체에는 Alertmanager 라우팅, Grafana 사이드카, 노드 익스포터 설정도 있다. 슬라이드에는 프로메테우스 저장과 관련된 줄만 올렸다.
  • Grafana 관리자 비밀번호는 실습용으로 값 파일에 적었다. 운영이라면 시크릿으로 넘긴다.

04FAILURE · 원인 읽기

DOWN 6개는 모두 connection refused: 루프백에만 열려 있다

# DOWN 타깃의 마지막 에러 (lastError)
kube-controller-manager: Get "https://172.20.0.4:10257/metrics": dial tcp 172.20.0.4:10257: connect: connection refused
kube-etcd:  Get "http://172.20.0.4:2381/metrics": ... connection refused
kube-proxy: Get "http://172.20.0.2:10249/metrics": ... connection refused   (노드 3개 모두)
kube-scheduler: Get "https://172.20.0.4:10259/metrics": ... connection refused
# 컨트롤 플레인 노드 안의 정적 파드 매니페스트
docker exec study-control-plane sh -c \
  "grep -h 'bind-address\|listen-metrics-urls' \
   /etc/kubernetes/manifests/*.yaml"
# 결과
- --bind-address=127.0.0.1          # controller-manager
- --bind-address=127.0.0.1          # scheduler
- --listen-metrics-urls=http://127.0.0.1:2381  # etcd

원인

네 구성요소가 메트릭 포트를 127.0.0.1(루프백)에만 열었다. 같은 노드 안에서만 닿고, 다른 노드의 프로메테우스는 닿을 수 없다. kube-proxy는 metricsBindAddress: ""(기본값 루프백).

차트는 "이 주소를 긁어라"라는 설정만 만든다. 대상 포트가 열려 있는지는 확인하지 않는다.
인증서·권한 문제가 아니라 그 포트에서 아무도 듣고 있지 않다{{PG}}
  • 출력은 실측. 에러 문자열은 줄였다.
  • 루프백 바인드는 kind(kubeadm)의 기본값이고 보안상 합당하다. 메트릭 포트는 인증 없이 클러스터 내부 정보를 내놓을 수 있기 때문이다.
  • kube-proxy 설정 확인 명령: kubectl -n kube-system get cm kube-proxy -o jsonpath='{.data.config\.conf}' | grep -i metricsBindAddress
04FAILURE · 고치기

메트릭 포트를 0.0.0.0으로 열면 28/28 up이 된다

정적 파드 3개: 파일을 고치면 kubelet이 파드를 다시 만든다

docker exec study-control-plane sh -c "
 sed -i 's|--bind-address=127.0.0.1|--bind-address=0.0.0.0|' \
   /etc/kubernetes/manifests/kube-controller-manager.yaml
 sed -i 's|--bind-address=127.0.0.1|--bind-address=0.0.0.0|' \
   /etc/kubernetes/manifests/kube-scheduler.yaml
 sed -i 's|--listen-metrics-urls=http://127.0.0.1:2381|--listen-metrics-urls=http://0.0.0.0:2381|' \
   /etc/kubernetes/manifests/etcd.yaml"

kube-proxy: 데몬셋이라 ConfigMap을 고치고 다시 띄운다

kubectl -n kube-system get cm kube-proxy -o yaml \
 | sed 's|metricsBindAddress: ""|metricsBindAddress: "0.0.0.0:10249"|' \
 | kubectl apply -f -
kubectl -n kube-system rollout restart ds kube-proxy
# 1~2분 뒤 다시 집계
총 28  up 28

이제 보이는 것

etcd_disk_wal_fsync_duration_seconds · scheduler_pending_pods · workqueue_depth 같은 컨트롤 플레인 메트릭

정적 파드 셋이 동시에 재시작되는 동안 API 서버 요청이 잠깐 타임아웃날 수 있다. 안정되면 같은 명령을 다시 친다.
kind 노드를 다시 만들면 이 설정은 사라진다. 다시 해야 한다{{PG}}
  • /etc/kubernetes/manifests 는 정적 파드 디렉터리다. kubelet이 이 디렉터리를 지켜보다가 파일이 바뀌면 파드를 다시 만든다. API 서버를 거치지 않으므로 API 서버 자신도 이 방식으로 뜬다.
  • 실습 중 kube-proxy ConfigMap 수정이 한 번 "Error from server (Timeout)"로 실패했다. 컨트롤 플레인이 안정된 뒤 같은 명령으로 성공했다.
  • 매번 하기 싫다면 kind-cluster.yaml 의 kubeadmConfigPatches 에 넣어 둘 수 있다. 여기서는 왜 필요한지 보여 주려고 일부러 넣지 않았다.
  • 운영 클러스터에서 0.0.0.0으로 열 때는 네트워크 정책이나 인증(authentication)으로 메트릭 포트 접근을 제한한다.

04FAILURE · PENDING

requests를 노드보다 크게 주면 Pending에서 멈춘다

# CPU 16개를 요청하는 파드 (노드 allocatable은 14)
kubectl -n apps run pending-demo --restart=Never \
  --image=registry.k8s.io/pause:3.10 \
  --overrides='{"spec":{"containers":[{"name":"pending-demo",
   "image":"registry.k8s.io/pause:3.10",
   "resources":{"requests":{"cpu":"16"}}}]}}'
# 프로메테우스 (약 1분 뒤)
kube_pod_status_phase{phase="Pending"} == 1
  {namespace="apps", pod="pending-demo"}  1
sum by (queue)(scheduler_pending_pods) > 0
  {queue="unschedulable"}                 1
kube_node_status_allocatable{resource="cpu"}  14 (노드마다)
kubectl -n apps describe pod pending-demo
Warning  FailedScheduling  default-scheduler
  0/3 nodes are available: 1 node(s) had untolerated taint(s),
  2 Insufficient cpu. preemption: ... not helpful
캡처Prometheus → Query
kube_pod_status_phase{phase="Pending"}
+ 터미널 describe 이벤트
정리: kubectl -n apps delete pod pending-demo{{PG}}
  • 2026-09-26 실습 클러스터에서 실제로 실행한 결과다. 끝나면 파드를 지운다.
  • 2장 "Pending일 때 노드에서 컴포넌트로 좁혀 가는 순서" 표를 그대로 따라간다. ① Pending 1개 확인 → ② 노드 allocatable 14 대 요청 16, 어느 노드에도 자리가 없다 → ③ 스케줄러는 up 1, unschedulable 큐에 1개 → ④ 이벤트가 이유를 말한다.
  • "1 node(s) had untolerated taint(s)": 컨트롤 플레인 노드는 일반 파드를 받지 않도록 taint가 걸려 있다. "2 Insufficient cpu": 워커 두 대는 CPU가 모자란다.
  • 이미지는 끝까지 받지 않는다. 스케줄되지 못한 파드는 이미지를 당기기 전 단계에서 멈춘다.
