00OUR QUESTION

"주문이 느려요"라는 제보 한 건을 끝까지 따라간다

1 · 메트릭으로 분석얼마나 느린가

P99 790ms.
평균 45ms만 보면 멀쩡해 보였다

2 · 메트릭으로 분석무엇이 느린가

URI별로 나눠 보니
/api/chaos/slow만 805ms

3 · 알림으로 확인사람이 안 봐도 알린다

AppHighErrorRate 발화
"order-api 에러율 5.9%"

4 · 로그로 원인 분석그 에러는 무엇이었나

알림이 난 시각의 로그에서
실패한 요청을 찾는다

P99 · 99th PERCENTILE

가장 느린 1% 요청의 경계값

요청 100건을 빠른 순으로 줄 세웠을 때 99번째 요청의 응답 시간. "P99 790ms"는 99%는 790ms 안에 끝났고, 가장 느린 1%는 그보다 오래 걸렸다는 뜻이다. 평균이 가리는 느린 요청을 드러낸다.

ALERT · FIRING

AppHighErrorRate가 "발화"했다

AppHighErrorRate는 우리가 정의한 알림 규칙의 이름이다. 조건은 "5xx(서버 오류) 응답 비율이 5%를 넘는 상태가 2분 이상 지속". 조건이 충족되면 규칙이 firing(발화) 상태가 되고 Alertmanager가 담당자에게 알림을 보낸다.

메트릭으로 분석하고, 알림으로 확인한 뒤, 로그로 원인을 분석한다.
메트릭 → 알림 → 로그{{PG}}
  • 1·2칸, 메트릭으로 분석: 실측. 평균 45ms, P50 0.59ms, P99 790ms. uri 라벨로 쪼개자 /api/chaos/slow 가 805ms.
  • P99 설명: 100건 중 가장 느린 1건을 빼면 나머지는 모두 이 값 이하. 정확한 계산 방법(히스토그램 버킷 + histogram_quantile)은 5장.
  • 3칸, 알림으로 확인: 사람이 대시보드를 보고 있지 않아도 규칙이 불러낸다. AppHighErrorRate 규칙은 labs/k8s/prometheusrule.yaml 에 있다. 식은 5xx 요청 비율 × 100 > 5, for: 2m. 발화 전 조건만 충족된 상태는 pending, 2분을 채우면 firing. 규칙 작성과 실제 발화 과정은 6장.
  • 4칸, 로그로 원인 분석: 알림이 말해 주는 것은 "에러율 5.9%"까지다. 어떤 요청이 왜 실패했는지는 로그가 답한다. 7장.

00MAP TERMS · 1/3 · 메트릭 수집과 저장

프로메테우스는 대상에서 메트릭을 가져와 시간 순으로 저장한다

용어원어 · 풀 네임뜻
스크레이프Scrape (직역: 긁어 오기)프로메테우스가 대상의 HTTP 주소(/metrics 등)에 주기적으로 요청해 그 순간의 메트릭 값을 읽어 가는 동작. 실습 주기는 30초
풀 방식Pull model수집기가 대상에 요청해서 가져온다. 반대는 대상이 수집기로 밀어 넣는 푸시(Push) 방식
타깃Target스크레이프할 대상 하나(주소 + 경로). 쿠버네티스에서는 라벨로 자동 발견한다. 같은 목적의 타깃 묶음은 잡(Job)
Prometheus프로메테우스 · CNCF(Cloud Native Computing Foundation) 졸업 프로젝트메트릭을 수집 · 저장 · 질의하고 알림 규칙을 평가하는 모니터링 시스템
TSDBTime Series Database · 시계열 데이터베이스(시각, 값) 쌍을 메트릭 이름 + 라벨별로 저장하는 DB. 프로메테우스는 자기 로컬 디스크에 2시간 단위 블록으로 쌓고, 보존 기한(실습: 3일 또는 4GB)이 지나면 지운다
최근 2시간치 데이터는 메모리에 있다. 들어온 값을 WAL(Write-Ahead Log · 선행 기록 로그)에 먼저 적어 두기 때문에 재시작해도 복구된다.
스크레이프는 가져오는 동작, TSDB는 시간 순 저장소{{PG}}
  • 스크레이프: 공식 용어집에서 타깃은 "어떻게 스크레이프할지를 정의한 대상", 잡은 "같은 목적의 타깃 묶음(예: 복제된 프로세스들)", 인스턴스는 잡 안의 타깃 하나를 가리키는 라벨이다.
  • 풀 방식이라 대상은 메트릭을 HTTP로 "보여 주기만" 하면 된다. 수집 주기와 대상 목록은 프로메테우스 쪽이 정한다. 대상이 죽으면 스크레이프 실패 자체가 신호(up == 0)가 된다. 자세한 내용은 3장.
  • TSDB 공식 문서: 들어온 샘플은 2시간 블록으로 묶이고 블록마다 chunks 디렉터리, 메타데이터, 인덱스 파일을 갖는다. 현재 블록은 메모리에 있고 WAL로 보호된다. 작은 블록은 백그라운드에서 더 큰 블록으로 합쳐진다(compaction).
  • 보존 기한을 안 정하면 기본 15일. 실습 values 에서는 retention 3d, retentionSize 4GB 로 줄였다.

00MAP TERMS · 2/3 · 로그 수집과 저장

Alloy가 로그를 수집해 보내고, Loki가 저장하고 조회한다

용어원어 · 풀 네임뜻
stdout · stderrStandard output · Standard error (표준 출력 · 표준 에러)프로그램이 출력을 내보내는 기본 통로. 컨테이너가 여기로 쓴 줄을 런타임이 노드의 /var/log/pods 아래 파일로 남긴다
AlloyGrafana Alloy · 그라파나 랩스의 수집 에이전트OpenTelemetry Collector 배포판에 프로메테우스 파이프라인을 내장한 수집기. 파드 로그를 읽어 라벨을 붙이고 Loki로 보낸다
LokiGrafana Loki · 로그 집계 시스템로그를 저장하고 조회한다. 로그 본문은 색인하지 않고 라벨만 색인하며, 본문은 압축 덩어리(chunk)로 저장한다. 색인이 작아 저장 비용이 낮다
로그 스트림Log stream라벨이 모두 같은 로그 줄의 묶음. Loki는 먼저 라벨로 스트림을 고르고, 그 안의 로그만 검색한다
프로메테우스가 메트릭을 라벨로 다루듯, Loki는 로그를 라벨로 다룬다{{PG}}
  • Loki 공식 설명: 프로메테우스에서 영감을 받은 로그 집계 시스템. 로그 라벨의 메타데이터만 색인하고, 실제 로그는 압축해 S3 · GCS · 로컬 파일시스템 같은 저장소에 둔다. 조회 시 색인으로 스트림을 고른 뒤 필요한 청크만 가져온다.
  • 그래서 라벨은 값의 종류가 적은 것(namespace, app)만 써야 한다. 요청 경로처럼 값이 끝없이 늘어나는 필드를 라벨로 올리면 스트림 수가 폭발한다. 7장에서 실패를 재현한다.
  • Alloy: 컴포넌트를 이어 파이프라인을 만든다. 이 실습의 흐름은 discovery.kubernetes(파드 찾기) → loki.source.kubernetes(로그 읽기) → loki.write(Loki로 전송). 7장에서 설정을 본다.
  • 책 3.10은 Promtail + loki-stack 차트로 설치한다. 둘 다 지금은 쓰지 않는다. 7장 정정 슬라이드에서 다룬다.

01METRICS VS LOGS · 책 3.1

메트릭은 횟수와 수치를, 로그는 사건의 내용을 알려 준다

METRIC

정해진 기간에 측정한 수치

http_server_requests_seconds_count{
  uri="/api/orders", status="500"} 731

크기가 작아 오래 보관하고 빠르게 집계할 수 있다. 대신 개별 요청의 정보는 숫자로 합쳐지면서 사라진다.

LOG

실행 중 일어난 사건의 기록

10.244.1.1 - - [05/Sep/2026:13:52:10 +0000]
  "GET /api/chaos/error HTTP/1.1" 500 15 3

요청마다 어느 경로가 언제, 몇 ms 걸려 실패했는지 남는다. 대신 양이 많아 저장 비용이 크고, 개수를 세려면 전부 읽어야 한다.

메트릭으로는 느리다는 사실까지만 알 수 있고, 원인은 앱이 남긴 로그에서 찾는다. 메트릭으로 먼저 좁히고, 로그로 확인한다.
책 3.1: 메트릭과 로그는 서로 보완하지만 용도가 다르다{{PG}}
  • 왼쪽 메트릭 줄은 order-api가 실제로 내놓는 형식이다. 이름 + 라벨 + 값. 731은 설명용 예시 값.
  • 오른쪽 로그는 order-api 톰캣 액세스 로그 형식 그대로다. 필드 순서: 클라이언트 IP, 시각, 요청 줄, 상태 코드, 응답 바이트, 처리 시간(ms). 값은 예시다. /api/chaos/error 는 예외 없이 500과 {"failed":true} 를 돌려준다.
  • 메트릭은 "지금 에러율이 몇 %인가", 로그는 "그 에러가 정확히 무엇이었나"에 답한다.

메트릭으로 시간과 대상을 좁힌 뒤 로그를 본다

① 메트릭으로 이상을 발견한다

에러율이 5.9%로 올랐다. 언제부터인지, 어느 앱의 어느 uri인지 라벨로 나눠 본다.

② 같은 시간·라벨로 로그를 조회한다

시간 범위(22:03~22:06)와 라벨(namespace=apps, app=order-api)을 로그 조회 조건에 그대로 쓴다.

③ 로그에서 원인을 확인한다

좁혀진 수백 줄에서 어느 경로가 어떤 상태 코드로, 몇 ms 만에 실패했는지 확인한다.

순서를 거꾸로 하면: 로그부터 뒤지면 하루 수백만 줄을 grep으로 훑게 된다. 무엇을 찾는지 모르면 검색이 끝나지 않는다.
이렇게 이어 보려면 메트릭과 로그가 같은 라벨 이름(namespace, pod, app)을 써야 한다.

밖에서 증상을 보고, 안에서 원인을 본다

{{FIG:ch03-fig2-closed-open.svg}}
책의 예: 폐쇄형은 "디스크가 꽉 찼다"를 알려 주고, 개방형은 "왜 꽉 찼을까?"에 답한다{{PG}}
  • 폐쇄형(책 3.2): 애플리케이션 밖에서 CPU·메모리·스토리지를 보던 전통적 방식. 인프라 컴포넌트에는 유용하지만 앱이 왜 그렇게 동작하는지 맥락이 없다.

  • 책의 폐쇄형 예: 파드를 하나 스케줄해 보는 테스트가 성공하면 스케줄러와 서비스 디스커버리는 정상이라고 판단한다.
  • 개방형(책 3.2): 총 HTTP 요청 수, 500 에러 횟수, 요청 레이턴시 같은 앱 내부 상태. "왜"에 대한 단서가 된다.
  • 구글 SRE 책의 정의: 블랙박스는 "사용자가 보듯이 겉으로 드러난 동작을 시험", 화이트박스는 "시스템 내부가 노출하는 메트릭 기반". 블랙박스는 지금 일어나는 문제(증상)를, 화이트박스는 곧 터질 문제와 원인을 잡는다.
  • 그림 오른쪽 숫자: 731/12,408 = 5.9%. 앞 슬라이드의 에러율과 맞춰 둔 설명용 값.

01WHY K8S IS DIFFERENT · 책 3.3

파드는 VM처럼 고정된 대상으로 모니터링할 수 없다

항목24/7 가동 VM쿠버네티스 파드
수명몇 달~몇 년배포·축소·장애 때마다 교체. 수명이 짧다(transient)
주소·이름고정 IP · 호스트명교체될 때마다 새 IP · 새 접미사(order-api-7c9…-x2kqp)
감시 대상 등록사람이 목록에 적는다API 서버에서 라벨로 자동으로 찾는다(서비스 디스커버리)
기록호스트 디스크에 남는다파드가 지워지면 그 컨테이너 로그도 노드에서 지워진다
kubectl top해당 없음metrics-server는 메모리에 있는 최근값만 보여 준다. 한 시간 전 값은 없다
그래서 쿠버네티스 모니터링에는 두 가지가 필요하다. 대상을 라벨로 찾아 수집하는 것, 값을 시간에 걸쳐 쌓아 두는 별도 저장소. 메트릭은 프로메테우스가, 로그는 Loki가 맡는다.
책 3.3: 수명이 짧고 자주 바뀌는 파드에 맞는 모니터링 체계가 필요하다{{PG}}
  • 책 3.3 도입: VM은 모든 상태가 보존되는지 확인하는 식으로 감시하지만, 쿠버네티스는 수명이 짧은 파드에 맞는 체계가 필요하다고만 쓴다. 표는 그 "왜"를 구체화한 것.
  • 로그 행(공식 문서): kubelet은 재시작 시 종료된 컨테이너 하나의 로그만 남기고, 파드가 축출(evict)되면 그 컨테이너와 로그도 함께 지워진다. 그래서 클러스터 수준 로깅은 노드·파드와 수명이 분리된 별도 백엔드가 필요하다.
  • kubectl top 행(공식 문서): 리소스 메트릭 파이프라인은 kubectl top 과 오토스케일러용의 제한된 메트릭만 제공한다.

01USE METHOD · 책 3.3

USE: 모든 자원의 사용률·포화도·에러를 본다

"For every resource, check utilization, saturation, and errors." — Brendan Gregg
U · UTILIZATION

사용률

자원이 일을 처리하느라 바빴던 시간의 평균 비율. 예: CPU 70%, 링크 대역폭의 40%.

S · SATURATION

포화도

처리하지 못하고 쌓여 있는 작업의 양. 주로 대기열(queue) 길이로 나타난다.

E · ERRORS

에러 수

에러 이벤트 횟수. 해석이 쉬워서 먼저 확인하면 시간이 절약된다.

사용률 100%가 곧 장애는 아니다. 포화도가 0보다 커지는 순간부터 요청이 대기열에 쌓이고 지연이 늘어난다. 사용률만 보면 이 시점을 놓친다.
책 3.3: 애플리케이션 수준에는 한계가 있어 주로 인프라 모니터링에 쓴다{{PG}}
  • 책의 예: 클러스터 노드의 네트워크를 사용률·포화도·에러 수로 보면 병목이나 네트워크 스택 문제를 쉽게 파악할 수 있다.
  • 그레그 원문 정의. 자원(resource): CPU·디스크·버스 등 서버의 물리 구성요소. 사용률: 자원이 작업을 처리하느라 바빴던 평균 시간. 포화도: 처리하지 못해 쌓인(대개 큐잉된) 추가 작업의 정도. 에러: 에러 이벤트 수.
  • 그레그는 에러를 먼저 보는 것을 "보통 더 빠르고 해석이 쉬워서" 권하는 최적화로 적는다.
  • 네트워크 예: 사용률 = 송수신 처리량 / 최대 대역폭, 포화도 = dropped · overruns 같은 NIC·OS 이벤트.
  • 이 개념을 노드 메트릭 이름으로 바꾸는 것은 4장 PromQL에서 한다.

포화도 Saturation서비스 자원이 한계에 얼마나 가까운지. 가장 부족한 자원을 기준으로 본다없음 → USE가 맡는다요청 때문에 서비스가 과도하게 사용되고 있나?
톰 윌키가 2015년에 RED를 만든 이유: "USE는 서비스에는 잘 맞지 않는다. 하드웨어·네트워크·디스크용 방법이다." 모든 마이크로서비스를 같은 세 지표로 재면 대시보드 하나로 모든 서비스를 비교할 수 있다.
책 3.3: RED 방법론은 구글의 4대 골든 시그널에 기반한다{{PG}}
  • 책은 프론트엔드 서비스에서 세 가지를 계산하라고 한다. 그 세 질문이 표 오른쪽 열이다. 세 번째 질문(과도하게 사용되고 있나)은 포화도 질문이라 RED가 아니라 USE 쪽에 붙는다.
  • 레이턴시에서 성공/실패를 나누는 이유(SRE 책): 빠르게 실패하는 500이 평균 지연을 끌어내려 "빨라졌다"고 착각하게 만든다. 느린 에러는 빠른 에러보다 더 나쁘다.
  • 에러의 "정책상 실패" 예: 응답 1초를 넘기면 실패로 친다는 약속이 있다면 1.2초짜리 200도 에러.

01WHERE TO APPLY

사용자가 겪는 문제는 RED로 발견하고, 원인은 USE로 찾는다

{{FIG:ch03-fig3-use-red.svg}}

실행 대기 줄 = run queue · 버려진 패킷 = dropped packets
스와핑 = swapping(RAM이 부족해 메모리를 디스크로 내려보냄. 느려짐) · OOM 킬 = Out Of Memory kill(메모리 부족으로 강제 종료)

책 3.3: 두 방법론은 서로 보완한다. USE는 인프라를, RED는 사용자 경험을 본다{{PG}}
  • 위 줄: 요청이 지나가는 구간마다 R·E·D 세 숫자를 둔다. 사용자가 실제로 겪는 것이라 "증상"이다.
  • 아래 줄: 그 요청을 실어 나르는 노드의 네 자원마다 U·S·E. 증상이 보였을 때 원인을 찾으러 내려가는 곳이다.
  • 스와핑: RAM이 모자라면 운영체제가 당장 안 쓰는 메모리 페이지를 디스크의 스왑 영역으로 내려보내고, 다시 필요하면 읽어 올린다. 디스크는 RAM보다 훨씬 느리므로 스왑이 잦으면 응답 지연이 크게 는다. 사용률만 보면 "95% 사용 중"으로 끝나지만 스왑이 일어나면 이미 메모리가 넘쳐 일이 밀리고 있다는 뜻이라 포화도(S)로 본다. 스왑도 부족하거나 꺼져 있으면 커널이 프로세스를 강제 종료한다(OOM 킬). 쿠버네티스 노드는 전통적으로 스왑을 끄고 운영해서, 파드 메모리 부족은 OOM 킬(컨테이너 재시작)로 먼저 드러나는 경우가 많다.
  • 프로메테우스 공식 가이드(The Zen of Prometheus): 사용자가 신경 쓰는 지표(지연·가용성)를 먼저 재고, CPU 포화 같은 내부 지표는 원인 추적과 용량 계획용으로 둔다. 알림 가이드도 "사용자에게 보이는 지연·에러에만 사람을 깨운다"고 적는다. 6장의 출발점이다.
  • 구글 SRE 책의 표현: 모니터링은 "무엇이 망가졌나(증상)와 왜 망가졌나(원인)" 두 질문에 답해야 한다.

01MEAN VS TAIL

평균 45ms는 빠른 요청도, 느린 요청도 대표하지 못한다

{{FIG:ch03-fig4-mean-vs-tail.svg}}
RED의 D(처리 시간)는 평균 대신 P50·P95·P99 분포로 본다{{PG}}
  • 실측: 요청 절반은 0.59ms 안에 끝나고 상위 1%는 790ms. 1300배 차이. 평균 45ms는 두 무리 사이 빈 곳에 떨어진다.
  • 이 부하에는 800ms짜리 /api/chaos/slow 요청이 초당 2건 섞여 있었다. 평균이 그것을 삼켰다.
  • 구글 SRE 책: 평균 지연만 보면 느린 꼬리가 가려진다. 지연을 구간(버킷)별 요청 수로 모아 히스토그램으로 보라.
  • 백분위수는 히스토그램 버킷에서 계산한다. 프로메테우스 공식 문서: 여러 파드의 요약(summary) 분위수를 평균 내는 것은 통계적으로 틀렸고, 히스토그램을 합친 뒤 histogram_quantile 로 계산해야 한다. 계산은 5장에서 직접 한다.
  • 막대 모양은 개략도다. 네 개의 숫자만 실측값이다.
