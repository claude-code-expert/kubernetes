05

앱을 수집 대상에 올리고 RED를 계산한다

order-api가 내놓는 메트릭을 ServiceMonitor로 연결하고, 요청률·에러율·지연을 PromQL로 뽑는다. 평균 뒤에 숨은 느린 요청을 분위수로 찾는다.

실습 · 책 3.12.1: 애플리케이션의 사용률, 에러 수, 실행 시간도 모니터링한다{{PG}}
  • 명령과 출력은 실습 가이드(lab-guide.html)의 절차를 kind 클러스터에서 실제로 실행한 결과다.
  • RED는 애플리케이션만 답할 수 있다. 밖에서는 요청이 성공했는지 실패했는지 알 수 없기 때문에 앱을 계측해야 한다.

05CUSTOM METRICS

코드의 이름과 노출되는 이름이 다를 수 있다

// OrderService.java (일부)
Counter.builder("orders.created")
    .tag("channel", "api").register(registry);
Counter.builder("orders.rejected")
    .tag("reason", "quantity_exceeded").register(registry);
Timer.builder("orders.processing")
    .publishPercentileHistogram().register(registry);
Gauge.builder("orders.stored", store, Map::size)
    .register(registry);
코드의 이름실제 노출 이름 (실측)
orders.createdorders_total ← _created가 빠짐
orders.rejectedorders_rejected_total
orders.processingorders_processing_seconds_bucket · _sum · _count · _max
orders.storedorders_stored (gauge)
_created는 OpenMetrics에서 "카운터가 만들어진 시각"을 뜻하는 예약 접미사라서 클라이언트 라이브러리가 떼어 낸다. 메트릭 이름은 코드가 아니라 엔드포인트에서 확인한다. 이름을 지을 때 _total · _created · _bucket · _sum · _count는 피한다.
대시보드에 orders_created_total 로 적으면 패널이 No data로 비어 있다{{PG}}
  • 노출 이름은 order-api 파드 안에서 /actuator/prometheus 를 받아 # TYPE 줄로 확인한 실측이다.
  • 실제로 "분당 주문 수" 패널이 sum(rate(orders_created_total[5m])) 로 적혀 있어 No data가 났다. orders_total 로 바꾸자 채워졌다.
  • 같은 클래스에서 만든 카운터 둘(created, rejected)의 이름 규칙이 달라진다. 코드만 봐서는 알 수 없다.
  • OpenMetrics: 프로메테우스 노출 형식을 표준화한 규격. CNCF 프로젝트.

05FAILURE ② ③

같은 방식으로 조용히 사라지는 실수 두 가지

② 포트를 숫자로 적는다 
endpoints:
  - port: "8080"     # 서비스 포트 번호
# 1분 뒤
order-api 타깃: 0 건 / 전체 28

port는 서비스 포트의 이름을 가리킨다. 이름 http로 되돌리면 2건. 서비스 포트에 이름이 없으면 ServiceMonitor를 쓸 수 없다.

③ labels와 selector를 헷갈린다 
# journal-api 서비스
metadata.labels = {"app.kubernetes.io/part-of":"journal", ...}
spec.selector   = {"app":"journal-api"}

ServiceMonitor가 보는 것은 metadata.labels(나는 누구인가)다. spec.selector(어느 파드를 묶나)에 있는 라벨로 고르면 잡히지 않는다. 서비스 labels에 app: journal-api를 추가해 고친다.

세 실수의 증상은 모두 같다: 오브젝트는 있고, 에러는 없고, 타깃은 0건. 진단은 앞의 세 명령으로 한다.
journal-api: 두 번째 관측 대상 앱 (Node · prom-client로 계측){{PG}}
  • 실측.
  • 숫자 포트를 쓰려면 endpoints[].targetPort 라는 다른 필드를 써야 한다.
  • journal-api는 Node(Express)로 만든 두 번째 앱이다. prom-client로 order-api와 같은 이름(http_server_requests_seconds)의 히스토그램을 직접 만든다. 이름을 맞춘 덕에 뒤의 RED 질의 하나가 두 앱을 함께 다룬다.
  • labels와 selector가 갈린 이유: kustomize가 공통 라벨을 붙이면서 selector에는 넣지 않도록(includeSelectors: false) 설정해 두었기 때문.

#명령 · 질의볼 것 (기준값)

4E: sum by (job) (rate(…_count{status=~"5.."}[5m])) / sum by (job) (rate(…_count[5m]))≈ 0.061 (6.1%)
5D: sum by (job) (rate(…_sum[5m])) / sum by (job) (rate(…_count[5m]))≈ 0.045 (평균 45ms)

…_count · …_sum · …_bucket = http_server_requests_seconds_*{{PG}}

  • 3: order-api 35.66 · journal-api 31.90.
  • 4: order-api 0.061. journal-api는 기동 중 /readyz 가 503을 낸 기록 때문에 5xx 시계열이 있어 0이 나온다. 분자와 분모에 uri=~"/api/.*" 를 붙여 API 요청만 세면 journal-api는 "결과 없음"이 되고, or (sum by (job) (rate(…_count{uri=~"/api/.*"}[5m])) * 0) 을 붙이면 0으로 채워진다(실습 가이드 8-3).
  • 5: order-api 45.2ms · journal-api 0.53ms.
  • 6: order-api P50 0.57ms · P95 725ms · P99 790ms. 평균 45ms는 두 무리 사이 빈 곳.
  • 7: /api/chaos/slow 805ms, 나머지는 /actuator/prometheus 9.7ms, /actuator/health/** 3.4ms, /api/orders 1.5ms, /api/chaos/error 1.3ms.

05FAILURE ④ · BUCKETS

버킷 경계를 베껴 오면 분위수가 가짜가 된다

journal-api: order-api의 SLO 경계를 그대로 옮긴 버킷

buckets: [0.05, 0.1, 0.2, 0.5, 1]
# 결과
평균 = 1.03 ms
P50  = 25.00 ms     ← 평균의 25배?

# 버킷별 초당 개수
le=0.05  20.533/s
le=0.1   20.533/s  … 모든 버킷 값이 같다
le=+Inf  20.533/s

원인

모든 요청(1ms대)이 첫 버킷 [0, 0.05] 안에 들어갔다. histogram_quantile은 버킷 안을 선형 보간하므로 P50 = 0.05의 절반 = 25ms. 데이터가 아니라 보간이 만든 숫자다.

# 앱의 실제 지연에 맞춘 경계
buckets: [0.0005, 0.001, 0.0025, 0.005,
          0.01, 0.025, 0.05, 0.1, 0.25, 0.5, 1]
# 결과
평균 1.15ms · P50 1.09ms · P95 2.45ms · P99 4.88ms
버킷 경계는 그 앱의 실제 지연 분포에 맞춘다. 바꾸면 옛 경계의 시계열이 보존 기간 동안 섞인다{{PG}}
  • 실측.
  • 버킷마다 값이 다르면 분포가 실제로 담겼다는 뜻이다. 고친 뒤 P50 1.09ms가 평균 1.15ms와 맞고, P99 4.88ms가 꼬리를 보여 준다.
  • 경계를 바꾼 직후 옛 경계(le=0.2)가 잠시 섞여 보였다. 경계는 계측을 설계할 때 정하고 되도록 건드리지 않는다. 바꾸면 대시보드·알림 임계값도 함께 다시 본다.
