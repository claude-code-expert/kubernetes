00시작 전에

실습 가이드는 대부분 터미널 명령으로 진행한다. 이 문서는 같은 클러스터를 웹 화면으로 다룬다. Prometheus 화면에서 질의하고, Grafana Explore에서 메트릭과 로그를 나란히 보고, 대시보드를 처음부터 만들고, Alertmanager에서 알림을 잠시 끈다. 시나리오는 실습 가이드와 같다. "주문이 느려요"라는 제보를 화면만으로 따라가고, 그 과정에서 쓴 질의를 대시보드와 알림으로 남긴다. 화면은 Prometheus 3.14, Grafana 13.2, Alertmanager 0.34 기준이다.

0-1. 출발점: 실습 가이드 10장까지 마친 클러스터

이 문서는 설치를 다루지 않는다. 실습 가이드 1~10장을 마쳐서 아래가 모두 떠 있어야 한다. 하나라도 없으면 실습 가이드의 해당 절로 돌아간다.

필요한 것만드는 곳확인
kind 클러스터 obs, 두 앱실습 가이드 1~2장kubectl get pods -n apps · -n journal 모두 Running
kube-prometheus-stack3장kubectl -n monitoring get pods 9개 Running(8장의 alert-sink 포함, node-exporter는 노드마다 하나라 3개)
앱 수집 연결(ServiceMonitor)6장curl -s 'localhost:9090/api/v1/targets?state=active' | jq '[.data.activeTargets[] | select(.health=="up")] | length' → 33
알림 규칙과 수신 서버8장kubectl -n monitoring get prometheusrule study-app-rules → study-app-rules 한 줄
"스터디" 대시보드9장Grafana Dashboards 목록에 "스터디" 폴더
Loki · Alloy10장kubectl -n logging get pods 4개 Running

0-2. Grafana 메모리 한도를 2Gi로 올린다 주의

실습 가이드의 값 파일은 Grafana 메모리 한도를 1Gi로 둔다. 명령 위주 실습에는 충분하지만, Explore와 대시보드 편집기를 번갈아 쓰면 1Gi를 넘겨(1071Mi에서 응답이 멈춘 적이 있다) 화면이 굳는다. 화면 실습 전에 한도를 올린다. 터미널에서, 실습 가이드와 같이 monitoring-logging 폴더에서 친다.

helm upgrade kps prometheus-community/kube-prometheus-stack -n monitoring \
  --version 89.2.2 -f labs/helm/kps-values.yaml \
  --set grafana.resources.limits.memory=2Gi --wait --timeout 12m
kubectl -n monitoring get pod -l app.kubernetes.io/name=grafana \
  -o jsonpath='{.items[0].spec.containers[?(@.name=="grafana")].resources.limits.memory}{"\n"}'
2Gi

마지막 줄이 2Gi이면 통과다. Grafana 파드가 새로 뜨므로, 화면에서 직접 만든 것이 있었다면 사라진다. ConfigMap으로 넣은 "스터디" 대시보드는 사이드카가 다시 넣는다.

0-3. 화면 세 개를 열고 부하를 넣는다

세 화면의 port-forward가 떠 있어야 한다. 0-2에서 Grafana 파드가 새로 떴으므로 실습 가이드에서 띄운 Grafana port-forward는 끊겨 있다. 첫 줄이 남아 있는 세 화면의 port-forward를 먼저 끄므로, 몇 번을 다시 쳐도 결과가 같다. 이 줄이 없으면 이미 떠 있는 포트에서 새 port-forward가 address already in use로 죽고 [4] + 72411 exit 1 kubectl … port-forward …가 찍힌다. 앱 port-forward(18082 · 18083)는 건드리지 않는다. 이 문서는 9장까지 부하가 도는 동안 진행하므로 부하는 40분으로 넣는다. 중간에 끝나면 같은 명령으로 다시 띄우고, 멈출 때는 그 터미널에서 Ctrl-C.

pkill -f 'port-forward svc/kps-(grafana|kube-prometheus-stack)'; sleep 1
kubectl -n monitoring port-forward svc/kps-kube-prometheus-stack-prometheus 9090:9090 >/dev/null 2>&1 &
kubectl -n monitoring port-forward svc/kps-grafana 3000:80 >/dev/null 2>&1 &
kubectl -n monitoring port-forward svc/kps-kube-prometheus-stack-alertmanager 9093:9093 >/dev/null 2>&1 &
sleep 2   # port-forward가 리슨을 시작할 때까지. 없으면 000이 나온다
for u in 9090/-/ready 3000/api/health 9093/-/ready; do curl -s -o /dev/null -w "$u %{http_code}\n" localhost:$u; done
# 새 터미널에서 (앱 port-forward 18082 · 18083도 떠 있어야 한다)
k6 run -e DURATION=40m labs/k6/k6-red.js
9090/-/ready 200
3000/api/health 200
9093/-/ready 200
화면주소로그인
Prometheushttp://localhost:9090없음
Grafanahttp://localhost:3000admin / obs-study
Alertmanagerhttp://localhost:9093없음

세 줄이 모두 200이고, 세 주소가 브라우저에서 열리고, k6 터미널에 진행 표시가 흐르면 통과다. 질의 결과를 기준값과 비교하려면 부하 시작 5분 뒤부터 본다. 질의가 5분 창으로 계산하기 때문이다.

01Prometheus 화면

Prometheus 화면은 위쪽 메뉴 세 개가 전부다. Query는 질의, Alerts는 알림 규칙의 상태, Status는 수집과 설정의 상태다. 빠르게 값 하나를 확인하거나 질의를 다듬을 때 쓴다. 저장이나 공유는 Grafana에서 한다.

1-1. 수집 대상이 모두 살아 있는지 본다

  1. 위쪽 Status → Target health
  2. 위쪽 두 번째 칸 Filter by target health를 눌러 DOWN을 고른다

DOWN을 고르면 묶음이 모두 접히고 "Hiding pools with no matching targets · Hiding 19 empty pools due to filters or no targets." 안내만 남아야 한다. 묶음이 하나라도 남으면 그 안에 DOWN 타깃이 있다. DOWN을 지우면 묶음(scrape pool)마다 오른쪽에 2 / 2 up처럼 살아 있는 대상 수 / 전체 대상 수가 나온다. 세 번째 칸에 order-api를 넣으면 order-api 묶음(2 / 2 up)만 남는다.

1-2. 질의를 넣고 Table과 Graph로 본다

  1. 위쪽 Query. 입력칸에 아래 질의를 붙여 넣고 Execute
  2. 결과 위 Table 탭: 지금 값. Graph 탭: 시간에 따른 선
sum by (job) (rate(http_server_requests_seconds_count[5m]))

이번에는 P99를 경로(uri)별로 나눠 Graph 탭에서 본다. 왼쪽 위 15m은 그래프 범위이고 −와 +로 줄이고 늘린다. 옆의 End time을 비워 두면 지금까지를 그린다. Unstacked는 선을 따로, Stacked는 쌓아서 그린다.

histogram_quantile(0.99, sum by (uri, le) (rate(http_server_requests_seconds_bucket{job="order-api"}[5m])))

부하 5분 뒤 Table 탭에서 order-api가 약 36이면 통과다. Graph 탭에서는 0.8초 근처의 선 하나가 나머지보다 높게 떠 있어야 한다. 선 위에 마우스를 올리면 그 선의 uri가 보인다.

1-3. 메트릭 이름을 모를 때: 메트릭 탐색기

  1. Query 입력칸 오른쪽 끝 ⋮(Show query options) → Explore metrics
  2. 창 위 검색칸에 http_server_requests
  3. 줄 오른쪽 아이콘 세 개 가운데 {+}(Insert at cursor and close explorer)를 누르면 이름이 입력칸에 들어가고 창이 닫힌다. 돋보기는 그 메트릭의 라벨을 보여 주고, 마지막 아이콘은 이름 복사다

http_server_requests_seconds_bucket · _count · _sum이 histogram으로 보이면 통과다. 앱이 어떤 메트릭을 제공하는지 코드를 열지 않고 확인하는 방법이다.

1-4. 긴 질의를 쪼개서 읽는다: 트리 보기와 Explain

  1. 1-2의 P99 질의를 입력칸에 둔 채 ⋮ → Show tree view
  2. 입력칸 아래에 질의가 나무 모양으로 펼쳐진다. 각 줄 오른쪽에 그 부분의 결과 개수가 나온다
  3. 트리에서 한 줄을 누르고 Explain 탭으로 간다

트리를 켜지 않고 Explain 탭을 열면 "To use the Explain view, enable the query tree view (also available via the expression input menu) and then select a node in the tree above." 안내만 나온다. 노드를 고른 뒤 설명이 나오면 통과다.

1-5. 알림이 울리고 있는지 본다: Alerts

  1. 위쪽 Alerts
  2. 첫 번째 칸 Filter by rule group state에서 FIRING을 고른다
  3. 옆 검색칸 Filter by rule name or labels에 App
  4. 울리는 규칙 이름을 누르면 조건과 라벨이 펼쳐진다

부하 시작 약 3분 뒤 AppHighErrorRate, 4분 반쯤 뒤 AppHighLatencyP95가 FIRING이면 통과다. 상태 선택지는 INACTIVE · PENDING · FIRING · UNKNOWN이고 괄호 안 숫자가 개수다. 이름 칸에 App만 넣으면 울리지 않는 AppTargetDown · AppSLOFastBurn까지 같이 나오므로 상태 필터를 함께 쓴다.

1-6. 규칙이 오류 없이 평가되는지 본다: Rule health

  1. Status → Rule health
  2. 목록이 여러 쪽으로 나뉜다. 위쪽 쪽 번호에서 마지막 쪽(4)을 누르고 아래로 내리면 study-app 묶음이 있다. 브라우저 찾기(Cmd-F · Ctrl-F)는 지금 쪽만 찾는다. 이름 칸에 App을 넣어도 철자가 비슷한 다른 묶음까지 걸린다(흩어진 글자도 맞는 것으로 치는 검색)

study-app의 규칙 4개가 모두 OK면 통과다. ERR이면 평가 중 오류가 난 것이다. 문법 오류는 적용 단계(kubectl apply)에서 거부되어 여기까지 오지 않는다. 그 규칙 아래에 "Rule failed to evaluate"와 Error: 메시지가 붙는다.

02Grafana Explore: 메트릭

Explore는 Grafana에서 저장하지 않고 질의하는 곳이다. Prometheus 화면과 하는 일은 같지만, 같은 화면에서 Loki 로그와 나란히 볼 수 있고 질의 기록과 공유 링크가 남는다.

2-1. 로그인하고 메뉴를 확인한다

  1. http://localhost:3000 → admin / obs-study → Log in
  2. 왼쪽 메뉴를 확인한다

왼쪽 메뉴가 보이면 통과다. 창이 좁아 메뉴가 접혀 있으면 왼쪽 위 ≡를 누른다. 이 문서는 Explore(2·3장), Dashboards(4~6장), Alerting(8장), Drilldown(9장)을 쓴다.

2-2. Code 모드로 에러율을 질의한다

  1. 왼쪽 Explore → 위쪽 데이터소스 선택칸에서 Prometheus
  2. 질의 편집기 오른쪽 위 Builder · Code 중 Code
  3. 아래 질의를 넣고 오른쪽 위 Run query(또는 Shift+Enter). 창이 좁으면 글자 없이 파란 새로고침 아이콘만 보인다
sum by (job) (rate(http_server_requests_seconds_count{status=~"5.."}[5m])) / sum by (job) (rate(http_server_requests_seconds_count[5m]))

order-api 선이 0.06 근처(6%), journal-api 선이 0이면 통과다. 오른쪽 위 시간 선택칸(Last 15 minutes 등)으로 범위를 바꾼다.

2-3. Builder 모드로 요청률 질의를 클릭으로 만든다

  1. Builder를 누른다
  2. Metric 칸에서 http_server_requests_seconds_count를 고른다
  3. Label filters에서 job = order-api
  4. + Operations → Range functions → Rate. 다시 + Operations → Aggregations → Sum by, 생긴 Label 칸에서 job을 고른다. 순서를 바꾸면 rate 안에 sum이 들어가 오류가 난다

Builder 아래에 표시되는 질의가 sum by(job) (rate(http_server_requests_seconds_count{job="order-api"}[$__rate_interval])) 모양이면 통과다. $__rate_interval은 Grafana가 수집 주기에 맞춰 정하는 창 크기다.

2-4. 질의 기록과 Query inspector

  1. 질의 편집기 아래 Query history: 아래쪽에 지금까지 실행한 질의 목록이 열린다. 줄마다 별표를 누르면 Starred 탭에 고정되고, Run query로 다시 실행한다
  2. 옆의 Query inspector → Query 탭 → Refresh: Grafana가 실제로 보낸 요청과 받은 응답을 펼쳐 보여 준다. Data 탭은 받은 숫자 표다

Query 탭에 Expr:로 시작하는 질의와 Step: 30s(Last 15 minutes 기준. 범위를 늘리면 Step도 커진다), 요청 url: "api/ds/query?ds_type=prometheus…"가 보이면 통과다. 브라우저는 Prometheus에 직접 묻지 않고 Grafana 서버의 api/ds/query로 보낸다. Grafana 서버가 이를 Prometheus 질의로 바꿔 대신 묻는다. 대시보드 숫자가 이상할 때 실제로 나간 질의와 Step을 이 창에서 확인한다.

03Grafana Explore: 로그와 메트릭 나란히 보기

메트릭에서 에러율이 오른 것을 봤으면, 같은 시각의 로그에서 어떤 요청이 실패했는지 찾는다. Explore는 두 화면을 나란히 놓고 시간 범위를 함께 움직일 수 있다.

3-1. Label browser로 고르기를 만든다

  1. Explore 데이터소스를 Loki로 바꾼다
  2. 오른쪽 위 Builder · Code 중 Code, 편집기 위 Label browser
  3. 1번 줄에서 namespace, app을 누른다 → 2번 칸에 라벨마다 값 목록이 생기면 apps, order-api를 누른다. 전에 고른 것이 남아 있으면 맨 아래 Clear로 지우고 시작한다
  4. 3번 칸에 고르기가 만들어지면 Show logs

편집기에 {app="order-api",namespace="apps"}가 들어가고 아래에 로그 줄이 나오면 통과다. 라벨은 알파벳순으로 붙는다. {namespace="apps", app="order-api"}와 같은 뜻이다.

3-2. 500 줄만 거르고 줄 하나를 펼친다

  1. 편집기 질의 뒤에 |~ " 500 "을 붙이고 Run query. 아래 블록처럼 바꿔 넣어도 같다
  2. 로그 줄 하나를 누른다
{namespace="apps", app="order-api"} |~ " 500 "

보이는 줄이 모두 "GET /api/chaos/error?rate=0.7 HTTP/1.1" 500이면 통과다. 질의 뒤에 != "chaos/error"를 더 붙여 Run query 하면 0줄이 나와야 한다. 500 에러가 한 경로에서만 났다는 뜻이다.

3-3. Split으로 에러율과 500 로그를 나란히 놓는다

  1. 위쪽 Split을 누르면 오른쪽에 두 번째 칸이 생긴다
  2. 왼쪽은 Prometheus에 2-2의 에러율 질의, 오른쪽은 Loki에 3-2의 500 질의
  3. 한쪽 그래프에서 시간 범위를 끌어 좁히면 다른 쪽도 같은 범위로 바뀐다(시간 동기화). 왼쪽 칸 시간 선택칸 옆 사슬 아이콘이 켜져 있어야 한다. 꺼져 있으면 눌러 켠다

두 칸의 시간축이 같고, 왼쪽 order-api 선이 있는 구간에 오른쪽 Logs volume 막대도 있으면 통과다. 범위를 k6를 시작한 시각이 들어가게(Last 30 minutes 등) 잡으면, 선이 시작되는 시각과 막대가 나타나는 시각이 맞는 것이 보인다. 메트릭으로 시각을 좁히고 로그로 원인을 확인하는 순서를 한 화면에서 한다.

3-4. 실시간으로 흘려 본다: Live

  1. Loki 칸 오른쪽 위 Live. Split 상태면 글자 없이 ▷ 아이콘만 보인다(마우스를 올리면 Start live stream your logs)
  2. 새 줄이 들어오는 대로 목록 아래에 붙는다. Live 글자 왼쪽 ‖를 누르면 잠시 멈추고, 오른쪽 □(Stop and exit the live stream)를 누르면 Live를 끝낸다

k6가 도는 동안 1초에 2줄 안팎(에러 시나리오가 초당 3건 중 70%를 500으로 만든다) 새 500 줄이 붙으면 통과다. 배포 직후 에러가 나는지 지켜볼 때 쓴다.

04대시보드를 처음부터 만든다

실습 가이드 9장에서는 완성된 대시보드 JSON을 ConfigMap으로 넣었다. 여기서는 같은 대시보드를 화면에서 한 패널씩 만든다. 다 만든 뒤 6장에서 JSON과 비교한다. 만드는 대시보드 이름은 UI실습-서비스 RED로 한다.

4-1. 빈 대시보드를 연다

  1. 왼쪽 Dashboards → 오른쪽 위 New → New dashboard
  2. 가운데 Select layout은 Custom grid(패널 위치와 크기를 직접 정함)
  3. 오른쪽 위 시간 선택칸을 Last 15 minutes로, Refresh 옆 선택을 30s로 바꾼다

오른쪽에 Add 사이드바가 열려 있으면 통과다. 닫혔으면 오른쪽 세로 막대의 +를 누른다.

4-2. 첫 패널: 초당 요청 수(Stat)

  1. Add 사이드바의 Panel 그림을 누른다 → 빈 패널 "New panel"이 생긴다
  2. 패널 가운데 Configure visualization → 패널 편집기가 열린다
  3. 데이터소스가 Prometheus인지 확인하고, 질의 칸 오른쪽 Builder · Code 중 Code를 누른다(처음에는 Builder가 켜져 있다)
  4. 아래 질의를 넣고 Run queries
  5. 오른쪽 위 All visualizations → Stat
  6. 오른쪽 옵션 맨 위 Title에 초당 요청 수. 옵션 칸 오른쪽 위 돋보기를 누르고 unit을 치면 Standard options → Unit만 남는다. Throughput → requests/sec (rps)로 고른다
  7. 오른쪽 위 Back(대시보드로 돌아가기)

4-3. 나머지 패널 일곱 개

05변수: 위쪽 선택칸

변수는 대시보드 위쪽 선택칸이다. 고른 값이 패널 질의 안의 $이름 자리에 들어간다. 대시보드 하나로 네임스페이스와 서비스를 바꿔 가며 볼 수 있다. 정답 대시보드(labs/dashboards/study-red.json)에는 datasource · namespace · service 세 개가 있다. 여기서는 namespace와 service만 만든다. datasource 변수는 Prometheus를 여러 개 둘 때 고르는 칸이라 이 실습에는 없어도 된다. 캡처에 보이는 "데이터소스" 선택칸과 질의 편집기의 ${datasource}는 그 변수가 있는 상태다. service 목록은 고른 namespace에 따라 바뀐다.

5-1. namespace 변수 Grafana 13

Grafana 13에서는 변수를 대시보드 편집 사이드바에서 만든다. 예전처럼 Settings → Variables로 가면 "Variable settings have moved to the dashboard's sidebar" 안내만 나오고, Take me there를 누르면 같은 사이드바로 간다.

  1. 대시보드 오른쪽 위 Edit. 오른쪽 사이드바 제목이 Dashboard가 아니면 오른쪽 세로 막대의 톱니를 누른다. Variables 칸이 있는 사이드바가 열린다
  2. 사이드바 Variables 칸의 Add variable → 종류 Query. 사이드바 Add → Dashboard controls → Variable로도 같은 곳에 간다
  3. 사이드바의 Query variable 양식에서 Name namespace, Label 네임스페이스, Display Above dashboard
  4. Query options → Open variable editor. 열린 창에서 Data source Prometheus, Query type Label values, Label namespace, Metric http_server_requests_seconds_count. 아래 미리보기 값을 확인하고 창을 닫는다
  5. Selection options에서 Multi-value와 Include All value를 켠다

미리보기 값에 apps, journal 두 값이 나오고, 위쪽 변수 줄에 "네임스페이스" 선택칸이 생기면 통과다. 질의로 쓰면 label_values(http_server_requests_seconds_count, namespace)와 같다.

5-2. namespace에 따라 바뀌는 service 변수

  1. 변수를 하나 더 추가한다. Name service, Label 서비스
  2. Open variable editor에서 Query type Label values, Label service, Metric http_server_requests_seconds_count
  3. Label filters에 namespace =~ $namespace
  4. Multi-value, Include All value를 켠다
  5. 사이드바 Variables의 Show dependencies를 누르면 service가 namespace에 기대는 관계가 그림으로 나온다

위쪽 네임스페이스 칸에서 apps만 골랐을 때 서비스 칸 목록에 order-api만 남으면 통과다. 앞 변수의 값이 뒤 변수의 질의에 들어가기 때문이다.

5-3. 패널 질의에 변수를 넣는다

4장에서 만든 패널의 질의 고르기 부분에 조건을 붙인다. 여러 값을 고를 수 있게 했으므로 =가 아니라 =~를 쓴다.

  1. 패널 위에 마우스를 올리고 e 키(또는 패널 메뉴 → Edit) → 질의에 조건을 붙이고 Back
  2. 바꾸는 패널은 여섯 개다. "분당 주문 수"는 order-api 하나뿐이라 그대로 둔다. "앱 로그"는 {namespace=~"apps|journal"}을 {namespace=~"$namespace"}로만 바꾼다. Loki 로그의 라벨은 service가 아니라 service_name이라 service=~"$service"를 넣으면 아무것도 나오지 않는다
  3. "5xx 에러율"은 namespace, service 조건을 status 앞에 넣는다. 6-2에서 정답과 글자 단위로 비교하기 때문이다
  4. 여섯 패널을 다 고친 뒤 오른쪽 위 Save → Save, 이어서 Exit edit
# 전
sum(rate(http_server_requests_seconds_count[2m]))
# 후
sum(rate(http_server_requests_seconds_count{namespace=~"$namespace", service=~"$service"}[2m]))

위쪽 서비스 칸에서 journal-api만 고르면 "5xx 에러율"이 0%, "초당 요청 수"가 30 안팎으로 바뀌면 통과다. 변수를 All로 둔 채 질의에 =를 쓰면 패널이 "No data"가 된다. 여러 값이 (apps|journal) 같은 정규식으로 바뀌어 들어가기 때문이다.

06저장 · 내보내기 · 가져오기

화면에서 만든 대시보드는 Grafana 파드가 다시 뜨면 사라진다. JSON으로 내보내면 저장소에 넣어 버전을 관리하고, 실습 가이드 9장처럼 ConfigMap으로 다시 넣을 수 있다.

6-1. JSON으로 내보낸다 Grafana 13

  1. 대시보드 오른쪽 세로 막대 맨 위 Export(내려받기 그림) → Export as code
  2. Advanced options를 펼쳐 Model을 Classic으로 바꾼다. 기본값 V2 Resource는 apiVersion · metadata · spec로 싸인 새 형식이라 labs/dashboards/study-red.json과 모양이 다르다
  3. Export for sharing externally를 켜면 데이터소스가 ${DS_PROMETHEUS} 같은 자리표시자로 바뀐다. 같은 Grafana에 다시 넣을 거면 끈 채로 둔다
  4. Download file. 브라우저 기본 내려받기 폴더(~/Downloads)에 UI실습-서비스 RED로 시작하는 이름의 JSON으로 저장된다

받은 파일 첫머리가 "annotations"로 시작하고 "panels" 배열이 보이면 통과다. "apiVersion": "dashboard.grafana.app/v2"로 시작하면 Model이 V2 Resource였던 것이니 Classic으로 다시 받는다.

6-2. 정답 대시보드와 비교한다

받은 파일과 labs/dashboards/study-red.json의 패널 제목과 질의를 비교한다. 패널 위치(gridPos)와 id는 달라도 되므로 제목 순으로 정렬해 비교한다. 6-1에서 파일을 두 번 받았을 수 있어 가장 최근 파일을 쓴다. 터미널에서 monitoring-logging 폴더에서 친다.

F=$(ls -t ~/Downloads/UI실습-*.json | head -1)
diff <(jq -r '.panels[] | "\(.title)\t\(.targets[0].expr)"' "$F" | sort) \
     <(jq -r '.panels[] | "\(.title)\t\(.targets[0].expr)"' labs/dashboards/study-red.json | sort)

아무 줄도 나오지 않으면 통과다. <로 시작하는 줄이 내 것, >가 정답이다. 라벨 조건 순서나 띄어쓰기만 다른 줄은 질의 자체는 맞다. 그 밖에 다른 줄이 있으면 그 패널을 열어 질의를 다시 본다.

6-3. 파일에서 가져온다

  1. Dashboards → New → Import
  2. Upload dashboard JSON file로 labs/dashboards/study-red.json을 고른다
  3. Name을 UI실습-가져온 RED로 바꾼다
  4. UID 칸은 잠겨 있고 "Dashboard named '스터디 — 서비스 RED' … has the same UID"가 뜬다. Change uid를 누르고 칸을 비운다 → Import (Overwrite)

가져온 대시보드가 새 주소(/d/ 뒤에 Grafana가 만든 UID)로 열리고 패널 여덟 개에 값이 나오면 통과다. UID를 비우면 버튼 이름이 Overwrite로 남아 있어도 새 대시보드로 만들어지고 "스터디" 대시보드는 그대로다. UID를 그대로 두고 누르면 "스터디" 쪽을 덮어쓴다.

07Alertmanager 화면: 알림 보기와 침묵

Prometheus가 판단한 알림은 Alertmanager로 간다. Alertmanager 화면에서는 지금 어떤 알림이 어떤 묶음으로 나가는지 보고, 점검 시간처럼 알림이 필요 없을 때 침묵(silence)을 건다. 7~9장은 부하가 있어야 하므로 0-3의 k6가 끝났으면 같은 명령으로 다시 띄우고 5분 뒤부터 본다.

7-1. 지금 들어온 알림을 본다

  1. http://localhost:9093 → 위쪽 Alerts
  2. Receiver 선택칸으로 수신자별로 거른다. 체크 상자 Silenced · Inhibited · Muted를 켜면 숨겨진 알림도 보인다. Muted는 시간 구간(time interval)으로 묶인 알림인데 이 실습에는 없다

부하가 도는 동안 receiver: study-default 묶음에 AppHighErrorRate가 보이면 통과다. AppHighLatencyP95는 for가 3분이라 1분쯤 뒤에 같은 묶음 아래 한 줄 더 붙는다.

7-2. 침묵을 건다

  1. 오른쪽 위 New Silence
  2. Duration에 10m
  3. Matchers 칸에 alertname="AppHighErrorRate"를 치고 Enter. 칸 왼쪽에 조건이 칩으로 붙는다
  4. Creator에 이름, Comment에 UI실습 침묵
  5. Preview Alerts → 걸리는 알림 목록 확인 → Create

Preview Alerts 뒤 Affected alerts: 1과 alertname=AppHighErrorRate 라벨이 나오고, Create 뒤 Alerts 화면에서 그 알림이 사라지면 통과다. Silenced 체크 상자를 켜면 다시 보인다. 침묵 중에는 Alertmanager가 그 알림을 수신자에게 보내지 않는다. 다만 이 실습의 repeat_interval이 4h라 10분 안에는 침묵이 없어도 재전송이 없어서, 수신 서버 로그로는 차이가 보이지 않는다.

7-3. 침묵을 푼다

  1. 위쪽 Silences → Active 탭에서 방금 만든 침묵 줄
  2. 줄 오른쪽 링크 View · Edit · Expire 중 Expire → "Are you sure you want to expire this silence?" 창에서 Confirm

침묵이 Expired 목록으로 옮겨 가고, 알림이 Alerts 화면에 다시 나오면 통과다. 침묵은 정해 둔 시간이 지나면 저절로 풀리지만, 점검이 일찍 끝나면 이렇게 직접 푼다.

08Grafana 알림 (선택)

실습 가이드는 알림 규칙을 PrometheusRule 파일로 넣고 Prometheus가 평가했다. Grafana에서도 화면으로 알림 규칙을 만들 수 있다. 이 실습은 규칙을 저장소의 YAML로 두므로 PrometheusRule이 기본이고, Grafana 알림은 Loki 로그처럼 Prometheus가 평가하지 못하는 조건에만 쓴다. 8-3이 그 예다.

8-1. 알림 메뉴를 확인한다

  1. 왼쪽 Alerting
  2. Alert rules 칸의 Manage alert rules. 목록이 Grafana-managed와 Data source-managed로 나뉜다

Data source-managed 아래 Prometheus에 study-app 묶음(AppTargetDown · AppHighErrorRate · AppHighLatencyP95 · AppSLOFastBurn)이 보이면 통과다. PrometheusRule로 넣은 규칙도 Grafana가 읽어서 보여 주지만, 화면에서 수정은 안 된다.

8-2. 연락처를 만든다

  1. Alerting → Contact points. Notification configuration 화면의 Contact points 탭이 열린다 → + Create contact point
  2. Name UI실습-웹훅, Integration Webhook, URL http://alert-sink.monitoring.svc:8080/grafana
  3. 오른쪽 Test → Notification message는 Predefined 그대로 → Send test notification
  4. 창을 닫고 Save contact point

Test를 누른 뒤 터미널에서 수신 서버 로그를 본다.

kubectl -n monitoring logs deploy/alert-sink --since=2m | tail -3
14:21:30Z [firing] TestAlert severity=None job=- receiver=webhook | Notification test

Test 창 위쪽에 "Test notification sent successfully"가 뜨고, 위 명령의 출력에 TestAlert 줄이 있으면 통과다. 시각은 실행할 때마다 다르다.

8-3. 로그로 알림 규칙을 만든다

PrometheusRule로는 만들 수 없는 규칙을 하나 만든다. Loki 로그에서 500 줄이 1분에 30줄을 넘으면 울린다.

  1. Alerting → Alert rules → + New alert rule
  2. 1번 칸 Name UI실습-500 로그 급증
  3. 2번 칸 데이터소스 Loki, Code에 sum(count_over_time({namespace="apps"} |~ " 500 " [1m])) → Run queries
  4. 바로 아래 Alert condition을 WHEN QUERY IS ABOVE 30 → Preview alert rule condition
  5. 3번 칸 New folder로 UI실습. 4번 칸 New evaluation group으로 UI실습(평가 주기 1m), Pending period 1m
  6. 5번 칸 Contact point UI실습-웹훅
  7. 6번 칸 Summary에 apps 500 로그 급증 → 맨 아래 Save

Preview에서 Table 값이 120 안팎(에러 시나리오가 초당 3건 중 70%를 500으로 만드니 1분에 약 126줄)이고 Series 1 옆에 Firing이 보이면 조건은 맞다. 저장 뒤 평가 1분 + Pending 1분 + 묶어 보내기 대기를 합쳐 2~3분 지나면 Alert rules 목록에서 이 규칙이 Firing이 되고, 8-2의 kubectl logs 명령에 아래 줄이 찍히면 통과다.

14:46:20Z [firing] UI실습-500 로그 급증 severity=None job=- receiver=UI실습-웹훅 | apps 500 로그 급증

09Drilldown: 질의 없이 둘러보기

Drilldown은 질의를 쓰지 않고 클릭으로 메트릭과 로그를 좁혀 가는 앱이다. 무엇을 질의해야 할지 모를 때 출발점으로 쓴다.

9-1. Metrics

  1. 왼쪽 Drilldown → Metrics. 메트릭마다 작은 그래프 카드가 나온다
  2. 위쪽 Filters에 job = order-api, 검색칸에 http_server_requests
  3. http_server_requests_seconds_count 카드의 Select → Breakdown 탭에서 By label을 uri로

uri별 그래프 가운데 /api/orders가 초당 30 안팎으로 가장 높으면 통과다. Add to filters를 누르면 그 uri가 위쪽 Filters에 붙어 다음 탐색의 조건이 된다.

9-2. Logs

  1. Drilldown → Logs. 서비스(service_name 라벨)별 로그 양 그래프와 최근 줄이 나온다
  2. order-api의 Show logs → 위쪽 탭 Logs · Labels · Fields · Patterns

Logs 탭에 order-api 줄이, Labels 탭에 라벨 값별 로그 양 그래프가 나오면 통과다. Patterns 탭은 "Pattern matching has not been configured"가 나오는 것이 이 실습 구성의 정상 상태다. 비슷한 줄을 묶어 보는 Patterns는 Loki 쪽에서 패턴 수집기를 켜야 동작한다. 화면 안내의 --pattern-ingester.enabled=true는 Loki 실행 옵션이고, 이 실습처럼 Helm으로 설치했다면 값 파일 loki: 아래 pattern_ingester.enabled가 같은 설정이다. 이 문서에서는 켜지 않는다.

10정리

10-1. 이 문서에서 만든 것을 지운다

  1. Dashboards에서 UI실습-으로 시작하는 대시보드를 고르고 Delete
  2. Alerting → Alert rules에서 UI실습 폴더의 규칙 삭제, Contact points에서 UI실습-웹훅 삭제
  3. Dashboards에서 UI실습 폴더 Delete. 규칙을 먼저 지웠으므로 빈 폴더다. 연락처는 규칙이 쓰는 동안 지울 수 없으니 규칙 → 연락처 → 폴더 순서로 지운다
  4. Alertmanager Silences에 남은 침묵이 있으면 Expire → Confirm
  5. k6가 아직 돌고 있으면 그 터미널에서 Ctrl-C

Dashboards 검색칸에 UI실습을 쳤을 때 결과가 없고, Alerting → Contact points 목록에 UI실습-웹훅이 없으면 통과다. 실습 가이드 12장의 정리(port-forward 종료, 클러스터 삭제)는 그대로 쓴다.

0-2에서 올린 Grafana 메모리 2Gi는 되돌리지 않아도 된다. 클러스터를 남겨 두고 나중에 --set 없이 값 파일만으로 helm upgrade를 하면 1Gi로 돌아간다. 6장에서 받은 ~/Downloads/UI실습-*.json은 지워도 되고 저장소에 넣어도 된다.
