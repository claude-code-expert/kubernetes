캡처를 슬라이드에 붙이는 방법

따라하기 슬라이드에는 이미지 자리가 따로 없다. 캡처는 발표 중 C 키로 슬라이드 위에 띄우는 화면으로 붙는다.

  1. 캡처를 images/에 저장한다. 파일 이름은 각 캡처 항목에 적힌 이름을 쓴다. 두 가지 형식이 있다.
    • 이름 키: install.png, targets.png처럼 슬라이드에 붙은 키. 슬라이드 순서가 바뀌어도 따라간다(4~7장).
    • 슬라이드 번호: use.png처럼 s + 번호(1~3장).
    한 슬라이드에 여러 장이면 뒤에 -2, -3을 붙인다(red-2.png).
  2. 다시 빌드한다: python3 src/build.py (출력에 captures attached: N)
  3. 발표 중 그 슬라이드에서 오른쪽 위 캡처 N · C 버튼이나 C 키. 여러 장이면 누를 때마다 다음 장, Esc나 클릭으로 닫는다. 방향키로 넘어가면 자동으로 닫힌다.

  name: order-api
  namespace: apps
  labels:
    release: kps                      # ① 이것이 없으면 오퍼레이터가 이 오브젝트를 보지 않는다

  selector:
    matchLabels:
      app.kubernetes.io/name: order-api   # ② Service 에 붙은 라벨
  namespaceSelector:
    matchNames: [apps]
  endpoints:
    - port: http                      # ③ Service 의 포트 이름
      path: /actuator/prometheus      # 스프링 액추에이터의 경로
      interval: 30s
      scrapeTimeout: 10s
---

metadata:
  name: journal-api
  namespace: journal
  labels:
    release: kps

    matchLabels:
      app: journal-api                # journal-api Service 는 이 라벨을 쓴다

# 알림 규칙 4개. RED 질의에 임계값과 지속 시간(for)을 붙였다.
#   kubectl apply -f labs/k8s/prometheusrule.yaml
#
# ServiceMonitor 와 같은 이유로 release: kps 라벨이 필요하다.
# 확인: kubectl -n monitoring get prometheus -o jsonpath='{.items[0].spec.ruleSelector}'
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: study-app-rules
  namespace: monitoring
  labels:
    release: kps
spec:
  groups:
    - name: study-app
      interval: 30s        # 이 그룹의 규칙을 얼마나 자주 평가할지
      rules:
        # ── ① 대상이 사라졌다 ────────────────────────────────────────────
        # 증상이 아니라 관측 자체의 고장이다. 이것이 울리면 다른 알림을 믿을 수 없다.
        - alert: AppTargetDown
          expr: up{job=~"order-api|journal-api"} == 0
          for: 1m
          labels:
            severity: critical
          annotations:
            summary: "{{ $labels.job }} 스크레이프 실패"
            description: "{{ $labels.pod }} 를 1분 이상 긁지 못하고 있습니다."

        # ── ② 에러율 ─────────────────────────────────────────────────────
        # 에러 비율 질의에 임계값 5% 와 지속 2분을 더했다.
        # or 절이 없으면 5xx 가 하나도 없는 앱은 결과 자체가 없어 평가에서 빠진다.
        - alert: AppHighErrorRate
          expr: |
            100 * (
              sum by (job) (rate(http_server_requests_seconds_count{job=~"order-api|journal-api", status=~"5.."}[5m]))
              /
              sum by (job) (rate(http_server_requests_seconds_count{job=~"order-api|journal-api"}[5m]))
            ) > 5
          for: 2m
          labels:
            severity: warning
          annotations:
            summary: "{{ $labels.job }} 에러율 {{ $value | printf \"%.1f\" }}%"
            description: "5xx 비율이 2분 이상 5% 를 넘고 있습니다."

        # ── ③ 지연 ───────────────────────────────────────────────────────
        # le 를 남겨야 histogram_quantile 이 동작한다.
        - alert: AppHighLatencyP95
          expr: |
            histogram_quantile(0.95,
              sum by (job, le) (rate(http_server_requests_seconds_bucket{job=~"order-api|journal-api"}[5m]))
            ) > 0.5
          for: 3m
          labels:
            severity: warning
          annotations:
            summary: "{{ $labels.job }} P95 {{ $value | printf \"%.2f\" }}초"
            description: "P95 응답 시간이 3분 이상 500ms 를 넘고 있습니다."

        # ── ④ SLO 소진 속도 ──────────────────────────────────────────────
        # SLO 기반 알림. "느리다"가 아니라
        # "이 속도면 이번 달 예산을 다 쓴다"를 알린다.
        #
        # SLO: 요청의 99% 가 200ms 안에. 오차 예산은 1%.
        # 5분 창에서 예산을 14.4배 속도로 태우면 30일 예산을 2일 만에 소진한다.
        # 14.4 는 구글 SRE 워크북의 빠른 소진 계수다.
        - alert: AppSLOFastBurn
          expr: |
            (
              1 - (
                sum by (job) (rate(http_server_requests_seconds_bucket{job=~"order-api|journal-api", le="0.2"}[5m]))
                /
                sum by (job) (rate(http_server_requests_seconds_count{job=~"order-api|journal-api"}[5m]))
              )
            ) > (14.4 * 0.01)
          for: 2m
          labels:
            severity: critical
          annotations:
            summary: "{{ $labels.job }} SLO 예산을 빠르게 소진 중"
            description: "200ms 를 넘긴 요청 비율이 {{ $value | printf \"%.1%\" }} 입니다. 이 속도면 30일 예산이 2일 만에 사라집니다."

10-5. LogQL: 좁히고 · 거르고 · 꺼내고 · 센다 슬라이드 92 · 93

같은 부하가 도는 동안 친다. 로그 줄을 돌려주는 질의용 함수 logq를 하나 더 만든다(최근 N줄의 본문만, 기본 3줄).

logq()  { curl -sG localhost:3100/loki/api/v1/query_range --data-urlencode "query=$1" --data-urlencode "limit=${2:-3}" | jq -r '.data.result[].values[][1] | rtrimstr("\n")' | head -${2:-3}; }

① 라벨로 좁히고, ② 본문 정규식으로 거른다. |~는 정규식이 맞는 줄만 남긴다. 상태 코드 앞뒤 공백까지 넣어야 응답 바이트 · 시간 속 "500"이 걸리지 않는다.

logq '{namespace="apps", app="order-api"} |~ " 500 "'

127.0.0.1 - - [27/Sep/2026:02:24:48 +0000] "GET /api/chaos/error?rate=0.7 HTTP/1.1" 500 25 155
127.0.0.1 - - [27/Sep/2026:02:24:47 +0000] "GET /api/chaos/error?rate=0.7 HTTP/1.1" 500 25 272

③ 본문에서 필드를 꺼내고 ④ 센다. order-api 로그는 JSON이 아니라서 pattern 파서로 자리를 맞춘다. <_>는 버리는 자리, <status>처럼 이름을 주면 그 자리 값이 필드가 된다.

lokiq 'sum by (status) (count_over_time({namespace="apps", app="order-api"} | pattern `<_> <_> <_> [<_>] "<method> <path> <_>" <status> <_> <dur>` [5m]))'
lokiq 'sum by (path) (count_over_time({namespace="apps", app="order-api"} | pattern `<_> <_> <_> [<_>] "<method> <path> <_>" <status> <_> <dur>` | status="500" [5m]))'
status=200  10115
status=500  634
path=/api/chaos/error?rate=0.7  634

상태 코드별 줄 수, 그리고 500을 낸 경로. 메트릭이 "에러율 6%"라고 말한 것을 로그는 "그 요청은 GET /api/chaos/error?rate=0.7이었다"로 말한다.

journal-api 로그는 JSON이라 | json 한 번이면 필드가 모두 꺼내진다. 파서 뒤에는 | __error__=""를 붙여 파싱에 실패한 줄을 뺀다.

logq '{namespace="journal", app="journal-api"} | json | __error__="" | status >= 200' 2

원인: path처럼 값이 끝없는 필드를 라벨로 올렸다. Alloy에 JSON의 path · status를 라벨로 올리는 단계(loki.process의 stage.json + stage.labels)를 넣고 서로 다른 경로로 60번 요청하자 journal-api 스트림이 1개에서 61개가 됐다(실측). 확인은 시리즈 API로 최근 5분 동안의 라벨 조합을 센다.

curl -sG localhost:3100/loki/api/v1/series \
  --data-urlencode 'match[]={app="journal-api"}' \
  --data-urlencode "start=$(( $(date +%s) - 300 ))000000000" \
  | jq -r '.data | "스트림 \(length) · path 값 \([.[].path // empty] | unique | length)"'
스트림 61 · path 값 60

해결: 라벨은 namespace · app · pod · container처럼 값이 정해진 것만. 경로 · 상태 코드는 본문에 두고 파서로 꺼낸다(10-5). 되돌린 뒤에도 /loki/api/v1/labels에는 path가 보인다. 보존 기간(72시간) 안에 한 번이라도 있었던 라벨을 모두 돌려주기 때문이다. 현재 상태는 위 시리즈 API로 본다.
