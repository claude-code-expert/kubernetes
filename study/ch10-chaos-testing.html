01이론 — 통제된 실험

책 5.3 · 5.7 · 5.8 — 실험에서 마주칠 개념만 다룬다.

테스트가 실패하면 빌드도 실패한 것이다

원칙 하나면 된다. 테스트가 깨진 소스를 이미지로 구워 레지스트리에 올리는 순간, 그 이미지는 언젠가 배포된다. 이 실습에서는 ./gradlew build가 테스트를 포함하므로 재배포 스크립트 앞에 게이트가 이미 있다.

검사 대상은 애플리케이션 코드만이 아니다. helm lint처럼 차트와 매니페스트 같은 인프라 구성물도 같은 파이프라인에서 검사할 수 있다.

새 버전이 정상인지 무엇으로 판단하는가

롤링 업데이트든 블루/그린이든 카나리든 같은 질문에 부딪힌다. 카나리로 트래픽 10%를 새 버전에 흘렸다면, 그 10%가 양호한지 판단할 메트릭이 있어야 다음 단계로 갈 수 있다. 그 메트릭이 02장에서 심고 06장에서 뽑아낸 RED 지표다.

배포 전략은 관측이 없으면 절반만 동작한다. 롤링 업데이트가 무중단이 되는 조건도 이미 매니페스트에 들어 있다 — 레디니스 프로브가 새 파드를 준비될 때까지 서비스에서 빼 두고, terminationGracePeriodSeconds가 종료 중인 파드에 진행 중인 요청을 마칠 시간을 준다. 03장에서 심은 이 설정들이 이번 실험의 피험자다.

게임 데이 네 단계

카오스 엔지니어링은 넷플릭스에서 시작된 방법이다. 통제된 실험으로 장애를 주입해 취약점을 미리 찾는다. 절차는 네 단계다.

  1. 정상 상태(steady state)에 대한 가설을 세운다
  2. 시스템에 영향을 줄 실제 이벤트를 준비한다
  3. 대조군을 만들고 실험하면서 정상 상태와 비교한다
  4. 실험으로 가설을 판정한다
폭발 반경 최소화

핵심 규율은 이것 하나다. 첫 실험은 파드 1개, 네임스페이스 하나, 5분. 라벨로 지우면 매칭되는 파드가 전부 죽으므로 반드시 이름을 골라 하나만 지운다.

“스테이징에서 하면 되지 않나”에 대한 책의 답은 명확하다 — 스테이징은 구성·트래픽·데이터·모니터링이 전부 프로덕션과 달라서, 스테이징에서의 생존이 프로덕션의 생존을 보장하지 않는다. 이 실습 환경은 스테이징조차 아니지만, 절차와 규율을 몸에 익히는 것이 목적이다.

책과 달라진 것 — 카오스 도구

책 5.9.4는 chaostoolkit으로 실습한다. Chaos Toolkit은 0.39.0(2024-04) 이후 릴리스가 없다. 이 실습은 Chaos Mesh를 쓴다 — CNCF 프로젝트이고, 실험을 쿠버네티스 커스텀 리소스로 선언해 저장소에 남길 수 있다는 점이 재현성에서 결정적이다.

03Chaos Mesh 설치

kind 노드는 containerd를 쓴다. 소켓 경로를 지정하지 않으면 기본값인 도커 소켓을 찾다가 파드는 전부 Running인데 실험이 아무 일도 하지 않는 상태가 된다. 09절에서 그 상태를 일부러 재현한다.

helm repo add chaos-mesh https://charts.chaos-mesh.org
helm repo update

# 실습 당일 최신 안정 버전을 다시 확인한다 (2026-08 기준 2.8.2)
helm search repo chaos-mesh/chaos-mesh
kubectl create ns chaos-mesh

helm install chaos-mesh chaos-mesh/chaos-mesh \
  --namespace chaos-mesh \
  --version 2.8.2 \
  --set chaosDaemon.runtime=containerd \
  --set chaosDaemon.socketPath=/run/containerd/containerd.sock

두 플래그가 전부다. runtime과 socketPath를 빼면 설치는 성공하고 동작만 하지 않는다.

검증

kubectl -n chaos-mesh get pods

chaos-daemon은 데몬셋이라 노드 수만큼 뜬다. 워커 2개 구성이면 3개다. 컨트롤러 매니저는 리더 선출 때문에 3개, 대시보드가 1개다. 전부 Running이어야 다음으로 간다.

04실험 준비 — 세 개의 창

실험 내내 세 개의 창을 띄워 둔다. 주입하는 창과 관찰하는 창이 분리돼 있어야 무엇이 언제 변했는지 말할 수 있다.

터미널 1 — 부하

while true; do
  curl -s -o /dev/null -X POST http://localhost:30080/api/orders \
    -H 'Content-Type: application/json' \
    -d '{"item":"latte","quantity":2}'
  sleep 0.3
done
이 루프를 끄는 방법

이 창에서 Ctrl-C. 10절 뒷정리에서 다시 확인한다. 끄지 않으면 실습이 끝난 뒤에도 계속 돌면서 다음 실험의 기준선을 오염시킨다.

터미널 2 — 파드 상태

kubectl -n apps get pods -w

브라우저

그라파나의 obs-red 대시보드와 프로메테우스 Alerts 화면(localhost:30900/alerts)을 나란히 연다. 알림의 pending → firing → resolved 전이를 눈으로 보기 위해서다.

05게임 데이 시트 네 단계

실험 1건당 시트 1장. labs/apps/chaos/gameday-sheet.md를 복사해 쓴다. 1~3번을 실험 전에 채운다 — 돌리고 나서 가설을 쓰면 게임 데이가 아니라 사후 합리화다.

칸무엇을 적나예
폭발 반경영향을 받을 수 있는 최대 범위apps 네임스페이스의 order-api 파드 1개
중단 조건여기 닿으면 즉시 실험을 멈춘다gateway 5xx 가 20% 를 넘으면 kubectl delete
1. 정상 상태 가설무엇이 변하지 않아야 성공인가gateway P95 ≤ 120ms, 5xx ≤ 0.5%
2. 주입할 이벤트무엇을 어떻게 얼마나PodChaos pod-kill, mode: one
3. 대조군비교 기준이 될 값과 그 출처실험 전 30분간의 P95 · 에러율
4. 판정채택인가 기각인가, 근거는 어느 화면인가실험 후에만 채운다
기각도 실험 성공이다

가설이 기각되면 그것이 이 게임 데이의 수확이다. 몰랐던 취약점을 장애 전에 찾은 것이기 때문이다. 09절 두 번째 실패 실습이 정확히 그런 경우다.

06실험 1 — 손으로 파드 하나

가설 — replicas 2와 레디니스 프로브 덕분에 order-api 파드 하나가 죽어도 gateway의 5xx 비율은 AppHighErrorRate 임계값 5%를 넘지 않는다.

첫 실험은 폭발 반경을 손으로 통제한다. 도구를 쓰기 전에 무슨 일이 일어나는지 먼저 본다.

kubectl -n apps get pods -l app.kubernetes.io/name=order-api

위 목록에서 이름을 하나 골라 지운다. 라벨로 지우면 두 개가 다 죽는다.

kubectl -n apps delete pod <고른 파드 이름>

관찰 포인트

  • 터미널 2에서 새 파드가 뜨고 startupProbe를 통과할 때까지 걸리는 시간
  • 대시보드의 처리율(Rate)이 절반으로 떨어지는지
  • 에러(Errors) 패널이 튀는지 — 여기가 가설의 판정 지점이다

남은 파드 하나가 트래픽 전부를 받으므로 P95가 소폭 오르는 것은 정상이다. 가설은 에러율에 대한 것이지 지연에 대한 것이 아니다.

07실험 2 — 같은 실험을 선언형으로

결과는 실험 1과 같아야 한다. 차이는 재현성이다. 이 YAML은 저장소에 남고, 다음 사람이 같은 실험을 같은 조건으로 돌릴 수 있다.

# labs/apps/chaos/10-podchaos-order-api-kill.yaml
apiVersion: chaos-mesh.org/v1alpha1
kind: PodChaos
metadata:
  name: order-api-pod-kill
  namespace: chaos-mesh
spec:
  action: pod-kill
  mode: one                      # 폭발 반경 최소화 — 무작위 1개만
  selector:
    namespaces:
      - apps
    labelSelectors:
      app.kubernetes.io/name: order-api
kubectl apply -f labs/apps/chaos/10-podchaos-order-api-kill.yaml
kubectl -n chaos-mesh describe podchaos order-api-pod-kill
kubectl delete -f labs/apps/chaos/10-podchaos-order-api-kill.yaml

describe의 이벤트에 어느 파드를 골랐는지가 기록된다. 시트의 4번 판정 칸에 이 이름을 옮겨 적으면 나중에 같은 실험을 추적할 수 있다.

08실험 3 — 지연으로 알림 발화시키기

가설 — order-api에 600ms 지연을 주입하면 gateway P95가 따라 올라가 AppHighLatencyP95(P95 > 0.5s, for: 3m)가 발화하고, 5분 뒤 실험이 끝나면 저절로 해소된다.

02장에서 예고했던 “지연이 전파되는 모습”을 이번에는 앱 코드가 아니라 인프라 수준에서 만든다.

# labs/apps/chaos/20-networkchaos-order-api-delay.yaml
apiVersion: chaos-mesh.org/v1alpha1
kind: NetworkChaos
metadata:
  name: order-api-delay
  namespace: chaos-mesh
spec:
  action: delay
  mode: all
  selector:
    namespaces:
      - apps
    labelSelectors:
      app.kubernetes.io/name: order-api
  delay:
    latency: "600ms"             # 임계값 0.5s 를 jitter 감안해도 확실히 넘긴다
    jitter: "100ms"
  duration: "5m"                 # for: 3m 인 알림이 발화하는 것까지 보려면 3분 이상
kubectl apply -f labs/apps/chaos/20-networkchaos-order-api-delay.yaml

타임라인

부하 루프가 돌고 있어야 한다. 트래픽이 없으면 P95를 계산할 표본이 없다.

시각무엇이 보이나
0 ~ 1분obs-red 대시보드에서 order-api 와 gateway 의 P95 가 같이 계단을 그린다
3분경프로메테우스 Alerts 에서 AppHighLatencyP95 가 pending → firing
5분실험 자동 종료. P95 가 내려온다
8분경알림 resolved

발화 여부는 화면 말고 API로도 남긴다. 시트에 붙일 근거가 된다.

curl -s http://localhost:30900/api/v1/alerts \
  | jq '.data.alerts[] | {name:.labels.alertname, state:.state, since:.activeAt}'
두 개의 지연을 구분한다

주입한 지연은 600ms인데 알림은 3분 뒤에 울린다. 그 3분은 for가 만든 것이고, 07장에서 다룬 네 구간 중 하나다. 고장이 난 시각과 알림이 온 시각은 같지 않다 — 이 실험이 그 간격을 눈으로 보여 준다.

09일부러 실패시키기

① 소켓 경로를 빼고 설치하면

03절의 두 플래그 없이 설치하면 모든 파드가 Running인데 PodChaos를 적용해도 파드가 죽지 않는다. 에러 화면도 없다.

kubectl -n chaos-mesh logs ds/chaos-daemon | grep -i error | head

no such file or directory 류의 컨테이너 런타임 접속 실패가 보인다. 데몬은 떠 있지만 붙을 소켓이 없는 것이다.

교훈 — “설치 성공”과 “동작함”은 다르다. 04장에서 타깃을 하나하나 확인했던 것과 같은 이유다.

helm upgrade chaos-mesh chaos-mesh/chaos-mesh -n chaos-mesh --reuse-values \
  --set chaosDaemon.runtime=containerd \
  --set chaosDaemon.socketPath=/run/containerd/containerd.sock

② 안전장치를 빼고 실험 1을 다시

이번에는 가설이 기각돼야 정상이다.

kubectl -n apps scale deploy/order-api --replicas=1
kubectl apply -f labs/apps/chaos/10-podchaos-order-api-kill.yaml

유일한 파드가 죽는 순간 gateway는 502를 뱉는다. JVM 기동과 startupProbe 통과까지 수십 초 동안 에러율이 100%에 머물고 AppHighErrorRate가 발화한다. 03장에서 replicas 2와 프로브 세 개를 심은 이유가, 그것을 빼는 순간 그래프로 증명된다.

kubectl delete -f labs/apps/chaos/10-podchaos-order-api-kill.yaml
kubectl -n apps scale deploy/order-api --replicas=2

시트의 4번 칸에 “기각”이라고 적고 근거 화면을 남긴다. 기각을 기록하지 않으면 다음 사람이 같은 함정에 빠진다.

10뒷정리

부하 루프를 먼저 끈다. 터미널 1에서 Ctrl-C.

kubectl -n chaos-mesh get podchaos,networkchaos

남아 있는 실험이 없어야 한다. 있으면 kubectl delete로 지운다. duration이 붙은 실험은 시간이 지나면 스스로 해제되지만, 리소스 자체는 남는다.

kubectl -n apps get deploy order-api        # READY 2/2 로 원복됐는지
helm uninstall chaos-mesh -n chaos-mesh    # Chaos Mesh 자체를 내릴 때

클러스터를 통째로 지우려면 09장의 정리 절차를 쓴다.

11완료 체크리스트

  • kubectl -n chaos-mesh get pods → 전부 Running, chaos-daemon 이 노드 수만큼
  • 실험 1·2 — 파드 킬 중에도 5xx 비율 5% 미만, 새 파드 RESTARTS 0 으로 Running
  • 실험 3 — AppHighLatencyP95 가 firing 까지 갔다가 resolved 로 돌아온 이력이 Alerts 화면에 남는다
  • 실패 실습 ② — AppHighErrorRate 발화, 시트에 “기각” 기록
  • 게임 데이 시트 4장이 채워져 있다 (1~3번은 실험 전에 쓴 것)
  • 부하 루프 종료 · kubectl -n chaos-mesh get podchaos,networkchaos → 결과 없음
  • kubectl -n apps get deploy order-api → READY 2/2
