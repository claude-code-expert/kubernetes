쿠버네티스 관측성

테스팅과 카오스 실험

여기까지 만든 관측 체계가 쓸모 있는지 확인하는 유일한 방법은 이상을 일부러 만들어 보는 것이다. 가설을 먼저 쓰고 실험을 나중에 돌린다.

01왜 이 장이 필요한가

09장까지 오면 대시보드가 있고 알림이 있다. 그런데 그것이 실제로 동작하는지는 아직 모른다. 알림은 한 번도 진짜 장애에 울려 본 적이 없고, 대시보드는 평온한 그래프만 보여 줬다.

확인하는 방법은 하나뿐이다 — 이상을 일부러 만들고, 만들어 둔 체계가 그것을 잡아내는지 판정하는 것. 07장에서 만든 알림이 우는지, 05·07장의 대시보드가 그것을 보여 주는지가 이 장의 시험 문제다.

그러려면 순서가 중요하다. 가설을 먼저 쓰고 실험을 나중에 돌린다. 돌리고 나서 “역시 이렇게 될 줄 알았다”고 적으면 그것은 실험이 아니라 사후 합리화다.

02알아야 할 개념

테스트가 실패하면 빌드도 실패한 것이다

책 5.3 · 5.7 · 5.8

원칙 하나면 된다. 테스트가 깨진 소스를 이미지로 구워 레지스트리에 올리는 순간, 그 이미지는 언젠가 배포된다. 이 실습에서는 ./gradlew build 가 테스트를 포함하므로 재배포 스크립트 앞에 게이트가 이미 있다. 검사 대상은 애플리케이션 코드만이 아니다 — helm lint 처럼 차트와 매니페스트도 같은 파이프라인에서 검사한다.

새 버전이 정상인지 무엇으로 판단하는가

롤링 업데이트든 블루/그린이든 카나리든 같은 질문에 부딪힌다. 카나리로 트래픽 10% 를 새 버전에 흘렸다면, 그 10% 가 양호한지 판단할 메트릭이 있어야 다음 단계로 갈 수 있다. 그 메트릭이 02장에서 심고 06장에서 뽑아낸 RED (Rate, Errors, Duration · 애플리케이션을 보는 세 지표) 지표다. 배포 전략은 관측이 없으면 절반만 동작한다.

게임 데이 네 단계

카오스 엔지니어링은 넷플릭스에서 시작된 방법이다. 통제된 실험으로 장애를 주입해 취약점을 미리 찾는다. 절차는 넷이고, 앞의 셋은 실험 전에 채운다.

단계무엇을 적나언제
1. 정상 상태 가설무엇이 변하지 않아야 성공인가실험 전
2. 주입할 이벤트무엇을 어떻게 얼마나실험 전
3. 대조군비교 기준이 될 값과 그 출처실험 전
4. 판정채택인가 기각인가, 근거는 어느 화면인가실험 후

폭발 반경 최소화

핵심 규율은 이것 하나다

첫 실험은 파드 1개, 네임스페이스 하나, 5분. 라벨로 지우면 매칭되는 파드가 전부 죽으므로 반드시 이름을 골라 하나만 지운다. 도구를 쓸 때는 mode: one 이 그 역할을 한다.

“스테이징에서 하면 되지 않나”에 대한 답은 명확하다 — 스테이징은 구성·트래픽·데이터·모니터링이 전부 프로덕션과 달라서, 스테이징에서의 생존이 프로덕션의 생존을 보장하지 않는다. 이 실습 환경은 스테이징조차 아니지만 절차와 규율을 몸에 익히는 것이 목적이다.

책과 달라진 것 — 카오스 도구

책 5.9.4 는 chaostoolkit 으로 실습한다. Chaos Toolkit 은 0.39.0(2024-04) 이후 릴리스가 없다. 이 실습은 Chaos Mesh 를 쓴다 — CNCF (Cloud Native Computing Foundation · 쿠버네티스·프로메테우스를 관리하는 재단) 프로젝트이고, 실험을 쿠버네티스 커스텀 리소스로 선언해 저장소에 남길 수 있다는 점이 재현성에서 결정적이다.

이 장을 마치면 할 수 있는 것

  1. 게임 데이 시트의 1~3번을 실험 전에 채우고, 4번만 실험 후에 채울 수 있다.
  2. 폭발 반경을 손으로도(delete pod) 선언형으로도(mode: one) 통제할 수 있다.

  5. 가설이 기각되는 실험을 일부러 돌리고, 기각을 기록할 수 있다.

실험 세 개를 돌리고 시트 네 장을 채운다. 그중 하나는 가설이 기각되는 실험이다 — 03장에서 심은 안전장치를 빼면 무슨 일이 일어나는지를 그래프로 증명한다.

게임 데이 시트와 폭발 반경

WHY시트와 폭발 반경을 코드로 남기는 곳

study/labs/apps/chaos/ — 이 장에서 쓰는 파일 
study/labs/apps/chaos/
├── gameday-sheet.md                     시트 양식. 실험 1건당 한 장 복사해 쓴다
├── 10-podchaos-order-api-kill.yaml      실험 2 — 파드 1개 강제 종료
└── 20-networkchaos-order-api-delay.yaml 실험 3 — 600ms 지연 주입
10-podchaos-order-api-kill.yaml — 가설이 파일 안에 들어 있다 
# 가설: replicas 2 + readinessProbe 덕분에 파드 1개가 죽어도
#       gateway의 5xx 비율은 AppHighErrorRate 임계값(5%) 아래에 머문다.
#
# mode: one — 폭발 반경 최소화. 대상 파드 중 무작위 1개만 종료한다.
apiVersion: chaos-mesh.org/v1alpha1
kind: PodChaos
metadata:
  name: order-api-pod-kill
  namespace: chaos-mesh
spec:
  action: pod-kill
  mode: one
  selector:
    namespaces:
      - apps
    labelSelectors:
      app.kubernetes.io/name: order-api
필드그림의 어느 부분바꾸면
mode: one주황 상자 하나all 로 바꾸면 매칭되는 파드가 전부 죽는다
selector.namespaces네임스페이스 경계넓히면 폭발 반경이 그만큼 커진다
selector.labelSelectors대상 후보라벨을 느슨하게 쓰면 의도치 않은 워크로드가 포함된다
파일 맨 위 주석의 가설시트 1번 칸—
가설을 YAML (YAML Ain't Markup Language · 들여쓰기로 구조를 적는 설정 형식) 주석에 적는 이유

실험 파일과 가설이 같은 파일에 있으면 저장소에서 함께 리뷰되고 함께 버전 관리된다. 시트만 따로 두면 시간이 지나며 실험 파일과 어긋난다. 파일을 연 사람이 “이 실험이 무엇을 증명하려는 것인가”를 바로 알 수 있다는 것도 이점이다.

고장 시각과 알림 시각은 같지 않다

WHY600ms 와 5분이라는 숫자 — 알림 설정에서 역산한다

20-networkchaos-order-api-delay.yaml — 숫자의 근거가 주석에 있다 
# 600ms인 이유: 알림 임계값이 0.5s이므로 jitter를 감안해도 확실히 넘긴다.
# duration 5m인 이유: for: 3m 인 알림이 발화하는 것까지 보려면 3분 이상 유지돼야 한다.
spec:
  action: delay
  mode: all
  selector:
    namespaces: [apps]
    labelSelectors:
      app.kubernetes.io/name: order-api
  delay:
    latency: "600ms"
    jitter: "100ms"
  duration: "5m"
실험 설정어느 값에서 역산했나
latency: 600ms07장 AppHighLatencyP95 의 임계값 > 0.5s. jitter 100ms 를 빼도 넘는다
duration: 5m같은 규칙의 for: 3m. 3분을 버텨야 발화하므로 여유를 둔다
mode: all여기서는 일부러 전부다 — 파드 하나만 느리면 나머지가 받아내 P95 가 덜 오른다
실험 3만 mode: all 인 이유

실험 2(파드 킬)는 mode: one, 실험 3(지연)은 mode: all 이다. 모순처럼 보이지만 폭발 반경의 성격이 다르다 — 파드를 죽이는 것은 되돌리는 데 시간이 걸리고, 지연 주입은 duration 이 지나면 자동으로 풀린다. 그리고 이 실험의 목적이 “알림이 우는지”이므로 P95 를 확실히 넘겨야 한다.

05Chaos Mesh 설치

목적: 실험을 커스텀 리소스로 선언할 수 있게 만든다.

kind 노드는 containerd 를 쓴다. 소켓 경로를 지정하지 않으면 기본값인 도커 소켓을 찾다가, 파드는 전부 Running 인데 실험이 아무 일도 하지 않는 상태가 된다. 11절에서 그 상태를 일부러 재현한다.

helm repo add chaos-mesh https://charts.chaos-mesh.org
helm repo update

helm upgrade --install chaos-mesh chaos-mesh/chaos-mesh \
  --namespace chaos-mesh --create-namespace \
  --set chaosDaemon.runtime=containerd \
  --set chaosDaemon.socketPath=/run/containerd/containerd.sock \
  --wait --timeout 10m

설치가 아니라 설정을 검증한다

kubectl -n chaos-mesh get pods

파드가 Running 인 것으로는 부족하다. 넘긴 플래그가 실제로 들어갔는지를 본다.

kubectl -n chaos-mesh get ds chaos-daemon \
  -o jsonpath='{.spec.template.spec.containers[0].command}' \
  | tr ',' '\n' | grep -A1 'runtime\|socket'

--- 출력 (전체 command 를 펼친 모습) ---

/usr/local/bin/chaos-daemon --runtime containerd --http-port 31766 --grpc-port 31767
  --pprof --ca /etc/chaos-daemon/cert/ca.crt ... --runtime-socket-path /host-run/containerd.sock
판정

--runtime containerd 와 --runtime-socket-path 가 보이면 된다. 소켓 경로가 /host-run/... 인 것은 데몬이 호스트 경로를 컨테이너 안의 그 위치에 마운트해 쓰기 때문이다 — 우리가 넘긴 /run/containerd/containerd.sock 이 그 자리에 붙는다.

--runtime docker 로 보이면 플래그가 안 들어간 것이다. 11절의 첫 번째 실패가 그 상태다.

chaos-daemon 은 DaemonSet 이므로 노드 수만큼 떠야 한다. 실제 주입은 이 파드가 한다.

07실험 1 — 손으로 파드 하나

가설 — replicas 2 와 레디니스 프로브 덕분에 order-api 파드 하나가 죽어도 gateway 의 5xx 비율은 AppHighErrorRate 임계값 5% 를 넘지 않는다.

첫 실험은 폭발 반경을 손으로 통제한다. 도구를 쓰기 전에 무슨 일이 일어나는지 먼저 본다.

kubectl -n apps get pods -l app.kubernetes.io/name=order-api

위 목록에서 이름을 하나 골라 지운다. 라벨로 지우면 두 개가 다 죽는다.

kubectl -n apps delete pod <고른 파드 이름>
어디를 보나무엇이 보여야 하나
터미널 2새 파드가 뜨고 startupProbe 를 통과할 때까지의 시간
대시보드 처리율(R)순간적으로 떨어졌다 회복된다
대시보드 에러율(E)여기가 가설의 판정 지점이다 — 5% 를 넘지 않아야 한다
대시보드 P95(D)소폭 오른다. 남은 파드 하나가 트래픽 전부를 받으므로 정상이다

가설은 에러율에 대한 것이지 지연에 대한 것이 아니다. 시트를 쓸 때 무엇에 대한 가설인지 분명히 적어야 판정이 흔들리지 않는다.

describe 의 이벤트에 어느 파드를 골랐는지가 기록된다. 시트의 4번 판정 칸에 이 이름을 옮겨 적으면 나중에 같은 실험을 추적할 수 있다. mode: one 은 무작위이므로 기록해 두지 않으면 어느 파드였는지 알 수 없다.

09실험 3 — 지연으로 알림 발화시키기

가설 — order-api 에 600ms 지연을 주입하면 gateway P95 가 따라 올라가 AppHighLatencyP95(P95 > 0.5s, for: 3m)가 발화하고, 5분 뒤 실험이 끝나면 저절로 해소된다.

02장에서 예고했던 “지연이 전파되는 모습”을 이번에는 앱 코드가 아니라 인프라 수준에서 만든다. 03절 그림 2 의 타임라인이 이 실험이다.

kubectl apply -f study/labs/apps/chaos/20-networkchaos-order-api-delay.yaml

부하 루프가 돌고 있어야 한다. 트래픽이 없으면 P95 를 계산할 표본이 없다.

시각무엇이 보이나
0 ~ 1분obs-red 대시보드에서 order-api 와 gateway 의 P95 가 같이 계단을 그린다
3분경프로메테우스 Alerts 에서 AppHighLatencyP95 가 pending → firing
5분실험 자동 종료. P95 가 내려온다
8분경알림 resolved

발화 여부는 화면 말고 API (Application Programming Interface · 프로그램끼리 주고받는 규약) 로도 남긴다. 시트에 붙일 근거가 된다.

curl -s http://localhost:30900/api/v1/alerts \
  | jq '.data.alerts[] | {name:.labels.alertname, state:.state, since:.activeAt}'
두 개의 지연을 구분한다

주입한 지연은 600ms 인데 알림은 3분 뒤에 울린다. 그 3분은 for 가 만든 것이고, 07장에서 다룬 네 구간 중 하나다. 대시보드는 즉시 반응하고 알림은 늦게 온다 — 둘 다 정상이며, 이 차이를 모르면 “알림이 고장났다”고 오해한다.

10일부러 실패시키기

① 소켓 경로를 빼고 설치하면

05절의 두 플래그 없이 설치하면 모든 파드가 Running 인데 PodChaos 를 적용해도 파드가 죽지 않는다. 에러 화면도 없다.

kubectl -n chaos-mesh logs ds/chaos-daemon | grep -i error | head

no such file or directory 류의 컨테이너 런타임 접속 실패가 보인다. 데몬은 떠 있지만 붙을 소켓이 없는 것이다.

교훈 — “설치 성공”과 “동작함”은 다르다

04장에서 타깃을 하나하나 확인했던 것과 같은 이유다. 이 실습 전체에서 반복되는 주제이기도 하다 — kubectl get pods 가 전부 Running 이어도 그것은 기동했다는 뜻일 뿐이다. 05절에서 command 플래그를 직접 확인한 이유가 이것이다.

helm upgrade chaos-mesh chaos-mesh/chaos-mesh -n chaos-mesh --reuse-values \
  --set chaosDaemon.runtime=containerd \
  --set chaosDaemon.socketPath=/run/containerd/containerd.sock

② 안전장치를 빼고 실험 1을 다시

이번에는 가설이 기각돼야 정상이다.

kubectl -n apps scale deploy/order-api --replicas=1
kubectl apply -f study/labs/apps/chaos/10-podchaos-order-api-kill.yaml

유일한 파드가 죽는 순간 gateway 는 502 를 뱉는다. JVM (Java Virtual Machine · 자바 가상 머신) 기동과 startupProbe 통과까지 수십 초 동안 에러율이 100% 에 머물고 AppHighErrorRate 가 발화한다.

03장의 설정이 여기서 증명된다

replicas 2 와 프로브 세 개를 심은 이유가, 그것을 빼는 순간 그래프로 증명된다. 실험 1에서는 같은 조작에도 에러율이 5% 아래였다. 차이는 복제본 하나뿐이다.

kubectl delete -f study/labs/apps/chaos/10-podchaos-order-api-kill.yaml
kubectl -n apps scale deploy/order-api --replicas=2

시트의 4번 칸에 “기각”이라고 적고 근거 화면을 남긴다. 기각을 기록하지 않으면 다음 사람이 같은 함정에 빠진다.

11뒷정리

부하 루프를 먼저 끈다. 터미널 1에서 Ctrl-C.

kubectl -n chaos-mesh get podchaos,networkchaos

남아 있는 실험이 없어야 한다. 있으면 kubectl delete 로 지운다. duration 이 붙은 실험은 시간이 지나면 스스로 해제되지만 리소스 자체는 남는다.

kubectl -n apps get deploy order-api        # READY 2/2 로 원복됐는지
helm uninstall chaos-mesh -n chaos-mesh    # Chaos Mesh 자체를 내릴 때

클러스터를 통째로 지우려면 09장의 정리 절차를 쓴다.
