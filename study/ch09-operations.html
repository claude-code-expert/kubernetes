쿠버네티스 관측성

운영과 모범 사례

여기까지 만든 것은 동작하는 관측 스택이다. 이 장은 그것을 망가지지 않는 스택으로 바꾸고, 실습에서 일부러 타협한 설정을 하나씩 되짚는다.

01왜 이 장이 필요한가

08장까지 오면 메트릭과 로그가 한 화면에 있다. 잘 돌아간다. 그런데 이 스택은 한 사람이 노트북에서 돌리는 것을 전제로 설정돼 있다 — 보존 기간이 짧고, 복제본이 없고, 인증이 열려 있고, 자원 제한이 헐겁다.

그대로 사내 클러스터에 올리면 대개 첫 주에 문제가 난다. 그 문제가 무엇인지, 그리고 어느 설정이 실습용 타협이었는지를 정리하는 것이 이 장이다.

가장 먼저 다룰 것은 카디널리티다. 프로메테우스를 죽이는 1번 원인이고, 06장에서 앱 메트릭을 붙인 순간부터 이미 시작된 문제다.

02알아야 할 개념

느낌이 아니라 숫자로 본다

책 3.12

“무겁다”로는 고칠 수 없다. 현재 시계열 개수, 초당 샘플 수, 디스크 사용량을 먼저 질의해 숫자로 만든 다음, 어느 메트릭이 상위를 차지하는지 찾아 잘라낸다. 이 장의 실습이 그 순서다.

카디널리티는 곱셈이다

시계열 하나하나가 메모리를 차지하는데, 시계열 개수는 라벨 값의 조합만큼 생긴다. 덧셈이 아니라 곱셈이라는 점이 무섭다. 라벨 하나를 잘못 추가하면 수만 배가 된다.

간격·보존·디스크는 한 덩어리다

스크레이프 간격을 줄이면 해상도가 오르지만 디스크와 메모리가 함께 는다. 보존 기간을 늘리면 과거를 볼 수 있지만 같은 대가를 치른다. 셋 중 둘을 정하면 나머지 하나가 결정되므로, 무엇을 포기할지를 먼저 정하고 숫자를 넣는다.

CPU 와 메모리는 성질이 다르다

CPU (Central Processing Unit · 중앙처리장치) 는 모자라면 느려진다. 메모리는 모자라면 죽는다. 그래서 CPU 제한은 신중하게 걸고, 메모리 제한은 반드시 건다. 03장에서 CPU limit 을 일부러 비워 둔 판단의 근거가 이것이고, 이 장에서 숫자로 확인한다.

이 장을 마치면 할 수 있는 것

  1. 시계열 개수와 초당 샘플 수를 질의해 현재 상태를 숫자로 말할 수 있다.
  2. 어느 메트릭이 카디널리티 상위를 차지하는지 찾고, 예상과 다르다는 것을 확인할 수 있다.

  5. 실습용 타협 설정 13가지를 짚고, 운영으로 옮길 때 무엇을 바꿀지 말할 수 있다.

--- 출력 ---

판정

4종류. 02장에서 @PathVariable 로 매핑했기 때문에 주문이 몇 건 생기든 이 숫자는 늘지 않는다. 이 숫자가 시간에 따라 계속 는다면 그것이 위험 신호다 — 며칠 간격으로 다시 재 보는 것이 카디널리티 감시의 실체다.

진단 질의는 습관적으로 쓰지 않는다

topk(10, count by (__name__) ({__name__=~".+"})) 같은 질의는 모든 시계열을 훑는다. 실습 규모에서는 순식간이지만 운영 프로메테우스에서는 그 자체가 부하다. 같은 정보를 /api/v1/status/tsdb(브라우저로는 /tsdb-status)가 이미 계산해 두고 있으므로 그쪽을 먼저 본다.

05잘라내기 실습

수집 단계에서 필요 없는 메트릭을 버린다. 저장된 뒤에 지우는 것보다 훨씬 싸고 확실하다. ServiceMonitor 의 metricRelabelings 가 그 자리다.

study/labs/k8s/monitoring/90-servicemonitors.yaml — order-api 엔드포인트에 추가 
  endpoints:
    - port: http
      path: /actuator/prometheus
      interval: 30s
      scrapeTimeout: 10s
      # 저장 직전에 적용된다. 여기서 drop된 것은 디스크에 남지 않는다.
      metricRelabelings:
        # 1) 실습에서 볼 일 없는 메트릭 묶음을 통째로 버린다
        - sourceLabels: [__name__]
          regex: "jvm_buffer_.*|jvm_classes_.*|process_start_time_seconds"
          action: drop

        # 2) 액추에이터 엔드포인트 자신에 대한 요청은 관심 대상이 아니다
        - sourceLabels: [uri]
          regex: "/actuator.*"
          action: drop

        # 3) 404가 찍히는 정체불명 경로는 uri 라벨을 통일해 버린다
        #    (스캐너가 임의 경로를 두드리면 카디널리티가 폭증한다)
        - sourceLabels: [status]
          regex: "404"
          targetLabel: uri
          replacement: "NOT_FOUND"
          action: replace
규칙무엇을 막나대가
① __name__ 으로 drop안 쓰는 메트릭 묶음이 디스크를 먹는 것나중에 필요해지면 없다
② uri=/actuator.* drop프로브와 스크레이프 자신이 만드는 잡음액추에이터 응답 시간을 볼 수 없다
③ 404 의 uri 를 NOT_FOUND 로스캐너가 만드는 무한 경로어떤 경로가 404 였는지는 로그로만 안다

③번이 실제로 사고를 막는 규칙이다. 인터넷에 노출된 서비스는 하루에도 수천 개의 임의 경로를 두드려 맞는데, 그것이 전부 uri 라벨 값이 되면 하루 만에 프로메테우스가 죽는다.

kubectl apply -f study/labs/k8s/monitoring/90-servicemonitors.yaml

# 적용 전후로 시계열 수를 비교한다 (반영에 1분 정도)
curl -s --get http://localhost:30900/api/v1/query \
  --data-urlencode 'query=prometheus_tsdb_head_series' \
  | jq -r '.data.result[0].value[1]'
숫자가 즉시 줄지 않는다

이미 저장된 시계열은 바로 사라지지 않는다. 새로 들어오는 데이터가 없으면 보존 기간이 지나며 정리된다. 드롭은 “앞으로 안 받는다”이지 “지금 지운다”가 아니다.

드롭 규칙은 되돌리기 어렵다

버린 데이터는 없는 데이터다. 장애 조사 중에 “그 메트릭이 있었더라면”이라고 후회하는 상황이 실제로 생긴다. 먼저 지울 것은 명백한 쓰레기부터, 애매한 것은 보존 기간을 줄이는 쪽으로 대응한다.

네이티브 히스토그램이라는 대안

버킷이 카디널리티의 큰 몫을 차지한다는 것을 04절에서 숫자로 봤다(le 493종). Prometheus 3.8 부터 정식이 된 네이티브 히스토그램은 버킷을 미리 정하지 않고 자동으로 나누므로 시계열 수를 근본적으로 줄인다.

다만 기존 대시보드와 histogram_quantile 사용법이 달라지고 스프링·그라파나 양쪽 지원 상태를 확인해야 한다. 지금 바꾸기보다 다음 분기 과제로 올려 두는 것을 권한다.

06간격·보존·디스크 계산

디스크 필요량은 곱셈 세 개로 어림한다.

필요 디스크 ≈ 보존 기간(초) × 초당 샘플 수 × 샘플당 바이트(1~2B)

예) 15일 보존, 초당 4,000샘플, 샘플당 2B
    = 1,296,000 × 4,000 × 2
    ≈ 10.4 GB   (여기에 여유 30~50%를 더한다)

초당 샘플 수는 04절에서 이미 쟀다 — 3,988. 위 계산에 그 값을 넣으면 된다.

조절 손잡이효과주의
scrapeInterval 30s → 60s샘플 수 절반rate() 윈도도 함께 늘려야 한다(간격의 4배 이상). 짧은 스파이크를 놓친다
retention 단축디스크 선형 감소주간 비교·용량 추세 분석이 불가능해진다
metricRelabelings 드롭디스크·메모리 모두 감소되돌릴 수 없다
retentionSize 지정디스크 상한 보장기간보다 먼저 걸리면 오래된 데이터가 조용히 사라진다
04장 설정에 함정이 하나 있다

값 파일에 retention: 3d 와 retentionSize: 4GB 를 함께 넣었다. 둘 중 먼저 도달하는 쪽이 이긴다. 실습에서 부하를 크게 걸면 3일이 되기 전에 4GB 에 걸려 “어제 그래프가 사라졌다”는 상황이 생긴다 — 버그가 아니라 설정대로 동작한 것이다.

규모가 더 커지면 손잡이를 돌리는 것으로는 부족하다. 그때는 원격 쓰기로 장기 저장을 분리하는 구조로 넘어간다. Prometheus 3.x 의 Remote-Write 2.0 이 그 통로다. 이 실습 범위를 벗어나므로 이름만 기억해 둔다.

07자원 튜닝과 무중단 리사이즈

  kube_pod_container_resource_limits{namespace="apps", resource="memory"}
)

0.9 를 넘나든다면 OOMKilled 가 임박한 것이다. CPU 는 모자라면 느려지지만, 메모리는 모자라면 죽는다. 그래서 CPU 제한은 신중하게, 메모리 제한은 반드시 건다.

재시작 없이 자원 바꾸기

예전에는 자원을 바꾸려면 파드를 다시 만들어야 했다. In-Place Pod Resize 가 1.35 에서 정식이 되면서 달라졌다. 01장에서 만든 클러스터는 1.36 이므로 바로 써 볼 수 있다.

POD=$(kubectl -n apps get pod -l app.kubernetes.io/name=order-api \
  -o jsonpath='{.items[0].metadata.name}')

# 바꾸기 전 상태
kubectl -n apps get pod "$POD" \
  -o jsonpath='{.spec.containers[0].resources}{"\n"}{.status.containerStatuses[0].restartCount}{"\n"}'

# resize 서브리소스로 메모리 상한을 올린다 (kubectl v1.32+ 필요)
kubectl -n apps patch pod "$POD" --subresource resize --type=merge \
  -p '{"spec":{"containers":[{"name":"order-api","resources":{"requests":{"memory":"448Mi"},"limits":{"memory":"768Mi"}}}]}}'

# 재시작 없이 반영됐는지 — restartCount 가 그대로여야 한다
kubectl -n apps get pod "$POD" \
  -o jsonpath='{.status.containerStatuses[0].resources}{"\n"}{.status.containerStatuses[0].restartCount}{"\n"}'
읽어야 할 곳이 두 군데가 됐다

spec.containers[*].resources 는 이제 원하는 상태이고, status.containerStatuses[*].resources 가 실제 적용된 값이다. 둘이 다를 수 있다는 것이 이 기능의 핵심이다 — 예전처럼 spec 만 보면 안 된다.

restartCount 가 그대로면 무중단으로 바뀐 것이다. 메모리를 줄이는 방향은 제약이 있다 — 이미 쓰고 있는 양보다 작게는 못 줄인다.

08실습 설정 → 운영 설정

이 시리즈에서 일부러 타협한 설정들이다. 실습을 빨리 굴리기 위한 선택이었고, 사내 클러스터로 옮길 때는 반드시 바꿔야 한다.

장실습에서의 선택운영에서 바꿀 것
01bind-address: 0.0.0.0 으로 컨트롤 플레인 메트릭 개방노드 IP (Internet Protocol · 네트워크에서 주소를 정하는 규약) 만 바인딩하거나 방화벽으로 대역 제한. kind 는 VM (Virtual Machine · 가상 머신) 안에 갇혀 있어 안전했을 뿐이다
02ChaosController 가 항상 활성@Profile 로 분리. 운영 프로파일에서는 빈 등록조차 되지 않게 한다
03CPU limit 미설정공용 클러스터라면 반드시 설정. 대신 스로틀링 메트릭을 함께 감시한다 (07절)
03readOnlyRootFilesystem 미적용적용하고 /tmp 에 emptyDir 을 붙인다
03레지스트리 없이 kind load사내 레지스트리 + 이미지 서명·스캔 파이프라인
04insecureSkipVerify: true노드 IP 를 SAN (Subject Alternative Name · 인증서가 보증하는 이름·주소 목록) 에 포함한 인증서를 발급해 검증을 켠다
04관측 스택을 노드 한 대에 몰아넣음분산 배치. 모니터링이 한 노드와 함께 죽으면 장애를 볼 눈이 없어진다
04그라파나 비밀번호를 값 파일에 평문으로Secret 또는 외부 시크릿 관리자. 가능하면 SSO (Single Sign-On · 한 번 로그인으로 여러 서비스를 쓰는 것) 연동
04NodePort 로 UI (User Interface · 사용자 인터페이스) 직접 노출인증을 거치는 진입점 뒤에 둔다. 프로메테우스 UI 에는 인증이 없다
04retention: 3d주간 비교가 가능한 길이로. 06절의 곱셈으로 디스크를 먼저 계산한다
05사이드카 searchNamespace: ALL필요한 네임스페이스만 나열. 권한과 API (Application Programming Interface · 프로그램끼리 주고받는 규약) 부하를 줄인다
07임계값 5% · 500ms 를 임의로 설정2주 이상 관측한 실제 분포를 근거로 재설정
08로키 파일시스템 단일 인스턴스오브젝트 스토리지 + 확장 모드. 파일시스템 단일 인스턴스는 데이터를 잃는 구성이다
08캐시 비활성운영 규모에서는 필수. 없으면 질의가 감당되지 않는다
가장 위험한 것은 값 파일이다

매니페스트는 리뷰를 거치지만 values.yaml 은 “잘 되는 설정”이라며 통째로 복사되는 일이 잦다. 파일 이름에 환경을 박아 둔다 — kps-values.kind.yaml 처럼. 이름만으로도 복사를 한 번 망설이게 만든다.

09트러블슈팅 12선

이 시리즈 전체에서 실제로 부딪히는 순서대로 정리했다.

#증상첫 번째로 볼 곳
1클러스터 생성이 타임아웃Docker Desktop 메모리 할당. 10 GiB (Gibibyte · 2의 30제곱 바이트. 쿠버네티스가 쓰는 단위) 미만이면 04장에서 반드시 막힌다
2컨트롤 플레인 타깃 DOWN01장 bind-address 패치. 클러스터 재생성이 필요하다
3ImagePullBackOffkind load 여부와 imagePullPolicy: IfNotPresent
4CrashLoopBackOff 인데 로그는 정상startupProbe 의 failureThreshold × periodSeconds
5ServiceMonitor 가 무시됨release: kps 라벨. 오류 없이 조용히 실패한다
6타깃 그룹은 있는데 대상 0개Service 라벨과 포트 이름
7_bucket 이 없어 P95 계산 불가02장 percentiles-histogram. 이미지 재빌드 필요
8histogram_quantile 이 NaNsum by 에 le 가 빠졌는지
9대시보드가 No data같은 질의를 프로메테우스 UI 에서 실행해 데이터 유무부터 분리
10알림이 안 울림/alerts 에서 pending 여부 → Alertmanager 라우팅 순으로
11로그가 안 보임라벨 이름부터(08장 09절). 그다음 Alloy UI(12345)
12어제 그래프가 사라짐retentionSize 에 먼저 걸렸는지. 설정대로 동작한 것이다
공통 원칙 — 범위를 절반으로 자른다

“안 된다”는 상황에서 가장 먼저 할 일은 범위를 절반으로 자르는 것이다. 대시보드가 비면 프로메테우스 UI 에서 같은 질의를 돌려 보고, 거기서도 비면 타깃 상태를 보고, 타깃이 UP 이면 앱 엔드포인트를 직접 curl 한다. 한 번에 한 계층씩 내려가면 대부분 세 번 안에 원인에 닿는다.

10대시보드와 알림이 늘어날 때

스택이 안정되면 다음 문제는 기술이 아니라 관리다. 대시보드는 만드는 사람은 있지만 지우는 사람이 없어서 늘어난다.

신호대응
비슷한 대시보드가 세 개 이상변수로 합친다. 07장에서 만든 service 변수가 그 방법이다
아무도 열지 않는 대시보드그라파나 사용 통계로 확인해 정리한다. Archive 폴더를 두는 것도 방법
같은 장애에 알림이 열 개증상 알림만 남기고 원인 알림은 지운다. inhibit_rules 도 함께 손본다
Silence 가 만료 없이 쌓임영구 침묵은 규칙 삭제와 같다. 만료 기간을 반드시 설정한다
한 번도 울리지 않은 알림임계값이 현실과 맞는지, 아니면 애초에 필요 없는 알림인지 판단한다

07장에서 정한 기준을 여기서도 쓴다 — 사람이 지금 무언가를 해야 하는가. 조치율이 낮은 알림부터 지운다.

#!/usr/bin/env bash
# 관측성 실습 환경 재구축 — 각 단계 문서를 대체하지 않는다. 복원용이다.
set -euo pipefail

ROOT="$HOME/k8s-observability"
CHART_VERSION="88.3.0"

echo "[1/6] 클러스터 생성"
kind create cluster --config "$ROOT/infra/kind-cluster.yaml"

echo "[2/6] 앱 이미지 빌드와 적재"
for app in order-api gateway; do
  (cd "$ROOT/apps/$app" && ./gradlew bootBuildImage)
  kind load docker-image "obs/${app}:0.0.1" --name obs
done

echo "[3/6] 앱 배포"
kubectl apply -f "$ROOT/k8s/00-namespace.yaml"
kubectl apply -f "$ROOT/k8s/10-order-api.yaml"

echo "[4/6] 관측 스택 설치"
helm upgrade --install kps prometheus-community/kube-prometheus-stack \
  --namespace monitoring --create-namespace \
  --version "$CHART_VERSION" \
  -f "$ROOT/monitoring/kps-values.yaml" \
  --wait --timeout 15m

echo "[5/6] 연동 리소스"
kubectl apply -f "$ROOT/k8s/monitoring/90-servicemonitors.yaml"
kubectl apply -f "$ROOT/k8s/monitoring/91-prometheusrule.yaml"

echo "[6/6] 대시보드"
kubectl -n monitoring create configmap obs-red-dashboard \
  --from-file=obs-red.json="$ROOT/monitoring/dashboards/obs-red.json" \
  --dry-run=client -o yaml | kubectl apply -f -
kubectl -n monitoring label configmap obs-red-dashboard grafana_dashboard=1 --overwrite

echo "완료 — http://localhost:30300 (grafana) · http://localhost:30900 (prometheus)"
