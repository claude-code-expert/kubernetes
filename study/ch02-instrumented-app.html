01이론 — 무엇을 측정할 것인가

책 3.3 — 측정 대상을 고르는 두 가지 방법론과, 평균이 감추는 것.

쿠버네티스가 기존 모니터링과 갈리는 지점부터 짚는다. 24시간 가동되는 VM은 상태 보존을 확인하면 되지만 파드는 수명이 짧다. 개별 인스턴스를 추적하는 방식은 성립하지 않고, 레이블로 묶은 집합을 봐야 한다.

방법론세 지표보는 대상
USE브렌던 그레그사용률(Utilization) · 포화도(Saturation) · 에러 수(Errors)인프라. 노드 네트워크의 병목을 이 셋으로 좁힌다
RED톰 윌키처리율(Rate) · 에러 수(Errors) · 처리 시간(Duration)애플리케이션. 얼마나 처리하고, 유저가 500을 얼마나 받고, 얼마나 걸리나

두 방법론은 상보적이다 — USE는 인프라, RED는 애플리케이션. 04장에서 설치할 스택의 내장 대시보드가 USE를 채우고, 이 장에서 심는 계측이 RED를 채운다. RED의 기반 사상이 구글의 4대 골든 시그널(지연·트래픽·에러·포화도)이다.

평균 40ms 뒤에 숨은 3초

요청 100건 중 99건이 10ms, 1건이 3초라면 평균은 40ms다. 대시보드는 초록색이고, 그 1건을 겪은 사용자는 이탈한다. P99를 보면 3초가 그대로 드러난다.

분위수는 공짜가 아니다

분위수를 계산하려면 히스토그램 버킷(_bucket 시계열)이 필요한데 기본으로 생성되지 않는다. percentiles-histogram을 켜야 만들어지고, 켜는 순간 시계열 수가 버킷 개수만큼 늘어난다. 알고 켜는 것과 모르고 켜는 것의 차이가 09장에서 카디널리티 문제로 돌아온다.

요청 하나가 만드는 것

이 장에서 만드는 앱은 요청 하나에 세 종류의 시계열을 남긴다. 프레임워크가 자동으로 만드는 HTTP 지표, 액추에이터가 노출하는 JVM·시스템 지표, 그리고 직접 심는 도메인 지표다. 세 번째가 이 실습의 핵심이고 orders.created·orders.rejected·orders.processing·orders.stored 네 개다.

이름을 바꾸지 않는다

06장의 PromQL과 07장의 대시보드 JSON이 이 네 이름에 의존한다. 마이크로미터가 .을 _로 바꿔 orders_created_total 형태로 노출한다는 점도 함께 기억한다.

02무엇을, 왜 두 개로 만드나

서비스 하나로도 메트릭 실습은 됩니다. 그럼에도 둘로 나누는 이유는 하나뿐입니다 — 지연이 전파되는 모습을 봐야 RED 지표가 왜 서비스별로 필요한지 체감할 수 있기 때문입니다. 주문 API가 500ms 느려질 때 게이트웨이의 P99가 어떻게 따라 움직이는지, 07장에서 두 그래프를 나란히 놓고 보게 됩니다.

서비스스택역할
gateway Spring Cloud Gateway Server WebFlux 외부 진입점. 라우팅과 게이트웨이 자체 메트릭 노출
order-api Spring MVC + Actuator 주문 생성·조회. 커스텀 비즈니스 메트릭과 지연·에러 시뮬레이션 담당
데이터베이스를 넣지 않는 이유

사내 프로젝트 컨벤션은 JPA와 Flyway를 쓰지만, 여기서는 주문을 ConcurrentHashMap에 보관합니다. DB를 붙이면 파드가 하나 더 늘고 커넥션 풀 문제로 디버깅 시간이 새는데, 정작 이 시리즈에서 배울 것은 커넥션 풀 메트릭이 아니라 계측 방법이기 때문입니다. HikariCP 메트릭(hikaricp_connections_active 등)은 액추에이터가 자동으로 잡아주므로, 사내 프로젝트에 옮길 때 코드 수정 없이 대시보드만 추가하면 됩니다.

03요청 하나가 만드는 메트릭

코드를 쓰기 전에 이것부터 이해해야 합니다. HTTP 요청 한 건이 들어오면 마이크로미터는 타이머 하나를 갱신하는데, 프로메테우스 포맷으로 나올 때는 시계열 세 종류로 쪼개집니다. 06장의 PromQL이 어렵게 느껴지는 이유의 8할이 이 구조를 모르기 때문입니다.

평균 대신 분위수를 보는 이유

요청 100건 중 99건이 10ms, 1건이 3초라면 평균은 40ms입니다. 대시보드는 초록색이고, 그 1건을 겪은 사용자는 이탈합니다. P99를 보면 3초가 그대로 드러납니다. 07장에서 만들 패널이 전부 분위수 기반인 이유입니다.

예외 처리가 메트릭에 미치는 영향

@RestControllerAdvice로 예외를 잡아 400을 반환하면 http.server.requests의 exception 태그는 none, status는 400, outcome은 CLIENT_ERROR가 됩니다. 예외를 잡지 않고 흘려보내면 exception="InvalidOrderException" 태그가 붙습니다. 06장에서 "에러율을 status로 셀 것인가 exception으로 셀 것인가"를 결정할 때 이 차이가 근거가 됩니다.

서비스 — 커스텀 메트릭이 들어가는 곳

service/OrderService.java

package com.study.obs.order.service;

import com.study.obs.order.domain.Order;
import com.study.obs.order.dto.OrderCreateRequest;
import com.study.obs.order.dto.OrderResponse;
import com.study.obs.order.exception.InvalidOrderException;
import io.micrometer.core.instrument.Counter;
import io.micrometer.core.instrument.Gauge;
import io.micrometer.core.instrument.MeterRegistry;
import io.micrometer.core.instrument.Timer;
import java.util.List;
import java.util.Map;
import java.util.Optional;
import java.util.Random;
import java.util.concurrent.ConcurrentHashMap;
import org.springframework.stereotype.Service;

@Service
public class OrderService {

    private static final int MAX_QUANTITY = 100;

    private final Map<String, Order> store = new ConcurrentHashMap<>();
    private final Random random = new Random();

    private final Counter createdCounter;
    private final Counter rejectedCounter;
    private final Timer processingTimer;

    public OrderService(MeterRegistry registry) {
        this.createdCounter = Counter.builder("orders.created")
                .description("생성에 성공한 주문 수")
                .tag("channel", "api")
                .register(registry);

        this.rejectedCounter = Counter.builder("orders.rejected")
                .description("검증에 걸려 거부된 주문 수")
                .tag("reason", "quantity_exceeded")
                .register(registry);

        this.processingTimer = Timer.builder("orders.processing")
                .description("주문 처리에 걸린 시간")
                .publishPercentileHistogram()
                .register(registry);

        Gauge.builder("orders.stored", store, Map::size)
                .description("메모리에 보관 중인 주문 수")
                .register(registry);
    }

    public OrderResponse create(OrderCreateRequest request) {
        return processingTimer.record(() -> {
            simulateWork();
            if (request.quantity() > MAX_QUANTITY) {
                rejectedCounter.increment();
                throw new InvalidOrderException(request.quantity());
            }
            Order order = Order.create(request.item(), request.quantity());
            store.put(order.id(), order);
            createdCounter.increment();
            return OrderResponse.from(order);
        });
    }

    public Optional<OrderResponse> findById(String id) {
        return Optional.ofNullable(store.get(id)).map(OrderResponse::from);
    }

    public List<OrderResponse> findAll() {
        return store.values().stream().map(OrderResponse::from).toList();
    }

    private void simulateWork() {
        try {
            Thread.sleep(random.nextLong(20, 120));
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
    }
}

계측 코드에서 눈여겨볼 네 가지

  • 메트릭 이름은 점 표기법으로 씁니다(orders.created). 프로메테우스 포맷으로 나갈 때 orders_created_total로 자동 변환됩니다. 마이크로미터의 이식성 규칙이라, 처음부터 언더스코어로 쓰면 오히려 어색해집니다.
  • 태그 값은 유한한 집합이어야 합니다. channel="api"는 안전하고, 주문 ID나 상품명을 태그로 넣으면 시계열이 폭발합니다.
  • publishPercentileHistogram()은 이 타이머에만 버킷을 만듭니다. 전역 설정 대신 필요한 곳에만 켜는 방식입니다.
  • 게이지는 참조를 등록합니다. 값을 넣는 게 아니라 "이 맵의 size를 물어봐라"라고 등록해 두면 스크레이프 시점마다 호출됩니다.
@Timed 애너테이션을 쓰고 싶다면

Spring Boot 4에서 @Timed·@Counted·@Observed 같은 애너테이션을 쓰려면 management.observations.annotations.enabled=true 설정과 org.aspectj:aspectjweaver(spring-boot-starter-aspectj에 포함) 의존성이 필요합니다. Boot 3 시절 문서가 안내하는 spring-boot-starter-aop만으로는 부족합니다. 실습에서는 의존성을 늘리지 않기 위해 MeterRegistry를 직접 주입하는 방식을 씁니다.

컨트롤러

controller/OrderController.java

package com.study.obs.order.controller;

import com.study.obs.order.common.ApiResponse;
import com.study.obs.order.dto.OrderCreateRequest;
import com.study.obs.order.dto.OrderResponse;
import com.study.obs.order.service.OrderService;
import jakarta.validation.Valid;
import java.util.List;
import org.springframework.http.HttpStatus;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RequestBody;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
@RequestMapping("/api/orders")
public class OrderController {

    private final OrderService orderService;

    public OrderController(OrderService orderService) {
        this.orderService = orderService;
    }

    @PostMapping
    public ResponseEntity<ApiResponse<OrderResponse>> create(
            @Valid @RequestBody OrderCreateRequest request) {
        OrderResponse response = orderService.create(request);
        return ResponseEntity.status(HttpStatus.CREATED)
                .body(ApiResponse.success(response, "주문이 생성되었습니다."));
    }

    @GetMapping("/{id}")
    public ResponseEntity<ApiResponse<OrderResponse>> findOne(@PathVariable String id) {
        return orderService.findById(id)
                .map(response -> ResponseEntity.ok(ApiResponse.success(response, "조회 성공")))
                .orElseGet(() -> ResponseEntity.notFound().build());
    }

    @GetMapping
    public ResponseEntity<ApiResponse<List<OrderResponse>>> findAll() {
        List<OrderResponse> responses = orderService.findAll();
        return ResponseEntity.ok(ApiResponse.success(responses, "조회 성공"));
    }
}

@GetMapping("/{id}") 로 매핑했기 때문에 메트릭의 uri 태그는 실제 UUID가 아니라 /api/orders/{id} 라는 템플릿으로 기록됩니다. 스프링이 알아서 해주는 부분이지만, 직접 문자열을 파싱해 라우팅하면 이 보호가 사라집니다.

controller/ChaosController.java

package com.study.obs.order.controller;

import java.util.Map;
import java.util.Random;
import org.springframework.http.HttpStatus;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RequestParam;
import org.springframework.web.bind.annotation.RestController;

/**
 * 대시보드와 알림 실습용 지연·에러 생성기.
 * 06~07장에서 이 엔드포인트로 그래프를 움직인다.
 */
@RestController
@RequestMapping("/api/chaos")
public class ChaosController {

    private static final long MAX_SLEEP_MS = 5_000L;

    private final Random random = new Random();

    @GetMapping("/slow")
    public Map<String, Object> slow(@RequestParam(defaultValue = "500") long ms)
            throws InterruptedException {
        long sleepMs = Math.min(ms, MAX_SLEEP_MS);
        Thread.sleep(sleepMs);
        return Map.of("sleptMs", sleepMs);
    }

    @GetMapping("/error")
    public ResponseEntity<Map<String, Object>> error(
            @RequestParam(defaultValue = "0.5") double rate) {
        if (random.nextDouble() < rate) {
            return ResponseEntity.status(HttpStatus.INTERNAL_SERVER_ERROR)
                    .body(Map.of("failed", true));
        }
        return ResponseEntity.ok(Map.of("failed", false));
    }
}
이 컨트롤러는 실습 전용이다

의도적으로 스레드를 잡아두고 500을 뱉는 코드입니다. 사내 프로젝트에 복사할 일이 있다면 프로파일로 분리하세요(@Profile("chaos")). 지금은 실습 편의를 위해 항상 켭니다.

apps/order-api/src/main/resources/application.yml

spring:
  application:
    name: order-api

server:
  port: 8080
  shutdown: graceful

management:
  endpoints:
    web:
      exposure:
        # 필요한 것만 연다. '*' 로 열면 env·heapdump 같은 민감 엔드포인트까지 노출된다.
        include: health,info,prometheus
  endpoint:
    health:
      # /actuator/health/liveness 와 /readiness 가 생긴다. 03장 프로브에서 쓴다.
      probes:
        enabled: true
      show-details: never
  metrics:
    distribution:
      # 이 설정이 있어야 _bucket 시계열이 생기고 P95·P99를 계산할 수 있다.
      percentiles-histogram:
        http.server.requests: true
      # SLO 경계를 명시하면 해당 지점에 버킷이 추가된다.
      slo:
        http.server.requests: 50ms,100ms,200ms,500ms,1s

일부러 넣지 않은 설정

많은 예제가 management.metrics.tags.application: ${spring.application.name} 같은 공통 태그를 넣습니다. 이 시리즈에서는 넣지 않습니다. 이유는 둘입니다.

  • 해당 프로퍼티는 Spring Boot 3.2에서 management.observations.key-values로 대체 예고됐고, 대체 프로퍼티는 옵저베이션 기반 메트릭에만 적용되는 등 동작 범위가 다릅니다. 버전을 넘나들며 헷갈릴 여지가 큽니다.
  • 쿠버네티스에서는 06장의 ServiceMonitor가 스크레이프 시점에 job·namespace·pod·service 라벨을 자동으로 붙입니다. 앱에서 또 붙이면 의미가 겹치는 라벨이 두 벌 생깁니다.
Boot 4의 기본값 변화

Spring Boot 4는 액추에이터 엔드포인트 접근을 기본적으로 읽기 전용으로 제한합니다 (management.endpoints.access.default=read-only). 로그 레벨을 런타임에 바꾸는 등 쓰기 동작이 필요하면 해당 엔드포인트만 access: unrestricted로 열어야 합니다. 실습에서는 읽기 전용으로 충분합니다.

07gateway 구현과 설정

게이트웨이는 자바 코드가 거의 없습니다. 생성된 메인 클래스를 그대로 두고 설정만 씁니다.

apps/gateway/src/main/resources/application.yml

spring:
  application:
    name: gateway
  cloud:
    gateway:
      server:
        webflux:
          # 프로퍼티 접두사가 spring.cloud.gateway.routes 에서 여기로 바뀌었다.
          # 옛 접두사로 쓰면 라우트가 등록되지 않고 404만 돌아온다.
          routes:
            - id: order-api
              uri: ${ORDER_API_URI:http://localhost:8081}
              predicates:
                - Path=/api/orders/**,/api/chaos/**
              filters:
                - AddRequestHeader=X-Gateway,obs-study

server:
  port: 8080
  shutdown: graceful

management:
  endpoints:
    web:
      exposure:
        # gateway 엔드포인트는 절대 열지 않는다. 아래 경고 참조.
        include: health,info,prometheus
  endpoint:
    health:
      probes:
        enabled: true
  metrics:
    distribution:
      percentiles-histogram:
        http.server.requests: true
        spring.cloud.gateway.requests: true
액추에이터 gateway 엔드포인트를 열지 않는 이유

management.endpoints.web.exposure.include에 gateway를 넣고 인증을 걸지 않으면, 런타임에 라우트를 조작하거나 환경 프로퍼티를 읽어내는 취약점 (CVE-2025-41243, CVE-2025-41253)의 성립 조건에 그대로 들어맞습니다. "로컬 실습이니까"라는 이유로 열어두면 그 설정이 사내로 복사됩니다.

X-Forwarded 헤더

2025.0부터 X-Forwarded-*와 Forwarded 헤더 처리는 기본 비활성입니다. 게이트웨이 뒤에서 클라이언트 IP를 봐야 한다면 spring.cloud.gateway.server.webflux.trusted-proxies에 신뢰할 프록시 대역을 정규식으로 지정해야 합니다. 이 실습에서는 필요 없습니다.

게이트웨이가 추가로 내보내는 메트릭

액추에이터가 클래스패스에 있으면 게이트웨이 메트릭은 별도 설정 없이 수집됩니다. 프로메테우스 포맷에서 이름은 spring_cloud_gateway_requests_seconds_*이고, routeId·routeUri·outcome·status 태그가 붙습니다. "어느 백엔드로 나가는 트래픽이 느린가"를 라우트 단위로 볼 수 있다는 뜻입니다.

09뒤 단계에서 쓸 메트릭 지도

지금 만든 것들이 어디서 쓰이는지 미리 짚어둡니다.

메트릭(프로메테우스 이름)타입쓰이는 곳
http_server_requests_seconds_count카운터06 — 처리율 R, 에러율 E
http_server_requests_seconds_bucket히스토그램06·07 — P95·P99 지연 D
spring_cloud_gateway_requests_seconds_*타이머07 — 라우트별 지연 비교

orders_rejected_total카운터07 — 거부율 알림 규칙

jvm_·process_·system_으로 시작하는 메트릭은 코드를 한 줄도 쓰지 않아도 나옵니다. 액추에이터가 등록하는 MeterBinder들이 JVM과 OS 지표를 자동으로 붙이기 때문입니다.
