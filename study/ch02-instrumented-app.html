쿠버네티스 관측성

계측 가능한 애플리케이션

관측할 대상을 먼저 만든다. 스프링 앱 두 개를 띄우고, 프레임워크가 주는 지표 위에 도메인 지표 네 개를 직접 심는다.

01왜 이 장이 필요한가

01장에서 클러스터가 섰다. 하지만 관측할 것이 없다. 프로메테우스를 먼저 설치해도 긁어 갈 대상이 없으면 빈 화면이다.

그래서 순서를 뒤집는다. 관측 도구보다 관측당할 애플리케이션을 먼저 만든다. 이 순서가 중요한 이유는, 04장에서 프로메테우스를 붙였을 때 “안 보인다”가 세 가지 중 어느 것인지 구분할 수 있어야 하기 때문이다 — 앱이 메트릭을 안 내놓는가, 프로메테우스가 못 찾는가, 질의가 틀렸는가. 앱 쪽을 먼저 확인해 두면 원인 하나가 지워진다.

또 하나. 프레임워크가 자동으로 주는 지표만으로는 “장애인가 아닌가”를 판정할 수 없다. HTTP 200 이 잘 나오는데 주문이 한 건도 생성되지 않는 상황을 HTTP 지표는 잡아내지 못한다. 이 장에서 도메인 지표 네 개를 직접 심는 이유가 그것이다.

02알아야 할 개념

무엇을 측정할 것인가 — USE 와 RED

책 3.3 — 측정 대상을 고르는 두 가지 방법론

쿠버네티스가 기존 모니터링과 갈리는 지점부터 짚는다. 24시간 가동되는 VM 은 상태 보존을 확인하면 되지만 파드는 수명이 짧다. 개별 인스턴스를 추적하는 방식은 성립하지 않고, 라벨로 묶은 집합을 봐야 한다.

방법론세 지표보는 대상
USE
(브렌던 그레그)		사용률 Utilization · 포화도 Saturation · 에러 수 Errors인프라. 노드와 네트워크의 병목을 이 셋으로 좁힌다
RED
(톰 윌키)		처리율 Rate · 에러 수 Errors · 처리 시간 Duration애플리케이션. 얼마나 처리하고, 사용자가 500 을 얼마나 받고, 얼마나 걸리나

두 방법론은 상보적이다. 04장에서 설치할 스택의 내장 대시보드가 USE 를 채우고, 이 장에서 심는 계측이 RED 를 채운다. RED 의 기반 사상이 구글의 4대 골든 시그널(지연 · 트래픽 · 에러 · 포화도)이다.

마이크로미터의 계측 타입 세 가지

마이크로미터(Micrometer)는 계측 API 다. 코드는 마이크로미터에만 의존하고, 어느 모니터링 시스템으로 내보낼지는 클래스패스에 어떤 레지스트리가 있는지가 정한다. SLF4J 가 로깅에서 하는 역할을 메트릭에서 한다고 보면 된다.

타입영문무엇을 재나이 장에서 쓰는 예
카운터Counter줄어들지 않고 늘기만 하는 누적값orders.created · orders.rejected
게이지Gauge지금 이 순간의 값. 오르내린다orders.stored — 보관 중인 주문 수
타이머Timer발생 횟수와 소요 시간을 함께orders.processing — 처리 시간

카운터는 값 자체가 아니라 증가 속도를 본다. 누적 42 라는 숫자는 의미가 없고 rate() 로 초당 몇 건인지를 본다. 파드가 재시작하면 0으로 돌아가는데, PromQL 의 rate() 가 그 리셋을 알아서 처리한다.

타이머 하나가 시계열 세 종류가 된다

코드를 쓰기 전에 이것부터 이해해야 한다. HTTP 요청 한 건이 들어오면 마이크로미터는 타이머 하나를 갱신하는데, 프로메테우스 포맷으로 나올 때는 시계열 세 종류로 쪼개진다. 06장의 PromQL 이 어렵게 느껴지는 이유의 대부분이 이 구조를 모르기 때문이다. 03절 그림 2 에서 자세히 본다.

평균 40ms 뒤에 숨은 3초

요청 100건 중 99건이 10ms, 1건이 3초라면 평균은 40ms 다. 대시보드는 초록색이고, 그 1건을 겪은 사용자는 이탈한다. P99 를 보면 3초가 그대로 드러난다. 07장에서 만들 패널이 전부 분위수 기반인 이유다.

분위수는 공짜가 아니다

분위수를 계산하려면 히스토그램 버킷(_bucket 시계열)이 필요한데 기본으로 생성되지 않는다. percentiles-histogram 을 켜야 만들어지고, 켜는 순간 시계열 수가 버킷 개수만큼 늘어난다. 알고 켜는 것과 모르고 켜는 것의 차이가 09장에서 카디널리티 문제로 돌아온다.

이 장을 마치면 할 수 있는 것

  1. 요청 한 건이 _count · _sum · _bucket 세 시계열로 갈라지는 과정을 설명하고, 실제 출력에서 셋을 찾을 수 있다.
  2. 카운터 · 게이지 · 타이머를 구분해 쓰고, MeterRegistry 를 주입받아 도메인 지표를 직접 심을 수 있다.
  3. percentiles-histogram 이 켜졌는지를 _bucket 개수로 판정할 수 있다.
  4. 액추에이터에서 열어야 할 것과 절대 열면 안 되는 것을 구분하고, 닫혀 있음을 404 로 확인할 수 있다.
  5. 스프링 클라우드 아티팩트 이름과 릴리스 트레인이 어긋났을 때의 에러를 읽고 고칠 수 있다.

03최종적으로 만들 것

서비스 두 개를 만든다. 하나로도 메트릭 실습은 되지만, 둘로 나누는 이유는 하나다 — 지연이 전파되는 모습을 봐야 RED 지표가 왜 서비스별로 필요한지 체감할 수 있다. 주문 API 가 500ms 느려질 때 게이트웨이의 P99 가 어떻게 따라 움직이는지, 07장에서 두 그래프를 나란히 놓고 본다.

두 서비스와 메트릭이 나가는 지점

  • 1 게이트웨이가 뜬다. 라우트가 등록됐는지는 요청을 넘겨 보면 안다. 확인 curl -s -o /dev/null -w '%{http_code}\n' -X POST localhost:8080/api/orders -H 'Content-Type: application/json' -d '{"item":"a","quantity":1}' → 201
  • 2 주문 API 가 도메인 지표를 내놓는다. 프로메테우스가 없어도 직접 볼 수 있다. 확인 curl -s localhost:8081/actuator/prometheus | grep '^orders_' → orders_created_total 을 포함한 여러 줄
  • 3 프로메테우스는 아직 없다. 04장에서 붙인다. 지금 확인할 것은 “긁어 갈 것이 준비됐는가”까지다. 확인 curl -s -o /dev/null -w '%{http_code}\n' localhost:8081/actuator/prometheus → 200

WHY이 구조를 만드는 설정 — 의존성 한 줄과 라우트 한 벌

그림에서 /actuator/prometheus 가 열려 있는 것은 코드 때문이 아니라 의존성과 설정 때문이다. 두 파일만 보면 된다.

study/labs/apps/order-api/build.gradle — 엔드포인트를 만드는 두 줄 
implementation 'org.springframework.boot:spring-boot-starter-actuator'

// 이 한 줄이 /actuator/prometheus 를 만든다.
// 액추에이터는 클래스패스에서 발견한 레지스트리를 자동 구성한다.
runtimeOnly 'io.micrometer:micrometer-registry-prometheus'
study/labs/apps/order-api/src/main/resources/application.yml — 열 것만 고른다 
management:
  endpoints:
    web:
      exposure:
        include: health,info,prometheus   # '*' 로 열면 env·heapdump 까지 나간다
study/labs/apps/gateway/src/main/resources/application.yml — 화살표를 만드는 라우트 
spring:
  cloud:
    gateway:
      server:
        webflux:                  # 이 두 단계가 빠지면 라우트가 등록되지 않는다
          routes:
            - id: order-api       # 이 값이 메트릭의 routeId 태그가 된다
              uri: ${ORDER_API_URI:http://localhost:8081}
              predicates:
                - Path=/api/orders/**,/api/chaos/**
그림의 요소그것을 만드는 설정빠졌을 때
클라이언트 → gateway 화살표predicates: Path=...게이트웨이가 404 만 반환한다
gateway → order-api 화살표uri: ${ORDER_API_URI:...}502. 뒤쪽 주소가 틀린 것이다
두 상자의 /actuator/prometheusmicrometer-registry-prometheus + exposure.include둘 중 하나만 있어도 404 다
게이트웨이에만 있는 gateway.requests게이트웨이 스타터가 자동 등록—

요청 하나가 만드는 메트릭

  • 1 _count 가 있는지. 이것이 없으면 앱이 요청을 세지 않는 것이다. 확인 curl -s localhost:8081/actuator/prometheus | grep -c 'http_server_requests_seconds_count' → 1 이상
  • 2 _sum 과 나누면 평균이 나온다. 평균만 보면 안 되는 이유는 위에 적었다. 확인 curl -s localhost:8081/actuator/prometheus | grep 'http_server_requests_seconds_sum' → 초 단위 숫자
  • 3 _bucket 이 있는지가 이 장의 판정 지점이다. 0 이면 07장의 P95 패널이 No data 로 남는다. 확인 curl -s localhost:8081/actuator/prometheus | grep -c 'http_server_requests_seconds_bucket' → 0 이 아니어야 한다

WHY세 번째 상자를 만드는 설정 — percentiles-histogram

study/labs/apps/order-api/src/main/resources/application.yml — 버킷을 켜는 곳 
management:
  metrics:
    distribution:
      # 이 설정이 있어야 _bucket 시계열이 생기고 P95·P99 를 계산할 수 있다.
      percentiles-histogram:
        http.server.requests: true
      # SLO 경계를 명시하면 그 지점에 버킷이 추가된다.
      slo:
        http.server.requests: 50ms,100ms,200ms,500ms,1s
그림의 상자필요한 설정없으면
_count · _sum없다. 액추에이터가 기본으로 만든다—
_bucket{le="..."}percentiles-histogram: truehistogram_quantile() 이 쓸 재료가 없다. 07장 P95 패널이 빈다
le="0.2" 같은 특정 경계slo: 목록기본 버킷 경계만 생긴다. SLO 지점을 정확히 못 읽는다
메트릭 이름은 점 표기로 쓴다

설정에도 코드에도 http.server.requests 처럼 점으로 쓴다. 프로메테우스 포맷으로 나갈 때 http_server_requests_seconds_count 로 자동 변환된다. 마이크로미터의 이식성 규칙이다 — 같은 코드가 프로메테우스로도, 다른 백엔드로도 나갈 수 있게 하려는 것이다. 반대로 06장에서 PromQL 을 쓸 때는 변환된 이름을 쓴다.

서비스 — 커스텀 메트릭이 들어가는 곳

service/OrderService.java 
package com.study.obs.order.service;

import com.study.obs.order.domain.Order;
import com.study.obs.order.dto.OrderCreateRequest;
import com.study.obs.order.dto.OrderResponse;
import com.study.obs.order.exception.InvalidOrderException;
import io.micrometer.core.instrument.Counter;
import io.micrometer.core.instrument.Gauge;
import io.micrometer.core.instrument.MeterRegistry;
import io.micrometer.core.instrument.Timer;
import java.util.List;
import java.util.Map;
import java.util.Optional;
import java.util.Random;
import java.util.concurrent.ConcurrentHashMap;
import org.springframework.stereotype.Service;

@Service
public class OrderService {

    private static final int MAX_QUANTITY = 100;

    private final Map<String, Order> store = new ConcurrentHashMap<>();
    private final Random random = new Random();

    private final Counter createdCounter;
    private final Counter rejectedCounter;
    private final Timer processingTimer;

    public OrderService(MeterRegistry registry) {
        this.createdCounter = Counter.builder("orders.created")
                .description("생성에 성공한 주문 수")
                .tag("channel", "api")
                .register(registry);

        this.rejectedCounter = Counter.builder("orders.rejected")
                .description("검증에 걸려 거부된 주문 수")
                .tag("reason", "quantity_exceeded")
                .register(registry);

        this.processingTimer = Timer.builder("orders.processing")
                .description("주문 처리에 걸린 시간")
                .publishPercentileHistogram()
                .register(registry);

        Gauge.builder("orders.stored", store, Map::size)
                .description("메모리에 보관 중인 주문 수")
                .register(registry);
    }

    public OrderResponse create(OrderCreateRequest request) {
        return processingTimer.record(() -> {
            simulateWork();
            if (request.quantity() > MAX_QUANTITY) {
                rejectedCounter.increment();
                throw new InvalidOrderException(request.quantity());
            }
            Order order = Order.create(request.item(), request.quantity());
            store.put(order.id(), order);
            createdCounter.increment();
            return OrderResponse.from(order);
        });
    }

    public Optional<OrderResponse> findById(String id) {
        return Optional.ofNullable(store.get(id)).map(OrderResponse::from);
    }

    public List<OrderResponse> findAll() {
        return store.values().stream().map(OrderResponse::from).toList();
    }

    private void simulateWork() {
        try {
            Thread.sleep(random.nextLong(20, 120));
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
    }
}

계측 코드에서 눈여겨볼 네 가지

코드왜 그렇게 쓰나
Counter.builder("orders.created")이름은 점 표기로 쓴다. 프로메테우스 포맷으로 나갈 때 orders_created_total 로 변환된다. 처음부터 언더스코어로 쓰면 다른 백엔드로 내보낼 때 어색해진다
.tag("channel", "api")태그 값은 유한한 집합이어야 한다. 주문 ID 나 상품명을 태그로 넣으면 시계열이 폭발한다 — 09장의 주제다
.publishPercentileHistogram()이 타이머에만 버킷을 만든다. 전역 설정 대신 필요한 곳에만 켜는 방식이다
Gauge.builder(..., store, Map::size)게이지는 값이 아니라 참조를 등록한다. “이 맵의 size 를 물어봐라”라고 등록해 두면 스크레이프 시점마다 호출된다
@Timed 애너테이션을 쓰고 싶다면

Spring Boot 4 에서 @Timed · @Counted · @Observed 를 쓰려면 management.observations.annotations.enabled=true 설정과 org.aspectj:aspectjweaver(spring-boot-starter-aspectj 에 포함) 의존성이 필요하다. Boot 3 시절 문서가 안내하는 spring-boot-starter-aop 만으로는 부족하다. 실습에서는 의존성을 늘리지 않으려고 MeterRegistry 를 직접 주입하는 방식을 쓴다.

controller/OrderController.java 
@RestController
@RequestMapping("/api/orders")
public class OrderController {

    private final OrderService orderService;

    public OrderController(OrderService orderService) {
        this.orderService = orderService;
    }

    @PostMapping
    public ResponseEntity<ApiResponse<OrderResponse>> create(
            @Valid @RequestBody OrderCreateRequest request) {
        OrderResponse response = orderService.create(request);
        return ResponseEntity.status(HttpStatus.CREATED)
                .body(ApiResponse.success(response, "주문이 생성되었습니다."));
    }

    @GetMapping("/{id}")
    public ResponseEntity<ApiResponse<OrderResponse>> findOne(@PathVariable String id) {
        return orderService.findById(id)
                .map(response -> ResponseEntity.ok(ApiResponse.success(response, "조회 성공")))
                .orElseGet(() -> ResponseEntity.notFound().build());
    }

    @GetMapping
    public ResponseEntity<ApiResponse<List<OrderResponse>>> findAll() {
        List<OrderResponse> responses = orderService.findAll();
        return ResponseEntity.ok(ApiResponse.success(responses, "조회 성공"));
    }
}

임포트 문은 지면을 아끼려고 생략했다. 전문은 저장소 파일에 있다.

@GetMapping("/{id}") 이 카디널리티를 지킨다

경로 변수로 매핑했기 때문에 메트릭의 uri 태그는 실제 UUID 가 아니라 /api/orders/{id} 라는 템플릿으로 기록된다. 스프링이 알아서 해 주는 부분이지만, 직접 문자열을 파싱해 라우팅하면 이 보호가 사라지고 주문 수만큼 시계열이 생긴다.

controller/ChaosController.java — 06·07장에서 그래프를 움직이는 용도 
@RestController
@RequestMapping("/api/chaos")
public class ChaosController {

    private static final long MAX_SLEEP_MS = 5_000L;

    private final Random random = new Random();

    @GetMapping("/slow")
    public Map<String, Object> slow(@RequestParam(defaultValue = "500") long ms)
            throws InterruptedException {
        long sleepMs = Math.min(ms, MAX_SLEEP_MS);
        Thread.sleep(sleepMs);
        return Map.of("sleptMs", sleepMs);
    }

    @GetMapping("/error")
    public ResponseEntity<Map<String, Object>> error(
            @RequestParam(defaultValue = "0.5") double rate) {
        if (random.nextDouble() < rate) {
            return ResponseEntity.status(HttpStatus.INTERNAL_SERVER_ERROR)
                    .body(Map.of("failed", true));
        }
        return ResponseEntity.ok(Map.of("failed", false));
    }
}

일부러 넣지 않은 설정

많은 예제가 management.metrics.tags.application: ${spring.application.name} 같은 공통 태그를 넣는다. 이 시리즈에서는 넣지 않는다. 이유는 둘이다.

첫째, 해당 프로퍼티는 Spring Boot 3.2 에서 management.observations.key-values 로 대체 예고됐고, 대체 프로퍼티는 옵저베이션 기반 메트릭에만 적용되는 등 동작 범위가 다르다. 버전을 넘나들며 헷갈릴 여지가 크다.

둘째, 쿠버네티스에서는 06장의 ServiceMonitor 가 스크레이프 시점에 job · namespace · pod · service 라벨을 자동으로 붙인다. 앱에서 또 붙이면 의미가 겹치는 라벨이 두 벌 생기고, 그만큼 시계열도 는다.

Boot 4 의 기본값 변화

Spring Boot 4 는 액추에이터 엔드포인트 접근을 기본적으로 읽기 전용으로 제한한다(management.endpoints.access.default=read-only). 로그 레벨을 런타임에 바꾸는 등 쓰기 동작이 필요하면 해당 엔드포인트만 access: unrestricted 로 열어야 한다. 실습에서는 읽기 전용으로 충분하다.

게이트웨이는 자바 코드가 사실상 없다. 이니셜라이저가 만든 메인 클래스를 그대로 두고 설정만 쓴다.

설정하는 일
id: order-api라우트 식별자. 메트릭의 routeId 태그 값이 된다 — 07장에서 라우트별 지연을 비교할 때 이 값으로 나눈다
uri: ${ORDER_API_URI:...}뒤쪽 주소. 로컬에서는 localhost:8081, 03장에서는 환경변수로 서비스 DNS 이름을 넣는다
predicates: Path=...이 경로로 오는 요청만 이 라우트로 보낸다
filters: AddRequestHeader뒤쪽으로 넘길 때 헤더를 붙인다. 게이트웨이를 거쳤는지 구분하는 용도
액추에이터 gateway 엔드포인트를 열지 않는 이유

exposure.include 에 gateway 를 넣고 인증을 걸지 않으면, 런타임에 라우트를 조작하거나 환경 프로퍼티를 읽어내는 취약점(CVE-2025-41243, CVE-2025-41253)의 성립 조건에 그대로 들어맞는다. “로컬 실습이니까”라는 이유로 열어 두면 그 설정이 사내로 복사된다.

X-Forwarded 헤더

2025.0 부터 X-Forwarded-* 와 Forwarded 헤더 처리는 기본 비활성이다. 게이트웨이 뒤에서 클라이언트 IP 를 봐야 한다면 spring.cloud.gateway.server.webflux.trusted-proxies 에 신뢰할 프록시 대역을 정규식으로 지정해야 한다. 이 실습에서는 필요 없다.

게이트웨이가 추가로 내보내는 메트릭

액추에이터가 클래스패스에 있으면 게이트웨이 메트릭은 별도 설정 없이 수집된다. 프로메테우스 포맷에서 이름은 spring_cloud_gateway_requests_seconds_* 이고 routeId · routeUri · outcome · status 태그가 붙는다. “어느 백엔드로 나가는 트래픽이 느린가”를 라우트 단위로 볼 수 있다는 뜻이다.

orders_rejected_total{reason="quantity_exceeded"} 5.0
orders_stored 40.0
orders_processing_seconds_count 45.0
orders_processing_seconds_sum 3.214
orders_processing_seconds_bucket{le="0.021845"} 0.0
...
판정

orders.created 가 orders_created_total 이 된 것을 확인한다 — 점은 언더스코어로, 카운터에는 _total 접미사가 붙는다. _count 가 45 인데 created 가 40 인 것은 거부된 5건도 타이머 안에서 처리됐기 때문이다. 06장에서 PromQL 을 쓸 때는 변환된 이름을 쓴다.

4. HTTP 메트릭과 버킷 확인

curl -s http://localhost:8081/actuator/prometheus \
  | grep 'http_server_requests_seconds_count'

--- 출력 (줄이 길어 두 줄만) ---

http_server_requests_seconds_count{error="none",exception="none",method="POST",outcome="SUCCESS",status="201",uri="/api/orders"} 40.0
http_server_requests_seconds_count{error="none",exception="none",method="GET",outcome="SERVER_ERROR",status="500",uri="/api/chaos/error"} 6.0
# 버킷이 실제로 생성됐는지 (percentiles-histogram 설정 확인)
curl -s http://localhost:8081/actuator/prometheus \
  | grep -c 'http_server_requests_seconds_bucket'
결과가 0 이면

percentiles-histogram 설정이 적용되지 않은 것이다. 이 상태로 진행하면 07장에서 P95 패널이 No data 로 남는다. 설정의 메트릭 이름을 점 표기로 썼는지 먼저 본다 — http_server_requests 로 쓰면 아무 일도 일어나지 않는다.

5. 게이트웨이 라우트 메트릭 확인

curl -s http://localhost:8080/actuator/prometheus \
  | grep 'spring_cloud_gateway_requests_seconds_count'

--- 출력 ---

spring_cloud_gateway_requests_seconds_count{httpMethod="POST",httpStatusCode="201",outcome="SUCCESSFUL",routeId="order-api",routeUri="http://localhost:8081",status="CREATED"} 40.0
판정

routeId="order-api" 가 보이면 설정의 id: 값이 메트릭 태그로 넘어온 것이다. 이 태그가 07장에서 라우트별 지연을 나누는 기준이 된다.

6. 노출하지 말아야 할 것이 닫혀 있는지

curl -s -o /dev/null -w '%{http_code}\n' http://localhost:8080/actuator/env
curl -s -o /dev/null -w '%{http_code}\n' http://localhost:8080/actuator/gateway/routes

--- 출력 ---

404
404
판정

둘 다 404 여야 한다. 200 이 나오면 exposure.include 를 다시 본다. 이것은 실습 편의가 아니라 보안 점검 항목이다.

10일부러 실패시키기 — 스프링 클라우드 버전 짝 맞추기

이 장에서 가장 많이 막히는 지점은 계측 코드가 아니라 의존성이다. 게이트웨이 아티팩트 이름과 릴리스 트레인이 최근에 바뀌었고, 검색으로 나오는 예제는 대부분 옛 이름이다. 두 가지를 실제로 틀려 보고 메시지를 읽는다.

아래 출력은 Gradle 9.7.1 · JDK 21 · Spring Boot 4.1.0 에서 재현했다 (확인 2026-09-13).

실패 1 — 제거된 아티팩트 이름

목적: “없는 이름”과 “버전을 못 찾는 것”을 구분해 읽는다.

dependencies {
    // 검색에 가장 많이 나오는 옛 이름
    implementation 'org.springframework.cloud:spring-cloud-starter-gateway'
}
./gradlew compileJava

--- 출력 ---

* What went wrong:
Execution failed for task ':compileJava'.
> Could not resolve all files for configuration ':compileClasspath'.
   > Could not find org.springframework.cloud:spring-cloud-starter-gateway:.
     Required by:
         root project 'gateway'
읽는 법

주목할 곳은 아티팩트 이름 뒤의 콜론 다음이 비어 있다는 점이다(...starter-gateway:). 버전을 BOM 에서 가져오는 구조인데, BOM 에 그 이름이 없으니 버전이 빈 채로 조회된 것이다. 즉 “버전을 잘못 적었다”가 아니라 “그 이름이 이 릴리스 트레인에 없다”는 뜻이다. 버전을 손으로 적어 넣는 식으로 우회하려 들면 시간만 버린다.

고치는 방법은 이름을 바꾸는 것 하나다.

implementation 'org.springframework.cloud:spring-cloud-starter-gateway-server-webflux'
./gradlew dependencies --configuration compileClasspath | head -4

--- 출력 ---

compileClasspath - Compile classpath for source set 'main'.
\--- org.springframework.cloud:spring-cloud-starter-gateway-server-webflux -> 5.0.2
     +--- org.springframework.cloud:spring-cloud-starter:5.0.2
     |    +--- org.springframework.boot:spring-boot-starter:4.0.7 -> 4.1.0
판정

버전 5.0.2 가 채워졌다. 릴리스 트레인 2025.1.2 가 이 버전을 가리킨다는 뜻이다. 아래 딸려 오는 spring-boot-starter 가 4.0.7 -> 4.1.0 으로 올라간 것도 정상이다 — 부트 플러그인이 자기 버전으로 맞춘다.

실패 2 — 릴리스 트레인이 한 세대 아래일 때

목적: “빌드가 되니까 맞는 조합”이라는 판단이 왜 위험한지 본다.

ext {
    set('springCloudVersion', '2025.0.0')   // Boot 3.5 세대
}
./gradlew compileJava

--- 출력 ---

BUILD SUCCESSFUL in 5s
성공했는데도 틀린 조합이다

의존성 해석은 통과한다. 무엇이 딸려 왔는지를 봐야 안다.

./gradlew dependencies --configuration compileClasspath \
  | grep -E 'spring-cloud-starter-gateway|spring-boot-starter:' | head -4

--- 출력 ---

\--- org.springframework.cloud:spring-cloud-starter-gateway-server-webflux -> 4.3.0
     +--- org.springframework.cloud:spring-cloud-starter:4.3.0
     |    +--- org.springframework.boot:spring-boot-starter:3.5.0 -> 4.1.0
읽는 법

게이트웨이는 4.3.0 — spring-boot-starter:3.5.0 을 기대하고 빌드된 버전이다. 그런데 부트 플러그인이 그것을 4.1.0 으로 끌어올린다. “Boot 3.5 용으로 컴파일된 게이트웨이가 Boot 4.1 위에서 돈다”는 상태가 되고, 바뀐 내부 API 를 건드리는 순간 실행 시점에 NoSuchMethodError 부류로 깨진다. 빌드 성공은 아무것도 보장하지 않는다.

Spring Boot짝이 되는 릴리스 트레인게이트웨이 버전
3.5.x2025.0.x4.3.x
4.1.x2025.1.x (Oakwood)5.0.x

정정해 둘 것이 하나 있다. 이 조합을 두고 “해석 단계에서 깨진다”고 적은 자료가 많은데 사실이 아니다. 위에서 본 대로 빌드는 성공한다. 그래서 더 위험하다 — 컴파일이 통과했다는 이유로 배포까지 갔다가 런타임에 드러난다. 조합을 확인하는 방법은 빌드 성공 여부가 아니라 dependencies 출력의 해석된 버전 숫자다.

11자주 겪는 문제

증상원인과 조치
/actuator/prometheus 가 404레지스트리 의존성이 없거나 exposure.include 에 prometheus 가 빠졌다. 둘 다 있어야 한다

12뒤 단계에서 쓸 메트릭 지도

지금 만든 것들이 어디서 쓰이는지 미리 짚어 둔다. 이 표가 이 장의 산출물이다.

메트릭 (프로메테우스 이름)타입쓰이는 곳
http_server_requests_seconds_count카운터06 — 처리율 R, 에러율 E
http_server_requests_seconds_bucket히스토그램06·07 — P95·P99 지연 D
spring_cloud_gateway_requests_seconds_*타이머07 — 라우트별 지연 비교
orders_created_total카운터07 — 비즈니스 지표 패널
orders_rejected_total카운터07 — 거부율 알림 규칙
orders_processing_seconds_*타이머06 — HTTP 지연과 내부 처리 지연 분리
orders_stored게이지07 — 게이지와 카운터의 그래프 차이
jvm_memory_used_bytes게이지07 — JVM 대시보드 (자동 수집)
jvm_gc_pause_seconds_*타이머10 — 지연 급증 원인 추적 (자동 수집)

jvm_ · process_ · system_ 으로 시작하는 메트릭은 코드를 한 줄도 쓰지 않아도 나온다. 액추에이터가 등록하는 MeterBinder 들이 JVM 과 OS 지표를 자동으로 붙이기 때문이다.
