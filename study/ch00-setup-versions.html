쿠버네티스 관측성

실습 환경 준비와 버전 고정

코드는 한 줄도 쓰지 않는다. 클러스터를 올리기 전에 도구를 갖추고, 모두가 같은 화면을 보도록 버전을 못 박는다.

01왜 이 장이 필요한가

관측성 실습은 도구가 서로 맞물려 돌아간다. 프로메테우스가 앱을 긁고, 그라파나가 프로메테우스에 질의하고, 오퍼레이터가 그 설정을 만든다. 어느 한 쪽 버전이 어긋나면 에러 없이 화면만 비는 상태가 된다.

예를 들어 대시보드 JSON (JavaScript Object Notation · 키·값으로 데이터를 적는 형식) 은 특정 차트 버전이 만드는 데이터소스 이름에 의존한다. 한 사람이 차트 88.3.0 으로, 다른 사람이 90.x 로 설치하면 같은 JSON 이 한쪽에서만 그려진다. 그런데 오류 메시지는 나오지 않는다. 패널이 비어 있을 뿐이다.

그래서 첫 장에서 버전을 정하고 넘어간다. 여기서 쓰는 시간이 뒤 열 장에서 아낄 시간이다.

02알아야 할 개념

메트릭이 이상을 알려주고, 로그가 이유를 말해준다

메트릭(Metric)은 정해진 간격으로 측정한 수치이고, 로그(Log)는 실행 중 일어난 사건의 기록이다. 파드의 응답 지연이 높게 나타났다고 하자. 메트릭은 “지금 이상하다”까지만 알려준다. 왜 이상한지는 그 시각의 애플리케이션 로그를 봐야 나온다.

이 실습의 순서가 그대로 이 축을 따른다. 04~07장이 메트릭이고 08장이 로그다. 순서를 바꾸지 않는 이유는, 로그를 먼저 모아 봐야 언제의 로그를 봐야 하는지 알 수 없기 때문이다.

폐쇄형 관측과 개방형 관측

구분영문무엇을 보나한계 / 쓸모
폐쇄형closed-box
(black-box)		 애플리케이션 바깥에서 관찰. CPU (Central Processing Unit · 중앙처리장치) · 메모리 · 디스크 인프라에는 유용하다. 앱이 왜 그렇게 동작하는지는 알려주지 못한다

이 실습에서 만드는 것의 대부분이 개방형이다. 02장에서 앱 안에 계측 코드를 심는 이유가 이것이다. 폐쇄형은 10장에서 다시 나온다 — 카오스 실험의 정상 상태 판정은 외부 관찰이기 때문이다.

메트릭은 당겨 오고, 로그는 밀어 보낸다

화살표 방향이 반대다. 프로메테우스는 대상의 /metrics 를 주기적으로 긁어 온다(pull). 대상은 자기가 어디로 보내야 하는지 모르고 그저 열어 두기만 한다. 로그는 반대로 수집기가 각 노드에서 읽어 로키로 밀어 넣는다(push).

이 비대칭이 04장의 ServiceMonitor 와 08장의 Alloy 설정이 왜 생김새가 다른지를 설명한다. 전자는 “어디를 긁을지”를 적고 후자는 “어디로 보낼지”를 적는다.

왜 pull 인가

수집 대상이 살아 있는지를 수집기가 직접 확인할 수 있다. 스크레이프에 실패하면 up == 0 이라는 메트릭이 자동으로 남는다. push 방식이라면 “메트릭이 안 오는 것”과 “앱이 죽은 것”을 구분할 수 없다.

03최종적으로 만들 것

실습 전체가 노트북 한 대 안에서 끝난다. 클라우드 계정도 별도 VM (Virtual Machine · 가상 머신) 도 필요 없다. 도커 컨테이너 3개가 쿠버네티스 노드 역할을 하고, 그 안에서 애플리케이션과 관측 스택이 함께 돈다.

물리 구조 — 컨테이너 3개가 노드 3개다

아래 세 단계는 서로 다른 작업이 아니다. ①이 만들고, ②와 ③은 그렇게 만들어진 같은 것을 두 각도에서 세는 것이다. 두 목록에 나오는 이름이 똑같다는 점을 확인하는 것이 목적이다.

  • 1 클러스터를 만든다. 이 명령 하나가 컨테이너 3개를 띄운다. 명령 kind create cluster --config kind-cluster.yaml · 01장에서 실행한다
  • 2 컨테이너가 3개인지 센다. 쿠버네티스가 아니라 도커의 관점이다. 명령 docker ps --filter name=obs- --format '{{.Names}}' → obs-control-plane · obs-worker · obs-worker2 세 줄
  • 3 같은 것을 쿠버네티스 관점에서 본다. 컨테이너 3개가 노드 3개로 보인다. 명령 kubectl get nodes → STATUS 가 셋 다 Ready
이 그림이 말하는 것

docker ps 의 3줄과 kubectl get nodes 의 3줄은 같은 것을 두 각도에서 본 것이다. 이 대응이 머리에 들어오면, 나중에 “노드에 들어가 확인한다”가 “그 컨테이너에 docker exec 한다”와 같은 말이라는 것이 자연스러워진다.

WHY그림이 이렇게 나오는 이유 — kind-cluster.yaml

컨테이너가 하필 3개이고 이름이 하필 obs- 로 시작하는 것은 kind 가 알아서 정한 것이 아니다. 설정 파일에 그렇게 적혀 있기 때문이다. 01장에서 실제로 쓸 파일을 여기서 미리 펼쳐 그림과 대조한다.

study/labs/infra/kind-cluster.yaml — 발췌 
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
name: obs                   # ① 클러스터 이름. 컨테이너 이름의 접두사가 된다

nodes:                      # ② 이 목록의 항목 수 = 뜨는 컨테이너 수
  - role: control-plane     #    1번째 항목
    image: kindest/node:v1.36.1@sha256:3489c767...   # 다이제스트는 줄였다
    extraPortMappings:      #    그림 2에서 다룬다
      - containerPort: 30300
        hostPort: 30300
        listenAddress: "127.0.0.1"
        protocol: TCP

  - role: worker            #    2번째 항목
    image: kindest/node:v1.36.1@sha256:3489c767...
    labels:
      workload: apps        # ③ 이 노드에 앱을 모은다 (03장 nodeSelector 가 쓴다)

  - role: worker            #    3번째 항목
    image: kindest/node:v1.36.1@sha256:3489c767...
    labels:
      workload: observability   # ③ 이 노드에 관측 스택을 모은다 (04장)

nodes: 목록의 항목이 셋이므로 컨테이너가 셋 뜬다. 메모리가 모자라면 워커 한 항목을 지워 2개로 줄여도 되고, 반대로 항목을 늘리면 노드가 는다. 그림의 상자 개수는 이 목록의 길이다.

이름이 정해지는 규칙

kind 는 <클러스터이름>-<역할> 로 컨테이너 이름을 짓고, 같은 역할이 둘 이상이면 두 번째부터 숫자를 붙인다. 첫 번째에는 숫자가 없다 — obs-worker1 이 아니라 obs-worker 다.

설정 파일의 위치도커 컨테이너 이름쿠버네티스 노드 이름이 노드가 맡는 일
name: obs + 1번째 role: control-planeobs-control-planeobs-control-planeAPI 서버 · etcd · 스케줄러. 호스트 포트도 이 노드로 들어온다
2번째 role: workerobs-workerobs-workerworkload: apps — 게이트웨이와 order-api
3번째 role: workerobs-worker2obs-worker2workload: observability — 프로메테우스 · 그라파나 · 로키
클러스터 이름을 기본값으로 두지 않는다

name: 을 빼면 클러스터 이름이 kind 가 되어 컨테이너가 kind-control-plane 으로 뜬다. 이 문서의 뒤쪽 명령은 전부 obs- 를 전제하므로 이름이 다르면 맞지 않는다. 이미 다른 이름으로 만들었다면 kind delete cluster --name <그이름> 으로 지우고 다시 만든다.

명령 한 줄이 실제로 하는 세 가지

01장에서 실행할 명령 
kind create cluster --config kind-cluster.yaml
  1. 도커 컨테이너 3개를 띄운다. 이미지는 kindest/node:v1.36.1 — 리눅스 한 벌에 kubelet 과 컨테이너 런타임이 미리 들어 있는 이미지다. 이것이 docker ps 에 보이는 3줄이다.
  2. 그 컨테이너 안에서 kubeadm 을 돌린다. 컨트롤 플레인 노드에 API 서버 · etcd · 스케줄러를 세우고, 나머지 둘을 조인시킨다. 이것이 kubectl get nodes 에 보이는 3줄이다.
  3. ~/.kube/config 에 컨텍스트를 추가한다. 이름은 kind-obs 이고 현재 컨텍스트로 바뀐다. 그래서 다음 명령부터 kubectl 이 이 클러스터를 가리킨다.

--config 를 빼면 위 파일을 읽지 않으므로 단일 노드 클러스터가 뜬다. 포트 매핑도 라벨도 없으니 05장에서 그라파나가 열리지 않는다. 옵션 하나가 뒤의 여러 장을 좌우한다.

요청이 흐르는 경로 — 브라우저에서 그라파나까지

  • 1 호스트 포트 → 노드 컨테이너. 01장의 kind-cluster.yaml 에 적은 extraPortMappings 가 뚫는다. 확인 docker port obs-control-plane → 30300/tcp -> 127.0.0.1:30300 이 보인다
  • 2 노드 포트 → 서비스. 04장에서 그라파나 서비스를 NodePort 30300 으로 연다. 확인 kubectl -n monitoring get svc kps-grafana → PORT(S) 열에 80:30300/TCP
  • 3 서비스 → 파드. 서비스가 고른 파드의 컨테이너 포트 3000 으로 전달된다. 확인 kubectl -n monitoring get endpointslices -l kubernetes.io/service-name=kps-grafana → 파드 IP (Internet Protocol · 네트워크에서 주소를 정하는 규약) 가 한 줄 이상
  • ✓ 세 칸이 전부 이어졌는지 한 번에 본다. 중간 어디가 끊겼는지는 위 셋을 순서대로 짚어 좁힌다. 확인 curl -s -o /dev/null -w '%{http_code}\n' http://localhost:30300/login → 200

WHY이 경로를 뚫는 설정 — 30300 이 세 번 나오는 이유

그림의 화살표 세 개는 각각 다른 파일의 다른 줄이 만든다. 같은 숫자 30300 이 두 파일에 적혀 있고, 그 둘이 맞아야 이어진다.

study/labs/infra/kind-cluster.yaml — ①번 화살표를 만드는 부분 
nodes:
  - role: control-plane
    extraPortMappings:
      - containerPort: 30300      # 노드 컨테이너 안쪽 포트
        hostPort: 30300           # 맥에서 열 포트 — 브라우저가 치는 번호
        listenAddress: "127.0.0.1"  # 이 맥에서만 접근 가능. 외부에 열지 않는다
        protocol: TCP
study/labs/monitoring/kps-values.yaml — ②번 화살표를 만드는 부분 (04장에서 설치) 
grafana:
  service:
    type: NodePort      # 노드의 포트를 열어 외부에서 들어올 수 있게 한다
    nodePort: 30300     # kind 쪽 containerPort 와 같은 번호여야 한다
번호구간그 구간을 만드는 설정끊겼을 때 증상
①맥 → 노드 컨테이너kind-cluster.yaml 의 extraPortMappings브라우저가 즉시 “연결할 수 없음”. docker port 에 줄이 없다
②노드 포트 → 서비스kps-values.yaml 의 nodePort: 30300포트는 열려 있는데 응답이 없다. 두 숫자가 어긋난 경우다
③서비스 → 파드서비스의 selector 와 파드 라벨EndpointSlice 가 비어 있다. 502 또는 무응답
포트 매핑은 나중에 못 늘린다

extraPortMappings 는 클러스터를 만드는 시점에만 정의된다. 도커 컨테이너의 포트 매핑이 생성 시점에 고정되는 것과 같은 이유다. 나중에 포트가 하나 더 필요해지면 클러스터를 지우고 다시 만들어야 하므로, 이 파일은 30080(게이트웨이) · 30300(그라파나) · 30900(프로메테우스) 세 개를 미리 뚫어 둔다.

데이터가 흐르는 방향 — 당기기와 밀기

  • 1 앱이 열어 둔 것을 직접 본다. 아직 프로메테우스가 없어도 확인할 수 있다. 확인 kubectl -n apps exec deploy/order-api -- curl -s localhost:8080/actuator/prometheus | head -3 → # HELP 로 시작하는 줄 (03장 이후)
  • 2 프로메테우스가 실제로 긁고 있는지 본다. 확인 curl -s 'http://localhost:30900/api/v1/query?query=up' | jq '.data.result | length' → 0 보다 큰 수 (04장 이후)
  • 3 로그가 로키에 도착했는지 본다. 방향이 반대이므로 확인 지점도 반대편이다. 확인 그라파나 → Explore → Loki → {namespace="apps"} 에 줄이 보인다 (08장 이후)

WHY방향을 정하는 설정 — 당기는 쪽과 미는 쪽

화살표 방향이 반대인 것은 설정이 놓인 위치가 반대이기 때문이다. pull 은 받는 쪽(프로메테우스)이 설정을 갖고, push 는 보내는 쪽(Alloy)이 설정을 갖는다. 앱에는 어느 쪽 설정도 없다.

study/labs/monitoring/kps-values.yaml — 당기는 쪽 (04장) 
prometheus:
  prometheusSpec:
    scrapeInterval: 30s     # 30초마다 대상들을 긁는다. 주기의 주인은 프로메테우스다
    nodeSelector:
      workload: observability    # 그림에서 이 상자가 obs-worker2 에 있는 이유

“무엇을 긁을지”는 여기에 적지 않는다. 06장에서 ServiceMonitor 라는 별도 리소스로 붙인다 — 앱을 배포하는 사람과 수집 설정을 하는 사람이 달라도 되게 하려는 설계다.

study/labs/monitoring/alloy-values.yaml — 미는 쪽 (08장) 
// 3) 쿠버네티스 API로 로그를 읽는다 (호스트 경로 마운트가 필요 없다)
loki.source.kubernetes "pods" {
  targets    = discovery.relabel.pod_logs.output
  forward_to = [loki.write.default.receiver]
}

// 4) 로키로 밀어 넣는다 — 목적지 주소가 보내는 쪽에 적혀 있다
loki.write "default" {
  endpoint {
    url = "http://loki-gateway.logging.svc.cluster.local/loki/api/v1/push"
  }
}

로키에는 “누구에게서 받을지”를 적는 곳이 없다. 주소를 아는 쪽은 Alloy 이고, 로키는 들어오는 것을 저장할 뿐이다. 프로메테우스와 정확히 뒤집힌 구조다.

study/labs/k8s/10-order-api.yaml — 앱 쪽 (03장) 
ports:
  - name: http          # 이 포트 '이름'을 06장 ServiceMonitor 가 참조한다
    containerPort: 8080

앱이 하는 일은 /actuator/prometheus 를 열어 두고 포트에 http 라는 이름을 붙인 것뿐이다. 프로메테우스 주소도, 로키 주소도 앱 어디에도 없다. 이것이 그림 3 의 요지다 — 앱은 관측 스택을 모른 채로 관측된다.

각 명령이 무엇을 확인하는가
  • docker version 의 Server 버전 — 데몬이 실제로 살아 있어야 값이 나온다. 여기서 막히면 Docker Desktop 이 안 떠 있는 것이다.
  • kubectl version --client — 클라이언트만 본다. 서버와 마이너 버전이 한 칸을 넘게 벌어지면 지원 범위 밖이다.
  • kind version — 노드 이미지 다이제스트와 짝이 맞아야 한다. 01장 설정 파일이 특정 kind 버전을 전제한다.
  • helm version — 차트 문법이 메이저 버전에서 갈린다. 3.16 이상이어야 OCI (Open Container Initiative · 컨테이너 이미지·런타임 표준) 아티팩트 차트를 다룰 수 있다.

헬름 저장소 등록

2026년에 가장 많이 틀리는 지점이다. 로키 · 그라파나 차트는 grafana 가 아니라 grafana-community 에 있다.

helm repo add prometheus-community https://prometheus-community.github.io/helm-charts
helm repo add grafana-community    https://grafana-community.github.io/helm-charts
helm repo update
저장소를 틀리면 조용히 실패한다

grafana/loki 경로로는 원하는 차트를 받지 못한다. 그런데 오류가 아니라 빈 결과가 돌아온다. “차트가 없어졌나” 하고 시간을 버리기 쉽다. 2026-03-16 부로 차트가 이전했고, 기존 grafana 저장소의 차트는 상용 사용자 대상으로만 유지된다.

05버전 고정

문서에 버전 숫자를 박아 두지 않는다. 대신 설치 직전에 확인하고 그 값을 팀 전체가 공유한다.

report() {
  # $1=도구명  $2=권장버전  $3=탐지된 버전
  if [ -z "$3" ]; then
    printf '%-10s %-24s %s\n' "$1" "MISSING" "설치 필요 (권장 $2)"
    return 1
  fi
  printf '%-10s %-24s %s\n' "$1" "$3" "(권장 $2)"
  return 0
}
