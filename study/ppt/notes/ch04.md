## 04-01 메모리 사용량이 왜 두 군데서 다른가

**화면** — 네 출처 그림 (`gaps.figure` — 새로 그려야 함)

**말할 것**

쿠버네티스에서 메트릭이 나오는 곳은 하나가 아니다. `kubectl top` 이 말하는 숫자와
그라파나 그래프의 숫자가 다르면 여기서 헤맨다.

| 출처 | 무엇을 재나 | 어디에 있나 |
|---|---|---|
| **cAdvisor** | 컨테이너의 실제 사용량 | kubelet 안에 내장 |
| **metrics-server** | cAdvisor 값을 모아 최근 값만 | 별도 설치. `kubectl top` 과 HPA 가 쓴다 |
| **node-exporter** | 노드 OS 상태 | 노드마다 DaemonSet |
| **kube-state-metrics** | API 서버가 아는 오브젝트 상태 | 클러스터에 하나 |

**말로 구분하려 하지 말고 각각을 직접 질의해서 나온 메트릭 이름으로 구분한다** —
이것이 이 장의 실습이다. 접두사가 출처를 말해 준다. `container_` 는 cAdvisor,
`node_` 는 node-exporter, `kube_` 는 kube-state-metrics.

**근거** — 책 3.4 · 3.5

## 04-02 기계의 상태와 API 서버가 아는 상태

**말할 것**

이름이 비슷해 자주 헷갈리는 둘이다.

- **node-exporter** — 기계의 상태. "이 노드의 메모리가 몇 바이트 남았는가"
- **kube-state-metrics** — API 서버가 아는 상태. "이 디플로이먼트가 레플리카 3개를 원하는데 실제로는 2개인가"

전자는 **노드마다 하나씩**(DaemonSet), 후자는 **클러스터에 하나만** 있으면 된다.
파드 수를 세어 보면 바로 구분된다.

앞은 사실이고 뒤는 **선언과 사실의 차이**다. 장애 판단에는 보통 뒤가 더 유용하다.

## 04-03 metrics-server 는 과거를 모른다

**화면** — 시간축 · 현재값만 표시

**말할 것**

metrics-server 는 장기 저장을 하지 않는다. **"10분 전 CPU 는?"에 답하지 못한다.**
그 답을 하려고 프로메테우스를 설치하는 것이다.

**배경 (질문이 나오면)** — 전임자 힙스터(Heapster)가 데이터 싱크 설계 문제로 사용 중단됐고,
리소스 메트릭 API 를 집계 API 로 표준화하면서 지금 형태가 됐다.
그래서 metrics-server 는 "지금 값"만 제공하는 좁은 역할로 남았다.

## 04-04 오퍼레이터는 스크레이프하지 않는다

**도판** — `figures/ch04-fig1.svg`

**말할 것**

가장 많이 오해하는 부분이다. 차트 하나를 설치하면 오퍼레이터 · 프로메테우스 본체 ·
알림매니저 · 그라파나 · node-exporter · kube-state-metrics 가 함께 들어온다.

**오퍼레이터는 메트릭을 긁지 않는다.** ServiceMonitor 같은 커스텀 리소스를 읽어
프로메테우스의 설정 파일을 만들고 리로드시키는 것이 전부다.
실제 스크레이프는 프로메테우스 본체가 한다.

**②번 단계에 함정이 있다** — 오퍼레이터는 아무 ServiceMonitor 나 읽지 않는다.
프로메테우스 리소스에 정의된 **셀렉터에 맞는 것만** 고른다.
기본값은 "헬름 릴리스 이름과 같은 `release` 라벨을 가진 것"이다.
**06장의 첫 관문이 이것이다.**

이 구조를 알면 "ServiceMonitor 를 만들었는데 타깃에 안 보인다"의 원인을 셋 중 하나로 좁힐 수 있다.

## 04-05 타깃 검증이 이 장의 핵심

**화면** — targets API 출력 · 판정 줄

**말할 것**

**01장의 스무 줄이 여기서 결과로 나온다.** `bind-address` 를 고쳤다면
controller-manager · scheduler · etcd · kube-proxy 가 전부 UP 이고,
안 고쳤다면 빨간 줄 네 개가 그대로 뜬다.

설치하고 파드가 Running 인 것으로 끝내지 않는다. **타깃이 전부 UP 인지까지 봐야
이 장이 끝난 것이다.**

**차트 버전은 설치 직전에 정한다** — 문서에 박아 두지 않고
`helm search repo ... --versions` 로 확인해 팀 공용 값으로 고정한다.
CHART VERSION 은 차트 버전이고 APP VERSION 은 오퍼레이터 버전이다. 둘이 다르다.

**CRD 는 헬름이 업그레이드해 주지 않는다** — 처음 설치 때는 CRD 가 함께 생성되지만
`helm upgrade` 로 차트 버전을 올릴 때는 갱신되지 않는다. 헬름의 설계상 그렇다.
실습 중에 버전을 올릴 일이 생기면 **지우고 다시 설치하는 편이 빠르다.**

**계층적으로 본다** — 책이 권하는 순서는 노드 → 클러스터 구성요소 → 애드온 → 애플리케이션이다.
파드가 대기 상태에 빠지면 먼저 노드 자원을 보고, 문제없으면 스케줄러를, 그다음 앱을 본다.
순서를 뒤집으면 앱 로그만 하루 종일 보게 된다.
