## 06-01 에러 없이 타깃이 사라진다

**도판** — `figures/ch06-fig1.svg`

**말할 것**

앱이 `/actuator/prometheus` 를 잘 노출하고 있어도 프로메테우스 타깃에 나타나지 않는 일이 흔하다.
**그리고 그때 에러 메시지가 없다.** 연결이 세 겹의 라벨 일치로만 이루어지기 때문이다.

| 겹 | 고르는 쪽 → 골라지는 쪽 |
|---|---|
| ① | Prometheus CR 의 `serviceMonitorSelector` → ServiceMonitor 의 라벨 |
| ② | ServiceMonitor 의 `selector` → Service 의 라벨 |
| ③ | Service 의 `selector` → 파드의 라벨 |

**03장에서 Service 에 라벨을 붙이고 포트에 `http` 라는 이름을 준 이유가 여기 있다.**
②와 ③은 그때 이미 준비해 둔 것이고, 이번에 새로 만드는 것은 ①과 ServiceMonitor 뿐이다.

**실습 순서** — `release` 라벨 없이 먼저 만들어 본다. 5분이면 되고, 이 경험이 몇 시간을 아낀다.

```
sleep 40
curl -s --get http://localhost:30900/api/v1/query \
  --data-urlencode 'query=up{namespace="apps"}' | jq '.data.result | length'

0
```

**0 이다. 오류도 경고 로그도 없다.**

## 06-02 어느 겹이 끊겼는지 보는 법

**화면** — 표 3행 · 확인 명령 · `tables/06-02-label-layers.tsv`

**말할 것**

세 겹은 각각 **다른 명령**으로 본다. 순서대로 내려가면 반드시 걸린다.

| 겹 | 확인 방법 |
|---|---|
| ① | `kubectl -n monitoring get prometheus -o yaml \| grep -A4 serviceMonitorSelector` |
| ② | 프로메테우스 UI 의 **Service Discovery** 화면 |
| ③ | `kubectl get endpointslices` |

①의 기본값을 직접 보여 준다.

```
serviceMonitorSelector:
  matchLabels:
    release: kps
```

**왜 이런 기본값인가** — 차트가 `serviceMonitorSelectorNilUsesHelmValues: true` 를 기본으로 둔다.
"이 헬름 릴리스가 관리하는 것만 본다"는 뜻이다. 한 클러스터에 프로메테우스를 여러 개 띄우는
상황(팀별 분리)에서 서로의 타깃을 침범하지 않게 하려는 장치다.

**04-04 와 이어 붙인다** — 오퍼레이터가 ServiceMonitor 를 고르는 그 셀렉터가 이것이다.

## 06-03 포트는 번호가 아니라 이름이다

**화면** — ServiceMonitor 발췌 · `snippets/code/06-03-servicemonitor.yaml`

**말할 것**

`ServiceMonitor` 의 `endpoints.port` 는 **포트 번호가 아니라 서비스에 정의된 포트 이름**이다.
숫자를 적으면 **조용히 안 붙는다.**

```yaml
endpoints:
  - port: http          # 8080 이 아니다
    path: /actuator/prometheus
```

03장에서 Service 포트에 `name: http` 를 준 것이 이 한 줄을 위해서였다.

**포트 이름을 나중에 바꾸면** 트래픽에는 아무 영향이 없는데 ServiceMonitor 만 조용히 끊긴다.
서비스 리팩터링에서 흔히 밟는다.

## 06-04 프로메테우스가 붙여 주는 라벨

**말할 것**

스크레이프한 메트릭에는 **앱이 만들지 않은 라벨**이 붙어 온다 —
`namespace` · `pod` · `service` · `job`.

이 라벨들 덕분에 **파드가 죽고 다시 떠도 같은 `job` 으로 묶여** 하나의 시계열처럼 보인다.
02-01 에서 말한 "개별 인스턴스를 추적하지 않고 레이블로 묶은 집합을 본다"가 여기서 실현된다.

PromQL 에서 집계 축을 고를 때 쓰는 것이 대부분 이 라벨이다.
앱이 붙인 라벨(`uri` · `status` · `application`)과 구분해 두면 질의를 쓸 때 헷갈리지 않는다.

## 06-05 RED 를 PromQL 로

**도판** — `figures/ch06-fig2.svg` · `snippets/code/06-05-red-queries.promql`

**말할 것**

02장에서 심은 지표가 여기서 그래프가 된다.

- **Rate** — `sum(rate(http_server_requests_seconds_count[5m]))`
- **Errors** — 5xx 비율. 분모가 0 일 때를 대비해 `or vector(0)` 를 붙인다
- **Duration** — `histogram_quantile(0.99, sum by (le) (rate(..._bucket[5m])))`

**카운터에는 거의 항상 `rate()` 를 씌운다.** 대괄호 안의 시간은 "이만큼을 돌아보며 평균 낸다"는
뜻이고 **스크레이프 간격의 4배 이상**을 권장한다. 우리는 30초 간격이므로 `[5m]` 이면 넉넉하다.

`histogram_quantile` 은 `sum by (le)` 로 파드별 버킷을 **먼저 합친 뒤** 계산해야 한다.
파드별로 따로 계산해 평균 내면 틀린 값이 나온다.

**02-04 와 이어 붙인다** — `_bucket` 이 없으면 이 질의가 빈 결과를 낸다.
`percentiles-histogram` 을 켰기 때문에 지금 값이 나온다.
