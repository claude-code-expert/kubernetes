## 02-01 파드는 오래 살지 않는다

**말할 것**

쿠버네티스가 기존 모니터링과 갈리는 첫 지점이다. 24시간 가동되는 VM 은 상태 보존을 확인하면 되지만
파드는 수명이 짧다. **개별 인스턴스를 추적하는 방식이 성립하지 않는다.**
레이블로 묶은 집합을 봐야 한다.

00장에서 프로메테우스를 쓰는 이유로 든 것이 이것이다 — 다차원 키/값 데이터 모델이
쿠버네티스의 레이블 방식과 구조가 같아서, 파드가 수십 번 죽고 다시 떠도
레이블로 묶어 하나의 서비스로 볼 수 있다.

**근거** — 책 3.3

## 02-02 USE 와 RED

**화면** — 표 2행 · `tables/02-02-use-red.tsv`

**말할 것**

| 방법론 | 무엇을 보나 | 대상 |
|---|---|---|
| **USE** | 사용률(Utilization) · 포화도(Saturation) · 에러 | 인프라 |
| **RED** | 처리율(Rate) · 에러(Errors) · 처리시간(Duration) | 애플리케이션 |

둘은 대립이 아니라 상보다. **04장에서 설치할 스택의 내장 대시보드가 USE 를 채우고,
이 장에서 심는 계측이 RED 를 채운다.**

RED 의 기반 사상이 구글의 4대 골든 시그널(지연 · 트래픽 · 에러 · 포화도)이다.

## 02-03 평균 40ms 뒤에 숨은 3초

**말할 것**

요청 100건 중 99건이 10ms, 1건이 3초라면 평균은 40ms 다.
**대시보드는 초록색이고, 그 1건을 겪은 사용자는 이탈한다.**

P99 를 보면 3초가 그대로 드러난다. 07장에서 만들 패널이 전부 분위수 기반인 이유가 이것이다.

**숫자를 칠판에 쓰면 좋다** — (99×10ms + 1×3000ms) / 100 = 40ms

## 02-04 분위수는 공짜가 아니다

**도판** — `figures/ch02-fig2.svg`

**말할 것**

분위수를 계산하려면 히스토그램 버킷(`_bucket` 시계열)이 필요한데 **기본으로 생성되지 않는다.**
`percentiles-histogram` 을 켜야 만들어지고, 켜는 순간 **시계열 수가 버킷 개수만큼 늘어난다.**

알고 켜는 것과 모르고 켜는 것의 차이가 09장에서 카디널리티 문제로 돌아온다.

**한 요청이 만드는 시계열 세 종류** — `_count`(요청 수) · `_sum`(총 소요 시간) · `_bucket`(구간별 누적).
06장의 PromQL 이 어렵게 느껴지는 이유의 8할이 이 구조를 모르기 때문이다.

## 02-05 요청 하나가 만드는 세 종류

**말할 것**

이 장에서 만드는 앱은 요청 하나에 세 종류의 시계열을 남긴다.

1. **HTTP 지표** — 프레임워크가 자동으로 만든다
2. **JVM · 시스템 지표** — 액추에이터가 노출한다
3. **도메인 지표** — 직접 심는다

**세 번째가 이 실습의 핵심이다.** `orders.created` · `orders.rejected` ·
`orders.processing` · `orders.stored` 네 개다.

**서비스를 둘로 나눈 이유** — 하나로도 메트릭 실습은 된다. 둘로 나누는 이유는 하나뿐이다.
**지연이 전파되는 모습을 봐야** RED 지표가 왜 서비스별로 필요한지 체감된다.
주문 API 가 500ms 느려질 때 게이트웨이의 P99 가 어떻게 따라 움직이는지를
07장에서 두 그래프를 나란히 놓고 본다.

**DB 를 넣지 않은 이유 (질문이 나오면)** — 주문을 `ConcurrentHashMap` 에 보관한다.
DB 를 붙이면 파드가 하나 늘고 커넥션 풀 문제로 디버깅 시간이 샌다.
여기서 배울 것은 커넥션 풀 메트릭이 아니라 계측 방법이다.
HikariCP 메트릭은 액추에이터가 자동으로 잡으므로, 사내 프로젝트에 옮길 때
코드 수정 없이 대시보드만 추가하면 된다.

## 02-06 이 네 이름을 바꾸지 않는다

**도판** — `figures/ch02-fig1.svg`

**말할 것**

**06장의 PromQL 과 07장의 대시보드 JSON 이 이 네 이름에 의존한다.**
바꾸면 뒤가 전부 깨진다.

마이크로미터가 `.` 을 `_` 로 바꾸고 카운터에 `_total` 을 붙인다.
코드에 `orders.created` 라고 쓰면 `/actuator/prometheus` 에는
**`orders_created_total`** 로 나온다. 이 변환을 모르면 06장에서 질의가 빈 결과를 낸다.

**게이트웨이만 다른 것 하나** — `spring.cloud.gateway.requests` 를 추가로 내보낸다.
라우트 ID 태그가 붙어 "어떤 백엔드로 가는 트래픽이 느린가"를 바로 볼 수 있다.
