## 01-01 설정 파일 20줄이 승부처

**말할 것**

kubeadm 으로 만든 클러스터는 컨트롤 플레인 구성요소의 메트릭 포트를 **루프백에만 연다.**
보안상 합리적인 기본값이지만, 프로메테우스는 다른 노드의 파드에서 스크레이프를 시도하므로
연결 자체가 성립하지 않는다.

기본 설정으로 클러스터를 만들면 04장 타깃 목록에 빨간 줄이 넷 뜬다 —
controller-manager · scheduler · etcd · kube-proxy.

**손봐야 할 것 넷**

| 대상 | 고칠 값 |
|---|---|
| controller-manager | `bind-address: 0.0.0.0` |
| scheduler | `bind-address: 0.0.0.0` |
| etcd | `listen-metrics-urls: http://0.0.0.0:2381` |
| kube-proxy | `metricsBindAddress: 0.0.0.0:10249` |

**따라 하면 안 되는 것** — 인터넷 가이드 일부가 `secure-port: "0"` 으로 HTTPS 를 끄고
평문 포트를 연다. 인증 없이 내부 메트릭이 노출되고, 04장의 차트 기본값(HTTPS 스크레이프)과도 어긋난다.

**운영에서는** — `0.0.0.0` 바인딩은 노드의 모든 인터페이스에 메트릭 포트를 연다.
kind 는 도커 VM 안에 갇혀 있어 실질 노출이 없지만, 실제 노드에서는 방화벽으로 제한하거나
노드 IP 만 바인딩한다. **이 설정을 그대로 사내 클러스터로 옮기지 않는다.**

## 01-02 만든 뒤에는 못 고친다

**말할 것**

클러스터를 만든 뒤에 이 설정을 바꾸려면 컨트롤 플레인 노드에 들어가 매니페스트를 고치고
각 구성요소를 재시작해야 한다. 만들 때 파일에 스무 줄을 적어 두는 것이 **비교할 수 없이 싸다.**

포트 매핑도 같다. `extraPortMappings` 는 클러스터를 만드는 순간 결정되고 나중에 추가할 수 없다.
그래서 지금 넉넉히 뚫어 둔다 — 30080(게이트웨이) · 30300(그라파나) · 30900(프로메테우스).

**함정 — v1beta3 예제**

검색으로 나오는 대부분의 예제는 `extraArgs: {bind-address: 0.0.0.0}` 형태의 **맵**이다.
지금은 `name`/`value` **목록** 형식(v1beta4)이다. Kubernetes 1.37부터 kubeadm 이
v1beta3 설정을 아예 받지 않는다.

## 01-03 맥에서 포트가 흐르는 경로

**도판** — `figures/ch01-fig1.svg`

**말할 것**

리눅스에서는 도커 네트워크 IP 로 컨테이너에 바로 붙을 수 있다. macOS 의 도커는 경량 VM 안에서 돈다.
호스트에서 노드 컨테이너 IP(172.18.x.x)로 핑을 보내면 응답이 없다.

그래서 경로가 한 겹 더 있다 — **호스트 → VM → 노드 컨테이너 → 파드.** 네 칸을 전부 뚫어야
브라우저에서 그라파나가 열린다.

방법은 둘뿐이다. `extraPortMappings` + NodePort, 또는 `kubectl port-forward`.
이 실습은 앞쪽을 쓴다 — port-forward 는 터미널을 닫으면 끊기고 파드가 재시작하면 죽지만,
포트 매핑은 클러스터가 살아 있는 동안 유지된다. 8명이 같은 화면을 봐야 하는 자리에서는 사고가 적다.

**포트 매핑은 컨트롤 플레인에만 걸어도 된다** — NodePort 는 모든 노드에서 열리므로
파드가 worker2 에 있어도 control-plane 을 거쳐 도달한다.

**카페에서 실습한다면** — `listenAddress: "127.0.0.1"` 을 빼면 매핑이 0.0.0.0 으로 열려
같은 와이파이의 다른 기기에서 그라파나에 접근할 수 있다. 반드시 넣는다.

## 01-04 클러스터 생성과 검증

**화면** — `kind create cluster` · `kubectl get nodes` 출력의 판정 줄

**말할 것**

첫 실행은 노드 이미지(약 1GB)를 받느라 5분 이상 걸릴 수 있다. 이후에는 2분 안팎이다.

```
kubectl get nodes -o wide

NAME                STATUS   ROLES           AGE   VERSION
obs-control-plane   Ready    control-plane   96s   v1.36.1
obs-worker          Ready    <none>          82s   v1.36.1
obs-worker2         Ready    <none>          82s   v1.36.1
```

**판정** — STATUS 가 셋 다 `Ready`.

**놓치기 쉬운 줄** — 생성 마지막 줄의 `Set kubectl context to "kind-obs"`.
다른 클러스터를 쓰고 있었다면 여기서 컨텍스트가 바뀐다.

**클러스터 이름을 obs 로 고정하는 이유** — kind 는 클러스터 이름을 컨테이너 이름과
kubeconfig 컨텍스트 이름에 그대로 쓴다. 문서 전체가 `obs-control-plane` · `kind-obs` 를
전제하므로 바꾸지 않는다. 기본값(`kind`)을 쓰면 기존 실습 클러스터와 충돌한다.

**워커를 둘로 나눈 이유** — 06 · 09장에서 노드셀렉터와 노드별 메트릭 차이를 실습한다.
메모리가 12 GiB 미만이면 워커를 하나로 줄이고 라벨 두 개를 같은 노드에 붙여도 된다.
