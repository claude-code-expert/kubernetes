## 03-01 docker images 에 보여도 파드는 안 뜬다

**도판** — `figures/ch03-fig1.svg`

**말할 것**

쿠버네티스는 이미지를 레지스트리에서 받아 온다고 가정한다. 그런데 방금 로컬에서 빌드한 이미지는
어느 레지스트리에도 없다. **도커 데몬의 이미지 저장소와 kind 노드 안의 컨테이너 런타임 저장소는
서로 다른 공간이다.** `docker images` 에 보인다고 파드가 뜨지 않는다.

`kind load docker-image` 가 그 간극을 메운다 — 이미지를 노드 컨테이너 안으로 밀어 넣어
런타임이 볼 수 있게 한다.

## 03-02 적재 확인은 노드 안에서

**화면** — `crictl images` 출력 · 판정 줄

**말할 것**

적재됐는지는 **노드 안에서** 확인해야 한다. `docker images` 로는 알 수 없다.

```
docker exec obs-worker crictl images | grep obs/

docker.io/obs/gateway     0.0.1   3f2a91c4e7b8f   289MB
docker.io/obs/order-api   0.0.1   b71c05de9a12c   276MB
```

**판정** — 두 줄이 보이면 된다. 여기서 확인하고 넘어가야 뒤에서 `ImagePullBackOff` 를 만났을 때
"이미지가 없는 것"과 "정책이 잘못된 것"을 구분할 수 있다.

## 03-03 latest 를 쓰면 조용히 깨진다

**화면** — imagePullPolicy 기본값 표 · `tables/03-03-pullpolicy.tsv`

**말할 것**

태그가 `latest` 면 기본 `imagePullPolicy` 가 `Always` 가 된다. 그러면 **이미 적재해 둔 이미지를
무시하고** 레지스트리를 찾아가 `ErrImagePull` 로 떨어진다.
레지스트리가 없는 이 실습에서는 그 자체로 실패 조건이다.

그래서 모든 이미지에 버전 태그를 박는다 — `obs/order-api:0.0.1`.
코드를 고칠 때마다 0.0.2, 0.0.3 으로 올리면 **"지금 도는 파드가 어느 코드인지"** 가 명확해진다.

**매니페스트에는 `imagePullPolicy: IfNotPresent` 를 명시한다.** 기본값에 기대지 않는다.

## 03-04 프로브 세 개가 답하는 서로 다른 질문

**도판** — `figures/ch03-fig2.svg` · 표 3행 `tables/03-04-probes.tsv`

**말할 것**

| 프로브 | 묻는 것 | 실패하면 |
|---|---|---|
| **startup** | 아직 기동 중인가 | 기다린다. 다른 프로브를 미룬다 |
| **readiness** | 지금 요청을 받을 수 있나 | 서비스 엔드포인트에서 뺀다 (파드는 살려 둔다) |
| **liveness** | 살아 있나, 갇혔나 | 컨테이너를 죽이고 다시 시작한다 |

셋을 헷갈리면 사고가 난다. **기동이 느린 앱에 liveness 만 걸면** 준비되기도 전에 죽이고
다시 만들기를 반복한다 — `CrashLoopBackOff` 의 흔한 원인이다. JVM 애플리케이션은 기동이 느려서
특히 그렇다. 파드가 재시작을 반복하면 그래프도 함께 엉망이 된다.

**02장의 준비물** — `management.endpoint.health.probes.enabled: true` 를 넣었기 때문에
`/actuator/health/liveness` 와 `/readiness` 두 경로가 존재한다.

**원칙** — liveness 에는 외부 의존성 검사를 넣지 않는다.
DB 가 잠깐 끊겼다고 앱을 재시작하면 상황이 더 나빠진다.

## 03-05 이미지 크기 — Dockerfile 네 개

**화면** — 크기 비교 막대 (`gaps.figure` — 새로 그려야 함)

**말할 것**

이 실습은 빌드팩(`bootBuildImage`)을 쓴다. Dockerfile 없이 JRE 선택 · 계층 분리 ·
메모리 계산까지 알아서 한다. 결과는 order-api 276MB · gateway 289MB.

Dockerfile 로 직접 만들면 무엇이 달라지는지는 별도 예제(`docker-sample`)로 재현한다.
같은 앱을 네 가지로 빌드하면 이렇게 갈린다.

| 방식 | 크기 | 무엇이 들어 있나 |
|---|---|---|
| 한 스테이지에서 빌드까지 | **1.02GB** | JDK · 메이븐 · 소스 · 의존성 캐시 · jar |
| jar 만 복사 | 475MB | JRE · jar |
| 멀티스테이지 | **475MB** | JRE · jar (빌드는 이미지 안에서) |

**메모리 설정의 차이 (질문이 나오면)** — 빌드팩 이미지는 메모리 계산기가 컨테이너 제한을 읽어
힙 크기를 자동으로 정한다. Dockerfile 로 만들면 그 장치가 없으므로
`-XX:MaxRAMPercentage` 를 직접 줘야 한다. 안 주면 제한의 25%만 힙으로 쓰거나
반대로 제한을 넘겨 OOMKilled 로 죽는다.

**Apple Silicon** — Spring Boot 3.4부터 빌드팩이 멀티 아키텍처를 지원해 M 시리즈 맥에서는
arm64 이미지가 만들어진다. kind 노드도 arm64 이므로 맞는다.
**각자 자기 맥에서 빌드한다. 이미지 파일을 서로 주고받지 않는다.**

## 03-06 배포와 검증

**화면** — `rollout status` · `describe` 이벤트

**말할 것**

뜨지 않으면 **이벤트부터 읽는다.** `kubectl describe pod` 의 Events 절에
왜 안 뜨는지가 그대로 적혀 있다.

자주 보는 셋 —
`ImagePullBackOff`(적재 안 됨 또는 정책 Always) ·
`CrashLoopBackOff`(프로브 또는 기동 실패) ·
`Pending`(자원 부족 또는 노드셀렉터 불일치).

여기까지 통과하면 앱이 클러스터에서 돈다. 다음 장에서 그것을 관측할 스택을 올린다.
