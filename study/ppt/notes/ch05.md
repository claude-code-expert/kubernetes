## 05-01 UI 에서 만든 대시보드는 클러스터와 함께 사라진다

**도판** — `figures/ch05-fig1.svg`

**말할 것**

그라파나 UI 에서 패널을 끌어다 놓으면 대시보드가 5분 만에 만들어진다.
그 대시보드는 **그라파나의 내부 DB 에 저장되고, 클러스터를 지우면 같이 사라진다.**
이 실습은 클러스터를 자주 지우고 다시 만드는 것을 전제하므로 그 방식으로는 진도가 안 나간다.

대신 대시보드 JSON 을 컨피그맵에 담고 **라벨 하나**를 붙인다.
그라파나 사이드카가 그 라벨을 가진 컨피그맵을 찾아 대시보드로 올린다.
클러스터를 새로 만들어도 `kubectl apply` 한 번이면 돌아온다.

**구조를 보여 주면 이해가 빠르다** — 그라파나 파드가 3/3 이었던 것을 기억시킨다.
컨테이너 셋이 한 파드에 있다.

```
grafana-sc-dashboard      ← 사이드카
grafana-sc-datasources    ← 사이드카
grafana
```

앞의 둘이 쿠버네티스 API 를 지켜보다가 라벨 붙은 ConfigMap 을 발견하면
그 내용을 파일로 꺼내 공유 볼륨에 쓴다. 그라파나는 그 디렉터리를 읽을 뿐이다.

**차트가 설치한 기본 대시보드 수십 개도 전부 이 구조로 들어와 있다.**
즉 우리도 같은 방법을 쓴다. 그라파나를 재시작할 필요도, UI 에서 임포트할 필요도 없다.

## 05-02 라벨 하나를 빼면 아무 일도 일어나지 않는다

**말할 것**

**에러도 없고 이벤트도 없다.** 컨피그맵은 멀쩡히 만들어져 있고 대시보드만 안 보인다.

이 장에서 **일부러 라벨을 빼고 적용해 그 침묵을 먼저 겪는다.**
겪어 두면 나중에 "대시보드가 안 뜬다"에서 5분 안에 원인을 찾는다.

확인 명령은 하나다.

```
kubectl -n monitoring get cm -l grafana_dashboard=1 --no-headers | wc -l
```

내 컨피그맵이 이 목록에 없으면 라벨이 빠진 것이다.
사이드카 로그(`kubectl logs ... -c grafana-sc-dashboard`)에도 반영 과정이 그대로 남는다.

**같은 함정이 세 번 나온다** — 04장의 ServiceMonitor `release` 라벨,
여기 대시보드 `grafana_dashboard`, 07장의 PrometheusRule `release` 라벨.
전부 **라벨이 없으면 조용히 무시된다.**

## 05-03 데이터소스는 uid 로 참조한다

**도판** — `figures/ch05-fig2.svg` · JSON 발췌 3줄

**말할 것**

대시보드 JSON 안에서 데이터소스를 **이름**(`Prometheus`)으로 적으면 환경에 따라 깨진다.
스택이 만드는 데이터소스의 **uid** 를 확인해 그것으로 참조해야
다른 클러스터에서도 같은 JSON 이 그대로 뜬다.

**현실적인 작업 순서** — 처음부터 JSON 을 손으로 쓰는 것은 비효율적이다.
**UI 에서 원하는 패널을 만들고 Export 로 JSON 을 받아 컨피그맵에 넣는다.**
이 장은 그 왕복을 한 번 돌려 본다.

**Export 옵션 하나 주의** — `Export for sharing externally` 를 켜면
데이터소스가 `${DS_...}` 변수로 치환된다. 팀 밖으로 공유할 때만 쓰고,
우리끼리 쓸 때는 끄고 내보낸다.

**아직 우리 앱의 지표는 없다** — 지금 보이는 기본 대시보드는 컨테이너 관점의 자원 사용량이다.
"주문 API 가 초당 몇 건을 처리하고 P99 가 몇 ms 인가"는 아직 어디에도 없다.
그 데이터를 만들려면 06장에서 ServiceMonitor 를 붙여야 한다.
