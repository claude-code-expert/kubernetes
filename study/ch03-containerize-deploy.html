쿠버네티스 관측성
212

02장에서 만든 두 앱을 이미지로 굽고 kind 클러스터에 올린다. 레지스트리는 쓰지 않는다. 여기서 정하는 라벨과 포트 이름이 06장 스크레이프의 조건이 된다.

01왜 이 장이 필요한가

02장의 앱은 맥에서 돌았다. 클러스터에는 아직 아무것도 없다. 그리고 로컬에서 도는 것과 클러스터에서 도는 것 사이에는 세 가지 새로운 문제가 있다.

첫째, 이미지가 노드에 없다. 쿠버네티스는 이미지를 레지스트리에서 받아 온다고 가정하는데, 방금 빌드한 이미지는 어느 레지스트리에도 없다. 둘째, 언제 트래픽을 보내도 되는지를 쿠버네티스가 알아야 한다. JVM (Java Virtual Machine · 자바 가상 머신) 앱은 기동이 느려서 이것을 잘못 설정하면 파드가 재시작을 반복한다. 셋째, 어느 노드에 둘 것인가를 정해야 한다. 01장에서 라벨을 붙여 둔 이유가 여기서 나온다.

그리고 하나 더 — 여기서 정하는 서비스의 라벨과 포트 이름이 06장 ServiceMonitor 의 선택 조건이 된다. 매니페스트를 그냥 복사하지 말고 라벨이 어디에 걸리는지만큼은 눈으로 따라간다.

02알아야 할 개념

이미지 저장소가 두 곳이다

맥의 도커 데몬이 가진 이미지 목록과, kind 노드 컨테이너 안쪽 런타임이 가진 목록은 서로 다른 공간이다. docker images 에 보인다고 파드가 뜨지 않는다.

kind load docker-image 가 그 간극을 메운다. 이미지를 노드 컨테이너 안으로 밀어 넣어 런타임이 볼 수 있게 한다. 적재됐는지는 노드 안에서 crictl images 로 확인해야 하고, docker images 로는 알 수 없다.

latest 를 쓰면 여기서 조용히 깨진다

태그가 latest 면 imagePullPolicy 기본값이 Always 가 되어, 이미 적재해 둔 이미지를 무시하고 레지스트리를 찾아가 ErrImagePull 로 떨어진다. 이 실습은 모든 이미지에 버전 태그를 박는다. 10절에서 실제로 그 에러를 만들어 본다.

프로브 세 개가 각각 답하는 질문

프로브답하는 질문실패하면
startupProbe아직 시작 중인가다른 두 프로브를 미룬다. 느린 JVM 기동을 감싸는 용도
readinessProbe지금 트래픽을 받아도 되나서비스 엔드포인트에서 빠진다. 파드는 살아 있다
livenessProbe살아 있나컨테이너를 죽이고 다시 만든다

셋을 헷갈리면 사고가 난다. 기동이 느린 앱에 liveness 만 걸면 준비되기도 전에 죽이고 다시 만들기를 반복한다 — CrashLoopBackOff 의 흔한 원인이다. liveness 에는 외부 의존성 검사를 넣지 않는 것이 원칙이다. DB 가 잠깐 끊겼다고 앱을 재시작하면 상황이 더 나빠진다.

같은 라벨이 네 자리에 쓰인다

app.kubernetes.io/name 은 ① Deployment 셀렉터, ② 파드 라벨, ③ Service 셀렉터, ④ Service 자신의 라벨에 각각 쓰인다. 앞의 셋은 파드를 묶기 위한 것이고, ④번만 역할이 다르다 — 06장 ServiceMonitor 가 서비스를 찾기 위한 것이다. 값이 같더라도 네 곳에 각각 써야 한다.

자원 요청과 제한

requests 는 스케줄러가 “이 파드를 놓을 자리가 있는가”를 계산할 때 쓰는 값이고, limits 는 실제 사용 상한이다. 이 실습은 메모리만 제한하고 CPU (Central Processing Unit · 중앙처리장치) 는 제한하지 않는다. 이유는 08절 매니페스트에서 설명한다.

이 장을 마치면 할 수 있는 것

  1. 레지스트리 없이 이미지를 노드에 적재하고, 적재됐는지 crictl images 로 판정할 수 있다.
  2. 프로브 세 개를 시간 구간으로 나눠 걸고, CrashLoopBackOff 가 프로브 때문인지 구분할 수 있다.
  3. 노드셀렉터로 파드를 의도한 노드에 모으고, Pending 의 이유를 이벤트에서 읽을 수 있다.
  4. 서비스의 라벨과 포트 이름을 06장이 쓸 형태로 맞출 수 있다.
  5. 코드를 고쳤을 때 태그를 올려 재배포하는 루틴을 한 번에 실행할 수 있다.

03최종적으로 만들 것

이 장이 끝나면 파드 3개(order-api 2개 · gateway 1개)가 obs-worker 에서 돌고, 맥의 localhost:30080 으로 주문이 생성된다. 그리고 /actuator/prometheus 가 클러스터 안에서 열려 있다 — 04장 프로메테우스가 긁어 갈 대상이 준비된 상태다.

이미지가 파드가 되기까지

  • 1 맥에 이미지가 생겼는지. 아직 클러스터와는 무관하다. 확인 docker images | grep '^obs/' → obs/order-api · obs/gateway 두 줄
  • 2 노드 안까지 들어갔는지. docker images 로는 알 수 없다. 노드 안의 런타임에 물어야 한다. 확인 docker exec obs-worker crictl images | grep obs/ → docker.io/obs/order-api 0.0.1
  • 3 파드가 의도한 노드에 떴는지. 셋 다 obs-worker 여야 한다. 확인 kubectl -n apps get pods -o wide → 1/1 Running 세 줄, NODE 열이 전부 obs-worker

WHY이 배치를 만드는 설정 — image · imagePullPolicy · nodeSelector

그림의 파드가 가운데 상자에만 있는 것도, 레지스트리를 찾아가지 않는 것도 매니페스트 세 줄이 정한다.

study/labs/k8s/10-order-api.yaml — 배치와 이미지를 정하는 부분 
spec:
  template:
    spec:
      # 01장에서 노드에 붙여 둔 라벨. 이 줄이 그림의 가운데 상자를 고른다.
      nodeSelector:
        workload: apps
      containers:
        - name: order-api
          image: obs/order-api:0.0.1     # 태그를 박는다. latest 를 쓰지 않는다
          # 레지스트리가 없으므로 반드시 IfNotPresent
          imagePullPolicy: IfNotPresent
          ports:
            # 이 포트 '이름'을 06장 ServiceMonitor 가 참조한다
            - name: http
              containerPort: 8080
설정그림의 무엇을 만드나빠지거나 틀리면
nodeSelector: workload: apps파드가 가운데 상자에만 뜬다워커 두 대에 흩어진다. 라벨이 없는 노드뿐이면 Pending
image: ...:0.0.1적재해 둔 이미지와 이름·태그가 일치철자가 다르면 ErrImagePull
imagePullPolicy: IfNotPresent레지스트리로 나가지 않는다Always 면 노드에 있어도 받으러 나간다
ports.name: http—06장 ServiceMonitor 가 포트를 못 찾는다
컨트롤 플레인에 앱이 뜨지 않는 이유

노드셀렉터를 빼도 컨트롤 플레인에는 앱이 뜨지 않는다. kubeadm 이 그 노드에 node-role.kubernetes.io/control-plane:NoSchedule 테인트를 걸어 두기 때문이다. 이미지는 세 노드 모두에 적재되지만 파드는 워커에만 뜬다.

프로브 세 개가 맡는 시간 구간

  • 1 기동이 끝났는지. 롤아웃이 끝날 때까지 기다린다. 확인 kubectl -n apps rollout status deploy/order-api --timeout=180s → successfully rolled out
  • 2 트래픽을 받을 준비가 됐는지. READY 가 1/1 이라는 것이 readiness 통과의 뜻이다. 확인 kubectl -n apps get pods → READY 1/1, RESTARTS 0
  • 3 재시작이 없는지. 숫자가 늘고 있으면 liveness 가 기동을 못 기다린 것이다. 확인 kubectl -n apps get pods -w → RESTARTS 가 계속 0

WHY구간을 나누는 설정 — failureThreshold × periodSeconds

study/labs/k8s/10-order-api.yaml — 프로브 세 개 
startupProbe:
  httpGet:
    path: /actuator/health/liveness
    port: http
  periodSeconds: 2          # 2초마다
  failureThreshold: 30      # 30번까지 봐준다 = 최대 60초
readinessProbe:
  httpGet:
    path: /actuator/health/readiness    # liveness 와 경로가 다르다
    port: http
  periodSeconds: 5
  failureThreshold: 3
livenessProbe:
  httpGet:
    path: /actuator/health/liveness
    port: http
  periodSeconds: 10
  failureThreshold: 3
값계산의미
startup 2s × 30최대 60초이 안에 기동이 끝나야 한다. JVM 기동이 8초 내외이므로 여유가 크다
readiness 5s × 315초15초 연속 실패하면 트래픽에서 뺀다
liveness 10s × 330초30초 연속 실패해야 재시작한다. 짧게 잡으면 사고가 난다
경로가 두 개인 이유

02장에서 management.endpoint.health.probes.enabled: true 를 넣었기 때문에 /actuator/health/liveness 와 /readiness 두 경로가 생겼다. liveness 는 “프로세스가 살아 있나”만 보고, readiness 는 “의존성까지 준비됐나”를 본다. 이 구분이 없으면 두 프로브가 같은 것을 보게 되어 프로브를 나눈 의미가 사라진다.

05이미지 빌드 — 빌드팩

목적: Dockerfile 없이 이미지를 만든다. 빌드팩이 JRE (Java Runtime Environment · 자바 실행 환경) 선택 · 계층 분리 · 메모리 계산까지 한다.

study/labs/apps/order-api/build.gradle — 파일 끝에 추가 
tasks.named('bootBuildImage') {
    imageName = "obs/order-api:0.0.1"
    // 최신 우분투 LTS 기반, 자바 관련 버트팩만 담은 빌더
    builder = "paketobuildpacks/builder-noble-java-tiny:latest"
    environment = [
        "BP_JVM_VERSION": "21",
        "BP_JVM_TYPE": "JRE",
        // 서비스 바인딩을 쓰지 않으므로 불필요한 jar 주입을 끈다
        "BP_SPRING_CLOUD_BINDINGS_DISABLED": "true"
    ]
}

gateway 프로젝트에도 같은 블록을 넣고 imageName 만 obs/gateway:0.0.1 로 바꾼다.

cd study/labs/apps/order-api && ./gradlew bootBuildImage
cd ../gateway && ./gradlew bootBuildImage

docker images | grep '^obs/'

빌더 태그의 latest 는 예외다

위 builder 값에만 latest 가 있다. 이것은 실행되는 이미지가 아니라 빌드 도구이고, 결과물에는 포함되지 않는다. 배포되는 이미지(imageName)에는 예외 없이 버전 태그를 박는다. 사내 파이프라인이라면 빌더도 다이제스트로 고정하는 편이 낫다.

태그를 올려 가며 쓰는 이유

코드를 고칠 때마다 0.0.2, 0.0.3 으로 올리면 “지금 도는 파드가 어느 코드인지”가 명확해진다. 같은 태그를 덮어쓰면 새 이미지가 반영될 때도, 캐시된 옛 이미지가 뜰 때도 있어 원인을 찾느라 시간을 버린다.

Apple Silicon

Spring Boot 3.4 부터 빌드팩이 멀티 아키텍처를 지원해 M 시리즈 맥에서는 arm64 이미지가 만들어진다. kind 노드도 arm64 이므로 그대로 맞는다. 문제는 인텔 맥과 섞였을 때인데, 각자 자기 맥에서 빌드하면 된다. 이미지 파일을 서로 주고받지 않는다.

06이미지 빌드 — Dockerfile (대안)

사내 파이프라인이 Dockerfile 기반이라면 이쪽을 쓴다. 계층 분리를 직접 해야 한다.

study/labs/apps/order-api/Dockerfile 
FROM eclipse-temurin:21-jdk AS builder
WORKDIR /build
COPY . .
RUN ./gradlew bootJar --no-daemon
RUN cp build/libs/*.jar app.jar \
 && java -Djarmode=tools -jar app.jar extract --layers --launcher --destination extracted

FROM eclipse-temurin:21-jre
WORKDIR /app
RUN useradd -u 1000 -m app
USER 1000
COPY --from=builder /build/extracted/dependencies/ ./
COPY --from=builder /build/extracted/spring-boot-loader/ ./
COPY --from=builder /build/extracted/snapshot-dependencies/ ./
COPY --from=builder /build/extracted/application/ ./
ENV JAVA_TOOL_OPTIONS="-XX:MaxRAMPercentage=70.0"
ENTRYPOINT ["java", "org.springframework.boot.loader.launch.JarLauncher"]
cd study/labs/apps/order-api
docker build -t obs/order-api:0.0.1 .
줄왜 그렇게 쓰나
COPY --from=builder .../dependencies/ 를 네 번의존성 · 로더 · 스냅숏 · 애플리케이션 순으로 나눠 넣는다. 코드만 고치면 마지막 계층만 다시 만들어져 빌드가 빨라진다
useradd -u 1000 + USER 1000숫자 UID (User Identifier · 사용자를 가리키는 숫자 식별자) 로 지정한다. 이름으로 지정하면 kubelet 이 runAsNonRoot 를 검증하지 못해 파드가 뜨지 않는다
MaxRAMPercentage=70.0JVM 이 컨테이너 메모리 제한의 70% 까지만 힙으로 쓰게 한다
jarmode 옵션이 바뀌었다

-Djarmode=layertools 는 Spring Boot 3.3 에서 폐기 예고됐고 4.x 에서 제거 수순이다. 현재 형태는 -Djarmode=tools ... extract --layers --launcher 이며, --layers 와 --launcher 를 명시해야 예전과 같은 결과가 나온다. 계층 디렉터리 이름이 헷갈리면 java -Djarmode=tools -jar app.jar list-layers 로 확인한다.

메모리 설정의 차이

빌드팩 이미지는 메모리 계산기가 컨테이너 제한을 읽어 힙 크기를 자동으로 정한다. Dockerfile 로 직접 만들면 그 장치가 없으므로 -XX:MaxRAMPercentage 를 직접 줘야 한다. 주지 않으면 JVM 이 제한의 25% 만 힙으로 쓰거나, 반대로 제한을 넘겨 OOMKilled 로 죽는다.

CPU limit 을 두지 않은 것은 의도된 선택이다

CPU 제한을 걸면 쿠버네티스는 CFS (Completely Fair Scheduler · 리눅스의 CPU 스케줄러. 제한을 넘으면 스로틀링한다) 쿼터로 스로틀링을 건다. 그러면 응답 시간 그래프에 애플리케이션과 무관한 톱니가 생기고, 06~07장에서 “이 지연이 코드 때문인가 스로틀링 때문인가”를 구분할 수 없게 된다. 메모리는 제한한다 — 압축 불가능한 자원이라 제한이 없으면 노드 전체가 위험해진다. 다만 이 판단은 실습 환경 기준이다. 공용 클러스터라면 CPU 제한이 필요하다.

더 조일 수 있는 것 — readOnlyRootFilesystem

운영 환경이라면 readOnlyRootFilesystem: true 를 추가한다. 다만 톰캣이 임시 디렉터리를 쓰므로 /tmp 에 emptyDir 볼륨을 붙여야 하고, 빌드팩 이미지는 쓰기 가능한 경로를 추가로 요구할 수 있다. 실습에서는 원인 파악에 시간이 새는 것을 피하려고 넣지 않았다.

10일부러 실패시키기 — 파드가 안 뜨는 두 가지 이유

배포가 실패하는 대부분은 이미지를 못 찾거나, 놓을 노드를 못 찾거나 둘 중 하나다. 두 경우 모두 kubectl get pods 의 STATUS 만으로는 부족하고 이벤트를 읽어야 한다. 실제로 만들어 본다.

11코드를 고쳤을 때의 재배포 루틴

#!/usr/bin/env bash
# 사용법: ./redeploy.sh order-api 0.0.2
set -euo pipefail

APP="${1:?앱 이름을 지정하세요 (order-api | gateway)}"
TAG="${2:?태그를 지정하세요 (예: 0.0.2)}"
IMAGE="obs/${APP}:${TAG}"

cd "$(dirname "$0")/${APP}"
./gradlew bootBuildImage --imageName="${IMAGE}"

kind load docker-image "${IMAGE}" --name obs

kubectl -n apps set image "deploy/${APP}" "${APP}=${IMAGE}"
kubectl -n apps rollout status "deploy/${APP}" --timeout=180s

echo "완료: ${IMAGE}"
chmod +x study/labs/apps/redeploy.sh
study/labs/apps/redeploy.sh order-api 0.0.2

docker build -t obs/order-api:0.0.1 .Dockerfile 방식(대안). 태그를 반드시 박는다
kind load docker-image obs/order-api:0.0.1 --name obs노드 안으로 이미지 적재. 이것 없이는 ErrImagePull
docker exec obs-worker crictl images노드 안 런타임 저장소 확인. docker images 로는 알 수 없다
kubectl apply -f k8s/네임스페이스·디플로이먼트·서비스를 한 번에
kubectl -n apps rollout status deploy/order-api롤아웃 완료까지 대기. 실패하면 0이 아닌 종료 코드
kubectl -n apps get pods -o wide어느 노드에 떴는지 확인
kubectl -n apps describe pod <파드>뜨지 않을 때 이벤트부터 읽는다
kubectl -n apps get endpointslices서비스가 실제로 어느 파드 IP 로 보내는지
kubectl -n apps port-forward svc/order-api 18080:8080클러스터 안 서비스를 맥의 포트로 잠시 끌어온다
kubectl -n apps set image deploy/order-api order-api=obs/order-api:0.0.2이미지 태그만 바꿔 롤링 업데이트
