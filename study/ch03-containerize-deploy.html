01이론 — 이미지가 클러스터에 닿는 경로

레지스트리 없이 — 로컬에서 만든 이미지를 kind 노드가 어떻게 보는가.

쿠버네티스는 이미지를 레지스트리에서 받아 온다고 가정한다. 그런데 방금 로컬에서 빌드한 이미지는 어느 레지스트리에도 없다. 도커 데몬의 이미지 저장소와 kind 노드 안의 컨테이너 런타임 저장소는 서로 다른 공간이라, docker images에 보인다고 파드가 뜨지는 않는다.

kind load docker-image가 그 간극을 메운다. 이미지를 노드 컨테이너 안으로 밀어 넣어 런타임이 볼 수 있게 한다. 적재됐는지는 노드 안에서 crictl images로 확인해야 하고, docker images로는 알 수 없다.

latest 를 쓰면 여기서 조용히 깨진다

태그가 latest면 기본 imagePullPolicy가 Always가 되어, 이미 적재해 둔 이미지를 무시하고 레지스트리를 찾아가 ErrImagePull로 떨어진다. 이 실습은 모든 이미지에 버전 태그를 박는다.

프로브 세 개가 각각 답하는 질문

프로브답하는 질문실패하면
startup아직 시작 중인가다른 두 프로브를 미룬다. 느린 JVM 기동을 감싸는 용도
readiness지금 트래픽을 받아도 되나서비스 엔드포인트에서 빠진다. 파드는 살아 있다
liveness살아 있나컨테이너를 죽이고 다시 만든다

셋을 헷갈리면 사고가 난다. 기동이 느린 앱에 liveness만 걸면 준비되기도 전에 죽이고 다시 만들기를 반복한다 — CrashLoopBackOff의 흔한 원인이다.

02레지스트리 없이 배포하는 경로

쿠버네티스는 이미지를 레지스트리에서 받아옵니다. 그런데 로컬에서 방금 만든 이미지는 어느 레지스트리에도 없습니다. kind는 이 문제를 노드 컨테이너의 이미지 저장소에 직접 밀어 넣는 방식으로 해결합니다.

03이미지 빌드 — 빌드팩

Dockerfile 없이 bootBuildImage 한 번으로 끝냅니다. 빌드팩이 JRE 선택, 계층 분리, 메모리 계산까지 알아서 합니다.

apps/order-api/build.gradle — 파일 끝에 추가

tasks.named('bootBuildImage') {
    imageName = "obs/order-api:0.0.1"
    // 최신 우분투 LTS 기반, 자바 관련 버트팩만 담은 빌더
    builder = "paketobuildpacks/builder-noble-java-tiny:latest"
    environment = [
        "BP_JVM_VERSION": "21",
        "BP_JVM_TYPE": "JRE",
        // 서비스 바인딩을 쓰지 않으므로 불필요한 jar 주입을 끈다
        "BP_SPRING_CLOUD_BINDINGS_DISABLED": "true"
    ]
}

gateway 프로젝트에도 같은 블록을 넣고 imageName만 obs/gateway:0.0.1로 바꿉니다. 

cd ~/k8s-observability/apps/order-api && ./gradlew bootBuildImage
cd ../gateway && ./gradlew bootBuildImage

docker images | grep '^obs/'
obs/gateway     0.0.1   3f2a91c4e7b8   ...   289MB
obs/order-api   0.0.1   b71c05de9a12   ...   276MB
태그에 latest를 쓰지 않는 이유

latest는 imagePullPolicy의 기본값을 Always로 바꿉니다. 레지스트리가 없는 이 실습에서는 그 자체로 실패 조건입니다. 또한 코드를 고칠 때마다 0.0.2, 0.0.3으로 올려야 "지금 도는 파드가 어느 코드인지"가 명확해집니다.

Apple Silicon

Spring Boot 3.4부터 빌드팩이 멀티 아키텍처를 지원해, M 시리즈 맥에서는 arm64 이미지가 만들어집니다. kind 노드도 arm64이므로 그대로 맞습니다. 문제는 인텔 맥과 섞였을 때인데, 각자 자기 맥에서 빌드하면 됩니다. 이미지 파일을 서로 주고받지 마세요.

04이미지 빌드 — Dockerfile(대안)

사내 파이프라인이 Dockerfile 기반이라면 이쪽을 쓰세요. 계층 분리를 직접 해야 합니다.

apps/order-api/Dockerfile

FROM eclipse-temurin:21-jdk AS builder
WORKDIR /build
COPY . .
RUN ./gradlew bootJar --no-daemon
RUN cp build/libs/*.jar app.jar \
 && java -Djarmode=tools -jar app.jar extract --layers --launcher --destination extracted

FROM eclipse-temurin:21-jre
WORKDIR /app
RUN useradd -u 1000 -m app
USER 1000
COPY --from=builder /build/extracted/dependencies/ ./
COPY --from=builder /build/extracted/spring-boot-loader/ ./
COPY --from=builder /build/extracted/snapshot-dependencies/ ./
COPY --from=builder /build/extracted/application/ ./
ENV JAVA_TOOL_OPTIONS="-XX:MaxRAMPercentage=70.0"
ENTRYPOINT ["java", "org.springframework.boot.loader.launch.JarLauncher"]
jarmode 옵션이 바뀌었다

-Djarmode=layertools는 Spring Boot 3.3에서 폐기 예고됐고 4.x에서 제거 수순입니다. 현재 형태는 -Djarmode=tools ... extract --layers --launcher이며, --layers와 --launcher를 명시해야 예전과 같은 결과가 나옵니다. 계층 디렉터리 이름이 헷갈리면 java -Djarmode=tools -jar app.jar list-layers로 확인하세요.

메모리 설정의 차이

빌드팩 이미지는 메모리 계산기가 컨테이너 제한을 읽어 힙 크기를 자동으로 정합니다. Dockerfile로 직접 만들면 그 장치가 없으므로 -XX:MaxRAMPercentage를 직접 줘야 합니다. 주지 않으면 JVM이 제한의 25%만 힙으로 쓰거나, 반대로 제한을 넘겨 OOMKilled로 죽습니다.

06프로브 세 개의 역할

매니페스트를 쓰기 전에 이것부터 정리합니다. 프로브를 잘못 걸면 관측 실습 내내 파드가 재시작을 반복해 그래프가 엉망이 됩니다. JVM 애플리케이션은 기동이 느려서 특히 그렇습니다.

프로브액추에이터 경로실패했을 때
startupProbe/actuator/health/liveness재시도. 한계를 넘으면 재시작
readinessProbe/actuator/health/readiness서비스에서 제외(트래픽 차단)
livenessProbe/actuator/health/liveness컨테이너 재시작

02단계에서 management.endpoint.health.probes.enabled: true를 넣었기 때문에 이 두 경로가 존재합니다. liveness에는 외부 의존성 검사를 넣지 않는 것이 원칙입니다. DB가 잠깐 끊겼다고 앱을 재시작하면 상황이 더 나빠지기 때문입니다.

라벨을 세 곳에 똑같이 쓰는 이유

app.kubernetes.io/name은 ① Deployment 셀렉터, ② 파드 라벨, ③ Service 셀렉터, ④ Service 자신의 라벨에 각각 쓰입니다. 앞의 셋은 파드를 묶기 위한 것이고, ④번은 06단계의 ServiceMonitor가 서비스를 찾기 위한 것입니다. 역할이 다르므로 값이 같더라도 각각 써야 합니다.

CPU limit을 두지 않은 것은 의도된 선택이다

CPU 제한을 걸면 쿠버네티스는 CFS 쿼터로 스로틀링을 겁니다. 그러면 응답 시간 그래프에 애플리케이션과 무관한 톱니가 생기고, 06~07단계에서 "이 지연이 코드 때문인가 스로틀링 때문인가"를 구분할 수 없게 됩니다. 메모리는 제한합니다. 메모리는 압축 불가능한 자원이라 제한이 없으면 노드 전체가 위험해집니다. 다만 이 판단은 실습 환경 기준입니다. 공용 클러스터라면 CPU 제한이 필요합니다.

더 조일 수 있는 것 — readOnlyRootFilesystem

운영 환경이라면 readOnlyRootFilesystem: true를 추가합니다. 다만 톰캣이 임시 디렉터리를 쓰므로 /tmp에 emptyDir 볼륨을 붙여야 하고, 빌드팩 이미지는 쓰기 가능한 경로를 추가로 요구할 수 있습니다. 실습에서는 원인 파악에 시간이 새는 것을 피하려고 넣지 않았습니다.

셋 다 obs-worker에 있어야 합니다. obs-worker2에 떴다면 노드셀렉터가 빠진 것이고, Pending이면 라벨이 안 붙었거나 자원이 모자란 것입니다. kubectl -n apps describe pod <이름>의 Events를 보세요.

2. 브라우저에서 접근되는가

curl -s -X POST http://localhost:30080/api/orders \
  -H 'Content-Type: application/json' \
  -d '{"item":"latte","quantity":3}' | python3 -m json.tool

01단계에서 hostPort: 30080을 control-plane 노드에 뚫어뒀고, 서비스의 nodePort가 30080이라 맥의 localhost:30080이 그대로 게이트웨이에 닿습니다. 파드가 다른 노드에 있어도 동작합니다.

3. 서비스 DNS로 서로를 찾는가

kubectl -n apps exec deploy/gateway -- \
  curl -s -o /dev/null -w '%{http_code}\n' \
  http://order-api.apps.svc.cluster.local:8080/actuator/health

200이 나와야 합니다. 빌드팩 이미지에 curl이 없어 실패하면 kubectl -n apps logs deploy/gateway로 라우팅 오류가 없는지 확인하는 것으로 대체하세요.

4. 메트릭 엔드포인트가 클러스터 안에서 열려 있는가

kubectl -n apps port-forward svc/order-api 18080:8080 >/dev/null 2>&1 &
sleep 2
curl -s http://localhost:18080/actuator/prometheus | grep -c '^orders_'
curl -s http://localhost:18080/actuator/prometheus | grep -c 'http_server_requests_seconds_bucket'
kill %1

두 숫자 모두 0보다 커야 합니다. 이것이 04단계 진입 조건입니다. 여기서 0이면 프로메테우스를 설치해도 앱 메트릭은 보이지 않습니다.

5. 부하를 넣어 그래프의 재료를 만든다

for i in $(seq 1 100); do
  curl -s -o /dev/null -X POST http://localhost:30080/api/orders \
    -H 'Content-Type: application/json' \
    -d '{"item":"latte","quantity":3}'
done

for i in $(seq 1 20); do
  curl -s -o /dev/null "http://localhost:30080/api/chaos/error?rate=0.3"
done

09코드를 고쳤을 때의 재배포 루틴

이 시리즈에서 앱을 여러 번 고치게 됩니다. 매번 반복할 절차를 스크립트로 만들어 두세요.

apps/redeploy.sh

#!/usr/bin/env bash
# 사용법: ./redeploy.sh order-api 0.0.2
set -euo pipefail

APP="${1:?앱 이름을 지정하세요 (order-api | gateway)}"
TAG="${2:?태그를 지정하세요 (예: 0.0.2)}"
IMAGE="obs/${APP}:${TAG}"

cd "$(dirname "$0")/${APP}"
./gradlew bootBuildImage --imageName="${IMAGE}"

kind load docker-image "${IMAGE}" --name obs

kubectl -n apps set image "deploy/${APP}" "${APP}=${IMAGE}"
kubectl -n apps rollout status "deploy/${APP}" --timeout=180s

echo "완료: ${IMAGE}"
chmod +x ~/k8s-observability/apps/redeploy.sh
~/k8s-observability/apps/redeploy.sh order-api 0.0.2
태그를 그대로 두고 rollout restart 하면

같은 태그로 이미지를 다시 적재한 뒤 kubectl rollout restart를 하면 새 이미지가 반영될 때도, 캐시된 옛 이미지가 그대로 뜰 때도 있습니다. 원인을 찾느라 30분을 쓰는 대신 태그를 올리세요. 위 스크립트가 태그를 필수 인자로 받는 이유입니다.

10자주 겪는 문제

증상원인과 조치
ErrImagePull / ImagePullBackOff kind load를 하지 않았거나 imagePullPolicy가 Always다. 태그에 latest를 썼는지도 확인
CreateContainerConfigError 와 함께 image has non-numeric user runAsNonRoot: true만 쓰고 runAsUser를 생략했을 때, 이미지의 USER가 이름(예: cnb)이면 kubelet이 검증하지 못한다. runAsUser: 1000을 명시하면 해결된다
파드가 Pending 노드셀렉터에 맞는 노드가 없거나 자원 부족. kubectl -n apps describe pod의 Events에 이유가 그대로 나온다
CrashLoopBackOff, 로그는 정상 기동 중 livenessProbe가 기동을 기다려주지 못했다. startupProbe의 failureThreshold × periodSeconds가 기동 시간보다 긴지 확인
OOMKilled (Exit Code 137) 메모리 제한 대비 힙이 크다. 빌드팩 이미지가 아니면 -XX:MaxRAMPercentage를 70 이하로 주거나 limit을 올린다
localhost:30080이 응답 없음 서비스의 nodePort와 01단계 hostPort가 어긋났다. kubectl -n apps get svc gateway로 실제 값 확인
게이트웨이가 502 / 503 ORDER_API_URI의 서비스 이름·네임스페이스 오타. kubectl -n apps get endpoints order-api에 파드 IP가 있는지도 확인
메트릭에 _bucket이 없음 02단계 application.yml이 이미지에 반영되지 않았다. 태그를 올려 다시 빌드
2026년에 알아두면 좋은 것

쿠버네티스 1.35에서 In-Place Pod Resize가 정식 기능이 됐습니다. 파드를 재시작하지 않고 CPU·메모리 요청과 제한을 바꿀 수 있다는 뜻입니다. 10단계에서 자원 튜닝을 다룰 때, 예전처럼 재배포하지 않고 조정하는 방법을 함께 봅니다.

11완료 체크리스트

  • kubectl -n apps get pods 에서 파드 3개가 모두 1/1 Running, 재시작 0회
  • 세 파드 모두 obs-worker 노드에 배치됐다
  • localhost:30080 으로 주문 생성이 201로 응답한다
  • 포트포워드로 /actuator/prometheus 에서 orders_ 메트릭이 보인다
  • http_server_requests_seconds_bucket 이 0개가 아니다
  • Service order-api·gateway 에 app.kubernetes.io/name 라벨이 붙어 있다
  • 두 Service의 포트 이름이 http 다
  • redeploy.sh 로 태그를 올려 재배포하는 흐름을 한 번 실행해 봤다

이 장에서 쓴 명령만 모았다. 전체 목록은 kubectl 치트시트에 있다.

명령하는 일

kind load docker-image obs/order-api:0.0.1 --name obs노드 안으로 이미지 적재. 이것 없이는 ErrImagePull
docker exec obs-worker crictl images노드 안 런타임 저장소 확인. docker images 로는 알 수 없다
kubectl apply -f k8s/네임스페이스·디플로이먼트·서비스를 한 번에
kubectl -n apps rollout status deploy/order-api롤아웃 완료까지 대기. 실패하면 0이 아닌 코드
