01이론 — 메트릭의 세 출처

책 3.4 · 3.5 — “메모리 사용량이 왜 두 군데서 다르게 나오나”에서 헤매지 않으려면.

쿠버네티스에서 메트릭이 나오는 곳은 하나가 아니다. 셋을 말로 구분하려 하지 말고, 각각을 직접 질의해서 나온 메트릭 이름으로 구분하는 것이 이 장의 실습이다.

출처무엇을 보나배치
cAdvisor컨테이너의 실제 자원 사용. 모든 컨테이너 메트릭의 진실 공급원이며 kubelet에 내장돼 있다노드마다
metrics-server리소스 메트릭 API의 구현체. kubectl top과 HPA가 소비한다클러스터에 하나
node-exporter기계의 상태 — 이 노드의 메모리가 몇 바이트 남았는가노드마다 (DaemonSet)
kube-state-metricsAPI 서버가 아는 상태 — 레플리카 3개를 원하는데 실제로는 2개인가클러스터에 하나
metrics-server 는 장기 저장을 하지 않는다

“10분 전 CPU는?”에 답하지 못한다. 그 답을 하려고 프로메테우스를 설치하는 것이다. 전임자 힙스터(Heapster)가 데이터 싱크 설계 문제로 사용 중단됐고, 리소스 메트릭 API를 집계 API로 표준화하면서 지금 형태가 됐다.

오퍼레이터는 스크레이프하지 않는다

차트 하나를 설치하면 프로메테우스 오퍼레이터, 프로메테우스 본체, 알림매니저, 그라파나, node-exporter, kube-state-metrics가 함께 들어온다. 여기서 역할을 헷갈리기 쉽다 — 오퍼레이터는 메트릭을 긁지 않는다. 오퍼레이터가 하는 일은 ServiceMonitor 같은 커스텀 리소스를 읽어 프로메테우스의 설정 파일을 만들어 주는 것뿐이고, 실제 스크레이프는 프로메테우스 본체가 한다.

06장에서 ServiceMonitor를 만들었는데 타깃이 안 잡히는 상황을 만들 때, 어느 쪽을 봐야 하는지가 이 구분에서 갈린다.

계층적으로 본다

책이 권하는 순서는 노드 → 클러스터 구성요소 → 애드온 → 애플리케이션이다. 파드가 자꾸 대기 상태에 빠지면 먼저 노드 자원을 보고, 문제없으면 스케줄러를, 그다음 애플리케이션을 본다. 순서를 뒤집으면 앱 로그만 하루 종일 보게 된다.

02차트 하나로 무엇이 설치되나

구성요소형태하는 일
Prometheus OperatorDeploymentCRD를 감시해 프로메테우스 설정을 대신 써준다
PrometheusStatefulSet실제로 스크레이프하고 시계열을 저장한다
AlertmanagerStatefulSet발생한 알림을 묶고 라우팅한다 (07단계)
GrafanaDeployment시각화. 기본 대시보드 수십 개가 함께 온다 (05단계)
node-exporterDaemonSet노드의 CPU·메모리·디스크·네트워크 지표
kube-state-metricsDeployment디플로이먼트 레플리카 수, 파드 상태 등 오브젝트 지표
CRD 8종CustomResourceDefinitionServiceMonitor, PrometheusRule 등
PrometheusRule 다수CR클러스터 기본 알림 규칙 세트
node-exporter와 kube-state-metrics의 차이

이름이 비슷해 자주 헷갈립니다. node-exporter는 기계의 상태를 봅니다 — 이 노드의 메모리가 몇 바이트 남았는가. kube-state-metrics는 API 서버가 아는 상태를 봅니다 — 이 디플로이먼트가 레플리카 3개를 원하는데 실제로는 2개인가. 전자는 노드마다 하나씩(DaemonSet), 후자는 클러스터에 하나만 있으면 됩니다.

03오퍼레이터는 스크레이프하지 않는다

가장 많이 오해하는 부분입니다. 오퍼레이터는 메트릭을 수집하지 않습니다. ServiceMonitor를 읽어 프로메테우스 설정 파일을 생성하고 리로드시키는 것이 전부입니다. 이 구조를 알면 06단계에서 "ServiceMonitor를 만들었는데 타깃에 안 보인다"의 원인을 셋 중 하나로 좁힐 수 있습니다.

04차트 버전 확정

문서에 버전을 박아두지 않습니다. 설치 직전에 확인하고, 그 값을 팀 전체가 공유합니다. 8명이 서로 다른 차트 버전을 쓰면 07단계에서 대시보드 JSON이 어긋납니다. 

helm repo update
helm search repo prometheus-community/kube-prometheus-stack --versions | head -4
NAME                                            CHART VERSION   APP VERSION
prometheus-community/kube-prometheus-stack      88.3.0          v0.91.0
prometheus-community/kube-prometheus-stack      88.2.1          v0.91.0
prometheus-community/kube-prometheus-stack      88.1.0          v0.90.2

CHART VERSION은 차트의 버전, APP VERSION은 Prometheus Operator의 버전입니다. 아래 명령의 --version에 맨 위 값을 넣으세요. 이 문서는 88.3.0 기준으로 씁니다.

CRD는 헬름이 업그레이드해주지 않는다

차트를 처음 설치할 때는 CRD가 함께 생성되지만, helm upgrade로 차트 버전을 올릴 때 CRD는 갱신되지 않습니다. 헬름의 설계상 그렇습니다. 메이저 버전을 건너뛰어 올릴 때는 릴리스 노트를 읽고 CRD를 kubectl apply로 먼저 갱신해야 합니다. 실습 중에 차트 버전을 올릴 일이 생기면, 그냥 지우고 다시 설치하는 편이 빠릅니다.

05값 파일 작성

mkdir -p ~/k8s-observability/monitoring
cd ~/k8s-observability/monitoring

monitoring/kps-values.yaml

# ── 프로메테우스 본체 ──────────────────────────────
prometheus:
  service:
    # 01단계에서 뚫어둔 호스트 포트 30900과 짝
    type: NodePort
    nodePort: 30900
  prometheusSpec:
    # 관측 스택은 obs-worker2에 모은다

      workload: observability

    scrapeInterval: 30s
    evaluationInterval: 30s

    # 실습용. 로컬 디스크를 아끼기 위해 짧게 잡는다.
    retention: 3d
    retentionSize: 4GB

    # kind에는 local-path 기반 기본 StorageClass(standard)가 이미 있다.
    # storageSpec을 생략하면 emptyDir이 되어 파드 재시작 시 데이터가 사라진다.
    storageSpec:
      volumeClaimTemplate:
        spec:
          accessModes: ["ReadWriteOnce"]
          resources:
            requests:
              storage: 8Gi

    resources:
      requests:
        cpu: 200m
        memory: 900Mi
      limits:
        memory: 1600Mi

  alertmanagerSpec:
    nodeSelector:
      workload: observability

        memory: 192Mi

grafana:
  # 실습 전용 비밀번호. 운영에서는 Secret으로 주입한다.
  adminPassword: obs-study

  nodeSelector:
    workload: observability

kube-state-metrics:
  nodeSelector:
    workload: observability

# ── 컨트롤 플레인 타깃 ────────────────────────────
# 01단계에서 bind-address를 0.0.0.0으로 열어둔 덕분에
# 아래 설정이 실제로 동작한다. 패치가 없으면 전부 DOWN이다.
kubeControllerManager:
  enabled: true
  service:
    port: 10257
    targetPort: 10257
  serviceMonitor:
    # HTTPS를 끄지 않는다. kind의 인증서는 노드 IP를 SAN에 갖고 있지 않으므로
    # 검증만 건너뛴다.
    https: true
    insecureSkipVerify: true

kubeScheduler:
  enabled: true
  service:
    port: 10259
    targetPort: 10259
  serviceMonitor:
    https: true
    insecureSkipVerify: true

kubeEtcd:
  enabled: true
  service:
    # 2379는 상호 TLS가 필요한 클라이언트 포트다.
    # 메트릭 전용 2381을 쓴다 (01단계 listen-metrics-urls 설정).
    port: 2381
    targetPort: 2381
  serviceMonitor:
    scheme: http

kubeProxy:
  enabled: true
  service:
    port: 10249
    targetPort: 10249
차트 기본값과 겹치는 부분이 있다

최근 차트는 kubeEtcd의 포트를 이미 2381로 두는 등 기본값이 개선됐습니다. 그래도 명시적으로 적는 이유는, 값 파일만 읽어도 "왜 이 포트인가"가 드러나게 하기 위해서입니다. 기본값에 의존하면 차트가 바뀌었을 때 원인을 찾기 어렵습니다.

insecureSkipVerify를 쓰는 이유와 한계

컨트롤 플레인 구성요소는 HTTPS로 메트릭을 제공하는데, 인증서에 노드 IP가 들어있지 않아 이름 검증에 실패합니다. 로컬 클러스터에서는 검증만 건너뛰는 것이 현실적입니다. 암호화와 토큰 인증은 그대로 유지되므로, 아예 HTTPS를 끄고 평문 포트를 여는 일부 블로그의 방법보다 안전합니다. 운영 클러스터에서는 적절한 SAN을 가진 인증서를 발급해 insecureSkipVerify를 끄는 것이 정답입니다.

07타깃 검증 — 이 문서의 핵심

브라우저에서 localhost:30900/targets 를 열면 타깃 목록이 보입니다. 하지만 눈으로 세는 것보다 질의로 확인하는 편이 빠르고 정확합니다. 

# job별로 살아있는 타깃 수를 센다
curl -s --get http://localhost:30900/api/v1/query \
  --data-urlencode 'query=sum by (job) (up)' \
  | python3 -m json.tool

jq가 있다면 더 읽기 좋습니다.

curl -s --get http://localhost:30900/api/v1/query \
  --data-urlencode 'query=sum by (job) (up)' \
  | jq -r '.data.result[] | "\(.metric.job)\t\(.value[1])"' \
  | sort

apiserver                   1
coredns                     2
kps-grafana                 1
kube-controller-manager     1
kube-dns                    2
kube-etcd                   1
kube-proxy                  3
kube-scheduler              1
kube-state-metrics          1

여기가 01단계의 채점 결과다

kube-controller-manager, kube-scheduler, kube-etcd, kube-proxy 네 개가 1 이상이면 bind-address 패치가 제대로 걸린 것입니다. 숫자가 아예 나오지 않거나 0이면 01단계 04절로 돌아가야 합니다. 클러스터를 다시 만들어야 하므로, 03단계 앱 배포를 다시 하게 됩니다. 그래서 01단계에서 미리 넣어둔 것입니다. 

# 실패한 타깃만 골라 본다 — 이상적으로는 아무것도 안 나와야 한다
curl -s --get http://localhost:30900/api/v1/query \
  --data-urlencode 'query=up == 0' \
  | jq -r '.data.result[] | "\(.metric.job)  \(.metric.instance)"'

출력이 비어 있으면 통과입니다. 무언가 나오면 /targets 화면에서 해당 항목의 Error 열을 확인하세요. connection refused는 바인딩 문제, x509는 인증서 문제, 401/403은 RBAC 문제로 나뉩니다.

10자주 겪는 문제

증상원인과 조치
설치가 timed out waiting for the condition으로 실패 대개 메모리 부족. kubectl -n monitoring get pods로 Pending 파드를 찾고 describe의 Events를 본다. Docker Desktop 할당을 10 GiB 이상으로 올린다
프로메테우스 파드가 Pending, PVC가 Pending 기본 StorageClass가 없거나 노드셀렉터와 볼륨의 노드 친화성이 충돌. kubectl get sc에 standard (default)가 있는지 확인
kube-controller-manager 타깃이 없음(목록에 아예 안 나옴) 값 파일에서 enabled: false이거나, 해당 서비스의 셀렉터에 맞는 파드가 없다. kubectl -n kube-system get svc | grep kps로 서비스 생성 여부 확인
타깃은 있는데 connection refused 01단계 bind-address 패치 누락. 클러스터 재생성이 필요하다
etcd 타깃이 context deadline exceeded 2379(클라이언트 포트)로 붙고 있다. 값 파일의 kubeEtcd.service.targetPort가 2381인지 확인
x509: cannot validate certificate insecureSkipVerify: true가 빠졌다
localhost:30900 접속 불가 01단계 hostPort: 30900과 값 파일의 nodePort: 30900이 어긋났다
대시보드가 비어 있고 No data 05단계에서 다룬다. 지금은 프로메테우스 UI만 확인하면 된다

다시 설치하기

helm -n monitoring uninstall kps

# PVC는 남는다. 데이터까지 지우려면 명시적으로 삭제한다.
kubectl -n monitoring delete pvc --all

# CRD는 uninstall로 지워지지 않는다. 완전히 초기화하려면 삭제한다.
# 주의: 다른 릴리스가 같은 CRD를 쓰고 있으면 함께 깨진다.
kubectl get crd -o name | grep monitoring.coreos.com | xargs -r kubectl delete

11완료 체크리스트

  • kubectl -n monitoring get pods 에서 모든 파드가 Running
  • node-exporter 파드가 노드 수와 같은 3개
  • 프로메테우스 PVC가 Bound
  • up == 0 질의 결과가 비어 있다
  • kube-controller-manager·kube-scheduler·kube-etcd·kube-proxy 네 job이 모두 보인다
  • localhost:30900/targets 가 브라우저에서 열린다
  • localhost:30300 에서 그라파나 로그인 화면이 뜬다 (admin / obs-study)
  • 팀이 사용할 차트 버전을 값 파일 주석이나 README에 기록했다
