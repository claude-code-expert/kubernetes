쿠버네티스 관측성

헬름 차트 하나로 프로메테우스·Alertmanager·그라파나·node-exporter·kube-state-metrics 가 한꺼번에 올라온다. 설치는 명령 두 줄이고, 이 장의 내용은 타깃이 전부 UP 으로 뜨는지 확인하는 절차다.

01왜 이 장이 필요한가

03장에서 앱이 /actuator/prometheus 를 열어 뒀다. 그런데 아무도 그것을 읽지 않는다. 읽어 갈 쪽을 세우는 것이 이 장이다.

설치 자체는 helm upgrade --install 한 줄이다. 진짜 내용은 그다음이다 — 01장에서 넣은 bind-address 패치가 값을 하는지 여기서 판가름 난다. 패치가 없으면 kube-controller-manager · kube-scheduler · etcd · kube-proxy 네 타깃이 DOWN 으로 남고, 고치려면 클러스터를 다시 만들어야 한다. 즉 03장 앱 배포까지 다시 하게 된다. 그래서 01장에서 미리 넣어 둔 것이고, 이 장의 검증 절이 그 채점표다.

또 하나 미리 알아 둘 것이 있다. 이 장을 마쳐도 우리 앱 메트릭은 여전히 안 보인다. 앱은 자동으로 잡히지 않는다. 그 연결이 06장의 주제이고, 여기서는 “클러스터 자체를 보는 눈”까지만 만든다.

02알아야 할 개념

메트릭이 나오는 곳이 하나가 아니다

책 3.4 · 3.5 — “메모리 사용량이 왜 두 군데서 다르게 나오나”에서 헤매지 않으려면

넷을 말로 구분하려 하지 말고, 각각을 직접 질의해서 나온 메트릭 이름으로 구분하는 것이 이 장의 실습이다. 이름의 접두사가 곧 출처다 — container_ 는 cAdvisor, node_ 는 node-exporter, kube_ 는 kube-state-metrics 다.

오퍼레이터는 스크레이프하지 않는다

가장 많이 오해하는 부분이다. 프로메테우스 오퍼레이터는 메트릭을 수집하지 않는다. ServiceMonitor 같은 커스텀 리소스를 읽어 프로메테우스의 설정 파일을 만들어 주는 것이 전부이고, 실제 스크레이프는 프로메테우스 본체가 한다.

이 구분이 06장에서 값을 한다. “ServiceMonitor 를 만들었는데 타깃에 안 보인다”의 원인을 ① 선언이 잘못됨 ② 오퍼레이터가 그것을 고르지 않음 ③ 네트워크·인증 실패 셋 중 하나로 좁힐 수 있다.

계층적으로 본다

책이 권하는 순서는 노드 → 클러스터 구성요소 → 애드온 → 애플리케이션이다. 파드가 자꾸 대기 상태에 빠지면 먼저 노드 자원을 보고, 문제없으면 스케줄러를, 그다음 애플리케이션을 본다. 순서를 뒤집으면 앱 로그만 하루 종일 보게 된다.

CRD 는 헬름이 관리해 주지 않는다

차트를 처음 설치할 때는 CRD 가 함께 생성된다. 그런데 helm upgrade 로 차트 버전을 올릴 때 CRD 는 갱신되지 않는다. 헬름의 설계상 그렇다. 그리고 helm uninstall 로도 지워지지 않는다. 실습 중에 차트 버전을 올릴 일이 생기면 지우고 다시 설치하는 편이 빠르다.

이 장을 마치면 할 수 있는 것

  1. 차트 하나가 무엇을 설치하는지 구성요소별로 말하고, kubectl -n monitoring get pods 의 각 줄이 무엇인지 짚을 수 있다.
  2. 메트릭 네 출처를 질의해서 구분할 수 있다 — 이름 접두사로 출처를 안다.
  3. sum by (job) (up) 한 줄로 타깃 상태를 판정하고, 01장 패치가 걸렸는지 확인할 수 있다.
  4. 타깃이 실패했을 때 connection refused · x509 · 401 을 각각 다른 원인으로 읽을 수 있다.
  5. 차트 버전을 고정해 팀과 공유하고, 없는 버전을 지정했을 때의 에러를 알아볼 수 있다.

03최종적으로 만들 것

이 장이 끝나면 monitoring 네임스페이스에 파드 여덟 개가 돌고, localhost:30900/targets 에 타깃 목록이 뜬다. 그리고 그 목록에서 DOWN 이 하나도 없어야 한다.

메트릭이 나오는 네 곳

  • 1 노드의 상태를 묻는다. node-exporter 가 살아 있는지 확인하는 질의다. 확인 node_memory_MemAvailable_bytes / 1024^3 → 노드 수만큼의 줄, GiB (Gibibyte · 2의 30제곱 바이트. 쿠버네티스가 쓰는 단위) 단위 숫자
  • 2 API 서버의 기대값을 묻는다. kube-state-metrics 가 살아 있는지 본다. 확인 count(kube_pod_info) → 클러스터 전체 파드 수 (한 자릿수~수십)
  • 3 컨테이너가 실제로 쓴 양을 묻는다. cAdvisor 경로가 살아 있는지 본다. 확인 sum by (namespace) (container_memory_working_set_bytes{namespace="apps"}) → 바이트 단위 숫자 한 줄

WHY이 네 곳을 켜는 설정 — 차트의 스위치

네 출처 중 셋은 차트가 알아서 켠다(cAdvisor 는 kubelet 에 내장, node-exporter 와 kube-state-metrics 는 차트가 설치). 값 파일에서 우리가 정하는 것은 어디에 둘지와 컨트롤 플레인 타깃을 켤지다.

study/labs/monitoring/kps-values.yaml — 배치와 스위치 
prometheus:
  prometheusSpec:
    nodeSelector:
      workload: observability     # 01장 라벨. 관측 스택을 obs-worker2 에 모은다
    scrapeInterval: 30s           # 그림의 "30초마다"

kube-state-metrics:
  nodeSelector:
    workload: observability

# 01장에서 bind-address 를 0.0.0.0 으로 열어둔 덕분에 아래가 동작한다.
# 패치가 없으면 네 개 모두 DOWN 이다.
kubeControllerManager:
  enabled: true
kubeScheduler:
  enabled: true
kubeEtcd:
  enabled: true
kubeProxy:
  enabled: true

선언이 스크레이프가 되기까지

  • 1 선언이 클러스터에 있는지. 지금은 차트가 만든 것들만 있다. 확인 kubectl -n monitoring get servicemonitors → 차트가 만든 열 몇 줄
  • 2 오퍼레이터가 그것을 골랐는지. 골라 만든 설정이 Secret 에 들어 있다. 확인 kubectl -n monitoring get prometheus -o jsonpath='{.items[0].spec.serviceMonitorSelector}' → {"matchLabels":{"release":"kps"}}
  • 3 실제로 긁고 있는지. 이 장의 최종 판정이다. 확인 curl -s --get localhost:30900/api/v1/query --data-urlencode 'query=up == 0' → result 가 빈 배열

WHY②번의 셀렉터 — release 라벨

오퍼레이터가 무엇을 고르는지는 프로메테우스 리소스에 적혀 있다. 값 파일에서 따로 건드리지 않으면 차트가 기본값을 넣는다.

kubectl -n monitoring get prometheus -o yaml \
  | grep -A3 'serviceMonitorSelector'

--- 출력 ---

    serviceMonitorSelector:
      matchLabels:
        release: kps
이 한 줄이 06장의 첫 관문이다

우리가 만들 ServiceMonitor 에 release: kps 라벨이 없으면, 문법이 완벽해도 오퍼레이터가 그것을 아예 읽지 않는다. 에러도 나지 않는다 — 그냥 조용히 무시된다. 06장에서 이것을 먼저 틀려 보고 고친다. 릴리스 이름을 kps 로 정한 이유이기도 하다.

05차트 버전 확정

목적: 팀 전체가 같은 차트 버전을 쓰게 만든다. 버전이 갈리면 07장에서 대시보드 JSON (JavaScript Object Notation · 키·값으로 데이터를 적는 형식) 이 어긋난다.

문서에 버전을 박아 두지 않는다. 설치 직전에 확인하고, 그 값을 공유한다.

helm repo add prometheus-community https://prometheus-community.github.io/helm-charts
helm repo update
helm search repo prometheus-community/kube-prometheus-stack --versions | head -4

prometheus-community/kube-prometheus-stack      88.3.0          v0.91.0
prometheus-community/kube-prometheus-stack      88.2.1          v0.91.0
prometheus-community/kube-prometheus-stack      88.1.0          v0.90.2
읽는 법

CHART VERSION 은 차트의 버전, APP VERSION 은 프로메테우스 오퍼레이터의 버전이다. 둘은 따로 움직인다. 아래 설치 명령의 --version 에 맨 위 값을 넣는다. 이 문서는 88.3.0 기준으로 쓴다.

CRD 는 헬름이 업그레이드해 주지 않는다

처음 설치할 때는 CRD 가 함께 생성되지만 helm upgrade 로는 갱신되지 않고, helm uninstall 로도 지워지지 않는다. 메이저 버전을 건너뛰어 올릴 때는 릴리스 노트를 읽고 CRD 를 kubectl apply 로 먼저 갱신해야 한다. 실습 중이라면 지우고 다시 설치하는 편이 빠르다 — 12절에 절차가 있다.

06값 파일

study/labs/monitoring/kps-values.yaml — 프로메테우스 본체 
prometheus:
  service:
    # 01장에서 뚫어둔 호스트 포트 30900과 짝
    type: NodePort
    nodePort: 30900
  prometheusSpec:
    # 관측 스택은 obs-worker2에 모은다
    nodeSelector:
      workload: observability

    scrapeInterval: 30s
    evaluationInterval: 30s

    # 실습용. 로컬 디스크를 아끼기 위해 짧게 잡는다.
    retention: 3d
    retentionSize: 4GB

    # kind에는 local-path 기반 기본 StorageClass(standard)가 이미 있다.
    # storageSpec을 생략하면 emptyDir이 되어 파드 재시작 시 데이터가 사라진다.
    storageSpec:
      volumeClaimTemplate:
        spec:
          accessModes: ["ReadWriteOnce"]
          resources:
            requests:
              storage: 8Gi

    resources:
      requests:
        cpu: 200m
        memory: 900Mi
      limits:
        memory: 1600Mi
설정정하는 것빼면
nodePort: 30900맥에서 여는 주소임의 포트가 배정돼 01장 매핑과 어긋난다
scrapeInterval: 30s얼마나 자주 긁을지차트 기본값(보통 30s)을 쓴다. 짧게 잡으면 시계열이 촘촘해지고 디스크를 더 쓴다
retention: 3d며칠 보관할지기본 10일. 노트북 디스크가 줄어든다
storageSpec디스크를 붙인다emptyDir 이 되어 파드가 재시작하면 시계열이 전부 사라진다
kps-values.yaml — 컨트롤 플레인 타깃 
# 01장에서 bind-address를 0.0.0.0으로 열어둔 덕분에
# 아래 설정이 실제로 동작한다. 패치가 없으면 전부 DOWN이다.
kubeControllerManager:
  enabled: true
  service:
    port: 10257
    targetPort: 10257
  serviceMonitor:
    # HTTPS를 끄지 않는다. kind의 인증서는 노드 IP를 SAN에 갖고 있지 않으므로
    # 검증만 건너뛴다.
    https: true
    insecureSkipVerify: true

kubeScheduler:
  enabled: true
  service:
    port: 10259
    targetPort: 10259
  serviceMonitor:
    https: true
    insecureSkipVerify: true

kubeEtcd:
  enabled: true
  service:
    # 2379는 상호 TLS가 필요한 클라이언트 포트다.
    # 메트릭 전용 2381을 쓴다 (01장 listen-metrics-urls 설정).
    port: 2381
    targetPort: 2381
  serviceMonitor:
    scheme: http

kubeProxy:
  enabled: true
  service:
    port: 10249
    targetPort: 10249
insecureSkipVerify 를 쓰는 이유와 한계

컨트롤 플레인 구성요소는 HTTPS (HTTP Secure · TLS 로 암호화한 HTTP) 로 메트릭을 제공하는데, 인증서에 노드 IP (Internet Protocol · 네트워크에서 주소를 정하는 규약) 가 들어 있지 않아 이름 검증에 실패한다. 로컬 클러스터에서는 검증만 건너뛰는 것이 현실적이다. 암호화와 토큰 인증은 그대로 유지되므로, 아예 HTTPS 를 끄고 평문 포트를 여는 방법보다 안전하다. 운영 클러스터에서는 적절한 SAN (Subject Alternative Name · 인증서가 보증하는 이름·주소 목록) 을 가진 인증서를 발급해 이 옵션을 끄는 것이 정답이다.

08타깃 검증 — 이 장의 핵심

브라우저에서 localhost:30900/targets 를 열면 타깃 목록이 보인다. 하지만 눈으로 세는 것보다 질의로 확인하는 편이 빠르고 정확하다.

목적: job 별로 살아 있는 타깃 수를 센다.

curl -s --get http://localhost:30900/api/v1/query \
  --data-urlencode 'query=sum by (job) (up)' \
  | jq -r '.data.result[] | "\(.metric.job)\t\(.value[1])"' \
  | sort

--- 출력 ---

alertmanager                1
apiserver                   1
coredns                     2
kps-grafana                 1
kube-controller-manager     1
kube-dns                    2
kube-etcd                   1
kube-proxy                  3
kube-scheduler              1
kube-state-metrics          1
kubelet                     3
node-exporter               3
prometheus                  1
prometheus-operator         1
여기가 01장의 채점 결과다

kube-controller-manager · kube-scheduler · kube-etcd · kube-proxy 네 개가 1 이상이면 bind-address 패치가 제대로 걸린 것이다. 아예 안 나오거나 0 이면 01장으로 돌아가야 하고, 클러스터를 다시 만들어야 하므로 03장 앱 배포도 다시 하게 된다.

kube-proxy 와 kubelet 과 node-exporter 가 3 인 것은 노드마다 하나씩이기 때문이다. 이 숫자가 2 라면 노드 하나가 빠진 것이다.

목적: 실패한 타깃만 골라 본다. 이상적으로는 아무것도 안 나와야 한다.

curl -s --get http://localhost:30900/api/v1/query \
  --data-urlencode 'query=up == 0' \
  | jq -r '.data.result[] | "\(.metric.job)  \(.metric.instance)"'
판정

출력이 비어 있으면 통과다. 무언가 나오면 /targets 화면에서 해당 항목의 Error 열을 읽는다. 문구에 따라 원인이 갈린다.

11일부러 실패시키기 — 버전과 CRD

아래 두 출력은 Helm v4.2.4 · kind 클러스터(Kubernetes 1.37)에서 재현했다 (확인 2026-09-13). 둘 다 클러스터를 바꾸지 않는다.

실패 1 — 문서에 박힌 버전이 사라졌을 때

목적: 버전을 고정하는 습관의 대가를 미리 겪는다. 차트 저장소는 옛 버전을 영원히 두지 않는다.

helm upgrade --install kps prometheus-community/kube-prometheus-stack \
  --namespace monitoring --create-namespace \
  --version 999.0.0 --dry-run=client

--- 출력 ---

Error: chart "kube-prometheus-stack" matching 999.0.0 not found in prometheus-community index.
(try 'helm repo update'): no chart version found for kube-prometheus-stack-999.0.0
읽는 법

메시지가 친절하게 try 'helm repo update' 를 권한다. 먼저 그것부터 한다 — 로컬 인덱스가 오래돼 새 버전을 모르는 경우가 실제로 흔하다. 업데이트 후에도 같은 메시지가 나오면 그 버전이 정말 없는 것이고, 05절의 helm search repo --versions 로 현재 있는 목록을 확인해 고른다.

--dry-run=client 를 붙였으므로 클러스터에는 아무 일도 일어나지 않는다. 설치 전에 값 파일과 버전을 점검할 때 쓰는 방법이다.

실패 2 — CRD 가 없는데 커스텀 리소스를 올릴 때

목적: 06장에서 만날 에러를 미리 본다. 설치 순서가 틀렸거나 apiVersion 이 틀리면 같은 메시지가 난다.

cat <<'EOF' | kubectl apply --dry-run=server -f -
apiVersion: monitoring.coreos.com/v1beta1   # 실제로는 v1 이다
kind: ServiceMonitor
metadata:
  name: bogus
  namespace: monitoring
spec:
  selector:
    matchLabels:
      app: none
  endpoints:
    - port: http
EOF

--- 출력 ---

error: resource mapping not found for name: "bogus" namespace: "monitoring" from "STDIN":
no matches for kind "ServiceMonitor" in version "monitoring.coreos.com/v1beta1"
ensure CRDs are installed first
읽는 법

no matches for kind 는 “그런 종류의 리소스를 이 클러스터가 모른다”는 뜻이다. 원인은 둘 중 하나다 — CRD 가 아직 설치되지 않았거나, apiVersion 을 틀리게 적었거나. 어느 쪽인지는 등록된 버전을 직접 물어보면 갈린다.

kubectl get crd servicemonitors.monitoring.coreos.com \
  -o jsonpath='{.spec.versions[*].name}'

값이 나오면 CRD 는 있는 것이고, 나온 버전(v1)을 쓰면 된다. 명령 자체가 NotFound 로 실패하면 차트가 CRD 를 만들지 못한 것이다 — 07절 설치로 돌아간다.

다시 설치하기

helm -n monitoring uninstall kps

# PVC는 남는다. 데이터까지 지우려면 명시적으로 삭제한다.
kubectl -n monitoring delete pvc --all

# CRD는 uninstall로 지워지지 않는다. 완전히 초기화하려면 삭제한다.
# 주의: 다른 릴리스가 같은 CRD를 쓰고 있으면 함께 깨진다.
kubectl get crd -o name | grep monitoring.coreos.com | xargs -r kubectl delete
