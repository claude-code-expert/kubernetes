쿠버네티스 관측성

앱 메트릭 연동과 PromQL

02장에서 연 /actuator/prometheus 를 04장의 프로메테우스에 붙인다. 연결 고리는 라벨 세 겹이고, 대부분 첫 번째 겹에서 막힌다. 일부러 한 번 실패시킨 뒤 고친다.

01왜 이 장이 필요한가

04장에서 프로메테우스가 섰지만 타깃 목록에 우리 앱이 없었다. 02장에서 앱이 /actuator/prometheus 를 열어 뒀는데도 그렇다. 둘 사이를 잇는 선언이 없기 때문이다.

그 선언이 ServiceMonitor 인데, 여기에 이 시리즈에서 가장 악명 높은 함정이 있다. 연결이 세 겹의 라벨 일치로만 이루어지고, 하나라도 어긋나면 에러 메시지가 없다. 리소스는 정상으로 만들어지고, 로그도 조용하고, 타깃만 안 생긴다.

그래서 이 장은 성공부터 하지 않는다. 먼저 실패시키고 그 침묵을 확인한 뒤 고친다. 5분이면 되는 경험이 나중에 몇 시간을 아낀다.

02알아야 할 개념

연결은 세 겹이다

겹무엇이 무엇을 고르나어긋나면확인하는 명령
①프로메테우스 CR (Custom Resource · CRD 로 정의한 타입의 실제 오브젝트) 의 serviceMonitorSelector 가 ServiceMonitor 를 고른다ServiceMonitor 가 아예 읽히지 않는다생성된 스크레이프 설정에 job_name 이 있는지
②ServiceMonitor 의 selector 가 Service 를 고른다타깃 그룹은 생기는데 대상이 0개kubectl -n apps get svc --show-labels
③Service 의 selector 가 파드를 고른다엔드포인트가 빈다kubectl -n apps get endpointslices

이 장에서 새로 만드는 것은 ①과 ServiceMonitor 뿐이다. ②와 ③은 03장에서 서비스에 라벨을 붙이고 포트에 http 라는 이름을 준 시점에 이미 준비됐다.

포트는 이름으로 고른다

ServiceMonitor 의 endpoints.port 는 포트 번호가 아니라 서비스에 정의된 포트 이름이다. 8080 이라고 숫자를 적으면 조용히 안 붙는다.

프로메테우스가 라벨을 덧붙인다

앱은 orders_created_total{channel="api"} 하나만 내보냈는데, 저장된 시계열에는 namespace · pod · service · job 이 붙어 있다. 쿠버네티스 서비스 디스커버리가 스크레이프 시점에 넣어 주는 것이다.

이 라벨들 덕분에 파드가 죽고 다시 떠도 같은 job 으로 묶여 하나의 흐름처럼 보인다. PromQL 에서 집계 축을 고를 때 쓰는 것이 대부분 이 라벨이다. 02장에서 앱에 공통 태그를 넣지 않은 이유가 여기 있다 — 넣었다면 의미가 겹치는 라벨이 두 벌 생겼을 것이다.

카운터는 그대로 보면 쓸모가 없다

카운터는 늘기만 한다. “지금 트래픽이 많은가”를 읽으려면 기울기를 봐야 하고, 그것이 rate() 다. 대괄호 안의 시간은 “이만큼을 돌아보며 평균 낸다”는 뜻이며 스크레이프 간격의 4배 이상을 권한다. 우리는 30초 간격이므로 최소 2분이다.

이 장을 마치면 할 수 있는 것

  1. 라벨 세 겹 중 어디가 끊겼는지를 각각 다른 명령으로 좁힐 수 있다.
  2. 생성된 스크레이프 설정을 직접 열어 job_name 유무로 ①번 고리를 판정할 수 있다.
  3. 메트릭에 붙은 라벨이 어디서 왔는지 하나씩 짚을 수 있다.
  4. RED 세 질의를 직접 쓰고, 결과가 비는 이유(분모 0, le 누락)를 설명할 수 있다.
  5. 백엔드 지연이 게이트웨이로 전파되는 모습을 두 그래프로 대조할 수 있다.

03최종적으로 만들 것

이 장이 끝나면 up{namespace="apps"} 가 파드 3개를 모두 1 로 돌려주고, RED 세 질의가 값을 낸다. 그 질의들이 07장 대시보드의 패널이 된다.

라벨 세 겹

  • 1 오퍼레이터가 골랐는지. 생성된 스크레이프 설정에 job_name 이 있으면 통과다. 확인 kubectl -n monitoring get secret prometheus-kps-kube-prometheus-prometheus -o jsonpath='{.data.prometheus\.yaml\.gz}' | base64 -d | gunzip | grep -o 'job_name: serviceMonitor/apps/[a-z-]*/0' → job_name: serviceMonitor/apps/order-api/0
  • 2 ServiceMonitor 가 Service 를 찾았는지. 라벨을 눈으로 대조한다. 확인 kubectl -n apps get svc --show-labels → app.kubernetes.io/name=order-api
  • 3 Service 가 파드를 잡았는지. 여기가 비면 스크레이프할 주소 자체가 없다. 확인 kubectl -n apps get endpointslices → ENDPOINTS 열에 파드 IP (Internet Protocol · 네트워크에서 주소를 정하는 규약)

WHY세 겹을 잇는 파일 — 90-servicemonitors.yaml

어느 고리에서 끊겼는지 확정한다

목적: 추측하지 않고 생성된 설정을 직접 연다. 프로메테우스가 실제로 읽는 설정은 시크릿에 gzip 으로 들어 있다.

kubectl -n monitoring get secret prometheus-kps-kube-prometheus-prometheus \
  -o jsonpath='{.data.prometheus\.yaml\.gz}' | base64 -d | gunzip \
  | grep -c 'order-api-broken'

kubectl -n monitoring get secret prometheus-kps-kube-prometheus-prometheus \
  -o jsonpath='{.data.prometheus\.yaml\.gz}' | base64 -d | gunzip \
  | grep -o 'job_name: serviceMonitor/apps/[a-z-]*/0' | sort -u

--- 출력 ---

0

job_name: serviceMonitor/apps/order-api/0
판정

첫 결과가 0 — 생성된 설정 어디에도 order-api-broken 이라는 문자열이 없다. 오퍼레이터가 그 리소스를 읽지 않았다는 뜻이고, ①번 고리에서 끊긴 것이 확정된다. 둘째 명령은 제대로 붙은 쪽이 어떤 모양인지 보여 준다 — serviceMonitor/<네임스페이스>/<이름>/<엔드포인트 번호> 형식이다.

이 명령 하나로 원인이 절반으로 갈린다. 여기에 없으면 ①번(라벨), 있는데도 타깃이 0개면 ②·③번이다.

왜 이런 기본값인가

kubectl -n monitoring get prometheus -o yaml | grep -A3 'serviceMonitorSelector'

--- 출력 ---

    serviceMonitorSelector:
      matchLabels:
        release: kps
차트가 이렇게 만드는 이유

차트는 serviceMonitorSelectorNilUsesHelmValues: true 를 기본으로 둔다. “이 헬름 릴리스가 관리하는 것만 본다”는 뜻이고, 한 클러스터에 프로메테우스를 여러 개 띄우는 상황(팀별 분리 등)에서 서로의 타깃을 침범하지 않게 하려는 장치다.

값 파일에 serviceMonitorSelectorNilUsesHelmValues: false 를 넣으면 무력화된다. 실습에서는 넣지 않는다 — 라벨을 붙이는 쪽이 원리를 드러내고, 운영 클러스터에서도 그쪽이 표준이다.

kubectl -n apps delete servicemonitor order-api-broken

08PromQL 최소 문법

여기서부터는 localhost:30900/graph 에 직접 입력하며 읽는다. 필요한 개념은 네 개뿐이다.

1. 카운터에는 rate 를 씌운다

그림 2 에서 본 것이다. 대괄호 안의 윈도는 스크레이프 간격의 4배 이상.

rate(orders_created_total[2m])

2. sum by — 필요한 축만 남긴다

# 파드별로 흩어진 값을 서비스 단위로 합친다
sum by (service) (rate(orders_created_total[2m]))

# by 대신 without 을 쓰면 "이 라벨만 빼고 나머지로 묶어라"가 된다
sum without (pod, instance) (rate(orders_created_total[2m]))

파드가 늘고 줄어도 그래프가 흔들리지 않게 하려면 pod 와 instance 를 지우는 쪽이 안전하다. 파드가 하나 재시작할 때마다 새 시계열이 생기기 때문이다.

3. 히스토그램에서 분위수 뽑기

# le(less or equal) 라벨을 반드시 남겨야 한다. 빠지면 계산이 안 된다.
histogram_quantile(
  0.95,
  sum by (le, service) (rate(http_server_requests_seconds_bucket{namespace="apps"}[5m]))
)
le 를 빠뜨리면 NaN 이 나온다

sum by (service) 라고만 쓰면 버킷 경계 정보가 사라져 분위수를 계산할 재료가 없어진다. 에러가 아니라 NaN 이 나오므로 원인을 찾기 어렵다. histogram_quantile 안쪽의 sum by 에는 항상 le 를 넣는다.

4. 비율 계산에서 조심할 것

# 트래픽이 없으면 분모가 0이 되어 결과가 비어버린다.
# 대시보드에서 'No data'가 뜨는 흔한 원인이다.
sum(rate(http_server_requests_seconds_count{namespace="apps", status=~"5.."}[5m]))
/
sum(rate(http_server_requests_seconds_count{namespace="apps"}[5m]))
네이티브 히스토그램은 아직 쓰지 않는다

Prometheus 3.8 부터 네이티브 히스토그램이 정식 기능이 됐다. 버킷 시계열이 폭증하는 문제를 근본적으로 줄여 준다. 다만 그라파나 패널과 기존 대시보드가 아직 고전 버킷 기준인 경우가 많아 이 실습은 _bucket 으로 진행한다. 09장 카디널리티 논의에서 전환 판단 기준을 다시 다룬다.

09RED 지표 완성

Rate(처리율) · Errors(에러율) · Duration(지연). 애플리케이션 관측은 이 셋으로 시작해 이 셋으로 끝난다. 아래 질의들이 07장 대시보드의 패널이 된다.

R — 서비스별 초당 요청 수

sum by (service) (
  rate(http_server_requests_seconds_count{namespace="apps"}[2m])
)

E — 서비스별 5xx 비율 (%)

100 * (
  sum by (service) (
    rate(http_server_requests_seconds_count{namespace="apps", status=~"5.."}[5m])
  )
  /
  sum by (service) (
    rate(http_server_requests_seconds_count{namespace="apps"}[5m])
  )
)

D — 서비스별 P95 응답 시간 (초)

histogram_quantile(
  0.95,
  sum by (le, service) (
    rate(http_server_requests_seconds_bucket{namespace="apps"}[5m])
  )
)

D 심화 — 엔드포인트별 P99, 느린 순서대로

topk(5,
  histogram_quantile(
    0.99,
    sum by (le, uri) (
      rate(http_server_requests_seconds_bucket{namespace="apps", service="order-api"}[5m])
    )
  )
)

uri 라벨이 /api/orders/{id} 처럼 템플릿으로 찍혀 있는 것을 확인한다. 02장에서 @PathVariable 로 매핑한 덕분이다.

비즈니스 지표 — 분당 주문 수와 거부율

# 분당 주문 건수
sum(rate(orders_created_total[5m])) * 60

# 거부 비율(%) — 검증에 걸린 주문의 비중
100 * (
  sum(rate(orders_rejected_total[5m]))
  /
  (sum(rate(orders_created_total[5m])) + sum(rate(orders_rejected_total[5m])))
)
RED 와 비즈니스 지표를 나란히 두는 이유

기술 지표만 보면 “에러율 0%, P95 정상”인데 매출이 떨어지는 상황을 놓친다. 주문 수가 평소의 30% 로 줄었는데 응답 시간은 오히려 좋아진 경우가 그렇다 — 사용자가 들어오지 못하고 있다는 뜻일 수 있다. 대시보드 맨 위에 비즈니스 지표를 두는 팀이 늘어나는 이유다.

10지연 전파 관찰

서비스를 둘로 나눈 이유를 확인할 차례다. 백엔드를 느리게 만들고 게이트웨이의 지연이 어떻게 따라 움직이는지 본다.

# 터미널 1 — 평상시 트래픽을 계속 흘린다
while true; do
  curl -s -o /dev/null -X POST http://localhost:30080/api/orders \
    -H 'Content-Type: application/json' \
    -d '{"item":"latte","quantity":2}'
  sleep 0.3
done
# 터미널 2 — 3분 동안 느린 요청을 섞는다
end=$((SECONDS+180))
while [ "$SECONDS" -lt "$end" ]; do
  curl -s -o /dev/null "http://localhost:30080/api/chaos/slow?ms=900"
  sleep 1
done
echo "지연 주입 종료"

두 질의를 그래프에 함께 띄워 비교한다.

# 게이트웨이가 본 P95 (클라이언트 관점)
histogram_quantile(0.95,
  sum by (le) (rate(http_server_requests_seconds_bucket{service="gateway"}[2m]))
)

# 백엔드가 본 P95 (서버 관점)
histogram_quantile(0.95,
  sum by (le) (rate(http_server_requests_seconds_bucket{service="order-api"}[2m]))
)
관찰되는 패턴해석
두 값이 거의 같이 오른다백엔드가 원인. 게이트웨이는 기다렸을 뿐이다
게이트웨이만 오르고 백엔드는 평온게이트웨이 자체 병목 — 커넥션 풀, CPU (Central Processing Unit · 중앙처리장치), 라우팅 필터를 의심
백엔드가 올랐는데 게이트웨이는 그대로느린 경로가 게이트웨이를 거치지 않았거나, 타임아웃으로 잘리고 있다

게이트웨이의 라우트 단위 지표로 한 번 더 확인할 수 있다. 02장에서 id: order-api 로 정한 값이 routeId 태그가 된다.

histogram_quantile(0.95,
  sum by (le, routeId) (rate(spring_cloud_gateway_requests_seconds_bucket[5m]))
)
실습이 끝나면 반드시 부하 루프를 끈다

터미널 1의 무한 루프를 켜 둔 채 잊으면 노트북 팬이 계속 돌고, 프로메테우스 저장 공간(04장에서 8Gi)이 예상보다 빨리 찬다. Ctrl+C 로 종료한다.
