쿠버네티스 관측성

로그 수집 — Loki 와 Alloy

메트릭은 “무언가 이상하다”까지 알려주고 멈춘다. 그다음 질문인 “무슨 일이 있었나”는 로그의 몫이다. 화살표 방향이 메트릭과 반대라는 것이 이 장의 핵심이다.

01왜 이 장이 필요한가

07장에서 알림이 울렸다고 하자. “에러율 12%”. 그래서 무슨 일이 일어난 것인가? 메트릭은 거기까지 답하지 못한다. 숫자는 얼마나를 말하고 왜는 말하지 않는다.

컨테이너의 로그는 표준 출력으로 나가 노드의 파일에 쌓인다. 그 파일은 파드가 사라지면 같이 사라진다. 사고를 조사할 때 필요한 로그가 대개 이미 사라진 로그라는 것이 수집기를 두는 이유다.

그리고 여기서 방향이 뒤집힌다. 프로메테우스는 앱이 열어 둔 것을 당겨 갔다. 로그는 수집기가 읽어서 로키로 밀어 넣는다. 00장 그림 3 의 보라 점선과 주황 실선이 이것이었다.

02알아야 할 개념

로키는 본문을 색인하지 않는다

책 3.8 ~ 3.10

엘라스틱서치는 로그 본문 전체를 색인한다. 검색은 빠르지만 저장 비용이 크다. 로키는 반대로 라벨만 색인하고 본문은 압축해 보관한다. 이 설계 하나가 사용법의 거의 모든 것을 결정한다.

따라오는 결론이 둘이다. 라벨은 적게 — 라벨 조합 하나가 곧 하나의 스트림이고 늘어나면 비용이 폭증한다. 그리고 질의는 항상 라벨로 시작 — 좁힌 뒤에 본문을 훑는다. 06장의 카디널리티 문제와 정확히 같은 구조다.

2026년에 바뀐 두 가지

검색 결과 상위에 있는 두 가지를 쓰지 않는다

① Promtail 은 2026-03-02 로 수명이 끝났다. 지금 새로 구성하는 스택에서는 Grafana Alloy 를 쓴다. 설정 형식이 완전히 달라서 Promtail 예제를 복사하면 아무것도 동작하지 않는다.

② 로키 헬름 차트가 grafana-community 저장소로 이전했다(2026-03-16). grafana/loki 경로로는 원하는 차트를 받지 못한다. 반면 Alloy 차트는 아직 grafana 저장소에 있다 — 둘이 갈렸다는 점이 헷갈리기 쉽다.

라벨로 좁히고 본문으로 거른다

LogQL 의 사고 순서가 여기서 나온다. {namespace="apps"} 로 스트림을 고르고, 그 안에서 |= "ERROR" 로 훑는다. 라벨 없이 전체에서 문자열을 찾는 질의는 느리거나 아예 거부된다.

이 장을 마치면 할 수 있는 것

  1. 로그가 앱에서 로키까지 가는 경로를 네 단계로 설명하고, 각 단계를 명령으로 확인할 수 있다.
  2. Alloy 의 리레이블 설정이 어떤 라벨을 만들지 결정한다는 것을 실제 라벨 목록으로 확인할 수 있다.
  3. LogQL 을 라벨 → 본문 순서로 쓰고, 로그를 숫자로 바꿔 메트릭처럼 그릴 수 있다.
  4. 없는 라벨로 질의했을 때 에러가 아니라 빈 결과가 온다는 것을 알고, 라벨 목록부터 확인하는 습관을 들인다.
  5. 07장 대시보드에 로그 패널을 붙여 그래프가 튄 시각의 로그를 같은 화면에서 볼 수 있다.

03최종적으로 만들 것

이 장이 끝나면 그라파나 한 화면에서 에러율 그래프가 튄 시각의 로그를 바로 아래에서 읽을 수 있다. 그 상태를 만드는 것이 이 시리즈의 목표였다.

로그가 지나는 네 칸

  • 1 앱이 로그를 내고 있는가. 수집과 무관하게 먼저 확인한다. 확인 kubectl -n apps logs deploy/order-api --tail=5 → 줄이 나온다
  • 2 Alloy 가 노드마다 떠 있는가. DaemonSet 이므로 노드 수와 같아야 한다. 확인 kubectl -n logging get pods -o wide → Alloy 파드가 노드 수만큼
  • 3 로키에 들어갔는가. 이 장의 최종 판정이다. 확인 그라파나 Explore → Loki → {namespace="apps"} → 줄이 보인다

WHY3번 칸을 만드는 설정 — alloy-values.yaml

Alloy 설정은 네 단계의 파이프라인이다. 발견 → 라벨 선택 → 읽기 → 쓰기. 주석의 번호가 그 순서다.

study/labs/monitoring/alloy-values.yaml 
alloy:
  configMap:
    content: |-
      // 1) 클러스터의 파드를 발견한다
      discovery.kubernetes "pods" {
        role = "pod"
      }

      // 2) 어떤 라벨을 붙일지 고른다. 여기서 고르지 않은 메타데이터는 버려진다.
      discovery.relabel "pod_logs" {
        targets = discovery.kubernetes.pods.targets
        rule {
          source_labels = ["__meta_kubernetes_namespace"]
          target_label  = "namespace"
        }
        rule {
          source_labels = ["__meta_kubernetes_pod_name"]
          target_label  = "pod"
        }
        rule {
          source_labels = ["__meta_kubernetes_pod_container_name"]
          target_label  = "container"
        }
        rule {
          source_labels = ["__meta_kubernetes_pod_label_app_kubernetes_io_name"]
          target_label  = "app"
        }
      }

      // 3) 쿠버네티스 API로 로그를 읽는다 (호스트 경로 마운트가 필요 없다)
      loki.source.kubernetes "pods" {
        targets    = discovery.relabel.pod_logs.output
        forward_to = [loki.write.default.receiver]
      }

      // 4) 로키로 밀어 넣는다 — 목적지 주소가 보내는 쪽에 있다
      loki.write "default" {
        endpoint {
          url = "http://loki-gateway.logging.svc.cluster.local/loki/api/v1/push"
        }
      }

# 노드마다 하나씩 뜨는 DaemonSet 이 기본값이다
controller:
  type: daemonset
블록정하는 것빼거나 틀리면
discovery.kubernetes어떤 대상을 찾을지대상이 없어 아무 로그도 안 들어온다
discovery.relabel 의 rule 네 개로키에 존재하게 될 라벨여기서 안 고른 메타데이터는 버려진다 — 나중에 그 라벨로 질의할 수 없다
loki.source.kubernetes로그를 읽는 방법파일 방식으로 바꾸면 호스트 마운트와 권한이 필요해진다
loki.write.endpoint.url보낼 곳주소가 틀리면 Alloy 로그에 전송 실패가 쌓인다
controller.type: daemonset노드마다 하나Deployment 면 한 노드의 로그만 모인다
2번이 이 장에서 가장 중요한 블록이다

여기서 고른 네 개(namespace · pod · container · app)가 로키에서 쓸 수 있는 라벨의 전부가 된다. 나중에 “deployment 라벨로 찾고 싶다”가 생겨도 그 라벨은 존재하지 않는다. 그리고 존재하지 않는 라벨로 질의하면 에러가 아니라 빈 결과가 온다 — 06절에서 직접 확인한다.

실습에서는 단일 바이너리 모드 + 파일시스템 저장을 쓴다. 공식 예제는 MinIO 를 쓰지만 파드가 하나 더 늘고, MinIO 서브차트는 폐기 예정이라 로컬 실습에서는 쓸 이유가 없다.

study/labs/monitoring/loki-values.yaml — 앞부분 
deploymentMode: Monolithic

loki:
  # 멀티테넌시를 끈다. 켜면 모든 요청에 X-Scope-OrgID 헤더가 필요해진다.
  auth_enabled: false

  commonConfig:
    path_prefix: /var/loki
    # 단일 인스턴스이므로 1. 기본값(3)이면 기동하지 못한다.
    replication_factor: 1

  storage:
    type: filesystem
    # 파일시스템을 써도 차트 템플릿이 이 값을 참조한다. 비워두면 렌더링이 깨질 수 있다.
    bucketNames:
      chunks: chunks
      ruler: ruler

  # 최근 차트는 schemaConfig를 명시하지 않으면 설치가 실패한다.
  schemaConfig:
    configs:
      - from: "2024-04-01"
        store: tsdb
        object_store: filesystem
        schema: v13
        index:
          prefix: loki_index_
          period: 24h

  limits_config:
    # 구조화 메타데이터 — 라벨을 늘리지 않고 필드를 붙이는 방법 (09절)
    allow_structured_metadata: true
    volume_enabled: true
    retention_period: 72h

singleBinary:
  replicas: 1
  persistence:
    enabled: true
    size: 10Gi
설정왜 이 값인가기본값으로 두면
deploymentMode: Monolithic실습은 한 프로세스로 충분하다read/write/backend 파드가 여러 개 뜬다
auth_enabled: false멀티테넌시를 끈다모든 요청에 X-Scope-OrgID 헤더가 필요해진다
replication_factor: 1인스턴스가 하나다기동하지 못한다 — 복제본 3개를 찾는다
schemaConfig최근 차트의 필수 항목설치가 실패한다
retention_period: 72h노트북 디스크를 지킨다무한 보관

나머지 절반은 노트북을 지키기 위한 설정이다. 다른 배포 모드의 파드가 뜨지 않도록 replicas 를 0 으로 박고, 캐시를 끈다.

08LogQL 최소 문법

1. 스트림 고르기 — 항상 여기서 시작한다

{namespace="apps"}
{namespace="apps", container="order-api"}

2. 본문 훑기

# 포함 / 불포함
{namespace="apps"} |= "ERROR"
{namespace="apps"} != "health"

# 정규식
{namespace="apps"} |~ "ERROR|WARN"

3. 로그를 숫자로 바꾸기

여기서부터 PromQL 과 닮는다. 로그 건수를 세면 메트릭처럼 그래프로 그릴 수 있다.

# 5분간 에러 로그 건수
count_over_time({namespace="apps"} |= "ERROR" [5m])

# 컨테이너별 초당 에러 로그 수
sum by (container) (rate({namespace="apps"} |= "ERROR" [5m]))
로그로 만든 지표를 알림에 쓸 수 있다

위 질의는 값이 숫자이므로 07장의 PrometheusRule 과 같은 방식으로 알림을 걸 수 있다(로키 룰러). 다만 메트릭으로 셀 수 있는 것은 메트릭으로 세는 편이 싸다 — 로그 훑기는 본문을 압축 해제해야 한다. 로그 기반 알림은 “메트릭에 없는데 로그에만 있는 사건”에 쓴다.

09일부러 실패시키기 — 없는 라벨로 질의하기

03절에서 “여기서 안 고른 메타데이터는 버려진다”고 했다. 그 결과를 직접 본다. 없는 라벨로 질의하면 에러가 나지 않는다 — 이것이 이 장의 함정이다.

 "stats":{"summary":{"totalLinesProcessed":0,"execTime":0.024357, ...}}}}
읽는 법

"status":"success" 다. 질의는 성공했고 결과가 없을 뿐이다. totalLinesProcessed 가 0 인 것도 눈여겨본다 — 훑을 로그조차 없었다는 뜻이다. 로키는 “그런 라벨은 없다”고 말해 주지 않는다. Alloy 가 만들지 않은 라벨이기 때문이다.

화면에서는 No logs found 로만 보인다. “로그가 없다”와 “라벨 이름이 틀렸다”가 같은 모습이라는 것이 이 실패의 핵심이다.

구분하는 방법 — 라벨 목록을 직접 물어본다

curl -s 'http://localhost:33100/loki/api/v1/labels' | jq -r '.data[]'

--- 출력 ---

app
container
instance
job
namespace
pod
service_name
판정

deployment 가 목록에 없다. 03절 Alloy 설정의 discovery.relabel 에서 고른 것이 namespace · pod · container · app 네 개였고, 나머지(instance · job · service_name)는 로키와 Alloy 가 자동으로 붙인 것이다. 이 목록에 없는 이름은 쓸 수 없다.

# 특정 라벨에 어떤 값이 있는지도 물어볼 수 있다
curl -s 'http://localhost:33100/loki/api/v1/label/namespace/values' | jq -r '.data[]' | head

그라파나 Explore 화면에서는 질의 입력창 위의 Label browser 가 같은 일을 한다. 라벨 이름을 손으로 치기 전에 거기서 골라 넣는 습관이 이 실패를 막는다.

대조 — 문법 오류는 조용하지 않다

curl -s --get 'http://localhost:33100/loki/api/v1/query_range' \
  --data-urlencode 'query={namespace="apps" |= "ERROR"' \
  --data-urlencode "start=${FROM}000000000" --data-urlencode "end=${NOW}000000000"

--- 출력 (닫는 중괄호를 빠뜨렸다) ---

parse error at line 0, col 19: syntax error: unexpected |=, expecting } or ,
실수결과어떻게 아나
없는 라벨 이름status: success, 빈 결과모른다. 라벨 목록을 직접 물어봐야 한다
라벨 값 오타 (namespace="app")같다 — 빈 결과라벨 값 목록을 물어본다
LogQL 문법 오류즉시 parse error열 번호까지 알려 준다
시간 범위가 보존 기간 밖빈 결과72시간 이전은 지워졌다

07장 알림 규칙과 같은 구조다 — 문법은 기계가 잡아 주고, 이름이 맞는지는 사람이 확인해야 한다.

kill %1   # 포트포워드 종료

2. 대시보드에 로그 패널 추가

obs-red.json 의 panels 배열 끝에 하나를 더한다. gridPos 의 y 는 마지막 패널(y:13, 높이 8) 다음인 21 이다.

study/labs/monitoring/dashboards/obs-red.json — panels 끝에 추가 
{
  "type": "logs",
  "title": "앱 로그 (에러만)",
  "gridPos": { "h": 10, "w": 24, "x": 0, "y": 21 },
  "datasource": { "type": "loki", "uid": "loki" },
  "options": {
    "showTime": true,
    "wrapLogMessage": true,
    "sortOrder": "Descending"
  },
  "targets": [
    {
      "refId": "A",
      "expr": "{namespace=\"$namespace\"} |= \"ERROR\""
    }
  ]
}
여기서만 uid 를 고정한다

로그 패널은 프로메테우스가 아니라 로키를 봐야 하므로 uid: loki 를 명시한다. 05장에서 “데이터소스를 지정하지 않는다”는 원칙을 세웠지만 데이터소스가 둘 이상인 대시보드에서는 예외다. 07절에서 값 파일에 uid: loki 를 못 박아 둔 것이 이것을 위해서다.

패널의 질의가 $namespace 를 쓰는 것도 눈여겨본다 — 07장에서 만든 같은 변수가 프로메테우스 패널과 로키 패널을 동시에 움직인다.

cd study/labs/monitoring
kubectl -n monitoring create configmap obs-red-dashboard \
  --from-file=obs-red.json=dashboards/obs-red.json \
  --dry-run=client -o yaml | kubectl apply -f -
kubectl -n monitoring label configmap obs-red-dashboard grafana_dashboard=1 --overwrite
kubectl -n monitoring annotate configmap obs-red-dashboard grafana_folder="Obs Study" --overwrite

11구조화 로그로 한 걸음 더

지금 로그는 사람이 읽기 좋은 텍스트다. 기계가 읽기에는 불편하다. | json 으로 필드를 뽑으려면 애플리케이션이 JSON 으로 찍어야 한다. Spring Boot 는 설정 한 줄로 지원한다.

study/labs/apps/order-api/src/main/resources/application.yml — 추가 
logging:
  structured:
    format:
      # ecs · logstash · gelf 중 선택. 로키에서는 어느 쪽이든 | json 으로 파싱된다.
      console: ecs

03장 redeploy.sh 로 태그를 올려 재배포한 뒤 로그를 다시 보면 한 줄이 JSON 객체로 바뀐다. 필드 이름은 형식에 따라 다르므로 실제 출력 한 줄을 먼저 확인하고 질의를 쓴다.

# JSON을 파싱하고 레벨로 거른다 (필드명은 실제 출력에 맞춰 조정)
{namespace="apps"} | json | log_level = "ERROR"

# 레벨별 로그 발생량
sum by (log_level) (count_over_time({namespace="apps"} | json [5m]))
요청 ID 는 라벨이 아니라 구조화 메타데이터로

“요청 ID 로 로그를 찾고 싶다”는 요구는 항상 나온다. 라벨에 넣으면 스트림이 폭증하고, 본문에만 두면 훑기가 느리다. 로키 3.x 의 구조화 메타데이터가 그 사이의 해법이다 — 색인되지 않지만 필드로 다룰 수 있다. 값 파일에 allow_structured_metadata: true 를 넣어 둔 이유다.

증상원인과 조치
차트 렌더링이 minio 관련 오류로 실패MinIO 서브차트는 폐기 예정이라 그냥 켜면 실패한다. storage.type: filesystem 을 쓰면 해당되지 않는다
