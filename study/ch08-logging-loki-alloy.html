로그 수집 (Loki + Alloy)

메트릭은 "무언가 이상하다"까지 알려주고 멈춥니다. 그다음 질문인 "무슨 일이 있었나"는 로그의 몫입니다. 로키를 올리고 Alloy로 파드 로그를 모은 뒤, 07장 대시보드와 같은 시간축에 놓습니다. 2026년 기준으로 Promtail은 쓰지 않으며, 차트 저장소도 바뀌었습니다.

01이론 — 무엇을, 얼마나, 어떻게 모으나

책 3.8 ~ 3.10 — 로그 수집은 메트릭과 화살표 방향이 반대다.

컨테이너의 로그는 표준 출력으로 나가고, 노드의 파일에 쌓인다. 그 파일은 파드가 사라지면 같이 사라진다. 사고를 조사할 때 필요한 로그가 대개 이미 사라진 로그라는 것이 로그 수집기를 두는 이유다.

수집기는 노드마다 하나씩(DaemonSet) 떠서 파일을 읽고 로키로 밀어 넣는다. 프로메테우스가 당겨 오는 것과 반대다.

검색하면 나오는 두 가지를 쓰지 않는다

Promtail은 2026-03-02 EOL이다. 지금 새로 구성하는 스택에서는 Grafana Alloy를 쓴다. 그리고 loki-stack 차트도 아니다 — 저장소는 grafana가 아니라 grafana-community다. 검색 결과 상위에 아직 둘 다 남아 있어 그대로 따라 하면 EOL 컴포넌트를 새로 설치하게 된다.

라벨이 아니라 내용으로 찾는다

로키는 로그 본문을 인덱싱하지 않는다. 인덱싱하는 것은 라벨뿐이고, 본문은 압축해 저장한다. 그래서 라벨을 많이 붙일수록 비용이 급격히 는다 — 메트릭의 카디널리티 문제와 정확히 같은 함정이다.

LogQL의 사고 순서도 여기서 나온다. 라벨로 먼저 좁히고, 좁혀진 스트림 안에서 문자열로 거른다. 라벨 없이 전체에서 문자열을 찾으면 느리다.

메트릭과 로그를 같은 시간축에

이 장의 마지막 검증은 07장에서 만든 알림이 울린 시각에 로그를 겹쳐 보는 것이다. 메트릭이 “언제 이상했는지”를 주고 로그가 “왜”를 주는 구조가 여기서 완성된다.

02로키는 어떻게 다른가

엘라스틱서치는 로그 본문 전체를 색인합니다. 검색은 빠르지만 저장 비용이 큽니다. 로키는 반대로 라벨만 색인하고 본문은 압축해 보관합니다. 이 설계 하나가 사용법의 거의 모든 것을 결정합니다.

03수집 경로와 구성요소

2026년에 바뀐 두 가지

① Promtail은 2026-03-02로 수명이 끝났습니다. 검색으로 나오는 대부분의 튜토리얼이 Promtail 기준이며, 설정 형식이 Alloy와 완전히 다릅니다. 복사하지 마세요.
② 로키 헬름 차트가 grafana-community 저장소로 이전했습니다(2026-03-16). grafana/loki 경로로는 원하는 차트를 받지 못합니다.

05Alloy 설치

Alloy 차트는 grafana 저장소에 있습니다. 로키 차트만 커뮤니티로 옮겨갔습니다. 헷갈리기 쉬우니 helm search repo로 한 번 확인하고 진행하세요. 

helm repo add grafana https://grafana.github.io/helm-charts
helm repo update
helm search repo grafana/alloy --versions | head -3

monitoring/alloy-values.yaml

alloy:
  configMap:
    content: |-
      logging {
        level  = "info"
        format = "logfmt"
      }

      // 1) 클러스터의 파드를 발견한다
      discovery.kubernetes "pods" {
        role = "pod"
      }

      // 2) 어떤 라벨을 붙일지 고른다. 여기서 고르지 않은 메타데이터는 버려진다.
      discovery.relabel "pod_logs" {
        targets = discovery.kubernetes.pods.targets

        rule {
          source_labels = ["__meta_kubernetes_namespace"]
          target_label  = "namespace"
        }
        rule {
          source_labels = ["__meta_kubernetes_pod_name"]
          target_label  = "pod"
        }
        rule {
          source_labels = ["__meta_kubernetes_pod_container_name"]
          target_label  = "container"
        }
        rule {
          source_labels = ["__meta_kubernetes_pod_label_app_kubernetes_io_name"]
          target_label  = "app"
        }
      }

      // 3) 쿠버네티스 API로 로그를 읽는다 (호스트 경로 마운트가 필요 없다)
      loki.source.kubernetes "pods" {
        targets    = discovery.relabel.pod_logs.output
        forward_to = [loki.write.default.receiver]
      }

      // 4) 로키로 밀어 넣는다
      loki.write "default" {
        endpoint {
          url = "http://loki-gateway.logging.svc.cluster.local/loki/api/v1/push"
        }
      }

  resources:
    requests:
      cpu: 50m
      memory: 128Mi
    limits:
      memory: 256Mi

# 노드마다 하나씩 뜨는 DaemonSet이 기본값이다
controller:
  type: daemonset
helm upgrade --install alloy grafana/alloy \
  --namespace logging \
  -f alloy-values.yaml \
  --wait --timeout 5m

kubectl -n logging get pods -o wide

Alloy 파드가 노드 수만큼(3개) 떠야 합니다. loki.source.kubernetes는 쿠버네티스 API를 통해 로그를 읽으므로 /var/log 호스트 마운트가 필요 없습니다 — macOS의 도커 VM 환경에서 문제가 덜 생기는 방식입니다. 

# Alloy가 로그를 밀어 넣고 있는지 자체 로그로 확인
kubectl -n logging logs -l app.kubernetes.io/name=alloy --tail=20 | head -20

# Alloy UI로 파이프라인 상태를 눈으로 본다 (컴포넌트별 healthy 여부)
kubectl -n logging port-forward svc/alloy 12345:12345 >/dev/null 2>&1 &
sleep 2
open http://localhost:12345

컴포넌트가 그래프로 그려지고 각각의 상태와 처리 건수가 보입니다. "로그가 안 들어온다"는 상황에서 어느 단계가 끊겼는지 즉시 알 수 있어, 설정 파일을 노려보는 것보다 훨씬 빠릅니다.

07LogQL 최소 문법

그라파나 Explore에서 데이터소스를 Loki로 바꾸고 아래를 차례로 입력하세요. PromQL과 닮았지만 반드시 라벨 셀렉터로 시작해야 한다는 점이 다릅니다.

1. 스트림 고르기

{namespace="apps"}
{namespace="apps", app="order-api"}

2. 본문 훑기

# 포함
{namespace="apps"} |= "ERROR"

# 제외
{namespace="apps"} |= "ERROR" != "ChaosController"

# 정규식 (대소문자 무시)
{namespace="apps"} |~ "(?i)exception|error"

3. 로그를 숫자로 바꾸기

# 5분 동안의 에러 로그 건수 — 파드별
sum by (pod) (count_over_time({namespace="apps"} |= "ERROR" [5m]))

# 초당 에러 로그 발생률 — 메트릭처럼 그래프로 그려진다
sum(rate({namespace="apps"} |= "ERROR" [5m]))
이것이 로그와 메트릭의 다리다

rate()를 씌우는 순간 로그가 시계열이 됩니다. 즉 로그 기반으로도 알림을 만들 수 있다는 뜻입니다. 다만 메트릭으로 잡을 수 있는 것을 굳이 로그로 세지는 마세요 — 비용도 지연도 로그 쪽이 훨씬 큽니다. "메트릭에 없는 사건"에만 쓰는 것이 원칙입니다.

연산자의미
|=문자열 포함
!=문자열 미포함
|~정규식 일치
!~정규식 불일치
| json / | logfmt본문을 파싱해 필드를 뽑는다 (09절)
count_over_time구간 내 로그 줄 수
rate초당 로그 발생률

08메트릭과 로그를 함께 보기

이 실습의 목적지입니다. 07장 대시보드에 로그 패널을 붙여 같은 시간축에서 그래프와 로그를 나란히 놓습니다.

1. 상황 만들기

end=$((SECONDS+120))
while [ "$SECONDS" -lt "$end" ]; do
  curl -s -o /dev/null "http://localhost:30080/api/chaos/error?rate=0.7"

echo "에러 주입 종료"

2. 대시보드에 로그 패널 추가

07장의 obs-red.json 맨 아래에 패널 하나를 더합니다. gridPos의 y는 마지막 패널(y:13, 높이 8) 다음인 21입니다.

monitoring/dashboards/obs-red.json — panels 배열 끝에 추가

{
  "type": "logs",
  "title": "앱 로그 (에러만)",
  "gridPos": { "h": 10, "w": 24, "x": 0, "y": 21 },
  "datasource": { "type": "loki", "uid": "loki" },
  "options": {
    "showTime": true,
    "wrapLogMessage": true,
    "sortOrder": "Descending"
  },
  "targets": [
    {
      "refId": "A",
      "expr": "{namespace=\"$namespace\"} |= \"ERROR\""
    }
  ]
}
여기서만 uid를 고정한다

로그 패널은 프로메테우스가 아닌 로키를 봐야 하므로 uid: loki를 명시합니다. 05장에서 데이터소스를 지정하지 않는 원칙을 세웠지만, 데이터소스가 둘 이상인 대시보드에서는 예외입니다. 그래서 06절에서 uid: loki를 값 파일에 못 박아 둔 것입니다. 

cd ~/k8s-observability/monitoring

kubectl -n monitoring create configmap obs-red-dashboard \
  --from-file=obs-red.json=dashboards/obs-red.json \
  --dry-run=client -o yaml | kubectl apply -f -

kubectl -n monitoring label configmap obs-red-dashboard grafana_dashboard=1 --overwrite
kubectl -n monitoring annotate configmap obs-red-dashboard grafana_folder="Obs Study" --overwrite

에러율 그래프가 솟은 지점에 마우스를 올리고, 아래 로그 패널에서 같은 시각의 줄을 찾습니다. "그래프가 언제 튀었나" → "그때 무슨 로그가 찍혔나"가 한 화면에서 이어지는 것이 이 시리즈에서 만들려던 상태입니다.

Explore의 분할 화면

09구조화 로그로 한 걸음 더

지금 로그는 사람이 읽기 좋은 텍스트입니다. 기계가 읽기에는 불편합니다. | json으로 필드를 뽑으려면 애플리케이션이 JSON으로 찍어야 합니다. Spring Boot는 이를 설정 한 줄로 지원합니다.

apps/order-api/src/main/resources/application.yml — 추가

logging:
  structured:
    format:
      # ecs · logstash · gelf 중 선택. 로키에서는 어느 쪽이든 | json 으로 파싱된다.
      console: ecs

03장 redeploy.sh로 태그를 올려 재배포한 뒤 로그를 다시 보면 한 줄이 JSON 객체로 바뀝니다. 필드 이름은 형식에 따라 다르므로 실제 출력 한 줄을 먼저 확인하고 질의를 씁니다. 

# JSON을 파싱하고 레벨로 거른다 (필드명은 실제 출력에 맞춰 조정)
{namespace="apps"} | json | log_level = "ERROR"

# 레벨별 로그 발생량
sum by (log_level) (count_over_time({namespace="apps"} | json [5m]))
구조화 메타데이터 — 라벨을 늘리지 않는 방법

"요청 ID로 로그를 찾고 싶다"는 요구는 항상 나옵니다. 라벨에 넣으면 스트림이 폭증하고, 본문에만 두면 훑기가 느려집니다. 로키 3.x의 구조화 메타데이터가 이 사이의 해법입니다 — 색인되지 않지만 필드로 다룰 수 있습니다. 값 파일에 allow_structured_metadata: true를 넣어둔 이유입니다. 요청 ID를 라벨이 아니라 구조화 메타데이터로 넣는 것이 이 시리즈에서 권하는 형태입니다.

10자주 겪는 문제

증상원인과 조치
차트 렌더링이 minio 관련 오류로 실패 MinIO 서브차트는 폐기 예정이라 그냥 켜면 실패한다. 이 실습처럼 storage.type: filesystem을 쓰면 해당되지 않는다
로키 파드가 기동 중 CrashLoopBackOff replication_factor가 1이 아니거나 schemaConfig가 없다. kubectl -n logging logs loki-0에 이유가 그대로 찍힌다
loki-read·loki-write 파드가 뜬다 deploymentMode가 적용되지 않았거나 다른 모드의 replicas를 0으로 두지 않았다
memcached 파드가 메모리를 크게 먹는다 캐시가 켜져 있다. chunksCache.enabled: false, resultsCache.enabled: false
Explore에서 No logs found 라벨 이름을 확인한다. 라벨 브라우저에서 실제 존재하는 라벨만 쓸 수 있다. Alloy의 relabel에서 만들지 않은 라벨은 없다
too many outstanding requests 시간 범위가 너무 넓거나 라벨 셀렉터가 느슨하다. 범위를 좁힌다
로그가 몇 분 뒤에야 보인다 정상 동작이다. 로키는 청크를 모아서 저장하므로 실시간이 아니다
Alloy 파드가 2개만 뜬다 노드 테인트나 리소스 부족. control-plane 노드에는 기본적으로 뜨지 않을 수 있다
디스크가 빠르게 찬다 retention_period를 줄이거나, 실습 후 네임스페이스를 삭제한다

11완료 체크리스트

  • kubectl -n logging get pods 에서 loki-0, loki-gateway, Alloy 3개가 Running
  • Alloy UI(12345)에서 컴포넌트 4개가 모두 healthy
  • 그라파나 데이터소스 목록에 Loki가 있고 Save & test가 통과
  • Explore에서 {namespace="apps"} 로 로그가 보인다
  • sum(rate({namespace="apps"} |= "ERROR" [5m])) 가 그래프로 그려진다
  • RED 대시보드 하단에 로그 패널이 붙어 있고 에러 로그가 보인다
  • 에러율 그래프가 튄 시각과 로그 시각이 맞아떨어진다
  • 부하 주입 루프와 포트포워드를 종료했다
