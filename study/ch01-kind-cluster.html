노드 3개짜리 로컬 클러스터를 만듭니다. 여기서 설정 파일 20줄을 제대로 쓰면 04장에서 프로메테우스 타깃이 전부 초록으로 뜨고, 대충 쓰면 kube-controller-manager· kube-scheduler·etcd·kube-proxy 네 개가 DOWN 상태로 남습니다. 그 차이를 만드는 것이 이 문서의 전부입니다.

01이론 — 설정 파일 20줄이 승부처다

이 장의 판돈 — 여기서 쓰는 클러스터 설정이 04장의 타깃 상태를 미리 결정한다.

kind는 도커 컨테이너를 노드처럼 쓰는 로컬 클러스터다. 실습에 쓰는 이유는 만들고 부수는 비용이 거의 없어서다 — 실습이 꼬이면 지우고 다시 만들면 된다. 클라우드 계정도 필요 없다.

그런데 기본 설정으로 만든 kind 클러스터에 프로메테우스를 설치하면 타깃 네 개가 DOWN으로 남는다. kube-controller-manager·kube-scheduler·etcd·kube-proxy다. 이유는 이 구성요소들이 기본적으로 127.0.0.1에만 바인드해서, 같은 클러스터 안의 프로메테우스조차 접근할 수 없기 때문이다.

먼저 막지 않으면 나중에 못 고친다

클러스터를 만든 뒤에 이 설정을 바꾸려면 컨트롤 플레인 노드에 들어가 매니페스트를 고치고 각 구성요소를 재시작해야 한다. 만들 때 설정 파일에 bindAddress를 적어 두는 것이 비교할 수 없이 싸다. 04장에서 타깃이 전부 초록으로 뜨는지 여부가 이 스무 줄에 달려 있다.

포트가 흐르는 경로

맥에서는 경로가 한 겹 더 있다. 도커 데스크톱이 리눅스 VM을 돌리고, 그 안에 kind 노드 컨테이너가 있고, 그 안에 파드가 있다. 브라우저에서 그라파나를 열려면 호스트 → VM → 노드 컨테이너 → 파드 네 칸을 전부 뚫어야 한다.

이 실습은 extraPortMappings로 노드 컨테이너의 NodePort를 호스트 포트에 직접 붙인다. kubectl port-forward는 터미널을 닫으면 끊기고 파드가 재시작하면 죽지만, 포트 매핑은 클러스터가 살아 있는 동안 유지된다. 8명이 같은 화면을 봐야 하는 실습에서는 이쪽이 사고가 적다.

클러스터 이름을 obs로 고정하는 이유

kind는 클러스터 이름을 컨테이너 이름과 kubeconfig 컨텍스트 이름에 그대로 씁니다. 이름을 obs로 정하면 컨테이너는 obs-control-plane, 컨텍스트는 kind-obs가 됩니다. 문서 전체가 이 이름을 전제로 하니 바꾸지 마세요. 기본값(kind)을 쓰면 기존에 만들어 둔 실습 클러스터와 충돌합니다.

03macOS에서 포트가 흐르는 경로

리눅스에서는 docker network의 IP로 컨테이너에 바로 접근할 수 있지만, macOS의 도커는 경량 VM 안에서 돕니다. 호스트에서 노드 컨테이너 IP(172.18.x.x)로 핑을 보내면 응답이 없습니다. 그래서 브라우저로 무언가를 열려면 경로가 두 개뿐입니다. extraPortMappings + NodePort, 또는 kubectl port-forward.

호스트 포트용도연결 시점
30080gateway (애플리케이션)03장
30300Grafana05장
30900Prometheus UI04장

04bind-address 문제 — 미리 막아야 하는 이유

kubeadm으로 만든 클러스터는 컨트롤 플레인 구성요소의 메트릭 포트를 루프백에만 엽니다. 보안상 합리적인 기본값이지만, 프로메테우스는 다른 노드의 파드에서 스크레이프를 시도하므로 연결 자체가 성립하지 않습니다. 04장에서 타깃 목록에 빨간 줄 네 개가 뜨는 원인이 이것입니다.

같은 이유로 손봐야 하는 대상이 넷입니다.

구성요소기본 바인딩패치 내용
kube-controller-manager127.0.0.1:10257bind-address: 0.0.0.0
kube-scheduler127.0.0.1:10259bind-address: 0.0.0.0
etcd메트릭 미분리listen-metrics-urls: http://0.0.0.0:2381 클라이언트 포트(2379)는 상호 TLS 인증이 필요하다. 2381은 메트릭 전용 포트로, 04장에서 이 포트를 스크레이프하도록 차트 값을 맞춘다
kube-proxy127.0.0.1:10249metricsBindAddress: 0.0.0.0:10249
프로덕션에서는 하지 말 것

0.0.0.0 바인딩은 노드의 모든 인터페이스에 메트릭 포트를 노출합니다. 로컬 kind 클러스터는 도커 VM 안에 갇혀 있어 실질적 노출이 없지만, 실제 노드에서는 방화벽으로 해당 포트를 노드 IP 대역으로 제한하거나 노드 IP만 바인딩하는 방식을 씁니다. 이 실습 설정을 그대로 사내 클러스터로 옮기지 마세요.

05클러스터 설정 파일 전문

작업 디렉터리를 하나 만들고 그 안에 파일을 둡니다. 이후 모든 단계가 이 디렉터리를 기준으로 진행됩니다. 

mkdir -p ~/k8s-observability/infra
cd ~/k8s-observability/infra

kind-cluster.yaml

kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
name: obs

# ── 컨트롤 플레인 메트릭을 클러스터 내부에서 스크레이프 가능하게 만드는 패치 ──
# kind v0.32.0 + Kubernetes 1.36 조합에서는 kubeadm v1beta4 포맷을 쓴다.
# v1beta3와 달리 extraArgs가 맵이 아니라 name/value 목록이다.
kubeadmConfigPatches:
  - |
    kind: ClusterConfiguration
    apiVersion: kubeadm.k8s.io/v1beta4
    controllerManager:
      extraArgs:
        - name: bind-address
          value: "0.0.0.0"
    scheduler:
      extraArgs:
        - name: bind-address
          value: "0.0.0.0"
    etcd:
      local:
        extraArgs:
          - name: listen-metrics-urls
            value: "http://0.0.0.0:2381"
  - |
    kind: KubeProxyConfiguration
    apiVersion: kubeproxy.config.k8s.io/v1alpha1
    metricsBindAddress: "0.0.0.0:10249"

nodes:
  - role: control-plane
    image: kindest/node:v1.36.1@sha256:3489c7674813ba5d8b1a9977baea8a6e553784dab7b84759d1014dbd78f7ebd5
    # 포트 매핑은 클러스터 생성 시점에만 정의할 수 있다. 나중에 못 늘린다.
    extraPortMappings:
      - containerPort: 30080      # gateway (03장)
        hostPort: 30080
        listenAddress: "127.0.0.1"
        protocol: TCP
      - containerPort: 30300      # Grafana (05장)
        hostPort: 30300
        listenAddress: "127.0.0.1"
        protocol: TCP
      - containerPort: 30900      # Prometheus UI (04장)
        hostPort: 30900
        listenAddress: "127.0.0.1"
        protocol: TCP

  - role: worker
    image: kindest/node:v1.36.1@sha256:3489c7674813ba5d8b1a9977baea8a6e553784dab7b84759d1014dbd78f7ebd5
    labels:
      workload: apps

  - role: worker
    image: kindest/node:v1.36.1@sha256:3489c7674813ba5d8b1a9977baea8a6e553784dab7b84759d1014dbd78f7ebd5
    labels:
      workload: observability

읽는 법 — 헷갈리기 쉬운 세 곳

  • 다이제스트를 노드마다 반복하는 것이 번거로우면 image: 줄을 모두 지우고 생성 시 --image 플래그로 한 번만 넘겨도 됩니다. 다만 파일만 공유했을 때 버전 정보가 사라지므로 스터디에서는 파일에 박아두는 쪽을 권합니다.
  • listenAddress: "127.0.0.1" 를 빼면 매핑이 0.0.0.0 으로 열려 같은 와이파이의 다른 기기에서 그라파나에 접근할 수 있게 됩니다. 카페에서 실습한다면 반드시 넣으세요.
  • labels 는 kind가 노드 등록 시 kubelet에 넘겨주는 값입니다. 클러스터를 만든 뒤 kubectl label 로 붙여도 결과는 같지만, 재생성할 때마다 다시 해야 합니다.
v1beta3 예제를 만났을 때

검색으로 나오는 대부분의 예제는 extraArgs: {bind-address: 0.0.0.0} 형태의 맵입니다. kind가 자동 변환을 시도하지만, 확실하게 하려면 위처럼 apiVersion을 명시한 목록 형식으로 쓰세요. Kubernetes 1.37부터는 kubeadm이 v1beta3 설정을 아예 받지 않습니다.

4. 컨트롤러 매니저·스케줄러 바인딩 주소

정적 파드 매니페스트를 직접 확인하는 것이 가장 확실합니다. kubelet이 이 파일을 읽어 파드를 띄우기 때문입니다. 

docker exec obs-control-plane \
  grep -h 'bind-address' \
  /etc/kubernetes/manifests/kube-controller-manager.yaml \
  /etc/kubernetes/manifests/kube-scheduler.yaml
    - --bind-address=0.0.0.0
    - --bind-address=0.0.0.0

127.0.0.1 이 나오면 패치가 적용되지 않은 것입니다. 설정 파일의 apiVersion: kubeadm.k8s.io/v1beta4 줄과 extraArgs 목록 형식을 다시 확인하고, 클러스터를 삭제한 뒤 다시 만드세요. 실행 중인 클러스터에 패치를 소급 적용할 수는 없습니다.

5. etcd 메트릭 포트

docker exec obs-control-plane \
  grep -h 'listen-metrics-urls' /etc/kubernetes/manifests/etcd.yaml
    - --listen-metrics-urls=http://0.0.0.0:2381

6. kube-proxy 메트릭 주소

kubectl -n kube-system get configmap kube-proxy \
  -o jsonpath='{.data.config\.conf}' | grep -E 'metricsBindAddress|mode:'
metricsBindAddress: 0.0.0.0:10249
mode: ""

mode가 비어 있으면 리눅스 기본값인 iptables 모드로 동작합니다. 2026년 기준 nftables 모드가 성능상 더 낫지만 아직 기본값은 아니며, 실습 규모에서는 차이가 없습니다.

7. 실제로 스크레이프가 되는지 (선택)

파드 안에서 노드 IP로 붙어봅니다. etcd 메트릭 포트는 인증이 없어 확인이 가장 간단합니다. 

NODE_IP=$(kubectl get node obs-control-plane \
  -o jsonpath='{.status.addresses[?(@.type=="InternalIP")].address}')
echo "control-plane InternalIP: ${NODE_IP}"

kubectl run etcd-check --rm -i --restart=Never \
  --image=curlimages/curl:latest -- \
  curl -s --max-time 5 "http://${NODE_IP}:2381/metrics" | head -3
# HELP etcd_cluster_version Which version is running. 1 for 'cluster_version' label with current cluster version
# TYPE etcd_cluster_version gauge
etcd_cluster_version{cluster_version="3.6"} 1

출력이 비어 있으면 4·5번 확인을 다시 하세요. 실습용이라 이미지 태그를 latest로 두었지만, 사내에서 쓸 때는 태그를 고정하는 것이 원칙입니다.

08macOS에서만 겪는 문제

포트 5000이 이미 잡혀 있다

macOS의 AirPlay 수신 기능이 5000번 포트를 씁니다. kind 공식 문서가 로컬 레지스트리에 5001을 쓰는 이유가 이것입니다. 5000을 쓰려면 시스템 설정 → 일반 → AirDrop 및 Handoff → AirPlay 수신 모드를 끄면 되지만, 그냥 5001을 쓰는 편이 낫습니다.

노드 컨테이너 IP로 접근이 안 된다

docker network inspect kind로 보이는 172.18.x.x 대역은 VM 내부 주소라 호스트에서 닿지 않습니다. 정상 동작입니다. docker exec는 되고 curl은 안 되는 이유가 여기 있습니다. 접근은 언제나 포트 매핑이나 kubectl port-forward로 합니다.

Apple Silicon에서의 이미지 아키텍처

위 다이제스트는 멀티 아키텍처 매니페스트를 가리키므로 M 시리즈 맥에서도 그대로 동작합니다. 다만 03장에서 만들 애플리케이션 이미지는 빌드한 아키텍처와 노드 아키텍처가 같아야 합니다. 인텔 맥과 M 시리즈 맥이 섞인 스터디라면 이미지를 서로 공유하지 말고 각자 빌드하세요.

Docker Desktop 설정 권장값

  • VirtioFS 파일 공유 — 기본값이며 gRPC FUSE보다 빠릅니다
  • Apple Virtualization framework 사용 — QEMU 대비 안정적입니다
  • Resources에서 CPU 4코어·메모리 10 GiB 이상

Docker Desktop 대신 OrbStack이나 Colima를 써도 kind는 동작합니다. 다만 포트 매핑·파일 공유 동작이 미묘하게 다르므로, 스터디 중 문제가 생기면 Docker Desktop 기준으로 맞추는 편이 시간을 아낍니다.

생성이 중간에 멈출 때

증상원인과 조치
failed to create cluster: ... timed out waiting for the condition 메모리 부족. Docker Desktop 할당을 10 GiB로 올리고 kind delete cluster --name obs 후 재시도
ERROR: failed to create cluster: node(s) already exist 같은 이름의 클러스터가 남아 있다. kind get clusters로 확인 후 삭제
Bind for 127.0.0.1:30300 failed: port is already allocated 다른 컨테이너가 그 포트를 쓰고 있다. lsof -nP -iTCP:30300 -sTCP:LISTEN로 범인 확인
파드가 Evicted / DiskPressure 도커 디스크 여유 부족. docker system prune -a로 정리

09삭제·재생성과 컨텍스트 관리

이 시리즈에서는 클러스터를 최소 두세 번 다시 만들게 됩니다. 재생성이 부담되지 않아야 설정을 과감하게 고칠 수 있습니다. 

# 클러스터 목록
kind get clusters

# 삭제 — 컨테이너와 kubeconfig 컨텍스트가 함께 지워진다
kind delete cluster --name obs

# 재생성
kind create cluster --config kind-cluster.yaml

# 컨텍스트 전환 (다른 클러스터를 함께 쓸 때)
kubectl config get-contexts
kubectl config use-context kind-obs
시간을 아끼는 습관

노드 이미지는 삭제해도 로컬에 남으므로 재생성은 2분이면 끝납니다. "설정을 고치려면 클러스터를 지워야 한다"는 제약을 부담으로 여기지 말고, 매니페스트를 고칠 때마다 지우고 다시 만드는 쪽이 상태가 꼬인 클러스터를 디버깅하는 것보다 훨씬 빠릅니다.

10부록 — 로컬 레지스트리(선택)

03장에서는 kind load docker-image로 이미지를 노드에 직접 밀어 넣습니다. 8명 실습에는 이 방식으로 충분합니다. 다만 이미지를 자주 고쳐 빌드하면 매번 3개 노드에 전송하느라 느려지므로, 그때는 로컬 레지스트리를 붙이는 편이 낫습니다.

방식전파 시간적합한 상황
kind load docker-image이미지당 20–60초배포 횟수가 적은 실습 (기본 선택)
로컬 레지스트리 + docker push5–10초코드를 고치며 반복 배포할 때

레지스트리를 쓰려면 클러스터 생성 전에 containerd 설정 패치가 필요합니다. 공식 문서의 스크립트가 최신 상태로 유지되고 있으니 그대로 쓰세요 — kind.sigs.k8s.io/docs/user/local-registry/. 핵심은 레지스트리 컨테이너를 127.0.0.1:5001에 띄우고, 노드의 containerd가 localhost:5001을 그 컨테이너로 라우팅하게 만드는 것입니다. 호스트와 파드 매니페스트가 같은 이름을 쓸 수 있게 하려는 장치입니다.

주의

kind v0.27부터 containerd 2.x를 쓰므로 레지스트리 설정은 config_path 방식이어야 합니다. 2023년 이전에 쓰인 registry.mirrors 인라인 방식 예제는 동작하지 않습니다. 또한 새 노드 이미지로 kind load를 쓰려면 kind 자체가 v0.32.0 이상이어야 합니다.
