쿠버네티스 관측성

kind 클러스터 구축

노드 3개짜리 로컬 클러스터를 만든다. 설정 파일 스무 줄을 제대로 쓰면 04장에서 프로메테우스 타깃이 전부 초록으로 뜨고, 대충 쓰면 네 개가 빨간 줄로 남는다.

01왜 이 장이 필요한가

00장에서 도구를 깔았지만 아직 클러스터가 없다. kubectl get nodes 를 쳐도 붙을 곳이 없다. 이 장에서 그 클러스터를 만든다.

만드는 것 자체는 명령 한 줄이다. 문제는 기본 설정으로 만든 클러스터에 04장의 프로메테우스를 설치하면 타깃 네 개가 DOWN 으로 남는다는 것이다. kube-controller-manager · kube-scheduler · etcd · kube-proxy 네 개다. 이 구성요소들은 메트릭 포트를 127.0.0.1 에만 열기 때문에, 같은 클러스터 안의 프로메테우스조차 접근하지 못한다.

더 곤란한 것은 만든 뒤에는 고치기 어렵다는 점이다. 컨트롤 플레인 노드에 들어가 정적 파드 매니페스트를 손으로 고치고 각 구성요소를 재시작해야 한다. 클러스터를 만드는 시점에 설정 파일 스무 줄을 적어 두는 것이 비교할 수 없이 싸다. 포트 매핑도 마찬가지다 — 나중에 포트 하나가 더 필요해지면 클러스터를 지우고 다시 만드는 수밖에 없다.

그래서 이 장은 “클러스터를 만든다”가 아니라 “04장에서 초록이 뜨는 클러스터를 만든다”가 목표다.

02알아야 할 개념

kind — 컨테이너 하나가 노드 하나다

kind(Kubernetes IN Docker)는 도커 컨테이너를 쿠버네티스 노드로 쓰는 도구다. 노드 이미지 kindest/node 안에 리눅스 한 벌과 kubelet · 컨테이너 런타임이 들어 있고, 그 컨테이너 안에서 kubeadm 이 돌아 클러스터가 선다.

실습에 쓰는 이유는 만들고 부수는 비용이 거의 없어서다. 상태가 꼬이면 지우고 2분이면 다시 만든다. 클라우드 계정도, 별도 VM 도 필요 없다. 대신 노드가 진짜 머신이 아니라는 데서 오는 차이가 몇 군데 있고, 이 장의 macOS 절이 그것을 다룬다.

컨트롤 플레인 구성요소는 각자 메트릭 포트를 연다

쿠버네티스 컨트롤 플레인은 하나의 프로그램이 아니라 네 개의 프로세스다. API 서버가 창구를 맡고, 스케줄러가 파드를 어느 노드에 둘지 정하고, 컨트롤러 매니저가 “원하는 상태”와 실제 상태를 맞추고, etcd 가 그 상태를 저장한다. 각자 자기 상태를 /metrics 로 내놓는다.

이 포트들은 기본적으로 루프백에만 열린다. 보안상 합리적인 기본값이다 — 노드에 로그인한 사람만 보라는 뜻이다. 하지만 프로메테우스는 다른 노드의 파드에서 접속을 시도하므로 연결 자체가 성립하지 않는다.

바인딩 주소 — 127.0.0.1 과 0.0.0.0

프로세스가 포트를 열 때 “어느 네트워크 인터페이스에서 받을 것인가”를 함께 정한다. 이것이 bind address다. 127.0.0.1 은 자기 자신에게서 온 연결만 받고, 0.0.0.0 은 모든 인터페이스에서 받는다. 포트 번호가 같아도 이 값이 다르면 밖에서는 “열려 있지 않은 포트”로 보인다.

이 설정을 사내 클러스터로 옮기지 않는다

0.0.0.0 바인딩은 노드의 모든 인터페이스에 메트릭 포트를 노출한다. 로컬 kind 클러스터는 도커 VM 안에 갇혀 있어 실질적 노출이 없지만, 실제 노드에서는 방화벽으로 포트를 노드 IP 대역에 제한하거나 노드 IP 만 바인딩한다. 실습 설정은 실습 설정이다.

정적 파드 — 설정이 파일로 남는다

컨트롤 플레인 구성요소는 정적 파드(static pod)로 뜬다. API 서버가 관리하는 보통의 파드와 달리, 노드의 kubelet 이 /etc/kubernetes/manifests/ 디렉터리의 YAML 을 직접 읽어 띄운다. API 서버가 죽어도 이것들이 떠 있어야 하므로 그렇게 만들어져 있다.

실습에서 이 사실이 유용한 이유는 설정이 적용됐는지 파일로 확인할 수 있기 때문이다. 06장 검증에서 docker exec 로 그 파일을 grep 한다.

이 장을 마치면 할 수 있는 것

  1. kind-cluster.yaml 의 각 줄이 어떤 결과를 만드는지 짚으며 클러스터를 만들 수 있다.
  2. 노드 3개가 도커 컨테이너 3개와 1:1 로 대응한다는 것을 두 명령으로 확인할 수 있다.
  3. 컨트롤 플레인 네 구성요소의 바인딩 주소가 0.0.0.0 인지 정적 파드 매니페스트에서 검증할 수 있다.
  4. 설정 파일을 틀렸을 때 kind 가 내는 에러 메시지를 읽고 어느 줄이 문제인지 찾을 수 있다.
  5. 클러스터를 지우고 다시 만드는 것을 부담 없이 할 수 있다.

03최종적으로 만들 것

이 장이 끝나면 노드 3개짜리 클러스터가 서 있고, 맥의 로컬 포트 3개가 그 클러스터 안으로 연결돼 있다. 아직 애플리케이션도 프로메테우스도 없다 — 그것들이 들어갈 자리를 만드는 것이 이 장이다.

클러스터의 모양 — 노드 3개와 호스트 포트 3개

  • 1 클러스터를 만든다. 이 명령 하나가 컨테이너 3개를 띄우고 쿠버네티스를 세운다. 명령 kind create cluster --config kind-cluster.yaml → 마지막 줄에 Set kubectl context to "kind-obs"
  • 2 컨테이너를 센다. 도커 관점이다. 확인 docker ps --filter name=obs- --format '{{.Names}}' → obs-control-plane · obs-worker · obs-worker2 세 줄
  • 3 같은 것을 쿠버네티스 관점에서 본다. 이름이 똑같다는 것이 핵심이다. 확인 kubectl get nodes -L workload → 세 줄 모두 Ready, WORKLOAD 열에 apps 와 observability

WHY이 모양을 만드는 설정 — kind-cluster.yaml 의 nodes

상자가 셋인 것도, 라벨이 apps 와 observability 인 것도 설정 파일에 그렇게 적혀 있기 때문이다. 05절에서 전문을 쓰기 전에, 그림과 대응하는 부분만 먼저 본다.

study/labs/infra/kind-cluster.yaml — nodes 부분 
name: obs                    # 컨테이너 이름의 접두사가 된다

nodes:                       # 항목 수 = 컨테이너 수 = 노드 수
  - role: control-plane      # → obs-control-plane
    image: kindest/node:v1.36.1@sha256:3489c767...
    extraPortMappings: ...   # 그림 2에서 다룬다

  - role: worker             # → obs-worker
    image: kindest/node:v1.36.1@sha256:3489c767...
    labels:
      workload: apps         # 그림의 초록 라벨

  - role: worker             # → obs-worker2
    image: kindest/node:v1.36.1@sha256:3489c767...
    labels:
      workload: observability   # 그림의 보라 라벨
설정 파일의 위치도커 컨테이너 이름노드 이름이 노드가 맡는 일
name: obs + 1번째 role: control-planeobs-control-plane같다컨트롤 플레인 네 구성요소. 호스트 포트가 들어오는 문
2번째 role: workerobs-worker같다workload: apps — gateway · order-api (03장)
3번째 role: workerobs-worker2같다workload: observability — 프로메테우스 · 그라파나 · 로키 (04·08장)

같은 역할이 둘 이상이면 두 번째부터 숫자가 붙는다. obs-worker1 이 아니라 obs-worker 다. 클러스터 이름을 빼면 접두사가 kind- 가 되어 이후 명령이 전부 어긋나므로 name: obs 는 지우지 않는다.

라벨을 설정 파일에 적는 것과 나중에 붙이는 것

kubectl label node obs-worker workload=apps 로 붙여도 결과는 같다. 다만 클러스터를 다시 만들 때마다 손으로 붙여야 한다. 설정 파일에 적으면 kind 가 노드를 등록할 때 kubelet 에 넘기므로 재생성해도 그대로다. 이 시리즈는 클러스터를 두세 번 다시 만들게 되므로 파일에 적는다.

맥에서 포트가 흐르는 경로

리눅스에서는 도커 네트워크의 IP 로 컨테이너에 바로 접근할 수 있다. 맥은 다르다. 도커가 경량 VM 안에서 돌기 때문에 호스트에서 노드 컨테이너 IP(172.18.x.x)로 핑을 보내도 응답이 없다. 브라우저로 무언가를 열려면 길이 두 개뿐이다 — extraPortMappings + NodePort, 또는 kubectl port-forward.

  • 1 맥의 포트가 노드 컨테이너로 뚫려 있는지. 클러스터를 만든 직후에 바로 확인할 수 있다. 확인 docker port obs-control-plane → 30080 · 30300 · 30900 이 127.0.0.1 로 매핑된 세 줄
  • 2 노드 IP 는 맥에서 닿지 않는다. 정상이라는 것을 확인해 둔다. 확인 kubectl get nodes -o wide → INTERNAL-IP 가 172.18.x.x. 이 주소로 curl 하면 응답이 없다
  • 3 길 전체가 이어졌는지는 05장에서 판정한다. 아직 그라파나가 없으므로 지금은 열리지 않는 것이 맞다. 확인 curl -s -o /dev/null -w '%{http_code}\n' http://localhost:30300/login → 05장 이후 200

WHY이 길을 뚫는 설정 — extraPortMappings

study/labs/infra/kind-cluster.yaml — control-plane 노드의 포트 매핑 
  - role: control-plane
    extraPortMappings:
      - containerPort: 30080        # 노드 컨테이너 안쪽 포트
        hostPort: 30080             # 맥에서 열리는 포트 — 브라우저가 치는 번호
        listenAddress: "127.0.0.1"  # 이 맥에서만 접근 가능
        protocol: TCP
      - containerPort: 30300        # Grafana (05장)
        hostPort: 30300
        listenAddress: "127.0.0.1"
        protocol: TCP
      - containerPort: 30900        # Prometheus UI (04장)
        hostPort: 30900
        listenAddress: "127.0.0.1"
        protocol: TCP
호스트 포트연결 대상실제로 붙는 시점이 번호를 정하는 다른 파일
30080gateway (애플리케이션)03장labs/k8s/20-gateway.yaml 의 nodePort
30300Grafana05장labs/monitoring/kps-values.yaml 의 grafana.service.nodePort
30900Prometheus UI04장labs/monitoring/kps-values.yaml 의 prometheus.service.nodePort

같은 번호가 두 파일에 적힌다. kind 쪽 containerPort 와 서비스 쪽 nodePort 가 어긋나면 포트는 열려 있는데 응답이 없다. 브라우저가 “연결할 수 없음”을 내면 kind 쪽이, 응답 없이 멈추면 서비스 쪽이 의심 대상이다.

매핑은 나중에 못 늘린다

extraPortMappings 는 클러스터를 만드는 시점에만 정의된다. 도커 컨테이너의 포트 매핑이 생성 시점에 고정되는 것과 같은 이유다. 그래서 지금 세 개를 넉넉히 뚫어 둔다. 뒤에서 포트 하나가 더 필요해지면 클러스터를 지우고 다시 만드는 수밖에 없다.

listenAddress 를 빼면

매핑이 0.0.0.0 으로 열려 같은 와이파이의 다른 기기에서 그라파나에 접근할 수 있게 된다. 그라파나 초기 비밀번호가 kps-values.yaml 에 평문으로 있는 실습 환경이므로, 카페나 공용 네트워크에서 실습한다면 이 줄을 반드시 넣는다.

왜 바인딩 주소를 미리 바꾸는가

여기까지가 “연결”의 이야기라면, 다음은 “수집”의 이야기다. 04장에서 프로메테우스를 설치했을 때 타깃이 초록으로 뜨는지 여부가 지금 적는 설정에 달려 있다.

  • 1 컨트롤러 매니저와 스케줄러. 정적 파드 매니페스트에 패치가 들어갔는지 본다. 확인 docker exec obs-control-plane grep -h bind-address /etc/kubernetes/manifests/kube-controller-manager.yaml /etc/kubernetes/manifests/kube-scheduler.yaml → --bind-address=0.0.0.0 두 줄
  • 2 etcd 는 포트가 따로다. 2379 가 아니라 메트릭 전용 2381 이다. 확인 docker exec obs-control-plane grep -h listen-metrics-urls /etc/kubernetes/manifests/etcd.yaml → --listen-metrics-urls=http://0.0.0.0:2381

WHY바인딩을 바꾸는 설정 — kubeadmConfigPatches

kind 는 노드 컨테이너 안에서 kubeadm 을 돌린다. 그 kubeadm 에 넘길 설정을 덧씌우는 자리가 kubeadmConfigPatches 다. 문자열 블록 안의 내용은 kind 문법이 아니라 kubeadm 문법이라서, apiVersion 을 따로 적는다.

study/labs/infra/kind-cluster.yaml — 네 구성요소의 바인딩 패치 
kubeadmConfigPatches:
  - |
    kind: ClusterConfiguration
    apiVersion: kubeadm.k8s.io/v1beta4
    controllerManager:
      extraArgs:
        - name: bind-address        # v1beta4 는 맵이 아니라 name/value 목록이다
          value: "0.0.0.0"
    scheduler:
      extraArgs:
        - name: bind-address
          value: "0.0.0.0"
    etcd:
      local:
        extraArgs:
          - name: listen-metrics-urls
            value: "http://0.0.0.0:2381"
  - |
    kind: KubeProxyConfiguration
    apiVersion: kubeproxy.config.k8s.io/v1alpha1
    metricsBindAddress: "0.0.0.0:10249"
구성요소기본 바인딩패치 내용왜 이 포트인가
kube-controller-manager127.0.0.1:10257bind-address: 0.0.0.0HTTPS 메트릭 포트. 토큰 인증이 걸려 있다
kube-scheduler127.0.0.1:10259bind-address: 0.0.0.0위와 같다
etcd메트릭 포트 미분리listen-metrics-urls: http://0.0.0.0:2381클라이언트 포트 2379 는 상호 TLS 가 필요하다. 2381 은 메트릭 전용이라 인증이 없다
kube-proxy127.0.0.1:10249metricsBindAddress: 0.0.0.0:10249kube-proxy 는 ConfigMap 으로 설정되므로 패치 블록이 따로다
검색으로 나오는 v1beta3 예제를 그대로 쓰지 않는다

예전 형식은 extraArgs: {bind-address: "0.0.0.0"} 처럼 맵이었다. v1beta4 는 - name: / value: 목록이다. 맵 형식을 쓰면 kind 가 설정 파일을 받아들이는 데까지는 성공하고 클러스터 생성 도중에 kubeadm 이 실패하므로, 원인을 찾기가 훨씬 번거롭다. apiVersion 을 명시해 두면 이런 혼동이 없다.

헷갈리기 쉬운 세 곳

다이제스트를 노드마다 반복하는 것이 번거로우면 image: 줄을 모두 지우고 생성할 때 --image 플래그로 한 번만 넘겨도 된다. 다만 파일만 공유했을 때 버전 정보가 사라지므로 이 교재는 파일에 박아 두는 쪽을 쓴다. 태그(v1.36.1)만 적고 다이제스트를 빼면 같은 태그가 다른 내용을 가리키게 될 수 있다 — 태그는 옮겨 달 수 있고 다이제스트는 못 옮긴다.

listenAddress 를 빼면 매핑이 모든 인터페이스에 열린다. 그림 2의 경고와 같은 이야기다.

labels 는 kind 가 노드를 등록할 때 kubelet 에 넘기는 값이다. 클러스터를 만든 뒤 kubectl label 로 붙여도 결과는 같지만, 재생성할 때마다 다시 해야 한다.

07일부러 실패시키기 — 설정 파일이 틀렸을 때

설정 파일을 틀리는 경로는 두 가지다. kind 가 파일을 읽는 단계에서 막히는 것과 파일은 통과했는데 클러스터 생성 도중에 실패하는 것이다. 앞쪽은 1초 만에 끝나고 컨테이너를 하나도 만들지 않는다. 뒤쪽은 몇 분을 쓰고 나서야 실패한다. 어느 쪽인지 구분할 줄 알면 디버깅 시간이 크게 줄어든다.

아래 세 메시지는 kind v0.33.0 에서 재현한 것이다 (확인 2026-09-13). 컨테이너는 생성되지 않으므로 안전하게 따라 해도 된다.

실패 1 — 필드 이름 오타

extraPortMappings 를 단수로 적는 실수는 흔하다. 복수형이다.

cat > /tmp/bad1.yaml <<'EOF'
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
name: obs
nodes:
  - role: control-plane
    extraPortMapping:
      - containerPort: 30300
        hostPort: 30300
EOF

kind create cluster --config /tmp/bad1.yaml

--- 출력 ---

ERROR: failed to create cluster: unable to decode config: yaml: unmarshal errors:
  line 6: field extraPortMapping not found in type v1alpha4.Node
읽는 법

line 6 — 파일의 몇째 줄인지 알려준다. not found in type v1alpha4.Node — 그 줄이 nodes: 항목 안에 있는데 v1alpha4 스키마의 노드에 그런 필드가 없다는 뜻이다. 필드 이름 오타는 전부 이 형태로 잡힌다. 컨테이너는 하나도 만들어지지 않았으므로 정리할 것도 없다.

실패 2 — 오래된 apiVersion

검색으로 나오는 몇 해 전 예제에는 v1alpha3 가 적혀 있다.

cat > /tmp/bad2.yaml <<'EOF'
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha3
name: obs
nodes:
  - role: control-plane
EOF

kind create cluster --config /tmp/bad2.yaml

--- 출력 ---

ERROR: failed to create cluster: unknown apiVersion: kind.x-k8s.io/v1alpha3
읽는 법

줄 번호가 없다. 파일을 파싱하기 전에 “어느 스키마로 읽을지”를 정하는 단계에서 막혔기 때문이다. 현재 kind 의 클러스터 설정은 v1alpha4 하나뿐이다. 예제를 복사해 왔을 때 가장 먼저 볼 줄이 이 줄이다.

실패 3 — 컨트롤 플레인이 없는 구성

워커만 적어도 스키마상으로는 올바른 YAML 이다. 그래도 클러스터는 성립하지 않는다.

cat > /tmp/bad3.yaml <<'EOF'
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
name: obs
nodes:
  - role: worker
    labels:
      workload: apps
EOF

kind create cluster --config /tmp/bad3.yaml

--- 출력 ---

ERROR: failed to create cluster: must have at least one control-plane node
읽는 법

문법이 아니라 의미를 검사해 막은 것이다. 앞의 둘과 달리 “어느 줄”이 아니라 “무엇이 없다”를 말한다. kind 의 설정 검증은 이렇게 두 겹이다 — 스키마 검사를 통과한 뒤 의미 검사를 한다.

여기서 막히지 않는 실수

반대로 설정 파일 검사를 통과해 버리는 실수가 더 곤란하다. 대표가 kubeadmConfigPatches 안의 내용이다. kind 에게 그 블록은 그냥 문자열이라 내용을 검사하지 않는다. v1beta3 의 맵 형식(extraArgs: {bind-address: "0.0.0.0"})을 적어도 파일은 통과하고, 노드 컨테이너가 뜬 뒤 kubeadm 이 실패하거나 설정이 조용히 무시된다. 몇 분을 쓰고 나서야 알게 되므로, 06장 검증의 4·5·6번을 매번 돌리는 이유가 이것이다.

실수언제 드러나나비용
필드 이름 오타 · 잘못된 apiVersion · 컨트롤 플레인 누락명령을 치자마자1초. 컨테이너도 안 만든다
패치 블록 안의 형식 오류클러스터가 뜬 뒤 검증 단계에서2~5분 + 재생성
포트 번호 불일치 (kind ↔ 서비스)04·05장에서 브라우저가 안 열릴 때장을 하나 건너뛴 뒤에 발견

08맥에서만 겪는 문제

포트 5000이 이미 잡혀 있다

macOS 의 AirPlay 수신 기능이 5000번 포트를 쓴다. kind 공식 문서가 로컬 레지스트리에 5001을 쓰는 이유가 이것이다. 시스템 설정 → 일반 → AirDrop 및 Handoff → AirPlay 수신 모드를 끄면 5000을 쓸 수 있지만, 그냥 5001을 쓰는 편이 낫다.

노드 컨테이너 IP 로 접근이 안 된다

docker network inspect kind 로 보이는 172.18.x.x 대역은 VM 내부 주소라 호스트에서 닿지 않는다. 정상 동작이다. docker exec 는 되는데 curl 은 안 되는 이유가 여기 있다. 접근은 언제나 포트 매핑이나 kubectl port-forward 로 한다.

Apple Silicon 에서의 이미지 아키텍처

설정 파일의 다이제스트는 멀티 아키텍처 매니페스트를 가리키므로 M 시리즈 맥에서도 그대로 동작한다. 다만 03장에서 만들 애플리케이션 이미지는 빌드한 아키텍처와 노드 아키텍처가 같아야 한다. 인텔 맥과 M 시리즈 맥이 섞인 스터디라면 이미지를 서로 공유하지 말고 각자 빌드한다.

09삭제와 재생성

이 시리즈에서는 클러스터를 최소 두세 번 다시 만들게 된다. 재생성이 부담되지 않아야 설정을 과감하게 고칠 수 있다.

# 클러스터 목록
kind get clusters

# 삭제 — 컨테이너와 kubeconfig 컨텍스트가 함께 지워진다
kind delete cluster --name obs

# 재생성
kind create cluster --config kind-cluster.yaml

# 컨텍스트 전환 (다른 클러스터를 함께 쓸 때)
kubectl config get-contexts
kubectl config use-context kind-obs
지우고 다시 만드는 쪽이 빠르다

노드 이미지는 클러스터를 지워도 로컬에 남으므로 재생성은 2분이면 끝난다. “설정을 고치려면 클러스터를 지워야 한다”는 제약을 부담으로 여기지 말 것 — 상태가 꼬인 클러스터를 디버깅하는 것보다 훨씬 빠르다.

부록 D. 선택 — 로컬 레지스트리

03장에서는 kind load docker-image 로 이미지를 노드에 직접 밀어 넣는다. 여덟 명 규모 실습에는 이 방식으로 충분하다. 다만 이미지를 자주 고쳐 빌드하면 매번 노드 3개에 전송하느라 느려진다.

방식전파 시간적합한 상황
kind load docker-image이미지당 20–60초배포 횟수가 적은 실습 (기본 선택)
로컬 레지스트리 + docker push5–10초코드를 고치며 반복 배포할 때

레지스트리를 쓰려면 클러스터 생성 전에 containerd 설정 패치가 필요하다. 공식 문서의 스크립트가 최신 상태로 유지되고 있으니 그대로 쓴다 — kind.sigs.k8s.io/docs/user/local-registry/. 핵심은 레지스트리 컨테이너를 127.0.0.1:5001 에 띄우고, 노드의 containerd 가 localhost:5001 을 그 컨테이너로 라우팅하게 만드는 것이다. 호스트와 파드 매니페스트가 같은 이름을 쓸 수 있게 하려는 장치다.

낡은 예제 주의

kind v0.27 부터 containerd 2.x 를 쓰므로 레지스트리 설정은 config_path 방식이어야 한다. 2023년 이전에 쓰인 registry.mirrors 인라인 방식 예제는 동작하지 않는다.
