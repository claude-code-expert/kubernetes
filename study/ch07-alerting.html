06장에서 쓴 질의를 대시보드 패널과 알림 규칙으로 옮깁니다. 기술적으로는 어렵지 않습니다. 어려운 것은 무엇을 넣지 않을지 정하는 일입니다. 패널 30개짜리 대시보드와 알림 40개는 아무도 보지 않게 되고, 결국 없는 것과 같아집니다.

01이론 — 알림은 양날의 검

책 3.11 — 그래프를 늘리는 것과 알림을 늘리는 것은 둘 다 관측을 나쁘게 만든다.

정보가 많으면 모니터링이 잘 되는 것 같지만 반대다. 패널이 40개인 대시보드는 아무도 보지 않는다. 이것을 그래프의 장벽이라 부른다. 한 화면은 하나의 질문에 답해야 하고, 이 실습의 RED 대시보드는 “지금 서비스가 정상인가”라는 질문 하나에만 답한다.

알림도 같은 함정이 있다. 울리는데 아무도 안 보는 알림은 없는 것보다 나쁘다 — 진짜 알림까지 같이 무시하게 만들기 때문이다. 알림은 사람이 지금 무언가를 해야 하는 것만 만든다. 나머지는 대시보드에 둔다.

발화까지의 네 구간

임계를 넘긴 순간과 슬랙에 메시지가 뜨는 순간 사이에는 네 개의 지연이 있다. 이 장에서는 각 구간을 실제로 재고, 어느 설정이 어느 구간을 정하는지 짚는다.

구간정하는 것
스크레이프 간격이상이 메트릭에 반영되기까지
규칙 평가 주기프로메테우스가 조건을 다시 계산하기까지
for조건이 계속 참이어야 하는 시간. 순간적인 튐을 걸러낸다
group_wait알림매니저가 같은 그룹을 모으는 시간

for를 0으로 두면 스파이크 한 번에 울리고, 10분으로 두면 진짜 장애를 10분 늦게 안다. 공짜인 값이 없다는 것이 이 표의 요점이다.

규칙에도 라벨이 필요하다

PrometheusRule 역시 release 라벨이 있어야 프로메테우스가 집어 간다. 이 장에서 라벨을 빼고 적용해 규칙이 조용히 무시되는 것을 먼저 본다.

02대시보드 한 장의 구조

대시보드는 트리아지 도구입니다. "지금 문제가 있는가"를 3초 안에 답하고, 그다음 "어디인가"로 좁혀가야 합니다. 위에서 아래로 읽는 순서가 곧 그 절차가 되도록 배치합니다.

03변수로 재사용 가능하게

서비스마다 대시보드를 복제하면 관리가 무너집니다. 변수를 쓰면 화면 하나로 모든 서비스를 봅니다. 변수는 세 개를 씁니다.

변수타입정의
datasourcedatasource 데이터소스를 고르게 한다. 대시보드 이식성의 핵심 — uid를 고정하지 않아도 어느 환경에서나 동작한다
namespacequery label_values(http_server_requests_seconds_count, namespace)
servicequery label_values(http_server_requests_seconds_count{namespace="$namespace"}, service) 다중 선택과 All을 허용한다
05장과 달라진 점

05장 예제에서는 datasource 필드를 아예 생략해 기본 데이터소스를 쓰게 했습니다. 패널만 있을 때는 그것으로 충분하지만, 쿼리 변수는 데이터소스를 명시해야 값을 채울 수 있습니다. 그래서 datasource 타입 변수를 만들고 ${datasource}로 참조합니다. 결과적으로 uid를 박아넣지 않으면서도 변수가 동작합니다.

06알림 규칙의 문법

알림은 "질의 결과가 비어 있지 않으면 발생"이라는 단순한 규칙입니다. 핵심은 for입니다. 이 값이 없으면 한 번 튄 값에도 알림이 울립니다.

07PrometheusRule 작성

k8s/monitoring/91-prometheusrule.yaml

apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: obs-study-app-rules
  namespace: apps
  labels:
    # ServiceMonitor와 같은 이유로 필요하다 (06장 ①번 고리)
    release: kps
spec:
  groups:
    - name: obs-study-app
      # 이 그룹의 규칙을 얼마나 자주 평가할지
      interval: 30s
      rules:
        - alert: AppTargetDown
          expr: up{namespace="apps"} == 0
          for: 1m
          labels:
            severity: critical
          annotations:
            summary: "{{ $labels.service }} 스크레이프 실패"
            description: "{{ $labels.pod }} 를 1분 이상 긁지 못하고 있습니다."

        - alert: AppHighErrorRate
          expr: |
            100 * (
              sum by (service) (
                rate(http_server_requests_seconds_count{namespace="apps", status=~"5.."}[5m])
              )
              /
              sum by (service) (
                rate(http_server_requests_seconds_count{namespace="apps"}[5m])
              )
            ) > 5
          for: 2m
          labels:
            severity: warning
          annotations:
            summary: "{{ $labels.service }} 에러율 {{ $value | printf \"%.1f\" }}%"
            description: "5xx 비율이 2분 이상 5%를 넘고 있습니다."

        - alert: AppHighLatencyP95
          expr: |
            histogram_quantile(0.95,
              sum by (le, service) (
                rate(http_server_requests_seconds_bucket{namespace="apps"}[5m])
              )
            ) > 0.5
          for: 3m
          labels:
            severity: warning
          annotations:
            summary: "{{ $labels.service }} P95 {{ $value | printf \"%.2f\" }}초"
            description: "P95 응답 시간이 3분 이상 500ms를 넘고 있습니다."

        - alert: OrderRejectionSpike
          expr: sum(rate(orders_rejected_total[5m])) > 0.2
          for: 5m
          labels:
            severity: info
          annotations:
            summary: "주문 거부가 늘고 있습니다"
            description: "초당 거부 건수가 5분 이상 0.2를 넘습니다. 클라이언트 오류 가능성."
kubectl apply -f 91-prometheusrule.yaml

# 프로메테우스가 규칙을 실제로 읽었는지 (읽는 데 30초 정도 걸린다)
sleep 40
curl -s http://localhost:30900/api/v1/rules \

임계값은 어떻게 정하나

위 숫자(5%, 500ms)는 예시일 뿐입니다. 실제로는 과거 데이터를 보고 정합니다 — 평소 P95가 200ms인 서비스에 500ms 임계값은 합리적이지만, 평소가 800ms인 서비스에는 매분 울리는 알림이 됩니다. 06장에서 만든 그래프를 며칠 관찰한 뒤 정하는 것이 정석이고, 급하면 "평소값의 2~3배"에서 시작해 조정합니다.

08Alertmanager 라우팅

프로메테우스는 알림을 발생시키고, Alertmanager는 그것을 묶고 억제하고 보냅니다. 값 파일에 라우팅을 정의합니다.

monitoring/kps-values.yaml — alertmanager 블록을 아래로 교체

alertmanager:
  alertmanagerSpec:
    nodeSelector:
      workload: observability
    resources:
      requests:
        cpu: 20m
        memory: 96Mi
      limits:
        memory: 192Mi

  # 이 블록을 쓰면 차트 기본 설정을 전부 대체한다.
  # Watchdog 처리와 억제 규칙을 빠뜨리면 안 되는 이유다.
  config:
    global:
      resolve_timeout: 5m

    route:
      # 같은 네임스페이스·같은 알림이면 한 덩어리로 묶어 보낸다
      group_by: ["namespace", "alertname"]
      # 첫 알림을 30초 기다렸다가 보낸다 — 연달아 터지는 것을 한 번에 묶기 위해
      group_wait: 30s
      # 같은 그룹에 새 알림이 추가되면 5분 간격으로 다시 보낸다
      group_interval: 5m
      # 해결되지 않은 알림을 4시간마다 재통보
      repeat_interval: 4h
      receiver: study-default
      routes:
        # Watchdog은 "모니터링이 살아있다"를 알리는 상시 알림이다. 버린다.
        - receiver: "null"
          matchers:
            - alertname =~ "InfoInhibitor|Watchdog"
        - receiver: study-critical
          matchers:
            - severity = "critical"

    # critical이 울리는 동안 같은 대상의 warning/info는 숨긴다
    inhibit_rules:
      - source_matchers:
          - severity = "critical"
        target_matchers:
          - severity =~ "warning|info"
        equal: ["namespace", "alertname"]

    receivers:
      - name: "null"
      - name: study-default
      - name: study-critical
      # 슬랙 웹훅이 있다면 위 receiver에 아래를 붙인다.
      # slack_configs:
      #   - api_url: https://hooks.slack.com/services/XXX/YYY/ZZZ
      #     channel: "#obs-study"
      #     send_resolved: true
cd ~/k8s-observability/monitoring

helm upgrade kps prometheus-community/kube-prometheus-stack \
  --namespace monitoring \
  --version 88.3.0 \
  -f kps-values.yaml \
  --wait --timeout 10m

라우팅이 의도대로 되는지 시뮬레이션

Alertmanager 이미지에는 amtool이 들어 있습니다. 실제로 알림을 터뜨리지 않고도 "이 라벨이면 어느 수신자로 가는가"를 확인할 수 있습니다. 

AM_POD=$(kubectl -n monitoring get pod \
  -l app.kubernetes.io/name=alertmanager \
  -o jsonpath='{.items[0].metadata.name}')
CFG=/etc/alertmanager/config_out/alertmanager.env.yaml

# 라우팅 트리 전체 보기
kubectl -n monitoring exec "$AM_POD" -c alertmanager -- \
  amtool config routes --config.file="$CFG"

# 특정 라벨 조합이 어디로 가는지
kubectl -n monitoring exec "$AM_POD" -c alertmanager -- \
  amtool config routes test --config.file="$CFG" \
  severity=critical namespace=apps alertname=AppTargetDown

study-critical이 출력되면 라우팅이 맞습니다. 설정 파일 경로가 다르면 kubectl exec ... -- ls /etc/alertmanager/config_out/로 확인하세요. 오퍼레이터 버전에 따라 파일명이 달라질 수 있습니다.

Silence — 알림을 잠시 끄기

계획된 배포나 실습 중에는 알림을 잠시 꺼두는 것이 정상적인 운영입니다. Alertmanager UI의 Silences에서 라벨 조건과 기간을 지정합니다. "시끄러우니 규칙을 지운다"와 "잠시 침묵시킨다"는 완전히 다릅니다. 전자는 다시 켜지지 않습니다.

10알림을 몇 개 만들 것인가

kube-prometheus-stack은 이미 수십 개의 기본 규칙을 설치했습니다. 거기에 우리 규칙을 얹으면 금세 백 개가 넘습니다. 기준이 필요합니다.

기준내용
사람이 행동할 수 있는가 받고 나서 할 일이 없다면 알림이 아니라 대시보드 패널이어야 한다. 이것 하나만 지켜도 알림 수가 절반으로 준다
증상인가 원인인가 "P95가 느리다"(증상)로 알리고, "GC가 잦다"(원인)는 대시보드에서 찾는다. 원인마다 알림을 만들면 하나의 장애에 알림 열 개가 쏟아진다
야간에 깨울 만한가 severity를 나누는 실질적 기준. critical만 호출하고 warning은 근무 시간에 본다
지난달에 울렸는가 한 번도 안 울린 알림과 매일 울린 알림은 둘 다 문제다. 정기적으로 발생 이력을 검토해 정리한다

기준Alertmanager (이 실습)Grafana Alerting

둘을 동시에 쓰는 것은 권하지 않습니다. 같은 장애에 두 경로로 알림이 오면 "이건 어디서 온 알림이지"부터 확인하게 됩니다. 이 실습이 Alertmanager를 택한 이유는 규칙이 클러스터 리소스로 남아 저장소에서 이력을 추적할 수 있기 때문입니다.
