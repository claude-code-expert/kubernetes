쿠버네티스 관측성

대시보드와 알림

06장에서 쓴 질의를 패널과 알림 규칙으로 옮긴다. 기술은 어렵지 않다. 어려운 것은 무엇을 넣지 않을지 정하는 일이다.

01왜 이 장이 필요한가

06장에서 질의 여섯 개를 만들었다. 그런데 그 질의들은 누군가 터미널에서 실행할 때만 값을 낸다. 새벽 세 시에 에러율이 20% 로 뛰어도 아무도 모른다.

그래서 두 가지를 만든다. 질의를 항상 떠 있는 화면으로 옮기고(대시보드), 조건을 넘으면 사람을 부르게 한다(알림).

다만 둘 다 늘리면 늘릴수록 나빠지는 물건이다. 패널이 40개인 대시보드는 아무도 보지 않고, 울리는데 아무도 안 보는 알림은 없는 것보다 나쁘다 — 진짜 알림까지 같이 무시하게 만들기 때문이다. 이 장에서 만드는 것은 패널 일곱 개와 알림 네 개뿐이고, 그 숫자를 지키는 근거가 이 장의 절반이다.

02알아야 할 개념

그래프의 장벽

책 3.11

정보가 많으면 모니터링이 잘 되는 것 같지만 반대다. 한 화면은 하나의 질문에 답해야 한다. 이 실습의 RED (Rate, Errors, Duration · 애플리케이션을 보는 세 지표) 대시보드는 “지금 서비스가 정상인가”에만 답한다. JVM (Java Virtual Machine · 자바 가상 머신) 힙이나 GC (Garbage Collection · 쓰지 않는 메모리를 회수하는 동작) 는 이 화면이 아니라 별도의 심층 대시보드에 둔다 — “응답이 느리다”를 확인한 다음에 보는 지표이기 때문이다.

임계를 넘은 순간과 알림이 오는 순간 사이

네 개의 지연이 겹쳐 있다. 각 구간을 어느 설정이 정하는지 알아야 “왜 5분이나 걸렸나”에 답할 수 있다.

구간정하는 설정이 실습의 값최악의 경우
이상이 메트릭에 반영되기까지scrapeInterval (04장)30초30초
프로메테우스가 조건을 다시 계산하기까지규칙 그룹의 interval30초30초
조건이 계속 참이어야 하는 시간for1~5분for 값 그대로
알림매니저가 같은 그룹을 모으는 시간group_wait30초30초

for: 2m 인 알림은 최악의 경우 30초 + 30초 + 2분 + 30초 ≈ 3분 30초 뒤에 슬랙에 뜬다. for 를 0 으로 두면 스파이크 한 번에 울리고, 10분으로 두면 진짜 장애를 10분 늦게 안다. 공짜인 값이 없다는 것이 이 표의 요점이다.

알림에는 세 가지 상태가 있다

조건이 참이 되는 순간 바로 울리지 않는다. pending 을 거친다. 이 상태를 프로메테우스 /alerts 화면에서 눈으로 보는 것이, 규칙이 동작하는지 확인하는 가장 빠른 방법이다.

묶기와 억제

파드 10개가 동시에 죽으면 알림도 10개다. Alertmanager 는 이것을 그룹화로 한 덩어리로 묶고, 억제로 “심각한 알림이 울리는 동안 같은 대상의 가벼운 알림은 숨긴다”를 처리한다. 프로메테우스는 알림을 발생시킬 뿐이고, 묶고 보내는 것은 전부 Alertmanager 의 일이다.

이 장을 마치면 할 수 있는 것

  1. 변수를 쓴 대시보드 하나로 여러 서비스를 보고, 패널을 늘리자는 요청에 근거를 들어 답할 수 있다.
  2. 알림이 inactive → pending → firing 으로 바뀌는 것을 직접 관찰할 수 있다.
  3. “왜 알림이 3분 뒤에 왔나”를 네 구간으로 분해해 설명할 수 있다.
  4. amtool 로 알림을 터뜨리지 않고 라우팅을 검증할 수 있다.
  5. 규칙의 PromQL (Prometheus Query Language · 프로메테우스 질의 언어) 문법 오류가 적용 시점에 걸린다는 것을 확인할 수 있다.

03최종적으로 만들 것

패널 일곱 개짜리 대시보드 한 장과 알림 규칙 네 개. 그리고 에러를 주입해 알림이 실제로 firing 이 되는 것까지 본다.

대시보드 한 장의 구조

  • 1 3초 안에 답이 나오는가. 맨 윗줄 숫자 네 개만 보고 정상 여부를 판정할 수 있어야 한다. 확인 그라파나에서 대시보드를 열고 상단 stat 4개에 값이 채워져 있다
  • 2 변수가 동작하는가. 드롭다운에서 서비스를 바꾸면 아래 그래프가 따라 바뀐다. 확인 service 를 order-api 로 바꾸면 처리율 그래프의 선이 하나만 남는다
  • 3 상세까지 내려갈 수 있는가. 맨 아래 패널이 “어느 요청”을 지목한다. 확인 하단 패널 범례에 /api/orders 같은 템플릿 경로가 보인다

05장과 달라진 점 — 여기서는 datasource 를 적는다

05장에서는 datasource 필드를 아예 생략해 기본 데이터소스를 쓰게 했다. 패널만 있을 때는 그것으로 충분하지만, 쿼리 변수는 데이터소스를 명시해야 값을 채울 수 있다. 그래서 datasource 타입 변수를 만들고 ${datasource} 로 참조한다 — 결과적으로 uid 를 박아 넣지 않으면서도 변수가 동작한다.

알림이 울리기까지

  • 1 규칙이 읽혔는가. 만들어진 것과 읽힌 것은 다르다 — 06장과 같은 이야기다. 확인 curl -s localhost:30900/api/v1/rules | jq -r '.data.groups[] | select(.name=="obs-study-app") | .rules[] | "\(.name)\t\(.state)"' → 4줄, 전부 inactive
  • 2 조건을 만들면 pending 이 되는가. 에러를 주입하고 상태를 지켜본다. 확인 같은 명령 → AppHighErrorRate 가 pending
  • 3 2분 뒤 firing 이 되는가. for: 2m 의 효과를 시계로 확인한다. 확인 같은 명령 → firing. Alertmanager /api/v2/alerts 에도 나타난다

WHY세 상태를 만드는 설정 — for 와 interval

study/labs/k8s/monitoring/91-prometheusrule.yaml — 발췌 
spec:
  groups:
    - name: obs-study-app
      # 이 그룹의 규칙을 얼마나 자주 평가할지 — 그림의 눈금 간격
      interval: 30s
      rules:
        - alert: AppHighErrorRate
          expr: |
            100 * ( ... ) > 5      # 조건 — 그림 윗줄의 참/거짓
          for: 2m                  # pending 을 버텨야 하는 시간
          labels:
            severity: warning      # Alertmanager 라우팅의 기준
          annotations:
            summary: "{{ $labels.service }} 에러율 {{ $value | printf \"%.1f\" }}%"
필드그림의 어느 부분바꾸면
interval: 30s윗줄 판정이 갱신되는 주기짧게 하면 CPU (Central Processing Unit · 중앙처리장치) 를 더 쓰고, 길면 발화가 늦어진다
expr참/거짓 자체임계값을 낮추면 pending 구간이 자주 생긴다
for: 2mpending 의 길이0 이면 왼쪽의 짧은 “참”에도 즉시 발화한다
labels.severity—08절 라우팅에서 어느 수신자로 갈지 정한다
annotations.summary—알림 본문. {{ $labels }} 와 {{ $value }} 를 쓸 수 있다

필드무엇을 정하나
unit: "percent" · "s" · "reqps"숫자 뒤에 붙는 단위. 틀리면 0.05초가 “50000”으로 보인다
thresholds값에 따른 색. 에러율 1% 부터 빨강이므로 보자마자 판정된다

에러율 패널의 or vector(0) 는 “트래픽이 없다”를 “에러가 없다”로 바꿔 보여 준다. 편하지만 서비스가 죽어서 요청이 0 인 상황도 초록색 0% 로 보인다. 그래서 초당 요청 수 패널을 그 옆에 나란히 둔다 — 둘을 함께 봐야 판정이 된다.

06PrometheusRule 적용

study/labs/k8s/monitoring/91-prometheusrule.yaml — 네 규칙 
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: obs-study-app-rules
  namespace: apps
  labels:
    # ServiceMonitor와 같은 이유로 필요하다 (06장 ①번 고리)
    release: kps
spec:
  groups:
    - name: obs-study-app
      interval: 30s
      rules:
        - alert: AppTargetDown
          expr: up{namespace="apps"} == 0
          for: 1m
          labels:
            severity: critical
          annotations:
            summary: "{{ $labels.service }} 스크레이프 실패"
            description: "{{ $labels.pod }} 를 1분 이상 긁지 못하고 있습니다."

        - alert: AppHighErrorRate
          expr: |
            100 * (
              sum by (service) (
                rate(http_server_requests_seconds_count{namespace="apps", status=~"5.."}[5m])
              )
              /
              sum by (service) (
                rate(http_server_requests_seconds_count{namespace="apps"}[5m])
              )
            ) > 5
          for: 2m
          labels:
            severity: warning
          annotations:
            summary: "{{ $labels.service }} 에러율 {{ $value | printf \"%.1f\" }}%"

        - alert: AppHighLatencyP95
          expr: |
            histogram_quantile(0.95,
              sum by (le, service) (
                rate(http_server_requests_seconds_bucket{namespace="apps"}[5m])
              )
            ) > 0.5
          for: 3m
          labels:
            severity: warning
          annotations:
            summary: "{{ $labels.service }} P95 {{ $value | printf \"%.2f\" }}초"

        - alert: OrderRejectionSpike
          expr: sum(rate(orders_rejected_total[5m])) > 0.2
          for: 5m
          labels:
            severity: info
          annotations:
            summary: "주문 거부가 늘고 있습니다"
kubectl apply -f study/labs/k8s/monitoring/91-prometheusrule.yaml

네 개가 모두 보이면 성공이다. 아무것도 안 나오면 release: kps 라벨을 확인한다 — ServiceMonitor 와 완전히 같은 이유로 조용히 무시된다.

임계값은 어떻게 정하나

위 숫자(5%, 500ms)는 예시일 뿐이다. 실제로는 과거 데이터를 보고 정한다 — 평소 P95 가 200ms 인 서비스에 500ms 임계값은 합리적이지만, 평소가 800ms 인 서비스에는 매분 울리는 알림이 된다. 06장에서 만든 그래프를 며칠 관찰한 뒤 정하는 것이 정석이고, 급하면 “평소값의 2~3배”에서 시작해 조정한다.

07Alertmanager 라우팅

프로메테우스는 알림을 발생시키고, Alertmanager 는 그것을 묶고 억제하고 보낸다. 값 파일에 라우팅을 정의한다.

study/labs/monitoring/kps-values.yaml — alertmanager.config 
alertmanager:
  # 이 블록을 쓰면 차트 기본 설정을 전부 대체한다.
  # Watchdog 처리와 억제 규칙을 빠뜨리면 안 되는 이유다.
  config:
    global:
      resolve_timeout: 5m

    route:
      # 같은 네임스페이스·같은 알림이면 한 덩어리로 묶어 보낸다
      group_by: ["namespace", "alertname"]
      # 첫 알림을 30초 기다렸다가 보낸다 — 연달아 터지는 것을 한 번에 묶기 위해
      group_wait: 30s
      # 같은 그룹에 새 알림이 추가되면 5분 간격으로 다시 보낸다
      group_interval: 5m
      # 해결되지 않은 알림을 4시간마다 재통보
      repeat_interval: 4h
      receiver: study-default
      routes:
        # Watchdog은 "모니터링이 살아있다"를 알리는 상시 알림이다. 통보는 버린다.
        - receiver: "null"
          matchers:
            - alertname =~ "InfoInhibitor|Watchdog"
        - receiver: study-critical
          matchers:
            - severity = "critical"

    # critical이 울리는 동안 같은 대상의 warning/info는 숨긴다
    inhibit_rules:
      - source_matchers:
          - severity = "critical"
        target_matchers:
          - severity =~ "warning|info"
        equal: ["namespace", "alertname"]

    receivers:
      - name: "null"
      - name: study-default
      - name: study-critical
      # 슬랙 웹훅이 있다면 위 receiver에 아래를 붙인다.
      # slack_configs:
      #   - api_url: https://hooks.slack.com/services/XXX/YYY/ZZZ
      #     channel: "#obs-study"
      #     send_resolved: true
helm upgrade kps prometheus-community/kube-prometheus-stack \
  --namespace monitoring --version 88.3.0 \
  -f kps-values.yaml --wait --timeout 10m

라우팅을 시뮬레이션한다 — amtool

목적: 알림을 실제로 터뜨리지 않고 “이 라벨이면 어디로 가는가”를 확인한다.

AM_POD=$(kubectl -n monitoring get pod \
  -l app.kubernetes.io/name=alertmanager \
  -o jsonpath='{.items[0].metadata.name}')
CFG=/etc/alertmanager/config_out/alertmanager.env.yaml

kubectl -n monitoring exec "$AM_POD" -c alertmanager -- \
  amtool config routes --config.file="$CFG"

--- 출력 ---

Routing tree:
.
└── default-route  receiver: study-default
    ├── {alertname=~"InfoInhibitor|Watchdog"}  receiver: null
    └── {severity="critical"}  receiver: study-critical
kubectl -n monitoring exec "$AM_POD" -c alertmanager -- \
  amtool config routes test --config.file="$CFG" \
  severity=critical namespace=apps alertname=AppTargetDown

--- 출력 ---

study-critical
판정

트리 출력의 들여쓰기가 곧 우선순위다. 위에서부터 먼저 맞는 가지로 간다 — Watchdog 가지가 critical 가지보다 위에 있으므로, Watchdog 은 severity 와 무관하게 버려진다. routes test 는 라벨 조합을 넣으면 최종 수신자 이름만 돌려준다.

설정 파일 경로가 다르면 kubectl -n monitoring exec "$AM_POD" -c alertmanager -- ls /etc/alertmanager/config_out/ 로 확인한다. 오퍼레이터 버전에 따라 파일명이 달라질 수 있다.

09일부러 실패시키기 — 규칙의 문법 오류

06장에서는 라벨을 틀려 조용히 무시되는 것을 봤다. 규칙에는 다른 종류의 실패가 하나 더 있다 — PromQL 문법 오류다. 이것은 조용하지 않다. 어떻게 다른지 확인한다.

아래 출력은 kube-prometheus-stack 이 설치된 kind 클러스터에서 재현했다 (확인 2026-09-13). --dry-run=server 를 쓰므로 클러스터에 저장되지 않는다.

cat <<'EOF' | kubectl apply --dry-run=server -f -
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: bad-rule-demo
  namespace: apps
  labels:
    release: kps
spec:
  groups:
    - name: bad
      rules:
        - alert: BadExpr
          # 괄호가 하나 모자란다 — sum by (le ( ...
          expr: sum by (le (rate(http_server_requests_seconds_bucket[5m]))
          for: 1m
EOF

--- 출력 ---

The  "prometheusrules" is invalid: : 5:11: group "bad", rule 1, "BadExpr":
could not parse expression: 1:12: parse error: unexpected "(" in grouping opts,
expected "," or ")"
읽는 법

메시지에 좌표가 두 개 나온다. 앞의 5:11 은 YAML (YAML Ain't Markup Language · 들여쓰기로 구조를 적는 설정 형식) 파일 안의 위치, 뒤의 1:12 는 그 표현식 문자열 안의 위치다. 그리고 group "bad", rule 1, "BadExpr" 로 어느 규칙인지 콕 집어 준다. 규칙이 수십 개인 파일에서 이 정보가 없으면 눈으로 찾아야 한다.

중요한 것은 저장되기 전에 막혔다는 점이다. 차트가 설치한 어드미션 웹훅이 kubectl apply 시점에 PromQL 을 파싱해 본다. 06장의 라벨 실수와는 성격이 정반대다.

실수언제 드러나나어떻게 아나
release 라벨 누락영원히 드러나지 않는다/api/v1/rules 에 규칙이 없다 — 직접 확인해야 한다
PromQL 문법 오류kubectl apply 하는 즉시에러 메시지가 줄 번호까지 알려 준다
임계값이 현실과 안 맞음운영 중에알림이 매분 울리거나, 장애인데 안 울린다
for 가 너무 짧음운영 중에스파이크마다 울렸다 풀렸다 한다

문법은 기계가 잡아 주지만 나머지 셋은 사람이 정해야 한다. 그래서 다음 절이 필요하다.

10알림을 몇 개 만들 것인가

이 장에서 만든 알림은 네 개다. 늘리고 싶은 유혹이 계속 생기는데, 판단 기준을 하나 두면 대부분 정리된다.

기준 하나 — 사람이 지금 무언가를 해야 하는가

“알면 좋은 것”은 알림이 아니라 대시보드에 둔다. 새벽 세 시에 깨울 만한 것만 알림으로 만든다. 이 기준을 적용하면 대부분의 “~가 평소보다 높음” 알림이 사라진다.

이 장의 알림사람이 할 일이 있나severity
AppTargetDown있다. 서비스가 안 보인다 — 파드나 네트워크를 봐야 한다critical
AppHighErrorRate있다. 사용자가 500 을 받고 있다warning
AppHighLatencyP95있다. 느려지고 있다 — 원인을 찾아야 한다warning
OrderRejectionSpike애매하다. 클라이언트 오류일 수 있다info — 통보는 하되 깨우지 않는다

네 번째가 info 인 이유가 이 표의 요점이다. 확신이 없는 알림을 critical 로 만들면, 몇 주 뒤 팀 전체가 critical 을 무시하게 된다. 심각도는 “얼마나 놀랐는가”가 아니라 “지금 일어나서 고쳐야 하는가”로 정한다.
