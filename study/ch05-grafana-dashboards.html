쿠버네티스 관측성

그라파나와 대시보드 프로비저닝

그라파나는 04장에서 이미 떠 있다. 이 장은 설치가 아니라 운영 방식을 정한다 — 대시보드를 클릭으로 만들지 않고 코드로 만든다.

01왜 이 장이 필요한가

그라파나 UI (User Interface · 사용자 인터페이스) 에서 패널을 끌어다 놓으면 대시보드가 5분 만에 만들어진다. 그 대시보드는 그라파나의 내부 DB 에 저장되고, 클러스터를 지우면 같이 사라진다. 이 실습은 클러스터를 자주 지우고 다시 만드는 것을 전제하므로 그 방식으로는 진도가 나가지 않는다.

대신 대시보드 JSON (JavaScript Object Notation · 키·값으로 데이터를 적는 형식) 을 컨피그맵에 담고 라벨 하나를 붙인다. 그라파나 사이드카가 그 라벨을 가진 컨피그맵을 찾아 대시보드로 올린다. 클러스터를 새로 만들어도 kubectl apply 한 번이면 돌아온다. 07장에서 만들 RED (Rate, Errors, Duration · 애플리케이션을 보는 세 지표) 대시보드도 같은 방법으로 배포한다.

그런데 이 방식에는 조용한 실패가 하나 있다. 라벨을 빠뜨리면 에러도 이벤트도 없이 대시보드만 안 보인다. 이 장에서 일부러 그것을 겪어 본다.

02알아야 할 개념

사이드카가 라벨을 보고 파일을 쓴다

그라파나 파드가 3/3 이었던 것을 기억할 것이다. 컨테이너 세 개가 한 파드에 들어 있고, 앞의 둘이 사이드카다. 이들은 쿠버네티스 API (Application Programming Interface · 프로그램끼리 주고받는 규약) 를 지켜보다가 특정 라벨이 붙은 ConfigMap 을 발견하면 그 내용을 파일로 꺼내 공유 볼륨에 쓴다. 그라파나는 그 디렉터리를 읽을 뿐이다.

데이터소스는 이름이 아니라 uid 로 참조한다

대시보드 JSON 안에서 데이터소스를 이름(Prometheus)으로 적으면 환경에 따라 깨진다. 팀원끼리 JSON 을 주고받을 때 uid 가 다르면 패널이 전부 비어 보인다. 가장 이식성이 좋은 방법은 아예 적지 않는 것이다 — 생략하면 기본 데이터소스가 쓰인다. 이 장의 실습이 그 방식이다.

UI 는 편집기이고 원본은 저장소다

처음부터 JSON 을 손으로 쓰는 것은 비효율적이다. UI 에서 원하는 패널을 만들고 Export 로 JSON 을 받아 컨피그맵에 넣는 순서가 현실적이다. 다만 프로비저닝된 대시보드를 UI 에서 고치고 저장하면 다음 적용 때 덮어씌워진다. “어제 고친 패널이 사라졌다”의 원인이 대부분 이것이다.

이 장을 마치면 할 수 있는 것

  1. 그라파나 파드의 컨테이너 셋이 각각 무엇을 하는지 말하고, 사이드카 로그로 대시보드 등록을 확인할 수 있다.
  2. 대시보드 JSON 을 ConfigMap 으로 올려 그라파나를 재시작하지 않고 반영할 수 있다.
  3. 라벨을 빠뜨렸을 때의 조용한 실패를 재현하고, 로그로 그 침묵을 확인할 수 있다.
  4. UI 에서 편집한 것을 JSON 으로 내보내 저장소에 반영하는 왕복을 한 번 돌릴 수 있다.
  5. 스택 내장 그라파나와 별도 설치 중 어느 쪽을 택할지 근거를 들어 판단할 수 있다.

03최종적으로 만들 것

이 장이 끝나면 그라파나에 Obs Study 폴더가 생기고 그 안에 우리가 만든 대시보드가 들어 있다. 그리고 그 대시보드의 원본은 그라파나 안이 아니라 kubectl apply 할 수 있는 YAML (YAML Ain't Markup Language · 들여쓰기로 구조를 적는 설정 형식) 파일이다.

ConfigMap 이 대시보드가 되기까지

  • 1 파드 안에 컨테이너가 셋인지. 앞의 둘이 사이드카다. 확인 kubectl -n monitoring get pod -l app.kubernetes.io/name=grafana -o jsonpath='{range .items[0].spec.containers[*]}{.name}{"\n"}{end}' → grafana-sc-dashboard · grafana-sc-datasources · grafana
  • 2 사이드카가 집어 가는 ConfigMap 이 몇 개인지. 차트가 만든 기본 대시보드들이다. 확인 kubectl -n monitoring get cm -l grafana_dashboard=1 --no-headers | wc -l → 수십 개
  • 3 그라파나가 실제로 등록했는지. 브라우저에서 확인한다. 확인 curl -s -o /dev/null -w '%{http_code}\n' http://localhost:30300/login → 200, 로그인 후 Dashboards 목록에 수십 개

WHY이 흐름을 켜는 설정 — sidecar 블록

사이드카가 어떤 라벨을 어느 네임스페이스에서 찾을지는 값 파일이 정한다. 기본값은 그라파나와 같은 네임스페이스만 본다 — 앱 대시보드를 apps 에 두려면 범위를 넓혀야 한다.

study/labs/monitoring/kps-values.yaml — grafana.sidecar 
grafana:
  adminPassword: obs-study
  nodeSelector:
    workload: observability
  service:
    type: NodePort
    nodePort: 30300

  # 기본 대시보드의 시간대. 한국 시간으로 보면 로그와 대조하기 쉽다.
  defaultDashboardsTimezone: Asia/Seoul

  sidecar:
    dashboards:
      enabled: true
      # 이 라벨이 붙은 ConfigMap 을 대시보드로 인식한다
      label: grafana_dashboard
      labelValue: "1"
      # 모든 네임스페이스를 감시 — apps 네임스페이스에 둔 대시보드도 잡힌다
      searchNamespace: ALL
      # ConfigMap 에 이 애너테이션을 달면 해당 폴더로 들어간다
      folderAnnotation: grafana_folder
      provider:
        foldersFromFilesStructure: true
    datasources:
      enabled: true
      label: grafana_datasource
      searchNamespace: ALL
설정정하는 것어긋나면
label: grafana_dashboard + labelValue: "1"무엇을 집어 갈지ConfigMap 에 이 라벨이 없으면 조용히 무시된다 (07절)
searchNamespace: ALL어디를 뒤질지기본값은 그라파나와 같은 네임스페이스만. apps 에 둔 대시보드가 안 보인다
folderAnnotation: grafana_folder폴더 이름을 어디서 읽을지모든 대시보드가 General 폴더에 쌓인다
defaultDashboardsTimezone차트 기본 대시보드의 시간대직접 만든 JSON 에는 적용되지 않는다 — JSON 안에 따로 적어야 한다
searchNamespace: ALL 의 비용

사이드카가 클러스터 전체의 ConfigMap 을 감시하게 되므로 그만큼 권한과 API 부하가 는다. 네임스페이스가 수백 개인 운영 클러스터에서는 필요한 것만 콤마로 나열하는 편이 낫다. 실습에서는 네임스페이스가 셋뿐이라 ALL 로 둔다.

# 04장에서 NodePort 30300으로 열어뒀다
open http://localhost:30300

# 비밀번호를 값 파일에 두지 않았다면 시크릿에서 꺼낸다
kubectl -n monitoring get secret kps-grafana \
  -o jsonpath='{.data.admin-password}' | base64 -d; echo

계정은 admin, 비밀번호는 04장 값 파일에 넣은 obs-study 다. 로그인하면 대시보드가 이미 수십 개 들어 있다. 직접 만든 적이 없는데도 그렇다 — 그림 1의 구조로 차트가 넣어 둔 것이다.

먼저 열어 볼 대시보드보는 것
Kubernetes / Compute Resources / Namespace (Pods)apps 네임스페이스를 고르면 03장에서 배포한 파드 3개의 CPU (Central Processing Unit · 중앙처리장치)·메모리가 보인다
Node Exporter / Nodes노드별 CPU·메모리·디스크. 실습 중 노트북이 버거워지면 여기부터 본다
Kubernetes / Kubelet노드별 파드 수, 컨테이너 런타임 동작 상태
아직 우리 앱의 지표는 없다

위 대시보드에 보이는 것은 컨테이너 관점의 자원 사용량이다. “주문 API 가 초당 몇 건을 처리하고 P99 가 몇 ms 인가”는 아직 어디에도 없다. 그 데이터를 만들려면 06장에서 ServiceMonitor 를 붙여야 한다.

데이터소스는 어떻게 연결돼 있나

kubectl -n monitoring get cm -l grafana_datasource=1 \
  -o custom-columns=NAME:.metadata.name --no-headers
# 실제 정의를 들여다본다 — uid 와 url 을 확인할 것
kubectl -n monitoring get cm -l grafana_datasource=1 \
  -o jsonpath='{.items[0].data}' | head -c 600; echo

프로메테우스 데이터소스의 url 이 클러스터 내부 서비스 주소로 되어 있는 것이 보인다. 그라파나는 브라우저가 아니라 자기 파드에서 프로메테우스에 질의하므로 localhost:30900 이 아니라 서비스 이름을 쓴다. 이 구분을 놓치면 “브라우저에서는 되는데 패널은 비어 있다”에서 헤맨다.

06대시보드를 코드로 만들기

목적: 클러스터를 다시 만들어도 kubectl apply 한 번으로 돌아오는 대시보드를 만든다.

아직 앱 메트릭이 없으므로 클러스터 지표로 구성한다. 07장에서는 같은 방법으로 RED 대시보드를 만든다.

study/labs/monitoring/dashboards/obs-overview.json 
{
  "uid": "obs-study-overview",
  "title": "Obs Study — 클러스터 한눈에",
  "tags": ["obs-study"],
  "timezone": "Asia/Seoul",
  "schemaVersion": 39,
  "refresh": "30s",
  "time": { "from": "now-30m", "to": "now" },
  "panels": [
    {
      "type": "stat",
      "title": "스크레이프 실패 타깃 수",
      "gridPos": { "h": 6, "w": 8, "x": 0, "y": 0 },
      "targets": [
        { "refId": "A", "expr": "count(up == 0) or vector(0)" }
      ]
    },
    {
      "type": "timeseries",
      "title": "노드별 여유 메모리 (GiB)",
      "gridPos": { "h": 6, "w": 16, "x": 8, "y": 0 },
      "fieldConfig": {
        "defaults": { "unit": "decgbytes" },
        "overrides": []
      },
      "targets": [
        {
          "refId": "A",
          "expr": "node_memory_MemAvailable_bytes{job=\"node-exporter\"} / 1024^3",
          "legendFormat": "{{instance}}"
        }
      ]
    },
    {
      "type": "timeseries",
      "title": "노드별 파드 수",
      "gridPos": { "h": 8, "w": 24, "x": 0, "y": 6 },
      "targets": [
        {
          "refId": "A",
          "expr": "sum by (node) (kube_pod_info)",
          "legendFormat": "{{node}}"
        }
      ]
    }
  ]
}
JSON 의 부분왜 그렇게 썼나
datasource 가 없다생략하면 기본 데이터소스가 쓰인다. uid 가 다른 환경에서도 그대로 동작한다
"timezone": "Asia/Seoul"값 파일의 defaultDashboardsTimezone 은 차트 기본 대시보드에만 적용된다. 직접 만든 JSON 에는 따로 적어야 한다
count(up == 0) or vector(0)up == 0 이 하나도 없으면 결과가 빈 벡터가 되어 패널이 “No data”가 된다. or vector(0) 가 그때 0 을 채운다
gridPos 의 y가로는 24칸 기준이다. y 가 겹치면 패널이 서로 밀어낸다 — 첫 줄 y:0, 다음 줄 y:6

ConfigMap 으로 감싸 적용

cd study/labs/monitoring

kubectl -n monitoring create configmap obs-overview-dashboard \
  --from-file=obs-overview.json=dashboards/obs-overview.json \
  --dry-run=client -o yaml > obs-overview-cm.yaml

생성된 파일에 라벨과 폴더 애너테이션을 넣는다. 이 두 줄이 이 장의 전부라고 해도 된다.

obs-overview-cm.yaml — metadata 부분 
apiVersion: v1
kind: ConfigMap
metadata:
  name: obs-overview-dashboard
  namespace: monitoring
  labels:
    # 이 라벨이 없으면 사이드카가 무시한다
    grafana_dashboard: "1"
  annotations:
    # 이 폴더가 없으면 자동으로 만들어진다
    grafana_folder: "Obs Study"
data:
  obs-overview.json: |
    { ... JSON 전체 ... }
kubectl apply -f obs-overview-cm.yaml

# 사이드카가 감지했는지 로그로 확인 (보통 10초 안에 반영된다)
kubectl -n monitoring logs -l app.kubernetes.io/name=grafana \
  -c grafana-sc-dashboard --tail=20

--- 출력 (시각은 환경마다 다르다) ---

{"time": "...", "level": "INFO", "msg": "Writing /tmp/dashboards/obs-overview.json (ascii)"}
{"time": "...", "level": "INFO", "msg": "None sent to http://localhost:3000/api/admin/provisioning/dashboards/reload.

두 줄이 핵심이다. Writing ...json 은 사이드카가 ConfigMap 을 집어 파일로 썼다는 뜻이고, Dashboards config reloaded 는 그라파나가 다시 읽었다는 뜻이다. 그라파나 좌측 Dashboards 에 Obs Study 폴더가 생기고 그 안에 대시보드가 들어 있다. 그라파나를 재시작하지 않았다는 점을 확인한다.

07일부러 실패시키기 — 라벨 없는 ConfigMap

이 방식의 유일한 함정은 실패해도 아무 말이 없다는 것이다. 에러도, 이벤트도, 경고도 없다. 한 번 겪어 두면 나중에 30분을 아낀다.

아래 출력은 kube-prometheus-stack 의 그라파나 사이드카에서 재현했다 (확인 2026-09-13). 끝에 지운다.

라벨을 빼고 올린다

cat > /tmp/lbl-demo.json <<'EOF'
{"uid":"lbl-demo","title":"Label Demo","schemaVersion":39,
 "panels":[{"type":"stat","title":"up","gridPos":{"h":6,"w":8,"x":0,"y":0},
 "targets":[{"refId":"A","expr":"count(up == 0) or vector(0)"}]}]}
EOF

kubectl -n monitoring create configmap lbl-demo \
  --from-file=lbl-demo.json=/tmp/lbl-demo.json

--- 출력 ---

configmap/lbl-demo created

성공했다고 나온다. 그런데 대시보드는 나타나지 않는다. 무엇이 잘못됐는지 둘을 나란히 물어보면 드러난다.

# ConfigMap 자체는 있는가
kubectl -n monitoring get cm lbl-demo

# 사이드카가 집어 가는 목록에 있는가
kubectl -n monitoring get cm -l grafana_dashboard=1 --no-headers | grep -c lbl-demo

--- 출력 ---

NAME       DATA   AGE
lbl-demo   1      0s

0
읽는 법

ConfigMap 은 멀쩡히 존재한다. 그런데 라벨 셀렉터로 조회하면 0 이다 — 사이드카에게는 보이지 않는 리소스라는 뜻이다. 사이드카 로그에도 이 이름이 전혀 나오지 않는다. 무시한 것조차 기록하지 않기 때문이다.

그래서 “대시보드가 안 보인다”의 첫 확인은 로그가 아니라 위 두 명령의 대조다. 첫 명령은 되는데 둘째가 0 이면 라벨 문제다.

라벨을 붙이면 즉시 반영된다

kubectl -n monitoring label cm lbl-demo grafana_dashboard=1 --overwrite
sleep 10
kubectl -n monitoring logs -l app.kubernetes.io/name=grafana \
  -c grafana-sc-dashboard --tail=6

{"time": "2026-09-13T14:04:44.350889+00:00", "level": "INFO", "msg": "None sent to
 http://localhost:3000/api/admin/provisioning/dashboards/reload.
 Response: 200 OK {\"message\":\"Dashboards config reloaded\"}"}
판정

ConfigMap 을 다시 만들지도, 그라파나를 재시작하지도 않았다. 라벨 한 줄을 붙인 것뿐인데 10초 안에 반영된다. 사이드카가 보는 것은 내용이 아니라 라벨이라는 사실이 이 실험의 요지다.

정리한다. 지우면 사이드카가 파일도 함께 걷어 간다.

kubectl -n monitoring delete cm lbl-demo
rm -f /tmp/lbl-demo.json

--- 로그 (삭제 직후) ---

{"time": "2026-09-13T14:04:57.662616+00:00", "level": "INFO", "msg": "Removing /tmp/dashboards/lbl-demo.json"}

08UI 에서 만들고 코드로 옮기기

현실적인 작업 흐름은 그림 2 와 같다. JSON 을 손으로 쓰는 것은 고통스럽고, UI 로만 만들면 재현이 안 된다. 둘을 합친다.

kubectl -n monitoring create configmap obs-overview-dashboard \
  --from-file=obs-overview.json=dashboards/obs-overview.json \
  --dry-run=client -o yaml | kubectl apply -f -

# 주의: 위 방식은 라벨과 애너테이션을 잃는다. 다시 붙인다.
kubectl -n monitoring label configmap obs-overview-dashboard \
  grafana_dashboard=1 --overwrite
kubectl -n monitoring annotate configmap obs-overview-dashboard \
  grafana_folder="Obs Study" --overwrite
UI 에서 저장한 변경은 임시다

프로비저닝된 대시보드를 UI 에서 고치고 저장해도, ConfigMap 이 다시 적용되는 순간 덮어씌워진다. UI 편집은 실험으로만 쓰고, 확정되면 반드시 JSON 을 저장소에 반영한다. 07절에서 본 대로 원본은 ConfigMap 이다.

09Grafana 13 에서 달라진 것

항목내용
Dynamic dashboards탭·조건부 표시·유연한 레이아웃이 정식 기능이 됐다. USE (Utilization, Saturation, Errors · 인프라를 보는 세 지표)·RED 형태의 레이아웃 템플릿도 함께 제공된다
양방향 Git 워크플로대시보드를 깃 저장소와 동기화하고 UI 변경을 풀 리퀘스트로 만들 수 있다. 이 실습의 ConfigMap 방식보다 진일보한 형태다
grafana-cli 폐기grafana cli, grafana server 형태로 통합됐다. 예전 명령을 쓰는 자동화 스크립트가 있다면 손봐야 한다
숫자 id 데이터소스 API 비활성데이터소스를 숫자 id 로 참조하던 API 가 기본 비활성이다. uid 로 참조하는 것이 유일한 방법이라고 보면 된다
gzip 기본 활성응답이 압축되어 전송된다. 대시보드가 많을 때 체감 로딩이 빨라진다
양방향 Git 워크플로를 지금 도입하지 않는 이유

“UI 로 편집 → 저장소 반영”의 수작업을 없애 준다. 다만 도입하면 대시보드 관리 방식 자체가 바뀐다. 원리가 드러나는 ConfigMap 방식을 먼저 익히고 나서 검토하는 순서를 권한다 — 자동화가 실패했을 때 무엇이 일어나고 있는지 알아야 고칠 수 있다.

10스택 내장 vs 별도 설치

이 실습은 kube-prometheus-stack 에 포함된 그라파나를 쓴다. 별도 차트로 설치하는 선택지도 있으니 판단 기준을 정리한다.

기준스택 내장 (지금 방식)별도 설치
기본 대시보드수십 개가 자동으로 따라온다직접 가져와야 한다
버전 관리차트 버전에 그라파나 버전이 묶인다독립적으로 올릴 수 있다
데이터소스프로메테우스가 자동 연결직접 프로비저닝
여러 클러스터 관측부적합 — 클러스터마다 그라파나가 생긴다적합 — 그라파나 하나로 여러 프로메테우스를 본다
인증 연동(SSO 등)가능하지만 값 파일이 복잡해진다깔끔하다

판단 기준은 클러스터 개수다. 하나면 내장이 편하고, 둘 이상을 한 화면에서 보려는 순간 별도 설치로 옮겨야 한다.

11자주 겪는 문제

증상원인과 조치
ConfigMap 을 만들었는데 대시보드가 안 보인다① 라벨 grafana_dashboard: "1" 누락 ② 그라파나와 다른 네임스페이스인데 searchNamespace: ALL 이 아님. 07절의 두 명령 대조부터 한다
대시보드는 보이는데 패널이 No data질의는 맞는데 데이터가 없거나 시간 범위가 데이터보다 앞선다. 같은 질의를 프로메테우스 UI(30900)에서 실행해 비교한다
패널에 Datasource ... was not foundJSON 이 다른 환경의 데이터소스 uid 를 참조하고 있다. 해당 필드를 지우는 것이 가장 간단한 해결이다
사이드카 로그에 403 ForbiddensearchNamespace: ALL 인데 RBAC (Role-Based Access Control · 역할로 권한을 주는 인가 방식) 이 좁다. helm upgrade 가 ClusterRole 까지 갱신했는지 확인
UI 에서 저장한 대시보드가 사라졌다프로비저닝된 대시보드는 원본이 ConfigMap 이다. JSON 을 저장소에 반영해야 한다
로그인이 안 된다값 파일의 adminPassword 는 최초 생성 시에만 반영된다. 이미 만들어진 뒤 바꾸려면 시크릿을 직접 수정하거나 재설치한다
시간이 UTC (Coordinated Universal Time · 세계 표준시) 로 보인다defaultDashboardsTimezone 은 차트 기본 대시보드에만 적용된다. 직접 만든 JSON 에는 "timezone": "Asia/Seoul" 을 넣는다
