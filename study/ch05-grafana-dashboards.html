01이론 — 대시보드는 코드다

왜 UI에서 만들지 않는가 — 클러스터를 지우면 같이 사라지는 것과 남는 것.

그라파나 UI에서 패널을 끌어다 놓으면 대시보드가 5분 만에 만들어진다. 그 대시보드는 그라파나의 내부 DB에 저장되고, 클러스터를 지우면 같이 사라진다. 이 실습은 클러스터를 자주 지우고 다시 만드는 것을 전제하므로 그 방식으로는 진도가 나가지 않는다.

대신 대시보드 JSON을 컨피그맵에 담고 라벨 하나를 붙인다. 그라파나 사이드카가 그 라벨을 가진 컨피그맵을 찾아 대시보드로 올린다. 클러스터를 새로 만들어도 kubectl apply 한 번이면 돌아온다.

라벨을 빠뜨리면 아무 일도 일어나지 않는다

에러도 없고 이벤트도 없다. 컨피그맵은 멀쩡히 만들어져 있고 대시보드만 안 보인다. 이 장에서 일부러 라벨을 빼고 적용해 그 침묵을 먼저 겪는다.

데이터소스는 이름이 아니라 uid로 참조한다

대시보드 JSON 안에서 데이터소스를 이름(Prometheus)으로 적으면 환경에 따라 깨진다. 스택이 만드는 데이터소스의 uid를 확인해 그것으로 참조해야 다른 클러스터에서도 같은 JSON이 그대로 뜬다.

UI에서 만들고 코드로 옮기는 순서

처음부터 JSON을 손으로 쓰는 것은 비효율적이다. UI에서 원하는 패널을 만들고 Export로 JSON을 받아 컨피그맵에 넣는 순서가 현실적이다. 이 장은 그 왕복을 한 번 돌려 본다.

02첫 로그인과 둘러볼 대시보드

# 04단계에서 NodePort 30300으로 열어뒀다
open http://localhost:30300

# 비밀번호를 값 파일에 두지 않았다면 시크릿에서 꺼낸다
kubectl -n monitoring get secret kps-grafana \
  -o jsonpath='{.data.admin-password}' | base64 -d; echo

계정은 admin, 비밀번호는 04단계 값 파일에 넣은 obs-study입니다.

로그인하면 대시보드가 이미 수십 개 들어 있습니다. 직접 만든 적이 없는데도 그렇습니다. 다음 세 개만 먼저 열어보세요. 앞으로 가장 자주 쓰게 됩니다.

대시보드보는 것
Kubernetes / Compute Resources / Namespace (Pods) apps 네임스페이스를 골라 보면 03단계에서 배포한 파드 3개의 CPU·메모리가 보인다
Node Exporter / Nodes 노드별 CPU·메모리·디스크. 실습 중 노트북이 버거워지면 여기부터 확인
Kubernetes / Kubelet 노드별 파드 수, 컨테이너 런타임 동작 상태
아직 우리 앱의 지표는 없다

위 대시보드에 보이는 것은 컨테이너 관점의 자원 사용량입니다. "주문 API가 초당 몇 건을 처리하고 P99가 몇 ms인가"는 아직 어디에도 없습니다. 그 데이터를 만들려면 06단계에서 ServiceMonitor를 붙여야 합니다.

03기본 대시보드는 어디서 왔나

그라파나 파드가 3/3이었던 것을 기억하세요. 컨테이너 세 개가 한 파드에 들어 있습니다. 

kubectl -n monitoring get pod -l app.kubernetes.io/name=grafana \
  -o jsonpath='{range .items[0].spec.containers[*]}{.name}{"\n"}{end}'
grafana-sc-dashboard
grafana-sc-datasources
grafana

앞의 둘이 사이드카입니다. 이들은 쿠버네티스 API를 지켜보다가 특정 라벨이 붙은 ConfigMap을 발견하면 그 내용을 파일로 꺼내 공유 볼륨에 씁니다. 그라파나는 그 디렉터리를 읽을 뿐입니다. 

# 기본 대시보드 ConfigMap이 몇 개인지 세어본다
kubectl -n monitoring get cm -l grafana_dashboard=1 --no-headers | wc -l

# 이름만 훑어보기
kubectl -n monitoring get cm -l grafana_dashboard=1 \
  -o custom-columns=NAME:.metadata.name --no-headers | head -10

04데이터소스도 같은 방식이다

kubectl -n monitoring get cm -l grafana_datasource=1 \
  -o custom-columns=NAME:.metadata.name --no-headers
# 실제 정의를 들여다본다 — uid와 url을 확인할 것
kubectl -n monitoring get cm -l grafana_datasource=1 \
  -o jsonpath='{.items[0].data}' | head -c 600; echo

프로메테우스 데이터소스의 url이 클러스터 내부 서비스 주소로 되어 있는 것이 보입니다. 그라파나는 브라우저가 아니라 자기 파드에서 프로메테우스에 질의하므로, localhost:30900이 아니라 서비스 이름을 씁니다.

uid를 기억해 둘 것

대시보드 JSON이 데이터소스를 지목할 때는 이름이 아니라 uid를 씁니다. 팀원끼리 대시보드 JSON을 주고받을 때 uid가 다르면 패널이 전부 비어 보입니다. 아래 실습에서는 패널에 데이터소스를 지정하지 않아 기본 데이터소스가 자동으로 쓰이게 합니다. 가장 이식성이 좋은 방법입니다.

05값 파일 보강과 재적용

사이드카 기본 설정은 그라파나와 같은 네임스페이스만 감시합니다. 앱 대시보드를 apps 네임스페이스에 두고 싶다면 감시 범위를 넓혀야 합니다. 폴더 정리도 지금 해둡니다.

monitoring/kps-values.yaml — grafana 블록을 아래로 교체

grafana:
  adminPassword: obs-study
  nodeSelector:
    workload: observability
  service:
    type: NodePort
    nodePort: 30300

  # 기본 대시보드의 시간대. 한국 시간으로 보면 로그와 대조하기 쉽다.
  defaultDashboardsTimezone: Asia/Seoul

  sidecar:
    dashboards:
      enabled: true
      # 이 라벨이 붙은 ConfigMap을 대시보드로 인식한다
      label: grafana_dashboard
      labelValue: "1"
      # 모든 네임스페이스를 감시 — apps 네임스페이스에 둔 대시보드도 잡힌다
      searchNamespace: ALL
      # ConfigMap에 이 애너테이션을 달면 해당 폴더로 들어간다
      folderAnnotation: grafana_folder
      provider:
        foldersFromFilesStructure: true
    datasources:
      enabled: true
      label: grafana_datasource
      searchNamespace: ALL

  resources:
    requests:
      cpu: 50m
      memory: 160Mi
    limits:
      memory: 384Mi
cd ~/k8s-observability/monitoring

helm upgrade kps prometheus-community/kube-prometheus-stack \
  --namespace monitoring \
  --version 88.3.0 \
  -f kps-values.yaml \
  --wait --timeout 10m

kubectl -n monitoring rollout status deploy/kps-grafana
searchNamespace: ALL의 비용

사이드카가 클러스터 전체의 ConfigMap을 감시하게 되므로 그만큼 권한과 API 부하가 늘어납니다. 네임스페이스가 수백 개인 운영 클러스터에서는 searchNamespace에 필요한 네임스페이스만 콤마로 나열하는 편이 낫습니다. 실습에서는 네임스페이스가 셋뿐이라 ALL로 둡니다.

패널에 datasource를 쓰지 않았습니다. 생략하면 기본 데이터소스가 쓰이므로 uid가 다른 환경에서도 그대로 동작합니다. gridPos의 y 값이 겹치지 않게 쌓는 것만 주의하면 됩니다.

ConfigMap으로 감싸 적용

cd ~/k8s-observability/monitoring

kubectl -n monitoring create configmap obs-overview-dashboard \
  --from-file=obs-overview.json=dashboards/obs-overview.json \
  --dry-run=client -o yaml > obs-overview-cm.yaml

생성된 파일에 라벨과 폴더 애너테이션을 넣습니다.

monitoring/obs-overview-cm.yaml — metadata 부분

apiVersion: v1
kind: ConfigMap
metadata:
  name: obs-overview-dashboard
  namespace: monitoring
  labels:
    # 이 라벨이 없으면 사이드카가 무시한다
    grafana_dashboard: "1"
  annotations:
    # 이 폴더가 없으면 자동으로 만들어진다
    grafana_folder: "Obs Study"
data:
  obs-overview.json: |
    { ... JSON 전체 ... }
kubectl apply -f obs-overview-cm.yaml

# 사이드카가 감지했는지 로그로 확인 (보통 10초 안에 반영된다)
kubectl -n monitoring logs -l app.kubernetes.io/name=grafana \
  -c grafana-sc-dashboard --tail=20

로그에 obs-overview.json 파일을 썼다는 줄이 보이면 성공입니다. 그라파나 좌측 Dashboards에 Obs Study 폴더가 생기고 그 안에 대시보드가 들어 있습니다. 그라파나를 재시작하지 않았다는 점을 확인하세요.

07UI에서 만들고 코드로 옮기기

현실적인 작업 흐름은 이렇습니다. JSON을 손으로 쓰는 것은 고통스럽고, UI로만 만들면 재현이 안 됩니다. 둘을 합칩니다.

내보낸 JSON으로 ConfigMap을 갱신하는 한 줄입니다.

kubectl -n monitoring create configmap obs-overview-dashboard \
  --from-file=obs-overview.json=dashboards/obs-overview.json \
  --dry-run=client -o yaml | kubectl apply -f -

# 주의: 위 방식은 라벨과 애너테이션을 잃는다. 다시 붙여준다.
kubectl -n monitoring label configmap obs-overview-dashboard grafana_dashboard=1 --overwrite
kubectl -n monitoring annotate configmap obs-overview-dashboard grafana_folder="Obs Study" --overwrite
UI에서 저장한 변경은 임시다

프로비저닝된 대시보드를 UI에서 고치고 저장해도, ConfigMap이 다시 적용되는 순간 덮어씌워집니다. "어제 고친 패널이 사라졌다"의 원인이 대부분 이것입니다. UI 편집은 실험으로만 쓰고, 확정되면 반드시 JSON을 저장소에 반영하세요.

08Grafana 13에서 달라진 것

항목내용
Dynamic dashboards 탭·조건부 표시·유연한 레이아웃이 정식 기능이 됐다. USE·RED 형태의 레이아웃 템플릿도 함께 제공된다
양방향 Git 워크플로 대시보드를 깃 저장소와 동기화하고 UI 변경을 풀 리퀘스트로 만들 수 있다. 이 실습의 ConfigMap 방식보다 진일보한 형태이며, 사내 도입을 검토할 만하다
grafana-cli 폐기 grafana cli, grafana server 형태로 통합됐다. 예전 명령을 쓰는 자동화 스크립트가 있다면 손봐야 한다
숫자 id 데이터소스 API 비활성 데이터소스를 숫자 id로 참조하던 API가 기본 비활성이다. uid로 참조하는 것이 유일한 방법이라고 생각하면 된다
gzip 기본 활성 응답이 압축되어 전송된다. 대시보드가 많을 때 체감 로딩이 빨라진다
스터디에서 다뤄볼 만한 것

양방향 Git 워크플로는 "UI로 편집 → 저장소 반영"의 수작업을 없애줍니다. 다만 도입하면 대시보드 관리 방식 자체가 바뀌므로, 이 시리즈에서는 원리가 드러나는 ConfigMap 방식을 먼저 익히고 나서 검토하는 순서를 권합니다.

09스택 내장 vs 별도 설치

이 실습은 kube-prometheus-stack에 포함된 그라파나를 씁니다. 별도 차트로 설치하는 선택지도 있으니 판단 기준을 정리합니다.

기준스택 내장 (지금 방식)별도 설치
기본 대시보드 수십 개가 자동으로 따라온다 직접 가져와야 한다
버전 관리 차트 버전에 그라파나 버전이 묶인다 독립적으로 올릴 수 있다
데이터소스 프로메테우스가 자동 연결 직접 프로비저닝
여러 클러스터 관측 부적합 — 클러스터마다 그라파나가 생긴다 적합 — 그라파나 하나로 여러 프로메테우스를 본다
인증 연동(SSO 등) 가능하지만 값 파일이 복잡해진다 깔끔하다

판단 기준은 클러스터 개수입니다. 클러스터가 하나면 내장이 편하고, 둘 이상을 한 화면에서 보려는 순간 별도 설치로 옮겨야 합니다. 별도 설치 시 차트는 grafana-community 저장소에 있습니다 — grafana 저장소가 아닙니다.

10자주 겪는 문제

증상원인과 조치
ConfigMap을 만들었는데 대시보드가 안 보인다 ① 라벨 grafana_dashboard: "1" 누락 ② 그라파나와 다른 네임스페이스인데 searchNamespace: ALL이 아님. 사이드카 로그부터 본다
대시보드는 보이는데 패널이 No data 질의는 맞는데 데이터가 없거나, 시간 범위가 데이터보다 앞선다. 같은 질의를 프로메테우스 UI(30900)에서 실행해 비교한다
패널에 Datasource ... was not found JSON이 다른 환경의 데이터소스 uid를 참조하고 있다. 해당 필드를 지우거나 현재 uid로 바꾼다
사이드카 로그에 403 Forbidden searchNamespace: ALL인데 RBAC이 좁다. helm upgrade가 ClusterRole까지 갱신했는지 확인
UI에서 저장한 대시보드가 사라졌다 프로비저닝된 대시보드는 원본이 ConfigMap이다. JSON을 저장소에 반영해야 한다
로그인이 안 된다 값 파일의 adminPassword는 최초 생성 시에만 반영된다. 이미 만들어진 뒤 바꾸려면 시크릿을 직접 수정하거나 재설치한다
시간이 UTC로 보인다 defaultDashboardsTimezone은 차트 기본 대시보드에만 적용된다. 직접 만든 JSON에는 "timezone": "Asia/Seoul"을 넣는다

11완료 체크리스트

  • 그라파나에 로그인해 기본 대시보드 3개를 열어봤다
  • 그라파나 파드의 컨테이너 3개 이름을 확인했다
  • kubectl get cm -l grafana_dashboard=1 결과가 여러 개 나온다
  • 값 파일에 searchNamespace: ALL과 folderAnnotation을 넣고 재적용했다
  • 직접 만든 Obs Study 폴더의 대시보드가 그라파나에 보인다
  • 그 대시보드의 패널 3개가 모두 데이터를 그린다
  • 대시보드 JSON을 팀 저장소에 커밋했다
