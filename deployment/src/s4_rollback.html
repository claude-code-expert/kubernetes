깃옵스에서 되돌리는 방법 세 가지

방법되돌리는 것속도깃옵스에서는
트래픽 전환사용자가 보는 버전 (블루/그린 셀렉터, 카나리 가중치 0)수 초전략이 허락할 때만. 코드는 그대로
git revert원하는 상태동기화 + 롤아웃기본은 이것. 기록이 남는다
kubectl rollout undo클러스터의 실제 상태롤아웃 시간깃은 그대로라 에이전트가 새 버전으로 다시 돌려놓는다
# 기본: 깃을 되돌리고 바로 동기화
git revert a41d77c && git push
flux reconcile kustomization order-api --with-source   # interval을 기다리지 않는다

# 급해서 클러스터를 직접 만져야 한다면, 에이전트부터 멈춘다
flux suspend kustomization order-api        # Argo CD는 auto-sync 끄기
kubectl -n order rollout undo deploy/order-api
# 그다음 깃을 맞추고 다시 켠다
발표 노트
  • 깃옵스에서 되돌리는 방법은 세 가지입니다. 블루/그린이나 카나리처럼 옛 버전이 떠 있으면 트래픽 전환이 제일 빠릅니다. 기본은 git revert이고, 바로 flux reconcile을 해서 동기화 주기를 기다리지 않습니다.
  • 세 번째 rollout undo가 함정입니다. undo로 되돌려도 깃에는 새 버전이 적혀 있어서, Flux나 selfHeal을 켠 Argo CD가 다시 새 버전으로 돌려놓습니다. 급하게 되돌렸는데 몇 분 뒤에 장애가 다시 나는 겁니다.
  • 그래서 직접 만져야 한다면 에이전트를 먼저 멈추고, 되돌린 뒤 깃을 맞추고, 다시 켭니다. Argo CD에서 selfHeal이 꺼져 있으면 undo가 남는 대신 깃과 클러스터가 다른 채로 남습니다. 어느 쪽이든 깃을 맞춰야 끝납니다.

되돌아갈 곳이 남아 있나

되돌아갈 곳어디에 있나없어지는 경우
옛 ReplicaSet클러스터, revisionHistoryLimit(기본 10)한도를 줄여 뒀거나 배포가 잦아서 밀려남
옛 이미지레지스트리"최근 N개만 보관" 수명 주기 정책이 지움. undo 했더니 ImagePullBackOff
옛 태그가 가리키는 것레지스트리같은 태그로 다시 push (latest, 태그 불변 미설정)
블루 환경클러스터너무 빨리 내림 (3부 "블루는 언제 내리나")
옛 원하는 상태깃거의 안 없어진다

노드 캐시에 옛 이미지가 남아 있으면 undo는 되는데, 새 노드로 스케줄되는 순간 실패한다

발표 노트
  • rollout undo가 있어도 돌아갈 이미지가 지워져 있으면 소용없습니다. 쿠버네티스에서 돌아갈 곳은 여러 군데에 흩어져 있습니다.
  • 실무에서 자주 걸리는 건 두 번째입니다. 레지스트리 비용을 줄이려고 최근 이미지 몇 개만 남기는 정책을 걸어 두면, 롤백하려는 이미지가 이미 지워져 있습니다. 노드 캐시에 남아 있어서 당장은 되다가 새 노드로 갈 때 터지는 경우도 있습니다. 개수 기준보다 배포 저장소에서 쓰고 있는 태그는 안 지우는 방식이 낫습니다.
  • 깃은 거의 안 없어집니다. 다만 깃이 가리키는 이미지는 레지스트리에 있어야 합니다.
4부 · 5.7, 5.10

롤백해도 데이터는 안 돌아간다

예시 서비스라면

  • 쿠폰 컬럼은 1.6.3 때 먼저 추가해 뒀다. 옛 코드는 무시하고 지나간다
  • 축소(NOT NULL 추가, 옛 경로 삭제)까지 끝냈다면 옛 코드가 새 제약과 부딪힌다
  • 새 버전이 큐에 넣은 새 형식 메시지를 옛 컨슈머가 못 읽는다

고쳐서 다시 내보내는 게 나을 때

  • 되돌릴 수 없는 변경이 이미 나갔을 때
  • 수정이 작고 확실하고, 트래픽은 이미 옛 버전으로 돌려 뒀을 때
  • 교재 7.5: 급하게 만든 "조치 완료" 빌드가 문제를 더 키우기도 한다. 같은 배포 전략으로 내보낸다
발표 노트
  • 롤백하면 코드는 옛 버전으로 돌아가지만 새 버전이 쓴 데이터는 그대로 남습니다. 옛 코드와 새 데이터 조합은 테스트한 적이 없습니다.
  • 예시 서비스는 쿠폰 컬럼을 1.6.3 배포 때 먼저 추가해 뒀기 때문에 옛 코드가 새 컬럼을 무시하고 잘 돕니다. 3부에서 확장 배포를 따로 한 게 여기서 효과를 봅니다. 그런데 축소까지 끝냈거나 새 형식 메시지를 큐에 넣었다면 얘기가 다릅니다.
  • 그럴 때는 고쳐서 다시 내보내는 게 나을 수 있습니다. 교재 7.5는 급하게 만든 수정 빌드가 더 나쁠 수 있다고 경고하니까, 수정 빌드도 카나리 같은 같은 전략으로 내보냅니다.
4부 · 6.4, 6.5

같이 되돌릴 것은 한 차트로 묶는다

  • 교재 6.5: 함께 롤백하거나 업그레이드할 서비스는 같은 헬름 차트로
  • helm rollback 한 번에 웹, DB 디플로이먼트, 잡 매니페스트가 같이 이전 버전으로 (데이터는 아니다)
  • 6.4 예제는 헬름 훅으로 업그레이드, 삭제, 롤백 직전에 DB를 백업한다
  • 교재는 훅 키를 세 번 써서 pre-rollback만 남는다 (1부)
  • 깃으로 되돌리면 Flux는 upgrade를 한다 (pre-rollback은 실패 대응으로 롤백할 때만). Argo CD는 helm template이라 롤백 훅이 없다
  • → 교재 예제 그대로면 깃으로 되돌릴 때 백업이 안 돈다
kind: Job
metadata:
  name: db-backup
  annotations:
    "helm.sh/hook": pre-upgrade,pre-delete,pre-rollback
    "helm.sh/hook-delete-policy": hook-succeeded
spec:
  template:
    spec:
      containers:
      - name: mysqldump
        image: evillgenius/mysqldump:v1
      restartPolicy: Never
발표 노트
  • 6장 모범 사례 중 롤백과 바로 이어지는 게 이겁니다. 같이 되돌려야 하는 서비스는 같은 헬름 차트로 묶으라는 겁니다. 그러면 helm rollback 한 번에 웹, DB 디플로이먼트, 잡 매니페스트가 같이 이전 버전으로 돌아갑니다. 데이터까지 돌아가는 건 아닙니다. 앞 장에서 본 그대로입니다. 6.4 예제는 훅으로 업그레이드, 삭제, 롤백 직전에 DB를 백업합니다.
  • 그런데 1부에서 봤듯이 교재는 훅 키를 세 번 써서 마지막 pre-rollback만 남습니다.
  • 여기에 깃옵스가 겹치면 더 복잡해집니다. 도구마다 나눠 보겠습니다.
  • Flux helm-controller는 깃에서 차트 버전이나 값을 되돌리면 옛 버전으로 upgrade를 합니다. 그래서 pre-upgrade 훅이 걸립니다. pre-rollback 훅은 업그레이드가 실패해서 Flux의 실패 대응 설정이 helm rollback을 할 때만 걸립니다.
  • Argo CD는 헬름 차트를 helm template으로 매니페스트로 바꿔서 적용합니다. 헬름 릴리스 자체를 만들지 않아서 pre-rollback 훅은 아예 돌지 않습니다. pre-upgrade 같은 일부 훅은 Argo CD 동기화 훅으로 바꿔서 돌려 주지만 롤백 훅은 대응하는 게 없습니다.
  • 그래서 교재 예제처럼 pre-rollback만 남아 있으면, 깃으로 되돌릴 때는 어느 도구든 백업이 돌지 않습니다. 오른쪽처럼 쉼표로 이어 쓰면 적어도 Flux에서는 pre-upgrade로 백업이 돕니다.
4부 · 7.5

롤백 체크리스트 예시

배포 전에

  • 직전 버전 태그와 배포 저장소 커밋
  • 그 이미지가 레지스트리에 있나
  • 이번 변경에 축소(옛 컬럼 삭제 등)가 있나
  • 메시지 형식, 외부 API 계약이 바뀌었나

되돌릴 때

  1. 옛 버전이 떠 있으면 트래픽부터 전환
  2. 배포 저장소에서 git revert, 바로 reconcile
  3. 급하면 에이전트 멈춤 → undo → 깃 맞춤 → 재개
  4. 에러율이 원래대로 왔는지 확인
  5. 걸린 시간과 막힌 곳 기록

교재 7.5: 아무리 뻔한 단계라도 빠짐없이 적는다. 급할 때는 가장 쉬운 단계부터 잊어버린다

발표 노트
  • 지금까지 내용을 체크리스트로 만들면 이렇게 됩니다. 교재 7.5절이 뻔한 단계까지 다 적으라고 해서 정말 뻔한 것까지 넣었습니다.
  • 왼쪽은 배포 전에 볼 것입니다. 이번 변경에 되돌릴 수 없는 게 있는지를 배포 전에 알면, 이번엔 롤백보다 고쳐서 내보내는 쪽으로 가야겠다는 걸 미리 정할 수 있습니다.
  • 오른쪽 마지막 줄, 걸린 시간과 막힌 곳은 꼭 적어 둡니다. 이게 쌓여야 3부에서 본 카나리 대기 시간도 정할 수 있습니다. 여러분 팀 체크리스트에 뭐가 더 있는지 토론 때 듣고 싶습니다.

롤백도 미리 연습한다

7.5: 급하지 않을 때 연습한다

  • 트래픽 옮기기, 걸린 시간 기록
  • 데이터 전체 복구
  • 이전 버전으로 롤백
  • 틀린 부분을 적어 두고 자동화한다

5.8: 카오스 실험

  1. 정상 상태에 대한 가설
  2. 실제로 일어날 법한 이벤트 준비
  3. 대조군과 비교
  4. 가설 검증

영향 범위는 작게, 실험은 자동화. 도구 예: Chaos Toolkit, KubeMonkey (5.9.4)

연습하면 어디서 막히는지 미리 알 수 있다. 카오스는 8주차 20장에서 자세히

발표 노트
  • 절차를 문서로만 두면 막상 돌릴 때 어디서 막히는지 모릅니다. 교재 7.5절은 급하지 않을 때 연습하라고 하고, 무엇을 연습할지도 적어 둡니다.
  • 5.8절 카오스 실험도 같은 얘기입니다. 가설을 세우고 대조군과 비교합니다. 3부 카나리의 베이스라인이 여기서도 대조군으로 나옵니다.
  • 연습해 보면 어디서 막히는지 미리 알 수 있습니다. 카오스는 다음 주에 남희 님이 자세히 다룹니다.
