발표 노트
  • 오늘 계속 쓸 예시입니다. 주문 API이고, 레플리카 10개에 초당 1,000 요청을 받습니다. 쿠폰 할인을 적용하는 1.7.0 배포입니다. 쿠폰 컬럼은 그 전 1.6.3 배포 때 미리 추가해 뒀습니다. 왜 따로 했는지는 3부에서 봅니다.

  • 이 버그는 교재 7.4에 나오는 예를 그대로 가져왔습니다. 교재는 "테스트할 때는 영어로만 입력하지만 실제 환경에서는 다양한 언어로 입력이 들어올 수 있다"고 씁니다. 7.4.3에도 비영어권에서는 문자열 처리 중 버그가 나기 쉬운 유니코드 문자가 더 많이 들어온다는 얘기가 있습니다.
  • 아까 금요일 6시에 깨진 그 배포입니다. 3부에서 이 배포를 전략만 바꿔서 세 번 해 보겠습니다.

전체 그림: 커밋에서 사용자까지

발표 노트
  • 본론에 들어가기 전에 오늘 나오는 것들이 어떻게 이어지는지 한 장으로 보고 가겠습니다. 그림은 3회차 카나리 기준입니다. 상자마다 붙은 색 표시가 몇 부에서 다루는지입니다.
  • 위쪽은 클러스터 밖입니다. 개발자가 앱 저장소에 커밋하면 CI가 테스트하고, 이미지를 빌드해서 서명하고, 레지스트리에 올립니다. 이미지 이름이 커밋 해시 태그와 다이제스트입니다. 그다음 CI가 하는 마지막 일이 배포 저장소에 새 태그를 커밋하는 겁니다. 여기까지가 1부입니다.
  • 아래 큰 상자가 클러스터입니다. Argo CD, 또는 Flux가 클러스터 안에서 배포 저장소를 당겨 가서 Rollout 리소스를 적용합니다. CI는 클러스터 권한이 없고 깃에 커밋만 합니다. 이것도 1부에서 봅니다.
  • Rollout을 받은 Argo Rollouts 컨트롤러가 파드를 어떻게 바꿀지 정합니다. 옛 버전 ReplicaSet과 새 버전 ReplicaSet을 두고, 각각을 가리키는 stable 서비스와 canary 서비스를 둡니다. Gateway의 HTTPRoute가 사용자 요청을 95 대 5로 두 서비스에 나눠 보냅니다. 롤링, 블루/그린, 카나리가 이 부분을 어떻게 다르게 하는지가 2부와 3부입니다.
  • 판정은 AnalysisRun이 1분마다 Prometheus나 Datadog에 물어봐서 합니다. 실패하면 컨트롤러가 가중치를 0으로 돌립니다. 노드는 파드를 띄울 때 레지스트리에서 이미지를 받습니다.
  • 마지막으로 노란 점선이 되돌리기입니다. 배포 저장소에서 git revert를 하면 Argo CD가 그걸 당겨 가서 옛 버전으로 맞춥니다. 4부입니다. 발표 중간중간 이 그림에서 지금 어디를 보고 있는지 다시 짚겠습니다.

손으로 배포하면 생기는 일

교재가 꼽는 문제

  • 에러가 나기 쉽다
  • 구성 드리프트: 실제 구성이 의도와 점점 달라진다
  • 배포 업데이트가 취약해진다
  • 앱을 전달하는 애질리티가 떨어진다

교재의 출발점

  • 깃 main 브랜치가 프로덕션
  • 앱 코드와 매니페스트, 헬름 차트를 같은 저장소에
  • CI는 작은 변경을 자주 합치고 커밋마다 빌드

5장의 목표: 코드를 체크인한 뒤 프로덕션에 나가기까지 사람이 손대지 않는 것

발표 노트
  • 5장은 앱을 손으로 업데이트할 때 생기는 문제로 시작합니다. 에러가 나기 쉽고, 실제 구성이 의도와 조금씩 달라지는 구성 드리프트가 생기고, 배포 업데이트가 취약해지고, 앱을 전달하는 애질리티가 떨어진다고 합니다.
  • 여기부터는 제 생각입니다. 손으로 하면 배포가 부담스러워서 자주 못 하고, 그러다 보니 한 번에 많이 묶여 나갑니다. 한 번에 많이 나가면 깨졌을 때 원인 찾기도 되돌리기도 어렵습니다.
  • 교재는 앱 코드와 매니페스트, 헬름 차트를 한 저장소에 두는 걸 출발점으로 잡습니다. 저장소를 어떻게 나눌지는 토론 Q4에서 다시 얘기하겠습니다.

    targetRevision: main

  destination:

targetRevision브랜치, 태그, 커밋HEAD

발표 노트
  • Application 설정값입니다. 크게 세 덩어리입니다. source는 무엇을, destination은 어디에, syncPolicy는 어떻게 맞출지입니다.
  • source에서 path가 2부에서 말한 환경별 폴더입니다. overlays/prod를 가리키면 프로덕션 overlay를 배포합니다. targetRevision은 어느 브랜치나 태그를 볼지인데, 교재 18.7 권장대로 환경은 브랜치가 아니라 폴더로 나누니까 보통 main 하나만 봅니다.
  • syncPolicy가 제일 헷갈리는 부분입니다. automated를 안 적으면 깃이 바뀌어도 OutOfSync로 표시만 하고, 사람이 Sync 버튼을 눌러야 적용됩니다. automated를 적으면 자동으로 적용하는데, 그 안의 prune과 selfHeal은 따로 켜야 합니다. 둘 다 기본값이 false입니다.
  • prune은 깃에서 파일을 지웠을 때 클러스터에서도 지울지입니다. 안 켜면 지운 리소스가 클러스터에 계속 남습니다.
  • selfHeal은 누가 kubectl로 손대서 바꾼 걸 깃 값으로 되돌릴지입니다. 직접 해 봤습니다. selfHeal을 끈 채로 replicas를 손으로 3으로 바꾸니까 Argo CD는 OutOfSync라고 표시만 하고 3이 그대로 남았습니다. selfHeal을 켜자 바로 깃에 적힌 1로 돌아갔습니다. 깃옵스 4원칙의 지속적 조정을 지키려면 selfHeal을 켜야 합니다.
  • 깃 변경을 얼마나 자주 보는지는 기본 3분입니다. 더 빨리 반영하려면 깃 웹훅을 Argo CD에 연결합니다.

디플로이먼트, 레플리카셋, 잡, 데몬셋은 셀렉터로 파드를 고른다

셀렉터는 한번 만들면 못 바꾼다

발표 노트
  • 6장에 이런 문장이 있습니다. 쿠버네티스에는 릴리스 컨트롤러가 없어서 릴리스라는 개념 자체가 없다는 겁니다.
  • 무슨 뜻이냐면, 디플로이먼트는 지금 원하는 파드 모양 하나만 압니다. 이게 몇 번째 릴리스인지, 어느 파이프라인이 만들었는지, 카나리인지 정식인지는 쿠버네티스가 따로 들고 있지 않습니다.
  • 그래서 그런 정보를 레이블에 적습니다. stable, canary 같은 이름을 붙이고, 조직이 크면 사내 사용자부터 ring-0, ring-1 식으로 나눠서 차례로 내보냅니다. 3부에서 볼 카나리도 레이블로 파드를 구분합니다.
  • 헬름은 조금 다릅니다. 헬름은 릴리스 이력을 클러스터에 따로 저장해 둬서, CD 도구들이 이걸 릴리스 기록으로 많이 씁니다.
  • 교재가 더 강조하는 건 셀렉터입니다. 디플로이먼트, 레플리카셋, 잡, 데몬셋은 레이블 셀렉터로 자기 파드를 고릅니다. 파드 레이블은 언제든 바꿀 수 있지만, 디플로이먼트의 셀렉터는 한번 만들면 못 바꿉니다. 이 차이가 다음 두 장에서 문제가 됩니다.

  • 이 장표는 6.4 종합 예제를 실제 클러스터에 그대로 넣어 보면 어디서 막히는지입니다. 결론부터 말하면, 셀렉터에 버전을 넣으면 그 버전 레이블을 다시는 올릴 수 없게 됩니다. 이미지만 바꾸는 배포는 되지만요.
  • 6.4 예제에는 버전 레이블이 세 종류 나옵니다. ver는 파드 스펙의 버전, appver는 앱 전체의 버전, release number는 CD 파이프라인 실행 ID입니다. 문제가 되는 건 ver입니다.
  • 먼저 배경입니다. 디플로이먼트의 spec.selector는 이 디플로이먼트가 관리할 파드를 고르는 조건이고, template.metadata.labels는 새로 만들 파드에 붙일 레이블입니다. 쿠버네티스는 이 둘이 맞는지 검사합니다. 템플릿으로 만든 파드를 셀렉터가 못 고르면 디플로이먼트가 자기가 만든 파드를 못 알아보니까요.
  • 또 하나, apps/v1 디플로이먼트는 만든 뒤에 셀렉터를 바꿀 수 없습니다. 셀렉터를 바꾸면 이미 떠 있는 레플리카셋과 파드가 갑자기 관리 대상에서 빠지거나 다른 디플로이먼트 것과 섞일 수 있어서 아예 막아 둔 겁니다.
  • 교재 예제는 셀렉터에 ver: 1.5.8을 넣었습니다. 다음 배포에서 파드 스펙 버전을 1.5.9로 올린다고 해 보겠습니다. template의 ver만 1.5.9로 바꾸면, 셀렉터는 1.5.8을 찾는데 새 파드는 1.5.9라서 selector does not match template labels 에러가 납니다.
  • 그럼 셀렉터도 같이 1.5.9로 바꾸면 될까요? 이번엔 field is immutable, 셀렉터는 못 바꾼다는 에러가 납니다. 두 에러 모두 kind 클러스터에서 그대로 나왔습니다.
  • 결국 이 디플로이먼트는 ver를 올릴 방법이 없습니다. 올리려면 디플로이먼트를 지우고 새로 만들어야 하는데, 그러면 무중단 롤링이 아니라 전부 내렸다가 올리는 배포가 됩니다.
  • 그래서 셀렉터에는 app, tier처럼 디플로이먼트가 살아 있는 동안 절대 안 바뀌는 것만 넣고, 버전은 template 레이블에만 둡니다. template 레이블은 바꿔도 되고, 바꾸면 롤아웃이 일어납니다. 바로 다음 장이 그 얘기입니다.
  • 두 번째 줄은 단순한 문법 문제입니다. 레이블 키에는 영문자, 숫자, 하이픈, 밑줄, 점만 쓸 수 있어서 release number처럼 공백이 있으면 API 서버가 받아 주지 않습니다. release-number로 쓰면 됩니다.
  • 세 번째 줄은 헬름 훅입니다. helm.sh/hook 어노테이션은 이 잡을 언제 돌릴지 헬름에게 알려 주는 표시입니다. 교재는 업그레이드 전, 삭제 전, 롤백 전에 DB를 백업하려고 이 키를 세 줄로 나눠 썼습니다.
  • 그런데 YAML은 같은 키가 여러 번 나오면 마지막 값만 남깁니다. 파서에 따라서는 에러를 내기도 합니다. 그래서 실제로는 pre-rollback만 남고, 업그레이드 전 백업은 돌지 않습니다. 여러 시점에 걸려면 쉼표로 이어서 한 줄로 씁니다.
  • 이 헬름 훅 문제는 4부 헬름 장표에서 다시 나옵니다. 깃옵스로 되돌리면 Flux는 롤백이 아니라 업그레이드를 하고 Argo CD는 롤백 훅을 아예 안 돌려서, 교재 예제 그대로면 깃으로 되돌릴 때 백업이 안 돈다는 얘기입니다.

  • 그다음 새 레플리카셋은 0에서부터 늘리고 옛 레플리카셋은 줄입니다. 이게 롤링 업데이트입니다.
  • 반대로 디플로이먼트 metadata 레이블만 바꾸면 template 해시가 그대로라서 아무 일도 안 일어납니다. kind에서 해 봤는데 레플리카셋이 하나 그대로였습니다. 교재도 이걸로 당황하는 경우가 흔하다고 합니다.
  • 롤백 쪽에서 보면, 컨트롤러는 옛 레플리카셋을 지우지 않고 레플리카 0으로 남겨 둡니다. revisionHistoryLimit 기본값인 10개까지요. rollout undo는 이 옛 레플리카셋의 template을 디플로이먼트에 다시 넣는 겁니다. 그래서 새 리비전 번호가 붙습니다.
  • rollout restart도 같은 원리입니다. template 어노테이션에 재시작 시각을 적어서 해시를 바꿉니다.

  • 원래 10개인데 maxSurge가 25%라 10의 25%, 2.5개를 올림해서 3개까지 더 떠 있어도 됩니다. 그래서 롤링이 시작되면 옛 파드를 끄기 전에 새 버전 파드 3개를 먼저 만듭니다. 이 순간 파드는 옛 10개와 새 3개, 13개입니다.
  • maxUnavailable이 0이라서 쓸 수 있는 파드가 10개 아래로 내려가면 안 됩니다. 그래서 새 파드 3개가 Ready가 된 뒤에야 옛 파드 3개를 끕니다. 그다음 다시 새 파드 3개를 만들고 옛 3개를 끄고, 이렇게 3개, 3개, 3개, 마지막 1개로 네 번 반복하면 전부 새 버전이 됩니다.
  • 잠깐 13개가 되니까 노드에 파드 3개분의 여유 자원이 있어야 합니다. 여유가 없으면 새 파드가 Pending에 걸리고 롤아웃이 거기서 멈춥니다.
  • 나머지 두 줄은 시간에 관한 설정입니다. readiness는 5초마다 /readyz를 보고, Ready가 된 뒤 10초를 버텨야 가용으로 칩니다. 이 두 값이 뒤에서 시간을 계산할 때 쓰입니다.
  • 오른쪽처럼 새 레플리카셋은 0, 3, 6, 9, 10으로 늘고 옛 레플리카셋은 10, 7, 4, 1, 0으로 줄어듭니다.
  • 그리고 교체되는 동안 두 버전이 같이 요청을 받습니다. 이게 무슨 문제를 만드는지 바로 다음 장에서 보겠습니다.

  • 위의 두 줄이 롤링의 속도와 용량을 정합니다. maxSurge는 교체하는 동안 원래 개수보다 더 떠 있어도 되는 수, maxUnavailable은 원래 개수보다 모자라도 되는 수입니다. 둘 다 개수나 퍼센트로 쓸 수 있고 기본값은 둘 다 25%입니다. 퍼센트일 때 maxSurge는 올림, maxUnavailable은 내림으로 계산합니다. 그래서 레플리카 10개면 surge 3개, unavailable 2개가 기본입니다.

  • revisionHistoryLimit은 옛 레플리카셋을 몇 개 남길지입니다. 기본 10개입니다. 이게 rollout undo로 돌아갈 곳의 목록이라, 줄여 두면 돌아갈 곳이 없어집니다.
  • 마지막 terminationGracePeriodSeconds는 파드를 끌 때 종료 신호를 보낸 뒤 강제로 죽이기까지 기다리는 시간입니다. 기본 30초입니다. 짧으면 하던 요청을 마치기 전에 잘립니다. 그 앞에 실행되는 preStop 훅은 3부 뒤쪽에서 따로 보겠습니다.

섞여도 괜찮으려면: 하위 호환

무엇이 섞이나괜찮은 변경안 되는 변경
API (다른 서비스, 프론트)응답에 필드 추가, 선택 파라미터 추가필드 삭제, 이름이나 의미 변경, 필수 파라미터 추가
DBNULL 허용 컬럼 추가 (확장)컬럼 삭제, 이름 변경, NOT NULL 추가를 같은 배포에서
큐 메시지, 이벤트필드 추가, 옛 컨슈머가 모르는 필드는 무시형식 변경. 옛 컨슈머가 새 메시지를 못 읽는다
캐시, 세션새 키 추가같은 키에 다른 형식 저장. 옛 버전이 읽다가 깨진다

그래서 보통 이렇게 한다

  • 새 버전은 옛 버전과 같이 돌아도 되게 짠다 (바로 앞 버전과 호환)
  • 새 기능은 플래그를 끈 채로 배포하고, 전부 교체된 뒤에 켠다
  • DB는 확장, 이전, 축소를 따로 배포 (뒤에서)

다른 전략에서는

  • 블루/그린: 한 번에 넘겨서 섞이는 시간이 짧다. 그래도 DB는 공유하고 keep-alive는 남는다
  • 카나리: 일부러 오래 섞는다. 호환이 더 필요하다
발표 노트
  • 섞여도 괜찮으려면 새 버전이 옛 버전과 같이 돌아도 문제없어야 합니다. 이걸 하위 호환이라고 합니다. 표는 무엇이 섞이는지와 어떤 변경은 괜찮고 어떤 변경은 안 되는지입니다.
  • 첫 줄 API입니다. 다른 서비스나 프론트가 우리 API를 부를 때, 롤링 중에는 옛 버전이 대답할 수도 있고 새 버전이 대답할 수도 있습니다. 응답에 필드를 추가하는 건 괜찮습니다. 옛 클라이언트는 모르는 필드를 무시하니까요. 반대로 필드를 지우거나 이름을 바꾸면, 새 버전 응답을 받은 쪽이 깨집니다.
  • DB는 3부 뒤쪽 "컬럼 추가는 세 번에 나눠서"에서 자세히 볼 확장, 축소 얘기입니다. NULL을 허용하는 컬럼을 추가하는 건 옛 버전이 몰라도 됩니다. 하지만 컬럼을 지우거나 이름을 바꾸는 걸 같은 배포에서 하면, 아직 떠 있는 옛 파드가 없는 컬럼을 찾다가 에러를 냅니다.
  • 큐 메시지와 캐시도 자주 잊습니다. 새 버전이 큐에 새 형식으로 메시지를 넣으면, 아직 옛 버전인 컨슈머가 그걸 못 읽습니다. 캐시도 같은 키에 새 형식으로 저장하면 옛 버전이 읽다가 깨집니다.
  • 그래서 보통 이렇게 합니다. 새 버전은 바로 앞 버전과 같이 돌아도 되게 짭니다. 새 기능은 플래그를 끈 채로 배포하고, 전부 교체된 뒤에 켭니다. 그러면 쿠폰 입력칸이 보였다 안 보였다 하는 일이 없습니다. DB는 확장, 이전, 축소를 따로 배포합니다.
  • 다른 전략과 비교하면, 블루/그린은 한 번에 넘기니까 섞이는 시간이 짧습니다. 그래도 DB는 두 환경이 공유하고, keep-alive 커넥션은 한동안 옛 버전에 남습니다. 카나리는 오히려 일부러 오래 섞어 두는 방식이라 호환을 더 꼼꼼히 챙겨야 합니다. 어느 전략이든 이 표는 지켜야 합니다.

롤링의 롤백은 롤링을 한 번 더 하는 것

되돌리는 방법

  • kubectl rollout undo: 0으로 남겨 둔 옛 RS의 template을 다시 적용 → 거꾸로 롤링
  • 깃옵스라면 배포 저장소에서 git revert → Flux가 맞춤
  • 걸리는 시간 = 롤아웃 시간. 옛 이미지를 노드가 다시 받아야 하면 더 길다

롤링에서 주의할 것

  • 프로브가 못 잡는 버그는 롤아웃을 끝까지 통과한다
  • 롤아웃이 멈춰도 쿠버네티스는 되돌리지 않는다 (다음 장)
  • 되돌리는 동안에도 교체가 일어나서 요청이 끊길 수 있다 (뒤에서 따로 봅니다)

깃옵스에서 rollout undo만 하면 에이전트가 깃에 적힌 새 버전으로 다시 돌려놓는다. 4부에서 자세히 본다

발표 노트
  • 롤링의 롤백은 롤링을 한 번 더 하는 겁니다. rollout undo는 0으로 남겨 둔 옛 레플리카셋의 template을 다시 적용해서 거꾸로 교체합니다. 깃옵스라면 배포 저장소에서 git revert를 합니다.
  • 그래서 되돌리는 시간이 롤아웃 시간과 같습니다. 옛 이미지를 노드가 다시 받아야 하면 더 깁니다. 1부에서 이미지를 작게 하자고 한 게 여기서 효과가 있습니다.
  • 롤링에서 주의할 게 세 가지 있는데, 첫째는 방금 본 대로 프로브가 못 잡는 버그는 그냥 통과한다는 겁니다. 둘째는 바로 다음 장에서 보고, 셋째는 세 번을 다 비교한 뒤에 따로 보겠습니다.

롤아웃이 실패해도 쿠버네티스는 되돌리지 않는다

$ kubectl rollout status deploy/web --timeout=90s
Waiting for deployment "web" rollout to finish:
  1 out of 3 new replicas have been updated...
error: deployment "web" exceeded its
  progress deadline
$ echo $?
1

$ kubectl get deploy web -o jsonpath=\
  '{.status.conditions[?(@.type=="Progressing")].reason}'
ProgressDeadlineExceeded

kind에서 없는 태그로 바꿔서 확인한 출력. 데모 예제는 progressDeadlineSeconds: 60

  • progressDeadlineSeconds(기본 600초)를 넘기면 상태 조건만 Progressing=False로 바뀐다
  • 옛 파드와 새 파드가 섞인 채로 멈춰 있다
  • 되돌리는 건 바깥에서: 파이프라인이 rollout status 종료 코드를 보고 판단
  • 깃옵스라면 Flux의 헬스 체크, Argo CD의 Health 상태가 이 조건을 읽는다

6.3: 이력이 남아서 "언제든 이전 버전으로 되돌릴 수 있다". 되돌릴 수 있을 뿐, 알아서 되돌리지는 않는다

발표 노트
  • 의외로 많이들 모르는 부분입니다. 롤아웃이 실패하면 쿠버네티스가 알아서 되돌릴 것 같은데, 안 되돌립니다.
  • progressDeadlineSeconds를 넘기면 상태 조건 하나만 바뀌고, 옛 파드와 새 파드가 섞인 채로 멈춰 있습니다. kind에서 없는 태그로 바꿔 봤습니다. 데모 예제는 progressDeadlineSeconds를 60초로 줄여 둬서 1분이면 실패로 표시됩니다. 종료 코드 1이 나오고, 파드 하나는 ErrImagePull, 옛 파드 세 개는 그대로 Running이었습니다. unavailable이 0이라 서비스는 계속 됐습니다.
  • 그래서 되돌리는 판단은 바깥에서 해야 합니다. 파이프라인이 종료 코드를 보고 판단하거나, 조금 뒤에 볼 카나리 컨트롤러가 합니다.
  • 깃옵스 도구도 이 조건을 읽기만 합니다. 배경부터 보면, Flux Kustomization에 wait: true를 켜거나 healthChecks로 디플로이먼트를 지정하면, Flux가 적용한 뒤 그 리소스가 준비될 때까지 기다립니다.
  • 디플로이먼트가 ProgressDeadlineExceeded로 멈추면 Flux는 Kustomization을 Ready=False로 표시하고 이유를 적어 둡니다. Argo CD도 같은 조건을 보고 앱을 Degraded로 표시합니다.
  • 둘 다 표시만 합니다. 옛 버전으로 되돌리지는 않습니다. 깃에 새 버전이 적혀 있으니 계속 그 상태로 맞추려고 할 뿐입니다. 이 상태를 보고 알림을 보내거나 git revert를 하는 건 사람이나 다른 도구의 몫입니다.

블루는 언제 내리나

너무 빨리 내리면

  • 문제가 늦게 드러나면 되돌릴 곳이 없다. 다시 배포해야 한다
  • Argo Rollouts 블루/그린의 scaleDownDelaySeconds 기본값은 30초
  • → 문제가 보이는 데 걸리는 시간만큼은 둬야 한다 (다음 카나리에서 다시)

교재가 꼽는 주의점

  • 두 환경을 동시에 띄울 용량이 필요하다
  • 진행 중인 트랜잭션, 스키마 호환 때문에 DB 마이그레이션이 어렵다. DB는 보통 공유한다
  • 실수로 두 환경을 다 지울 수 있다

셀렉터를 바꿔도 이미 맺은 keep-alive 커넥션은 한동안 옛 파드에 남는다

발표 노트
  • 블루/그린의 가치는 옛 버전이 살아 있어서 되돌리는 게 전환이 된다는 점입니다. 그러면 블루를 언제 내릴지 정해야 합니다.
  • 너무 빨리 내리면 문제가 늦게 드러났을 때 되돌릴 곳이 없습니다. Argo Rollouts로 블루/그린을 하면 옛 버전을 내리는 기본값이 30초입니다. 그대로 두면 30초 뒤부터는 되돌리기가 재배포가 됩니다. 얼마나 둬야 하는지는 카나리에서 대기 시간을 보면서 같이 보겠습니다.
  • 교재가 꼽는 주의점도 있습니다. 용량이 두 배 들고, DB는 보통 두 환경이 공유해서 여전히 두 버전을 다 지원해야 합니다.

  • 2회차에서 블루/그린을 서비스 셀렉터를 손으로 바꿔서 했는데, 이걸 컨트롤러가 대신 해 주는 게 Argo Rollouts입니다. kind에 1.10.0을 직접 설치해 봤습니다.
  • 설치는 네임스페이스와 매니페스트 하나입니다. 그런데 공식 문서대로 그냥 kubectl apply를 했더니 CRD 두 개가 거부됐습니다. 메시지가 오른쪽입니다. 어노테이션이 너무 길다는 건데, 일반 kubectl apply는 적용한 내용 전체를 last-applied라는 어노테이션에 저장합니다. 다음 apply 때 비교하려고요. Rollout CRD는 스키마가 커서 이 어노테이션이 256KB 한도를 넘습니다. --server-side로 적용하면 비교를 API 서버가 해서 이 어노테이션을 안 쓰니까 들어갑니다. 큰 CRD를 설치할 때 자주 만나는 문제라 알아 두시면 좋습니다.
  • 설치되는 건 컨트롤러 하나와 CRD 다섯 개입니다. Rollout이 디플로이먼트 대신 쓸 리소스고, AnalysisTemplate과 AnalysisRun이 판정, Experiment가 카나리에서 본 베이스라인 비교입니다.
  • 상태를 보거나 promote, abort를 하려면 kubectl 플러그인을 따로 설치합니다.
  • 디플로이먼트를 Rollout으로 바꾸는 건 간단합니다. apiVersion과 kind를 바꾸고 strategy 자리에 blueGreen이나 canary를 적습니다. 파드 template은 디플로이먼트와 똑같습니다. 기존 디플로이먼트를 그대로 두고 Rollout이 workloadRef로 가리키게 해서 조금씩 옮기는 방법도 있습니다.

  • 블루/그린 설정값입니다. 2회차에서 손으로 했던 게 각 필드에 어떻게 대응되는지 보겠습니다.
  • activeService는 실제 사용자 트래픽을 받는 서비스이고, previewService는 그린만 따로 보는 서비스입니다. 2회차의 order-api와 order-api-preview입니다. 서비스 셀렉터에는 app만 적어 두면 되고, 블루냐 그린이냐는 컨트롤러가 해시를 붙여서 정합니다. 다음 장에서 실제로 보여 드리겠습니다.
  • autoPromotionEnabled는 기본값이 true입니다. 그대로 두면 그린이 Ready가 되자마자 자동으로 넘어가서, preview로 확인할 틈이 없습니다. 2회차처럼 확인하고 넘기려면 false로 두고 promote 명령으로 넘깁니다. 일정 시간 뒤 자동으로 넘기고 싶으면 autoPromotionSeconds를 씁니다.

  • prePromotionAnalysis를 걸면 전환 전에 자동으로 판정해서, 실패하면 전환을 안 합니다. 2회차에서 사람이 하던 스모크 테스트를 여기에 넣는 겁니다. postPromotionAnalysis는 전환 후에 판정해서 실패하면 블루로 되돌립니다.

카나리는 베이스라인과 비교한다

배포 전후 비교는 더 나쁘다. 그 사이 시간대, 트래픽, 다른 팀 배포가 바뀐다

베이스라인은 판정이 끝나면 카나리와 같이 내린다

발표 노트
  • 이번 회차에서 먼저 보셔야 할 부분입니다. 카나리를 무엇과 비교하느냐입니다.
  • 배경부터 보면, 카나리 판정은 결국 비교입니다. 새 버전 파드의 에러율이나 레이턴시가 옛 버전보다 나쁜지를 봅니다. 그래서 비교 상대를 잘못 고르면 멀쩡한 배포를 멈추거나, 나쁜 배포를 통과시킵니다.
  • 흔히 카나리를 나머지 프로덕션과 비교합니다. 그런데 프로덕션 파드는 며칠째 떠 있어서 캐시가 따뜻하고, JVM이면 워밍업도 끝났고, 개수도 훨씬 많습니다. 카나리는 방금 떴습니다. 그러면 카나리가 느린 게 새 파드라서인지 새 버전이라서인지 구분이 안 됩니다.
  • 그래서 옛 버전으로 카나리와 같은 크기의 파드를 하나 더 방금 새로 띄웁니다. 이게 베이스라인입니다. 트래픽도 카나리와 같은 비율로 줍니다. 그림에서는 프로덕션 90%, 베이스라인 5%, 카나리 5%입니다. 프로덕션 파드는 10개 그대로 둡니다. 트래픽 라우터로 비율을 나누면 Argo Rollouts가 기존 파드 수를 줄이지 않습니다.
  • 그러면 베이스라인과 카나리는 같은 크기, 같은 나이, 같은 시각, 같은 트래픽이고 다른 건 버전 하나입니다. 그래서 둘 사이에 차이가 나면 버전 때문이라고 말할 수 있습니다.
  • 배포 전 30분과 배포 후 30분을 비교하는 건 더 나쁩니다. 그 사이에 시간대도 바뀌고 다른 팀 배포도 나가니까요. 베이스라인은 판정이 끝나면 카나리와 같이 내립니다.

spec:
  rules:
  - backendRefs:
    - {name: order-api-stable, port: 80, weight: 95}
    - {name: order-api-canary, port: 80, weight: 5}
발표 노트
  • 교재는 카나리를 일정 비율의 트래픽을 새 버전으로 보내는 거라고 하고, 대부분의 인그레스와 서비스 메시가 이 기능을 준다고 합니다. 쿠버네티스에서는 어디서 나누느냐에 따라 정밀도가 다릅니다.
  • 제일 단순한 건 레플리카 비율입니다. 같은 셀렉터에 옛 버전 9개, 새 버전 1개를 두면 서비스가 둘을 구분하지 않고 나눠 줍니다. 그런데 1%를 하려면 파드가 100개 있어야 합니다.
  • 비율이 흔들리는 이유도 있습니다. 배경부터 보면, 서비스로 가는 요청은 kube-proxy가 커넥션을 맺을 때 파드를 하나 고릅니다. 요청마다 고르는 게 아닙니다.
  • 그래서 keep-alive를 쓰는 클라이언트나 HTTP/2처럼 커넥션 하나로 요청을 계속 보내는 클라이언트는 처음 고른 파드에 계속 붙습니다. 그런 클라이언트가 몇 개 없으면 10%로 잡아도 실제로는 0%나 30%가 될 수 있습니다.
  • 요청 단위로 나누려면 인그레스나 게이트웨이가 필요합니다. 지금 표준은 Gateway API의 HTTPRoute weight입니다. 커뮤니티 ingress-nginx는 2026년 3월에 유지보수가 끝나서 지금은 은퇴한 프로젝트입니다. 그래서 표에 예전 방식으로 적었습니다. 새로 만든다면 Gateway API를 쓰면 됩니다. 서비스 메시는 5주차에 봤듯이 서비스끼리 호출까지 나눌 수 있습니다.
  • 헤더, 쿠키 줄은 비율이 아니라 사람으로 나눕니다. 예를 들어 사내 직원 요청에만 헤더를 붙여 새 버전으로 보내는 식입니다. 교재가 A/B나 다크 릴리스라고 부르는 게 이 방식이고, 뒤에서 A/B와 카나리를 따로 비교합니다.

  • 트래픽이 적으면 5%로는 표본이 모자란다 → 더 오래

발표 노트
  • 단계마다 얼마나 기다리느냐입니다. 7장이 여러 리전에 배포할 때 쓰는 기준을 그대로 가져왔습니다. time-to-smoke, 연기가 날 때까지의 시간이라는 말인데, 배포 뒤 문제가 보이기까지 걸리는 시간입니다.
  • 교재 경험칙은 과거 평균의 두 배입니다. 지난 사고들이 평균 5분 만에 드러났다면 단계마다 10분 기다립니다. 이걸 쓰려면 사고마다 배포 후 몇 분 만에 알았는지 적어 둬야 합니다.
  • 기다리는 이유는 교재 7장과 5.8에 있습니다. 버그는 확률적이고, 늦게 보이는 것도 있고, 스테이징은 프로덕션과 다르니까 프로덕션에서 조금씩 확인하는 겁니다. 아까 블루를 언제 내리냐는 질문도 이 기준으로 답하면 됩니다.

  • 카나리 설정값입니다. 핵심은 steps입니다. 위에서부터 한 단계씩 실행합니다.
  • setWeight는 새 버전에 보낼 비율입니다. 여기서 알아 둘 게 있습니다. trafficRouting, 즉 트래픽을 나누는 장치를 연결하지 않으면 비율을 파드 수로 흉내 냅니다. 레플리카 10개에 setWeight 20이면 새 버전 2개, 옛 버전 8개로 맞춥니다. 그래서 5%처럼 파드 수로 안 떨어지는 비율은 정확히 안 나옵니다. 정확히 하려면 다음 장의 트래픽 라우터가 필요합니다.
  • pause는 두 가지가 있습니다. duration을 적으면 그 시간만큼 기다렸다가 다음 단계로 갑니다. 3회차의 대기 시간이 여기 들어갑니다. 중괄호만 쓰면 시간이 없는 거라서, 사람이 promote 명령을 줄 때까지 무한히 멈춰 있습니다. 25%까지는 자동으로 가고 거기서 사람이 한 번 보고 넘기고 싶을 때 씁니다.
  • analysis 단계에서 판정하고, 실패하면 거기서 중단합니다. 3회차의 베이스라인 비교는 analysis 대신 experiment 단계로 합니다.
  • canaryService와 stableService는 카나리 파드만, 안정 버전 파드만 가리키는 서비스입니다. 컨트롤러가 블루/그린 때처럼 해시를 붙여서 관리하고, 트래픽 라우터가 이 두 서비스로 비율을 나눠 보냅니다.
  • maxSurge와 maxUnavailable은 롤링에서 본 것과 같은 뜻으로, 단계 사이에서 파드를 늘리고 줄일 때 씁니다. dynamicStableScale은 라우터가 있을 때 쓰는 값인데, 기본 false라서 카나리가 5%를 받아도 안정 버전 파드는 10개를 그대로 둡니다. 3회차에서 프로덕션 파드를 10개로 둔 이유가 이겁니다.

이 장은 문서 기준입니다. kind 실습은 라우터 없이 파드 수 방식으로 했습니다 (다음다음 장)

발표 노트
  • 앞 장에서 라우터가 없으면 비율을 파드 수로 흉내 낸다고 했는데, 정확히 5%를 보내려면 트래픽을 나누는 장치를 연결해야 합니다. 3부 앞에서 본 Gateway API로 연결하는 방법입니다. 이 장은 문서를 보고 정리한 것이고, kind 실습은 라우터 없이 했습니다.
  • 세 단계입니다. 먼저 Argo Rollouts 컨트롤러에 Gateway API 플러그인을 등록합니다. argo-rollouts-config라는 ConfigMap에 플러그인 이름과 내려받을 위치를 적습니다.
  • 두 번째로 HTTPRoute를 만들고 백엔드로 stable 서비스와 canary 서비스 두 개를 둡니다. 앞 장의 stableService, canaryService입니다.

  • 컨트롤러가 HTTPRoute를 수정해야 하니 RBAC 권한을 추가해야 하고, Istio나 NGINX Ingress, AWS ALB는 플러그인 없이 바로 지원됩니다. 중단되면 weight가 0으로 돌아가서 트래픽이 전부 stable로 갑니다.

발표 노트
  • 판정을 정하는 AnalysisTemplate 설정값입니다. 무엇으로 재고, 몇 번 재고, 언제 실패로 볼지를 정합니다.
  • provider가 무엇으로 잴지입니다. Prometheus 쿼리, Datadog 쿼리, 웹 호출, 그리고 Job을 띄워서 그 결과로 판정하는 방법도 있습니다. 회사에서 Datadog을 쓰신다면 argo-rollouts 네임스페이스에 API 키 시크릿을 만들고 Datadog 쿼리를 그대로 적으면 됩니다.
  • 시간 관련이 세 개입니다. initialDelay는 첫 측정 전에 기다리는 시간입니다. 기본값이 0이라서 안 적으면 카나리에 트래픽이 들어오기도 전에 잽니다. interval은 몇 분마다 잴지, count는 몇 번 잴지입니다. count를 안 적으면 측정이 끝나지 않아서 롤아웃이 그 단계에서 안 넘어갑니다. 1분 간격 10번이면 약 10분 동안 봅니다.
  • 판정은 successCondition에 합격 조건을 적습니다. result가 쿼리 결과고, 예시는 카나리와 베이스라인 에러율 차이가 0.005, 즉 0.5%p보다 작아야 합격입니다.
  • failureLimit은 불합격을 몇 번까지 봐줄지입니다. 기본값이 0이라 한 번만 불합격이어도 실패입니다. 일시적인 흔들림에 멈추는 게 싫으면 1이나 2로 올립니다. consecutiveErrorLimit은 불합격이 아니라 쿼리 자체가 에러일 때입니다. 예를 들어 새 파드가 아직 5xx를 한 번도 안 내서 결과가 비어 있으면 에러가 되는데, 연속 4번까지 봐줍니다. 그래서 쿼리에 or vector(0)을 붙여서 비어 있으면 0으로 나오게 합니다.

자동으로 판정하기: Argo Rollouts

kind: Rollout          # argoproj.io/v1alpha1
spec:
  strategy:
    canary:
      trafficRouting: {…}  # 가중치를 쓰려면 필요
      steps:               # 25%, 50% 단계는 examples/04
      - experiment:        # 베이스라인과 카나리를 같이 띄움
          duration: 10m
          templates:
          - {name: baseline, specRef: stable, weight: 5}
          - {name: canary,   specRef: canary, weight: 5}
          analyses:
          - {name: compare, templateName: canary-vs-baseline}
---
kind: AnalysisTemplate
metadata: {name: canary-vs-baseline}
spec:
  metrics:
  - name: error-rate-diff
    initialDelay: 1m        # 트래픽이 먼저 들어오게
    interval: 1m
    count: 10
    failureLimit: 0        # 한 번만 넘어도 실패
    successCondition: result[0] < 0.005
    provider:
      prometheus:
        query: 카나리 5xx 비율 − 베이스라인 5xx 비율  # 5xx 없으면 0
  • experiment 단계가 베이스라인(옛 버전)과 카나리(새 버전)를 같은 크기로 띄운다
  • 1분 기다린 뒤, 1분마다 두 집단의 에러율 차이를 10번 잰다
  • failureLimit: 0: 한 번만 기준을 넘어도 자동으로 중단하고 가중치를 0으로
  • experiment의 weight는 trafficRouting이 있어야 쓸 수 있다
  • 6.3에서 본 대로 쿠버네티스는 알아서 되돌리지 않는다. 그 판단을 이런 컨트롤러가 맡는다
  • Flagger도 같은 일을 한다. Argo Rollouts는 Flux와 같이 써도 된다

예제 전체는 examples/04-argo-rollouts. 필드는 쓰는 버전의 문서로 확인

발표 노트
  • 이걸 사람이 대시보드를 보면서 하면 금요일 저녁에 아무도 안 봅니다. 그래서 자동으로 판정하는 도구를 씁니다. 예시는 Argo Rollouts입니다.
  • 배경부터 보면, Argo Rollouts는 Deployment 대신 Rollout이라는 리소스를 씁니다. 파드 템플릿은 Deployment와 같고, strategy 부분에 카나리 단계를 순서대로 적습니다. 컨트롤러가 이 단계를 하나씩 실행합니다.
  • 첫 단계가 experiment입니다. 여기서 베이스라인과 카나리를 같이 띄웁니다. specRef: stable은 지금 돌고 있는 옛 버전 템플릿으로, specRef: canary는 새 버전 템플릿으로 파드를 만든다는 뜻입니다. 둘 다 트래픽을 5%씩 받습니다. 이렇게 요청 비율로 가중치를 주려면 trafficRouting에 Gateway API나 Istio 같은 라우터가 설정돼 있어야 합니다.
  • experiment가 도는 동안 아래 AnalysisTemplate이 1분마다 프로메테우스에 물어봅니다. 카나리 5xx 비율에서 베이스라인 5xx 비율을 뺀 값이 0.5%p보다 작은지를 봅니다. count 10, interval 1m이라 약 10분 동안 재고, experiment 기간과 맞습니다. initialDelay 1m은 첫 측정 전에 트래픽이 먼저 들어오게 기다리는 시간입니다. 가중치가 막 붙은 직후에 재면 요청이 거의 없어서 값이 의미가 없으니까요.
  • 실제 쿼리는 5xx가 한 건도 없을 때를 챙겨야 합니다. 5xx가 없으면 프로메테우스가 빈 결과를 돌려줘서 뺄셈이 안 됩니다. 그래서 예제 파일에서는 5xx 쪽을 or vector(0)으로 감싸서 0으로 칩니다.
  • failureLimit은 실패를 몇 번까지 봐줄지입니다. 0으로 두면 한 번만 기준을 넘어도 분석이 실패하고, 롤아웃이 바로 중단되면서 가중치가 0으로 돌아갑니다. 1로 두면 두 번째 실패에서 멈춥니다.
  • 통과하면 다음 단계로 가서 25%, 50%로 늘립니다. 장표에서는 줄였고 전체는 examples/04에 있습니다.
  • 1회차에서 롤아웃이 성공으로 끝나 버린 걸 기억하시죠. 쿠버네티스는 버전이 괜찮은지 판단하지 않습니다. 그 판단을 메트릭으로 해 주는 게 이 컨트롤러입니다. Flagger도 같은 일을 하고, Argo Rollouts는 Argo CD 없이 Flux와 같이 써도 됩니다.

  • 마지막 줄이 중요합니다. 중단됐는데도 Rollout의 spec에 적힌 이미지는 새 버전 그대로입니다. 컨트롤러는 트래픽과 파드만 옛 버전으로 돌렸고, 원하는 상태는 안 바꿨습니다. 깃옵스라면 깃에도 새 버전이 그대로 있어서, 다음 날 git revert로 맞춰야 한다는 게 4부 얘기입니다.

  • 블루/그린과 카나리가 줄이는 게 다릅니다. 블루/그린은 되돌리는 시간을 줄입니다. 겪는 비율은 여전히 100%입니다. 카나리는 겪는 사람 자체를 줄입니다. 5%만 겪었고, 그것도 자동으로 멈췄습니다.
  • 숫자를 한 번에 다시 보면 이렇습니다. 롤링은 전부 새 버전인 300초에 초당 30건, 오르내리는 360초에 초당 15건이라 약 1만 4천 건입니다. 블루/그린은 초당 30건이 180초라 5,400건입니다. 카나리는 초당 50건의 3%, 1.5건이 60초라 약 90건입니다.
  • 하나 감안할 게 있습니다. 롤링은 알람에서 결정까지 3분, 블루/그린은 1분으로 잡았습니다. 롤링도 1분 만에 결정했다면 약 1만 1천 건이고, 나머지 차이가 되돌리는 방식에서 나옵니다.
  • 대신 아래 줄처럼 미리 있어야 할 게 늘어납니다. 롤링은 좋은 프로브만 있으면 되지만, 카나리는 트래픽을 나누는 장치, 메트릭, 판정 컨트롤러까지 필요합니다.
  • 여러분 서비스라면 어느 쪽이 맞을까요? 트래픽이 적으면 카나리 5%로는 판정할 표본이 모자라서 블루/그린이 나을 수도 있습니다.

파드가 죽을 때 두 일이 동시에 시작된다

교재 5.7: "롤링 업데이트 중에는 클라이언트와의 커넥션이 끊어질 수 있으니 주의하자. 그래서 레디니스 프로브와 preStop 라이프 사이클 훅이 필요하다"

발표 노트
  • 세 번을 비교했으니, 어느 전략이든 파드를 바꿀 때 공통으로 챙길 것을 하나 보겠습니다. 1회차 되돌리기에서 미뤄 둔, 교체 중에 요청이 끊기는 문제입니다. 롤링은 물론이고, 블루/그린에서 블루를 내릴 때나 카나리 파드를 내릴 때도 똑같이 생깁니다.
  • 교재는 롤링 중에 커넥션이 끊길 수 있으니 레디니스와 preStop이 필요하다고만 합니다. 왜 끊기는지 그림으로 보겠습니다.
  • 파드를 지우면 두 일이 동시에 시작됩니다. 위는 네트워크 쪽입니다. 파드가 EndpointSlice에서 먼저 종료 중, 준비 안 됨으로 표시되고 그다음 빠집니다. kube-proxy와 로드밸런서가 그걸 알아채는 데 또 시간이 걸립니다. 아래는 kubelet 쪽입니다. preStop을 부르고 SIGTERM을 보냅니다. 둘 사이에 순서가 없습니다.
  • 아래가 더 빠르면 앱은 이미 종료 중인데 로드밸런서는 아직 그 파드로 요청을 보냅니다. 롤링 업데이트가 끊기는 가장 흔한 이유입니다.
  • 위쪽에는 클러스터 밖도 들어갑니다. 클라우드 로드밸런서가 타깃을 빼는 데는 수 초에서 수십 초가 걸립니다. 그래서 외부 LB를 쓰는 환경에서 더 잘 보입니다. 데모에서 다시 봅니다.

어느 전략이든 두 버전이 같이 돈다(블루/그린도 DB는 공유). 그래서 확장, 이전, 축소는 전략과 상관없이 필요하다

발표 노트
  • 3부 정리입니다. 상황별로 이렇게 고르면 될 것 같습니다.
  • 처음이면 교재 말대로 롤링부터 하고, 프로브와 preStop을 제대로 챙깁니다. 되돌리는 시간을 줄이고 싶고 용량이 있으면 블루/그린, 트래픽이 많고 메트릭이 갖춰져 있으면 카나리입니다. 기능 단위로 조절하고 싶으면 플래그를 같이 씁니다.
  • 어느 전략이든 공통으로 걸리는 게 하나 있습니다. 두 버전이 같이 돈다는 겁니다. 블루/그린도 DB는 공유하니까요. 그래서 앞에서 본 확장, 이전, 축소는 전략과 상관없이 필요합니다. 4부로 가기 전에 교재 7장의 리전 이야기를 짧게 보겠습니다.

교재내용

리전이 하나뿐이면 리전을 클러스터나 가용 영역으로 바꿔 읽어도 같은 얘기입니다

  • 배포 전략 관점에서 보면 7장의 롤아웃은 3부에서 본 카나리를 크게 키운 겁니다. 3부에서는 한 클러스터 안에서 요청 5%로 나눴다면, 7장은 리전 하나를 한 단계로 씁니다.
  • 순서는 카나리 리전부터입니다. 사내 팀이나 위험이 적은 고객의 트래픽을 받는 곳이고 며칠 둡니다. 그다음 비슷하고 작은 곳, 비슷하고 큰 곳, 성격이 다른 곳 순서입니다. 교재는 입력이나 부하가 크게 다른 리전은 한 번에 하나씩만 내라고 합니다. 여러 곳에 한꺼번에 내면 문제가 났을 때 어느 리전의 차이 때문인지 가리기 어렵습니다. 단계 사이 대기 시간은 3부에서 본 time-to-smoke를 그대로 씁니다.
  • 그 밖에 챙길 게 두 가지입니다. 이미지를 쓰는 곳 가까이에 둬야 노드가 죽었을 때 빨리 복구되고, 리전별 설정은 복사하지 말고 공통 하나에 차이만 덮어써야 어긋나지 않습니다.
  • 마지막으로 7.5절입니다. 문제가 생기면 롤아웃 안 한 리전으로 트래픽을 먼저 옮기라고 하는데, DNS로 나누고 있으면 캐시 때문에 다 빠지는 데 하루가 걸릴 수도 있다고 합니다. 그래서 몇 분 걸리는지 평소에 재서 연습하라고 합니다. 여기까지가 7장이고, 다시 배포 얘기로 돌아가겠습니다.

깃옵스에서 되돌리는 방법 세 가지

방법되돌리는 것속도깃옵스에서는
트래픽 전환사용자가 보는 버전 (블루/그린 셀렉터, 카나리 가중치 0)수 초전략이 허락할 때만. 코드는 그대로
git revert원하는 상태동기화 + 롤아웃기본은 이것. 기록이 남는다
kubectl rollout undo클러스터의 실제 상태롤아웃 시간깃은 그대로라 에이전트가 새 버전으로 다시 돌려놓는다
# 기본: 깃을 되돌리고 바로 동기화
git revert a41d77c && git push
flux reconcile kustomization order-api --with-source   # interval을 기다리지 않는다

# 급해서 클러스터를 직접 만져야 한다면, 에이전트부터 멈춘다
flux suspend kustomization order-api        # Argo CD는 auto-sync 끄기
kubectl -n order rollout undo deploy/order-api
# 그다음 깃을 맞추고 다시 켠다
발표 노트
  • 깃옵스에서 되돌리는 방법은 세 가지입니다. 블루/그린이나 카나리처럼 옛 버전이 떠 있으면 트래픽 전환이 제일 빠릅니다. 기본은 git revert이고, 바로 flux reconcile을 해서 동기화 주기를 기다리지 않습니다.
  • 세 번째 rollout undo가 함정입니다. undo로 되돌려도 깃에는 새 버전이 적혀 있어서, Flux나 selfHeal을 켠 Argo CD가 다시 새 버전으로 돌려놓습니다. 급하게 되돌렸는데 몇 분 뒤에 장애가 다시 나는 겁니다.
  • 그래서 직접 만져야 한다면 에이전트를 먼저 멈추고, 되돌린 뒤 깃을 맞추고, 다시 켭니다. Argo CD에서 selfHeal이 꺼져 있으면 undo가 남는 대신 깃과 클러스터가 다른 채로 남습니다. 어느 쪽이든 깃을 맞춰야 끝납니다.

Argo CD에서 되돌릴 때

$ argocd app history guestbook
ID  DATE                  REVISION
0   2026-10-04 11:20:45   HEAD (8088f4c)

$ argocd app rollback guestbook 0
rpc error: code = FailedPrecondition
desc = rollback cannot be initiated
       when auto-sync is enabled

# 기본: 깃을 되돌린다
git revert a41d77c && git push
argocd app sync order-api      # 3분 주기를 기다리지 않고

# 급할 때: 자동 동기화를 끄고 되돌린 뒤 깃을 맞춘다
argocd app set order-api --sync-policy none
argocd app rollback order-api <ID>
git revert … && git push
argocd app set order-api --sync-policy automated
상황Argo CD에서
auto-sync 켜짐app rollback은 거부된다. 깃이 다시 덮어쓰기 때문
selfHeal 켜짐kubectl rollout undo도 다시 새 버전으로 덮어쓴다
selfHeal 꺼짐undo는 남지만 OutOfSync로 깃과 어긋난 채
Rollout이 중단됨Application Health가 Degraded. 표시만 하고 되돌리지 않는다
헬름 차트pre-rollback 훅은 실행 안 한다 (helm template으로 렌더링)

Flux로 하면: flux suspend → kubectl rollout undo → git revert → flux resume (앞 장)

발표 노트
  • Argo CD를 쓸 때 되돌리는 방법입니다. kind에서 직접 해 봤습니다.
  • Argo CD에도 rollback 명령이 있습니다. app history로 이력을 보고 app rollback에 이력 번호를 주면 그때 상태로 되돌립니다. 그런데 자동 동기화를 켜 둔 상태에서 해 보니 거부됐습니다. 메시지가 왼쪽 빨간 줄입니다. 자동 동기화가 켜져 있으면 rollback을 시작할 수 없다는 겁니다. 되돌려 봤자 깃에는 새 버전이 적혀 있어서 바로 다시 덮어쓰니까, 아예 막아 둔 겁니다.
  • 그래서 기본은 Flux와 같습니다. 배포 저장소에서 git revert를 하고, 3분 주기를 기다리지 않게 argocd app sync로 바로 동기화합니다.
  • 정말 급해서 깃 커밋을 기다릴 수 없으면, 자동 동기화를 끄고 app rollback으로 되돌린 다음, 깃을 맞추고 자동 동기화를 다시 켭니다. Flux의 suspend, resume과 같은 순서입니다.
  • 오른쪽 표는 상황별로 정리한 겁니다. selfHeal이 켜져 있으면 kubectl rollout undo도 다시 덮어씁니다. 1부에서 selfHeal을 켜자 replicas가 바로 깃 값으로 돌아간 것과 같은 동작입니다. Argo Rollouts가 중단되면 Application은 Degraded로 표시만 하고 되돌리지는 않습니다. 헬름 차트는 템플릿으로만 렌더링해서 pre-rollback 훅이 안 돕니다.

  • 롤백하면 코드는 옛 버전으로 돌아가지만 새 버전이 쓴 데이터는 그대로 남습니다. 옛 코드와 새 데이터 조합은 테스트한 적이 없습니다.

  • 그럴 때는 고쳐서 다시 내보내는 게 나을 수 있습니다. 교재 7.5는 급하게 만든 수정 빌드가 더 나쁠 수 있다고 경고하니까, 수정 빌드도 카나리 같은 같은 전략으로 내보냅니다.

같이 되돌릴 것은 한 차트로 묶는다

  • 교재 6.5: 함께 롤백하거나 업그레이드할 서비스는 같은 헬름 차트로
  • helm rollback 한 번에 웹, DB 디플로이먼트, 잡 매니페스트가 같이 이전 버전으로 (데이터는 아니다)
  • 6.4 예제는 헬름 훅으로 업그레이드, 삭제, 롤백 직전에 DB를 백업한다
  • 교재는 훅 키를 세 번 써서 pre-rollback만 남는다 (1부)
  • 깃으로 되돌리면 Flux는 upgrade를 한다 (pre-rollback은 실패 대응으로 롤백할 때만). Argo CD는 helm template이라 롤백 훅이 없다
  • → 교재 예제 그대로면 깃으로 되돌릴 때 백업이 안 돈다
kind: Job
metadata:
  name: db-backup
  annotations:
    "helm.sh/hook": pre-upgrade,pre-delete,pre-rollback
    "helm.sh/hook-delete-policy": hook-succeeded
spec:
  template:
    spec:
      containers:
      - name: mysqldump
        image: evillgenius/mysqldump:v1
      restartPolicy: Never
발표 노트
  • 6장 모범 사례 중 롤백과 바로 이어지는 게 이겁니다. 같이 되돌려야 하는 서비스는 같은 헬름 차트로 묶으라는 겁니다. 그러면 helm rollback 한 번에 웹, DB 디플로이먼트, 잡 매니페스트가 같이 이전 버전으로 돌아갑니다. 데이터까지 돌아가는 건 아닙니다. 앞 장에서 본 그대로입니다. 6.4 예제는 훅으로 업그레이드, 삭제, 롤백 직전에 DB를 백업합니다.
  • 그런데 1부에서 봤듯이 교재는 훅 키를 세 번 써서 마지막 pre-rollback만 남습니다.
  • 여기에 깃옵스가 겹치면 더 복잡해집니다. 도구마다 나눠 보겠습니다.
  • Flux helm-controller는 깃에서 차트 버전이나 값을 되돌리면 옛 버전으로 upgrade를 합니다. 그래서 pre-upgrade 훅이 걸립니다. pre-rollback 훅은 업그레이드가 실패해서 Flux의 실패 대응 설정이 helm rollback을 할 때만 걸립니다.
  • Argo CD는 헬름 차트를 helm template으로 매니페스트로 바꿔서 적용합니다. 헬름 릴리스 자체를 만들지 않아서 pre-rollback 훅은 아예 돌지 않습니다. pre-upgrade 같은 일부 훅은 Argo CD 동기화 훅으로 바꿔서 돌려 주지만 롤백 훅은 대응하는 게 없습니다.
  • 그래서 교재 예제처럼 pre-rollback만 남아 있으면, 깃으로 되돌릴 때는 어느 도구든 백업이 돌지 않습니다. 오른쪽처럼 쉼표로 이어 쓰면 적어도 Flux에서는 pre-upgrade로 백업이 돕니다.

  • 메시지 형식, 외부 API 계약이 바뀌었나

되돌릴 때

  1. 옛 버전이 떠 있으면 트래픽부터 전환
  2. 배포 저장소에서 git revert, 바로 reconcile
  3. 급하면 에이전트 멈춤 → undo → 깃 맞춤 → 재개
  4. 에러율이 원래대로 왔는지 확인
  5. 걸린 시간과 막힌 곳 기록

교재 7.5: 아무리 뻔한 단계라도 빠짐없이 적는다. 급할 때는 가장 쉬운 단계부터 잊어버린다

발표 노트
  • 지금까지 내용을 체크리스트로 만들면 이렇게 됩니다. 교재 7.5절이 뻔한 단계까지 다 적으라고 해서 정말 뻔한 것까지 넣었습니다.
  • 왼쪽은 배포 전에 볼 것입니다. 이번 변경에 되돌릴 수 없는 게 있는지를 배포 전에 알면, 이번엔 롤백보다 고쳐서 내보내는 쪽으로 가야겠다는 걸 미리 정할 수 있습니다.
  • 오른쪽 마지막 줄, 걸린 시간과 막힌 곳은 꼭 적어 둡니다. 이게 쌓여야 3부에서 본 카나리 대기 시간도 정할 수 있습니다. 여러분 팀 체크리스트에 뭐가 더 있는지 토론 때 듣고 싶습니다.

  • 데이터 전체 복구

  • 틀린 부분을 적어 두고 자동화한다

5.8: 카오스 실험

  1. 정상 상태에 대한 가설
  2. 실제로 일어날 법한 이벤트 준비
  3. 대조군과 비교
  4. 가설 검증

영향 범위는 작게, 실험은 자동화. 도구 예: Chaos Toolkit, KubeMonkey (5.9.4)

연습하면 어디서 막히는지 미리 알 수 있다. 카오스는 8주차 20장에서 자세히

발표 노트
  • 절차를 문서로만 두면 막상 돌릴 때 어디서 막히는지 모릅니다. 교재 7.5절은 급하지 않을 때 연습하라고 하고, 무엇을 연습할지도 적어 둡니다.
  • 5.8절 카오스 실험도 같은 얘기입니다. 가설을 세우고 대조군과 비교합니다. 3부 카나리의 베이스라인이 여기서도 대조군으로 나옵니다.
  • 연습해 보면 어디서 막히는지 미리 알 수 있습니다. 카오스는 다음 주에 남희 님이 자세히 다룹니다.
