# 7주차 발표 스크립트: 릴리스 파이프라인

`slides.html` 각 장의 발표 노트를 뽑아 연습용으로 정리한 문서입니다. 발표할 때는 `P` 키로 발표자 창을 띄우면 같은 원고와 다음 장, 시계가 같이 보입니다.

원고를 고칠 때는 `src/`의 조각을 고치고 `python3 src/build.py`로 다시 만듭니다. 장표와 이 문서가 같이 바뀝니다.

### 흐름

- **서론**: 제일 중요한 게 뭘까 → 흔한 답 → 금요일 6시 배포 사고 → 일단 되돌리고 싶다 → 처음부터 되돌리기 쉽게 내보내는 게 배포 전략
- **1부 준비**: 돌아갈 이름(태그, 다이제스트), 기록(깃옵스 pull), 레이블과 셀렉터, template이 바뀌면 새 RS
- **2부**: 전략 다섯 가지 한 그림, 쿠버네티스가 기본으로 주는 건 둘
- **3부**: 같은 조건(평소 5xx 0.1%) → 롤링(두 버전이 섞인다, 1만 4천 건, 롤아웃은 성공) → 블루/그린(5천 4백 건, 되돌리기 2초) → 카나리(베이스라인 비교, 약 90건) → 비교표 → 파드 교체 때 끊김과 preStop → A/B와 다름 → 기능 플래그 → 확장/축소 → 데모 → 7장 리전 보충(시간 없으면 건너뜀)
- **4부**: 깃옵스에서 되돌리기, 돌아갈 곳, 데이터는 안 돌아간다, 헬름 훅, 체크리스트, 연습 → 처음 질문의 답

### 9. 전체 그림

`서론 · 전체 그림` · 예상 2:32 · 누적 9:19

**화면**: 전체 그림: 커밋에서 사용자까지

**말할 것**

> 본론에 들어가기 전에 오늘 나오는 것들이 어떻게 이어지는지 한 장으로 보고 가겠습니다. 그림은 3회차 카나리 기준입니다. 상자마다 붙은 색 표시가 몇 부에서 다루는지입니다.

> 위쪽은 클러스터 밖입니다. 개발자가 앱 저장소에 커밋하면 CI가 테스트하고, 이미지를 빌드해서 서명하고, 레지스트리에 올립니다. 이미지 이름이 커밋 해시 태그와 다이제스트입니다. 그다음 CI가 하는 마지막 일이 배포 저장소에 새 태그를 커밋하는 겁니다. 여기까지가 1부입니다.

> 아래 큰 상자가 클러스터입니다. Argo CD, 또는 Flux가 클러스터 안에서 배포 저장소를 당겨 가서 Rollout 리소스를 적용합니다. CI는 클러스터 권한이 없고 깃에 커밋만 합니다. 이것도 1부에서 봅니다.

> Rollout을 받은 Argo Rollouts 컨트롤러가 파드를 어떻게 바꿀지 정합니다. 옛 버전 ReplicaSet과 새 버전 ReplicaSet을 두고, 각각을 가리키는 stable 서비스와 canary 서비스를 둡니다. Gateway의 HTTPRoute가 사용자 요청을 95 대 5로 두 서비스에 나눠 보냅니다. 롤링, 블루/그린, 카나리가 이 부분을 어떻게 다르게 하는지가 2부와 3부입니다.

> 판정은 AnalysisRun이 1분마다 Prometheus나 Datadog에 물어봐서 합니다. 실패하면 컨트롤러가 가중치를 0으로 돌립니다. 노드는 파드를 띄울 때 레지스트리에서 이미지를 받습니다.

> 마지막으로 노란 점선이 되돌리기입니다. 배포 저장소에서 git revert를 하면 Argo CD가 그걸 당겨 가서 옛 버전으로 맞춥니다. 4부입니다. 발표 중간중간 이 그림에서 지금 어디를 보고 있는지 다시 짚겠습니다.

### 25. 6.4 예제의 함정

`1부 · 6.4 예제를 그대로 apply 하면` · 예상 4:41 · 누적 31:38

**화면**: 6.4 예제의 함정

**말할 것**

> 이 장표는 6.4 종합 예제를 실제 클러스터에 그대로 넣어 보면 어디서 막히는지입니다. 결론부터 말하면, 셀렉터에 버전을 넣으면 그 버전 레이블을 다시는 올릴 수 없게 됩니다. 이미지만 바꾸는 배포는 되지만요.

> 6.4 예제에는 버전 레이블이 세 종류 나옵니다. ver는 파드 스펙의 버전, appver는 앱 전체의 버전, release number는 CD 파이프라인 실행 ID입니다. 문제가 되는 건 ver입니다.

> 먼저 배경입니다. 디플로이먼트의 spec.selector는 이 디플로이먼트가 관리할 파드를 고르는 조건이고, template.metadata.labels는 새로 만들 파드에 붙일 레이블입니다. 쿠버네티스는 이 둘이 맞는지 검사합니다. 템플릿으로 만든 파드를 셀렉터가 못 고르면 디플로이먼트가 자기가 만든 파드를 못 알아보니까요.

> 또 하나, apps/v1 디플로이먼트는 만든 뒤에 셀렉터를 바꿀 수 없습니다. 셀렉터를 바꾸면 이미 떠 있는 레플리카셋과 파드가 갑자기 관리 대상에서 빠지거나 다른 디플로이먼트 것과 섞일 수 있어서 아예 막아 둔 겁니다.

> 교재 예제는 셀렉터에 ver: 1.5.8을 넣었습니다. 다음 배포에서 파드 스펙 버전을 1.5.9로 올린다고 해 보겠습니다. template의 ver만 1.5.9로 바꾸면, 셀렉터는 1.5.8을 찾는데 새 파드는 1.5.9라서 selector does not match template labels 에러가 납니다.

> 그럼 셀렉터도 같이 1.5.9로 바꾸면 될까요? 이번엔 field is immutable, 셀렉터는 못 바꾼다는 에러가 납니다. 두 에러 모두 kind 클러스터에서 그대로 나왔습니다.

### 34. 롤링 설정 한눈에

> progressDeadlineSeconds는 이 시간 동안 롤아웃에 진척이 없으면 실패로 표시하는 값입니다. 기본 600초입니다. 표시만 하고 되돌리지는 않습니다. 이건 뒤에서 데모로 봅니다.

> revisionHistoryLimit은 옛 레플리카셋을 몇 개 남길지입니다. 기본 10개입니다. 이게 rollout undo로 돌아갈 곳의 목록이라, 줄여 두면 돌아갈 곳이 없어집니다.

> 마지막 terminationGracePeriodSeconds는 파드를 끌 때 종료 신호를 보낸 뒤 강제로 죽이기까지 기다리는 시간입니다. 기본 30초입니다. 짧으면 하던 요청을 마치기 전에 잘립니다. 그 앞에 실행되는 preStop 훅은 3부 뒤쪽에서 따로 보겠습니다.

`3부 · 2회차 · 직접 해 보기` · 예상 2:28 · 누적 66:06

Rollout CRD는 스키마가 커서 이 어노테이션이 256KB 한도를 넘습니다. --server-side로 적용하면 비교를 API 서버가 해서 이 어노테이션을 안 쓰니까 들어갑니다. 큰 CRD를 설치할 때 자주 만나는 문제라 알아 두시면 좋습니다.

> 상태를 보거나 promote, abort를 하려면 kubectl 플러그인을 따로 설치합니다.

> 디플로이먼트를 Rollout으로 바꾸는 건 간단합니다. apiVersion과 kind를 바꾸고 strategy 자리에 blueGreen이나 canary를 적습니다. 파드 template은 디플로이먼트와 똑같습니다. 기존 디플로이먼트를 그대로 두고 Rollout이 workloadRef로 가리키게 해서 조금씩 옮기는 방법도 있습니다.

> Argo CD에도 rollback 명령이 있습니다. app history로 이력을 보고 app rollback에 이력 번호를 주면 그때 상태로 되돌립니다. 그런데 자동 동기화를 켜 둔 상태에서 해 보니 거부됐습니다. 메시지가 왼쪽 빨간 줄입니다. 자동 동기화가 켜져 있으면 rollback을 시작할 수 없다는 겁니다. 되돌려 봤자 깃에는 새 버전이 적혀 있어서 바로 다시 덮어쓰니까, 아예 막아 둔 겁니다.

> 그래서 기본은 Flux와 같습니다. 배포 저장소에서 git revert를 하고, 3분 주기를 기다리지 않게 argocd app sync로 바로 동기화합니다.

> 정말 급해서 깃 커밋을 기다릴 수 없으면, 자동 동기화를 끄고 app rollback으로 되돌린 다음, 깃을 맞추고 자동 동기화를 다시 켭니다. Flux의 suspend, resume과 같은 순서입니다.

> 오른쪽 표는 상황별로 정리한 겁니다. selfHeal이 켜져 있으면 kubectl rollout undo도 다시 덮어씁니다. 1부에서 selfHeal을 켜자 replicas가 바로 깃 값으로 돌아간 것과 같은 동작입니다. Argo Rollouts가 중단되면 Application은 Degraded로 표시만 하고 되돌리지는 않습니다. 헬름 차트는 템플릿으로만 렌더링해서 pre-rollback 훅이 안 돕니다.

`4부 · 6.4, 6.5` · 예상 2:14 · 누적 120:58

**화면**: 같이 되돌릴 것은 한 차트로 묶는다

**말할 것**

> Flux helm-controller는 깃에서 차트 버전이나 값을 되돌리면 옛 버전으로 upgrade를 합니다. 그래서 pre-upgrade 훅이 걸립니다. pre-rollback 훅은 업그레이드가 실패해서 Flux의 실패 대응 설정이 helm rollback을 할 때만 걸립니다.

> Argo CD는 헬름 차트를 helm template으로 매니페스트로 바꿔서 적용합니다. 헬름 릴리스 자체를 만들지 않아서 pre-rollback 훅은 아예 돌지 않습니다. pre-upgrade 같은 일부 훅은 Argo CD 동기화 훅으로 바꿔서 돌려 주지만 롤백 훅은 대응하는 게 없습니다.

> 그래서 교재 예제처럼 pre-rollback만 남아 있으면, 깃으로 되돌릴 때는 어느 도구든 백업이 돌지 않습니다. 오른쪽처럼 쉼표로 이어 쓰면 적어도 Flux에서는 pre-upgrade로 백업이 돕니다.

## 예상 질문

**Q. Argo Rollouts를 쓰면 Deployment를 버려야 하나요?**

Rollout이 Deployment를 대신하는 게 기본입니다. 기존 Deployment를 그대로 두고 `workloadRef`로 가리키는 방식도 있어서 조금씩 옮길 수 있습니다.

**Q. 깃옵스에서 급한 핫픽스는 어떻게 하나요?**

원칙은 같은 길(커밋 → 동기화)을 빨리 타는 겁니다. 정말 급하면 4부 순서대로 에이전트를 멈추고(`flux suspend`, Argo CD auto-sync 끄기) 직접 조치한 뒤, 깃을 맞추고 다시 켭니다. 이 절차는 미리 문서로 두고 연습해 둡니다.

**Q. 깃옵스에서 DB 마이그레이션은 누가 돌리나요?**

많이 쓰는 건 셋입니다. 앱이 뜰 때 Flyway나 Liquibase로, Argo CD PreSync 훅이나 헬름 pre-upgrade 훅의 Job으로, Flux `dependsOn`으로 마이그레이션을 앱보다 먼저. 어느 쪽이든 확장/축소는 그대로 필요합니다.

**Q. helm rollback은 깃옵스에서 써도 되나요?**

rollout undo와 같은 문제가 있습니다. Flux helm-controller는 깃에 있는 HelmRelease 값으로 다시 올립니다. 깃을 되돌리는 게 맞습니다.

**Q. 트래픽이 적은 서비스도 카나리 판정이 되나요?**

요청이 적으면 에러 몇 건으로 비율이 크게 흔들려서 판단이 어렵습니다. 카나리 기간을 늘리거나, 합성 트래픽을 더하거나, 비율 대신 에러 건수 조건을 같이 겁니다.

**Q. preStop sleep은 몇 초가 적당한가요?**

엔드포인트 제거가 끝까지 퍼지는 시간보다 길어야 합니다. 클러스터 안만이면 몇 초, 클라우드 LB가 타깃을 빼는 시간까지 치면 더 깁니다. terminationGracePeriodSeconds는 sleep과 앱 종료 시간을 합친 것보다 길게 둡니다. AWS Load Balancer Controller는 pod readiness gate로 타깃 등록 상태를 파드 Ready에 반영할 수도 있습니다.

**Q. 쿠버네티스는 왜 실패한 롤아웃을 자동으로 되돌리지 않나요?**

진척이 없는 이유가 이미지 오류일 수도, 노드 부족이나 이미지 받는 게 느려서일 수도 있어서 컨트롤러가 실패로 단정하기 어렵습니다. 그래서 상태만 알리고 판단은 파이프라인이나 카나리 컨트롤러에 맡깁니다 (토론 Q2).

**Q. 블루/그린이면 DB 문제는 없는 것 아닌가요?**

DB는 대부분 두 환경이 같이 써서 두 버전이 같은 스키마를 봅니다. 확장/축소가 필요한 건 똑같습니다. 교재 5.7도 이걸 블루/그린 주의점으로 꼽습니다.
