# 7주차 · 릴리스 파이프라인

- 일시: 2026-10-04 (일) 20:00, 약 90분
- 교재 범위: 5장 지속적 통합, 테스팅, 배포 / 6장 버저닝, 릴리스, 롤아웃 / 7장 글로벌 애플리케이션 분산과 스테이징 / 18장 깃옵스와 배포
- 자료: [`slides.html`](./slides.html) (발표자 창 `P`), [`script.md`](./script.md) (발표 원고), [`examples/`](./examples/) (kind에서 돌려 본 예제)

## 진행 방식

"릴리스 파이프라인에서 제일 중요한 게 뭘까?"로 시작합니다. 제 답은 롤백입니다.
롤백이 제일 중요하다면 처음부터 되돌리기 쉽게 내보내면 되고, 그게 배포 전략입니다.
배포 전략은 새 버전을 누구에게, 얼마나, 어떤 순서로 보여 줄지 정하는 것입니다.

| 순서 | 내용 | 교재 |
| --- | --- | --- |
| 서론 | 제일 중요한 건 롤백, 배포 전략이란 | |
| 1부 준비 | 돌아갈 이름(태그, 다이제스트), 기록(깃옵스), 레이블과 셀렉터, template이 바뀌면 새 RS | 5.1 ~ 5.6, 6장, 18장 |
| 2부 배포 전략 한눈에 | Recreate, 롤링, 블루/그린, 카나리, A/B. 쿠버네티스가 기본으로 주는 건 둘 | 5.7, 6.3 |
| 3부 같은 배포, 세 번 | 같은 배포를 롤링, 블루/그린, 카나리로 한 번씩 + 파드 교체 때 끊김 + 데모 + 7장 리전 보충 | 5.7, 5.8, 6.3, 7장 |
| 4부 되돌리기 | 깃옵스에서 되돌리기, 돌아갈 곳, 데이터, 헬름 훅, 체크리스트, 연습 | 7.5, 6.5, 18장 |
| 토론 | 질문 4개 (Q3, Q4는 시간이 되면) | |

예시는 가상의 주문 API(`order-api`, 레플리카 10개, 초당 1,000 요청)의 1.6.3 → 1.7.0 배포입니다.
커밋은 `3f9c2e1` "쿠폰 할인 적용"이고, 쿠폰 컬럼은 그 전 1.6.3 배포 때 미리 추가해 뒀습니다.
이 버전에는 쿠폰 코드에 이모지나 일본어가 들어오면 결제가 실패하는 버그가 있고, 그런 요청이 전체의 3%입니다.
교재 7.4의 "테스트할 때는 영어로만 입력하지만 실제 환경에서는 다양한 언어로 입력이 들어올 수 있다"를 그대로 옮긴 상황입니다.
평소 결제 5xx 비율은 0.1%라서 새 버전 파드는 약 3.1%가 되고, 알람은 결제 5xx가 1%를 넘은 채로 1분 가면 울립니다.
3부에서 이 배포를 전략만 바꿔 세 번 합니다.

| | 롤링 | 블루/그린 | 카나리 (베이스라인 비교) |
| --- | --- | --- | --- |
| 실패한 결제 | 약 1만 4천 건 | 약 5천 4백 건 | 약 90건 |
| 겪은 비율 | 0 → 100%로 점점 | 전환 순간 100% | 5% |
| 알아챈 방법 | 알람, CS | 알람 | 베이스라인 비교 (자동) |
| 되돌리기 | 거꾸로 롤링, 수 분 | 셀렉터 전환, 수 초 | 가중치 0, 자동 |

계산: 롤링은 전부 새 버전인 300초 × 초당 30건 + 오르내리는 360초 × 평균 초당 15건 ≈ 1만 4천 건.
블루/그린은 초당 30건 × 180초 = 5,400건. 카나리는 초당 50건(5%) × 3% × 60초 ≈ 90건이고, 이때 전체 에러율은 평소 0.1% + 0.15% ≈ 0.25%라 알람이 안 울립니다.
롤링은 알람에서 결정까지 3분, 블루/그린은 1분으로 잡았습니다. 롤링도 1분 만에 결정했다면 약 1만 1천 건입니다.

## 학습 목표

- 배포 전략이 버그를 겪는 사람 수, 알아채는 시점, 되돌리는 시간, 추가 비용을 어떻게 바꾸는지 설명할 수 있다
- 디플로이먼트가 무엇이 바뀔 때 롤아웃을 시작하고, 실패했을 때 무엇을 하지 않는지 설명할 수 있다
- 롤링 중 두 버전이 섞일 때 지켜야 할 하위 호환을 설명할 수 있다
- 파드를 교체할 때 요청이 끊기는 이유와 readiness, preStop으로 막는 방법을 설명할 수 있다
- 카나리를 프로덕션 전체와 비교하면 안 되는 이유와 베이스라인을 두는 방법을 설명할 수 있다
- 카나리와 A/B 테스트가 무엇을 묻는지 구분할 수 있다
- 두 버전이 같이 도는 동안의 DB 변경을 확장, 이전, 축소로 나눌 수 있다
- 깃옵스에서 `git revert`, 트래픽 전환, `rollout undo`의 차이를 설명할 수 있다

## 핵심 요약

1. 되돌아갈 이름이 있어야 한다. `latest` 대신 커밋 SHA 태그, 가능하면 다이제스트까지 쓴다. 한 번 빌드한 이미지를 환경마다 올려 보낸다. (5.5, 5.6)
2. 원하는 상태는 깃에 두고 클러스터 안의 에이전트가 가져가게 한다. CI는 배포 저장소의 환경 폴더(`overlays/prod`)에 커밋까지만 하고, 되돌릴 땐 `git revert`. 교재 18.3의 구조는 모두 앱 코드와 같은 저장소지만, 예시는 배포 저장소를 따로 뒀다. (18장)
3. 쿠버네티스에는 릴리스가 없어서 레이블로 적는다. 셀렉터에는 안 바뀌는 것만 넣는다. 셀렉터는 만든 뒤에 못 바꾼다. (6.2, 6.4)
4. 롤아웃은 `spec.template`이 바뀔 때만 일어나고, 실패해도 멈추기만 한다. 되돌리는 판단은 파이프라인이나 카나리 컨트롤러가 한다. (6.3)
5. 같은 버그라도 전략에 따라 결과가 다르다. 롤링은 결국 전부에게 나가고, 블루/그린은 되돌리는 시간을 줄이고, 카나리는 겪는 사람을 줄인다. (5.7)
6. 카나리는 같은 크기로 방금 띄운 옛 버전(베이스라인)과 비교한다. 프로덕션 전체와 비교하면 새 파드라서 생긴 차이가 섞인다. 단계마다 과거에 문제를 발견하기까지 걸린 시간의 약 2배를 기다린다. (5.7 보충, 7.4.4)
7. A/B 테스트는 두 안 중 어느 쪽이 나은지를 묻고, 같은 사용자를 계속 같은 쪽에 둔다. 카나리는 새 버전이 안전한지를 묻는다. (5.7)
8. 어느 전략이든 두 버전이 같이 돈다. 스키마 변경은 확장, 이전, 축소를 따로 배포한다. 축소 뒤에는 롤백이 어렵다. (5.7)
9. 롤백해도 데이터는 안 돌아간다. 옛 버전이 떠 있으면 트래픽부터 옮기고, 절차는 평소에 연습한다. (7.5)

## 교재 모범 사례 요약

장표 "참고 자료"에서 가리키는 요약입니다. 교재 각 장 끝의 모범 사례를 줄여 옮겼습니다.

**5.10 CI/CD 모범 사례**

- 자동화와 빠른 빌드에 집중한다. 빌드가 빠르면 잘못된 변경을 개발자에게 빨리 알려 줄 수 있다.
- 파이프라인에 안정적인 테스트를 둔다. 피드백 주기가 짧을수록 생산성이 오른다.
- 파이프라인을 코드로 정의할 수 있는 CI/CD 도구를 고른다.
- 이미지는 작게 만들어 보안 취약점 노출을 줄인다. 멀티스테이지 빌드로 실행에 필요 없는 패키지를 뺀다.
- 이미지 태그에 `latest`를 쓰지 않는다. 빌드 ID나 깃 커밋을 거꾸로 찾아갈 수 있는 태그를 쓴다.
- CD가 처음이면 롤링 업데이트부터 쓴다. 익숙해지면 블루/그린, 카나리를 검토한다.
- CD 단계에서 클라이언트 연결과 DB 스키마 업그레이드를 테스트한다.
- 프로덕션 테스트는 작게 시작하고 영향 범위를 제한한다.

**6.5 버저닝, 릴리스, 롤아웃 모범 사례**

- 애플리케이션에 시맨틱 버저닝을 적용한다. 컨테이너, 파드 스펙, 앱 전체의 버전을 따로 관리한다.
- 디플로이먼트 메타데이터에 릴리스 이름과 릴리스 번호 레이블을 두고, CI/CD 도구의 실제 기록과 맞춘다. 그래야 클러스터에서 롤백 대상을 쉽게 찾는다.
- 헬름을 쓴다면 함께 롤백하거나 업그레이드할 서비스는 같은 차트로 묶고, 라이프사이클 훅으로 순서를 정한다.
- 조직의 운영 속도에 맞는 릴리스 이름 규칙을 정한다. 보통 `stable`, `canary`, `alpha` 정도면 충분하다.

**7.6 글로벌 롤아웃 모범 사례**

- 이미지를 쓰는 곳 가까이에 분산해 둔다. 자동 릴리스 파이프라인에 지리적 분산을 포함한다.
- 통합 테스트와 재현 테스트를 가능한 한 많이 한다. 잘 동작한다는 확신이 드는 릴리스만 내보낸다.
- 먼저 카나리 리전에 내보낸다.
- 리전마다 특성을 파악하고, 위험이 낮은 리전부터 내보낸다.
- 롤백 같은 대응 절차를 문서로 남기고 연습한다. 사고가 나면 해야 할 일을 잊기 쉽다.

**18.7 깃옵스 모범 사례**

- 작은 애플리케이션부터 시작해 점점 범위를 넓힌다.
- 요건에 맞는 도구인지 평가한다. 자신이 없으면 Flux나 Argo CD처럼 검증된 오픈소스로 시작한다.
- 저장소 레이아웃에 브랜치를 쓰지 않는다. 복잡하고 에러가 나기 쉽다.
- 환경별로 폴더를 나눈다. 쿠스토마이즈나 헬름 같은 도구를 쓰기 쉬워진다.
- 시크릿은 Sealed Secrets나 외부 시크릿 공급자로 관리한다.
- 깃옵스는 도구가 아니라 프로세스다. 지금 쓰는 도구가 요건에 더 맞을 수도 있다.
