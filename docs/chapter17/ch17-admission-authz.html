CHAPTER 17

어드미션 컨트롤과 인가

4장에서 RBAC(인가)을, 10·11장에서 어드미션의 실제 활용(파드 보안, 정책 엔진)을 이미 다뤘다. 이 장은 그 둘을 API 요청 파이프라인이라는 하나의 그림 위에 올려놓고, "인증 → 인가 → 어드미션"이 정확히 어떤 순서로, 무엇을 묻는지 짚는다.

2026-08 기준 변경 사항 주석 포함 · 11장 정책 엔진 논의와 직결됩니다

핵심 3줄

1. 모든 API 요청은 인증("누구냐") → 인가("뭘 해도 되냐") → 어드미션("이 내용 그대로 저장해도 되냐") 순서를 반드시 통과한다.

2. 어드미션 컨트롤러는 표준(코드에 내장)과 다이내믹(웹훅)로 나뉜다 — 2026년 현재는 웹훅 없이 CEL로 직접 평가하는 정책 API가 세 번째 선택지로 추가됐다(11장).

3. 인가 모듈은 RBAC이 사실상 표준이다 — ABAC·웹훅·Node는 특수한 상황에만 쓴다.

17.1어드미션 컨트롤 17.2인가

17.1어드미션 컨트롤

17.1.1 어드미션 컨트롤러란?

어드미션 컨트롤러 (Admission Controller)는 API 서버가 요청을 처리하는 파이프라인의 한 단계다 — 인증과 인가 이후, 오브젝트가 실제로 저장되기 전에 요청을 가로채 유효성을 검사하거나 변형(또는 둘 다)한다.

17.1.2 어드미션 컨트롤의 중요성

모든 요청이 지나는 길목이라는 위치 덕분에 쓰임이 다양하다. 가장 흔한 세 가지는 정책·거버넌스(11장의 정책 엔진), 보안 강화(10장의 파드 시큐리티 어드미션), 그리고 기본값 주입(예: 지정 안 된 StorageClass를 자동으로 채움)이다.

17.1.3 어드미션 컨트롤러 타입

크게 두 계급이 있다 — 표준 (Standard)은 API 서버 코드에 컴파일되어 릴리스와 함께 배포되고, --enable-admission-plugins 플래그로 켠다. 다이내믹 (Dynamic)은 런타임에 구성 가능하며 코어 코드베이스 밖에서 개발된다 — 그 유일한 형태가 HTTP 콜백으로 요청을 받는 어드미션 웹훅이다.

현재 기본 활성화된 표준 어드미션 컨트롤러에는 LimitRanger, ResourceQuota, PodSecurity, DefaultStorageClass, ServiceAccount 등이 있고, 여기에 MutatingAdmissionWebhook·ValidatingAdmissionWebhook이라는 특수한 표준 컨트롤러가 포함된다 — 이 둘은 자체 로직이 없고, 그저 요청을 웹훅 엔드포인트로 전달하는 "배달부" 역할만 한다.

2026-08 기준 갱신 주석 원서는 어드미션 컨트롤러를 "표준 vs 웹훅" 두 갈래로만 설명하지만, 11장에서 이미 다룬 ValidatingAdmissionPolicy·MutatingAdmissionPolicy가 사실상 세 번째 갈래다 — CEL 표현식을 API 서버 프로세스 안에서 직접 평가해, 웹훅처럼 클러스터 밖(또는 별도 파드)으로 네트워크 왕복을 하지 않는다. 다음 절의 웹훅 구성 트레이드오프(지연·실패 모드)가 애초에 발생하지 않는다는 뜻이다. 단순 검증·변형 규칙이라면 이쪽이 새 기본값이다. 출처: 11장 갱신 주석(kubernetes.io 공식 문서, VAP/MAP GA 현황) 참고

17.1.4 어드미션 웹훅 구성

웹훅의 장점은 다이내믹한 구성이지만, 대가로 일관성·실패 모드를 직접 신경 써야 한다. 핵심 필드 몇 가지만 짚는다.

apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingWebhookConfiguration
metadata:
  name: pod-policy.example.com
webhooks:
- name: pod-policy.example.com
  clientConfig:
    service:
      name: webhook-server
      namespace: webhook-ns
      path: "/validate"
    caBundle: 
  rules:
  - apiGroups: [""]
    apiVersions: ["v1"]
    operations: ["CREATE"]
    resources: ["pods"]
  failurePolicy: Fail
  sideEffects: None
  timeoutSeconds: 5

failurePolicy가 특히 중요하다 — Fail은 웹훅이 응답하지 못하면 요청 자체를 거부한다(안전하지만, 웹훅이 죽으면 클러스터 전체의 해당 리소스 생성이 멎을 수 있다). Ignore는 웹훅이 응답하지 못해도 요청을 통과시킨다(가용성은 높지만 정책이 조용히 우회될 수 있다). timeoutSeconds를 짧게 잡아 웹훅 장애가 API 서버 전체를 느리게 만들지 않게 하는 것도 중요하다.

17.1.5 어드미션 컨트롤 모범 사례

  • 어드미션 플러그인 순서는 신경 쓸 필요 없다 — 초기 버전엔 순서가 중요했지만, 지금은 뮤테이팅이 전부 실행된 뒤 밸리데이팅이 실행되는 구조로 고정되어 있다.
  • 웹훅은 빠르고 가용성 높게 — timeoutSeconds를 짧게, 웹훅 서버 자체의 가용성을 클러스터 핵심 인프라 수준으로 관리한다.
  • 변형은 예측 가능하게 — 15장에서 다룬 사이드카 자동 주입처럼, 사용자가 몰라도 되지만 디버깅할 땐 반드시 추적 가능해야 한다.

17.2인가

인가 (Authorization)는 "이 유저가 어느 리소스에 무슨 일을 할 수 있는가?"에 대한 답이다. 인증 이후, 어드미션 이전에 처리된다.

17.2.1 인가 모듈

액세스는 명시적으로 허용된 것만 허용되고, 나머지는 전부 암묵적으로 거부된다. 기본 제공 모듈은 넷이다.

  • ABAC — 각 컨트롤 플레인 노드의 로컬 파일에 정책을 둔다.
  • RBAC — 쿠버네티스 API로 정책을 선언한다(4장에서 이미 깊이 다뤘다). 사실상 표준.
  • Webhook — 원격 REST 엔드포인트가 승인 여부를 판단한다.
  • Node — kubelet의 요청만 전담하는 특수 목적 모듈.

여러 모듈을 --authorization-mode에 순서대로 지정할 수 있다. 어드미션과 다르게 인가는 하나의 모듈만 승인해도 요청이 통과한다 — 전부 거부해야만 에러가 난다.

권한 문제를 디버깅할 때 유용한 전용 API도 있다 — authorization.k8s.io 그룹의 SelfSubjectAccessReview(내가 이걸 할 수 있나), SubjectAccessReview(다른 유저가 할 수 있나), SelfSubjectRulesReview(내가 이 네임스페이스에서 할 수 있는 것 전체)다. 4장에서 쓴 kubectl auth can-i 명령이 내부적으로 SelfSubjectAccessReview를 호출하는 것이다.

체크포인트권한이 막혔을 때 로그부터 뒤지지 말고 kubectl auth can-i <verb> <resource> --as=<user>로 먼저 확인한다 — 위 API를 그대로 감싼 명령이라 훨씬 빠르다.
