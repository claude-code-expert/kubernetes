1.1애플리케이션 개요

예제는 온라인 저널(일기장)이다. 규모는 작지만 실제 서비스가 갖출 구성 요소를 전부 갖고 있다.

먼저 이 장 전체를 관통하는 두 단위부터. 파드 (Pod)는 하나 이상의 컨테이너를 묶어 배포·스케줄링하는 쿠버네티스의 최소 실행 단위이고, 워크로드 (Workload)는 그 파드들을 직접 만들지 않고 컨트롤러 리소스(Deployment, StatefulSet 등)에 맡겨 굴리는 애플리케이션 전체를 가리키는 상위 개념이다. 어떤 워크로드 리소스를 고르느냐가 이 장의 첫 번째 판단이다.

컴포넌트기술쿠버네티스에서 맡는 리소스
API 프론트엔드TypeScript로 작성한 Node.js 앱, 8080 포트의 /api/* 처리Deployment + Service
데이터 저장소Redis — 저널 엔트리 조회·추가·삭제StatefulSet + Service 2개
정적 파일HTML·CSS·JS를 NGINX가 서빙Deployment + Service
외부 진입점경로 기반 HTTP 라우팅Ingress

이 장의 진짜 주제는 저널 앱이 아니라, 위 네 줄을 채우는 데 필요한 판단 기준이다. 어떤 워크로드에 어떤 리소스를 쓰고, 구성은 어디에 두는가.

1.2구성 파일 관리

쿠버네티스는 선언형 (Declarative) 시스템이다. "이 컨테이너를 실행해라"라고 절차를 명령하는 대신, 애플리케이션이 도달해야 할 원하는 상태 (Desired State)를 기술해 제출하면 시스템이 그 상태를 스스로 유지한다. 이 선언을 담은 YAML/JSON 파일이 매니페스트 (Manifest)다 — apiVersion, kind, metadata, spec 네 가지가 기본 골격이다. 매니페스트를 클러스터에 적용하는 CLI 도구가 kubectl (Kube Control)이다.

선언이 파일이라는 사실이 곧 운영 방식을 결정한다. YAML을 Git에 두면:

  • 리뷰 — 인프라 변경이 코드 리뷰(PR)를 통과한다.
  • 이력과 롤백 — 장애 시 "지난주의 그 상태"로 정확히 되돌릴 수 있다.
  • 단일 진실 공급원 — 클러스터를 직접 만지는 대신 리포지터리를 고치고 적용한다. 클러스터에서 먼저 고쳤다면 반드시 리포지터리에 역반영해야 한다.

애플리케이션마다 디렉터리 하나, 그 안에 리소스별 YAML과 README를 두는 단순한 구조로 시작하면 충분하다. 이 아이디어를 끝까지 밀어붙인 것이 18장의 깃옵스다.

1.3디플로이먼트를 이용한 복제 서비스 생성

프론트엔드는 상태가 없으므로(모든 상태는 Redis에) 동일한 복제본을 여러 개 띄우기만 하면 된다. 이 일을 하는 리소스가 디플로이먼트 (Deployment) — 무상태 애플리케이션의 표준 배포 단위로, 이미지 교체 시 파드를 점진적으로 갈아 끼우고(롤링 업데이트) 롤백 이력을 관리한다. 실제 파드 개수 유지는 디플로이먼트가 내부적으로 만드는 레플리카셋 (ReplicaSet)이 맡는다 — 지정한 개수의 동일 파드를 항상 유지하는 컨트롤러다.

1.3.1 이미지 관리 모범 사례

두 가지가 핵심이다. 첫째, latest 태그를 프로덕션에 쓰지 않는다. 어느 시점의 어떤 코드가 돌고 있는지 알 수 없게 되고, 노드마다 다른 버전이 캐시될 수 있다. 시맨틱 버전 + 빌드 식별자(예: 커밋 해시) 조합으로 태그를 고정한다. 둘째, 한 번 푸시한 태그 위에 다른 이미지를 덮어쓰지 않는다(불변 태그).

1.3.2 애플리케이션 레플리카 생성

최소한의 프로덕션 요건을 담은 Deployment 예시다. 읽기 전에 용어 세 개만. 레이블 (Label)은 오브젝트에 붙이는 키-값 메타데이터, 셀렉터 (Selector)는 그 레이블 조건으로 대상을 골라내는 질의문이다 — 서비스가 파드를 찾고 디플로이먼트가 자기 파드를 인식하는 근거가 전부 이 둘이다. 프로브 (Probe)는 kubelet이 컨테이너 상태를 주기 점검하는 헬스체크로, liveness는 실패 시 컨테이너를 재시작하고 readiness는 실패 시 트래픽 대상에서 제외한다(재시작하지 않음).

apiVersion: apps/v1
kind: Deployment
metadata:
  name: frontend
  labels:
    app: frontend
spec:
  replicas: 2
  selector:
    matchLabels:
      app: frontend
  template:
    metadata:
      labels:
        app: frontend
    spec:
      containers:
      - name: frontend
        image: my-repo/journal-frontend:v1.0.2-abc123
        ports:
        - containerPort: 8080
        resources:
          requests:
            cpu: "500m"
            memory: "256Mi"
          limits:
            cpu: "500m"
            memory: "256Mi"
        livenessProbe:
          httpGet:
            path: /healthz
            port: 8080
          initialDelaySeconds: 10
        readinessProbe:
          httpGet:
            path: /ready
            port: 8080

리소스 요청과 제한 (Resource Requests / Limits)은 컨테이너가 보장받을 자원(requests)과 넘을 수 없는 상한(limits)이다. 위처럼 둘을 같게 두면 QoS 클래스 (Quality of Service Class) 중 축출 우선순위가 가장 낮은 Guaranteed 등급이 되어 예측 가능성이 최대가 된다(상세는 8장). 적용과 확인은 kubectl apply -f frontend.yaml 후 kubectl get pods -l app=frontend. 적용한 YAML은 잊지 말고 Git에 커밋한다.

1.4HTTP 트래픽을 처리하는 외부 인그레스 설치

파드는 기본적으로 클러스터 밖에서 접근할 수 없다. 외부 노출에는 리소스 두 개가 협력한다. 서비스 (Service)는 계속 생겼다 사라지는 파드 집합 앞에 고정된 이름과 가상 IP를 제공하는 추상화로, 기본 타입인 ClusterIP는 클러스터 내부에서만 접근 가능한 가상 IP를 부여한다. 그 앞단의 인그레스 (Ingress)는 호스트 이름과 URL 경로 기준으로 외부 HTTP/HTTPS 트래픽을 어느 서비스로 보낼지 정하는 라우팅 규칙이다. 단, 인그레스는 규칙 선언일 뿐이라 이를 읽어 실제 리버스 프록시로 반영하는 구현체인 인그레스 컨트롤러 (Ingress Controller)가 클러스터에 없으면 아무 일도 일어나지 않는다.

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: journal-ingress
spec:
  rules:
  - http:
      paths:
      - path: /api
        pathType: Prefix
        backend:
          service:
            name: frontend
            port:
              number: 8080
2026-08 기준 갱신 주석 책 집필 시점과 달리 두 가지가 크게 바뀌었다. ① Ingress API는 동결(frozen) 상태다. 안정(GA) API로 계속 쓸 수는 있지만 신규 기능 개발이 없으며, 쿠버네티스 프로젝트는 공식적으로 게이트웨이 API (Gateway API) — Ingress의 한계를 보완하려고 GatewayClass(인프라 제공자) / Gateway(진입점) / HTTPRoute(라우팅 규칙)로 역할을 분리한 차세대 트래픽 라우팅 표준 — 사용을 권장한다. ② 가장 널리 쓰이던 컨트롤러 ingress-nginx가 2026년 3월부로 은퇴(retired)했다. 이후 보안 패치가 전혀 없으므로 신규 학습·구축이라면 Gateway API 구현체(Envoy Gateway, Cilium, Traefik, kgateway 등)나 유지보수 중인 다른 컨트롤러를 선택해야 한다. 스터디에서 실습할 때 인그레스 개념은 그대로 배우되, 컨트롤러로 ingress-nginx를 새로 깔지 않는 것을 권장. 출처: kubernetes.io/docs/concepts/services-networking/ingress (Ingress 동결 및 Gateway API 권장) · kubernetes.io/blog/2026/01/29/ingress-nginx-statement (Steering Committee 공식 성명)

1.5컨피그맵으로 애플리케이션 구성

"페이지당 엔트리 10개" 같은 설정값을 이미지 안에 굽지 않는 이유는 하나다 — 같은 바이너리를 환경마다 다르게 굴리기 위해서. 설정을 바꿀 때마다 이미지를 재빌드·재배포하는 것은 느리고, 코드 변경과 설정 변경의 이력이 섞여 원인 추적도 어려워진다. 이 비밀 아닌 설정 데이터를 키-값으로 담는 오브젝트가 컨피그맵 (ConfigMap)이다. 환경 변수나 마운트된 파일로 파드에 주입하며, 전체 크기는 1MiB로 제한된다.

apiVersion: v1
kind: ConfigMap
metadata:
  name: frontend-config
data:
  journalEntries: "10"

파드에서는 환경 변수(env.valueFrom.configMapKeyRef)나 볼륨 마운트로 읽는다. 주의: 환경 변수로 주입한 값은 컨피그맵을 고쳐도 이미 뜬 파드에 반영되지 않는다. 반영하려면 롤아웃 재시작(kubectl rollout restart deployment/frontend)이 필요하다. 볼륨 마운트 방식은 갱신이 전파되지만 지연이 있다.

1.6시크릿 인증 관리

Redis 패스워드 같은 민감 정보는 소스 코드에도, 이미지에도 넣지 않는다. 이미지에 넣는 순간 레지스트리 접근 권한 = 패스워드 열람 권한이 되고, 환경별로 다른 패스워드도 쓸 수 없게 된다. 쿠버네티스의 답이 시크릿 (Secret) — 비밀번호·토큰·인증서 등 민감 정보를 담는 오브젝트다. 사용법은 컨피그맵과 같지만 전용 타입(TLS, docker-registry 등)이 있고, RBAC으로 접근을 좁혀 쓰는 것이 전제다.

# 생성
kubectl create secret generic redis-passwd --from-literal=passwd=${RANDOM}

# 파드에서 파일로 마운트 (컨테이너 spec 일부)
volumeMounts:
- name: passwd-volume
  mountPath: /etc/redis-passwd
  readOnly: true

환경 변수보다 읽기 전용 볼륨 마운트가 낫다. 환경 변수는 프로세스 덤프나 자식 프로세스로 새기 쉽다.

2026-08 기준 갱신 주석 Secret의 base64는 인코딩이지 암호화가 아니다. 기본 설정에서 etcd에 평문(base64)으로 저장되므로, 실무에서는 EncryptionConfiguration으로 저장 시 암호화(encryption at rest)를 켜거나 KMS 프로바이더를 연동하는 것이 표준이다. 이 내용은 4장·19장에서 다시 다룬다. 출처: kubernetes.io/docs/concepts/configuration/secret (기본 미암호화 명시) · kubernetes.io/docs/tasks/administer-cluster/encrypt-data

1.7간단한 스테이트풀 데이터베이스 배포

파드는 노드 장애·업그레이드·리밸런싱으로 언제든 다른 머신으로 옮겨질 수 있다. 무상태 앱은 상관없지만, 데이터를 든 앱이 옮겨지면 로컬 디스크의 데이터는 사라진다. 그래서 상태 보유 워크로드에는 두 가지 장치가 붙는다.

  • 스테이트풀셋 (StatefulSet) — 고유한 신원과 안정적 스토리지가 필요한 앱을 위한 컨트롤러. 파드 이름이 redis-0, redis-1처럼 고정되고 생성·삭제 순서가 보장되므로, "누가 마스터인가"를 이름으로 지목할 수 있게 된다.
  • 퍼시스턴트볼륨클레임 (PersistentVolumeClaim, PVC) — 앱이 필요한 용량·접근 모드를 적어 스토리지를 요청하는 리소스. 실제 디스크 실체인 퍼시스턴트볼륨 (PersistentVolume, PV)과 바인딩되어, 파드가 어느 노드로 가든 데이터가 따라붙는다. volumeClaimTemplates를 쓰면 레플리카마다 PVC가 자동으로 하나씩 만들어진다.
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: redis
spec:
  serviceName: redis
  replicas: 3
  selector:
    matchLabels:
      app: redis
  template:
    metadata:
      labels:
        app: redis
    spec:
      containers:
      - name: redis
        image: redis:7
        ports:
        - containerPort: 6379
  volumeClaimTemplates:
  - metadata:
      name: data
    spec:
      accessModes: ["ReadWriteOnce"]
      resources:
        requests:
          storage: 10Gi

redis-0을 마스터로, 나머지를 복제본으로 구성하는 초기화는 컨피그맵에 담은 설정/스크립트로 처리한다. 스테이트풀 워크로드의 심화(오퍼레이터 포함)는 16장의 주제다.

1.8서비스를 응용한 TCP 로드 밸런서 구축

Redis는 읽기와 쓰기의 갈 곳이 다르다. 읽기는 세 레플리카 어디로 가도 되지만, 쓰기는 마스터(redis-0)로만 가야 한다. 해법은 의외로 단순하다 — 셀렉터가 다른 서비스를 두 개 만든다. 스테이트풀셋이 파드마다 자동으로 붙여주는 statefulset.kubernetes.io/pod-name 레이블 덕분에 특정 파드 하나만 셀렉트할 수 있다.

# 읽기: 모든 레플리카로 분산
apiVersion: v1
kind: Service
metadata:
  name: redis-readonly
spec:
  ports:
  - port: 6379
  selector:
    app: redis
---
# 쓰기: redis-0 한 파드만
apiVersion: v1
kind: Service
metadata:
  name: redis
spec:
  ports:
  - port: 6379
  selector:
    statefulset.kubernetes.io/pod-name: redis-0

애플리케이션 입장에서는 클러스터 내부 DNS가 만들어 주는 이름 redis(쓰기)와 redis-readonly(읽기)만 알면 된다 — 이 이름 해석을 담당하는 클러스터 애드온이 코어DNS (CoreDNS)다. HTTP가 아닌 순수 TCP도 서비스로 이렇게 로드 밸런싱된다.

1.9인그레스를 이용해 트래픽을 스태틱 파일 서버로 전달

정적 파일은 API 서버가 아니라 전용 NGINX 파드가 서빙하게 분리한다. 개발자는 API 코드에 집중하고, 파일 서빙은 그 일에 최적화된 서버에 맡기는 관심사 분리다. 진입점은 늘리지 않는다 — 기존 인그레스에 규칙을 추가해 /api는 frontend로, 나머지는 파일 서버로 보낸다.

1.10헬름을 이용한 애플리케이션 파라미터화

개발·스테이징·프로덕션에 같은 앱을 배포하려면 환경마다 YAML 전체를 복사하게 되는데, 그러면 공통 변경이 세 벌의 수정이 된다. 헬름 (Helm)은 쿠버네티스의 패키지 매니저로, 매니페스트를 템플릿으로 만들고 환경별 차이만 values 파일로 분리한다. 템플릿과 기본값을 하나로 묶은 배포 패키지 단위가 차트 (Chart)다.

# values.yaml
replicaCount: 2

# templates/frontend.yaml (일부)
spec:
  replicas: {{ .Values.replicaCount }}

# 환경별 배포
helm install journal-prod ./journal --values values-prod.yaml

원칙: 환경 간에 정말 달라야 하는 값만 파라미터로 뽑는다. 파라미터가 늘수록 "환경들이 서로 얼마나 다른가"를 아무도 설명할 수 없게 된다.

2026-08 기준 갱신 주석 책의 예제는 Helm 3 기준이다. Helm 4.0.0이 2025년 11월 12일 출시되었고(6년 만의 메이저), Helm 3는 2026-09-09 마지막 기능 릴리스 후 2027-02-10까지 보안 패치만 제공된다. 차트 문법은 대부분 호환되므로 학습 내용은 유효하지만, 신규 설치라면 Helm 4를 받고 Server-Side Apply 기반 배포·플러그인 체계 변경을 확인할 것. 출처: helm.sh/blog/helm-4-released · helm.sh/blog/helm-v3-end-of-life

부록 A · 서비스 간 호출 경로 — 이름에서 파드까지

1.4절·1.8절에서 다룬 Service를 "안정적인 이름과 IP"까지만 배웠다면, 여기서는 그 이름이 실제 패킷이 되어 다른 노드의 파드까지 도달하는 전체 경로를 한 걸음씩 뜯어본다. 이 내용은 9장(네트워킹) 9.1·9.3.1절에서 본편으로 다시 다룬다.

A.1전체 그림

시나리오는 하나다 — 워커 노드 1의 order 파드가 워커 노드 2의 payment 파드를 payment-svc라는 이름으로 부른다.

A.2사전 구성

이 경로가 성립하려면 먼저 Deployment와 Service가 있어야 한다. selector가 파드를 고르는 조건이고, targetPort가 실제 컨테이너 포트로 이어진다는 점은 1.4절에서 이미 다뤘다 — 여기서는 그 뒤에 무슨 일이 일어나는지가 주제다.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: payment
spec:
  replicas: 2
  selector:
    matchLabels:
      app: payment
  template:
    metadata:
      labels:
        app: payment
    spec:
      containers:
      - name: payment
        image: myrepo/payment:1.0
        ports:
        - containerPort: 8080
---
apiVersion: v1
kind: Service
metadata:
  name: payment-svc
spec:
  selector:
    app: payment          # 이 레이블을 가진 파드가 대상
  ports:
  - port: 80               # 서비스가 받는 포트
    targetPort: 8080       # 파드 컨테이너 포트

이 매니페스트가 적용되는 순간 세 가지가 만들어진다.

  • ClusterIP 할당 — 10.96.0.15 같은 값이 배정된다. 어느 장비의 네트워크 카드에도 없는 가상 주소다.
  • EndpointSlice (EndpointSlice) 생성 — 셀렉터에 맞고 Ready (Readiness) 상태인 파드의 IP 목록(예: [10.244.2.7, 10.244.2.8])을 담는다. 4장에서 배운 readiness 프로브가 여기서 다시 등장한다 — 프로브를 통과하지 못한 파드는 이 목록에서 빠진다.
  • 모든 노드의 iptables 갱신 — kube-proxy(노드마다 하나씩 상주하며 네트워크 규칙을 관리하는 컴포넌트)가 이 매핑을 각 노드 커널에 규칙으로 심는다. 그림에서 "모든 노드가 동일 규칙 보유"라고 적은 것이 이 뜻이다.

A.3호출 흐름 다섯 단계

order 파드(10.244.1.5)가 http://payment-svc/pay를 호출하는 순간을 그대로 따라간다.

  1. ① 이름 조회 — CoreDNS. order 파드의 /etc/resolv.conf는 이미 CoreDNS를 가리키도록 설정되어 있다. payment-svc 조회는 같은 네임스페이스이므로 payment-svc.default.svc.cluster.local로 확장되고, CoreDNS는 10.96.0.15를 응답한다. 파드 IP가 아니라 서비스의 가상 IP를 받는다는 점이 핵심이다.
  2. ② 커널의 주소 변환 — kube-proxy iptables DNAT. order 파드가 10.96.0.15:80으로 패킷을 보낸다. 패킷이 노드 1의 커널을 지나는 순간, kube-proxy가 심어둔 iptables 규칙이 목적지를 실제 파드 중 하나로 바꾼다: 10.96.0.15:80 → 10.244.2.7:8080. 파드가 2개이므로 확률적으로 분산된다. kube-proxy 프로세스가 트래픽을 중계하는 게 아니라, 규칙만 심어두고 변환은 커널이 한다.
  3. ③④ CNI · 노드 간 배달. 목적지가 10.244.2.7(노드 2의 파드 대역)이 됐으니, CNI (Container Network Interface)가 구성해 둔 라우팅을 따라 노드 1(192.168.0.5) → 노드 2(192.168.0.6)로 패킷이 이동한다.
  4. ⑤ 파드 도착. 노드 2의 CNI가 패킷을 payment 파드(10.244.2.7)의 네트워크 인터페이스로 넣어준다. 응답은 역경로로 돌아가며, 커널의 conntrack (Connection Tracking)(커널이 진행 중인 연결을 추적하는 기능)이 출발지 주소를 다시 10.96.0.15로 복원해 order 파드는 마치 서비스와 직접 대화한 것처럼 보게 된다.

A.4단계별 검증 명령

0장 kind 클러스터에서 위 시나리오와 같은 구조(디플로이먼트+서비스)를 하나 띄워 두고, 아래 명령으로 각 단계를 직접 확인한다.

# ① DNS: 이름이 ClusterIP로 해석되는가
kubectl run dns-test --image=busybox:1.36 -it --rm --restart=Never \
  -- nslookup payment-svc.default.svc.cluster.local

# ②의 전제: 서비스가 실제 파드 IP 목록을 갖고 있는가
kubectl get endpointslices -l kubernetes.io/service-name=payment-svc

# 전체 연결: 파드 안에서 실제 호출
kubectl run curl-test --image=curlimages/curl:8.8.0 -it --rm --restart=Never \
  -- curl -sS http://payment-svc:80/pay
체크포인트첫 명령이 10.96.x.x 형태의 주소를 돌려주면 ①이 정상, 두 번째 명령의 ENDPOINTS 목록이 비어 있지 않으면 ②의 전제가 정상이다.

A.5실무 주의점

함정 1 — ClusterIP에 ping은 안 된다 가상 주소이므로 ICMP (Internet Control Message Protocol)(ping이 쓰는 프로토콜) 요청에 응답할 실체가 없다. ping 실패는 장애가 아니다. "서비스 IP에 ping이 안 되는데 장애인가요?"는 매우 흔한 헛다리짚기이며, 커널이 그 주소로 가는 TCP/UDP 패킷만 낚아채 바꿔치기하기 때문에 실제 통신(curl 등)은 정상 동작한다.
함정 2 — 연결이 안 되면 EndpointSlice부터 본다 목록이 비어 있다면 원인은 둘 중 하나다 — 셀렉터 레이블 불일치, 또는 readiness 프로브 실패. 이 둘이 서비스 장애의 최다 원인이다. Service 자체나 CNI를 의심하기 전에 kubectl get endpointslices부터 확인하는 습관을 들인다.
함정 3 — 컨트롤 플레인은 데이터 경로에 없다 API 서버가 죽어도 이미 심어진 iptables 규칙으로 기존 통신은 계속 동작한다. 그림에서 컨트롤 플레인이 점선(제어 통신)으로만 연결된 이유다 — 컨트롤 플레인 장애 ≠ 서비스 통신 장애. 다만 새 파드가 뜨거나 죽어 EndpointSlice가 갱신돼야 하는 상황이라면, 그 갱신 자체는 컨트롤 플레인을 거치므로 영향을 받는다.
2026-08 기준 확인 사항 이 부록은 가장 널리 쓰이는 iptables 모드를 기준으로 설명했다. kube-proxy는 리눅스에서 iptables·ipvs·nftables 세 모드를 지원하며, 쿠버네티스 공식 문서는 iptables와 IPVS 모드를 대체할 차세대 표준으로 nftables 모드를 권장하고 있다(규칙 수가 많을 때의 성능·정합성 문제 개선). 원리(DNAT로 가상 IP를 실제 파드 IP로 바꾼다는 것)는 세 모드 모두 동일하다. 한 가지 더 — Cilium 같은 eBPF 기반 CNI를 쓰면 kube-proxy 자체를 완전히 대체해 이 경로를 eBPF 프로그램이 대신 처리하기도 한다. 출처: kubernetes.io/docs/reference/networking/virtual-ips (프록시 모드 종류 및 nftables 권장 명시)
