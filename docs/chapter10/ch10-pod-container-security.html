CHAPTER 10

파드와 컨테이너 보안

4장에서 "누가 클러스터에 무엇을 할 수 있는가"(RBAC)를 다뤘다면, 이 장은 "그 안에서 도는 파드 자체가 얼마나 위험할 수 있는가"다. 위험한 스펙으로 아예 못 뜨게 막고(어드미션), 뜨더라도 커널까지 못 뚫게 격리하고(런타임클래스), 그 안에서 이상한 짓을 하면 잡아낸다(탐지 툴) — 세 절이 배포 전부터 실행 중까지 이어지는 방어선이다.

2026-08 기준 변경 사항 주석 포함

핵심 3줄

1. 파드 시큐리티 어드미션은 privileged·baseline·restricted 세 수준과 enforce·warn·audit 세 모드의 조합이다 — 클러스터 기본값은 여전히 아무 제한 없는 privileged다.

2. 런타임클래스는 워크로드마다 격리 강도를 고를 수 있게 한다 — runc(기본)부터 gVisor, 카타 컨테이너, 파이어크래커까지 오버헤드와 안전성이 함께 오른다.

3. 사전 차단(어드미션)·구조적 격리(런타임클래스)·실시간 탐지(Falco 등)는 서로 대체재가 아니라 겹겹의 방어선이다.

10.1파드 시큐리티 어드미션 컨트롤러

파드 스펙에는 privileged: true, 호스트 네임스페이스 공유처럼 보안에 민감한 필드가 여럿 있다. 파드 시큐리티 어드미션 (Pod Security Admission)은 이런 필드를 클러스터·네임스페이스 수준에서 일괄 통제하는 내장 어드미션 컨트롤러다.

10.1.1 파드 시큐리티 어드미션 활성화

이 기능은 쿠버네티스 1.22에서 베타로 도입되어 이전의 PodSecurityPolicy(PSP)를 대체했다. PSP는 설정이 난해하고 디버깅이 어렵다는 오랜 악명이 있었다 — 그 이전에는 관리자가 각 워크로드에 SecurityContext를 일일이 따로 정의하거나, 커스텀 어드미션 컨트롤러를 직접 만들어야 했다. 1.22 이상이면 기본 탑재되어 있으므로 별도 설치가 필요 없다.

10.1.2 파드 보안 수준

세 보안 수준 (Security Level)과 세 활성화 모드 (Mode)를 조합해 쓴다.

  • privileged — 제한이 사실상 없다. 클러스터의 기본 보안 수준이라는 점을 놓치기 쉽다 — 아무것도 안 하면 이 상태다.
  • baseline — 권한 상승 공격 등 잘 알려진 취약점을 막는다.
  • restricted — 현재 파드 보안의 모범 사례 전체를 강제한다.

처음부터 모든 네임스페이스에 restricted+enforce를 걸고 싶겠지만, 기존 구성이나 서드파티 소프트웨어와 충돌해 파드가 아예 안 뜰 수 있다. 먼저 warn·audit 모드로 시작해 위반 현황을 파악한 뒤 enforce로 올리는 것이 안전한 순서다.

10.1.3 네임스페이스 레이블을 이용한 파드 시큐리티 활성화

적용 단위는 네임스페이스이고, 방법은 레이블 하나를 붙이는 것으로 끝난다 — 별도 컨트롤러 설치가 필요 없다.

apiVersion: v1
kind: Namespace
metadata:
  name: production
  labels:
    pod-security.kubernetes.io/enforce: restricted
    pod-security.kubernetes.io/warn: restricted
    pod-security.kubernetes.io/audit: restricted

레이블 키의 enforce·warn·audit 각각에 독립적으로 수준을 지정할 수 있다 — 예를 들어 enforce: baseline, warn: restricted로 걸면 "지금 당장 막는 건 baseline까지, restricted 위반은 경고만" 같은 점진적 전환이 가능하다.

10.2워크로드 격리와 런타임클래스

컨테이너는 여전히 커널을 호스트와 공유한다 — VM만큼 격리되어 있지 않다는 뜻이다. "지금 가장 널리 쓰이는 런타임이 안전하다"고 공식적으로 증명할 방법도 마땅치 않다. 신뢰할 수 없는 코드(외부 사용자가 올린 코드, 멀티테넌시 환경의 낯선 워크로드 등)를 돌려야 한다면 격리를 더 강화해야 한다 — 이때 쓰는 것이 런타임클래스 (RuntimeClass)다.

10.2.1 런타임클래스 사용하기

클러스터 관리자가 여러 런타임클래스를 미리 등록해 뒀다면, 파드는 그중 하나를 지정하기만 하면 된다.

apiVersion: v1
kind: Pod
metadata:
  name: untrusted-workload
spec:
  runtimeClassName: gvisor
  containers:
  - name: app
    image: myrepo/untrusted:1.0

10.2.2 런타임 구현체

격리 강도가 다른 여러 오픈소스 런타임이 있다. 이 목록이 전부는 아니고, 방향을 잡는 참고용이다.

런타임방식한 줄 특징
containerdCRI 구현체단순성·견고성·이식성에 집중한 표준 컨테이너 런타임 API
cri-oCRI 구현체쿠버네티스 전용으로 만든 경량 OCI 기반 런타임
gVisor유저 공간 커널OCI 호환 샌드박스 — 시스템 콜을 가로채 커널 노출을 줄임
카타 컨테이너경량 VM컨테이너처럼 쓰지만 실제로는 별도 커널을 가진 VM
파이어크래커KVM 마이크로VM비가상화 환경에서도 매우 빠르게 격리된 VM을 띄움

10.2.3 워크로드 격리와 런타임클래스 모범 사례

  • 런타임을 워크로드마다 잘게 쪼개 섞지 않는다 — 런타임 간에는 워크로드가 이식되지 않고, 기능 매트릭스를 다 파악하기도 어려워 운영이 복잡해진다. 가급적 런타임 종류별로 클러스터를 나누는 편이 낫다.
  • 워크로드 격리가 곧 멀티테넌시 보안은 아니다 — 런타임을 안전하게 격리해도, 공격자가 쿠버네티스 API 자체를 통해 워크로드를 건드릴 길은 따로 막아야 한다(4장 RBAC, 10.1절).
  • 런타임마다 도구 생태계가 다르다 — 런타임이 바뀌면 docker ps 같은 익숙한 명령이 그대로 안 통할 수 있어, 트러블슈팅 난이도가 오른다.

10.3파드와 컨테이너 보안 관련 고려 사항

어드미션 컨트롤과 런타임 격리로 끝이 아니다. "생성 시점"과 "격리 구조" 다음은 "실행 중 행동"이다.

10.3.1 어드미션 컨트롤러

파드 시큐리티 어드미션이 너무 제약적이거나(또는 반대로 너무 느슨하다고) 느껴진다면, 더 정교한 정책을 짤 수 있는 범용 어드미션 컨트롤러(OPA Gatekeeper, Kyverno 등)가 대안이다. 어드미션 컨트롤 자체의 원리와 웹훅 구성은 17장에서 깊이 다룬다.

10.3.2 침입 및 이상 징후 탐지 툴

정책은 "무엇을 막을지"를 정하지만, 이미 돌고 있는 컨테이너 내부에서 실제로 무슨 일이 일어나는지는 별개의 문제다. 대표 도구가 CNCF 프로젝트인 Falco다 — 데몬셋으로 설치되어, 리눅스 시스템 콜을 감시(주로 eBPF (extended Berkeley Packet Filter) 방식)하며 셸 실행, 민감 파일 접근 같은 수상한 행동을 규칙 기반으로 탐지한다.

2026-08 기준 갱신 주석 Falco는 CNCF Graduated 프로젝트로 자리 잡아 컨테이너 런타임 위협 탐지의 사실상 표준이 됐다. 다만 Falco는 탐지·경고까지만 한다 — 공격을 막지는 않는다. 여기서 한 걸음 더 나간 것이 Cilium 진영의 Tetragon(역시 eBPF 기반)이다 — 커널의 LSM 훅을 이용해 위험한 시스템 콜을 탐지와 동시에 실제로 차단할 수 있다. 2026년 현재 실무에서 흔한 조합은 "폭넓은 규칙과 알림 생태계는 Falco, 특정 위험 행동에 대한 실제 강제 차단은 Tetragon"을 함께 쓰는 것이다. 출처: CNCF 프로젝트 성숙도 분류(Falco Graduated) · Cilium/Isovalent 공식 문서(Tetragon 아키텍처) — 업계 비교 자료 다수 교차 확인
