Volume은 Pod에 정의된다. 각 컨테이너는 필요한 Volume만 자신의 경로에 명시적으로 마운트한다.

오늘 가져갈 관점경로 ≠ 저장 위치
오늘 사용할 Volume의 정의입니다. Volume은 물리 디스크 하나를 뜻하지 않습니다. Pod가 사용할 저장소 source와 컨테이너에서 보일 경로를 연결하는 Kubernetes의 추상화입니다. Pod의 volumes에 source를 정의하고 각 컨테이너의 volumeMounts가 이름으로 선택해 mountPath에 연결합니다. 같은 Volume을 여러 컨테이너가 마운트할 수도 있고, 아무 Volume도 마운트하지 않는 컨테이너도 있습니다. 데이터의 실제 위치와 생명주기는 emptyDir, PVC 같은 Volume 종류에 따라 달라집니다. 일반적으로 파일시스템 경로로 마운트하지만 raw block을 volumeDevices로 제공하는 방식도 있습니다.

01SHARING

하나의 Volume, 여러 컨테이너

CONTAINER A · APP

CONTAINER B · SIDECAR

READ컨테이너에서 보이는 위치mountPath: /logsshared-data:/ = /logs
shared-data Volume의 루트 · /실제 파일 · /output.log

A:/var/log/app/output.log = VOLUME:/output.log = B:/logs/output.log

mountPath는 Volume 안에 만드는 경로가 아니다. Volume의 루트가 컨테이너에서 나타날 위치다.

Pod-level resourcesidecar · init container
mountPath는 Volume 내부에 디렉터리를 만드는 설정이 아닙니다. Volume의 루트 슬래시가 해당 컨테이너에서 어느 경로로 보일지를 정합니다. A에서는 shared-data의 루트가 /var/log/app으로 보이고, B에서는 같은 루트가 /logs로 보입니다. 따라서 Volume 내부의 /output.log 하나가 A에게는 /var/log/app/output.log, B에게는 /logs/output.log입니다. 만약 A가 Volume 안의 /a를, B가 /b를 따로 마운트하는 subPath 설정을 사용한다면 그때는 같은 파일이 아닙니다.

공유 File System

NFS·CephFS 같은 프로토콜로 디렉터리를 mount
지원하면 여러 노드가 같은 파일 공유

둘 다 네트워크 기반일 수 있다. 차이는 Block Device를 받는가, File System 서비스를 받는가.

device attach vs filesystem mount실제 동시 접근은 드라이버·Access Mode 확인
Block과 File의 차이는 네트워크 사용 여부가 아니라 제공되는 인터페이스입니다. 클라우드 Block Storage도 보통 네트워크를 통해 노드에 연결되지만 운영체제에는 디스크 장치로 보입니다. 노드가 그 장치를 포맷하고 파일시스템을 마운트합니다. NFS나 CephFS는 스토리지 서버가 파일시스템을 관리하고 노드는 원격 디렉터리를 마운트합니다. Block은 보통 한 노드 읽기·쓰기, 공유 File System은 여러 노드 RWX에 적합하지만 실제 가능 여부는 CSI 드라이버와 Access Mode를 확인해야 합니다.

지금까지 emptyDir처럼 Pod 안에서 시작하고 끝나는 임시 공간을 봤습니다. 그렇다면 외부 Block Volume이나 공유 File System을 Pod가 어떻게 사용할까요? 애플리케이션이 제품 주소나 디스크 ID를 직접 적는 대신 PVC로 필요한 조건을 요청합니다. PV는 실제 외부 스토리지를 Kubernetes 클러스터 자원으로 표현합니다. Pod는 PVC 이름만 알고, Kubernetes가 PVC 조건에 맞는 PV를 연결합니다. 다음 장에서 PV를 미리 만들어야 하는지, 자동으로 만들 수 있는지를 이어서 봅니다.

PVC · PENDING

PVC가 직접 만드는 것이 아니라 CSI provisioner가 PVC를 보고 실제 스토리지와 PV를 생성한다.

Static = PV first · Dynamic = PVC first없고 만들 수도 없으면 Pending
PV가 항상 먼저 필요한 것은 아닙니다. 정적 방식은 관리자가 실제 디스크와 PV를 먼저 준비합니다. 동적 방식은 PVC가 먼저 생기고, StorageClass가 지정한 CSI provisioner가 실제 스토리지와 PV를 만듭니다. 둘 다 없으면 PVC는 Pending에 머물고 이 PVC를 쓰는 Pod도 실행되지 못합니다.

맞습니다. 외부 볼륨을 가져다 붙이는 주체는 CSI 드라이버입니다. PVC가 요구사항을 내고 StorageClass가 생성 방식을 고르며, 만들어진 또는 기존 외부 볼륨은 PV로 표현됩니다. Pod가 노드에 배치되면 CSI가 블록 볼륨을 attach하고 kubelet 쪽 CSI 플러그인이 컨테이너의 /data에 mount합니다. NFS 같은 파일 스토리지는 attach 없이 바로 mount할 수도 있습니다.

05YAML

마운트 방식은 같고, 출처가 다르다

EPHEMERAL
volumeMounts:
- name: data
  mountPath: /data

volumes:
- name: data
  emptyDir: {}
PERSISTENT
volumeMounts:
- name: data
  mountPath: /data

volumes:
- name: data
  persistentVolumeClaim:
    claimName: app-data

컨테이너 코드는 그대로 · Kubernetes가 /data 뒤의 구현을 바꾼다.

volumeMounts + volumes같은 인터페이스, 다른 수명
애플리케이션은 둘 다 /data만 봅니다. Pod 명세에서 volume source를 emptyDir에서 PVC로 바꾸면 뒤쪽의 생명주기와 구현이 바뀝니다.
05CONFIG · DYNAMIC

동적 방식: StorageClass + PVC

storage-class.yaml · AWS EBS 예시
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: fast-block
provisioner: ebs.csi.aws.com
parameters:
  type: gp3
reclaimPolicy: Delete
volumeBindingMode: WaitForFirstConsumer
allowVolumeExpansion: true
pvc.yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: app-data
spec:
  storageClassName: fast-block
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 10Gi

PVC.spec.storageClassName: fast-block → 같은 이름의 StorageClass 선택 → PV 자동 생성

환경에 따라 provisioner·parameters 변경작성: SC + PVC · 자동: PV
동적 방식에서는 StorageClass와 PVC를 작성합니다. 이 예시는 AWS EBS CSI의 gp3이므로 다른 환경에서는 provisioner와 parameters를 바꿔야 합니다. PVC가 fast-block을 요청하면 CSI provisioner가 실제 10Gi 디스크와 PV를 만들고 PVC와 바인딩합니다. WaitForFirstConsumer이므로 이 PVC를 쓰는 Pod의 배치 위치가 결정된 뒤 적절한 영역에 디스크를 만듭니다.
05CONFIG · PRE-PROVISIONED PV

정적 방식: PV를 먼저 프로비저닝

pv.yaml · 기존 NFS 예시
apiVersion: v1
kind: PersistentVolume
metadata:
  name: app-nfs-pv
spec:
  capacity:
    storage: 10Gi
  accessModes:
    - ReadWriteMany
  persistentVolumeReclaimPolicy: Retain
  storageClassName: manual-nfs
  nfs:
    server: 10.0.0.20
    path: /exports/app
pvc.yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: app-data
spec:
  storageClassName: manual-nfs
  accessModes:
    - ReadWriteMany
  resources:
    requests:
      storage: 5Gi

Binding 조건
storageClassName 동일
accessModes 호환
PV 용량 ≥ PVC 요청 용량
app-nfs-pv ↔ app-data · Bound

외부 스토리지 → PV 먼저 → PVC 나중END · Q & A
정적 방식에서는 관리자가 기존 NFS와 이를 나타내는 PV를 먼저 정의합니다. 이후 PVC의 storageClassName과 Access Mode가 PV와 같고, 요청 5Gi를 PV의 10Gi가 만족하므로 둘이 Bound 됩니다. 실제 환경에서는 NFS 서버와 export 경로를 바꿔야 합니다. 여기까지 설정한 app-data PVC를 앞 페이지의 Pod volume에서 claimName으로 참조하면 됩니다.
