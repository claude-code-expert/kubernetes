CHAPTER 18

깃옵스와 배포

2장에서 "클러스터 수정은 항상 리포지터리를 거쳐서"라는 원칙을 배웠고, 5장·7장·12장에서 그 원칙이 CI/CD와 멀티클러스터·글로벌 배포로 계속 확장되는 것을 봤다. 이 장은 그 모든 것에 이름을 붙인다 — 깃옵스. 정의부터 리포지터리 구조, 시크릿 관리, 실제 설치까지 한 바퀴 돈다.

2026-08 기준 변경 사항 주석 포함

핵심 3줄

1. 깃옵스는 CNCF가 4대 원칙(선언적·버전관리·자동 풀·지속적 조정)으로 공식 정의했다 — 넷 중 하나라도 빠지면 그냥 CI/CD이지 깃옵스가 아니다.

2. 리포지터리 구조는 4가지 전략이 있지만, 환경별 브랜치만은 실무에서도 원서에서도 피하라고 입을 모은다 — 대신 브랜치 안에서 환경별 폴더로 나눈다.

3. 시크릿 관리 5가지 방법 중 실무 권장은 둘뿐이다 — Sealed Secrets(암호화해 Git에 커밋) 또는 외부 시크릿 프로바이더(Git엔 참조만).

18.1깃옵스란?

깃옵스 (GitOps)는 위브웍스(Weaveworks)가 프로덕션에서 쿠버네티스를 운영한 경험에서 만든 용어다 — 소프트웨어 개발 생명주기의 개념(버전 관리, 리뷰, 자동화된 적용)을 운영 그 자체에 적용한 것이다.

2026-08 기준 갱신 주석 — 공식 정의 등장 원서 집필 시점엔 깃옵스가 위브웍스의 용어로만 설명됐지만, 이후 CNCF 산하 GitOps Working Group이 벤더 중립적인 공식 정의를 OpenGitOps 프로젝트로 문서화했다(Principles v1.0.0). 네 원칙은 ① 선언적(Declarative) — 원하는 상태를 선언으로 기술, ② 버전 관리·불변(Versioned and Immutable) — Git에 저장해 이력·롤백이 자동으로 따라옴, ③ 자동으로 끌어옴(Pulled Automatically) — 사람이 kubectl apply하지 않고 에이전트가 감시, ④ 지속적 조정(Continuously Reconciled) — 실제 상태가 어긋나면 스스로 되돌림이다. 이 네 가지를 기준으로 보면, "CI가 끝나고 스크립트가 kubectl apply를 한 번 호출하는" 파이프라인은 ③④가 빠져 있어 엄밀히는 깃옵스가 아니다. 출처: opengitops.dev(공식 4대 원칙) · github.com/open-gitops/documents(v1.0.0 릴리스) · cncf.io/projects/opengitops(CNCF Sandbox 등재)

18.2깃옵스가 필요한 이유

깃옵스는 클러스터에 애플리케이션을 배포하고 클러스터·애플리케이션 구성을 관리하는 데 탁월한 수단이다. 사람이 직접 kubectl로 클러스터를 만지는 방식과 비교하면 이점이 뚜렷하다 — 모든 변경이 감사 가능하고(누가, 언제, 왜), 재현 가능하며(클러스터를 통째로 잃어도 리포지터리만 있으면 복구), 코드 리뷰라는 기존 프로세스에 자연스럽게 편입된다.

18.3깃옵스 리포지터리 구조

가장 일반적인 4대 전략이 있고, 각각 장단점이 뚜렷하다.

  • 단일 리포지터리 — 모든 매니페스트와 애플리케이션 코드를 한곳에. 가장 단순하지만 회사가 커지면 관심사가 뒤섞인다.
  • 팀별 리포지터리 — 팀마다 리포를 나누되 매니페스트는 같은 리포에 둔다. 정리는 되지만 애플리케이션이 늘수록 관리 부담이 는다. 확신이 없다면 여기서 시작하라는 것이 원서의 권장이다.
  • 애플리케이션별 리포지터리 — 앱마다 리포를 나눈다. 팀 단위 읽기 권한을 세밀하게 걸 수 있지만, 전체를 한눈에 보기 어렵다.
  • 환경별 브랜치 — 같은 리포 안에서 main·staging·dev 브랜치로 환경을 나눈다. 머지만으로 승격되는 매력이 있지만, 브랜치 충돌 위험이 있고 헬름·쿠스토마이즈 같은 템플릿 툴과 궁합이 나쁘다.

18.4시크릿 관리

깃옵스 워크플로에서 가장 까다로운 문제다 — 선언한 것을 전부 Git에 두는 게 원칙인데, 시크릿까지 그대로 두면 곤란하다. 다섯 가지 방법이 있다.

  1. Git에 직접 저장 — 가장 간단하지만 절대 권장하지 않는다. 프라이빗 리포라도 여러 사용자가 접근하면 결국 시크릿도 건드리게 된다.
  2. 컨테이너 이미지에 내장 — 조금 낫지만, 로테이션마다 재빌드해야 하고 이미지를 가져오는 모두가 시크릿에 접근하게 된다.
  3. 쿠버네티스 Secret 그대로 사용 — 가장 쉽게 시작할 수 있다. 다만 1장·4장에서 이미 확인했듯 base64는 암호화가 아니다.
  4. Sealed Secrets — 클러스터의 공개키로 암호화한 값을 Git에 커밋한다. 그 클러스터의 개인키로만 복호화되므로, 리포지터리가 유출돼도 안전하다.
  5. 외부 시크릿 프로바이더 — Vault나 클라우드 시크릿 매니저가 원본을 갖고, Git에는 참조만 남는다. 4장에서 다룬 External Secrets Operator가 정확히 이 방식을 구현한다.

18.5플럭스 설치

플럭스 (Flux)는 Git 리포지터리의 변경을 감지해 자동으로 클러스터에 반영하는 쿠버네티스 오퍼레이터다 — CNCF Graduated 등급의 성숙한 깃옵스 툴이다.

실습 환경 안내 원서는 이 실습에도(3장과 마찬가지로) brew install minikube로 전용 클러스터를 새로 만든다. 이 노트에서는 0장에서 이미 띄워 둔 kind 클러스터를 그대로 사용한다 — 이유는 3장 갱신 노트와 동일하다(도구 통일). 플럭스 CLI 설치와 이후 명령은 클러스터 종류와 무관하게 동일하게 동작한다. 
# 플럭스 CLI 설치 (macOS)
brew install fluxcd/tap/flux

# 0장 kind 클러스터에 플럭스 요구사항 충족 여부 확인
flux check --pre

# 클러스터에 플럭스 컴포넌트 배포 (GitHub 예시)
flux bootstrap github \
  --owner= \
  --repository=<리포지터리명> \
  --branch=main \
  --path=clusters/study \
  --personal

flux bootstrap 한 번이면 컨트롤러 설치부터, 그 컨트롤러가 감시할 리포지터리·경로 등록까지 한 번에 끝난다 — 이후로는 clusters/study 경로에 매니페스트를 커밋하는 것이 곧 배포다.

18.6깃옵스 툴

선정 기준은 사용 편의성, 엔터프라이즈 기능, 확장성이다. 가장 많이 쓰는 툴 넷.

  • 플럭스 — CNCF Graduated. 위브웍스가 호스티드 서비스도 제공한다.
  • 아르고CD — 역시 CNCF Graduated. 선언형 인프라를 계속 모니터링하며 실제 상태와의 차이를 리졸빙한다. 5장·7장·11장에서 이미 여러 번 등장했다 — 카나리 배포(Argo Rollouts), 멀티리전 웨이브 롤아웃(ApplicationSet RollingSync) 모두 아르고 생태계다.
  • 코드프레시 — 깃옵스를 구축하는 CI/CD 플랫폼. 아르고CD 호스티드 버전도 제공.
  • 하네스 — 엔터프라이즈 대상의 성숙한 CD 툴셋.
스터디 참고플럭스와 아르고CD는 철학이 다르다 — 플럭스는 여러 개의 작은 컨트롤러 조합, 아르고CD는 웹 UI를 포함한 통합 플랫폼에 가깝다. 5·7·11장에서 아르고 생태계 예제를 이미 다뤘으므로, 이 장의 실습은 플럭스로 균형을 맞췄다.
