CHAPTER 07

글로벌 애플리케이션 분산과 스테이징

지금까지는 클러스터 하나를 대상으로 배포·릴리스·롤아웃을 다뤘다. 이 장은 그 배포를 지구 전체로 늘렸을 때의 문제다. 이미지를 어디에 두고, 리전마다 무엇을 다르게 하고, 트래픽을 어떻게 흘리고, 무엇보다 — 실수했을 때 전 세계가 동시에 멎지 않게 어떻게 단계를 나누는가.

2026-08 기준 변경 사항 주석 포함 · 원문 용어 정정 1건 포함

핵심 3줄

1. 이미지는 한 번만 빌드하고 지리 복제 레지스트리로 퍼뜨린다 — 리전마다 다시 빌드하지 않는다. 다른 건 헬름 values나 오버레이로만 바꾼다.

2. 글로벌 롤아웃은 절대 한 번에 하지 않는다 — 카나리 리전 → 가장 비슷하거나 트래픽 적은 리전 → 나머지 순으로, 웨이브 사이에 "연기 날 때까지" 기다린다.

3. 장애가 나면 순서가 생명이다 — 원인 파악보다 트래픽을 건강한 리전으로 돌리는 "지혈"이 항상 먼저다.

7.1이미지 분산 배포

전 세계에서 애플리케이션을 돌리려면, 먼저 그 이미지가 전 세계 클러스터에서 당겨받을 수 있어야 한다. 가장 먼저 검토할 것은 이미지 레지스트리의 자동 지리 복제 (Automatic Geo-replication) — 한 리전에 이미지를 푸시하면 다른 리전의 레지스트리로 자동 동기화되는 기능이다.

지리 복제가 없는 레지스트리를 쓴다면 대안은 리전마다 이미지 이름을 조금씩 다르게 관리하는 것이다 — 다만 이러면 "같은 코드가 리전마다 다른 이름의 아티팩트"가 되어 5장에서 강조한 불변 태그 원칙과 충돌하기 쉽다. 가능하면 지리 복제 레지스트리를 쓰는 편이 관리 부담을 크게 줄인다.

7.2배포 파라미터화

이미지는 하나로 고정해도 리전마다 구성은 다를 수밖에 없다 — 레플리카 수, 로케일 기본값, 데이터 거주(residency) 요건 같은 것들이다. 1장·2장에서 배운 헬름 values(또는 Kustomize 오버레이)가 여기서 정확히 이 역할을 한다: 이미지는 그대로 두고, 리전별 차이만 파라미터로 분리한다.

# values-us-east.yaml
replicaCount: 12
region: us-east

# values-eu-west.yaml
replicaCount: 6
locale: de-DE

helm install journal-us-east ./journal --values values-us-east.yaml --kube-context us-east
helm install journal-eu-west ./journal --values values-eu-west.yaml --kube-context eu-west

원칙은 1.10절과 같다 — 리전 간에 정말 달라야 하는 값만 파라미터로 뽑는다. 이미지 태그까지 리전별로 다르게 관리하기 시작하면 "지금 전 세계에 뭐가 떠 있지?"라는 6.1절의 질문에 답할 수 없게 된다.

7.3글로벌 트래픽 로드 밸런싱

애플리케이션이 전 세계에서 돌고 있다면, 이제 트래픽을 어디로 흘릴지 정해야 한다. 기본 원칙은 지리적으로 가까운 곳으로 보내 지연을 줄이되, 장애 시 다른 리전으로 넘어갈 수 있어야 한다는 것 — 이 전환을 페일오버 (Failover)라 부른다.

단일 호스트네임(예: myapp.myco.com)으로 서비스한다고 하면, 방식은 크게 둘로 갈린다.

  • DNS 기반 로드 밸런싱 — 사용자가 myapp.myco.com을 조회하면, DNS 서버가 사용자의 위치와 그 시점의 리전 가용성에 따라 다른 IP를 돌려준다. 리전 전환이 곧 DNS 응답을 바꾸는 일이라, 7.5절에서 볼 캐싱 문제가 여기서 생긴다.
  • 애니캐스트 (Anycast) — 동일한 IP 주소를 인터넷의 여러 위치에서 동시에 전파(BGP로 광고)한다. 사용자가 조회하면 DNS는 항상 같은 IP를 돌려주지만, 실제 패킷은 네트워크 라우팅에 의해 가장 가까운 위치로 자동으로 간다.
원문 용어 정정 원서 7.3절은 이 두 번째 방식을 "멀티캐스트 IP"라고 표기하지만, 설명된 동작(동일 IP를 여러 위치에서 전파해 라우팅으로 가장 가까운 곳에 도달) 자체는 애니캐스트 (Anycast)다. 멀티캐스트 (Multicast)는 하나의 송신자가 구독한 여러 수신자 그룹에 동시에 전달하는 완전히 다른 개념이라, 이 문맥에는 맞지 않는다. Cloudflare, AWS Global Accelerator, 각 클라우드의 글로벌 로드밸런서가 실제로 쓰는 방식이 애니캐스트다.

7.4안정적인 글로벌 롤아웃

리전별 구성 템플릿까지 끝났다면 남은 문제는 "이걸 전 세계에 어떻게 배포하는가"다. 전 리전 동시 배포는 유혹적이지만, 실수 하나가 곧 전면 글로벌 장애가 된다. 신중하게, 단계적으로 간다.

7.4.1 사전 롤아웃 검사

글로벌 롤아웃 전에 복합 테스팅(synthetic testing)을 통과해야 한다는 건 최소 조건일 뿐이다. 테스트를 다 통과했다고 프로덕션에서 문제가 없다는 뜻은 아니다 — 실제 사용자의 언어, 실제 입력 데이터의 분포는 테스트 환경이 완벽히 흉내 낼 수 없다. 그래서 각 리전 롤아웃은 새로운 문제를 발견할 기회로 취급해야 한다.

7.4.2 카나리 리전

카나리 리전 (Canary Region)은 릴리스를 검증하기 위해 실제 트래픽(내부 팀이든 소수 외부 사용자든)을 먼저 받는 배포 공간이다. 5장에서 배운 카나리 배포(파드 단위로 트래픽 일부만 새 버전으로)와 정확히 같은 발상을, 리전 단위로 한 단계 확장한 것이다.

7.4.3 리전 타입 식별

리전마다 특성이 다르다는 것을 미리 표로 정리해 둔다. 이 차이를 놓치면 카나리 리전에서는 안 보이던 문제가 프로덕션 리전에서 터진다.

특성왜 리전마다 다른가
디바이스 비중개발도상국에 가까운 리전일수록 모바일 브라우저 트래픽 비중이 높다.
입력 문자 집합비영어권 리전은 유니코드 처리 버그가 드러나기 쉬운 문자열을 더 많이 보낸다.
API 사용 패턴리전별 사용자 행동 차이로 특정 API만 유독 많이 호출되는 리전이 생긴다.

7.4.4 글로벌 롤아웃 전략 수립

웨이브 순서 원칙: 카나리와 가장 비슷한 리전, 또는 트래픽이 가장 적은 리전부터. 문제가 생겨도 영향이 작다. 웨이브 사이 대기 시간은 임의로 정하지 않는다 — 연기를 내기까지의 시간 (Time-to-smoke), 즉 과거에 문제가 실제로 드러나기까지 걸린 평균 시간의 2배를 기준으로 삼는다(예: 평균 1시간 만에 발견됐다면 다음 웨이브까지 2시간 대기).

2026-08 기준 갱신 주석 이 절차(웨이브·대기·건강 확인 통과 시에만 다음 단계 진행)를 손으로 하면 실수하기 쉽다. 2026년 현재 이를 코드로 구현하는 표준 도구는 ArgoCD ApplicationSet의 RollingSync 전략이다 — 클러스터(리전)를 스텝으로 묶고, 앞 스텝이 모두 Healthy가 될 때까지 다음 스텝을 진행하지 않는다. 
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: journal-global-rollout
spec:
  generators:
  - list:
      elements:
      - cluster: canary-internal
        wave: "0"
      - cluster: us-east
        wave: "1"
      - cluster: eu-west
        wave: "2"
      - cluster: ap-northeast
        wave: "2"
  strategy:
    type: RollingSync
    rollingSync:
      steps:
      - matchExpressions:
        - {key: wave, operator: In, values: ["0"]}
      - matchExpressions:
        - {key: wave, operator: In, values: ["1"]}
      - matchExpressions:
        - {key: wave, operator: In, values: ["2"]}
        maxUpdate: 50%
  template:
    metadata:
      name: 'journal-{{cluster}}'
    spec:
      destination:
        name: '{{cluster}}'
Flagger나 Argo Rollouts(5장)가 파드 단위 카나리를 다루듯, ApplicationSet RollingSync는 그 판단 단위를 클러스터(리전) 단위로 끌어올린 것이라고 보면 된다. 출처: argo-cd 공식 문서(ApplicationSet Progressive Syncs) · argoproj/argo-cd 프로젝트

7.5문제 발생 시 대처 요령

아무리 신중해도 문제는 생긴다. 관건은 극심한 스트레스 상황에서도 정확한 순서로 대응하는 것이다 — 소방관들이 실제 화재 현장에서 가장 단순한 절차조차 잊어버리는 것과 같은 이유로, 장애 상황의 사람도 뻔한 단계를 건너뛰는 실수를 저지른다. 그래서 체크리스트를 평상시에, 스트레스 없는 상태에서 미리 만들고 연습해 둔다.

첫 번째로 숙달해야 할 동작은 하나다 — 영향받은 리전의 트래픽을 건강한 리전으로 옮기는 것. 근본 원인 조사는 그다음이다. 이걸 연습하다 보면 예상 못 한 현실을 만난다 — DNS 기반 트래픽 전환은 클라이언트·리졸버의 캐시 때문에 "전환했다고 끝"이 아니다. 특정 리전으로 가는 트래픽의 99%를 드레인하는 데 얼마나 걸리는지 실제로 재 보고, 그 시간을 목표치로 못 박아 두어야 장애 순간에 헤매지 않는다.

연습해야 할 것은 트래픽 전환만이 아니다 — 전체 데이터 복구, 이전 버전으로의 글로벌 롤백도 평상시에 실제로 해 봐야 한다. 실수를 발견할 때마다 기록하고, 검토하고, 가능하면 자동화해 사람이 명령을 복붙하다 실수할 여지를 없앤다.
