CHAPTER 08

리소스 관리

스케줄러가 파드를 어디에 놓을지 어떻게 정하는가부터, 파드 하나가 자원을 얼마나 써도 되는지, 그리고 부하가 바뀔 때 무엇을(파드 수·파드 크기·노드 수) 늘릴 것인가까지 — 클러스터 자원 관리의 전체 그림을 다루는 장이다. 이 장의 개념들은 8주 스터디에서 가장 촘촘하게 서로 얽힌다.

2026-08 기준 변경 사항 주석 포함

핵심 3줄

1. 스케줄링은 두 단계다 — 못 쓸 노드를 걸러내고(Filter, 구 프레디킷), 남은 노드 중 최선을 고른다(Score, 구 우선순위).

2. 자원 관리는 세 계층으로 나뉜다 — 파드 몇 개(HPA), 파드 하나가 얼마나(VPA), 노드 몇 대(클러스터 오토스케일러). 셋은 서로를 촉발한다.

3. requests·limits를 어떻게 설정하느냐가 QoS 클래스(Guaranteed·Burstable·BestEffort)를 정하고, 이는 곧 자원 부족 시 "누가 먼저 죽는가"를 정한다.

8.1쿠버네티스 스케줄러

스케줄러 (kube-scheduler)는 컨트롤 플레인에 있는 컴포넌트로, 새로 생긴 파드를 어느 노드에 배치할지 결정한다. 결정은 클러스터의 제약 조건과 사용자가 지정한 조건을 종합해 이뤄진다.

8.1.1 프레디킷

스케줄러가 쓰는 첫 함수는 어느 노드가 이 파드를 아예 받을 수 없는지 걸러내는 것이다. true/false만 반환하는 강한 제약조건 (Hard Constraint)이다 — 예를 들어 노드에 남은 메모리가 파드 요청량보다 적으면 즉시 탈락, 파드가 요구하는 포트가 이미 그 노드에서 쓰이고 있으면 탈락.

8.1.2 우선순위

탈락시키고 남은 노드들에는 상대적인 점수가 매겨진다. 여유 자원이 많은 노드를 우대하거나, 같은 레플리카셋의 파드를 여러 노드에 골고루 분산시키는 식이다. 가장 높은 점수를 받은 노드가 최종 배치지가 된다.

2026-08 기준 갱신 주석 — 용어 체계 변경 "프레디킷"·"우선순위"라는 이름은 옛 스케줄러 구조의 용어다. 현재 스케줄러는 스케줄링 프레임워크 (Scheduling Framework)로 재구성되어, queueSort·preFilter·filter·postFilter·preScore·score·reserve·permit·preBind·bind·postBind 11개 확장점(extension point)의 플러그인 체인으로 동작한다. 이 장에서 말하는 프레디킷은 filter 확장점에, 우선순위는 score 확장점에 대응한다 — 동작 원리는 같고 이름과 커스터마이즈 방식만 정교해졌다. 출처: kubernetes.io/docs/reference/scheduling/config (확장점 정의) · kubernetes.io/docs/reference/scheduling/

8.2고급 스케줄링 기법

쿠버네티스는 대부분의 경우 알아서 잘 배치한다 — 여유 있는 노드를 우선하고, 같은 레플리카셋은 흩어 놓는다. 하지만 기본 동작을 오버라이드해야 할 때가 있다. 방법은 세 가지이고, 방향이 서로 다르다.

8.2.1 파드 어피니티와 안티-어피니티

어피니티 (Affinity)는 파드를 다른 파드 기준으로 상대 배치하는 규칙이다. "이 파드는 X 파드와 같은 노드에"(어피니티) 또는 "같은 노드에 두지 마라"(안티-어피니티)를 선언한다. 강제(requiredDuringScheduling…)와 선호(preferredDuringScheduling…) 두 강도가 있다. 실무에서 가장 흔한 쓰임은 같은 워크로드의 레플리카를 서로 다른 가용 영역에 흩어 고가용성을 확보하는 것이다.

8.2.2 노드셀렉터

노드셀렉터 (nodeSelector)는 파드를 특정 노드에 배치하는 가장 단순한 방법이다 — 키/값 레이블이 정확히 일치하는 노드만 후보가 된다. GPU가 달린 노드에만 GPU 워크로드를 배치하는 것이 전형적인 예다. 표현력은 낮지만(동등 조건만 가능) 이해하기 쉬워 간단한 경우엔 이것으로 충분하다.

8.2.3 테인트와 톨러레이션

테인트 (Taint)는 노드에 걸어 두는 "거부" 표식이다 — 이 표식이 있으면 대응하는 톨러레이션 (Toleration)을 가진 파드만 그 노드에 배치될 수 있다. 안티-어피니티와 얼핏 비슷해 보이지만 방향이 반대다 — 어피니티는 파드가 노드를 선택하는 것이고, 테인트는 노드가 파드를 거부하는 것이다. 그래서 "이 노드는 GPU 전용, 톨러레이션 없는 일반 파드는 원천 차단"처럼 노드를 예약해 둘 때 테인트를 쓴다.

8.3파드 리소스 관리

쿠버네티스 운영에서 가장 신경 써야 할 부분이다. 목표는 하나 — 클러스터 전체 사용률을 낭비 없이, 그러나 어느 워크로드도 굶기지 않게 최적화하는 것.

8.3.1 리소스 요청

리소스 요청 (Resource Request)은 컨테이너가 스케줄링되는 데 필요한 최소 CPU·메모리다. 스케줄러는 이 값을 보고 배치 가능한 노드를 판단한다 — 요청이 8Gi인데 모든 노드의 여유 메모리가 4Gi뿐이라면, 그 파드는 영원히 Pending이다.

8.3.2 리소스 리밋과 파드 QoS

리소스 리밋 (Resource Limit)은 사용량의 상한이다. 도달했을 때 결과가 자원마다 다르다는 점이 중요하다 — CPU는 그 이상을 못 쓰게 제한(스로틀링)될 뿐이지만, 메모리는 초과 시 컨테이너가 OOMKilled로 즉시 종료된다.

requests와 limits를 어떻게 설정했는지에 따라 파드는 세 QoS 클래스 (Quality of Service Class) 중 하나로 자동 분류되고, 이는 노드에 자원 압박이 왔을 때 축출 순서를 결정한다.

# Guaranteed — requests == limits (모든 리소스)
resources:
  requests: { cpu: "500m", memory: "256Mi" }
  limits:   { cpu: "500m", memory: "256Mi" }

# Burstable — requests < limits, 또는 일부만 지정
resources:
  requests: { cpu: "250m", memory: "128Mi" }
  limits:   { cpu: "500m", memory: "256Mi" }

# BestEffort — 아무것도 지정하지 않음 (프로덕션에서는 피할 것)

8.3.3 PodDisruptionBudgets

파드가 노드에서 쫓겨나는 축출 (Eviction)에는 두 종류가 있다. 비자발적 축출은 노드 장애처럼 사람이 통제할 수 없는 상황이고, 자발적 축출은 노드 드레인·클러스터 업그레이드처럼 사람(또는 자동화)이 의도적으로 일으키는 것이다. PodDisruptionBudget (PDB)은 후자를 통제한다 — "이 워크로드는 자발적 축출 중에도 최소 N개(또는 N% 미만 손실)는 항상 떠 있어야 한다"를 선언한다.

apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: frontend-pdb
spec:
  minAvailable: 2
  selector:
    matchLabels:
      app: frontend

8.3.4 네임스페이스를 이용한 리소스 관리

2장에서 배운 네임스페이스가 여기서 다시 등장한다 — 리소스쿼터·RBAC·네트워크 정책을 네임스페이스 단위로 걸 수 있다는 것은, 곧 네임스페이스가 멀티테넌시의 기본 격리 단위라는 뜻이다.

8.3.5 리소스쿼터

여러 팀이 클러스터 하나를 같이 쓴다면 네임스페이스마다 ResourceQuota를 반드시 걸어야 한다 — 걸지 않으면 한 팀의 실수(또는 버그)가 클러스터 전체의 자원을 잠식할 수 있다. 2장에서 다룬 개발자 온보딩의 리소스쿼터가 바로 이 장치다.

8.3.6 리밋레인지

컨테이너 수준에 requests·limits를 설정하는 방법은 8.3.1~2에서 봤다. 그런데 사용자가 실수로 이 값을 빼먹으면? LimitRange가 네임스페이스에 미리 걸려 있으면, 값이 없는 파드에 자동으로 기본값을 채워준다 — BestEffort 파드가 실수로 양산되는 것을 막는 안전망이다.

8.3.7 클러스터 스케일링

노드 자체의 개수·크기를 조정하는 층이다. 워크로드가 다양하게 섞인 클러스터라면 인스턴스 크기 선택은 과학보다는 경험에 가깝다 — 처음엔 수동으로 조정하며 워크로드 프로파일을 파악하고, 패턴이 보이면 자동화한다.

2026-08 기준 갱신 주석 전통적인 클러스터 오토스케일러 (Cluster Autoscaler)는 미리 정의된 노드 그룹(ASG 등)의 크기를 늘리고 줄이는 방식이라 간접적이고 느리다(수 분 단위). 대안으로 떠오른 Karpenter는 노드 그룹 개념 없이 클라우드 API를 직접 호출해 대기 중인 파드에 딱 맞는 인스턴스를 즉시 골라 띄운다(수십 초 단위) — 2026년 현재 CNCF Incubating 프로젝트로 GA 상태이며, AWS·Azure에서 안정적으로 쓰인다(GCP는 아직 베타). 다만 AWS 밖이나 온프레미스, 멀티클라우드 환경에서는 지원 범위가 넓은 클러스터 오토스케일러가 여전히 더 안전한 기본값이다. 이벤트 기반으로 파드를 0개까지 줄이는 워크로드(큐 처리 등)에는 별도로 KEDA(CNCF Graduated)를 HPA와 함께 쓰는 조합이 흔하다. 출처: 업계 비교 자료 다수(2026년) 교차 확인 — Karpenter CNCF Incubating·AWS/Azure 안정, GCP 베타 / KEDA CNCF Graduated

8.3.8 애플리케이션 스케일링

가장 단순한 스케일링은 Deployment의 replicas를 수동으로 바꾸는 것이다(0장에서 이미 해봤다). 이제부터는 이걸 자동화하는 두 축 — 수평(HPA)과 수직(VPA) — 을 본다.

8.3.9 HPA를 이용한 수평 스케일링

HPA (HorizontalPodAutoscaler)는 CPU·메모리 또는 커스텀 메트릭에 따라 Deployment의 레플리카 수를 자동 조정한다. 4장에서 배운 메트릭 서버가 CPU·메모리 지표의 원천이다.

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: frontend-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: frontend
  minReplicas: 2
  maxReplicas: 10
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 70
2026-08 기준 확인 autoscaling/v2가 유일한 표준 API다. 옛 자료에 보이는 autoscaling/v2beta2·v2beta1은 1.26에서 완전히 제거되어 더 이상 존재하지 않는다. 출처: kubernetes.io/docs/reference/using-api/deprecation-guide

8.3.10 커스텀 메트릭을 이용한 HPA

CPU·메모리만으로는 부족할 때가 있다 — 큐 길이, 초당 요청 수 같은 애플리케이션 고유 지표로 스케일링하고 싶다면 커스텀 메트릭이 필요하다. 3장에서 설치한 프로메테우스가 이미 이런 지표를 갖고 있다면, Prometheus Adapter가 그 값을 쿠버네티스 커스텀 메트릭 API 형태로 노출해 HPA가 읽을 수 있게 중개한다.

8.3.11 수직 파드 오토스케일러

VPA (VerticalPodAutoscaler)는 레플리카 수가 아니라 파드 하나가 가진 requests 값 자체를 조정한다. "이 컨테이너는 실제로 늘 300m CPU만 쓰는데 requests를 1 코어로 잡아 뒀다"처럼 잘못된 사이징을 과거 사용량 데이터로 교정해 준다.

2026-08 기준 갱신 주석 — VPA의 오랜 약점이 해소됨 VPA는 오랫동안 치명적인 단점이 있었다 — 값을 바꾸려면 파드를 축출하고 재생성해야 했다(실행 중인 컨테이너의 requests·limits는 불변 필드였다). 이는 쿠버네티스 1.35(2025-12)에서 해결됐다 — 인플레이스 파드 리사이즈 (In-Place Pod Resize)가 정식(GA) 기능이 되어, 재시작 없이 실행 중인 컨테이너의 CPU·메모리를 바로 바꿀 수 있게 됐다. VPA는 이를 활용하는 updateMode: "InPlaceOrRecreate"를 지원한다 — 가능하면 무중단으로 즉시 반영하고, 리사이즈가 불가능한 상황(예: 그 노드에 여유가 없음)에서만 기존처럼 축출 후 재생성으로 대체한다. 
apiVersion: autoscaling.k8s.io/v1
kind: VerticalPodAutoscaler
metadata:
  name: frontend-vpa
spec:
  targetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: frontend
  updatePolicy:
    updateMode: "InPlaceOrRecreate"
참고로 HPA와 VPA를 CPU·메모리 같은 같은 지표로 동시에 쓰면 서로 충돌할 수 있다(VPA가 파드를 키우는 동안 HPA는 그 지표를 보고 파드 수를 줄이려 하는 식) — 함께 쓴다면 지표를 겹치지 않게 나누는 것이 정석이다. 출처: kubernetes.io/blog (In-Place Pod Resize GA 발표, 1.35) · kubernetes.io/docs/concepts/workloads/autoscaling/vertical-pod-autoscale

8.4리소스 관리 모범 사례

원칙왜 / 확인 질문
고가용성이 필요한 워크로드는 안티-어피니티로 영역 분산가용 영역 하나가 죽으면 서비스 전체가 죽지 않는가?
특수 하드웨어(GPU 등)는 테인트로 노드를 예약일반 워크로드가 GPU 노드를 낭비하고 있진 않은가?
노드 조건 이상은 NodeCondition 테인트로 선제 대응장애 징후가 있는 노드에 새 파드가 계속 배치되고 있진 않은가?
다양한 크기의 노드로 실험 후 프로덕션 적용비용·성능의 적정 조합을 데이터로 확인했는가, 감으로 정했는가?
워크로드 특성이 다르면 노드 풀을 분리배치·상시 서비스가 같은 노드 풀에서 서로 자원을 다투고 있진 않은가?
모든 파드에 CPU·메모리 requests·limits 설정BestEffort로 도는 프로덕션 파드가 있진 않은가?
