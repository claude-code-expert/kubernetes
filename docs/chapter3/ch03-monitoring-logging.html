CHAPTER 03

모니터링과 로깅

파드는 계속 생겼다 사라지고 IP는 매번 바뀐다 — 서버에 SSH로 들어가 로그를 보던 방식은 여기서 무너진다. 이 장은 그 대안이다: 메트릭과 로그를 중앙에서 수집하고(프로메테우스·로키), 시각화하고(그라파나), 사람이 움직여야 할 때만 알린다(얼럿매니저). 각 툴의 특징·설치·사용법을 0장 kind 클러스터에서 바로 따라 할 수 있는 튜토리얼로 정리했다.

2026-08 기준 변경 사항 주석 포함 · 실습 명령은 0장 kind 클러스터 기준 검증

핵심 3줄

1. 메트릭 파이프라인은 두 갈래다 — 메트릭 서버(최신값, kubectl top·HPA용)와 프로메테우스(시계열 저장, 분석·알림용). 역할이 달라 둘 다 필요하다.

2. 설치는 헬름 두 방이면 끝난다 — kube-prometheus-stack(프로메테우스+그라파나+얼럿매니저 일괄), 로키+Alloy(로그). 수집기는 Promtail이 아니라 Alloy다(2026-03 Promtail EOL).

3. 모니터링은 USE/RED 패턴으로 "무엇을 볼지"를 먼저 정하고, 알림은 "사람이 지금 행동할 일"만 보낸다 — 나머지는 대시보드와 티켓으로.

3.1메트릭 vs 로그

둘은 대체재가 아니라 짝이다. 메트릭 (Metric)은 일정 주기로 측정한 숫자의 시계열 (Time Series) — 시간 축 위에 찍힌 값의 나열 — 이고, 로그는 특정 순간에 일어난 사건의 기록이다.

메트릭로그
답하는 질문"무엇이, 얼마나, 언제부터 이상한가""왜 그런 일이 일어났는가"
형태숫자 + 레이블 (CPU 사용률 = 0.82)텍스트 이벤트 (요청 처리 중 예외 발생 …)
비용싸다 — 오래 보관 가능비싸다 — 보존 기간을 짧게
쓰임대시보드 · 알림 · 오토스케일링원인 분석 · 감사 추적

실전 순서는 대개 이렇다: 메트릭 알림으로 이상을 감지하고 → 대시보드로 범위를 좁힌 뒤 → 그 시간대 로그로 원인을 확정한다.

3.2모니터링 기법

관찰 위치에 따라 두 기법으로 나뉜다. 블랙박스 모니터링 (Black-box Monitoring)은 시스템 바깥에서 사용자처럼 두드려 보는 방식이다 — "HTTP 200이 오는가", "응답이 3초 안에 오는가". 내부를 몰라도 되고, 사용자가 겪는 증상을 그대로 본다. 화이트박스 모니터링 (White-box Monitoring)은 시스템 내부가 스스로 드러내는 지표를 보는 방식이다 — 큐 길이, 캐시 적중률, GC 시간. 원인 단서를 준다.

쿠버네티스처럼 구성 요소가 수시로 나타났다 사라지는 동적 환경에서는 "서버 A가 죽었는가"식 정적 점검이 무의미해진다. 그래서 이 장의 도구들은 화이트박스 중심으로, 대상을 자동 발견해 지표를 긁어오는 구조를 갖는다.

3.3모니터링 패턴

"무엇을 볼 것인가"에는 검증된 두 공식이 있다. 자원에는 USE, 서비스에는 RED.

패턴풀네임대상보는 것
USEUtilization · Saturation · Errors자원 (노드 CPU, 메모리, 디스크, 네트워크)사용률 / 포화도(대기 큐) / 에러 수
REDRate · Errors · Duration서비스 (API, 마이크로서비스)초당 요청 수 / 실패율 / 응답 시간

이 여섯 지표만 갖춰도 "느려요"라는 신고에 대해 자원 문제인지(USE) 서비스 문제인지(RED)를 몇 분 안에 갈라낼 수 있다. 이후 절의 대시보드·알림 예시도 전부 이 틀 위에 세운다.

3.4쿠버네티스 메트릭 개요

쿠버네티스 메트릭의 뼈대는 세 컴포넌트다. 이름이 비슷해 헷갈리지만 역할이 정확히 갈린다.

3.4.1 cAdvisor

cAdvisor (Container Advisor)는 노드에서 도는 모든 컨테이너의 CPU·메모리·네트워크·파일시스템 사용량을 측정하는 오픈소스 에이전트다. 특징: 따로 설치하지 않는다 — 각 노드의 kubelet(노드 에이전트) 안에 내장되어 항상 돌고 있다. 사용법: 직접 쓰기보다는, 뒤에 나올 메트릭 서버와 프로메테우스가 이것을 데이터 원천으로 삼는다. 모든 컨테이너 사용량 지표의 뿌리라고 기억하면 된다.

3.4.2 메트릭 서버

메트릭 서버 (Metrics Server)는 각 노드의 kubelet에서 사용량을 모아 리소스 메트릭 API로 노출하는 클러스터 애드온이다(과거 이 역할을 하던 힙스터(Heapster)는 사용 중단됐다). 특징: 최신값만 메모리에 유지하고 이력을 저장하지 않는다 — 용도는 오직 kubectl top과 오토스케일러(HPA·VPA, 8장)의 판단 재료다. 모니터링 백엔드로 쓰라고 만든 물건이 아니다.

설치 튜토리얼 (0장 kind 클러스터 기준) — 관리형 클러스터(EKS·GKE·AKS)에는 대개 기본 탑재되어 있지만, kind에는 직접 깐다. kind의 kubelet 인증서는 자체 서명이라 TLS 검증 예외 플래그를 패치해야 동작한다(실습 전용 — 프로덕션 금지).

# 1) 설치
kubectl apply -f https://github.com/kubernetes-sigs/metrics-server/releases/latest/download/components.yaml

# 2) kind용 패치: kubelet 자체 서명 인증서 허용 (실습 전용)
kubectl patch deployment metrics-server -n kube-system --type='json' \
  -p='[{"op": "add", "path": "/spec/template/spec/containers/0/args/-", "value": "--kubelet-insecure-tls"}]'

# 3) 1~2분 뒤 사용
kubectl top nodes
kubectl top pods -A
체크포인트kubectl top nodes가 노드별 CPU(m)·메모리(Mi)를 출력하면 성공. "Metrics API not available"이 나오면 아직 파드가 뜨는 중이다.

3.4.3 kube-state-metrics

kube-state-metrics는 사용량이 아니라 오브젝트 상태를 메트릭으로 바꿔주는 애드온이다 — "디플로이먼트 frontend의 가용 레플리카가 몇 개인가", "CrashLoopBackOff인 파드가 몇 개인가" 같은 것. cAdvisor가 "얼마나 쓰나"라면 이쪽은 "쿠버네티스가 보기에 지금 상태가 어떤가"다. 설치: 단독으로도 깔 수 있지만, 3.7절의 kube-prometheus-stack에 포함되어 함께 설치되므로 보통 따로 만질 일이 없다. 대표 메트릭: kube_deployment_status_replicas_available, kube_pod_status_phase, kube_pod_container_status_restarts_total.

3.5어떤 메트릭을 모니터링하나?

"전부 다"는 답이 아니다 — 잡음이 신호를 묻는다. 계층별로 필수만 고르면 다음과 같다.

계층반드시 볼 것
컨트롤 플레인API 서버 요청 지연·에러율, etcd 지연, 스케줄러 동작
노드CPU·메모리·디스크·네트워크의 USE, 노드 Ready 상태
파드 / 쿠버네티스 상태재시작 횟수, 원하는 레플리카 vs 가용 레플리카 격차, Pending 파드
애플리케이션RED — 요청률, 실패율, 응답 시간(p95·p99)

3.6모니터링 툴

선택지는 크게 "직접 운영하는 오픈소스"와 "돈 내고 맡기는 SaaS"로 갈린다.

툴유형한 줄 특징
프로메테우스오픈소스 (CNCF 졸업)쿠버네티스 모니터링의 사실상 표준. 레이블·서비스 디스커버리와 궁합이 좋다 → 3.7절에서 실습
그라파나오픈소스시각화 표준. 프로메테우스·로키를 한 화면에서 조회
InfluxDB오픈소스/상용범용 시계열 DB. 쿠버네티스 특화는 아님
Datadog · New Relic상용 SaaS에이전트만 깔면 수집·저장·알림을 통째로 대행. 편하지만 데이터량 과금이 커질 수 있음
클라우드 내장 (CloudWatch Container Insights, Azure Monitor, Google Cloud Monitoring)상용해당 클라우드 관리형 클러스터와 통합이 쉬움. 멀티클라우드에선 파편화

스터디와 소규모 팀의 기본값은 프로메테우스 + 그라파나다. 개념(시계열, 레이블, 쿼리)이 다른 모든 도구로 이식되기 때문에 학습 투자 가치도 가장 크다.

3.7프로메테우스를 이용한 쿠버네티스 모니터링

프로메테우스 (Prometheus)는 사운드클라우드에서 시작해 CNCF에서 두 번째로 졸업한 오픈소스 모니터링 시스템이다. 특징 세 가지가 쿠버네티스와의 궁합을 만든다.

  • 풀(pull) 모델 — 앱이 지표를 보내는 게 아니라, 프로메테우스가 각 대상의 /metrics HTTP 엔드포인트를 주기적으로 긁어간다(스크레이프). 대상이 죽으면 긁기가 실패하므로 "죽었다는 사실" 자체가 감지된다.
  • 서비스 디스커버리 — 쿠버네티스 API를 보고 파드·서비스가 생기고 사라지는 것을 자동 추적한다. 동적 환경에서 수집 대상 목록을 손으로 관리하지 않는다.
  • 레이블 기반 시계열 + PromQL (Prometheus Query Language) — 모든 지표가 이름{레이블=값} 형태로 저장되고, 전용 질의 언어로 자르고 집계한다.

설치 튜토리얼 — kube-prometheus-stack

실습 환경 안내 이 실습에는 진짜로 동작하는 쿠버네티스 클러스터가 필요하다 — 그 클러스터를 무엇으로 준비하느냐는 도구 선택의 문제일 뿐 실습 내용에는 영향이 없다. 원서는 이 시점에 brew install minikube로 미니큐브 (minikube)(로컬에 단일 노드 쿠버네티스 클러스터를 띄워 주는 도구)를 새로 설치해 전용 클러스터를 만든다. 이 노트에서는 별도 설치 없이 0장에서 이미 띄워 둔 kind 클러스터를 그대로 사용한다 — kind와 minikube는 "로컬에 진짜 클러스터를 만든다"는 점에서 같은 역할이며(0장 0.1절 비교), 이 스터디는 8장(리소스 관리) 이후의 멀티 노드 실습과 도구를 통일하기 위해 처음부터 kind로 고정했다. minikube로 이미 익숙하다면 brew install minikube && minikube start로 대체해도 아래 helm 명령은 동일하게 동작한다.

프로메테우스·그라파나·얼럿매니저·kube-state-metrics·node-exporter·수백 개의 기본 대시보드와 알림 룰을 헬름 차트 하나로 설치한다. 커뮤니티 표준 방식이다.

# 1) 차트 저장소 등록
helm repo add prometheus-community https://prometheus-community.github.io/helm-charts
helm repo update

# 2) 설치 (릴리스 이름: mon, 네임스페이스: monitoring)
helm install mon prometheus-community/kube-prometheus-stack \
  --namespace monitoring --create-namespace

# 3) 전부 뜰 때까지 확인 (2~3분)
kubectl get pods -n monitoring

사용법 ① — 그라파나 대시보드

# 그라파나 접속 터널 (서비스 이름은 <릴리스명>-grafana)
kubectl port-forward svc/mon-grafana 3000:80 -n monitoring

브라우저에서 http://localhost:3000 — 기본 계정은 admin, 비밀번호는 차트 기본값 prom-operator다(values로 변경 가능). Dashboards 메뉴에 노드·파드·네임스페이스별 대시보드가 이미 수십 개 들어 있다 — USE 지표는 "Node Exporter / Nodes", 쿠버네티스 상태는 "Kubernetes / Compute Resources" 계열을 먼저 보라.

사용법 ② — PromQL 첫 세 문장

# 네임스페이스 default의 파드별 CPU 사용량 (최근 5분 평균, 코어 단위)
sum(rate(container_cpu_usage_seconds_total{namespace="default"}[5m])) by (pod)

# frontend 디플로이먼트의 가용 레플리카 수 (kube-state-metrics 제공)
kube_deployment_status_replicas_available{deployment="frontend"}

# 최근 1시간 컨테이너 재시작 증가량 — 조용한 크래시 루프 탐지
increase(kube_pod_container_status_restarts_total[1h]) > 0

패턴만 기억하면 된다: rate(카운터[구간])으로 증가율을 만들고, sum(...) by (레이블)로 원하는 축으로 접는다. 프로메테우스 UI에서 직접 실험하려면 kubectl port-forward svc/mon-kube-prometheus-stack-prometheus 9090:9090 -n monitoring 후 localhost:9090.

사용법 ③ — 내 앱을 수집 대상에 넣기

스택은 서비스모니터 (ServiceMonitor)라는 커스텀 리소스를 쓴다 — "이 레이블을 가진 서비스의 이 포트를 긁어라"를 선언하면 프로메테우스 설정이 자동 갱신된다. 앱이 /metrics를 노출하고 있다면 아래 선언 하나로 수집이 시작된다.

apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: frontend
  namespace: monitoring
  labels:
    release: mon        # 스택이 이 레이블로 대상을 선별한다
spec:
  namespaceSelector:
    matchNames: ["default"]
  selector:
    matchLabels:
      app: frontend
  endpoints:
  - port: http
    path: /metrics
    interval: 30s

3.8로깅 개요

메트릭이 전체 흐름을 보여준다면, 로그는 사건의 현장이다. 쿠버네티스에서 로깅의 제1원칙: 앱은 파일이 아니라 표준 출력(STDOUT)에 쓴다. 컨테이너 런타임이 그것을 노드의 파일로 받아 적고, 수집기가 노드 단위로 걷어 중앙 저장소로 보낸다. 파드가 죽어도 로그는 남는다.

"전부 다 로깅"도 함정이다 — 저장 비용이 폭증하고 정작 필요한 줄을 못 찾는다. 수집 대상은 앱 로그 + 노드/컨트롤 플레인 로그 + 감사(audit) 로그 정도로 정하고, 보존은 짧게(모범 사례는 30~45일), 그 이상은 저렴한 장기 보관소로 넘긴다.

3.9로깅 툴

수집기는 대부분 데몬셋 (DaemonSet) — 모든 노드에 파드를 정확히 하나씩 깔아주는 워크로드 컨트롤러 — 형태로 돈다. 노드마다 한 명씩 배치된 로그 배달부라고 보면 된다.

스택구성한 줄 특징
로키 스택Alloy(수집) + Loki(저장) + 그라파나(조회)레이블만 인덱싱해 가볍고 저렴. 프로메테우스와 같은 레이블 체계 → 3.10절에서 실습
EFK / ELKFluentd·Fluent Bit(수집) + Elasticsearch(저장) + Kibana(조회)전문(full-text) 인덱싱으로 검색이 강력하지만 자원·운영 비용이 크다
상용 SaaS (Datadog Logs, Sumo Logic 등)에이전트 + 클라우드 저장운영 부담 제로, 데이터량 과금 주의

3.10로키 스택을 사용한 로깅

로키 (Loki)는 그라파나 랩스가 만든 로그 저장소다. 특징: 로그 본문을 통째로 인덱싱하지 않고 레이블만 인덱싱한다 — 그래서 일래스틱서치보다 훨씬 가볍고 싸며, 프로메테우스와 동일한 레이블 체계를 써서 "이 파드의 메트릭"과 "이 파드의 로그"를 같은 그라파나 화면에서 오간다. 스스로 "로그계의 프로메테우스"를 표방한다.

2026-08 기준 갱신 주석 로키의 수집기로 오랫동안 쓰인 Promtail은 은퇴했다 — 2025-02 LTS 전환, 2026-03-02 EOL(업데이트 전면 중단). 후속은 Alloy (Grafana Alloy) — OpenTelemetry Collector 기반으로 로그·메트릭·트레이스를 하나로 수집하는 그라파나의 통합 에이전트다. 기존 Promtail 설정은 alloy convert 명령으로 변환할 수 있다. 검색 상위에 아직 Promtail 튜토리얼이 많으니 따라 하지 말 것. 출처: grafana.com/docs/alloy (공식 문서) · Grafana Labs Promtail LTS/EOL 공지(2025-02-13 LTS, 2026-03-02 EOL) — SUSE·Big Bang 등 벤더 마이그레이션 공지에서 교차 확인

설치 튜토리얼 — Loki + Alloy

# 1) 그라파나 차트 저장소
helm repo add grafana https://grafana.github.io/helm-charts
helm repo update

# 2) Loki 설치 — 실습용 최소 구성(단일 바이너리 모드, 파일 저장)
#    loki-values.yaml 내용은 아래 참고
helm install loki grafana/loki -n logging --create-namespace -f loki-values.yaml

# 3) Alloy 설치 — 데몬셋으로 노드 로그 수집
helm install alloy grafana/alloy -n logging -f alloy-values.yaml
# loki-values.yaml — 실습용 최소 구성 (프로덕션은 오브젝트 스토리지 권장)
deploymentMode: SingleBinary
loki:
  auth_enabled: false
  commonConfig:
    replication_factor: 1
  storage:
    type: filesystem
singleBinary:
  replicas: 1

Alloy의 수집 파이프라인은 "발견 → 수집 → 전송" 컴포넌트를 배선하는 자체 설정 언어로 기술한다. 쿠버네티스 파드 로그를 로키로 보내는 최소 골격은 다음과 같다(values의 alloy.configMap.content에 넣는다).

// alloy 설정 — 파드 발견 → 로그 수집 → 로키 전송
discovery.kubernetes "pods" {
  role = "pod"
}

loki.source.kubernetes "pods" {
  targets    = discovery.kubernetes.pods.targets
  forward_to = [loki.write.default.receiver]
}

loki.write "default" {
  endpoint {
    url = "http://loki:3100/loki/api/v1/push"
  }
}

사용법 — 그라파나에서 LogQL

3.7절 그라파나에 데이터 소스로 Loki(http://loki.logging:3100)를 추가하면 Explore 화면에서 바로 조회할 수 있다. 질의 언어 LogQL (Log Query Language)은 PromQL과 닮았다 — 레이블로 스트림을 고르고, 파이프로 거른다.

# frontend 파드들의 로그 중 "error" 포함 줄만
{namespace="default", pod=~"frontend.*"} |= "error"

# 네임스페이스별 에러 로그 발생률 — 로그를 메트릭처럼 집계
sum(rate({namespace="default"} |= "error" [5m]))
체크포인트0장의 hello 디플로이먼트에 curl을 몇 번 날린 뒤, Explore에서 {namespace="default"}로 nginx 액세스 로그가 보이면 파이프라인 완성.

3.11알림

알림은 양날의 검이다 — 부족하면 장애를 놓치고, 과하면 알림 피로로 사람이 알림 자체를 무시하게 된다. 기준은 하나다: 사람이 지금 즉시 행동해야 하는 것만 호출한다. 스스로 회복되는 일시적 문제(파드 재시작 한 번 등)는 알리지 않거나 티켓으로만 남긴다.

얼럿매니저 (Alertmanager)는 프로메테우스가 발화한 알림을 받아 그룹핑(같은 원인 100건을 1건으로), 중복 제거, 억제(상위 장애가 뜨면 하위 알림 침묵), 심각도별 라우팅을 수행하는 컴포넌트다 — kube-prometheus-stack에 이미 포함되어 있다. 설계 요령:

  • 지속 시간 조건을 걸어 순간 스파이크에 발화하지 않게 한다 — "5분간 지속되면"이 기본기.
  • 알림에는 런북 (Runbook) — 이 알림을 받았을 때 확인·조치 절차를 적은 문서 — 링크를 반드시 붙인다. 새벽 3시의 나는 아무것도 기억하지 못한다.
  • 완벽한 알림 세트는 없다 — 오탐이 잦은 룰은 회고 때마다 조이거나 지운다.
# 알림 룰 예시 — frontend 가용 레플리카가 원하는 수보다 5분 이상 부족
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: frontend-alerts
  namespace: monitoring
  labels:
    release: mon
spec:
  groups:
  - name: frontend
    rules:
    - alert: FrontendReplicasMismatch
      expr: kube_deployment_spec_replicas{deployment="frontend"} != kube_deployment_status_replicas_available{deployment="frontend"}
      for: 5m
      labels:
        severity: warning
      annotations:
        summary: "frontend 가용 레플리카 부족"
        runbook_url: "https://wiki.example.com/runbooks/frontend-replicas"
