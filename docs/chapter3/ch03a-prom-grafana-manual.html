CHAPTER 03 — 부록 A

프로메테우스 · 그라파나 UI 매뉴얼

3장에서 설치한 두 도구를 "화면에서 어떻게 쓰는가" 관점으로 정리한 사용 설명서. 메뉴 하나하나가 무엇이고, 어떤 순서로 눌러 무엇을 확인하는지를 공식 문서 기준으로 담았다. 3.7절(설치)을 마친 상태를 전제로 한다.

기준 버전: 프로메테우스 v3 계열(2024-11 이후 기본 UI) · 그라파나 v12 계열(2025-05 GA) — kube-prometheus-stack 현행 배포 버전과 일치 · 검증일 2026-08-15

핵심 3줄

1. 프로메테우스 UI는 메뉴가 셋뿐이다 — Query(질의 실험), Alerts(알림 상태), Status(수집·서버 상태 점검). 대시보드는 만들지 않는다.

2. 그라파나는 좌측 사이드바가 전부의 입구다 — Dashboards(보기), Explore(질의), Drilldown(클릭 탐색), Alerting(알림), Connections(데이터소스), Administration(관리).

3. 두 도구의 관계: 프로메테우스에서 쿼리를 다듬고, 그라파나에서 그 쿼리를 패널로 고정한다 — "실험실과 전시실".

A.2프로메테우스 — Query 페이지

사용 동선은 네 단계다: 입력 → 실행 → 탭 선택 → 시간 조절.

  1. 입력창 — 타이핑을 시작하면 메트릭 이름·함수·레이블이 자동완성된다. 입력창 옆 메트릭 탐색기 버튼을 누르면 전체 메트릭 목록과 레이블·카디널리티 (Cardinality)(레이블 값 조합의 가짓수 — 많을수록 저장·질의 비용 증가)를 훑어보고 클릭으로 쿼리를 시작할 수 있다. 뭘 쳐야 할지 모를 때 여기부터.
  2. Execute — 실행. Enter로도 된다.
  3. 결과 탭 — Table은 이 순간의 값 목록(레이블 조합별 한 줄), Graph는 시간축 그래프, Explain은 쿼리가 어떤 구조로 평가되는지 해설한다. 복잡한 쿼리는 트리 뷰로 하위 표현식을 펼쳐 부분별 결과를 확인할 수 있다 — PromQL 학습에 특히 유용.
  4. 시간 조절 — 그래프 위 컨트롤에서 조회 범위와 해상도를 바꾸고, 그래프를 드래그하면 그 구간으로 확대된다. Add query panel로 쿼리 패널을 여러 개 쌓아 나란히 비교한다.

익혀 둘 조작 습관 하나: 새 메트릭을 만나면 먼저 메트릭 이름만 실행해 Table 탭에서 레이블 구조부터 본다. 어떤 레이블이 있는지 알아야 sum by (...)로 접을 축이 보인다.

A.3프로메테우스 — Alerts · Status

Alerts 페이지

모든 알림 룰이 세 상태로 표시된다. Inactive(조건 미충족 — 평상시), Pending(조건은 충족했지만 for: 지속 시간을 아직 못 채움), Firing(발화 — 얼럿매니저로 전송됨). 3장에서 만든 PrometheusRule이 목록에 보이면 배선이 된 것이다. 룰 이름을 펼치면 원본 PromQL과 현재 값을 확인할 수 있다.

A.4프로메테우스 — 10분 따라하기

실습 시나리오 — 0장 hello 앱을 프로메테우스에서 추적한다
  1. Status → Targets에서 전체 대상이 UP인지 확인한다. DOWN이 있으면 에러 문구를 읽는다.
  2. Query에서 up을 실행하고 Table 탭으로 대상별 1/0을 본다 — 가장 단순하고 가장 중요한 메트릭.
  3. 메트릭 탐색기에서 kube_deployment를 검색해 kube-state-metrics 계열 지표를 훑는다.
  4. kube_deployment_status_replicas_available{deployment="hello"} 실행 → Graph 탭 → 다른 터미널에서 kubectl scale deployment hello --replicas=4 실행 → 그래프가 계단으로 오르는 것을 관찰한다.
  5. 같은 쿼리를 Explain 탭으로 열어 구조 해설을 읽는다 — PromQL 문법이 눈에 붙기 시작한다.

B.2그라파나 — 대시보드 보기·조작

kube-prometheus-stack이 이미 수십 개의 대시보드를 넣어 두었다. Dashboards에서 "Kubernetes / Compute Resources / Namespace (Pods)"를 열고 아래 조작을 익힌다.

  • 시간 피커(우상단) — 조회 범위 선택. 그 옆 새로고침 버튼으로 자동 갱신 주기(예: 30s)를 켠다. 상황실 모니터에 띄울 때의 기본 설정.
  • 대시보드 변수 (Template Variable) — 상단 드롭다운 줄. 하나의 대시보드를 네임스페이스·노드별로 갈아 끼우는 매개변수다. namespace를 default로 바꾸면 모든 패널이 그 범위로 다시 그려진다.
  • 그래프 드래그 — 구간을 드래그하면 확대되고, 같은 대시보드의 모든 패널이 같은 시간대로 동기화된다. 장애 시각을 좁힐 때의 핵심 조작.
  • 범례 클릭 — 시리즈 이름을 클릭하면 그것만 표시(격리), Ctrl/Cmd+클릭으로 추가·제외.
  • 패널 메뉴(패널 우상단 ⋮) — View(전체 화면), Edit, Explore(이 패널의 쿼리를 Explore로 가져가 실험), Metrics drilldown, New alert rule(이 쿼리 그대로 알림 만들기), Duplicate, Copy.

B.3그라파나 — 패널 편집

패널 (Panel)은 대시보드의 최소 단위다 — 질의 하나(또는 여러 개) + 시각화 하나. 패널 메뉴 → Edit로 들어가면 편집 화면은 세 구역이다.

  1. Query 탭(하단) — 데이터소스를 고르고 질의를 작성한다. 프로메테우스 질의 편집기는 Builder(드롭다운으로 조립)와 Code(PromQL 직접 입력) 두 모드를 오갈 수 있다. A.2에서 다듬은 쿼리를 Code 모드에 붙여 넣는 흐름이 실전 표준.
  2. Transform 탭 — 질의 결과를 시각화 전에 가공(정렬, 계산 필드, 조인 등). 쿼리로 안 되는 마지막 정리를 여기서.
  3. 우측 옵션 패널 — 시각화 유형(Time series, Stat, Gauge, Table, Bar 등)을 고르고, 단위(Unit)·소수점·범례·Thresholds(임계값별 색 — 예: 80% 이상 빨강)를 설정한다. 색은 장식이 아니라 임계값 의미 전달에만 쓰는 것이 좋은 대시보드의 관례다.

수정 후 우상단 Save dashboard를 눌러야 저장된다 — 내장 대시보드를 고칠 때는 사본(Save as copy)으로 저장하는 습관을 들이자. 원본은 차트 업그레이드 때 되돌아간다.

B.4그라파나 — 대시보드 가져오기

커뮤니티가 만든 대시보드를 ID 하나로 가져올 수 있다. 공개 저장소는 grafana.com/grafana/dashboards — 예를 들어 노드 지표의 사실상 표준인 "Node Exporter Full"(ID 1860)이 널리 쓰인다.

  1. Dashboards → New → Import
  2. ID 입력(예: 1860) 후 Load — 또는 JSON 파일 업로드
  3. 데이터소스 매핑에서 Prometheus를 지정하고 Import

팀 대시보드를 공유할 때도 같은 원리다 — 대시보드 설정(Export)에서 JSON을 내보내 Git에 두고, 받는 쪽은 Import 한다. v12부터는 Git Sync로 이 과정을 자동화할 수도 있다.

B.5그라파나 — Explore와 Drilldown

Explore — 자유 질의

대시보드를 만들 필요 없이 데이터소스에 직접 묻는 화면이다. 상단에서 데이터소스(Prometheus 또는 Loki)를 고르고 질의를 실행한다. Split 버튼으로 화면을 좌우로 갈라 "왼쪽엔 메트릭, 오른쪽엔 같은 시간대 로그"를 나란히 놓는 것이 장애 분석의 정석 동선이다. 질의 히스토리가 자동 저장되어 어제 쓴 쿼리를 다시 꺼낼 수 있다.

Drilldown — 쿼리 없는 탐색

Drilldown은 PromQL·LogQL을 몰라도 데이터를 탐색하게 해주는 v12의 정식 메뉴다(구 명칭 Explore Apps). Metrics는 메트릭 목록을 미리 그린 그래프 타일로 보여주고 레이블 필터를 클릭으로 좁혀 간다. Logs는 서비스별 로그 볼륨과 패턴을 보여주며 클릭으로 파고든다. 신규 팀원 온보딩과 "쿼리가 막힌" 순간의 우회로로 좋다 — 각 화면에서 Explore로 건너가는 링크가 있어, 클릭으로 좁힌 결과의 실제 쿼리를 열어 학습할 수도 있다.

B.6그라파나 — 데이터소스 · Alerting · 관리

Connections → Data sources

데이터소스 (Data Source)는 그라파나가 질의할 저장소 연결 정보다. kube-prometheus-stack은 Prometheus와 Alertmanager를 자동 등록해 준다. 3.10절의 Loki를 붙이려면: Connections → Data sources → Add new data source → Loki 선택 → URL에 http://loki.logging:3100 입력(같은 클러스터의 서비스 DNS) → Save & test. 초록 체크가 뜨면 Explore·Drilldown에서 Loki를 선택할 수 있다.

Alerting

알림 룰의 관리 주체는 두 갈래다 — 3장의 PrometheusRule처럼 데이터소스(프로메테우스) 쪽에서 관리되는 룰과, 그라파나 자체가 평가하는 Grafana-managed 룰. 후자는 패널 메뉴의 New alert rule로 그 쿼리 그대로 만들 수 있어 진입이 쉽다. 스터디에서는 3장 방식(코드로 관리되는 PrometheusRule)을 기본으로 두고, Alerting 메뉴는 발화 현황·무음(silence) 확인 용도로 쓰는 정리를 권한다 — 알림 정의가 두 곳에 흩어지면 "이 알림 어디서 왔지"가 사고의 시작이 된다.

Administration

사용자·팀·권한(폴더 단위로 대시보드 접근 제어), 플러그인 설치, 기본 테마·홈 대시보드 설정이 모여 있다. 스터디 공용 인스턴스라면 기본 admin 비밀번호부터 바꾸는 것이 첫 관리 작업이다.

B.7그라파나 — 15분 따라하기

실습 시나리오 — 쿼리 하나를 "실험 → 패널 → 알림"까지 끌고 간다
  1. Explore에서 Prometheus 선택, Code 모드로 sum(rate(container_cpu_usage_seconds_total{namespace="default"}[5m])) by (pod) 실행.
  2. Split을 눌러 오른쪽에 Loki 선택, {namespace="default"} 실행 — 메트릭과 로그를 같은 시간축에서 본다.
  3. Dashboards → New → New dashboard → Add visualization → Prometheus 선택 → 1번 쿼리 붙여넣기 → 시각화 Time series, Unit은 CPU 코어로 설정 → Save.
  4. 만든 패널의 ⋮ → New alert rule — 쿼리가 미리 채워진 알림 편집기가 열리는 것 확인(만들지 않고 나가도 좋다 — 알림 정의는 3장 PrometheusRule 방식이 기본).
  5. Drilldown → Metrics를 열어 같은 결론에 클릭만으로 도달해 본다 — 두 경로의 차이를 체감하는 것이 목적.
