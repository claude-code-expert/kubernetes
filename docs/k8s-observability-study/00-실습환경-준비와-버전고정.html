01최종적으로 만들 것

실습 전체가 노트북 한 대 안에서 끝납니다. 클라우드 계정도, 별도 VM도 필요 없습니다. 도커 컨테이너 3개가 쿠버네티스 노드 역할을 하고, 그 안에서 애플리케이션과 관측 스택이 함께 돕니다.

논리 구조는 네임스페이스 세 개로 나뉩니다. 여기서 중요한 것은 상자의 위치가 아니라 화살표의 방향입니다. 메트릭은 프로메테우스가 가져가고(pull), 로그는 수집기가 밀어 넣습니다(push). 이 비대칭이 뒤 문서 전체의 설정 차이를 만듭니다.

왜 pull 방식인가

수집 대상이 살아있는지를 수집기가 직접 확인할 수 있기 때문입니다. 스크레이프에 실패하면 up == 0 이라는 메트릭이 자동으로 남습니다. push 방식이라면 "메트릭이 안 오는 것"과 "앱이 죽은 것"을 구분할 수 없습니다.

07사전 점검 스크립트

다음 스크립트를 preflight.sh로 저장하고 실행하세요. 실습 첫 모임에서 8명이 각자 돌려 결과를 공유하면, 진도가 어긋나는 원인의 대부분을 미리 걷어냅니다. 

#!/usr/bin/env bash
# preflight.sh — 관측성 실습 사전 점검 (2026-08 기준)
set -u

report() {
  # $1=도구명  $2=권장버전  $3=탐지된 버전
  if [ -z "$3" ]; then
    printf '%-10s %-24s %s\n' "$1" "MISSING" "설치 필요 (권장 $2)"
    return 1
  fi
  printf '%-10s %-24s %s\n' "$1" "$3" "(권장 $2)"
  return 0
}

fail=0
echo "=== 도구 버전 ==="
report docker  "24.0+"   "$(docker version --format '{{.Server.Version}}' 2>/dev/null)" || fail=1
report kubectl "v1.36.x" "$(kubectl version --client -o yaml 2>/dev/null | awk '/gitVersion/{print $2; exit}')" || fail=1
report kind    "v0.32.0" "$(kind version 2>/dev/null | awk '{print $2}')" || fail=1
report helm    "v3.16+"  "$(helm version --short 2>/dev/null)" || fail=1
report java    "21"      "$(java -version 2>&1 | awk -F'"' '/version/{print $2; exit}')" || fail=1

echo
echo "=== 도커 자원 ==="
dk="$(docker info --format '{{.NCPU}} {{.MemTotal}}' 2>/dev/null || true)"
if [ -n "$dk" ]; then
  echo "$dk" | awk '{printf "CPU %s코어 / MEM %.1f GiB\n", $1, $2/1073741824}'
else
  echo "도커 데몬에 접속할 수 없습니다"
  fail=1
fi

echo
echo "=== cgroup 버전 (cgroup2fs 여야 정상) ==="
if [ "$(uname -s)" = "Linux" ]; then
  stat -fc %T /sys/fs/cgroup/
else
  docker run --rm alpine stat -fc %T /sys/fs/cgroup/ 2>/dev/null || echo "확인 불가"
fi

echo
if [ "$fail" -eq 0 ]; then
  echo "결과: 통과 — 01단계로 진행하세요"
else
  echo "결과: 미충족 항목 있음 — 06절 설치 절차를 확인하세요"
fi
exit "$fail"
chmod +x preflight.sh
./preflight.sh

kubectl    v1.36.1                  (권장 v1.36.x)
kind       v0.32.0                  (권장 v0.32.0)
helm       v3.16.4+g7877b45         (권장 v3.16+)
java       21.0.7                   (권장 21)

=== 도커 자원 ===
CPU 6코어 / MEM 10.0 GiB

=== cgroup 버전 (cgroup2fs 여야 정상) ===
cgroup2fs

결과: 통과 — 01단계로 진행하세요
버전이 정확히 일치하지 않아도 되는 경우

kubectl은 API 서버와 마이너 버전 차이가 ±1까지 허용됩니다. 1.35나 1.37이어도 1.36 클러스터에는 문제없이 붙습니다. 반면 kind와 노드 이미지는 조합이 어긋나면 kind load가 실패하므로 정확히 맞춰야 합니다.

08지금 알아야 할 함정 3가지

이 세 가지는 검색으로 나오는 튜토리얼 대부분이 아직 반영하지 못한 변경점입니다. 04·08단계에서 실제로 부딪히기 전에 머리에 넣어두세요.

1. 헬름 저장소 이전 — grafana → grafana-community

2026-03-16부로 로키 헬름 차트가 커뮤니티 저장소로 포크됐습니다. 기존 grafana/loki 경로로 설치하면 상용 제품(GEL) 대상 차트를 받거나 아예 못 찾습니다. kube-prometheus-stack의 그라파나 서브차트도 이미 새 저장소를 참조합니다.

2. Promtail은 EOL — 로그 수집기는 Alloy

Promtail은 2026-03-02에 수명을 다했습니다. 책과 대부분의 블로그가 Promtail 기준으로 쓰여 있으니 08단계에서 설정 파일을 그대로 복사하지 마세요. 형식 자체가 다릅니다.

3. Spring Cloud Gateway의 프로퍼티 접두사 변경

spring.cloud.gateway.routes 로 시작하는 예제는 이제 동작하지 않거나 경고를 냅니다. 현재 형태는 spring.cloud.gateway.server.webflux.routes 입니다. X-Forwarded-* 헤더 처리도 기본 비활성이라, 게이트웨이 뒤에서 클라이언트 IP를 봐야 한다면 trusted-proxies를 정규식으로 지정해야 합니다.

보안 메모 — 02단계에서 다시 다룸

게이트웨이에서 액추에이터 gateway 엔드포인트를 무인증으로 노출하면 런타임 라우트 조작 및 환경 프로퍼티 노출로 이어지는 취약점(CVE-2025-41243, CVE-2025-41253) 조건에 해당합니다. 실습이라도 management.endpoints.web.exposure.include 는 health,info,prometheus 정도로 제한합니다.

09자원 예산 계산

단계가 올라갈수록 메모리를 먹습니다. 아래는 기본 설정 기준의 대략치입니다.

단계까지 완료 시메모리 사용(대략)주 구성요소
01 — 빈 클러스터1.5 GiB노드 3개 + 컨트롤 플레인
03 — 앱 배포2.5 GiB+ gateway, order-api (각 512 MiB 상한)
05 — 관측 스택5–6 GiB+ Prometheus, Grafana, Alertmanager, exporter류
08 — 로그까지7–8 GiB+ Loki, Alloy, MinIO

도커에 10 GiB를 주고 시작하면 08단계까지 여유가 있습니다. 부족할 때 가장 먼저 줄일 것은 프로메테우스 보존 기간(retention)과 워커 노드 수입니다. 대시보드나 익스포터를 빼면 실습 자체가 성립하지 않습니다.

10완료 체크리스트

  • ./preflight.sh 가 "통과"로 끝난다
  • 도커에 CPU 4코어 이상, 메모리 10 GiB 이상이 할당돼 있다
  • cgroup 확인 결과가 cgroup2fs 다
  • helm repo list 에 prometheus-community 와 grafana-community 가 모두 보인다
  • 팀에서 사용할 kube-prometheus-stack 차트 버전을 하나로 정해 공유했다
  • 그림 2의 화살표 방향(메트릭 pull / 로그 push)을 설명할 수 있다
