CHAPTER 13

외부 서비스와 쿠버네티스 통합

현실의 클러스터는 섬이 아니다 — 레거시 DB, 온프레미스 시스템, 다른 팀의 클러스터와 늘 맞닿아 있다. 이 장은 그 경계를 넘는 법이다. 외부의 무언가를 클러스터 안으로 자연스럽게 끌어들이거나(임포트), 클러스터 안의 서비스를 밖에서 쓸 수 있게 내보내는(익스포트) 패턴, 그리고 그 둘을 조합해 클러스터끼리 서비스를 공유하는 법까지.

2026-08 기준 변경 사항 주석 포함

핵심 3줄

1. 외부 서비스를 끌어들이는 방법은 안정성에 따라 셋이다 — IP가 고정이면 셀렉터리스 서비스, DNS 이름이 있으면 CNAME, 아무것도 안정적이지 않으면 직접 짠 컨트롤러.

2. 내보내는 방법은 정확히 그 반대편이다 — 클라우드면 내부 로드밸런서, 온프레미스면 NodePort, 그걸로도 부족하면 외부 레지스트리와 긴밀 통합.

3. 클러스터 간 서비스 공유는 이 두 패턴의 조합이었지만, 지금은 Multi-Cluster Services API라는 표준으로 정식화되고 있다.

13.1쿠버네티스로 서비스 임포트

클러스터 밖의 무언가(레거시 DB가 흔한 예)를 클러스터 안의 파드가 마치 내부 서비스처럼 부르게 만들고 싶다. 방법은 외부 리소스가 얼마나 안정적인가에 따라 셋으로 갈린다.

13.1.1 셀렉터리스 서비스로 안정적인 IP 주소 사용

가장 단순한 방법이다. 셀렉터리스 서비스 (Selector-less Service)는 셀렉터가 없는 Service — 애초에 매치될 파드가 없으니 로드밸런싱도 일어나지 않는다. 대신 이 서비스가 가리킬 주소를 직접 지정해 준다.

apiVersion: v1
kind: Service
metadata:
  name: my-external-database
spec:
  ports:
  - protocol: TCP
    port: 3306
    targetPort: 3306

서비스를 만들었다면, 실제로 어디를 가리킬지 엔드포인트를 채워야 한다.

2026-08 기준 갱신 주석 원서는 이 자리에 Endpoints(v1) 오브젝트를 직접 만드는 예제를 쓴다 — 지금도 동작은 하지만, 쿠버네티스 공식 문서가 권장하는 현재 방식은 EndpointSlice (discovery.k8s.io/v1)를 직접 만드는 것이다. 여러 서비스의 엔드포인트가 몰려도 확장성 있게 관리되도록 설계된 API라, 신규로 짠다면 이쪽을 쓴다. 
apiVersion: discovery.k8s.io/v1
kind: EndpointSlice
metadata:
  name: my-external-database-1
  labels:
    kubernetes.io/service-name: my-external-database  # 서비스 이름과 일치해야 함
addressType: IPv4
ports:
- name: mysql
  protocol: TCP
  port: 3306
endpoints:
- addresses:
  - "24.1.2.3"
출처: kubernetes.io/docs/concepts/services-networking/service(Service Without Selector, EndpointSlice 수동 생성 예제)

파드가 my-external-database를 조회하면 클러스터 DNS 서버가 이 주소로 응답한다 — 개발자 입장에서는 자신이 클러스터 밖을 호출하고 있다는 사실조차 모른다.

13.1.2 CNAME 기반 서비스로 안정적인 DNS 네임 사용

외부 리소스의 IP는 바뀌어도 DNS 이름은 고정인 경우가 많다(클라우드 관리형 DB가 전형적이다). 이럴 땐 셀렉터리스 서비스 대신 ExternalName 타입을 쓴다.

apiVersion: v1
kind: Service
metadata:
  name: my-external-database
spec:
  type: ExternalName
  externalName: db.vendor.com

이 서비스를 조회하면 프록시나 IP 변환 없이 그냥 CNAME을 돌려준다 — 9장에서 이미 다룬 그 타입이다.

13.1.3 액티브 컨트롤러 방식

IP도 DNS 이름도 안정적이지 않은 제약 많은 환경이라면, 앞의 두 방법 다 못 쓴다. 이럴 때 쓰는 것이 제어 루프다 — 외부 인프라를 동적으로 조회해 최신 주소를 알아내고, 그 값으로 서비스의 엔드포인트를 계속 채워 넣는 컨트롤러를 직접 만든다. 원리는 쿠버네티스 컨트롤러 매니저가 평소 하는 일(셀렉터로 파드를 찾아 엔드포인트를 채우는 것)과 같다 — 다만 그 대상이 클러스터 밖에 있을 뿐이다.

13.2쿠버네티스에서 서비스 익스포트

반대 방향이다 — 클러스터 안의 서비스를 클러스터 밖에서 쓸 수 있게 내보낸다. 사내 CRM이 쿠버네티스 안의 고객 관리 서비스를 불러야 하는 상황이 전형적인 예다.

13.2.1 내부 로드 밸런서로 서비스 익스포트

클라우드 환경이라면 가장 쉽다. 이미 익숙한 Service 오브젝트에 클라우드별 애너테이션 한 줄만 추가하면, 인터넷이 아니라 내부 네트워크에서만 닿는 로드밸런서가 만들어진다.

13.2.2 NodePort로 서비스 익스포트

온프레미스처럼 내부 로드밸런서 자체가 없는 환경에서는 9장에서 배운 NodePort가 대안이다 — 모든 노드의 고정 포트로 외부에서 접근한다.

13.2.3 외부 서버와 쿠버네티스 통합

내부 로드밸런서나 NodePort로도 부족한 경우가 있다 — 다이내믹 서비스 디스커버리가 필요할 만큼 긴밀한 통합이 필요할 때다. 이때는 Consul 같은 외부 서비스 레지스트리와 양방향으로 동기화하는 최후의 방법을 쓴다.

13.3쿠버네티스 간 서비스 공유

클러스터 A의 서비스를 클러스터 B가 부르게 하려면? 13.1·13.2절의 패턴을 조합하면 된다 — 먼저 클러스터 A에서 내부 로드밸런서로 서비스를 익스포트(13.2.1)하고, 그 가상 IP를 클러스터 B에서 셀렉터리스 서비스로 임포트(13.1.1)한다. 두 단계로 서비스 디스커버리가 완성된다.

다만 이건 정적인 수작업이다. 서비스가 자주 뜨고 사라지는 환경이라면, 특정 애너테이션(예: myco.com/exported-service)이 붙은 서비스를 감시하다가 자동으로 다른 클러스터에 셀렉터리스 서비스로 임포트해 주는 데몬을 양쪽 클러스터에 각각 띄우는 편이 낫다 — 더 이상 익스포트되지 않는 서비스를 가비지 컬렉션하는 것도 이 데몬의 몫이다.

2026-08 기준 갱신 주석 원서는 이 절 끝에 "멀티클러스터 서비스 API가 아직 실험 단계"라고 적어 뒀다 — 그 이후의 진행 상황이다. MCS API (Multi-Cluster Services API)는 KEP-1645로 표준화가 진행 중이며(API 자체는 아직 alpha/beta 단계), ServiceExport(공유하겠다는 선언)와 ServiceImport(다른 클러스터에서의 표현)라는 두 CRD로 정확히 위 문단에서 설명한 "감시 데몬" 패턴을 표준화했다. 직접 데몬을 짤 필요 없이, Submariner나 Cilium Cluster Mesh 같은 구현체가 이 API를 지원한다 — CNI가 네트워킹의 구현체 자유를 주듯, MCS API도 표준만 정의하고 실제 연결은 구현체에 맡기는 같은 패턴이다. 출처: multicluster.sigs.k8s.io(공식 개념 문서) · kubernetes-sigs/mcs-api(GitHub, API 버전 현황) · docs.cilium.io(Cluster Mesh MCS API 구현)

13.4서드파티 툴

서비스 메시(9장에서 이미 깊이 다뤘다)를 경험해 봤다면 임포트·익스포트 개념이 낯설지 않을 것이다 — 메시는 이 문제를 데이터 플레인 수준에서 통째로 해결하려는 시도다. 이 장의 수작업 패턴들은 메시 없이도 같은 문제를 푸는 저수준 도구들이라고 보면 된다 — 클러스터 규모가 작거나 메시 도입 비용(9.7절)이 부담스러울 때 특히 유용하다.
