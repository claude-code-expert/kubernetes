CHAPTER 05

지속적 통합, 테스팅, 배포

코드 한 줄이 커밋되고 나서 사용자 화면에 반영되기까지, 그 사이에 있어야 할 모든 자동화 단계를 다루는 장. 버전 관리에서 시작해 빌드·테스트·이미지화·배포 전략·프로덕션 검증까지 한 파이프라인으로 잇고, 마지막엔 0장 kind 클러스터에서 그 파이프라인의 핵심 동작을 직접 손으로 재현한다.

2026-08 기준 변경 사항 주석 포함 · 실습 명령은 0장 kind 클러스터 기준

핵심 3줄

1. CI는 "작은 변경을 자주 통합해 즉시 검증"하는 것이고, CD는 "검증된 변경을 사람 개입 없이 승격"하는 것 — 목적이 다르니 같은 파이프라인 안에서도 역할을 섞지 않는다.

2. 배포 전략은 롤링(기본, 트래픽 제어 없음) → 블루/그린(즉시 전환) → 카나리(점진적 검증) 순으로 안전해지지만 그만큼 구성이 복잡해진다.

3. 이미지는 불변 태그로 고정하고 서명한다 — 2026년 현재 SBOM·이미지 서명은 선택이 아니라 규제 요건이 된 지역이 있다.

5.1버전 관리

모든 CI/CD 파이프라인의 출발점은 배포가 아니라 버전 관리 (Version Control) — 코드와 구성의 변경 이력을 추적하는 체계다. 지금은 Git이 사실상 유일한 표준이다.

핵심 관례 하나만 기억한다: main 브랜치는 항상 프로덕션에 배포 가능한 상태여야 한다. 기능 개발은 별도 브랜치에서 하고, main에 합쳐지는 순간 그 코드는 "배포 후보"가 된다. 브랜치 전략(Git Flow처럼 복잡한 것부터 Trunk-Based Development처럼 단순한 것까지)은 팀마다 다르지만, "main은 항상 정상"이라는 원칙만은 CI/CD 전체가 이 위에 서 있다.

5.2지속적 통합

CI (Continuous Integration)는 코드 변경분을 리포지터리에 계속 통합하는 프로세스다. 핵심은 "크게 가끔"이 아니라 "작게 자주"다 — 변경이 작을수록 무엇이 무엇을 망가뜨렸는지 바로 드러난다. main에 커밋(또는 PR)이 올라가는 순간 빌드가 자동으로 시작되고, 실패하면 그 자리에서 개발자에게 알린다.

실무에서 CI 서버가 하는 일은 네 가지로 좁혀진다: ① 소스를 체크아웃하고 ② 빌드하고 ③ 테스트를 돌리고 ④ 통과하면 배포 가능한 산출물(대개 컨테이너 이미지)을 만든다. 이 네 단계가 실패 없이 몇 분 안에 끝나는 것이 좋은 CI의 정의다.

5.3테스팅

파이프라인에 테스트를 넣는 목적은 하나다 — 빌드를 망친 변경분을 최대한 빨리 알아내는 것. 언어마다 프레임워크는 다르지만(Go는 go test, JS는 Jest, Python은 pytest…) 파이프라인 안에서의 위치는 같다: 빌드 직후, 이미지화 이전.

테스트는 계층으로 쌓인다 — 테스트 피라미드 (Test Pyramid)가 그 기준이다. 아래로 갈수록 많이, 빠르게, 격리해서 돌리고, 위로 갈수록 적게, 느리게, 통합해서 돌린다.

계층범위속도 · 개수
단위 테스트함수·클래스 하나, 의존성은 모킹초 단위 · 수백~수천 개
통합 테스트DB·인접 서비스 등 실제 의존성 포함분 단위 · 수십 개
E2E 테스트사용자 시나리오 전체(브라우저·API 흐름)수 분~수십 분 · 소수

피라미드가 뒤집혀 E2E만 잔뜩 있으면 파이프라인이 느려지고 실패 원인 추적도 어려워진다. "이 결함을 잡는 가장 값싼 계층이 무엇인가"를 항상 먼저 묻는다.

5.4컨테이너 빌드

테스트를 통과한 코드는 컨테이너 이미지로 굳혀진다. 여기서 최적화 목표는 이미지 크기다 — 작을수록 가져오고 배포하는 시간이 줄고, 담긴 패키지가 적을수록 취약점 표면도 준다.

표준 기법은 멀티스테이지 빌드 (Multi-stage Build) — 빌드에 필요한 컴파일러·도구는 첫 스테이지에서만 쓰고, 최종 이미지에는 실행에 필요한 산출물만 옮겨 담는 Dockerfile 패턴이다.

# 멀티스테이지 빌드 예시 — Node.js 앱
FROM node:20 AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM node:20-slim
WORKDIR /app
COPY --from=build /app/dist ./dist
COPY --from=build /app/node_modules ./node_modules
CMD ["node", "dist/server.js"]

더 밀어붙이면 distroless (Distroless Image) — 셸도 패키지 매니저도 없이 애플리케이션 실행에 꼭 필요한 파일만 담은 베이스 이미지 — 까지 간다. 공격 표면이 극단적으로 줄지만, 2장에서 다뤘듯 kubectl exec으로 셸에 들어갈 수 없으니 디버깅은 임시 컨테이너(kubectl debug)로 해야 한다.

5.5컨테이너 이미지 태깅

1장에서 이미 강조한 원칙이 여기서 파이프라인 규칙으로 굳는다 — latest 금지, 불변 태그 사용. CI가 자동으로 커밋 해시나 빌드 번호를 태그에 새기게 하면 사람이 실수로 애매한 태그를 붙일 일이 없어진다.

# CI에서 흔한 태깅 패턴 — 커밋 해시 + 시맨틱 버전
IMAGE_TAG="v1.4.2-$(git rev-parse --short HEAD)"
docker build -t myrepo/journal-frontend:${IMAGE_TAG} .
docker push myrepo/journal-frontend:${IMAGE_TAG}
2026-08 기준 갱신 주석 태그보다 더 신뢰할 수 있는 식별자가 있다 — 다이제스트 (Digest)(이미지 내용의 SHA256 해시). 태그는 누군가 실수로 덮어쓸 수 있지만 다이제스트는 내용이 1비트만 바뀌어도 값이 달라진다. 여기에 더해 2026년 현재 SBOM(소프트웨어 구성 명세)과 이미지 서명이 사실상 의무가 됐다 — 미국 행정명령(EO 14028), EU 사이버 복원력법(CRA)이 공급망 투명성을 요구하면서다. 표준 도구 조합은 Syft(SBOM 생성) + Cosign(Sigstore 프로젝트의 이미지 서명 도구) + Rekor(서명 투명성 로그)이며, Kyverno·OPA Gatekeeper 같은 어드미션 컨트롤러(17장)로 "서명 안 된 이미지는 배포 자체를 차단"까지 엮는 것이 현재 표준 파이프라인이다. 
# cosign 키리스 서명 예시 (CI의 OIDC 신원으로 서명, 개인키 보관 불필요)
cosign sign myrepo/journal-frontend@sha256:abcd1234...
출처: sigstore.dev(Cosign·Rekor) · 미국 행정명령 14028, EU Cyber Resilience Act(SBOM 의무화 배경)

5.6지속적 배포

CD (Continuous Deployment / Delivery)는 CI를 통과한 이미지를 사람 개입 없이 프로덕션까지 매끄럽게 승격시키는 기술이다. 컨테이너가 강점을 발휘하는 지점이기도 하다 — 개발에서 검증한 바로 그 이미지(다이제스트까지 동일한)가 스테이징을 거쳐 프로덕션까지 그대로 올라간다. "프로덕션에서만 재현되는 버그"의 상당수는 환경마다 다시 빌드하던 시절의 유산이다.

승격은 보통 환경을 계단으로 오른다 — dev(모든 커밋 자동 배포) → staging(사람 또는 자동 게이트 통과) → production(추가 승인 또는 자동 카나리 분석 통과). 18장에서 다룰 깃옵스는 이 승격 자체를 "Git의 브랜치·태그 상태 = 클러스터 상태"로 선언해 CD를 완전히 자동화하는 접근이다.

5.7배포 전략

이미지를 새 버전으로 바꾸는 방법은 하나가 아니다. 실패했을 때 "얼마나 적은 사용자가 영향을 받는가"를 기준으로 세 전략을 비교한다.

  • 롤링 업데이트 — 쿠버네티스 Deployment의 기본 동작. 설정 없이 kubectl set image 한 줄로 시작된다. 단점은 트래픽 제어가 없다는 것 — 새 파드가 Ready 되는 즉시 실제 트래픽을 받는다.
  • 블루/그린 — 새 버전 전체를 별도로 다 띄운 뒤, Service 셀렉터를 한 번에 전환한다. 전환·롤백이 즉시다. 대신 전환 순간 두 배의 리소스가 필요하다.
  • 카나리 — 새 버전에 트래픽의 일부(예: 10%)만 먼저 보내고, 지표가 정상이면 비율을 단계적으로 올린다. 가장 안전하지만 트래픽을 퍼센트 단위로 쪼개는 것 자체가 쿠버네티스 기본 리소스만으로는 안 된다.
2026-08 기준 갱신 주석 카나리·블루/그린을 "직접 구현"하던 시절은 지났다. 현재 표준은 Argo Rollouts 또는 Flagger다 — 둘 다 Deployment를 대체하는 CRD(Rollout 등)로 트래픽 비율 조정, 프로메테우스 지표 기반 자동 분석·승격·롤백을 제공하는 프로그레시브 딜리버리 컨트롤러다. Argo Rollouts는 ArgoCD와, Flagger는 FluxCD와 궁합이 좋아 18장의 깃옵스 도구 선택과 맞물린다 — 단계별 수동 승인이 필요하면 Argo Rollouts, 지표 기반 완전 자동 승격을 원하면 Flagger가 흔한 선택 기준이다. 출처: argo-rollouts.readthedocs.io(개념·전략 정의) · flagger 공식 문서

5.8프로덕션 테스팅

스테이징이 아무리 정교해도 프로덕션과 완전히 같을 수 없다 — 실제 트래픽 패턴, 실제 데이터 규모, 실제 사용자 행동은 프로덕션에만 있다. 프로덕션 테스팅 (Testing in Production)은 이 간극을 인정하고, 블라스트 반경(영향 범위)을 통제된 상태로 유지하며 실환경에서 검증하는 접근이다.

5.7절의 카나리가 이미 프로덕션 테스팅의 한 형태다. 여기에 더해 기능 플래그(코드는 배포하되 스위치로 노출 통제), 섀도우 트래픽(실 요청을 복제해 새 버전에도 흘려보내되 응답은 버림)이 흔히 쓰인다. 이 장의 마지막 절인 5.9.4의 카오스 실험도 넓게 보면 프로덕션 테스팅의 일종이다 — "장애가 나면 시스템이 정말 회복하는가"를 실제로 확인하는 것.

5.9파이프라인 구축과 카오스 실험

지금까지의 개념을 0장 kind 클러스터에서 손으로 재현한다. 실제 CI 서버 없이도 파이프라인의 핵심 동작(빌드 → 반입 → 롤아웃 → 관찰)은 로컬에서 완전히 재현할 수 있다.

5.9.1 CI 구축

실습 환경 안내 원서는 이 실습에 Drone이라는 CI 서비스를 쓴다. Drone은 2026년 현재도 존재하지만(Harness에 인수된 뒤 커뮤니티 에디션으로 유지) 개발 속도가 느려졌고, 상당수 사용자가 GitHub Actions, GitLab CI, 또는 Drone의 커뮤니티 포크인 Woodpecker CI로 옮겨갔다. 이 노트에서는 가장 널리 쓰이는 GitHub Actions로 CI 설정 파일의 구조만 익히고, 실제 실행은 로컬 kind로 대체한다(클라우드 CI 러너는 로컬 클러스터에 네트워크로 닿지 않으므로, 원격 CI와 로컬 클러스터를 직접 연결하는 것 자체가 실습 범위 밖이다). 
# .github/workflows/ci.yaml — 구조 학습용 (이 저장소에서 실행할 필요는 없다)
name: CI
on:
  push:
    branches: [main]
jobs:
  build-test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Run tests
        run: npm test
      - name: Build image
        run: docker build -t journal-frontend:${{ github.sha }} .

구조를 눈에 익혔다면 아래부터는 같은 단계를 로컬에서 직접 실행한다.

5.9.2 CD 구축

원서는 이 단계에서 클러스터로 이미지를 밀어 넣는 CD 플러그인을 쓴다. kind 클러스터에는 레지스트리가 없어도 kind load docker-image로 로컬에 빌드한 이미지를 노드에 직접 반입할 수 있다 — 실습 목적에는 이쪽이 더 간단하고 원리도 그대로 드러난다.

# ① 코드 한 줄을 바꿨다고 가정하고 새 이미지를 빌드
docker build -t journal-frontend:v2 .

# ② 레지스트리 없이 kind 클러스터 노드로 직접 반입
kind load docker-image journal-frontend:v2 --name study

# ③ 디플로이먼트가 새 이미지를 쓰도록 갱신 — 이것이 CD의 핵심 동작이다
kubectl set image deployment/frontend frontend=journal-frontend:v2

5.9.3 롤링 업그레이드 수행

①~③을 실행한 직후 롤아웃을 관찰한다. 0장에서 이미 "파드를 지우면 되살아난다"를 봤다면, 이번엔 "이미지가 바뀌면 무슨 일이 일어나는가"를 본다.

# 진행 상황 실시간 관찰 — 완료될 때까지 대기
kubectl rollout status deployment/frontend

# 방금 일어난 일의 이력
kubectl rollout history deployment/frontend

# 문제가 있었다면 직전 버전으로 즉시 되돌리기
kubectl rollout undo deployment/frontend
체크포인트rollout status가 "successfully rolled out"으로 끝나고, kubectl get pods -o jsonpath='{.items[*].spec.containers[*].image}'로 전체 파드의 이미지가 v2로 바뀐 것을 확인했다면 통과.

5.9.4 간단한 카오스 실험

원서는 파드를 강제 종료해 회복 탄력성을 확인하는 실험에 Chaos Toolkit을 쓴다. 개념 학습용으로는 여전히 가볍고 유효하다.
