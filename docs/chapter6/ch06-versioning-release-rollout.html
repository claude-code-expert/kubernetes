CHAPTER 06

버저닝, 릴리스, 롤아웃

5장이 "코드가 이미지가 되기까지"였다면, 6장은 "그 이미지가 클러스터에서 정확히 무엇으로 불리고, 어떻게 바뀌는가"다. 쿠버네티스에는 릴리스라는 개념이 아예 없다 — 레이블로 흉내 낼 뿐이다. 이 장은 그 사실 하나에서 출발해 롤아웃의 실제 메커니즘까지 파고든다.

2026-08 기준 변경 사항 주석 포함 · 실습 명령은 0장 kind 클러스터 기준

핵심 3줄

1. 쿠버네티스에는 릴리스 컨트롤러가 없다 — "릴리스"는 레이블(예: release, release-number)로 여러 리소스를 하나의 배포 단위로 묶어 흉내 내는 관례일 뿐이다.

2. Deployment의 selector는 생성 후 절대 바꿀 수 없다 — 버전처럼 자주 바뀌는 값을 셀렉터에 넣으면 롤아웃 자체가 막힌다.

3. 롤아웃은 파일 하나를 고치는 게 아니라 리비전마다 새 ReplicaSet을 만드는 것이다 — 그래서 롤백은 "되돌리기"가 아니라 "이전 ReplicaSet을 다시 키우기"다.

6.1버저닝

버전 관리 체계 자체를 발명할 필요는 없다 — 시맨틱 버저닝 (Semantic Versioning, SemVer)이 이미 표준이다. MAJOR.MINOR.PATCH 형식으로, MAJOR는 호환 깨지는 변경, MINOR는 하위 호환되는 기능 추가, PATCH는 버그 수정을 뜻한다.

이 장의 관심사는 "어떤 체계를 쓸까"가 아니라 "정한 체계를 클러스터 전역에서 일관되게 유지하는 법"이다. 애플리케이션 버전(SemVer), 이미지 태그(5.5절 — 불변 태그), 쿠버네티스 리소스의 레이블에 적는 버전 표기가 서로 다른 규칙을 쓰면, "지금 프로덕션에 뭐가 떠 있지?"라는 가장 기본적인 질문에 답할 수 없게 된다. 세 곳 모두 같은 값을 가리키게 하는 것이 6장 전체의 밑그림이다.

6.2릴리스

먼저 짚어야 할 사실 — 쿠버네티스에는 릴리스라는 오브젝트도, 릴리스 컨트롤러도 없다. Deployment, Job, ConfigMap은 각자 독립적으로 존재할 뿐, "이것들이 한 릴리스다"라고 선언하는 API가 애초에 없다. 그래서 이 개념은 전적으로 레이블 관례로 흉내 낸다 — release: journal-stable, release-number: 34e57f01 같은 레이블을 관련된 모든 리소스에 똑같이 붙이는 것.

이름 붙이기에 조직 나름의 규칙이 있다면 릴리스 레이블은 특히 유용해진다. stable, canary 같은 값은 서비스 메시나 인그레스가 라우팅을 결정할 때 손잡이가 되고, 사용자 계층을 나눠 점진 배포하는 조직은 ring-0, ring-1 같은 링 배포 (Ring Deployment) 체계를 쓰기도 한다.

헬름을 쓴다면 이 개념이 이미 내장되어 있다 — 헬름의 릴리스 (Release)는 특정 차트를 특정 이름으로 설치한 한 인스턴스를 가리키며, 설치 이력을 자동으로 보관해 helm rollback 한 줄로 되돌릴 수 있게 해 준다. 많은 CD 도구가 헬름을 릴리스 관리 계층으로 그대로 채택하는 이유다.

함정 — 셀렉터에 변하는 값을 넣지 않는다 레이블은 API 문법만 지키면 어떤 키/값이든 자유롭게 쓸 수 있다. 문제는 레이블 셀렉터(selector)는 한번 생성되면 절대 바꿀 수 없다는 점이다. Deployment든 Job이든 DaemonSet이든 마찬가지다. 만약 selector에 ver: 1.5.8처럼 버전을 넣었다면, 다음 배포에서 ver: 1.5.9로 바뀐 파드는 더 이상 이 셀렉터와 매치되지 않는다 — 기존 ReplicaSet이 갱신되는 게 아니라 아예 새 리소스가 필요해지거나, 최악의 경우 파드가 하나도 없는 채로 멈춘다. 다음 절의 롤아웃을 이해하는 데 가장 중요한 전제다.

6.3롤아웃

Deployment가 없던 시절엔 kubectl rolling-update가 유일한 롤아웃 수단이었다 — 문제는 이 명령이 매니페스트의 일부가 아니라 그때그때 실행하는 명령이라, 선언형 CD와는 궁합이 나빴다(무엇을 배포했는지가 Git이 아니라 누군가의 터미널 히스토리에만 남았다). Deployment 컨트롤러는 롤아웃 자체를 선언된 상태로 바꿔 이 문제를 해결했다.

메커니즘은 단순하다 — Deployment는 파드를 직접 관리하지 않는다. 파드 템플릿이 바뀔 때마다(정확히는 파드 템플릿의 해시가 바뀔 때마다) 새 ReplicaSet을 하나 만들고, 기존 ReplicaSet은 서서히 줄이면서 새 것을 서서히 키운다. 각 ReplicaSet에는 pod-template-hash 레이블이 자동으로 붙어 리비전을 구분한다.

# 롤아웃 조작의 전부
kubectl rollout status deployment/frontend      # 진행 상황 실시간 관찰
kubectl rollout history deployment/frontend     # 리비전 이력
kubectl rollout undo deployment/frontend        # 직전 리비전으로
kubectl rollout undo deployment/frontend --to-revision=2   # 특정 리비전으로
kubectl rollout pause deployment/frontend       # 진행 중인 롤아웃 일시 정지
kubectl rollout resume deployment/frontend      # 재개

전환 속도와 안전성은 두 필드가 결정한다 — maxSurge(원하는 개수를 넘어 얼마나 더 만들 수 있는가)와 maxUnavailable(원하는 개수에서 얼마나 부족해도 되는가). 둘 다 기본값은 25%다. 무중단이 절대적으로 중요하다면 maxUnavailable: 0으로 낮추고, 배포 속도가 더 중요하다면 maxSurge를 올린다.

spec:
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 25%
      maxUnavailable: 25%
2026-08 기준 확인 apps/v1 API 기준 현재 기본값을 정리하면: maxSurge·maxUnavailable 각 25%, revisionHistoryLimit(보관할 옛 ReplicaSet 개수) 10, progressDeadlineSeconds(진행이 멈췄다고 판단하는 시간) 600초다. 오래된 자료에 종종 나오는 spec.rollbackTo 필드는 apps/v1에서 완전히 제거됐다 — 롤백은 오직 kubectl rollout undo로만 한다. 출처: kubernetes.io/docs/reference/using-api/deprecation-guide (apps/v1 전환 시 기본값·제거 필드 명시)

6.4종합 예제

지금까지의 개념을 저널 앱에 적용한다. 웹·DB·백업 잡, 세 리소스가 하나의 릴리스로 묶이는 모습이다.

# 웹 — 무상태, 롤링 업데이트
apiVersion: apps/v1
kind: Deployment
metadata:
  name: journal-web
  labels:
    app: journal
    release: journal-stable
    release-number: "34e57f01"
spec:
  replicas: 4
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 1
  selector:
    matchLabels:
      app: journal
      component: web
  template:
    metadata:
      labels:
        app: journal
        component: web
        ver: "1.5.9"
        release: journal-stable
        release-number: "34e57f01"
    spec:
      containers:
      - name: web
        image: myrepo/journal-web:1.5.9-34e57f0
---
# DB — 상태 보유, Recreate 전략
apiVersion: apps/v1
kind: Deployment
metadata:
  name: journal-db
  labels:
    app: journal
    release: journal-stable
    release-number: "34e57f01"
spec:
  replicas: 1
  strategy:
    type: Recreate
  selector:
    matchLabels:
      app: journal
      component: db
  template:
    metadata:
      labels:
        app: journal
        component: db
        release: journal-stable
        release-number: "34e57f01"
    spec:
      containers:
      - name: db
        image: mysql:8.0

두 가지만 눈여겨보면 된다. 첫째, selector에는 app·component처럼 절대 안 바뀌는 값만 들어 있고, ver·release-number처럼 매번 바뀌는 값은 template.metadata.labels에만 있다(6.2절 함정의 실제 적용). 둘째, DB는 왜 RollingUpdate가 아니라 Recreate인가 — 상태 보유 워크로드는 신·구버전이 동시에 같은 볼륨에 쓰기 경합을 할 수 있어, 구버전을 완전히 내린 뒤에야 신버전을 올리는 편이 안전하다(1장 StatefulSet과 같은 이유).
