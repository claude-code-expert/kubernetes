1이론

클러스터는 두 층이다. 결정을 내리는 컨트롤 플레인과, 결정대로 컨테이너를 돌리는 노드. 그 사이를 잇는 것은 API 서버 하나뿐이다.

1.1 클러스터의 두 층

클러스터(cluster)는 컨테이너를 실행하는 머신(노드(node))의 집합이다. 그중 한 대 이상이 컨트롤 플레인(control plane) 역할을 맡아 "무엇을 어디에 몇 개 띄울지"를 결정하고 상태를 저장한다. 나머지는 워커 노드로, 컨트롤 플레인이 배정한 파드(Pod)를 실제로 실행한다. 파드는 컨테이너 하나 이상을 담는 배포 단위이며, D1에서 만든 컨테이너가 파드 안에 들어간다.

오늘 만드는 클러스터는 노드 1개다. 그 한 노드가 컨트롤 플레인이면서 워커다. D5에서 3노드로 늘리면 컨트롤 플레인 1 + 워커 2가 된다.

1.2 컨트롤 플레인 네 요소

요소하는 일없으면 생기는 일
kube-apiserver클러스터의 유일한 창구. kubectl, kubelet, 컨트롤러 전부가 이 HTTP API로만 말한다. 인증·인가·어드미션을 거쳐 요청을 검증하고 etcd에 쓴다.kubectl이 아무것도 못 한다. 단, 이미 돌던 파드는 계속 돈다.
etcd클러스터 상태 전체를 담는 키-값 저장소. "원하는 상태"(내가 apply한 것)와 "현재 상태"(kubelet이 보고한 것)가 모두 여기 있다.상태를 잃는다. 백업 대상은 etcd 하나다.
kube-scheduler노드가 배정되지 않은 파드를 찾아 리소스·제약 조건을 보고 노드를 고른다. 고른 결과를 파드의 spec.nodeName에 쓴다.새 파드가 Pending에 머문다.
kube-controller-manager수십 개 컨트롤러를 한 프로세스로 묶은 것. 각 컨트롤러는 자기 오브젝트를 감시하다가 원하는 상태와 현재 상태가 다르면 맞춘다(디플로이먼트·레플리카셋·노드·잡·엔드포인트슬라이스 컨트롤러 등).파드를 지워도 다시 안 생긴다. 노드가 죽어도 파드를 옮기지 않는다.

클라우드에서는 cloud-controller-manager가 하나 더 붙어 로드밸런서·노드 정보를 클라우드 API와 맞춘다. 로컬에는 없다. Docker Desktop은 그 빈자리를 desktop-cloud-provider-kind 컨테이너로 메워 LoadBalancer 서비스를 localhost로 열어 준다(D5).

1.3 노드 세 요소

요소하는 일
kubelet노드마다 하나. API 서버에서 "이 노드에 배정된 파드" 목록을 감시하고, 컨테이너 런타임에게 만들라고 시킨 뒤 상태를 API 서버로 보고한다. 프로브(D8)를 실행하는 것도 kubelet이다.
kube-proxy노드의 네트워크 규칙(iptables/nftables)을 관리해 Service의 가상 IP가 실제 파드 IP로 가도록 한다(D5).
컨테이너 런타임containerd. D1에서 Docker Desktop VM 안에 있던 그 containerd와 같은 프로그램이다. kubelet은 CRI(Container Runtime Interface)로 containerd에 말하고, containerd는 runc로 프로세스를 만든다.

1.4 선언형과 조정 루프

쿠버네티스에는 "nginx를 띄워라"는 명령이 없다. "nginx 파드가 3개 있는 상태를 원한다"고 선언하면, 컨트롤러가 현재 상태를 보고 부족한 만큼 만들고 넘치는 만큼 지운다. 이 비교-조치를 끝없이 반복하는 것이 조정 루프(reconciliation loop)다. 파드 하나가 죽으면 "3개를 원하는데 2개다"가 되어 자동으로 하나가 더 생긴다. 사람이 개입하지 않는다.

이 구조 때문에 장애에 강하다. 컨트롤러가 잠시 죽어도 다시 뜨면 etcd의 원하는 상태와 현재 상태를 비교해 밀린 일을 처리한다. kubelet이 잠시 끊겨도 자기 노드의 컨테이너를 계속 돌리다가 재접속하면 상태를 보고한다. 누가 누구를 호출하는 구조가 아니라 각자 저장소를 보고 움직이는 구조다.

1.5 kubectl과 kubeconfig

kubectl은 API 서버에 HTTP 요청을 보내는 클라이언트다. 어느 서버에, 어떤 인증서로 접속할지는 ~/.kube/config(kubeconfig)에 적혀 있다. 이 파일은 클러스터(서버 주소·CA), 사용자(인증서·토큰), 그리고 둘을 짝지은 컨텍스트로 구성된다. Docker Desktop은 클러스터를 만들 때 docker-desktop 컨텍스트를 이 파일에 추가하고 현재 컨텍스트로 잡는다. 다른 클러스터를 쓴 적이 있어 컨텍스트가 어긋나면 Unable to connect to the server가 나온다.

1.6 오늘 만나는 오브젝트

API 서버가 다루는 모든 것은 오브젝트다. 오브젝트마다 apiVersion·kind·metadata·spec(원하는 상태)·status(현재 상태)를 가진다. 오늘은 셋만 쓴다.

kind역할자세히
Node노드 하나. kubelet이 자기 자신을 등록한다.오늘
Pod컨테이너 묶음. 최소 실행 단위. 직접 만들면 죽어도 되살아나지 않는다.D3
Deployment"이 파드를 N개 유지하라"는 선언. 컨트롤러가 되살린다.D4

4첫 파드: hello-world

D1에서 docker run hello-world로 했던 것을 클러스터에 시킨다. 같은 이미지, 다른 실행 주체.

$ kubectl run hello --image=hello-world --restart=Never
pod/hello created

$ kubectl get pod hello
NAME    READY   STATUS      RESTARTS   AGE
hello   0/1     Completed   0          8s

$ kubectl logs hello | head -3

Hello from Docker!
This message shows that your installation appears to be working correctly.

$ kubectl get pod hello -o jsonpath='{.spec.nodeName}  {.status.phase}{"\n"}'
desktop-control-plane  Succeeded

$ kubectl delete pod hello
pod "hello" deleted

읽을 것 — 이미지 이름에 레지스트리가 없으면 Docker Hub에서 받는다(D1과 같다). --restart=Never는 "끝나면 끝"이라는 뜻이고, 그래서 STATUS가 Completed, phase가 Succeeded다. nodeName에 노드명이 들어 있다. 스케줄러가 써 넣은 값이다(도판 2의 4번). 노드가 하나뿐이라 고를 것이 없었지만 절차는 같았다.

5직접 만든 파드와 디플로이먼트가 만든 파드

1.4절 조정 루프를 눈으로 본다. 파드를 지웠을 때 되살아나는지가 유일한 차이다.

터미널을 두 개 연다. 첫 번째에서 파드 변화를 계속 지켜본다.

# 터미널 A
$ kubectl get pods -w
# 터미널 B — (a) 파드를 직접 만든다
$ kubectl run web --image=nginx:1.30
$ kubectl get pod web -o jsonpath='{.metadata.ownerReferences}{"\n"}'
(빈 줄 — 소유자가 없다)
$ kubectl delete pod web

터미널 A — web Pending → ContainerCreating → Running 순서로 바뀌고, 삭제 후 Terminating을 거쳐 사라진다. 그것으로 끝이다. 아무도 다시 만들지 않는다.

# 터미널 B — (b) 디플로이먼트로 만든다
$ kubectl create deployment web --image=nginx:1.30
deployment.apps/web created
$ kubectl get pods
NAME                   READY   STATUS    RESTARTS   AGE
web-5c8f6b7d4-t7x2q    1/1     Running   0          6s
$ kubectl get pod -l app=web -o jsonpath='{.items[0].metadata.ownerReferences[0].kind} / {.items[0].metadata.ownerReferences[0].name}{"\n"}'
ReplicaSet / web-5c8f6b7d4
$ kubectl delete pod -l app=web
pod "web-5c8f6b7d4-t7x2q" deleted
$ kubectl get pods
NAME                   READY   STATUS    RESTARTS   AGE
web-5c8f6b7d4-m4k9z    1/1     Running   0          3s

터미널 A — 지운 파드가 Terminating으로 바뀌는 것과 거의 동시에 다른 이름의 파드가 Pending으로 나타나 Running이 된다. 이름 앞부분 web-5c8f6b7d4가 같다. 소유자인 레플리카셋이 "1개를 원하는데 0개다"를 감지해 만든 것이다. 이게 조정 루프다. 터미널 A는 Ctrl-C로 끝낸다.

오늘은 여기까지

Deployment → ReplicaSet → Pod의 소유 관계, 개수 조절, 롤링 업데이트는 D4에서 다룬다. 오늘 기억할 것은 하나다. 파드를 직접 만들면 일회용이고, 디플로이먼트로 만들면 유지된다.

6컨텍스트를 일부러 어긋내고 고친다

가장 흔한 첫 오류를 안전한 상태에서 한 번 겪어 둔다.

$ kubectl config get-contexts
CURRENT   NAME             CLUSTER          AUTHINFO         NAMESPACE
*         docker-desktop   docker-desktop   docker-desktop

$ kubectl config set-context broken --cluster=nowhere --user=docker-desktop
$ kubectl config use-context broken
$ kubectl get nodes
error: cluster "nowhere" does not exist

$ kubectl config use-context docker-desktop
Switched to context "docker-desktop".
$ kubectl config delete-context broken
$ kubectl get nodes
NAME                    STATUS   ROLES           AGE   VERSION
desktop-control-plane   Ready    control-plane   20m   v1.36.4

$ kubectl config view --minify -o jsonpath='{.clusters[0].cluster.server}{"\n"}'
https://127.0.0.1:6443

읽을 것 — kubectl 오류의 절반은 "어느 클러스터를 보고 있나"에서 나온다. 순서는 항상 get-contexts로 현재 위치 확인 → use-context로 이동. 마지막 줄의 127.0.0.1:6443이 API 서버 주소다. Docker Desktop이 VM 안 노드 컨테이너의 6443 포트를 macOS로 포워딩해 준 것이고, D1 도판 3의 보라색 경로가 kubectl에도 똑같이 적용된다.

7API 서버에 직접 말 걸기

kubectl은 HTTP 클라이언트일 뿐이다. 같은 요청을 URL로 보내 본다.

$ kubectl get --raw /version
{"major":"1","minor":"36","gitVersion":"v1.36.4", ...}

$ kubectl get --raw /livez?verbose | tail -3
[+]shutdown ok
livez check passed

$ kubectl get --raw /api/v1/namespaces/default/pods | python3 -c 'import sys,json; print([p["metadata"]["name"] for p in json.load(sys.stdin)["items"]])'
['web-5c8f6b7d4-m4k9z']

$ kubectl get events --sort-by=.lastTimestamp | tail -5
LAST SEEN   TYPE     REASON      OBJECT                     MESSAGE
3m          Normal   Scheduled   pod/web-5c8f6b7d4-m4k9z    Successfully assigned default/web-5c8f6b7d4-m4k9z to desktop-control-plane
3m          Normal   Pulled      pod/web-5c8f6b7d4-m4k9z    Container image "nginx:1.30" already present on machine
3m          Normal   Created     pod/web-5c8f6b7d4-m4k9z    Created container nginx
3m          Normal   Started     pod/web-5c8f6b7d4-m4k9z    Started container nginx

읽을 것 — kubectl get pods는 GET /api/v1/namespaces/default/pods다. 이벤트 네 줄은 도판 2의 4·5번이 실제로 남긴 기록이다. Scheduled는 스케줄러가, Pulled·Created·Started는 kubelet이 썼다. 내일부터 파드가 안 뜰 때 가장 먼저 볼 것이 이 이벤트다.

4체크포인트 A

문서를 덮고 진행한다. 1단계(D1~D3)의 첫 관문이다.

  1. docker ps 출력에서 노드 컨테이너를 가리키고, kubectl get nodes -o wide의 CONTAINER-RUNTIME이 무엇인지 말한다.
  2. kube-system의 파드 중 컨트롤 플레인 네 요소를 이름으로 짚고, 왜 그 넷의 이름 끝에 노드명이 붙는지 한 문장으로 설명한다.
  3. kubectl run으로 만든 파드와 kubectl create deployment로 만든 파드를 각각 지운 뒤, -w 출력의 차이를 보인다.
  4. 컨텍스트를 잘못된 것으로 바꿔 오류를 낸 뒤, get-contexts·use-context 두 명령으로 복구한다.
  5. kubectl get events에서 스케줄러가 남긴 줄과 kubelet이 남긴 줄을 구분한다.

5개 중 4개 이상이면 D3로 간다. 3번이 안 되면 5단계 (a)와 (b)의 ownerReferences 출력을 다시 비교한다.

5정리

클러스터는 끄지 않는다. 내일 그대로 쓴다. 오늘 만든 디플로이먼트만 지운다.

$ kubectl delete deployment web
$ kubectl get pods
No resources found in default namespace.
$ kubectl config current-context
docker-desktop

노트북을 닫아도 된다. Docker Desktop이 다시 뜨면 노드 컨테이너도 함께 뜬다. 클러스터를 완전히 지우려면 Kubernetes 화면의 Stop(컨테이너 제거)을 쓴다. 이 경우 내일 다시 만들어야 하고 /usr/local/bin/kubectl도 함께 제거된다.

D3 예고

오늘 kubectl run으로 만든 파드를 내일은 YAML 파일로 쓴다. apiVersion · kind · metadata · spec 네 줄이 뼈대이고, kubectl get pod -o yaml로 오늘 본 180줄짜리 출력이 그 네 줄에 status가 붙은 것임을 확인한다. 네임스페이스로 칸을 나누고, Headlamp를 설치해 같은 것을 화면으로 본다.
