컨테이너와 Docker Desktop

컨테이너는 가상 머신이 아니라 격리된 프로세스다. 오늘은 그 사실을 명령어로 확인하고, 이미지를 직접 빌드하고, 데이터와 네트워크를 컨테이너 밖으로 빼는 법까지 한 대의 노트북 안에서 끝낸다. 내일 클러스터를 켜면 이 컨테이너들이 여러 노드로 흩어진다.

  4. Compose 파일 하나로 위 구성을 한 번에 올리고 내린다.

1이론

네 가지만 잡는다. 컨테이너의 정체, 이미지의 구조, Docker Desktop이 macOS에서 돌아가는 방식, 그리고 데이터·네트워크를 분리하는 이유.

1.1 컨테이너는 프로세스다

리눅스 커널의 두 기능이 컨테이너를 만든다. 네임스페이스(namespace)는 프로세스가 볼 수 있는 범위를 나눈다. PID·네트워크·마운트·호스트명이 각각 따로 격리되어, 컨테이너 안의 프로세스는 자기가 PID 1이고 인터페이스가 하나뿐이라고 믿는다. cgroup(control group)은 쓸 수 있는 양을 제한한다. CPU 시간, 메모리, I/O 대역이 여기서 정해진다.

그래서 컨테이너에는 별도의 커널이 없다. 호스트(정확히는 Docker Desktop의 리눅스 VM) 커널을 그대로 쓰는 프로세스이고, 시작이 밀리초 단위로 끝나는 이유가 이것이다. 가상 머신은 하드웨어를 흉내 내고 게스트 커널을 부팅하지만, 컨테이너는 fork한 프로세스에 네임스페이스와 cgroup을 씌운다.

1.2 이미지는 읽기 전용 레이어의 묶음이다

이미지는 파일 시스템 스냅샷을 층층이 쌓은 것이다. Dockerfile의 명령 하나가 대개 레이어 하나가 되고, 각 레이어는 내용 해시(digest)로 식별된다. 같은 베이스 레이어를 쓰는 이미지가 열 개면 디스크에는 한 번만 저장되고, 빌드할 때 바뀌지 않은 레이어는 캐시에서 재사용된다.

컨테이너를 시작하면 이미지 위에 얇은 쓰기 가능 레이어 하나가 얹힌다. 컨테이너 안에서 만든 파일은 전부 이 층에 들어가고, 컨테이너를 지우면 이 층도 사라진다. 데이터가 날아가는 이유이자 볼륨이 필요한 이유다.

1.3 Docker Desktop은 macOS 위에 리눅스 VM을 하나 띄운다

macOS 커널에는 네임스페이스와 cgroup이 없다. Docker Desktop은 Apple Virtualization Framework(또는 Docker VMM)로 경량 리눅스 VM을 하나 만들고, 그 안에 dockerd·containerd를 띄운다. 터미널의 docker CLI는 유닉스 소켓을 통해 VM 안의 데몬에게 명령을 전달할 뿐이다. 컨테이너는 전부 VM 안에서 돈다.

이 구조에서 세 가지가 따라온다. (1) -p 8080:80은 macOS 포트를 VM을 거쳐 컨테이너로 이어 주는 포워딩이다. (2) -v $(pwd):/data는 macOS 디렉터리를 VM에 공유(VirtioFS)한 뒤 컨테이너에 마운트하므로 파일 I/O가 많은 작업은 느릴 수 있다. (3) Settings에서 정한 CPU·메모리는 이 VM 하나의 크기이고, 내일 켤 쿠버네티스 노드도 같은 VM 안의 컨테이너로 만들어진다.

1.4 데이터는 볼륨에, 통신은 네트워크에

볼륨

컨테이너 수명과 분리된 저장소다. 네임드 볼륨은 Docker가 VM 안에서 관리하며 DB처럼 영속 데이터에 쓴다. 바인드 마운트는 macOS의 경로를 직접 연결하며 개발 중 소스 반영이나 설정 파일 주입에 쓴다. 쿠버네티스의 PersistentVolume(D9)은 네임드 볼륨을 클러스터 규모로 확장한 개념이다.

네트워크

컨테이너마다 네트워크 네임스페이스가 있으므로 기본적으로 서로 보이지 않는다. 사용자 정의 브리지 네트워크에 두 컨테이너를 붙이면 Docker 내장 DNS가 컨테이너 이름을 IP로 풀어 준다. 쿠버네티스의 Service와 CoreDNS(D5)가 하는 일이 정확히 이것이다.

1.5 한 대에서 끝나는 것과 끝나지 않는 것

오늘 만드는 nginx + postgres 구성은 Compose로 한 번에 올릴 수 있다. 문제는 그다음이다. 컨테이너가 죽으면 누가 다시 띄우나. 노트북 한 대의 메모리가 모자라면 두 번째 노트북으로 어떻게 넘기나. 트래픽이 늘면 nginx를 세 개로 늘리고 요청을 어떻게 나누나. Docker는 "한 대 안에서 컨테이너를 만드는 법"을 정의하고, 쿠버네티스는 "여러 대에 걸쳐 원하는 개수를 유지하는 법"을 정의한다. 내일부터 그 두 번째 질문을 다룬다.

3따라하기

작업 디렉터리 하나를 만들고 그 안에서 진행한다. 모든 명령은 그대로 붙여 넣어 실행할 수 있고, 회색 줄은 기대 출력이다(ID·시간은 다르다).

$ mkdir -p ~/k8s-study/day01 && cd ~/k8s-study/day01

1첫 컨테이너: 이미지를 받아서 실행하고 지운다

run 한 번에 pull·create·start 세 단계가 일어난다. 무엇이 어디에 남는지 본다.

$ docker run --name first hello-world
Unable to find image 'hello-world:latest' locally
latest: Pulling from library/hello-world
...
Hello from Docker!
This message shows that your installation appears to be working correctly.
...

$ docker ps -a --format 'table {{.Names}}\t{{.Image}}\t{{.Status}}'
NAMES     IMAGE         STATUS
first     hello-world   Exited (0) 5 seconds ago

$ docker images hello-world --format '{{.Repository}}:{{.Tag}}  {{.Size}}'
hello-world:latest  20.3kB

$ docker rm first
$ docker rmi hello-world

읽을 것 — 프로세스가 메시지를 찍고 종료(exit 0)했으므로 컨테이너는 Exited로 남는다. 컨테이너를 지워도 이미지는 남고, 이미지를 지워야 디스크에서 사라진다. 두 개는 별개의 오브젝트다.

2웹 서버 실행: 포트 공개, 로그, 셸 접속

백그라운드(-d)로 띄우고 macOS 포트와 연결한다. 태그를 고정해 다음 주에도 같은 버전이 뜨게 한다.

$ docker run -d --name web -p 8080:80 nginx:1.30
3f9c2a...(컨테이너 ID)

$ curl -s localhost:8080 | head -4
<!DOCTYPE html>
<html>
<head>
<title>Welcome to nginx!</title>

$ docker logs web
... 172.17.0.1 - - [30/Aug/2026:02:10:41 +0000] "GET / HTTP/1.1" 200 615 "-" "curl/8.7.1" "-"

$ docker exec -it web bash
root@3f9c2a:/# ls /usr/share/nginx/html
50x.html  index.html
root@3f9c2a:/# exit

읽을 것 — 요청 IP가 172.17.0.1이다. macOS의 curl이 VM의 브리지 게이트웨이를 거쳐 들어왔다는 뜻이고, 도판 3의 보라색 경로가 실제로 존재함을 로그가 보여 준다. exec의 대상은 이미지 이름이 아니라 컨테이너 이름(web)이다.

3컨테이너는 프로세스다: PID 1과 메모리 제한

1.1절을 명령으로 확인한다. 안에서 보면 PID 1, 밖에서 보면 그냥 프로세스 하나.

$ docker exec web cat /proc/1/comm
nginx

$ docker exec web sh -c 'ls -d /proc/[0-9]* | wc -l'
5

$ docker top web -o pid,user,comm
PID     USER    COMMAND
2311    root    nginx
2352    101     nginx
2353    101     nginx
2354    101     nginx
2355    101     nginx

$ docker exec web hostname
3f9c2a1b8d0e

$ docker exec web cat /sys/fs/cgroup/memory.max
max

읽을 것 — 안에서 보면 PID 1이 nginx이고 프로세스가 5개뿐이다(PID 네임스페이스). 같은 프로세스를 밖(docker top, VM 관점)에서 보면 PID 2311짜리 평범한 프로세스다. nginx 이미지에는 ps가 없어서 /proc을 직접 읽었다. 호스트명은 컨테이너 ID다(UTS 네임스페이스). 메모리 제한은 max, 즉 없다. 제한을 걸어 본다.

$ docker run -d --name web-limited --memory=64m nginx:1.30
$ docker exec web-limited cat /sys/fs/cgroup/memory.max
67108864

$ docker stats --no-stream --format 'table {{.Name}}\t{{.MemUsage}}\t{{.MemPerc}}' web web-limited
NAME          MEM USAGE / LIMIT   MEM %
web           9.4MiB / 7.76GiB    0.12%
web-limited   9.2MiB / 64MiB      14.38%

$ docker rm -f web-limited

읽을 것 — 같은 이미지, 같은 프로세스인데 한쪽만 LIMIT이 64MiB다. cgroup 값 하나가 다를 뿐이다. 쿠버네티스의 resources.limits.memory(D8)는 이 파일에 숫자를 써 넣는 일이다.

4이미지 빌드: Dockerfile 세 줄과 레이어 읽기

기본 페이지를 내 페이지로 바꾼 이미지를 만든다. 빌드 컨텍스트에 뭐가 들어가는지도 함께 통제한다.

$ cat > index.html <<'EOF'
<h1>Day 1 — hello from my image</h1>
EOF

$ cat > Dockerfile <<'EOF'
FROM nginx:1.30
COPY index.html /usr/share/nginx/html/index.html
EXPOSE 80
EOF

$ cat > .dockerignore <<'EOF'
.git
*.md
.DS_Store
EOF

$ docker build -t day01-web:v1 .
[+] Building 1.2s (7/7) FINISHED
 => [internal] load build definition from Dockerfile
 => [1/2] FROM docker.io/library/nginx:1.30
 => [2/2] COPY index.html /usr/share/nginx/html/index.html
 => exporting to image
 => => naming to docker.io/library/day01-web:v1

$ docker history day01-web:v1 --format 'table {{.CreatedBy}}\t{{.Size}}' | head -4
CREATED BY                                            SIZE
EXPOSE map[80/tcp:{}]                                 0B
COPY index.html /usr/share/nginx/html/index.html      42B
CMD ["nginx" "-g" "daemon off;"]                      0B

$ docker rm -f web
$ docker run -d --name web -p 8080:80 day01-web:v1
$ curl -s localhost:8080
<h1>Day 1 — hello from my image</h1>

읽을 것 — history의 맨 위 두 줄이 내가 추가한 레이어다. COPY는 42B짜리 레이어를 만들고 EXPOSE는 0B(메타데이터)다. 그 아래는 전부 nginx:1.30에서 상속한 레이어이며, 디스크에는 이미 있으므로 새로 받지 않았다.

index.html의 문구를 바꾸고 다시 빌드해 보면 [1/2] FROM은 CACHED로 표시되고 COPY 레이어만 새로 만들어진다. 이 캐시가 빌드 시간을 정한다. 자주 바뀌는 파일은 Dockerfile에서 아래에 둔다.

5볼륨: 컨테이너를 지워도 데이터가 남게 한다

PostgreSQL을 볼륨 없이 띄워 데이터를 잃어 보고, 볼륨을 붙여 같은 일을 다시 한다.

# (a) 볼륨 없이
$ docker run -d --name db -e POSTGRES_PASSWORD=study postgres:18
$ until docker exec db pg_isready -q; do sleep 1; done
$ docker exec db psql -U postgres -c "CREATE TABLE orders(id int); INSERT INTO orders VALUES (1),(2);"
INSERT 0 2
$ docker rm -f db
$ docker run -d --name db -e POSTGRES_PASSWORD=study postgres:18
$ until docker exec db pg_isready -q; do sleep 1; done
$ docker exec db psql -U postgres -c "SELECT count(*) FROM orders;"
ERROR:  relation "orders" does not exist
$ docker rm -f db

읽을 것 — 테이블이 없다. 데이터는 도판 2의 초록 층에 있었고 rm과 함께 사라졌다.

# (b) 네임드 볼륨
$ docker volume create pgdata
$ docker run -d --name db -e POSTGRES_PASSWORD=study -v pgdata:/var/lib/postgresql postgres:18
$ until docker exec db pg_isready -q; do sleep 1; done
$ docker exec db psql -U postgres -c "CREATE TABLE orders(id int); INSERT INTO orders VALUES (1),(2);"
$ docker rm -f db
$ docker run -d --name db -e POSTGRES_PASSWORD=study -v pgdata:/var/lib/postgresql postgres:18
$ until docker exec db pg_isready -q; do sleep 1; done
$ docker exec db psql -U postgres -c "SELECT count(*) FROM orders;"
 count
-------
     2

$ docker volume inspect pgdata --format '{{.Mountpoint}}'
/var/lib/docker/volumes/pgdata/_data

읽을 것 — 컨테이너를 새로 만들었는데 행 2개가 그대로다. Mountpoint는 VM 안의 경로이고 macOS Finder에서는 보이지 않는다. postgres 18 이미지는 데이터 디렉터리가 /var/lib/postgresql(하위에 버전별 디렉터리)이므로 이 경로에 마운트한다.

바인드 마운트는 방향이 반대다. macOS 경로를 컨테이너에 준다. :ro로 읽기 전용을 걸 수 있다.

$ mkdir -p html && echo '<h1>bind mount</h1>' > html/index.html
$ docker run -d --name web-bind -p 8081:80 -v "$(pwd)/html:/usr/share/nginx/html:ro" nginx:1.30
$ curl -s localhost:8081
<h1>bind mount</h1>
$ echo '<h1>edited on macOS</h1>' > html/index.html
$ curl -s localhost:8081
<h1>edited on macOS</h1>
$ docker rm -f web-bind

6네트워크: 컨테이너끼리 이름으로 부른다

기본 브리지에서는 이름 해석이 안 된다. 사용자 정의 네트워크를 만들면 내장 DNS가 붙는다.

$ docker network create study-net
$ docker network connect study-net web
$ docker network connect study-net db

$ docker run --rm --network study-net alpine:3.24 wget -qO- http://web
<h1>Day 1 — hello from my image</h1>

$ docker run --rm --network study-net postgres:18 pg_isready -h db -p 5432
db:5432 - accepting connections

$ docker network inspect study-net --format '{{range .Containers}}{{.Name}} {{.IPv4Address}}{{"\n"}}{{end}}'
web 172.19.0.2/16
db 172.19.0.3/16

읽을 것 — http://web, -h db처럼 컨테이너 이름이 호스트명이 됐다. 포트를 macOS에 공개하지 않은 db(5432)에도 같은 네트워크 안에서는 접근된다. 공개(-p)는 바깥용, 네트워크는 안쪽용이다.

이름 해석이 되지 않는 경우를 한 번 본다.

$ docker run --rm alpine:3.24 wget -qO- -T 3 http://web ; echo "exit=$?"
wget: bad address 'web'
exit=1

읽을 것 — --network를 빼면 기본 브리지에 붙고, 거기엔 DNS가 없어 web을 못 찾는다(bad address = 이름 해석 실패). 쿠버네티스에서 서비스 이름이 안 풀릴 때 가장 먼저 의심할 것이 "같은 네트워크(네임스페이스)인가"다.

7Compose: 위 구성을 파일 하나로

손으로 친 run·volume·network 명령을 선언으로 바꾼다. 내일부터 쓰는 쿠버네티스 매니페스트도 같은 발상이다.

$ docker rm -f web db && docker network rm study-net

$ cat > compose.yaml <<'EOF'
services:
  web:
    build: .
    image: day01-web:v1
    ports:
      - "8080:80"
  db:
    image: postgres:18
    environment:
      POSTGRES_PASSWORD: study
    volumes:
      - pgdata:/var/lib/postgresql
volumes:
  pgdata:
    external: true      # 5단계에서 만든 볼륨을 그대로 쓴다
EOF

$ docker compose up -d
[+] Running 3/3
 ✔ Network day01_default  Created
 ✔ Container day01-db-1   Started
 ✔ Container day01-web-1  Started

$ docker compose ps --format 'table {{.Service}}\t{{.Status}}\t{{.Ports}}'
SERVICE   STATUS          PORTS
db        running         5432/tcp
web       running         0.0.0.0:8080->80/tcp

$ docker compose exec db psql -U postgres -c "SELECT count(*) FROM orders;"
 count
-------
     2

읽을 것 — Compose가 네트워크 day01_default를 만들어 두 서비스를 붙였고, external: true 덕에 5단계의 pgdata 볼륨을 그대로 써서 행 2개가 보인다. external을 빼면 Compose는 day01_pgdata라는 새 볼륨을 만든다. 서비스 이름 db가 곧 DNS 이름이다.

4체크포인트

문서를 덮고 진행한다. 통과 기준은 출력이다.

  1. docker info에서 OSType이 linux임을 보이고, 왜 macOS에서 linux가 나오는지 한 문장으로 말한다.
  2. 임의의 문구를 담은 정적 페이지 이미지를 myweb:v1로 빌드하고, curl localhost:9000이 그 문구를 반환한다.
  3. docker history myweb:v1에서 본인이 추가한 레이어가 몇 개인지 가리킨다.
  4. postgres 컨테이너에 테이블을 만들고, 컨테이너를 지웠다 새로 만들어도 테이블이 남아 있게 한다.
  5. 사용자 정의 네트워크에서 curl http://<컨테이너이름>이 되고, 기본 브리지에서는 안 되는 것을 보인다.

5개 중 4개 이상이면 D2로 간다. 4번이 안 되면 5단계 (b)를 다시 하고, 5번이 안 되면 --network 유무를 비교한다.

5정리

내일은 클러스터를 켜므로 오늘의 컨테이너는 전부 내린다. 이미지 day01-web:v1은 D4에서 레지스트리에 올리는 연습에 다시 쓰니 남겨 둔다.

$ docker compose down              # 컨테이너·네트워크 제거 (external 볼륨은 남는다)
$ docker volume rm pgdata
$ docker ps -a --format '{{.Names}}'   # 비어 있어야 한다
$ docker images --format '{{.Repository}}:{{.Tag}}' | sort
alpine:3.24
day01-web:v1
nginx:1.30
postgres:18

디스크를 아끼고 싶으면 docker image prune으로 태그 없는 중간 레이어만 정리한다. docker system prune -a는 위 이미지까지 전부 지우므로 D4 전에는 쓰지 않는다.
