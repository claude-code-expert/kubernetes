1.3 노드를 비운다: cordon · drain · PDB

kubectl cordon은 노드를 SchedulingDisabled로 만들어 새 파드가 오지 못하게 한다. drain은 cordon 뒤 그 노드의 파드를 축출(evict)한다. 축출은 삭제와 달리 PDB(D8)를 확인한다. 허용 중단 수가 0이면 그 파드는 축출되지 않고 drain이 기다린다. 데몬셋 파드는 --ignore-daemonsets로 건너뛰고, emptyDir을 가진 파드는 --delete-emptydir-data로 동의해야 한다. 로컬 디스크 PVC를 가진 파드(D9의 postgres)는 축출되더라도 PV의 nodeAffinity 때문에 다른 노드에 갈 수 없어 Pending이 된다. 이것이 로컬 스토리지의 대가다. 작업이 끝나면 uncordon.

4장애 주입 · 5종, 각 5분

진행자가 하나씩 넣는다. 참가자는 증상부터 시작해 1.1절의 순서로 내려가며 원인 문장을 말한다("서비스 셀렉터가 order-apx로 바뀌어 엔드포인트가 비었다"). 고치는 것은 진행자가 한다. 진행자용 스크립트는 접어 두었다.

진행자: 먼저 Argo CD 자동 동기화를 끈다

selfHeal이 켜져 있으면 주입한 장애가 수십 초 안에 되돌아간다. 라운드 시작 전에 kubectl -n argocd patch application study-app --type merge -p '{"spec":{"syncPolicy":null}}', 끝나면 kubectl apply -f platform/argocd-app-study.yaml로 복구. 이 사실 자체가 마지막 질문거리다("왜 장애가 저절로 안 고쳐졌나").

진행자용 inject.sh (참가자는 열지 않는다) 
$ cat > ~/k8s-study/gitops/inject.sh <<'EOF'
#!/usr/bin/env bash
# 사용: ./inject.sh <1-5> [fix]
set -euo pipefail
n=$1; mode=${2:-break}
case "$n:$mode" in
  1:break) kubectl -n study set image deployment/order-api app=order-api:v9 ;;
  1:fix)   kubectl -n study set image deployment/order-api app=order-api:v6 ;;
  2:break) kubectl -n study patch svc order-api -p '{"spec":{"selector":{"app":"order-apx"}}}' ;;
  2:fix)   kubectl -n study patch svc order-api -p '{"spec":{"selector":{"app":"order-api"}}}' ;;
  3:break) kubectl -n study patch secret postgres-secret -p '{"stringData":{"POSTGRES_PASSWORD":"wrong-pw"}}'
           kubectl -n study delete pod -l app=order-api --wait=false ;;
  3:fix)   kubectl -n study patch secret postgres-secret -p '{"stringData":{"POSTGRES_PASSWORD":"orders-pw-2026"}}'
           kubectl -n study delete pod -l app=order-api --wait=false ;;
  4:break) kubectl -n study set resources deployment/order-api --limits=memory=96Mi ;;
  4:fix)   kubectl -n study set resources deployment/order-api --limits=memory=512Mi ;;
  5:break) kubectl delete clusterrolebinding kps-kube-prometheus-stack-prometheus ;;
  5:fix)   helm upgrade kps prometheus-community/kube-prometheus-stack -n monitoring --version 88.3.0 -f ~/k8s-study/day10/kps-values.yaml --reuse-values >/dev/null ;;
  *) echo "usage: $0 <1-5> [fix]"; exit 1 ;;
esac
echo "fault $n $mode done"
EOF
$ chmod +x ~/k8s-study/gitops/inject.sh

라운드 1

증상: 대시보드는 멀쩡한데 Argo CD가 Degraded. kubectl get pods에 order-api 파드 하나가 ImagePullBackOff. localhost/orders는 200.

기대 진단

① get: 새 레플리카셋 파드 1개 ImagePull, 옛 파드는 Running. ② describe: order-api:v9 not found. 결론: 없는 태그로 이미지가 바뀌었고 디플로이먼트가 옛 파드를 지키고 있다(D4 8단계). Git에는 v6이므로 selfHeal이 켜져 있었다면 되돌아왔을 것. 첫 명령은 describe, 3분 안에 끝나야 한다.

라운드 2

증상: localhost/orders가 500. 파드는 전부 Running. 대시보드 요청률이 0으로 떨어짐.

기대 진단

① get: 이상 없음. ② events: 없음. ③ logs: 조용함(요청이 안 온다). ④ 연결: get httproute status는 정상, get endpointslices -l kubernetes.io/service-name=order-api가 비어 있음 → describe svc order-api의 Selector가 app=order-apx. 500인 이유: Envoy가 라우트는 찾았는데 보낼 엔드포인트가 없다(D6 4단계). 로그부터 열었다면 시간을 버린다.

라운드 3

증상: order-api 파드가 CrashLoopBackOff. 알림 OrderApiDown 후보. postgres는 Running.

기대 진단

③ logs --previous: FATAL: password authentication failed for user "orders". 시크릿의 비밀번호가 바뀌었고 재시작된 파드가 새 값을 읽었다. 이미 떠 있던 파드는 옛 값을 쓰고 있었을 것이다(D7의 환경 변수 반영 시점). 확인: get secret postgres-secret -o jsonpath | base64 -d. 진행자 질문: "postgres 자체는 왜 멀쩡한가" — postgres는 시작 시 비밀번호를 읽어 DB에 저장했고 시크릿 변경과 무관하다.

라운드 4

증상: order-api 파드가 재시작을 반복. 로그가 비어 있다. Grafana Pod 대시보드에서 메모리가 톱니 모양.

기대 진단

② describe의 Last State: OOMKilled, exit 137, limits memory 96Mi. 로그가 없는 이유는 SIGKILL(D8 4단계). get deploy -o jsonpath로 limits가 512에서 96으로 바뀐 것을 확인. Git과 diff하면 한 줄. Argo CD UI의 diff 탭이 가장 빠르다.

라운드 5

증상: 앱은 정상. Grafana의 모든 패널이 몇 분 전부터 끊김. 알림도 없음.

기대 진단

Prometheus Targets가 전부 down. kubectl -n monitoring logs prometheus-kps-…-0 -c prometheus에 403 Forbidden·cannot list resource "pods". ⑤ 권한: Prometheus의 ServiceAccount가 쓰는 ClusterRoleBinding이 없다. kubectl get clusterrolebinding | grep kps. "알림도 없음"이 함정이다. 모니터링 자체가 죽으면 알림도 죽는다. 그래서 Prometheus의 up을 밖에서 보는 메타 모니터링이 있다.

라운드 뒤: 시각 대조

$ q() { curl -s "localhost:9090/api/v1/query" --data-urlencode "query=$1" | python3 -c 'import sys,json; r=json.load(sys.stdin)["data"]["result"]; [print(x["metric"], x["value"][1]) for x in r[:6]]'; }
$ q 'sum by (pod) (kube_pod_container_status_restarts_total{namespace="study"} > 0)'
$ q 'count(up == 0)'
$ q 'changes(kube_deployment_spec_replicas{namespace="study"}[1h])'

Grafana Explore에서 지난 1시간 범위로 Error ratio, restarts, up 세 쿼리를 한 화면에 놓고, 라운드 1~5의 시각에 어느 선이 먼저 움직였는지 짚는다. D10 6단계의 기준선 다섯 숫자와 비교한다. 라운드 2는 오류율이, 3·4는 재시작이, 5는 up이 먼저 움직였다. 1은 아무 지표도 안 움직였다. 디플로이먼트가 옛 파드를 지켰기 때문이며, 그것을 잡는 것은 kube_deployment_status_replicas_unavailable 같은 상태 지표다.
