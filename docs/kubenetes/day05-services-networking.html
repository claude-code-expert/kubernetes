파드 IP는 바뀐다 — 서비스와 클러스터 안 네트워크의 실제 경로

어제 파드 4개에 IP가 4개 있었고, 지우면 다 바뀌었다. 오늘은 그 앞에 고정된 이름과 주소를 하나 세운다. 그 주소는 실체가 없는 가상 IP다. 프록시 서버가 있는 게 아니라 커널의 주소 변환과 CNI의 배달만 있다. 이걸 알아야 "왜 port-forward는 한 파드로만 가는가", "왜 이름이 안 풀리는가"에 답할 수 있다. 클러스터를 3노드로 늘려 다른 노드의 파드까지 요청이 가는 것을 확인하고, 두 번째 앱 gateway를 올려 서비스 이름으로 호출한다.

  2. 서비스 이름이 IP로 풀리는 과정을 nslookup과 /etc/resolv.conf로 설명하고, 다른 네임스페이스에서 FQDN이 필요한 이유를 말한다.

  5. LoadBalancer 서비스로 localhost에서 앱에 접속하고, gateway → order-api 호출이 다른 노드의 파드까지 도달함을 증명한다.

1이론

서비스가 무엇을 고정하는지, 네 가지 타입, 이름이 풀리는 규칙, 그리고 요청 하나가 실제로 지나는 경로.

1.1 서비스는 이름과 가상 IP를 고정한다

서비스(Service)는 라벨 셀렉터로 고른 파드 집합에 고정 이름과 고정 가상 IP(ClusterIP)를 준다. 파드가 죽고 새로 생겨 IP가 바뀌어도 서비스 IP는 그대로다. 호출하는 쪽은 파드 IP를 몰라도 되고 알아서도 안 된다.

서비스와 파드 사이에는 엔드포인트슬라이스(EndpointSlice)가 있다. 컨트롤러가 셀렉터에 맞는 파드의 IP·포트 목록을 이 오브젝트에 계속 갱신한다. 서비스 IP로 온 요청은 이 목록 중 하나로 보내진다. 셀렉터가 틀리면 목록이 비고, 요청은 갈 곳이 없다. 오류 메시지 없이.

1.2 네 가지 타입

type무엇이 열리나이 환경에서
ClusterIP클러스터 안에서만 닿는 가상 IP. 기본값. 파드끼리 부를 때 쓴다.기본. 밖에서는 port-forward로만
NodePortClusterIP에 더해 모든 노드의 같은 포트(30000~32767)를 연다. 어느 노드로 들어와도 서비스로 간다.노드 컨테이너끼리는 닿는다. macOS에서 직접은 보장 안 됨
LoadBalancerNodePort에 더해 외부 로드밸런서를 요청한다. 클라우드에서는 클라우드 LB, 로컬에서는 구현체가 있어야 한다.Docker Desktop이 localhost로 열어 준다

세 타입은 층층이 쌓인다. LoadBalancer 서비스도 ClusterIP와 NodePort를 함께 가진다. 그리고 clusterIP: None으로 만드는 헤드리스(headless) 서비스는 가상 IP 없이 DNS가 파드 IP들을 직접 돌려준다. 파드를 개별로 지목해야 하는 스테이트풀셋(D9)이 쓴다.

1.3 이름이 풀리는 규칙

D2에서 본 coredns 파드가 클러스터 DNS다. 서비스마다 <서비스>.<네임스페이스>.svc.cluster.local이라는 이름이 생기고, 그 이름은 ClusterIP로 풀린다. 파드의 /etc/resolv.conf에는 kubelet이 넣어 준 검색 목록(search study.svc.cluster.local svc.cluster.local cluster.local)이 있어서, 같은 네임스페이스면 order-api만 쳐도 첫 항목이 붙어 풀린다. 다른 네임스페이스의 서비스는 order-api.study처럼 최소 네임스페이스까지 적어야 한다.

1.4 요청 하나가 지나는 실제 경로

서비스 IP에는 프로세스가 없다. 그 IP로 보낸 패킷을 파드 IP로 바꾸는 것은 각 노드의 kube-proxy가 커널에 써 넣은 규칙(iptables 또는 nftables)이다. 바뀐 패킷을 다른 노드의 파드까지 실어 나르는 것은 CNI 플러그인(kindnet)이 만든 라우팅이다. 컨트롤 플레인은 이 경로에 개입하지 않는다. API 서버가 죽어도 이미 만들어진 규칙은 동작한다.

1.5 CNI가 하는 일

CNI(Container Network Interface) 플러그인은 두 가지를 맡는다. 파드가 생길 때 네트워크 인터페이스를 만들어 노드의 파드 CIDR에서 IP를 하나 주는 것, 그리고 노드끼리 "저 CIDR은 저 노드로"라는 경로를 유지하는 것. kind의 기본 플러그인 kindnet은 노드마다 /24를 하나씩 배정하고(10.244.0.0/24, 10.244.1.0/24, …) 각 노드의 라우팅 테이블에 다른 노드의 CIDR을 그 노드 IP 경유로 적는다. 오버레이 터널도 NAT도 없다. 모든 파드 IP는 클러스터 안 어디서든 직접 닿는다. 이것이 쿠버네티스 네트워크 모델의 요구 사항이고, 플러그인마다 구현 방식만 다르다.

1.6 Docker Desktop이 LoadBalancer를 여는 방식

클라우드가 없으니 로드밸런서도 없어야 하지만, D2에서 본 desktop-cloud-provider-kind 컨테이너가 그 역할을 흉내 낸다. LoadBalancer 서비스가 생기면 Envoy 프록시를 하나 띄워 노드의 NodePort로 보내고, 그 포트를 macOS의 localhost로 포워딩한다. kubectl get svc의 EXTERNAL-IP에 localhost가 찍히면 된 것이다. 같은 포트를 두 서비스가 요구하면 두 번째는 <pending>에 머문다.

# nftables 모드라면 (mode: nftables)
$ docker exec desktop-worker sh -c 'nft list ruleset | grep -A4 "order-api" | head -20'

읽을 것 — 첫 줄: 목적지가 10.96.34.18:8080이면 서비스 체인으로. 다음 넷: 1/4, 1/3, 1/2, 나머지 확률로 엔드포인트 체인 하나를 고른다(균등 분배를 확률로 구현). 마지막: 목적지 주소를 파드 IP로 DNAT. 이 규칙은 모든 노드에 똑같이 있다(desktop-worker2에서도 확인해 본다). 프로세스가 아니라 커널 규칙이므로 kube-proxy 파드를 잠시 지워도 기존 규칙은 남아 동작한다.

6실제 경로 ②: 노드 간 라우팅

DNAT된 패킷이 다른 노드로 가는 길을 라우팅 테이블에서 찾는다.

$ kubectl get nodes -o custom-columns='NODE:.metadata.name,IP:.status.addresses[0].address,PODCIDR:.spec.podCIDR'

읽을 것 — worker의 라우팅 테이블에 "10.244.2.0/24는 192.168.97.4(worker2)로"가 있다. kindnet이 적어 둔 줄이다. 같은 노드의 파드는 veth 인터페이스로 직접, 다른 노드의 파드는 그 노드 IP를 경유. 서비스 없이 파드 IP로 직접 호출해도 되고, traceroute가 2홉(내 노드의 게이트웨이 → 상대 파드)으로 끝난다. 터널도 NAT도 없다.

7NodePort와 LoadBalancer: 밖으로 여는 두 단계

타입을 바꾸며 무엇이 추가로 열리는지 본다. LoadBalancer에서 macOS의 curl이 파드 넷에 분산되는 것으로 D4의 숙제를 푼다.

$ kubectl patch svc order-api -p '{"spec":{"type":"NodePort"}}'
$ kubectl get svc order-api
NAME        TYPE       CLUSTER-IP    EXTERNAL-IP   PORT(S)          AGE
order-api   NodePort   10.96.34.18   <none>        8080:31742/TCP   20m

# 노드 컨테이너에서: 어느 노드의 31742로 들어가도 서비스에 닿는다
$ docker exec desktop-control-plane sh -c 'curl -s http://192.168.97.4:31742/'
order-api v2 on order-api-5b8d7c9f2-n8v3x
$ docker exec desktop-control-plane sh -c 'curl -s http://192.168.97.3:31742/'
order-api v2 on order-api-5b8d7c9f2-p4r7t

읽을 것 — ClusterIP는 그대로이고 31742가 추가됐다. 컨트롤 플레인 노드(파드가 없는 노드)의 IP로 들어가도 워커의 파드가 응답한다. kube-proxy 규칙이 모든 노드에 있기 때문이다. macOS에서 localhost:31742는 kind 프로비저너에서 열리지 않는다. 노드는 VM 안의 컨테이너이고 그 포트는 macOS에 게시되지 않았다. 그래서 다음 단계가 필요하다.

$ kubectl patch svc order-api -p '{"spec":{"type":"LoadBalancer"}}'
$ sleep 5 && kubectl get svc order-api
NAME        TYPE           CLUSTER-IP    EXTERNAL-IP   PORT(S)          AGE
order-api   LoadBalancer   10.96.34.18   localhost     8080:31742/TCP   21m

# macOS 터미널에서
$ for i in 1 2 3 4 5 6; do curl -s localhost:8080/; done

order-api v2 on order-api-5b8d7c9f2-p4r7t

order-api v2 on order-api-5b8d7c9f2-p4r7t

$ docker ps --format '{{.Names}}\t{{.Image}}' | grep -i envoy

읽을 것 — EXTERNAL-IP가 localhost다. Docker Desktop이 Envoy 컨테이너를 하나 띄워 NodePort로 이어 줬다. 이제 macOS에서 서비스로 들어가고, 여섯 번의 curl이 여러 파드로 흩어진다. 어제 port-forward로는 볼 수 없던 장면이다. 서비스는 이 상태(LoadBalancer)로 두고 간다. D6에서 Gateway API를 올린 뒤 다시 ClusterIP로 되돌린다.

트래픽을 흘리면서 롤링 업데이트를 한 번 다시 본다.

# 터미널 A
$ while true; do curl -s -m 1 localhost:8080/ || echo "FAIL $(date +%T)"; sleep 0.3; done
# 터미널 B
$ kubectl rollout restart deployment/order-api
$ kubectl rollout status deployment/order-api

읽을 것 — 호스트명이 새 파드 이름으로 하나씩 바뀐다. 중간에 FAIL이나 빈 줄이 몇 개 섞일 수 있다. 새 파드의 컨테이너가 떴지만 Spring Boot가 아직 포트를 열기 전에 엔드포인트에 들어가기 때문이다. 이 빈틈을 D8의 readinessProbe가 막는다. 오늘은 빈틈이 있다는 사실만 확인하고 터미널 A를 Ctrl-C로 끝낸다.

actuator gateway 엔드포인트는 열지 않는다

D11에서 actuator를 붙일 때 management.endpoints.web.exposure.include에 gateway를 넣지 않는다. 그 엔드포인트가 열려 있고 인증이 없으면 라우트를 원격에서 조작할 수 있다(CVE-2025-41243). 메트릭은 prometheus만 연다.

4체크포인트

문서를 덮고 진행한다.

  1. gateway 서비스의 ClusterIP·NodePort·EXTERNAL-IP 세 값을 읽고, 각각 어디서 닿는 주소인지 말한다.
  2. 임시 파드에서 order-api를 반복 호출해 서로 다른 두 노드의 파드가 응답했음을 -o wide와 대조해 보인다.
  3. 서비스 셀렉터를 일부러 틀리게 한 뒤 describe svc·get endpointslices·get pods -l 세 명령으로 원인을 찾아 고친다.
  4. default 네임스페이스의 파드에서 order-api가 안 풀리고 order-api.study가 풀리는 이유를 /etc/resolv.conf로 설명한다.
  5. 노드의 라우팅 테이블에서 다른 노드 파드 CIDR로 가는 줄 하나를 가리킨다.

5개 중 4개 이상이면 D6으로 간다. 3번이 막히면 4단계의 진단 순서를 다시 본다.

오늘 서비스 두 개가 각각 localhost:8080, localhost:8081을 차지했다. 서비스가 열 개면 포트 열 개다. 내일은 진입점 하나(80번)를 세우고 경로(/orders, /)와 호스트로 나누는 Gateway API를 올린다. 서비스는 전부 ClusterIP로 되돌리고 Gateway 뒤로 숨긴다.
