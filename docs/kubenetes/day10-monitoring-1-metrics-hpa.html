오늘의 대시보드는 USE다. 노드와 파드의 CPU·메모리·네트워크. RED는 앱이 요청을 세어야 하므로 D11에서 Micrometer를 붙인 뒤 만든다. 대시보드를 열었을 때 "이 패널은 USE의 U인가 RED의 D인가"를 붙여 보면 무엇이 빠졌는지 보인다.

1.3 쿠버네티스 메트릭의 층

지표는 여러 곳에서 나오고, 소비자도 둘이다. 짧은 수명의 현재값을 쓰는 리소스 메트릭 파이프라인과, 저장해서 그래프로 보는 Prometheus 파이프라인이 나란히 있다.

1.4 Prometheus 모델 다섯 가지

  • pull — 앱이 보내지 않는다. Prometheus가 /metrics를 주기적으로 긁어 간다. 대상이 죽으면 up=0이 남는다.
  • 시계열 — 이름 + 라벨 집합이 하나의 시계열. container_cpu_usage_seconds_total{namespace="study", pod="order-api-…"}.
  • 타입 — counter(누적, 줄지 않음), gauge(현재값), histogram(구간별 누적 + 합계·개수). 요청 수는 counter, 메모리는 gauge, 지연 시간은 histogram.
  • rate — counter는 그대로 그리면 우상향 직선이라 의미가 없다. rate(x[5m])로 초당 증가량을 본다.
  • 집계 — sum by (pod) (…). 라벨을 남기고 나머지를 합친다.

오늘 쓰는 PromQL은 이 다섯으로 충분하다. D11에서 histogram_quantile 하나를 더한다.

1.5 HPA

HPA는 리소스 메트릭 API(도판 1의 주황 경로)에서 파드들의 CPU 사용량을 읽어 목표 사용률에 맞게 replicas를 조절한다. 사용률은 requests 대비다. D8에서 requests를 250m으로 잡았으므로 "50%"는 파드당 125m을 뜻한다. 계산은 원하는 개수 = ceil(현재 개수 × 현재 사용률 / 목표 사용률)이고, 15초마다 평가한다. 늘리는 것은 즉시, 줄이는 것은 기본 5분 안정화 창을 두어 튀는 것을 막는다. HPA가 replicas를 소유하므로 디플로이먼트 파일에서는 replicas를 빼야 apply할 때 충돌하지 않는다.

# 터미널 A
$ kubectl -n monitoring port-forward svc/kps-kube-prometheus-stack-prometheus 9090:9090

# 터미널 B — HTTP API로 같은 것을 조회
$ q() { curl -s "localhost:9090/api/v1/query" --data-urlencode "query=$1" | python3 -c 'import sys,json; r=json.load(sys.stdin)["data"]["result"]; [print(x["metric"].get("job",x["metric"].get("pod","")), x["value"][1]) for x in r[:8]]'; }
$ q 'count by (job) (up == 1)'
apiserver 1
coredns 2
kube-state-metrics 1
kubelet 3
node-exporter 3
prometheus 1
...

읽을 것 — up은 Prometheus가 대상마다 자동으로 만드는 지표다. 1이면 긁혔고 0이면 못 긁었다. kubelet 3, node-exporter 3은 노드 수다. 셸 함수 q는 오늘 계속 쓴다. 이 API가 곧 Grafana가 부르는 것이다.

2PromQL 다섯 개

1.4절의 다섯 요소를 하나씩 쓴다. 출력은 시각에 따라 다르다.

# (1) 재시작 수 — counter, kube-state-metrics가 낸다
$ q 'sum by (pod) (kube_pod_container_status_restarts_total{namespace="study"} > 0)'
(D8·D9에서 재시작된 파드가 남아 있으면 보인다. 없으면 빈 출력)

# (2) 노드 메모리 여유 — gauge, node-exporter
$ q 'node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes'
node-exporter 0.81
node-exporter 0.79
node-exporter 0.80

# (3) 컨테이너 CPU — counter를 rate로, 파드별 합계 (cAdvisor via kubelet)
$ q 'sum by (pod) (rate(container_cpu_usage_seconds_total{namespace="study", container!=""}[5m]))'
gateway-… 0.003
order-api-… 0.004
order-api-… 0.004
postgres-0 0.002
...

# (4) 디플로이먼트 가용 레플리카 — gauge, kube-state-metrics
$ q 'kube_deployment_status_replicas_available{namespace="study"}'
gateway 2
order-api 4
order-api-canary 1

# (5) CPU 사용률을 requests 대비로 — 두 지표를 나눈다 (HPA가 보는 값과 같은 뜻)
$ q 'sum by (pod) (rate(container_cpu_usage_seconds_total{namespace="study", container="app"}[2m])) / sum by (pod) (kube_pod_container_resource_requests{namespace="study", container="app", resource="cpu"})'
order-api-… 0.016
order-api-… 0.015
...

읽을 것 — (3)과 (5)의 container!=""·container="app"은 파드 전체 합계 행(container 라벨이 빈 것)과 pause 컨테이너를 빼기 위한 필터다. (5)가 1.6%라는 것은 250m 중 4m을 쓴다는 뜻이고, 이 값이 HPA 목표(50%)에 닿으려면 부하가 30배는 필요하다. 5단계에서 그 부하를 만든다. 지표 이름은 localhost:9090/graph의 자동완성이나 curl localhost:9090/api/v1/label/__name__/values로 찾는다.

3Grafana 내장 대시보드 읽기

같은 지표를 그래프로. 어느 패널이 어느 PromQL인지 확인한다.

# 터미널 C
$ kubectl -n monitoring port-forward svc/kps-grafana 3000:80

http://localhost:3000 → admin / study. 왼쪽 Dashboards에서 세 개를 순서대로 연다.

  1. Node Exporter / Nodes — 노드를 고르면 CPU·부하·메모리·디스크·네트워크. USE의 U와 S. 2.1절의 kubectl top nodes와 CPU 값이 대략 맞는지 본다.
  2. Kubernetes / Compute Resources / Namespace (Pods) — 네임스페이스 study를 고른다. 파드별 CPU·메모리를 requests·limits와 함께 보여 준다. order-api의 메모리가 limit 512Mi 중 얼마인지, CPU가 requests 250m 중 얼마인지 읽는다.
  3. Kubernetes / Compute Resources / Pod — 파드 하나를 고르면 컨테이너별 시계열. 아래 postgres-0을 골라 D9에서 재시작한 시각 부근의 끊김을 찾아본다.

아무 패널의 제목을 눌러 Edit을 열면 PromQL이 보인다. 2단계 (3)과 거의 같은 식이 들어 있다. 대시보드는 마법이 아니라 쿼리 묶음이다.

읽을 것 — 패널마다 "이건 USE의 무엇인가"를 붙여 본다. 지금 있는 대시보드에는 RED가 하나도 없다. 요청 수·오류율·지연은 쿠버네티스가 모르기 때문이다. 그것이 D11의 일이다.

4HPA를 건다

디플로이먼트 파일에서 replicas를 빼고, HPA가 소유하게 한다.

$ cd ~/k8s-study/week1
$ sed -i.bak '/^  replicas: 4$/d' 20-order-api-deploy.yaml && rm 20-order-api-deploy.yaml.bak
$ grep -c '^  replicas' 20-order-api-deploy.yaml
0
$ cat > 24-order-api-hpa.yaml <<'EOF'
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: order-api
  namespace: study
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: order-api
  minReplicas: 2
  maxReplicas: 8
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 50
  behavior:
    scaleDown:
      stabilizationWindowSeconds: 60
EOF
$ kubectl apply -f 24-order-api-hpa.yaml -f 20-order-api-deploy.yaml
$ sleep 30 && kubectl get hpa order-api
NAME        REFERENCE              TARGETS       MINPODS   MAXPODS   REPLICAS   AGE
order-api   Deployment/order-api   cpu: 2%/50%   2         8         2          30s
$ kubectl get deploy order-api
NAME        READY   UP-TO-DATE   AVAILABLE   AGE
order-api   2/2     2            2           6d

읽을 것 — 파일에서 replicas를 뺐으므로 apply가 4를 건드리지 않았고, HPA가 사용률 2%를 보고 minReplicas 2로 줄였다. TARGETS의 2%가 2단계 (5)와 같은 값이다. stabilizationWindowSeconds를 60으로 줄인 것은 실습 시간 때문이다. 운영 기본값은 300초다.

  Normal  SuccessfulRescale  2m    horizontal-pod-autoscaler  New size: 6; reason: cpu resource utilization (percentage of request) above target

읽을 것 — 141%는 "requests 250m의 1.41배 = 352m을 쓴다"는 뜻이다. 계산 ceil(2 × 141 / 50) = 6으로 한 번에 6이 됐고, 다시 계산해 8(상한)까지 갔다. D8의 토폴로지 제약 덕에 8개가 4:4로 놓였다. 부하가 계속되는데 8에서 멈춘 것은 maxReplicas 때문이고, 사용률이 39%로 내려간 것은 8개가 나눠 받기 때문이다. Grafana의 Namespace (Pods) 대시보드를 이 시점에 보면 order-api CPU 그래프가 계단처럼 오른 것이 보인다.

$ kubectl delete -f ~/k8s-study/day10/load.yaml
# 터미널 D — 60초 안정화 뒤
order-api   Deployment/order-api   cpu: 3%/50%    2         8         8          8m
order-api   Deployment/order-api   cpu: 2%/50%    2         8         2          9m

읽을 것 — 부하를 빼자 사용률은 곧 2%로 떨어졌지만 replicas는 60초를 기다린 뒤 2로 내려갔다. 안정화 창이 없으면 잠깐의 정적에도 줄였다가 다시 늘리는 진동이 생긴다. Grafana에서 늘어난 시각과 줄어든 시각을 찾아 그 사이 간격을 읽어 둔다. 터미널 D는 Ctrl-C.

6기록: 지금 클러스터의 숫자 다섯 개

D11·D14에서 "정상일 때는 얼마였나"가 필요하다. 지금 적어 둔다.

$ q 'sum(kube_pod_status_phase{phase="Running"})'
 34
$ q 'sum(node_memory_MemTotal_bytes - node_memory_MemAvailable_bytes) / 1024/1024/1024'
 4.6
$ q 'sum(rate(container_cpu_usage_seconds_total{container!=""}[5m]))'
 0.42
$ q 'count(up == 0)'
 0    ← 또는 kind에서 못 긁는 컨트롤 플레인 대상 수
$ q 'sum by (namespace) (kube_pod_container_status_restarts_total) > 0'

읽을 것 — 이 다섯 줄이 클러스터의 평상시 기준선이다. D14에서 장애를 넣었을 때 어느 숫자가 먼저 움직이는지 본다. 값은 환경마다 다르다. 자기 값을 ~/k8s-study/day10/baseline.txt에 적어 둔다.

4체크포인트

  1. kubectl top pods -n study의 CPU 값이 어느 컴포넌트를 거쳐 오는지 순서대로 말한다.
  2. PromQL로 study 네임스페이스 파드별 메모리 사용량(container_memory_working_set_bytes)을 파드별 합계로 조회한다.
  3. Grafana에서 order-api 파드 하나의 CPU 패널을 열어 그 PromQL을 읽고, rate가 왜 들어 있는지 설명한다.
  4. 부하를 걸어 HPA가 replicas를 늘리는 과정을 get hpa -w와 Grafana 그래프 양쪽에서 같은 시각으로 보인다.
  5. 부하를 뺀 뒤 replicas가 바로 줄지 않는 이유를 필드 이름으로 말한다.

5개 중 4개 이상이면 D11로 간다. 2번이 막히면 2단계 (3)의 필터를 그대로 두고 지표 이름만 바꾼다.
