1이론

1.1 볼륨의 수명은 무엇에 묶이나

볼륨수명용도
emptyDir파드. 파드가 사라지면 함께 사라진다. 노드 재시작에도 사라진다.같은 파드 안 컨테이너끼리 파일 공유, 임시 캐시

1.2 PVC · PV · StorageClass

앱 개발자는 "10Gi, 읽기쓰기 가능, 빠른 디스크"라고 요청(PVC)만 쓴다. 어느 스토리지 시스템에서 어떻게 만들지는 모른다. PV(PersistentVolume)는 실제 저장소 하나를 나타내는 클러스터 범위 오브젝트다. 스토리지클래스(StorageClass)는 "이런 요청이 오면 이 프로비저너로 이렇게 만들어라"는 정책이고, 그 프로비저너가 CSI(Container Storage Interface) 드라이버다. 클라우드면 디스크 API를 부르고, 이 환경에서는 노드 디렉터리를 하나 만든다. 앱 매니페스트는 클라우드든 노트북이든 같다. 스토리지클래스만 다르다.

1.3 세 가지 속성

속성값
접근 모드 accessModesReadWriteOnce(한 노드에서 읽기쓰기, 대부분의 블록 디스크) · ReadWriteMany(여러 노드, NFS 류) · ReadOnlyMany · ReadWriteOncePod(한 파드만). DB는 RWO 또는 RWOP.
회수 정책 reclaimPolicyPVC를 지웠을 때 PV를 Delete(디스크까지 삭제)할지 Retain(PV와 디스크를 남기고 수동 정리)할지. 동적 프로비저닝의 기본은 Delete. 운영 DB는 Retain을 고려한다.
바인딩 시점 volumeBindingModeImmediate(PVC 생성 즉시) 또는 WaitForFirstConsumer(파드가 스케줄될 때). 후자는 파드가 갈 노드를 보고 그 노드의 디스크를 만든다. 로컬 디스크 계열은 반드시 후자.

이 환경의 standard 클래스는 노드의 로컬 디렉터리를 쓰는 local-path 프로비저너다. 그래서 PV에 nodeAffinity가 붙고, 그 PVC를 쓰는 파드는 그 노드에만 갈 수 있다. 노드가 사라지면 데이터도 사라진다. 클라우드의 네트워크 디스크는 노드를 옮겨 다닌다. 개념은 같고 내구성이 다르다.

1.4 StatefulSet: 이름과 디스크가 고정되는 파드

디플로이먼트의 파드는 이름이 랜덤이고 서로 바꿔 쓸 수 있다. DB는 다르다. "1번 인스턴스"가 죽으면 "1번의 디스크"를 가진 "1번"이 돌아와야 한다. 스테이트풀셋(StatefulSet)은 그것을 보장한다.

  • 고정 이름 — postgres-0, postgres-1. 재생성돼도 같은 이름.
  • 파드별 PVC — volumeClaimTemplates로 파드마다 PVC를 하나씩 만들고(data-postgres-0), 파드가 재생성되면 같은 PVC를 다시 붙인다. 스테이트풀셋을 지워도 PVC는 남는다(persistentVolumeClaimRetentionPolicy로 조정).
  • 순서 — 0번이 Ready가 된 뒤 1번을 만든다. 줄일 때는 역순.
  • 고정 DNS — 헤드리스 서비스(D5)와 짝을 이뤄 postgres-0.postgres.study.svc.cluster.local처럼 파드 하나를 이름으로 지목할 수 있다.

1.5 DB를 클러스터 안에 둘 것인가

스테이트풀셋 하나로 올린 PostgreSQL은 단일 인스턴스다. 복제본을 2로 늘려도 두 번째 파드는 독립된 빈 DB일 뿐 레플리카가 아니다. 복제·장애 조치·백업·업그레이드는 DB의 규칙을 아는 오퍼레이터(Operator)(CloudNativePG, Crunchy 등)가 CRD로 관리하거나, 관리형 DB(RDS 등)를 클러스터 밖에 두고 D5의 ExternalName으로 연결한다. 오늘의 단일 인스턴스는 개발·실습·소규모 내부 도구 수준이며, 그 한계를 7단계에서 직접 본다.

$ cat > src/main/java/study/OrderApiApplication.java <<'EOF'
package study;

import java.util.List;
import java.util.Map;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.jdbc.core.simple.JdbcClient;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RequestBody;
import org.springframework.web.bind.annotation.RestController;

@SpringBootApplication
@RestController
public class OrderApiApplication {

    private final JdbcClient jdbc;

    @Value("${store.name:unset}")
    private String storeName;

    @Value("${store.region:unset}")
    private String storeRegion;

    @Value("${api.key:unset}")
    private String apiKey;

    public OrderApiApplication(JdbcClient jdbc) {
        this.jdbc = jdbc;
    }

    public static void main(String[] args) {
        SpringApplication.run(OrderApiApplication.class, args);
    }

    @GetMapping("/")
    public String root() {
        return "order-api " + version() + " on " + host() + "\n";
    }

    @GetMapping("/orders")
    public Map<String, Object> orders() {
        List<Map<String, Object>> rows = jdbc
            .sql("SELECT id, item FROM orders ORDER BY id")
            .query().listOfRows();
        return Map.of("version", version(), "host", host(), "orders", rows);
    }

    @PostMapping("/orders")
    public Map<String, Object> create(@RequestBody Map<String, String> body) {
        int n = jdbc.sql("INSERT INTO orders(item) VALUES (:item)")
            .param("item", body.getOrDefault("item", "unknown"))
            .update();
        return Map.of("inserted", n, "host", host());
    }

    @GetMapping("/config")
    public Map<String, Object> config() {
        return Map.of(
            "version", version(),
            "host", host(),
            "store.name", storeName,
            "store.region", storeRegion,
            "api.key", mask(apiKey));
    }

    private static String mask(String s) {
        if (s == null || s.length() < 4) return "****";
        return s.substring(0, 2) + "****" + s.substring(s.length() - 2);
    }

    private static String version() {
        String v = System.getenv("APP_VERSION");
        return v == null ? "dev" : v;
    }

    private static String host() {
        String h = System.getenv("HOSTNAME");
        return h == null ? "unknown" : h;
    }
}
EOF

D3의 사이드카 파드에 공유 볼륨을 붙인다. 한 컨테이너가 쓰고 다른 컨테이너가 읽는다.

apiVersion: v1
kind: Pod

  name: emptydir-demo
spec:
  containers:
  - name: writer

PVC를 만들고 파드에 붙였다 떼며 PV·데이터·노드 디렉터리가 어느 시점에 생기고 남는지 본다.

읽을 것 — PVC는 처음에 Pending이었다. WaitForFirstConsumer라서 파드가 스케줄될 때 그 노드에 디렉터리를 만들고 PV를 생성해 Bound가 됐다. 노드 컨테이너 안에 실제 파일이 있다. 파드를 지워도 PVC는 Bound 그대로이고, 다시 만든 파드에는 두 줄이 있다. 두 번째 파드도 desktop-worker에 갔다. PV의 nodeAffinity 때문이며, 로컬 디스크 스토리지의 제약이다.

$ docker exec desktop-worker sh -c 'ls /var/local-path-provisioner/ | grep -c demo-data || true'
0

읽을 것 — PVC를 지우자 reclaimPolicy: Delete대로 PV와 노드 디렉터리까지 사라졌다. 운영 DB라면 PVC 삭제 한 번이 데이터 삭제다. Retain 정책이거나 백업이 있어야 한다.

3PostgreSQL 스테이트풀셋 + 헤드리스 서비스

비밀번호는 시크릿, 데이터는 volumeClaimTemplates. D8에서 예고한 대로 requests = limits로 Guaranteed.

$ cat > ~/k8s-study/week1/12-postgres.yaml <<'EOF'
apiVersion: v1
kind: Secret
metadata:
  name: postgres-secret
  namespace: study
type: Opaque
stringData:
  POSTGRES_USER: orders
  POSTGRES_PASSWORD: orders-pw-2026
  POSTGRES_DB: orders
---
apiVersion: v1
kind: Service
metadata:
  name: postgres
  namespace: study
spec:
  clusterIP: None
  selector:
    app: postgres
  ports:
  - port: 5432
    targetPort: 5432
---
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: postgres
  namespace: study
spec:
  serviceName: postgres
  replicas: 1
  selector:
    matchLabels:
      app: postgres
  template:
    metadata:
      labels:
        app: postgres
    spec:
      terminationGracePeriodSeconds: 30
      containers:
      - name: postgres
        image: postgres:18
        ports:
        - containerPort: 5432
        envFrom:
        - secretRef:
            name: postgres-secret
        resources:
          requests:
            cpu: 500m
            memory: 512Mi
          limits:
            cpu: 500m
            memory: 512Mi
        readinessProbe:
          exec:
            command: ["pg_isready", "-U", "orders", "-d", "orders"]
          periodSeconds: 5
        livenessProbe:
          exec:
            command: ["pg_isready", "-U", "orders", "-d", "orders"]
          periodSeconds: 15
          failureThreshold: 3
        volumeMounts:
        - name: data
          mountPath: /var/lib/postgresql
  volumeClaimTemplates:
  - metadata:
      name: data
    spec:
      accessModes: [ReadWriteOnce]
      resources:
        requests:
          storage: 1Gi
EOF

Address 1: 10.244.2.21 postgres-0.postgres.study.svc.cluster.local

읽을 것 — 파드 이름이 postgres-0, PVC 이름이 data-postgres-0(템플릿명-스테이트풀셋명-순번). 서비스의 CLUSTER-IP가 None인 헤드리스라 postgres-0.postgres가 파드 IP로 직접 풀린다. postgres만 치면 파드들의 IP 목록이 돌아온다(지금은 하나). QoS가 Guaranteed다. requests와 limits를 같게 준 유일한 워크로드다.

4D1의 실험을 클러스터에서: 파드를 지워도 데이터는 남는다

$ kubectl exec postgres-0 -- psql -U orders -d orders -c "CREATE TABLE t(v text); INSERT INTO t VALUES ('before delete');"
INSERT 0 1
$ kubectl delete pod postgres-0 --wait=true

$ kubectl rollout status statefulset/postgres
$ kubectl get pod postgres-0 -o jsonpath='{.metadata.name} age={.metadata.creationTimestamp} pvc={.spec.volumes[0].persistentVolumeClaim.claimName}{"\n"}'
postgres-0 age=2026-08-30T03:52:40Z pvc=data-postgres-0
$ kubectl exec postgres-0 -- psql -U orders -d orders -tAc "SELECT v FROM t;"
before delete
$ kubectl exec postgres-0 -- psql -U orders -d orders -c "DROP TABLE t;"

읽을 것 — 새로 만들어진 파드인데(creationTimestamp가 방금) 이름도 postgres-0, PVC도 data-postgres-0이고 행이 남아 있다. 디플로이먼트였다면 이름이 바뀌고 PVC를 다시 붙여야 했다. 이것이 스테이트풀셋이 보장하는 "1번은 1번의 디스크로 돌아온다"이다.

# DB 파드를 지워도 API는 회복된다

6고장: 쓰는 중인 PVC를 지우면

삭제가 Terminating에서 멈춘다. 이유는 finalizer다.

$ kubectl delete pvc data-postgres-0 --wait=false
persistentvolumeclaim "data-postgres-0" deleted
$ kubectl get pvc data-postgres-0
NAME              STATUS        VOLUME       CAPACITY   ACCESS MODES   STORAGECLASS   AGE
data-postgres-0   Terminating   pvc-8b2d…    1Gi        RWO            standard       15m
$ kubectl get pvc data-postgres-0 -o jsonpath='{.metadata.finalizers}{"\n"}'
["kubernetes.io/pvc-protection"]
$ kubectl exec postgres-0 -- psql -U orders -d orders -tAc "SELECT count(*) FROM orders;"
2

읽을 것 — "deleted"라고 찍혔지만 PVC는 Terminating으로 살아 있고 DB도 정상이다. pvc-protection finalizer가 "이 PVC를 쓰는 파드가 있는 한 실제 삭제를 보류"한다. 파드가 사라지는 순간 삭제가 진행되고 데이터가 없어진다. 즉 지금 이 PVC는 시한폭탄이다. 되돌릴 방법은 없다(삭제 표시는 취소되지 않는다). 새 PVC로 데이터를 옮기거나, 실습이므로 스테이트풀셋과 함께 지우고 다시 만든다.

$ kubectl delete statefulset postgres --wait=true
$ sleep 5 && kubectl get pvc data-postgres-0 2>&1 | tail -1
Error from server (NotFound): persistentvolumeclaims "data-postgres-0" not found
$ kubectl apply -f 12-postgres.yaml && kubectl rollout status statefulset/postgres
$ kubectl rollout restart deployment/order-api && kubectl rollout status deployment/order-api
$ curl -s localhost/orders | grep -o '"orders":\[.*\]'
"orders":[]

읽을 것 — 파드가 사라지자 보류됐던 삭제가 실행됐고, 새 스테이트풀셋은 새 PVC를 만들어 빈 DB로 시작했다. 주문 두 건이 없어졌다. order-api를 재시작한 이유는 schema.sql이 시작 시에만 돌기 때문이다. finalizer는 PVC뿐 아니라 네임스페이스·CRD 등 여러 오브젝트에 있으며, Terminating에서 멈춘 오브젝트를 만나면 .metadata.finalizers를 먼저 본다.

7복제본 2는 레플리카가 아니다

스테이트풀셋을 2로 늘려 순서·PVC·데이터 독립성을 본 뒤 되돌린다.

$ curl -s -X POST -H 'Content-Type: application/json' -d '{"item":"monitor"}' localhost/orders >/dev/null
$ kubectl scale statefulset/postgres --replicas=2
$ kubectl get pods -l app=postgres -w
NAME         READY   STATUS              RESTARTS   AGE
postgres-0   1/1     Running             0          3m
postgres-1   0/1     Pending             0          0s
postgres-1   0/1     ContainerCreating   0          1s
postgres-1   1/1     Running             0          8s
^C
$ kubectl get pvc -l app=postgres
NAME              STATUS   VOLUME      CAPACITY   ACCESS MODES   STORAGECLASS   AGE
data-postgres-0   Bound    pvc-c1d2…   1Gi        RWO            standard       4m
data-postgres-1   Bound    pvc-e3f4…   1Gi        RWO            standard       20s
$ kubectl exec postgres-0 -- psql -U orders -d orders -tAc "SELECT count(*) FROM orders;"
1
$ kubectl exec postgres-1 -- psql -U orders -d orders -tAc "SELECT count(*) FROM orders;"
ERROR:  relation "orders" does not exist

$ kubectl scale statefulset/postgres --replicas=1
$ sleep 15 && kubectl get pods,pvc -l app=postgres
NAME             READY   STATUS    RESTARTS   AGE
pod/postgres-0   1/1     Running   0          5m

NAME                                    STATUS   VOLUME      CAPACITY   ACCESS MODES   STORAGECLASS   AGE
persistentvolumeclaim/data-postgres-0   Bound    pvc-c1d2…   1Gi        RWO            standard       5m
persistentvolumeclaim/data-postgres-1   Bound    pvc-e3f4…   1Gi        RWO            standard       1m
$ kubectl delete pvc data-postgres-1

읽을 것 — postgres-1은 0번 뒤에 순서대로 생겼고 자기 PVC를 따로 받았다. 그리고 빈 DB다. 테이블조차 없다. 스테이트풀셋은 "이름과 디스크를 고정한 파드 N개"를 줄 뿐 데이터 복제는 모른다. 복제는 PostgreSQL의 스트리밍 복제 설정이 필요하고, 그것을 자동화하는 것이 오퍼레이터다. 1로 줄이자 파드는 사라졌지만 PVC data-postgres-1은 남았다. 다시 2로 늘리면 그 디스크가 돌아온다. 오늘은 손으로 지운다.

4체크포인트

  1. PVC를 만들고 파드에 붙여 파일을 쓴 뒤, 파드를 지우고 새 파드에서 그 파일을 읽는다. PV가 어느 노드의 어느 경로인지 말한다.
  2. DB 파드를 지운 뒤 재기동한 파드에서 이전 주문 데이터가 curl localhost/orders로 조회된다.
  3. postgres-0.postgres가 풀리는 이유(헤드리스)와 order-api가 풀리는 방식(ClusterIP)의 차이를 말한다.
  4. PVC 삭제가 Terminating에 멈추는 원인 필드를 가리키고, 그 상태가 왜 위험한지 말한다.
  5. 스테이트풀셋 복제본 2의 두 번째 파드가 왜 빈 DB인지 설명한다.

5개 중 4개 이상이면 D10으로 간다. 2번이 안 되면 4단계의 PVC 이름을 다시 확인한다.
