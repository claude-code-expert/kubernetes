쿠버네티스 14일 · 4단계 보안과 자동화 · Day 12

누가 무엇을 할 수 있나 — RBAC·파드 시큐리티·네트워크 정책·어드미션

D7에서 시크릿이 get secret -o yaml 한 줄로 열리는 것을 봤다. 진짜 보호막은 인코딩이 아니라 접근 권한이다. API 서버로 오는 요청은 세 관문을 순서대로 지난다. 누구인가(인증), 해도 되는가(인가), 내용이 규칙에 맞는가(어드미션). 오늘은 세 관문을 하나씩 만지고, 파드가 노드에서 할 수 있는 일을 제한하고, 파드끼리의 통신을 제한하는 정책을 쓴다. 그리고 관문을 통과한 이미지에 latest 태그가 없도록 클러스터가 스스로 거부하게 한다.

오늘 끝나면 할 수 있는 것

  1. 요청 하나가 인증 → 인가 → 어드미션을 지나는 순서를 말하고, 각 관문에서 거부됐을 때의 오류 메시지를 구분한다.
  2. 파드는 조회되지만 시크릿은 Forbidden인 계정을 만들어 kubectl과 Headlamp 양쪽에서 확인한다.
  3. 파드 안에서 ServiceAccount 토큰으로 API 서버를 호출해 보고, 필요 없는 토큰 마운트를 끈다.
  4. Pod Security Admission의 세 수준을 네임스페이스 라벨로 걸고, restricted에서 거부되는 파드를 securityContext로 고친다.
  5. NetworkPolicy를 쓰고 이 CNI에서 집행되지 않음을 확인하며, ValidatingAdmissionPolicy로 latest 태그를 거부한다.

1이론

1.1 세 관문

1.2 인증: 사람과 파드의 신분

사람은 kubeconfig의 클라이언트 인증서(D2에서 본 docker-desktop 사용자가 이것이다)나 외부 IdP의 OIDC 토큰으로 인증한다. 쿠버네티스에는 사용자 오브젝트가 없다. 인증서의 CN이 곧 사용자명이고 O가 그룹이다. 파드는 서비스어카운트(ServiceAccount)로 인증한다. 네임스페이스마다 default SA가 있고, 파드는 명시하지 않으면 그것을 쓴다. kubelet이 파드에 단기 토큰(기본 1시간, 자동 갱신)을 /var/run/secrets/kubernetes.io/serviceaccount/token에 넣어 주고, 파드는 그것으로 API 서버에 말할 수 있다. 사용자명은 system:serviceaccount:<ns>:<name>이다.

API를 부를 일이 없는 앱(order-api·gateway가 그렇다)에 토큰이 마운트되어 있으면 공격 표면일 뿐이다. automountServiceAccountToken: false로 끈다.

1.3 인가: RBAC 네 오브젝트

오브젝트범위뜻
Role네임스페이스동사(get·list·watch·create·update·patch·delete)와 리소스의 목록. "무엇을 할 수 있나"
ClusterRole클러스터같은 것을 클러스터 범위로. 노드·네임스페이스 같은 비네임스페이스 리소스는 여기에만 적을 수 있다
RoleBinding네임스페이스Role 또는 ClusterRole을 주체(사용자·그룹·SA)에게 그 네임스페이스 안에서 준다
ClusterRoleBinding클러스터ClusterRole을 클러스터 전체에서 준다. D3에서 Headlamp에 cluster-admin을 이렇게 줬다

Role을 만드는 것만으로는 아무도 권한을 갖지 않는다. 바인딩이 범위를 정한다. 같은 ClusterRole(예: 내장 view)을 RoleBinding으로 묶으면 네임스페이스 하나에서만, ClusterRoleBinding으로 묶으면 전부에서 유효하다. RBAC은 허용만 쌓인다. 거부 규칙이 없으므로 권한은 최소로 시작해 필요한 만큼만 더한다. 시크릿에 list를 주면 그 네임스페이스의 비밀이 전부 열린다는 것을 기억한다.

1.4 어드미션: 내용을 검사한다

RBAC은 "파드를 만들 수 있나"까지만 본다. YAML 안에 privileged: true가 있는지는 보지 않는다. 특권 컨테이너 하나면 그 노드의 모든 비밀이 열리므로, 내용을 검사하는 관문이 따로 있다.

수단방식오늘
Pod Security Admission내장. 네임스페이스 라벨로 privileged / baseline / restricted 세 수준을 enforce(거부)·audit(감사 로그)·warn(경고) 세 모드로 건다. 파드 spec만 본다.4·5단계
ValidatingAdmissionPolicy내장. CEL 표현식으로 아무 리소스나 검증. 웹훅 서버가 필요 없다. 정책과 바인딩이 분리돼 같은 정책을 여러 범위에 다른 모드(Deny·Warn·Audit)로 건다.7단계
Kyverno외부 정책 엔진(CNCF Graduated). YAML로 검증·변경·생성·이미지 서명 검증까지. 웹훅으로 동작.비교표
OPA Gatekeeper외부. Rego 언어. 감사 리포트가 강점.비교표

선택 기준은 단순하다. 파드 보안 기준선은 PSA로(무료, 내장, 표준). 그 밖의 검증(태그 금지, 라벨 필수, 리소스 필수)은 VAP로. 변경(기본값 주입)·생성·서명 검증이 필요해지면 그때 Kyverno를 본다.

1.5 PSA 세 수준

수준금지하는 것우리 파드
privileged없음. 제한 없음.—
baselineprivileged 컨테이너, hostPath·hostNetwork·hostPID, 위험한 capability 추가, 기본 seccomp 해제전부 통과
restrictedbaseline + root 실행 금지, 권한 상승 금지, capability 전부 drop, seccomp RuntimeDefault 필수securityContext 없이는 전부 거부

1.6 NetworkPolicy

네트워크 정책은 파드 단위의 방화벽이다. 기본은 전부 허용이고, 어떤 파드를 선택하는 정책이 하나라도 생기면 그 파드는 정책에 적힌 것 외에는 거부된다(정책이 있는 방향에 한해). 규칙은 D3의 라벨 셀렉터로 쓴다. 단, 이것은 명세이고 집행은 CNI 플러그인이 한다. kind의 기본 kindnet은 라우팅만 하고 정책을 집행하지 않는다. 오브젝트는 만들어지지만 아무 일도 안 생긴다. Cilium·Calico로 바꾸면 같은 오브젝트가 그대로 동작한다. 6단계에서 그 사실을 직접 확인한다.

3따라하기

1Role은 종이다: 바인딩 전과 후

개발자 계정 dev-kim(SA로 대신한다)을 만들고, Role을 만든 뒤에도 권한이 없음을 can-i --as로 본다.

$ kubectl create serviceaccount dev-kim
$ cat > rbac-pod-viewer.yaml <<'EOF'
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-viewer
  namespace: study
rules:
- apiGroups: [""]
  resources: ["pods", "pods/log"]
  verbs: ["get", "list", "watch"]
- apiGroups: ["apps"]
  resources: ["deployments", "replicasets"]
  verbs: ["get", "list", "watch"]
EOF
$ kubectl apply -f rbac-pod-viewer.yaml
$ kubectl auth can-i list pods --as=system:serviceaccount:study:dev-kim
no

$ cat > rbac-pod-viewer-binding.yaml <<'EOF'
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: dev-kim-pod-viewer
  namespace: study
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: Role
  name: pod-viewer
subjects:
- kind: ServiceAccount
  name: dev-kim
  namespace: study
EOF
$ kubectl apply -f rbac-pod-viewer-binding.yaml
$ for r in pods secrets configmaps deployments.apps; do printf '%-18s ' $r; kubectl auth can-i list $r --as=system:serviceaccount:study:dev-kim; done
pods               yes
secrets            no
configmaps         no
deployments.apps   yes
$ kubectl auth can-i list pods -n default --as=system:serviceaccount:study:dev-kim
no
$ kubectl auth can-i delete pods --as=system:serviceaccount:study:dev-kim
no

읽을 것 — Role만 있을 때는 no, 바인딩 후 yes. 시크릿·컨피그맵은 Role에 없으니 no, default 네임스페이스는 바인딩 범위 밖이니 no, delete는 동사 목록에 없으니 no. --as는 관리자가 남의 권한을 미리 확인하는 표준 방법이다.

읽을 것 — 403 메시지가 정확하다. 누가(User), 무엇을(동사·리소스·API 그룹), 어디서(네임스페이스). 권한 문제를 만나면 이 한 줄을 그대로 Role과 대조하면 된다. pods/log는 파드의 하위 리소스라 따로 적어야 로그를 볼 수 있다.

같은 토큰으로 Headlamp에 들어간다(D3 7단계의 port-forward를 다시 켠다). echo $TOKEN으로 복사해 로그인하면 네임스페이스 study의 파드와 디플로이먼트는 보이고, Secrets·ConfigMaps 메뉴는 비어 있거나 403을 표시하며, 네임스페이스 선택에서 monitoring을 골라도 아무것도 안 나온다. Headlamp는 kubectl과 같은 관문을 지난다.

4Pod Security Admission: 아무것도 안 하면 아무것도 안 막힌다

study에 baseline을 집행하고 restricted는 경고로 건다. 특권 파드가 거부되는 것을 본다.

# 지금은 아무 제한이 없다
$ cat > ~/k8s-study/day12/privileged-pod.yaml <<'EOF'
apiVersion: v1
kind: Pod
metadata:
  name: privileged-demo
spec:
  containers:
  - name: shell
    image: busybox:1.37
    command: ["sh", "-c", "sleep 3600"]
    securityContext:
      privileged: true
EOF
$ kubectl apply -f ~/k8s-study/day12/privileged-pod.yaml
pod/privileged-demo created
$ kubectl exec privileged-demo -- sh -c 'ls /dev | wc -l; mount | grep -c " / "'
300
1
$ kubectl delete pod privileged-demo --wait=false

읽을 것 — 특권 컨테이너는 노드의 장치를 전부 본다(/dev에 300개). 여기서 노드 디스크를 마운트하면 D9의 PVC 디렉터리든 kubelet 인증서든 다 읽힌다. RBAC은 이것을 막지 못한다. "파드를 만들 권한"이 있는 사람이 만든 것이기 때문이다.

$ cat > 00-namespace.yaml <<'EOF'
apiVersion: v1
kind: Namespace
metadata:
  name: study
  labels:
    pod-security.kubernetes.io/enforce: baseline
    pod-security.kubernetes.io/enforce-version: latest
    pod-security.kubernetes.io/warn: restricted
    pod-security.kubernetes.io/audit: restricted
EOF
$ kubectl apply -f 00-namespace.yaml
Warning: existing pods in namespace "study" violate the new PodSecurity enforce level "baseline:latest"
Warning: privileged-demo (and 0 other pods): privileged   ← 아직 Terminating 중이면 이 줄이 보인다
namespace/study configured
$ kubectl apply -f ~/k8s-study/day12/privileged-pod.yaml
Error from server (Forbidden): error when creating "…/privileged-pod.yaml": pods "privileged-demo" is forbidden: violates PodSecurity "baseline:latest": privileged (container "shell" must not set securityContext.privileged=true)

$ kubectl rollout restart deployment/order-api && kubectl rollout status deployment/order-api
Warning: would violate PodSecurity "restricted:latest": allowPrivilegeEscalation != false (container "app" must set securityContext.allowPrivilegeEscalation=false), unrestricted capabilities (container "app" must set securityContext.capabilities.drop=["ALL"]), runAsNonRoot != true (pod or container "app" must set securityContext.runAsNonRoot=true), seccompProfile (pod or container "app" must set securityContext.seccompProfile.type to "RuntimeDefault" or "Localhost")
deployment.apps/order-api restarted
deployment "order-api" successfully rolled out

읽을 것 — 라벨 네 줄로 네임스페이스에 정책이 걸렸다. 특권 파드는 Forbidden과 함께 어느 필드가 왜 위반인지 적혀 온다. 어드미션 거부는 RBAC 거부와 문장이 다르다("violates PodSecurity"). restricted는 warn이라 롤링 재시작은 성공했지만 경고 네 줄이 나왔다. 그 네 줄이 곧 다음 단계에서 고칠 목록이다. 운영 클러스터에 restricted enforce를 바로 걸면 이 네 줄이 전부 거부가 되어 장애가 난다. warn → 고치기 → enforce 순서다.

5restricted를 통과하도록 securityContext를 고친다

경고 네 줄을 하나씩 없앤다. 그리고 restricted를 enforce하는 별도 네임스페이스에서 거부→통과를 확인한다.

$ python3 - <<'EOF'
sc_pod='''      securityContext:
        runAsNonRoot: true
        runAsUser: 10001
        runAsGroup: 10001
        seccompProfile:
          type: RuntimeDefault
'''
sc_ctr='''        securityContext:
          allowPrivilegeEscalation: false
          capabilities:
            drop: ["ALL"]
'''
for p in ('20-order-api-deploy.yaml','30-gateway.yaml','22-order-api-canary.yaml'):
    t=open(p).read()
    if 'runAsNonRoot' in t: continue
    t=t.replace('      containers:\n', sc_pod+'      containers:\n',1)
    t=t.replace('        ports:\n        - containerPort: 8080\n', sc_ctr+'        ports:\n        - containerPort: 8080\n',1)
    open(p,'w').write(t)
EOF
$ grep -cE 'runAsNonRoot|drop: \["ALL"\]' 20-order-api-deploy.yaml 30-gateway.yaml 22-order-api-canary.yaml
20-order-api-deploy.yaml:2
30-gateway.yaml:2
22-order-api-canary.yaml:2
$ kubectl apply -f 20-order-api-deploy.yaml -f 30-gateway.yaml -f 22-order-api-canary.yaml
deployment.apps/order-api configured      ← 경고 없음
deployment.apps/gateway configured
deployment.apps/order-api-canary configured
$ kubectl rollout status deployment/order-api && kubectl rollout status deployment/gateway
$ POD=$(kubectl get pod -l app=order-api -o jsonpath='{.items[0].metadata.name}')
$ kubectl exec $POD -- id
uid=10001 gid=10001 groups=10001
$ curl -s localhost/orders | cut -c1-60; echo
{"version":"v6","host":"order-api-…","orders":[{"id":1,"it

읽을 것 — 경고가 사라졌고 앱은 UID 10001로 돈다. Temurin JRE 이미지는 root를 요구하지 않으므로 그대로 된다. 포트 8080은 1024 이상이라 비root로 열린다. 80을 쓰는 앱이었다면 포트를 바꾸거나 NET_BIND_SERVICE capability 하나만 더해야 한다. postgres는 13-postgres를 손대지 않았다. baseline은 통과하고 restricted 경고만 남는데, 비root 실행에는 PVC 소유권(fsGroup) 문제가 얽혀 오늘 범위를 넘는다. 경고로 남겨 둔다.

# restricted enforce 네임스페이스에서 거부 → 통과를 직접 본다

$ kubectl label namespace study-restricted pod-security.kubernetes.io/enforce=restricted

$ kubectl delete namespace study-restricted --wait=false

읽을 것 — 같은 매니페스트가 restricted enforce에서 생성 자체는 통과했다(어드미션의 몫은 거기까지다). 크래시는 설정과 DB가 없어서이고 그것은 정책과 무관하다. 어드미션이 거부하면 오브젝트가 아예 안 생기고, 통과하면 그 다음은 D3의 진단 순서로 돌아간다. 두 종류를 섞지 않는다.

$ cat > 60-networkpolicy.yaml <<'EOF'

7ValidatingAdmissionPolicy: latest를 거부한다

CEL 한 줄로 태그 없는 이미지를 막는다. 웹훅 서버 없이 API 서버가 직접 평가한다.

$ cat > 61-vap-image-tag.yaml <<'EOF'
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicy
metadata:
  name: require-image-tag
spec:
  failurePolicy: Fail
  matchConstraints:
    resourceRules:
    - apiGroups: [""]
      apiVersions: ["v1"]
      operations: ["CREATE", "UPDATE"]
      resources: ["pods"]
    - apiGroups: ["apps"]
      apiVersions: ["v1"]
      operations: ["CREATE", "UPDATE"]
      resources: ["deployments", "statefulsets"]
  variables:
  - name: containers
    expression: "has(object.spec.template) ? object.spec.template.spec.containers : object.spec.containers"
  validations:
  - expression: "variables.containers.all(c, c.image.contains(':') && !c.image.endsWith(':latest'))"
    message: "모든 컨테이너 이미지에 명시적 태그가 있어야 하며 :latest 는 금지된다"
    reason: Invalid
---
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicyBinding
metadata:
  name: require-image-tag-study
spec:
  policyName: require-image-tag
  validationActions: [Deny]
  matchResources:
    namespaceSelector:
      matchLabels:
        kubernetes.io/metadata.name: study
EOF
$ kubectl apply -f 61-vap-image-tag.yaml
$ kubectl get validatingadmissionpolicy require-image-tag -o jsonpath='{range .status.conditions[*]}{.type}={.status}{"\n"}{end}'
Ready=True

$ kubectl run tagless --image=nginx
The pods "tagless" is invalid: : ValidatingAdmissionPolicy 'require-image-tag' with binding 'require-image-tag-study' denied request: 모든 컨테이너 이미지에 명시적 태그가 있어야 하며 :latest 는 금지된다
$ kubectl run tagged --image=nginx:latest 2>&1 | cut -c1-80
The pods "tagged" is invalid: : ValidatingAdmissionPolicy 'require-image-tag' wi
$ kubectl run tagged --image=nginx:1.30 && kubectl delete pod tagged --wait=false
pod/tagged created
pod "tagged" deleted
$ kubectl run tagless -n default --image=nginx && kubectl delete pod tagless -n default --wait=false
pod/tagless created      ← 바인딩이 study에만 걸려 있다
pod "tagless" deleted
$ cd ~/k8s-study/week1 && kubectl apply -f . --dry-run=server 2>&1 | grep -c denied
0

읽을 것 — 정책(무엇을 검사하나)과 바인딩(어디에 어떤 강도로)이 분리됐다. 같은 정책을 다른 바인딩으로 default에는 Warn으로 걸 수도 있다. 메시지는 내가 쓴 문장 그대로 나온다. variables로 파드와 디플로이먼트의 컨테이너 경로 차이를 한 번에 흡수했다. 마지막 줄: week1/의 매니페스트는 전부 통과한다. 태그를 고정하라는 D4의 원칙이 이제 클러스터가 집행하는 규칙이 됐다. kubectl explain validatingadmissionpolicy.spec으로 필드를 더 볼 수 있다.

4체크포인트

  1. dev-kim 컨텍스트로 파드는 조회되고 시크릿은 Forbidden인 것을 보이고, 403 메시지의 세 요소(누가·무엇·어디)를 읽는다.
  2. 같은 계정에 컨피그맵 읽기 권한을 Role 수정 없이 추가한다(힌트: 내장 ClusterRole view를 RoleBinding으로).
  3. 파드 안에서 토큰 없이 API를 부르면 401, 토큰을 붙이면 403임을 보인다.
  4. restricted enforce 네임스페이스에서 거부되는 파드를 만들고 securityContext 네 항목을 채워 통과시킨다.
  5. VAP를 하나 더 써서 app 라벨이 없는 디플로이먼트를 거부한다(has(object.metadata.labels.app)).

5개 중 4개 이상이면 D13으로 간다. 2번이 막히면 1.3절의 "ClusterRole을 RoleBinding으로"를 다시 읽는다.
