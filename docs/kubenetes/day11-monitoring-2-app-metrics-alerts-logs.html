1이론

1.1 앱이 지표를 내놓는 방식

Spring Boot Actuator는 Micrometer라는 지표 추상화를 쓴다. Prometheus 레지스트리 의존성 하나를 더하면 /actuator/prometheus에 Prometheus 텍스트 형식으로 노출된다. 코드를 안 써도 JVM(힙·GC·스레드), HTTP 서버(요청 수·지연), 데이터소스(커넥션 풀), 로그백(로그 레벨별 건수)이 자동으로 나온다. 오늘 쓰는 것은 http_server_requests_seconds 하나다.

지표타입라벨
http_server_requests_seconds_countcountermethod, uri, status, outcome, exception
http_server_requests_seconds_sumcounter (지연 합계)
http_server_requests_seconds_bucket{le="…"}histogram 구간 (설정으로 켠다)
jvm_memory_used_bytesgaugearea, id
hikaricp_connections_activegaugepool

count와 sum을 나누면 평균 지연이다. 평균은 꼬리를 숨기므로 p95·p99가 필요하고, 그것은 bucket에서 histogram_quantile로 계산한다. bucket은 기본으로 꺼져 있어 management.metrics.distribution.percentiles-histogram.http.server.requests=true로 켠다.

1.2 ServiceMonitor: 스크레이프 대상을 오브젝트로

Prometheus 자체 설정 파일에 대상을 적을 수도 있지만, Operator 환경에서는 ServiceMonitor 오브젝트를 만든다. Operator가 그것을 읽어 Prometheus 설정을 다시 쓴다. 매칭은 세 층으로 일어나고, 어느 하나가 어긋나면 Targets에 아무 말 없이 안 나타난다.

1.3 RED 세 쿼리

패널PromQL
Ratesum(rate(http_server_requests_seconds_count{job="order-api"}[1m]))
Errorssum(rate(http_server_requests_seconds_count{job="order-api", status=~"5.."}[1m])) / sum(rate(http_server_requests_seconds_count{job="order-api"}[1m]))
Duration p95histogram_quantile(0.95, sum by (le) (rate(http_server_requests_seconds_bucket{job="order-api"}[5m])))

job 라벨은 ServiceMonitor가 스크레이프할 때 서비스 이름으로 자동으로 붙는다. histogram_quantile은 구간별 누적 개수(le 라벨)로 분위수를 추정하므로 sum by (le)로 다른 라벨을 먼저 접어야 한다.

1.4 알림: 규칙, 라우팅, 피로

PrometheusRule은 "이 PromQL이 이 시간 동안 참이면 알림"을 적은 오브젝트다. Prometheus가 평가해 Alertmanager로 보내고, Alertmanager가 그룹으로 묶고, 반복을 억제하고, 수신자(Slack·메일·페이저)로 보낸다. 알림은 사람이 지금 행동해야 하는 것에만 건다. CPU 80%는 알림이 아니라 대시보드다. "오류율 5% 초과가 2분 지속"은 알림이다. 규칙에는 for(지속 시간)를 두어 한 번의 튐으로 울리지 않게 한다.

1.5 로그: stdout에서 Loki까지

컨테이너는 파일이 아니라 stdout/stderr에 로그를 쓴다. 노드의 containerd가 그것을 /var/log/pods/…에 파일로 남기고, kubectl logs는 kubelet을 거쳐 그 파일을 읽는다. 파드가 사라지면 파일도 사라진다. 그래서 수집기가 필요하다. Alloy는 노드마다 하나씩(DaemonSet) 돌며 파드 로그를 모아 라벨(네임스페이스·파드·앱)을 붙여 Loki로 보낸다. Loki는 로그 본문이 아니라 라벨만 인덱싱하므로 가볍고, 조회는 LogQL로 라벨을 먼저 좁힌 뒤 본문을 grep한다: {namespace="study", app="order-api"} |= "Exception". Grafana가 Prometheus와 Loki를 같은 시간축에 놓아 준다.

4알림 규칙과 오류 주입

오류율 5% 초과가 1분 이상이면 알림. /boom을 두드려 실제로 울린다.

$ cat > 52-prometheusrule.yaml <<'EOF'

kind: PrometheusRule
metadata:
  name: study-app-rules
  namespace: study
  labels:
    release: kps
spec:
  groups:
  - name: study.rules
    rules:
    - alert: OrderApiHighErrorRate
      expr: |
        sum(rate(http_server_requests_seconds_count{job="order-api", status=~"5.."}[1m]))
          / sum(rate(http_server_requests_seconds_count{job="order-api"}[1m])) > 0.05
      for: 1m
      labels:
        severity: warning
      annotations:
        summary: "order-api 5xx 비율 5% 초과"
        description: "지난 1분 오류율 {{ $value | humanizePercentage }}"
    - alert: OrderApiDown
      expr: up{job="order-api"} == 0
      for: 2m
      labels:
        severity: critical
      annotations:
        summary: "order-api 스크레이프 실패 ({{ $labels.pod }})"
EOF

OrderApiHighErrorRate inactive

        }

        forward_to = [loki.write.default.receiver]

6같은 시각, 지표와 로그

4단계에서 알림이 울린 시각의 로그를 Loki에서 찾는다.

Grafana(터미널 C의 port-forward를 다시 켠다) → Explore → 데이터소스 Loki. 시간 범위를 지난 30분으로.

{namespace="study", app="order-api"} |= "boom"

4단계 이후 order-api 파드들이 남긴 IllegalStateException: boom: injected failure on order-api-… 스택 트레이스가 초당 수십 건 흐른다. 오른쪽 위 Split을 누르고 왼쪽에 Prometheus 데이터소스로 Error ratio 쿼리를 넣으면 같은 시간축에 그래프와 로그가 나란히 놓인다. 오류율이 뛰기 시작한 시각과 첫 boom 로그의 시각이 일치한다.

# LogQL로 파드별 오류 로그 건수 (로그에서 지표를 뽑는다)
sum by (pod) (count_over_time({namespace="study", app="order-api"} |= "boom" [1m]))

# 터미널에서도 확인 — Loki API 직접
$ kubectl -n monitoring port-forward svc/loki 3100:3100 &
$ sleep 1 && curl -s -G localhost:3100/loki/api/v1/query --data-urlencode 'query=sum(count_over_time({namespace="study", app="order-api"} |= "boom" [5m]))' | python3 -c 'import sys,json; print(json.load(sys.stdin)["data"]["result"][0]["value"][1], "boom lines / 5m")'
18420 boom lines / 5m
$ kill %1
$ kubectl delete pod boom --wait=false

읽을 것 — 지표는 "언제부터 얼마나"를, 로그는 "무엇이"를 말한다. 알림(4단계)이 사람을 부르고, 대시보드(3단계)가 범위를 좁히고, 로그(6단계)가 원인을 준다. 이 셋이 같은 시간축에 있어야 한다. boom 파드를 지우면 몇 분 뒤 알림이 resolved로 바뀐다.

4체크포인트 C · 그라파나에 내 앱 지표

3단계(D8~D11)의 관문.

  1. ServiceMonitor 하나를 새로 써서(예: postgres용, 스크레이프될 엔드포인트가 없어 down이어도 된다) Targets에 나타나게 한다. 안 나타나면 세 층 중 어디가 틀렸는지 말한다.
  2. Grafana에서 order-api와 gateway의 요청률·오류율·p95 패널이 살아 있다.
  3. 오류를 주입하면 2분 안에 OrderApiHighErrorRate가 firing이 되고, 주입을 멈추면 resolved가 된다.
  4. 알림이 울린 시각의 boom 로그를 Loki에서 LogQL 한 줄로 찾는다.
  5. week1/에 ServiceMonitor·대시보드 ConfigMap·PrometheusRule 파일이 있고 kubectl diff -f .가 비어 있다.

5개 중 4개 이상이면 D12로 간다. 1번이 막히면 도판 1의 ①②③을 순서대로 대조한다.
