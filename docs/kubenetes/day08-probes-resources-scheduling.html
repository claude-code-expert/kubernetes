D5에서 롤링 재시작 중 요청이 몇 개 실패했다. 새 파드의 컨테이너가 "떴다"와 요청을 "받을 수 있다"는 다르기 때문이다. 오늘은 앱이 그 둘을 스스로 보고하게 하는 프로브 세 종류를 넣어 실패를 0으로 만든다. 그리고 CPU·메모리 요청과 제한이 스케줄러의 배치 결정과 OOM 종료에 어떻게 작용하는지, 실행 중인 파드의 리소스를 재시작 없이 바꾸는 법, 3노드에 파드를 고르게 퍼뜨리는 법을 다룬다.

1이론

1.1 프로브 세 종류

kubelet은 컨테이너 프로세스가 살아 있는지만 안다. 프로세스는 살아 있는데 앱이 멈춘 상태(데드락, 무한 재시도, 초기화 중)는 앱이 말해 줘야 한다. 그 통로가 프로브(probe)다. HTTP GET, TCP 연결, 명령 실행, gRPC 네 방식이 있고 결과는 성공/실패뿐이다.

프로브질문실패하면전형적 오용
startupProbe초기화가 끝났나계속 기다린다(failureThreshold × periodSeconds까지). 그동안 다른 두 프로브는 쉰다. 한도를 넘으면 컨테이너를 죽인다.느린 JVM 앱에 이걸 안 두고 liveness의 initialDelay로 때우기
readinessProbe지금 요청을 받을 수 있나엔드포인트슬라이스에서 뺀다. 컨테이너는 그대로 둔다. 다시 성공하면 넣는다.DB 같은 외부 의존성을 여기서 검사해, DB 장애 때 앱 전체가 트래픽에서 빠지게 만들기
livenessProbe다시 시작해야 하나컨테이너를 죽이고 restartPolicy대로 다시 띄운다.readiness와 같은 검사를 두어 일시적 과부하에 재시작 폭풍 만들기

세 프로브는 시간 순서로 겹친다. startup이 성공하는 순간부터 readiness와 liveness가 각자 주기로 돈다. readiness는 자주(5초), liveness는 드물게(10~30초) 검사하고, liveness는 "재시작으로 고쳐지는 상태"만 봐야 한다. 외부 의존성은 readiness에서도 신중히 다룬다. DB가 죽었을 때 앱 파드 전부가 트래픽에서 빠지면 상태 페이지조차 못 보여 준다.

1.2 요청과 제한

resources.requests는 스케줄러가 노드를 고를 때 쓰는 예약량이다. 노드의 할당 가능량에서 그 노드에 이미 배치된 파드의 requests 합을 뺀 여유가 있어야 놓인다. 실제 사용량과 무관하다. resources.limits는 cgroup에 쓰이는 상한이다(D1 3단계에서 본 memory.max). 메모리는 넘으면 커널이 프로세스를 죽인다(OOMKilled). CPU는 넘으면 죽이지 않고 스로틀링한다.

이 교재는 CPU limit을 걸지 않는다. CPU 스로틀링은 요청 처리 중 프로세스를 강제로 멈추는 것이라 지연 시간을 왜곡하고, D11에서 볼 p95 지표가 스로틀링 때문인지 앱 때문인지 구분하기 어려워진다. requests만 정해 스케줄링을 통제하고, 메모리는 limit을 걸어 한 파드가 노드를 잡아먹지 못하게 한다.

1.3 QoS 클래스

노드 메모리가 부족해지면 kubelet이 파드를 쫓아낸다(eviction). 그 순서가 QoS 클래스로 정해진다. 따로 지정하는 것이 아니라 requests·limits 조합에서 자동으로 결정된다.

클래스조건축출 순서
Guaranteed모든 컨테이너가 CPU·메모리 둘 다 requests = limits마지막
Burstablerequests나 limits가 하나라도 있고 Guaranteed가 아님중간
BestEffort아무것도 없음가장 먼저

CPU limit을 안 거는 이 교재의 파드는 전부 Burstable이다. 그래도 된다. 축출은 노드 압박 상황의 마지막 수단이고, 메모리 limit이 있으면 노드가 그 지경에 가기 전에 파드 단위로 OOM이 먼저 난다.

1.4 실행 중 리소스 변경

파드의 resources는 오랫동안 생성 후 바꿀 수 없는 필드였다. 지금은 resize 서브리소스로 실행 중인 파드의 CPU·메모리 requests·limits를 바꿀 수 있다(In-Place Pod Vertical Scaling, GA). 컨테이너별 resizePolicy가 재시작 여부를 정하며 기본값은 재시작 없음(NotRequired)이다. JVM처럼 시작 시 힙 크기를 정하는 앱은 cgroup 한도가 늘어나도 힙은 안 늘어나므로, 메모리를 늘릴 때는 RestartContainer 정책이 맞을 수 있다. 오늘은 기본값으로 늘려 보고 그 한계를 본다.

1.5 어디에 놓을지 정하는 네 가지

수단방향뜻
nodeSelector / nodeAffinity파드 → 노드"이 라벨이 있는 노드에만(또는 우선)". 하드웨어(GPU, SSD)·존 지정.
taint + toleration노드 → 파드노드가 "허락 없이 오지 마"라고 표시(taint). 톨러레이션이 있는 파드만 온다. 컨트롤 플레인 노드가 D5에서 이 방식으로 일반 파드를 막았다.
podAffinity / podAntiAffinity파드 → 파드"저 파드와 같은 노드에(또는 다른 노드에)". 같은 앱의 복제본을 한 노드에 몰리지 않게.
topologySpreadConstraints파드 집합 → 토폴로지"노드(또는 존)마다 이 라벨의 파드 수 차이가 maxSkew 이하". anti-affinity보다 표현이 정확하다.

1.6 곱게 죽이기

파드가 삭제되면 두 가지가 동시에 시작된다. 엔드포인트슬라이스에서 파드를 빼는 일(비동기, 수 초 걸림)과 컨테이너에 SIGTERM을 보내는 일. 앱이 SIGTERM을 받고 즉시 죽으면, 아직 이 파드로 오고 있던 요청이 끊긴다. 그래서 두 가지를 한다. preStop 훅으로 몇 초 기다려 엔드포인트 제거가 퍼지게 하고, 앱은 SIGTERM을 받으면 새 요청을 거절하되 진행 중인 요청은 마치고 종료한다(Spring Boot의 server.shutdown=graceful). terminationGracePeriodSeconds(기본 30초)가 지나면 SIGKILL이다.

PodDisruptionBudget은 노드 점검(drain) 같은 자발적 중단에서 "동시에 몇 개까지 내려가도 되나"를 정한다. 오늘 만들어 두고 D14의 drain에서 동작을 본다.

3고장: liveness를 너무 급하게 잡으면

startupProbe를 빼고 liveness를 1초 주기·1회 실패로 잡는다. JVM이 뜨기도 전에 죽인다.

$ cat > bad-liveness.yaml <<'EOF'
apiVersion: v1
kind: Pod
metadata:
  name: bad-liveness
spec:
  containers:
  - name: app
    image: order-api:v4
    ports:
    - containerPort: 8080
    livenessProbe:
      httpGet:
        path: /actuator/health/liveness
        port: 8080

      failureThreshold: 1
EOF

읽을 것 — 앱은 멀쩡한데 CrashLoopBackOff다. 기동에 5초가 걸리는 앱을 1초 만에 "죽었다"고 판정해 죽였다. 로그 끝에 Started가 없는 것이 증거다. 이 파드의 문제는 코드가 아니라 프로브 설정이고, D3의 CrashLoop(exit 1)과 겉모습은 같지만 Events의 Killing … failed liveness probe로 구분한다. 해법은 startupProbe다. initialDelaySeconds로 때우면 기동 시간이 늘어날 때마다 다시 고쳐야 한다.

4OOMKilled: 메모리 limit을 넘으면

같은 앱에 limit 96Mi를 준다. JVM이 그 안에 못 들어간다.

  name: oom-demo

읽을 것 — Reason: OOMKilled, exit 137(128 + SIGKILL 9). 커널이 cgroup 한도에서 프로세스를 죽였고 kubelet은 restartPolicy대로 다시 띄웠다. 로그에는 아무것도 없다(죽는 프로세스는 남길 틈이 없다). 앱 로그가 비어 있고 137이면 메모리를 의심한다. STATUS가 CrashLoopBackOff로 보이는 시점도 있는데, 그때는 lastState를 본다. limit을 넉넉히 주면 사라진다. 96Mi에서도 뜬다면(JVM 버전에 따라) 64Mi로 낮춰 본다.

requests=256Mi limits=512Mi restarts=0

$ kubectl patch pod $POD --subresource resize --type=merge \
    -p '{"spec":{"containers":[{"name":"app","resources":{"requests":{"memory":"320Mi"},"limits":{"memory":"640Mi"}}}]}}'
pod/order-api-… patched
$ sleep 3 && kubectl get pod $POD -o jsonpath='requests={.spec.containers[0].resources.requests.memory} limits={.spec.containers[0].resources.limits.memory} restarts={.status.containerStatuses[0].restartCount} allocated={.status.containerStatuses[0].resources.limits.memory}{"\n"}'
requests=320Mi limits=640Mi restarts=0 allocated=640Mi
$ kubectl exec $POD -- cat /sys/fs/cgroup/memory.max
671088640
$ kubectl get pod $POD -o jsonpath='{range .status.conditions[?(@.type=="PodResizeInProgress")]}{.status} {.reason}{end}{"\n"}'

읽을 것 — restarts=0인 채로 cgroup 한도가 640Mi(671088640바이트)로 바뀌었다. status.containerStatuses[].resources가 실제로 적용된 값이다. 다만 JVM 힙은 시작 시 정해졌으므로 이 파드의 힙 상한은 여전히 512Mi의 60%다. 한도는 늘었지만 앱이 그만큼 쓰지는 못한다. JVM 앱이라면 resizePolicy: [{resourceName: memory, restartPolicy: RestartContainer}]를 두는 편이 맞고, 그러면 재시작 1회가 따라온다. 이 변경은 파드에만 적용됐고 디플로이먼트 템플릿은 그대로다. 파드가 새로 만들어지면 원래 값으로 돌아간다.

6테인트: 노드가 파드를 거부한다

worker2에 테인트를 걸고 롤링 재시작하면 파드가 전부 worker로 몰린다. 톨러레이션을 주면 돌아온다.

$ kubectl taint nodes desktop-worker2 dedicated=db:NoSchedule
node/desktop-worker2 tainted
$ kubectl get pods -l app=order-api -o custom-columns='POD:.metadata.name,NODE:.spec.nodeName'
(worker2의 파드는 그대로 돌고 있다 — NoSchedule은 새 배치만 막는다)
$ kubectl rollout restart deployment/order-api && kubectl rollout status deployment/order-api
$ kubectl get pods -l app=order-api -o custom-columns='POD:.metadata.name,NODE:.spec.nodeName'
POD                          NODE
order-api-…-a1b2c            desktop-worker
order-api-…-d3e4f            desktop-worker
order-api-…-g5h6i            desktop-worker
order-api-…-j7k8l            desktop-worker

$ kubectl scale deployment/order-api --replicas=20 && sleep 20
$ kubectl get pods -l app=order-api --field-selector status.phase=Pending -o name | wc -l
4
$ kubectl describe pod -l app=order-api | grep -m1 'FailedScheduling'
  Warning  FailedScheduling  ...  0/3 nodes are available: 1 node(s) had untolerated taint {dedicated: db}, 1 node(s) had untolerated taint {node-role.kubernetes.io/control-plane: }, 1 Insufficient cpu. ...
$ kubectl scale deployment/order-api --replicas=4
$ kubectl taint nodes desktop-worker2 dedicated=db:NoSchedule-
node/desktop-worker2 untainted

읽을 것 — 넷이 전부 worker에 놓였다. 20개로 늘리자 worker의 CPU requests 합(250m × 20 = 5000m)이 노드 할당 가능량(약 4000m)을 넘어 Pending이 생겼고, 이유가 셋으로 나뉘어 적혔다. 테인트 둘(worker2, 컨트롤 플레인)과 CPU 부족. 이 메시지가 스케줄러 진단의 전부다. 어느 노드가 왜 안 되는지 하나씩 적혀 있다. 톨러레이션은 파드 spec에 tolerations: [{key: dedicated, operator: Equal, value: db, effect: NoSchedule}]로 적는다. D9의 DB 스테이트풀셋에 이 조합을 쓴다.

7고르게 퍼뜨리기와 PDB

토폴로지 분산 제약으로 노드당 파드 수 차이를 1 이하로 묶고, PDB를 만들어 둔다.

$ cd ~/k8s-study/week1
$ python3 - <<'EOF'
import re
p='20-order-api-deploy.yaml'; t=open(p).read()
t=t.replace('''      terminationGracePeriodSeconds: 30
''','''      terminationGracePeriodSeconds: 30
      topologySpreadConstraints:
      - maxSkew: 1
        topologyKey: kubernetes.io/hostname
        whenUnsatisfiable: DoNotSchedule
        labelSelector:
          matchLabels:
            app: order-api
''')
open(p,'w').write(t)
EOF
$ grep -A6 topologySpread 20-order-api-deploy.yaml | head -7
$ kubectl apply -f 20-order-api-deploy.yaml && kubectl rollout status deployment/order-api
$ kubectl get pods -l app=order-api -o custom-columns='NODE:.spec.nodeName' --no-headers | sort | uniq -c
   2 desktop-worker
   2 desktop-worker2

$ cat > 23-order-api-pdb.yaml <<'EOF'
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: order-api
  namespace: study
spec:
  minAvailable: 3
  selector:
    matchLabels:
      app: order-api
EOF
$ kubectl apply -f 23-order-api-pdb.yaml
$ kubectl get pdb
NAME        MIN AVAILABLE   MAX UNAVAILABLE   ALLOWED DISRUPTIONS   AGE
order-api   3               N/A               1                     5s
$ kubectl diff -f . ; echo "exit=$?"
exit=0

읽을 것 — 2:2다. 6단계에서 4:0으로 몰렸던 것이 제약 하나로 고르게 됐다. DoNotSchedule이라 만족할 수 없으면 Pending이 된다. 운영에서는 ScheduleAnyway(최선 노력)를 쓰는 경우도 많다. PDB의 ALLOWED DISRUPTIONS 1은 "지금 4개 중 1개까지는 자발적으로 내려도 된다"는 뜻이다. D14에서 drain이 이 숫자를 보고 멈추는 것을 본다. week1/에 파일이 하나 늘었고 diff는 비어 있다.

4체크포인트

  1. 트래픽을 흘리며 rollout restart를 해서 200번 요청 중 실패 0건을 보인다.
  2. liveness 재시작 루프와 exit 1 CrashLoop를 Events 한 줄로 구분해 말한다.
  3. 메모리 limit을 넘겨 OOMKilled · 137을 만들고, 로그가 비어 있는 이유를 말한다.
  4. 실행 중 파드의 memory limit을 늘려 restartCount가 0인 채 cgroup 값이 바뀐 것을 보인다.
  5. 노드 하나에 테인트를 걸어 Pending을 만들고 FailedScheduling 메시지에서 노드 세 개의 사유를 각각 읽는다.
  6. order-api 파드가 워커 두 노드에 2:2로 놓이게 한다.

6개 중 5개 이상이면 D9로 간다. 1번에서 실패가 나오면 preStop 시간과 readiness period를 다시 본다.
