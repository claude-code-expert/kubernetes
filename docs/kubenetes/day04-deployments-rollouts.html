쿠버네티스 14일 · 2단계 배포와 노출 · Day 4

파드는 직접 만들지 않는다 — 디플로이먼트와 롤링 업데이트

어제 파드를 delete하면 그냥 사라졌다. 오늘은 "이 파드를 3개 유지하라"를 선언하고, 그 선언을 지키는 컨트롤러가 어떻게 파드를 되살리는지, 이미지를 v1에서 v2로 바꿀 때 어떻게 한 번에 끊기지 않게 교체하는지, 잘못됐을 때 어떻게 되돌리는지를 본다. 실습 앱은 Spring Boot로 만든 order-api이고, 이 앱을 D14까지 계속 키운다.

오늘 끝나면 할 수 있는 것

  1. Spring Boot 앱을 멀티 스테이지 Dockerfile로 이미지화하고, 그 이미지를 클러스터의 노드가 pull하는 것을 crictl로 확인한다.
  2. Deployment → ReplicaSet → Pod 소유 관계를 ownerReferences로 추적하고, 파드·레플리카셋을 지워도 되살아나는 것을 본다.
  3. 이미지를 v2로 바꿔 롤링 업데이트를 수행하고, 레플리카셋 두 개가 교대하는 과정을 -w로 읽는다.
  4. 잘못된 이미지로 배포가 멈췄을 때 rollout undo로 직전 리비전에 돌아간다.

1이론

세 오브젝트의 관계, 셀렉터와 템플릿의 규칙, 롤링 업데이트가 실제로 하는 일, 이미지 태그와 pull 정책, 그리고 내 노트북의 이미지가 노드까지 가는 길.

1.1 세 층의 소유 관계

디플로이먼트(Deployment)는 "이 파드 템플릿을 N개 유지하고, 템플릿이 바뀌면 점진적으로 교체하라"는 선언이다. 디플로이먼트는 파드를 직접 만들지 않는다. 레플리카셋(ReplicaSet)을 만들고, 레플리카셋이 파드 개수를 맞춘다. 템플릿이 바뀔 때마다 새 레플리카셋이 하나 더 생기고, 옛 것은 0개로 줄어든 채 이력으로 남는다. 그 이력이 롤백의 재료다.

각 파드의 metadata.ownerReferences에 레플리카셋이, 레플리카셋의 ownerReferences에 디플로이먼트가 적혀 있다. 이 사슬 덕분에 디플로이먼트를 지우면 레플리카셋과 파드가 함께 정리되고(가비지 컬렉션), 반대로 파드를 지우면 레플리카셋이 "부족하다"를 감지해 채운다.

1.2 셀렉터와 템플릿의 규칙

디플로이먼트 매니페스트의 spec에는 세 부분이 있다.

필드뜻규칙
replicas유지할 파드 개수생략하면 1
selector"내 파드"를 고르는 라벨 조건 (D3의 셀렉터)만든 뒤 바꿀 수 없다
template파드 매니페스트의 metadata+spec. D3에서 쓴 것이 그대로 들어간다template.metadata.labels가 selector를 만족해야 한다. 아니면 API 서버가 거부

셀렉터가 넓으면 남의 파드까지 "내 것"으로 세어 버린다. 그래서 디플로이먼트마다 고유한 라벨(app: order-api)을 쓰고, 셀렉터는 그 라벨 하나로 좁게 잡는다. 레플리카셋은 여기에 pod-template-hash 라벨을 자동으로 덧붙여 자기 세대의 파드만 고른다.

1.3 롤링 업데이트가 실제로 하는 일

template이 바뀌면(대개 이미지 태그) 디플로이먼트는 새 해시의 레플리카셋을 만들고, 새 것을 하나 늘리고 옛 것을 하나 줄이는 일을 반복한다. 속도는 두 값이 정한다.

  • maxSurge — 원하는 개수보다 몇 개까지 더 띄울 수 있나. 기본 25%.
  • maxUnavailable — 원하는 개수에서 몇 개까지 모자라도 되나. 기본 25%.

replicas 3에 기본값이면 (반올림 규칙에 따라) 최대 4개, 최소 3개를 유지하며 교체한다. 옛 파드를 먼저 죽이지 않으므로 요청을 받을 파드가 항상 있다. 단, "새 파드가 준비됐다"를 판단하는 기준이 없으면 컨테이너가 뜨자마자 옛 파드를 줄이므로 앱이 아직 초기화 중일 때 요청이 실패할 수 있다. 그 기준(readinessProbe)은 D8에서 넣는다.

kubectl rollout undo는 옛 레플리카셋을 다시 3으로 올리고 새 것을 0으로 내리는 것, 즉 같은 롤링 업데이트를 반대 방향으로 하는 것이다. 이력은 revisionHistoryLimit(기본 10)개까지 남는다. 새 파드가 계속 뜨지 못하면(잘못된 이미지 등) 디플로이먼트는 옛 파드를 더 줄이지 않고 멈추며, progressDeadlineSeconds(기본 600초)가 지나면 Progressing=False 조건을 남긴다. 그때 되돌리는 것이 오늘 마지막 실습이다.

1.4 이미지 태그와 pull 정책

롤링 업데이트는 템플릿의 변화를 감지한다. image: order-api:latest를 새로 빌드해 같은 태그로 올리면 템플릿이 그대로이므로 아무 일도 일어나지 않는다. 그래서 태그는 빌드마다 달라야 한다. 오늘은 v1·v2처럼 손으로 붙이고, D13에서 git SHA를 쓴다.

imagePullPolicy는 kubelet이 노드에 이미 있는 이미지를 쓸지 정한다. 태그가 latest이거나 생략이면 Always(매번 레지스트리 확인), 그 외 태그면 IfNotPresent(있으면 재사용)가 기본이다. 태그를 고정하면 이 정책도 자연히 안전한 쪽이 된다.

1.5 내 노트북의 이미지가 노드까지 가는 길

D2에서 봤듯 노드는 별도 컨테이너이고 자기 containerd를 가진다. docker build로 만든 이미지는 호스트 쪽 이미지 스토어에 있다. Docker Desktop의 kind 프로비저너는 이 둘을 desktop-containerd-registry-mirror 컨테이너로 잇는다. 노드의 containerd가 이미지를 pull하려 할 때 이 미러를 먼저 거치고, 미러는 호스트의 containerd 이미지 스토어에 있는 이미지를 그대로 내준다. 그래서 push 없이 image: order-api:v1만 적어도 노드가 이미지를 받는다.

조건이 하나 있다. Docker Desktop이 containerd 이미지 스토어를 쓰고 있어야 한다(Settings → General → Use containerd for pulling and storing images). 옛 Docker 이미지 스토어를 쓰는 설치에서는 kind 노드가 로컬 이미지를 보지 못한다. 2.1절에서 확인한다. 이 경로가 막히면 Docker Hub에 push하는 대안이 있고, 3단계 끝에 적어 두었다.

package study;

import java.util.List;
import java.util.Map;
import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;

@SpringBootApplication
@RestController
public class OrderApiApplication {

    public static void main(String[] args) {
        SpringApplication.run(OrderApiApplication.class, args);
    }

    @GetMapping("/")
    public String root() {
        return "order-api " + version() + " on " + host() + "\n";
    }

    @GetMapping("/orders")
    public Map<String, Object> orders() {
        return Map.of(
            "version", version(),
            "host", host(),
            "orders", List.of(
                Map.of("id", 1, "item", "keyboard"),
                Map.of("id", 2, "item", "mouse")));
    }

    private static String version() {
        String v = System.getenv("APP_VERSION");
        return v == null ? "dev" : v;
    }

    private static String host() {
        String h = System.getenv("HOSTNAME");
        return h == null ? "unknown" : h;
    }
}
EOF

ImagePullBackOff가 나면

2.1절의 containerd 이미지 스토어 설정을 다시 확인한다. 그래도 안 되면 Docker Hub 경로를 쓴다. docker login 후 docker tag order-api:v1 <hub-id>/order-api:v1 && docker push <hub-id>/order-api:v1, 그리고 이하 모든 매니페스트의 image:를 <hub-id>/order-api:v1로 바꾼다. 나머지 실습은 동일하다.

읽을 것 — 파드 셋을 한꺼번에 지웠는데 6초 뒤 셋이 돌아왔다(레플리카셋의 일). 레플리카셋을 지우자 파드도 함께 사라졌다가(소유 사슬의 가비지 컬렉션) 디플로이먼트가 같은 이름의 레플리카셋을 다시 만들었다(디플로이먼트의 일). 이름이 같은 이유는 템플릿이 그대로라 해시가 같기 때문이다. 어느 층을 부숴도 위층이 복구한다. 디플로이먼트를 지우면 전부 사라진다. 그 위층은 없다.

5셀렉터와 템플릿이 어긋나면

1.2절의 규칙. API 서버가 어떤 문장으로 거부하는지 읽어 둔다.

$ sed 's/^      app: order-api$/      app: order-api-typo/' order-api-deploy.yaml > bad-selector.yaml
$ diff order-api-deploy.yaml bad-selector.yaml
11c11
<       app: order-api
---
>       app: order-api-typo
$ kubectl apply -f bad-selector.yaml
The Deployment "order-api" is invalid:
* spec.template.metadata.labels: Invalid value: map[string]string{"app":"order-api"}: `selector` does not match template `labels`
* spec.selector: Invalid value: ...: field is immutable
$ rm bad-selector.yaml

읽을 것 — 두 가지가 한 번에 걸렸다. 셀렉터와 템플릿 라벨이 다르다는 것, 그리고 이미 있는 디플로이먼트의 셀렉터는 바꿀 수 없다는 것. 셀렉터를 바꿔야 한다면 디플로이먼트를 새로 만든다.

6개수 조절: 명령으로, 그리고 파일로

scale은 빠르지만 파일과 어긋난다. 어긋난 상태에서 apply하면 무슨 일이 생기는지 본다.

$ kubectl scale deployment/order-api --replicas=5
$ kubectl get deploy order-api
NAME        READY   UP-TO-DATE   AVAILABLE   AGE
order-api   5/5     5            5           4m

$ kubectl apply -f order-api-deploy.yaml
deployment.apps/order-api configured
$ kubectl get deploy order-api
NAME        READY   UP-TO-DATE   AVAILABLE   AGE
order-api   3/3     3            3           4m

$ sed -i.bak 's/replicas: 3/replicas: 4/' order-api-deploy.yaml && rm order-api-deploy.yaml.bak
$ kubectl apply -f order-api-deploy.yaml
$ kubectl get deploy order-api -o jsonpath='{.spec.replicas}{"\n"}'
4

읽을 것 — scale로 5를 만들었지만 파일에는 3이 적혀 있었고, apply가 파일을 이겨 3으로 돌아갔다. 파일이 원본이다. 개수를 바꾸려면 파일을 고치고 apply한다. 앞으로 scale은 D10의 HPA처럼 자동화가 대신 하도록 두고, 사람은 파일을 고친다. (sed -i.bak는 macOS·Linux 어느 쪽에서도 동작하는 형식이다.)

7롤링 업데이트: v2로

템플릿의 이미지 한 줄을 바꾸고, 레플리카셋 두 개가 교대하는 것을 지켜본다.

$ docker build --build-arg APP_VERSION=v2 -t order-api:v2 order-api/
[+] Building 6.4s (15/15) FINISHED     ← 캐시 덕에 빠르다

$ sed -i.bak 's/image: order-api:v1/image: order-api:v2/' order-api-deploy.yaml && rm order-api-deploy.yaml.bak
$ kubectl apply -f order-api-deploy.yaml && kubectl annotate deployment/order-api kubernetes.io/change-cause="image v2" --overwrite
$ kubectl rollout status deployment/order-api
Waiting for deployment "order-api" rollout to finish: 1 out of 4 new replicas have been updated...
Waiting for deployment "order-api" rollout to finish: 2 out of 4 new replicas have been updated...
Waiting for deployment "order-api" rollout to finish: 1 old replicas are pending termination...
deployment "order-api" successfully rolled out

$ kubectl get rs -l app=order-api
NAME                    DESIRED   CURRENT   READY   AGE
order-api-5b8d7c9f2     4         4         4       40s
order-api-7d9c4f6b8     0         0         0       9m

$ kubectl port-forward deployment/order-api 8080:8080 &
$ sleep 1 && curl -s localhost:8080/
order-api v2 on order-api-5b8d7c9f2-k2p8n
$ kill %1

$ kubectl rollout history deployment/order-api
REVISION  CHANGE-CAUSE
1         <none>
2         image v2

읽을 것 — 터미널 A(-w)에서는 새 해시(5b8d7c9f2)의 파드가 하나 Running이 될 때마다 옛 해시의 파드 하나가 Terminating으로 바뀐다. 끝나면 옛 레플리카셋은 0개로 남아 있다. 지워지지 않았다. 리비전 2가 현재이고 리비전 1이 그 레플리카셋이다.

지금은 확인하지 않는 것

교체 중 요청이 실패했는지는 오늘 볼 수 없다. port-forward는 파드 하나에만 붙기 때문이다. 여러 파드에 트래픽을 흘리며 관찰하는 것은 D5에서 서비스를 만든 뒤, 실패를 0으로 만드는 것은 D8에서 readinessProbe를 넣은 뒤에 한다.

8고장 난 배포와 롤백

존재하지 않는 이미지로 v3를 배포한다. 디플로이먼트가 서비스를 죽이지 않고 멈추는 것, 그리고 되돌리는 법.

$ sed -i.bak 's/image: order-api:v2/image: order-api:v3/' order-api-deploy.yaml && rm order-api-deploy.yaml.bak
$ kubectl apply -f order-api-deploy.yaml && kubectl annotate deployment/order-api kubernetes.io/change-cause="image v3 (없는 태그)" --overwrite
$ kubectl rollout status deployment/order-api --timeout=30s
Waiting for deployment "order-api" rollout to finish: 1 out of 4 new replicas have been updated...
error: timed out waiting for the condition

$ kubectl get rs,pods -l app=order-api
NAME                              DESIRED   CURRENT   READY   AGE
replicaset.apps/order-api-9f3e1a7c4   1         1         0       40s
replicaset.apps/order-api-5b8d7c9f2   4         4         4       5m
replicaset.apps/order-api-7d9c4f6b8   0         0         0       14m

NAME                            READY   STATUS             RESTARTS   AGE
pod/order-api-9f3e1a7c4-h6j2w   0/1     ImagePullBackOff   0          40s
pod/order-api-5b8d7c9f2-k2p8n   1/1     Running            0          5m
pod/order-api-5b8d7c9f2-...     1/1     Running            0          5m
(v2 파드 4개 그대로)

$ kubectl get deploy order-api
NAME        READY   UP-TO-DATE   AVAILABLE   AGE
order-api   4/4     1            4           14m

읽을 것 — 새 레플리카셋은 1개를 띄우려다 ImagePullBackOff에 걸렸고, 그 파드가 Ready가 되지 않으니 디플로이먼트는 옛 파드를 하나도 줄이지 않았다. READY 4/4, AVAILABLE 4. 서비스는 v2로 멀쩡히 돌고 있다. UP-TO-DATE 1이 "새 템플릿의 파드는 1개뿐"이라는 뜻이다. 10분(progressDeadlineSeconds)이 지나면 Progressing=False가 되지만 그때도 옛 파드는 유지된다.

$ kubectl rollout undo deployment/order-api
deployment.apps/order-api rolled back
$ kubectl rollout status deployment/order-api
deployment "order-api" successfully rolled out
$ kubectl rollout history deployment/order-api
REVISION  CHANGE-CAUSE
1         <none>
3         image v3 (없는 태그)
4         image v2
$ kubectl get deploy order-api -o jsonpath='{.spec.template.spec.containers[0].image}{"\n"}'
order-api:v2

# 파일도 되돌려 클러스터와 맞춘다
$ sed -i.bak 's/image: order-api:v3/image: order-api:v2/' order-api-deploy.yaml && rm order-api-deploy.yaml.bak
$ kubectl diff -f order-api-deploy.yaml ; echo "exit=$?"
exit=0

읽을 것 — undo는 직전 리비전(v2)의 레플리카셋을 다시 올렸다. 이력에서 리비전 2가 사라지고 4가 된 것은 같은 템플릿이 "새 리비전으로 재사용"됐기 때문이다. 리비전 1(v1)로 가려면 --to-revision=1. 마지막으로 파일을 클러스터 상태와 맞췄다. kubectl diff가 아무것도 출력하지 않고 exit 0이면 파일과 클러스터가 같다. 롤백 뒤 이 한 줄을 습관으로 둔다. 그러지 않으면 다음 apply가 v3를 다시 밀어 넣는다.

4체크포인트

문서를 덮고 진행한다.

  1. day01-web:v1(D1) 또는 nginx:1.30으로 replicas 2짜리 디플로이먼트 cp-web을 파일로 써서 apply하고, 파드의 pod-template-hash를 읽는다.
  2. 그 파드 둘을 지우고 다시 2개가 되는 것을 -w로 보인다.
  3. 이미지를 다른 태그로 바꿔 apply하고 rollout status·get rs로 레플리카셋 두 개를 보인다.
  4. 존재하지 않는 태그로 apply한 뒤 READY 수가 줄지 않았음을 보이고 rollout undo로 복구한다.
  5. 롤백 뒤 kubectl diff가 비어 있게 파일을 맞춘다.

5개 중 4개 이상이면 D5로 간다. 4번이 막히면 8단계의 get deploy 출력에서 READY·UP-TO-DATE·AVAILABLE 세 열의 뜻을 다시 읽는다.

5정리

order-api 디플로이먼트는 v2·4개인 채로 남긴다. 내일 서비스를 붙인다. 체크포인트에서 만든 것만 지운다.

$ kubectl delete deployment cp-web --ignore-not-found
$ kubectl get deploy,rs,pods -l app=order-api
deployment.apps/order-api   4/4   ...
replicaset.apps/order-api-5b8d7c9f2   4   4   4
replicaset.apps/order-api-7d9c4f6b8   0   0   0
replicaset.apps/order-api-9f3e1a7c4   0   0   0
pod/... × 4  Running
$ docker images order-api --format '{{.Repository}}:{{.Tag}}'
order-api:v2
order-api:v1

0개짜리 레플리카셋 두 개는 이력이다. 지우지 않는다(revisionHistoryLimit이 관리한다). order-api-deploy.yaml은 D5부터 계속 고쳐 쓰므로 ~/k8s-study/day04/에 그대로 둔다.

D5 예고

4개 파드에 IP가 4개 있고 매번 바뀐다. 내일은 그 앞에 고정된 이름과 IP 하나를 세우는 서비스를 만들고, 그 IP가 실체 없는 가상 주소라는 것과 요청이 어느 파드로 어떻게 배달되는지를 노드 3개로 늘려 확인한다. 오늘 본 롤링 업데이트를 트래픽을 흘리면서 다시 한다.
