1이론

파드가 무엇인지, 매니페스트 네 줄이 무엇을 뜻하는지, 파드가 어떤 상태를 거치는지, 그리고 리소스를 묶는 두 도구(네임스페이스·라벨).

1.1 파드는 컨테이너를 담는 최소 단위다

쿠버네티스는 컨테이너를 직접 다루지 않는다. 파드(Pod)가 배포·스케줄링·삭제의 단위이고, 컨테이너는 파드 안에 하나 이상 들어간다. 한 파드 안의 컨테이너들은 세 가지를 공유한다.

  • 네트워크 — 같은 IP, 같은 포트 공간. 서로를 localhost로 부른다. 그래서 한 파드 안에서 두 컨테이너가 같은 포트를 쓸 수 없다.
  • 스토리지 — 파드에 선언한 볼륨을 여러 컨테이너가 같이 마운트할 수 있다(D9).
  • 수명 — 같은 노드에 함께 배치되고 함께 죽는다.

그래서 "한 파드 = 한 애플리케이션 프로세스 + 그것을 돕는 보조 컨테이너"가 기본형이다. 로그를 수집하거나 프록시를 붙이는 보조 컨테이너를 사이드카(sidecar)라 부른다. 서로 무관한 두 앱(예: 웹 서버와 DB)을 한 파드에 넣지 않는다. 따로 늘리고 따로 죽일 수 없어지기 때문이다.

파드는 일회용이다. 파드가 죽거나 노드가 사라지면 그 파드는 끝이고, D2에서 봤듯 되살리는 것은 상위 컨트롤러(D4)의 몫이다. 파드 IP도 재생성 때마다 바뀐다. 그래서 파드 IP를 어디에도 적어 두지 않는다(D5 Service).

1.2 매니페스트 네 줄

API 서버에 보내는 모든 오브젝트는 같은 뼈대를 가진다. kubectl run이 만들어 준 것도 결국 이 구조를 채워 보낸 것이다.

kubectl create -f는 없으면 만들고 있으면 실패한다. kubectl apply -f는 없으면 만들고 있으면 파일대로 고친다. 파일을 고쳐서 다시 적용하는 흐름이 기본이므로 apply만 쓴다. apply는 마지막으로 적용한 내용을 오브젝트에 기록해 두고(kubectl.kubernetes.io/last-applied-configuration), 다음 apply 때 세 가지(마지막 적용본·현재 파일·실제 오브젝트)를 비교해 바뀐 부분만 반영한다.

1.3 파드의 상태: phase와 컨테이너 상태

kubectl get pods의 STATUS 열은 두 층의 정보를 합쳐 보여 준다. 파드 전체의 단계(phase)와, 그 안 컨테이너 각각의 상태다.

재시작 여부는 spec.restartPolicy가 정한다. 기본값 Always는 컨테이너가 어떤 코드로 끝나든 다시 띄우고, OnFailure는 0이 아닐 때만, Never는 안 띄운다. 재시작이 반복되면 kubelet이 간격을 10초·20초·40초… 최대 5분까지 늘리는데, 그 대기 상태가 CrashLoopBackOff다.

1.4 네임스페이스: 클러스터 안의 칸막이

네임스페이스(Namespace)는 이름의 유효 범위다. 같은 이름의 파드가 서로 다른 네임스페이스에 공존할 수 있고, 조회·권한(D12)·리소스 한도가 이 단위로 걸린다. 클러스터를 만들면 네 개가 있다.

네임스페이스용도
default네임스페이스를 안 적으면 여기. 실습이 아니면 쓰지 않는 습관을 들인다.
kube-systemD2에서 본 컨트롤 플레인·CNI·DNS. 손대지 않는다.
kube-public인증 없이 읽을 수 있는 공개 정보(클러스터 정보 컨피그맵).
kube-node-lease노드가 살아 있음을 알리는 하트비트(Lease) 오브젝트.

네임스페이스에 속하지 않는 오브젝트도 있다. 노드, 네임스페이스 자체, 스토리지클래스, 클러스터롤이 그렇다. kubectl api-resources의 NAMESPACED 열이 false인 것들이다.

1.5 라벨: 연결의 접착제

라벨(label)은 metadata.labels의 키-값 쌍이다. 이름은 하나뿐이지만 라벨은 여러 개를 붙일 수 있고, 무엇보다 다른 오브젝트가 이것으로 파드를 고른다. 디플로이먼트가 자기 파드를 찾을 때(D4), 서비스가 트래픽을 보낼 파드를 고를 때(D5), 네트워크 정책이 대상을 정할 때(D12) 전부 라벨 셀렉터(selector)를 쓴다. 쿠버네티스에는 "이 서비스는 저 파드를 가리킨다"는 직접 참조가 없다. 라벨이 맞으면 연결되고, 틀리면 아무 말 없이 연결되지 않는다.

어노테이션(annotation)은 같은 자리에 있지만 셀렉터에 쓰이지 않는다. 빌드 번호, 담당자, 도구가 남기는 메모가 들어간다. 1.2절의 last-applied-configuration이 어노테이션이다.

3따라하기

매니페스트 하나로 시작해, 고장 난 파드 두 종류를 고치고, 네임스페이스·라벨로 정리한 뒤, 같은 것을 Headlamp에서 본다.

1파드 매니페스트: 쓰고, 적용하고, 돌려받는다

D2의 kubectl run web을 파일로 바꾼다. 내가 쓴 것과 클러스터가 채운 것을 비교한다.

$ cat > web-pod.yaml <<'EOF'
apiVersion: v1
kind: Pod
metadata:
  name: web
  labels:
    app: web
spec:
  containers:
  - name: nginx
    image: nginx:1.30
    ports:
    - containerPort: 80
EOF

$ kubectl apply -f web-pod.yaml
pod/web created

$ kubectl get pod web -o wide
NAME   READY   STATUS    RESTARTS   AGE   IP           NODE                    NOMINATED NODE   READINESS GATES
web    1/1     Running   0          6s    10.244.0.9   desktop-control-plane   <none>           <none>

$ kubectl get pod web -o yaml | grep -n -E '^(apiVersion|kind|metadata|spec|status):'
1:apiVersion: v1
2:kind: Pod
3:metadata:
21:spec:
68:status:

$ kubectl get pod web -o jsonpath='{.spec.restartPolicy} / {.spec.nodeName} / {.status.podIP} / {.status.phase}{"\n"}'
Always / desktop-control-plane / 10.244.0.9 / Running

읽을 것 — 12줄을 보냈는데 100줄 가까이 돌아왔다. metadata에는 uid·creationTimestamp가, spec에는 내가 안 쓴 기본값(restartPolicy: Always, dnsPolicy, serviceAccountName)과 스케줄러가 쓴 nodeName이, status에는 kubelet이 보고한 IP·phase·컨테이너 상태가 들어 있다. 파일에는 이 중 spec까지만 쓴다.

$ kubectl apply -f web-pod.yaml
pod/web unchanged
$ kubectl create -f web-pod.yaml
Error from server (AlreadyExists): error when creating "web-pod.yaml": pods "web" already exists

$ kubectl port-forward pod/web 8080:80 &
$ sleep 1 && curl -s localhost:8080 | grep title
<title>Welcome to nginx!</title>
$ kill %1

읽을 것 — 같은 파일을 두 번 apply하면 unchanged, create는 오류. 이래서 apply만 쓴다. port-forward는 내 터미널과 파드 하나를 잇는 임시 터널이다. 파드 IP 10.244.0.9는 클러스터 안 주소라 macOS에서 직접 닿지 않는다.

2고장 ①: 이미지를 못 받는 파드

가장 흔한 첫 장애. STATUS만 보지 말고 Events를 읽는 습관을 만든다.

$ sed 's/nginx:1.30/nginx:1.30-nonexistent/; s/name: web$/name: web-broken/' web-pod.yaml > web-broken.yaml
$ kubectl apply -f web-broken.yaml
$ sleep 15 && kubectl get pod web-broken
NAME         READY   STATUS             RESTARTS   AGE
web-broken   0/1     ImagePullBackOff   0          15s

$ kubectl describe pod web-broken | sed -n '/^Events:/,$p'
Events:
  Type     Reason     Age                From               Message
  ----     ------     ----               ----               -------
  Normal   Scheduled  20s                default-scheduler  Successfully assigned default/web-broken to desktop-control-plane
  Normal   Pulling    18s (x2 over 20s)  kubelet            Pulling image "nginx:1.30-nonexistent"
  Warning  Failed     17s (x2 over 19s)  kubelet            Failed to pull image "nginx:1.30-nonexistent": ... not found
  Warning  Failed     17s (x2 over 19s)  kubelet            Error: ErrImagePull
  Normal   BackOff    5s (x3 over 18s)   kubelet            Back-off pulling image "nginx:1.30-nonexistent"
  Warning  Failed     5s (x3 over 18s)   kubelet            Error: ImagePullBackOff

$ kubectl get pod web-broken -o jsonpath='{.status.phase} / {.status.containerStatuses[0].state}{"\n"}'
Pending / {"waiting":{"message":"Back-off pulling image ...","reason":"ImagePullBackOff"}}

읽을 것 — phase는 여전히 Pending이다. STATUS 열의 ImagePullBackOff는 컨테이너 Waiting 상태의 reason이다(도판 2). Events의 From 열을 보면 스케줄링은 끝났고(default-scheduler) 그 뒤는 전부 kubelet의 실패다. 즉 문제는 노드에서, 이미지 이름에서 났다.

$ sed -i '' 's/nginx:1.30-nonexistent/nginx:1.30/' web-broken.yaml   # Linux/WSL: sed -i 's/.../.../'
$ kubectl apply -f web-broken.yaml
pod/web-broken configured
$ kubectl get pod web-broken
NAME         READY   STATUS    RESTARTS   AGE
web-broken   1/1     Running   0          70s

읽을 것 — configured는 apply가 기존 오브젝트를 고쳤다는 뜻이다. 파드의 image는 실행 중에도 바꿀 수 있는 몇 안 되는 필드다. 대부분의 spec 필드는 파드 생성 후 바꿀 수 없어 지우고 다시 만들어야 한다(그래서 D4의 디플로이먼트가 필요하다).

3고장 ②: 계속 죽는 파드

이미지는 받았는데 프로세스가 바로 끝나는 경우. 이때는 Events보다 이전 컨테이너의 로그가 답이다.

$ cat > crash.yaml <<'EOF'
apiVersion: v1
kind: Pod
metadata:
  name: crash
spec:
  containers:
  - name: app
    image: busybox:1.37
    command: ["sh", "-c", "echo 'config file missing: /etc/app.conf'; exit 1"]
EOF
$ kubectl apply -f crash.yaml
$ sleep 40 && kubectl get pod crash
NAME    READY   STATUS             RESTARTS      AGE
crash   0/1     CrashLoopBackOff   3 (12s ago)   40s

$ kubectl logs crash --previous
config file missing: /etc/app.conf

$ kubectl get pod crash -o jsonpath='{.status.containerStatuses[0].lastState.terminated.exitCode} / {.status.containerStatuses[0].lastState.terminated.reason}{"\n"}'
1 / Error

읽을 것 — RESTARTS가 오르고 STATUS가 CrashLoopBackOff다. restartPolicy: Always라서 kubelet이 계속 다시 띄우고, 간격을 늘려 가며 기다리는 중이다. logs --previous는 직전에 죽은 컨테이너의 출력을 보여 준다. 대개 원인은 여기 적혀 있다. exitCode 1 · reason Error가 도판 2의 Terminated 상태다.

$ kubectl delete -f crash.yaml -f web-broken.yaml
pod "crash" deleted
pod "web-broken" deleted

4사이드카: 한 파드, 두 컨테이너, 하나의 localhost

1.1절의 "네트워크 공유"를 본다. 두 번째 컨테이너가 첫 번째를 localhost로 부른다.

$ cat > web-sidecar.yaml <<'EOF'
apiVersion: v1
kind: Pod
metadata:
  name: web-sidecar
  labels:
    app: web
    tier: front
spec:
  containers:
  - name: nginx
    image: nginx:1.30
    ports:
    - containerPort: 80
  - name: probe
    image: busybox:1.37
    command: ["sh", "-c", "while true; do wget -qO- -T 2 http://localhost >/dev/null && echo \"$(date +%T) nginx ok\" || echo \"$(date +%T) nginx down\"; sleep 5; done"]
EOF
$ kubectl apply -f web-sidecar.yaml
$ sleep 12 && kubectl get pod web-sidecar
NAME          READY   STATUS    RESTARTS   AGE
web-sidecar   2/2     Running   0          12s

$ kubectl logs web-sidecar -c probe | tail -3
02:41:07 nginx ok
02:41:12 nginx ok
02:41:17 nginx ok

$ kubectl exec web-sidecar -c probe -- hostname
web-sidecar
$ kubectl exec web-sidecar -c nginx -- hostname
web-sidecar

읽을 것 — READY가 2/2다. probe 컨테이너는 nginx 컨테이너에 아무 설정 없이 http://localhost로 닿는다. 두 컨테이너의 호스트명이 같다. 같은 네트워크 네임스페이스를 쓰기 때문이다. 컨테이너가 둘 이상이면 logs·exec에 -c로 어느 컨테이너인지 적어야 한다.

5네임스페이스: 칸을 나누고 기본 칸을 바꾼다

앞으로 모든 실습 리소스는 study 네임스페이스에 둔다. default를 비워 두면 정리가 쉽다.

$ cat > ns-study.yaml <<'EOF'
apiVersion: v1
kind: Namespace
metadata:
  name: study
EOF
$ kubectl apply -f ns-study.yaml
namespace/study created

$ kubectl get namespaces
NAME                 STATUS   AGE
default              Active   1d
kube-node-lease      Active   1d
kube-public          Active   1d
kube-system          Active   1d
local-path-storage   Active   1d
study                Active   5s

$ kubectl apply -f web-pod.yaml -n study
pod/web created
$ kubectl get pods -n study
NAME   READY   STATUS    RESTARTS   AGE
web    1/1     Running   0          4s
$ kubectl get pods -A -l app=web -o custom-columns='NS:.metadata.namespace,NAME:.metadata.name,IP:.status.podIP'
NS        NAME          IP
default   web           10.244.0.9
default   web-sidecar   10.244.0.11
study     web           10.244.0.12

읽을 것 — web이라는 파드가 default와 study에 하나씩 있다. 이름은 네임스페이스 안에서만 유일하면 된다. 파일에 metadata.namespace를 적지 않았으므로 -n이 결정했다. 파일에 적으면 파일이 이긴다.

$ kubectl config set-context --current --namespace=study
Context "docker-desktop" modified.
$ kubectl get pods
NAME   READY   STATUS    RESTARTS   AGE
web    1/1     Running   0          40s
$ kubectl config view --minify -o jsonpath='{.contexts[0].context.namespace}{"\n"}'
study

읽을 것 — 이제 -n을 안 붙이면 study다. 이 설정은 kubeconfig의 컨텍스트에 저장된다. 다른 사람 화면에서 get pods 결과가 다르면 이것부터 확인한다. 남은 14일은 이 상태로 진행한다.

6라벨: 붙이고, 고르고, 한 번에 지운다

라벨 셀렉터가 실제로 무엇을 잡고 무엇을 놓치는지 본다. 도판 3을 손으로 재현한다.

$ for i in 1 2; do sed "s/name: web$/name: web-$i/" web-pod.yaml | kubectl apply -f -; done
pod/web-1 created
pod/web-2 created
$ kubectl label pod web-1 web-2 tier=front
$ kubectl label pod web tier=canary
$ sed 's/name: web$/name: web-typo/; s/app: web/app: wed/' web-pod.yaml | kubectl apply -f -

$ kubectl get pods --show-labels
NAME       READY   STATUS    RESTARTS   AGE   LABELS
web        1/1     Running   0          3m    app=web,tier=canary
web-1      1/1     Running   0          30s   app=web,tier=front
web-2      1/1     Running   0          30s   app=web,tier=front
web-typo   1/1     Running   0          10s   app=wed

$ kubectl get pods -l app=web -L tier
NAME    READY   STATUS    RESTARTS   AGE   TIER
web     1/1     Running   0          3m    canary
web-1   1/1     Running   0          40s   front
web-2   1/1     Running   0          40s   front

$ kubectl get pods -l 'app=web,tier=front' -o name
pod/web-1
pod/web-2
$ kubectl get pods -l 'app in (web,wed), tier!=canary' -o name
pod/web-1
pod/web-2
pod/web-typo

읽을 것 — -l app=web은 오타 난 web-typo를 조용히 뺀다. 오류도 경고도 없다. 셀렉터는 등호(=, !=)와 집합(in, notin, 키 존재)을 지원하고, 쉼표는 AND다. -L tier는 라벨 값을 열로 뽑는다.

$ kubectl annotate pod web-1 study.example/owner=villain study.example/note="첫 라벨 실습"
$ kubectl get pod web-1 -o jsonpath='{.metadata.annotations}{"\n"}'
{"kubectl.kubernetes.io/last-applied-configuration":"{...}","study.example/note":"첫 라벨 실습","study.example/owner":"villain"}

$ kubectl delete pods -l tier=front
pod "web-1" deleted
pod "web-2" deleted
$ kubectl delete pod web-typo

읽을 것 — 어노테이션에는 apply가 남긴 last-applied-configuration이 이미 들어 있다(1.2절). 라벨 셀렉터로 여러 파드를 한 번에 지웠다. 셀렉터가 넓으면 넓은 만큼 지워지므로, 삭제 전에는 같은 셀렉터로 get을 먼저 친다.

7Headlamp: 같은 것을 화면으로

Helm으로 웹 UI를 설치하고 ServiceAccount 토큰으로 로그인한다. Helm과 RBAC은 각각 D13·D12에서 제대로 다룬다. 오늘은 절차만 따른다.

$ helm repo add headlamp https://kubernetes-sigs.github.io/headlamp/
$ helm repo update
$ helm install headlamp headlamp/headlamp --namespace kube-system
NAME: headlamp
NAMESPACE: kube-system
STATUS: deployed
...

$ kubectl get pods -n kube-system -l app.kubernetes.io/name=headlamp
NAME                        READY   STATUS    RESTARTS   AGE
headlamp-7c9d5b8f6d-x4k2p   1/1     Running   0          30s

# 로그인용 ServiceAccount와 권한 (실습용 cluster-admin)
$ kubectl -n kube-system create serviceaccount headlamp-admin
$ kubectl create clusterrolebinding headlamp-admin \
    --serviceaccount=kube-system:headlamp-admin \
    --clusterrole=cluster-admin

# 토큰 발급 (기본 1시간 유효) — 출력을 복사해 둔다
$ kubectl create token headlamp-admin -n kube-system

$ kubectl port-forward -n kube-system service/headlamp 8080:80

브라우저에서 http://localhost:8080을 열고 토큰을 붙여 넣는다. 로그인 후 확인할 것 세 가지.

  1. 왼쪽 Namespace 선택에서 study를 고른다. 파드 목록에 web 하나가 보인다. 5단계의 kubectl get pods와 같다.
  2. web을 눌러 상세로 들어간다. Labels에 app=web, tier=canary, Events에 Scheduled·Pulled·Created·Started 네 줄. 2단계에서 describe로 본 것이다.
  3. 상단 YAML 탭. 1단계의 get -o yaml과 같은 내용이며 status까지 보인다.

읽을 것 — Headlamp는 kubectl과 똑같이 API 서버에 요청을 보내는 클라이언트일 뿐이다. 토큰이 곧 신분이고, 그 신분에 cluster-admin을 묶었으니 전부 보인다. 토큰이 만료되면 kubectl create token을 다시 실행한다. port-forward 터미널은 Ctrl-C로 끝낸다.

cluster-admin은 실습용이다

공유 클러스터에서는 필요한 권한만 담은 Role을 묶는다. D12에서 pod-viewer 권한으로 Headlamp에 로그인해 시크릿이 안 보이는 것을 확인한다.

4체크포인트

문서를 덮고 진행한다. 3번은 파일 없이 kubectl run으로 만들어도 된다.

  1. 이름 cp-web, 라벨 app=cp, 이미지 nginx:1.30인 파드 매니페스트를 써서 study 네임스페이스에 apply하고 Running을 확인한다.
  2. get -o yaml 출력에서 스케줄러가 쓴 필드 하나와 kubelet이 쓴 필드 하나를 가리킨다.
  3. 존재하지 않는 이미지 태그로 파드를 만들고, Events에서 어느 컴포넌트(From 열)가 실패를 보고했는지 말한 뒤 고친다.
  4. exit 1로 끝나는 파드를 만들고 logs --previous로 마지막 출력을 읽는다.
  5. 파드 3개에 라벨을 붙여 셀렉터 하나로 2개만 조회하고, 같은 셀렉터로 그 2개만 삭제한다.
  6. Headlamp에서 1번 파드의 Events를 찾는다.

6개 중 5개 이상이면 D4로 간다. 2번이 막히면 1단계의 jsonpath 명령을 다시 본다.

5정리

default 네임스페이스는 비우고, study 네임스페이스와 Headlamp는 남긴다. 컨텍스트의 기본 네임스페이스는 study 그대로 둔다.

$ kubectl delete pod web web-sidecar -n default
$ kubectl delete pod web                       # study (현재 기본 네임스페이스)
$ kubectl get pods -A --field-selector metadata.namespace!=kube-system,metadata.namespace!=local-path-storage
No resources found
$ kubectl get ns study
NAME    STATUS   AGE
study   Active   50m

Headlamp를 지우려면 helm uninstall headlamp -n kube-system과 kubectl delete clusterrolebinding headlamp-admin, kubectl -n kube-system delete serviceaccount headlamp-admin 세 줄이다. D14까지 두는 편이 편하다.

D4 예고

오늘 파드를 지우면 그냥 사라졌다. 내일은 "이 파드를 3개 유지하라"를 선언하는 디플로이먼트를 쓴다. 파드 템플릿이 오늘 매니페스트의 spec이고, 그것을 셀렉터(오늘의 라벨)로 묶는다. Spring Boot 앱을 이미지로 만들어 로컬 레지스트리에 올리고, v1→v2 롤링 업데이트와 롤백까지 간다.
