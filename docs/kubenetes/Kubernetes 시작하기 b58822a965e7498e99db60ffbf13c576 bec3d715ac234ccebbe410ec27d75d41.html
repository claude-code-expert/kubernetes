쿠버네티스 컴포넌트

  • 클러스터 : 쿠버네티스가 시스템을 구성하는 다양한 이벤트를 처리하는데 사용되는 다수의 호스트저장소와 네트워킹 자원의 집합
  • 노드 : 쿠버네티스 워커 머신의 집합
  • 파드 : 클러스터에서 실행중인 컨테이너의 집합
  • 컨트롤 플레인 : 컨테이너의 라이프사이클을 관리하기 위한 API와 인터페이스를 노출하는 컨테이너 오케스트레이션 레이어
    • kube-apiserver : 쿠버네티스 API를 노출하는 컴포넌트, 모든 컴포넌트의 통신을 담당한다.

      기본적으로 쿠버네티스에 대한 조작은 모두 API를 통해 이루어진다.

    • etcd : 모든 클러스터 데이터를 담는 쿠버네티스 뒷단의 저장소로 일관성, 고가용성을 가지는 키-벨류 스토어
    • kube-scheduler : 새로 생성된 파드를 감지하고 실행할 노드를 선택한다.
    • kube-controller-manager : 컨트롤러 프로세스를 실행하는 컴포넌트
      • 노드 컨트롤러 : 노드가 다운되었을 때 통지와 대응
      • 잡 컨트롤러 : 일회성 작업을 나타내는 잡 오브젝트를 감시
      • 엔드포인트 슬라이스 컨트롤러 : 서비스와 파드 사이의 연결고리
      • 서비스 어카운트 컨트롤러 : 새로운 네임스페이스에 대한 기본 어카운트를 생성
    • cloud-controller-manager : 클라우드 공급자의 API에 연결하고 해당 클라우드 플랫폼과 상호 작용하는 컴포넌트 (클러스터와 작용하는 컴포넌트와 구분)
  • 노드 컴포넌트 : 동작중인 파드를 유지시키고 쿠버네티스 런타임 환경을 제공하며, 모든 노드 상에서 동작한다.
    • kubelet : 클러스터의 각 노드에서 실행되는 에이전트
    • kube-proxy : 노드의 네트워크 규칙을 관리
    • 컨테이너 런타임 : 컨테이너 실행을 담당하는 소프트웨어

쿠버네티스 API 오브젝트

쿠버네티스 오프젝트는 내부 시스템에서 영속성을 가지는 엔티티로서, 컨트롤러, 서비스, 파드 등의 인스턴스를 의미하며 쿠버네티스에 의해 제어된다.

같은 종류의 오브젝트 이름은 하나의 네임스페이스에서 유일해야 한다.

  • 워크로드 : 오브젝트의 카테고리를 나타내는 용어로 컨테이너와 파드, 컨트롤러 그룹을 의미한다. 컨테이너의 실행 환경과 관련된 리소스들을 정의하고 관리한다.
  • 컨테이너 : 어플리케이션의 실행 단위로 파드와 함께 실행에 필요한 명령어들을 설정할 수 있다.
  • Pod: 쿠버네티스에서 실행되는 가장 작은 단위의 배포 가능한 유닛이다. 컨테이너화된 애플리케이션을 실행하기 위한 프로세스를 정의한다.
  • Service: 네트워크 노출과 로드 밸런싱을 위한 가상 IP와 포트를 제공한다. 클러스터 내부 또는 외부에서 Pod에 접근하기 위해 사용한다.
  • Deployment: Pod를 생성하고 업데이트하기 위한 선언적인 방법을 제공한다. Pod의 복제본 갯수를 관리하고 롤링 업데이트와 롤백 등을 지원한다.
  • Ingress: 클러스터 내부의 서비스를 외부로 노출하기 위해 트래픽을 관리하는 규칙과 설정을 제공한다.
  • ConfigMap: 애플리케이션의 설정 데이터를 저장하고 전달하기 위한 키-값 쌍을 제공한다.
  • Secret: 애플리케이션에서 사용되는 민감한 정보(인증서, 비밀번호 등)를 안전하게 저장하고 전달한다.
  • Namespace: 쿠버네티스 클러스터의 가상 클러스터로, 리소스를 분리하고 격리하는 데 사용된다

Kubectl 설치

kubectl은 Kubernetes 클러스터와 상호 작용하기 위한 커맨드 라인 도구이다.
Kubernetes Cluster management tool로써 Kubernetes API 서버와 상호 작용하여 클러스터의 상태를 관리하고, 애플리케이션을 배포하고, 클러스터 리소스를 관리하는 데 사용된다.

사용시에 - 옵션 명령어를 통해 몇가지 지정할 수 있는데, 각 옵션들의 의미는 아래와 같다.

  • n 또는 namespace: 특정 네임스페이스를 지정한다. 예를 들어, n my-namespace과 같이 사용하여 my-namespace 네임스페이스 내의 리소스에 접근할 수 있다.
  • f 또는 filename: YAML 또는 JSON 형식의 파일을 사용하여 리소스를 생성 또는 업데이트 한다. 예를 들어, f deployment.yaml과 같이 사용하여 deployment.yaml 파일을 통해 디플로이먼트를 생성할 수 있다.
  • l 또는 selector: 리소스를 라벨 셀렉터를 사용하여 선택한다. 예를 들어, l app=my-app과 같이 사용하여 라벨이 app=my-app인 리소스를 선택할 수 있다.
  • o 또는 output: 출력 형식을 지정한다. 예를 들어, o json 또는 o yaml과 같이 사용하여 JSON 또는 YAML 형식으로 출력할 수 있다.
  • w 또는 watch: 지정된 리소스를 실시간으로 감시한다. 리소스의 변경사항을 실시간으로 확인하고 출력한다.
  • h 또는 help: 도움말을 표시한다. kubectl 명령어와 사용 가능한 옵션들에 대한 간단한 설명을 확인할 수 있다.

Kubernetes에서 Hello-world 컨테이너 실행

가장 기본적인 명령어로 이미지를 실행하고 삭제하는 방법을 먼저 알아보자.

kubectl run hello-world --image=hello-world -it --restart=Never

K8S를 조작하기 위한 커맨드인 kubectl 을 이용하여 컨테이너 실행 명령인 run을 통해 쿠버네티스 오브젝트의 이름을 hello-world라고 지정하였다.
컨테이너의 이미지 (리포지토리명이 없을 경우 도커 허브 사용)인 hello-world를 사용하며 키보드 입출력과 터미널 연결 옵션을 설정 하였다.

Pod의 정보를 조회해보자.

kubectl get pod>NAME          READY   STATUS      RESTARTS   AGEhello-world   0/1     Completed   0          57s

log를 확인해보자.

kubectl logs hello-world

Pod를 종료해보자.

kubectl delete pod hello-world

쿠버네티스 클러스터에 nginx 컨테이너 실행하기

nginx-app 이라는 이름의 새로운 컨테이너를 실행해보자.

kubectl run nginx-app --image nginx --port=80

run을 통해 docker 이미지인 nginx를 80 포트로 [nginx-app] 이라는 이름의 컨테이너를 하나 실행한다.

하지만 쿠버네티스 내부에서 사용하는 네트워크는 외부와는 격리되어 있기 때문에 80으로 직접 접근할수는 없고 Port Forwarding을 하거나 쿠버네티스 service를 사용해야 한다.

Port forwarding 을 통한 외부 접근의 경우 내부 80 포트를 지정된 포트(아래에서는 8081로 설정)로 포워드하여 접근이 가능하다.

kubectl port-forward pod/nginx-app 8081:80

Service 타입으로 외부 노출을 위한 NotePort 연결하기는 내부 포트에 연결된 외부 포트로 접근이 가능해진다.

kubectl expose pod nginx-app --type=NodePort --port=80 --target-port=80 --name=nginx-service

expose로 노출시킬 파드의 이름을 지정하였고 서비스의 유형을 NodePort로 설정하여 모든 노드의 특정 포트로 접근 할 수 있도록 서비스 외부에 노출시키는 방법이다.

kubectl get service 명령어로 nginx-app의 80 port가 어떤 외부 port 에 연결되었는지 확인할 수 있다.

CodeVillains  ~/private-workspace/kube-workspace : > **kubectl get service**NAME        TYPE        CLUSTER-IP     EXTERNAL-IP   PORT(S)                  AGEkube-dns    ClusterIP   10.96.0.10     <none>        53/UDP,53/TCP,9153/TCP   5d15hnginx-service NodePort  10.108.28.47   <none>        80:**30760**/TCP             21m

네임스페이스 (Namespace) 생성

# 네임스페이스 조회kubectl get namespace

별도의 공간을 분리해서 작업해야 하는 환경에서 네임스페이스를 통해 논리적으로 공간을 분리할 수 있다.

클러스터를 생성하면 기본적으로 kube-system과 default 라는 네임스페이스가 생성된다.

kube-system: 쿠버네티스 시스템에서 관리하는 네임스페이스

default: 사용자용 네임스페이스. 별도의 네임스페이스를 명시하지 않으면, 항상 default 네임스페이스가 적용됨

아래와 같이 namespace-sample.yml을 만들어서 파드를 만들어보자.

apiVersion: v1kind: Namespacemetadata:  name: sample

namespace-sample.yml을 실행해보자.

# kubectl apply -f 매니페스트_파일명 혹은 URLkubectl apply -f namespace-sample.yml> namespace/sample created

create 와 apply 는 생성을 할 것인지, 있는 경우 수정 반영하고 없으면 생성하는지로 구분해서 사용하면 된다.

해당 네임스페이스를 이용해서 파드를 만들어보자

kubectl run sample-nginx --image=nginx --namespace=sample> pod/sample-nginx created

sample 네임 스페이스에 파드가 만들어졌는지 확인해보자

kubectl get pod -n sample

쿠버네티스 클러스터에서 sample 이라는 네임 스페이스에 속하는 모든 pod 정보를 조회해온다.

네임 스페이스를 삭제하려면 아래와 같이 입력한다.

kubectl delete pod sample-nginx -n sample> pod "sample-nginx" deletedkubectl delete namespace sample> namespace "sample" deleted

쿠버네티스 구성 요소 중 가장 작은 단위이다. 따라서 클러스터 내에서도 상대적으로 짧은 생명주기를 가진다.

노드가 삭제되거나 생성될 때 파드의 IP가 바뀌게 되므로 이 앞단에서 Service라고 하는 오브젝트를 통해 고정된 단일 엔드포인트를 제공할 수 있다.

파드안의 컨테이너들은 IP 주소와 포트 공간을 공유하게 되고, localhost를 통해 서로를 찾을 수 있다.

nginx 이미지를 사용하여 pod를 생성해보자.

먼저 파드 생성을 위한 파일을 정의한 뒤 apply를 통해 정의한 파드를 생성할 것이다.

apiVersion: v1kind: Podmetadata:  name: nginx-podspec:  containers:    - name: nginx-container      image: nginx      ports:        - containerPort: 80

nginx-pod 라는 이름으로 파드를 생성하며 파드안에는 nginx-container 라는 이름의 컨테이너가 포함되어 있다. nginx 이미지를 사용하여 80포트로 트래픽을 수신한다.

파드를 생성해보자

kubectl apply -f nginx-pod.yml

생성된 파드를 확인해보자.

파드의 생명주기

Pending : 파드의 컨테이너 이미지 생성이 아직 완료되지 않은 상태. (이미지 다운로드 시간 포함)

Running : 파드가 노드에 포함되어 컨테이너 생성이 완료된 상태 (시작 또는 재시작)

Succeeded : 파드에 있는 모든 컨테이너가 성공적으로 생성된 상태

Failed : 파드에 있는 모든 컨테이너가 종료 되거나 시패로 종료된 상태

Unknown : 오류. 호스트와의 통신 오류 등

이제 파드에 접근하기 위해 생성된 nginx 에 포트포워딩(혹은 서비스 설정)을 통해 접근할 수 있다.

kubectl port-forward pod/nginx-pod 8082:80Forwarding from 127.0.0.1:8082 -> 80Forwarding from [::1]:8082 -> 80

localhost의 8082번 포트로 접근해보면 nginx가 제대로 나오는 것을 확인할 수 있을 것이다.

파드를 삭제하려면 아래와 같이 입력하면 된다.

kubectl delete pod nginx-pod

파드를 다시 확인해보면 정상적으로 삭제된 것을 확인할 수 있다.

Dockerfile을 통한 이미지 생성

먼저 Docker 빌드 파일을 만든다.

FROM nginx:latestRUN echo '<h1> Hello World! </h1>' >> index.htmlRUN cp /index.html /usr/share/nginx/html

FROM nginx:latest 명령어는 nginx의 최신 버전 이미지를 Docker Hub의 공식 Registry 를 사용하여 현재 Dockerfile의 베이스 이미지로 사용한다는 내용이고, 두번째 줄의 내용처럼 hello world 라는 태그로 index.html을 작성하였다.

현재 디렉토리의 index.html 을 가상의 디렉토리에 있는 nginx의 document root에 복사하여 컨테이너가 실행할 때 생성한 index.html 을 보여주게 되는 것이다.

Docker 이미지의 파일 시스템은 컨테이너 내부에 존재하는 독립적인 파일 시스템이다. Docker 컨테이너는 호스트 시스템과 완전히 분리되어 있으며, 각 컨테이너는 자체 파일 시스템을 가지고 있다.

Nginx 컨테이너는 정적 파일을 서비스하기 위해 특정 디렉토리를 사용하는데, 일반적으로 /usr/share/nginx/html 디렉토리가 Nginx의 기본 디렉토리로 사용되므로 해당 디렉토리를 지정해주었다. 이 디렉토리에 위치한 파일들이 nginx에 의해 서비스 될 것이다.

이미지를 빌드하려면 아래와 같이 실행 해야 한다.

docker build -t nginx-app .
  • t 는 tag, -f는 Dockerfile의 경로와 이름을 지정할 수 있다. 현재 디렉토리에 Dockerfile이 존재하므로 . 으로 현재 경로를 지정하였다.

. 으로 인해 현재 경로의 Dockerfile을 사용하여 nginx-app이라는 이름의 도커 이미지를 빌드하였다.

URL을 지정해줄 수도 있다.

# ctx 경로의 Dockerfile을 이용해 URL을 지정한 경우docker build -f ctx/Dockerfile http://server/ctx.tar.gz

현재 빌드한 이미지를 Docker hub에 업로드 하기전에, 잘 동작하는지 부터 확인해보자.

docker run --name=web_server -d -p 80:80 nginx-app

이 명령어는 호스트의 80 포트와 컨테이너의 80 포트를 연결하여 Nginx 웹 서버가 실행된다.

설정 이름은 —name으로 web_server 라고 지정 해주었다. 실행헤사 정상적으로 처리가 되었다면 a905b8c5ea14b43a1e3fe0ed242d956318b1dbc39b60a30dc11293b6af185a2a 와 같이 컨테이너의 ID가 출력된다.

이제 호스트에서 http://localhost로 접속하면 Nginx 서버가 작동하는 것을 확인할 수 있다.

혹은 curl localhost:80 을 호출해도 hello world 가 출력되는 것을 확인할 수 있을 것이다

Spring Helloworld 어플리케이션 배포하기

쿠버네티스 클러스터에 기본 어플리케이션을 배포해보도록 하자.

배포 과정은 우선 어플리케이션의 이미지를 빌드한 뒤, service 설정과 deployment 설정 파일을 배포하는 형태가 될 것이다.

서비스

클라이언트의 요청을 파드에 전달하는 역할을 담당한다.

서비스는 로드밸런서의 역할을 가지며 클라이언트의 요청을 받기 위한 대표 IP(Cluster IP) 주소를 획득한다. 이는 내부 DNS에 등록되기 때문에 클라이언트는 서비스의 이름으로 IP에 접근할 수 있다.

Service 파일은 서비스 유형과 포트, 프로토콜 등을 정의하는 파일로 Pod 그룹에 대한 네트워크 엔드포인트를 노출하고, 로드 밸런싱 및 서비스 디스커버리를 가능하게 한다. 서비스를 통해 클러스터 내에서 L4(IP와 포트를 통한 통신) 역할로 어플리케이션의 네트워크 접근을 관리한다.

부하분산, DNS 접근, 환경 변수 설정, 타입 지정, 어피니티, 셀렉터와 라벨등을 부여한 파드 연결등을 담당한다.

파드가 어플리케이션 수정/배포시에 생성이나 삭제가 빈번하기 때문에 노드가 바뀔때마다 IP가 변경되는 문제를 내부에서 고정된 단일 엔드포인트로 제공할 필요가 있기 때문에 Service 라는 오브젝트가 사용되는 것이다.

서비스 타입은 아래 4가지로 구분한다.

  1. ClusterIP: 쿠버네티스 클러스터 내부에서만 접근 가능한 IP를 할당한다. 일반적으로 내부 서비스 간 통신에 사용.
  1. NodePort: 클러스터의 각 노드에 특정 포트를 열어 해당 포트를 통해 서비스에 접근할 수 있도록 한다. 외부에서 노드의 IP와 NodePort를 통해 서비스에 접근할 수 있다.
  1. LoadBalancer: 외부의 로드밸런서를 파드에 연결한다. 접근 가능한 외부 IP를 부여하여 클러스터 외부에서 파드에 접근할 수 있다.
  1. ExternalName: 클러스터 내부에서 외부 서비스에 대한 DNS 조회를 하여 클러스터 외부에 접근할 수 있다.

Deployment는 어플리케이션의 배포를 정의하는데 사용한다. 어플리케이션의 컨테이너 이미지, 환경 변수, 복제본 인스턴스등의 생성과 스케일링, 업데이트등을 관리하며 가용성과 확장성을 제공하게 된다.

쿠버네티스에서 설정은 yml(혹은 yaml) 형식으로 정의하여 설정 파일들을 적용하게 되는데, 첫 어플리케이션으로 helloworld 라는 이름의 앱을 설정해보도록 한다.

IntelliJ에서 File > New > Project를 선택한 후 Spring boot 기본 프로젝트를 생성한다. 여기서는 lombok과 Spring web 만 Gradle에 포함하였다.

Controller를 하나 생성한 뒤 프로젝트 루트에서 gradle 빌드를 실행해보자. 기본 설정만 세팅 했기 때문에 IntelliJ의 Terminal 에서 간단하게 빌드할 수 있을것이다.

package com.example.k8ssampleboot.controller;import lombok.extern.slf4j.Slf4j;import org.springframework.core.env.Environment;import org.springframework.web.bind.annotation.GetMapping;import org.springframework.web.bind.annotation.RestController;@Slf4j@RestControllerpublic class IndexController {    private final Environment environment;    public IndexController(Environment environment) {        this.environment = environment;    }    @GetMapping("/hello")    public String getHello() {        String helloWorld = "Hello World! V1";        String host = environment.getProperty("HOSTNAME");        log.info("##### getHello V1 = {} and Host = {}", helloWorld, host);        return helloWorld + " (Host = " + host + ")";    }}

간단히 hello world 를 출력하고 접속한 Pod의 인스턴스 명이 무엇인지 확인해야 하므로 환경 변수의 Host name을 출력하고, 동시에 로그도 추가해주었다.
http://localhost:8080/hello 로 접근하면 문자가 출려되는 간단한 어플리케이션이다.

Service 로드밸런서 생성

서비스는 파드에 접근할 수 있도록 정책을 정의하는 역할을 한다. LoadBalancer를 통해 서비스가 외부에 노출을 하게 된다거나 포트를 연결하여 해당 파트와 통신할 수 있게 한다.

apiVersion: v1kind: Servicemetadata:  name: k8s-sample-boot-servicespec:  type: LoadBalancer  selector:    app: k8s-sample-boot  ports:    - protocol: TCP      port: 8080      targetPort: 8080      nodePort: 32000

로드밸런서 타입으로 서비스를 생성하되, 서비스가 사용할 포트 8080과 서비스로 전달된 요청을 받을 Pod 의 포트 번호 (targetPort)를 8080으로 설정하였다.

위와 같이 yaml 파일을 통해 어플리케이션의 관리와 정책을 정의하는 선언서 파일을 매니페스트라고 한다. 이 정책 파일이 오브젝트별로 다양하기 때문에 템플릿화 하여 사용하는것이 좋고, 주로 쓰는 템플릿 도구는 helm 이나 kustomize 가 있다.

서비스는 클러스터 외부에서 nodePort 에 접근할 수 있다. apply 구문으로 file 옵션을 주어 현재 디렉토리의 service 파일을 통해 서비스를 생성한다.

kubectl apply -f service.yml

만약 서비스가 제대로 생성되었는지 확인하려면 레이블을 app=[서비스명]으로 필터링해서 오브젝트를 찾아볼 수 있다.

# 서비스 목록 조회kubectl get service# 네임스페이스로 생성된 서비스 레이블 조회kubectl get all -l app=k8s-sample-boot-service

서비스 목록 조회 결과는 아래와 같이 나올것이다.

/private-workspace/k8s-sample-boot > kubectl get serviceNAME                      TYPE           CLUSTER-IP    EXTERNAL-IP   PORT(S)          AGEk8s-sample-boot-service   LoadBalancer   10.96.38.41   localhost     8080:32000/TCP   4h47mkubernetes                ClusterIP      10.96.0.1     <none>        443/TCP          12d

여기서 CLUSTER-IP는 해당 서비스의 고정된 IP이다. 서비스를 삭제하지 않는 한 IP는 변하지 않는다.

하지만 클러스터 외부에서는 CLUSTER-IP 로 만들어진 서비스의 해당 IP로 접근할 수 없다. 이를 외부에서 접근할수 있도록 NodePort 등을 이용하여 노출시켜줘야 접근이 가능해진다.

NodePort는 쿠버네티스에서 단일 파드의 서비스 포트를 호스트의 특정 포트에 매핑시켜서 [host-ip:port] 와 같은 형식으로 노출시켜주는 서비스를 말한다.

NodePort 타입으로 지정 가능한 호스트의 포트 대역은 30000-32767 까지이다.

디플로이먼트(Deployment) 생성

Deployment는 어플리케이션의 배포 관리를 위한 리소스이다. 주로 파드의 갯수와 스케일링, 롤링 업데이트, 롤백 등을 처리하기 위한 용도이다.

아래는 Deployment 리소스를 정의 파일인데, 파드와 레플리카셋(복제본)에 대한 정의를 담고 있는 컨트롤러이다.

apiVersion: apps/v1 # Deployment 가 사용하는 API 버전kind: Deploymentmetadata:  name: k8s-sample-bootspec:  replicas: 3  selector:    matchLabels:      app: k8s-sample-boot  template:    metadata:      labels:        app: k8s-sample-boot    spec:      containers:        - name: k8s-sample-boot                    # 로컬 Registry일 경우 localhost:5000/demo/k8s-sample-boot:v1          image: demo/k8s-sample-boot:latest  # 이미지 경로          ports:            - protocol: TCP              containerPort: 8080

파일을 살펴보면 kind는 Deployment로 지정하였고, Deployment Spec은 3개의 본제본 (ReplicaSet) 인스턴스를 생성하도록 지정하였다.

사용할 컨테이너의 이미지를 지정한 뒤 컨테이너에서 개방해야 할 포트를 지정해주면 된다.

이 역시 apply 를 통해서 생성한다.

kubectl apply -f deployment.yml

Port-forward로 연결한 뒤 cURL이나 브라우저에서 hello API를 호출하면 아래와 같이 결과가 나올 것이다.

다만, 브라우저로 테스트할 때는 요청이 있을때마다 파드에 지정된 곳으로만 쏠리는 것을 확인할 수 있는데, 이는 Port-forward 설정에 따른 브라우저의 동작 방식 때문이다.

Port-forward는 로컬 머신과 Kubernetes 클러스터 내부의 파드간에 특정 포트를 전달해주는 방식으로 로컬 포트와 Kubernetes 파드의 포트를 매핑하고, 로컬에서 파드에 직접 요청을 전달하게 된다.
Port-forward는 로컬 머신과 Pod 간의 1:1 연결을 생성하므로, 특정 파드에 대한 요청은 해당 파드로만 전달 되고, 따라서 우리가 생각한 분산 처리가 이루어지지 않는다.

단순히 번갈아가면서 파드를 호출하는지를 보려면 Proxy를 실행하여 이 프록시를 통해 cURL로 호출해서 테스트 해보면 될 것이다.

kubectl proxycurl http://localhost:8001/api/v1/namespaces/default/services/k8s-sample-boot-service:8080/proxy/hello

로컬에서 실행 중인 Kubernetes 클러스터 API 서버의 엔드포인트(8081)을 통해 서비스 포트로 프록시를 설정해서 서비스를 통해 직접 hello를 호출하는 방식이다.

proxy가 잘 동작한다면 브라우저에서 http://localhost:8001로 접근할 때 Kubernetes API 서버의 정보들이 출력된다.

curl -X GET http://localhost:8080/hello

프록시 동작후 localhost curl을 호출해보면 각 Pod에 요청이 전달될 것이다.

인그레스

NodePort는 지정된 포트 대역 (30000~32767) 만 사용할 수 있기 때문에 실제 어플리케이션을 설계할때는 ingress 컨트롤러를 설정해서 외부에서 접근 가능한 URL을 제공하는 것이 일반적이다.

ingress는 쿠버네티스 외부에서 클러스터 내부로 접근하는 규칙과 설정을 정의하는 리소스 모음이다.

서비스의 NodePort로 클러스터 외부에서 내부 파드로 접근은 할 수 있지만, URL로 접근할수는 없기 때문에 인그레스를 통해 URL 경로에 따라 내부 서비스로 전달(라우팅)을 하게 된다.

Ingress 컨트롤러는 Ingress 리소스를 사용하여 라우팅 규칙을 정의하고, 클러스터 외부에서 이를 접근할 수 있도록 엔드포인트를 노출 한다.

이를 통해 클러스터 내의 서비스를 외부에 노출하고, 트래픽을 적절히 분배하고 (부하분산), SSL/TLS 암호화 등을 관리할 수 있다.

Ingress 컨트롤러는 Kubernetes 클러스터 외부에서 접근 가능한 IP 또는 도메인을 사용하여 트래픽을 라우팅하므로, 클러스터 외부에서 Ingress에 정의된 경로 또는 도메인으로 접근하면 해당 서비스에 정의한대로 각 도메인 경로에 트래픽을 전송하게 된다.

따라서 인그레스 리소스를 사용하려면 클러스터에는 반드시 실행 중인 인그레스 컨트롤러(Ingress Controller)가 존재해야 한다.

쿠버네티스에서 공식적으로 제공하는 인그레스 컨트롤러는 ingress-gce와 ingress-nginx 가 있다.

정리하면 인그레스는

  • URL과 어플리케이션 매핑
  • 가상 호스트를 통한 복수의 도메인 지원
  • 클라이언트의 요청을 여러 파드에 분산
  • SSL/TLS
  • 세션 어피니티 지원

과 같은 기능들을 지원한다.
