외부에서 들어오는 길 — Gateway API

어제 서비스 두 개가 localhost:8080과 8081을 하나씩 차지했다. 서비스가 열 개면 포트 열 개다. 오늘은 진입점 하나(80번)를 세우고 경로와 호스트로 나눈다. 서비스는 L4(포트)까지, 그 위 L7(URL·헤더) 라우팅은 Gateway API가 맡는다. 표준(Gateway API)과 구현체(Envoy Gateway)를 구분해서 보고, 서비스는 전부 ClusterIP로 되돌려 Gateway 뒤로 숨긴다.

  1. GatewayClass·Gateway·HTTPRoute 세 오브젝트가 각각 누구의 것이고 무엇을 정하는지 말한다.
  2. Envoy Gateway를 설치하고 curl localhost/orders가 ClusterIP 서비스까지 도달하게 한다.
  3. HTTPRoute의 status 조건(Accepted, ResolvedRefs)으로 잘못된 backendRef를 진단한다.
  4. 경로 재작성(URLRewrite)과 가중치 분배(weight)를 HTTPRoute 한 파일로 설정한다.
  5. 빈 클러스터에서 D4~D6 매니페스트만으로 전체를 재구축한다(체크포인트 B).

1이론

서비스와 무엇이 다른지, 세 오브젝트의 역할 분리, 구현체가 실제로 만드는 것, 그리고 Ingress 리소스의 현재 위치.

1.1 L4와 L7

D5의 서비스는 "이 IP의 이 포트로 온 것은 저 파드들 중 하나로"까지만 안다. 패킷의 목적지 주소·포트만 보고 결정하는 L4다. HTTP 요청 안의 URL 경로, 호스트 헤더, 메서드는 보지 않는다. 그래서 /orders는 order-api로, /users는 user-api로 나누려면 요청을 열어 읽는 L7 프록시가 필요하다. 그 프록시를 어떻게 선언할지 정한 표준이 Gateway API다.

1.2 세 오브젝트, 세 역할

오브젝트누가 관리하나무엇을 정하나
GatewayClass인프라 제공자"어떤 구현체가 처리하나". 컨트롤러 이름 하나를 가리킨다. 클러스터 범위, 보통 하나.
Gateway클러스터·플랫폼 운영자"어디로 들어오나". 리스너(포트·프로토콜·호스트명·TLS)를 나열한다. 만들면 구현체가 실제 프록시 파드와 LoadBalancer 서비스를 띄운다.
HTTPRoute애플리케이션 개발자"어떤 요청을 어느 서비스로". Gateway에 붙어(parentRefs) 경로·헤더 매칭과 backendRefs를 정한다. 네임스페이스 범위.

이 분리가 핵심이다. 개발자는 자기 네임스페이스에서 HTTPRoute만 만지고, 포트 80을 여는 결정과 TLS 인증서는 Gateway를 가진 쪽이 한다. 기본적으로 HTTPRoute는 같은 네임스페이스의 Gateway에만 붙을 수 있고, 다른 네임스페이스의 Gateway나 서비스를 참조하려면 상대편이 ReferenceGrant로 허락해야 한다. 오늘은 셋 다 study에 두어 그 문제를 피한다.

1.3 구현체가 하는 일

Gateway API는 CRD(사용자 정의 리소스)로 이루어진 명세일 뿐이다. 오브젝트를 만들어도 그것을 읽어 프록시를 띄우는 컨트롤러가 없으면 아무 일도 안 생긴다. 오늘 쓰는 Envoy Gateway는 CNCF의 Envoy 프록시를 데이터 플레인으로 쓰는 구현체다. Helm 차트 하나가 CRD와 컨트롤러(envoy-gateway 디플로이먼트)를 설치하고, 이후 Gateway를 만들 때마다 Envoy 파드 + LoadBalancer 서비스를 envoy-gateway-system에 생성한다. Docker Desktop이 그 LoadBalancer를 localhost로 열어 주는 것은 D5와 같은 원리다.

구현체는 여럿이다(Envoy Gateway, Cilium, Istio, NGINX Gateway Fabric, 클라우드 LB 컨트롤러). HTTPRoute 파일은 어느 구현체에서도 같다. 그래서 표준을 배우는 것이 구현체 하나의 설정 문법을 배우는 것보다 오래 간다.

1.4 HTTPRoute가 할 수 있는 것

기능필드오늘
경로 매칭matches.path — PathPrefix / Exact / RegularExpression3단계
호스트 매칭hostnames — 리스너 hostname과 교집합3단계
헤더·쿼리·메서드 매칭matches.headers / queryParams / method6단계 (헤더)
경로 재작성filters[type=URLRewrite]5단계
헤더 추가·제거filters[type=RequestHeaderModifier]5단계
리다이렉트filters[type=RequestRedirect]8단계 (HTTP→HTTPS)

TLS 종료Gateway 리스너 tls.certificateRefs8단계

Envoy Gateway는 이 밖에 인증·속도 제한·타임아웃을 자체 CRD(SecurityPolicy, BackendTrafficPolicy)로 붙인다. 표준을 넘는 기능은 구현체마다 다르므로 오늘은 표준 필드만 쓴다.

1.5 Ingress 리소스의 위치

networking.k8s.io/v1의 Ingress는 지금도 API에 있고 제거 계획이 없다. 다만 기능이 동결됐고(feature-frozen) 새 기능은 Gateway API에만 들어간다. Ingress도 컨트롤러가 있어야 동작하는데, 널리 쓰이던 커뮤니티 ingress-nginx 컨트롤러는 2026년 3월 은퇴해 보안 패치가 없다. 신규 구성은 Gateway API로 만들고, 기존 Ingress 파일이 있으면 ingress2gateway로 변환한다. 7단계에서 같은 라우팅을 Ingress로 적어 두 문법을 비교하고 변환 도구를 돌려 본다.

3HTTPRoute: 경로를 서비스에 잇는다

개발자 몫의 파일. /orders는 order-api로.

$ cat > order-api-route.yaml <<'EOF'
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: order-api-route
  namespace: study
spec:
  parentRefs:
  - name: web-gateway
  rules:
  - matches:
    - path:
        type: PathPrefix
        value: /orders
    backendRefs:
    - name: order-api
      port: 8080
EOF

읽을 것 — localhost/orders가 여러 파드로 분산돼 응답한다. localhost/는 여전히 404다. HTTPRoute가 /orders만 알기 때문이다. status의 두 조건이 진단의 전부다. Accepted는 "Gateway가 이 라우트를 받아 줬나", ResolvedRefs는 "backendRefs가 실제 서비스를 가리키나". 서비스 셀렉터 오류(D5 4단계)와 달리 이쪽은 상태 필드에 이유가 적힌다.

4고장: 없는 서비스를 가리키면

읽을 것 — 라우트는 받아들여졌지만(Accepted=True) 참조가 안 풀렸다(BackendNotFound, 메시지에 이름까지). 클라이언트는 500을 받는다. 404가 아니라 500인 이유는 "경로는 매칭됐는데 보낼 곳이 없다"이기 때문이다. 404=경로 없음, 500=경로는 있는데 백엔드 없음, 503=백엔드는 있는데 파드가 준비 안 됨. 이 셋을 구분하면 어느 층이 고장인지 바로 안다.

5두 번째 경로와 재작성: /gw/orders → gateway → order-api

D5의 gateway 앱은 /orders만 안다. 밖에서 /gw/…로 받아 접두사를 떼고 넘긴다. 요청 헤더도 하나 얹어 어느 경로로 들어왔는지 앱이 알게 한다.

$ cat > gateway-route.yaml <<'EOF'
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: gateway-route
  namespace: study
spec:
  parentRefs:
  - name: web-gateway
  rules:
  - matches:
    - path:
        type: PathPrefix
        value: /gw
    filters:
    - type: URLRewrite
      urlRewrite:
        path:
          type: ReplacePrefixMatch
          replacePrefixMatch: /
    - type: RequestHeaderModifier
      requestHeaderModifier:
        add:
        - name: X-Entry
          value: web-gateway
    backendRefs:
    - name: gateway
      port: 8081
EOF
$ kubectl apply -f gateway-route.yaml
$ sleep 2 && curl -s localhost/gw/orders | cut -c1-58; echo
{"version":"v2","host":"order-api-5b8d7c9f2-w2e5r","orde
$ kubectl get httproute
NAME              HOSTNAMES   AGE
gateway-route                 20s
order-api-route               12m
$ kubectl logs deployment/gateway --tail=3 | grep -i orders || echo "(gateway 앱은 기본 로그를 남기지 않는다)"

읽을 것 — 요청이 두 번 라우팅됐다. Envoy가 /gw/orders를 /orders로 바꿔 gateway 서비스로, gateway 앱이 다시 order-api로. 응답은 같은 order-api 파드들에서 온다. HTTPRoute 두 개가 같은 Gateway에 붙어 있고 경로 접두사로 갈린다. 더 긴 접두사가 우선하므로 /gw와 /가 함께 있어도 충돌하지 않는다.

6가중치와 헤더 매칭: v1을 10%만 섞는다

읽을 것 — 규칙은 위에서부터 평가되고, 더 구체적인 매칭(경로+헤더)이 경로만 있는 것보다 우선한다. 헤더가 있으면 첫 규칙으로 100% v1, 없으면 둘째 규칙으로 90:10. 30번 중 v1이 정확히 3번은 아닐 수 있다(확률). 이 파일 한 장이 카나리 배포의 전부이고, D13에서 가중치를 단계적으로 옮기며 D11의 대시보드로 오류율을 비교한다.

7같은 라우팅을 Ingress로 적어 보고 변환한다

기존 매니페스트를 만났을 때 읽을 수 있어야 한다. Ingress에는 컨트롤러가 없으므로 이 클러스터에서는 아무 일도 안 생긴다.

$ cat > legacy-ingress.yaml <<'EOF'
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: order-api-ingress
  namespace: study
spec:
  ingressClassName: nginx
  rules:
  - http:
      paths:
      - path: /orders
        pathType: Prefix
        backend:
          service:
            name: order-api
            port:
              number: 8080
EOF
$ kubectl apply -f legacy-ingress.yaml
$ kubectl get ingress
NAME                CLASS   HOSTS   ADDRESS   PORTS   AGE
order-api-ingress   nginx   *                 80      5s
$ kubectl get ingressclass
No resources found
$ kubectl delete -f legacy-ingress.yaml

읽을 것 — ADDRESS가 비어 있다. nginx라는 IngressClass도, 그것을 처리할 컨트롤러도 없어서 오브젝트만 저장됐다. Ingress는 경로·백엔드까지는 같지만 재작성·헤더·가중치는 표준 필드가 없어 컨트롤러별 어노테이션으로 해 왔다. 그 어노테이션을 HTTPRoute 필드로 옮겨 주는 것이 ingress2gateway다.

# 변환 도구 (선택) — GitHub 릴리스에서 macOS arm64 바이너리를 받아 실행
$ I2G=https://github.com/kubernetes-sigs/ingress2gateway/releases/download/v1.1.0
$ curl -sSL "$I2G/ingress2gateway_Darwin_arm64.tar.gz" | tar xz ingress2gateway
$ ./ingress2gateway print --providers=ingress-nginx --input-file=legacy-ingress.yaml
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: nginx
  namespace: study
spec:
  gatewayClassName: nginx
  listeners:
  - name: http
    port: 80
    protocol: HTTP
---
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: order-api-ingress-all-hosts
  namespace: study
spec:
  parentRefs:
  - name: nginx
  rules:
  - backendRefs:
    - name: order-api
      port: 8080
    matches:
    - path:
        type: PathPrefix
        value: /orders

읽을 것 — 3단계에서 손으로 쓴 HTTPRoute와 같은 구조가 나온다. Gateway 이름과 클래스는 Ingress의 클래스명을 따라 nginx로 생성되므로 실제로 쓰려면 eg·web-gateway로 바꾼다. 릴리스 파일명·플래그는 ./ingress2gateway print --help로 한 번 확인한다. Intel Mac은 Darwin_x86_64, Linux는 Linux_x86_64.

8TLS 리스너 (선택): 443을 열고 80은 리다이렉트

자체 서명 인증서로 TLS 종료를 Gateway에 맡긴다. 앱은 여전히 평문 8080만 안다.

$ openssl req -x509 -nodes -newkey rsa:2048 -days 30 \
    -keyout tls.key -out tls.crt -subj "/CN=study.local" \
    -addext "subjectAltName=DNS:study.local" 2>/dev/null
$ kubectl create secret tls study-local-tls --cert=tls.crt --key=tls.key
$ rm tls.key tls.crt

$ cat > gateway-api.yaml <<'EOF'
apiVersion: gateway.networking.k8s.io/v1
kind: GatewayClass
metadata:
  name: eg
spec:
  controllerName: gateway.envoyproxy.io/gatewayclass-controller
---
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: web-gateway
  namespace: study
spec:
  gatewayClassName: eg
  listeners:
  - name: http
    protocol: HTTP
    port: 80
    allowedRoutes:
      namespaces:
        from: Same
  - name: https
    protocol: HTTPS
    port: 443
    hostname: study.local
    tls:
      mode: Terminate
      certificateRefs:
      - name: study-local-tls
    allowedRoutes:
      namespaces:
        from: Same
EOF
$ kubectl apply -f gateway-api.yaml
$ sleep 5 && kubectl get gateway web-gateway -o jsonpath='{range .status.listeners[*]}{.name}: {range .conditions[?(@.type=="Programmed")]}{.status}{end}{"\n"}{end}'
http: True
https: True

$ curl -sk --resolve study.local:443:127.0.0.1 https://study.local/orders | cut -c1-40; echo
{"version":"v2","host":"order-api-5b8d7
$ curl -sk --resolve study.local:443:127.0.0.1 -o /dev/null -w '%{ssl_verify_result} %{http_code}\n' https://study.local/orders
18 200

읽을 것 — 리스너 둘 다 Programmed. HTTPRoute는 parentRefs에 리스너 이름을 안 적었으므로 두 리스너에 다 붙는다. --resolve는 DNS 없이 study.local을 127.0.0.1로 보내는 curl 옵션이고, -k는 자체 서명 인증서를 허용한다(ssl_verify_result 18 = 자체 서명). 인증서는 Secret에, 종료는 Envoy에, 앱은 모른다. 80을 443으로 보내려면 http 리스너에 붙는 HTTPRoute에 RequestRedirect(scheme https, statusCode 301) 필터를 두면 된다. 오늘은 80을 열어 둔 채로 간다.

4체크포인트 B · 빈 클러스터에서 재구축

2단계(D4~D6)의 관문. 파일만으로 전부 다시 올린다. 클러스터를 지우지는 않고, study 네임스페이스만 지운다.

  1. kubectl delete ns study로 실습 리소스를 전부 지운다(Gateway·HTTPRoute 포함. envoy-gateway-system은 남는다).
  2. ~/k8s-study의 파일만 사용해 네임스페이스 → order-api 디플로이먼트·서비스 → gateway 디플로이먼트·서비스 → GatewayClass·Gateway → HTTPRoute 순서로 apply한다. 문서를 보지 않는다.
  3. curl http://localhost/orders가 200과 v2 응답을 돌려주고, curl http://localhost/gw/orders도 200이다.
  4. HTTPRoute 하나의 backendRef를 틀리게 고쳐 ResolvedRefs=False를 만들고, message를 읽은 뒤 되돌린다.
  5. 목표 시간 10분. 넘기면 어느 파일이 어디에 있는지 몰라서였는지, 순서를 몰라서였는지 적어 둔다. 그 답이 D13(Helm)의 동기다.
