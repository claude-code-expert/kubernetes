쿠버네티스 14일 · 2단계 배포와 노출 · Day 7

설정을 이미지 밖으로 — 컨피그맵·시크릿, 그리고 1주차 종합

DB 주소 한 줄 때문에 이미지를 세 번 빌드하는 팀이 있다. 설정값은 빌드가 아니라 컨테이너 시작 시점에 정해져야 한다. 오늘은 값을 별도 오브젝트로 빼서 환경 변수와 파일 두 방식으로 주입하고, 값을 고쳤을 때 앱이 언제부터 새 값을 쓰는지를 방식별로 확인한다. 시크릿의 base64가 암호화가 아님을 눈으로 본 뒤, 1주차 파일 전부를 디렉터리 하나로 정리한다.

  2. ConfigMap을 고친 뒤 환경 변수·볼륨 파일·앱 응답 세 곳의 반영 시점이 왜 다른지 설명한다.
  3. 설정 해시 어노테이션으로 "설정이 바뀌었을 때만" 롤링 재배포되게 한다.
  4. get secret -o yaml로 시크릿 값을 그대로 읽어 보이고, 진짜 보호막이 무엇인지 말한다.
  5. D3~D7의 매니페스트를 디렉터리 하나로 정리해 apply -f dir/ 한 번으로 올린다.

1이론

1.1 설정은 이미지에 굽지 않는다

같은 이미지가 개발·스테이징·운영에서 다른 값(DB 주소, 외부 API 키, 기능 플래그)으로 돌아야 한다. 값이 이미지 안에 있으면 환경마다 이미지가 달라지고, 값 하나를 고치려고 빌드·푸시·배포를 반복한다. 쿠버네티스는 값을 두 오브젝트에 담는다. 일반 설정은 컨피그맵(ConfigMap), 비밀은 시크릿(Secret). 둘 다 키-값 묶음이고, 파드 매니페스트에는 값이 아니라 "어느 오브젝트의 어느 키를 가져올지"를 적는다.

1.2 주입 방식은 둘: 환경 변수, 볼륨 파일

방식매니페스트앱이 읽는 법값이 바뀌면
환경 변수 (개별)env[].valueFrom.configMapKeyRef / secretKeyRefSystem.getenv, Spring 프로퍼티 바인딩재시작 전까지 옛 값
환경 변수 (전부)envFrom[].configMapRef / secretRef키 이름이 그대로 변수명재시작 전까지 옛 값
볼륨 파일volumes[].configMap / secret + volumeMounts키 = 파일명, 값 = 파일 내용약 1분 안에 파일 갱신. 앱이 다시 읽어야 반영
볼륨 파일 (subPath)volumeMounts[].subPath로 키 하나만파일 하나갱신되지 않음

환경 변수는 프로세스가 시작할 때 한 번 심긴다. 리눅스 프로세스의 환경은 그 뒤로 바꿀 수 없으므로, 컨피그맵을 고쳐도 살아 있는 컨테이너에는 아무 일도 없다. 볼륨 파일은 kubelet이 주기적으로(기본 1분 동기화 + 캐시) 새 내용으로 바꿔 준다. 심볼릭 링크를 통째로 교체하는 방식이라 원자적이다. 단, subPath로 마운트한 파일은 이 교체 대상에서 빠진다.

1.3 바뀌었을 때만 재배포하기

환경 변수 방식에서 새 값을 쓰려면 파드를 다시 만들어야 한다. kubectl rollout restart로 손으로 할 수도 있지만, 사람이 잊는다. 대신 컨피그맵 내용의 해시를 파드 템플릿의 어노테이션에 적어 둔다. 컨피그맵이 바뀌면 해시가 바뀌고, 템플릿이 바뀌었으니 디플로이먼트가 D4의 롤링 업데이트를 시작한다. 안 바뀌면 해시도 그대로라 아무 일도 없다. 이 기법은 D13의 Helm 차트에서 함수 한 줄(sha256sum)로 자동화된다.

1.4 시크릿: base64는 암호화가 아니다

시크릿은 컨피그맵과 구조가 같고 값이 base64로 인코딩되어 저장된다는 점만 다르다. 인코딩은 누구나 되돌릴 수 있다. kubectl get secret -o yaml을 칠 수 있는 사람은 값을 읽을 수 있고, etcd도 기본 설정에서는 평문으로 저장한다(암호화하려면 API 서버에 EncryptionConfiguration을 붙인다). 그럼에도 시크릿을 따로 두는 이유는 취급이 다르기 때문이다.

  • RBAC에서 컨피그맵과 별개로 권한을 줄 수 있다. 파드는 볼 수 있어도 시크릿은 못 보게(D12).
  • kubelet은 시크릿을 노드 디스크가 아닌 tmpfs(메모리)에 마운트한다.
  • describe와 로그에서 값이 가려진다. 컨피그맵은 그대로 찍힌다.
  • 이미지 pull 인증(kubernetes.io/dockerconfigjson), TLS 인증서(kubernetes.io/tls, D6에서 씀) 같은 타입이 있어 소비하는 쪽이 형식을 안다.

진짜 보호막은 인코딩이 아니라 누가 읽을 수 있는가다. 그래서 D12의 RBAC이 오늘의 후속이다. 그리고 시크릿을 Git에 그대로 넣지 않는 문제는 D13에서 다룬다.

1.5 불변 오브젝트

immutable: true를 붙이면 그 컨피그맵·시크릿은 수정할 수 없고 지우고 다시 만들어야 한다. 실수로 운영 설정을 덮어쓰는 것을 막고, kubelet이 변경 감시를 멈춰 API 서버 부하도 준다. 값이 바뀔 때 이름도 바뀌는(order-api-config-v3) 운영 방식과 짝이 맞는다.

2실습 준비 · order-api v3

설정을 읽는 앱이 필요하다. /config 엔드포인트를 추가해 환경 변수(store.name, api.key)와 파일(store.region)을 보여 준다.

$ cd ~/k8s-study/day04/order-api
$ cat > src/main/java/study/OrderApiApplication.java <<'EOF'
package study;

import java.util.List;
import java.util.Map;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;

@SpringBootApplication
@RestController
public class OrderApiApplication {

    @Value("${store.name:unset}")
    private String storeName;

    @Value("${store.region:unset}")
    private String storeRegion;

    @Value("${api.key:unset}")
    private String apiKey;

    public static void main(String[] args) {
        SpringApplication.run(OrderApiApplication.class, args);
    }

    @GetMapping("/")
    public String root() {
        return "order-api " + version() + " on " + host() + "\n";
    }

    @GetMapping("/orders")
    public Map<String, Object> orders() {
        return Map.of(
            "version", version(),
            "host", host(),
            "orders", List.of(
                Map.of("id", 1, "item", "keyboard"),
                Map.of("id", 2, "item", "mouse")));
    }

    @GetMapping("/config")
    public Map<String, Object> config() {
        return Map.of(
            "version", version(),
            "host", host(),
            "store.name", storeName,
            "store.region", storeRegion,
            "api.key", mask(apiKey));
    }

    private static String mask(String s) {
        if (s == null || s.length() < 4) return "****";
        return s.substring(0, 2) + "****" + s.substring(s.length() - 2);
    }

    private static String version() {
        String v = System.getenv("APP_VERSION");
        return v == null ? "dev" : v;
    }

    private static String host() {
        String h = System.getenv("HOSTNAME");
        return h == null ? "unknown" : h;
    }
}
EOF

$ mkdir -p src/main/resources
$ cat > src/main/resources/application.properties <<'EOF'
spring.config.import=optional:configtree:/config/
EOF

$ docker build --build-arg APP_VERSION=v3 -t order-api:v3 .
$ docker run --rm -e STORE_NAME=local-test -e API_KEY=sk-test-1234 -p 8080:8080 -d --name oa order-api:v3
$ sleep 4 && curl -s localhost:8080/config; echo
{"store.region":"unset","api.key":"sk****34","version":"v3","host":"…","store.name":"local-test"}
$ docker stop oa
$ mkdir -p ~/k8s-study/day07 && cd ~/k8s-study/day07

확인 — 환경 변수 STORE_NAME이 프로퍼티 store.name으로 바인딩됐다(Spring의 완화된 바인딩: 대문자·밑줄 → 소문자·점). store.region은 unset이다. /config/ 디렉터리가 없기 때문이고, 클러스터에서 볼륨으로 채운다. configtree:는 디렉터리 구조를 프로퍼티 이름으로 읽는 Spring Boot 기능이다. /config/store/region 파일이 store.region이 된다.

3따라하기

1컨피그맵 둘, 시크릿 하나

환경 변수용과 파일용을 따로 만든다. 시크릿은 stringData로 써서 base64를 손으로 만들지 않는다.

$ cat > order-api-config.yaml <<'EOF'
apiVersion: v1
kind: ConfigMap
metadata:
  name: order-api-config
data:
  STORE_NAME: study-store
---
apiVersion: v1
kind: ConfigMap
metadata:
  name: order-api-store
data:
  region: seoul
EOF
$ cat > order-api-secret.yaml <<'EOF'
apiVersion: v1
kind: Secret
metadata:
  name: order-api-secret
type: Opaque
stringData:
  API_KEY: sk-live-7f3a9c2e
EOF
$ kubectl apply -f order-api-config.yaml -f order-api-secret.yaml

configmap/order-api-store created
secret/order-api-secret created

$ kubectl get cm,secret

configmap/kube-root-ca.crt    1      2d
configmap/order-api-config    1      5s
configmap/order-api-store     1      5s

NAME                      TYPE                DATA   AGE
secret/order-api-secret   Opaque              1      5s
secret/study-local-tls    kubernetes.io/tls   2      1d

읽을 것 — 시크릿 두 개의 TYPE이 다르다. D6의 TLS 시크릿은 kubernetes.io/tls로 키 이름이 tls.crt·tls.key로 정해져 있고, 오늘 것은 Opaque(자유 형식). kube-root-ca.crt는 모든 네임스페이스에 자동으로 생기는 컨피그맵으로, 파드가 API 서버를 검증할 때 쓴다.

2파드에 주입: 환경 변수 둘 + 볼륨 하나

D4의 디플로이먼트 파일에 세 군데를 추가한다. 이미지도 v3로.

$ cat > order-api-deploy.yaml <<'EOF'
apiVersion: apps/v1
kind: Deployment
metadata:
  name: order-api
  labels:
    app: order-api
spec:
  replicas: 4
  selector:
    matchLabels:
      app: order-api
  template:
    metadata:
      labels:
        app: order-api
      annotations:
        config-hash: "0000000000000000"
    spec:
      containers:
      - name: app
        image: order-api:v3
        ports:
        - containerPort: 8080
        env:
        - name: STORE_NAME
          valueFrom:
            configMapKeyRef:
              name: order-api-config
              key: STORE_NAME
        - name: API_KEY
          valueFrom:
            secretKeyRef:
              name: order-api-secret
              key: API_KEY
        volumeMounts:
        - name: store-config
          mountPath: /config/store
          readOnly: true
      volumes:
      - name: store-config
        configMap:
          name: order-api-store
EOF

읽을 것 — 세 값이 다 앱에 도착했다. 컨테이너 안에서 API_KEY는 평문이다. 시크릿은 파드 안에서는 그냥 값이다. /config/store/region은 실제 파일이 아니라 ..data를 거치는 심볼릭 링크다. 1.2절의 "링크를 통째로 교체"가 이 구조다. 지금 파일의 실체는 타임스탬프 디렉터리 안에 있다.

3값을 고친다: 세 곳의 반영 시점

도판 1을 실제로 밟는다. 컨피그맵 둘을 고치고, 환경 변수·파일·앱 응답을 시간차로 본다.

$ sed -i.bak 's/STORE_NAME: study-store/STORE_NAME: study-store-v2/; s/region: seoul/region: busan/' order-api-config.yaml && rm order-api-config.yaml.bak
$ kubectl apply -f order-api-config.yaml
configmap/order-api-config configured
configmap/order-api-store configured
$ kubectl get pods -l app=order-api -o custom-columns='POD:.metadata.name,AGE:.metadata.creationTimestamp'
(파드 4개, 생성 시각 변화 없음 — 재시작되지 않았다)

$ kubectl exec $POD -- sh -c 'echo $STORE_NAME; cat /config/store/region'
study-store
seoul
$ sleep 75 && kubectl exec $POD -- sh -c 'echo $STORE_NAME; cat /config/store/region; ls /config/store/'
study-store
busan
region
$ curl -s localhost/config; echo
{"store.region":"seoul","api.key":"sk****2e","version":"v3","host":"order-api-6e2f8a1b9-…","store.name":"study-store"}

읽을 것 — 75초 뒤: 환경 변수는 여전히 옛 값, 파일은 busan으로 바뀌었다(..data 링크가 새 디렉터리를 가리킨다). 그런데 앱 응답은 둘 다 옛 값이다. 환경 변수는 프로세스 시작 시 한 번 심겼고, 파일은 바뀌었지만 Spring이 configtree를 시작할 때 한 번만 읽었다. 쿠버네티스는 파일까지 책임졌고, 그 다음은 앱의 몫이다. 파일을 다시 읽는 앱(Spring Cloud의 @RefreshScope, 직접 감시 등)이 아니면 재시작해야 한다.

$ kubectl rollout restart deployment/order-api && kubectl rollout status deployment/order-api
$ curl -s localhost/config; echo
{"store.region":"busan","api.key":"sk****2e","version":"v3","host":"order-api-6e2f8a1b9-…","store.name":"study-store-v2"}

읽을 것 — 재시작하니 둘 다 새 값이다. 최악은 죽는 것이 아니라 틀린 설정으로 계속 도는 것이다. 파일 방식은 "파일은 새 값, 앱은 옛 값"인 상태가 조용히 지속된다. 그래서 다음 단계처럼 설정 변경을 재배포에 묶는다.

4설정 해시: 바뀌었을 때만 자동 재배포

컨피그맵 파일의 해시를 템플릿 어노테이션에 넣는 스크립트를 만든다. 값을 안 바꾸면 apply가 unchanged, 바꾸면 롤링.

$ cat > apply-with-hash.sh <<'EOF'
#!/usr/bin/env bash
# 컨피그맵·시크릿 파일의 해시를 디플로이먼트 템플릿 어노테이션에 심고 전부 apply 한다.
set -euo pipefail
HASH=$(cat order-api-config.yaml order-api-secret.yaml | shasum -a 256 | cut -c1-16)
sed -i.bak "s/config-hash: \".*\"/config-hash: \"${HASH}\"/" order-api-deploy.yaml
rm -f order-api-deploy.yaml.bak
echo "config-hash=${HASH}"
kubectl apply -f order-api-config.yaml -f order-api-secret.yaml -f order-api-deploy.yaml
EOF
$ chmod +x apply-with-hash.sh

$ ./apply-with-hash.sh
config-hash=9a3f1c7e2b8d4f60
configmap/order-api-config unchanged
configmap/order-api-store unchanged
secret/order-api-secret unchanged
deployment.apps/order-api configured      ← 어노테이션 0000… → 해시. 이번 한 번은 롤링
$ kubectl rollout status deployment/order-api

$ ./apply-with-hash.sh
config-hash=9a3f1c7e2b8d4f60
configmap/order-api-config unchanged
configmap/order-api-store unchanged
secret/order-api-secret unchanged
deployment.apps/order-api unchanged       ← 해시 동일 → 아무 일도 없음

$ sed -i.bak 's/region: busan/region: incheon/' order-api-config.yaml && rm order-api-config.yaml.bak
$ ./apply-with-hash.sh && kubectl rollout status deployment/order-api
config-hash=4d7e2a9b1f3c8e05
configmap/order-api-store configured
deployment.apps/order-api configured      ← 해시 변경 → 롤링 업데이트
deployment "order-api" successfully rolled out
$ curl -s localhost/config | grep -o '"store.region":"[a-z]*"'
"store.region":"incheon"
$ kubectl rollout history deployment/order-api | tail -3

읽을 것 — 어노테이션은 파드 템플릿의 일부라 바뀌면 새 레플리카셋이 생긴다(D4). 어노테이션이라 셀렉터나 앱 동작에는 영향이 없다. 이제 "설정 수정 = apply 한 번"이고, 재시작을 잊을 수 없다. shasum은 macOS 기본 명령이다. Linux는 sha256sum으로 바꾼다.

5시크릿을 읽어 본다

base64가 무엇을 막고 무엇을 못 막는지 직접 본다.

$ kubectl get secret order-api-secret -o yaml | grep -A2 '^data'
data:
  API_KEY: c2stbGl2ZS03ZjNhOWMyZQ==
$ kubectl get secret order-api-secret -o jsonpath='{.data.API_KEY}' | base64 -d; echo
sk-live-7f3a9c2e

$ kubectl describe secret order-api-secret | tail -3
Data
====
API_KEY:  16 bytes
$ kubectl describe cm order-api-config | sed -n '/^Data/,/^$/p'
Data
====
STORE_NAME:
----
study-store-v2

$ kubectl get secret order-api-secret -o jsonpath='{.metadata.annotations}' | grep -c stringData
0

읽을 것 — base64 -d 한 번에 값이 나온다. describe는 시크릿 값을 길이만 보여 주고 컨피그맵은 값을 그대로 보여 준다. 취급이 다르다는 것이 이것이다. 마지막 줄: apply 때 쓴 stringData는 저장되지 않고 data(base64)로만 남는다. 단, 어노테이션 last-applied-configuration에는 stringData 원문이 남을 수 있으니 시크릿을 apply로 관리할 때 이 점을 안다(D13에서 대안).

이 값을 읽을 수 있는 사람이 곧 시크릿의 보안 수준이다

지금 우리는 cluster-admin이라 다 보인다. D12에서 get pods는 되지만 get secrets는 Forbidden인 계정을 만들고, Headlamp에서 시크릿 메뉴가 비는 것을 확인한다. 그것이 시크릿의 실제 보호막이다.

6시크릿 타입 둘: 레지스트리 인증, 불변 시크릿

타입이 정해진 시크릿과 immutable의 동작을 짧게 본다.

# (a) 사설 레지스트리 pull 시크릿 — 형식만 확인 (실제 로그인 정보는 넣지 않는다)
$ kubectl create secret docker-registry regcred \
    --docker-server=registry.example.com \
    --docker-username=study --docker-password=not-a-real-password \
    --dry-run=client -o yaml | head -12
apiVersion: v1
data:
  .dockerconfigjson: eyJhdXRocyI6eyJyZWdpc3RyeS5leGFtcGxlLmNvbSI6...
kind: Secret
metadata:
  name: regcred
type: kubernetes.io/dockerconfigjson
# 파드에서는 spec.imagePullSecrets: [{name: regcred}] 로 참조한다

# (b) 불변 시크릿
$ cat > order-api-secret-v2.yaml <<'EOF'
apiVersion: v1
kind: Secret
metadata:
  name: order-api-secret-v2
type: Opaque
immutable: true
stringData:
  API_KEY: sk-live-0b4d6e8f
EOF
$ kubectl apply -f order-api-secret-v2.yaml
$ sed 's/0b4d6e8f/changed00/' order-api-secret-v2.yaml | kubectl apply -f -
The Secret "order-api-secret-v2" is invalid: data: Forbidden: field is immutable when `immutable` is set
$ kubectl delete secret order-api-secret-v2

읽을 것 — dockerconfigjson 타입은 키 이름이 .dockerconfigjson으로 고정이고 kubelet이 그 형식을 알고 읽는다. 불변 시크릿은 수정이 거부된다. 바꾸려면 이름을 바꿔 새로 만들고 디플로이먼트가 새 이름을 가리키게 한다. 이름이 바뀌면 템플릿이 바뀌므로 4단계의 해시 없이도 롤링이 일어난다. 두 기법(해시 vs 이름 버전)은 같은 문제의 두 해법이다.

apply -f 디렉터리의 한계

파일명 순서에 의존하고, 환경별(dev/prod) 값 차이를 표현할 수 없고, 지운 파일의 리소스는 클러스터에 남는다(--prune은 실험적). 이 세 문제를 D13의 Helm·Kustomize·GitOps가 각각 푼다. 오늘은 "파일이 원본"까지만 만들면 된다.

5체크포인트

  1. 컨피그맵 값을 바꾸고, 재빌드 없이 curl localhost/config의 응답이 바뀌게 한다. 어떤 주입 방식이었고 무엇 때문에 그 시점에 바뀌었는지 말한다.
  2. 볼륨으로 마운트한 파드에서 ..data 링크가 가리키는 디렉터리 이름이 컨피그맵 수정 전후로 달라지는 것을 보인다.
  3. apply-with-hash.sh를 값 변경 없이 두 번 실행해 두 번째가 unchanged임을 보인다.
  4. 시크릿 값을 base64 -d로 읽고, describe secret과 describe cm의 출력 차이를 말한다.
  5. week1/ 디렉터리로 kubectl diff -f .가 빈 상태(exit 0)를 만든다.

5개 중 4개 이상이면 D8로 간다. 1번에서 "볼륨인데 안 바뀐다"면 3단계의 마지막 문단을 다시 읽는다.
