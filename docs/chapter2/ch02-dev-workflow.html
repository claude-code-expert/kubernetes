CHAPTER 02

개발자 워크플로

클러스터는 앱을 돌리는 곳이기 이전에 개발자가 일하는 곳이다. 이 장의 질문은 하나 — 팀에 합류한 개발자가 얼마나 빨리, 얼마나 안전하게, 서로 방해 없이 클러스터에서 개발할 수 있는가. 개발 클러스터 전략, 온보딩, 네임스페이스 격리, 그리고 매일 도는 개발 루프를 다룬다.

2026-08 기준 변경 사항 주석 포함

핵심 3줄

1. 개발 클러스터는 "개발자별 1개"가 아니라 "공용 1개 + 네임스페이스 격리"가 기본 — 비용·관리·환경 일관성 모두에서 유리하다.

2. 온보딩은 인증 → kubeconfig → 네임스페이스(쿼터·TTL) → RoleBinding까지를 스크립트 하나로 자동화하고, "30분 내 첫 배포" 같은 KPI로 측정한다.

3. 개발자 경험은 온보딩·개발·테스팅 3단계로 나눠 각각을 설계한다 — 느린 단계가 곧 팀 전체의 병목이다.

2.1목표 2.2개발 클러스터 구축 2.3여러 개발자가 사용할 공용 클러스터 구축 2.4개발자 워크플로 활성화 2.5개발 환경 설정 모범 사례

2.1목표

개발 환경의 품질은 감이 아니라 단계별 KPI로 측정한다. 개발자 경험은 세 단계로 쪼개진다.

단계내용KPI 예시
① 온보딩신규 개발자에게 계정을 발급하고 첫 배포까지 이끄는 과정아무것도 모르는 신입이 30분 안에 최신 앱을 실행
② 개발매일 하는 일 — 코드를 짜서 클러스터에 반복 반영코드 수정이 클러스터에 반영되기까지 수 분 이내
③ 테스팅변경 검증과 결함 원인 추적결함 재현부터 원인 파악까지의 소요 시간

중요한 전제 하나. 개발 클러스터는 프로덕션과 반드시 분리한다. 개발자의 실험이 실사용자에게 닿아서는 안 되고, 반대로 프로덕션 수준의 잠금이 개발 속도를 죽여서도 안 된다.

2.2개발 클러스터 구축

첫 결정: 개발자마다 클러스터를 하나씩 줄 것인가, 큰 클러스터 하나를 함께 쓸 것인가.

개발자별 클러스터는 격리가 완벽하고 남을 망가뜨릴 걱정이 없다. 대신 비용이 인원수에 비례해 늘고, 클러스터마다 버전·애드온이 어긋나며, 운영팀이 관리할 대상이 N개가 된다. 공용 클러스터는 그 반대다 — 자원을 공유해 싸고, 환경이 하나로 통일되며, 모니터링·로깅 같은 공용 서비스를 한 번만 깔면 된다. 남는 문제는 "서로 간섭하지 않게 만드는 것"이고, 그 해법이 다음 절의 네임스페이스다.

참고로 0장에서 만든 kind 클러스터는 "개발자별 클러스터"의 초경량 버전이다. 개인 학습엔 그것으로 충분하지만, 팀 스케일에서는 이 장의 공용 클러스터 설계가 필요해진다.

2.3여러 개발자가 사용할 공용 클러스터 구축

공용 클러스터의 목표는 여러 사용자가 서로의 존재를 느끼지 못하게 만드는 것이다. 격리 단위는 네임스페이스 (Namespace) — 클러스터를 논리적으로 나누는 가상 구획으로, 이름 충돌을 막고 권한과 자원 한도의 적용 경계가 된다. 내 네임스페이스의 frontend 서비스와 옆 사람의 frontend 서비스는 다른 이름 공간에 살기 때문에 충돌하지 않는다.

2.3.1 유저 온보딩

네임스페이스를 주기 전에 사용자가 클러스터에 로그인부터 할 수 있어야 한다. 방법은 두 갈래다.

  • 인증서 기반 — 사용자별 클라이언트 인증서를 발급하고 그것이 담긴 kubeconfig(kubectl의 접속 프로필 파일)를 건넨다. 외부 시스템 없이 되지만, 인증서는 만료 전까지 폐기할 방법이 없다는 치명적 약점이 있다.
  • 외부 아이덴티티 연동 — Microsoft Entra ID, AWS IAM 같은 회사의 기존 신원 시스템으로 클러스터 인증을 위임한다. 퇴사·권한 회수가 신원 시스템에서 한 번에 처리된다.
2026-08 기준 갱신 주석 쿠버네티스 공식 하드닝 가이드는 클라이언트 인증서 방식의 한계를 명시한다 — 개별 폐기 불가(유출돼도 만료까지 유효), 그룹 변경 불가, 키 암호 보호 불가. 사람 사용자 인증의 실무 표준은 OIDC (OpenID Connect) — 외부 신원 제공자가 발급한 토큰으로 로그인하는 개방형 인증 표준 — 또는 클라우드 IAM 연동이다. 인증서는 학습·시스템 컴포넌트용으로만 이해하자. 출처: kubernetes.io/docs/concepts/security/hardening-guide/authentication-mechanisms · kubernetes.io/docs/reference/access-authn-authz/authentication (폐기 미지원 명시)

2.3.2 네임스페이스 생성과 보안

생성 자체는 kubectl create namespace dev-kim 한 줄이다. 실무의 요점은 그 위에 얹는 세 가지다. 첫째, 담당자·팀 같은 메타데이터를 애너테이션 (Annotation) — 셀렉터 조회용이 아닌 보관용 키-값 메타데이터 — 으로 붙여 "이 네임스페이스는 누구 것인가"에 항상 답할 수 있게 한다(수십 개가 되면 템플릿으로 찍어낸다). 둘째, 권한. 셋째, 자원 한도.

apiVersion: v1
kind: Namespace
metadata:
  name: dev-kim
  annotations:
    team: journal-squad
    contact: kim@example.com
    dev-ns/expiry: "2026-08-22"

권한은 RBAC (Role-Based Access Control) — "누가(subject) 무엇을(verb) 어떤 리소스에" 할 수 있는지 역할 단위로 묶어 부여하는 인가 체계 — 로 건다. 권한 묶음이 롤 (Role), 그 묶음을 사용자에게 연결하는 것이 롤바인딩 (RoleBinding)이다. 개발자에게는 롤을 새로 짜기보다 쿠버네티스 내장 ClusterRole인 edit을 자기 네임스페이스 범위로 바인딩하는 것이 정석이다.

apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: dev-kim-edit
  namespace: dev-kim
subjects:
- kind: User
  name: kim@example.com
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: ClusterRole
  name: edit
  apiGroup: rbac.authorization.k8s.io

자원 한도는 리소스쿼터 (ResourceQuota) — 네임스페이스 하나가 쓸 수 있는 CPU·메모리·오브젝트 개수의 총량 상한 — 로 건다. 한 사람이 클러스터를 통째로 먹는 사고를 막는 안전핀이다.

apiVersion: v1
kind: ResourceQuota
metadata:
  name: dev-quota
  namespace: dev-kim
spec:
  hard:
    requests.cpu: "4"
    requests.memory: 8Gi
    pods: "20"

온보딩이 끝난 사용자는 kubectl auth can-i create pods -n dev-kim으로 자기 권한을 직접 확인할 수 있다.

2.3.3 네임스페이스 관리

네임스페이스를 어떻게 나눠줄 것인가에는 두 방식이 있고, 갈림길은 수명이다.

  • 영구 개인 워크스페이스 — 온보딩 때 개발자마다 하나씩. 단순하지만 시간이 지나면 아무도 안 쓰는 리소스가 쌓여 클러스터가 쓰레기장이 된다.
  • 목적별 임시 네임스페이스 + TTL (Time To Live) — 기능 개발·테스트 단위로 만들고, 만료 시각을 애너테이션으로 박아 기한이 지나면 자동 정리한다(쿠버네티스에 내장된 기능이 아니라 만료 애너테이션을 훑어 지우는 간단한 정리 잡을 직접 돌리는 패턴이다). 개발 환경을 늘 "새로 만들 수 있는 소모품"으로 유지시키는 부수 효과가 크다.

어느 쪽이든 원칙은 같다 — 네임스페이스는 셀프서비스로 즉시 발급되고, 소유자가 명확하며, 방치되면 사라진다.

2.3.4 클러스터 수준 서비스

네임스페이스 격리 위에, 모든 개발자가 공유하는 서비스를 클러스터 차원에서 한 번만 깔아준다. 대표가 중앙 로깅(LaaS, Logging as a Service)이다 — 앱이 표준 출력에 찍은 로그를 한곳에 모아두면, 파드가 죽어 사라진 뒤에도 로그가 남고 kubectl logs의 길이 제한에도 걸리지 않는다. 여기에 모니터링, 공용 인그레스 정도가 개발 클러스터의 기본 패키지다. 개별 개발자가 각자 깔게 두면 N벌의 중복과 N가지 버전이 생긴다.

2.4개발자 워크플로 활성화

온보딩된 개발자가 실제로 굴러가게 만드는 단계다. 그림 2-1의 ②·③에 해당한다.

2.4.1 초기 설치

애플리케이션 배포에서 정말 어려운 건 앱이 아니라 의존성이다. 마이크로서비스 하나를 개발하려 해도 데이터베이스와 이웃 서비스들이 먼저 떠 있어야 한다. 해법은 의존성 전체를 코드로 기술해 한 명령으로 세우는 것 — 1장에서 배운 헬름 차트가 여기서 힘을 쓴다. helm install deps ./our-app-deps 한 줄로 개발에 필요한 주변 세계가 서는 상태를 만들고, 이 차트를 팀이 함께 최신으로 유지한다. 문서로만 관리되는 설치 절차는 반드시 썩는다.

2.4.2 액티브한 개발 환경

하루 종일 도는 루프다: 코드 수정 → 컨테이너 이미지 빌드 → 레지스트리 푸시 → 클러스터 롤아웃 → 확인. 프로덕션과 달리 개발에서는 이 한 바퀴의 속도가 전부다. 그래서 개발용 이미지에는 커밋 해시나 타임스탬프처럼 매번 달라지는 태그를 붙여 교체를 강제하고(같은 태그 재사용은 캐시 때문에 "고쳤는데 안 바뀌는" 미스터리를 만든다), 롤아웃은 kubectl set image나 helm upgrade로 짧게 끝낸다. 루프가 분 단위를 넘는다면 그 자체가 KPI 위반 — 빌드 캐시, 로컬 레지스트리, 파일 동기화 도구 등으로 줄일 대상이다.

2.4.3 테스팅과 디버깅

클러스터 안에서 도는 앱을 들여다보는 기본기 네 가지. 전부 kubectl에 들어 있다.

# 1) 로그 — 표준 출력 확인 (-f 실시간, --previous 직전 죽은 컨테이너)
kubectl logs -f deployment/frontend -n dev-kim
kubectl logs --previous <파드이름> -n dev-kim

# 2) 셸 진입 — 컨테이너 내부에서 직접 확인
kubectl exec -it <파드이름> -n dev-kim -- sh

# 3) 터널 — 로컬에서 서비스 직접 호출 (0장에서 익힌 그것)
kubectl port-forward service/frontend 8080:8080 -n dev-kim

# 4) 임시 컨테이너 — exec이 안 될 때의 디버깅
kubectl debug -it <파드이름> -n dev-kim --image=busybox:1.36 --target=frontend
2026-08 기준 갱신 주석 4번 kubectl debug는 알아둘 가치가 커졌다. 보안상 셸조차 없는 distroless 이미지가 표준이 되면서 kubectl exec이 통하지 않는 컨테이너가 흔해졌기 때문이다. 임시 컨테이너 (Ephemeral Container) — 실행 중인 파드에 진단 도구를 담아 잠깐 덧붙이는 일회용 컨테이너 — 를 파드에 주입해 같은 프로세스 공간을 들여다보는 방식이며, 현재 정식(GA) 기능이다. 출처: kubernetes.io/docs/tasks/debug/debug-application/debug-running-pod (distroless 등 exec 불가 상황의 공식 해법으로 명시)

테스트 데이터도 설계 대상이다. 스키마와 유사 데이터를 채워주는 시딩(seeding) 스크립트를 의존성 차트와 함께 제공하면, "내 환경에선 되는데" 문제의 절반이 사라진다.
