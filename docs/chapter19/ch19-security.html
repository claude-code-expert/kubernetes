4장(RBAC)·9장(네트워크 정책)·10장(파드 보안)·11장(정책 엔진)·17장(어드미션·인가)에서 보안의 조각들을 하나씩 배웠다. 이 장은 그 조각들을 코드·클러스터·워크로드 세 계층의 지도 위에 정리하고, 아직 안 다룬 나머지(etcd·kubelet·감사 로깅·공급망 보안)를 채운다.

핵심 3줄

1. 보안은 코드(빌드 전)·클러스터(인프라)·워크로드(뜬 파드) 세 계층이다 — 이 장은 그 지도를 완성한다.

2. kubelet의 기본 미인증 API와 클라우드 메타데이터 API는 파드 하나의 침해를 클라우드 계정 전체의 침해로 키우는 가장 위험한 경로다.

3. 공급망 보안(SLSA·Scorecard·서명)은 이제 "있으면 좋은 것"이 아니라 대부분의 성숙한 오픈소스·기업이 채택한 기본 관행이다.

19.1클러스터 보안

이 절부터 코드·클러스터·워크로드 세 계층을 순서대로 훑는다.

19.1.1 etcd 액세스

etcd는 쿠버네티스의 기본 저장소이자 클러스터의 모든 상태(시크릿 포함)가 담긴 곳이다. 공유되지 않는 강력한 크리덴셜로 API 서버만 접근하게 하고, 네트워크 수준에서도 etcd로 가는 경로를 API 서버로 제한해야 한다.

19.1.2 인증

베어러 토큰, 클라이언트 인증서, OIDC, LDAP 통합까지 다양한 인증 수단을 지원한다 — 2장에서 다룬 대로 사람 인증은 OIDC가 실무 표준이다.

19.1.3 인가

17장 참고 — 인가는 이미 깊이 다뤘다. 보안 관점에서 요점 하나만 반복한다: 누가 무엇을 할 수 있는지가 늘 최신 상태로 유지되어야 한다.

19.1.4 TLS

쿠버네티스 API 엔드포인트는 기본적으로 TLS가 적용된다. 문제는 다른 툴·플랫폼이다 — 클러스터에 붙는 애드온이나 내부 서비스가 평문 HTTP를 쓰도록 방치되기 쉽다. 클러스터에 붙는 모든 컴포넌트의 통신을 주기적으로 점검한다.

19.1.5 kubelet과 클라우드 메타데이터 액세스

kubelet은 노드마다 하나씩 있는, 파드를 실제로 관리하는 컴포넌트다. 기본적으로 미인증 API가 활성화되어 있다는 게 문제다 — 이 API는 매우 강력해서, 직접 클러스터를 구축한다면 인증·인가가 켜져 있는지 반드시 재확인해야 한다.

클라우드에서 쿠버네티스를 돌린다면 위험이 하나 더 있다 — 노드가 클라우드 메타데이터 API (Cloud Metadata API)(보통 169.254.169.254)에 접근할 권한을 갖고 있는 경우가 많은데, 이 API가 쿠버네티스 프로비저닝에 쓰인 크리덴셜을 노출한다.

방어는 두 가지다 — kubelet 인증·인가를 강제하고, 네트워크 정책(9장)으로 메타데이터 엔드포인트 접근 자체를 차단한다.

19.1.6 시크릿

1장·4장 복습 — 쿠버네티스 시크릿은 기본적으로 암호화되어 있지 않다. API 서버의 암호화 프로바이더 설정으로 저장 시 암호화를 켜는 방법(4장)에 더해, 이 장은 Secrets Store CSI Driver를 추가로 소개한다 — 임시 램디스크 파일시스템으로 시크릿을 파드에 직접 마운트해, 쿠버네티스 Secret 오브젝트 자체를 거치지 않고 외부 시크릿 스토어에 직접 접근하는 방식이다. 4장의 External Secrets Operator가 "외부 값을 K8s Secret으로 동기화"한다면, 이쪽은 "K8s Secret 자체를 아예 안 만든다"는 차이가 있다.

19.1.7 로깅과 감사

API 서버의 감사 로깅 (Audit Logging)을 켜서 보안 관련 이벤트를 시간순으로 남긴다. 로깅을 켜는 것만으로는 부족하다 — 3장에서 배운 중앙 집계 파이프라인으로 로그를 모으고, 의심스러운 이벤트가 보이면 보안팀에 알리는 트리거까지 구성해야 완성이다.

19.1.8 클러스터 보안 태세 툴

클러스터 전체를 스캔해 흔한 설정 실수를 찾아주는 오픈소스 툴이 있다.

2026-08 기준 갱신 주석 원서가 언급한 Kubescape는 이후 크게 성장했다 — CNCF Incubating 등급에 올랐고, CIS Benchmark·NSA-CISA 하드닝 가이드·MITRE ATT&CK 프레임워크 기준으로 클러스터·매니페스트·이미지를 종합 평가하는 사실상 무료 CNAPP(클라우드 네이티브 애플리케이션 보호 플랫폼) 수준으로 발전했다. kubescape fix로 발견된 YAML 설정 실수를 자동 교정하고, kubescape vap로는 발견한 문제를 막는 ValidatingAdmissionPolicy를 직접 생성한다(11장·17장에서 다룬 그 API다) — 스캔 결과가 곧바로 강제 규칙이 되는 것이다. 출처: CNCF 블로그(Kubescape 4.0 발표, Incubating 등급) · CNCF 프로젝트 성숙도 카탈로그

19.3워크로드 컨테이너 보안

클러스터 자체를 지켰다면, 이제 그 위에서 도는 워크로드 하나하나다.

19.3.1 파드 시큐리티 어드미션

10장 참고 — privileged·baseline·restricted 세 수준, enforce·warn·audit 세 모드는 이미 상세히 다뤘다.

19.3.2 Seccomp, AppArmor, SELinux

리눅스 자체가 제공하는 보안 메커니즘 셋이다. Seccomp (Secure Computing Mode)은 컨테이너가 호출할 수 있는 시스템 콜의 종류를 제한한다 — 애초에 필요 없는 커널 기능은 아예 못 부르게 막는 것이다. AppArmor와 SELinux는 프로세스가 접근할 수 있는 파일·리소스 자체를 제한하는 강제 접근 제어(MAC) 시스템이다 — 배포판마다 기본 제공하는 쪽이 다르다(우분투는 AppArmor, RHEL 계열은 SELinux). 파드 스펙의 securityContext에서 프로파일을 지정한다.

19.3.3 어드미션 컨트롤러

보안 관련 어드미션 컨트롤러는 대부분 기본 활성화되어 있다 — 예컨대 NodeRestriction은 kubelet이 자기 노드와 무관한 오브젝트를 건드리지 못하게 막는다. 자세한 원리는 17장에서 이미 다뤘다.

19.3.4 오퍼레이터

16장·21장 참고 — 오퍼레이터는 애플리케이션 단위 조정이 필요한 워크로드에 커스텀 리소스를 제공하는 컨트롤러다. 보안 관점에서는 오퍼레이터에 부여되는 권한(대개 광범위한 RBAC)이 곧 공격 표면이 된다는 점을 주의한다 — 신뢰할 수 있는 오퍼레이터만 설치한다.

19.3.5 네트워크 정책

9장 참고 — 네트워크 정책 리소스가 존재해도, CNI가 실제로 이를 구현하는지 반드시 재확인해야 한다는 점을 다시 강조한다.

19.3.6 런타임 보안

대부분의 클러스터는 containerd나 CRI-O 위에서 리눅스 cgroup으로 경량 격리를 제공한다. 보안에 민감한 워크로드는 10장에서 다룬 gVisor·카타 컨테이너 같은 더 강한 격리로 올리고, Falco·Tetragon(역시 10장)으로 실행 중 이상 행동을 탐지한다.

19.3.7 워크로드 컨테이너 보안 모범 사례

쿠버네티스 보안 툴셋은 한 번에 다 이해하기엔 너무 방대하다. 우선순위를 매긴다면: 파드 시큐리티 어드미션 → 네트워크 정책 → 런타임 탐지 순으로 갖춰 나가는 것이 실무적으로 무난하다.

19.4코드 보안

보안은 코드가 쿠버네티스에 도달하기도 전부터 시작된다.

19.4.1 넌루트와 무배포 컨테이너

5장 복습 — 컨테이너 빌드 파일에 넌루트(non-root) 유저를 지정하고, distroless 같은 무배포 베이스 이미지를 쓴다. 공격 표면이 극단적으로 줄어든다.

19.4.2 컨테이너 취약점 탐색

Trivy 같은 오픈소스 스캐너가 컨테이너 이미지의 알려진 취약점을 베이스라인으로 잡아 준다. 스캔 자체보다 중요한 것은 그 결과를 배포 정책에 실제로 연결하는 것이다 — 심각도가 높은 취약점이 있으면 어드미션 단계(17장)에서 아예 막는 식으로.

19.4.3 코드 리포지터리 보안

SLSA (Supply-chain Levels for Software Artifacts)는 소프트웨어 공급망 보안을 점진적 수준으로 나눈 체크리스트 프레임워크다 — 레벨이 잘 정의되어 있어 그대로 따라가면 된다. OpenSSF 스코어카드 (Scorecard)는 의존 중인 오픈소스 리포지터리의 보안 태세를 0~10점으로 자동 평가해, 그 프로젝트를 얼마나 신뢰할지 판단하는 근거를 준다.
