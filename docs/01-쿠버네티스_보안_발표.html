기초 다지기, 오늘 계속 나올 단어

파드는 컨테이너를 담는 최소 배포 단위다

클러스터는 서버 여러 대를 묶은 하나의 시스템
노드는 그 안의 서버 한 대
파드는 컨테이너 하나 이상을 묶은 최소 단위
한 노드에 여러 팀의 파드가 섞여서 돈다
용어 클러스터
서버 여러 대를 묶어 하나처럼 쓰는 단위
용어 파드
컨테이너 하나 이상을 묶은 배포 최소 단위. IP를 공유한다

파드는 직접 만들지 않고 디플로이먼트로 선언한다

원하는 상태를 적으면 시스템이 맞춘다
파드가 죽으면 알아서 다시 띄운다
이미지를 바꾸면 롤링 업데이트를 돈다
핵심, 디플로이먼트는 자기 파드 정의가 바뀔 때만 움직인다
용어 디플로이먼트
파드를 몇 개 어떤 모습으로 유지할지 선언하는 오브젝트
용어 롤아웃
파드 정의가 바뀌었을 때 새 파드로 교체하는 과정

네임스페이스는 클러스터 안의 논리적 칸막이다

오브젝트를 담는 칸을 나눈다
이름은 칸 안에서만 안 겹치면 된다
권한과 리소스 할당량도 칸 단위로 건다
컨피그맵과 시크릿은 자기를 쓰는 파드와 같은 칸에 있어야 한다
용어 네임스페이스
클러스터를 논리적으로 나눈 칸. 오브젝트가 여기에 속한다

yaml은 네 줄만 읽을 줄 알면 된다

apiVersion: v1
kind: ConfigMap # 무엇인가
metadata:
name: mysql-config # 이름
namespace: myapp-prod # 어느 칸

mysqldb: myappdb1
user: mysqluser1
kind, 이게 무슨 종류의 오브젝트인가
metadata.name, 이름은 무엇인가
metadata.namespace, 어느 칸에 사는가
그 아래, 종류마다 다른 실제 내용
kubectl apply -f 파일.yaml 로 클러스터에 적용한다
용어 매니페스트
원하는 상태를 적은 yaml 파일
용어 kubectl
클러스터에 명령을 보내는 명령줄 도구

설정을 코드 밖으로, 컨피그맵

DB 주소 한 줄 때문에 이미지를 세 번 빌드한다

설정이 application.yml에 박혀 있다
개발 스테이징 운영 주소가 서로 다르다
환경마다 이미지를 따로 빌드한다
설정 한 줄 바꿔도 전체 재빌드
운영에 올라간 이미지는 아무도 테스트하지 않은 물건이다
용어 이미지
앱과 실행 환경을 통째로 굳혀 놓은 실행 파일 묶음
용어 레지스트리
이미지를 보관하고 배포하는 저장소

설정값은 빌드가 아니라 컨테이너 시작 시점에 정해진다

컨테이너는 조합 가능하도록 만들어졌다
실행 시점에 환경 변수나 볼륨으로 주입한다
기능과 그 기능이 도는 환경을 분리한다
build once, deploy many. 한 번 만든 이미지로 모든 환경을 돈다

설정을 별도 오브젝트로 빼면 고칠 곳이 한 군데가 된다

키와 값 목록을 담는 오브젝트
여러 파드가 같은 것을 참조한다
민감하지 않은 설정 전용
평문이다. 읽을 권한이 있는 사람에게 전부 보인다
용어 컨피그맵
설정값을 키와 값으로 담는 쿠버네티스 오브젝트

02

비밀은 다르게, 시크릿

컨피그맵에 비밀번호를 넣으면 명령 한 줄에 노출된다

data:
mysqldb: myappdb1
user: mysqluser1
password: p@ssw0rd123
컨피그맵 읽기 권한만 있으면 누구나 본다
$ kubectl get configmap mysql-config -o yaml
data:
mysqldb: myappdb1
user: mysqluser1
password: p@ssw0rd123
로그, 모니터링 화면, 백업 파일에도 그대로 남는다

시크릿의 base64는 암호화가 아니다

kind: Secret
metadata:
name: myapp-api-key
type: Opaque
data:
myapikey: YWRtaW4xMjM=
$ echo YWRtaW4xMjM= | base64 -d
admin123
base64는 바이너리를 yaml에 담기 위한 인코딩
누구나 되돌릴 수 있다
보안 장치가 아니다
용어 base64
임의의 데이터를 텍스트로 바꾸는 인코딩. 키 없이 되돌릴 수 있다

시크릿의 값어치는 인코딩이 아니라 취급 방식이다

01
메모리에만 올린다
필요한 파드가 있는 노드에만 tmpfs로 마운트. 파드가 사라지면 함께 사라져 노드 디스크에 흔적이 없다
02
권한을 분리할 수 있다
타입이 다르므로 설정은 읽되 비밀은 못 읽는 권한을 줄 수 있다. 이것이 뒤의 RBAC
03
저장 암호화를 걸 수 있다
etcd 저장 시 암호화와 외부 키 관리 시스템 연동 대상이 된다. 컨피그맵은 대상이 아니다
04
화면에 원문이 안 뜬다
로그와 터미널에 평문이 바로 노출되지는 않는다
용어 tmpfs
디스크가 아니라 메모리에 만들어지는 임시 파일시스템
용어 etcd
쿠버네티스가 모든 오브젝트를 저장하는 클러스터의 데이터베이스

시크릿은 용도에 따라 타입이 나뉜다

generic
일반 키와 값
kubectl create secret generic db-pass --from-literal=password=***
docker-registry
레지스트리 로그인 정보
kubectl create secret docker-registry registryKey --docker-server=myreg.example.io --docker-username=myreg --docker-password=***
tls
인증서와 개인키 쌍
kubectl create secret tls www-tls --key=./wwwtls.key --cert=./wwwtls.crt

기본 설정 etcd만 놓고 보면 시크릿도 평문이다

시크릿은 etcd에 일반 텍스트로 저장된다
etcd 디스크를 가져가면 그대로 읽힌다
관리자가 별도로 걸어야 안전해진다
시크릿의 이점은 털려도 안전이 아니라 암호화를 걸 자리가 있다는 것
etcd 노드 간 mTLS
서버와 클라이언트가 서로를 인증한다
저장 시 암호화
API 서버 구성에 암호화 프로바이더를 지정한다
외부 키 관리 시스템
KMS 연동으로 키를 클러스터 밖에서 관리한다
외부 시크릿 저장소
Vault, Secrets Manager. 감사와 키 회전이 강하다
용어 mTLS
서버만 인증하는 일반 TLS와 달리 양쪽이 서로를 인증하는 방식
용어 KMS
암호화 키를 따로 보관하고 관리해 주는 외부 시스템

고친 값은 앱까지 어떻게 가나

컨피그맵을 고쳤다.
앱은 언제부터 새 값을 쓸까

즉시 바뀐다
잠시 뒤 바뀐다
파드를 다시 띄워야 바뀐다
영원히 안 바뀐다
주입 방식에 따라 네 가지 답이 모두 정답이 될 수 있다

같은 수정이 주입 방식에 따라 세 갈래로 갈린다

용어 kubelet
각 노드에서 파드를 만들고 돌보는 쿠버네티스 에이전트

환경 변수는 프로세스 시작 시 한 번만 심긴다

프로세스가 뜰 때 커널이 넘겨주는 값
실행 중에 바깥에서 바꿀 방법이 없다
파일이 없으므로 감시할 대상도 없다
컨피그맵은 새 값, 앱은 옛 값. 조용한 불일치가 생긴다

쿠버네티스는 파일까지만 책임진다

kubelet이 주기적으로 파일을 교체한다
앱은 시작할 때 읽은 값을 메모리에 들고 있다
파일이 바뀐 것을 앱에게 알려주지 않는다
앱이 파일 변경을 감지해 다시 읽어야 반영된다. 그것이 파일 감시기
subPath로 파일 하나만 마운트하면 파일 갱신 자체가 안 된다
nginx
reload 명령으로 설정을 다시 읽는다. 감시기 방식이 잘 맞는다
스프링 부트 기본
시작 시 한 번 읽고 끝. 감시기 없이는 반영 안 된다
직접 구현
파일 변경 이벤트를 받아 설정 객체를 갈아 끼운다
용어 파일 감시기
파일 변경을 감지해 앱이 설정을 다시 읽게 하는 기능

누가 읽을 수 있나, RBAC

시크릿의 진짜 보호막은 접근 권한이다

base64
되돌릴 수 있다. 보호막이 아니다
tmpfs
노드 디스크에 안 남을 뿐, 읽는 것은 막지 못한다
etcd 암호화
디스크를 훔친 경우에만 유효하다
RBAC
누가 이 시크릿을 읽을 수 있는가를 직접 정한다
설정을 밖으로 빼낸 대가로 접근 통제가 필요해졌다. 그래서 같은 장에 있다
시크릿은 API로 읽는 오브젝트다
권한이 있으면 읽히고 없으면 안 읽힌다
나머지 장치는 보조 수단이다

용어 인가

용어 verbs
get, list, watch, create, delete 등 수행 가능한 동작. 서로 별개 권한이다

범위를 정하는 것은 바인딩이다

Role + ClusterRoleBinding
롤은 이미 칸에 속해 있다

앱이 뚫리면 피해가 칸 전체

용어 get

용어 list
이름을 몰라도 목록 전체를 훑는 동작

권한은 상시 소유가 아니라 대여로 바꾼다

사람, 적시 권한
평소에는 조회 권한만 갖는다
필요할 때 사유와 기간을 붙여 요청
만료되면 자동으로 회수된다
고권한은 별도 아이덴티티로 발급
실제로는 롤바인딩을 그때 만들었다가 지우는 것
자동화, 전용 계정
개인 계정 토큰을 CI에 넣지 않는다
퇴사하면 배포가 멈춘다
감사 로그가 전부 그 사람 이름으로 남는다
배포에 필요한 최소 권한만 부여
누가 무엇을 배포하고 삭제했는지 추적 가능해진다
용어 적시 권한
필요한 시점에만 권한을 부여하고 만료 시 회수하는 방식

RBAC은 yaml 안에 무엇이 적혔는지 보지 않는다

인증
김씨 맞다. 통과
인가

내용

용어 어드미션 컨트롤러
인증과 인가를 통과한 요청의 내용을 검사해 허용, 거부, 수정하는 관문

특권 컨테이너 하나면 그 노드의 비밀이 다 열린다

이전의 파드시큐리티폴리시를 대체했다
적용 단위는 네임스페이스
한계, 같은 칸 안에서 파드마다 다른 수준을 줄 수 없다
더 정교한 정책이 필요하면 게이트키퍼 같은 별도 솔루션을 얹는다. 소규모 단일 팀 클러스터는 이것만으로 충분하다
용어 파드 시큐리티 어드미션
파드 보안 설정을 네임스페이스 단위로 검사하는 기본 어드미션 컨트롤러

아무것도 안 하면 아무것도 막히지 않는다

privileged기본값
사실상 제한 없음
특권 컨테이너도 그대로 통과한다
baseline
알려진 권한 상승 공격 차단
대부분의 앱이 손대지 않고 통과한다
restricted
현재의 파드 보안 모범 사례
루트 실행 금지 등 강하게 조인다
용어 권한 상승 공격
제한된 권한에서 시작해 더 높은 권한을 얻어내는 공격

운영 클러스터에 바로 enforce를 걸면 장애가 난다

restricted 조건을 기존 앱이 안 지킬 수 있다
납품 소프트웨어와 커뮤니티 차트는 고칠 수도 없다
켜는 순간 파드가 안 뜨고 롤아웃이 실패한다
audit과 warn을 먼저 켜서 상태를 파악한 뒤 enforce로 넘어간다
06

뚫렸다고 가정한다, 워크로드 격리

컨테이너 격리는 커널 하나에 의존한다

한 노드의 모든 컨테이너가 같은 커널을 쓴다
격리는 커널 기능으로 만든 울타리다
커널 취약점 하나면 울타리가 통째로 열린다
책은 컨테이너 런타임을 안전하지 못한 격리 경계라고 못 박는다
해결책은 커널을 나눠 갖지 않는 런타임, 카타 컨테이너와 gVisor. 고르는 방법과 운영 주의점은 부록에 있다

런타임 격리는 API 경로를 막지 않는다

런타임 격리는 밖으로 나가는 경로만 막는다
API로 들어오는 경로는 RBAC과 어드미션의 몫이다
워크로드를 격리해도 멀티테넌시가 해결되지는 않는다
보안은 레이어 하나로 완성되지 않는다. 처음부터 끝까지 함께 봐야 한다

방어선은 다섯 겹이고 각자 못 막는 것이 있다

3줄 요약

1설정은 이미지에 넣지 말고 밖에서 주입한다. 바이너리는 하나로 유지한다
2값을 바꾸는 것과 앱에 닿는 것은 별개다. 해시로 재배포를 유발하는 것이 기본값이다
3시크릿의 진짜 보호막은 인코딩이 아니라 권한이다. 최소 권한으로 좁힌다

예상 질문

Q. 컨피그맵을 고쳤는데 반영이 안 된다
환경 변수 방식이면 파드를 재시작해야 한다. kubectl rollout restart 또는 해시 어노테이션
Q. 시크릿을 깃에 올려도 되나
base64는 보호가 아니므로 안 된다. 외부 시크릿 저장소나 봉인된 시크릿을 쓴다
Q. RBAC 롤을 만들었는데 권한이 없다
롤바인딩을 안 만들었거나 주체를 유저로 적었을 가능성. 앱이면 서비스 어카운트로
Q. restricted를 바로 켜도 되나
안 된다. audit과 warn으로 먼저 위반 목록을 확인한 뒤 단계적으로 넘어간다
