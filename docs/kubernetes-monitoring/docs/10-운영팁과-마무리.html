01완성된 스택 되돌아보기

현재 상태를 숫자로 확인해 둡니다. 뒤 절에서 비교 기준이 됩니다.

curl -s --get http://localhost:30900/api/v1/query \
  --data-urlencode 'query=prometheus_tsdb_head_series' \
  | jq -r '.data.result[0].value[1]'

curl -s --get http://localhost:30900/api/v1/query \
  --data-urlencode 'query=rate(prometheus_tsdb_head_samples_appended_total[5m])' \
  | jq -r '.data.result[0].value[1]'

앞의 값은 현재 시계열 개수, 뒤의 값은 초당 저장되는 샘플 수입니다. 실습 규모라면 시계열 3만~8만, 초당 샘플 500~2000 정도가 나옵니다.

02카디널리티 — 1번 사망 원인

프로메테우스가 죽는 이유는 대개 트래픽이 아니라 라벨입니다. 시계열 하나하나가 메모리를 차지하는데, 라벨 값의 조합만큼 시계열이 생기기 때문입니다. 곱셈이라는 점이 무섭습니다.

진단 질의

# 시계열을 가장 많이 차지하는 메트릭 10개
topk(10, count by (__name__) ({__name__=~".+"}))
# 특정 라벨이 몇 종류의 값을 갖는지 — 이 숫자가 계속 늘면 위험 신호
count(count by (uri) (http_server_requests_seconds_count))
# 스크레이프 대상별로 몇 개의 시계열을 만들어내는지
topk(10, count by (job, instance) ({__name__=~".+"}))
더 편한 방법 — TSDB Status

localhost:30900/tsdb-status를 열면 메트릭별·라벨별 시계열 수가 표로 정리돼 있습니다. 질의를 외울 필요 없이 여기부터 보는 것이 실전에서 빠릅니다. 위 진단 질의들은 모든 시계열을 훑으므로 운영 프로메테우스에서 습관적으로 쓰면 안 됩니다.

03잘라내기 실습

수집 단계에서 필요 없는 메트릭을 버립니다. 저장된 뒤에 지우는 것보다 훨씬 싸고 확실합니다. ServiceMonitor의 metricRelabelings가 그 자리입니다.

k8s/monitoring/90-servicemonitors.yaml — order-api 엔드포인트에 추가

  endpoints:
    - port: http
      path: /actuator/prometheus
      interval: 30s
      scrapeTimeout: 10s
      # 저장 직전에 적용된다. 여기서 drop된 것은 디스크에 남지 않는다.
      metricRelabelings:
        # 1) 실습에서 볼 일 없는 메트릭 묶음을 통째로 버린다
        - sourceLabels: [__name__]
          regex: "jvm_buffer_.*|jvm_classes_.*|process_start_time_seconds"
          action: drop

        # 2) 액추에이터 엔드포인트 자신에 대한 요청은 관심 대상이 아니다
        - sourceLabels: [uri]
          regex: "/actuator.*"
          action: drop

        # 3) 404가 찍히는 정체불명 경로는 uri 라벨을 통일해 버린다
        #    (스캐너가 임의 경로를 두드리면 카디널리티가 폭증한다)
        - sourceLabels: [status]
          regex: "404"
          targetLabel: uri
          replacement: "NOT_FOUND"
          action: replace
kubectl apply -f k8s/monitoring/90-servicemonitors.yaml

# 적용 전후로 시계열 수를 비교한다
sleep 60
curl -s --get http://localhost:30900/api/v1/query \
  --data-urlencode 'query=prometheus_tsdb_head_series' \
  | jq -r '.data.result[0].value[1]'

이미 저장된 시계열은 즉시 사라지지 않습니다. 새로 들어오는 데이터가 없으면 보존 기간이 지나며 자연스럽게 정리됩니다.

드롭 규칙은 되돌리기 어렵다

버린 데이터는 없는 데이터입니다. 장애 조사 중에 "그 메트릭이 있었더라면"이라고 후회하는 상황이 실제로 생깁니다. 먼저 지울 것은 명백한 쓰레기부터, 애매한 것은 보존 기간을 줄이는 쪽으로 대응하세요.

네이티브 히스토그램이라는 대안

버킷이 카디널리티의 큰 몫을 차지한다는 것을 그림 2에서 봤습니다. Prometheus 3.8부터 정식 기능이 된 네이티브 히스토그램은 버킷을 미리 정하지 않고 자동으로 나누므로, 시계열 수를 근본적으로 줄입니다. 다만 기존 대시보드와 histogram_quantile 사용법이 달라지고, 스프링·그라파나 양쪽 지원 상태를 확인해야 하므로 지금 당장 바꾸기보다 다음 분기 과제로 올려두는 것을 권합니다.

04간격·보존·디스크 계산

디스크 필요량은 곱셈 세 개로 어림합니다.

필요 디스크 ≈ 보존 기간(초) × 초당 샘플 수 × 샘플당 바이트(1~2B)

예) 15일 보존, 초당 2,000샘플, 샘플당 2B
    = 1,296,000 × 2,000 × 2
    ≈ 5.2 GB  (여기에 여유 30~50%를 더한다)
# 우리 클러스터의 실제 초당 샘플 수
curl -s --get http://localhost:30900/api/v1/query \
  --data-urlencode 'query=sum(rate(prometheus_tsdb_head_samples_appended_total[10m]))' \
  | jq -r '.data.result[0].value[1]'
조절 손잡이효과주의
scrapeInterval을 30s→60s 샘플 수 절반 rate() 윈도도 함께 늘려야 한다(간격의 4배 이상). 짧은 스파이크를 놓친다
retention 단축 디스크 선형 감소 주간 비교·용량 추세 분석이 불가능해진다
metricRelabelings 드롭 디스크·메모리 모두 감소 되돌릴 수 없다
retentionSize 지정 디스크 상한 보장 기간보다 먼저 걸리면 오래된 데이터가 조용히 사라진다
04단계 설정의 함정

값 파일에 retention: 3d와 retentionSize: 4GB를 함께 넣었습니다. 둘 중 먼저 도달하는 쪽이 이깁니다. 실습에서 부하를 크게 걸면 3일이 되기 전에 4GB에 걸려 "어제 그래프가 사라졌다"는 상황이 생깁니다. 버그가 아니라 설정대로 동작한 것입니다.

규모가 더 커지면 손잡이를 돌리는 것으로는 부족합니다. 그때는 원격 쓰기로 장기 저장을 분리하는 구조로 넘어갑니다. Prometheus 3.x의 Remote-Write 2.0이 그 통로입니다. 이 실습 범위를 벗어나므로 이름만 기억해 두세요.

05자원 튜닝과 무중단 리사이즈

먼저 스로틀링부터 확인한다

03단계에서 애플리케이션에 CPU 제한을 걸지 않았습니다. 그 판단이 왜 필요했는지 숫자로 확인합니다. 

# CPU 스로틀링 비율 — 0에 가까워야 정상
sum by (pod) (rate(container_cpu_cfs_throttled_periods_total{namespace="apps"}[5m]))
/
sum by (pod) (rate(container_cpu_cfs_periods_total{namespace="apps"}[5m]))

이 값이 0.2를 넘으면 컨테이너가 주기의 20%를 강제로 쉬고 있다는 뜻입니다. 응답 시간 그래프의 톱니가 코드 때문인지 스로틀링 때문인지는 이 질의를 함께 봐야만 구분됩니다.

메모리는 다르게 다룬다

# 제한 대비 실제 사용률
max by (pod) (
  container_memory_working_set_bytes{namespace="apps", container!=""}
)
/
max by (pod) (
  kube_pod_container_resource_limits{namespace="apps", resource="memory"}
)

0.9를 넘나든다면 OOMKilled가 임박한 것입니다. CPU는 모자라면 느려지지만, 메모리는 모자라면 죽습니다. 그래서 CPU 제한은 신중하게, 메모리 제한은 반드시 겁니다.

재시작 없이 자원 바꾸기 (Kubernetes 1.35+)

예전에는 자원을 바꾸려면 파드를 다시 만들어야 했습니다. In-Place Pod Resize가 1.35에서 정식 기능이 되면서 달라졌습니다. 01단계에서 만든 클러스터는 1.36이므로 바로 써볼 수 있습니다. 

POD=$(kubectl -n apps get pod -l app.kubernetes.io/name=order-api \
  -o jsonpath='{.items[0].metadata.name}')

# 바꾸기 전 상태
kubectl -n apps get pod "$POD" \
  -o jsonpath='{.spec.containers[0].resources}{"\n"}{.status.containerStatuses[0].restartCount}{"\n"}'

# resize 서브리소스로 메모리 상한을 올린다 (kubectl v1.32+ 필요)
kubectl -n apps patch pod "$POD" --subresource resize --type=merge \
  -p '{"spec":{"containers":[{"name":"order-api","resources":{"requests":{"memory":"448Mi"},"limits":{"memory":"768Mi"}}}]}}'

# 재시작 없이 반영됐는지 — restartCount가 그대로여야 한다
kubectl -n apps get pod "$POD" \
  -o jsonpath='{.status.containerStatuses[0].resources}{"\n"}{.status.containerStatuses[0].restartCount}{"\n"}'
읽어야 할 두 곳이 생겼다

spec.containers[*].resources는 이제 원하는 상태이고, status.containerStatuses[*].resources가 실제 적용된 값입니다. 둘이 다를 수 있다는 것이 이 기능의 핵심이며, 진행 상황은 PodResizePending·PodResizeInProgress 조건으로 노출됩니다. 노드에 여유가 없으면 Infeasible 사유로 거절됩니다.

디플로이먼트를 고치는 것과 다르다

위 명령은 파드 하나를 고칩니다. 디플로이먼트의 템플릿은 그대로이므로, 파드가 어떤 이유로든 다시 만들어지면 원래 값으로 돌아갑니다. 영구 반영은 여전히 매니페스트를 고쳐 배포하는 것입니다. 리사이즈는 지금 당장 죽어가는 파드를 살리는 용도로 쓰세요.

06실습 설정 → 운영 설정

이 시리즈에서 일부러 타협한 설정들입니다. 실습을 빨리 굴리기 위한 선택이었고, 사내 클러스터로 옮길 때는 반드시 바꿔야 합니다. 스터디 마지막 시간에 이 표를 함께 읽는 것을 권합니다.

단계실습에서의 선택운영에서 바꿀 것
01 bind-address: 0.0.0.0으로 컨트롤 플레인 메트릭 개방 노드 IP만 바인딩하거나 방화벽으로 대역 제한. kind는 VM 안에 갇혀 있어 안전했을 뿐이다
02 ChaosController가 항상 활성 @Profile로 분리. 운영 프로파일에서는 빈 등록조차 되지 않게 한다
03 CPU limit 미설정 공용 클러스터라면 반드시 설정. 대신 스로틀링 메트릭을 함께 감시한다
03 readOnlyRootFilesystem 미적용 적용하고 /tmp에 emptyDir을 붙인다
03 레지스트리 없이 kind load 사내 레지스트리 + 이미지 서명·스캔 파이프라인
04 insecureSkipVerify: true 노드 IP를 SAN에 포함한 인증서를 발급해 검증을 켠다
04 관측 스택을 노드 한 대에 몰아넣음 분산 배치. 모니터링이 한 노드와 함께 죽으면 장애를 볼 눈이 없어진다
04 그라파나 비밀번호를 값 파일에 평문으로 Secret 또는 외부 시크릿 관리자. 가능하면 SSO 연동
04 NodePort로 UI 직접 노출 인증을 거치는 진입점 뒤에 둔다. 프로메테우스 UI는 인증이 없다
05 사이드카 searchNamespace: ALL 필요한 네임스페이스만 나열. 권한과 API 부하를 줄인다
07 임계값 5% · 500ms를 임의로 설정 2주 이상 관측한 실제 분포를 근거로 재설정
08 로키 파일시스템 단일 인스턴스 오브젝트 스토리지 + 확장 모드. 파일시스템은 데이터를 잃는 구성이다
08 캐시 비활성 운영 규모에서는 필수. 없으면 질의가 감당 안 된다
가장 위험한 것은 값 파일이다

매니페스트는 리뷰를 거치지만, values.yaml은 "잘 되는 설정"이라며 통째로 복사되는 일이 잦습니다. 파일 이름에 환경을 박아두세요 — kps-values.kind.yaml처럼요. 이름만으로도 복사를 한 번 망설이게 만듭니다.

07트러블슈팅 12선

전 단계에서 실제로 부딪히는 순서대로 정리했습니다.

#증상첫 번째로 볼 곳
1클러스터 생성이 타임아웃Docker Desktop 메모리 할당. 10 GiB 미만이면 04단계에서 반드시 막힌다
2컨트롤 플레인 타깃 DOWN01단계 bind-address 패치. 클러스터 재생성이 필요하다
3ImagePullBackOffkind load 여부와 imagePullPolicy: IfNotPresent
4CrashLoopBackOff인데 로그는 정상startupProbe의 failureThreshold × periodSeconds
5ServiceMonitor가 무시됨release: kps 라벨. 오류 없이 조용히 실패한다
6타깃 그룹은 있는데 대상 0개Service 라벨과 포트 이름
7_bucket이 없어 P95 계산 불가02단계 percentiles-histogram. 이미지 재빌드 필요
8histogram_quantile이 NaNsum by에 le가 빠졌는지
9대시보드가 No data같은 질의를 프로메테우스 UI에서 실행해 데이터 유무부터 분리
10알림이 안 울림/alerts에서 pending 여부 → Alertmanager 라우팅 순으로
11로그가 안 보임Alloy UI(12345)에서 컴포넌트 상태. 설정 파일보다 빠르다
12어제 그래프가 사라짐retentionSize에 먼저 걸렸는지. 설정대로 동작한 것이다
공통 원칙

"안 된다"는 상황에서 가장 먼저 할 일은 범위를 절반으로 자르는 것입니다. 대시보드가 비면 프로메테우스 UI에서 같은 질의를 돌려보고, 거기서도 비면 타깃 상태를 보고, 타깃이 UP이면 앱 엔드포인트를 직접 curl 합니다. 한 번에 한 계층씩 내려가면 대부분 세 번 안에 원인에 닿습니다.

08대시보드와 알림이 늘어날 때

스택이 안정되면 다음 문제는 기술이 아니라 관리입니다. 대시보드는 만드는 사람은 있지만 지우는 사람이 없어서 늘어납니다.

신호대응
비슷한 대시보드가 세 개 이상 변수로 합친다. 07단계에서 만든 service 변수가 그 방법이다
아무도 열지 않는 대시보드 그라파나 사용 통계로 확인해 정리한다. 폴더에 Archive를 두는 것도 방법
같은 장애에 알림이 열 개 증상 알림만 남기고 원인 알림은 지운다. inhibit_rules도 함께 손본다
Silence가 만료 없이 쌓임 영구 침묵은 규칙 삭제와 같다. 만료 기간을 반드시 설정한다
한 번도 울리지 않은 알림 임계값이 비현실적이거나 질의가 틀렸다. 의도적으로 터뜨려 검증한다

분기에 한 번 알림 회고를 하는 팀이 늘고 있습니다. "지난 분기에 울린 알림 목록"과 "그중 실제로 조치한 것"을 나란히 놓고, 조치율이 낮은 알림부터 지웁니다.

09정리와 재현

실습이 끝났다면 노트북 자원을 돌려받습니다.

# 전체 삭제 — 클러스터를 지우면 안의 모든 것이 사라진다
kind delete cluster --name obs

# 도커에 남은 이미지·볼륨 정리
docker system prune -a --volumes

다시 처음부터 만들 때는 아래 순서 그대로입니다. 저장소에 커밋해 둔 파일만 있으면 40분 안에 복원됩니다.

rebuild.sh

#!/usr/bin/env bash
# 관측성 실습 환경 재구축 — 각 단계 문서를 대체하지 않는다. 복원용이다.
set -euo pipefail

ROOT="$HOME/k8s-observability"
CHART_VERSION="88.3.0"

echo "[1/6] 클러스터 생성"
kind create cluster --config "$ROOT/infra/kind-cluster.yaml"

echo "[2/6] 앱 이미지 빌드와 적재"
for app in order-api gateway; do
  (cd "$ROOT/apps/$app" && ./gradlew bootBuildImage)
  kind load docker-image "obs/${app}:0.0.1" --name obs
done

echo "[3/6] 앱 배포"
kubectl apply -f "$ROOT/k8s/00-namespace.yaml"
kubectl apply -f "$ROOT/k8s/10-order-api.yaml"
kubectl apply -f "$ROOT/k8s/20-gateway.yaml"
kubectl -n apps rollout status deploy/order-api --timeout=180s
kubectl -n apps rollout status deploy/gateway --timeout=180s

echo "[4/6] 관측 스택 설치"
helm upgrade --install kps prometheus-community/kube-prometheus-stack \
  --namespace monitoring --create-namespace \
  --version "$CHART_VERSION" \
  -f "$ROOT/monitoring/kps-values.yaml" \
  --wait --timeout 15m

echo "[5/6] 연동 리소스"
kubectl apply -f "$ROOT/k8s/monitoring/90-servicemonitors.yaml"
kubectl apply -f "$ROOT/k8s/monitoring/91-prometheusrule.yaml"

echo "[6/6] 대시보드"
kubectl -n monitoring create configmap obs-red-dashboard \
  --from-file=obs-red.json="$ROOT/monitoring/dashboards/obs-red.json" \
  --dry-run=client -o yaml | kubectl apply -f -
kubectl -n monitoring label configmap obs-red-dashboard grafana_dashboard=1 --overwrite
kubectl -n monitoring annotate configmap obs-red-dashboard grafana_folder="Obs Study" --overwrite

echo "완료 — http://localhost:30300 (grafana) · http://localhost:30900 (prometheus)"

로그 스택(08단계)은 메모리를 크게 쓰므로 이 스크립트에 넣지 않았습니다. 필요할 때만 별도로 설치하세요.

10스터디 과제와 마무리

과제 — 각자 하나씩 골라 다음 모임에서 공유

과제내용
장애 시나리오 동료에게 클러스터를 망가뜨리게 하고(파드 삭제, 자원 축소, 잘못된 라벨 등), 대시보드와 로그만으로 원인을 찾아 5분 안에 설명하기
알림 하나 만들기 기존 규칙과 겹치지 않는 알림 하나를 설계하고, 왜 이것이 사람이 행동할 수 있는 알림인지 근거 대기
카디널리티 감사 TSDB Status를 열어 상위 5개 메트릭을 분석하고, 드롭 규칙 하나를 제안하기
사내 이전 계획 06절 표에서 자기 팀에 해당하는 항목 3개를 골라 구체적 대안을 작성하기

최종 체크리스트

  • TSDB Status에서 상위 메트릭과 시계열 수를 확인했다
  • metricRelabelings를 적용하고 시계열 수 변화를 비교했다
  • CPU 스로틀링과 메모리 사용률 질의를 실행해 봤다
  • resize 서브리소스로 재시작 없이 자원을 바꿔 봤다
  • 06절 "실습 → 운영" 표를 팀과 함께 읽었다
  • rebuild.sh로 재구축이 되는지 한 번 검증했다
  • 모든 매니페스트·값 파일·대시보드 JSON이 저장소에 있다
  • 실습이 끝난 클러스터를 삭제해 자원을 돌려받았다
시리즈를 마치며

10개 문서를 지나오며 만든 것은 도구 모음이 아니라 질문의 순서입니다. "지금 문제가 있는가"(대시보드 상단) → "어느 서비스인가"(RED 지표) → "언제부터인가"(시계열) → "무슨 일이 있었나"(로그). 도구는 몇 년 안에 바뀝니다. Promtail이 사라지고 Alloy가 온 것처럼요. 하지만 이 순서는 남습니다. 다음에 새 도구를 도입할 때 "이 순서의 어느 칸을 채우는가"만 물으면 됩니다.
