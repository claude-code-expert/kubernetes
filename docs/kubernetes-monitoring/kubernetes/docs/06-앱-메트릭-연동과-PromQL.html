01라벨 세 겹

ServiceMonitor는 "이 서비스를 긁어라"라는 선언입니다. 그런데 그 선언이 실제로 효력을 가지려면 세 군데의 라벨이 모두 맞아야 합니다. 하나라도 어긋나면 아무 오류 없이 조용히 무시됩니다. 이것이 이 단계가 어려운 유일한 이유입니다.

02일부러 실패시켜 보기

먼저 release 라벨 없이 만들어 봅니다. 5분이면 되고, 이 경험이 앞으로 몇 시간을 아껴줍니다. 

mkdir -p ~/k8s-observability/k8s/monitoring
cd ~/k8s-observability/k8s/monitoring

cat <<'EOF' > 90-servicemonitor-broken.yaml
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: order-api-broken
  namespace: apps
spec:
  selector:
    matchLabels:
      app.kubernetes.io/name: order-api
  namespaceSelector:
    matchNames: [apps]
  endpoints:
    - port: http
      path: /actuator/prometheus
EOF

kubectl apply -f 90-servicemonitor-broken.yaml
kubectl -n apps get servicemonitor

리소스는 정상적으로 만들어집니다. 이제 타깃에 나타나는지 확인합니다. 

sleep 40
curl -s --get http://localhost:30900/api/v1/query \
  --data-urlencode 'query=up{namespace="apps"}' \
  | jq '.data.result | length'
0

0입니다. 오류 메시지도, 경고 로그도 없습니다. 프로메테우스 CR의 셀렉터를 직접 확인해 보면 이유가 보입니다. 

kubectl -n monitoring get prometheus -o yaml \
  | grep -A4 'serviceMonitorSelector:'
    serviceMonitorSelector:
      matchLabels:
        release: kps
왜 이런 기본값인가

차트는 serviceMonitorSelectorNilUsesHelmValues: true를 기본으로 둡니다. "이 헬름 릴리스가 관리하는 것만 본다"는 뜻입니다. 한 클러스터에 프로메테우스를 여러 개 띄우는 상황(팀별 분리 등)에서 서로의 타깃을 침범하지 않게 하려는 장치입니다.

이 선택을 무력화하려면 값 파일에 serviceMonitorSelectorNilUsesHelmValues: false를 넣으면 됩니다. 실습에서는 넣지 않습니다. 라벨을 붙이는 쪽이 원리를 드러내고, 운영 클러스터에서도 그쪽이 표준이기 때문입니다. 

kubectl delete -f 90-servicemonitor-broken.yaml

03ServiceMonitor 작성

k8s/monitoring/90-servicemonitors.yaml

apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: order-api
  namespace: apps
  labels:
    # ① 04단계 헬름 릴리스 이름과 일치해야 오퍼레이터가 고른다
    release: kps
spec:
  # ② 이 라벨을 가진 Service를 찾는다 (03단계에서 붙여둔 것)
  selector:
    matchLabels:
      app.kubernetes.io/name: order-api
  namespaceSelector:
    matchNames:
      - apps
  endpoints:
    # ③ Service의 포트 '이름'이다. 숫자가 아니다.
    - port: http
      path: /actuator/prometheus
      # 04단계 전역 설정과 같은 값. 명시해두면 나중에 이 서비스만 조정하기 쉽다.
      interval: 30s
      scrapeTimeout: 10s
---
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: gateway
  namespace: apps
  labels:
    release: kps
spec:
  selector:
    matchLabels:
      app.kubernetes.io/name: gateway
  namespaceSelector:
    matchNames:
      - apps
  endpoints:
    - port: http
      path: /actuator/prometheus
      interval: 30s
      scrapeTimeout: 10s
kubectl apply -f 90-servicemonitors.yaml
kubectl -n apps get servicemonitor
Service가 없을 때는 PodMonitor

배치 작업처럼 Service를 붙이지 않는 워크로드는 PodMonitor를 씁니다. 구조는 같고 ②번 고리가 Service 대신 파드 라벨로 바뀝니다. Service가 있다면 ServiceMonitor를 쓰는 편이 낫습니다 — 엔드포인트 정보를 쿠버네티스가 관리해주기 때문입니다.

04연결 검증

1. 타깃이 생겼는가

sleep 40
curl -s --get http://localhost:30900/api/v1/query \
  --data-urlencode 'query=up{namespace="apps"}' \
  | jq -r '.data.result[] | "\(.metric.job)\t\(.metric.pod)\t\(.value[1])"'
gateway     gateway-7d9c4b8f6-qk2xp     1
order-api   order-api-6b8f7d5c9-h4nm2   1
order-api   order-api-6b8f7d5c9-t8wcv   1

파드 3개가 각각 하나의 타깃입니다. 서비스가 아니라 파드 단위로 긁는다는 점이 중요합니다. 레플리카를 늘리면 타깃도 자동으로 늘어납니다.

2. 앱 메트릭이 실제로 들어왔는가

curl -s --get http://localhost:30900/api/v1/query \
  --data-urlencode 'query=orders_created_total' \
  | jq -r '.data.result[] | "\(.metric.pod)\t\(.value[1])"'

03단계에서 부하를 넣었다면 값이 보입니다. 비어 있으면 다시 요청을 몇 번 보내고 40초 기다리세요.

3. 오퍼레이터가 만든 설정을 직접 열어보기

이것이 가장 확실한 디버깅 방법입니다. 프로메테우스가 실제로 읽는 설정 파일은 시크릿에 gzip으로 들어 있습니다. 

kubectl -n monitoring get secret prometheus-kps-kube-prometheus-prometheus \
  -o jsonpath='{.data.prometheus\.yaml\.gz}' \
  | base64 -d | gunzip | grep -A12 'job_name.*order-api' | head -20

job_name이 보이면 ①번 고리는 통과한 것입니다. 여기에 없으면 라벨 문제이고, 있는데도 타깃이 0개면 ②·③번 문제입니다. 이 명령 하나로 원인을 절반으로 좁힐 수 있습니다.

05프로메테우스가 붙여준 라벨

앱은 orders_created_total{channel="api"} 하나만 내보냈는데, 프로메테우스에 저장된 시계열에는 라벨이 훨씬 많습니다. 

curl -s --get http://localhost:30900/api/v1/query \
  --data-urlencode 'query=orders_created_total' \
  | jq '.data.result[0].metric'
{
  "__name__": "orders_created_total",
  "channel": "api",
  "container": "order-api",
  "endpoint": "http",
  "instance": "10.244.1.7:8080",
  "job": "order-api",
  "namespace": "apps",
  "pod": "order-api-6b8f7d5c9-h4nm2",
  "service": "order-api"
}
라벨어디서 왔나
channel앱이 직접 붙인 태그 (02단계 Counter.builder)
jobService 이름. ServiceMonitor 기반 타깃의 기본 규칙
namespace / pod / service / container쿠버네티스 서비스 디스커버리가 자동으로 부여
endpointServiceMonitor에 쓴 포트 이름
instance스크레이프 대상 주소
02단계에서 공통 태그를 넣지 않은 이유

앱에 application=order-api 같은 태그를 넣었다면, 지금 job·service와 의미가 겹치는 라벨이 세 개가 됐을 겁니다. 질의할 때 무엇을 기준으로 묶어야 할지 매번 고민하게 되고, 팀원마다 다른 라벨을 쓰기 시작합니다. 쿠버네티스에서는 수집 계층이 붙여주는 라벨을 표준으로 삼는 것이 깔끔합니다.

06PromQL 최소 문법

여기서부터는 localhost:30900/graph에 직접 입력하며 읽으세요. 필요한 개념은 네 개뿐입니다.

1. 카운터는 그대로 보면 쓸모가 없다

2. sum by — 필요한 축만 남긴다

# 파드별로 흩어진 값을 서비스 단위로 합친다
sum by (service) (rate(orders_created_total[2m]))

# by 대신 without을 쓰면 "이 라벨만 빼고 나머지로 묶어라"가 된다
sum without (pod, instance) (rate(orders_created_total[2m]))

3. 히스토그램에서 분위수 뽑기

# le(less or equal) 라벨을 반드시 남겨야 한다. 빠지면 계산이 안 된다.
histogram_quantile(
  0.95,
  sum by (le, service) (rate(http_server_requests_seconds_bucket{namespace="apps"}[5m]))
)
네이티브 히스토그램

Prometheus 3.8부터 네이티브 히스토그램이 정식 기능이 됐습니다. 버킷 시계열이 폭증하는 문제를 근본적으로 줄여줍니다. 다만 그라파나 패널과 기존 대시보드가 아직 고전 버킷 기준인 경우가 많아, 이 실습은 고전 버킷(_bucket)으로 진행합니다. 10단계 카디널리티 논의에서 전환 판단 기준을 다시 다룹니다.

4. 비율 계산에서 조심할 것

# 트래픽이 없으면 분모가 0이 되어 결과가 비어버린다.
# 대시보드에서 'No data'가 뜨는 흔한 원인이다.
sum(rate(http_server_requests_seconds_count{namespace="apps", status=~"5.."}[5m]))
/
sum(rate(http_server_requests_seconds_count{namespace="apps"}[5m]))

07RED 지표 완성

Rate(처리율) · Errors(에러율) · Duration(지연). 애플리케이션 관측은 이 셋으로 시작해서 이 셋으로 끝납니다. 아래 질의들이 07단계 대시보드의 패널이 됩니다.

R — 서비스별 초당 요청 수

sum by (service) (
  rate(http_server_requests_seconds_count{namespace="apps"}[2m])
)

E — 서비스별 5xx 비율(%)

100 * (
  sum by (service) (
    rate(http_server_requests_seconds_count{namespace="apps", status=~"5.."}[5m])
  )
  /
  sum by (service) (
    rate(http_server_requests_seconds_count{namespace="apps"}[5m])
  )
)

D — 서비스별 P95 응답 시간(초)

histogram_quantile(
  0.95,
  sum by (le, service) (
    rate(http_server_requests_seconds_bucket{namespace="apps"}[5m])
  )
)

D 심화 — 엔드포인트별 P99, 느린 순서대로

topk(5,
  histogram_quantile(
    0.99,
    sum by (le, uri) (
      rate(http_server_requests_seconds_bucket{namespace="apps", service="order-api"}[5m])
    )
  )
)

uri 라벨이 /api/orders/{id}처럼 템플릿으로 찍혀 있는 것을 확인하세요. 02단계에서 @PathVariable로 매핑한 덕분입니다.

비즈니스 지표 — 분당 주문 수와 거부율

# 분당 주문 건수
sum(rate(orders_created_total[5m])) * 60

# 거부 비율(%) — 검증에 걸린 주문의 비중
100 * (
  sum(rate(orders_rejected_total[5m]))
  /
  (sum(rate(orders_created_total[5m])) + sum(rate(orders_rejected_total[5m])))
)
RED와 비즈니스 지표를 나란히 두는 이유

기술 지표만 보면 "에러율 0%, P95 정상"인데 매출이 떨어지는 상황을 놓칩니다. 주문 수가 평소의 30%로 줄었는데 응답 시간은 오히려 좋아진 경우가 그렇습니다 — 사용자가 들어오지 못하고 있다는 뜻일 수 있습니다. 대시보드 맨 위에 비즈니스 지표를 두는 팀이 늘어나는 이유입니다.

08지연 전파 관찰

서비스를 둘로 나눈 이유를 확인할 차례입니다. 백엔드를 느리게 만들고, 게이트웨이의 지연이 어떻게 따라 움직이는지 봅니다. 

# 터미널 1 — 평상시 트래픽을 계속 흘린다
while true; do
  curl -s -o /dev/null -X POST http://localhost:30080/api/orders \
    -H 'Content-Type: application/json' \
    -d '{"item":"latte","quantity":2}'
  sleep 0.3
done
# 터미널 2 — 3분 동안 느린 요청을 섞는다
end=$((SECONDS+180))
while [ "$SECONDS" -lt "$end" ]; do
  curl -s -o /dev/null "http://localhost:30080/api/chaos/slow?ms=900"
  sleep 1
done
echo "지연 주입 종료"

두 질의를 그래프에 함께 띄워 비교합니다.

# 게이트웨이가 본 P95 (클라이언트 관점)
histogram_quantile(0.95,
  sum by (le) (rate(http_server_requests_seconds_bucket{service="gateway"}[2m]))
)

# 백엔드가 본 P95 (서버 관점)
histogram_quantile(0.95,
  sum by (le) (rate(http_server_requests_seconds_bucket{service="order-api"}[2m]))
)
관찰되는 패턴해석
두 값이 거의 같이 오른다 백엔드가 원인. 게이트웨이는 기다렸을 뿐이다
게이트웨이만 오르고 백엔드는 평온 게이트웨이 자체 병목 — 커넥션 풀, CPU, 라우팅 필터를 의심
백엔드가 올랐는데 게이트웨이는 그대로 느린 경로가 게이트웨이를 거치지 않았거나, 타임아웃으로 잘리고 있다

게이트웨이의 라우트 단위 지표로 한 번 더 확인할 수 있습니다.

histogram_quantile(0.95,
  sum by (le, routeId) (rate(spring_cloud_gateway_requests_seconds_bucket[5m]))
)
실습이 끝나면 반드시 부하 루프를 끄세요

터미널 1의 무한 루프를 켜둔 채 잊으면 노트북 팬이 계속 돌고, 프로메테우스 저장 공간(04단계에서 8Gi)이 예상보다 빨리 찹니다. Ctrl+C로 종료하세요.

09자주 겪는 문제

증상확인 순서
타깃 목록에 앱이 아예 없다 ①번 고리. release: kps 라벨과 프로메테우스 CR의 셀렉터를 대조한다
타깃 그룹은 있는데 대상이 0개 ②번 고리. kubectl -n apps get svc --show-labels로 Service 라벨을 확인
server returned HTTP status 404 path가 /actuator/prometheus인지, 앱의 exposure 설정에 prometheus가 있는지
connection refused 포트 이름이 가리키는 실제 포트가 앱의 리슨 포트와 다르다
메트릭은 있는데 _bucket만 없다 앱 설정 문제. 02단계 percentiles-histogram을 확인하고 이미지를 다시 빌드
histogram_quantile 결과가 NaN sum by에서 le를 빠뜨렸거나, 해당 구간에 샘플이 없다
비율 질의가 빈 결과 분모가 0. 트래픽을 넣거나 or vector(0)로 기본값을 준다
그래프가 톱니처럼 끊긴다 rate 윈도가 스크레이프 간격에 비해 짧다. [2m] 이상으로 늘린다
지금부터 조심해야 할 것 — 카디널리티

앱 메트릭이 붙는 순간 시계열 개수가 급증합니다. http_server_requests_seconds_bucket 하나가 (엔드포인트 수) × (상태 코드 수) × (버킷 수) × (파드 수)만큼의 시계열을 만듭니다. 실습 규모에서는 문제없지만, 운영에서 uri 태그에 ID가 섞이는 순간 프로메테우스가 메모리 부족으로 죽습니다. 10단계의 주제입니다. 

# 지금 시계열이 몇 개인지 확인해두면 나중에 비교하기 좋다
prometheus_tsdb_head_series

# 메트릭 이름별 시계열 수 상위 10개
topk(10, count by (__name__) ({__name__=~".+"}))

10완료 체크리스트

  • release 라벨 없이 만들면 타깃이 안 생긴다는 것을 직접 확인했다
  • up{namespace="apps"} 결과가 파드 3개 모두 1이다
  • 시크릿에서 생성된 스크레이프 설정을 열어 job_name을 확인했다
  • 메트릭에 job·namespace·pod·service 라벨이 붙어 있다
  • RED 질의 세 개가 모두 값을 반환한다
  • uri 라벨이 /api/orders/{id} 형태로 템플릿화되어 있다
  • 지연 주입 실습에서 게이트웨이와 백엔드의 P95 곡선을 함께 봤다
  • 부하 생성 루프를 종료했다
  • 질의 6개를 팀 저장소의 메모에 정리했다 (07단계에서 패널로 옮긴다)
다음 문서

07 · 대시보드와 알림 — 방금 만든 질의들을 05단계의 프로비저닝 방식으로 대시보드에 옮깁니다. 변수(namespace·service)를 넣어 하나의 대시보드로 여러 서비스를 보고, PrometheusRule로 알림 규칙을 선언한 뒤 Alertmanager에서 라우팅합니다. "알림을 몇 개 만들 것인가"라는 더 어려운 질문도 함께 다룹니다.
