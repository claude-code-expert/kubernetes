# 책 3장 「모니터링과 로깅」 추출 노트

원전: 『쿠버네티스 창시자에게 배우는 모범 사례 2판』(한빛미디어, 2024) 77~104쪽.
강의 이론 파트의 원천 자료다. 쪽수는 책 기준이며 PDF 쪽수와 동일하다.
책의 실습 명령 일부는 2026년 기준으로 낡았다 — 정정 목록은
`03-책-docs-격차와-강의-설계.md`에 있다. 이 파일은 책 내용을 충실히 옮기는 것이 목적이다.

## 3.1 메트릭 vs 로그 (78쪽)

- **메트릭**: 정해진 기간에 측정한 수치
- **로그**: 에러·경고·중요 이벤트 등 프로그램 실행 중 일어난 사건의 추적

둘은 상호 보완적이되 용도가 다르다. 책이 드는 사례: 파드의 레이턴시가 높게 나타나면
메트릭만으로는 원인을 알기 어렵고, 그 시점의 애플리케이션 로그를 봐야 에러를 조사할 수 있다.
"메트릭이 이상을 알려주고, 로그가 이유를 말해준다"로 요약 가능 — 강의에서 M1 도입부와
M6(로그) 도입부 양쪽에 쓸 수 있는 축이다.

## 3.2 모니터링 기법 (78~79쪽)

- **폐쇄형 모니터링**(closed-box): 애플리케이션 외부에서 관찰. CPU·메모리·스토리지 등
  전통적 인프라 모니터링 방식. 인프라 수준 컴포넌트에는 유용하지만 앱이 왜 그렇게
  동작하는지 맥락을 주지 못한다. 책 예시: 파드 스케줄링 테스트가 성공하면 스케줄러와
  서비스 디스커버리는 정상이라고 판정하는 식
- **개방형 모니터링**(open-box): 총 HTTP 요청 수, 500 에러 횟수, 요청 레이턴시 같은
  애플리케이션 내부 상태에 주목. "디스크가 꽉 찼다"가 아니라 "왜 꽉 찼을까"를 물을 수 있다

일반적으로 블랙박스/화이트박스 모니터링으로 불리는 개념이다. 번역서가 폐쇄형/개방형을
택했으므로 강의에서는 두 용어를 병기하는 편이 안전하다.

## 3.3 모니터링 패턴 (79~81쪽)

쿠버네티스가 기존 모니터링과 다른 이유부터 짚는다: 24/7 가동되는 VM은 상태 보존을
확인하면 되지만, 파드는 수명이 짧고 다이내믹해서 그 특성을 담을 체계가 따로 필요하다.

**USE 방법론** (브렌던 그레그):
- Utilization(사용률) · Saturation(포화도) · Errors(에러 수)
- "모든 리소스에 대해 사용률·포화도·에러를 확인하라"
- 인프라 수준 모니터링용. 애플리케이션 수준에는 한계가 뚜렷
- 예시: 노드 네트워크의 병목을 세 지표로 빠르게 찾는다

**RED 방법론** (톰 윌키):
- Rate(처리율) · Errors(에러 수) · Duration(처리 시간)
- 애플리케이션의 엔드 유저 경험 위주
- 프론트엔드 서비스라면: 요청을 얼마나 처리하나 / 유저가 500을 얼마나 받나 /
  서비스가 과사용되고 있나

**구글 4대 골든 시그널** (RED의 기반 사상):
레이턴시(처리 시간) · 트래픽(수요량) · 에러(실패 비율) · 포화도(사용률)

두 방법론은 상보적이다: USE는 인프라, RED는 애플리케이션.
강의 연결점 — docs/06의 "RED 질의 6개"가 이 절의 실습 대응물이고,
docs/05의 kube-prometheus-stack 내장 USE 대시보드가 USE의 실습 대응물이다.

## 3.4 쿠버네티스 메트릭 개요 (81~84쪽)

클러스터 구성 요소 전부가 모니터링 대상이다. 컨트롤 플레인(API 서버, etcd, 스케줄러,
컨트롤러 매니저)과 노드 컴포넌트(kubelet, 컨테이너 런타임, kube-proxy, kube-dns, 파드).

### 3.4.1 cAdvisor (82쪽)

노드에서 실행 중인 컨테이너의 리소스·메트릭을 수집하는 오픈 소스 구현체.
**kubelet과 한몸으로** 모든 노드에서 실행된다. cgroup 트리에서 메모리·CPU를,
리눅스 커널 statfs에서 디스크 메트릭을 수집한다.
책의 강조점: cAdvisor는 **모든 컨테이너 메트릭의 진실 공급원**이므로 구현 세부는 몰라도
어떤 정보가 어떻게 표출되는지는 알아야 한다.

### 3.4.2 메트릭 서버 (82~83쪽)

역사 먼저: 힙스터(Heapster)는 데이터 싱크 설계 문제로 사용 중단됐고, 리소스/커스텀
메트릭 API를 쿠버네티스 집계(aggregated) API로 구현하면서 해결됐다 — API를 바꾸지
않고 구현체를 교체할 수 있게 됐다.

두 가지를 이해해야 한다:
1. **메트릭 서버는 리소스 메트릭 API의 표준 구현체**다. CPU·메모리를 kubelet API에서
   수집해 **메모리에 저장**한다(장기 저장 없음). 스케줄러, HPA, VPA가 소비한다
2. **커스텀 메트릭 API**로 모니터링 시스템의 임의 메트릭을 확장할 수 있다.
   프로메테우스가 최초의 커스텀 메트릭 어댑터 — 큐 사이즈 같은 외부 메트릭 기반
   HPA 스케일링이 가능해진다

### 3.4.3 kube-state-metrics (83~84쪽)

쿠버네티스에 저장된 **오브젝트의 상태**를 모니터링하는 애드온. cAdvisor·메트릭 서버가
리소스 사용량을 보는 반면, 이쪽은 배포된 오브젝트가 의도한 상태인지를 본다.

책이 나열한 확인 항목:
- 파드: 배포 수, 대기 상태 수, 리소스 충분 여부
- 디플로이먼트: 실행 중 vs 의도한 파드 수, 가용 레플리카, 업데이트 여부
- 노드: 상태, 할당 가능 CPU 코어 수, 스케줄링 불가 노드 존재 여부
- 잡: 시작·완료 시각, 실패 수

세 컴포넌트의 역할 구분(사용량 vs 상태)이 시험 문제로 나올 만큼 중요한 대비다.
강의 M3에서 표 하나로 정리할 것.

## 3.5 어떤 메트릭을 모니터링하나 (84~85쪽)

"전부 다"는 답이 아니다 — 잡다한 메트릭에 정작 봐야 할 신호가 묻힌다.
**계층적 접근**을 권장한다:

1. 물리/가상 노드
2. 클러스터 컴포넌트
3. 클러스터 애드온
4. 엔드 유저 애플리케이션

예시: 파드가 자꾸 대기 상태면 먼저 노드 리소스 사용률을 체크하고, 문제없으면
클러스터 수준 컴포넌트로 좁혀 들어간다.

타깃팅할 메트릭 목록:
- 노드: CPU·메모리·네트워크·디스크 사용률
- 클러스터 컴포넌트: etcd 레이턴시
- 클러스터 애드온: 클러스터 오토스케일러, 인그레스 컨트롤러
- 애플리케이션: 컨테이너 메모리 사용률·포화도, CPU 사용률, 네트워크 사용률·에러율,
  프레임워크 특정 메트릭

## 3.6 모니터링 툴 (85~88쪽)

- **프로메테우스**: 사운드클라우드 출신 OSS. 2016년 쿠버네티스 다음으로 CNCF 합류.
  독립 거버넌스 강조
- **InfluxDB**: TICK 스택의 핵심. 높은 쓰기/쿼리 부하용 시계열 DB
- **데이터독**: SaaS 기반 클라우드 스케일 모니터링
- **시스딕 모니터**: 컨테이너 네이티브 상용 툴. 프로메테우스 메트릭 수집·상관·쿼리
- **클라우드 프로바이더**: GCP 스택드라이버(주의 — 역주에 따르면 2020-08 사용 중단,
  Google Cloud Operations로 개편), 컨테이너용 애저 모니터, AWS CloudWatch
  컨테이너 인사이트

책의 평가 기준 두 가지가 나열보다 중요하다:
- 메트릭이 **어떻게 저장되는지** 보라. 키/값 시계열 DB를 제공하는 툴이 더 고수준의
  속성을 제공한다
- TIP: 새 툴 도입은 학습·적용 비용이 크므로 신중히 평가하라. 현재 쓰는 툴과
  도입할 툴이 요건에 맞는지가 우선이다

강의에서는 툴 백화점식 나열 대신 이 두 기준 + "왜 프로메테우스인가"로 압축한다
(CLAUDE.md 문체 규약: 나열식 비교 금지).

## 3.7 프로메테우스를 이용한 쿠버네티스 모니터링 (88~94쪽)

**개념 파트** (강의에 그대로 쓸 것):
- 구글 내부 모니터링 시스템 **보그몬**(Borgmon)에서 아이디어를 가져옴.
  키/값 다차원 데이터 모델 — 쿠버네티스의 레이블 방식과 상당히 유사.
  쿠버네티스의 레이블·서비스 디스커버리·메타데이터와 "찰떡궁합"인 이유
- 사람이 읽을 수 있는 텍스트 포맷:
  ```
  # HELP node_cpu_seconds_total Seconds the CPU is spent in each mode.
  # TYPE node_cpu_seconds_total counter
  node_cpu_seconds_total{cpu="0",mode="idle"} 5144.64
  ```
- **풀(pull) 모델**: 타깃 엔드포인트에서 직접 긁어온다. 쿠버네티스 자체와
  Nginx·Traefik·이스티오·링커드 등이 이미 프로메테우스 포맷으로 표출.
  아닌 서비스는 **익스포터**로 변환
- TIP: 클러스터 모니터링은 프로덕션에 영향을 주지 않게 별도 '유틸리티 클러스터'에서
  하는 것이 좋다. 타노스(Thanos)로 고가용성·외부 스토리지 익스포트 가능

**kube-prometheus-stack 구성 요소** (책 90쪽 — docs/04와 동일 구조):
프로메테우스 서버 / 프로메테우스 오퍼레이터(쿠버네티스 리소스 정의로 프로메테우스·
알림매니저 관리) / 노드 익스포터(호스트 메트릭) / kube-state-metrics / 알림매니저 /
그라파나

**실습 파트** (책 90~93쪽 — 낡음, docs/04로 대체):
minikube 기반, `helm repo add prometheus-community ...` + 구 stable 저장소 추가 후
`helm install --namespace monitoring prometheus prometheus-community/kube-prometheus-stack`.
grafana 접속은 port-forward 3000:80, 계정 admin / prom-operator.
내장 "Node Exporter / USE Method / Cluster" 대시보드로 USE 지표 확인 — 이론(3.3)이
설치 직후 바로 눈에 보이게 되는 구성이라 강의 시연 순서로 좋다.

**"그래프의 장벽" 경고** (94쪽 TIP): 대시보드를 너무 많이 만들면 트러블슈팅에 오히려
방해가 된다. 정보가 많다고 모니터링이 잘 되는 게 아니다. 대시보드는 결과와
문제 해결 시간에 초점을 두고 설계하라. — docs/07의 "무엇을 넣지 않을지 정하는 일"과
직결되는 대목.

## 3.8 로깅 개요 (94~96쪽)

"모든 걸 다 로깅하자"의 두 가지 문제:
- 노이즈가 많아 문제를 빨리 찾기 어렵다
- 리소스 소모와 비용이 과도하다

보존 정책: 엔드 유저 관점에서 **30~45일**이면 충분. 컴플라이언스로 장기 보존이
필요하면 더 저렴한 리소스에 보관(역주: 전자금융거래법상 전자금융거래기록 5년 보존 사례).

수집 대상 4종:
1. **노드 로그**: 필수 노드 서비스(예: 컨테이너 데몬)의 이벤트
2. **컨트롤 플레인 로그**: API 서버·컨트롤러 매니저·스케줄러
   (호스트의 /var/log/kube-apiserver.log 등). 예시 — LoadBalancer 서비스가 대기
   상태일 때 이벤트만으로는 원인 파악이 어렵고 컨트롤러 매니저 로그가 필요
3. **감사(audit) 로그**: 누가 언제 무엇을 했나. 노이즈가 극심하므로 반드시 환경에 맞게
   조정. 처음 켜면 폭발적으로 쌓일 수 있음
4. **애플리케이션 컨테이너 로그**

앱 로그 수집 두 가지 방식:
- **권장: 모든 로그를 STDOUT으로**. 일관된 로깅 + 데몬셋 수집기가 노드에서 직접 수집
- **사이드카 패턴**: 앱이 파일에 로그를 쓸 때만. 로그 전달기가 리소스를 많이 먹으므로
  가급적 제한 (3.12.2)

docs/08의 전제("컨테이너는 stdout으로 찍고 수집기가 노드에서 걷는다")의 이론적 근거가
이 절이다. M6 이론 파트의 뼈대.

## 3.9 로깅 툴 (96~97쪽)

로키, 일래스틱 스택, 데이터독, 수모 로직, 시스딕, 클라우드 프로바이더 서비스.
평가 기준: 데몬셋으로 실행 가능한지, STDOUT 불가 앱에 사이드카로 붙일 수 있는지,
기존 운영 노하우가 있는지. 운영 비용 절감 차원에서 호스티드 서비스도 고려하라 —
자체 호스팅은 환경이 커질수록 관리 시간이 막대해진다.

## 3.10 로키 스택을 사용한 로깅 (97~100쪽)

자체 로깅 플랫폼 구축에 대한 책의 시각: 처음엔 그럴싸해도 시간이 지나면 과도하게
복잡해지는 경우가 많다. 정답은 없고 비즈니스 요건으로 결정하라. 그라파나의 로키
호스티드 서비스도 선택지.

책의 스택 구성: **로키 + 프롬테일 + 그라파나**.
설치: `helm repo add grafana https://grafana.github.io/helm-charts` 후
`helm upgrade --install loki --namespace=monitoring grafana/loki-stack`.
그라파나에서 데이터 소스로 로키 추가(URL `http://loki:3100`), Explorer 패널에서
`namespace=kube-system` 식 레이블 필터로 조회.

**주의 — 이 절의 실습 절차는 2026년 기준으로 낡았다.** Promtail은 2026-03 EOL이고
수집기는 Alloy, 차트 저장소는 grafana-community다. 개념 구조(수집기 → 로키 →
그라파나, 레이블 기반 조회)만 가져오고 실습은 docs/08을 쓴다.
상세는 `03-책-docs-격차와-강의-설계.md`.

## 3.11 알림 (100~102쪽)

강의 M5의 이론 뼈대. 책의 논리 흐름:

1. **알림은 양날의 검**: 너무 많으면 무감각해져 중요한 이벤트가 파묻힌다.
   파드 실패마다 알림? — 쿠버네티스의 꽃이 자동 재시작인데 그건 알림 대상이 아니다
2. **SLO 기반으로 보내라**: 유저는 SLO에 영향을 주는 이벤트만 알림 받고 싶어 한다.
   SLO가 없으면 비현실적 기대치가 요구된다. 예: 응답 시간 SLO 20ms인 프론트엔드의
   레이턴시가 평균 이상이면 즉시 알림
3. **사람이 개입할 일만**: 저절로 해결되던 문제는 호출하지 않는다. 즉시 조치가
   필요 없는 알림은 원인을 자동으로 바로잡는다 — 디스크가 차면 로그 자동 삭제,
   미응답 프로세스는 라이브니스 프로브로 자동 재시작
4. **임계치 설계**: 너무 짧으면 오탐 남발. **최소 5분 이상**. 5분/10분/30분/1시간처럼
   패턴을 표준화해 임계치 관리 부담을 줄인다
5. **알림에 맥락을 실어라**: 플레이북 링크, 데이터 센터·지역·앱 소유자·영향 시스템
6. **라우팅**: 팀 전체 이메일로 뿌리면 노이즈로 걸러진다. 실제로 해결할 사람에게 보낸다
7. **완벽한 알림은 없다**: 점진적으로 개선하는 것이 바람직하다

참고 문헌: 롭 에와슈크 「My Philosophy on Alerting」 (구글 SRE 경험담).

## 3.12 모니터링, 로깅, 알림 모범 사례 (103~104쪽)

책의 요약 그대로:

**모니터링**
- 모든 노드와 쿠버네티스 컴포넌트에 사용률·포화도·에러율(USE)을 모니터링
- 애플리케이션에는 사용률·에러 수·실행 시간(RED)을 모니터링
- 예측하기 어려운 상태·징후는 폐쇄형, 시스템 내부 조사는 개방형 모니터링
- 시계열 기반 메트릭으로 애플리케이션 동작의 인사이트를 얻어라
- 키를 레이블로 쓰는 다차원 데이터 모델(프로메테우스류)을 구축하라

**로깅**
- 메트릭 모니터링과 로깅을 함께 써서 전체 동작을 파악하라
- 로그는 30~45일 이상 쌓아두지 말라. 장기 보존은 저렴한 리소스로
- 사이드카 로그 전달기는 리소스 소모가 크니 제한하라. 데몬셋 + STDOUT이 대안

**알림**
- 알림 피로는 담당자와 프로세스 모두를 해친다
- 완벽한 알림은 없다 — 점진적으로 개선하라
- 즉시 대응이 필요 없는 일시적 문제는 알림 금지. SLO와 고객 영향 증상에만 알림

## 정리 절의 핵심 문장 (104쪽)

"나중에 사고가 나서야 모니터링을 구현하는 경우를 참 많이 봐왔다."
모니터링의 목표는 시스템을 더 잘 들여다볼 수 있게 만들어 복원성을 높이고 엔드 유저에게
양질의 경험을 제공하는 것 — 강의 오프닝 또는 클로징 멘트 후보.
