# 책 5장 「지속적 통합, 테스팅, 배포」 테스팅 관련 추출 노트

원전: 『쿠버네티스 창시자에게 배우는 모범 사례 2판』 125~147쪽. 보조로 2.4.3
「테스팅과 디버깅」(74~75쪽)을 포함한다.

강의의 "테스팅" 축은 기존 docs/ 시리즈에 없는 신규 영역이다. 5장 전체가 CI/CD를
다루지만, 강의 주제(모니터링·로깅·관측·테스팅)에 필요한 것은 테스팅 파트다.
CI/CD 파이프라인 구축 자체(5.1, 5.4~5.6, 5.9.1~5.9.3)는 배경 지식으로만 요약하고,
테스팅·프로덕션 테스팅·카오스(5.3, 5.7의 검증 관점, 5.8, 5.9.4)를 중심으로 추출한다.

## 이 장이 관측성 강의와 연결되는 지점

책 5.8의 문장이 연결 고리다 (138쪽):

> "프로덕션 환경에서 수행한 테스트의 효과를 정확하게 식별할 수 있는 깊이 있는
> 관찰 가능성(observability) 전략이 필요하다. 엔드 유저의 애플리케이션 경험에 영향을
> 미치는 메트릭을 관찰할 능력도 없는데 정작 시스템의 회복 탄력성을 개선하기 위해
> 어디에 집중해야 할지 가늠하기는 어려울 것이다."

즉 **관측 스택이 완성된 뒤에야 프로덕션 테스팅(카오스 실험)이 가능하다.**
기존 docs 00~10이 끝나는 지점(관측 완성)이 테스팅 모듈의 입력이 된다.
강의 서사: "우리가 만든 대시보드와 알림이 진짜 동작하는지, 장애를 주입해 증명한다."

## 5.3 테스팅 — 파이프라인 안의 테스트 (128쪽)

- 목적: 빌드를 망친 코드 변경분에 대한 **신속한 피드백**
- 원칙: **파이프라인에서 테스트가 실패하면 빌드도 실패한 것으로 간주한다.**
  테스트가 실패한 소스를 컨테이너 이미지로 빌드해 레지스트리에 푸시하면 대형 사고
- 테스트는 애플리케이션 코드에만 있는 게 아니다: `helm lint`처럼 인프라 구성물
  (차트·매니페스트)도 테스트 대상
- 단위 테스트는 개발자 몫이지만 스모크 테스트처럼 협력이 필요한 것도 있다.
  엔드-투-엔드 파이프라인에서는 많은 테스트가 병행돼야 하며 팀 간 협력이 필요하다

강의 적용: order-api의 JUnit 테스트(Gradle `test` 태스크)가 단위 테스트 대응물.
매니페스트 검증(`kubectl apply --dry-run=server`, `helm lint`)을 실습에 추가할 수 있다.

## 5.7 배포 전략 — 검증 관점 (132~137쪽)

배포 전략 자체는 CD 주제지만, 셋 다 "새 버전이 정상인지 판정하는 문제"를 안고 있어
테스팅·관측과 붙는다.

**롤링 업데이트** (쿠버네티스 기본):
- `maxSurge` / `maxUnavailable`로 속도 제어
- 커넥션 유실 방지 장치 두 가지가 필수:
  - **레디니스 프로브**: 새 버전이 트래픽 받을 준비가 됐는지 확인
  - **preStop 라이프 사이클 훅**: 종료 전 커넥션 드레이닝. 동기 호출이며 최종 종료
    시그널 전에 완료돼야 한다. 책 예시는 `nginx -s quit`으로 그레이스풀 셧다운
    (SIGTERM 즉시 종료와 대비)
- 롤링 중에는 두 버전이 동시 실행 → DB 스키마가 양쪽을 지원해야 한다.
  기능 플래그로 새 컬럼을 다루고 완료 후 옛 컬럼 삭제
- 라이브니스 vs 레디니스 구분: 라이브니스는 "살아 있나"(아니면 재시작 — 데드락 케이스),
  레디니스는 "트래픽 받을 준비 됐나"(아니면 엔드포인트에서 제외)

**블루/그린**: 트래픽 전환 시점을 제어할 수 있어 예측 가능한 릴리스. 대가 —
두 환경 동시 유지 용량, 인플라이트 트랜잭션과 스키마 호환으로 DB 마이그레이션이
어려워짐, 실수로 두 환경 모두 삭제할 위험.

**카나리**: 일부 트래픽(예: 10%)만 새 버전으로. 판단 기준이 필요하다 —
"새 릴리스가 정상 상태(steady state)인지 어떻게 확신할 것인가?
상태가 양호/불량인지 판단하기 위한 **메트릭**". 유저가 모르게 하는 변형이 A/B(다크) 릴리스.

강의 연결: 카나리의 "판단 메트릭"이 바로 docs/06에서 만든 RED 지표다.
프로브 3종의 역할 분담은 docs/03에서 이미 실습했으므로 이 절은 이론 보강으로 연결만 한다.

## 5.8 프로덕션 테스팅 (138~139쪽)

- 프로덕션 테스팅이 주는 것: 회복 탄력성(resiliency)·확장성·UX에 대한 확신
- 전제 조건 둘: **깊이 있는 관측 전략** + 주입한 장애를 자동 복구할 **높은 수준의 자동화**
- 기법 목록: 카나리 배포, 블루/그린, 트래픽 전환, 기능 플래그, 분산 추적,
  인스트루멘테이션, 카오스 엔지니어링, 트래픽 섀도잉

**카오스 엔지니어링** (넷플릭스 기원): 라이브 프로덕션 시스템에 실험을 배포해 취약점을
발견한다. 통제된 실험으로 시스템을 이해한다는 발상.

게임 데이(game-day) 실험 절차 — 강의 실습 템플릿으로 쓸 것:
1. 정상 상태(steady state)에 대한 가설을 세운다
2. 시스템에 영향을 줄 수 있는 다양한 수준의 실제 이벤트를 준비한다
3. 대조군을 만들고 실험하면서 정상 상태와 비교한다
4. 실험으로 가설을 테스트한다

원칙: **폭발 반경(blast radius)을 최소화**하고, 실험은 가능한 한 자동화한다.

"스테이징에서 테스트하면 안 되나?"에 대한 책의 답 — 스테이징의 고질적 한계 6가지:
- 리소스를 프로덕션과 똑같이 배포할 수 없다
- 프로덕션과 구성이 다르다
- 트래픽과 유저 행위는 복합적으로 일어난다
- 생성된 요청 수와 실제 워크로드 간 괴리
- 스테이징은 모니터링이 빈약하다
- 데이터 서비스의 데이터·부하가 실제와 다르다

## 5.9.4 간단한 카오스 실험 (145~146쪽)

카오스 툴 4종:
- **Gremlin**: 고급 기능의 호스티드 서비스
- **PowerfulSeal**: 고급 시나리오 기능의 오픈 소스
- **Chaos Toolkit**: 커뮤니티 기반 툴킷·API 제공이 목표인 오픈 소스
- **KubeMonkey**: 파드 대상 기본 회복 탄력성 테스트 오픈 소스

책의 예제는 Chaos Toolkit으로 파드를 자동 종료시켜 회복 탄력성을 확인한다:

```bash
pip install -U chaostoolkit
pip install chaostoolkit-kubernetes
export FRONTEND_URL="http://$(kubectl get svc frontend \
  -o jsonpath="{.status.loadBalancer.ingress[*].ip}"):8080/api/"
chaos run experiment.json
```

주의: 책은 experiment.json의 내용을 싣지 않았다. 강의 실습으로 옮길 때는
실험 정의(정상 상태 프로브 + 파드 킬 액션 + 롤백)를 직접 작성해야 하며,
2026년 기준 chaostoolkit-kubernetes의 최신 버전·호환성을 재검증해야 한다.

## 5.10 CI/CD 모범 사례 중 테스팅 관련 (146~147쪽)

- 파이프라인에 **안정적인 테스트**를 구축하라. 피드백 주기가 짧을수록 개발자
  워크플로 생산성이 올라간다
- CD 단계에서 클라이언트 연결 방식과 DB 스키마 업그레이드 처리를 테스트하라
- **프로덕션 테스팅은 소규모로 시작하고 실험의 폭발 반경을 제한하라.**
  모니터링이 제대로 되는지 확인하는 용도로도 유용하다

## 배경 요약 — 5장의 나머지 (강의에서는 한 문단 처리)

- 5.1 버전 관리: 앱 코드와 구성 코드(매니페스트·차트)를 한 리포지터리에 —
  개발·운영이 같이 작업해야 안정적 배포에 대한 믿음이 생긴다
- 5.2 CI: 작은 변경분을 자주 커밋, 커밋마다 즉시 빌드 → 빠른 피드백
- 5.4 이미지 최적화: 멀티스테이지 빌드 / 무배포(distroless, 셸 없어 디버깅 불편) /
  알파인·데비안 슬림 같은 최적화 베이스
- 5.5 태깅: **latest 절대 금지**. 빌드 ID, 깃 해시, 또는 조합
- 5.6 CD: 불변 이미지의 환경 승격. 구성 드리프트 방지. CD 전에 CI부터 탄탄하게
- 5.9.1~5.9.3: drone.io 기반 파이프라인 예제 — 2026년 기준 실습 가치 낮음
  (`03-책-docs-격차와-강의-설계.md` 참조). 개념 흐름(빌드→테스트→이미지→배포→검증)만 차용

## 2.4.3 테스팅과 디버깅 (74~75쪽)

개발 단계의 테스팅·디버깅 이야기. kubectl은 만능이지만(`logs`, `exec`, `port-forward`)
옵션이 많아 학습 비용이 크다. VS Code 쿠버네티스 익스텐션 같은 IDE 통합이
kubeconfig의 클러스터를 자동 검색해 트리뷰로 보여주고, 우클릭으로 포트 포워딩·로그·
터미널 접속을 제공한다 — 쿠버네티스 경험이 적은 개발자의 온보딩 수단.
강의에서는 M1 환경 준비에서 한 문단 + 시연 거리로 충분하다.
