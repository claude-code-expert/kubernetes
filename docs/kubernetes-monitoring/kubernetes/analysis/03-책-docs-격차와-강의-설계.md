## 3. docs가 채우는 것 — 책에 없는 실습 깊이

역방향 확인. 책은 개론서라 다음이 없다:
- 계측 코드 작성 (Spring Boot Micrometer, 커스텀 메트릭 이름·태그 설계) — docs/02
- ServiceMonitor 라벨 연결과 의도적 실패·복구 — docs/06
- PromQL 작성 (RED 질의 6개, 히스토그램 분위수) — docs/06
- 대시보드 프로비저닝을 코드로 (ConfigMap 사이드카) — docs/05
- PrometheusRule 작성 — docs/07
- 카디널리티·보존 기간 계산·트러블슈팅 — docs/10
- 버전 고정과 사전 점검 스크립트 — docs/00

즉 책 = 왜(개념·판단 기준), docs = 어떻게(동작하는 절차). 강의는 각 모듈에서
책 이론을 앞에, docs 실습을 뒤에 배치하면 된다. CLAUDE.md의 모듈 골격
(왜 → 이론 → 실습 → 실패 → 검증 → 다음)과 그대로 맞는다.

## 4. 신규 모듈 제안 — M8 테스팅과 카오스 실험

기존 CLAUDE.md의 M1~M7에는 테스팅 축이 없다. 책 5장을 근거로 M8을 추가한다.

**M8. 테스팅과 카오스 실험** (이론: 책 5.3·5.7·5.8·5.9.4 / 실습: 신규 제작)

서사: M1~M7에서 만든 관측 스택은 "장애가 나면 보인다"까지 증명했다. M8은 거꾸로
장애를 일부러 만들어 관측 스택과 애플리케이션의 회복 탄력성을 검증한다.
책 5.8의 "관측 없이 프로덕션 테스팅 없다"가 M7 → M8 연결 논거.

실습 설계 초안 (기존 자산 재사용):
1. **가설 수립**: "order-api 파드 1개가 죽어도 gateway의 5xx 비율은 SLO 이내"
   — docs/07에서 만든 RED 패널·알림이 판정 도구
2. **부하 유지**: docs/06의 부하 생성 루프 재사용
3. **장애 주입**:
   - 1차(수동): `kubectl delete pod` — 폭발 반경 최소의 첫 실험
   - 2차(도구): Chaos Toolkit + chaostoolkit-kubernetes로 experiment.json 작성.
     책에 없는 실험 정의를 직접 만든다 (정상 상태 프로브 = 프로메테우스 질의,
     액션 = 파드 종료, 롤백 포함)
   - 3차(앱 수준): order-api의 ChaosController로 지연·에러 주입 — 인프라 장애가
     아닌 앱 열화 시나리오. 07단계 알림 발화 → 해소 관찰
4. **관찰·판정**: 실험 전/중/후 대시보드 비교, 알림 발화 여부, 가설 채택/기각
5. **검증 기준**: 레디니스 프로브 덕에 5xx가 억제되는지 vs 프로브를 일부러 빼면
   무엇이 달라지는지 (docs/03 프로브 실습의 회귀 검증 — "일부러 실패시키기" 요건 충족)

주의: 실습 전 Chaos Toolkit의 2026년 최신 버전·K8s 1.36 호환성 재검증 필요.
게임 데이 4단계(가설→이벤트→대조→판정)를 실습 시트 양식으로 만들 것.
