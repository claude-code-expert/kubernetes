CHAPTER 12

멀티클러스터 관리

7장이 "하나의 애플리케이션을 전 세계에 배포하는 법"이었다면, 이 장은 한 걸음 더 나아가 "클러스터 자체를 여러 개 두는 게 맞는가, 두면 무엇이 힘들어지는가"다. 멀티클러스터는 기본값이 아니다 — 명확한 이유가 있을 때만 감수하는 복잡도다.

2026-08 기준 변경 사항 주석 포함

핵심 3줄

1. 멀티클러스터를 쓰는 이유는 넷 중 하나다 — 블라스트 반경 제한, 컴플라이언스 분리, 특수 워크로드 격리, 지리적 분산. 이유 없이 쓰면 복잡도만 는다.

2. 단일 클러스터에선 안 하던 고민(데이터 복제·서비스 디스커버리·크로스 클러스터 라우팅·운영 오버헤드·멀티클러스터 CD)이 통째로 새로 생긴다.

3. 페더레이션 v1·v2(KubeFed)는 이미 죽었다 — 지금은 CRD 기반으로 다시 설계된 Karmada·OCM이 그 자리를 잇는다.

12.1멀티클러스터의 필요성

클러스터를 늘리는 것은 절대 공짜가 아니다 — 그럼에도 여러 클러스터를 두는 조직이 많은 데는 이유가 있다.

12.2멀티클러스터 설계 문제

멀티클러스터를 선택하면 아키텍처가 급격히 복잡해지는 다섯 지점이 있다. 이 목록이 길게 느껴진다면 — 실제로 길다. 그래서 12.1절의 이유가 이 비용을 넘어설 때만 선택하라는 것이다.

데이터 복제가 가장 근본적이다 — 여러 리전에 클러스터를 두는 것 자체는 쉽지만, 그 안의 데이터가 최종 일관성 (Eventual Consistency)을 감내할 수 있는지, 리전 간 레이턴시를 허용할 수 있는지는 애플리케이션 설계 단계부터 답해야 한다. Cloud Spanner·CosmosDB 같은 관리형 서비스는 이 복잡도를 대신 떠안아 주는 대가로 존재한다.

12.3멀티클러스터 배포 관리

클러스터 자체를 어떻게 만들고 유지할지부터 정해야 한다. 손으로 하나씩 만드는 것은 클러스터 수가 둘만 넘어도 곧 재앙이 된다 — IaC (Infrastructure as Code) 툴로 배포 파이프라인을 구축하는 것이 출발점이다. Terraform, kubespray, kops, 또는 클라우드 프로바이더가 제공하는 배포 툴 어느 것이든 좋다. 중요한 건 도구 선택이 아니라 클러스터 생성 자체가 재현 가능한 절차여야 한다는 것 — 1장의 "선언형으로, Git에" 원칙이 이제 클러스터 단위로 올라간다.

12.4배포와 관리 패턴

쿠버네티스 오퍼레이터 (Operator)는 IaS (Infrastructure as Software)의 구현체로 볼 수 있다 — 사람이 반복하던 운영 절차(백업, 장애 복구, 버전 업그레이드)를 소프트웨어가 대신 수행하도록 클러스터 수준에서 추상화한 것이다. 멀티클러스터에서는 이 자동화의 가치가 배가된다 — 프로메테우스 오퍼레이터, 일래스틱서치 오퍼레이터처럼 반복되는 운영 작업을 클러스터마다 사람이 다시 하지 않게 만든다(오퍼레이터를 직접 만드는 법은 21장에서 다룬다).

12.5깃옵스로 클러스터를 관리하는 방식

깃옵스 (GitOps)는 위브웍스(Weaveworks)가 프로덕션에서 쿠버네티스를 운영한 경험에서 만든 용어다 — 소프트웨어 개발 생명주기의 개념(버전 관리, 리뷰, 자동화된 적용)을 운영 그 자체에 적용한 것이다. Git 리포지터리가 "지금 클러스터가 어떤 상태여야 하는가"의 단일 진실 공급원이 되고, 클러스터는 그 상태에 스스로를 맞춘다.

18장 예고 — 깃옵스의 구체적인 구현(플럭스 설치, 리포지터리 구조, 시크릿 관리)은 18장에서 손으로 실습한다. 여기서는 "왜 멀티클러스터 관리에 특히 유용한가"만 짚는다 — 클러스터가 늘수록 사람이 각 클러스터에 개별적으로 kubectl apply하는 방식은 감당이 안 되는데, 깃옵스는 "Git에 반영되면 모든 클러스터가 알아서 따라온다"로 이 문제를 근본적으로 없앤다.

12.6멀티클러스터 관리 툴

클러스터가 여러 개면 kubectl의 컨텍스트 전환부터 헷갈리기 시작한다 — 지금 내가 어느 클러스터에 명령을 보내고 있는지 매번 확인해야 한다(0장에서 이미 경고한 그 실수). kubectx·kubens는 컨텍스트와 네임스페이스를 빠르게 전환하는 CLI 도구로, 이 전환을 훨씬 덜 위험하게 만든다. 더 큰 규모에서는 Rancher처럼 여러 클러스터를 하나의 UI로 통합 관리하는 플랫폼을 쓰기도 한다.

12.7쿠버네티스 페더레이션

페더레이션 (Federation)은 "여러 클러스터에 하나의 애플리케이션 정의를 뿌린다"는 발상이다. Federation v1은 쿠버네티스 1.3에서 처음 나왔지만 코어 API에 지나치게 결합된 모놀리식 구조라 심각한 설계 문제에 부딪혔다 — 애초에 CRD가 없던 시절이라 다른 선택지가 없었다. 그 후속인 Federation v2(KubeFed)도 이미 사용 중단됐다.

2026-08 기준 갱신 주석 원서가 쓰인 시점엔 "페더레이션은 죽었고 후속이 불투명하다"는 서술로 끝났지만, 지금은 두 CNCF 프로젝트가 그 자리를 잇고 있다. Karmada(화웨이 클라우드 주도, CNCF)는 Federation v1·v2의 정신적 후속작을 표방하며 PropagationPolicy·OverridePolicy 같은 쿠버네티스 네이티브 CRD로 멀티클러스터 배포·장애 조치·트래픽 스케줄링을 제공한다. OCM (Open Cluster Management)(레드햇 주도, CNCF)도 같은 문제를 다른 API 설계로 접근한다. 둘 다 v1이 실패한 이유(코어 API 강결합)를 정확히 피해, 처음부터 CRD 기반 확장 가능한 구조로 설계됐다는 공통점이 있다 — 멀티클러스터 배포 자동화가 필요하다면 이제 이 둘이 출발점이다. 출처: karmada.io(공식 문서, CNCF Incubating) · cncf.io 블로그(Karmada·OCM 소개, Federation v1/v2 EOL 배경)
