CHAPTER 00

로컬 실습 환경 구축 — macOS

1장을 따라 하려면 명령을 칠 클러스터가 먼저 있어야 한다. 맥 한 대에 쿠버네티스를 띄우고, 첫 애플리케이션을 배포·접속·확장·삭제하는 데까지 약 30분. 이 문서를 끝내면 1장의 모든 명령을 그대로 실행할 수 있다.

2026-08 기준 도구 선택 · 명령 검증 완료

핵심 3줄

1. 설치는 세 층이다: Homebrew → 컨테이너 런타임(OrbStack 권장) → kubectl + kind + helm.

2. 클러스터는 kind create cluster 한 줄이면 뜬다 — 노드조차 도커 컨테이너라서 만들고 부수는 비용이 거의 없다.

3. 첫 배포 루프(배포 → 확인 → 접속 → 확장 → 자가 복구 관찰 → 정리)를 손으로 한 번 돌리면 1장이 글이 아니라 경험이 된다.

0.1도구 선택 — 무엇을 왜 쓰나 0.2설치 (10분) 0.3클러스터 생성과 구조 이해 0.4첫 배포 — 15분 실습 루프 0.51장 실습 연결 — 인그레스 준비 (선택) 0.6자주 막히는 지점 0.7정리와 초기화

0.1도구 선택 — 무엇을 왜 쓰나

쿠버네티스를 맥에서 돌리려면 두 가지 결정이 필요하다. 컨테이너를 실행할 런타임, 그리고 그 위에 클러스터를 만들 도구.

먼저 컨테이너 런타임 (Container Runtime) — 컨테이너 이미지를 받아 실제 프로세스로 실행하는 소프트웨어다. 맥에서는 리눅스 컨테이너를 직접 못 돌리므로 모든 선택지가 내부적으로 경량 리눅스 VM을 쓴다.

런타임특징이런 경우
OrbStack (스터디 권장)맥 전용. 시작 2초 수준, 유휴 메모리·배터리 소모가 Docker Desktop 대비 크게 낮음. docker CLI 완전 호환개인 맥에서 실습. 개인 사용 무료
Docker Desktop공식 제품, 크로스 플랫폼, 내장 쿠버네티스 포함회사 표준이 이미 이것일 때. 직원 250인 이상 또는 연매출 $10M 이상 기업은 유료 구독 필요
ColimaCLI 전용, 오픈소스 무료GUI가 싫고 전부 무료여야 할 때

클러스터 도구는 스터디 표준으로 kind (Kubernetes IN Docker)를 쓴다 — 도커 컨테이너 하나하나를 쿠버네티스 노드로 사용해 로컬 클러스터를 만드는 공식 SIG 도구다. 원래 쿠버네티스 자체를 테스트하려고 만들어져 가볍고, 멀티 노드 구성이 설정 파일 몇 줄이며, 만들고 지우는 데 1~2분이면 된다. 대안인 minikube(애드온 풍부), OrbStack/Docker Desktop 내장 쿠버네티스(클릭 한 번, 단일 노드 고정)도 1장 실습에는 문제없지만, 노드 여러 개를 다루는 8장(스케줄링) 이후를 생각하면 kind로 통일하는 편이 스터디 운영에 유리하다.

0.2설치 (10분)

맥 패키지 관리자인 Homebrew가 없다면 그것부터. 터미널을 열고 순서대로 실행한다.

# 1) Homebrew (이미 있으면 건너뛴다)
/bin/bash -c "$(curl -fsSL https://raw.githubusercontent.com/Homebrew/install/HEAD/install.sh)"

# 2) 컨테이너 런타임 — 하나만 선택
brew install --cask orbstack        # 권장
# brew install --cask docker        # Docker Desktop을 쓸 경우

# 3) 쿠버네티스 도구 3종
brew install kubectl kind helm

설치 후 OrbStack(또는 Docker Desktop) 앱을 한 번 실행해 둔다 — 런타임이 떠 있어야 kind가 노드 컨테이너를 만들 수 있다. 확인:

docker version          # Server 정보까지 나오면 런타임 정상
kubectl version --client
kind version
helm version
체크포인트docker version에서 Server 섹션이 보이고, 나머지 세 명령이 버전을 출력하면 통과.
2026-08 기준 주석 brew install helm은 이제 Helm 4를 설치한다(2025-11-12 출시). 1장 이후의 헬름 실습 명령은 그대로 동작하며, Helm 3 차트 대부분과 호환된다. 출처: helm.sh/blog/helm-4-released · formulae.brew.sh/formula/kind (brew install kind)

0.3클러스터 생성과 구조 이해

노드 3개짜리 클러스터를 만든다. 노드 (Node)는 파드가 실제로 실행되는 워커 머신인데, kind에서는 이 노드가 물리 서버가 아니라 도커 컨테이너 하나다. 아래 설정 파일을 kind-config.yaml로 저장한다.

# kind-config.yaml — control-plane 1 + worker 2
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
nodes:
- role: control-plane
- role: worker
- role: worker
kind create cluster --name study --config kind-config.yaml

# 생성 확인
kubectl cluster-info --context kind-study
kubectl get nodes

get nodes에 노드 3개가 Ready로 보이면 성공이다. 여기서 컨텍스트 (Context) 개념 하나만 짚자 — kubectl이 "어느 클러스터에, 어떤 사용자로" 명령을 보낼지 정하는 접속 프로필로, ~/.kube/config(kubeconfig) 파일에 저장된다. kind가 클러스터를 만들면 kind-study 컨텍스트를 자동 등록하고 현재 컨텍스트로 전환해 준다. 회사 클러스터를 함께 쓰는 사람은 kubectl config get-contexts로 현재 대상을 반드시 확인하는 습관을 들이자 — 엉뚱한 클러스터에 명령을 쏘는 사고의 90%가 여기서 난다.

0.4첫 배포 — 15분 실습 루프

1장에서 상세히 배울 세 리소스를 몸으로 먼저 만난다. 파드 (Pod)는 컨테이너를 묶어 실행하는 최소 단위, 디플로이먼트 (Deployment)는 동일한 파드 복제본 개수를 유지·교체해 주는 컨트롤러, 서비스 (Service)는 계속 바뀌는 파드들 앞의 고정된 이름과 IP다. 정의는 여기까지 — 지금은 손이 먼저다.

① 배포하고 확인한다

kubectl create deployment hello --image=nginx:1.27 --replicas=2
kubectl get pods -o wide

-o wide로 보면 파드 2개가 서로 다른 worker 노드에 흩어져 뜬 것까지 보인다. STATUS가 Running이 될 때까지 몇 초 걸릴 수 있다.

② 서비스로 묶고 접속한다

kubectl expose deployment hello --port=80
kubectl port-forward service/hello 8080:80

새 터미널에서 curl http://localhost:8080 — nginx 환영 페이지 HTML이 나오면 성공. 방금 쓴 포트 포워딩 (Port Forwarding)은 내 맥의 포트를 클러스터 안 서비스/파드 포트로 잇는 임시 터널이다. 외부 노출 설정 없이 개발 중 접속 확인에 쓰는 표준 수단이고, 터미널을 끄면(Ctrl+C) 터널도 사라진다.

③ 확장하고, 죽여보고, 되살아나는 걸 본다

# 2개 → 4개로 확장
kubectl scale deployment hello --replicas=4
kubectl get pods

# 파드 하나를 일부러 삭제 (이름은 get pods 출력에서 복사)
kubectl delete pod <파드이름>
kubectl get pods -w        # -w: 변화를 실시간 관찰, Ctrl+C로 종료

삭제하자마자 새 파드가 자동으로 생겨나는 것이 보인다. 이것이 1장 그림 1-1에서 말하는 조정 루프다 — 우리는 "replicas: 4"라는 원하는 상태만 선언했고, 실제 상태가 3이 되는 순간 컨트롤러가 되돌렸다. 이 15분이 쿠버네티스 전체의 핵심 아이디어다.

체크포인트curl 응답 수신 + 파드 삭제 후 자동 재생성 관찰. 둘 다 됐다면 1장을 시작할 준비 완료.

0.51장 실습 연결 — 인그레스 준비 (선택)

1장 1.4절·1.9절의 인그레스 실습까지 로컬에서 하려면 인그레스 컨트롤러가 필요하다. CNCF에서 유지보수 중인 Contour(Envoy 기반)를 설치한다 — 표준 Ingress 리소스를 그대로 지원해 1장 YAML을 수정 없이 쓸 수 있다.

# Contour + Envoy 설치
kubectl apply -f https://projectcontour.io/quickstart/contour.yaml
kubectl get pods -n projectcontour        # 모두 Running/Completed까지 대기

# 로컬 접속용 터널 (인그레스가 받는 80 포트를 내 맥 8888로)
kubectl -n projectcontour port-forward service/envoy 8888:80

이후 1장에서 인그레스 리소스를 만들면 curl http://localhost:8888/api처럼 경로 라우팅을 확인할 수 있다. 이 단계는 1장 진도에 맞춰 그때 해도 된다.

2026-08 기준 주석 검색하면 아직도 상위에 나오는 ingress-nginx 설치 가이드는 따라 하지 말 것. 해당 프로젝트는 2026년 3월부로 은퇴해 보안 패치가 중단됐다. 로컬 실습이라도 지금 배우는 도구는 유지보수되는 것으로 — Contour, Traefik, Envoy Gateway 등이 대안이다. 출처: kubernetes.io/blog/2026/01/29/ingress-nginx-statement · projectcontour.io/getting-started (설치·port-forward 명령 원 출처)

0.6자주 막히는 지점

증상원인과 해법
Cannot connect to the Docker daemon런타임이 안 떠 있다. OrbStack/Docker Desktop 앱을 실행하고 docker version으로 재확인.
kind create cluster가 이미지 pull에서 멈춤노드 이미지(kindest/node, 수백 MB) 첫 다운로드 중. 네트워크 문제면 잠시 후 kind delete cluster --name study 후 재시도.
kubectl이 엉뚱한 클러스터를 바라봄kubectl config get-contexts로 확인 후 kubectl config use-context kind-study.
port-forward가 address already in use로컬 8080을 다른 프로세스가 사용 중. kubectl port-forward service/hello 9090:80처럼 다른 포트로.
파드가 ImagePullBackOff이미지 이름·태그 오타가 대부분. kubectl describe pod <이름>의 Events에 정확한 원인이 찍힌다. Apple Silicon에서 arm64 미지원 이미지일 때도 발생 — nginx 등 공식 이미지는 멀티 아키텍처라 문제없다.
맥 재부팅 후 클러스터가 안 보임런타임 앱이 아직 안 뜬 것. 앱 실행 후 1분 내 노드 컨테이너가 자동 복귀한다. 그래도 안 되면 지우고 새로 만드는 게 빠르다 — kind 클러스터는 소모품이다.

0.7정리와 초기화

# 실습 리소스만 정리
kubectl delete service hello
kubectl delete deployment hello

# 클러스터 통째로 삭제 (다음 스터디 때 다시 만들면 된다)
kind delete cluster --name study

# 디스크 정리 (선택): 안 쓰는 이미지·컨테이너 제거
docker system prune -a

클러스터를 아끼지 말 것. 꼬였다 싶으면 지우고 새로 만드는 데 2분이다 — 이 부담 없음이 로컬 kind로 실습하는 가장 큰 이유다.
