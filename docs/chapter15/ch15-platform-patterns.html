CHAPTER 15

고수준 애플리케이션 패턴 구축

지금까지는 쿠버네티스를 직접 쓰는 법을 배웠다. 이 장은 한 겹 위에서 — 조직 안의 다른 개발자들이 쿠버네티스를 (또는 쿠버네티스인 줄도 모르고) 쉽게 쓰게 만드는 법이다. 원서가 원리로 설명한 이 내용은, 2026년 현재 "플랫폼 엔지니어링"이라는 이름의 독립된 분야로 자리 잡았다.

2026-08 기준 변경 사항 주석 포함 · 이 장의 개념과 2026년 실제 도구 생태계를 연결했습니다

핵심 3줄

1. 고수준 추상화는 두 전략 중 하나다 — 쿠버네티스를 완전히 감추는 래핑, 또는 CRD로 API 자체를 넓히는 확장. 유저가 "유리를 깨고 탈출"할 필요가 있는지가 기준이다.

2. 확장의 접점은 셋이다 — 사이드카(파드 옆에 붙임), 어드미션 컨트롤러(제출 순간 가로챔), CRD(아예 새 어휘를 만듦).

3. 이 장 전체가 그리는 청사진은 지금 Backstage(CNCF)라는 이름의 실제 오픈소스로 존재한다 — 직접 다 짓지 않아도 되는 시대가 됐다.

15.1고수준 추상화 개발 방식

쿠버네티스 위에 더 높은 수준의 프리미티브를 만드는 방법은 두 가지다.

판단 기준은 명확하다 — 유저가 절대 "유리를 깨고 탈출"할 필요가 없다는 확신이 든다면 래핑이 낫다(머신러닝 파이프라인처럼, 유저의 전문성이 쿠버네티스가 아닌 다른 곳에 있을 때). 애플리케이션 개발처럼 요구가 끝없이 다양해지는 영역이라면 확장이 낫다 — 쿠버네티스의 기존 툴 생태계(모니터링, CD 등)를 그대로 재사용할 수 있고, 나중에 새 툴이 나와도 자동으로 호환되며, 쿠버네티스 경험자 채용도 상대적으로 쉽다.

15.2쿠버네티스 확장

추상화 레이어는 저마다 고유해 일반화하기 어렵지만, 확장에 쓰이는 기술 자체는 공통적이다.

15.2.1 쿠버네티스 클러스터 확장

쿠버네티스 리소스가 맞물리는 접점은 대략 셋이다.

  • 사이드카 — 메인 컨테이너 옆에 부가 기능을 붙인다. mTLS 같은 서비스 메시 기능이 전형적이다. CNCF 프로젝트 Dapr (Distributed Application Runtime)은 암호화·키값 저장소·펍섭 큐 같은 기능을 일관된 API의 사이드카로 만들어 주는 좋은 예다.
  • 어드미션 컨트롤러 (Admission Controller) — API 서버에 제출된 오브젝트가 저장되기 전에 가로채는 인터셉터(11장에서 이미 깊이 다뤘다). 사이드카를 자동으로 주입하거나, 리소스 요청이 빠진 파드를 거부하는 린터 역할도 할 수 있다 — 개발자는 이런 장치가 있는지조차 몰라도 된다.
  • CRD + 제어 루프 — 아예 새로운 리소스 타입을 클러스터에 추가한다. 예컨대 ReplicatedService라는 리소스를 만들면, 그 인스턴스 하나로 Deployment와 Service가 자동 생성되게 할 수 있다 — 공통 패턴을 개발자가 한 줄로 쓸 수 있게 압축한 것이다.

15.2.2 쿠버네티스 UX 확장

새 리소스를 추가하는 것만으로는 부족하다 — 쿠버네티스 툴은 커스텀 리소스를 아주 제네릭하게만 다뤄 사용자 친화적이지 않다. kubectl-foo 형식으로 만드는 kubectl 플러그인은 kubectl foo로 호출되며, 새 리소스를 위한 전용 UX를 자유롭게 구현하면서도 개발자에게 익숙한 도구를 그대로 쓰게 해 준다. 그래픽 인터페이스가 필요하다면 오픈소스 프로젝트 Headlamp가 웹·데스크톱 대시보드를 빠르게 만드는 라이브러리를 제공한다.

15.2.3 컨테이너화 개발 간소화

쿠버네티스에 배포하려면 먼저 컨테이너화해야 한다 — 클라우드 네이티브에 익숙한 개발자에겐 당연하지만, 모두가 그렇지는 않다. 빌드팩 (Buildpacks) 같은 도구는 Dockerfile을 직접 쓰지 않아도 소스 코드를 분석해 컨테이너 이미지를 자동으로 만들어 준다.

15.2.4 '푸시-투-디플로이' 환경 구축

많은 PaaS의 핵심 기능이다 — Git에 코드를 한 번 푸시하면 알아서 배포까지 끝난다. 과거엔 대형 관리형 PaaS만 갖던 기능이지만, 지금은 GitHub Actions 같은 CI/CD와 5장에서 배운 깃옵스를 조합하면 직접 구축할 수 있다. 파이프라인이 테스트·빌드·이미지 패키징·레지스트리 푸시를 자동화하고, 그 새 이미지를 깃옵스가 감지해 실제 배포까지 이어간다.

15.3플랫폼 구축 시 설계 고려 사항

수많은 플랫폼의 성공·실패 사례에서 공통된 패턴이 보인다. 언젠가 버려질 레거시가 아니라 오래 살아남는 플랫폼을 만들기 위한 지침이다.

15.3.1 컨테이너 이미지로 익스포트하는 기능 지원

유저가 완전한 컨테이너 이미지 대신 단순 코드(FaaS 함수)나 네이티브 패키지(JAR 파일)만 건네는 방식으로 플랫폼을 단순화하는 경우가 많다. 유저에게 익숙한 도구를 그대로 쓰게 해 주는 매력이 있지만, 함정이 있다 — 특정 언어 런타임 버전이 필요하거나 자동 컨테이너화 범위 밖의 리소스를 패키징해야 할 때, 플랫폼이 제공한 환경의 한계에 부딪힌다. 이럴 때를 대비해 완전한 컨테이너 이미지를 직접 제출하는 탈출구를 항상 열어 둬야 한다 — 15.1절의 판단 기준이 여기서 다시 등장한다.

15.3.2 기존 서비스와 서비스 디스커버리 메커니즘 지원

플랫폼은 진화하며 다른 시스템과 계속 연결된다. 개발자가 플랫폼 안에서는 만족스럽게 일해도, 실제 애플리케이션은 플랫폼 밖의 기존 서비스(레거시 DB 등, 13장에서 다룬 그것)에 의존하기 마련이다. 플랫폼이 이런 외부 연결을 처음부터 배제하면, 결국 예외 처리투성이가 되거나 아예 버려진다.

2026-08 기준 갱신 주석 — 이 장이 예견한 미래 원서는 "플랫폼 엔지니어링"이라는 이름을 쓰지 않지만, 이 장 전체가 정확히 그 분야의 청사진이다. 2026년 현재 이 분야는 독립된 직군·컨퍼런스·모범 사례를 가진 성숙한 규율이 됐다 — Gartner는 플랫폼팀을 운영하는 대규모 조직 비율이 2022년 45%에서 2026년 80%까지 늘 것으로 전망했다. 그 사실상 표준 구현체가 Backstage다 — 스포티파이가 만들어 2022년 CNCF에 기증한 오픈소스로, 15.2.2절의 UX 확장은 소프트웨어 카탈로그로, 15.2.4절의 푸시-투-디플로이는 스캐폴더(Golden Path 템플릿)로, 15.3.2절의 외부 연동은 수백 종에 달하는 플러그인 생태계로 각각 구현되어 있다. CRD 기반 확장(15.1·15.2.1)을 실제로 손쉽게 만들어 주는 도구로는 Crossplane이 널리 쓰인다 — 클라우드 인프라 자체를 쿠버네티스 CRD로 추상화한다. 이 장을 원리로 이해했다면, Backstage 같은 도구의 내부에서 정확히 무슨 일이 벌어지는지 이미 알고 있는 셈이다. 출처: CNCF 공식 발표(Backstage 다큐멘터리, 2026-03) · Gartner 전망 인용 업계 자료 다수(2026) 교차 확인
