CHAPTER 14

쿠버네티스에서 머신러닝 실행하기

머신러닝 워크로드는 쿠버네티스가 가진 거의 모든 기능을 동시에, 그것도 가장 극단적인 강도로 요구한다 — 스케줄링, 특수 하드웨어, 스토리지, 네트워킹. 이 장은 그 요구를 원서가 쓰인 2024년의 "훈련 중심" 세계에서 출발해, 2026년 현재의 인프라 지형(특히 GPU 스케줄링의 근본적 전환)까지 잇는다.

2026-08 기준 변경 사항 주석 포함 · 이 장은 원서 대비 변화 폭이 가장 큰 장 중 하나입니다

핵심 3줄

1. ML 워크플로는 데이터셋 준비 → 모델 개발 → 훈련 → 제공(서빙) 4단계다 — 원서는 훈련에 집중하지만, 2026년 실무 비중은 서빙 쪽으로 크게 이동했다.

2. GPU를 "정수 개수"로 요청하던 디바이스 플러그인 모델은 저물고 있다 — 2026년 현재는 속성 기반으로 정확히 매칭하는 DRA가 표준(GA)이다.

3. 분산 훈련 하나가 스케줄링(8장)·네트워킹(9장)·스토리지(16장)를 동시에 극한으로 요구한다 — 이 장은 사실상 지금까지 배운 것들의 "가장 가혹한 시험대"다.

14.1머신러닝에 쿠버네티스를 사용하면 좋은 점 14.2머신러닝 워크플로 14.3클러스터 관리자가 고려해야 할 사항 14.4데이터 과학자의 관심사 14.5쿠버네티스 머신러닝 모범 사례

14.1머신러닝에 쿠버네티스를 사용하면 좋은 점

쿠버네티스가 이미 잘하는 것들 — 리소스 추상화, 스케줄링, 확장성, 이식성 — 은 머신러닝 워크로드에도 그대로 이득이 된다. 온프레미스든 클라우드든 같은 매니페스트로 훈련 잡을 굴릴 수 있고, GPU 같은 특수 자원도 CPU·메모리와 같은 방식(요청·제한)으로 다룰 수 있다는 것이 핵심 매력이다.

14.2머신러닝 워크플로

딥러닝의 요구사항을 이해하려면 먼저 전체 워크플로를 알아야 한다. 크게 네 단계다.

  • ① 데이터셋 준비 — 스토리지, 인덱싱, 카탈로그화. 수백 MB부터 PB 단위까지 다양해, 규모에 맞는 블록·오브젝트 저장소가 필요하다.
  • ② 모델 개발 — 데이터 과학자가 알고리즘을 설계·공유하는 단계. JupyterHub 같은 툴이 다른 워크로드와 비슷하게 동작해 쿠버네티스에 쉽게 올라간다.
  • ③ 훈련 — 데이터셋으로 모델을 학습시킨다. 스케줄링·특수 하드웨어·스토리지·네트워킹을 전부 동시에 요구하는, 쿠버네티스의 모든 기능을 시험하는 단계다.
  • ④ 제공(서빙) — 훈련된 모델이 클라이언트의 요청에 추론으로 응답하는 단계.
2026-08 기준 갱신 주석 — 무게중심 이동 원서의 4단계 워크플로 자체는 지금도 정확하다. 다만 뒤이은 14.3절은 8개 하위 절 전부를 훈련에 쓰고, 서빙은 워크플로 도입부에서 한 번 언급된 뒤 다시 등장하지 않는다. 2026년 현재는 정반대다 — LLM 추론 서빙이 폭발적으로 늘며, "머신러닝을 쿠버네티스에서 돌린다"는 말의 실무적 의미가 상당 부분 서빙 인프라 운영으로 옮겨갔다. vLLM 같은 추론 엔진, KServe 같은 서빙 전용 플랫폼, 9장에서 다룬 Gateway API Inference Extension(추론 트래픽에 특화된 라우팅)이 이 새 영역의 표준 도구로 떠올랐다. 이 장의 나머지(14.3)는 원서 그대로 훈련에 집중하되, 서빙은 별도로 학습할 영역임을 여기서 짚어 둔다. 출처: 9장 갱신 주석(Gateway API 확장) 참고 · 업계 동향 자료 다수(2026) 교차 확인

14.3쿠버네티스 클러스터 관리자가 고려해야 할 사항

데이터 과학자 팀을 지원하는 클러스터 관리자가 마주치는 가장 큰 어려움은, 훈련이라는 워크로드가 평소 다루던 웹 서비스와 근본적으로 다른 자원 패턴을 요구한다는 것이다.

14.3.1 모델 훈련

훈련에는 CPU·GPU가 필요하고, 리소스를 더 투입할수록 더 빨리 끝난다. 대부분의 훈련은 필요한 자원이 갖춰진 단일 머신에서 수행된다 — 분산 훈련(다음 절)은 그 자체로 별도의 난이도를 갖는다.

14.3.2 분산 훈련

여러 머신에 훈련을 분산하는 것은 원서 집필 시점 기준 "아직 걸음마 단계"였다 — GPU 8개가 필요하다면, 4개짜리 서버 2대보다 8개짜리 서버 1대가 거의 항상 빠르다. 여러 머신에 걸치는 순간 네트워크가 병목이 되기 쉽기 때문이다(14.3.7).

14.3.3 리소스 제약조건

머신러닝 워크로드는 클러스터 전반에 걸쳐 특정한 구성을 요구한다. 자원 소모는 주로 훈련 단계에 집중되며, 훈련은 대부분 배치성 워크로드다 — 8장의 오토스케일링 논의가 여기서 직접 적용된다.

14.3.4 특수 하드웨어

모델 훈련은 GPU 같은 특수 하드웨어에서 압도적으로 효율적이다. 쿠버네티스는 전통적으로 디바이스 플러그인 (Device Plugin)을 통해 이런 자원에 접근했다 — 파드가 nvidia.com/gpu: 1처럼 정수 개수로 요청하면 스케줄러가 남은 개수만 보고 배치하는 단순한 모델이다.

2026-08 기준 갱신 주석 — GPU 스케줄링의 세대교체 디바이스 플러그인 모델은 2017년부터 거의 그대로였다 — nvidia.com/gpu: 1은 "GPU 하나"라고만 말할 뿐, 어떤 모델인지 메모리가 얼마인지 토폴로지가 어떤지는 스케줄러가 전혀 몰랐다. 실무에서는 이를 노드 레이블과 테인트/톨러레이션(14.5절)으로 우회해 왔다. 이 한계가 근본적으로 해소된 것이 DRA (Dynamic Resource Allocation)다 — resource.k8s.io API 그룹으로, 워크로드가 ResourceClaim에 필요한 장비 속성(예: "메모리 80GB 이상")을 CEL 표현식으로 선언하면, 드라이버가 ResourceSlice로 공개한 실제 노드별 장비 속성과 스케줄러가 직접 매칭한다. 쿠버네티스 1.34에서 GA, 1.35부터는 기능 게이트가 기본 활성으로 고정됐다. NVIDIA가 자사 DRA 드라이버를 CNCF에 기증했고, 갱 스케줄링·큐잉을 더한 KAI 스케줄러가 AI 워크로드 참조 구현으로 떠올랐다. PV/PVC가 스토리지에 해 준 일을, DRA는 GPU 같은 가속기에 대해 해 준다고 이해하면 된다. 출처: kubernetes.io/blog(DRA GA 발표) · CNCF 블로그(DRA 이해하기, 2026) · Google Cloud 블로그(DRA GA 안정화 설명)

14.3.5 라이브러리, 드라이버, 커널 모듈

특수 하드웨어에 접근하려면 전용 라이브러리·드라이버·커널 모듈이 필요하고, 컨테이너 안에서 이를 쓰려면 컨테이너 런타임에 마운트되어 있어야 한다 — "그냥 컨테이너 안에 다 넣으면 되지 않나?" 싶겠지만, 호스트 커널과 버전이 어긋나면 동작하지 않는다.

14.3.6 스토리지

머신러닝 워크플로에서 가장 중요한 요소로 꼽힌다 — 훈련 중 데이터셋을 워커 노드 전체에 배포하는 문제, 체크포인트 저장·복구 문제 모두 스토리지 설계에 달려 있다.

14.3.7 네트워킹

분산 훈련일수록 네트워크가 성패를 가른다 — 파라미터 서버 아키텍처에서는 각 노드가 파라미터 서버와 끊임없이 가중치를 주고받는다. 노드 간 대역폭·지연이 곧 훈련 속도다.

14.3.8 전용 프로토콜

벤더마다 다르지만, 목표는 같다 — 분산 훈련의 병목이 되는 통신 구간을 최대한 제거하는 것. NCCL(GPU 간 집합 통신), RDMA(CPU를 거치지 않는 원격 메모리 접근) 같은 프로토콜이 이 역할을 한다.

14.4데이터 과학자의 관심사

지금까지는 클러스터 관리자의 시점이었다. 쿠버네티스 비전문가인 데이터 과학자가 쓰기 편하게 만들어 주는 도구들도 있다.

  • Kubeflow — 쿠버네티스 네이티브 머신러닝 툴킷. JupyterHub, 파이프라인, 훈련용 커스텀 컨트롤러를 포함한다.
  • Polyaxon — 여러 프레임워크를 지원하는 워크플로 관리 툴. 오픈소스·상용 버전이 있다.
  • Pachyderm — 데이터셋 준비·버저닝·파이프라인에 특화된 엔터프라이즈 플랫폼.
2026-08 기준 갱신 주석 Kubeflow는 그동안 프로젝트로서 한층 성숙했고, 그 생태계 안에서 KServe가 서빙 전용 서브프로젝트로 독립적인 위상을 가지게 됐다 — 14.2절 갱신 주석에서 언급한 서빙 무게중심 이동의 실제 수혜자다. 분산 컴퓨팅 프레임워크 Ray도 쿠버네티스 위에서(KubeRay 오퍼레이터로) 훈련·서빙 양쪽에 널리 쓰이는 선택지로 자리잡았다. Polyaxon·Pachyderm은 여전히 존재하지만, 신규 구축에서는 Kubeflow·KServe·Ray 조합이 훨씬 자주 언급된다.
