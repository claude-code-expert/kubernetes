CHAPTER 21 · 마지막 장

오퍼레이터 구현

12장·15장·16장·19장에서 오퍼레이터를 "누군가 만들어 둔 것을 쓰는 입장"으로 계속 언급했다. 이 장은 입장을 바꾼다 — 직접 만드는 법이다. CRD로 새 API를 정의하고, 컨트롤러로 그 API가 실제 의미를 갖게 만드는 것. 21개 장을 관통한 "선언하면 클러스터가 알아서 맞춘다"는 1장의 원칙이, 여기서는 여러분이 그 "알아서"를 직접 코드로 짜는 입장이 된다.

2026-08 기준 확인 — kubebuilder·controller-runtime은 2026년 현재도 활발히 개발되는 현행 표준입니다

핵심 3줄

1. 오퍼레이터는 CRD(새 API)와 컨트롤러(그 API를 실행 상태로 조정하는 로직) 두 컴포넌트로 이뤄진다 — kubebuilder가 둘 다의 상용구 코드를 대신 만들어 준다.

2. 컨트롤러의 심장은 Reconcile 메서드다 — 무엇이 바뀌었는지 따지지 않고, 이벤트가 있을 때마다 처음부터 전체 상태를 다시 확인한다(레벨 기반 트리거링).

3. 오퍼레이터는 무거운 도구다 — 헬름·쿠스토마이즈·테라폼으로 충분하다면 굳이 쓰지 않는다. "배포 이후에도 계속 판단하고 행동해야 하는가"가 판단 기준이다.

21.1오퍼레이터 핵심 컴포넌트

오퍼레이터 프레임워크 (Operator Framework)는 SDK·라이프사이클 관리·퍼블리싱 도구를 갖춘 오픈소스 툴킷이다(16장에서 이미 CoreOS 기원을 다뤘다). 쿠버네티스 API 머시너리 SIG가 kubebuilder 개발을 후원했고, 구글의 지원을 받으며 오퍼레이터의 2대 컴포넌트 — CRD와 컨트롤러 — 를 다루는 베이스 SDK로 자리 잡았다. 이 장의 예제도 kubebuilder 구문이지만, 근본 개념은 다른 오퍼레이터 SDK와 크게 다르지 않다.

2026-08 기준 확인kubebuilder와 그 기반 라이브러리인 controller-runtime은 2026년 현재도 kubernetes-sigs 조직에서 활발히 커밋되는 현행 프로젝트다. 이 장에서 배우는 접근법은 지금 그대로 써도 되는 표준이다.

21.2커스텀 리소스 정의

복잡한 애플리케이션의 요건을 네이티브 리소스만으로 표현하려면 Job·initContainer가 뒤섞인 거대한 YAML 템플릿이 필요해진다. CRD (CustomResourceDefinition)는 쿠버네티스 API 자체를 확장해, 그 요건을 선언형으로 더 잘 표현하는 새 리소스 타입을 만든다. 내장 리소스와 달리 독립적으로 관리·갱신할 수 있고, spec.scope로 네임스페이스 범위인지 클러스터 범위인지 정한다.

21.2.1 쿠버네티스 API 오브젝트, 리소스, 버전, 그룹 및 카인드

다섯 용어를 정리한다. 오브젝트는 클러스터 상태를 나타내는 실제 엔티티(파드 하나 같은 것), 리소스는 같은 카인드의 오브젝트 컬렉션을 가리키는 API 엔드포인트, 버전은 API의 안정성 단계(v1alpha1 → v1beta1 → v1), 그룹은 관련 리소스를 묶는 API 네임스페이스, 카인드는 오브젝트의 타입 이름(Pod, Deployment처럼)이다.

21.3API 생성

CRD는 YAML로 직접 쓸 수도 있지만, kubebuilder 같은 SDK로 자동 생성하는 편이 훨씬 간편하다.

# 프로젝트 초기화
kubebuilder init --domain example.com --repo github.com/myorg/my-operator

# API(CRD + 컨트롤러 뼈대) 생성
kubebuilder create api --group platform --version v1alpha1 --kind ReplicatedService

이 한 줄로 CRD YAML, Go 타입 정의, 컨트롤러 파일(controllers/<kind>_controller.go)의 뼈대가 한 번에 만들어진다.

21.4컨트롤러 조정

컨트롤러 코드는 API 생성 시점에 함께 만들어지고, 필요한 상용구는 대부분 이미 채워져 있다. 오퍼레이터를 이해하려면 코드 자체보다 백그라운드에서 벌어지는 일에 주목해야 한다.

오퍼레이터는 관심 있는 리소스 타입의 이벤트를 계속 감시하는 서비스다. 조건에 맞는 이벤트가 발생하면 Reconcile 메서드가 실행되어 의도한 상태를 실행 중인 상태로 조정한다. 무엇이 정확히 바뀌었는지는 상관없다 — 매번 전체를 처음부터 다시 확인한다. 이를 레벨 기반 트리거링 (Level-based Triggering)이라 한다. 효율적이진 않지만, 쿠버네티스 같은 복잡한 분산 시스템에는 오히려 이 단순함이 잘 맞는다.

CR이 소유하지 않은 외부 리소스(클라우드 리소스, PV 등)를 다룬다면 파이널라이저 (Finalizer)를 구현해야 한다 — 정리 로직이 끝날 때까지 CR이 실제로 삭제되지 않도록 막는 장치다. 16장에서 다룬 PV의 회수 정책과 같은 이유다 — "삭제됐다"고 표시하기 전에 반드시 지켜야 할 뒷정리가 있다.

21.5리소스 검사

요청된 리소스가 유효한지 검사하는 것은 오퍼레이터 설계의 핵심이다. 일관된 동작을 위해 중복된(redundant) 검증 계층을 갖춰야 한다.

첫 번째 계층은 CRD spec에 정의하는 OpenAPI 스키마 검증이다 — 형식이 틀린 리소스가 애초에 etcd에 닿지 못하게 막는다. 두 번째 계층은 스키마로 표현 못 하는 복잡한 규칙을 검사하는 검증 어드미션 웹훅 (Validating Admission Webhook)이다 — 17장에서 다룬 바로 그 웹훅이다. 조정 루프 안에도 검사를 넣을 수는 있지만, 그건 이미 클러스터에 들어온 리소스에 대한 뒤늦은 검증이다 — 가능한 한 앞단에서 막는 것이 항상 낫다.

21.6컨트롤러 구현

지금까지 설명한 개념이 실제 코드에서 어떻게 나타나는지 뼈대만 본다. kubebuilder는 RBAC 마커 주석으로 컨트롤러에 필요한 권한을 코드 옆에 선언하고, 이를 controller-gen이 실제 RBAC 매니페스트로 자동 변환한다.

// +kubebuilder:rbac:groups=platform.example.com,resources=replicatedservices,verbs=get;list;watch;create;update;patch;delete
// +kubebuilder:rbac:groups=apps,resources=deployments,verbs=get;list;watch;create;update;patch;delete
// +kubebuilder:rbac:groups=core,resources=services,verbs=get;list;watch;create;update;patch;delete

func (r *ReplicatedServiceReconciler) Reconcile(ctx context.Context, req ctrl.Request) (ctrl.Result, error) {
	// 1. CR 인스턴스 조회
	var rs platformv1alpha1.ReplicatedService
	if err := r.Get(ctx, req.NamespacedName, &rs); err != nil {
		// CR이 없으면(삭제됨) 파이널라이저 로직으로
		return ctrl.Result{}, client.IgnoreNotFound(err)
	}

	// 2. 원하는 Deployment/Service가 존재하는지 확인, 없으면 생성 (메인 로직)
	// ...

	// 3. 다음 조정까지 재스케줄
	return ctrl.Result{RequeueAfter: 30 * time.Second}, nil
}

이 골격이 그림 21-2의 흐름을 그대로 코드로 옮긴 것이다 — 조회 실패는 삭제 경로로, 성공하면 메인 로직으로, 끝나면 재조정을 예약한다.

21.7오퍼레이터 라이프 사이클

오퍼레이터 개발은 결코 만만치 않다. 처음부터 모든 운영 문제를 오퍼레이터로 풀려 하지 말고, 가장 큰 걸림돌부터 해결하며 반복적으로 넓혀 간다.

21.7.1 버전 업그레이드

CRD도 애플리케이션처럼 버전이 진화한다 — v1alpha1로 시작해 안정화되면 v1beta1, v1로 올라간다. 여러 버전을 동시에 지원해야 할 때는 컨버전 웹훅 (Conversion Webhook)으로 버전 간 필드를 서로 변환한다.

2026-08 기준 확인CRD 자체의 API(apiextensions.k8s.io)는 v1만 유효하다 — 예전에 흔했던 v1beta1은 1.22에서 완전히 제거됐다. 이건 CRD "그릇"의 버전 얘기고, 본문에서 말하는 v1alpha1 같은 버전은 여러분이 만드는 커스텀 리소스 "내용물"의 버전이라 서로 다른 개념이다 — 혼동하지 않는다.

21.7.2 오퍼레이터 모범 사례

오퍼레이터는 헬름 차트, 쿠스토마이즈 리포지터리, 테라폼 모듈 같은 더 단순한 패러다임으로 대체 가능한지부터 따져야 한다. 판단 기준은 하나다 — 배포 이후에도 계속 판단하고 행동해야 하는가. 배포 시점에 값 한 번 채우고 끝이라면 헬름으로 충분하고, 환경별 정적인 차이뿐이라면 쿠스토마이즈·테라폼으로 충분하다. 백업·페일오버·리더 선출처럼 살아있는 동안 계속 돌봐야 할 일이 있는 워크로드(16장의 스테이트풀 시스템)만이 오퍼레이터를 정당화한다.
