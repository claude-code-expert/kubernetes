CHAPTER 11

클러스터 정책과 거버넌스

RBAC(4장)이 "누가 무엇을 할 수 있는가"였다면, 이 장은 "그 리소스의 내용이 우리 조직의 규칙에 맞는가"다. "프로덕션 네임스페이스엔 승인된 레지스트리 이미지만", "모든 파드는 리소스 리밋 필수" 같은 규칙을 사람이 리뷰로 거르지 않고 클러스터가 스스로 강제하게 만드는 것 — 그 표준 도구였던 게이트키퍼를 중심으로, 2026년 현재 이 자리를 두고 벌어지는 3파전까지 다룬다.

2026-08 기준 변경 사항 주석 포함 · 정책 엔진 생태계 갱신 포함

핵심 3줄

1. 게이트키퍼는 정책 로직(ConstraintTemplate, Rego로 작성)과 적용 범위·파라미터(Constraint)를 분리한다 — 하나의 템플릿을 여러 팀이 값만 바꿔 재사용한다.

2. 새 정책은 절대 deny로 시작하지 않는다 — dryrun(기록만) → warn(경고만) → deny(차단) 순으로 검증하며 올린다.

3. 2026년 현재 선택지는 셋이다 — 단순 검증은 내장 ValidatingAdmissionPolicy(CEL), 그 외 대부분은 Kyverno(YAML, 채택률 1위), 기존 Rego 자산이 있다면 Gatekeeper.

11.1정책과 거버넌스의 중요성

의료·금융처럼 규제가 엄격한 산업은 물론, 그렇지 않은 조직도 클러스터가 커질수록 같은 문제를 만난다 — 사람이 PR 리뷰로 "이 이미지 출처가 맞나요?", "리소스 리밋 넣으셨나요?"를 매번 확인하는 방식은 규모가 커지면 반드시 무너진다. 거버넌스 (Governance)를 코드로, 즉 클러스터가 스스로 강제하는 규칙으로 바꾸는 것이 이 장의 목표다.

11.2정책의 변별성

정책 (Policy)은 사실 쿠버네티스 곳곳에 이미 있다. 4장의 리소스쿼터·RBAC, 9장의 네트워크 정책, 10장의 파드 시큐리티 어드미션 — 전부 "무엇을 허용·불허할지"를 선언한 정책이다. 이 장이 다루는 것은 그중에서도 범용 정책 엔진이다 — 특정 기능 하나가 아니라, 조직이 원하는 임의의 규칙을 표현할 수 있는 일반화된 도구.

11.3클라우드 네이티브 정책 엔진

OPA (Open Policy Agent)는 클러스터 리소스의 컴플라이언스 여부를 유연하게 판단하기 위한 범용 정책 엔진이다. 쿠버네티스 전용이 아니라 API·CI/CD·Terraform 등 어디에나 같은 정책 언어(Rego)로 붙일 수 있다는 것이 핵심 설계 철학이다.

2026-08 기준 갱신 주석 — 정책 엔진 지형 변화 원서 집필 시점엔 "쿠버네티스 정책 엔진 = OPA/게이트키퍼"가 사실상 유일한 답이었다. 지금은 세 갈래로 나뉜다. ① Kyverno — Rego 없이 정책 자체를 쿠버네티스 매니페스트처럼 YAML로 쓴다. 2024년 CNCF Graduated(쿠버네티스·프로메테우스와 같은 최고 성숙도 등급)에 올랐고, 2026년 여러 설문에서 채택률이 게이트키퍼를 앞질렀다. 검증뿐 아니라 변형·리소스 생성까지 기본 지원한다. ② ValidatingAdmissionPolicy (VAP) — 쿠버네티스 1.30 전후로 안정화된 내장 기능이다. CEL (Common Expression Language)로 규칙을 표현식 하나에 적으며, 별도 컴포넌트 설치도 웹훅 왕복 지연도 없다. 다만 외부 호출이나 리소스 간 상태 비교(11.4.5의 데이터 복제 같은 것)는 못 한다 — 순수 검증에 적합. 최근에는 변형까지 하는 MutatingAdmissionPolicy도 추가됐다. ③ 게이트키퍼는 여전히 유효한 선택이다 — 특히 Rego 정책을 쿠버네티스 밖(API, Terraform 등)에서도 재사용하고 싶다면. 출처: kubernetes.io/docs/reference/access-authn-authz/validating-admission-policy(VAP 공식 문서) · CNCF 프로젝트 성숙도 카탈로그(Kyverno Graduated 2024) · 업계 비교 자료 다수(2026) 교차 확인

11.4게이트키퍼 개요

게이트키퍼 (Gatekeeper)는 OPA를 쿠버네티스 어드미션 웹훅 (Admission Webhook)으로 감싼 오픈소스 프로젝트다. 여전히 CNCF Graduated 등급이고, 위 세 갈래 중 하나로 유효하다.

11.4.1 정책 예제

구체적인 구성에 들어가기 전에 강조할 것 하나 — 처음부터 정책 라이브러리 전체를 욕심내지 말고, 자신의 조직이 실제로 겪는 문제에만 집중한다. 남의 정책을 그대로 복사해 오면 우리 클러스터엔 맞지 않는 규칙이 섞여 예상 못 한 곳에서 파드 생성이 막힌다.

11.4.2 게이트키퍼 용어

세 용어만 알면 된다.

  • 제약조건 (Constraint) — "정책"을 조금 길게 부르는 말. 무언가를 불허하겠다는 선언이며, 명시적으로 막지 않은 것은 암묵적으로 허용된다(쿠버네티스 리소스 스펙 자체가 계속 바뀌는 특성을 고려한 설계).
  • Rego — OPA의 네이티브 쿼리 언어. 저장된 데이터에 대한 단언(assertion)을 표현한다.
  • 제약조건 템플릿 (ConstraintTemplate) — 이식·재사용 가능한 정책 템플릿. 파라미터화된 Rego + 타입이 지정된 파라미터 스키마로 구성된다.

11.4.3 제약조건 템플릿 정의

"승인된 레지스트리 이미지만 허용"하는 템플릿의 뼈대다.

apiVersion: templates.gatekeeper.sh/v1
kind: ConstraintTemplate
metadata:
  name: k8sallowedrepos
  annotations:
    metadata.gatekeeper.sh/title: "Allowed Repositories"
    metadata.gatekeeper.sh/version: 1.0.0
spec:
  crd:
    spec:
      names:
        kind: K8sAllowedRepos
  targets:
  - target: admission.k8s.gatekeeper.sh
    rego: |
      package k8sallowedrepos
      violation[{"msg": msg}] {
        image := input.review.object.spec.containers[_].image
        not startswith_any(image, input.parameters.repos)
        msg := sprintf("container image %v is not from an allowed repository", [image])
      }

이 템플릿을 적용하면 K8sAllowedRepos라는 새 커스텀 리소스 타입(CRD)이 클러스터에 생긴다 — 이제 이 타입으로 실제 정책 인스턴스를 만들 수 있다.

11.4.4 제약조건 정의

템플릿에 실제 값을 채워 넣는 것이 Constraint다.

apiVersion: constraints.gatekeeper.sh/v1beta1
kind: K8sAllowedRepos
metadata:
  name: prod-repo-is-openpolicyagent
spec:
  enforcementAction: deny
  match:
    kinds:
    - apiGroups: [""]
      kinds: ["Pod"]
    namespaces:
    - "production"
  parameters:
    repos:
    - "openpolicyagent/"

구조는 둘로 나뉜다 — match가 "어디에 적용할지"(여기선 production 네임스페이스의 Pod만), parameters가 "정책의 실제 내용"(openpolicyagent/로 시작하는 이미지만 허용)이다. 같은 필드를 검사하는 제약조건이 여럿이면 논리 AND로 동작한다 — 하나라도 위반하면 요청 전체가 거부된다.

11.4.5 데이터 복제

"인그레스 호스트네임이 중복되면 안 된다"처럼 지금 만들려는 리소스를 클러스터의 다른 리소스와 비교해야 하는 정책도 있다. 이런 평가를 하려면 OPA가 클러스터의 관련 리소스 전체를 캐시로 갖고 있어야 한다 — 게이트키퍼는 Config 리소스로 어떤 리소스를 이 캐시에 복제해 둘지 지정한다. VAP가 못 하는 것이 바로 이 부분이다(11.3절 갱신 주석).

11.4.6 UX

게이트키퍼는 정책을 위반하면 kubectl apply 응답에 즉시 피드백을 준다 — 왜 거부됐는지 메시지로 바로 알 수 있어, "왜 안 되는지 모르겠다"는 사용자 불만을 최소화한다.

11.5집행 액션과 감사 적용

11.5.1 변형

게이트키퍼는 검사뿐 아니라 변형 정책 (Mutation Policy) — 어드미션 시점에 리소스 내용을 자동으로 바꾸는 것 — 도 지원한다. 저자의 입장은 분명하다: 대체로 삼가는 것이 좋다. 어드미션 시점에 사용자 모르게 리소스가 바뀌는 것은 클라우드 네이티브 안티패턴이자, 쿠버네티스의 선언형 철학(1.2절)과도 어긋난다. 정말 대안이 없을 때만 최후 수단으로 쓴다.

11.5.2 정책 테스팅

깃옵스가 표준이 된 지금, 정책도 CI/CD 파이프라인에서 검증하는 것이 필수다. 게이트키퍼는 gator라는 CLI를 제공한다 — 제약조건 템플릿과 제약조건을 로컬에서 평가해, 프로덕션에 올리기 전에 샘플 리소스로 미리 테스트할 수 있다(5장의 CI 파이프라인에 이 단계를 끼워 넣는 것이 정석이다).

11.5.3 게이트키퍼 연습하기

게이트키퍼 공식 리포지터리에는 은행 컴플라이언스 요건을 처음부터 끝까지 구현해 보는 상세 예제가 있다. 직접 손으로 따라 해 보는 것이 개념을 익히는 가장 빠른 길이다. 정책 라이브러리는 아티팩트허브(ArtifactHub)에서도 검색할 수 있다.

# Kyverno로 같은 정책(승인된 레지스트리만 허용)을 짠다면 — Rego 없이 YAML만
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: allowed-repos
spec:
  validationFailureAction: Enforce
  rules:
  - name: check-registry
    match:
      resources:
        kinds: ["Pod"]
        namespaces: ["production"]
    validate:
      message: "이미지는 openpolicyagent/ 에서만 가져올 수 있습니다"
      pattern:
        spec:
          containers:
          - image: "openpolicyagent/*"

11.4.3~11.4.4의 게이트키퍼 예제와 같은 정책이지만, ConstraintTemplate·Constraint 두 리소스와 Rego 문법 대신 ClusterPolicy 하나와 익숙한 YAML 패턴 매칭으로 끝난다 — Kyverno가 "쿠버네티스 네이티브"를 내세우는 이유가 이것이다.
