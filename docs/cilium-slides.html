큰 그림: Istio는 통신 문제를 프록시(Envoy)로, Cilium은 네트워크 자체를 eBPF 데이터 플레인으로 해결한다.

Cilium 공부 = 새 서비스 메시 하나가 아니라, K8s 네트워크 동작 방식 전체를 공부하는 것.

WHY ISTIO

  • Deployment 배포

⚠️ 앱이 떠안던 것

  • 재시도 · 타임아웃 · 서킷브레이커
  • 카나리 · A/B 트래픽 분배

서비스마다 이 기능을 언어·프레임워크별로 제각각 반복 구현 → 정책 일관성 붕괴. 이걸 앱 밖으로 빼자는 게 서비스 메시.
SIDECAR

해법 — 공통 기능을 Envoy로

애플리케이션 트래픽이 반드시 Envoy를 통과하므로, 통신 안정성·보안·관측을 인프라 계층에서 일괄 처리.
COST

Sidecar 방식의 문제점

📦

Pod마다 Envoy

App 1,000개 → Envoy ~1,000개. CPU·메모리·시작지연↑, 노드당 Pod수↓. mTLS만 필요해도 범용 L7 프록시 = 과잉.

🔗

생명주기 결합

프록시 업그레이드·설정·인증서 문제가 앱 Pod 재시작을 유발. 앱 코드는 그대로인데도.

🕵️

장애 경로 증가

App→Envoy→iptables→net→Envoy→App. 문제 위치를 앱/Envoy/Istiod/인증서/정책 중에서 골라야.

해결한 문제는 분명하지만, 모든 Pod에 범용 L7 프록시를 두는 구조가 새 비용을 만들었다 → Ambient의 동기.
RESOURCE · 공식

Envoy 사이드카가 요구하는 자원

항목값 (Istio 공식)
처리량당 (1.8.3)0.35 vCPU + 40 MB / 1,000 rps
처리량당 (1.24)~0.20 vCPU + 60 MB / 1,000 rps
기본 requestsCPU 100m · Mem 128Mi
기본 limitsCPU 2000m · Mem 1024Mi
  • 메모리는 config state(listener·cluster·route·endpoint)에 비례 → Sidecar로 스코프 축소.
  • CPU limit 과소 → 스파이크 때 스로틀링 = 앱 지연. limit은 높게/unset 권장.
  • 오버라이드: global.proxy.resources 또는 sidecar.istio.io/proxyCPU 등 애노테이션.
규모 감각: Pod 1,000개 = 사이드카 requests만 100 vCPU + ~125 GiB(1000×128Mi), limits로는 ~2,000 vCPU + ~1 TiB. 앱이 아니라 프록시 계층에만 드는 비용 — Ambient·eBPF가 이 곱셈을 없애려는 이유.

출처: Istio Performance and Scalability · 기본값 = 차트 values.global.proxy.resources

AMBIENT

Istio Ambient — L4/L7 계층화

  • ztunnel (DaemonSet·노드당 1개): L4 mTLS·신원·정책. HTTP 미파싱.
  • Waypoint (Deployment·네임스페이스/SA 단위, DaemonSet 아님): L7 필요 시만. istioctl waypoint apply로 생성, 앱과 독립 스케일.
기본 보안은 공유 L4, 필요할 때만 L7. 다만 여전히 K8s 네트워크 위에 얹는 메시.
02
Envoy는 어떻게 뜨고
어떻게 프록시하나
주입 → 가로채기 → 프록시 → 설정 배포
먼저 · 용어

그런데 Envoy가 뭔가

Envoy = Istio가 데이터 플레인으로 쓰는 고성능 L4/L7 프록시(CNCF 졸업 프로젝트·C++·원래 Lyft 제작). 앱 대신 연결을 받고/보내며 그 사이에서 정책을 적용하는 중개자.

🔀

L4/L7 처리

TCP뿐 아니라 HTTP/2·gRPC를 이해 → 경로·헤더 라우팅, 재시도·타임아웃·서킷브레이커, TLS(mTLS).

⚙️

동적 설정 (xDS)

재시작 없이 API로 설정을 받아 실시간 반영 → istiod가 수천 Envoy를 중앙 조종. 메시의 핵심.

🔭

관측 내장

상세 통계·분산 트레이싱·액세스 로그 기본 제공.

Listener  # 수신 지점 15006/15001
  └ Filter Chain # TLS·HTTP
      └ Route     # host/path → Cluster
          └ Cluster   # upstream 서비스
              └ Endpoint # 실제 Pod IP
각 계층이 xDS(LDS/RDS/CDS/EDS)에 대응. Sidecar·Waypoint·Cilium의 L7 — "L7 프록시"라 하면 대부분 이 Envoy다.
① 주입

사이드카 주입 — Mutating Webhook

  • Pod 생성 요청을 MutatingAdmissionWebhook(istio-sidecar-injector)이 가로채 스펙을 수정.
  • 대상: 네임스페이스 istio-injection=enabled 또는 Pod sidecar.istio.io/inject.
  • 주입되는 것: istio-init(initContainer) + istio-proxy(사이드카).
# 주입 후 Pod
spec:
  initContainers:
  - name: istio-init        # ① iptables 세팅 후 종료
    args: [istio-iptables,
      -p,"15001", -z,"15006",
      -u,"1337", -m,REDIRECT]
  containers:
  - name: my-app            # 원래 앱
  - name: istio-proxy       # ② pilot-agent + Envoy

istio-init은 앱보다 먼저 실행돼 netns에 iptables를 심고 종료 · istio-proxy 안 pilot-agent가 Envoy를 부트스트랩.

② 가로채기

iptables로 투명하게 가로채기

[Inbound] PREROUTING
  ISTIO_INBOUND      # 들어오는 TCP
   └ (15090/15021/15020 제외)
  ISTIO_IN_REDIRECT
   └ REDIRECT → 15006

[Outbound] OUTPUT
  ISTIO_OUTPUT       # 나가는 TCP
   ├ UID/GID 1337 발 → RETURN (루프X)
   ├ dst 127.0.0.1   → RETURN
   └ ISTIO_REDIRECT
      └ REDIRECT → 15001
인자의미
-p 15001outbound → Envoy 15001
-z 15006inbound → Envoy 15006
-u 1337Envoy UID (루프 방지 키)
-m REDIRECT캡처 모드 (또는 TPROXY)
UID 1337이 핵심: Envoy가 내보내는 패킷도 OUTPUT을 지나므로, 소유자 UID가 1337이면 RETURN해서 무한 루프를 막는다.
③ 프록시 · 포트

Envoy 포트 구성

포트역할
15001Envoy outbound listener — 앱이 밖으로 보내는 트래픽이 iptables로 도착
15006Envoy inbound listener — 밖에서 이 Pod로 오는 트래픽이 iptables로 도착
15000Envoy admin API (config_dump·통계, 디버깅)
15020istio-agent 병합 텔레메트리 + health check 집계
15021health check (/healthz/ready, kubelet readiness probe)
15090Envoy Prometheus 메트릭 (pilot-agent가 scrape)
15090·15021·15020은 iptables 캡처에서 제외 — health check·metrics·admin이 Envoy로 되돌려지면 안 되므로.
INBOUND

트래픽이 들어오는 흐름

앱은 항상 localhost로 들어온 요청만 본다. mTLS 검증·L7 인가·관측은 앱이 받기 전에 Envoy가 끝낸다.
OUTBOUND

트래픽이 나가는 흐름

앱은 그냥 payment ClusterIP로 connect했을 뿐 — iptables가 소켓을 15001로 돌리고 Envoy가 엔드포인트 선택·mTLS·정책을 대신 수행.
④ 설정 배포

제어 플레인 — istiod ↔ Envoy (xDS)

xDS = istiod가 Envoy에 설정을 내려주는 API 묶음(x = L/R/C/E/S, DS = Discovery Service). Envoy는 스스로 라우팅을 모르고, istiod가 K8s API를 watch해 gRPC 스트림으로 실시간 push한다.

종류무엇을쉽게 말하면
LDS
Listener		어떤 포트에서 받을지"15001(out)·15006(in)에서 받아라"
RDS
Route		HTTP를 어디로 보낼지host/path 보고 어느 서비스로 (VirtualService)
CDS
Cluster		upstream 서비스 묶음보낼 수 있는 백엔드 그룹 + LB/TLS (DestinationRule)
EDS
Endpoint		실제 Pod IP 목록그 서비스의 진짜 Pod IP들 (죽/뜨면 갱신)
SDS
Secret		인증서·키·CAmTLS용 인증서, istio-agent가 발급·회전
4단계 요약: 주입(webhook) → 가로채기(iptables 15006/15001) → 프록시(Envoy) → 설정 배포(istiod xDS/SDS).

K8s 기본 네트워크
CNI · CoreDNS · kube-proxy
Pod가 IP를 얻는 법(CNI)부터, DNS 질의가 흐르는 법까지
CNI · 기초

Pod는 어떻게 IP를 얻나 — CNI

CNI(Container Network Interface) = 컨테이너에 네트워크를 붙이는 방법을 규정한 CNCF 표준 + 그 구현 플러그인(Cilium·Calico·Flannel·AWS VPC CNI…). CNI 자체는 네트워킹을 "제공"하지 않는다 — 런타임이 플러그인을 어떻게 호출할지만 정의.

🔢

IPAM

Pod에 클러스터에서 겹치지 않는 IP 할당.

🔌

인터페이스

veth pair 생성 — Pod의 eth0 ↔ 호스트 namespace.

🧭

라우팅

같은/다른 노드 Pod·외부와 통신하도록 경로 세팅.

K8s 네트워크 모델: ① 모든 Pod는 고유 IP ② Pod↔Pod는 NAT 없이(노드 넘어서도) ③ 노드 에이전트는 그 노드 Pod와 통신. Service LB(kube-proxy)·DNS는 CNI의 일이 아니다 — CNI는 IP·L3 연결까지.
CNI · 흐름

Pod가 뜰 때 CNI 호출 흐름

# kubelet → 런타임 → CNI
kubelet → CRI: sandbox(pause) 생성
런타임: Pod netns 생성
런타임 → CNI 플러그인 (CNI_COMMAND=ADD)
   # conf: /etc/cni/net.d
   # bin:  /opt/cni/bin
플러그인: IP 할당 → veth 생성 → 라우팅
→ Pod가 IP 획득, 앱 컨테이너 시작
   # 삭제 시 CNI_COMMAND=DEL

플러그인 명령: ADD / DEL / CHECK

노드 넘는 Pod 통신 = 두 datapath:

오버레이

VXLAN/Geneve로 캡슐화. 이식성↑·오버헤드有. (Flannel, Cilium VXLAN)

네이티브 라우팅

BGP·클라우드 라우트로 직접 광고. 성능↑·하부 지원 필요. (Calico BGP, Cilium native)

Cilium은 CNI이면서 veth·iptables 대신 eBPF(tc/XDP)로 datapath 처리 → IP 할당(CNI)과 Service LB·정책·관측을 한 데이터 플레인에서.
배포 형태

무엇이 DaemonSet인가

컴포넌트배포 형태노드 분포역할
kube-proxyDaemonSet노드마다 1개Service→Pod LB 규칙(iptables/IPVS)을 각 노드 커널에
CoreDNSDeployment (기본)노드별 아님 (기본 2 replica)클러스터 DNS 서버 · kube-dns Service로 프론트
NodeLocal DNSCacheDaemonSet노드마다 1개노드 로컬 DNS 캐시 · 선택 애드온
CoreDNS는 기본이 DaemonSet이 아니라 Deployment다. 노드별로 확실히 하나씩 도는 것은 kube-proxy. 이어서 DNS 질의가 어떻게 CoreDNS Pod까지 도달하는지 따라가 본다.
kube-proxy

kube-proxy는 프록시가 아니다

# iptables nat 테이블
KUBE-SERVICES        # dst=ClusterIP:port
  └ KUBE-SVC-XXXX    # 가상 LB (random)
      ├ KUBE-SEP-A 33% → DNAT PodA:port
      ├ KUBE-SEP-B 33% → DNAT PodB:port
      └ KUBE-SEP-C 34% → DNAT PodC:port
  • API를 watch → Service/EndpointSlice 변경 시 커널 규칙만 갱신(규칙 프로그래머).
  • ClusterIP는 가상 IP — 커널이 DNAT로 실제 Pod IP로 바꿀 뿐.
  • 규칙은 모든 노드에 동일(그래서 DaemonSet).
  • DNAT 후 노드 간 라우팅은 CNI가 담당.

실제 패킷 변환(DNAT)은 커널이 한다. kube-proxy는 트래픽을 직접 나르지 않는다.

DNS 경로

Pod의 DNS 조회 end-to-end

resolv.conf: nameserver 10.96.0.10 · ndots:5 (점 5개 미만이면 search 도메인부터 순차 시도 → 외부 도메인은 불필요 질의 다수, 튜닝 포인트)

둘은 직접 통신하지 않는다. CoreDNS는 kube-dns Service 뒤의 평범한 Pod이고, kube-proxy가 심은 Service DNAT 덕에 질의가 CoreDNS로 로드밸런싱돼 도달할 뿐.

Ingress & Egress
외부 ↔ 클러스터, North-South 트래픽 관리
INGRESS

Ingress — 외부를 안으로

Ingress + Controller

host/path→Service 규칙을 nginx/Envoy 컨트롤러가 L7로 구현.

Gateway API

후속 표준. GatewayClass/Gateway/HTTPRoute로 역할 분리, 멀티테넌시.

Istio

istio-ingressgateway(Envoy)가 입구에서 Gateway+VirtualService로 메시 전달.

EGRESS

Egress — 밖으로 나가는 통제

기본은 모든 egress 허용. 통제하려면:

NetworkPolicy (egress)

L3/L4로 "이 CIDR/포트로만". 단 IP/포트 기반이라 도메인 통제는 어려움(외부 IP가 자주 바뀜).

DNS/FQDN 기반

도메인 단위 통제. 표준으론 불가 → Cilium toFQDNs 같은 확장 필요.

Egress Gateway

특정 Pod 트래픽을 게이트웨이 노드로 몰아 고정 IP로 SNAT. 외부 방화벽 allowlist·레거시 연동.

Istio Egress

ServiceEntry로 외부 등록, 선택적 istio-egressgateway로 한 지점에서 정책·mTLS.

PHILOSOPHY

커널에서 eBPF로, 필요할 때만 Envoy

Cilium은 서비스 메시가 아닌 CNI에서 출발. CNI + Service LB + kube-proxy 대체 + NetworkPolicy + Hubble + Ingress/Gateway + 일부 메시를 하나의 데이터 플레인으로.
kube-proxy 대체

소켓 레벨 로드밸런싱

iptables 모드

connect
 → KUBE-SERVICES 선형 매칭
 → DNAT → conntrack
 → 전송

규칙이 서비스 수만큼 선형 증가 → 대규모에서 지연↑.

Cilium socket LB

connect()
 → cgroup eBPF (connect/sendmsg)
   가 즉시 백엔드IP로 치환
 → 바로 전송 (스택 우회)

eBPF 해시맵 O(1) 조회 · per-packet DNAT·conntrack 없음.

kubeProxyReplacement 활성화 시 kube-proxy DaemonSet과 iptables Service 규칙이 사라진다. DNS 질의도 이 경로로 CoreDNS에 도달 → DNS 경로에서 iptables 제거.
DNS · FQDN

DNS Proxy로 도메인 egress 통제

표준 NetworkPolicy로 불가능한 도메인 단위 egress를 해결: toFQDNs: api.github.com → 응답 IP만 TTL 동안 허용. 이후 그 IP로의 L3 연결만 통과.
Ingress · Egress

Cilium의 Ingress & Egress Gateway

⬇️

Ingress / Gateway API

  • 네이티브 지원 — 별도 Controller Deployment 불필요.
  • L7 라우팅은 Cilium이 관리하는 노드 단위 Envoy로 위임.
  • L3/L4는 eBPF, L7 HTTP만 Envoy — 같은 철학.
⬆️

Egress Gateway

  • 특정 Pod(라벨)→특정 외부 CIDR를 게이트웨이 노드로.
  • 그 노드의 고정 IP로 SNAT — 방화벽 allowlist·레거시.
  • 전제: BPF masquerade + kube-proxy 대체 활성화.

Envoy는 Cilium에서 L7일 때만 등장 — 그리고 그 L7 심층 사용 자체가 실무에선 드물다. L3/L4·Service LB·NetworkPolicy·마스커레이드는 전부 eBPF(커널).

완전한 대체재가 아니다. Cilium은 CNI·kube-proxy 대체·FQDN·flow 가시성에 강하고, Ambient는 성숙한 mTLS·Zero Trust·정교한 L7에 앞선다. Cilium을 CNI로 깔고 그 위에 Ambient 조합도 쓰인다.
실무 관점

왜 Cilium을 먼저 고려하는가

현실에서 깊은 L7 트래픽 관리(정교한 라우팅·fault injection·복잡한 L7 authz)를 쓰는 경우는 많지 않다. 대다수 워크로드는 L4·mTLS·기본 정책·관측 수준이면 충분 — 이때 Cilium의 이점이 커진다.

🧩

Mesh + CNI 단일 관리

별도 CNI + 별도 메시(각자 제어 플레인·업그레이드) 대신 하나의 eBPF 데이터 플레인으로 통합 → 운영 표면 축소.

🔭

Hubble 옵저버빌리티

커널 데이터 플레인이라 allow/drop·identity·DNS·flow를 사이드카 없이 관찰 → "어느 계층에서 끊겼나" 즉시 추적.

📉

L7 의존 낮음

깊은 L7을 안 쓰면 Ambient가 앞서는 성숙한 L7 메시의 이점이 상대적으로 작아진다.

판단: L7을 깊게 다루지 않는 대다수 환경이라면 Cilium을 Istio Ambient보다 먼저 도입하는 편이 낫다. 단 mTLS·Zero Trust·정교한 L7이 핵심이면 Ambient(또는 Cilium 위 Ambient 병용) 검토.
장단점

Cilium 장단점 한눈에

✅ 장점

  • Mesh + CNI 단일 관리 — 하나의 eBPF 데이터 플레인.
  • kube-proxy 대체(socket LB, O(1)) — iptables 제거.
  • Hubble 관측 — 사이드카 없이 flow 가시성.
  • FQDN egress·Egress Gateway 등 정책 강력.
  • 사이드카 없음 → 리소스·지연 절감.

⚠️ 단점 · 주의

  • mTLS·Zero Trust 성숙도는 Istio에 못 미침(버전 확인).
  • 정교한 L7 트래픽 관리(fault injection 등)는 Istio가 앞섬.
  • eBPF·커널 버전 의존, 러닝커브.
  • 깊은 서비스 메시 기능은 여전히 Istio 생태계가 풍부.
L7을 깊게 안 쓰는 대다수 환경 → Cilium 우선. mTLS·정교한 L7이 핵심 → Ambient(또는 Cilium+Ambient 병용).

WHY STUDY

Cilium을 공부해야 하는 이유

① 가장 아래 계층까지

Pod 패킷이 노드를 어떻게 나가고, Service IP가 어떻게 Endpoint로, kube-proxy/iptables가 무엇을, eBPF가 어느 훅에서 — 데이터 플레인 전체를 배운다.

② 통합의 방향

CNI·kube-proxy·정책·관측·Ingress·메시로 흩어진 역할이 왜 하나의 eBPF 데이터패스로 수렴하는지 보인다.

③ 흐름 기준 장애 분석

DNS 실패? Endpoint 선택? NetworkPolicy drop? L7 거절? — Hubble로 allow/drop·identity·flow를 관찰.

④ Ambient도 정확히

ztunnel이 왜 노드 단위 공유 프록시인지, 사이드카를 왜 없앴는지 — netns·리다이렉션·identity를 알아야 보인다.

Istio = 프록시로 추상화
Cilium = 네트워크 자체를 재설계
사이드카가 어떻게 뜨는지(webhook·iptables·Envoy·xDS), Service·DNS가 어떻게 도는지(kube-proxy DNAT·kube-dns), Ingress·Egress가 어떻게 통제되는지를 알고 나면 —
Cilium은 그 조각들을 커널로 끌어내려 하나로 합친 결과임이 보인다.
Cilium 공부 = Kubernetes 네트워킹의 다음 단계를 공부하는 것
