CHAPTER 04

구성, 시크릿, RBAC

1장에서 스쳐 지나간 세 리소스를 운영 수준으로 파고드는 장. 질문은 세 개다 — 구성을 고치면 언제 반영되는가(ConfigMap), 비밀은 어디까지 지켜지는가(Secret), 누가 무엇을 할 수 있는가(RBAC). 세 답이 곧 클러스터 사고의 예방 목록이 된다.

2026-08 기준 변경 사항 주석 포함 · 실습 명령은 0장 kind 클러스터 기준

핵심 3줄

1. 구성 주입 경로가 갱신 반영을 결정한다 — 환경 변수는 재시작 전엔 안 바뀌고, 볼륨은 지연 후 갱신되며, subPath는 영영 안 바뀐다.

2. 시크릿 보안은 층으로 쌓는다 — 원본은 외부 매니저, 저장은 암호화(KMS v2), 접근은 RBAC 최소화, 소비는 메모리(tmpfs), Git에는 평문 금지.

3. RBAC의 문장 구조는 하나다 — "주체가 RoleBinding을 통해 롤의 권한을 갖는다." 실무 정석은 내장 ClusterRole(view·edit)을 네임스페이스 범위로 빌려 쓰는 것.

4.1컨피그맵과 시크릿을 통한 구성

둘은 쓰는 법이 거의 같고, 다른 것은 담기는 데이터의 민감성과 그에 따른 취급이다. 컨피그맵은 공개해도 되는 설정, 시크릿은 유출되면 사고가 되는 값 — 이 구분이 이 장 전체를 관통한다.

4.1.1 컨피그맵

만드는 방법은 세 가지, 파드에 넣는 경로는 두 가지다.

# 생성 ① 리터럴       ② 파일       ③ 매니페스트(권장 — Git 관리 가능)
kubectl create configmap app-config --from-literal=journalEntries=10
kubectl create configmap app-config2 --from-file=./config.properties
kubectl apply -f app-config.yaml
# 두 경로를 모두 쓴 파드 예시
apiVersion: v1
kind: Pod
metadata:
  name: config-demo
spec:
  containers:
  - name: app
    image: nginx:1.27
    env:
    - name: JOURNAL_ENTRIES            # 경로 ① 키 하나를 환경 변수로
      valueFrom:
        configMapKeyRef:
          name: app-config
          key: journalEntries
    envFrom:                            # 경로 ① 전체 키를 한꺼번에
    - configMapRef:
        name: app-config
    volumeMounts:
    - name: config-vol                  # 경로 ② 파일로 마운트
      mountPath: /etc/config
      readOnly: true
  volumes:
  - name: config-vol
    configMap:
      name: app-config

경로별 성격을 기억하자. 환경 변수(①)는 시작할 때 한 번 찍히는 스냅숏이라 컨피그맵을 고쳐도 재시작 전엔 반영되지 않는다. 볼륨 마운트(②)는 kubelet이 주기적으로 갱신해 지연 후 자동 반영된다 — 단, subPath(볼륨 전체가 아니라 그 안의 특정 파일 하나만 골라 마운트하는 옵션)로 마운트한 파일은 갱신이 전파되지 않는다. envFrom은 편하지만 키 전부가 환경에 쏟아지므로, 키 이름 충돌과 "무엇이 주입되는지 모르는" 문제를 낳기 쉽다.

4.1.2 시크릿

사용법은 컨피그맵과 같지만 세 가지가 다르다. 첫째, 타입이 있다 — 범용 Opaque 외에 TLS 인증서용 kubernetes.io/tls, 프라이빗 레지스트리 인증용 kubernetes.io/dockerconfigjson 등 용도별 형식이 정의되어 있다. 둘째, 값이 base64로 저장된다 — 다시 강조하지만 이는 인코딩이지 암호화가 아니다. base64 -d 한 줄이면 풀린다. 셋째, 볼륨으로 마운트하면 노드 디스크가 아니라 tmpfs(메모리 파일시스템)에 올라가므로, 파드가 사라지면 흔적도 사라진다 — 시크릿은 환경 변수보다 볼륨 마운트가 권장되는 이유가 하나 더 있는 셈이다(환경 변수는 프로세스 덤프·자식 프로세스로 새기 쉽다).

# 생성 예시
kubectl create secret generic redis-passwd --from-literal=passwd='s3cr3t!'
kubectl create secret tls journal-tls --cert=tls.crt --key=tls.key

# 내용 확인이 이렇게 쉽다 — "base64는 보호가 아니다"의 증명
kubectl get secret redis-passwd -o jsonpath='{.data.passwd}' | base64 -d

4.2컨피그맵, 시크릿 API 모범 사례

이 API에서 생기는 사고의 대부분은 "고쳤을 때 무슨 일이 일어나는지"를 모르는 데서 온다. 그래서 모범 사례의 방향은 하나로 수렴한다 — 갱신을 예측 가능하게 만들어라.

  • 구성 오브젝트를 제자리에서 고치지 말고, 새 이름으로 만들어 교체하라. app-config-v2처럼 버전을 이름에 붙여 만들고 디플로이먼트의 참조를 바꾸면, 그 변경 자체가 롤아웃을 일으켜 모든 파드가 같은 시점에 새 구성으로 넘어간다. 반영 시점이 명확하고, 문제가 생기면 참조만 되돌리면 롤백이다.
  • 애플리케이션이 구성 재로딩을 지원하지 않는다면 볼륨 갱신 전파에 기대지 말고 위 교체 방식이나 kubectl rollout restart로 재시작을 명시하라. "일부 파드만 새 설정"인 상태가 가장 위험하다.
  • envFrom보다 필요한 키만 골라 주입하라. 어떤 값이 들어가는지 매니페스트에 드러나는 것이 곧 문서다.
  • 작게 유지하라. 컨피그맵은 1MiB 제한이 있고, 큰 데이터는 애초에 구성이 아니라 볼륨(16장)의 일이다.
2026-08 기준 갱신 주석 위의 "새 이름으로 교체" 패턴과 짝을 이루는 공식 기능이 불변 오브젝트 (Immutable ConfigMap / Secret)다 — 매니페스트에 immutable: true 한 줄을 넣으면 이후 수정이 금지된다(고치려면 삭제 후 재생성). 실수로 제자리 수정하는 사고를 원천 차단할 뿐 아니라, kubelet이 변경 감시(watch)를 중단해도 되므로 대규모 클러스터에서 API 서버 부하를 크게 줄인다. 버전 이름 교체 패턴을 쓴다면 켜지 않을 이유가 없다. 
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config-v2
immutable: true
data:
  journalEntries: "20"
출처: kubernetes.io/docs/concepts/configuration/configmap · kubernetes.io/docs/concepts/configuration/secret (immutable 필드)

4.3시크릿 모범 사례

시크릿은 "쿠버네티스에 넣었다"로 끝나지 않는다. 보호는 겹겹의 층이다.

  • 저장 시 암호화를 켠다. 기본 상태의 etcd에는 base64 평문으로 남는다. EncryptionConfiguration으로 저장 시 암호화 (Encryption at Rest)를 켜거나, 키 관리를 클라우드에 맡기는 KMS (Key Management Service) 연동을 쓴다.
  • 접근을 RBAC으로 좁힌다. 시크릿에 대한 get은 물론, 목록을 쓸어 담을 수 있는 list·watch 권한을 특히 조심한다. "네임스페이스의 모든 시크릿 read"를 아무 워크로드에나 주지 않는다.
  • 쿠버네티스 API가 필요 없는 워크로드는 토큰 자동 마운트를 끈다. 모든 파드에는 기본으로 서비스어카운트 (ServiceAccount) — 사람이 아닌 워크로드의 클러스터 신원 — 토큰이 마운트되는데, API를 안 쓰는 앱에게 이 토큰은 순수한 공격 표면이다. automountServiceAccountToken: false로 끈다.
  • Git에는 어떤 형태로든 평문 시크릿을 두지 않는다. 매니페스트 리포지터리에 들어가야 한다면 암호화된 형태(Sealed Secrets, SOPS — 18장에서 실습)나 외부 매니저 참조만 둔다.
  • 로그와 셸 히스토리에 흘리지 않는다. --from-literal로 만든 값은 히스토리에 남는다 — 파일 입력 후 파일 삭제, 또는 외부 매니저 동기화가 낫다.
# API 불필요 워크로드의 토큰 자동 마운트 차단
apiVersion: v1
kind: ServiceAccount
metadata:
  name: frontend-sa
  namespace: default
automountServiceAccountToken: false
2026-08 기준 갱신 주석 현행 표준 두 가지. ① 저장 암호화의 KMS 연동은 KMS v2가 표준이다(v1 대비 성능·키 회전 개선). ② 시크릿의 원본을 클러스터 밖 전문 매니저에 두고 동기화하는 패턴이 사실상 기본값이 됐다 — 대표 도구인 External Secrets Operator (ESO)는 AWS Secrets Manager·Vault 등 외부 매니저의 값을 읽어 쿠버네티스 Secret으로 자동 생성·갱신하는 CNCF 프로젝트다(2025년 유지보수 인력 부족으로 릴리스가 잠시 멈췄다가 재개되어 현재 정기 릴리스 중 — 도입 시 프로젝트 상태를 한 번 확인할 것). 참고로 Vault는 라이선스가 BUSL로 바뀌어, 완전 오픈소스가 필요하면 호환 포크인 OpenBao가 대안이다. 출처: kubernetes.io/docs/tasks/administer-cluster/kms-provider (KMS v2) · external-secrets.io, cncf.io/projects/external-secrets (CNCF 등재·프로젝트 상태)

4.4RBAC

여기서부터는 "누가 무엇을 할 수 있는가"다. 먼저 용어 정리 — 인증 (Authentication)은 "너는 누구인가"(2장의 OIDC·인증서), 인가 (Authorization)는 "그래서 무엇을 해도 되는가"이며, RBAC은 쿠버네티스 인가의 표준 방식이다. 모든 API 요청은 인증 → 인가 순서로 심사받는다.

4.4.1 RBAC 기초

구성 요소는 셋이다. 주체(User·Group·ServiceAccount), 권한 규칙을 담은 롤(리소스 × 동사 — get, list, watch, create, update, patch, delete), 그리고 둘을 잇는 바인딩. 범위(스코프)에 따라 네 오브젝트로 조합된다.

네임스페이스 범위클러스터 범위
권한 정의RoleClusterRole
권한 부여RoleBindingClusterRoleBinding

조합의 핵심 한 가지: RoleBinding은 ClusterRole을 참조할 수 있다. 공용으로 정의해 두고 네임스페이스 범위로만 부여하는 것 — 내장 ClusterRole 네 가지(view 읽기 전용, edit 리소스 수정 가능, admin 네임스페이스 관리, cluster-admin 전권)를 이렇게 빌려 쓰는 것이 롤을 직접 짜는 것보다 먼저다. 직접 짤 때의 최소 예시:

# 읽기 전용 롤 정의 + 서비스어카운트에 부여
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
  namespace: default
rules:
- apiGroups: [""]
  resources: ["pods", "pods/log"]
  verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: frontend-pod-reader
  namespace: default
subjects:
- kind: ServiceAccount
  name: frontend-sa
  namespace: default
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
# 권한 확인 — 트러블슈팅의 시작점
kubectl auth can-i list pods -n default
kubectl auth can-i create deployments -n default --as=system:serviceaccount:default:frontend-sa
kubectl auth can-i --list -n default   # 내가 가진 권한 전체 나열
2026-08 기준 갱신 주석 구버전 자료와 다른 점 하나 — 서비스어카운트를 만들면 토큰 시크릿이 자동 생성되던 동작은 1.24부터 사라졌다. 현행 표준은 수명이 짧고 자동 회전되는 토큰을 그때그때 발급받는 방식이며, 수동 발급이 필요하면 kubectl create token frontend-sa를 쓴다. "서비스어카운트의 시크릿을 찾아 토큰을 꺼내라"는 옛 튜토리얼은 따라 해도 시크릿이 없다. 출처: kubernetes.io/docs/concepts/configuration/secret (kubectl create token 권장) · kubernetes.io/docs/reference/access-authn-authz (레거시 토큰 정리)

4.4.2 RBAC 모범 사례

원칙왜 / 확인 질문
최소 권한 원칙 (Principle of Least Privilege) — 필요한 리소스·동사만와일드카드(resources: ["*"], verbs: ["*"])가 롤에 있진 않은가?
cluster-admin은 사람 몇 명, 그리고 비상용으로만워크로드(서비스어카운트)에 cluster-admin이 바인딩된 곳은 없는가?
바인딩은 개인이 아니라 그룹에퇴사·이동 시 바인딩을 일일이 고치고 있진 않은가? (2장의 신원 시스템 그룹과 연결)
앱마다 전용 서비스어카운트default 서비스어카운트로 도는 워크로드가 있진 않은가?
내장 롤 우선, 커스텀 롤은 최후에view·edit로 충분한 곳에 커스텀 롤을 짜고 있진 않은가? (커스텀 롤도 잘게 만들어 조합)
정기 감사kubectl auth can-i --list와 바인딩 목록을 분기마다 훑는 절차가 있는가? (19장 보안 태세 도구와 연결)
